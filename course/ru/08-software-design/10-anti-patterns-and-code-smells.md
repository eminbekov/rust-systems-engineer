# Урок 08.10 — Антипаттерны и «запахи» кода

> **Этап 08 — Проектирование ПО: принципы, паттерны и соглашения** · Урок 10 из 17 · ⏱ около 2,5 часа (2 занятия)

## Что вы узнаете

- Что такое «запах» кода (code smell) и антипаттерн (anti-pattern) и почему «запах» — это вопрос, а не приговор.
- Самые частые «запахи» в любом языке: магические числа, строковая типизация, булевы параметры, длинные списки параметров, дублирование кода, «божественные» типы.
- Пять антипаттернов, характерных для Rust: лишний `clone`, `unwrap` для внешних данных, `Rc<RefCell<T>>` повсюду, «наследование» через `Deref` и `#![deny(warnings)]`.
- Как Clippy (линтер Rust) находит часть «запахов» за вас и как решить, нужно ли исправлять конкретный.

## Новые слова

| Слово | Значение |
|---|---|
| **«запах» кода** (code smell) | Внешний признак в коде, который *может* указывать на более глубокую проблему проектирования. Код работает, но что-то не так. |
| **антипаттерн** (anti-pattern) | Распространённое «решение», которое выглядит разумно, но обычно создаёт больше проблем, чем решает. |
| **магическое число** (magic number) | Голое число в коде, смысл которого не ясен из окружающего кода, например `86400` или `0.8`. |
| **строковая типизация** (stringly-typed) | Использование `String` или `&str` для данных с несколькими допустимыми значениями (статус, код страны) вместо `enum`. |
| **одержимость примитивами** (primitive obsession) | Использование простых `u32`, `bool` или `String` для всего вместо маленьких типов с именами и правилами. |
| **булева слепота** (boolean blindness) | Аргумент типа `bool`, смысл которого не виден в месте вызова: `render(true, false)`. |
| **«божественный» тип** (god type) | Структура, которая знает и делает слишком много: десятки полей и методов на несвязанные темы. |
| **линтер** (linter) | Инструмент, который читает ваш код, не запуская его, и предупреждает о подозрительном или неидиоматичном коде. Одно правило предупреждения — это **lint**. |
| **Clippy** | Официальный линтер Rust. Запускается командой `cargo clippy`. |

## 1. «Запахи» и антипаттерны

**«Запах» кода** — это подсказка. Длинная функция — «запах»: сегодня она ничего не ломает, но длинные функции
трудно читать и тестировать, и в них прячутся ошибки. Если пахнет дымом, вы проверяете, но не вызываете
пожарных сразу. **Антипаттерн** сильнее: это *рецепт*, который люди продолжают применять, потому что он
выглядит как решение, а на деле создаёт новые проблемы. «Проверка заимствований (borrow checker) ругается,
значит, добавлю `.clone()` везде» — как раз такой рецепт: он прячет настоящий вопрос (кто должен владеть этими данными?).

Три правила на весь урок:

1. «Запах» — это *вопрос*. Иногда ответ: «всё в порядке».
2. Назовите **конкретную проблему** (ошибка, трудный тест, трудное изменение). Если не можете, оставьте код
   в покое (Урок 08.1: KISS, «Keep It Simple, Stupid» — «делай проще», и YAGNI, «You Aren't Gonna Need It» — «тебе это не понадобится»).
3. Исправляйте «запахи» **при наличии тестов** ([Урок 08.13](13-refactoring-and-code-review.md) показывает как).

## 2. «Запахи» в любом коде

Мы будем использовать один сквозной пример: функцию, которая считает стоимость доставки посылки.

### 2.1 Магические числа, строковая типизация и булева слепота

```rust
fn shipping(weight: u32, country: &str, express: bool) -> u32 {
    let mut cost = if weight < 1000 {
        500
    } else if weight < 5000 {
        900
    } else {
        1500
    };
    if country == "DE" {
        cost = cost * 80 / 100;
    } else if country != "FR" {
        cost += 700;
    }
    if express {
        cost *= 2;
    }
    cost
}

fn main() {
    println!("{}", shipping(500, "DE", false));
    println!("{}", shipping(500, "de", false));
    println!("{}", shipping(500, "DE", true));
}
```

**Что происходит:**

1. `weight` — это `u32`. Функция не говорит, граммы это или килограммы; числа `1000` и `5000` не имеют
   имён. Это **магические числа**.
2. `country` — это `&str`. «Домом» считается только точный текст `"DE"`; `"FR"` — сосед; любой другой текст —
   заграница. Это **строковая типизация**.
3. `express` — это `bool`. В месте вызова `shipping(500, "DE", true)` читатель не знает, что значит `true`.
   Это **булева слепота**.
4. Второй вызов передаёт `"de"` строчными буквами. Никто не возражает.

```text
400
1200
800
```

Вторая строка — настоящая проблема. Опечатка в коде страны молча даёт неверную цену (`1200` вместо `400`):
ни ошибки, ни предупреждения, и ошибка может месяцами жить в продакшене.

Вот та же логика после небольших механических изменений: константы с именами, `enum` для зоны, `enum` для
скорости и функция для ценовых ступеней.

```rust
const LIGHT_LIMIT_GRAMS: u32 = 1_000;
const MEDIUM_LIMIT_GRAMS: u32 = 5_000;
const LIGHT_PRICE: u32 = 500;
const MEDIUM_PRICE: u32 = 900;
const HEAVY_PRICE: u32 = 1_500;
const FOREIGN_SURCHARGE: u32 = 700;
const HOME_DISCOUNT_PERCENT: u32 = 20;

#[derive(Debug, Clone, Copy, PartialEq)]
enum Zone {
    Home,
    Neighbour,
    Foreign,
}

impl Zone {
    fn from_country_code(code: &str) -> Option<Zone> {
        match code {
            "DE" => Some(Zone::Home),
            "FR" => Some(Zone::Neighbour),
            "US" | "JP" => Some(Zone::Foreign),
            _ => None,
        }
    }
}

#[derive(Debug, Clone, Copy, PartialEq)]
enum Speed {
    Standard,
    Express,
}

fn base_price(weight_grams: u32) -> u32 {
    if weight_grams < LIGHT_LIMIT_GRAMS {
        LIGHT_PRICE
    } else if weight_grams < MEDIUM_LIMIT_GRAMS {
        MEDIUM_PRICE
    } else {
        HEAVY_PRICE
    }
}

fn shipping(weight_grams: u32, zone: Zone, speed: Speed) -> u32 {
    let mut cost = base_price(weight_grams);
    match zone {
        Zone::Home => cost = cost * (100 - HOME_DISCOUNT_PERCENT) / 100,
        Zone::Neighbour => {}
        Zone::Foreign => cost += FOREIGN_SURCHARGE,
    }
    if speed == Speed::Express {
        cost *= 2;
    }
    cost
}

fn main() {
    println!("{:?}", Zone::from_country_code("de"));
    let zone = Zone::from_country_code("DE").unwrap();
    println!("{}", shipping(500, zone, Speed::Standard));
    println!("{}", shipping(500, zone, Speed::Express));
}
```

**Что происходит:**

1. У каждой константы есть имя, которое несёт единицу измерения (`_GRAMS`) или смысл (`FOREIGN_SURCHARGE`).
   Читатель больше не спрашивает «что такое 700?», а изменение цены делается в одном месте.
2. У `Zone` три варианта. Единственное место, где текст становится `Zone`, — `from_country_code`, которая
   возвращает `Option<Zone>`: неизвестный или с опечаткой код даёт `None`, и вызывающий код должен решить,
   что делать.
3. В `match zone` нет ветки `_`, поэтому, если позже вы добавите четвёртую зону, компилятор укажет на каждый
   `match`, который нужно обновить.
4. `Speed::Express` читается прямо в месте вызова. (Идею за этим объясняет Урок 08.5: сделайте недопустимые
   состояния невозможными.)

```text
None
400
800
```

> ⚠️ **Частая ошибка:** называть константу по её значению: `const FIVE_THOUSAND: u32 = 5_000;`. Имя должно
> говорить, что число *значит* (`MEDIUM_LIMIT_GRAMS`), а не повторять, чем оно *является*.

### 2.2 Каталог

Вот «запахи», которые вы встречаете чаще всего, — каждый с конкретной проблемой, которую он создаёт, и
обычным направлением исправления. Используйте таблицу как чек-лист при код-ревью (Урок 08.13).

| «Запах» | Как выглядит | Какую проблему создаёт | Обычное исправление |
|---|---|---|---|
| **Длинная функция** | Одна функция на 80 строк с комментариями вроде `// step 2` | Трудно читать, трудно протестировать один шаг отдельно | Выделить функции, по одной на шаг |
| **Магическое число** | `if age > 17`, `* 86400` | Смысл скрыт; изменение приходится искать поиском | Именованная `const` или `enum` |
| **Строковая типизация** | `status: String` со значениями `"open"`, `"closed"` | Опечатка — тихая ошибка, а не ошибка компиляции | `enum` + одна функция `parse` |
| **Булева слепота** | `draw(true, false, true)` | Вызов нечитаем; аргументы путают местами | `enum` на каждый флаг или структура с параметрами |
| **Длинный список параметров** | Функция с 8 параметрами | Трудно вызывать; ошибки порядка | Структура для группы или строитель (Урок 08.6) |
| **Одержимость примитивами** | `user_id: u64` и `order_id: u64` | Можно передать id заказа там, где ждут id пользователя | Newtype для каждого id (Урок 08.5) |
| **Дублирование кода** | Одни и те же 10 строк в трёх местах | Исправление ошибки надо повторять, и одну копию забывают | Выделить одну функцию (но см. правило трёх, Урок 08.1) |
| **«Божественный» тип** | `struct App` с 30 полями: база данных, состояние экрана, настройки | Всё зависит от всего; тестам нужно всё сразу | Разделить по ответственности (Урок 08.2) |
| **Зависть к чужим данным** (feature envy) | Метод, который в основном читает поля *другой* структуры | Логика находится далеко от данных, которые использует | Перенести метод в тип, которому принадлежат данные |
| **Стрельба дробью** (shotgun surgery) | Одно небольшое изменение требует правок в десяти файлах | Легко пропустить одно место | Собрать разбросанное знание в один модуль |

Обратите внимание: в каждой строке есть «какую проблему создаёт». Это проверка из раздела 1: «запах» без
конкретной проблемы — просто стилистическое мнение.

> 📏 **Соглашение:** функция, которая помещается на один экран (примерно 30–40 строк), принимает не больше
> четырёх-пяти параметров и делает одно дело, — хорошая цель. Clippy предупреждает при **восьми** параметрах
> (`clippy::too_many_arguments`); это страховка, а не цель.

## 3. Антипаттерны, частые в Rust

### 3.1 Лишний `clone`, чтобы компилятор замолчал

Проверка заимствований (Урок 03.5) иногда говорит «нет», и самый быстрый путь к зелёной сборке — `.clone()`.
Иногда это правильно. Часто это прячет неверную сигнатуру. Здесь `longest_word` принимает `text: String`,
то есть *забирает владение*, и вызывающему коду, который хочет сохранить `text`, приходится сначала
скопировать весь текст:

```rust
fn longest_word(text: String) -> String { /* ... */ }

let word = longest_word(text.clone());
```

Но функция только *читает* текст; владение ей не требовалось. Это работает, и именно поэтому это
антипаттерн: никто не замечает, что каждый вызов копирует текст. Исправление — в сигнатуре. Принимайте `&str`
(заимствованный вид) и возвращайте заимствованную часть:

```rust
fn longest_word(text: &str) -> &str {
    let mut best = "";
    for word in text.split_whitespace() {
        if word.len() > best.len() {
            best = word;
        }
    }
    best
}

fn main() {
    let text = String::from("the quick brown fox");
    let word = longest_word(&text);
    println!("{word} (from: {text})");
}
```

```text
quick (from: the quick brown fox)
```

Копирования нет: `word` указывает внутрь `text`. Правило: **когда хочется написать `.clone()`, спросите, кто
должен владеть данными**. Часто ответ: «владеть никому не нужно; заимствуйте».

> ⚡ **Производительность:** `clone` для `String` или `Vec` выделяет новую память и копирует каждый элемент.
> Один раз клонировать маленькое значение — нормально; клонировать большое значение в цикле — получить
> медленную программу без видимой причины в коде. Сначала измеряйте (Урок 05.12), но не добавляйте клоны
> «на всякий случай».

### 3.2 `unwrap` и `expect` для данных, пришедших снаружи

`unwrap()` означает «если это ошибка, аварийно завершить всю программу». В примере или тесте это нормально.
В коде, который обрабатывает *ввод* (файл, сетевое сообщение, текст от пользователя), он превращает обычное
событие (плохой ввод) в аварию:

```rust
fn parse_port(text: &str) -> u16 {
    text.trim().parse().unwrap()
}

fn main() {
    println!("{}", parse_port("8080"));
    println!("{}", parse_port("80 80"));
}
```

```text
8080

thread 'main' (4616161) panicked at src/main.rs:2:25:
called `Result::unwrap()` on an `Err` value: ParseIntError { kind: InvalidDigit }
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

(Число в скобках — идентификатор потока; у вас оно будет другим.) Сообщение говорит, что пошло не так
технически, но не *какой именно ввод* плох и что делать пользователю. Исправление — вернуть `Result` и
позволить вызывающему коду решить (Урок 04.10):

```rust
fn parse_port(text: &str) -> Result<u16, std::num::ParseIntError> {
    text.trim().parse()
}
```

> 🔒 **Безопасность:** программу, которая паникует от плохого ввода, может «уронить» любой, кто способен
> прислать ей плохой ввод. Считайте «аварию из-за ввода» ошибкой и обрабатывайте её как ошибку (`Result`).
> Этап 10 (Урок 10.4) посвящён этому.

Когда `unwrap` допустим? Когда сбой означал бы ошибку в *вашем* коде, а не плохой ввод: например,
`"127.0.0.1".parse::<IpAddr>().unwrap()` для константы. Тогда лучше `expect("объясните причину")`, чтобы
сообщение паники показало читателю, какое предположение нарушилось.

### 3.3 `Rc<RefCell<T>>` повсюду

`Rc<RefCell<T>>` (Уроки 05.9 и 06.4) даёт общие изменяемые данные и переносит проверку заимствований со
времени компиляции на **время выполнения**. Новички встречают его как «то, что заставляет компилятор
перестать жаловаться». Жалоба была сигналом о проектировании, а теперь проблема приходит позже — в виде аварии:

```rust
use std::cell::RefCell;
use std::rc::Rc;

fn main() {
    let counter = Rc::new(RefCell::new(0));
    let first = counter.borrow_mut();
    let mut second = counter.borrow_mut();
    *second += 1;
    println!("{first} {second}");
}
```

```text

thread 'main' (4616312) panicked at src/main.rs:7:30:
RefCell already borrowed
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

Два изменяемых заимствования одновременно — ровно то, что компилятор отклонил бы. С `RefCell` код
компилируется и падает во время работы, возможно, только на одной редкой ветке. Обращайтесь к
`Rc<RefCell<T>>` только когда действительно нужно разделяемое владение, которое нельзя выразить одним
владельцем и ссылками, например в графе, где узлы указывают друг на друга. В большинстве программ лучше один
владелец и `&mut`, передаваемый функциям, которые меняют значение.

### 3.4 «Наследование» через `Deref`

В Rust нет наследования (Урок 08.4). Некоторые пытаются его имитировать: `Employee` реализует `Deref` с
`Target = Person`, чтобы `employee.greet()` находил `Person::greet`:

```rust
use std::ops::Deref;

struct Person {
    name: String,
}

impl Person {
    fn greet(&self) -> String {
        format!("Hello, I am {}", self.name)
    }
}

struct Employee {
    person: Person,
}

impl Deref for Employee {
    type Target = Person;
    fn deref(&self) -> &Person {
        &self.person
    }
}

trait Describe {
    fn describe(&self) -> String;
}

impl Describe for Person {
    fn describe(&self) -> String {
        format!("person {}", self.name)
    }
}

fn print_description<T: Describe>(item: &T) {
    println!("{}", item.describe());
}

fn main() {
    let boss = Employee { person: Person { name: String::from("Ana") } };
    println!("{}", boss.greet());
    print_description(&boss);
}
```

```text
error[E0277]: the trait bound `Employee: Describe` is not satisfied
  --> src/main.rs:41:23
   |
41 |     print_description(&boss);
   |     ----------------- ^^^^^ unsatisfied trait bound
   |     |
   |     required by a bound introduced by this call
   |
help: the trait `Describe` is not implemented for `Employee`
...
```

**Что происходит:**

1. `boss.greet()` компилируется: когда метод не найден у `Employee`, компилятор пробует `*boss` — это `Person`.
2. Но `Deref` даёт только *поиск методов*. `Employee` — **не** `Person` и не получает его трейты, поэтому
   `print_description(&boss)` не компилируется. Кроме того, каждый публичный метод, который появится у
   `Person` в будущем, молча станет методом `Employee`.

`Deref` предназначен для умных указателей (`Box`, `Rc`, `String` в `str`), где одно значение *указывает на*
другое. Для отношения «имеет» используйте **композицию** (Урок 08.4): приватное поле и те методы, которые вы
решили предложить.

### 3.5 `#![deny(warnings)]` в исходном коде

`#![deny(warnings)]` в начале `main.rs` превращает каждое предупреждение компилятора в ошибку. Звучит строго и
хорошо. Если в `main` есть `let unused = 5;`, сборка падает так:

```text
error: unused variable: `unused`
 --> src/main.rs:4:9
  |
4 |     let unused = 5;
  |         ^^^^^^ help: if this is intentional, prefix it with an underscore: `_unused`
  |
note: the lint level is defined here
 --> src/main.rs:1:9
  |
1 | #![deny(warnings)]
  |         ^^^^^^^^
```

Проблема не в сегодняшнем коде, а в **завтрашнем компиляторе**. Каждый релиз Rust может добавить
предупреждения. Крейт с `deny(warnings)`, который вчера собирался, может перестать собираться после того, как
вы или пользователь вашей библиотеки обновите Rust, хотя код не изменился. Оставляйте предупреждения
предупреждениями в исходном коде и делайте их ошибками только в контроле качества: `cargo clippy -- -D
warnings` (Урок 05.6) и позже в CI (Continuous Integration, непрерывная интеграция: сервер, который
автоматически запускает ваши проверки; Этап 09). Ваша собственная проверка строга, а чужие сборки не ломаются.

## 4. Пусть Clippy найдёт простые случаи

Многие «запахи» находит **Clippy**. Поместите этот рабочий, но неидиоматичный код в `src/main.rs`:

```rust
fn total(prices: &Vec<u32>) -> u32 {
    let mut sum = 0;
    for i in 0..prices.len() {
        sum += prices[i];
    }
    sum
}

fn label(a: u32, b: u32, c: u32, d: u32, e: u32, f: u32, g: u32, h: u32) -> u32 {
    a + b + c + d + e + f + g + h
}

fn main() {
    println!("{}", total(&vec![1, 2, 3]));
    println!("{}", label(1, 2, 3, 4, 5, 6, 7, 8));
}
```

Запустите `cargo clippy`. Настоящий вывод (сокращён):

```text
warning: writing `&Vec` instead of `&[_]` involves a new object where a slice will do
 --> src/main.rs:1:18
  |
1 | fn total(prices: &Vec<u32>) -> u32 {
  |                  ^^^^^^^^^
  = note: `#[warn(clippy::ptr_arg)]` on by default
help: change this to
  |
1 - fn total(prices: &Vec<u32>) -> u32 {
1 + fn total(prices: &[u32]) -> u32 {

warning: the loop variable `i` is only used to index `prices`
 --> src/main.rs:3:14
  |
3 |     for i in 0..prices.len() {
  |              ^^^^^^^^^^^^^^^
  = note: `#[warn(clippy::needless_range_loop)]` on by default

warning: this function has too many arguments (8/7)
  --> src/main.rs:10:1
   |
10 | fn label(a: u32, b: u32, c: u32, d: u32, e: u32, f: u32, g: u32, h: u32) -> u32 {
   | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
   = note: `#[warn(clippy::too_many_arguments)]` on by default
```

**Что происходит:**

1. `&Vec<u32>` (и `&String`) как тип параметра без нужды узок. `&[u32]` принимает `Vec`, массив или часть
   вектора; `&str` принимает `String` или литерал. Это тот же урок, что и в примере с `clone`: берите самый
   общий *заимствованный* тип, который справляется с задачей.
2. `for i in 0..prices.len()` с `prices[i]` — цикл по индексу. Итератор (`prices.iter().sum()`) не может выйти
   за границы и говорит читателю, чего вы хотите.
3. Восемь параметров — «запах» «длинный список параметров». Предел Clippy по умолчанию — семь.

Не у каждого «запаха» есть lint, и не каждый lint подходит вашему случаю. Как выбирать уровни lint-ов,
разрешать (`allow`) lint с обоснованием и настраивать Clippy для всего проекта — в
[Уроке 08.11](11-conventions-naming-clippy-and-api-guidelines.md).

## 5. Что делать, когда вы почувствовали «запах»

1. **Назовите проблему.** «Эта функция длинная» — описание; «я не могу протестировать правило скидки, не
   собрав целый заказ» — *проблема*.
2. **Оцените цену бездействия.** Код, который никто не меняет, может остаться некрасивым. Исправляйте
   «запахи» в коде, который меняется каждую неделю.
3. **Сначала поставьте тесты вокруг поведения** (характеризационные тесты, Урок 08.13), затем исправляйте
   **один «запах» за раз** в небольшом коммите.
4. **Не меняйте один «запах» на другой.** Замена трёх дублирующихся строк абстракцией в четыре уровня — это
   не прогресс (Урок 08.1).

> 🧪 **Тестирование:** «запахи» легко превращаются в тесты. Для примера с доставкой
> `assert_eq!(Zone::from_country_code("de"), None)` фиксирует поведение, которое раньше было тихой ошибкой.

## Частые ошибки

1. **Считать каждый «запах» ошибкой.** `match` с десятью ветками может быть самым ясным кодом из возможных.
   Сначала назовите проблему.
2. **«Исправлять» «запах» без тестов.** Вы не можете знать, что поведение осталось прежним.
3. **Заглушать инструмент, а не читать его.** `#[allow(clippy::too_many_arguments)]`, добавленный только ради
   исчезновения предупреждения, прячет сигнал. Если вы разрешаете lint, напишите комментарий почему.
4. **Переусердствовать.** Если превратить каждый `bool` и `String` в тип, трейт и модуль, маленькая
   программа станет труднее для чтения. Исправляйте то, что болит.

## Упражнения

### Упражнение 1 — Назовите «запах» (легко)

Для каждого фрагмента назовите «запах» и одним предложением скажите, какую конкретную проблему он создаёт.

1. `connect("db", 5432, true, false, true)` для `fn connect(host: &str, port: u16, tls: bool, retry: bool, verbose: bool)`.
2. `if user.role == "admin" || user.role == "Admin"`, повторённое в шести файлах.
3. `struct Shop` с полями `customers`, `invoices`, `theme_color`, `mail_password`, `window_size`.
4. `let timeout = 30 * 60 * 1000;` посреди функции.

<details>
<summary>Подсказка</summary>

Посмотрите на таблицу в разделе 2.2. Спросите себя: «что будет, когда кто-то это изменит или сделает опечатку?»

</details>

<details>
<summary>Ответ</summary>

1. *Булева слепота* и *длинный список параметров*: никто не знает, какое из `true` относится к `tls`, а
   перестановка двух флагов компилируется. Исправление: структура с параметрами или `enum` на каждый флаг.
2. *Строковая типизация* и *дублирование кода*: два написания показывают, что строки уже расходятся.
   Исправление: `enum Role` с одним методом `is_admin`.
3. *«Божественный» тип*: бизнес-данные, настройки и состояние экрана смешаны, поэтому для теста счетов нужен
   пароль почты и размер окна. Исправление: разделить по ответственности.
4. *Магическое число*: читателю приходится вычислять, что это 30 минут в миллисекундах. Исправление:
   `const SESSION_TIMEOUT: Duration = Duration::from_secs(30 * 60);`.

</details>

### Упражнение 2 — Замените строки на enum и протестируйте (средне)

Программа обработки обращений в поддержку хранит `status: String` со значениями `"open"`, `"pending"` и
`"closed"` и функцию `can_edit(status: &str) -> bool`, которая возвращает `false` только для `"closed"`.
Напишите `enum Status` с `Status::parse(text) -> Result<Status, UnknownStatus>` и методом `can_edit`.
Напишите тесты: известные слова разбираются, опечатка вроде `"Open"` — ошибка, закрытое обращение
редактировать нельзя.

<details>
<summary>Подсказка</summary>

Пусть `UnknownStatus` будет структурой-кортежем с плохим текстом. Выведите `Debug` и `PartialEq` для обоих
типов, чтобы работал `assert_eq!`.

</details>

<details>
<summary>Ответ</summary>

В библиотечном пакете (`cargo new --lib code/p08-tickets`), `src/lib.rs`:

```rust
#[derive(Debug, Clone, Copy, PartialEq)]
pub enum Status {
    Open,
    Pending,
    Closed,
}

#[derive(Debug, PartialEq)]
pub struct UnknownStatus(pub String);

impl Status {
    pub fn parse(text: &str) -> Result<Status, UnknownStatus> {
        match text {
            "open" => Ok(Status::Open),
            "pending" => Ok(Status::Pending),
            "closed" => Ok(Status::Closed),
            other => Err(UnknownStatus(other.to_string())),
        }
    }

    pub fn can_edit(self) -> bool {
        self != Status::Closed
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn parses_known_words() {
        assert_eq!(Status::parse("open"), Ok(Status::Open));
        assert_eq!(Status::parse("closed"), Ok(Status::Closed));
    }

    #[test]
    fn rejects_typos() {
        assert_eq!(Status::parse("Open"), Err(UnknownStatus("Open".to_string())));
    }

    #[test]
    fn closed_cannot_be_edited() {
        assert!(Status::Open.can_edit());
        assert!(!Status::Closed.can_edit());
    }
}
```

Почему это работает: единственное место, где текст становится статусом, — `parse`. После этого компилятор
знает, что у `Status` ровно три значения. `can_edit` использует `!=`, что работает, потому что мы вывели
`PartialEq`.

</details>

### Упражнение 3 — Замените `Deref` композицией (сложно)

Исправьте `Employee` из раздела 3.4 без `Deref`. `Employee` хранит приватный `Person`, предлагает `greet()` и
`person()` только для чтения. Напишите тест для приветствия.

<details>
<summary>Подсказка</summary>

`fn greet(&self) -> String { self.person.greet() }` — это *делегирующий* метод. Добавьте
`Employee::new(name)`, потому что приватное поле нельзя заполнить снаружи.

</details>

<details>
<summary>Ответ</summary>

```rust
pub struct Person {
    pub name: String,
}

impl Person {
    pub fn greet(&self) -> String {
        format!("Hello, I am {}", self.name)
    }
}

pub struct Employee {
    person: Person,
}

impl Employee {
    pub fn new(name: &str) -> Employee {
        Employee { person: Person { name: name.to_string() } }
    }
    pub fn person(&self) -> &Person {
        &self.person
    }
    pub fn greet(&self) -> String {
        self.person.greet()
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn employee_greets_through_its_person() {
        let e = Employee::new("Ana");
        assert_eq!(e.greet(), "Hello, I am Ana");
        assert_eq!(e.person().name, "Ana");
    }
}
```

Почему это работает: `Employee` *имеет* `Person` и говорит об этом явно. Его интерфейс — только те методы,
которые вы написали; если хотите, чтобы `Employee` реализовал `Describe`, вы пишете этот `impl` сами, часто
делегируя внутреннему `Person`.

</details>

## Вопросы для самопроверки

1. Чем «запах» кода отличается от ошибки?

<details>
<summary>Ответ</summary>

Ошибка — это неверное поведение. «Запах» — признак того, что *проектирование* может быть проблемой.
Пахнущий код может быть корректным сегодня; цена проявляется, когда вы его меняете, тестируете или читаете.

</details>

2. Когда допустим `unwrap()`?

<details>
<summary>Ответ</summary>

В тестах и примерах, а также когда сбой означал бы ошибку в вашем собственном коде (константа, которая не
может не разобраться); тогда лучше `expect("причина")`. Никогда — для данных извне программы.

</details>

3. В примере с доставкой: почему опечатка `"de"` дала неверную цену без всякой ошибки и что убирает проблему?

<details>
<summary>Ответ</summary>

Страна была `&str`, и любой текст, кроме двух точных значений, считался «заграницей». Если один раз
преобразовать текст функцией, возвращающей `Option<Zone>` (или `Result`), опечатка превращается в заметный
`None` или ошибку.

</details>

4. Почему реализация `Deref` ради «наследования» — антипаттерн?

<details>
<summary>Ответ</summary>

`Deref` меняет только поиск методов. Внешний тип не становится внутренним, поэтому ограничения трейтов и
обобщённый код с ним не работают, а все публичные методы внутреннего типа «протекают» во внешний.
Используйте композицию.

</details>

## Итоги

- **«Запах» кода** — подсказка, что в проектировании может быть проблема; **антипаттерн** — популярный рецепт,
  который обычно делает хуже. Всегда называйте конкретную проблему, прежде чем менять код.
- Частые «запахи»: длинные функции, магические числа, строковая типизация, булевы параметры, длинные списки
  параметров, одержимость примитивами, дублирование кода, «божественные» типы, зависть к чужим данным и
  стрельба дробью.
- Заменяйте строковую типизацию на `enum` с одной функцией `parse`; заменяйте магические числа именованными
  константами.
- Антипаттерны Rust: лишний `clone` (исправьте сигнатуру), `unwrap` для внешних данных (возвращайте
  `Result`), `Rc<RefCell<T>>` повсюду (предпочитайте одного владельца и `&mut`), `Deref` как наследование
  (используйте композицию) и `#![deny(warnings)]` в исходном коде (используйте `-D warnings` в контроле качества).
- В параметрах берите `&str` и `&[T]`, а не `&String` и `&Vec<T>`.
- Clippy находит многие «запахи»; исправляйте их небольшими шагами, при наличии тестов.
