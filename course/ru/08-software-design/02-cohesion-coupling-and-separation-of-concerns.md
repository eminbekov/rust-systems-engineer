# Урок 08.2 — Связность, сопряжение и разделение ответственности

> **Этап 08 — Проектирование ПО: принципы, паттерны и соглашения** · Урок 2 из 17 · ⏱ около 135 минут

## Что вы узнаете

- Что такое **связность** (cohesion) и **сопряжение** (coupling) и почему мы хотим высокую связность и низкое сопряжение.
- Как разделить программу, которая «делает всё», на части, каждая из которых занимается одной **ответственностью**.
- Как скрыть внутренности модуля с помощью приватных полей, чтобы другой код не мог от них зависеть.
- Как проектировать функции, которые легко тестировать, потому что они ничего не печатают и не читают файлы.
- Когда разделение заходит слишком далеко.

## Новые слова

| Слово | Значение |
|---|---|
| **связность** (cohesion) | Насколько тесно то, что находится внутри одной части (функции, структуры, модуля), относится друг к другу. *Высокая* связность: всё в ней служит одной цели. |
| **сопряжение** (coupling) | Насколько одна часть зависит от деталей другой. *Низкое* (или *слабое*) сопряжение: одну часть можно менять, не трогая другую. |
| **ответственность** (concern) | Одна отдельная тема, которой должна заниматься программа, например «прочитать ввод», «применить бизнес-правила», «показать результат». |
| **разделение ответственности** (separation of concerns) | Хранение каждой ответственности в своей части кода. |
| **инкапсуляция** (encapsulation) | Сокрытие внутренностей части (её полей и вспомогательных функций) и предложение вместо этого небольшого набора публичных операций. |
| **побочный эффект** (side effect) | Всё, что функция делает кроме возврата значения: печать, чтение файла, изменение глобального состояния. |
| **чистая функция** (pure function) | Функция, которая только читает свои аргументы и возвращает значение, без побочных эффектов. Одинаковый вход всегда даёт одинаковый выход. |
| **I/O** (Input/Output, ввод-вывод) | Всё, что общается с миром вне программы: клавиатура, экран, файлы, сеть. |

## 1. Две меры

Представьте кухню. На хорошо организованной кухне все ножи лежат в одном ящике, а все специи — на одной полке. Это **высокая связность**: то, что лежит в одном месте, относится друг к другу. Если вам приходится открывать пять ящиков, чтобы собрать части одного инструмента, связность низкая.

Теперь представьте двух поваров на одной кухне. Если повару A нужно спрашивать повара B, прежде чем переставить сковороду, потому что B тайно зависит от того, где она стоит, они **жёстко сопряжены**. Если у каждого своя станция и готовые тарелки они передают через окошко, сопряжение **низкое**.

В коде:

| | Что измеряет | Цель | Тревожный признак |
|---|---|---|---|
| **Связность** | Относится ли содержимое этой части друг к другу? | Высокая | Модуль `utils`; структура, поля которой используются разными несвязанными методами |
| **Сопряжение** | Сколько эта часть знает о внутренностях других частей? | Низкое | Небольшое изменение в одном месте заставляет править много других |

Эти две идеи лежат в основе большинства советов по проектированию. **Разделение ответственности** — практическая привычка, которая даёт и то и другое: поместите каждую ответственность в свою часть и пусть части общаются через небольшие и понятные интерфейсы.

## 2. Программа, которая делает всё

Программа читает строки вида `ana 90` (имя и баллы), пропускает плохие строки, печатает каждый результат и среднее. Вот она одним куском:

```rust
fn main() {
    let input = "ana 90\nbo 72\nbad line\ncy 85";
    let mut total = 0;
    let mut count = 0;
    for line in input.lines() {
        let parts: Vec<&str> = line.split_whitespace().collect();
        if parts.len() != 2 {
            println!("skipped: {line}");
            continue;
        }
        match parts[1].parse::<u32>() {
            Ok(points) => {
                total += points;
                count += 1;
                println!("{:<6}{:>4}", parts[0], points);
            }
            Err(_) => println!("skipped: {line}"),
        }
    }
    println!("average: {:.1}", total as f64 / count as f64);
}
```

**Что происходит:**

1. Здесь `input` — фиксированный текст, чтобы пример было легко запускать.
2. Для каждой строки код делит её на слова (это **разбор**, parsing) и проверяет, что слов ровно два.
3. Он разбирает баллы, прибавляет их к `total` и сразу печатает строку (это **отчёт**, reporting).
4. В конце он вычисляет среднее и печатает его (это **вычисление**, calculating).

```text
ana     90
bo      72
skipped: bad line
cy      85
average: 82.3
```

Работает. Но посмотрите, что будет, когда требования изменятся, а они меняются всегда:

- «Читать строки из файла». Придётся менять цикл, а разбор находится в его середине.
- «Печатать отчёт в CSV (comma-separated values, значения через запятую)». Придётся править вызовы `println!`, перемешанные с циклом разбора.
- «А если нет ни одной корректной строки?» Выражение `total as f64 / count as f64` делит ноль на ноль, и программа печатает `average: NaN`. Чтобы это исправить и *проверить* исправление тестом, нужно запустить всю программу и прочитать, что она напечатала.

Три разные темы (разбор, вычисление, отчёт) спутаны в одной функции. Это **низкая связность**: у функции три причины меняться. И ни одну часть нельзя протестировать отдельно, потому что каждая часть что-то печатает.

## 3. Разделим ответственности

Дадим каждой ответственности свой дом. Разбор превращает текст в `Score`. Вычисления работают с обычными числами. Отчёт превращает данные в текст. К экрану прикасается только `main`:

```rust
mod parse {
    #[derive(Debug, PartialEq)]
    pub struct Score {
        pub name: String,
        pub points: u32,
    }

    pub fn parse_line(line: &str) -> Result<Score, String> {
        let parts: Vec<&str> = line.split_whitespace().collect();
        if parts.len() != 2 {
            return Err(format!("expected `name points`, got {line:?}"));
        }
        let points = parts[1]
            .parse::<u32>()
            .map_err(|_| format!("bad number in {line:?}"))?;
        Ok(Score {
            name: parts[0].to_string(),
            points,
        })
    }
}

mod stats {
    pub fn average(points: &[u32]) -> Option<f64> {
        if points.is_empty() {
            return None;
        }
        let total: u32 = points.iter().sum();
        Some(f64::from(total) / points.len() as f64)
    }
}

mod report {
    use crate::parse::Score;

    pub fn render(scores: &[Score], average: Option<f64>) -> String {
        let mut text = String::new();
        for score in scores {
            text.push_str(&format!("{:<6}{:>4}\n", score.name, score.points));
        }
        match average {
            Some(avg) => text.push_str(&format!("average: {avg:.1}\n")),
            None => text.push_str("average: n/a\n"),
        }
        text
    }
}

fn main() {
    let input = "ana 90\nbo 72\nbad line\ncy 85";
    let mut scores = Vec::new();
    for line in input.lines() {
        match parse::parse_line(line) {
            Ok(score) => scores.push(score),
            Err(message) => println!("skipped: {message}"),
        }
    }
    let points: Vec<u32> = scores.iter().map(|s| s.points).collect();
    print!("{}", report::render(&scores, stats::average(&points)));
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn parse_line_accepts_a_name_and_points() {
        let score = parse::parse_line("ana 90").unwrap();
        assert_eq!(
            score,
            parse::Score {
                name: "ana".to_string(),
                points: 90
            }
        );
    }

    #[test]
    fn parse_line_rejects_bad_input() {
        assert!(parse::parse_line("bad line").is_err());
        assert!(parse::parse_line("ana").is_err());
    }

    #[test]
    fn average_of_nothing_is_none() {
        assert_eq!(stats::average(&[]), None);
        assert_eq!(stats::average(&[90, 80]), Some(85.0));
    }

    #[test]
    fn render_prints_one_line_per_score_and_the_average() {
        let scores = vec![parse::Score {
            name: "bo".to_string(),
            points: 72,
        }];
        assert_eq!(
            report::render(&scores, Some(72.0)),
            "bo      72\naverage: 72.0\n"
        );
    }
}
```

**Что происходит:**

1. `mod parse` знает, как выглядит строка. `parse_line` возвращает `Result<Score, String>`: либо результат, либо сообщение о том, что не так.
2. `mod stats` знает только о числах. `average` принимает `&[u32]` (срез) и возвращает `Option<f64>`: `None` для пустого списка, поэтому случай деления на ноль просто не может возникнуть.
3. `mod report` знает, как выглядит отчёт. `render` **не** печатает; она строит и возвращает `String`. Чтобы перейти на CSV, нужно изменить только эту функцию.
4. `main` — единственное место с побочными эффектами. Она читает ввод, собирает результаты и печатает.

```text
skipped: bad number in "bad line"
ana     90
bo      72
cy      85
average: 82.3
```

Сообщение о пропущенной строке выводится первым, потому что `main` печатает его в процессе сбора результатов, до печати отчёта.

Теперь каждая часть — **чистая функция**, и тестировать легко. Тесты в конце файла проверяют каждую ответственность отдельно, без печати:

```text
running 4 tests
test tests::average_of_nothing_is_none ... ok
test tests::parse_line_accepts_a_name_and_points ... ok
test tests::parse_line_rejects_bad_input ... ok
test tests::render_prints_one_line_per_score_and_the_average ... ok

test result: ok. 4 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

> 🧪 **Тестирование:** хорошее правило: держите «мышление» в чистых функциях, а побочные эффекты (чтение, печать, сохранение) — в тонком слое на краю, обычно в `main`. Чистые функции легко тестировать, а тонкий слой так мал, что ошибаться в нём почти негде. Некоторые инженеры называют это «функциональное ядро, императивная оболочка» (functional core, imperative shell).

> 📏 **Соглашение:** внутри функции хорошая проверка связности — её имя. Если в имени нужно «и» (`parse_and_print`), скорее всего, она делает две вещи.

## 4. Уменьшаем сопряжение

### Скрывайте представление

Посмотрите на модуль `inventory` ниже. Он хранит предметы в `Vec`. Поле приватное, а код снаружи пытается до него добраться:

```rust
mod inventory {
    pub struct Inventory {
        items: Vec<(String, u32)>,
    }

    impl Inventory {
        pub fn new() -> Self {
            Inventory { items: Vec::new() }
        }
        pub fn add(&mut self, name: &str, count: u32) {
            self.items.push((name.to_string(), count));
        }
    }
}

fn main() {
    let mut inv = inventory::Inventory::new();
    inv.add("bolt", 40);
    println!("{}", inv.items[0].1);
}
```

```text
error[E0616]: field `items` of struct `Inventory` is private
  --> src/main.rs:19:24
   |
19 |     println!("{}", inv.items[0].1);
   |                        ^^^^^ private field

For more information about this error, try `rustc --explain E0616`.
error: could not compile `demo` (bin "demo") due to 1 previous error
```

Компилятор здесь принуждает к низкому сопряжению. Внешний код не имеет права знать, что предметы лежат в векторе, поэтому не может от этого зависеть. Автор `Inventory` теперь может изменить хранилище, например на `HashMap`, и поменять придётся только код внутри модуля:

```rust
mod inventory {
    use std::collections::HashMap;

    pub struct Inventory {
        items: HashMap<String, u32>, // was a Vec before; nobody outside notices
    }

    impl Inventory {
        pub fn new() -> Self {
            Inventory {
                items: HashMap::new(),
            }
        }
        pub fn add(&mut self, name: &str, count: u32) {
            *self.items.entry(name.to_string()).or_insert(0) += count;
        }
        pub fn count(&self, name: &str) -> u32 {
            self.items.get(name).copied().unwrap_or(0)
        }
    }
}

fn main() {
    let mut inv = inventory::Inventory::new();
    inv.add("bolt", 40);
    inv.add("bolt", 2);
    println!("{}", inv.count("bolt"));
    println!("{}", inv.count("nut"));
}
```

**Что происходит:**

1. Поле `items` приватное. Единственные публичные операции — `new`, `add` и `count`: это весь **интерфейс** модуля.
2. `add` и `count` переписаны под `HashMap`, но `main` — ровно то, что написал бы пользователь старой версии с `Vec`, и она по-прежнему работает.
3. Программа печатает количество `"bolt"` (40 + 2) и `"nut"` (никогда не добавляли).

```text
42
0
```

Это **инкапсуляция**. Будь поле `pub`, каждый пользователь мог бы написать `inv.items[0]`, и хранилище нельзя было бы изменить, не сломав их всех.

> 💡 **Совет:** начинайте с того, что всё приватно. Делайте элемент `pub` только тогда, когда он нужен снаружи, а `pub(crate)` используйте для элементов, которые нужны другим модулям вашего крейта, но не должны быть видны внешнему миру. Сделать что-то публичным позже легко, а забрать обратно — очень трудно.

### Просите минимум

Функция `stats::average` принимает `&[u32]` — обычный список чисел. Она могла бы принимать `&[Score]`, но тогда `stats` должен был бы знать о `Score` и о модуле `parse`. Поскольку она просит только то, что ей действительно нужно, она работает с баллами, с температурами, с чем угодно. Чем конкретнее параметр, тем жёстче сопряжение.

Родственная привычка: не лезьте сквозь много слоёв, как в `order.customer().address().city().name()`. Каждая точка — зависимость от внутренностей другого типа. Если вам нужно название города, спросите у заказа одним методом (`order.shipping_city()`) и пусть заказ сам решает, как его найти. У этой привычки есть название — *закон Деметры* (Law of Demeter), но практическая версия проста: разговаривайте с соседями, а не с соседями ваших соседей.

## 5. Повышаем связность

Связность относится и к типам. Эта структура `Order` содержит две группы полей. Одну использует `total_cents`, другую — `greeting`:

```rust
struct Order {
    customer_name: String,
    customer_email: String,
    prices_cents: Vec<u64>,
    discount_percent: u64,
}

impl Order {
    fn total_cents(&self) -> u64 {
        let sum: u64 = self.prices_cents.iter().sum();
        sum - sum * self.discount_percent / 100
    }
    fn greeting(&self) -> String {
        format!("Dear {} <{}>", self.customer_name, self.customer_email)
    }
}

fn main() {
    let order = Order {
        customer_name: "Ana".to_string(),
        customer_email: "ana@mail.org".to_string(),
        prices_cents: vec![1000, 550],
        discount_percent: 10,
    };
    println!("{}", order.greeting());
    println!("{}", order.total_cents());
}
```

```text
Dear Ana <ana@mail.org>
1395
```

Ни один из методов не использует все поля. Это признак того, что `Order` — на самом деле две склеенные вещи. Когда изменится способ связи с клиентами (телефон, язык), поменяется `Order`, хотя с ценами ничего не произошло. Разделим:

```rust
struct Customer {
    name: String,
    email: String,
}

impl Customer {
    fn greeting(&self) -> String {
        format!("Dear {} <{}>", self.name, self.email)
    }
}

struct Order {
    prices_cents: Vec<u64>,
    discount_percent: u64,
}

impl Order {
    fn total_cents(&self) -> u64 {
        let sum: u64 = self.prices_cents.iter().sum();
        sum - sum * self.discount_percent / 100
    }
}

fn main() {
    let customer = Customer {
        name: "Ana".to_string(),
        email: "ana@mail.org".to_string(),
    };
    let order = Order {
        prices_cents: vec![1000, 550],
        discount_percent: 10,
    };
    println!("{}", customer.greeting());
    println!("{}", order.total_cents());
}
```

Вывод тот же, но теперь у каждой структуры одна причина меняться. Кроме того, `Customer` можно использовать для других задач, например для рассылок, не таща за собой список цен. (В следующих уроках этот строительный блок «имеет» используется часто: Урок 08.4 объясняет композицию.)

> 📏 **Соглашение:** быстрая проверка структуры: выпишите её поля и методы и отметьте, какой метод какое поле использует. Если отметки образуют два отдельных кластера, скорее всего, у вас две структуры.

## 6. Когда НЕ разделять

У разделения есть цена: больше имён, больше файлов, больше мест, где нужно искать. Будьте осторожны в таких случаях:

- **Слишком мелко.** Модуль с одной функцией, которая вызывается один раз, — шум. Разделяйте, когда у части есть собственная причина меняться или когда нужно протестировать её отдельно, а не раньше (это YAGNI из Урока 08.1).
- **Слои-посредники.** Функция, которая просто вызывает другую функцию с теми же аргументами, добавляет переход и не даёт пользы.
- **Разделение одной ответственности.** Разрезание одной идеи на три модуля только ради коротких файлов может *повысить* сопряжение, потому что модулям теперь нужно знать о внутренностях друг друга.
- **Измерение строк вместо причин.** Функция на 200 строк с одной ясной целью может быть лучше десяти функций по 20 строк, которые нужны только вместе. Вопрос всегда один: что и по какой причине меняется?

## Частые ошибки

**Ошибка 1: модуль `utils`.** Модуль с именем `utils`, `helpers` или `common` собирает всё, что не подошло в другое место: фокусы со строками, разбор дат, отправку писем. У него нет цели, поэтому связность у него самая низкая из возможных. Называйте модули по тому, о чём они (`text`, `dates`, `mail`).

**Ошибка 2: всё `pub`.** Делать все поля и функции публичными «на всякий случай» значит связывать каждую часть с каждой. Если что-то `pub`, это обещание.

**Ошибка 3: функции, которые печатают.** Функцию, вызывающую `println!` посреди своей логики, нельзя повторно использовать для файла, веб-страницы или теста. Возвращайте `String` или значение и пусть вызывающий код решает.

**Ошибка 4: модули, зависящие друг от друга в обе стороны.** Если `parse` использует `report`, а `report` использует `parse`, нельзя изменить ни один из них отдельно. Внутри одного крейта Rust такие циклы допускает, но это проблема дизайна; нарисуйте стрелки между модулями и держите их направленными в одну сторону (слои разбирает Урок 08.14).

1. Создайте пакет и начните с запутанной программы:

```bash
cd ~/projects/rust
cargo new code/p08-coupling
cd code/p08-coupling
```

2. Поместите запутанную программу из раздела 2 (ту, где `main` делает всё) в `src/main.rs` и запустите его через `cargo run`. Вы увидите вывод из раздела 2.

3. Попробуйте написать тест для «среднего пустого списка». Заметьте, что это невозможно: нет функции, которую можно вызвать.

4. Выполняйте рефакторинг шаг за шагом, запуская `cargo run` после каждого шага; вывод не должен меняться (кроме порядка сообщения о пропуске):
   1. Перенесите разбор в `mod parse` с функцией `parse_line`.
   2. Перенесите среднее в `mod stats` как функцию над `&[u32]`, возвращающую `Option<f64>`.
   3. Перенесите форматирование в `mod report` как функцию, возвращающую `String`.
   4. Пусть `main` занимается только склейкой.

5. Добавьте четыре теста из раздела 3 (или свои версии) и выполните:

```bash
cargo test
cargo clippy
git add .
git commit -m "refactor(p08): separate parse, stats and report"
```

**Что происходит:** на шаге 3 вы не могли протестировать среднее, потому что оно было спрятано внутри `main`. После разделения `stats::average(&[])` — тест в одну строку. Тестируемость — очень хорошая мера разделения.

## Упражнения

### Упражнение 1 — Связность или сопряжение? (легко)

Для каждого предложения скажите, про связность оно или про сопряжение и описывает ли оно что-то хорошее или плохое:

1. «Переименование поля в `Config` заставило меня править девять других файлов».
2. «Всё в `geometry.rs` — про фигуры и их площади».
3. «В структуре `Report` есть поле, которое нужно только коду отправки писем, и поле, которое нужно только коду печати».

<details>
<summary>Подсказка</summary>

Сопряжение — это про стрелки между частями. Связность — про то, что внутри одной части.

</details>

<details>
<summary>Ответ</summary>

1. Сопряжение, плохо (жёсткое): другие файлы зависят от детали `Config`.
2. Связность, хорошо (высокая): у модуля одна тема.
3. Связность, плохо (низкая): две несвязанные группы полей живут в одной структуре.

Почему это работает: сопряжение — стрелки между частями; связность — единство внутри части.

</details>

### Упражнение 2 — Скройте представление (средне)

Модуль `temp` выставляет наружу своё поле. Сделайте поле приватным, дайте типу конструктор `from_celsius` и метод `fahrenheit` и обновите `main`. Затем **напишите тест**: `100.0` °C — это `212.0` °F, а `0.0` °C — это `32.0` °F.

```rust
mod temp {
    pub struct Reading {
        pub celsius: f64,
    }
}

fn main() {
    let r = temp::Reading { celsius: 100.0 };
    println!("{}", r.celsius * 9.0 / 5.0 + 32.0);
}
```

<details>
<summary>Подсказка</summary>

Не добавляйте геттер для `celsius`, если он никому не нужен (YAGNI). Функцию, создающую значение, обычно называют конструктором; в Rust это ассоциированная функция без `self`.

</details>

<details>
<summary>Ответ</summary>

```rust
mod temp {
    pub struct Reading {
        celsius: f64,
    }

    impl Reading {
        pub fn from_celsius(celsius: f64) -> Self {
            Reading { celsius }
        }
        pub fn fahrenheit(&self) -> f64 {
            self.celsius * 9.0 / 5.0 + 32.0
        }
    }
}

fn main() {
    let r = temp::Reading::from_celsius(100.0);
    println!("{}", r.fahrenheit());
}

#[cfg(test)]
mod tests {
    use super::temp::Reading;

    #[test]
    fn boiling_point_in_fahrenheit() {
        assert_eq!(Reading::from_celsius(100.0).fahrenheit(), 212.0);
        assert_eq!(Reading::from_celsius(0.0).fahrenheit(), 32.0);
    }
}
```

Почему это работает: снаружи модуля никто не видит поле, поэтому автор может позже хранить кельвины или градусы Фаренгейта и менять только `temp`. `main` и тест пользуются только публичным интерфейсом.

</details>

### Упражнение 3 — Разберите свалку (сложно)

В проекте есть файл `utils.rs` с четырьмя функциями: `slugify` (превращает заголовок в текст, безопасный для URL (Uniform Resource Locator, веб-адрес)), `parse_date`, `send_email` и `hash_password`. Предложите модули с именами, говорящими об их назначении, и объясните, почему эти функции не должны оставаться вместе.

<details>
<summary>Подсказка</summary>

Для каждой функции спросите: что заставит её измениться? Новый почтовый сервис меняет `send_email`; новый формат даты меняет `parse_date`; новый алгоритм хеширования меняет `hash_password`.

</details>

<details>
<summary>Ответ</summary>

```rust
#![allow(dead_code)]

mod text {
    pub fn slugify(title: &str) -> String {
        title.to_lowercase().replace(' ', "-")
    }
}

mod dates {
    pub fn parse_date(text: &str) -> Option<(u32, u32, u32)> {
        let mut parts = text.split('-').map(|p| p.parse::<u32>().ok());
        Some((parts.next()??, parts.next()??, parts.next()??))
    }
}

mod mail {
    pub fn send_email(to: &str, body: &str) {
        println!("to {to}: {body}");
    }
}

mod passwords {
    pub fn hash_password(password: &str) -> String {
        format!("hash-of-{}", password.len()) // placeholder, not real hashing
    }
}

fn main() {
    println!("{}", text::slugify("Hello World"));
    println!("{:?}", dates::parse_date("2026-11-18"));
    mail::send_email("ana@mail.org", "hi");
    println!("{}", passwords::hash_password("secret"));
}
```

Почему это работает: каждый модуль меняется по своей причине, а читатель, который ищет код паролей, смотрит в `passwords`. Тела функций здесь — лишь небольшие заглушки (`hash_password` на самом деле ничего не хеширует). В настоящем проекте `passwords` и `mail` чувствительны к безопасности, поэтому их размещение в отдельных модулях ещё и упрощает проверку. У этих функций нет ничего общего, кроме «мы не знали, куда их положить», — признак низкой связности.

</details>

## Вопросы для самопроверки

1. Чего мы хотим: высокой или низкой связности? Высокого или низкого сопряжения?

<details>
<summary>Ответ</summary>

Высокой связности и низкого сопряжения.

</details>

2. Почему приватное поле снижает сопряжение?

<details>
<summary>Ответ</summary>

Другой код не может зависеть от того, как хранятся данные, поэтому владелец может свободно менять хранилище.

</details>

3. Почему `render(...) -> String` проще тестировать, чем `print_report(...)`?

<details>
<summary>Ответ</summary>

У неё нет побочных эффектов; тест может вызвать её и сравнить возвращённый текст через `assert_eq!`.

</details>

4. Какая часть программы должна заниматься вводом и выводом при хорошем разделении?

<details>
<summary>Ответ</summary>

Тонкий внешний слой, обычно `main`; остальное должно состоять из чистых функций.

</details>

5. Назовите одну опасность разбиения кода на слишком много крошечных модулей.

<details>
<summary>Ответ</summary>

Больше имён и файлов, по которым нужно ориентироваться, функции-посредники, которые ничего не добавляют, а иногда и более высокое сопряжение, потому что части должны знать друг о друге.

</details>

## Итоги

- **Связность** — насколько содержимое одной части относится друг к другу; **сопряжение** — насколько части зависят от внутренностей друг друга. Стремитесь к высокой связности и низкому сопряжению.
- **Разделение ответственности**: разбор, вычисление и отчёт принадлежат разным местам.
- Держите побочные эффекты (печать, файлы, сеть) в тонком внешнем слое; середину стройте из чистых функций, которые легко тестировать.
- Скрывайте представление приватными полями; компилятор (ошибка E0616) тогда сам обеспечивает низкое сопряжение.
- Просите только то, что нужно: `&[u32]` вместо `&Vec<Score>`; избегайте длинных цепочек вызовов через другие типы.
- Структура, поля которой делятся на два кластера, используемых разными методами, — вероятно, две структуры.
- Не разделяйте ради разделения: модули `utils`, слои-посредники и модули из одной функции стоят больше, чем дают.
