# Урок 18.8 — Партиционирование и согласованное хеширование

> **Этап 18 — Распределённые системы** · Урок 8 из 15 · ⏱ около 120 минут

## Что вы узнаете

- Зачем большие системы делят данные на партиции и как партиционирование работает вместе с репликацией.
- Два основных способа делить данные — по диапазону ключей и по хешу — и что такое горячая точка.
- Почему все узлы должны использовать одну и ту же стабильную хеш-функцию и почему хешер `HashMap` для этого не годится.
- Почему «хеш по модулю числа узлов» при добавлении узла перемещает почти все данные — с измерением на 100 000 ключей.
- Как согласованное хеширование с виртуальными узлами перемещает лишь около 1/N ключей — кольцо, построенное на `BTreeMap`.

## Новые слова

| Слово | Значение |
|---|---|
| **партиция** (partition) | Часть набора данных, которая хранится на одном узле (и его репликах). Её также называют **шардом** (shard). |
| **партиционирование** (partitioning) | Разделение данных на партиции, чтобы каждый узел хранил и обслуживал только их часть. Также называется **шардированием** (sharding). |
| **ключ партиционирования** (partition key) | Значение, которое решает, к какой партиции относится запись, например id пользователя. |
| **партиционирование по диапазону ключей** (key-range partitioning) | Каждая партиция владеет непрерывным диапазоном ключей, как тома энциклопедии (А–В, Г–Е, …). |
| **хеш-партиционирование** (hash partitioning) | Партиция выбирается по хешу ключа; это равномерно распределяет ключи, но разрушает их порядок. |
| **горячая точка** (hot spot) | Партиция, которая получает намного больше нагрузки, чем остальные. |
| **перебалансировка** (rebalancing) | Перемещение данных между узлами, когда узлы добавляют или убирают или когда нагрузка неравномерна. |
| **согласованное хеширование** (consistent hashing) | Способ распределять ключи по узлам на кольце хеш-значений, при котором добавление или удаление узла перемещает лишь малую долю ключей. |
| **виртуальный узел** (virtual node) | Одна из многих точек, которыми один настоящий узел владеет на кольце. Больше точек — равномернее доля. |
| **FNV** (Fowler–Noll–Vo) | Простая и быстрая некриптографическая хеш-функция, названная по фамилиям трёх авторов. |

## 1. Зачем делить данные?

Репликация (Урок 18.6) даёт каждой реплике **все** данные. Это не помогает, когда сами данные слишком велики для одной
машины или когда записей больше, чем способен обработать один лидер. Тогда мы **партиционируем**: делим данные так,
чтобы каждый узел отвечал только за часть.

Партиционирование и репликацию используют вместе. Каждая партиция реплицируется, поэтому кластер из шести машин может
держать три партиции по две реплики:

```text
             partition 1 (users a–h)   partition 2 (users i–p)   partition 3 (users q–z)
machine 1        leader
machine 2        follower                  leader
machine 3                                  follower                  leader
machine 4                                                            follower
...
```

Цель партиционирования — распределить **данные и нагрузку равномерно**. Если одна партиция получает большую часть
запросов, остальные машины простаивают, а одна перегружена. Всё решают два вопроса: к какой партиции относится ключ и
что происходит, когда мы добавляем машину?

## 2. Два способа делить: по диапазону или по хешу

| | Партиционирование по диапазону ключей | Хеш-партиционирование |
|---|---|---|
| Правило | партиция 1 владеет ключами от "a" до "h", партиция 2 — от "i" до "p", … | партиция = функция от hash(key) |
| Запросы по диапазону («все заказы мая») | быстрые: ключи лежат рядом в одной партиции | медленные: ключи разбросаны по всем партициям |
| Равномерность | только если границы выбраны удачно, и их приходится двигать по мере роста данных | автоматически, если хеш хороший |
| Типичная опасность | **горячие точки**: если ключ — метка времени, все новые записи идут в партицию «сегодня» | один очень популярный ключ всё равно попадает в одну партицию |

Горячая точка может появиться при любом способе. Если знаменитость с миллионами подписчиков — это один ключ, каждый
запрос к нему уходит в одну партицию при любой схеме. Тогда приложения делят такие ключи вручную, например добавляя к
ключу маленькое случайное число и читая все варианты.

Этот урок строит хеш-партиционирование, потому что его используют большинство хранилищ «ключ-значение», включая то,
которое вы будете реплицировать в Уроке 18.14.

## 3. Хеш, о котором договорились все узлы

Все узлы, клиенты и маршрутизаторы должны вычислять **одну и ту же** партицию для одного ключа — сегодня и после
обновления. Поэтому хеш-функция должна полностью определяться своим алгоритмом. Мы используем **FNV-1a**, которая
занимает три строки, и добавляем шаг **перемешивания**, потому что сама по себе FNV даёт похожие значения для похожих
ключей вроде `user:1` и `user:2`. Поместите это в `src/lib.rs`:

```rust
//! Partitioning and consistent hashing (Lesson 18.8).

/// The 64-bit FNV-1a hash. Its result is fixed by its definition, so every node and every
/// version of the program computes the same number for the same key.
pub fn fnv1a(bytes: &[u8]) -> u64 {
    let mut hash: u64 = 0xcbf2_9ce4_8422_2325;
    for &byte in bytes {
        hash ^= u64::from(byte);
        hash = hash.wrapping_mul(0x0100_0000_01b3);
    }
    hash
}

/// Mixes the bits of `x` (the "finalizer" of MurmurHash3), so that similar keys such as
/// "user:1" and "user:2" end up far apart.
pub fn mix(mut x: u64) -> u64 {
    x ^= x >> 33;
    x = x.wrapping_mul(0xff51_afd7_ed55_8ccd);
    x ^= x >> 33;
    x = x.wrapping_mul(0xc4ce_b9fe_1a85_ec53);
    x ^= x >> 33;
    x
}

/// The hash used for partitioning in this lesson.
pub fn key_hash(key: &str) -> u64 {
    mix(fnv1a(key.as_bytes()))
}

/// The simple way: node number = hash modulo the number of nodes.
pub fn mod_n(key: &str, nodes: u64) -> u64 {
    key_hash(key) % nodes
}
```

**Что происходит:**

1. FNV-1a начинает с фиксированного числа («offset basis») и для каждого байта применяет к нему XOR (исключающее «или»,
   `^`) и умножает на фиксированное простое число. `wrapping_mul` намеренно разрешает умножению переполниться, оставляя
   младшие 64 бита (Урок 12.2).
2. `mix` снова сдвигает и умножает, так что изменение одного бита на входе меняет примерно половину битов на выходе.
   Константы взяты из известного хеша MurmurHash3; понимать, почему работают именно эти числа, не нужно — важно лишь,
   что они фиксированы.
3. `mod_n` — очевидный способ выбрать одну из `nodes` партиций: остаток от деления хеша на число узлов.

> ⚠️ **Частая ошибка: использовать хешер `HashMap` для партиционирования.** `HashMap` использует `RandomState`, который
> выбирает новые случайные ключи в **каждом процессе**, чтобы защититься от *hash flooding* (атакующий отправляет много
> ключей с одинаковым хешем, чтобы замедлить таблицу). Два узла расходились бы в каждом ключе. Вот доказательство,
> `src/bin/random_state.rs`:

```rust
use std::collections::hash_map::RandomState;
use std::hash::BuildHasher;

fn main() {
    // The hasher that HashMap uses by default: its keys are chosen at random in every process.
    let hasher = RandomState::new();
    let partition = hasher.hash_one("user:1") % 4;
    println!("user:1 belongs to partition {partition}");
}
```

Пять запусков `cargo run --bin random_state` (у вас будет иначе):

```text
user:1 belongs to partition 3
user:1 belongs to partition 2
user:1 belongs to partition 2
user:1 belongs to partition 3
user:1 belongs to partition 2
```

`std::hash::DefaultHasher::new()` лучше (его ключи фиксированы), но в его документации сказано, что алгоритм может
меняться между выпусками Rust, поэтому два узла, собранные разными версиями компилятора, всё равно могут разойтись.

## 4. Хеш по модулю N и что происходит, когда N меняется

`hash % nodes` распределяет ключи равномерно. Проблемы начинаются, когда меняется число узлов. Посчитаем, сколько из
100 000 ключей переедет на другой узел, когда к четырём присоединится пятый, `src/bin/mod_n.rs`:

```rust
use p18_partitioning::mod_n;

fn main() {
    let keys: Vec<String> = (0..100_000).map(|i| format!("user:{i}")).collect();
    let moved = keys
        .iter()
        .filter(|key| mod_n(key, 4) != mod_n(key, 5))
        .count();
    println!(
        "hash mod N, from 4 to 5 nodes: {moved} of {} keys move",
        keys.len()
    );
}
```

`cargo run --bin mod_n`:

```text
hash mod N, from 4 to 5 nodes: 80091 of 100000 keys move
```

**80 %** данных нужно скопировать по сети, хотя новый узел должен забрать только 20 % (свою честную пятую часть).
Причина: `h % 4` и `h % 5` совпадают, только когда остатки случайно равны, а это примерно каждый пятый ключ. Во время
переезда кластер, которому хотелось **больше** мощности, занят копированием почти всего.

## 5. Согласованное хеширование: кольцо

Согласованное хеширование помещает и **узлы**, и **ключи** на одну окружность хеш-значений от 0 до 2⁶⁴ − 1, которая
замыкается сама на себя. Ключ принадлежит **первому узлу по часовой стрелке** от своей позиции:

```text
                 0 / 2^64
                    │
          n3 ●──────┼──────● n1        key k1 → walk clockwise → n1
            ╱       │       ╲          key k2 → walk clockwise → n2
           │    k1 ×│        │
  k3 ×     │        │        │         when n4 is added between n1 and n2,
           │        │   × k2 │         only keys between n1 and n4 change owner
            ╲       │       ╱          (they move from n2 to n4); nobody else moves
          n2 ●──────┼──────●
                    │     n4 (new)
```

Когда узел присоединяется, он забирает только ключи между своей позицией и предыдущим узлом: остальные ключи остаются
у своих владельцев. Но при одной точке на узел дуги между точками очень разной длины, поэтому одни узлы владеют
намного большим, чем другие. Решение — **виртуальные узлы**: каждый настоящий узел ставится на кольцо много раз, в
позиции `hash("n1#0")`, `hash("n1#1")` и так далее. Множество маленьких дуг усредняется.

`BTreeMap<u64, String>` из позиции на кольце в имя узла — идеальное кольцо: позиции в нём отсортированы, а
`range(hash..)` находит первую позицию не раньше ключа. Добавьте `use std::collections::BTreeMap;` в начало
`src/lib.rs`, а затем:

```rust
/// A consistent-hashing ring. Each node owns several points on a circle of u64 values.
#[derive(Default)]
pub struct Ring {
    points: BTreeMap<u64, String>,
    vnodes: u32,
}

impl Ring {
    pub fn new(vnodes: u32) -> Self {
        Ring {
            points: BTreeMap::new(),
            vnodes,
        }
    }

    pub fn add(&mut self, node: &str) {
        for i in 0..self.vnodes {
            let point = key_hash(&format!("{node}#{i}"));
            self.points.insert(point, node.to_string());
        }
    }

    pub fn remove(&mut self, node: &str) {
        self.points.retain(|_, owner| owner != node);
    }

    /// The owner of `key`: the first point at or after the key's hash, going around the circle.
    pub fn node_for(&self, key: &str) -> Option<&str> {
        let hash = key_hash(key);
        self.points
            .range(hash..)
            .next()
            .or_else(|| self.points.iter().next())
            .map(|(_, node)| node.as_str())
    }
}
```

**Что происходит:**

1. `add` вставляет `vnodes` точек для узла. `format!("{node}#{i}")` даёт каждой точке своё имя, поэтому их хеши
   разлетаются по всему кольцу.
2. `remove` удаляет все точки узла через `retain`, который оставляет только записи, для которых замыкание говорит `true`.
3. `node_for` хеширует ключ и спрашивает у отображения первую точку не раньше него. Если такой нет (ключ после
   последней точки), он переходит к первой точке окружности. Это и есть «обход по часовой стрелке» в две строки.

Теперь сравним одну точку на узел со ста точками на узел, `src/bin/ring.rs`:

```rust
use std::collections::BTreeMap;

use p18_partitioning::Ring;

/// How many of the keys each node owns.
fn load(ring: &Ring, keys: &[String]) -> BTreeMap<String, usize> {
    let mut load = BTreeMap::new();
    for key in keys {
        *load
            .entry(ring.node_for(key).unwrap().to_string())
            .or_insert(0) += 1;
    }
    load
}

fn main() {
    let keys: Vec<String> = (0..100_000).map(|i| format!("user:{i}")).collect();
    for vnodes in [1, 100] {
        let mut ring = Ring::new(vnodes);
        for node in ["n1", "n2", "n3", "n4"] {
            ring.add(node);
        }
        let owners: Vec<String> = keys
            .iter()
            .map(|k| ring.node_for(k).unwrap().to_string())
            .collect();
        println!(
            "{vnodes} point(s) per node, 4 nodes: {:?}",
            load(&ring, &keys)
        );

        ring.add("n5");
        let moved = keys
            .iter()
            .zip(&owners)
            .filter(|(key, old)| ring.node_for(key).unwrap() != old.as_str())
            .count();
        println!(
            "{vnodes} point(s) per node, 5 nodes: {:?}",
            load(&ring, &keys)
        );
        println!("keys moved: {moved}\n");
    }
}
```

`cargo run --bin ring`:

```text
1 point(s) per node, 4 nodes: {"n1": 62520, "n2": 4163, "n3": 9375, "n4": 23942}
1 point(s) per node, 5 nodes: {"n1": 3185, "n2": 4163, "n3": 9375, "n4": 23942, "n5": 59335}
keys moved: 59335

100 point(s) per node, 4 nodes: {"n1": 22608, "n2": 22804, "n3": 26474, "n4": 28114}
100 point(s) per node, 5 nodes: {"n1": 18901, "n2": 17019, "n3": 20875, "n4": 23017, "n5": 20188}
keys moved: 20188
```

**Что происходит:**

1. При одной точке на узел кольцо очень неравномерно: `n1` владеет 62 % ключей, а `n2` — всего 4 %. Когда приходит
   `n5`, его единственная точка случайно попадает внутрь огромной дуги `n1`, и он забирает 59 % всех ключей у одного
   `n1`. Правильно, но плохо сбалансировано.
2. При 100 точках на узел каждый узел владеет от 22 % до 28 %, а новый узел забирает **20 188** ключей — почти ровно
   свою пятую часть, понемногу у каждого старого узла.
3. Сравните с разделом 4: хеш по модулю N при том же изменении переместил 80 091 ключ.

> 🧪 **Тестирование:** самое важное свойство согласованного хеширования легко проверить: когда добавляется узел,
> каждый ключ либо остаётся на месте, либо переезжает на **новый** узел, но никогда не между двумя старыми. Упражнение 2
> пишет этот тест.

> ⚡ **Производительность:** `node_for` — один хеш и один поиск в `BTreeMap`, O(log P) для P точек на кольце: при
> 5 узлах × 100 точках это около 9 сравнений. Маршрутизация дешёвая даже для тысяч виртуальных узлов.

## 6. Маршрутизация и перебалансировка

Остаются два практических вопроса.

**Кто знает отображение?** Клиенту, которому нужен ключ `user:42`, нужно найти его узел. Три распространённых схемы:

| Схема | Как это работает |
|---|---|
| Отвечает любой узел | клиент спрашивает любой узел; тот пересылает запрос или говорит клиенту, куда идти |
| Слой маршрутизации | прокси (Урок 15.14) знает отображение и пересылает каждый запрос |
| Умный клиент | клиентская библиотека сама знает отображение и обращается сразу к нужному узлу |

Во всех трёх случаях само отображение нужно где-то надёжно хранить, и все стороны должны о нём договориться. Многие
системы держат его в маленькой службе координации на основе консенсуса (Уроки 18.9–18.11), например в etcd.

**Как перемещаются данные?** Когда кольцо меняется, новый владелец в фоне копирует затронутые ключи у старого, пока
старый продолжает их обслуживать, и отображение переключается только после завершения копирования. Перемещение данных
стоит пропускной способности сети и времени диска — именно поэтому так важно перемещать 20 %, а не 80 %.

> 🔒 **Безопасность:** если клиенты могут свободно выбирать ключи, атакующий может попробовать создать много ключей,
> попадающих в одну партицию, и перегрузить её. Хеш с ключом (с секретом, как у `RandomState`) это предотвращает — но
> тогда всем узлам нужен один и тот же секрет. Системы, принимающие ключи от недоверенных клиентов, обычно хешируют с
> фиксированным секретным ключом, общим для всего кластера.

## Частые ошибки

> ⚠️ **Частая ошибка: партиционировать по метке времени.** При партиционировании по диапазону поля «создано в» все
> новые записи идут в самую новую партицию: постоянная горячая точка. Поставьте в начало ключа другое значение
> (например, id пользователя) или используйте хеш-партиционирование.

> ⚠️ **Частая ошибка: слишком мало виртуальных узлов.** При одной точке на узел раздел 5 показал разделение 62 % / 4 %.
> Используйте от десятков до сотен точек на узел.

2. После добавления `n5` вызовите `ring.remove("n1")` и снова напечатайте нагрузку. Куда ушли ключи `n1`?
3. В `mod_n.rs` посчитайте перемещённые ключи при переходе с 4 на 8 узлов вместо 5. Почему это примерно половина?

## Упражнения

### Упражнение 1 — Сверить хеш с определением (легко)

У FNV-1a есть опубликованные контрольные значения: пустой вход даёт `0xcbf29ce484222325`, `"a"` даёт
`0xaf63dc4c8601ec8c`, а `"foobar"` даёт `0x85944171f73967e8`. Напишите модульный тест в `src/lib.rs`, который проверяет
все три. Почему такой тест важнее в распределённой системе, чем в одной программе?

<details>
<summary>Подсказка</summary>

Байтовые строковые литералы вроде `b"foobar"` имеют тип `&[u8; 6]`, который автоматически превращается в `&[u8]`.
Подчёркивания в числовых литералах (`0xcbf2_9ce4_...`) нужны только для читаемости.

</details>

<details>
<summary>Ответ</summary>

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn fnv1a_matches_the_published_test_values() {
        assert_eq!(fnv1a(b""), 0xcbf2_9ce4_8422_2325);
        assert_eq!(fnv1a(b"a"), 0xaf63_dc4c_8601_ec8c);
        assert_eq!(fnv1a(b"foobar"), 0x8594_4171_f739_67e8);
    }
}
```

`cargo test --lib`:

```text
test tests::fnv1a_matches_the_published_test_values ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Почему это работает: тест привязывает хеш к его определению. Если кто-то «улучшит» функцию, тест упадёт раньше, чем
изменение попадёт в продакшен, где узлы со старой и новой версией отправляли бы один и тот же ключ в разные партиции.

</details>

### Упражнение 2 — Между старыми узлами ничего не переезжает (средне)

Напишите интеграционный тест `tests/ring_moves.rs`: постройте кольцо из четырёх узлов по 100 точек, запомните владельцев
10 000 ключей, добавьте `n5` и проверьте, что каждый ключ либо сохранил владельца, либо переехал на `n5`. Затем удалите
`n5` и проверьте, что каждый ключ вернулся к исходному владельцу.

<details>
<summary>Подсказка</summary>

Храните владельцев как `Vec<String>` (владеющие строки), потому что потом кольцо меняется, а заимствованные результаты
`&str` этому помешали бы. `keys.iter().zip(&before)` проходит по ключам и старым владельцам вместе.

</details>

<details>
<summary>Ответ</summary>

```rust
use p18_partitioning::Ring;

#[test]
fn a_new_node_only_takes_keys_and_never_shuffles_the_others() {
    let mut ring = Ring::new(100);
    for node in ["n1", "n2", "n3", "n4"] {
        ring.add(node);
    }
    let keys: Vec<String> = (0..10_000).map(|i| format!("user:{i}")).collect();
    let before: Vec<String> = keys
        .iter()
        .map(|k| ring.node_for(k).unwrap().to_string())
        .collect();

    ring.add("n5");
    for (key, old) in keys.iter().zip(&before) {
        let new = ring.node_for(key).unwrap();
        assert!(new == old || new == "n5", "{key} moved from {old} to {new}");
    }

    ring.remove("n5");
    let back: Vec<String> = keys
        .iter()
        .map(|k| ring.node_for(k).unwrap().to_string())
        .collect();
    assert_eq!(back, before); // removing the node gives every key back to its old owner
}
```

`cargo test --test ring_moves`:

```text
test a_new_node_only_takes_keys_and_never_shuffles_the_others ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.02s
```

Почему это работает: добавление точек на кольцо может только укоротить дуги существующих точек; ключ, чей обход теперь
останавливается раньше, останавливается на точке нового узла. Удаление этих точек в точности восстанавливает старые
дуги.

</details>

### Упражнение 3 — Rendezvous-хеширование (сложно)

Rendezvous-хеширование (его также называют *highest random weight*, «наибольший случайный вес») вообще не нуждается в
кольце: для ключа вычислите оценку `hash(node + key)` для каждого узла, и ключом владеет узел с наибольшей оценкой.
Создайте `src/rendezvous.rs` (и `pub mod rendezvous;`) с `pub fn owner<'a>(key: &str, nodes: &[&'a str]) -> Option<&'a str>`.
Проверьте, что при добавлении пятого узла к четырём каждый переехавший ключ уходит на новый узел и что переезжает от
15 % до 25 % из 10 000 ключей.

<details>
<summary>Подсказка</summary>

`nodes.iter().copied().max_by_key(|node| key_hash(&format!("{node}/{key}")))`. Время жизни `'a` говорит, что
возвращаемое имя живёт столько же, сколько имена узлов в срезе, а не сколько ключ.

</details>

<details>
<summary>Ответ</summary>

```rust
//! Exercise 3: rendezvous hashing.

use crate::key_hash;

/// Rendezvous ("highest random weight") hashing: every node gets a score for the key,
/// and the node with the highest score owns it.
pub fn owner<'a>(key: &str, nodes: &[&'a str]) -> Option<&'a str> {
    nodes
        .iter()
        .copied()
        .max_by_key(|node| key_hash(&format!("{node}/{key}")))
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn a_new_node_takes_about_a_fifth_and_only_for_itself() {
        let keys: Vec<String> = (0..10_000).map(|i| format!("user:{i}")).collect();
        let four = ["n1", "n2", "n3", "n4"];
        let five = ["n1", "n2", "n3", "n4", "n5"];
        let mut moved = 0;
        for key in &keys {
            let before = owner(key, &four).unwrap();
            let after = owner(key, &five).unwrap();
            if before != after {
                assert_eq!(after, "n5", "{key} moved between old nodes");
                moved += 1;
            }
        }
        assert!((1500..2500).contains(&moved), "moved {moved}");
    }
}
```

`cargo test --lib`:

```text
test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.01s
```

Почему это работает: добавление узла ничего не меняет в оценках старых узлов, поэтому ключ меняет владельца, только если
оценка нового узла побила старый максимум, а это случается примерно для одного ключа из пяти. Цена: поиск владельца
стоит одного хеша на каждый узел, O(N), а не поиска по кольцу — нормально для десятков узлов, медленно для тысяч.

</details>

## Вопросы для самопроверки

1. Почему партиционирование и репликацию обычно используют вместе?

<details>
<summary>Ответ</summary>

Партиционирование распределяет данные и нагрузку по машинам; репликация сохраняет каждую партицию доступной и целой,
когда машина отказывает. У каждой партиции свои реплики (и часто свой лидер).

</details>

2. Вы партиционируете заказы по диапазону даты заказа. Какой проблемы вы ожидаете?

<details>
<summary>Ответ</summary>

Горячей точки: у всех новых заказов сегодняшняя дата, поэтому все записи идут в одну партицию, а остальные простаивают.

</details>

3. Почему хеш для партиционирования не должен использовать хешер `HashMap` по умолчанию?

<details>
<summary>Ответ</summary>

`RandomState` выбирает случайные ключи в каждом процессе, поэтому каждый узел вычислил бы для одного ключа свою партицию.
Хеш должен быть зафиксирован своим алгоритмом и одинаков на каждом узле и в каждой версии.

</details>

4. Кластер растёт с 10 до 11 узлов. Примерно сколько ключей переедет при хеше по модулю N и сколько при согласованном
   хешировании?

<details>
<summary>Ответ</summary>

При модуле N — почти все: свой узел сохраняет лишь примерно 1 ключ из 11, так что переезжает около 91 %. При
согласованном хешировании (и достаточном числе виртуальных узлов) — около 1/11, примерно 9 %, и все на новый узел.

</details>

5. Что исправляют виртуальные узлы?

<details>
<summary>Ответ</summary>

Неравные дуги кольца с одной точкой на узел. При многих точках на узел доля каждого узла усредняется и приближается к
1/N, а новый узел забирает понемногу у каждого старого, а не много у одного.

</details>

## Итоги

- Партиционирование (шардирование) делит данные так, чтобы каждый узел хранил и обслуживал только их часть; каждая
  партиция ещё и реплицируется.
- Партиционирование по диапазону ключей держит диапазоны вместе, но рискует горячими точками; хеш-партиционирование
  распределяет ключи равномерно, но теряет их порядок.
- Хеш для партиционирования должен быть стабильным и одинаковым везде: фиксированный алгоритм вроде FNV-1a с шагом
  перемешивания, но никогда не `RandomState`.
- `hash % N` при изменении N перемещает большинство ключей: 80 % при переходе с 4 на 5 узлов.
- Согласованное хеширование на кольце перемещает лишь около 1/N ключей, все на новый узел; виртуальные узлы
  выравнивают доли.
- Кто-то должен хранить отображение и договариваться о нём (часто это служба на основе консенсуса), а данные
  перемещаются в фоне.
