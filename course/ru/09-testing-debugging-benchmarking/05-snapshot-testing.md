# Урок 09.5 — Снапшот-тестирование

> **Этап 09 — Тестирование, отладка и бенчмарки** · Урок 5 из 14 · ⏱ около 2,5 часа (2 занятия)

## Что вы узнаете

- Что такое снапшот-тест и когда он лучше длинного `assert_eq!`.
- Как пользоваться крейтом `insta` и инструментом `cargo insta`: создавать, просматривать, принимать и отклонять снапшоты.
- Как делать снапшоты текста, вывода `Debug` и JSON и как скрывать значения, которые меняются при каждом запуске (редактирование значений, redactions).
- Как снапшот-тесты ведут себя в CI (Continuous Integration, непрерывная интеграция) и какие привычки делают их надёжными.

## Новые слова

| Слово | Значение |
|---|---|
| **снапшот** (snapshot) | Сохранённая копия вывода вашего кода, лежащая в файле рядом с кодом, с которой сравниваются последующие запуски. |
| **снапшот-тест** (snapshot test) | Тест, который производит какой-то вывод и сравнивает его с сохранённым снапшотом. Различие роняет тест. |
| **`insta`** | Крейт для снапшот-тестирования в Rust (макросы вроде `assert_snapshot!`). |
| **`cargo-insta`** | Инструмент командной строки, используемый как `cargo insta …`, для просмотра и принятия снапшотов, которые создаёт `insta`. |
| **просмотр** (review) | Изучение разницы между старым и новым снапшотом и решение, задумано ли изменение. |
| **принять / отклонить** (accept / reject) | Принять: сделать новый вывод сохранённым снапшотом. Отклонить: выбросить его. |
| **встроенный снапшот** (inline snapshot) | Снапшот, записанный внутри файла с кодом Rust, прямо в тесте, а не в отдельном файле. |
| **редактирование значений** (redaction) | Замена значения, которое меняется при каждом запуске (идентификатор, время), на фиксированную заглушку перед сравнением. |
| **сериализация** (serialization) | Превращение значения в текст или байты в известном формате, например JSON (JavaScript Object Notation, текстовый формат для структурированных данных). |
| **serde** | Крейт, дающий `#[derive(Serialize)]`, которым значения Rust превращают в JSON и другие форматы (Урок 05.11). |
| **переменная окружения** (environment variable) | Именованная настройка, которую система передаёт программе, например `CI=true`. |

## 1. Проблема: длинные ожидаемые значения

Допустим, функция рисует счёт в виде таблицы. Чтобы протестировать её через `assert_eq!`, нужно написать весь ожидаемый текст в
тесте:

```rust
assert_eq!(
    render_invoice(&invoice),
    "Invoice #1042 for Ada Lovelace\n--------------------------------\nPens        2 x   1.50 =    3.00\n…"
);
```

Это неудобно: длинная строка, полная `\n`, пробелы приходится считать вручную, а любое небольшое изменение формата (более широкая
колонка) заставляет перепечатывать все ожидаемые тексты во всех тестах.

**Снапшот-тестирование** решает это. В первый раз вы запускаете код, и библиотека *сохраняет его вывод в файл*. Вы один раз смотрите на файл, и если он
выглядит правильно, принимаете его. Дальше тест сравнивает вывод с сохранённым файлом и падает при любом различии. Это как
сфотографировать правильный ответ и позже сверяться с фотографией.

Идея лучше всего работает, когда вывод большой, структурированный, легко читается человеком и стабилен: отрисованный текст, форматированные отчёты, вывод `Debug`
структуры данных, JSON. Для одного числа или ответа «да/нет» она не подходит: там `assert_eq!` короче и
яснее.

[dev-dependencies]

`serde` нужен коду (он выводит `Serialize`). `insta` нужен только тестам. Его фича `json` добавляет `assert_json_snapshot!`, а
`redactions` добавляет скрытие значений (раздел 6).

Установите инструмент просмотра (один раз; это отдельная программа, как `cargo-nextest`):

```bash
cargo install --locked cargo-insta
cargo insta --version
```

```text
cargo-insta 1.49.0
```

Если инструмента нет, `cargo insta` печатает `error: no such command: `insta``.

## 3. Тестируемый код

Замените `src/lib.rs` (тесты добавим через минуту):

```rust
use serde::Serialize;

#[derive(Debug, Clone, Serialize)]
pub struct Item {
    pub name: String,
    pub quantity: u32,
    pub unit_cents: u64,
}

#[derive(Debug, Clone, Serialize)]
pub struct Invoice {
    pub number: u32,
    pub customer: String,
    pub items: Vec<Item>,
}

fn money(cents: u64) -> String {
    format!("{}.{:02}", cents / 100, cents % 100)
}

/// Draws the invoice as a text table, 32 characters wide.
pub fn render_invoice(invoice: &Invoice) -> String {
    let line = "-".repeat(32);
    let mut out = format!(
        "Invoice #{} for {}\n{line}\n",
        invoice.number, invoice.customer
    );
    let mut total = 0;
    for item in &invoice.items {
        let cost = u64::from(item.quantity) * item.unit_cents;
        total += cost;
        out.push_str(&format!(
            "{:<10} {:>2} x {:>6} = {:>7}\n",
            item.name,
            item.quantity,
            money(item.unit_cents),
            money(cost)
        ));
    }
    out.push_str(&format!("{line}\n{:<25}{:>7}\n", "Total", money(total)));
    out
}

/// A receipt for a paid invoice. The `id` is different every time it is created.
#[derive(Debug, Serialize)]
pub struct Receipt {
    pub id: u128,
    pub paid_cents: u64,
    pub invoice: Invoice,
}

pub fn make_receipt(invoice: Invoice) -> Receipt {
    let now = std::time::SystemTime::now()
        .duration_since(std::time::UNIX_EPOCH)
        .expect("the clock is before 1970")
        .as_nanos();
    let paid_cents = invoice
        .items
        .iter()
        .map(|item| u64::from(item.quantity) * item.unit_cents)
        .sum();
    Receipt {
        id: now,
        paid_cents,
        invoice,
    }
}
```

**Что происходит:**

1. `Invoice` и `Item` хранят данные. `#[derive(Debug)]` позволяет печатать их через `{:?}`, а `#[derive(Serialize)]` позволяет `serde` превращать
   их в JSON.
2. `render_invoice` строит таблицу с параметрами ширины: `{:<10}` дополняет имя справа до 10 символов, `{:>2}`
   дополняет количество слева до 2 и так далее. Последняя строка дополняет `Total` до 25 символов, а сумму — до 7.
3. `make_receipt` делает `Receipt` с `id`, равным текущему времени в наносекундах. Оно разное при каждом запуске, и это
   будет важно в разделе 6.

## 4. Первый снапшот-тест

Добавьте модуль тестов в конец `src/lib.rs`:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    fn sample_invoice() -> Invoice {
        Invoice {
            number: 1042,
            customer: "Ada Lovelace".to_string(),
            items: vec![
                Item {
                    name: "Pens".to_string(),
                    quantity: 2,
                    unit_cents: 150,
                },
                Item {
                    name: "Notebook".to_string(),
                    quantity: 1,
                    unit_cents: 420,
                },
            ],
        }
    }

    #[test]
    fn invoice_text() {
        insta::assert_snapshot!(render_invoice(&sample_invoice()));
    }
}
```

Запустите `cargo test`. Тест **падает**, потому что сохранённого снапшота ещё нет:

**Что происходит:**

1. `insta::assert_snapshot!(value)` превращает значение в текст и ищет файл, названный по тесту:
   `src/snapshots/<крейт>__<модуль>__<имя теста>.snap`. Его нет.
2. `insta` записывает вывод в новый файл `….snap.new` («кандидат») и роняет тест. Новый снапшот должен быть *одобрен человеком*,
   прежде чем он засчитывается; иначе тест мог бы проходить только потому, что его никогда не проверяли.
3. Отчёт показывает новый вывод с `+` перед каждой строкой. Это ваш момент, чтобы **прочитать его**: тот ли это счёт, который вы хотите? Колонки
   выровнены, итог 7.20 (2 × 1.50 + 4.20). Всё верно.

Примите его. Проще всего — инструментом просмотра (`cargo insta review` показывает каждое изменение и спрашивает: принять (`a`), отклонить (`r`) или пропустить (`s`); для всех сразу
есть `cargo insta accept` и `cargo insta reject`):

```bash
cargo insta accept
```

```text
insta review finished
accepted:
  src/lib.rs (invoice_text.snap)
```

Теперь посмотрите на созданный файл:

```bash
cat src/snapshots/p09_snapshots__tests__invoice_text.snap
```

```text
---
source: src/lib.rs
expression: render_invoice(&sample_invoice())
---
Invoice #1042 for Ada Lovelace
--------------------------------
Pens        2 x   1.50 =    3.00
Notebook    1 x   4.20 =    4.20
--------------------------------
Total                       7.20
```

Часть между строками `---` — метаданные (какой файл и какое выражение это породили); ниже — сам снапшот. **Этот файл принадлежит Git.**
Он часть спецификации вашей программы. Запустите `cargo test` снова: тест проходит.

## 5. Изменение вывода

Через неделю кто-то меняет код: `"Total"` становится `"TOTAL"` в `render_invoice`. Запустите `cargo test`:

```text
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ Snapshot Summary ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Snapshot file: src/snapshots/p09_snapshots__tests__invoice_text.snap
Snapshot: invoice_text
Source: src/lib.rs:94
────────────────────────────────────────────────────────────────────────────────
Expression: render_invoice(&sample_invoice())
────────────────────────────────────────────────────────────────────────────────
-old snapshot
+new results
────────────┬───────────────────────────────────────────────────────────────────
    2     2 │ --------------------------------
    3     3 │ Pens        2 x   1.50 =    3.00
    4     4 │ Notebook    1 x   4.20 =    4.20
    5     5 │ --------------------------------
    6       │-Total                       7.20
          6 │+TOTAL                       7.20
────────────┴───────────────────────────────────────────────────────────────────
To update snapshots run `cargo insta review` or set `INSTA_UPDATE=always`
```

**Что это значит:** отчёт — это **diff**. Два столбца чисел — номера строк в старом и в новом тексте; `-` отмечает
строку из старого снапшота, а `+` — из нового вывода. Изменилась только одна строка, и вы видите её сразу, не
считая символов.

Теперь вы решаете:

- **Изменение задумано** (мы действительно хотели заглавные буквы): выполните `cargo insta accept`. Файл `.snap` меняется, и
  изменение появляется в вашем Git diff, где его видит ревьюер.
- **Изменение — ошибка**: исправьте код, и тест снова проходит.

Это и есть **рабочий процесс**; команды такие:

| Команда | Что делает |
|---|---|
| `cargo test` | запускает тесты; новые или изменённые снапшоты записываются в файлы `.snap.new`, а тесты падают |
| `cargo insta test` | запускает тесты и собирает все ожидающие снапшоты; с `--review` сразу после открывает просмотр, с `--accept` принимает всё |
| `cargo insta review` | проходит по ожидающим снапшотам по одному: принять, отклонить или пропустить |
| `cargo insta accept` / `reject` | принимает / отклоняет все ожидающие снапшоты |
| `cargo insta pending-snapshots` | перечисляет снапшоты, ожидающие решения |

> ⚠️ **Частая ошибка:** принимать не читая. `cargo insta accept` — быстрая команда, и запускать её каждый раз заманчиво. Но
> снапшот, который вы не прочитали, ничего не защищает: он с радостью «одобрит» ошибку. **Читайте каждый diff** так, как читаете код-ревью.
> Git diff файлов `.snap` — второй шанс заметить ошибку.

> 📏 **Соглашение:** коммитьте файлы `.snap`. Не коммитьте файлы `.snap.new` и `.pending-snap`: они
> временные. Добавьте их в `.gitignore`:
> ```text
> *.snap.new
> .*.pending-snap
> ```

## 6. Другие виды снапшотов

### Вывод `Debug`

`assert_debug_snapshot!` сохраняет форму `{:#?}` (красивый `Debug`) любого значения, реализующего `Debug`. Это идеально для структуры данных, когда нужно видеть все
её поля. Добавьте в `mod tests`:

```rust
    #[test]
    fn invoice_debug_view() {
        insta::assert_debug_snapshot!(sample_invoice());
    }
```

После `cargo insta test --accept` файл `…invoice_debug_view.snap` содержит:

```text
---
source: src/lib.rs
expression: sample_invoice()
---
Invoice {
    number: 1042,
    customer: "Ada Lovelace",
    items: [
        Item {
            name: "Pens",
            quantity: 2,
            unit_cents: 150,
        },
        Item {
            name: "Notebook",
            quantity: 1,
            unit_cents: 420,
        },
    ],
}
```

### JSON и редактирование значений

`assert_json_snapshot!` сохраняет значение как JSON (нужны `Serialize` и фича `json`). Но у нашего `Receipt` есть `id`, равный текущему времени. Без
помощи тест падал бы при каждом запуске:

```rust
    #[test]
    fn receipt_as_json() {
        let receipt = make_receipt(sample_invoice());
        insta::assert_json_snapshot!(receipt);
    }
```

После принятия первого запуска второй запуск показывает такой diff:

```text
    1     1 │ {
    2       │-  "id": 1794984885511749000,
          2 │+  "id": 1794984893895514000,
    3     3 │   "paid_cents": 720,
```

`id` каждый раз другой. **Редактирование значений** (redaction) заменяет значение по пути фиксированным текстом *до* сравнения. Запишите его вторым аргументом:

```rust
    #[test]
    fn receipt_as_json() {
        let receipt = make_receipt(sample_invoice());
        insta::assert_json_snapshot!(receipt, { ".id" => "[id]" });
    }
```

После принятия сохранённый снапшот содержит `"id": "[id]"`, и тест стабилен:

```text
{
  "id": "[id]",
  "paid_cents": 720,
  "invoice": {
    "number": 1042,
    "customer": "Ada Lovelace",
    "items": [
      {
        "name": "Pens",
        "quantity": 2,
        "unit_cents": 150
      },
      {
        "name": "Notebook",
        "quantity": 1,
        "unit_cents": 420
      }
    ]
  }
}
```

**Что происходит:** путь `".id"` выбирает поле `id` значения верхнего уровня. Синтаксис селектора включает `.field`, `[0]` для элемента списка,
`[]` для *каждого* элемента списка (как в `".items[].unit_cents"`) и `.*` для каждого поля. Редактирование значений — стандартный ответ на идентификаторы, время,
случайные значения и всё прочее, чем вы не управляете. (А ещё лучше, когда возможно, передать в код фиксированные часы, как в
Уроке 09.3; редактирование значений используйте, когда это невозможно.)

Если забыть фичу `json`, макроса не будет:

```text
error[E0433]: cannot find `assert_json_snapshot` in `insta`
   --> src/lib.rs:105:16
    |
105 |         insta::assert_json_snapshot!(receipt, { ".id" => "[id]" });
    |                ^^^^^^^^^^^^^^^^^^^^ could not find `assert_json_snapshot` in `insta`
```

### Встроенные снапшоты

Снапшот может жить в самом тесте. Напишите `@""` вторым аргументом, запустите `cargo insta test --accept`, и `cargo-insta` **отредактирует ваш
исходный файл** и вставит текст:

```rust
    #[test]
    fn an_empty_invoice_inline() {
        let invoice = Invoice {
            number: 1,
            customer: "Nobody".to_string(),
            items: vec![],
        };
        insta::assert_snapshot!(render_invoice(&invoice), @"
        Invoice #1 for Nobody
        --------------------------------
        --------------------------------
        Total                       0.00
        ");
    }
```

Встроенные снапшоты хороши для коротких выводов, потому что ожидаемое значение находится прямо рядом с тестом. Длинным выводам место в файлах.

## 7. Снапшоты в CI и в команде

На вашем компьютере новый снапшот записывается в файл `.snap.new`, чтобы вы могли его просмотреть. На CI-сервере никто не может нажать `accept`, а запись
файлов лишь скрыла бы проблему. `insta` это знает: когда задана переменная окружения `CI` (GitHub Actions, GitLab CI и большинство других
её задают), он **ничего не записывает**, и тест просто падает. Поведением можно управлять через `INSTA_UPDATE`:

| `INSTA_UPDATE` | Поведение |
|---|---|
| `auto` (по умолчанию) | `no`, если задана `CI`, иначе `new` |
| `new` | записывать файлы `.snap.new`, не трогать принятые снапшоты |
| `no` | ничего не записывать; тест просто падает |
| `always` | сразу перезаписывать сохранённые снапшоты (используйте, только если потом прочитаете Git diff) |

Попробуйте: снова замените `"Total"` на `"TOTAL"` и запустите `CI=true cargo test`. Тест падает, а в `src/snapshots/` нет файла `.snap.new`.
Запустите `INSTA_UPDATE=always cargo test`, и файл снапшота перезапишется, так что изменение будет видно в `git diff`.

Привычки, которые поддерживают набор снапшотов здоровым:

- **Просматривайте diff файлов `.snap` в каждом pull request**, как код. Ревьюер, увидев `+TOTAL`, может спросить «это задумано?».
- **Держите снапшоты маленькими и стабильными.** Снапшот на 2000 строк невозможно прочитать, поэтому изменения проскальзывают. Делайте снапшот той части, что важна.
- **Убирайте шум перед сохранением:** идентификаторы, время, случайные значения, абсолютные пути (редактированием значений или передачей фиксированных значений).
- **Для единичных фактов используйте обычные проверки.** `assert_eq!(total, 720)` яснее, чем снапшот одного числа.
- **Хорошо называйте тесты.** Имя теста входит в имя файла. Переименование теста создаёт новый снапшот и оставляет старый файл.

> 🔒 **Безопасность:** снапшот — это файл в вашем репозитории, и его может прочитать каждый. Не делайте снапшоты ответов, содержащих настоящие токены,
> пароли или персональные данные, либо используйте для этих полей редактирование значений.

## Частые ошибки

**1. Принимать всё подряд.** См. предупреждение в разделе 5.

**2. Вывод, который меняется между запусками.** Время, случайные идентификаторы, абсолютные пути, порядок элементов в `HashMap`. Тест падает случайно. Используйте
редактирование значений, фиксированные часы или сортируйте данные перед снапшотом.

**3. Забытые файлы `.snap` в Git.** На вашем компьютере тест проходит; в CI он падает с «нет снапшота», потому что файл так и не был
закоммичен. Выполните `git status` и поищите `src/snapshots/`.

**4. Снапшот не того.** Снапшот вывода `Debug` типа, поля которого часто меняются, делает шумный тест, падающий после каждого безвредного
изменения. Делайте снапшот *результата, важного пользователю*.

**5. Отсутствие фичи.** `assert_json_snapshot!` требует фичи `json`, а редактирование значений — `redactions` (раздел 6). Ошибка компилятора
`cannot find assert_json_snapshot in insta` значит, что фичи нет в `Cargo.toml`.

## Попробуйте сами

1. Создайте пакет, `Cargo.toml`, `src/lib.rs` и первый тест. Установите `cargo-insta`. Запустите `cargo test`, прочитайте отчёт, выполните `cargo insta accept`.
2. Замените `"Total"` на `"TOTAL"`, запустите `cargo test` и прочитайте diff. Выполните `cargo insta reject`, затем верните `"Total"`.
3. Добавьте `invoice_debug_view`, `receipt_as_json` (сначала без редактирования значений, дважды, чтобы увидеть падение, затем с ним) и `an_empty_invoice_inline`
   (с `@""`). Примите через `cargo insta test --accept`.
4. Запустите `CI=true cargo test` после изменения и убедитесь, что ничего не записывается.
5. Добавьте в `.gitignore` строки `*.snap.new` и `.*.pending-snap`. Выполните `cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test`,
   затем закоммитьте вместе со снапшотами: `git add code/p09-snapshots && git commit -m "Add p09-snapshots: snapshot tests with insta"`.

## Упражнения

### Упражнение 1 — Читайте, прежде чем принимать (легко)

Добавьте тест `a_long_item_name` с таким счётом: номер 7, клиент `"Grace Hopper"`, один товар `"Coffee beans"` (12 букв), количество 3, цена
1299. Примите снапшот только после прочтения. Что не так с картинкой?

<details>
<summary>Подсказка</summary>

Используйте `insta::assert_snapshot!(render_invoice(&invoice))`. Сравните длину строки товара с линией из дефисов.

</details>

<details>
<summary>Ответ</summary>

```rust
    #[test]
    fn a_long_item_name() {
        let invoice = Invoice {
            number: 7,
            customer: "Grace Hopper".to_string(),
            items: vec![Item {
                name: "Coffee beans".to_string(),
                quantity: 3,
                unit_cents: 1299,
            }],
        };
        insta::assert_snapshot!(render_invoice(&invoice));
    }
```

Новый снапшот такой:

```text
Invoice #7 for Grace Hopper
--------------------------------
Coffee beans  3 x  12.99 =   38.97
--------------------------------
Total                      38.97
```

Строка товара на два символа длиннее линии из дефисов: имя шире 10 символов своей колонки и сдвигает
остальное вправо. Написанный вручную `assert_eq!`, скорее всего, был бы составлен по выводу *кода* и скрыл бы
это; чтение снапшота делает это видимым. (Принимать ли его? Пока нет: следующее упражнение исправит код.)

</details>

### Упражнение 2 — Исправьте код, просмотрите diff (средне)

Исправьте `render_invoice` так, чтобы имя длиннее 10 символов обрезалось до 10. Запустите тесты, прочитайте diff
`a_long_item_name` и примите его, только если он показывает ровно то, что вы задумали.

<details>
<summary>Подсказка</summary>

`item.name.chars().take(10).collect::<String>()` даёт первые 10 символов. Используйте это значение в `format!` вместо `item.name`.

</details>

<details>
<summary>Ответ</summary>

В цикле `render_invoice`:

```rust
        let name: String = item.name.chars().take(10).collect();
        out.push_str(&format!(
            "{:<10} {:>2} x {:>6} = {:>7}\n",
            name,
            item.quantity,
            money(item.unit_cents),
            money(cost)
        ));
```

Diff показывает ровно одну изменённую строку, а другие тесты не меняются:

```text
    3       │-Coffee beans  3 x  12.99 =   38.97
          3 │+Coffee bea  3 x  12.99 =   38.97
```

Почему это работает: теперь строка имеет ту же ширину, что и дефисы. (`chars().take(10)` считает символы, а не байты, поэтому обрезка никогда не разрезает букву
посередине.) Примите изменение через `cargo insta accept`, и новый снапшот попадёт в Git вместе с исправлением.

</details>

### Упражнение 3 — Спрячьте цены (сложно)

Напишите тест `prices_hidden_with_a_redaction`, который сохраняет `sample_invoice()` как JSON, но с каждым `unit_cents`, заменённым на `"[price]"`.

<details>
<summary>Подсказка</summary>

Селектор для поля внутри каждого элемента списка `items` — `".items[].unit_cents"`.

</details>

<details>
<summary>Ответ</summary>

```rust
    #[test]
    fn prices_hidden_with_a_redaction() {
        insta::assert_json_snapshot!(sample_invoice(), {
            ".items[].unit_cents" => "[price]",
        });
    }
```

Сохранённый снапшот содержит `"unit_cents": "[price]"` в обоих товарах:

```text
{
  "number": 1042,
  "customer": "Ada Lovelace",
  "items": [
    {
      "name": "Pens",
      "quantity": 2,
      "unit_cents": "[price]"
    },
    {
      "name": "Notebook",
      "quantity": 1,
      "unit_cents": "[price]"
    }
  ]
}
```

Почему это работает: `[]` в селекторе значит «каждый элемент списка», поэтому одно редактирование значений покрывает все товары.

</details>

## Вопросы для самопроверки

1. Что происходит при первом запуске снапшот-теста, когда файла снапшота нет?

<details>
<summary>Ответ</summary>

`insta` записывает вывод в файл `.snap.new`, и тест падает. Человек должен просмотреть и принять снапшот, прежде чем он засчитывается.

</details>

2. Чем `cargo insta accept` отличается от `cargo insta reject`?

<details>
<summary>Ответ</summary>

`accept` делает новый вывод сохранённым снапшотом (файл `.snap`); `reject` удаляет ожидающие файлы `.snap.new` и сохраняет старый снапшот.

</details>

3. Почему тест с `assert_json_snapshot!(receipt)` падает при каждом запуске и как это исправить?

<details>
<summary>Ответ</summary>

Поле `id` содержит текущее время, поэтому вывод каждый раз разный. Используйте редактирование значений, например `{ ".id" => "[id]" }`, или сделайте так, чтобы код принимал фиксированные часы.

</details>

4. Что делает `insta` на CI-сервере и почему?

<details>
<summary>Ответ</summary>

Когда задана `CI`, он не записывает файлы `.snap.new` и просто роняет тест, потому что там никто не может просмотреть и принять снапшот.

</details>

5. Какие файлы нужно коммитить в Git, а какие нет?

<details>
<summary>Ответ</summary>

Коммитьте файлы `.snap` (они часть спецификации). Не коммитьте файлы `.snap.new` и `.pending-snap`: они временные.

</details>

6. Когда `assert_eq!` лучше снапшота?

<details>
<summary>Ответ</summary>

Для одного небольшого факта (число, ответ «да/нет», короткая строка). Снапшот нужен для большого структурированного стабильного вывода, который удобно читать целиком.

</details>

## Итоги

- Снапшот-тест сравнивает вывод вашего кода с сохранённым файлом. Различие роняет тест; человек просматривает и принимает задуманные изменения.
- С `insta`: `assert_snapshot!` (текст), `assert_debug_snapshot!` (`Debug`), `assert_json_snapshot!` (JSON, фича `json`), встроенные снапшоты через `@""`.
- Рабочий процесс: `cargo test` (или `cargo insta test`) → прочитать diff → `cargo insta accept` или исправить код. Всегда читайте diff.
- Редактирование значений (`{ ".id" => "[id]" }`) скрывает значения, меняющиеся при каждом запуске; фиксированные часы лучше, когда вы можете ими управлять.
- Коммитьте файлы `.snap`; игнорируйте `*.snap.new` и `.*.pending-snap`. В CI (задана `CI`) `insta` ничего не пишет и роняет тест; `INSTA_UPDATE` это меняет.
- Используйте снапшоты для большого, читаемого, стабильного вывода; для единичных фактов используйте `assert_eq!`.
