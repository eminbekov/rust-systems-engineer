## Новые слова

| Слово | Значение |
|---|---|
| **рефакторинг** (refactoring) | Изменение внутренней структуры кода, чтобы его было легче понимать и менять, **без изменения того, что он делает** для пользователей. |
| **наблюдаемое поведение** (observable behaviour) | Всё, что видят вызывающие: возвращаемые значения, вывод, ошибки, побочные эффекты. Рефакторинг сохраняет его. |
| **характеризационный тест** (characterization test, golden test) | Тест, который записывает, что код делает *сейчас*, включая странные результаты, чтобы вы заметили, когда изменение их меняет. |
| **страховочная сетка** (safety net) | Набор быстрых тестов, которые за секунды сообщают, сломало ли что-то изменение. |
| **код-ревью** (code review) | Чтение изменения, сделанного другим человеком, до его слияния, чтобы найти ошибки и проблемы проектирования и поделиться знаниями. |
| **придирка** (nit) | Очень мелкий комментарий ревью о вкусе или стиле («nit: переименуйте это»). Автор может его проигнорировать. |
| **IDE** (Integrated Development Environment, интегрированная среда разработки) | Программа для написания кода со встроенными поиском, рефакторингом и отладкой. RustRover — одна из них. |

## 1. Что такое рефакторинг

**Рефакторинг** — это улучшение *структуры* кода при сохранении его *поведения*. Вы не добавляете возможности и не исправляете
ошибки; вы делаете код легче для чтения, тестирования и изменения. Его определяют два правила:

1. **Поведение остаётся прежним.** Если вывод изменился, это не рефакторинг, а изменение.
2. **Вы работаете малыми шагами**, и после каждого шага код компилируется, а тесты проходят.

Представьте две шляпы. В шляпе *возможности* вы добавляете поведение и пишете новые тесты. В шляпе *рефакторинга* вы меняете структуру и
не трогаете тесты. Носите одну шляпу за раз и делайте коммит между шляпами. Коммит, смешивающий обе, невозможно толком проверить на ревью, а когда появляется ошибка, нельзя понять, какое изменение её вызвало.

Главное предложение этого урока: **безопасно рефакторить можно, только если что-то быстро сообщает, что поведение не изменилось.** Это «что-то» — набор тестов.

## 2. Страховочная сетка: характеризационные тесты

А если у кода нет тестов — что бывает обычно? Вы пишете тесты, описывающие то, что он делает *сегодня*. Они называются
**характеризационными тестами**. Правила:

- Не решайте, что код *должен* делать. Запустите его, посмотрите на результат и запишите этот результат в тест.
- Включайте странные случаи, даже если результат выглядит неверным (округление, пустой ввод, неизвестный вид). От этого может кто-то зависеть. Если вы считаете это ошибкой, зафиксируйте её, закончите рефакторинг и исправьте ошибку отдельным коммитом.
- Покройте каждую ветку. Ветка без случая — это ветка, которую рефакторинг может молча сломать.

Вот наш пациент — функция, печатающая одну строку счёта. Поместите её в `code/p08-invoice/src/lib.rs`:

```rust
pub fn invoice_line(qty: u32, unit_cents: u32, kind: &str, vip: bool) -> String {
    let mut total = qty * unit_cents;
    if kind == "book" {
        if qty >= 10 {
            total = total * 85 / 100;
        } else {
            total = total * 95 / 100;
        }
    } else if kind == "food" {
        total = total + total * 7 / 100;
    } else {
        if qty >= 10 {
            total = total * 90 / 100;
        }
    }
    if vip {
        total = total - total * 5 / 100;
    }
    let dollars = total / 100;
    let cents = total % 100;
    if cents < 10 {
        format!("{} x {} = {}.0{}", qty, kind, dollars, cents)
    } else {
        format!("{} x {} = {}.{}", qty, kind, dollars, cents)
    }
}
```

**Что происходит:** функция умножает количество на цену, применяет правила по виду товара (книги: скидка 5%, от десяти штук — 15%; еда: налог 7%; остальное: скидка 10%
от десяти штук), даёт VIP-клиентам (Very Important Person, особо важным) скидку 5% и форматирует деньги двумя способами. Все суммы — целые центы, деление округляет вниз. «Запахи»: магические числа,
строковый `kind`, вложенные `if`, дублирование форматирования.

Чтобы написать характеризационный тест, запустите функцию на нескольких входах и скопируйте результаты. Выберите хотя бы по одному входу для каждой ветки. Добавьте в конец файла:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn pins_down_current_behaviour() {
        let cases = [
            // (qty, unit_cents, kind, vip, expected text)
            (1, 1000, "book", false, "1 x book = 9.50"),
            (10, 1000, "book", false, "10 x book = 85.00"),
            (3, 199, "food", false, "3 x food = 6.38"),
            (3, 199, "food", true, "3 x food = 6.07"),
            (10, 250, "toy", false, "10 x toy = 22.50"),
            (2, 250, "toy", true, "2 x toy = 4.75"),
            (1, 1, "pen", false, "1 x pen = 0.01"),
            (1, 1005, "pen", false, "1 x pen = 10.05"),
            (7, 333, "gift", true, "7 x gift = 22.15"),
        ];
        for (qty, unit, kind, vip, expected) in cases {
            assert_eq!(invoice_line(qty, unit, kind, vip), expected);
        }
    }
}
```

**Что происходит:**

1. Каждый кортеж — один вход и результат, который мы увидели, запустив исходный код. Например, 3 штуки еды по 199 центов: 597, плюс налог 7% (`597 * 7 / 100 = 41`) — 638, что печатается как `6.38`.
2. `1 x pen = 0.01` и `10.05` покрывают обе ветки форматирования (центы меньше 10 и нет).
3. Тест — *таблица*; чтобы добавить случай, вы добавляете строку (Урок 05.6).

`cargo test` проходит на нетронутом коде:

```text
running 1 test
test tests::pins_down_current_behaviour ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Сделайте коммит: `git add . && git commit -m "test(p08): characterization tests for invoice_line"`. Страховочная сетка на месте.

> 🧪 **Тестирование:** для программы, которая печатает текст, характеризационный тест часто сравнивает весь вывод с сохранённым «золотым» файлом. Это техника проекта в Уроке 08.16.
> Этап 09 учит снапшот-тестированию, которое её автоматизирует.

## 3. Цикл: изменить, проверить, закоммитить

Теперь рефакторим шагами. После каждого шага запускайте `cargo test`. Если тест красный, отмените последний шаг (`git restore .`), а не отлаживайте большое изменение.

**Шаг 1: уберите дублирование форматирования.** Обе ветки печатают одно и то же, кроме нуля. Формат `{:02}` дополняет число нулями до двух цифр. Вынесите форматирование денег в функцию:

```rust
fn format_money(cents_total: u32) -> String {
    format!("{}.{:02}", cents_total / 100, cents_total % 100)
}
```

и замените последний `if cents < 10 { ... } else { ... }` в `invoice_line` одной строкой: `format!("{} x {} = {}", qty, kind, format_money(total))`. Зелёный. Коммит: `refactor(p08): extract format_money`.

**Шаг 2: «безобидное» упрощение, которое таким не является.** Строка для VIP `total = total - total * 5 / 100;` выглядит как неуклюжая запись `total * 95 / 100`. Попробуйте:

```text
---- tests::pins_down_current_behaviour stdout ----

thread 'tests::pins_down_current_behaviour' (4805567) panicked at src/lib.rs:45:13:
assertion `left == right` failed
  left: "3 x food = 6.06"
 right: "3 x food = 6.07"
```

(Номер строки и номер потока на вашем компьютере будут другими.)

Две формулы равны в школьной арифметике, но не с целыми числами, которые округляют вниз: `638 - 638 * 5 / 100` — это `638 - 31 = 607`, а `638 * 95 / 100` — `606`. Ревьюер, скорее всего,
одобрил бы такое «упрощение». Тест поймал его за секунду. Отмените. (Если бизнес-правило действительно «95%, округлить вниз», то это *изменение поведения*: коммит в шляпе возможности со своим тестом.)

**Шаг 3: назовите числа.** Замените `10`, `7`, `5`, `85`, `95` и `90` константами, имена которых говорят, что они значат. Зелёный.

**Шаг 4: замените строку на enum.** Сравнения `kind == "book"` — «запах» строковой типизации. Создайте `enum Kind { Book, Food, Other }` с функцией `parse`, которая сопоставляет `"book"` и `"food"`, а всё остальное отправляет в `Other`
(именно так старый код вёл себя с неизвестным видом, и тесты это фиксируют). Публичная функция сохраняет сигнатуру, поэтому тесты не меняются. Замените цепочку `if` на `match` по `(kind, bulk)`. Зелёный.

**Шаг 5: вынесите арифметику.** `x * p / 100` встречается много раз. Назовите это `percent_of`. Зелёный.

Вот код после пяти шагов. Модуль тестов не изменился и остаётся в конце файла:

```rust
const BULK_QUANTITY: u32 = 10;
const FOOD_TAX_PERCENT: u32 = 7;
const VIP_DISCOUNT_PERCENT: u32 = 5;
const BOOK_BULK_PAY_PERCENT: u32 = 85;
const BOOK_PAY_PERCENT: u32 = 95;
const OTHER_BULK_PAY_PERCENT: u32 = 90;

#[derive(Clone, Copy)]
enum Kind {
    Book,
    Food,
    Other,
}

impl Kind {
    fn parse(text: &str) -> Kind {
        match text {
            "book" => Kind::Book,
            "food" => Kind::Food,
            _ => Kind::Other,
        }
    }
}

/// `percent` percent of `amount`, rounded down.
fn percent_of(amount: u32, percent: u32) -> u32 {
    amount * percent / 100
}

fn after_kind_rules(total: u32, qty: u32, kind: Kind) -> u32 {
    let bulk = qty >= BULK_QUANTITY;
    match (kind, bulk) {
        (Kind::Book, true) => percent_of(total, BOOK_BULK_PAY_PERCENT),
        (Kind::Book, false) => percent_of(total, BOOK_PAY_PERCENT),
        (Kind::Food, _) => total + percent_of(total, FOOD_TAX_PERCENT),
        (Kind::Other, true) => percent_of(total, OTHER_BULK_PAY_PERCENT),
        (Kind::Other, false) => total,
    }
}

fn format_money(cents_total: u32) -> String {
    format!("{}.{:02}", cents_total / 100, cents_total % 100)
}

pub fn invoice_line(qty: u32, unit_cents: u32, kind: &str, vip: bool) -> String {
    let mut total = after_kind_rules(qty * unit_cents, qty, Kind::parse(kind));
    if vip {
        total -= percent_of(total, VIP_DISCOUNT_PERCENT);
    }
    format!("{qty} x {kind} = {}", format_money(total))
}
```

**Что происходит:**

1. `invoice_line` теперь состоит из четырёх строк, читающихся как бизнес-правило: посчитать сумму, применить правила вида товара, дать скидку VIP, отформатировать.
2. Правила видов лежат в одном `match` без ветки `_`, так что новый вид (`Kind::Toy`) заставит компилятор указать на единственное место, которое нужно обновить.
3. `(Kind::Food, _)` показывает то, что старый код делал неявно: у еды нет скидки за объём.
4. Округление по-прежнему «делить в последнюю очередь, округлять вниз», в точности как раньше: тесты это доказывают. `cargo test` и `cargo clippy -- -D warnings` зелёные.

Результат длиннее оригинала, и это нормально. Рефакторинг не про меньшее число строк; он про то, чтобы следующее изменение было лёгким. Хороший вопрос: «Что мне придётся тронуть, чтобы добавить новый вид товара или изменить скидку
VIP?» Раньше вы читали все 25 строк; теперь вы трогаете одну.

## 4. Каталог полезных рефакторингов

| Рефакторинг | Когда применять | В Rust |
|---|---|---|
| **Переименование** (Rename) | Имя скрывает смысл | IDE переименовывает везде, включая другие файлы и тесты. |
| **Выделение функции** (Extract function) | У блока есть имя в вашей голове («посчитать цену VIP») | *Extract Function* в IDE определяет параметры и тип результата. |
| **Встраивание функции** (Inline function) | Функция лишь прячет тривиальное выражение | Обратное выделению. |
| **Введение константы** | Магическое число | `const NAME: u32 = ...;` |
| **Замена строки/флага на enum** | Строковое значение или булев аргумент | `enum` + `match` без ветки `_`. |
| **Введение объекта-параметра** | Одни и те же 3 аргумента ходят вместе | Небольшая `struct`; позже строитель (Урок 08.6). |
| **Замена вложенного `if` ранним возвратом** | Пирамиды из скобок | `return`, `?` и `let ... else { return ...; }` |
| **Замена цикла цепочкой итераторов** | Цикл, который строит значение | `map`, `filter`, `sum`, `collect` (Урок 05.5). Только если читается лучше. |
| **Перенос функции в тип, которому принадлежат данные** | Функция в основном использует поля другого типа (feature envy) | Сделайте её методом в `impl` этого типа. |
| **Разделение модуля / выделение крейта** | Файл или модуль выполняет несколько работ | Новый файл с `mod`; крейт — только для настоящей границы (Урок 08.12). |
| **Замена `clone` заимствованием** | Клоны добавлены ради borrow checker | Замените параметры `String` на `&str` (Урок 08.10). |

Два помощника, специфичных для Rust, заслуживают отдельного упоминания.

**Опирайтесь на компилятор.** Проверка типов Rust — очень хорошая страховочная сетка для *структурных* изменений. Хотите заменить поле `u32` на newtype `Cents`? Измените определение и идите по ошибкам компиляции одну за другой; когда код снова компилируется, все использования
обновлены. То же работает при добавлении варианта в `enum`, который сопоставляется без `_`: компилятор перечисляет каждый `match`, который нужно обновить. Поэтому мы избегаем веток `_ =>` для `enum`-ов, которыми владеем.

**Используйте инструменты.** В меню *Refactor* RustRover есть *Rename*, *Extract Function*, *Inline*, *Change Signature*, *Move* и другие, с предпросмотром изменений. Сочетание клавиш каждого пункта указано в меню; *Rename* — `Shift+F6`.
Рефакторинги, сделанные инструментом, обычно безопасны, но тесты вы всё равно запускаете. А `cargo clippy --fix` (Урок 08.11) применяет механические.

## 5. Когда не рефакторить

- **Тестов нет, и написать их нельзя.** Сначала напишите характеризационные тесты или оставьте код в покое.
- **Код никогда не меняется.** Некрасивая функция, стабильная годами, ничего не стоит; не трогайте её ради красоты.
- **Дедлайн завтра.** Рефакторинг в одном изменении со срочным исправлением делает изменение рискованным. Сначала исправьте; рефакторьте в следующем изменении.
- **Вы хотите переписать всё.** У большого переписывания нет страховочной сетки, и оно теряет забытые знания, скрытые в старом коде (те самые «странные» случаи). Улучшайте шаг за шагом.
- **Нет «запаха» с проблемой** (Урок 08.10). «Я бы написал иначе» — не причина.

## 6. Код-ревью

**Код-ревью** — это когда другой человек читает ваше изменение до его слияния. Урок 01.9 показал процесс pull request. Здесь — образ мышления.

### 6.1 Зачем ревью

Ревью находит ошибки, но другие его плюсы так же важны: код остаётся понятным как минимум двоим, команда узнаёт приёмы друг друга, и уровень кода растёт. Никто не пишет идеальный код в одиночку.

### 6.2 Если вы автор

- **Делайте изменение небольшим**: одна идея, в идеале не больше пары сотен строк. Никто не может по-настоящему проверить на ревью 2000 строк.
- **Объясните в описании**, что изменилось и *почему*, и как вы это проверили (шаблон What / Why / How / Testing из Урока 01.9).
- **Сначала просмотрите собственный diff.** Вы найдёте забытые отладочные выводы и лишние файлы.
- **Запустите контроль качества** (`cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`) до того, как просить ревью. Человек не должен сообщать вам о пропущенном пробеле.
- **Разделяйте рефакторинг и изменение поведения** на разные коммиты или pull request.

### 6.3 Если вы ревьюер

Читайте в таком порядке. Более ранние пункты потом исправлять дороже всего:

1. **Проектирование.** Относится ли изменение сюда? Соблюдает ли оно слои и границы (Урок 08.14)? Возможно ли решение проще?
2. **Корректность.** Граничные случаи: пустой ввод, ноль, очень большие числа, ошибки. Что происходит при сбое?
3. **Тесты.** Протестировано ли новое поведение, включая случаи сбоя? Упал бы тест, если бы код был неверным?
4. **Читаемость.** Можно ли понять код без автора? Имена, размер функций, комментарии, объясняющие *почему*.
5. **Стиль.** В последнюю очередь и только то, что не проверяет ни один инструмент. Форматирование и Clippy — дело машины.

Чек-лист, специфичный для Rust, чтобы держать рядом:

| На что смотреть | Вопрос |
|---|---|
| `unwrap()` / `expect()` | Может ли это упасть из-за ввода извне? Тогда это должен быть `Result`. |
| `clone()` | Он нужен, или сигнатура без причины принимает владеемое значение? |
| `pub`-элементы, публичные поля | Действительно ли каждый — часть API (Application Programming Interface, программный интерфейс)? Не может ли он быть приватным или `pub(crate)`? |
| Новая зависимость в `Cargo.toml` | Нужна ли она, поддерживается ли, правильна ли лицензия (Этап 10)? |
| `unsafe` | Есть ли комментарий `// SAFETY:` и верны ли рассуждения (Этап 06, Этап 10)? |
| Обработка ошибок | Типизированы ли ошибки и информативны ли они? Не глотается ли ошибка через `let _ =`? |
| Публичные функции | Документированы? Разделы `# Errors` и `# Panics`? Пример? |
| Числа | Переполнение? Приведения через `as`? Деньги в `f64`? |

### 6.4 Как писать комментарий

- **Комментируйте код, а не человека.** «Эта функция может паниковать на пустом списке» лучше, чем «вы забыли про пустой список».
- **Говорите почему и предлагайте путь.** «`&Vec<f64>` заставляет вызывающих владеть `Vec`; `&[f64]` принимает больше.»
- **Помечайте вес**, чтобы автор знал, что обязательно. Типичные метки: `blocking:` (изменить до слияния), `suggestion:` (хорошая идея; на ваше усмотрение), `question:` (я не понимаю, объясните), `nit:` (вкус; можно игнорировать).
- **Хвалите хорошее.** Короткое «хороший тест» — тоже информация.
- **Задавайте вопрос, если не уверены.** Возможно, вы не увидели причину.

### 6.5 Если вы получаете комментарии

Не обороняйтесь; поймите. Если не согласны, объясните свои доводы фактами (тест, измерение, ссылка). Если обсуждение идёт дольше двух кругов, поговорите с человеком. Когда ревьюер прав, измените код; когда правы оба, запишите причину в комментарии к коду, чтобы следующий читатель не спрашивал снова.

## Частые ошибки

1. **Рефакторинг без тестов.** Вы надеетесь, что ничего не сломалось. Сначала напишите характеризационные тесты.
2. **Гигантский шаг.** Десять изменений в одном коммите, и одно из них сломало тест. Делайте шаги по несколько минут и коммитьте часто.
3. **Смешивание рефакторинга с исправлением ошибки или новой возможностью.** Отдельные коммиты.
4. **«Исправление» странного результата в характеризационном тесте.** Тест фиксирует то, что есть; меняйте ожидаемое значение только в осознанном отдельном изменении поведения.
5. **Ревью только стиля.** Стиль делает машина. Люди смотрят на проектирование, корректность и тесты.
6. **Комментарий ревью «это плохо».** Скажите, что не так, почему и что бы сделали вы.

## Упражнения

### Упражнение 1 — Напишите страховочную сетку (средне)

Функция `fn shipping(weight_grams: u32, express: bool) -> u32` возвращает 500 для веса меньше 1000 граммов, 900 для веса меньше 5000 и 1500 в остальных случаях; `express` удваивает цену. Вы знаете только
это описание. Напишите тест в духе характеризационного, с таблицей, которая покрывает каждую ветку **и** границы (999, 1000, 4999, 5000).

<details>
<summary>Подсказка</summary>

Ошибки с `<` и `<=` живут на границах. Для каждой границы проверьте число чуть ниже и число на границе. Включите `express = true` минимум в двух случаях.

</details>

<details>
<summary>Ответ</summary>

```rust
pub fn shipping(weight_grams: u32, express: bool) -> u32 {
    let base = if weight_grams < 1000 {
        500
    } else if weight_grams < 5000 {
        900
    } else {
        1500
    };
    if express { base * 2 } else { base }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn covers_every_branch_and_border() {
        let cases = [
            // (weight, express, expected)
            (0, false, 500),
            (999, false, 500),
            (1000, false, 900),
            (4999, false, 900),
            (5000, false, 1500),
            (999, true, 1000),
            (5000, true, 3000),
        ];
        for (weight, express, expected) in cases {
            assert_eq!(
                shipping(weight, express),
                expected,
                "weight {weight}, express {express}"
            );
        }
    }
}
```

Почему это работает: каждая ступень и каждая граница есть в таблице, так что замена `<` на `<=` или цены сделала бы тест красным. Своё сообщение после `expected` говорит, какой случай упал.

</details>

### Упражнение 2 — Рефакторинг под защитой тестов (средне)

Используя таблицу из Упражнения 1, разделите `shipping` на три части: именованные константы для границ и цен, функцию `base_price(weight_grams: u32) -> u32` и функцию `shipping`, применяющую `express`. Покажите, что
тот же тест по-прежнему проходит.

<details>
<summary>Подсказка</summary>

Скопируйте цепочку `if` в `base_price`, заменяйте числа константами по одному и запускайте тест после каждого переноса.

</details>

<details>
<summary>Ответ</summary>

```rust
const LIGHT_LIMIT_GRAMS: u32 = 1_000;
const MEDIUM_LIMIT_GRAMS: u32 = 5_000;
const LIGHT_PRICE: u32 = 500;
const MEDIUM_PRICE: u32 = 900;
const HEAVY_PRICE: u32 = 1_500;
const EXPRESS_FACTOR: u32 = 2;

fn base_price(weight_grams: u32) -> u32 {
    if weight_grams < LIGHT_LIMIT_GRAMS {
        LIGHT_PRICE
    } else if weight_grams < MEDIUM_LIMIT_GRAMS {
        MEDIUM_PRICE
    } else {
        HEAVY_PRICE
    }
}

pub fn shipping(weight_grams: u32, express: bool) -> u32 {
    let base = base_price(weight_grams);
    if express { base * EXPRESS_FACTOR } else { base }
}
```

Модуль `tests` из Упражнения 1 не меняется и проходит. (Параметр `express: bool` сам по себе «запах», Урок 08.10; замена его на `enum` меняет сигнатуру, так что таблицу в тесте вы обновите отдельным шагом.)

</details>

### Упражнение 3 — Проведите ревью изменения (сложно)

Коллега открывает pull request с этим кодом. Напишите минимум пять комментариев ревью, каждый с меткой (`blocking:`, `suggestion:`, `question:` или `nit:`).

```rust
pub fn load_prices(path: &str) -> Vec<f64> {
    let text = std::fs::read_to_string(path).unwrap();
    let mut prices = Vec::new();
    for line in text.lines().clone() {
        let p: f64 = line.parse().unwrap();
        prices.push(p);
    }
    prices
}

pub fn average(prices: &Vec<f64>) -> f64 {
    let mut sum = 0.0;
    for i in 0..prices.len() { sum += prices[i]; }
    sum / prices.len() as f64
}
```

<details>
<summary>Подсказка</summary>

Пройдите по чек-листу Rust из раздела 6.3 строка за строкой. Спросите также, что возвращает `average(&vec![])` и должны ли деньги быть числами с плавающей точкой. В PR (pull request) нет тестов.

</details>

<details>
<summary>Ответ</summary>

Возможные комментарии:

1. `blocking:` `read_to_string(path).unwrap()` и `line.parse().unwrap()` аварийно завершают программу при отсутствии файла или плохой строке, а ввод приходит извне. Верните `Result` (например, `io::Result<Vec<_>>`) и сообщите вызывающему, какая строка плоха.
2. `blocking:` `average` пустого списка делит на ноль и возвращает `NaN` (проверено: `average(&vec![])` печатает `NaN`). Верните `Option<_>` или задокументируйте и протестируйте поведение.
3. `blocking:` нет тестов. Добавьте тесты для пустого списка, для обычного списка и для плохой строки.
4. `suggestion:` `&Vec<f64>` должно быть `&[f64]`, а `path: &str` может быть `&Path`; Clippy сообщает о первом (`ptr_arg`) и о цикле по индексу (`needless_range_loop`). Используйте `prices.iter().sum::<f64>()`.
5. `suggestion:` цены — это деньги; `f64` накапливает ошибки округления. Храните целые центы в целочисленном типе.
6. `nit:` `text.lines().clone()` без причины клонирует итератор; пройдите циклом по `text.lines()`.
7. `nit:` у публичных функций нет doc-комментариев (`# Errors`).
8. `question:` задумано ли, что пустые строки — ошибка? (`"".parse::<f64>()` завершается ошибкой.)

Для сравнения, исправленная `average` — это `pub fn average(prices: &[u64]) -> Option<u64>` с `let count = u64::try_from(prices.len()).ok()?; prices.iter().sum::<u64>().checked_div(count)`; тесты
`assert_eq!(average(&[]), None)` и `assert_eq!(average(&[100, 201]), Some(150))` проходят.

</details>

## Вопросы для самопроверки

1. Что определяет рефакторинг и что им *не* является?

<details>
<summary>Ответ</summary>

Изменение структуры кода при сохранении его наблюдаемого поведения. Добавление возможности, исправление ошибки или изменение вывода рефакторингом не является.

</details>

2. Что такое характеризационный тест и зачем записывать странные результаты?

<details>
<summary>Ответ</summary>

Тест, фиксирующий то, что код делает сейчас. Странные результаты записывают, потому что от них может кто-то зависеть и потому что рефакторинг не должен менять поведение; предполагаемая ошибка исправляется позже отдельным изменением.

</details>

3. Почему замена `total - total * 5 / 100` на `total * 95 / 100` провалила тест?

<details>
<summary>Ответ</summary>

Целочисленное деление округляет вниз. `638 - 31` — это 607, а `638 * 95 / 100` — 606, так что для целых чисел эти выражения различны. Показать это может только тест с реальными значениями.

</details>

4. В каком порядке ревьюер смотрит на изменение?

<details>
<summary>Ответ</summary>

Сначала проектирование, затем корректность, тесты, читаемость, а стиль — в последнюю очередь (и только то, что не проверяют инструменты).

</details>

5. О чём говорят автору метки `blocking:` и `nit:`?

<details>
<summary>Ответ</summary>

`blocking:` нужно изменить до слияния. `nit:` — мелочь вкуса, которую автор может проигнорировать.

</details>

## Итоги

- **Рефакторинг** меняет структуру, а не поведение, малыми шагами, и после каждого шага тесты зелёные. Носите одну шляпу за раз: рефакторинг или новое поведение, в отдельных коммитах.
- Нет тестов? Сначала напишите **характеризационные тесты**: запустите код, запишите, что он делает (включая странные результаты), покройте каждую ветку и границу.
- Даже «безобидное» упрощение может изменить целочисленное округление; тест ловит это за секунды.
- Полезные рефакторинги: переименование, выделение функции, введение константы, замена строки/флага на `enum`, объект-параметр, ранний возврат, перенос в тип-владелец. Опирайтесь на компилятор и пользуйтесь IDE.
- Не рефакторьте код, который никто не меняет, код без страховочной сетки и не делайте этого посреди срочного исправления.
- При **ревью** сначала смотрите на проектирование, корректность и тесты; форматирование и lint-ы оставьте инструментам. Пишите комментарии о коде, давайте причины и помечайте вес (`blocking:`, `suggestion:`, `question:`, `nit:`).
