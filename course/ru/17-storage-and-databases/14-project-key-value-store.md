# Урок 17.14 — Проект: собственное хранилище «ключ-значение»

> **Этап 17 — Как устроены хранилища и базы данных** · Урок 14 из 15 · ⏱ около 15 часов (8 занятий)

## Что вы узнаете

- Как объединить идеи этого этапа в один движок хранения: надёжный журнал, индекс, компакцию и восстановление.
- Как сделать многошаговое изменение (компакцию) устойчивым к сбоям с единственной точкой фиксации — файлом `MANIFEST`.
- Как доказать устойчивость к сбоям тестами: сбой на каждом байте, сбой посреди компакции и тест на модели против
  `BTreeMap`.
- Как измерить свой движок через `criterion` и объяснить числа.

У этого урока нет полного решения. Он даёт контракт, вехи, небольшие подсказки и точные команды, показывающие, что веха
пройдена. Рассчитывайте на несколько занятий; время выше — только на чтение плана.

## Новые слова

| Слово | Значение |
|---|---|
| **движок хранения** (storage engine) | Часть базы данных, которая хранит и находит байты на диске: записи, индексы, журналы, компакция, восстановление. |
| **`MANIFEST`** | Маленький файл, который называет файлы данных, составляющие текущее состояние хранилища. Его атомарная замена — точка фиксации компакции. |
| **поколение** (generation) | Число, которое растёт каждый раз, когда компакция создаёт новые файлы данных; оно входит в их имена (`data-000002.log`). |
| **надгробие** (tombstone) | Запись «этот ключ удалён». Она должна жить, пока могут читаться более старые записи этого ключа. |
| **тест на модели** (model-based test) | Тест, который выполняет случайные операции над вашим хранилищем **и** над простой, очевидно правильной моделью (здесь `BTreeMap`) и проверяет, что ответы всегда совпадают. |
| **приёмочный тест** (acceptance test) | Команда с ожидаемым выводом, которая доказывает, что веха пройдена («Готово, когда»). |
| **усиление записи** (write amplification) | Сколько байтов движок записывает на диск на каждый байт, записанный пользователем. Компакция его увеличивает. |

## Проект

### Что вы создадите

```text
  p17-kv put / get / delete / compact / stats        (CLI, src/main.rs)
             |
             v
  +----------------------- Store (src/lib.rs) ------------------------+
  |  index in RAM: key -> where the newest record is                  |
  |                                                                   |
  |  append-only data file  data-<generation>.log   (CRC per record)  |
  |  MANIFEST: which data file(s) are current                         |
  +-------------------------------------------------------------------+
             |
             v
     directory given by --dir (default ./data)
```

Хранилище «ключ-значение» для командной строки, данные которого переживают перезапуски и сбои. Каждый `put` и `delete`
надёжно сохранён до того, как команда напечатает ответ. `compact` выбрасывает устаревшие записи, и сбой посреди неё
никогда не теряет данные.

Вы выбираете **один** из двух вариантов устройства. Оба удовлетворяют одному контракту:

| | Вариант A: журнал + хеш-индекс (рекомендуется) | Вариант B: LSM-дерево (LSM — Log-Structured Merge, слияние структурированных журналов) |
|---|---|---|
| Запись | дописать запись в файл данных, `sync_data` | дописать в WAL (write-ahead log, журнал упреждающей записи), `sync_data`, вставить в memtable |
| Индекс | `HashMap<ключ, (смещение, длина)>` в RAM (Урок 17.5) | memtable + отсортированные SSTable, от новых к старым (Урок 17.7) |
| Компакция | переписать живые записи в новый файл данных | слить SSTable в одну, выбросив перекрытые записи и надгробия (Урок 17.8) |
| Точка фиксации компакции | `MANIFEST` называет новый файл | `MANIFEST` перечисляет новые SSTable |

Вариант A короче. Вариант B учит большему и поддерживает сканирование диапазонов как дополнительную цель. Запишите в
README свой выбор и причину.

### Контракт

**Командная строка** (`clap` derive). Каждая команда принимает `--dir <DIR>` (по умолчанию `data`); если каталога нет,
он создаётся.

| Команда | Печатает в stdout | Код возврата |
|---|---|---|
| `put <KEY> <VALUE>` | `OK` | 0 |
| `get <KEY>` | значение | 0; если ключа нет: `not found` в **stderr**, код 1 |
| `delete <KEY>` | `deleted` | 0; если ключа нет: `not found` в stderr, код 1 |
| `compact` | `compacted: <байты до> -> <байты после> bytes` | 0 |
| `stats` | `keys: <число живых ключей>` и `disk bytes: <байты всех файлов данных>` двумя строками | 0 |
| любая ошибка (ввод-вывод, неверный ввод, испорченные данные) | `error: <сообщение>` в stderr | 2 |

**Библиотека** (`src/lib.rs`), чтобы тесты и бенчмарки могли пользоваться хранилищем без CLI (только сигнатуры; тела —
ваша работа):

```rust
pub struct Store { /* your fields */ }
pub struct Stats { pub keys: usize, pub disk_bytes: u64 }
pub enum Error { Io(std::io::Error), EmptyKey, TooLarge, Corrupt(String) }

impl Store {
    pub fn open(dir: &Path) -> Result<Store, Error>;
    pub fn put(&mut self, key: &[u8], value: &[u8]) -> Result<(), Error>;
    pub fn get(&self, key: &[u8]) -> Result<Option<Vec<u8>>, Error>;
    pub fn delete(&mut self, key: &[u8]) -> Result<bool, Error>; // false: the key did not exist
    pub fn compact(&mut self) -> Result<(), Error>;
    pub fn stats(&self) -> Stats;
}
```

`Error` реализует `std::fmt::Display` и `std::error::Error`. (Варианту B может понадобиться `&mut self` для `get`; это
разрешено.)

**Правила:**

1. Ключи — от 1 до 1024 байтов, значения — от 0 до 1 048 576 байтов (1 МиБ, один мебибайт). Пустой ключ — `Error::EmptyKey`, всё,
   что больше, — `Error::TooLarge`.
2. **Надёжность:** когда `put` или `delete` возвращает `Ok`, изменение лежит в постоянном хранилище (был вызван
   `sync_data`).
3. **Целостность:** у каждой записи на диске есть CRC-32 (Cyclic Redundancy Check, циклический избыточный код, 32 бита). Длины, прочитанные с диска, проверяются по пределам из
   правила 1 до того, как выделяется какой-либо буфер.
4. **Восстановление:** `open` проигрывает текущие данные, а разорванная запись в конце самого нового файла отрезается
   (как в Уроках 17.4 и 17.10). Плохая запись в любом другом месте — `Error::Corrupt`: тот файл когда-то был целым,
   значит, повреждение настоящее.
5. **Атомарная компакция:** сбой в любой момент `compact` оставляет хранилище либо точно таким, как до, либо точно
   таким, как после. `open` удаляет оставшиеся файлы, которые `MANIFEST` не называет.
6. Удаление отсутствующего ключа ничего не пишет.

**Тесты**, которые должны существовать (имена — часть контракта, чтобы «Готово, когда» мог на них ссылаться):

| Тест | Что он доказывает |
|---|---|
| `torn_tail_at_every_byte_is_cut_off` | после сбоя на любом байте последней записи `open` сохраняет все прежние данные, а файл кончается после последней целой записи |
| `crash_during_compaction_keeps_old_or_new_state` | остановка компакции после каждого её шага и повторное открытие дают те же ответы, что и до неё |
| `matches_btreemap_model` | случайные последовательности `put` / `delete` / `compact` / повторного открытия дают те же ответы, что `BTreeMap` |
| `put_then_get_in_a_new_process` (в `tests/cli.rs`) | CLI действительно сохраняет данные между процессами |
| `missing_key_exits_with_1` (в `tests/cli.rs`) | код возврата и stderr из контракта |

### Пошаговый план

#### M1 — Надёжный журнал с индексом и CLI

**Цель:** `put`, `get`, `delete` и `stats` работают между отдельными запусками программы.

**Указания:** начните со своего `HashLog` из Урока 17.5 или хранилища с WAL из Урока 17.4, но передавайте в `open`
каталог, а не файл. Пока что в каталоге лежит один файл данных `data-000001.log`; `MANIFEST` добавит M3. Используйте
формат записи из Урока 17.3 с меткой «запись/удаление». Вызывайте `sync_data` после каждого дописывания. В `main`
разберите аргументы через `clap`, вызовите библиотеку, напечатайте ровно текст контракта и верните
`std::process::ExitCode`. Напишите два теста CLI с `assert_cmd`.

<details>
<summary>Подсказка</summary>

`fn main() -> ExitCode` со вспомогательной `fn run(cli: Cli) -> Result<ExitCode, Error>` держит обработку ошибок в
одном месте: `main` сопоставляет результат, при `Err` печатает `error: {e}` и возвращает `ExitCode::from(2)`. Для
отсутствующего ключа сама `run` печатает `not found` через `eprintln!` и возвращает `Ok(ExitCode::from(1))`.

</details>

**Готово, когда:**

```bash
cargo run -q -- --dir demo put apple red
cargo run -q -- --dir demo put kiwi green
cargo run -q -- --dir demo get apple
cargo run -q -- --dir demo get mango; echo "exit code: $?"
cargo run -q -- --dir demo delete kiwi
cargo run -q -- --dir demo get kiwi; echo "exit code: $?"
cargo run -q -- --dir demo stats
cargo run -q -- --dir demo put '' x; echo "exit code: $?"
```

```text
OK
OK
red
not found
exit code: 1
deleted
not found
exit code: 1
keys: 1
disk bytes: 60
error: the key must not be empty
exit code: 2
```

Число байтов на диске зависит от вашего формата записи (60 даёт 13-байтовый заголовок); всё остальное должно совпадать.
`cargo test --test cli` проходит оба теста CLI. Коммит: `M1: durable log, index and CLI`.

#### M2 — Устойчивость журнала к сбоям

**Цель:** сбой посреди записи никогда не портит прежние данные, а испорченной записи никогда не доверяют.

**Указания:** пусть `open` останавливается на первой записи, которая не полна или имеет неверный CRC, обрезает там
файл через `set_len` и синхронизирует его. Прежде чем читать ключ и значение записи, проверьте длины по пределам
(правило 3): случайная 4-байтовая длина в повреждённом файле иначе могла бы запросить выделение 4 ГиБ (гибибайт). Напишите
`torn_tail_at_every_byte_is_cut_off`: зафиксируйте одно значение, затем для каждого `cut` из `0..record.len()`
дописывайте первые `cut` байтов второй записи, открывайте заново и проверяйте первое значение и длину файла (та же идея,
что в Уроке 17.10).

<details>
<summary>Подсказка</summary>

Тесту нужны байты записи без вызова `put`. Сделайте свой кодировщик `pub(crate) fn encode(...)` в библиотеке, чтобы
модульные тесты того же крейта могли его вызывать. `std::fs::metadata(path)?.len()` даёт длину файла.

</details>

**Готово, когда:**

```bash
cargo test torn_tail
```

```text
running 1 test
test tests::torn_tail_at_every_byte_is_cut_off ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 2 filtered out; finished in 0.07s
```

(Число отфильтрованных тестов зависит от того, сколько других тестов у вас уже есть.) Коммит: `M2: torn-tail recovery`.

#### M3 — Компакция с `MANIFEST`

**Цель:** `compact` убирает устаревшие записи и удалённые ключи, а сбой во время компакции безвреден.

**Указания:** у компакции несколько шагов, и здесь работает приём из Урока 17.10: сделайте точкой фиксации ровно
**один** шаг. Для варианта A:

```text
1. write all live records to data-<generation+1>.log, sync_all       (crash here: old MANIFEST, new file ignored)
2. write MANIFEST.tmp naming generation+1, sync_all                    (crash here: still the old state)
3. rename MANIFEST.tmp -> MANIFEST, sync the directory   <- COMMIT POINT
4. delete the old data file, sync the directory                         (crash here: new state, a leftover file)
```

`open` читает `MANIFEST` (если его нет, создаёт его для поколения 1), открывает только названный в нём файл и удаляет
все остальные файлы `data-*.log` и `*.tmp`: это остатки сбоя до или после точки фиксации. Без `MANIFEST` сбой между
шагами 3 и 4 оставил бы два файла данных, и ключ, удалённый до компакции, мог бы вернуться из старого файла. Для
варианта B `MANIFEST` перечисляет SSTable, а компакция сначала пишет слитые SSTable. Напишите
`crash_during_compaction_keeps_old_or_new_state`.

<details>
<summary>Подсказка</summary>

Чтобы «упасть» в тесте, не убивая процесс теста, дайте библиотеке вариант только для тестов, например
`fn compact_with_crash(&mut self, stop_after: Option<u8>)`, который возвращается раньше после шага 1 или шага 2, а
`compact` пусть вызывает его с `None`. Удалите хранилище, откройте заново и сравните ответы и список файлов через
`std::fs::read_dir`.

</details>

**Готово, когда:**

```bash
cargo build -q
KV=./target/debug/p17-kv
for i in $(seq 1 300); do $KV --dir demo2 put counter "$i" > /dev/null; done
$KV --dir demo2 put name kv
$KV --dir demo2 stats
$KV --dir demo2 compact
$KV --dir demo2 stats
$KV --dir demo2 get counter
ls demo2
```

```text
OK
keys: 2
disk bytes: 6811
compacted: 6811 -> 42 bytes
keys: 2
disk bytes: 42
300
MANIFEST
data-000002.log
```

Ваши числа байтов снова будут другими, но компакция должна сжать 301 запись двух ключей до 2 записей, и остаться
могут только `MANIFEST` и один файл данных (вариант B: файлы, которые называет ваш `MANIFEST`). Коммит:
`M3: atomic compaction`.

#### M4 — Тест на модели

**Цель:** уверенность, что верна каждая последовательность операций, а не только те, о которых вы подумали.

**Указания:** с помощью `proptest` порождайте `Vec` операций: `Put(key, value)`, `Delete(key)`, `Compact` и `Reopen`
(удалить хранилище и открыть снова). Используйте мало ключей (например, 8 однобайтовых), чтобы операции часто попадали
в одни и те же ключи. Применяйте каждую операцию к хранилищу и к `BTreeMap`; после каждой проверяйте `get` для каждого
ключа и что `delete` возвращает тот же `bool`, что `BTreeMap::remove(...).is_some()`.

<details>
<summary>Подсказка</summary>

Операции описывают `enum Op` и стратегия, построенная через `prop_oneof![...]` и `prop_map`. Каждый `put` синхронизирует
диск, поэтому держите случаи маленькими: `ProptestConfig::with_cases(64)` и последовательности до 40 операций
занимают несколько секунд.

</details>

**Готово, когда:**

```bash
cargo test
```

показывает все пять тестов контракта (порядок может отличаться, и ваши собственные дополнительные тесты тоже
появятся):

```text
test tests::torn_tail_at_every_byte_is_cut_off ... ok
test tests::crash_during_compaction_keeps_old_or_new_state ... ok
test tests::matches_btreemap_model ... ok
test put_then_get_in_a_new_process ... ok
test missing_key_exits_with_1 ... ok
```

Сломайте что-нибудь нарочно (например, пропускайте надгробие при проигрывании) и проверьте, что
`matches_btreemap_model` падает и печатает короткую падающую последовательность. Коммит: `M4: model-based test`.

#### M5 — Бенчмарки

**Цель:** знать, насколько быстр ваш движок и почему.

**Указания:** создайте `benches/kv.rs` с `criterion` (и `[[bench]] name = "kv"`, `harness = false` в `Cargo.toml`).
Один раз загрузите несколько тысяч ключей, затем измерьте `get` существующих ключей и синхронизированный `put`.
Используйте маленький размер выборки (`group.sample_size(10)`), потому что синхронизированные записи медленные.
Запускайте с коротким временем измерения: `cargo bench --bench kv -- --warm-up-time 1 --measurement-time 3`.

<details>
<summary>Подсказка</summary>

Загрузка 10 000 ключей с синхронизацией каждого занимает на Mac около 40 секунд, потому что каждая синхронизация —
полный `F_FULLFSYNC` (Урок 17.2). Загрузите меньше ключей или добавьте `put_many`, который синхронизирует один раз на
весь пакет (дополнительная цель 1).

</details>

**Готово, когда:** `cargo bench` печатает время для обоих бенчмарков. На Mac, использованном для этого курса,
эталонная реализация варианта A напечатала:

```text
kv/get                  time:   [530.77 ns 685.99 ns 914.79 ns]
kv/put (synced)         time:   [3.8685 ms 4.0176 ms 4.1678 ms]
```

Ваши числа будут другими. Запишите в README, что определяет каждое число (`get` — это поиск в хеш-таблице плюс один
`read_at`, обслуженный из страничного кэша; синхронизированный `put` — почти целиком время синхронизации) и сколько
синхронизированных записей в секунду это означает. Коммит: `M5: benchmarks`.

#### M6 — README и контроль качества

**Цель:** проект, который другой человек может понять и которому может доверять.

**Указания:** README объясняет выбранный вариант, формат на диске (таблица полей записи), точку фиксации компакции, что
тесты доказывают и чего не доказывают, и результаты бенчмарков. Затем запустите контроль качества.

**Готово, когда:**

```bash
cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test
```

завершается без предупреждений и ошибок. Коммит: `M6: README and quality gate`.

### Дополнительные цели

1. **Групповая фиксация:** `put_many(&[(key, value)])` пишет несколько записей и синхронизирует один раз; измерьте,
   сколько ключей в секунду это даёт по сравнению с отдельными синхронизированными записями (Урок 17.2).
2. **Настоящий тест сбоя:** интеграционный тест, который в цикле запускает CLI, пишущий ключи, убивает его сигналом
   `SIGKILL` после случайной задержки, открывает хранилище заново и проверяет, что присутствует каждый ключ, для которого
   было напечатано `OK`.
3. **Сегменты:** начинайте новый файл данных, когда текущий достигает предела размера, чтобы компакция могла
   переписывать старые сегменты, пока записи продолжаются в самом новом. Тогда `MANIFEST` перечисляет несколько файлов.
4. **Сканирование диапазонов (вариант B):** `scan <FROM> <TO>` печатает все ключи по порядку, сливая memtable и SSTable.
5. **Сервер:** TCP-сервер (TCP — Transmission Control Protocol, протокол управления передачей) на Tokio со строчным протоколом (`PUT k v`, `GET k`, `DEL k`) перед тем же `Store`, с одной
   задачей-писателем, которая владеет хранилищем и получает команды через канал (Урок 14.13).
6. **Файлы-подсказки (hint files, вариант A):** при компакции пишите ещё и маленький файл только с ключами и
   смещениями, чтобы `open` не приходилось читать все значения (Урок 17.5).

## Частые ошибки

> ⚠️ **Частая ошибка:** печатать `OK` до того, как вернулся `sync_data`. Контракт говорит, что `OK` значит «надёжно
> сохранено»; сбой сразу после печати сделал бы это ложью.

> ⚠️ **Частая ошибка:** выполнять компакцию, переписывая файл данных **на месте**. Сбой посередине уничтожит
> единственную копию. Всегда сначала пишите новое состояние в новые файлы, а затем переключайтесь одним атомарным шагом.

> ⚠️ **Частая ошибка:** забывать синхронизировать **каталог** после `rename` и после создания или удаления файлов.
> Данные файла надёжно сохранены, но запись каталога, которая его называет, может быть ещё нет (Урок 13.12).

> 🔒 **Безопасность:** каталог данных — это тоже ввод. Повреждённый или вредоносный файл может содержать любое поле
> длины; проверяйте длины до выделения памяти и возвращайте `Error::Corrupt` вместо паники. Паника движка хранения во
> время `open` означает сервис, который не может запуститься.

## Вопросы для самопроверки

1. Почему `put` вызывает `sync_data` до того, как напечатать `OK`, и сколько это стоит на Mac?

<details>
<summary>Ответ</summary>

`OK` обещает надёжность; без синхронизации запись могла бы ещё лежать только в страничном кэше и пропасть при сбое. На
Mac каждая синхронизация — `F_FULLFSYNC` длиной в несколько миллисекунд, поэтому отдельных синхронизированных записей
получается лишь несколько сотен в секунду.

</details>

2. Что является точкой фиксации компакции и что `open` делает с файлами до неё и после?

<details>
<summary>Ответ</summary>

Атомарный `rename` файла `MANIFEST.tmp` в `MANIFEST`. До него старый `MANIFEST` называет старый файл, а новый файл —
остаток, который `open` удаляет. После него новый `MANIFEST` называет новый файл, а остатком становится старый.

</details>

3. Почему плохая запись в конце самого нового файла отрезается, а плохая запись в середине считается повреждением?

<details>
<summary>Ответ</summary>

Сбой может оборвать только ту запись, которая дописывалась, — в конце. Плохая запись в середине файла, который был
целым и синхронизированным, означает настоящее повреждение (ошибку диска или баг); скрыть её значит молча потерять
данные.

</details>

4. Что находит `matches_btreemap_model` из того, что другие тесты могут пропустить?

<details>
<summary>Ответ</summary>

Ошибки в сочетаниях операций, о которых вы не подумали, например удаление, за которым следуют компакция и повторное
открытие. proptest ещё и сжимает падающую последовательность до короткой, которую легко отлаживать.

</details>

## Итоги

- Движок хранения объединяет надёжный журнал только для дописывания, индекс, восстановление и компакцию; этот проект
  строит все четыре части.
- `OK` значит «надёжно сохранено»: синхронизируйте до ответа.
- Каждая запись несёт CRC; восстановление отрезает разорванный хвост и отвергает настоящее повреждение.
- У многошаговых изменений одна точка фиксации; для компакции это атомарная замена `MANIFEST`.
- Устойчивость к сбоям доказывается тестами: каждый байт разорванной записи, каждый шаг компакции и тест на модели.
- Бенчмарки полезны, только если объяснено, что определяет числа.
