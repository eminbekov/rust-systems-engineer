# Урок 15.3 — TCP и UDP

> **Этап 15 — Сети** · Урок 3 из 16 · ⏱ около 105 минут

## Что вы узнаете

- Как порты и «четвёрка» (four-tuple) обозначают один разговор двух программ.
- Что обещает TCP (надёжный упорядоченный поток байтов) и как он выполняет обещание: номера последовательности, подтверждения, повторная передача, управление потоком и управление перегрузкой.
- Как TCP-соединение открывается (тройное рукопожатие) и закрывается — по настоящему захвату, и что означают состояния `LISTEN`, `ESTABLISHED` и `TIME-WAIT`.
- Что вместо этого даёт UDP (отдельные сообщения, никаких гарантий) и когда это лучший выбор.

## Новые слова

| Слово | Значение |
|---|---|
| **соединение** (connection) | В TCP — договорённость двух программ обмениваться потоком байтов, с состоянием, которое хранят обе стороны. |
| **четвёрка** (four-tuple) | Четыре значения, которые обозначают TCP-соединение: IP отправителя, порт отправителя, IP получателя, порт получателя. |
| **эфемерный порт** (ephemeral port) | Временный порт, который операционная система выбирает для клиентской стороны соединения. |
| **поток байтов** (byte stream) | Данные как один длинный ряд байтов без границ сообщений, как при чтении файла. |
| **номер последовательности** (sequence number) | Номер первого байта в TCP-сегменте. Позволяет получателю расставить байты по порядку и найти пропуски. |
| **подтверждение** (acknowledgement, ACK) | Сообщение «я получил всё до байта N». В TCP это число в заголовке плюс флаг ACK. |
| **повторная передача** (retransmission) | Повторная отправка данных, потому что подтверждение не пришло вовремя. |
| **RTT** (Round-Trip Time, время приёма-передачи) | Время, за которое пакет доходит до другой стороны, плюс время, за которое возвращается ответ. |
| **управление потоком** (flow control) | Ограничение, чтобы отправитель не слал больше, чем может сохранить *получатель*. TCP использует для этого *окно приёма*. |
| **управление перегрузкой** (congestion control) | Ограничение, чтобы отправитель не слал больше, чем может пропустить *сеть*. |
| **рукопожатие** (handshake) | Первые сообщения протокола, в которых обе стороны договариваются о разговоре. Рукопожатие TCP состоит из трёх сегментов. |
| **SYN, ACK, FIN, RST, PSH** | Флаги TCP: синхронизация (открыть), подтверждение, завершение (я больше не отправляю), сброс (немедленно прервать), проталкивание (доставить сразу). |
| **MSS** (Maximum Segment Size, максимальный размер сегмента) | Наибольший объём данных в одном TCP-сегменте; сообщается при рукопожатии. |
| **TIME-WAIT** | Состояние, в котором сторона, закрывшая соединение первой, остаётся какое-то время (60 секунд в Linux) после его окончания. |
| **датаграмма** (datagram) | Одно UDP-сообщение. Доставляется целиком или не доставляется вовсе. |
| **ss** (socket statistics, статистика сокетов) | Команда Linux, которая показывает сокеты и их состояния. |
| **TCP / UDP / IP** (Transmission Control Protocol / User Datagram Protocol / Internet Protocol — протокол управления передачей / протокол пользовательских датаграмм / межсетевой протокол) | Два транспортных протокола этого урока и межсетевой протокол под ними (Урок 15.1). |
| **HTTP, HTTPS, DNS, SSH, TLS** | Протоколы поверх TCP или UDP, знакомые по Уроку 15.1: HyperText Transfer Protocol (протокол передачи гипертекста, веб), HTTP Secure (HTTP внутри TLS), Domain Name System (система доменных имён: имена в адреса), Secure Shell (удалённый вход), Transport Layer Security (протокол защиты транспортного уровня, шифрование). |
| **ICMP** (Internet Control Message Protocol, протокол межсетевых управляющих сообщений) и **QUIC** | ICMP переносит служебные сообщения и сообщения об ошибках, например «port unreachable»; QUIC — более новый транспорт поверх UDP (Урок 15.13). |
| **URG** (urgent, срочно) | Флаг TCP для «срочных данных»; он есть в заголовке, но почти никогда не используется. |

## 1. Порты и разговоры

Уровень IP доставляет пакет нужному **компьютеру**. Но на компьютере одновременно работает много
программ, которые пользуются сетью. Транспортный уровень добавляет **порты**: 16-битные числа,
которые говорят, какой программе принадлежит пакет. Сервер *слушает* хорошо известный порт (80 для
HTTP, 443 для HTTPS, 53 для DNS, 22 для SSH). Клиент получает от операционной системы **эфемерный
порт**. В Linux диапазон такой:

```bash
cat /proc/sys/net/ipv4/ip_local_port_range
```

```text
32768	60999
```

(macOS использует диапазон от 49152 до 65535.) Одно TCP-соединение обозначается **четвёркой**:

```text
 (source IP,  source port,  destination IP,  destination port)
 (127.0.0.1,  36932,        127.0.0.1,       9000)            ← the "hello" connection of 15.1
```

Поскольку порты клиентов различаются, один порт сервера может обслуживать тысячи клиентов
одновременно. Добавьте протокол (TCP или UDP) — получится «пятёрка» (five-tuple), которой пользуются
файрволы и балансировщики нагрузки.

## 2. Что обещает TCP

IP лишь *пытается* доставить пакеты. Они могут теряться, дублироваться или менять порядок. TCP
работает поверх IP и даёт вашей программе нечто гораздо более удобное: **надёжный упорядоченный поток
байтов**. То, что вы записали на одной стороне, выходит на другой — каждый байт, в том же порядке, —
либо вы получаете ошибку. Чтобы сдержать это обещание, TCP использует пять идей:

1. **Номера последовательности.** У каждого байта есть номер. Сегмент несёт номер своего первого
   байта. Поэтому получатель может отсортировать сегменты и увидеть пропуски.
2. **Подтверждения.** Получатель отвечает «ACK N»: «у меня есть всё до байта N, присылай N
   следующим».
3. **Повторная передача.** Если отправитель не получает подтверждения за время ожидания (чуть больше
   одного RTT), он отправляет данные снова. Дубликаты узнаются по номерам последовательности и
   отбрасываются.
4. **Управление потоком.** Каждый сегмент несёт **окно**: сколько ещё байтов может сохранить
   получатель. Если принимающая программа читает медленно, её окно сжимается, и отправитель должен
   ждать. При окне 0 отправитель останавливается полностью.
5. **Управление перегрузкой.** Отправитель также оценивает, сколько может пропустить *сеть*. Он
   начинает медленно, отправляет больше, пока всё подтверждается, и резко сбавляет, когда пакеты
   теряются, потому что потери обычно означают переполненную очередь маршрутизатора.

Есть ещё одно свойство, которое удивляет многих новичков и важно для Урока 15.7: TCP — это **поток
байтов, а не сообщений**. Если вы отправили `hello`, а затем `world` двумя записями, другая сторона
может прочитать `helloworld` за одно чтение или `hel`, а потом `loworld`. TCP сохраняет байты и их
порядок, но не сохраняет границы ваших сообщений.

## 3. Открыть, поговорить, закрыть: читаем настоящий разговор

Вот 8 пакетов захвата `hello` из Урока 15.1, без шестнадцатеричного дампа. Клиент — порт `36932`,
сервер — порт `9000`:

```text
1  127.0.0.1.36932 > 127.0.0.1.9000: Flags [S], seq 4058503438, win 65495, options [mss 65495,sackOK,TS val 2778587979 ecr 0,nop,wscale 10], length 0
2  127.0.0.1.9000 > 127.0.0.1.36932: Flags [S.], seq 2766373507, ack 4058503439, win 65483, options [mss 65495,sackOK,TS val 1523372706 ecr 2778587979,nop,wscale 10], length 0
3  127.0.0.1.36932 > 127.0.0.1.9000: Flags [.], ack 1, win 64, options [nop,nop,TS val 2778587979 ecr 1523372706], length 0
4  127.0.0.1.36932 > 127.0.0.1.9000: Flags [P.], seq 1:7, ack 1, win 64, options [nop,nop,TS val 2778587979 ecr 1523372706], length 6
5  127.0.0.1.9000 > 127.0.0.1.36932: Flags [.], ack 7, win 64, options [nop,nop,TS val 1523372706 ecr 2778587979], length 0
6  127.0.0.1.36932 > 127.0.0.1.9000: Flags [F.], seq 7, ack 1, win 64, options [nop,nop,TS val 2778587979 ecr 1523372706], length 0
7  127.0.0.1.9000 > 127.0.0.1.36932: Flags [F.], seq 1, ack 8, win 64, options [nop,nop,TS val 1523372706 ecr 2778587979], length 0
8  127.0.0.1.36932 > 127.0.0.1.9000: Flags [.], ack 2, win 64, options [nop,nop,TS val 2778587979 ecr 1523372706], length 0
```

(Номера строк слева добавлены, а отметки времени убраны для удобства чтения.) В tcpdump `S` — это
SYN, `.` — ACK, `P` — PSH, `F` — FIN, а `R` был бы RST. Тот же разговор в виде картинки:

```text
 client :36932                                         server :9000
      │ ── 1  SYN      seq=4058503438 ───────────────────► │   "let's talk, my bytes start here"
      │ ◄─ 2  SYN+ACK  seq=2766373507 ack=4058503439 ───── │   "OK, mine start here; got yours"
      │ ── 3  ACK      ack=1 ────────────────────────────► │   handshake done: ESTABLISHED
      │ ── 4  PSH+ACK  seq=1:7  "hello\n" ───────────────► │   6 bytes of data
      │ ◄─ 5  ACK      ack=7 ──────────────────────────── │   "I have bytes 1..6, next is 7"
      │ ── 6  FIN+ACK  seq=7 ────────────────────────────► │   client: "I will send no more"
      │ ◄─ 7  FIN+ACK  seq=1 ack=8 ────────────────────── │   server: "me neither"
      │ ── 8  ACK      ack=2 ────────────────────────────► │   client enters TIME-WAIT
```

**Что происходит:**

1. **Пакеты 1–3, тройное рукопожатие.** Каждая сторона выбирает случайный начальный номер
   последовательности (*initial sequence number*), отправляет его с SYN и подтверждает номер другой
   стороны плюс один. SYN считается за один байт, поэтому сервер отвечает `ack 4058503439`
   (= 4058503438 + 1). Случайные начальные номера мешают атакующему вставлять поддельные сегменты в
   соединение.
2. `options` согласуют детали: `mss 65495` — самый большой сегмент, который принимает каждая сторона
   (большой, потому что это петлевой интерфейс; в Ethernet это 1460), а `wscale` позволяет окну быть
   больше 65 535 байт.
3. **Начиная с пакета 3, tcpdump показывает относительные номера**: `ack 1` означает «начальный номер
   + 1». Так tcpdump только печатает; в настоящем заголовке по-прежнему большие числа.
4. **Пакеты 4–5, данные.** `seq 1:7` несёт байты с 1 по 6 (`hello\n`, `length 6`). Сервер отвечает
   `ack 7`: всё до байта 7 пришло. `win 64` (умноженное на 2^10 из-за `wscale 10`) — это окно
   приёма.
5. **Пакеты 6–8, закрытие.** Каждое направление закрывается отдельно с помощью FIN. Клиент
   отправляет FIN (данных у него больше нет), сервер отвечает своим FIN, а клиент его подтверждает.
   FIN тоже считается за один байт, поэтому подтверждения становятся `ack 8` и `ack 2`.

Всё это делает ядро. В Rust рукопожатие происходит внутри `TcpStream::connect`, сегменты с данными —
внутри `write`, а FIN — когда поток уничтожается (или когда вы вызываете `shutdown`). Можно даже
увидеть, что для рукопожатия не нужен код вашего сервера. Сохраните как `src/bin/handshake.rs`:

```rust
use std::net::{TcpListener, TcpStream};
use std::time::Instant;

fn main() -> std::io::Result<()> {
    // Порт 0 просит операционную систему выбрать любой свободный порт.
    let listener = TcpListener::bind("127.0.0.1:0")?;
    let addr = listener.local_addr()?;

    let start = Instant::now();
    let stream = TcpStream::connect(addr)?; // мы ни разу не вызываем accept()!
    println!("connected to {addr} in {:?}", start.elapsed());
    println!("our side of the connection: {}", stream.local_addr()?);

    drop(listener); // закрываем слушающий сокет
    match TcpStream::connect(addr) {
        Ok(_) => println!("connected again?"),
        Err(e) => println!("second connect: {e} (kind: {:?})", e.kind()),
    }
    Ok(())
}
```

**Что происходит:**

1. Привязка к порту `0` позволяет операционной системе выбрать свободный порт; `local_addr()`
   сообщает, какой именно.
2. `connect` возвращается после тройного рукопожатия. Он успешен, хотя программа ни разу не вызывает
   `accept()`: ядро само завершает рукопожатия для слушающего сокета и держит готовые соединения в
   очереди (*backlog*), пока программа их не примет (Урок 15.4).
3. После `drop(listener)` этот порт никто не слушает. Ядро отвечает на следующий SYN пакетом RST, и
   `connect` возвращает ошибку вида `ConnectionRefused`.

`cargo run --bin handshake` на Mac печатает (ваши порты и время будут другими):

```text
connected to 127.0.0.1:53416 in 63.083µs
our side of the connection: 127.0.0.1:53417
second connect: Connection refused (os error 61) (kind: ConnectionRefused)
```

Рукопожатие заняло 63 микросекунды, потому что «сетью» был петлевой интерфейс. Через полмира оно
занимает один RTT, часто 50–150 мс, прежде чем можно отправить хотя бы первый байт данных. Поэтому
открывать новое соединение на каждый запрос медленно, и поэтому HTTP держит соединения открытыми
(Урок 15.8).

Отклонённое соединение выглядит в tcpdump так (захвачено в контейнере командой
`nc -v 127.0.0.1 9001`, когда порт 9001 никто не слушал):

```text
nc: connect to 127.0.0.1 port 9001 (tcp) failed: Connection refused
07:15:11.419945 IP 127.0.0.1.56060 > 127.0.0.1.9001: Flags [S], seq 283570947, win 65495, options [mss 65495,sackOK,TS val 1777619782 ecr 0,nop,wscale 10], length 0
07:15:11.419954 IP 127.0.0.1.9001 > 127.0.0.1.56060: Flags [R.], seq 0, ack 283570948, win 0, length 0
```

SYN, на который сразу ответили RST. Запомните этот шаблон: «connection refused» означает, что
компьютер доступен, но этот порт никакая программа не слушала. Если же в ответ не приходит вообще
ничего, `connect` висит до тайм-аута: тогда вероятнее проблема с файрволом или маршрутизацией.

## 4. Состояния соединения и `ss`

Обе стороны хранят состояние каждого соединения, и `ss` (socket statistics) его показывает. В
контейнере запустите сервер, подключите клиента, который остаётся на две секунды, и посмотрите
дважды:

```bash
docker run --rm -it p15-nettools bash
nc -l 127.0.0.1 9000 > /dev/null &
(sleep 2) | nc -N 127.0.0.1 9000 &
sleep 1
ss -tan
sleep 3
ss -tan
```

(`-t` — только TCP, `-a` — все сокеты, включая слушающие, `-n` — числа. `nc -N` закрывает
соединение, когда заканчивается его ввод, то есть после `sleep 2`.)

```text
State  Recv-Q Send-Q Local Address:Port  Peer Address:Port 
LISTEN 0      1          127.0.0.1:9000       0.0.0.0:*    
ESTAB  0      0          127.0.0.1:9000     127.0.0.1:47088
ESTAB  0      0          127.0.0.1:47088    127.0.0.1:9000 
State     Recv-Q Send-Q Local Address:Port  Peer Address:Port
TIME-WAIT 0      0          127.0.0.1:47088    127.0.0.1:9000
```

1. `LISTEN` — слушающий сокет: он принимает новые соединения и сам никогда не передаёт данные.
2. Две строки `ESTAB` (established, установлено): *одно и то же* соединение с обоих концов, потому
   что клиент и сервер работают на одной машине. Обратите внимание, что локальный адрес и адрес
   собеседника поменялись местами.
3. После закрытия серверная сторона исчезла, а клиентская находится в **TIME-WAIT**. Сторона, которая
   отправила первый FIN, ждёт там 60 секунд (в Linux), чтобы поздние, задержавшиеся сегменты старого
   соединения нельзя было принять за новое соединение с той же четвёркой.
4. `Recv-Q` и `Send-Q` показывают байты, ждущие в буферах ядра. Растущий `Recv-Q` у установленного
   сокета означает, что программа читает недостаточно быстро.

> 💡 **Совет:** в продакшене многое говорят два состояния. Тысячи сокетов `TIME-WAIT` на клиенте
> означают, что он открывает новое соединение на каждый запрос: переиспользуйте соединения. Много
> сокетов в `CLOSE-WAIT` означает, что *другая* сторона закрыла соединение, а ваша программа так и не
> закрыла свой конец: это ошибка в вашем коде, обычно поток, который никогда не уничтожается.

## 5. UDP: просто отправьте сообщение

UDP почти ничего не добавляет к IP: порты, длину и контрольную сумму. Его заголовок занимает всего
8 байтов:

```text
 ┌──────────────────┬──────────────────┐
 │ source port      │ destination port │
 ├──────────────────┼──────────────────┤
 │ length           │ checksum         │
 └──────────────────┴──────────────────┘
   then the data of one datagram
```

Нет соединения, нет рукопожатия, нет подтверждений, нет повторной передачи и нет упорядочивания.
Каждый `send` порождает одну **датаграмму**, и каждый приём возвращает ровно одну целую датаграмму:
UDP **сохраняет границы сообщений**. Два сообщения, отправленные через `nc -u` в контейнере:

```bash
tcpdump -i lo -n -c 2 udp port 9002 &
printf "first\n" | nc -u -w 0 127.0.0.1 9002
printf "second\n" | nc -u -w 0 127.0.0.1 9002
```

```text
07:15:28.417843 IP 127.0.0.1.47723 > 127.0.0.1.9002: UDP, length 6
07:15:28.419811 IP 127.0.0.1.46760 > 127.0.0.1.9002: UDP, length 7
```

Два пакета, больше ничего. Порт 9002 никто не слушал, и отправитель так об этом и не узнал. Когда
датаграмма приходит на порт без слушателя, принимающее ядро может ответить ICMP-сообщением (здесь
захвачено для порта 9003):

```text
07:15:15.438910 IP 127.0.0.1.39002 > 127.0.0.1.9003: UDP, length 7
07:15:15.438949 IP 127.0.0.1 > 127.0.0.1: ICMP 127.0.0.1 udp port 9003 unreachable, length 43
```

Но это сообщение — лишь любезность: файрволы часто его отбрасывают, а потерянные датаграммы вообще
не порождают никаких сообщений. С UDP *ваша программа* должна решать, что делать с потерями, порядком
и дубликатами (Урок 15.5).

Зачем это кому-то нужно? Потому что иногда гарантии TCP мешают:

| | TCP | UDP |
|---|---|---|
| Подготовка перед данными | рукопожатие, один RTT | нет |
| Доставка | надёжная, по порядку, без дубликатов | может быть, в любом порядке, может дважды |
| Единица | поток байтов (без границ сообщений) | датаграмма (границы сохраняются) |
| Потерянный пакет | всё, что после него, ждёт повторной отправки | теряется только это сообщение |
| Кто использует | HTTP/1.1 и HTTP/2, SSH, базы данных, TLS | DNS, видео- и голосовые звонки, игры, QUIC и HTTP/3 |

Ключевая строка — «потерянный пакет». TCP доставляет по порядку, поэтому один потерянный сегмент
задерживает все последующие байты, даже если они уже пришли. Это называется **блокировкой начала
очереди** (head-of-line blocking). Для голосового звонка звук, пришедший поздно, бесполезен; лучше
его пропустить. DNS использует UDP, потому что вопрос и ответ помещаются каждый в одну датаграмму, а
потерянный вопрос просто задают снова. QUIC (Урок 15.13) строит собственные надёжные потоки поверх
UDP, чтобы избежать блокировки начала очереди между потоками.

> ⚡ **Производительность:** цена TCP — рукопожатие (один RTT до любых данных), блокировка начала
> очереди и медленный старт управления перегрузкой на каждом новом соединении. Бо́льшая часть этих
> затрат исчезает, когда одно соединение переиспользуется для многих запросов. Измерьте, прежде чем
> решить, что вам «нужен UDP».

## Частые ошибки

> ⚠️ **Частая ошибка: ожидать одно чтение на одну запись.** Сервер, который делает один `read` и
> считает, что получил ровно одно сообщение, работает на loopback в тестах и ломается в настоящей
> сети, где сегменты делятся и склеиваются. TCP не сохраняет границы сообщений. Урок 15.7 показывает,
> как разбивать поток на сообщения.

> ⚠️ **Частая ошибка: считать «refused» и «timed out» одним и тем же.** `ConnectionRefused` означает,
> что хост ответил RST: программа не запущена или слушает другой порт или адрес. Тайм-аут означает,
> что ответа нет вообще: проверьте файрволы, маршрутизацию и сам адрес.

> ⚠️ **Частая ошибка: думать, что UDP сообщает об ошибках.** `send_to` завершается успешно, даже если
> датаграмму никто не получит. Что-то сказать вам может только ответ (или его отсутствие после
> тайм-аута).

## Попробуйте сами

1. В контейнере запустите `tcpdump -i lo -n tcp port 9000 &`, затем `nc -l 127.0.0.1 9000 &`, затем
   подключитесь командой `nc 127.0.0.1 9000` и введите две строки, нажимая Enter после каждой.
2. Найдите два сегмента с данными. Длина каждого равна длине строки плюс 1 (перевод строки), а
   номера последовательности продолжаются. Если вы ввели `abc` и `de`, вы увидите `seq 1:5` с
   `length 4`, затем `seq 5:8` с `length 3`.
3. Нажмите Ctrl+C в клиенте и найдите сегменты FIN. Какая сторона отправила первый FIN?
4. Выполните `ss -tan` и найдите сокет в `TIME-WAIT`. Он на той стороне, что закрыла первой?

## Упражнения

### Упражнение 1 — Кто закрыл первым? (легко)

На сервере вы видите в `ss -tan` такую строку:

```text
TIME-WAIT 0      0          10.0.0.5:8080     10.0.0.9:51312
```

Какая программа отправила первый FIN: та, что на `10.0.0.5:8080`, или та, что на `10.0.0.9:51312`?
Какая из них, скорее всего, сервер?

<details>
<summary>Подсказка</summary>

TIME-WAIT держит сторона, закрывшая соединение первой. Какой порт похож на порт сервера, а какой — на
эфемерный?

</details>

<details>
<summary>Ответ</summary>

Сокет в TIME-WAIT принадлежит `10.0.0.5:8080`, значит, первый FIN отправила эта сторона. Порт 8080 —
типичный порт сервера, а 51312 — эфемерный порт клиента: здесь соединение первым закрыл **сервер**,
что нормально для HTTP-серверов, отвечающих с `Connection: close`.

</details>

### Упражнение 2 — Разбор флагов TCP с тестами (средне)

Флаги TCP-сегмента — это биты байта 13 заголовка TCP: FIN = `0x01`, SYN = `0x02`, RST = `0x04`,
PSH = `0x08`, ACK = `0x10`, URG = `0x20`. Напишите `src/bin/tcp_flags.rs` с функцией
`fn tcp_flags(flags: u8) -> String`, которая записывает их как tcpdump, в порядке F, S, R, P, `.`
(ACK), U, и `"none"`, если ни один флаг не установлен. Протестируйте как минимум SYN (`"S"`), SYN+ACK
(`"S."`), PSH+ACK (`"P."`) и FIN+PSH+ACK (`"FP."`). Байт 13 пакета `hello` из Урока 15.1 равен
`0x18`; что напечатает ваша функция для него?

<details>
<summary>Подсказка</summary>

Храните список пар `(бит, символ)` в правильном порядке и проверяйте каждый бит через
`flags & bit != 0` (Урок 12.4).

</details>

<details>
<summary>Ответ</summary>

```rust
/// Writes TCP flags the way tcpdump does: "S" for SYN, "." for ACK, and so on.
fn tcp_flags(flags: u8) -> String {
    const NAMES: [(u8, char); 6] = [
        (0x01, 'F'), // FIN: больше данных от меня не будет
        (0x02, 'S'), // SYN: синхронизировать номера последовательности (открыть)
        (0x04, 'R'), // RST: сброс, прервать соединение
        (0x08, 'P'), // PSH: передать данные программе сразу
        (0x10, '.'), // ACK: номер подтверждения действителен
        (0x20, 'U'), // URG: срочные данные (почти не используется)
    ];
    let mut out = String::new();
    for (bit, name) in NAMES {
        if flags & bit != 0 {
            out.push(name);
        }
    }
    if out.is_empty() {
        out.push_str("none");
    }
    out
}

fn main() {
    // Байт 13 заголовка TCP в пакете "hello" из Урока 15.1 равен 0x18.
    for byte in [0x02, 0x12, 0x10, 0x18, 0x11, 0x14] {
        println!("{byte:#04x} -> [{}]", tcp_flags(byte));
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn handshake_flags() {
        assert_eq!(tcp_flags(0x02), "S");
        assert_eq!(tcp_flags(0x12), "S.");
        assert_eq!(tcp_flags(0x10), ".");
    }

    #[test]
    fn data_and_closing_flags() {
        assert_eq!(tcp_flags(0x18), "P.");
        assert_eq!(tcp_flags(0x11), "F.");
        assert_eq!(tcp_flags(0x19), "FP.");
        assert_eq!(tcp_flags(0x14), "R.");
    }

    #[test]
    fn no_flags() {
        assert_eq!(tcp_flags(0), "none");
    }
}
```

```text
0x02 -> [S]
0x12 -> [S.]
0x10 -> [.]
0x18 -> [P.]
0x11 -> [F.]
0x14 -> [R.]
```

`cargo test --bin tcp_flags` сообщает `3 passed`. Почему это работает: каждый флаг — это один бит,
поэтому байт — маленький набор ответов «да/нет»; проверка каждого бита в фиксированном порядке
воспроизводит запись tcpdump. `0x18` — это `[P.]`, ровно то, что tcpdump напечатал для пакета с
данными.

</details>

### Упражнение 3 — Проследите за номерами (средне)

В захвате из раздела 3 начальный номер последовательности клиента — 4058503438. В настоящих
(абсолютных) числах ответьте: (a) Какой номер последовательности у байта `h` из `hello`? (b) Какой
номер подтверждения сервер отправляет в пакете 5? (c) Какой номер последовательности у FIN клиента и
какое число его подтверждает?

<details>
<summary>Подсказка</summary>

SYN расходует один номер последовательности. Данные начинаются со следующего номера. FIN тоже
расходует один номер. Относительный номер 1 в tcpdump означает «начальный номер + 1».

</details>

<details>
<summary>Ответ</summary>

(a) 4058503439 (начальный номер + 1, потому что SYN занял 4058503438). (b) Данные занимают номера с
4058503439 по 4058503444 (шесть байтов), поэтому сервер подтверждает 4058503445 (относительный
`ack 7`). (c) У FIN номер последовательности 4058503445 (относительный `seq 7`), а подтверждается он
числом 4058503446 (относительный `ack 8`).

</details>

## Вопросы для самопроверки

1. Почему один порт сервера (скажем, 443) может одновременно обслуживать тысячи клиентов?

<details>
<summary>Ответ</summary>

Соединение обозначается всей четвёркой. У каждого клиента другой IP-адрес или другой эфемерный
порт, поэтому все соединения различаются, хотя серверная сторона одна и та же.

</details>

2. Что означает номер подтверждения 1000?

<details>
<summary>Ответ</summary>

«Я получил все байты до байта 1000; следующий ожидаемый байт — 1000».

</details>

3. Чем управление потоком отличается от управления перегрузкой?

<details>
<summary>Ответ</summary>

Управление потоком защищает получателя: отправитель не может превысить окно приёма, о котором
сообщает получатель. Управление перегрузкой защищает сеть: отправитель сам себя ограничивает по
потерям и задержкам, потому что переполненные очереди маршрутизаторов отбрасывают пакеты.

</details>

4. Клиент вызывает `connect` и получает «connection refused». Что произошло в сети?

<details>
<summary>Ответ</summary>

Клиент отправил SYN, а компьютер сервера ответил RST, потому что на этом адресе и порту никакой
сокет не слушал.

</details>

5. Какая сторона TCP-соединения оказывается в TIME-WAIT и зачем существует это состояние?

<details>
<summary>Ответ</summary>

Сторона, отправившая первый FIN. Она ждёт, чтобы задержавшиеся сегменты старого соединения исчезли,
прежде чем ту же четвёрку можно будет использовать снова, и чтобы можно было повторить последний
ACK, если он потерялся.

</details>

6. Почему DNS обычно использует UDP, а не TCP?

<details>
<summary>Ответ</summary>

Вопрос и ответ помещаются каждый в одну датаграмму. UDP не требует рукопожатия, поэтому хватает
одного обмена, а потерянную датаграмму просто запрашивают снова после короткого тайм-аута.

</details>

## Итоги

- Порты выбирают программу; TCP-соединение обозначается четвёркой (IP и порт отправителя, IP и порт
  получателя). Клиенты используют эфемерные порты.
- TCP даёт **надёжный упорядоченный поток байтов** с помощью номеров последовательности, подтверждений,
  повторной передачи, управления потоком (окно приёма) и управления перегрузкой.
- Соединение открывается тройным рукопожатием (SYN, SYN+ACK, ACK) и закрывается FIN в каждом
  направлении; RST прерывает соединение, а «connection refused» — это SYN, на который ответили RST.
- `ss -tan` показывает состояния: `LISTEN`, `ESTAB`, `TIME-WAIT` (сторона, закрывшая первой),
  `CLOSE-WAIT` (ваша программа ещё не закрыла соединение).
- TCP **не** сохраняет границы сообщений; UDP сохраняет, но не даёт гарантий доставки, порядка и
  отсутствия дубликатов.
- UDP подходит для маленьких протоколов «вопрос — ответ» и данных в реальном времени; цена TCP —
  RTT на рукопожатие и блокировка начала очереди.
