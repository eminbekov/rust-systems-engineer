## Новые слова

| Слово | Значение |
|---|---|
| **контрольная точка** (checkpoint) | Пауза в конце этапа, чтобы проверить себя, прежде чем идти дальше. |
| **по памяти** (closed book) | Отвечать только по памяти, ничего не подглядывая. |
| **бюджет повторов** (retry budget) | Правило на вызывающей стороне: повторы могут составлять не больше фиксированной доли всех запросов, например 10 %. |
| **контроль допуска** (admission control) | Решение на входе, можно ли впустить новый запрос, вместо того чтобы он ждал внутри. |

### Надёжность и паники (Уроки 20.1 и 20.2)

1. Чем неисправность (fault) отличается от отказа (failure)? Приведите по одному примеру для веб-сервиса.

<details>
<summary>Ответ</summary>

**Неисправность** — причина: ошибка в коде, заполненный диск, медленная база данных, потерянный пакет. **Отказ** — то, что видят пользователи: страница ошибки, неверный ответ, отсутствие ответа. Пример: база данных стала медленной (неисправность), и страница оформления заказа не дожидается ответа (отказ). Работа над надёжностью не даёт неисправностям превращаться в отказы. (Урок 20.1.)

</details>

2. Сервис отказывает раз в 999 часов, и на восстановление нужен 1 час. Какова его доступность? Назовите два способа её улучшить и тот, что часто дешевле.

<details>
<summary>Ответ</summary>

`MTBF / (MTBF + MTTR)` = 999 / 1000 = **99,9 %** (MTBF — среднее время между отказами, MTTR — среднее время восстановления). Отказывать реже (больше MTBF) или восстанавливаться быстрее (меньше MTTR). Быстрее восстановиться часто дешевле: автоматические перезапуски, проверки работоспособности и быстрые откаты. (Урок 20.1.)

</details>

3. Задача Tokio паникует, держа `std::sync::Mutex`. Что видит код, который ждёт эту задачу, и что возвращают последующие вызовы `lock()`?

<details>
<summary>Ответ</summary>

Ожидание `JoinHandle` даёт `Err(JoinError)` с `is_panic() == true`; остальные задачи продолжают работать. Мьютекс **отравлен** (poisoned): `lock()` возвращает `Err(PoisonError)`, а `into_inner()` всё равно отдаёт данные, которые могут быть изменены наполовину. (Урок 20.2.)

</details>

4. Когда вы выберете `panic = "abort"` и что тогда должно существовать вне программы?

<details>
<summary>Ответ</summary>

Когда ошибка означает, что состоянию в памяти больше нельзя доверять, например в движке хранения посреди записи (подход *crash-only*). Первая паника сразу завершает весь процесс (код возврата 134), без `Drop`, поэтому **супервизор** (systemd, Kubernetes) должен его перезапустить, а программа — восстановить состояние из надёжного хранилища. (Урок 20.2.)

</details>

<details>
<summary>Ответ</summary>

### Перегрузка и готовность (Уроки 20.8–20.10)

13. Сервис получает 400 запросов в секунду, каждый занимает 250 мс. Сколько запросов в работе? Какова ёмкость при лимите конкурентности 50?

<details>
<summary>Ответ</summary>

400 × 0,25 = **100** в работе (закон Литтла). Ёмкость = 50 ÷ 0,25 с = **200 запросов в секунду**, так что около 200 в секунду должны ждать или получить отказ. (Урок 20.8.)

</details>

14. Когда сервис отвечает `429`, когда `503` и какой заголовок нужен обоим?

<details>
<summary>Ответ</summary>

`429 Too Many Requests` — когда один клиент превысил свой лимит частоты; `503 Service Unavailable` — когда перегружен весь сервис или недоступна зависимость. Оба несут `Retry-After`. (Урок 20.8.)

</details>

15. Что шаг за шагом происходит, когда хорошо построенный сервис получает SIGTERM (сигнал остановки, который посылает менеджер служб)?

<details>
<summary>Ответ</summary>

Готовность становится «не готов» (`503`), а живость остаётся `200`; сервис ждёт короткое время отвода трафика, чтобы балансировщик нагрузки перестал слать запросы; затем он перестаёт принимать новые соединения, завершает открытые запросы в пределах жёсткого лимита времени и выходит с кодом `0`. (Урок 20.9.)

</details>

16. Почему в axum функция `app` заканчивается на `.with_state(...)` после слоёв tower, даже когда состояние — `()`?

<details>
<summary>Ответ</summary>

Иначе axum заново строит слои обработчика для каждого запроса, и `ConcurrencyLimitLayer` даёт каждому запросу свой новый лимит, то есть ничего не ограничивает. `.with_state(...)` один раз превращает обработчики в маршруты, и все запросы делят один стек слоёв. Тест с двумя одновременными запросами и лимитом 1 ловит эту ошибку. (Уроки 20.8 и 20.10.)

</details>

### Задание 1 — Парсер заголовков, который никогда не паникует (Уроки 20.2 и 20.3)

Напишите в `src/header.rs` функцию `split_header(line: &str) -> Option<(&str, &str)>`. Она делит `Name: value` на имя и обрезанное по краям значение. Правила: строка не длиннее `MAX_LINE = 1024` байт; имя — от 1 до 64 букв, цифр ASCII (American Standard Code for Information Interchange, американский стандартный код для обмена информацией) или `-`; всё остальное даёт `None`. Функция **никогда не должна паниковать**, на любом тексте. Напишите модульные тесты, затем фаззинг-цель `header` (`cargo fuzz init -t header`) с двумя свойствами: функция никогда не паникует, а разобранная строка, записанная заново как `format!("{name}: {value}")`, разбирается в те же две части. Запустите её на 30 секунд.

<details>
<summary>Подсказка</summary>

`str::split_once(':')` возвращает `None`, если двоеточия нет, и никогда не паникует, в отличие от среза по индексу, который вы вычислили сами. Имя проверяйте через `bytes().all(…)`. Для второго свойства подумайте о строке длиной ровно 1024 байта без пробела после двоеточия.

</details>

<details>
<summary>Ответ</summary>

```rust
//! Task 1: a header line parser that never panics.

/// The longest line we accept, in bytes.
pub const MAX_LINE: usize = 1024;

/// Splits `Name: value` into the name and the trimmed value.
/// The name is 1 to 64 ASCII letters, digits or `-`.
pub fn split_header(line: &str) -> Option<(&str, &str)> {
    if line.len() > MAX_LINE {
        return None;
    }
    let (name, value) = line.split_once(':')?;
    let name_ok = (1..=64).contains(&name.len())
        && name.bytes().all(|b| b.is_ascii_alphanumeric() || b == b'-');
    if !name_ok {
        return None;
    }
    Some((name, value.trim()))
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn splits_a_normal_line() {
        assert_eq!(split_header("Retry-After: 1"), Some(("Retry-After", "1")));
        assert_eq!(split_header("x:"), Some(("x", "")));
    }

    #[test]
    fn rejects_bad_lines() {
        assert_eq!(split_header("no colon"), None);
        assert_eq!(split_header(": empty name"), None);
        assert_eq!(split_header("bad name: x"), None);
        assert_eq!(split_header("é: x"), None);
        assert_eq!(split_header(&"a".repeat(2000)), None);
    }
}

#[cfg(test)]
mod edge_tests {
    use super::*;

    #[test]
    fn writing_a_full_line_again_can_make_it_too_long() {
        let line = format!("x:{}", "a".repeat(MAX_LINE - 2));
        let (name, value) = split_header(&line).unwrap();
        assert_eq!(split_header(&format!("{name}: {value}")), None);
    }
}
```

Фаззинг-цель `fuzz/fuzz_targets/header.rs`:

```rust
#![no_main]

use libfuzzer_sys::fuzz_target;
use p20_checkpoint::header::{MAX_LINE, split_header};

fuzz_target!(|line: &str| {
    // Property 1: never panics. Property 2: a parsed line, written again, parses to the same parts
    // (only if the new line still fits: "x:a" becomes the longer "x: a").
    if let Some((name, value)) = split_header(line) {
        let again = format!("{name}: {value}");
        if again.len() <= MAX_LINE {
            assert_eq!(split_header(&again), Some((name, value)));
        }
    }
});
```

```bash
cargo +nightly fuzz run header -- -max_total_time=30
```

```text

```

Почему это работает: `split_once` и `bytes()` не могут паниковать, а каждая длина проверяется до использования. Второе свойство верно, только пока переписанная строка ещё помещается: `"x:"` + 1022 × `"a"` — ровно 1024 байта, а `"x: "` + … — уже 1025, и такая строка отвергается. Поэтому цель проверяет повторный разбор, только когда `again.len() <= MAX_LINE`. Неверное свойство заставляет фаззер сообщать об «ошибке», которая на самом деле ошибка в тесте; к тому же фаззер может за 30 секунд и не дойти до такого длинного особого входа, поэтому в ответе есть ещё и модульный тест на этот граничный случай.

</details>

### Задание 2 — Контроль допуска со сбросом (Урок 20.8)

Напишите в `src/limiter.rs` тип `Limiter` с `new(max)`, `try_enter(&self) -> Option<…>` и `in_flight(&self) -> usize`. `try_enter` **никогда не должен ждать**: он возвращает разрешение, если место свободно, и сразу `None`, если нет. Удаление разрешения (drop) освобождает место. Клоны `Limiter` делят одни и те же места. Напишите тесты: при лимите 2 третий запрос отвергается; после удаления одного разрешения запрос снова проходит; клоны делят места.

<details>
<summary>Подсказка</summary>

`tokio::sync::Semaphore` считает свободные места. `Arc<Semaphore>::try_acquire_owned()` сразу возвращает `Ok(OwnedSemaphorePermit)` или ошибку; владеющее разрешение возвращает своё место в `Drop`. `available_permits()` говорит, сколько мест свободно.

</details>

<details>
<summary>Ответ</summary>

```rust
//! Task 2: admission control that refuses instead of waiting.

use std::sync::Arc;

use tokio::sync::{OwnedSemaphorePermit, Semaphore};

#[derive(Clone)]
pub struct Limiter {
    slots: Arc<Semaphore>,
    max: usize,
}

impl Limiter {
    pub fn new(max: usize) -> Limiter {
        Limiter {
            slots: Arc::new(Semaphore::new(max)),
            max,
        }
    }

    /// A permit if a slot is free, `None` at once if not. Dropping the permit frees the slot.
    pub fn try_enter(&self) -> Option<OwnedSemaphorePermit> {
        Arc::clone(&self.slots).try_acquire_owned().ok()
    }

    /// How many slots are taken right now.
    pub fn in_flight(&self) -> usize {
        self.max - self.slots.available_permits()
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn refuses_when_full_and_recovers() {
        let limiter = Limiter::new(2);
        let first = limiter.try_enter();
        let second = limiter.try_enter();
        assert!(first.is_some() && second.is_some());
        assert!(
            limiter.try_enter().is_none(),
            "a third request must be shed"
        );
        assert_eq!(limiter.in_flight(), 2);

        drop(first);
        assert_eq!(limiter.in_flight(), 1);
        assert!(limiter.try_enter().is_some());
    }

    #[test]
    fn clones_share_the_slots() {
        let limiter = Limiter::new(1);
        let copy = limiter.clone();
        let _permit = limiter.try_enter().unwrap();
        assert!(copy.try_enter().is_none());
    }
}
```

Почему это работает: семафор — это счётчик свободных мест, а разрешение — guard-объект, как `MutexGuard`: держать его значит «я внутри», удалить — «я вышел», даже если запрос запаниковал или был отменён. Поскольку семафор лежит в `Arc`, клоны делят его; без `Arc` у каждого клона были бы свои места, и лимит бы не работал — та же ошибка, что и построение слоя на каждый запрос.

</details>

### Задание 3 — Бюджет повторов (Уроки 20.8 и 18.3)

Напишите в `src/budget.rs` тип `RetryBudget`: `new(ratio)`, `record_request(&mut self)` для каждой первой попытки и `try_retry(&mut self) -> bool`, который разрешает повтор, только пока повторов не больше `ratio` × число запросов (с округлением вниз), и учитывает его. Тесты: при `0.1` и 100 запросах разрешаются ровно 10 из 20 попыток повтора; без запросов повтор не разрешается.

<details>
<summary>Подсказка</summary>

Храните два счётчика. `(requests as f64 * ratio).floor() as u64` — число разрешённых повторов.

</details>

<details>
<summary>Ответ</summary>

```rust
//! Task 3: a retry budget.

/// Allows retries only while they are at most `ratio` of all requests.
pub struct RetryBudget {
    ratio: f64,
    requests: u64,
    retries: u64,
}

impl RetryBudget {
    pub fn new(ratio: f64) -> RetryBudget {
        RetryBudget {
            ratio,
            requests: 0,
            retries: 0,
        }
    }

    /// Call once for every first attempt.
    pub fn record_request(&mut self) {
        self.requests += 1;
    }

    /// Asks for one retry. `true` means: retry, and it is counted.
    pub fn try_retry(&mut self) -> bool {
        let allowed = (self.requests as f64 * self.ratio).floor() as u64;
        if self.retries < allowed {
            self.retries += 1;
            true
        } else {
            false
        }
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn ten_percent_of_one_hundred_is_ten_retries() {
        let mut budget = RetryBudget::new(0.1);
        for _ in 0..100 {
            budget.record_request();
        }
        let granted = (0..20).filter(|_| budget.try_retry()).count();
        assert_eq!(granted, 10);
    }

    #[test]
    fn no_requests_no_retries() {
        let mut budget = RetryBudget::new(0.1);
        assert!(!budget.try_retry());
    }
}
```

Почему это работает: когда неудачных запросов немного (обычные случайные сбои), бюджета хватает на все их повторы. Когда отказывает сразу много запросов (другой сервис перегружен), бюджет быстро кончается, и клиент перестаёт добавлять нагрузку: шторм повторов не может начаться. Настоящие бюджеты ещё и забывают старые запросы (например, учитывают только последние десять секунд); это хорошее расширение.

</details>
