## Вопросы для самопроверки

1. Запишите `0x2A` в двоичной и в десятичной системе.

<details>
<summary>Ответ</summary>

`0x2A` = `0b0010_1010` = 42. Каждая шестнадцатеричная цифра — четыре бита: `2` = `0010`, `A` = `1010`; 2 × 16 + 10 = 42. (Урок 12.1)

</details>

2. В каком порядке хранятся на вашем Mac байты значения `u32` `0x1234_5678`?

<details>
<summary>Ответ</summary>

`78 56 34 12`: Mac (arm64) — little-endian, поэтому младший байт идёт первым, по наименьшему адресу. `0x1234_5678_u32.to_le_bytes()` даёт `[78, 56, 34, 12]` в шестнадцатеричном виде. Сетевые протоколы обычно используют big-endian, `12 34 56 78`. (Урок 12.1)

</details>

3. Что даёт `-1i8 as u8` и почему?

<details>
<summary>Ответ</summary>

255. В дополнительном коде −1 — это все единицы (`1111_1111`). `as` между типами одной ширины сохраняет биты и меняет только их смысл, а как беззнаковое число все единицы — это 255. (Урок 12.2)

</details>

4. Чему равны `200u8.checked_add(100)` и `200u8.wrapping_add(100)`? И если переменная `x` типа `u8` во время выполнения содержит 200, что делает `x + 100` в сборках debug и release?

<details>
<summary>Ответ</summary>

`checked_add` даёт `None`; `wrapping_add` даёт 44 (300 − 256). `x + 100` паникует с «attempt to add with overflow» в сборке debug, где проверки переполнения включены, и молча заворачивается в 44 в сборке release. (Если записать две константы, `200u8 + 100` даже не скомпилируется: компилятор видит переполнение.) (Уроки 12.2 и 12.8)

</details>

5. Почему `0.1 + 0.2` печатает `0.30000000000000004` и как тест должен сравнивать такие результаты?

<details>
<summary>Ответ</summary>

0.1 и 0.2 нельзя точно записать суммой степеней двойки, поэтому оба округлены, а сумма округляется ещё раз — до значения рядом с 0.3, но не ближайшего к нему. Сравнивайте с допуском, например `(a - b).abs() <= 1e-12 * a.abs().max(b.abs())`, и никогда через `==`. (Урок 12.3)

</details>

6. Чему равно `0b1011_0100 & (0b1011_0100 - 1)` и что в общем случае делает приём `x & (x - 1)`?

<details>
<summary>Ответ</summary>

`0b1011_0000` (176). Вычитание 1 превращает младшую `1` в `0`, а нули под ней — в единицы; AND затем оставляет всё, кроме этой младшей `1`. Поэтому `x & (x - 1)` сбрасывает младший установленный бит и равен 0 ровно тогда, когда `x` равен 0 или степени двойки. (Урок 12.4)

</details>

7. Сколько байт и сколько `char` в строке `"é"`? Сколько байт занимает `'🦀'` в UTF-8 (Unicode Transformation Format, 8-bit, формат преобразования Unicode, 8 бит)?

<details>
<summary>Ответ</summary>

`"é".len()` равно 2 (U+00E9 требует двух байт в UTF-8), а `"é".chars().count()` равно 1. Краб, U+1F980, больше U+FFFF, поэтому занимает 4 байта. (Урок 12.5)

</details>

8. Цикл складывает числа в одну переменную `total`. Почему разбиение на четыре независимые суммы может ускорить его, хотя работа та же?

<details>
<summary>Ответ</summary>

Каждое `total += x` должно ждать предыдущего сложения: это цепочка зависимостей, ограниченная **задержкой** одного сложения. Четыре независимые суммы позволяют ядру с внеочередным выполнением держать несколько сложений «в полёте», и цикл идёт со скоростью **пропускной способности** сумматора. (Урок 12.6)

</details>

9. В каких регистрах функция на arm64 получает первые два целочисленных аргумента и куда возвращает результат? А на x86-64 Linux?

<details>
<summary>Ответ</summary>

arm64: аргументы в `x0` и `x1`, результат в `x0`. x86-64 (соглашение о вызовах System V): аргументы в `rdi` и `rsi`, результат в `rax`. Соблюдение этих правил гарантировано только для функций `extern "C"`. (Урок 12.7)

</details>

10. Назовите две вещи, которые делают сборку release программой, отличной от сборки debug.

<details>
<summary>Ответ</summary>

Оптимизация (`opt-level = 3`: встраивание, свёртка констант, векторизация) и выключенные проверки: проверки переполнения и `debug_assert!`. Проверки границ остаются в обеих, если оптимизатор не докажет, что они никогда не сработают. (Урок 12.8)

</details>

11. Попадание в L1 (кэш уровня 1) на вашем Mac стоит около 1 ns (наносекунды). Сколько примерно стоит загрузка, когда данные есть только в RAM (Random Access Memory, оперативная память), и почему сумма большого массива по порядку не платит эту цену за каждый элемент?

<details>
<summary>Ответ</summary>

Около 100–120 ns. По порядку одна 128-байтовая кэш-линия приносит сразу 16 значений `u64`, а предвыборка видит регулярный шаблон и загружает следующие линии до того, как они понадобятся. Полную задержку каждый раз платят только случайные зависимые обращения (погоня за указателями). (Урок 12.9)

</details>

12. Два потока увеличивают каждый свой счётчик, но программа замедляется, когда стартует второй поток. Счётчики — поля одной маленькой структуры. Что происходит и как это исправить?

<details>
<summary>Ответ</summary>

Ложное разделение: оба счётчика лежат в одной кэш-линии, поэтому каждая запись одного ядра отбирает линию у другого. Дайте каждому счётчику свою линию, например через `#[repr(align(128))]` или `crossbeam_utils::CachePadded`. (Урок 12.10)

</details>

13. Чему равно `size_of::<(u8, u32, u16)>()`? И почему `Option<Box<u8>>` и `Option<u64>` занимают 8 и 16 байт?

<details>
<summary>Ответ</summary>

8: компилятор может переставлять поля кортежа, поэтому он может хранить `u32`, `u16`, `u8` и один байт заполнения. `Box` никогда не бывает нулевым, поэтому `Option<Box<u8>>` использует адрес 0 как `None` (ниша) и остаётся 8-байтовым; каждый битовый шаблон `u64` — допустимое число, поэтому `Option<u64>` нужен отдельный тег, что с заполнением даёт 16. (Урок 12.11)

</details>

14. Сборка падает с «Undefined symbols … referenced from …» в macOS или «undefined reference to …» в Linux. Какой инструмент об этом сообщает и каковы два обычных исправления?

<details>
<summary>Ответ</summary>

Компоновщик (`ld`), уже после успешной компиляции. Символ, который использует ваш код, не определён ни в одном переданном ему объектном файле или библиотеке. Исправление: скомпилировать код, который его определяет (например, крейтом `cc`), или скомпоновать библиотеку, в которой он есть. (Урок 12.12)

</details>

15. Программа успешно компонуется, но при старте падает с «error while loading shared libraries: libfoo.so: cannot open shared object file». Кто об этом сообщает и какие команды помогут разобраться?

<details>
<summary>Ответ</summary>

Загрузчик (`ld.so` в Linux) при старте программы: исполняемый файл называет `libfoo.so` в своём списке `NEEDED`, но загрузчик не находит файл в своих путях поиска. `readelf -d` показывает, что нужно программе, `ldd` — где лежит каждая библиотека (или «not found»); `LD_LIBRARY_PATH` или установка библиотеки решают проблему. В macOS нужные библиотеки перечисляет `otool -L`. (Урок 12.12)

</details>

16. Назовите два правила, которым должна следовать каждая реализация `GlobalAlloc`.

<details>
<summary>Ответ</summary>

Любые два из: возвращать блок как минимум запрошенного размера и выравнивания либо null; никогда не возвращать блок, пересекающийся с живым блоком; никогда не выделять память внутри `alloc` или `dealloc` (ни `println!`, ни `Vec`); быть безопасной при вызове из многих потоков одновременно, потому что она общая через `&self`; `dealloc` получает ровно указатель и размещение из прежнего `alloc`. (Уроки 12.13 и 12.14)

</details>

17. В аллокаторе со списком свободных блоков свободно 32 байта, но запрос на 24 байта не выполняется. Как это называется и какой приём это уменьшает?

<details>
<summary>Ответ</summary>

Внешняя фрагментация: свободная память разбита на блоки, каждый из которых меньше 24 байт. Её уменьшает слияние соседних свободных блоков при освобождении (это легко, когда список отсортирован по адресам). (Урок 12.13)

</details>

### Задание 1 — Байты в порядке хранения

В `src/lib.rs` напишите `pub fn to_hex_le(x: u32) -> String`, которая возвращает четыре байта `x` в порядке little-endian как двузначные шестнадцатеричные числа через пробел: `to_hex_le(0x1234_5678)` — это `"78 56 34 12"`. Добавьте тест для этого значения и для 1.

<details>
<summary>Подсказка</summary>

`x.to_le_bytes()` даёт `[u8; 4]`. `format!("{b:02x}")` печатает один байт двумя шестнадцатеричными цифрами; соберите в `Vec<String>` и сделайте `join(" ")`.

</details>

<details>
<summary>Ответ</summary>

```rust
/// The bytes of `x` in memory order on a little-endian machine, as hex.
pub fn to_hex_le(x: u32) -> String {
    x.to_le_bytes()
        .iter()
        .map(|b| format!("{b:02x}"))
        .collect::<Vec<_>>()
        .join(" ")
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn hex_le_puts_the_lowest_byte_first() {
        assert_eq!(to_hex_le(0x1234_5678), "78 56 34 12");
        assert_eq!(to_hex_le(1), "01 00 00 00");
    }
}
```

`to_le_bytes` делает результат одинаковым на любом компьютере; чтение сырой памяти `x` давало бы little-endian только на little-endian процессоре. (Уроки 12.1 и 12.4)

</details>

### Задание 2 — Среднее, которое не может переполниться

Напишите `pub fn midpoint(a: u32, b: u32) -> u32`: среднее `a` и `b`, округлённое вниз. `(a + b) / 2` переполняется для больших чисел; ваша версия не должна, и она не должна использовать более широкий тип. Проверьте её с `u32::MAX` и сравните с `u32::midpoint` из стандартной библиотеки на нескольких парах.

<details>
<summary>Подсказка</summary>

Биты, общие для `a` и `b`, считаются полностью (`a & b`); биты, в которых они различаются, — наполовину (`(a ^ b) >> 1`). Ни одна часть не может переполниться.

</details>

<details>
<summary>Ответ</summary>

Добавьте в `src/lib.rs` (тесты идут в тот же `mod tests`):

```rust
/// The average of `a` and `b`, rounded down, without overflow.
pub fn midpoint(a: u32, b: u32) -> u32 {
    (a & b) + ((a ^ b) >> 1)
}
```

```rust
    #[test]
    fn midpoint_never_overflows() {
        assert_eq!(midpoint(u32::MAX, u32::MAX), u32::MAX);
        assert_eq!(midpoint(u32::MAX, u32::MAX - 1), u32::MAX - 1);
        assert_eq!(midpoint(3, 4), 3);
        assert_eq!(midpoint(0, 10), 5);
    }

    #[test]
    fn midpoint_matches_the_standard_library() {
        for (a, b) in [(1, 2), (7, 100), (u32::MAX, 0), (12345, 67890)] {
            assert_eq!(midpoint(a, b), a.midpoint(b), "a = {a}, b = {b}");
        }
    }
```

Почему это работает: `a + b = 2 × (a & b) + (a ^ b)`, потому что общие биты считаются дважды, а различающиеся — один раз. Деление на два даёт `(a & b) + (a ^ b) / 2`, и каждая часть не больше `u32::MAX`, как и их сумма. (Уроки 12.2 и 12.4)

</details>

### Задание 3 — Длина в UTF-8 по кодовой точке

Напишите `pub fn utf8_len(c: char) -> usize`, которая возвращает, сколько байт `c` занимает в UTF-8, используя только его кодовую точку (`u32::from(c)`) и диапазоны UTF-8. Проверьте её с `char::len_utf8` для **каждого** `char`.

<details>
<summary>Подсказка</summary>

До `0x7F`: 1 байт; до `0x7FF`: 2; до `0xFFFF`: 3; выше: 4. `char::MIN..=char::MAX` — диапазон, по которому можно пройти циклом; суррогаты он пропускает сам.

</details>

<details>
<summary>Ответ</summary>

/// How many bytes `c` takes in UTF-8, from its code point alone.
pub fn utf8_len(c: char) -> usize {
    match u32::from(c) {
        0..=0x7F => 1,
        0x80..=0x7FF => 2,
        0x800..=0xFFFF => 3,
        _ => 4,
    }
}
```

            assert_eq!(utf8_len(c), c.len_utf8(), "char U+{:04X}", u32::from(c));
        }
    }
```

### Задание 4 — Структура, которая лучше помещается в кэш

Эта структура `repr(C)` описывает одно измерение:

```rust
#[repr(C)]
struct SampleBefore {
    flag: bool,
    time: u64,
    id: u16,
    value: f32,
    kind: u8,
}
```

В `src/bin/task4.rs` посчитайте её размер вручную, затем напишите структуру `Sample` с `repr(C)` и теми же полями в лучшем порядке, добавьте константную проверку `const` её размера и напечатайте, сколько экземпляров каждой помещается в одну 128-байтовую кэш-линию.

<details>
<summary>Подсказка</summary>

Запишите смещения: `flag` на 0, затем `time` должен начинаться с кратного 8. Отсортируйте поля по выравниванию, сначала наибольшее.

</details>

<details>
<summary>Ответ</summary>

```rust
#[allow(dead_code)]
#[repr(C)]
struct SampleBefore {
    flag: bool,
    time: u64,
    id: u16,
    value: f32,
    kind: u8,
}

#[allow(dead_code)]
#[repr(C)]
struct Sample {
    time: u64,
    value: f32,
    id: u16,
    flag: bool,
    kind: u8,
}

const _: () = assert!(size_of::<Sample>() == 16);

fn main() {
    let line = 128;
    let before = size_of::<SampleBefore>();
    let after = size_of::<Sample>();
    println!("before: {before} bytes, {} per cache line", line / before);
    println!("after:  {after} bytes, {} per cache line", line / after);
}
```

```text
before: 32 bytes, 4 per cache line
after:  16 bytes, 8 per cache line
```

Почему это работает: в старом порядке за `flag` (0) идут 7 байт заполнения, `time` на 8, `id` на 16, 2 байта заполнения, `value` на 20, `kind` на 24, и 7 байт заполнения округляют размер до 32. В новом порядке поля заполняют 8 + 4 + 2 + 1 + 1 = 16 байт вообще без заполнения. Вдвое больше измерений на кэш-линию — вдвое меньше трафика памяти для цикла по всем измерениям. (Уроки 12.10 и 12.11)

</details>

### Задание 5 — Меньше выделений памяти

В `src/bin/task5.rs` установите считающий глобальный аллокатор (Урок 12.13) и посчитайте выделения двух функций, которые складывают количество цифр чисел `0..1000`: одна использует в цикле `i.to_string()`, другая повторно использует один буфер `String` через `buffer.clear()` и `write!(buffer, "{i}")`. Напечатайте оба счёта.

<details>
<summary>Подсказка</summary>

`write!` в `String` требует `use std::fmt::Write;`. Читайте счётчик до и после каждой функции. `String`, созданной через `String::with_capacity(10)`, никогда не придётся расти для чисел меньше 1000.

</details>

<details>
<summary>Ответ</summary>

```rust
use std::alloc::{GlobalAlloc, Layout, System};
use std::fmt::Write;
use std::sync::atomic::{AtomicUsize, Ordering};

struct Counting;

static ALLOCATIONS: AtomicUsize = AtomicUsize::new(0);

// SAFETY: every call is passed on unchanged to `System`.
unsafe impl GlobalAlloc for Counting {
    unsafe fn alloc(&self, layout: Layout) -> *mut u8 {
        ALLOCATIONS.fetch_add(1, Ordering::Relaxed);
        // SAFETY: the caller upholds the rules of `GlobalAlloc::alloc`.
        unsafe { System.alloc(layout) }
    }

    unsafe fn dealloc(&self, ptr: *mut u8, layout: Layout) {
        // SAFETY: `ptr` was allocated by `System` with this `layout`.
        unsafe { System.dealloc(ptr, layout) }
    }
}

#[global_allocator]
static GLOBAL: Counting = Counting;

fn digits_new_strings(n: u32) -> usize {
    let mut total = 0;
    for i in 0..n {
        total += i.to_string().len();
    }
    total
}

fn digits_one_buffer(n: u32) -> usize {
    let mut total = 0;
    let mut buffer = String::with_capacity(10);
    for i in 0..n {
        buffer.clear();
        write!(buffer, "{i}").expect("writing to a String cannot fail");
        total += buffer.len();
    }
    total
}

fn main() {
    let before = ALLOCATIONS.load(Ordering::Relaxed);
    let a = digits_new_strings(1000);
    let middle = ALLOCATIONS.load(Ordering::Relaxed);
    let b = digits_one_buffer(1000);
    let after = ALLOCATIONS.load(Ordering::Relaxed);
    println!("new strings: {a} digits, {} allocations", middle - before);
    println!("one buffer:  {b} digits, {} allocations", after - middle);
}
```

```text
new strings: 2890 digits, 1000 allocations
one buffer:  2890 digits, 1 allocations
```

Почему это работает: каждый `to_string()` создаёт новую `String` в куче, которая снова освобождается в конце тела цикла. `clear()` обнуляет длину, но сохраняет ёмкость, поэтому буфер выделяется один раз и используется 1000 раз. Результат (2890 цифр) доказывает, что обе версии сделали одну и ту же работу. (Урок 12.13)
