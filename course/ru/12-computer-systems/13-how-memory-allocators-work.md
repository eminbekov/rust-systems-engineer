## Новые слова

| Слово | Значение |
|---|---|
| **аллокатор** (allocator) | Код, который по запросу выдаёт блоки памяти из кучи и забирает их обратно, когда они освобождаются. |
| **выделить / освободить** (allocate / deallocate, free) | Попросить у аллокатора блок / вернуть блок. |
| **блок** (block) | Один кусок памяти, выданный аллокатором. |
| **`Layout`** | Тип Rust (`std::alloc::Layout`), который описывает блок: его размер и выравнивание. |
| **глобальный аллокатор** (global allocator) | Единственный аллокатор, которым в программе пользуются `Box`, `Vec`, `String` и все остальные стандартные коллекции. |
| **`GlobalAlloc`** | Трейт, который должен реализовать тип, чтобы стать глобальным аллокатором. |
| **`System`** | Аллокатор операционной системы (`malloc` и `free` из библиотеки C). Rust использует его по умолчанию. |
| **арена** (arena) | Большая область памяти, которую аллокатор режет на блоки. |
| **bump-аллокатор** (bump allocator) | Аллокатор, который выдаёт блоки, сдвигая один указатель вперёд, и освобождает всё сразу. |
| **список свободных блоков** (free list) | Связный список свободных блоков, который ведёт аллокатор, чтобы повторно использовать освобождённую память. |
| **заголовок** (header) | Несколько байт перед блоком (или внутри него), где аллокатор хранит свою информацию, например размер блока. |
| **разделение / слияние** (splitting / coalescing) | Разрезание большого свободного блока на нужную часть и меньший свободный остаток / объединение соседних свободных блоков в один. |
| **фрагментация** (fragmentation) | Потерянная память: внутри блоков (*внутренняя*: заполнение, округление) или между блоками (*внешняя*: свободная память разрезана на слишком мелкие куски). |
| **класс размера** (size class) | Фиксированный размер блока (16, 32, 48, … байт). Настоящие аллокаторы округляют каждый запрос до класса размера и держат по списку свободных блоков на класс. |
| **OOM** (Out Of Memory, нехватка памяти) | Ситуация, когда аллокатор не может выдать запрошенную память. |

## 1. От `Box::new` до операционной системы

Когда вы пишете `Box::new(5_u64)`, Rust нужно 8 байт памяти в куче. Он не обращается к операционной системе напрямую — это было бы медленно, потому что каждый запрос к ядру — системный вызов (Этап 13). Вместо этого между ними есть слой:

```text
   your code:     Box::new, Vec::push, String::from, format!, …
                        │ alloc(Layout { size: 8, align: 8 })
                        ▼
   global allocator:  by default `System` = malloc / free of the C library
                        │ only when its own reserve runs out:
                        ▼ "give me 1 MiB more"
   operating system:  mmap (maps fresh pages into the process)
```

Аллокатор время от времени получает от операционной системы большие области и режет их для вас на маленькие блоки — очень часто и очень быстро. Когда вы освобождаете блок, он обычно **не** возвращается операционной системе; аллокатор оставляет его у себя и отдаёт при следующем запросе.

Каждый аллокатор должен быстро отвечать на два вопроса: «где свободный блок такого размера и выравнивания?» и «куда девать этот освобождённый блок?». Остальная часть урока показывает несколько ответов.

> ⚡ **Производительность:** выделение памяти занимает от нескольких наносекунд до гораздо большего — в зависимости от аллокатора и размера, и каждое выделение может затронуть память, которой нет в кэше. Код, который выделяет память в горячем цикле, часто медленнее из-за аллокатора, а не из-за собственной работы. Раздел 3 показывает, как считать выделения.

## 2. `Layout` и выделение вручную

Аллокатору нужны два числа: сколько байт и какое выравнивание (Урок 12.11). `std::alloc::Layout` хранит оба и проверяет, что они осмысленны (выравнивание — степень двойки, размер не переполняется). Глобальный аллокатор можно вызвать самому через `std::alloc::alloc` и `dealloc`. Это `unsafe`, потому что компилятор не может проверить, что вы освободите блок ровно один раз, с тем же размещением, и не будете использовать его после этого. Поместите это в `src/main.rs`:

```rust
use std::alloc::{Layout, alloc, dealloc};

fn main() {
    // Ask for room for 4 u32 values, aligned for u32.
    let layout = Layout::array::<u32>(4).expect("size fits in isize");
    println!("size {} bytes, align {}", layout.size(), layout.align());

    // SAFETY: the layout has a non-zero size.
    let ptr = unsafe { alloc(layout) } as *mut u32;
    if ptr.is_null() {
        std::alloc::handle_alloc_error(layout);
    }

    // SAFETY: ptr points to room for 4 u32 values that we own.
    unsafe {
        for i in 0..4 {
            ptr.add(i).write(10 * (i as u32 + 1));
        }
        let values = std::slice::from_raw_parts(ptr, 4);
        println!("values {values:?} at {ptr:p}");
        dealloc(ptr as *mut u8, layout);
    }
}
```

```text
size 16 bytes, align 4
values [10, 20, 30, 40] at 0x104d21450
```

**Что происходит:**

1. `Layout::array::<u32>(4)` описывает место для четырёх `u32`: 16 байт, выравнивание 4. Ошибку он возвращает, только если размер получился бы абсурдно большим. `Layout::new::<T>()` делает то же для одного значения типа `T`.
2. `alloc(layout)` возвращает `*mut u8` — сырой указатель на неинициализированную память. Нулевой указатель означает, что аллокатор не смог выдать память (OOM, нехватка памяти); тогда `handle_alloc_error` останавливает программу — ровно так поступил бы `Vec`.
3. `ptr.add(i).write(…)` кладёт значения в блок. Для `u32` подошло бы и простое присваивание через `*ptr = …`, но `write` — правильная привычка для памяти, которая никогда не была инициализирована.
4. `dealloc(ptr, layout)` возвращает блок. Он должен получить **тот же указатель и то же размещение**, что использовал `alloc`. Аллокатор может полагаться на размещение, чтобы узнать размер блока.

Запустите и под Miri: `cargo +nightly miri run`. Он печатает те же строки (с другим адресом) и никаких ошибок, потому что все правила соблюдены.

> 🔒 **Безопасность:** ошибки use-after-free (использование после освобождения) и double free (двойное освобождение) в аллокаторах — классические дыры в безопасности: атакующий, который может заставить программу повторно использовать освобождённый блок, часто может управлять его содержимым. Безопасный Rust (`Box`, `Vec`) делает их невозможными; в коде аллокатора с `unsafe` вы должны предотвращать их сами, а Miri помогает их находить.

## 3. `GlobalAlloc`: замена аллокатора

Каждый `Box`, `Vec` и `String` вызывает **глобальный аллокатор**. Можно установить свой: напишите тип, реализующий трейт `GlobalAlloc`, и пометьте одну `static` этого типа атрибутом `#[global_allocator]`. У трейта два обязательных метода:

```text
unsafe trait GlobalAlloc {
    unsafe fn alloc(&self, layout: Layout) -> *mut u8;
    unsafe fn dealloc(&self, ptr: *mut u8, layout: Layout);
    // with default implementations: alloc_zeroed, realloc
}
```

Сам трейт реализовывать `unsafe`: вы обещаете возвращать блок, который действительно имеет запрошенный размер и выравнивание и которым больше никто не пользуется. Вызывать методы `unsafe`: вызывающая сторона обещает передавать размещение ненулевого размера и освобождать только блоки этого аллокатора с их исходным размещением.

Первый аллокатор не делает собственной работы. Он передаёт каждый вызов в `System` и считает вызовы. Замените `src/main.rs`:

```rust
use std::alloc::{GlobalAlloc, Layout, System};
use std::sync::atomic::{AtomicUsize, Ordering};

/// Wraps the system allocator and counts what passes through it.
struct Counting;

static ALLOCATIONS: AtomicUsize = AtomicUsize::new(0);
static BYTES: AtomicUsize = AtomicUsize::new(0);

// SAFETY: every call is passed on unchanged to `System`, which is a correct allocator.
unsafe impl GlobalAlloc for Counting {
    unsafe fn alloc(&self, layout: Layout) -> *mut u8 {
        ALLOCATIONS.fetch_add(1, Ordering::Relaxed);
        BYTES.fetch_add(layout.size(), Ordering::Relaxed);
        // SAFETY: the caller of `alloc` upholds the rules of `GlobalAlloc::alloc`.
        unsafe { System.alloc(layout) }
    }

    unsafe fn dealloc(&self, ptr: *mut u8, layout: Layout) {
        // SAFETY: `ptr` was allocated by `System` with this `layout`.
        unsafe { System.dealloc(ptr, layout) }
    }
}

#[global_allocator]
static GLOBAL: Counting = Counting;

/// Runs `work` and prints how many allocations it made.
fn count(name: &str, work: impl FnOnce()) {
    let before_count = ALLOCATIONS.load(Ordering::Relaxed);
    let before_bytes = BYTES.load(Ordering::Relaxed);
    work();
    let count = ALLOCATIONS.load(Ordering::Relaxed) - before_count;
    let bytes = BYTES.load(Ordering::Relaxed) - before_bytes;
    println!("{name:<28} {count:>3} allocations, {bytes:>5} bytes");
}

fn main() {
    count("let x = 5", || {
        let x = 5;
        std::hint::black_box(x);
    });
    count("Box::new(5_u64)", || {
        std::hint::black_box(Box::new(5_u64));
    });
    count("String::from(\"hello\")", || {
        std::hint::black_box(String::from("hello"));
    });
    count("Vec: push 1000 times", || {
        let mut v = Vec::new();
        for i in 0..1000_u32 {
            v.push(i);
        }
        std::hint::black_box(v);
    });
    count("Vec::with_capacity(1000)", || {
        let mut v = Vec::with_capacity(1000);
        for i in 0..1000_u32 {
            v.push(i);
        }
        std::hint::black_box(v);
    });
    count("format!(\"{} {}\", 1, 2)", || {
        std::hint::black_box(format!("{} {}", 1, 2));
    });
}
```

```text
let x = 5                      0 allocations,     0 bytes
Box::new(5_u64)                1 allocations,     8 bytes
String::from("hello")          1 allocations,     5 bytes
Vec: push 1000 times           9 allocations,  8176 bytes
Vec::with_capacity(1000)       1 allocations,  4000 bytes
format!("{} {}", 1, 2)         1 allocations,     3 bytes
```

**Что происходит:**

1. `Counting` — тип нулевого размера; всё его состояние — в двух атомарных счётчиках, потому что глобальный аллокатор общий для всех потоков, а методы `GlobalAlloc` получают только `&self`.
2. `#[global_allocator] static GLOBAL: Counting = Counting;` устанавливает его. С этого момента каждое выделение памяти в куче в программе проходит через `Counting::alloc`, включая выделения внутри стандартной библиотеки.
3. `let x = 5` живёт на стеке: выделений нет вообще.
4. Добавление 1000 чисел в пустой `Vec` даёт 9 выделений. Ёмкость растёт 4, 8, 16, …, 1024 (Урок 07.3). Каждый рост вызывает `realloc`; мы не писали `realloc`, поэтому используется версия трейта по умолчанию, которая вызывает наш `alloc` для нового блока, копирует данные и вызывает `dealloc` для старого. Всего запрошено 4 × (4 + 8 + … + 1024) = 8176 байт.
5. `Vec::with_capacity(1000)` просит один раз, ровно 4000 байт. Если вы заранее знаете размер, сообщите его коллекции.

> 💡 **Совет:** считающий аллокатор — дешёвый и точный инструмент профилирования. Оберните им тест или обработчик запроса, чтобы увидеть, сколько выделений он делает; полноценные профилировщики памяти — на Этапе 19.

## 4. Bump-аллокатор

Самый простой настоящий аллокатор — **bump-аллокатор**. У него есть арена и одно число `next` — первый свободный адрес. Чтобы выделить блок, он округляет `next` вверх до нужного выравнивания, выдаёт этот адрес и сдвигает `next` вперёд на размер. Освобождение одного блока ничего не делает; вся арена снова становится свободной, только когда освобождены *все* блоки.

```text
   arena: addresses 1000 … 1063

   start                                   alloc(1, align 1) → 1000
   [a.......................................]  next = 1001
         alloc(8, align 8): round 1001 up to 1008 → 1008
   [a|pad|bbbbbbbb..........................]  next = 1016
         alloc(4, align 4) → 1016
   [a|pad|bbbbbbbb|cccc.....................]  next = 1020
```

Округление вверх — классический битовый приём (Урок 12.4): если `align` — степень двойки, `(addr + align - 1) & !(align - 1)` прибавляет ровно столько, чтобы дойти до следующего кратного, и затем обнуляет младшие биты. Чтобы посмотреть на алгоритм без небезопасного кода, эта модель работает с обычными числами вместо настоящей памяти. Поместите её в `src/lib.rs`:

```rust
/// Rounds `addr` up to the next multiple of `align`.
/// `align` must be a power of two.
pub fn align_up(addr: usize, align: usize) -> usize {
    debug_assert!(align.is_power_of_two());
    (addr + align - 1) & !(align - 1)
}

/// A bump allocator that works on plain numbers instead of real memory,
/// so that we can watch the algorithm. `start..end` is the arena.
pub struct BumpModel {
    start: usize,
    next: usize,
    end: usize,
    live: usize,
}

impl BumpModel {
    pub fn new(start: usize, size: usize) -> BumpModel {
        BumpModel {
            start,
            next: start,
            end: start + size,
            live: 0,
        }
    }

    /// Returns the address of a new block, or `None` if the arena is full.
    pub fn alloc(&mut self, size: usize, align: usize) -> Option<usize> {
        let start = align_up(self.next, align);
        let new_next = start.checked_add(size)?;
        if new_next > self.end {
            return None;
        }
        self.next = new_next;
        self.live += 1;
        Some(start)
    }

    /// A bump allocator cannot reuse one block. It only counts, and when
    /// the last live block is freed, it starts again from the beginning.
    pub fn dealloc(&mut self) {
        self.live -= 1;
        if self.live == 0 {
            self.next = self.start;
        }
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn align_up_rounds_to_the_next_multiple() {
        assert_eq!(align_up(0, 8), 0);
        assert_eq!(align_up(1, 8), 8);
        assert_eq!(align_up(8, 8), 8);
        assert_eq!(align_up(13, 4), 16);
        assert_eq!(align_up(13, 1), 13);
    }

    #[test]
    fn blocks_are_aligned_and_do_not_overlap() {
        let mut bump = BumpModel::new(1000, 64);
        let a = bump.alloc(1, 1).unwrap(); // 1000
        let b = bump.alloc(8, 8).unwrap(); // 1008: 1001 rounded up
        let c = bump.alloc(4, 4).unwrap(); // 1016
        assert_eq!((a, b, c), (1000, 1008, 1016));
    }

    #[test]
    fn a_full_arena_returns_none() {
        let mut bump = BumpModel::new(0, 16);
        assert!(bump.alloc(16, 1).is_some());
        assert_eq!(bump.alloc(1, 1), None);
    }

    #[test]
    fn freeing_everything_resets_the_arena() {
        let mut bump = BumpModel::new(0, 16);
        bump.alloc(10, 1).unwrap();
        bump.alloc(6, 1).unwrap();
        bump.dealloc();
        assert_eq!(bump.alloc(1, 1), None, "one block is still live");
        bump.dealloc();
        assert_eq!(bump.alloc(16, 1), Some(0), "all freed: start again");
    }
}
```

```text
running 4 tests
....
test result: ok. 4 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

(Это `cargo test -q --lib`.)

**Что происходит:**

1. Пример `align_up`: `addr = 13`, `align = 4`. `13 + 3 = 16` (в двоичной записи `10000`), а `!(4 - 1)` — маска с двумя обнулёнными младшими битами, поэтому результат 16. Если `addr` уже выровнен, прибавление `align - 1` не доходит до следующего кратного, и он остаётся прежним.
2. `alloc` использует `checked_add`: огромный `size` должен дать `None`, а не переполнение, которое заворачивается в маленький адрес (Урок 12.2). Такая ошибка в аллокаторе выдала бы память, принадлежащую кому-то другому.
3. `live` считает блоки, которые ещё используются. Только когда он доходит до нуля, `next` может вернуться к `start`.

Bump-выделение чрезвычайно быстрое (несколько инструкций), и заголовков нет вообще. Оно идеально, когда много объектов создаются вместе и вместе умирают: один запрос в веб-сервере, один кадр в игре, один проход компилятора. Крейт `bumpalo` (версия 3.20) предлагает такую арену для обычного кода на Rust. В роли *глобального* аллокатора для долго работающих программ он плох: память переиспользуется, только когда освобождено всё. В проекте (Урок 12.14) вы превратите эту модель в настоящий `GlobalAlloc` над настоящей ареной.

## 5. Списки свободных блоков, разделение и слияние

Чтобы повторно использовать отдельные блоки, аллокатор должен помнить, какие блоки свободны. Классический способ — **список свободных блоков**: каждый свободный блок хранит внутри своих (неиспользуемых) байт свой размер и указатель на следующий свободный блок. Список не стоит лишней памяти, потому что живёт в памяти, которой сейчас никто не пользуется.

```text
   heap:   [ used 16 ][ FREE 32  ][ used 16 ][ FREE 64          ]
                       │ size 32               │ size 64
   head ──────────────►│ next ─────────────────►│ next ──► (none)
```

**Выделение** по принципу *первого подходящего* (first fit): пройти по списку и взять первый блок, которого хватает (с учётом выравнивания). Если он намного больше нужного, **разделить** его: выдать переднюю часть, а остаток вернуть в список как меньший свободный блок.

```text
   alloc(16) from the FREE 32 block:
   [ used 16 ][ NEW 16 ][ FREE 16 ][ used 16 ][ FREE 64 ]
```

**Освобождение**: вернуть блок в список. Если его сосед в памяти тоже свободен, **слить** их в один больший блок, иначе куча постепенно распадается на мелкие куски. Слияние проще всего, когда список **отсортирован по адресам**: тогда соседи блока — его соседи в списке.

```text
   free the 16-byte block between two free blocks:
   before: [ FREE 16 ][ used 16 ][ FREE 32 ]
   after:  [ FREE 64                       ]
```

Остаются два вида потерь:

- **Внутренняя фрагментация**: память, потерянная внутри блоков, например заполнение для выравнивания или запрос на 17 байт, округлённый до 32.
- **Внешняя фрагментация**: свободной памяти в сумме достаточно, но она разрезана на куски, каждый из которых слишком мал. Упражнение 4 показывает это на числах.

Есть и другие стратегии поиска: *лучший подходящий* (best fit — самый маленький подходящий блок: меньше потерь, но нужно просмотреть весь список) и *следующий подходящий* (next fit — продолжить с места, где остановился прошлый поиск). И каждый аллокатор со списком свободных блоков должен решить, где хранить размер блока, чтобы `dealloc` мог его найти. В Rust это проще, чем в C: `dealloc` получает `Layout`, поэтому размер известен и без заголовка.

## 6. Как настоящие аллокаторы остаются быстрыми

Один список свободных блоков под одной блокировкой был бы медленным: долгий поиск, и все потоки ждут одну и ту же блокировку. Системный `malloc`, jemalloc и mimalloc используют похожие идеи:

1. **Классы размеров.** Каждый маленький запрос округляется до одного из нескольких десятков размеров (8, 16, 32, 48, 64, …). У каждого класса свой список свободных блоков, поэтому «найти блок» — это просто «взять первый»: ни поиска, ни разделения. Цена — некоторая внутренняя фрагментация.
2. **Страницы на класс размера.** Блоки одного класса нарезаются из одной страницы памяти (например, 16 KiB на вашем Mac), поэтому аллокатор узнаёт класс блока по его адресу.
3. **Кэши на каждый поток.** Каждый поток держит для себя несколько свободных блоков каждого класса. Большинство выделений и освобождений вообще не берут блокировку.
4. **Большие блоки — прямо от операционной системы.** Запросы больше некоторого предела (часто сотни KiB) получают собственные страницы через `mmap` и возвращаются через `munmap` при освобождении.

Заменить глобальный аллокатор Rust на один из них — три строки и одна зависимость (`cargo add mimalloc@0.1`):

```rust
use mimalloc::MiMalloc;

#[global_allocator]
static GLOBAL: MiMalloc = MiMalloc;

fn main() {
    let words: Vec<String> = (0..5).map(|i| format!("word{i}")).collect();
    println!("{}", words.join(" "));
}
```

```text
word0 word1 word2 word3 word4
```

Больше в программе ничего не меняется: `Vec`, `String` и `format!` теперь используют mimalloc. (`tikv-jemallocator`, версия 0.7, работает так же для jemalloc.) Быстрее ли это для *вашей* программы, скажет только бенчмарк (Урок 05.12).

> 📏 **Соглашение:** выбирайте глобальный аллокатор только в итоговом бинарнике (`main.rs`), никогда в библиотеке: библиотека, которая задаёт `#[global_allocator]`, навязала бы свой выбор каждой программе, которая её использует, а глобальный аллокатор в программе может быть только один.

## Частые ошибки

**1. Освобождение с другим размещением.** Размещение, переданное в `dealloc`, должно быть тем же, что и для `alloc`. Программа может казаться рабочей; Miri это не принимает:

```rust
use std::alloc::{Layout, alloc, dealloc};

fn main() {
    let layout = Layout::array::<u32>(4).expect("size fits in isize");
    // SAFETY: the layout has a non-zero size.
    let ptr = unsafe { alloc(layout) };
    if ptr.is_null() {
        std::alloc::handle_alloc_error(layout);
    }
    let wrong = Layout::array::<u32>(8).expect("size fits in isize");
    // BUG: the layout must be the same one that was used for `alloc`.
    unsafe { dealloc(ptr, wrong) };
    println!("freed");
}
```

`cargo run` печатает `freed`. `cargo +nightly miri run` останавливается:

```text
error: Undefined Behavior: incorrect layout on deallocation: alloc294 has size 16 and alignment 4, but gave size 32 and alignment 4
  --> src/main.rs:12:14
   |
12 |     unsafe { dealloc(ptr, wrong) };
   |              ^^^^^^^^^^^^^^^^^^^ Undefined Behavior occurred here
```

Храните размещение рядом с указателем (как `Vec` хранит свою ёмкость), чтобы всегда освобождать с исходным.

**2. Забыть освободить.** Блок, который никогда не освобождается, — это **утечка**. Rust не считает утечку UB (Undefined Behaviour, неопределённое поведение), но Miri сообщает о ней в конце запуска:

```rust
use std::alloc::{Layout, alloc};

fn main() {
    let layout = Layout::new::<u64>();
    // SAFETY: the layout has a non-zero size.
    let ptr = unsafe { alloc(layout) };
    println!("allocated at {ptr:p}, never freed");
}
```

```text
allocated at 0x812b0, never freed
error: memory leaked: alloc283 (Rust heap, size: 8, align: 8), allocated here:
 --> src/main.rs:6:24
  |
6 |     let ptr = unsafe { alloc(layout) };
  |                        ^^^^^^^^^^^^^
```

**3. Выделение памяти внутри аллокатора.** Код внутри `GlobalAlloc::alloc` не должен выделять память, потому что это снова вызывает `alloc`. Соблазнительная отладочная строка `println!("alloc {} bytes", layout.size());` внутри `alloc` привела к тому, что тестовая программа ничего не напечатала и зависла навсегда (её пришлось остановить снаружи через 10 секунд): `println!` самому нужен буфер в куче и блокировка стандартного вывода. Считайте с помощью атомарных операций, как в разделе 3, и печатайте числа потом.

**4. Забыть, что глобальный аллокатор общий.** Методы `GlobalAlloc` принимают `&self` и могут вызываться из многих потоков одновременно. Общему состоянию нужны атомарные операции или блокировка. `Cell` внутри аллокатора даже не скомпилируется (`static` должен быть `Sync`, а `Cell` — нет), а изменение `static mut` из нескольких потоков — это гонка данных, то есть UB.

## Упражнения

### Упражнение 1 — Округление вручную (легко)

Вычислите на бумаге `align_up(17, 8)`, `align_up(32, 16)`, `align_up(5, 1)` и `align_up(1, 4096)`. Затем объясните одним предложением, почему приём работает, только когда `align` — степень двойки.

<details>
<summary>Подсказка</summary>

Запишите числа в двоичном виде. `!(align - 1)` для `align = 8` — маска, которая заканчивается на `…11111000`.

</details>

<details>
<summary>Ответ</summary>

`align_up(17, 8)` = 24 (17 + 7 = 24, уже кратно 8). `align_up(32, 16)` = 32 (уже выровнено). `align_up(5, 1)` = 5 (выравнивание 1 ничего не меняет). `align_up(1, 4096)` = 4096.

Почему только степени двойки: у степени двойки `align - 1` — это ряд единичных битов (8 − 1 = `0b111`), поэтому `& !(align - 1)` обнуляет ровно биты ниже выравнивания. Для 6 `6 - 1 = 0b101` — не такой ряд, и маска даёт неверные результаты; по этой причине `Layout` отвергает выравнивания, не являющиеся степенью двойки.

</details>

### Упражнение 2 — Сколько осталось? (средне)

Добавьте в `BumpModel` метод `pub fn remaining(&self) -> usize`: свободные байты в конце арены. Напишите два теста: заполнение считается занятым (в арене на 32 байта `alloc(1, 1)`, а затем `alloc(8, 8)` оставляют 16 байт) и блок нулевого размера не занимает места (`alloc(0, 1)` в арене на 8 байт возвращает начало и оставляет 8).

<details>
<summary>Подсказка</summary>

`remaining` — одно вычитание. Посчитайте заполнение в первом тесте вручную: второй блок начинается с 8, а не с 1.

</details>

<details>
<summary>Ответ</summary>

Добавьте в `impl BumpModel`:

```rust
    /// How many bytes are still free at the end of the arena.
    pub fn remaining(&self) -> usize {
        self.end - self.next
    }
```

Добавьте в `mod tests`:

```rust
    #[test]
    fn remaining_counts_padding_as_used() {
        let mut bump = BumpModel::new(0, 32);
        assert_eq!(bump.remaining(), 32);
        bump.alloc(1, 1).unwrap();
        bump.alloc(8, 8).unwrap(); // 7 bytes of padding before it
        assert_eq!(bump.remaining(), 16);
    }

    #[test]
    fn zero_sized_blocks_take_no_space() {
        let mut bump = BumpModel::new(0, 8);
        assert_eq!(bump.alloc(0, 1), Some(0));
        assert_eq!(bump.remaining(), 8);
    }
```

```text
running 6 tests
......
test result: ok. 6 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Почему это работает: после первого блока `next` равен 1; второй блок выровнен по 8, поэтому занимает 8..16, и `next` становится 16; 32 − 16 = 16. 7 байт заполнения (1..8) потеряны до сброса арены: внутренняя фрагментация. Настоящий `GlobalAlloc` никогда не видит размер 0 (правила это запрещают), но модель всё равно должна вести себя разумно.

</details>

### Упражнение 3 — Итераторы и выделения (средне)

С помощью считающего аллокатора из раздела 3 посчитайте две строки: `let v: Vec<u32> = (0..1000).collect();` и `let v: Vec<u32> = (0..1000).filter(|x| x % 2 == 0).collect();`. Второй вектор вдвое короче. Почему он делает больше выделений?

<details>
<summary>Подсказка</summary>

`collect` спрашивает у итератора подсказку о размере (`size_hint`, Урок 05.5) и сразу резервирует столько. Насколько точно `filter` может знать свою длину?

</details>

<details>
<summary>Ответ</summary>

Замените `main` в считающей программе на:

```rust
fn main() {
    count("collect 1000 from a range", || {
        let v: Vec<u32> = (0..1000).collect();
        std::hint::black_box(v);
    });
    count("collect 500 after filter", || {
        let v: Vec<u32> = (0..1000).filter(|x| x % 2 == 0).collect();
        std::hint::black_box(v);
    });
}
```

```text
collect 1000 from a range      1 allocations,  4000 bytes
collect 500 after filter       8 allocations,  4080 bytes
```

Почему это работает: диапазон знает свою точную длину, поэтому `collect` один раз выделяет 4000 байт. `filter` не может знать, сколько элементов пройдёт; его подсказка о размере говорит «от 0 до 1000», поэтому `collect` начинает с малого и растёт: ёмкости 4, 8, …, 512 — восемь выделений и всего 4080 байт. Если у вас есть хорошая оценка, используйте `Vec::with_capacity(n)` и `extend`.

</details>

### Упражнение 4 — Список свободных блоков на бумаге (сложно)

Аллокатор со списком свободных блоков управляет 64 байтами по смещениям 0..64. Он использует первый подходящий блок, разделяет блоки, держит список отсортированным по адресам и сливает соседей. Заголовки и выравнивание не учитывайте. Запишите список свободных блоков после каждого шага и скажите, что происходит на шаге 5:

1. `a = alloc(16)` 2. `b = alloc(16)` 3. `c = alloc(16)` 4. `free(b)` 5. `d = alloc(24)` 6. `free(a)` 7. `d = alloc(24)` 8. `free(c)`

<details>
<summary>Подсказка</summary>

Записывайте свободные блоки как диапазоны, например `[16..32)`. На шаге 5 посчитайте свободные байты в сумме, затем посмотрите на размер каждого свободного блока.

</details>

<details>
<summary>Ответ</summary>

| Шаг | Результат | Список свободных блоков после шага |
|---|---|---|
| начало | | `[0..64)` |
| 1. `a = alloc(16)` | a = 0 | `[16..64)` |
| 2. `b = alloc(16)` | b = 16 | `[32..64)` |
| 3. `c = alloc(16)` | c = 32 | `[48..64)` |

## Вопросы для самопроверки

1. Почему Rust не просит память у операционной системы при каждом `Box::new`?

<details>
<summary>Ответ</summary>

Каждый запрос к ядру — системный вызов, а это медленно по сравнению с несколькими инструкциями в программе. Аллокатор время от времени получает большие области и быстро выдаёт из них маленькие блоки, повторно используя освобождённые.

</details>

2. Какие два числа хранит `Layout` и зачем он нужен `dealloc`?

<details>
<summary>Ответ</summary>

Размер и выравнивание блока. Они нужны `dealloc`, потому что аллокатор может использовать их, чтобы найти класс размера блока или размер, который нужно вернуть; правила требуют ровно того размещения, которое использовалось в `alloc`.

</details>

3. Как заменить глобальный аллокатор и почему его состояние должно быть потокобезопасным?

<details>
<summary>Ответ</summary>

Реализовать `GlobalAlloc` для типа и объявить `#[global_allocator] static NAME: Type = …;`. Все потоки программы одновременно выделяют память через это одно значение, по `&self`, поэтому его состоянию нужны атомарные операции или блокировки.

</details>

4. В чём сильные и слабые стороны bump-аллокатора?

<details>
<summary>Ответ</summary>

Сильные: выделение — несколько инструкций, заголовков нет, а освобождение всей арены сразу мгновенно. Слабые: отдельные блоки нельзя использовать повторно; память возвращается, только когда освобождён каждый блок арены, поэтому долго работающая программа со смешанными временами жизни объектов исчерпывает память.

</details>

5. Чем внутренняя фрагментация отличается от внешней?

<details>
<summary>Ответ</summary>

Внутренняя: потерянные байты внутри выданных блоков (заполнение для выравнивания, округление до класса размера). Внешняя: свободной памяти в сумме достаточно, но она разбита на куски, каждый из которых слишком мал для запроса.

</details>

6. Назовите два приёма, благодаря которым аллокаторы вроде mimalloc быстры при многих потоках.

<details>
<summary>Ответ</summary>

Классы размеров (по списку свободных блоков на размер, поэтому нет ни поиска, ни разделения) и кэши на каждый поток (большинство выделений и освобождений не берут блокировку). Большие запросы идут прямо к операционной системе через `mmap`.

</details>

## Итоги

- **Аллокатор** выдаёт и забирает блоки кучи; глобальный аллокатор Rust по умолчанию — `System` (`malloc`/`free`), который получает большие области от операционной системы и режет их.
- `Layout` (размер + выравнивание) описывает каждый блок; `std::alloc::alloc` и `dealloc` — сырой интерфейс с `unsafe`, и `dealloc` должен получить то же размещение, что и `alloc`.
- Реализация `GlobalAlloc` и объявление `static` с `#[global_allocator]` заменяют аллокатор для всей программы; его состояние общее для всех потоков.
- Считающий аллокатор показывает настоящие числа: рост `Vec`, `with_capacity` и подсказки о размере итераторов меняют, как часто вы выделяете память.
- **Bump-аллокатор** сдвигает указатель вперёд с помощью `align_up` и освобождает всё сразу; **аллокатор со списком свободных блоков** повторно использует блоки через первый подходящий, разделение и слияние и страдает от **фрагментации**.
- Настоящие аллокаторы используют **классы размеров**, **кэши на каждый поток** и `mmap` для больших блоков; замена на mimalloc или jemalloc — три строки в `main.rs`.
- Miri ловит неверные размещения, двойные освобождения, использование после освобождения и утечки: запускайте его на каждом аллокаторе, который пишете.
