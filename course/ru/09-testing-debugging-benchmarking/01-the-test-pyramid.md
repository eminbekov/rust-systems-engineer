# Урок 09.1 — Пирамида тестов и стратегия тестирования

> **Этап 09 — Тестирование, отладка и бенчмарки** · Урок 1 из 14 · ⏱ около 2,5 часа (2 занятия)

## Что вы узнаете

- Три уровня тестов (модульные, интеграционные, сквозные), сколько стоит каждый и что каждый доказывает.
- Почему у здорового набора тестов форма пирамиды и что происходит, когда пирамида перевёрнута.
- Как одна и та же ошибка выглядит на каждом уровне (вы увидите это на реальном выводе).
- Короткий набор правил: *что и где тестировать* и как делать тесты надёжными.

## Новые слова

| Слово | Значение |
|---|---|
| **уровень теста** (test level) | Охват теста: сколько программы он запускает за раз. Мы используем три уровня: модульный, интеграционный, сквозной. |
| **модульный тест** (unit test) | Тест одной небольшой части (одной функции или типа), обычно в том же файле, внутри `#[cfg(test)] mod tests`. |
| **интеграционный тест** (integration test) | Тест в папке `tests/`, который использует ваш крейт снаружи, через его публичный API (Application Programming Interface, программный интерфейс: элементы, которые ваш крейт предлагает другому коду), не запуская программу. |
| **сквозной тест** (end-to-end test, E2E) | Тест, который запускает *настоящую готовую программу*, подаёт ей ввод так, как это сделал бы пользователь, и проверяет, что получилось на выходе. «Сквозной» значит: от ввода пользователя до вывода программы. |
| **пирамида тестов** (test pyramid) | Картинка и практическое правило: много быстрых модульных тестов внизу, меньше интеграционных в середине, несколько сквозных наверху. |
| **уверенность** (confidence) | Насколько уверенно успешный тест говорит, что программа действительно работает для пользователя. |
| **время обратной связи** (feedback time) | Как долго вы ждёте, чтобы узнать, что что-то сломалось. Короткое время обратной связи делает вас быстрее. |
| **детерминированный** (deterministic) | Всегда даёт один и тот же результат для одного и того же входа. Тест должен быть детерминированным. |
| **нестабильный тест** (flaky test) | Тест, который иногда проходит, а иногда падает без изменений в коде (Урок 05.6). |
| **stdout / stderr** (standard output / standard error, стандартный вывод / стандартный вывод ошибок) | Два текстовых канала программы: обычные результаты идут в stdout, сообщения об ошибках — в stderr. |
| **код возврата** (exit code) | Число, которое программа возвращает системе при завершении. `0` значит успех; любое другое — неудачу. |
| **процесс** (process) | Запущенная программа. Запуск процесса намного медленнее вызова функции. |
| **Arrange–Act–Assert** (AAA, «подготовить — выполнить — проверить») | Способ структурировать тест: подготовить данные (arrange), вызвать код (act), проверить результат (assert). |

## 1. Зачем больше одного вида тестов?

Представьте, что вы собираете автомобиль. Вы проверяете каждый болт (затянут ли он?), проверяете двигатель на
испытательном стенде и в конце едете на тест-драйв всей машиной. У каждой проверки своя цена:

- Проверка одного болта очень дешёвая и точно показывает, какой болт ослаб, но ничего не говорит о том, поедет ли машина.
- Тест-драйв — единственная проверка, которая показывает, что *вся машина* работает, но он занимает час, и если
  машина не завелась, причину всё равно придётся искать.

С тестами то же самое. Каждый тест делает три компромисса:

1. **Скорость.** Сколько он выполняется? (Это ваше время обратной связи.)
2. **Точность.** Когда он падает, указывает ли сообщение на сломанную строку или только говорит «что-то не так»?
3. **Уверенность.** Какую часть настоящей программы он задействует? Тест, который запускает больше настоящего кода, доказывает больше.

Ни один тест не лучший во всех трёх. Поэтому мы используем три уровня:

| | Модульный | Интеграционный | Сквозной |
|---|---|---|---|
| **Запускает** | одну функцию или тип | публичный API крейта | настоящую собранную программу в отдельном процессе |
| **Скорость** | микросекунды | от микросекунд до миллисекунд | сотни миллисекунд |
| **Точность** | указывает на одну функцию | указывает на одну возможность | говорит только «вывод неверный» |
| **Уверенность** | низкая (одна часть) | средняя (части работают вместе) | высокая (то, что получает пользователь) |
| **Ломается, когда** | меняется функция | меняется публичный API | меняется что угодно, даже текст сообщения |

Остальная часть урока показывает каждый уровень на одной маленькой программе.

## 2. Пример программы: делитель счёта

Трое друзей поужинали; счёт — 10.00. Если поделить на троих, каждому достаётся 3,3333… Деньги нельзя делить на
доли цента, поэтому кто-то платит на один цент больше. Наша программа делает это честно: доли всегда в сумме дают
точный итог, а лишние центы платят первые люди. Программа запускается так:

```text
p09-pyramid 10.00 3
```

Создайте пакет (библиотека и программа в одном пакете; про `src/lib.rs` и `src/main.rs` рассказывал Урок 04.6):

```bash
cd ~/projects/rust
git switch main
git switch -c lesson/09-01-test-pyramid
cargo new --lib code/p09-pyramid
```

Замените `src/lib.rs` кодом ниже (тесты появятся в следующих разделах):

```rust
//! Bill splitting: share a total amount of money fairly between people.

use std::fmt;

/// Everything that can go wrong when a user runs the program.
#[derive(Debug, PartialEq, Eq)]
pub enum CliError {
    /// The wrong number of arguments.
    Usage,
    /// The amount of money is not a valid number like `12.50`.
    BadAmount(String),
    /// The number of people is not a whole number of at least 1.
    BadPeople(String),
}

impl fmt::Display for CliError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            CliError::Usage => write!(f, "usage: p09-pyramid <total> <people>"),
            CliError::BadAmount(text) => write!(f, "'{text}' is not a valid amount"),
            CliError::BadPeople(text) => write!(f, "'{text}' is not a valid number of people"),
        }
    }
}

impl std::error::Error for CliError {}

/// Turns text like `12.5` or `7` into cents (`1250` or `700`).
pub fn parse_money(text: &str) -> Option<u64> {
    let (whole, fraction) = match text.split_once('.') {
        Some((whole, fraction)) => (whole, fraction),
        None => (text, ""),
    };
    if whole.is_empty() || fraction.len() > 2 {
        return None;
    }
    let all_digits = |part: &str| part.chars().all(|c| c.is_ascii_digit());
    if !all_digits(whole) || !all_digits(fraction) {
        return None;
    }
    let cents_from_fraction = match fraction.len() {
        0 => 0,
        1 => fraction.parse::<u64>().ok()? * 10,
        _ => fraction.parse::<u64>().ok()?,
    };
    whole
        .parse::<u64>()
        .ok()?
        .checked_mul(100)?
        .checked_add(cents_from_fraction)
}

/// Turns cents back into text: `1250` becomes `12.50`.
pub fn format_money(cents: u64) -> String {
    format!("{}.{:02}", cents / 100, cents % 100)
}

/// Splits `total_cents` between `people`. The shares add up to the total exactly;
/// the first `total_cents % people` people pay one cent more than the others.
pub fn split_bill(total_cents: u64, people: u64) -> Vec<u64> {
    let base = total_cents / people;
    let extra = total_cents % people;
    (0..people)
        .map(|i| if i < extra { base + 1 } else { base })
        .collect()
}

/// Runs the whole program for the given arguments (without the program name)
/// and returns the text to print.
pub fn run(args: &[String]) -> Result<String, CliError> {
    let [total, people] = args else {
        return Err(CliError::Usage);
    };
    let total_cents = parse_money(total).ok_or_else(|| CliError::BadAmount(total.clone()))?;
    let people = match people.parse::<u64>() {
        Ok(n) if n >= 1 => n,
        _ => return Err(CliError::BadPeople(people.clone())),
    };
    let lines: Vec<String> = split_bill(total_cents, people)
        .iter()
        .enumerate()
        .map(|(i, cents)| format!("person {}: {}", i + 1, format_money(*cents)))
        .collect();
    Ok(lines.join("\n"))
}
```

Создайте `src/main.rs`:

```rust
fn main() {
    let args: Vec<String> = std::env::args().skip(1).collect();
    match p09_pyramid::run(&args) {
        Ok(text) => println!("{text}"),
        Err(error) => {
            eprintln!("error: {error}");
            std::process::exit(2);
        }
    }
}
```

**Что происходит:**

1. `parse_money` делит текст по точке. Она отвергает пустую целую часть, больше двух знаков после точки и любой
   символ, не являющийся цифрой, поэтому `"-3"`, `"1.234"` и `"abc"` дают `None`. Она использует `checked_mul` и
   `checked_add`, которые возвращают `None` вместо переполнения (Урок 05.6).
2. `split_bill` даёт каждому `total / people` центов (целочисленное деление отбрасывает остаток), а первые
   `total % people` человек получают ещё по одному центу. Остаток всегда меньше `people`, поэтому каждый
   получает не больше одного лишнего цента.
3. `run` — это вся программа как *функция*: аргументы на входе, текст или ошибка на выходе. Строка
   `let [total, people] = args else { … }` сопоставляет срез ровно из двух элементов; любая другая длина попадает в
   ветку `else` и становится ошибкой использования.
4. `main` — всего лишь тонкая оболочка. Она собирает аргументы, вызывает `run`, печатает текст в stdout или печатает
   ошибку в stderr и завершается с кодом 2. Так как в `main` почти нет логики, в ней почти нечему ломаться.

> 📏 **Соглашение:** держите `main` крошечной, а логику кладите в библиотечную функцию вроде `run`. Функцию, которая
> принимает значения и возвращает значения, легко тестировать; `main`, которая работает с настоящим терминалом, — нет.
> Эту идею называют «тонкая оболочка вокруг тестируемого ядра».

Попробуйте вручную:

```bash
cd code/p09-pyramid
cargo run -q -- 10.00 3
cargo run -q -- ten 3
echo "exit code: $?"
```

```text
person 1: 3.34
person 2: 3.33
person 3: 3.33
error: 'ten' is not a valid amount
exit code: 2
```

## 3. Уровень 1: модульные тесты

Модульный тест проверяет одну небольшую часть отдельно от остальных. Добавьте в конец `src/lib.rs`:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn parses_whole_and_fractional_amounts() {
        assert_eq!(parse_money("12.50"), Some(1250));
        assert_eq!(parse_money("12.5"), Some(1250));
        assert_eq!(parse_money("7"), Some(700));
    }

    #[test]
    fn rejects_text_that_is_not_money() {
        assert_eq!(parse_money(""), None);
        assert_eq!(parse_money("-3"), None);
        assert_eq!(parse_money("1.234"), None);
        assert_eq!(parse_money("abc"), None);
    }

    #[test]
    fn formats_cents_with_two_digits() {
        assert_eq!(format_money(1250), "12.50");
        assert_eq!(format_money(5), "0.05");
    }

    #[test]
    fn leftover_cents_go_to_the_first_people() {
        assert_eq!(split_bill(1000, 3), vec![334, 333, 333]);
    }

    #[test]
    fn even_split_has_no_leftovers() {
        assert_eq!(split_bill(900, 3), vec![300, 300, 300]);
    }
}
```

```bash
cargo test --lib
```

```text
running 5 tests
test tests::even_split_has_no_leftovers ... ok
test tests::formats_cents_with_two_digits ... ok
test tests::leftover_cents_go_to_the_first_people ... ok
test tests::rejects_text_that_is_not_money ... ok
test tests::parses_whole_and_fractional_amounts ... ok

test result: ok. 5 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

**Что происходит:** каждый тест вызывает одну функцию с маленькими, подобранными вручную входами и сравнивает результат
с ожидаемым. Все пять тестов вместе занимают намного меньше миллисекунды. Можно написать сотни таких тестов и всё
равно не ждать. Когда один падает, его имя говорит, какая функция неверна (как называть тесты предложениями, объяснял Урок 05.6).

> 🧪 **Тестирование:** модульные тесты — правильное место для *граничных случаев*: пустой текст, ноль, самое большое число,
> знак минус. Они дешёвые, поэтому покрывайте здесь все необычные входы, а не на верхних уровнях.

## 4. Уровень 2: интеграционные тесты

Интеграционный тест проверяет, что части работают *вместе*, только через публичный API. Создайте `tests/api.rs`:

```rust
use p09_pyramid::{CliError, run};

fn args(items: &[&str]) -> Vec<String> {
    items.iter().map(|s| s.to_string()).collect()
}

#[test]
fn splits_ten_dollars_between_three_people() {
    let output = run(&args(&["10.00", "3"])).unwrap();
    assert_eq!(output, "person 1: 3.34\nperson 2: 3.33\nperson 3: 3.33");
}

#[test]
fn zero_people_is_an_error() {
    assert_eq!(
        run(&args(&["10.00", "0"])),
        Err(CliError::BadPeople("0".to_string()))
    );
}

#[test]
fn wrong_number_of_arguments_is_a_usage_error() {
    assert_eq!(run(&args(&["10.00"])), Err(CliError::Usage));
}
```

```bash
cargo test --test api
```

```text
running 3 tests
test wrong_number_of_arguments_is_a_usage_error ... ok
test zero_people_is_an_error ... ok
test splits_ten_dollars_between_three_people ... ok

test result: ok. 3 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

**Что происходит:**

1. Файл в `tests/` компилируется как отдельный крейт и импортирует `p09_pyramid`, как любой пользователь. Он не может
   вызывать приватные элементы.
2. `args` — маленькая вспомогательная функция, которая превращает значения `&str` в `Vec<String>`, нужный `run`.
3. Тесты вызывают `run` — ту же функцию, что вызывает `main`, — поэтому разбор, деление и форматирование
   проверяются *вместе*. Они проверяют и случаи ошибок (`BadPeople`, `Usage`), потому что именно на этих путях
   части должны быть согласованы.

Эти тесты всё ещё не запускают программу, поэтому они почти так же быстры, как модульные. Чего они проверить не могут —
это саму `main`: действительно ли текст попадает в stdout и верен ли код возврата.

## 5. Уровень 3: сквозные тесты

Сквозной тест запускает настоящую программу. Cargo собирает бинарный файл перед запуском тестов из `tests/` и
сообщает тесту, где он лежит, через переменную окружения `CARGO_BIN_EXE_<имя>` (здесь `<имя>` — имя программы
`p09-pyramid`). Создайте `tests/e2e.rs`:

```rust
use std::process::Command;

fn program() -> Command {
    Command::new(env!("CARGO_BIN_EXE_p09-pyramid"))
}

#[test]
fn prints_the_shares_and_exits_with_zero() {
    let output = program().args(["10.00", "3"]).output().unwrap();
    assert!(output.status.success());
    let stdout = String::from_utf8(output.stdout).unwrap();
    assert_eq!(stdout, "person 1: 3.34\nperson 2: 3.33\nperson 3: 3.33\n");
}

#[test]
fn bad_input_prints_to_stderr_and_exits_with_two() {
    let output = program().args(["ten", "3"]).output().unwrap();
    assert_eq!(output.status.code(), Some(2));
    let stderr = String::from_utf8(output.stderr).unwrap();
    assert_eq!(stderr, "error: 'ten' is not a valid amount\n");
}
```

```bash
cargo test --test e2e
```

```text
running 2 tests
test prints_the_shares_and_exits_with_zero ... ok
test bad_input_prints_to_stderr_and_exits_with_two ... ok

test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.14s
```

**Что происходит:**

1. `env!("CARGO_BIN_EXE_p09-pyramid")` читается **при компиляции теста** и превращается в путь к собранной программе,
   что-то вроде `…/target/debug/p09-pyramid`.
2. `Command::new(path).args([...]).output()` (из стандартной библиотеки) запускает программу как новый процесс,
   ждёт его завершения и собирает его stdout, stderr и статус завершения.
3. Первый тест проверяет путь успеха: нулевой статус и точный текст в stdout (обратите внимание на последний `\n`,
   который добавляет `println!`). Второй проверяет путь ошибки: код возврата 2 и точное сообщение в stderr.
4. Только сквозной тест может доказать эти два факта. Если бы кто-то заменил `eprintln!` на `println!` в `main`,
   ни один модульный и ни один интеграционный тест этого бы не заметил.

Двум тестам нужно около 0,14 секунды, а пять модульных и три интеграционных вместе укладываются меньше чем в
0,01 секунды. Точные числа зависят от компьютера, но соотношение всегда большое: запуск процесса медленный по
сравнению с вызовом функции.

> ⚡ **Производительность:** набор из 1000 сквозных тестов по 70 мс занимает больше минуты. Те же проверки в виде
> модульных тестов занимают меньше секунды. Медленные тесты запускают реже, а тесты, которые не запускают,
> ничего не защищают. Переносите каждую проверку, какую можно, на уровень ниже.

Лучший инструмент для сквозных тестов программ командной строки Этап 09 разбирает в [Уроке 09.2](02-testing-command-line-programs.md);
здесь для понимания идеи достаточно стандартной библиотеки.

## 6. Одна ошибка, три уровня

Сломаем код нарочно и посмотрим, какие тесты это заметят. В `split_bill` замените `i < extra` на `i <= extra`
(классическая ошибка на единицу: лишний цент достаётся на одного человека больше):

```rust
        .map(|i| if i <= extra { base + 1 } else { base })
```

Запустите все файлы тестов, даже если часть упадёт (`--no-fail-fast`, объяснено в «Частых ошибках»):

```bash
cargo test --no-fail-fast
```

Важные строки реального вывода:

```text

test tests::leftover_cents_go_to_the_first_people ... FAILED
test tests::even_split_has_no_leftovers ... FAILED
---- tests::leftover_cents_go_to_the_first_people stdout ----
assertion `left == right` failed
  left: [334, 334, 333]
 right: [334, 333, 333]
---- tests::even_split_has_no_leftovers stdout ----
assertion `left == right` failed
  left: [301, 300, 300]
 right: [300, 300, 300]
test result: FAILED. 3 passed; 2 failed; …

     Running tests/api.rs (…)
test splits_ten_dollars_between_three_people ... FAILED
assertion `left == right` failed
  left: "person 1: 3.34\nperson 2: 3.34\nperson 3: 3.33"
 right: "person 1: 3.34\nperson 2: 3.33\nperson 3: 3.33"
test result: FAILED. 2 passed; 1 failed; …

     Running tests/e2e.rs (…)
test prints_the_shares_and_exits_with_zero ... FAILED
assertion `left == right` failed
  left: "person 1: 3.34\nperson 2: 3.34\nperson 3: 3.33\n"
 right: "person 1: 3.34\nperson 2: 3.33\nperson 3: 3.33\n"

```

**Что происходит:** одна и та же ошибка роняет тесты на всех трёх уровнях, но сообщения разные.

- **Модульные тесты** падают с названиями двух случаев и небольшими массивами. Увидев `[301, 300, 300]` там, где
  ожидалось `[300, 300, 300]`, вы сразу понимаете: «даже идеальное деление дало кому-то лишний цент», значит, проблема
  в `split_bill`, в выборе того, кто получает лишний цент. Падение *точное*.
- **Интеграционный** и **сквозной** тесты падают с длинными строками. Они говорят, *что* результат неверен, но чтобы
  найти, *где*, нужно прочитать текст и подумать.
- Три падения из-за одной ошибки — это нормально и не проблема. Навык в том, чтобы читать падения снизу пирамиды
  вверх: сначала исправьте падения модульных тестов, и верхние обычно сами станут зелёными.

Верните `<=` обратно на `<`, прежде чем идти дальше.

## 7. Пирамида и рожок мороженого

Поставьте три уровня друг на друга, дешёвый внизу:

```text
          /\
         /E2E\          few: the happy path and one or two failures
        /------\
       /integra-\       some: features working together
      /  tion    \
     /------------\
    /  unit tests  \    many: every function, every edge case
   /________________\
```

Чем шире слой, тем больше в нём тестов. Логика этой формы:

- Низ быстрый и точный, поэтому позволить себе его можно много. Здесь вы проверяете *множество* комбинаций входов.
- Верх медленный и хрупкий (ломается при любом изменении), поэтому сквозных тестов пишут столько, сколько нужно,
  чтобы доказать, что части действительно соединены: обычно основной путь успеха и один путь ошибки.

Противоположная форма называется **рожком мороженого** (ice-cream cone): много сквозных тестов (обычно написанных
ручным кликаньем или длинными скриптами), мало модульных. Набор тестов команды медленный, падает по причинам, которые
трудно найти, и люди перестают ему доверять. Если вы видите проект, где `cargo test` идёт десять минут, ищите рожок.

Пирамида — это ориентир, а не закон. Если ваша программа — тонкая обёртка над базой данных, интеграционные тесты
могут оказаться важнее модульных. Важно рассуждение: **запускайте каждую проверку на самом низком уровне, который
всё ещё может поймать проблему.**

## 8. Стратегия тестирования: что и где тестировать

Используйте эту таблицу, когда не знаете, куда поместить тест.

| Вы хотите проверить… | Поместите тест на уровень… | Пример здесь |
|---|---|---|
| вычисление, парсер, граничный случай | модульный | `parse_money("1.234")` даёт `None` |
| что две или больше частей работают вместе | интеграционный | `run` с `["10.00", "3"]` |
| ошибку, проходящую через несколько частей | интеграционный | `run` с `["10.00", "0"]` даёт `BadPeople` |
| что видит пользователь: stdout, stderr, код возврата | сквозной | `ten 3` завершается с кодом 2 |
| что `main` соединена с библиотекой | сквозной | один тест успеха |
| ошибку, о которой сообщили | **самый низкий** уровень, где она воспроизводится | обычно модульный тест |

А эти шесть правил делают тесты полезными надолго:

1. **Тестируйте поведение, а не реализацию.** Тест должен говорить, *что* код обещает («доли в сумме дают итог»), а не
   *как* он устроен внутри («он дважды вызывает `checked_add`»). Тогда вы можете свободно делать рефакторинг (переписывать
   внутренности, не меняя поведения), и тесты останутся зелёными.
2. **Arrange, Act, Assert.** Пишите каждый тест из трёх видимых частей: подготовить данные, вызвать код, проверить
   результат. В наших тестах «подготовка» часто — просто аргументы, но когда она разрастается, разделяйте части
   пустой строкой.
3. **Одна причина падения.** Тест, который проверяет одно поведение, говорит вам, что сломано. Тест, который проверяет
   десять вещей, говорит лишь, что сломана одна из десяти. (Несколько вызовов `assert_eq!` для *одного и того же*
   поведения — нормально.)
4. **Будьте детерминированными.** Тест должен давать один ответ при каждом запуске. Обычные враги — настоящие часы,
   случайные числа, сеть, порядок элементов в `HashMap` и тесты, которые делят общий файл. Уберите их из тестируемого
   кода, передавая их как параметры (вы сделаете это с тестовыми двойниками в
   [Уроке 09.3](03-test-doubles.md)).
5. **Каждая ошибка сначала получает тест.** Когда вы нашли ошибку, сначала напишите тест, который падает из-за неё
   (красный), затем исправьте код (зелёный). Тогда ошибка не сможет вернуться незамеченной (*регрессионный тест*, Урок 05.6).
6. **Держите контроль качества.** Перед каждым коммитом запускайте контроль качества из Урока 05.6:
   `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`.

> 🔒 **Безопасность:** тесты — это код в вашем репозитории. Никогда не кладите настоящие пароли, токены или данные
> клиентов в файлы тестов или в вывод тестов. Используйте заведомо фальшивые значения вроде `"test-password"`.

## 9. Запуск одного уровня за раз

Не всегда хочется запускать всё. `cargo test --lib` запускает только модульные тесты библиотеки (самый быстрый;
используйте его, пока пишете код). `cargo test --test api` и `cargo test --test e2e` запускают один файл из `tests/`.
`cargo test --doc` запускает примеры из документации. `cargo test leftover` запускает тесты, в имени которых есть
`leftover`. `cargo test --no-fail-fast` запускает каждый файл тестов даже после падения. Хороший ритм:
`cargo test --lib`, пока пишете код, и весь контроль качества перед коммитом.

## Частые ошибки

**1. Ожидать, что `cargo test` покажет все падения.** Когда файл тестов падает, Cargo останавливается, не запуская
следующий. Если падают модульные тесты, вы вообще не увидите результатов интеграционных и сквозных:

```text
error: test failed, to rerun pass `--lib`
```

Обратите внимание: в тексте нет ни `tests/api.rs`, ни `tests/e2e.rs` — они даже не запускались. Используйте
`cargo test --no-fail-fast`, когда нужна полная картина, как в разделе 6.

**2. Использовать `CARGO_BIN_EXE_…` в модульном тесте.** Переменная существует только для файлов в `tests/`. Если вы
напишете `env!("CARGO_BIN_EXE_p09-pyramid")` внутри `src/lib.rs`, компилятор скажет:

```text
error: environment variable `CARGO_BIN_EXE_p09-pyramid` not defined at compile time
   --> src/lib.rs:127:20
    |
127 |         let path = env!("CARGO_BIN_EXE_p09-pyramid");
    |                    ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    |
    = help: `CARGO_BIN_EXE_p09-pyramid` may not be available for the current Cargo target
```

**Что это значит:** модульные тесты собираются только для библиотеки, без бинарного файла. Сквозному тесту место в `tests/`.

**3. Тестировать всё сквозными тестами.** «Надёжнее, если запускается настоящая программа». Нет: набор становится
медленным, а каждое падение — расплывчатым (раздел 7, рожок мороженого). Проверяйте каждое правило один раз на самом
низком уровне, а сквозные тесты оставьте для соединений.

## Упражнения

### Упражнение 1 — Новый граничный случай (легко)

Добавьте модульный тест `parses_zero_and_small_amounts`, который проверяет, что `parse_money("0")` равно `Some(0)`,
`parse_money("0.05")` равно `Some(5)`, а `parse_money("0.")` равно `Some(0)`. Запустите `cargo test --lib`. Проходит ли
последний? Если результат вас удивил, решите, права программа или тест.

<details>
<summary>Подсказка</summary>

Поместите тест внутрь `mod tests` в `src/lib.rs`. Разберите `"0."` вручную: текст делится по точке на `"0"` и
`""`. Разрешает ли код пустую дробную часть?

</details>

<details>
<summary>Ответ</summary>

```rust
    #[test]
    fn parses_zero_and_small_amounts() {
        assert_eq!(parse_money("0"), Some(0));
        assert_eq!(parse_money("0.05"), Some(5));
        assert_eq!(parse_money("0."), Some(0));
    }
```

Все три проходят. Текст `"0."` делится на `"0"` и `""`; пустая дробная часть имеет длину 0, поэтому код считает это
«нет центов». Это проектное решение: некоторые программы отвергли бы `"0."`. Если вы решите, что это неверно, тест —
ваша спецификация: измените тест на `None`, посмотрите, как он падает (красный), а затем измените `parse_money`
(зелёный). Написание теста сделало скрытое решение видимым — одно из лучших свойств тестов.

</details>

### Упражнение 2 — Разложите тесты по уровням (средне)

Для каждой проверки скажите, к какому уровню она относится — модульному, интеграционному или сквозному, — и почему:

1. `format_money(0)` должна давать `"0.00"`.
2. Программа печатает сообщение об использовании, когда запущена без аргументов.
3. `run(["5", "2"])` даёт `person 1: 2.50` и `person 2: 2.50`.
4. Программа завершается с кодом 2, когда сумма неверна.
5. Для `split_bill(1, 5)` доли равны `[1, 0, 0, 0, 0]`.

<details>
<summary>Подсказка</summary>

Спросите себя, какой самый дешёвый тест всё ещё мог бы поймать проблему. Коды возврата и stderr существуют только в настоящем процессе.

</details>

<details>
<summary>Ответ</summary>

1. Модульный: одна функция, крошечный граничный случай.
2. Интеграционный: `run(&[])` даёт `Err(CliError::Usage)`. Сквозной тест для неверной суммы уже доказывает, что stderr подключён.
3. Интеграционный: разбор, деление и форматирование работают вместе через `run`.
4. Сквозной: код возврата принадлежит процессу.
5. Модульный: одна функция, граничный случай, когда людей больше, чем центов.

Правило: выбирайте самый низкий уровень, на котором тест всё ещё может упасть из-за проблемы, которая вас беспокоит.

</details>

### Упражнение 3 — Сначала напишите тест (сложно)

Новое требование: программа должна отвергать больше 1000 человек новой ошибкой `CliError::TooManyPeople(String)` с
сообщением `'<текст>' is too many people (the maximum is 1000)`. Работайте от теста. (а) Напишите интеграционный тест
в `tests/api.rs` для `["10.00", "1001"]` и увидьте, как он падает (сначала он даже не компилируется — это тоже
красное состояние). (б) Сделайте так, чтобы он компилировался и проходил. (в) Имеет ли смысл сквозной тест для этой возможности?

<details>
<summary>Подсказка</summary>

Добавьте вариант перечисления и ветку `Display`, затем проверьте число в `run` после его разбора. Помните, что
само `1000` должно оставаться разрешённым: напишите это вторым тестом.

</details>

<details>
<summary>Ответ</summary>

Тест (в `tests/api.rs`):

```rust
#[test]
fn more_than_a_thousand_people_is_an_error() {
    assert_eq!(
        run(&args(&["10.00", "1001"])),
        Err(CliError::TooManyPeople("1001".to_string()))
    );
}

#[test]
fn exactly_a_thousand_people_is_allowed() {
    assert!(run(&args(&["10.00", "1000"])).is_ok());
}
```

Код в `src/lib.rs`: добавьте `TooManyPeople(String)` в перечисление, ветку
`CliError::TooManyPeople(text) => write!(f, "'{text}' is too many people (the maximum is 1000)")`, а в
`run` после `match` — `if people > 1000 { return Err(CliError::TooManyPeople(people_text)); }` (сохраните исходный
текст в переменной, прежде чем затенить `people`).

(в) Нет. Сквозной тест для `ten 3` уже доказывает, что ошибки доходят до stderr с кодом возврата 2. Новое правило —
это логика, поэтому интеграционного теста достаточно.

</details>

## Вопросы для самопроверки

1. Назовите три уровня тестов и скажите, какой из них самый быстрый.

<details>
<summary>Ответ</summary>

Модульный, интеграционный, сквозной (E2E). Модульные тесты самые быстрые, потому что вызывают одну функцию в том же
процессе.

</details>

2. Почему в пирамиде *мало* сквозных тестов?

<details>
<summary>Ответ</summary>

Они медленные (запускают процесс), ломаются по многим причинам, а их падения не указывают на сломанную строку.
Нескольких достаточно, чтобы доказать, что настоящая программа соединена; множество комбинаций входов дешевле
проверять ниже.

</details>

3. Что может проверить сквозной тест такого, чего не может интеграционный тест `run`?

<details>
<summary>Ответ</summary>

То, что принадлежит настоящему процессу и `main`: действительно ли текст попадает в stdout или stderr и верен ли код возврата.

</details>

4. Что такое «рожок мороженого» и почему это плохо?

<details>
<summary>Ответ</summary>

Перевёрнутая пирамида: много сквозных тестов и мало модульных. Набор медленный, нестабильный и трудно отлаживаемый,
поэтому его реже запускают и меньше ему доверяют.

</details>

5. Пользователь сообщил об ошибке. Что вы делаете первым делом?

<details>
<summary>Ответ</summary>

Пишете тест, который воспроизводит ошибку, на самом низком уровне, где её можно воспроизвести, и видите, как он падает.
Затем исправляете код и видите, как он проходит. Тест остаётся как регрессионный.

</details>

## Итоги

- Каждый тест делает компромисс между скоростью, точностью и уверенностью. Модульные, интеграционные и сквозные тесты
  делают разные компромиссы.
- Модульные тесты: одна часть, микросекунды, точные. Интеграционные: публичный API, части вместе. Сквозные:
  настоящая программа в своём процессе, единственный способ проверить stdout, stderr и коды возврата.
- Здоровый набор — пирамида: много модульных тестов, несколько интеграционных, мало сквозных. Перевёрнутый «рожок
  мороженого» медленный и хрупкий.
- Запускайте каждую проверку на самом низком уровне, который всё ещё может поймать проблему.
- Держите `main` тонкой, а логику — в тестируемой библиотечной функции.
- Тестируйте поведение, а не реализацию; делайте тесты детерминированными; для каждой ошибки сначала пишите тест.
- `cargo test --lib`, `--test <файл>`, `--doc` и `--no-fail-fast` позволяют запускать один уровень или все.
