## Новые слова

| Слово | Значение |
|---|---|
| **конвейер наблюдаемости** (observability pipeline) | Программа, которая собирает логи, метрики и трассировки из многих мест, меняет их по дороге и отправляет в системы хранения. Часто работает как **агент** на каждой машине. |
| **событие** (event) | Одна единица данных в конвейере: строка лога с её полями или одно значение метрики. |
| **источник** (source) | Компонент, который производит события: файл лога, стандартный ввод, HTTP-эндпоинт, метрики хоста. |
| **преобразование** (transform) | Компонент, который меняет события: разбирает, добавляет поля, фильтрует, скрывает секреты, прореживает, превращает логи в метрики. |
| **приёмник** (sink) | Компонент, который отправляет события дальше: стандартный вывод, файл, HTTP-бэкенд. |
| **топология** (topology) | Граф источников, преобразований и приёмников, соединённых их `inputs`. В нём не должно быть циклов. |
| **logfmt** | Простой формат логов из пар `key=value` в одной строке, например `level=info msg="user logged in"`. |
| **чтение хвоста файла** (tailing) | Чтение файла, который продолжает расти, строка за строкой по мере записи новых строк — как `tail -f`. |
| **ротация логов** (log rotation) | Замена разросшегося файла лога: старый файл переименовывается (или копируется и обрезается), и начинается новый, пустой. |
| **inode** | Номер, по которому файловая система Unix опознаёт файл независимо от его имени. Переименованный файл сохраняет свой inode. |
| **контрольная точка чтения** (checkpoint) | Сохранённая позиция в файле («прочитано до байта 81 920 inode 1234»), чтобы после перезапуска агент продолжил с неё. |
| **сквозное подтверждение** (end-to-end acknowledgement) | Приёмник сообщает источнику, что пакет надёжно доставлен; только тогда источник может сдвинуть свою контрольную точку. |
| **буфер** (buffer) | Ограниченная очередь между компонентами, в памяти или на диске, с правилом на случай заполнения: блокировать или отбрасывать. |
| **кардинальность** (cardinality) | Число разных сочетаний меток метрики. Высокая кардинальность (метка на каждый идентификатор пользователя) делает хранение метрик медленным и дорогим. |
| **OTLP** (OpenTelemetry Protocol, протокол OpenTelemetry) | Протокол, по которому инструменты OpenTelemetry отправляют логи, метрики и трассировки через gRPC (протокол удалённого вызова процедур) или HTTP. |
| **DaemonSet** | Объект Kubernetes, который запускает по одной копии пода на каждом узле — обычный способ развернуть агент узла. |
| **HTTP** (HyperText Transfer Protocol, протокол передачи гипертекста) | Протокол запросов и ответов веба; HTTPS — это HTTP поверх зашифрованного соединения. |
| **CPU** (Central Processing Unit, центральный процессор) | Процессор; «использование CPU» — какую долю его времени занимает программа. |
| **TOML** (Tom's Obvious Minimal Language) | Простой формат конфигурации, который использует `Cargo.toml`. |
| **JSON** (JavaScript Object Notation, нотация объектов JavaScript) | Текстовый формат структурированных данных, например `{"error":"no route"}`. |
| **CI** (Continuous Integration, непрерывная интеграция) | Сервер, который автоматически запускает ваши проверки при каждой отправке (Урок 09.12). |
| **ВМ** (виртуальная машина, VM — Virtual Machine) | Целый компьютер, имитируемый программой; Linux-ВМ курса называется `dev` (Урок 11.1). |
| **TCP** (Transmission Control Protocol, протокол управления передачей) | Интернет-протокол, который даёт двум программам надёжный упорядоченный поток байтов. |

## 1. Что вы строите и почему это важно

Вы строите `pipe` — маленький агент в духе Vector, Fluent Bit или OpenTelemetry Collector. Он читает строки логов из файлов, которые пишутся и ротируются, разбирает их в структурированные события, обогащает и фильтрует их, превращает часть из них в метрики и пакетами доставляет в бэкенды по HTTP. Он работает на каждой машине кластера, поэтому должен быть **дешёвым** (мало CPU и памяти), **безопасным** (никогда не ронять машину вместе с собой) и **честным** (никогда не терять данные молча: каждое отброшенное событие считается).

Это похоже на «сантехнику», но это плотная системная задача:

- **С файлами непросто.** Файлы переименовывают, обрезают и заменяют, пока вы их читаете; агент перезапускается; строки дописаны наполовину. Прочитать каждую строку ровно один раз (или хотя бы один раз после сбоя) требует inode, контрольных точек и аккуратности.
- **Бэкенды отказывают.** Система хранения недоступна пять минут. Блокировать, буферизовать в памяти, буферизовать на диске или отбрасывать? У каждого ответа своя цена, и агент должен делать эту цену видимой.
- **Пропускная способность важна.** Загруженная машина производит десятки тысяч строк в секунду; агент должен успевать, не занимая целое ядро процессора.

Почему это важно: почти каждая организация, у которой есть сервисы, держит такие конвейеры, и многие сбои находят (или пропускают) именно благодаря им. Если на Этапе 22 вы выбрали направление eBPF или cloud native, этот итоговый проект прямо его продолжает: источник на eBPF или преобразование с метаданными Kubernetes — естественная дополнительная цель.

## 2. Эталонная архитектура

```text
                        pipe.toml --> config check (graph, cycles) --> topology
 sources                     transforms                        sinks
+------------------+       +---------------------+          +----------------------+
| file: app/*.log  |--+    | parse (logfmt/json) |          | http: batch, retry,  |
|  inode, offset,  |  +--->|  -> add_fields      |--------->|  backoff, ack        |
|  rotation        |  |    |  -> drop / redact   |    +---->| (to a log backend)   |
+--------+---------+  |    +----------+----------+    |     +----------+-----------+
         ^            |               |               |                |
         |   +--------+---------+     v               |     +----------+-----------+
         |   | stdin            |  +--------------+   |     | prometheus endpoint  |
         |   +------------------+  | log_to_metric|---+---->| /metrics (pull)      |
         |                         +--------------+         +----------------------+
         |       every arrow is a bounded buffer: memory or disk, block or drop
         |
   checkpoints  <------------ acknowledgements from sinks (batch delivered)

 self-observability: /metrics with events in/out, buffer fill, dropped, retries
```

Части и их задачи:

1. **Источники** читают данные и превращают их в события. Файловый источник для каждого файла помнит inode и смещение в байтах, до которого он дочитал.
2. **Преобразования** — маленькие чистые шаги. Большинство из них берёт одно событие и выдаёт ноль, одно или много событий — это легко тестировать без всякого ввода-вывода (I/O, input/output).
3. **Приёмники** собирают события в пакеты и доставляют их с повторными попытками. Когда пакет доставлен, приёмник **подтверждает** его.
4. **Буферы** стоят на каждом ребре графа. Они ограничены: когда буфер полон, он либо *блокирует* (производитель ждёт, и давление переходит обратно к источнику — обратное давление), либо *отбрасывает* (и считает).
5. **Контрольные точки** сдвигаются вперёд только для данных, которые подтвердил каждый приёмник, поэтому сбой может вызвать повторы, но никогда — потерю.

> 💡 **Совет:** нарисуйте свою топологию графом в проектном документе и дайте каждому ребру два числа: его ёмкость и поведение при заполнении. Большинство трудных вопросов этого итогового проекта — вопросы об этих числах.

## Проект

### Что вы создадите

Рабочее пространство Cargo `code/p23-pipe`:

| Крейт | Вид | Задача |
|---|---|---|
| `pipe-core` | библиотека | модель событий, трейт `Transform` и все преобразования — чистые, без ввода-вывода |
| `pipe-config` | библиотека | конфигурация, проверка графа (неизвестные входы, циклы) |
| `pipe-io` | библиотека | источники, приёмники, буферы, контрольные точки |
| `pipe` | бинарник | связывание компонентов, сигналы, собственные метрики, `pipe check` |
| `pipe-tests` | только тесты | сквозные тесты с тестовым HTTP-бэкендом, который по команде умеет отказывать |

**Не-цели:** никаких трассировок (только логи и метрики), никакого языка запросов для преобразований (фиксированный список типов преобразований), никакой агрегации на весь кластер, никакого пользовательского интерфейса.

### Контракт

**Командная строка:**

```text
pipe --config <FILE> [--data-dir <DIR>]     run; checkpoints and disk buffers live in --data-dir
pipe check --config <FILE>                  validate the file and the graph; print "config ok: …" or the error
pipe --version
```

**Конфигурация** (TOML): у каждого компонента есть уникальное имя, `type` и — у преобразований и приёмников — `inputs`:

```toml
[sources.app]
type = "file"
include = ["/var/log/app/*.log"]

[transforms.parse]
type = "parse_logfmt"
inputs = ["app"]

[transforms.prod]
type = "add_fields"
inputs = ["parse"]
fields = { env = "prod" }

[transforms.quiet]
type = "drop_levels"
inputs = ["prod"]
levels = ["debug"]

[sinks.backend]
type = "http"
inputs = ["quiet"]
url = "http://127.0.0.1:9000/ingest"
batch = { max_events = 500, timeout_ms = 1000 }
buffer = { type = "disk", max_bytes = 268435456, when_full = "block" }
```

**Модель событий:** у события лога есть метка времени, сообщение и поля (строковые ключи, строковые значения); у события метрики — имя, вид (`counter` или `gauge`), значение и метки. Ваш проектный документ фиксирует точные типы и форму JSON, которую отправляют приёмники.

**Правила:**

1. **Граф:** конфигурация отклоняется, если вход называет неизвестный компонент, если у источника есть входы или если в графе есть цикл; ошибка называет цикл (например, `cycle: a -> b -> a`). О компонентах, до которых не доходит ни один приёмник, сообщается предупреждением.
2. **Порядок:** события из одного файла доходят до каждого приёмника в порядке строк файла.
3. **Доставка:** хотя бы один раз (at-least-once) от файловых источников до подтверждающих приёмников. Контрольная точка файла сдвигается за строку, только когда каждый приёмник, получающий события из этой строки, их подтвердил. После сбоя чтение продолжается с контрольной точки; некоторые события могут быть доставлены дважды, но ни одно не теряется.
4. **Буферы:** у каждого ребра есть ограниченный буфер. `when_full = "block"` заставляет вышестоящий компонент ждать; `"drop_newest"` отбрасывает входящее событие и увеличивает `pipe_events_dropped_total{component="…"}`. Использование памяти остаётся ниже настроенных лимитов, что бы ни делал бэкенд.
5. **Файловый источник:** подхватывает новые файлы, подходящие под `include`; следует за ротацией переименованием (дочитывает старый inode до конца, затем переключается) и обрезкой (начинает снова со смещения 0); опознаёт файлы по устройству и inode, а не по имени; строки длиннее `max_line_bytes` (по умолчанию 102 400) обрезаются и считаются.
6. **Приёмники:** отправляют пакет, когда он достиг `max_events` или `timeout_ms`; повторяют при тайм-аутах, ошибках соединения и `5xx` с экспоненциальной задержкой и джиттером; не повторяют `4xx` (кроме `429`): отбрасывают пакет, считают его и пишут одну строку ошибки в лог.
7. **Собственная наблюдаемость:** `GET /metrics` на `127.0.0.1:9598` как минимум с входящими и исходящими событиями по компонентам, заполненностью буферов, отброшенными событиями, повторами приёмников и задержкой запросов приёмников; `GET /health`.
8. **Завершение:** по `SIGTERM` остановить источники, сбросить буферы в приёмники не дольше `drain_timeout_ms`, сохранить контрольные точки, выйти с кодом 0.
9. **Накладные расходы:** README указывает использование CPU и памяти при 10 000 событий в секунду на указанном оборудовании.

**Контракт преобразований в коде.** В преобразованиях больше всего правил и меньше всего ввода-вывода, поэтому с них и начинают. Попробуйте модель в учебном пакете `code/p23-pipe-model`:

```rust
use std::collections::BTreeMap;

/// One log event moving through the pipeline.
#[derive(Clone, Debug, PartialEq)]
pub struct Event {
    pub message: String,
    pub fields: BTreeMap<String, String>,
}

impl Event {
    pub fn new(message: &str, fields: &[(&str, &str)]) -> Event {
        let fields = fields
            .iter()
            .map(|(k, v)| (k.to_string(), v.to_string()))
            .collect();
        Event {
            message: message.to_string(),
            fields,
        }
    }
}

/// One step of the pipeline: takes one event, emits zero, one or many.
pub trait Transform {
    fn apply(&mut self, event: Event, out: &mut Vec<Event>);
}

/// Adds the same field to every event.
pub struct AddField {
    pub key: String,
    pub value: String,
}

impl Transform for AddField {
    fn apply(&mut self, mut event: Event, out: &mut Vec<Event>) {
        event.fields.insert(self.key.clone(), self.value.clone());
        out.push(event);
    }
}

/// Drops events whose `level` field is in the list.
pub struct DropLevels {
    pub levels: Vec<String>,
}

impl Transform for DropLevels {
    fn apply(&mut self, event: Event, out: &mut Vec<Event>) {
        let dropped = event
            .fields
            .get("level")
            .is_some_and(|level| self.levels.contains(level));
        if !dropped {
            out.push(event);
        }
    }
}

/// Runs a batch of events through a chain of transforms, in order.
pub fn run_chain(chain: &mut [Box<dyn Transform>], batch: Vec<Event>) -> Vec<Event> {
    let mut current = batch;
    for transform in chain.iter_mut() {
        let mut next = Vec::with_capacity(current.len());
        for event in current {
            transform.apply(event, &mut next);
        }
        current = next;
    }
    current
}

fn main() {
    let mut chain: Vec<Box<dyn Transform>> = vec![
        Box::new(AddField {
            key: "host".into(),
            value: "web-1".into(),
        }),
        Box::new(DropLevels {
            levels: vec!["debug".into()],
        }),
    ];
    let input = vec![
        Event::new("user logged in", &[("level", "info")]),
        Event::new("cache miss", &[("level", "debug")]),
        Event::new("disk almost full", &[("level", "error")]),
    ];
    for event in run_chain(&mut chain, input) {
        println!("{} {:?}", event.message, event.fields);
    }
}
```

**Что происходит:**

1. `Event` хранит поля в `BTreeMap`, отсортированной по ключу. Тогда вывод всегда в одном порядке, и тесты и снапшот-файлы стабильны.
2. `Transform::apply` принимает событие **по значению** и пишет результаты в `out`. Перемещение события избегает копий; запись в `Vec` позволяет одному преобразованию отбросить событие (ничего не записать) или разделить его на несколько.
3. `&mut self` допускает преобразования с состоянием, например прореживатель, который оставляет каждое десятое событие, или преобразование, которое считает события, чтобы выдать метрику.
4. `DropLevels` использует `Option::is_some_and`: событие без поля `level` сохраняется.
5. `run_chain` пропускает весь пакет через одно преобразование за другим. `Box<dyn Transform>` (трейт-объект, Урок 06.1) позволяет конфигурации выбирать преобразования во время работы.

```bash
cargo run
```

```text
user logged in {"host": "web-1", "level": "info"}
disk almost full {"host": "web-1", "level": "error"}
```

### Планка качества

| Область | Что это значит здесь |
|---|---|
| Модульные и снапшот-тесты | каждое преобразование; снапшот-тесты для разбора и вывода JSON |
| Тесты на основе свойств | `parse_logfmt` никогда не паникует и обратимо разбирает события, которые сам выдал; проверка графа принимает каждый ациклический граф и отклоняет каждый циклический |
| Тесты на сбои | ротация, обрезка, падение и перезапуск (M2, M3), бэкенд недоступен, медленный и возвращает `4xx`/`5xx` (M3, M4) |
| Фаззинг | парсеры logfmt и JSON, загрузчик конфигурации, чтение буфера на диске |
| Бенчмарки | события в секунду на ядро для примерного конвейера; `criterion` для каждого парсера |
| Наблюдаемость | собственные метрики из правила 7; одна строка лога на изменение состояния, никогда — на каждое событие |
| Устойчивость | ограниченные буферы везде, максимальная длина строки, тайм-ауты на каждом HTTP-запросе |

> 🔒 **Безопасность:** логи часто содержат секреты, которые вообще не должны были туда попасть: пароли, токены, номера карт. Преобразование `redact` рядом с источником — настоящая возможность, а не игрушка. Кроме того, считайте строки логов враждебным вводом: парсер, который выделяет память по числу из строки, или регулярное выражение, которое может работать экспоненциально долго, позволяют одной плохой строке остановить агент.

## Частые ошибки

**1. Сдвигать контрольную точку при чтении строки.** Агент читает строку, сохраняет позицию, падает до того, как приёмник её доставил, — строка потеряна. Правило 3: контрольная точка следует за подтверждениями, а не за чтением.

**2. Опознавать файлы по имени.** После ротации `app.log` — это новый файл; агент продолжает со старого смещения в новом файле и пропускает его начало (или читает мусор). Исправление: устройство и inode плюс проверка на обрезку (файл короче вашего смещения).

**3. Неограниченные каналы.** `tokio::sync::mpsc::unbounded_channel` между быстрым источником и медленным приёмником: во время сбоя память растёт, пока машина не убьёт агент — а может, и другие программы. Исправление: правило 4, везде.

**4. Одна строка лога на каждое событие о самом агенте.** «dropped event» десять тысяч раз в секунду делает агент самым большим источником логов. Исправление: счётчики в метриках и строки лога с ограничением частоты.

**5. Бесконечно повторять `400 Bad Request`.** Пакет никогда не пройдёт, а он блокирует всё за собой. Исправление: правило 6 — отбросить, посчитать, записать в лог один раз.

**6. Метки с высокой кардинальностью.** Метка метрики из `user_id` создаёт в бэкенде миллионы временных рядов. Исправление: список разрешённых ключей меток (M5).

### Упражнение 1 — Когда можно сдвинуть контрольную точку? (легко)

Строки 1–100 файла попадают в пакет, который отправляет приёмник `http`; строки 101–200 — во второй пакет. Второй пакет подтверждается первым, затем агент падает до того, как подтверждён первый. До какой строки могла сдвинуться контрольная точка и что происходит после перезапуска?

<details>
<summary>Подсказка</summary>

Правило 3 говорит «за строку, только когда каждый приёмник … её подтвердил». Подтверждено ли всё до строки 200?

</details>

<details>
<summary>Ответ</summary>

Контрольная точка должна оставаться перед строкой 1 (на позиции начала строки 1), потому что строка 1 не подтверждена, хотя строки 101–200 подтверждены. После перезапуска агент снова читает строки 1–200; строки 101–200 доставляются второй раз. Это цена доставки «хотя бы один раз», и поэтому контрольная точка — это «наибольшая позиция, ниже которой подтверждено всё».

</details>

### Упражнение 2 — Напишите тесты для `DropLevels` (средне)

Добавьте тестовый модуль с двумя тестами: событие `debug` отбрасывается, а событие `warn` сохраняется; событие без поля `level` сохраняется.

<details>
<summary>Подсказка</summary>

Вызывайте `apply` напрямую с пустым `Vec` в качестве `out`, затем смотрите на `Vec`. Маленькая вспомогательная функция, которая строит преобразование, делает тесты короткими.

</details>

<details>
<summary>Ответ</summary>

```rust
#[cfg(test)]
mod tests {
    use super::*;

    fn drop_debug() -> DropLevels {
        DropLevels {
            levels: vec!["debug".into()],
        }
    }

    #[test]
    fn debug_events_are_dropped_and_others_kept() {
        let mut out = Vec::new();
        drop_debug().apply(Event::new("a", &[("level", "debug")]), &mut out);
        drop_debug().apply(Event::new("b", &[("level", "warn")]), &mut out);
        assert_eq!(out, vec![Event::new("b", &[("level", "warn")])]);
    }

    #[test]
    fn events_without_a_level_are_kept() {
        let mut out = Vec::new();
        drop_debug().apply(Event::new("no level here", &[]), &mut out);
        assert_eq!(out.len(), 1);
    }
}
```

```text
running 2 tests
..
test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Почему это работает: у преобразований нет ввода-вывода, поэтому тест — это просто «вызвать и сравнить». Второй тест закрепляет решение (сохранять события без уровня), которое легко сломать позже.

</details>

### Упражнение 3 — Преобразование `Redact`, сначала тест (средне)

Напишите преобразование `Redact { keys: Vec<String> }`, которое заменяет **значение** каждого перечисленного поля на `***` и оставляет всё остальное. Начните с теста `secrets_are_redacted`: событие с `user = ana` и `password = hunter2` должно выйти с `user = ana` и `password = ***`.

<details>
<summary>Подсказка</summary>

Пока `Redact` не существует, тест не компилируется — для нового типа это и есть шаг «красный». `BTreeMap::get_mut` возвращает `Option<&mut String>`; присваивайте через него с `*value = …`.

</details>

<details>
<summary>Ответ</summary>

Тест внутри `mod tests`:

```rust
#[test]
fn secrets_are_redacted() {
    let mut redact = Redact {
        keys: vec!["password".into(), "token".into()],
    };
    let mut out = Vec::new();
    let event = Event::new("login", &[("user", "ana"), ("password", "hunter2")]);
    redact.apply(event, &mut out);
    assert_eq!(
        out,
        vec![Event::new("login", &[("user", "ana"), ("password", "***")])]
    );
}
```

Пока преобразования нет, `cargo test` останавливается с:

```text
error[E0422]: cannot find struct, variant or union type `Redact` in this scope
   --> src/main.rs:118:26
    |
118 |         let mut redact = Redact {
    |                          ^^^^^^ not found in this scope
```

Преобразование (поместите его перед `fn main`):

```rust
/// Replaces the values of secret fields with `***`.
pub struct Redact {
    pub keys: Vec<String>,
}

impl Transform for Redact {
    fn apply(&mut self, mut event: Event, out: &mut Vec<Event>) {
        for key in &self.keys {
            if let Some(value) = event.fields.get_mut(key) {
                *value = "***".to_string();
            }
        }
        out.push(event);
    }
}
```

Почему это работает: меняются только существующие поля (`token` в событии нет, поэтому для него ничего не происходит), и поле остаётся на месте, так что читатель всё ещё видит, что пароль был. Сам текст сообщения не скрывается — настоящему преобразованию `redact` нужны ещё и шаблоны для сообщения, и ваш проектный документ должен это обсудить.

</details>

### Упражнение 4 — Рассчитайте буфер (сложно)

Ваш агент получает 2 000 событий в секунду, примерно по 300 байт. Бэкенд может быть недоступен до 5 минут. (a) Каким должен быть буфер, чтобы вместить весь сбой? (b) Хорошая ли идея — буфер в памяти на машине, где агент должен использовать меньше 100 МиБ? (c) Напишите функцию `buffer_bytes(events_per_second, bytes_per_event, outage_seconds) -> u64` с тестом для этого случая.

<details>
<summary>Подсказка</summary>

Перемножьте частоту, размер и время. 1 МиБ — это 1 048 576 байт.

</details>

<details>
<summary>Ответ</summary>

(a) 2 000 × 300 × 300 с = 180 000 000 байт, около 172 МиБ. (b) Нет: это больше всего бюджета памяти агента. Используйте буфер на диске для сбоя (события пишутся последовательно, а это диски делают хорошо) и маленький буфер в памяти перед ним; или решите отбрасывать после лимита и скажите об этом. В любом случае решение и его числа идут в проектный документ.

```rust
/// Bytes a buffer must hold to survive an outage of the sink without dropping events.
pub fn buffer_bytes(events_per_second: u64, bytes_per_event: u64, outage_seconds: u64) -> u64 {
    events_per_second * bytes_per_event * outage_seconds
}

#[test]
fn five_minutes_at_two_thousand_events_per_second() {
    assert_eq!(buffer_bytes(2_000, 300, 5 * 60), 180_000_000);
}
```

Почему это работает: это та же арифметика «на салфетке», что в Уроке 23.2, оформленная как протестированная функция, чтобы её можно было перезапускать со своими числами (и добавить в `code/p23-estimate`).

</details>

<details>
<summary>Ответ</summary>

Источники производят события, преобразования их меняют, приёмники отправляют дальше. Они образуют граф через `inputs` преобразований и приёмников, и каждое ребро графа — ограниченный буфер.

</details>

2. Почему файловый источник опознаёт файлы по устройству и inode, а не по имени?

<details>
<summary>Ответ</summary>

Потому что ротация переименовывает файлы и создаёт новые файлы со старым именем. Inode остаётся с содержимым файла, поэтому агент может дочитать старый файл и начать новый со смещения 0.

</details>

3. Чего доставка «хотя бы один раз от файла до приёмника» требует от контрольных точек?

<details>
<summary>Ответ</summary>

Контрольная точка может сдвинуться за строку только после того, как каждый приёмник, получивший события из этой строки, их подтвердил. Тогда сбой может вызвать повторы, но никогда — потерю.

</details>

4. Чем `when_full = "block"` отличается от `"drop_newest"` и что агент обязан делать во втором случае?

<details>
<summary>Ответ</summary>

С `block` вышестоящий компонент ждёт, и давление переходит обратно к источнику (он перестаёт читать). С `drop_newest` входящие события отбрасываются; агент должен считать каждое отброшенное событие в метрике, чтобы потеря никогда не была молчаливой.

</details>

5. Почему трейт `Transform` устроен так, что принимает событие по значению и пишет в `out: &mut Vec<Event>`?

<details>
<summary>Ответ</summary>

Приём по значению избегает копий, а запись в `out` позволяет одному преобразованию с одной сигнатурой выдать ноль событий (фильтр), одно (изменение) или много (разделение).

</details>

6. Почему метка с высокой кардинальностью — проблема и как контракт её предотвращает?

<details>
<summary>Ответ</summary>

Каждое отдельное значение метки создаёт новый временной ряд в бэкенде метрик, что делает его медленным и дорогим. M5 использует список разрешённых (или запрещённых) ключей меток, который проверяет `pipe check`.

</details>

7. Почему о собственных проблемах агента нужно сообщать метриками, а не строкой лога на каждое событие?

<details>
<summary>Ответ</summary>

Строка лога на каждое отброшенное событие может давать тысячи строк в секунду и сделать агент самым большим источником логов. Счётчики показывают то же самое дёшево; строк лога об изменениях состояния достаточно.

</details>

## Итоги

- Вариант 4 — агент наблюдаемости: источники, преобразования и приёмники в проверенном графе, соединённые ограниченными буферами.
- Файловый источник следует за ротацией и обрезкой по inode и сохраняет контрольные точки; контрольные точки сдвигаются только со сквозными подтверждениями, что даёт доставку «хотя бы один раз».
- Буферы блокируют или отбрасывают, в памяти или на диске; каждое отбрасывание считается, а память остаётся ограниченной, что бы ни делал бэкенд.
- Контракт фиксирует командную строку, граф конфигурации, модель событий и девять правил; трейт `Transform` и его тесты — первый код.
- Вехи: M0 `pipe check`, M1 первый конвейер, M2 надёжное чтение файлов, M3 надёжная доставка по HTTP, M4 буферы, M5 метрики, M6 производительность и DaemonSet.
- Изучайте Vector, OpenTelemetry Collector, Fluent Bit и спецификацию remote write после того, как сами спроектировали каждую часть.
