## Новые слова

| Слово | Значение |
|---|---|
| **действие XDP** (XDP action) | Ответ, который программа XDP возвращает для пакета: пропустить, отбросить, отправить обратно или перенаправить. |
| **`XDP_PASS` / `XDP_DROP`** | «Отдать пакет обычному сетевому стеку» / «выбросить сейчас же». |
| **`XDP_TX` / `XDP_REDIRECT`** | «Отправить обратно через тот же интерфейс» / «отправить на другой интерфейс или процессор». |
| **`XDP_ABORTED`** | «Что-то пошло не так»: пакет отбрасывается, и учитывается событие ошибки. |
| **данные пакета / `data_end`** (packet data) | Начальный и конечный адреса байтов пакета; каждое чтение должно оставаться до `data_end`. |
| **проверка границ** (bounds check) | Сравнение, которое доказывает верификатору, что чтение остаётся внутри пакета. |
| **сетевое пространство имён** (network namespace) | Отдельная копия сетевого стека: свои интерфейсы, адреса и маршруты (Урок 13.15). |
| **пара veth** (veth pair, virtual Ethernet) | Два виртуальных сетевых интерфейса, соединённых как два конца кабеля. |
| **нативный / универсальный XDP** (native / generic XDP) | XDP, выполняемый сетевым драйвером (быстро) / XDP, выполняемый чуть позже ядром для любого интерфейса (работает везде). |
| **заголовок Ethernet** (Ethernet header) | Первые 14 байтов кадра: MAC-адреса (Media Access Control, управление доступом к среде) назначения и источника и EtherType. |
| **EtherType** | 2-байтовое число, которое говорит, что идёт после заголовка Ethernet, например `0x0800` для IPv4. |
| **ICMP** (Internet Control Message Protocol, протокол управляющих сообщений интернета) | Протокол `ping` (номер протокола IP — 1). |
| **блок-лист** (blocklist) | Список адресов, пакеты от которых нужно отбрасывать. |

**Сокращения из прошлых уроков:** BPF (Berkeley Packet Filter, пакетный фильтр Беркли — имя, из которого вырос eBPF),
ВМ (виртуальная машина; Linux-ВМ `dev`), CPU (Central Processing Unit, центральный процессор), IP (Internet
Protocol, межсетевой протокол; IPv4 и IPv6 — его версии 4 и 6), TCP (Transmission Control Protocol, протокол
управления передачей) и UDP (User Datagram Protocol, протокол пользовательских датаграмм) из Урока 15.3, ARP (Address
Resolution Protocol, протокол определения адреса: находит MAC-адрес по IP-адресу), LSM (Linux Security Modules, модули
безопасности Linux, Урок 22.6) и SKB (от `sk_buff`, «socket buffer», буфер сокета — структура пакета в ядре).

## 1. XDP: одно решение на пакет

XDP выполняет вашу программу в сетевом драйвере для каждого принятого пакета, **до того** как ядро построит свою
обычную структуру пакета (`sk_buff`), и до любого правила брандмауэра, сокета или решения о маршрутизации:

```text
  network card ──> driver ──> [ XDP program ] ──> kernel network stack ──> sockets ──> your server
                                   │
                                   ├── XDP_DROP      (gone, almost no cost)
                                   ├── XDP_TX        (bounced back out)
                                   └── XDP_REDIRECT  (to another interface or CPU)
```

Так как XDP работает так рано, отбросить пакет в нём очень дёшево: так крупные сервисы переживают потоки ненужного
трафика. Цена — вы видите только **сырые байты**: заголовок Ethernet, затем (возможно) заголовок IPv4, затем
(возможно) TCP, UDP или ICMP — разбирать их вы должны сами.

Контекст `XdpContext` даёт два адреса: `ctx.data()` — первый байт пакета и `ctx.data_end()` — байт после последнего.
Верификатор отклоняет любое чтение, о котором не может доказать, что оно до `data_end`. Поэтому каждое обращение к
заголовку начинается с проверки вроде этой вспомогательной функции:

```rust
#[inline(always)]
fn ptr_at<T>(ctx: &XdpContext, offset: usize) -> Option<*const T> {
    let start = ctx.data();
    let end = ctx.data_end();
    if start + offset + core::mem::size_of::<T>() > end {
        return None;
    }
    Some((start + offset) as *const T)
}
```

После `if` верификатор знает, что `size_of::<T>()` байтов по адресу `start + offset` находятся внутри пакета, и
разрешает чтение через возвращённый указатель. `#[inline(always)]` держит проверку в той же функции, что и чтение, где
верификатор видит обе. Слишком короткий пакет просто даёт `None`.

На практике важны два режима. **Нативный** XDP выполняет сам драйвер; это быстрый путь, и виртуальные интерфейсы
`veth` из этого урока его поддерживают. **Универсальный** XDP (его называют ещё режимом SKB) выполняется чуть позже в
ядре и работает с любым интерфейсом; он медленнее, но полезен для тестирования. `XdpMode::Default` в Aya позволяет
ядру выбрать самому.

## 2. Тестовая сеть в ВМ

Никогда не подключайте отбрасывающую программу к настоящему сетевому интерфейсу ВМ: вы можете оборвать собственное
соединение. Постройте вместо этого частную тестовую сеть: второе сетевое пространство имён, `p22-peer`, соединённое с
основным парой veth. Сохраните это как `netns.sh` в папке проекта:

```sh
#!/bin/sh
# Создаёт второе сетевое пространство имён, соединённое с этим парой veth.
set -eu
ip netns add p22-peer
ip link add p22-host type veth peer name p22-peer netns p22-peer
ip addr add 10.22.0.1/24 dev p22-host
ip link set p22-host up
ip netns exec p22-peer ip addr add 10.22.0.2/24 dev p22-peer
ip netns exec p22-peer ip link set p22-peer up
```

```text
 main namespace (the VM)                 namespace p22-peer
 ┌──────────────────────┐   veth pair   ┌──────────────────────┐
 │ p22-host 10.22.0.1   ├───────────────┤ p22-peer 10.22.0.2   │
 │   ↑ XDP runs here    │               │   ping 10.22.0.1     │
 └──────────────────────┘               └──────────────────────┘
```

**Что происходит:**

1. `ip netns add p22-peer` создаёт пустое сетевое пространство имён.
2. `ip link add ... type veth peer name p22-peer netns p22-peer` создаёт оба конца виртуального кабеля и сразу
   переносит один конец в новое пространство имён.
3. Каждый конец получает адрес в `10.22.0.0/24` и включается.
4. `ip netns exec p22-peer <command>` запускает команду внутри другого пространства имён. `ping` оттуда на `10.22.0.1`
   приходит на `p22-host`, где и будет стоять ваша программа XDP.

Запустите это один раз в ВМ через `sudo ./netns.sh` (после перезагрузки ВМ нужно запустить снова). Чтобы потом убрать
тестовую сеть: `sudo ip link del p22-host; sudo ip netns del p22-peer`.

## 3. Самая маленькая программа XDP

Создайте новое рабочее пространство `code/p22-netwatch`, скопировав структуру `p22-tracer` из Урока 22.7: тот же
`.cargo/config.toml`, те же два файла `build.rs` и файлы `Cargo.toml`, где `tracer` везде переименован в `netwatch`.
Зависимости рабочего пространства — как в Уроке 22.8 (без `aya-log`):

```toml
[workspace]
resolver = "3"
members = ["netwatch", "netwatch-ebpf"]
default-members = ["netwatch"]

[workspace.package]
edition = "2024"

[workspace.dependencies]
aya = "0.16"
aya-build = "0.2"
aya-ebpf = "0.3"
anyhow = "1"
cargo_metadata = "0.23"
tokio = { version = "1", features = ["macros", "rt-multi-thread", "signal", "time"] }
which = "8"

[profile.release.package.netwatch-ebpf]
debug = 2
codegen-units = 1
```

`netwatch-ebpf/src/main.rs` считает каждый пакет и пропускает его:

```rust
#![no_std]
#![no_main]

use aya_ebpf::{
    bindings::xdp_action,
    macros::{map, xdp},
    maps::PerCpuArray,
    programs::XdpContext,
};

/// One packet counter per CPU.
#[map]
static PACKETS: PerCpuArray<u64> = PerCpuArray::with_max_entries(1, 0);

#[xdp]
pub fn netwatch(_ctx: XdpContext) -> u32 {
    if let Some(count) = PACKETS.get_ptr_mut(0) {
        // SAFETY: the pointer points to this CPU's counter in the map.
        unsafe { *count += 1 };
    }
    xdp_action::XDP_PASS
}

#[cfg(not(test))]
#[panic_handler]
fn panic(_info: &core::panic::PanicInfo) -> ! {
    loop {}
}

#[unsafe(link_section = "license")]
#[unsafe(no_mangle)]
static LICENSE: [u8; 13] = *b"Dual MIT/GPL\0";
```

`netwatch/src/main.rs` подключает её к интерфейсу и каждую секунду печатает итог:

```rust
use std::ffi::CString;
use std::time::Duration;

use aya::maps::PerCpuArray;
use aya::programs::{Xdp, XdpMode};

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let iface = std::env::args().nth(1).unwrap_or_else(|| "lo".to_string());

    let mut ebpf = aya::Ebpf::load(aya::include_bytes_aligned!(concat!(
        env!("OUT_DIR"),
        "/netwatch"
    )))?;
    let program: &mut Xdp = ebpf.program_mut("netwatch").unwrap().try_into()?;
    program.load()?;
    program.attach(&CString::new(iface.as_str())?, XdpMode::Default)?;

    let packets: PerCpuArray<_, u64> = PerCpuArray::try_from(ebpf.map("PACKETS").unwrap())?;
    println!("Counting packets on {iface}. Press Ctrl-C to stop.");
    loop {
        tokio::select! {
            _ = tokio::signal::ctrl_c() => break,
            _ = tokio::time::sleep(Duration::from_secs(1)) => {
                let total: u64 = packets.get(&0, 0)?.iter().sum();
                println!("packets: {total}");
            }
        }
    }
    Ok(())
}
```

**Что происходит:**

1. `#[xdp]` делает `netwatch` программой XDP. Она возвращает действие; `XDP_PASS` передаёт каждый пакет дальше без
   изменений.
2. Массив по процессорам с одной ячейкой — самый дешёвый глобальный счётчик: пакеты приходят на многие процессоры
   одновременно, и каждый процессор увеличивает свою копию.
3. `program.attach(name, XdpMode::Default)` подключает её к интерфейсу. Aya принимает имя как строку C (`CString`),
   потому что интерфейс ядра использует строки C.
4. `tokio::select!` (Урок 14.14) ждёт того, что наступит раньше: Ctrl-C или следующего тика раз в секунду, когда
   значения процессоров складываются и печатаются.

Соберите и запустите в ВМ (после `sudo ./netns.sh`), а во втором терминале пингуйте из соседнего пространства имён:

```bash
cargo run --release -- p22-host
```

```bash
sudo ip netns exec p22-peer ping -c 3 -i 0.2 10.22.0.1
```

```text
3 packets transmitted, 3 received, 0% packet loss, time 412ms
```

```text
Counting packets on p22-host. Press Ctrl-C to stop.
packets: 2
packets: 8
packets: 9
```

Приходит больше трёх пакетов: кроме трёх эхо-запросов ICMP соседняя сторона посылает сообщения ARP (Address Resolution
Protocol, протокол определения адреса) и сообщения IPv6 о соседях. Пока программа работает, `ip link show p22-host`
показывает, что она подключена:

```text
12: p22-host@if11: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 xdp qdisc noqueue state UP mode DEFAULT group default qlen 1000
    link/ether 06:ca:3f:b4:d4:b2 brd ff:ff:ff:ff:ff:ff link-netns p22-peer
    prog/xdp id 8285 name netwatch tag c1449139186ca030 jited
```

Слово `xdp` и строка `prog/xdp` показывают, что подключена нативная программа XDP с именем `netwatch`. Когда вы
останавливаете `netwatch`, программа отключается автоматически.

## Проект

### Что вы создадите

`p22-netwatch` v1: инструмент XDP, который считает пакеты по протоколам на одном интерфейсе и отбрасывает все пакеты
IPv4 от заблокированных адресов. Если заблокирован `10.22.0.2` и соседняя сторона трижды пингует, эталонное решение
печатает:

```text
blocking 10.22.0.2
watching p22-host, Ctrl-C to stop
icmp 0 tcp 0 udp 0 other 1 dropped 0
icmp 3 tcp 0 udp 0 other 2 dropped 3
icmp 3 tcp 0 udp 0 other 2 dropped 3
```

а ping в соседнем пространстве имён сообщает `3 packets transmitted, 0 received, 100% packet loss`.

### Контракт

- **Использование:** `netwatch <interface> [--block <ipv4-address>]...`, запуск от root (через раннер).
- **Запуск:** по одной строке `blocking <address>` на каждый заблокированный адрес, затем
  `watching <interface>, Ctrl-C to stop`.
- **Каждую секунду:** одна строка `icmp <n> tcp <n> udp <n> other <n> dropped <n>`, итоги с момента запуска.
- **Подсчёт:** пакеты IPv4 попадают в `icmp`, `tcp` или `udp` по номеру протокола (1, 6, 17), всё остальное (другие
  протоколы IPv4, IPv6, ARP, слишком короткие пакеты) — в `other`.
- **Блокировка:** пакет IPv4, адрес **источника** которого есть в блок-листе, отбрасывается (`XDP_DROP`) и
  учитывается ещё и в `dropped`. Все остальные пакеты проходят.
- **Ошибки:** неправильный адрес вроде `--block 10.22.0.300` завершает программу с ошибкой до того, как что-либо
  подключено.
- **Качество:** чистая логика (классификация протокола, разбор аргументов) живёт в `netwatch-common` с модульными
  тестами; `cargo clippy` и `cargo fmt --check` проходят чисто; есть README; по одному коммиту на веху.

### Пошаговый план

#### M1 — Считаем по протоколам

**Цель:** пять счётчиков вместо одного, которые заполняются разбором заголовков Ethernet и IPv4 с проверками границ.

**Указания:** добавьте на сторону ядра крейт `network-types = "0.2"`; в нём есть структуры `#[repr(C)]` `EthHdr` и
`Ipv4Hdr`. Используйте вспомогательную функцию `ptr_at` из раздела 1 для каждого заголовка. Сделайте массив по
процессорам длиной пять ячеек и дайте номерам ячеек имена (константы) в новом крейте `netwatch-common`, которым
пользуются обе стороны.

<details>
<summary>Подсказка</summary>

`EthHdr::LEN` — размер заголовка Ethernet, поэтому заголовок IPv4 находится в `ptr_at::<Ipv4Hdr>(ctx, EthHdr::LEN)`.
Поле `ether_type` у `EthHdr` — сырое `u16` в сетевом порядке байтов; сравнивайте его с `EtherType::Ipv4 as u16`,
которое крейт определяет уже преобразованным. У `Ipv4Hdr` есть поля `proto: u8` и `src_addr: [u8; 4]`.

</details>

**Готово, когда:** три пинга от соседа дают строку с `icmp 3` (счётчик `other` меняется):

```text
watching p22-host, Ctrl-C to stop
icmp 0 tcp 0 udp 0 other 2 dropped 0
icmp 3 tcp 0 udp 0 other 6 dropped 0
```

#### M2 — Блок-лист

**Цель:** `--block <address>` (можно повторять) заполняет карту, а программа XDP отбрасывает пакеты от этих
источников.

**Указания:** `HashMap<[u8; 4], u8>` на стороне ядра (значение не используется; ключ — байты адреса в сетевом порядке,
ровно как они стоят в заголовке). На стороне пользователя разберите каждый адрес через `std::net::Ipv4Addr` и вставьте
`ip.octets()` **после** загрузки программы, но до или после подключения — подумайте, что лучше, и запишите причину в
README.

<details>
<summary>Подсказка</summary>

Сторона пользователя: `let mut blocked: HashMap<_, [u8; 4], u8> = HashMap::try_from(ebpf.map_mut("BLOCKED").unwrap())?;`
и `blocked.insert(&ip.octets(), &1, 0)?;`. Сторона ядра: `if unsafe { BLOCKED.get(&src) }.is_some() { ... XDP_DROP }`.
Учтите отброшенный пакет в ячейке `DROPPED` перед возвратом.

</details>

**Готово, когда:** с `cargo run --release -- p22-host --block 10.22.0.2` пинг от соседа не проходит:

```bash
sudo ip netns exec p22-peer ping -c 3 -i 0.2 -W 1 10.22.0.1
```

```text
3 packets transmitted, 0 received, 100% packet loss, time 412ms
```

а `netwatch` печатает `dropped 3`. Без `--block` тот же пинг снова работает.

#### M3 — Чистая логика и её тесты

**Цель:** вынести в `netwatch-common` каждое решение, которому не нужно ядро, и тестировать его на любой машине.

**Указания:** как минимум две чистые функции: `bucket(is_ipv4: bool, proto: u8) -> u32` (в какую ячейку счётчика
попадает пакет) и разбор аргументов, который возвращает имя интерфейса и список заблокированных адресов или ошибку.
Сторона ядра вызывает `bucket`; сторона пользователя — разбор аргументов.

<details>
<summary>Подсказка</summary>

Оставьте `netwatch-common` с `#![cfg_attr(not(test), no_std)]`. Разбору аргументов нужны `Vec` и `String`, которых нет
в `core`: поместите его в библиотечную часть крейта стороны пользователя (`netwatch/src/lib.rs`) или за фичу (feature)
Cargo `user` общего крейта, как это делает официальный шаблон Aya. Случаи для тестов: ICMP/TCP/UDP/другое; нет
аргументов; `--block` без адреса; неправильный адрес.

</details>

**Готово, когда:** `cargo test` (в ВМ, из рабочего пространства) запускает минимум шесть тестов и они проходят, а
программа отклоняет плохой адрес:

```text
Error: invalid IPv4 address syntax
```

#### M4 — Сквозной тестовый скрипт

**Цель:** `test.sh` проверяет всё поведение: пинг проходит без блокировки, ICMP считается, пинг не проходит с
блокировкой, и отбрасываются три пакета.

**Указания:** запустите `netwatch` в фоне через `&`, запомните ID его процесса из `$!`, выполните пинг, немного
подождите, чтобы напечаталась ещё одна строка, остановите его через `kill -INT` и проверьте сохранённый вывод через
`grep`. Запускайте скрипт через `sudo` после `./netns.sh`.

<details>
<summary>Подсказка</summary>

```sh
$bin p22-host --block 10.22.0.2 > /tmp/netwatch-block.txt &
sleep 1
if ip netns exec p22-peer ping -c 3 -i 0.2 -W 1 10.22.0.1 > /dev/null; then
  echo "FAIL: ping should be blocked"; kill -INT $!; exit 1
fi
```

</details>

**Готово, когда:**

```bash
cargo build --release && sudo ./test.sh
```

```text
ok:   ping passes without a block
ok:   icmp packets counted
ok:   ping is blocked
ok:   3 packets dropped
all checks passed
```

#### M5 — Завершение

**Цель:** проект, который не стыдно показать. `cargo clippy` и `cargo fmt --check` проходят чисто, есть README с
командами из разделов 2–3 и M4, короткий абзац «как это работает» со схемой из раздела 1, а `git log --oneline`
показывает по одному коммиту на веху.

**Готово, когда:** ваш знакомый может клонировать репозиторий, пройти по README в чистой ВМ и увидеть
`all checks passed`.

### Дополнительные цели

- **Блокировка по порту назначения.** Разбирайте ещё и заголовки TCP и UDP (`TcpHdr`, `UdpHdr` из `network-types`) и
  отбрасывайте, например, все пакеты UDP на порт 9. Помните о новой проверке границ для каждого заголовка.
- **Изменение блок-листа на лету.** Пусть программа работает, а вы добавляете или удаляете адреса во время её работы
  (например, читая команды со стандартного ввода). Сторона ядра не меняется вообще — в этом сила карт.
- **Статистика по источникам.** `PerCpuHashMap<[u8; 4], u64>` со счётчиками пакетов по адресам источника и печать
  «пятёрки лидеров» каждую секунду.
- **`XDP_TX`.** Отвечайте на пинги сами: поменяйте местами MAC- и IP-адреса, замените тип ICMP на «эхо-ответ»,
  исправьте контрольную сумму и верните `XDP_TX`.
- **Бенчмарк.** Измерьте генератором пакетов, сколько пакетов в секунду обрабатывает ваша программа, и сравните с
  одним только `XDP_PASS` (Урок 19.2 о нагрузочном тестировании).

## Частые ошибки

> ⚠️ **Частая ошибка:** читать заголовок без проверки границ, например `(ctx.data() + EthHdr::LEN) as *const Ipv4Hdr`
> без сравнения с `data_end`. Загрузка падает:
>
> ```text
> invalid access to packet, off=27 size=1, R3(id=0,off=27,r=14)
> R3 offset is outside of the packet
> ```
>
> Верификатор знает только, что проверены 14 байтов (`r=14`, заголовок Ethernet), а программа читает байт 27 (внутри
> заголовка IPv4). Используйте `ptr_at` для каждого заголовка.

> ⚠️ **Частая ошибка:** сравнивать EtherType или адреса не в том порядке байтов. Поля заголовков хранятся в big-endian
> (сетевой порядок), а ваш процессор — little-endian. `EtherType::Ipv4 as u16` из `network-types` уже преобразован;
> адреса сравниваются как массивы `[u8; 4]`, у которых проблемы с порядком байтов нет.

> ⚠️ **Частая ошибка:** подключить отбрасывающую программу XDP к основному интерфейсу ВМ (`eth0`). Вы можете потерять
> соединение с ВМ. Тестируйте на паре veth; если это всё же случилось, перезапустите ВМ через `limactl stop dev` и
> `limactl start dev`.

> ⚠️ **Частая ошибка:** забыть, что пара veth и пространство имён исчезают при перезапуске ВМ. Если `netwatch`
> говорит, что интерфейса нет, снова выполните `sudo ./netns.sh`.

## Вопросы для самопроверки

1. Почему отбросить пакет в XDP дешевле, чем отбросить его правилом брандмауэра позже в ядре?

<details>
<summary>Ответ</summary>

XDP работает в драйвере до того, как ядро выделит свою структуру пакета, и до поиска маршрута, правил брандмауэра и
сокетов. Отброшенный пакет почти ничего не стоит, кроме чтения его первых байтов.

</details>

2. Что требует верификатор, прежде чем программа XDP прочитает заголовок IPv4?

<details>
<summary>Ответ</summary>

Проверку того, что весь заголовок лежит до `data_end` (начало + смещение + размер ≤ конец). Без такого сравнения на
пути к чтению программа отклоняется.

</details>

3. Чем отличаются `XDP_PASS`, `XDP_DROP` и `XDP_TX`?

<details>
<summary>Ответ</summary>

`XDP_PASS` отдаёт пакет обычному сетевому стеку, `XDP_DROP` сразу его выбрасывает, а `XDP_TX` отправляет обратно через
интерфейс, через который он пришёл (обычно после изменения).

</details>

4. Почему проект использует пару veth и сетевое пространство имён, а не настоящий интерфейс ВМ?

<details>
<summary>Ответ</summary>

Это частная, управляемая сеть: вы знаете каждый пакет (свои пинги), а ошибка, которая отбрасывает пакеты, не может
оборвать ваше собственное соединение с ВМ.

</details>

5. Почему блок-лист можно менять, пока программа XDP работает, не перезагружая её?

<details>
<summary>Ответ</summary>

Программа только ищет адрес источника в карте. Пространство пользователя может добавлять или удалять записи карты в
любой момент; следующий пакет видит новое содержимое.

</details>

## Итоги

- XDP выполняет программу eBPF в драйвере для каждого принятого пакета и возвращает действие: пропустить, отбросить,
  отправить обратно или перенаправить.
- Данные пакета — сырые байты между `data()` и `data_end()`; каждое чтение заголовка требует проверки границ
  (`ptr_at`), иначе верификатор отклоняет программу.
- Сетевое пространство имён и пара veth — безопасная тестовая сеть внутри ВМ.
- Проект: счётчики по протоколам в массиве по процессорам, блок-лист IPv4 в хеш-таблице, чистая логика с тестами и
  сквозной тестовый скрипт.
- Дальше: Aya book, *Learning eBPF*, *BPF Performance Tools*, XDP tutorial и вклад в Aya, bpf-linker, bpfman,
  bpftrace или Cilium.
