## Новые слова

| Слово | Значение |
|---|---|
| **криптография** (cryptography) | Наука о том, как с помощью математики сохранять информацию секретной, неизменной и подтверждённой по автору. |
| **хеш-функция** (hash function) | Функция, которая превращает любой объём данных в короткое значение фиксированного размера (*хеш*, *дайджест* или *отпечаток*). Один и тот же вход всегда даёт один и тот же результат. |
| **SHA-256** (Secure Hash Algorithm, 256 bits, безопасный алгоритм хеширования, 256 бит) | Стандартная хеш-функция, выдающая 32 байта (256 бит). Входит в семейство SHA-2. |
| **коллизия** (collision) | Два разных входа с одинаковым хешем. Хорошая хеш-функция делает поиск коллизии практически невозможным. |
| **лавинный эффект** (avalanche effect) | Крошечное изменение входа меняет около половины битов результата. |
| **MAC** (Message Authentication Code, код аутентификации сообщения) | Короткая метка, вычисленная из сообщения **и секретного ключа**. Правильную метку может создать только тот, кто знает ключ. |
| **HMAC** (Hash-based Message Authentication Code, MAC на основе хеша) | Стандартный способ построить MAC из хеш-функции, например SHA-256. |
| **ключ** (key) | Секретное значение (случайные байты), которое использует алгоритм. Алгоритм открыт, секрет — это ключ. |
| **атака по времени** (timing attack) | Выведывание секрета через измерение того, сколько времени программа отвечает. |
| **за постоянное время** (constant-time) | Код, время работы которого не зависит от секретных значений. |
| **энтропия** (entropy) | Мера непредсказуемости, измеряется в битах. У ключа со 128 битами энтропии 2^128 равновероятных значений. |
| **CSPRNG** (Cryptographically Secure Pseudo-Random Number Generator, криптографически стойкий генератор псевдослучайных чисел) | Генератор случайных чисел, чей вывод никто не может предсказать, даже увидев много предыдущего вывода. |
| **seed** (начальное значение) | Стартовое значение генератора псевдослучайных чисел. Одинаковый seed — одинаковая последовательность. |
| **hex** (hexadecimal, шестнадцатеричная запись) | Запись байтов двумя символами из `0-9a-f` на каждый. 32 байта превращаются в 64 символа. |
| **base64** | Запись байтов 64 печатными символами (`A-Z a-z 0-9 + /`). Вариант *base64url* использует `-` и `_`, чтобы текст безопасно помещался в URL. |

## 1. Первое правило: не изобретайте криптографию

Криптографию легко написать и крайне трудно написать **правильно**. Самодельный алгоритм может выглядеть
случайным, проходить все ваши тесты и всё равно быть взломанным за вечер тем, кто знает предмет. Даже
правильный алгоритм ломается, если им пользоваться неверно, например повторно использовать значение или потерять ключ.

Поэтому правила этого этапа такие:

1. Никогда не придумывайте свой алгоритм или протокол.
2. Используйте **проверенный** (audited), широко применяемый крейт (чей код просмотрели эксперты).
3. Используйте его **высокоуровневый API** (Application Programming Interface, программный интерфейс: функции, которые предлагает библиотека, например «зашифруй это сообщение»), а не низкоуровневые детали.
4. Читайте документацию крейта именно для той версии, которую используете. Несколько таких крейтов изменили API в 2025 и 2026 годах, поэтому старые руководства могут не компилироваться.

Этот урок даёт три «кирпичика»: хеши, MAC и случайность. Урок 10.10 добавляет шифрование
и подписи. Урок 10.11 показывает, как все они работают вместе в TLS (Transport Layer Security, протоколе защиты сетевых соединений).

## 2. Хеш-функции и SHA-256

Хеш-функция — это **машина отпечатков для данных**. Вы подаёте что угодно (одну букву, фотографию,
файл на 4 ГБ; ГБ — гигабайт, около миллиарда байтов). На выходе получается короткое значение фиксированного размера. На рисунке ниже `H` — хеш-функция:

```text
  "hello"                      ┐
  a 4 GB video file            ├──►  H  ──►  2cf24dba5fb0a30e...  (always 32 bytes)
  (nothing at all)             ┘
```

У хеш-функции, которую используют для безопасности, есть такие свойства:

| Свойство | Значение |
|---|---|
| **Детерминированность** | Один и тот же вход всегда даёт один и тот же хеш. |
| **Фиксированный размер** | SHA-256 всегда выдаёт 32 байта при любой длине входа. |
| **Односторонность** | По хешу нельзя найти вход, который его даёт (кроме как перебирая входы). |
| **Стойкость к коллизиям** | Нельзя найти два разных входа с одним хешем. |
| **Лавинный эффект** | Изменение одного бита входа меняет около половины битов результата. |

Создайте `src/bin/sha_basics.rs`:

```rust
use sha2::{Digest, Sha256};

fn main() {
    // Один вызов: хеш среза байтов.
    let hash = Sha256::digest(b"hello");
    println!("hello          -> {}", hex::encode(hash));

    // Тот же вход — тот же результат; крошечное изменение даёт совсем другой результат.
    println!("hello (again)  -> {}", hex::encode(Sha256::digest(b"hello")));
    println!("Hello          -> {}", hex::encode(Sha256::digest(b"Hello")));

    // По частям: подаём данные кусками.
    let mut hasher = Sha256::new();
    hasher.update(b"hel");
    hasher.update(b"lo");
    let pieces = hasher.finalize();
    println!("hel + lo       -> {}", hex::encode(pieces));

    // Результат всегда 32 байта (256 бит), какой бы длинной ни была входная строка.
    let long = vec![b'a'; 1_000_000];
    println!("1 million 'a'  -> {} bytes of output", Sha256::digest(&long).len());
}
```

**Что происходит:**

1. `use sha2::{Digest, Sha256}` импортирует тип `Sha256` и трейт `Digest`. Трейт даёт методы `digest`, `new`, `update` и `finalize`. Пока он не импортирован, этих методов нет (Rust позволяет вызывать методы трейта, только если трейт импортирован).
2. `Sha256::digest(b"hello")` хеширует весь срез байтов сразу. `b"hello"` — *байтовая строка*: байты текста. Результат — 32 байта.
3. `hex::encode(hash)` превращает 32 байта в 64 читаемых шестнадцатеричных символа. Сырые байты не печатаются, поэтому хеш мы всегда показываем в hex.
4. Для больших данных создают хешер через `Sha256::new()`, вызывают `update` сколько угодно раз и один раз в конце `finalize`. Если подать `hel`, а затем `lo`, хеш получится тот же, что и для `hello`.
5. Миллион байт на входе всё равно даёт 32 байта на выходе.

Запустите: `cargo run --bin sha_basics`:

```text
hello          -> 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
hello (again)  -> 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
Hello          -> 185f8db32271fe25f561a6fc938b2e264306ec304eda518007d1764826381969
hel + lo       -> 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
1 million 'a'  -> 32 bytes of output
```

Первое значение можно проверить программой, которая уже есть на вашем Mac. Это другая программа,
реализующая тот же стандарт, поэтому результаты обязаны совпасть:

```bash
echo -n hello | shasum -a 256
```

```text
2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824  -
```

(`echo -n` печатает без завершающего перевода строки. Без `-n` вы захешировали бы шесть байтов `hello\n` и получили бы другое значение.)

Строки `hello` и `Hello` выше показывают **лавинный эффект**: одна изменённая буква даёт совершенно другой хеш
(переворачивается около половины из 256 битов результата). Поэтому хеш — хороший отпечаток: никто не может сделать «чуть изменённый» файл с «чуть отличающимся» хешем.

### Для чего нужен хеш

- **Целостность при случайных повреждениях и для загрузок.** Рядом с файлом публикуют его хеш; пользователь хеширует свою копию и сравнивает. Так же устроены `Cargo.lock` и реестры пакетов (Урок 10.13).
- **Отпечатки и идентификаторы.** Git называет каждый коммит и файл по хешу его содержимого (Этап 01).
- **«Кирпичик»** внутри MAC, подписей и хеширования паролей.

### Для чего хеш НЕ нужен

> ⚠️ **Частая ошибка:** «Я хранил в базе `SHA-256(пароль)`, значит пароли в безопасности». Это не так. Хеш по замыслу
> **быстрый**, поэтому злоумышленник с украденной базой может пробовать миллиарды вариантов в секунду.
> Паролям нужен намеренно медленный алгоритм с солью. Это Argon2, из [Урока 10.6](06-authentication-and-password-hashing.md).

> ⚠️ **Частая ошибка:** «Хеш доказывает, кто отправил файл». Нет. Злоумышленник, изменив файл, просто
> вычислит и новый хеш. Если файл и его хеш идут по одному и тому же ненадёжному пути, хеш защищает только от случайных повреждений.
> Чтобы защититься от намеренной атаки, нужен **ключ**: MAC (раздел 4) или подпись (Урок 10.10).

> 📏 **Соглашение:** для нового кода используйте SHA-256 (или SHA-512, SHA-3). **MD5** (Message Digest 5, «дайджест сообщения 5») и **SHA-1** для безопасности сломаны:
> исследователи получили настоящие коллизии (два разных файла с одним хешем). Как быструю контрольную сумму
> от случайных повреждений их ещё можно применять, но никогда там, где есть злоумышленник.

> ⚡ **Производительность:** SHA-256 работает со скоростью сотен мегабайт в секунду и выше на современном CPU (Central Processing Unit, центральный процессор).
> Для контрольных сумм эта скорость — достоинство, для паролей — катастрофа. Чтобы хешировать большой файл, вызывайте `update` для каждого прочитанного куска, тогда весь файл не лежит в памяти.

## 3. Кодирование — это не шифрование

Хеши и ключи — это сырые байты. Чтобы вывести их на экран или положить в JSON (JavaScript Object Notation, текстовый формат данных), URL (веб-адреса) или файл настроек, их **кодируют**
в текст. Два распространённых способа — hex и base64. Создайте `src/bin/encode.rs`:

```rust
use base64::Engine;
use base64::engine::general_purpose::{STANDARD, URL_SAFE_NO_PAD};

fn main() {
    let bytes = [0xfb, 0xff, 0x00, 0x42];
    println!("hex            : {}", hex::encode(bytes));
    println!("base64         : {}", STANDARD.encode(bytes));
    println!("base64url      : {}", URL_SAFE_NO_PAD.encode(bytes));

    // Для декодирования ключ вообще не нужен.
    let decoded = URL_SAFE_NO_PAD.decode("cGFzc3dvcmQxMjM").unwrap();
    println!("decoded        : {}", String::from_utf8(decoded).unwrap());
}
```

**Что происходит:**

1. В `base64` 0.23 вы выбираете *движок* (engine, набор настроек). `STANDARD` использует `+` и `/` и заканчивается дополнением `=`; `URL_SAFE_NO_PAD` использует `-` и `_` и без дополнения. Чтобы получить `encode` и `decode`, нужно импортировать трейт `Engine`.
2. Одни и те же четыре байта в каждой кодировке выглядят по-разному.
3. Мы декодируем строку, похожую на секрет. Ключ и усилия не понадобились: это просто `password123`.

```text
hex            : fbff0042
base64         : +/8AQg==
base64url      : -_8AQg
decoded        : password123
```

> 🔒 **Безопасность:** кодирование ничего не скрывает. Любой декодирует base64 за секунду. «Пароль в base64» — это обычный пароль.
> Если вы видите base64 в файле настроек, в cookie или токене, считайте, что читатель может это прочитать.

## 4. MAC и HMAC: хеш с секретным ключом

Задача: Алиса отправляет Бобу сообщение `user=alice;role=reader` вместе с его хешем SHA-256. Мэллори
находится между ними. Она меняет сообщение на `role=admin` и вычисляет новый хеш. Боб не может отличить подделку.

**MAC** решает это, подмешивая в вычисление **секретный ключ**. Алиса и Боб знают ключ;
Мэллори — нет, поэтому правильную метку для изменённого сообщения она создать не может.

```text
  message ──┐
            ├──►  HMAC-SHA256  ──►  tag (32 bytes)        sent together: message + tag
  key ──────┘

  Bob recomputes the tag with the same key and compares it with the received tag.
  Different message or different key  =>  different tag  =>  reject.
```

Можно подумать: «просто захешируем `ключ + сообщение`». Не делайте так: у SHA-256 есть известная слабость (*length extension*, удлинение сообщения): тот,
кто видит `hash(ключ + сообщение)`, может вычислить `hash(ключ + сообщение + дополнение)`, не зная ключа.
**HMAC** — стандартная конструкция (она хеширует дважды, подмешивая ключ двумя разными способами), которая этого избегает.
Писать её самому не нужно, вы вызываете крейт. Создайте `src/bin/hmac_demo.rs`:

```rust
use hmac::{Hmac, KeyInit, Mac};
use sha2::Sha256;

type HmacSha256 = Hmac<Sha256>;

fn main() {
    let key = b"a secret key that only the server knows";
    let message = b"user=alice;role=reader";

    // Считаем метку.
    let mut mac = HmacSha256::new_from_slice(key).expect("HMAC accepts keys of any length");
    mac.update(message);
    let tag = mac.finalize().into_bytes();
    println!("tag      = {}", hex::encode(tag));

    // Проверяем настоящее сообщение.
    let mut check = HmacSha256::new_from_slice(key).unwrap();
    check.update(message);
    println!("genuine  = {:?}", check.verify_slice(&tag));

    // Проверяем сообщение, которое изменил злоумышленник.
    let mut check = HmacSha256::new_from_slice(key).unwrap();
    check.update(b"user=alice;role=admin ");
    println!("tampered = {:?}", check.verify_slice(&tag));

    // Проверяем с неверным ключом.
    let mut check = HmacSha256::new_from_slice(b"some other key").unwrap();
    check.update(message);
    println!("wrong key= {:?}", check.verify_slice(&tag));
}
```

**Что происходит:**

1. `type HmacSha256 = Hmac<Sha256>;` даёт короткое имя понятию «HMAC на основе SHA-256».
2. `new_from_slice(key)` создаёт состояние MAC из ключа. Этот метод приходит из трейта `KeyInit`, а `update` и `verify_slice` — из трейта `Mac`. Оба трейта нужно импортировать.
3. `mac.finalize().into_bytes()` возвращает 32-байтовую метку.
4. `verify_slice(&tag)` пересчитывает и сравнивает. Он возвращает `Ok(())`, если метка верна, и `Err(MacError)`, если нет. Сравнение внутри выполняется **за постоянное время** (объясняется дальше).
5. Изменённое сообщение и неверный ключ дают ошибку.

```text
tag      = 1b237df19bae7910ef38f6977156889d50fa1374f37f2ccd455f4840d2e3644b
genuine  = Ok(())
tampered = Err(MacError)
wrong key= Err(MacError)
```

Метку можно проверить программой `openssl`, которая есть в macOS (вторая, независимая реализация):

```bash
echo -n 'user=alice;role=reader' | openssl dgst -sha256 -hmac 'a secret key that only the server knows'
```

```text
1b237df19bae7910ef38f6977156889d50fa1374f37f2ccd455f4840d2e3644b
```

(Другие сборки OpenSSL перед тем же значением хеша печатают метку вроде `SHA2-256(stdin)= `.)

### Почему `verify_slice`, а не `==`

Если сравнивать две метки через `==`, сравнение обычно останавливается на **первом различающемся байте**. Догадка,
у которой первый байт верный, отвергается чуть дольше, чем догадка с неверным первым байтом. Злоумышленник, который может
отправлять много догадок и очень точно измерять время, способен узнать метку байт за байтом. Это **атака по времени** (timing attack; вы коротко встречали её в [Уроке 10.6](06-authentication-and-password-hashing.md)).

Создайте `src/bin/compare.rs`, чтобы увидеть идею, не измеряя время. Программа считает, сколько байтов просмотрело наивное сравнение:

```rust
use subtle::ConstantTimeEq;

/// Наивное сравнение, которое останавливается на первом отличии. Возвращает (равны ли, сколько байтов просмотрено).
fn naive_eq(a: &[u8], b: &[u8]) -> (bool, usize) {
    if a.len() != b.len() {
        return (false, 0);
    }
    for i in 0..a.len() {
        if a[i] != b[i] {
            return (false, i + 1);
        }
    }
    (true, a.len())
}

fn main() {
    let secret = b"s3cr3t-t0ken";
    for guess in [&b"x3cr3t-t0ken"[..], b"s3cr3t-t0kex", b"s3cr3t-t0ken"] {
        let (equal, looked) = naive_eq(secret, guess);
        println!("naive    {:<14} equal={equal:<5} looked at {looked} bytes", String::from_utf8_lossy(guess));
    }

    // За постоянное время: всегда просматривает каждый байт. `ct_eq` возвращает `Choice`, а не bool.
    let choice = secret.ct_eq(b"s3cr3t-t0ken");
    println!("constant-time equal = {}", bool::from(choice));
}
```

```text
naive    x3cr3t-t0ken   equal=false looked at 1 bytes
naive    s3cr3t-t0kex   equal=false looked at 12 bytes
naive    s3cr3t-t0ken   equal=true  looked at 12 bytes
constant-time equal = true
```

**Что происходит:**

1. Наивная функция выдаёт информацию: «1 байт» значит, что неверен первый байт; «12 байтов» значит, что первые одиннадцать верны. Каждый ответ сужает поиск.
2. `ct_eq` из крейта `subtle` всегда обрабатывает каждый байт и возвращает `Choice` — значение, устроенное так, чтобы компилятор не превратил проверку обратно в ранний выход. Переводите его в `bool` через `bool::from` только в самом конце.

> 🔒 **Безопасность:** для меток MAC используйте `verify_slice`, а для любого другого секрета, который вы сравниваете, — `subtle::ConstantTimeEq`
> (токены API, идентификаторы сессий, коды сброса). Не пишите `if provided == expected` для секретов.

### От метки к токену

Очень частое применение MAC — *подписанный токен*: текст `payload.tag`, обе части в base64url. Сервер может отдать его браузеру
и позже доверять ему без базы данных, пока метка проверяется. Есть два правила. Первое: проверяйте метку **до** того, как читать или разбирать полезную нагрузку.
Второе: MAC не скрывает полезную нагрузку (любой декодирует base64) и не защищает от **повтора** (replay — повторной отправки старого верного токена), поэтому
настоящий токен несёт внутри подписанных данных ещё и срок действия. Именно это вы построите в Упражнении 3. Скрывать данные — задача шифрования (Урок 10.10).

## 5. Случайность

Ключам, солям, nonce, токенам сессий и кодам сброса нужны числа, которые никто не угадает. Существует два вида
генераторов случайных чисел:

| Вид | Пример | Для чего |
|---|---|---|
| **Псевдослучайный, предсказуемый** | генератор, созданный из `seed` | симуляции, игры, тесты, которые должны повторяться |
| **Криптографически стойкий (CSPRNG)** | байты от операционной системы | ключи, токены, соли, nonce, всё, что злоумышленник не должен угадать |

Псевдослучайный генератор — это просто формула. Запустите его с тем же seed — получите те же числа.
(Урок 10.7 использовал `getrandom::fill` для токенов сессий; вот почему это был правильный выбор.) Если злоумышленник угадает seed (классический плохой seed — текущее время в секундах), он вычислит все ваши
«случайные» значения. Создайте `src/bin/random_demo.rs`:

```rust
use rand::rngs::StdRng;
use rand::{Rng, RngExt, SeedableRng};

fn main() {
    // 1. Генератор с заданным seed — чистая функция от seed: полностью предсказуем.
    let mut a = StdRng::seed_from_u64(42);
    let mut b = StdRng::seed_from_u64(42);
    let (x, y): (u32, u32) = (a.random(), b.random());
    println!("seed 42 twice : {x} and {y}");

    // 2. Секретные байты прямо от операционной системы.
    let mut key = [0u8; 32];
    getrandom::fill(&mut key).expect("the operating system could not give random bytes");
    println!("OS random     : {}", hex::encode(key));

    // 3. Потоковый генератор rand инициализируется от ОС и криптографически стоек.
    let mut token = [0u8; 16];
    rand::rng().fill_bytes(&mut token);
    println!("rand token    : {}", hex::encode(token));
}
```

**Что происходит:**

1. Два генератора, созданные из seed `42`, выдают одно и то же число. Всё, что получено из выбранного вами seed, секретом не является.
2. `getrandom::fill` обращается к источнику случайности операционной системы (в macOS и Linux ядро собирает непредсказуемые события и подаёт их в CSPRNG). Он заполняет массив байтов и возвращает `Result`, потому что в редких случаях (самый ранний этап загрузки, жёсткая песочница) система ответить не может. Для секрета эту ошибку нужно обработать, а не игнорировать.
3. `rand::rng()` возвращает генератор для текущего потока, который крейт `rand` документирует как криптографически стойкий и регулярно переинициализирует от операционной системы. `fill_bytes` заполняет массив. В `rand` 0.10 трейт `Rng` содержит базовые методы (`fill_bytes`), а `RngExt` — удобные (`random`, `random_range`).

```text
seed 42 twice : 572990626 and 572990626
OS random     : 5e26b893468ccd97371c7640045c63ce4d6526c1988c907bdccf2f619a7c5f8b
rand token    : 6b97f6729c97166fb974f25fb553e2f0
```

Последние две строки при каждом запуске разные; повторяется только первая. Сколько байтов достаточно?
Думайте в **битах энтропии**: у случайного 128-битного значения 2^128 вариантов, около 3,4 × 10^38.
Даже при триллионе попыток в секунду перебор всех заняло бы намного больше времени, чем возраст Вселенной.

| Для чего | Случайных байтов |
|---|---|
| Токен сессии, токен сброса, ключ API | 32 (256 бит) |
| Ключ шифрования (Урок 10.10) | 32 |
| Соль для хеша пароля (Урок 10.6) | 16 |
| Nonce для XChaCha20-Poly1305 (Урок 10.10) | 24 |

> 🔒 **Безопасность:** если число что-то защищает, оно берётся от операционной системы или из CSPRNG — никогда не из времени,
> не из счётчика, не из генератора с заданным seed и не из хеша чего-то угадываемого. Не сводите секрет к «случайному числу от 0 до 999999»,
> когда можно взять 32 случайных байта.

> 🧪 **Тестирование:** одним assert нельзя проверить, что байты «достаточно случайны», но можно проверить форму: длину, допустимые символы и то, что два токена различаются (Упражнение 2).

## Частые ошибки

**1. Забыли импортировать трейт.** Уберите `KeyInit` из строки `use hmac::…` в `hmac_demo.rs`. Компилятор не находит `new_from_slice`, хотя `Hmac` импортирован:

```text
error[E0599]: no associated function or constant named `new_from_slice` found for struct `Hmac<D>` in the current scope
  --> src/bin/hmac_demo.rs:11:31
   |
11 |     let mut mac = HmacSha256::new_from_slice(key).expect("HMAC accepts keys of any length");
   |                               ^^^^^^^^^^^^^^ associated function or constant not found in `Hmac<Sha256>`
   |
   = help: items from traits can only be used if the trait is in scope
help: trait `KeyInit` which provides `new_from_slice` is implemented but not in scope; perhaps you want to import it
   |
 1 + use hmac::KeyInit;
   |
```

Подсказка компилятора точна: добавьте `KeyInit` (и `Mac` для `update`) в строку `use`. Это то же правило, что вы видели выше с `Digest`.

**2. Печать хеша через `{:x}`.** В старых руководствах пишут `println!("{:x}", hash)`. В `sha2` 0.11 тип результата больше не реализует `LowerHex`
(`error[E0277]: … LowerHex is not satisfied`). Используйте `hex::encode(hash)`.

**3. Сравнение меток через `==`.** Код компилируется и работает, но выдаёт информацию о времени. Используйте `verify_slice` или `ct_eq`.

**4. Генератор с заданным seed или со временем в роли seed для секретов.** Он компилируется, работает — и угадывается.

**5. Ключ, зашитый в исходный код.** Ключ в `hmac_demo.rs` нужен для обучения. Настоящие ключи берутся из хранилища секретов, о котором вы узнали в Уроке 10.8, и это случайные байты, а не слова.

## Упражнения

### Упражнение 1 — Проверка загрузки (легко)

Создайте `note.txt` с любым текстом. Сохраните его хеш командой `shasum -a 256 note.txt > note.sha256`, затем проверьте
командой `shasum -a 256 -c note.sha256`. Измените `note.txt` и проверьте снова. Что печатается каждый раз?

<details>
<summary>Подсказка</summary>

`-c` значит «check» (проверить): команда пересчитывает хеш каждого файла из списка в `.sha256` и сравнивает.

</details>

<details>
<summary>Ответ</summary>

```bash
printf 'my note\n' > note.txt
shasum -a 256 note.txt > note.sha256
shasum -a 256 -c note.sha256
printf 'changed\n' >> note.txt
shasum -a 256 -c note.sha256
```

```text
note.txt: OK
note.txt: FAILED
shasum: WARNING: 1 computed checksum did NOT match
```

Почему это работает: один изменённый байт даёт совершенно другой хеш (лавинный эффект), поэтому сравнение не проходит.

</details>

### Упражнение 2 — Генератор токена сброса с тестом (средне)

В новом библиотечном пакете (`cargo new --lib code/p10-token`) напишите `pub fn new_token() -> String`, которая возвращает 32 случайных байта в виде 64 hex-
символов, взятых от операционной системы. Напишите тест, который проверяет длину, то, что каждый символ — hex-цифра, и что два токена различаются.

<details>
<summary>Подсказка</summary>

`cargo add getrandom@0.4 hex@0.4`. Заполните массив `[0u8; 32]` через `getrandom::fill`. Тест случайных данных проверяет *форму*, а не значения.

</details>

<details>
<summary>Ответ</summary>

```rust
pub fn new_token() -> String {
    let mut bytes = [0u8; 32];
    getrandom::fill(&mut bytes).expect("no OS randomness");
    hex::encode(bytes)
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn tokens_have_right_shape_and_differ() {
        let (a, b) = (new_token(), new_token());
        assert_eq!(a.len(), 64);
        assert!(a.chars().all(|c| c.is_ascii_hexdigit()));
        assert_ne!(a, b);
    }
}
```

`cargo test` печатает `test tests::tokens_have_right_shape_and_differ ... ok`.

Почему это работает: два случайных 256-битных значения совпадают с вероятностью около 1 к 10^77, поэтому `assert_ne!` не упадёт по невезению. Тест поймал бы ошибку вроде возврата фиксированной строки.

</details>

### Упражнение 3 — Токен со сроком действия (сложно)

Постройте подписанный токен как библиотеку с функциями `sign(key, payload, expires_at)`, которая возвращает `body.tag` (обе части в base64url, а `body` — текст `payload|expires_at`), и `verify(key, token, now)`. Время — в секундах Unix
(целые секунды с 1970-01-01). Срок действия должен быть **внутри подписанных данных**, чтобы злоумышленник не мог его продлить. Тесты: верный токен, просроченный
токен, токен с изменённым сроком и неверный ключ. Передавайте `now` параметром, чтобы тесты не зависели от часов.

<details>
<summary>Подсказка</summary>

Подписывайте текст `"{payload}|{expires_at}"`. В `verify` сначала проверьте метку, затем разделите по последнему `|` через `rsplit_once('|')`, разберите число и сравните с `now`.

</details>

<details>
<summary>Ответ</summary>

```rust
use base64::Engine;
use base64::engine::general_purpose::URL_SAFE_NO_PAD as B64;
use hmac::{Hmac, KeyInit, Mac};
use sha2::Sha256;

type HmacSha256 = Hmac<Sha256>;

pub fn sign(key: &[u8], payload: &str, expires_at: u64) -> String {
    let body = format!("{payload}|{expires_at}");
    let mut mac = HmacSha256::new_from_slice(key).unwrap();
    mac.update(body.as_bytes());
    let tag = mac.finalize().into_bytes();
    format!("{}.{}", B64.encode(&body), B64.encode(tag))
}

pub fn verify(key: &[u8], token: &str, now: u64) -> Option<String> {
    let (body_b64, tag_b64) = token.split_once('.')?;
    let body = B64.decode(body_b64).ok()?;
    let tag = B64.decode(tag_b64).ok()?;
    let mut mac = HmacSha256::new_from_slice(key).ok()?;
    mac.update(&body);
    mac.verify_slice(&tag).ok()?; // сначала проверяем метку, и только потом доверяем содержимому
    let body = String::from_utf8(body).ok()?;
    let (payload, expires) = body.rsplit_once('|')?;
    let expires: u64 = expires.parse().ok()?;
    if now >= expires {
        return None;
    }
    Some(payload.to_string())
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn valid_token_is_accepted_until_it_expires() {
        let key = b"k";
        let token = sign(key, "user=alice", 1000);
        assert_eq!(verify(key, &token, 999).as_deref(), Some("user=alice"));
        assert_eq!(verify(key, &token, 1000), None);
    }

    #[test]
    fn tampering_is_rejected() {
        let key = b"k";
        let token = sign(key, "user=alice", 1000);
        let (_, tag) = token.split_once('.').unwrap();
        // Та же метка, новый срок далеко в будущем.
        let forged = format!("{}.{}", B64.encode("user=alice|9999999"), tag);
        assert_eq!(verify(key, &forged, 10), None);
        assert_eq!(verify(b"other key", &token, 10), None);
    }
}
```

`cargo test` показывает оба теста `ok`.

Почему это работает: срок действия входит в текст, который покрывает метка, поэтому его изменение делает метку недействительной. Передача `now` параметром делает функцию чистой (те же входы — тот же ответ), и поэтому её легко тестировать.

</details>

## Вопросы для самопроверки

1. В SHA-256 подают вход из 5 байт и другой вход из 5 гигабайт. Какой длины два результата?

<details>
<summary>Ответ</summary>

Оба по 32 байта (64 hex-символа). Хеш-функция всегда выдаёт результат фиксированного размера.

</details>

2. Почему `SHA-256(пароль)` — плохой способ хранить пароли?

<details>
<summary>Ответ</summary>

SHA-256 быстрый, поэтому злоумышленник с украденными хешами может проверять миллиарды вариантов в секунду. Паролям нужен медленный алгоритм с солью, например Argon2 (Урок 10.6).

</details>

3. Мэллори может изменить сообщение и пересчитать его обычный хеш SHA-256. Почему она не может сделать то же с меткой HMAC?

<details>
<summary>Ответ</summary>

Для правильной метки HMAC нужен секретный ключ, которого у Мэллори нет.

</details>

4. Что не так с `if token == expected_token` для секретного токена?

<details>
<summary>Ответ</summary>

Сравнение может остановиться на первом различающемся байте, поэтому его время зависит от того, какая часть догадки верна. Это может выдать секрет при атаке по времени. Используйте `subtle::ConstantTimeEq` (или `verify_slice` для меток MAC).

</details>

5. Вам нужен токен сессии. Что правильно: `StdRng::seed_from_u64(now_in_seconds)` или 32 байта из `getrandom::fill`?

<details>
<summary>Ответ</summary>

32 байта из `getrandom::fill`. Генератор, инициализированный временем, может воспроизвести любой, кто угадает время. И помните, что base64 или hex от токена — не защита: это кодировки без ключа.

</details>

## Итоги

- Никогда не изобретайте криптографию. Используйте проверенные крейты, их высокоуровневые API и документацию именно той версии, которую применяете.
- Хеш (SHA-256) — отпечаток данных фиксированного размера: детерминированный, односторонний и стойкий к коллизиям. MD5 и SHA-1 сломаны.
- Обычный хеш обнаруживает случайные повреждения, но не злоумышленника, и он слишком быстр для паролей.
- MAC (HMAC-SHA256) добавляет секретный ключ, поэтому правильную метку могут создать только владельцы ключа. Он подтверждает подлинность сообщения, но не скрывает его.
- Сравнивайте секреты за постоянное время: `verify_slice` для меток, `subtle::ConstantTimeEq` для всего остального.
- Hex и base64 — это кодировки, а не защита.
- Секретные байты берутся от операционной системы (`getrandom`) или из CSPRNG (`rand::rng()`), никогда из генератора с заданным seed или временем. Берите от 16 до 32 байтов.
