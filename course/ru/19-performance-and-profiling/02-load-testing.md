# Урок 19.2 — Нагрузочное тестирование сервисов

> **Этап 19 — Производительность и профилирование** · Урок 2 из 11 · ⏱ около 120 минут

## Что вы узнаете

- Что такое **нагрузочный тест** и чем генератор нагрузки с **закрытой моделью** отличается от генератора с **открытой моделью**.
- Как дать нагрузку на веб-сервис с помощью `oha` и прочитать каждую часть его отчёта.
- Как найти **точку насыщения** сервиса — нагрузку, при которой задержка начинает взрывообразно расти.
- Почему один блокирующий вызов внутри `async`-обработчика может замедлить *все* эндпоинты и как нагрузочный тест это показывает.

## Перед началом

- Вы прошли [Урок 19.1 — Задержка, пропускная способность и перцентили](01-latency-throughput-and-percentiles.md): перцентили, закон Литтла и скоординированный пропуск используются здесь повсюду.
- Вы умеете писать сервис на axum и тестировать его роутер через `oneshot` ([Урок 16.3 — Веб-сервисы на axum](../16-backend-services/03-web-services-with-axum.md)).
- Вы знаете задачи Tokio и `spawn_blocking` ([Урок 14.13 — Tokio подробно: задачи и каналы](../14-concurrency-and-async/13-tokio-tasks-and-channels.md)).
- Вам нужны два окна терминала: в одном работает сервис, в другом — генератор нагрузки.

## Новые слова

| Слово | Значение |
|---|---|
| **нагрузочный тест** (load test) | Запуск сервиса под множеством запросов, чтобы увидеть, как ведут себя его задержка и пропускная способность. |
| **генератор нагрузки** (load generator) | Программа, которая отправляет запросы в нагрузочном тесте. Здесь — `oha`. |
| **соединение** (connection) | Одна открытая связь TCP (Transmission Control Protocol, протокол управления передачей) между клиентом и сервером. С **keep-alive** много запросов используют одно соединение повторно. |
| **конкурентность** (concurrency) | Сколько запросов выполняется одновременно. В `oha` параметр `-c` задаёт число одновременно работающих соединений. |
| **закрытая модель** (closed model) | Генератор с фиксированным числом пользователей: каждый отправляет запрос, ждёт ответа, затем отправляет следующий. Когда сервер замедляется, нагрузка падает. |
| **открытая модель** (open model) | Генератор, который отправляет запросы с фиксированной **частотой** (например, 300 в секунду) независимо от того, пришли ли ответы на прежние, — как настоящие пользователи в интернете. |
| **QPS** (Queries Per Second, запросов в секунду) | Частота запросов, которые отправляет генератор. То же, что req/s. |
| **насыщение** (saturation) | Состояние, в котором ресурс (ядра процессора, CPU — Central Processing Unit, потоки, соединения) занят всё время. Дополнительная нагрузка тогда только удлиняет очередь. |
| **колено** (knee) | Точка на кривой «нагрузка → задержка», где задержка перестаёт быть ровной и начинает быстро расти. |
| **ёмкость** (capacity) | Наибольшая нагрузка, которую сервис выдерживает, всё ещё укладываясь в цель по задержке (например, p99 ниже 50 мс). |
| **TUI** (Text User Interface, текстовый интерфейс пользователя) | Экран внутри терминала, который сам перерисовывается, с полосками и числами. `oha` показывает его, если не передать `--no-tui`. |
| **DNS** (Domain Name System, система доменных имён) | Система, которая превращает имя хоста, например `example.com`, в IP-адрес (Internet Protocol, межсетевой протокол). |
| **DoS** (Denial of Service, отказ в обслуживании) | Атака (или случайность), которая делает сервис непригодным, давая ему больше работы, чем он может выполнить. |

## 1. Что такое нагрузочный тест

Бенчмарк (Урок 09.11) измеряет один фрагмент кода отдельно. **Нагрузочный тест** измеряет весь работающий сервис снаружи: сетевой стек, разбор HTTP (HyperText Transfer Protocol, протокол передачи гипертекста), асинхронный рантайм, ваши обработчики — всё сразу, под множеством одновременных запросов. Он отвечает на вопросы вроде:

- Сколько запросов в секунду этот сервис выдерживает на этой машине?
- Каковы p50 и p99 при 1000 req/s? При 10 000 req/s?
- При какой нагрузке он **насыщается** и что происходит тогда: плавно замедляется или падает?

Нагрузочные тесты бывают разные. **Дымовой тест** (smoke test) даёт небольшую нагрузку, просто чтобы проверить, что всё работает. **Нагрузочный тест** воспроизводит ожидаемый трафик. **Стресс-тест** (stress test) выходит за его пределы, чтобы найти предел. **Тест на выносливость** (soak test) часами держит обычную нагрузку, чтобы найти медленные утечки. В этом уроке мы сделаем первые три на вашем Mac.

Сам генератор нагрузки может работать двумя способами, и разница важна (вспомните скоординированный пропуск из Урока 19.1):

```text
closed model (oha -c 10)                 open model (oha -q 300)
10 "users", each one:                    a clock sends a request every 1/300 s:
  send -> wait for answer -> send ...      send, send, send, send ...  (does not wait)
server slow  => fewer requests sent      server slow  => requests pile up, latency grows
good for: "how much can it do?"          good for: "what do users feel at this traffic?"
```

> 🔒 **Безопасность:** нагрузочный тест — разновидность DoS. Запускайте его только против своих сервисов: на своей машине, в ВМ (виртуальной машине) `dev` (Этап 11) или в тестовом окружении, которым вам разрешено пользоваться. Никогда не направляйте генератор нагрузки на чужой сайт или API (Application Programming Interface, программный интерфейс: адреса, через которые программы обращаются к сервису).

## 2. Сервис для тестирования

Соберём небольшой сервис с четырьмя эндпоинтами, которые ведут себя совсем по-разному. Создайте пакет:

```bash
cd ~/projects/rust/code
cargo new p19-load
cd p19-load
cargo add axum@0.8
cargo add tokio@1 --features full
cargo add serde@1 --features derive
cargo add --dev tower@0.5 --features util
cargo add --dev http-body-util@0.1
```

`src/main.rs`:

```rust
use std::time::Duration;

use axum::{Router, extract::Query, routing::get};
use serde::Deserialize;

/// Pretend CPU work: `n` thousand rounds of arithmetic. n = 100 takes about 0.1 ms.
fn checksum(n: u64) -> u64 {
    let mut x = n;
    for _ in 0..n * 1000 {
        x = x.wrapping_mul(6364136223846793005).wrapping_add(1);
    }
    x
}

#[derive(Deserialize)]
struct WorkParams {
    n: Option<u64>,
}

async fn hello() -> &'static str {
    "hello\n"
}

async fn work(Query(params): Query<WorkParams>) -> String {
    let n = params.n.unwrap_or(100).min(10_000);
    format!("{}\n", checksum(n))
}

/// Waits 20 ms without using a thread, like a call to a database.
async fn wait() -> &'static str {
    tokio::time::sleep(Duration::from_millis(20)).await;
    "waited\n"
}

/// WRONG on purpose: blocks a whole runtime thread for 20 ms.
async fn blocking() -> &'static str {
    std::thread::sleep(Duration::from_millis(20));
    "blocked\n"
}

fn app() -> Router {
    Router::new()
        .route("/hello", get(hello))
        .route("/work", get(work))
        .route("/wait", get(wait))
        .route("/blocking", get(blocking))
}

#[tokio::main(worker_threads = 4)]
async fn main() {
    let listener = tokio::net::TcpListener::bind("127.0.0.1:3019")
        .await
        .unwrap();
    println!("listening on http://127.0.0.1:3019 with 4 worker threads");
    axum::serve(listener, app()).await.unwrap();
}
```

**Что происходит:**

1. `/hello` почти ничего не делает. Он показывает стоимость самого HTTP и рантайма.
2. `/work` тратит время CPU (Central Processing Unit, центральный процессор): `checksum(100)` — это около 0,1 мс арифметики. Параметр запроса `n` меняет объём работы.
3. `/wait` ждёт 20 мс через `tokio::time::sleep`. Пока он ждёт, рабочий поток свободен и обслуживает другие запросы — ровно как при ожидании ответа базы данных.
4. `/blocking` ждёт 20 мс через `std::thread::sleep`. Это останавливает **весь рабочий поток**. Это ошибка, сделанная намеренно; что она вызывает, покажет раздел 5.
5. `#[tokio::main(worker_threads = 4)]` фиксирует рантайм на 4 рабочих потоках. По умолчанию их по одному на ядро; фиксированное число делает результаты понятнее и оставляет ядра свободными для генератора нагрузки, который работает на том же Mac.
6. Порт — 3019, чтобы не конфликтовать с сервисом Этапа 16 на порту 3000.

> 🔒 **Безопасность:** `.min(10_000)` ограничивает, сколько работы может запросить один запрос. Без этого один запрос `/work?n=99999999999` занял бы ядро на часы. Никогда не позволяйте клиенту выбирать неограниченный объём работы.

В первом терминале запустите сервис **в режиме release**:

```bash
cargo run --release
```

```text
listening on http://127.0.0.1:3019 with 4 worker threads
```

Во втором терминале один раз проверьте каждый эндпоинт вручную. Нагрузочный тест сломанного эндпоинта ничего полезного не измеряет:

```bash
curl -s http://127.0.0.1:3019/hello
curl -s 'http://127.0.0.1:3019/work?n=100'
curl -s http://127.0.0.1:3019/wait
```

```text
hello
13404730972402714436
waited
```

## 3. Первый нагрузочный тест с oha

`oha` — генератор нагрузки, написанный на Rust. Установите его (компиляция займёт несколько минут):

```bash
cargo install --locked oha
oha --version
```

```text
oha 1.17.0
```

Отправьте 2000 запросов по 10 соединениям на `/hello`:

```bash
oha -n 2000 -c 10 --no-tui http://127.0.0.1:3019/hello
```

**Что происходит** (читайте отчёт сверху вниз):

1. `-n 2000` отправляет всего 2000 запросов; `-c 10` держит 10 соединений занятыми одновременно (закрытая модель с 10 пользователями). `--no-tui` печатает простой отчёт вместо живого экрана. Без него `oha` рисует в терминале живой экран с индикатором прогресса, текущими запросами в секунду и растущей гистограммой, а в конце печатает тот же отчёт.
2. **Summary** (сводка). *Success rate* — доля запросов, получивших хоть какой-то HTTP-ответ (проверяйте её первой!). *Total* — общее время теста по часам. *Requests/sec* — пропускная способность: около 62 000 req/s. Закон Литтла согласен: 10 в работе ÷ 0,147 мс ≈ 68 000.
3. **Response time histogram** (гистограмма времени ответа). Та же картинка с корзинами, что в Уроке 19.1: 1988 запросов были около 0,25 мс или быстрее, а 10 — около 1,5 мс.
4. **Response time distribution** (распределение времени ответа). Перцентили: p50 = 0,137 мс, p99 = 0,193 мс, p99.9 = 1,58 мс.
5. **Details** (подробности). *DNS+dialup* — время открытия соединения (поиск имени плюс рукопожатие TCP), оно измеряется один раз на соединение: 10 соединений по 0,7 мс. Это объясняет 10 медленных запросов: первый запрос на каждом соединении ещё и ждал, пока соединение откроется.
6. **Status code distribution** (распределение кодов ответа). Все 2000 ответов — `200 OK`. Если вы видите здесь `500` или `429`, ваше число пропускной способности считает ошибки, а они часто очень быстрые. Быстрая ошибка — не успех.

> 💡 **Совет:** `oha` может работать и фиксированное время: `-z 10s` вместо `-n`. В конце запросы, которые ещё выполняются, отменяются и попадают в отчёт как `aborted due to deadline`; это нормально, и их число примерно равно числу соединений.

## 4. Ищем предел

Один нагрузочный тест говорит мало. На самом деле вам нужна **кривая**: как меняется задержка с ростом нагрузки. Запустите `/work` со всё большим числом соединений, по 5 секунд на каждое:

```bash
for c in 1 2 4 8 16 64 256; do
  echo "--- $c connections"
  oha -z 5s -c "$c" --no-tui 'http://127.0.0.1:3019/work?n=100' | grep -E 'Requests/sec|50.00%|99.00%'
done
```

Вывод, собранный в таблицу (один запуск; в полном выводе для каждого шага те же три строки):

```text
connections   req/s     p50        p99
     1         7 020    0.137 ms   0.209 ms
     2         9 001    0.216 ms   0.295 ms
     4        24 869    0.153 ms   0.248 ms
     8        34 491    0.228 ms   0.382 ms
    16        34 199    0.459 ms   0.888 ms
    64        35 505    1.798 ms   3.275 ms
   256        34 683    7.195 ms  15.774 ms
```

Читайте это как историю:

- **От 1 до 8 соединений:** пропускная способность быстро растёт, задержка остаётся меньше половины миллисекунды. У четырёх рабочих потоков ещё бывают свободные моменты. (Очень малые нагрузки неравномерны: здесь 2 соединения дали меньше прироста, чем ожидалось. Не делайте выводов по одной строке.)
- **От 8 соединений и выше:** пропускная способность останавливается на уровне около 35 000 req/s. 4 рабочих потока **насыщены**: каждому запросу нужно около 0,11 мс CPU, так что 4 потока могут сделать не больше 4 ÷ 0,11 мс ≈ 36 000 req/s.
- **После насыщения** новые соединения добавляют только ожидание. Закон Литтла это предсказывает: 64 в работе ÷ 35 505 req/s = 1,8 мс — ровно измеренный p50. С 256 соединениями p99 равен 16 мс: в 80 раз хуже, чем при малой нагрузке, *без* какого-либо выигрыша в пропускной способности.

Точка, где кривая изгибается, здесь около 8 соединений, — это **колено**. Здоровый сервис работает *ниже* своего колена, с запасом на пики трафика.

```text
p99 latency
   |                                          *   256
   |
   |                             *  64
   |                *  16
   |  *  *  *  * 8          <- knee
   +--------------------------------------------- connections (load)
```

> ⚡ **Производительность:** обычно сервис «достаточно быстр» задолго до насыщения. Сначала выберите цель по задержке (например, p99 ниже 1 мс), затем найдите наибольшую нагрузку, которая ей удовлетворяет. Эта нагрузка и есть ваша **ёмкость**, и она ниже максимальной пропускной способности.

## 5. Ожидание против блокировки

Теперь сравним `/wait` и `/blocking`. Оба занимают 20 мс. Отличается только то, как они ждут. По 5 секунд, с 10 и со 100 соединениями:

```bash
oha -z 5s -c 10 --no-tui http://127.0.0.1:3019/wait | grep -E 'Requests/sec|50.00%|99.00%'
oha -z 5s -c 100 --no-tui http://127.0.0.1:3019/wait | grep -E 'Requests/sec|50.00%|99.00%'
oha -z 5s -c 10 --no-tui http://127.0.0.1:3019/blocking | grep -E 'Requests/sec|50.00%|99.00%'
oha -z 5s -c 100 --no-tui http://127.0.0.1:3019/blocking | grep -E 'Requests/sec|50.00%|99.00%'
```

```text
  Requests/sec:	441.7495
  50.00% in 23.1151 ms
  99.00% in 23.8267 ms
  Requests/sec:	4395.1061
  50.00% in 22.8651 ms
  99.00% in 24.3705 ms
  Requests/sec:	153.8951
  50.00% in 67.2152 ms
  99.00% in 106.6218 ms
  Requests/sec:	176.0175
  50.00% in 0.6080 sec
  99.00% in 1.0819 sec
```

**Что происходит:**

1. `/wait`, 10 соединений: 442 req/s, p50 23 мс (20 мс сна плюс задержка таймера и планирования). Закон Литтла: 10 ÷ 0,023 с ≈ 435.
2. `/wait`, 100 соединений: в десять раз больше пропускной способности при *той же* задержке. Спящая задача не держит поток, поэтому 4 потока могут обслуживать тысячи ждущих запросов.
3. `/blocking`, 10 соединений: всего 154 req/s и p50 67 мс. Каждый запрос держит один из 4 потоков 20 мс, поэтому сервис никогда не сделает больше 4 ÷ 0,020 с = 200 req/s. Остальные запросы ждут в очереди.
4. `/blocking`, 100 соединений: всё так же меньше 200 req/s, а p50 теперь 0,6 **секунды**. Чистое ожидание в очереди.

Дальше хуже: заблокированный поток не может обслуживать *никакой* эндпоинт. Дайте нагрузку на `/blocking` в одном терминале и измерьте `/hello` из другого, пока она идёт:

```bash
oha -z 8s -c 100 --no-tui http://127.0.0.1:3019/blocking > /dev/null &
sleep 2
oha -z 3s -c 1 --no-tui http://127.0.0.1:3019/hello | grep -E 'Requests/sec|50.00%|99.00%'
```

```text
  Requests/sec:	2.3311
  50.00% in 395.6002 ms
  99.00% in 673.4340 ms
```

Обычно `/hello` отвечает за 0,14 мс. Под нагрузкой на `/blocking` он отвечал 400 мс, а пропускная способность одного соединения упала примерно с 7000 req/s до 2. Один неправильный `sleep` (или медленное чтение файла, тяжёлое вычисление, блокирующий драйвер базы данных) внутри асинхронного обработчика вредит всему сервису. Модульные тесты этого никогда не покажут; нагрузочный тест показывает сразу. Исправление — `tokio::task::spawn_blocking` (Упражнение 2) или асинхронная версия вызова. Урок 19.9 подробнее разбирает производительность асинхронного кода.

## 6. Открытая модель: фиксированная частота

Закрытая модель спрашивает «сколько он может?». Но настоящие пользователи не ждут друг друга: они приходят с какой-то частотой. `-q 300` заставляет `oha` отправлять 300 запросов в секунду. `/blocking` может меньше 200 в секунду, поэтому очередь обязана расти. Сравните отчёт без `--latency-correction` и с ним:

```bash
oha -z 10s -c 50 -q 300 --no-tui http://127.0.0.1:3019/blocking | grep -E 'Requests/sec|50.00%|90.00%|99.00%'
oha -z 10s -c 50 -q 300 --latency-correction --no-tui http://127.0.0.1:3019/blocking | grep -E 'Requests/sec|50.00%|90.00%|99.00%'
```

```text
  Requests/sec:	169.0926
  50.00% in 298.8903 ms
  90.00% in 426.0512 ms
  99.00% in 510.9163 ms
  Requests/sec:	172.3733
  50.00% in 2.2162 sec
  90.00% in 3.9832 sec
  99.00% in 4.3683 sec
```

**Что происходит:**

1. Оба запуска достигают лишь около 170 req/s, хотя планировалось 300: сервис насыщен.
2. Без поправки `oha` измеряет каждый запрос от момента, когда он был *реально* отправлен. Когда все 50 соединений заняты, многие запланированные запросы уходят с опозданием, и их ожидание до отправки не учитывается: p50 = 0,3 с. Это скоординированный пропуск (Урок 19.1).
3. `--latency-correction` измеряет от момента, когда каждый запрос был *запланирован*. Теперь p50 равен 2,2 с, а p99 — 4,4 с: очередь росла все 10 секунд, и именно это почувствовали бы пользователи, приходящие по 300 в секунду.

Используйте открытую модель с поправкой, когда вопрос звучит «какую задержку получают пользователи при *таком* трафике?». Ответ на вопрос «какова ёмкость?» — наибольшая частота, при которой исправленный p99 всё ещё укладывается в вашу цель (Упражнение 3).

> 🧪 **Тестирование:** нагрузочный тест — не тест правильности. Прежде чем нагружать сервис, имейте обычные тесты, доказывающие, что его ответы верны (Упражнение 1), и проверяйте *Success rate* и *Status code distribution* в каждом отчёте.

## Частые ошибки

1. **Нагружать отладочную сборку.** С `cargo run` (debug) тот же тест `/work` с 16 соединениями дал 6 895 req/s и p50 2,3 мс вместо 34 199 req/s и 0,46 мс. Всегда `cargo run --release`.
2. **Игнорировать ошибки.** Сервис, отвечающий `500 Internal Server Error` за 50 мкс, выглядит очень быстрым. Читайте долю успешных запросов и коды ответа раньше, чем скорость.
3. **Один запуск — одно число.** Результаты меняются от запуска к запуску и от всего остального, чем занят ваш Mac. Повторяйте каждый шаг, закрывайте тяжёлые программы и сохраняйте одинаковые условия при сравнении.
4. **Узкое место — сам генератор.** `oha` тоже нужен CPU. Если генератор и сервис делят ядра, вы, возможно, измеряете генератор. Оставляйте свободные ядра (здесь: 4 рабочих потока на 12-ядерном Mac), следите за обоими процессами в Activity Monitor, а для серьёзных чисел запускайте генератор на другой машине.
5. **Слишком коротко.** Тест в 1 секунду скрывает медленные эффекты: заполнение кэшей, рост памяти, исчерпание пулов соединений. Для чисел, которые вы хотите сохранить, используйте хотя бы 10–30 секунд, а для тестов на выносливость — намного дольше.
6. **Только закрытая модель.** Тест с закрытой моделью никогда не перегрузит сервис, поэтому никогда не покажет, насколько плохо бывает с очередью. Добавьте запуск с открытой моделью: `-q` и `--latency-correction`.

## Попробуйте сами

1. Запустите `/work?n=1000` (около 1 мс CPU на запрос) с 1, 4 и 16 соединениями. Где новая максимальная пропускная способность? (Ожидайте около 4 ÷ 1,1 мс, примерно 3600 req/s; один запуск дал 3767 req/s с 16 соединениями.)
2. Перезапустите сервис с `worker_threads = 8` и повторите перебор из раздела 4. Сдвинулось ли колено?
3. Запустите `oha` без `--no-tui` против `/wait` на 10 секунд и посмотрите на живой экран. Нажмите `q`, чтобы остановить раньше.

## Упражнения

### Упражнение 1 — Сначала тест, потом нагрузка (легко)

Добавьте в `src/main.rs` тесты на `oneshot` (Урок 16.3): `/work?n=0` отвечает `200` с телом `"0\n"`; `/work` без `n` отвечает `200` с `checksum(100)` и переводом строки; `/work?n=abc` отвечает `400 Bad Request`.

<details>
<summary>Подсказка</summary>

Напишите одну вспомогательную функцию `async fn get_text(uri: &str) -> (StatusCode, String)`, которая строит `Request::get(uri)`, вызывает `app().oneshot(request)` и собирает тело через `BodyExt::collect`.

</details>

<details>
<summary>Ответ</summary>

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use axum::body::Body;
    use axum::http::{Request, StatusCode};
    use http_body_util::BodyExt;
    use tower::ServiceExt;

    async fn get_text(uri: &str) -> (StatusCode, String) {
        let request = Request::get(uri).body(Body::empty()).unwrap();
        let response = app().oneshot(request).await.unwrap();
        let status = response.status();
        let bytes = response.into_body().collect().await.unwrap().to_bytes();
        (status, String::from_utf8(bytes.to_vec()).unwrap())
    }

    #[tokio::test]
    async fn work_returns_the_checksum() {
        assert_eq!(
            get_text("/work?n=0").await,
            (StatusCode::OK, "0\n".to_string())
        );
        let expected = format!("{}\n", checksum(100));
        assert_eq!(get_text("/work").await, (StatusCode::OK, expected));
    }

    #[tokio::test]
    async fn work_rejects_a_bad_number() {
        let (status, _) = get_text("/work?n=abc").await;
        assert_eq!(status, StatusCode::BAD_REQUEST);
    }
}
```

```text
running 2 tests
test tests::work_rejects_a_bad_number ... ok
test tests::work_returns_the_checksum ... ok

test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Почему это работает: при `n = 0` цикл не выполняется ни разу, и `x` остаётся 0. Экстрактор `Query` не может превратить `"abc"` в `u64` и отклоняет запрос с кодом `400` ещё до запуска обработчика.

</details>

### Упражнение 2 — Исправьте блокирующий обработчик (средне)

Измените `blocking` так, чтобы 20-миллисекундный `std::thread::sleep` выполнялся внутри `tokio::task::spawn_blocking`. Перезапустите сервис и выполните `oha -z 5s -c 100 --no-tui http://127.0.0.1:3019/blocking`. Что стало с пропускной способностью и p50?

<details>
<summary>Подсказка</summary>

`spawn_blocking` принимает замыкание и возвращает дескриптор, который вы ожидаете через `.await`. Результат — `Result` (ошибка, если замыкание запаниковало).

</details>

<details>
<summary>Ответ</summary>

```rust
/// Fixed: the blocking call runs on Tokio's separate pool for blocking work.
async fn blocking() -> &'static str {
    tokio::task::spawn_blocking(|| std::thread::sleep(Duration::from_millis(20)))
        .await
        .unwrap();
    "blocked\n"
}
```

```text
  Requests/sec:	4071.0477
  50.00% in 24.0089 ms
  99.00% in 31.3822 ms
```

Почему это работает: `spawn_blocking` переносит блокирующий вызов в отдельный пул потоков (по умолчанию до 512), и 4 рабочих потока остаются свободными. Пропускная способность выросла со 176 примерно до 4 000 req/s, а p50 упал с 0,6 с до 24 мс — близко к числам `/wait`. Но лишние потоки не бесплатны: для настоящего ожидания (сеть, база данных) асинхронный API всё равно лучше.

</details>

### Упражнение 3 — Найдите ёмкость (сложно)

Цель: p99 ниже 60 мс. С *неисправленным* обработчиком `/blocking` найдите наибольшую частоту (попробуйте `-q` 100, 150 и 200, по 10 секунд, 50 соединений, с `--latency-correction`), которая укладывается в цель. Объясните результат числами из раздела 5.

<details>
<summary>Подсказка</summary>

Теоретический предел — 4 потока ÷ 20 мс = 200 req/s. Около предела очереди растут без конца, так что ждите резкого скачка.

</details>

<details>
<summary>Ответ</summary>

```bash
for q in 100 150 200; do
  echo "--- $q per second"
  oha -z 10s -c 50 -q "$q" --latency-correction --no-tui http://127.0.0.1:3019/blocking | grep -E 'Requests/sec|50.00%|99.00%'
done
```

Один запуск:

```text
--- 100 per second
  Requests/sec:	100.1663
  50.00% in 28.3066 ms
  99.00% in 45.2070 ms
--- 150 per second
  Requests/sec:	150.1711
  50.00% in 29.3505 ms
  99.00% in 52.1046 ms
--- 200 per second
  Requests/sec:	164.1685
  50.00% in 1.0870 sec
  99.00% in 2.0776 sec
```

Почему это работает: при 100 и 150 req/s сервис успевает, p99 около 45–52 мс, так что ёмкость для этой цели — около 150 req/s. При 200 req/s запланированная частота находится на реальном пределе около 170 req/s (на практике выше него); очередь растёт весь запуск, и p99 прыгает до 2 секунд. Ёмкость всегда ниже максимальной пропускной способности.

</details>

## Вопросы для самопроверки

1. Чем отличаются `oha -c 50` и `oha -q 500`?

<details>
<summary>Ответ</summary>

`-c 50` — закрытая модель: 50 соединений, каждое отправляет следующий запрос только после предыдущего ответа. `-q 500` задаёт частоту открытой модели: 500 запросов в секунду планируются независимо от того, как быстро приходят ответы (отправляются они всё равно по соединениям из `-c`).

</details>

2. Что происходит с пропускной способностью и задержкой после колена, если добавлять соединения?

<details>
<summary>Ответ</summary>

Пропускная способность почти не меняется (сервис насыщен), а задержка растёт примерно пропорционально числу соединений, как говорит закон Литтла: задержка = в работе ÷ пропускная способность.

</details>

3. Почему `std::thread::sleep` в одном обработчике замедляет другой эндпоинт?

<details>
<summary>Ответ</summary>

Он блокирует рабочий поток рантайма. Пока все рабочие потоки заблокированы, ни одна задача не может выполняться, включая задачи других эндпоинтов, поэтому их запросы ждут в очереди.

</details>

4. Отчёт показывает 80 000 req/s, success rate 100%, а распределение кодов ответа — 79 000 ответов `[503]`. Быстрый ли сервис?

<details>
<summary>Ответ</summary>

Нет. *Success rate* означает лишь, что HTTP-ответ пришёл. Почти все ответы были ошибками (`503 Service Unavailable`), а их дёшево производить. Полезная пропускная способность — около 1000 req/s.

</details>

5. Почему нельзя проводить нагрузочный тест через `cargo run` без `--release`?

<details>
<summary>Ответ</summary>

Отладочная сборка не оптимизирована; в этом уроке она была примерно в 5 раз медленнее. Вы найдёте пределы отладочной сборки, а не той программы, которую развёртываете.

</details>

6. Что меняет `--latency-correction` и когда это важно?

<details>
<summary>Ответ</summary>

Каждый запрос измеряется от момента, на который его запланировала частота `-q`, а не от момента реальной отправки. Это важно, когда сервис не успевает: тогда запросы уходят с опозданием, и без поправки их время ожидания скрыто (скоординированный пропуск).

</details>

## Итоги

- **Нагрузочный тест** измеряет работающий сервис снаружи: пропускную способность, перцентили и ошибки под конкурентными запросами.
- `oha -n N -c C` (закрытая модель) показывает, что сервис может; `oha -q R --latency-correction` (открытая модель) показывает, что чувствуют пользователи при заданной частоте.
- Всегда сначала читайте долю успешных запросов и коды ответа, затем пропускную способность, затем перцентили.
- Перебирайте нагрузку и находите **колено**: после насыщения пропускная способность ровная, а задержка растёт, как предсказывает закон Литтла.
- **Ёмкость** — наибольшая нагрузка, которая укладывается в цель по задержке, и она ниже максимальной пропускной способности.
- Блокирующий вызов в асинхронном обработчике блокирует рабочий поток и замедляет *каждый* эндпоинт; используйте `spawn_blocking` или асинхронные API.
- Нагружайте только свои сервисы, в режиме release, достаточно долго и со свободными ядрами для генератора.
