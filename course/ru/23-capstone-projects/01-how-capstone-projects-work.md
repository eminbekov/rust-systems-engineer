# Урок 23.1 — Как устроены итоговые проекты

> **Этап 23 — Итоговые проекты** · Урок 1 из 10 · ⏱ около 135 минут

## Что вы узнаете

- Что такое итоговый проект и чем он отличается от проектов, которые вы строили до сих пор.
- Правила этого этапа: два итоговых проекта по 4–7 недель и как их выбрать.
- Жизненный цикл итогового проекта: проектный документ, вехи с проверками «Готово, когда», планка качества, результаты и презентация.
- Как подготовить репозиторий итогового проекта в виде рабочего пространства Cargo с *ходячим скелетом* и приёмочными тестами.
- Как планировать время, вести журнал работы и что делать, если вы застряли или не успеваете.

## Новые слова

| Слово | Значение |
|---|---|
| **итоговый проект** (capstone project) | Большой завершающий проект, который объединяет навыки из всего курса. На этом этапе вы строите два. |
| **портфолио** (portfolio) | Небольшая подборка ваших лучших открытых работ, которая показывает работодателям, что вы умеете. |
| **объём работ** (scope) | Список того, что проект будет делать. Всё, что вне объёма, не строится. |
| **расползание объёма** (scope creep) | Когда проект понемногу обрастает возможностями, которые никто не планировал, и поэтому никогда не заканчивается. |
| **не-цель** (non-goal) | То, что вы письменно решили *не* строить. Она защищает объём работ. |
| **ходячий скелет** (walking skeleton) | Самая маленькая версия всей системы, которая собирается, запускается и проверяется сквозным тестом. Она почти ничего не делает, но все части уже соединены. |
| **веха** (milestone) | Запланированная точка в проекте, где понятный кусок работы закончен и проверен. Здесь: M0, M1, M2, … |
| **приёмочный тест** (acceptance test) | Тест, который снаружи, как пользователь, проверяет одно обещание из контракта. Веха готова, когда её приёмочные тесты проходят. |
| **планка качества** (quality bar) | Минимальное качество, которого должен достичь каждый итоговый проект: тесты, линтеры, бенчмарки, документация, CI и наблюдаемость. |
| **критерии готовности** (definition of done) | Короткий список условий, каждое из которых должно выполняться, прежде чем работа считается законченной. |
| **тайм-бокс** (time box) | Заранее отведённое на задачу время. Когда оно кончилось, вы останавливаетесь и решаете, что делать дальше. |
| **запас времени** (buffer) | Время в плане, оставленное на сюрпризы. |
| **журнал работы** (work log) | Файл, куда вы после каждого занятия записываете, что сделали, сколько это заняло и что дальше. |
| **аннотированный тег** (annotated tag) | Метка Git с сообщением, прикреплённая к одному коммиту, например `m1`. Отмечает законченную веху. |
| **CI** (Continuous Integration, непрерывная интеграция) | Сервер, который автоматически запускает ваши проверки (форматирование, линтеры, тесты) при каждой отправке. Конвейеры CI вы строили в Уроке 09.12. |
| **MVP** (Minimum Viable Product, минимально жизнеспособный продукт) | Самая маленькая версия продукта, которая уже полезна настоящему пользователю. |
| **TCP** (Transmission Control Protocol, протокол управления передачей) | Интернет-протокол, который даёт двум программам надёжный упорядоченный поток байтов. |
| **HTTP** (HyperText Transfer Protocol, протокол передачи гипертекста) | Протокол запросов и ответов веба; HTTPS — это HTTP поверх зашифрованного соединения. |
| **ИИ** (искусственный интеллект, AI — Artificial Intelligence) | Здесь: ИИ-ассистент, программа, которая отвечает на вопросы на естественном языке. Используйте его как рецензента, а не как автора. |
| **CLI** (Command-Line Interface, интерфейс командной строки) | Способ пользоваться программой, набирая команды и параметры в терминале. |

## 1. Что такое итоговый проект

Все проекты до сих пор были *упражнениями*. Каждый тренировал несколько идей одного этапа, контракт давал урок, а вехи были небольшими. Итоговый проект — другое дело. Это **законченная система**, которую вы сами проектируете, строите, тестируете, измеряете и объясняете. Он использует сразу много этапов.

Представьте разницу между тем, чтобы приготовить одно блюдо по рецепту, и тем, чтобы неделю вести маленький ресторан. Навыки готовки те же, но теперь вы сами составляете меню, закупаете продукты, следите за чистотой кухни и обслуживаете настоящих гостей.

| | Проекты до сих пор | Итоговый проект |
|---|---|---|
| Кто пишет контракт | урок | урок даёт эталонный контракт; вы адаптируете его в своём проектном документе |
| Размер | от одного до трёх занятий | 4–7 недель примерно по 10 часов |
| Используемые этапы | в основном один | пять и больше |
| Тесты | модульные и сквозные | все уровни: модульные, на основе свойств, сквозные, на сбои, нагрузочные, фаззинг |
| Документы | короткий README | README, проектный документ, записи о решениях, результаты с числами |
| Результат | практика | проект для портфолио, который вы показываете и объясняете другим инженерам |

Итоговый проект показывает, что вы умеете делать всю работу системного инженера: понять задачу, выбрать архитектуру и защитить её, построить систему по шагам, доказать, что она работает, измерить её и понятно объяснить. Именно это хочет увидеть интервьюер на позицию системного инженера. Один глубокий, законченный и хорошо объяснённый проект говорит больше, чем много маленьких незаконченных.

## 2. Правила этого этапа

1. **Постройте два итоговых проекта.** Не один и не четыре. Два законченных проекта гораздо лучше четырёх наполовину сделанных.
2. **Выберите два разных вида.** Один проект должен углубиться в специализацию, которую вы выбрали на Этапе 22. Другой должен охватить другую область, чтобы портфолио показывало широту.
3. **Каждый итоговый проект занимает 4–7 недель** примерно при 10 часах в неделю (40–70 часов). Весь этап занимает 10–14 недель. Стройте проекты один за другим, а не одновременно.
4. **Сначала проект, потом код.** Сначала напишите проектный документ ([Урок 23.2](02-writing-a-design-document.md)). Код начинается, когда в документе есть цели, не-цели, архитектура, режимы отказов и план тестирования.
5. **Работайте веха за вехой.** Веха готова, только когда все её проверки «Готово, когда» проходят **в CI**, а работа закоммичена и отмечена тегом. Не начинайте следующую веху раньше.
6. **Достигните планки качества** (раздел 4). Она обязательна, и её не добавляют в последнюю неделю.
7. **Главная идея должна быть вашим кодом.** Берите крейты для «обвязки» (`tokio`, `serde`, `clap`, `hyper`, `tracing`). Сердце проекта должно быть вашим: в хранилище «ключ-значение» — репликация и хранение; в прокси — маршрутизация, балансировка и логика перезагрузки конфигурации. Если вы используете крейт для главной части (например, `openraft`), прямо скажите об этом в README и постройте сами что-то другое такой же глубины.
8. **Изучайте настоящие системы, но не копируйте их.** Разбираться, как etcd или Envoy решают задачу, — полезно. Копировать их код — нет. Если идея пришла из настоящей системы, назовите её в проектном документе.
9. **Завершите презентацией и проверкой.** Итоговый проект закончен после [Урока 23.9 — Как представить свою работу](09-presenting-your-work.md) и проверки в [Уроке 23.10](10-checkpoint-capstone-review.md).

Пять вариантов описаны в Уроках 23.3–23.7:

| Вариант | Что вы строите | Опирается в основном на | Подходит к направлению | Самое трудное |
|---|---|---|---|---|
| 1 — [Распределённое хранилище «ключ-значение»](03-capstone-distributed-key-value-store.md) | реплицированное хранилище, маленький etcd | Этапы 17, 18, 16 | базы данных | оставаться корректным, когда узлы падают |
| 2 — [Обратный HTTP-прокси](04-capstone-http-reverse-proxy.md) | прокси и балансировщик нагрузки, маленький Envoy | Этапы 15, 14, 19 | сети | хвостовая задержка, перезагрузка без потери запросов |
| 3 — [Брокер сообщений](05-capstone-message-broker.md) | постоянный журнал с группами потребителей, маленькая Kafka | Этапы 17, 15, 18 | базы данных или сети | смещения, репликация, надёжность записи |
| 4 — [Конвейер наблюдаемости](06-capstone-observability-pipeline.md) | агент, который собирает, преобразует и отправляет логи и метрики, маленький Vector | Этапы 16, 20, 21 | eBPF или cloud native | обратное давление, никаких тихих потерь данных |
| 5 — [Ваша собственная идея](07-capstone-your-own-idea.md) | ядро, движок запросов, оператор, … | ваше направление | любое | выбрать объём, который вы успеете закончить |

> 💡 **Совет:** перед выбором быстро прочитайте все пять уроков с вариантами. Затем выбирайте по двум вопросам: «Какой продолжает мою специализацию?» и «О каком мне больше всего хочется рассказать на собеседовании?»

## 3. Жизненный цикл итогового проекта

Каждый итоговый проект проходит одни и те же стадии. Уроки этого этапа идут в том же порядке:

```text
 week 0          weeks 1-5 (about)                 week 6          week 7
+---------+    +----+----+----+----+----+         +-----------+   +------------+
| choose  |    | M0 | M1 | M2 | M3 | M4 | ...      | harden:   |   | present:   |
| design  | -> |    |    |    |    |    |   ---->  | tests,    |-> | README,    | -> review
| doc     |    +----+----+----+----+----+         | benchmarks|   | results,   |   (23.10)
| (23.2)  |    each: build -> Done when -> tag     | (23.8)    |   | talk (23.9)|
+---------+                                        +-----------+   +------------+
```

1. **Выбор и проектирование** (около 10% времени). Выберите вариант, напишите `docs/design.md` и получите на него отзыв.
2. **Работа по вехам** (около 55%). M0 — ходячий скелет (раздел 5). Каждая следующая веха добавляет одну возможность и заканчивается приёмочными тестами.
3. **Укрепление** (около 15%). Закройте пробелы в тестах, запустите фаззеры и тесты на сбои, проведите бенчмарки и профилирование ([Урок 23.8](08-testing-benchmarking-and-hardening-capstones.md)). Часть укрепления идёт в каждой вехе; эта стадия его завершает.
4. **Презентация** (около 10%). Напишите README и `docs/results.md`, запишите демонстрацию, подготовьте короткий доклад ([Урок 23.9](09-presenting-your-work.md)).
5. **Запас** (около 10%). Что-нибудь всегда занимает больше времени, чем планировалось. Запас — для этого, а не для новых возможностей.

## 4. Планка качества

Каждый итоговый проект должен достичь этой планки, прежде чем вы назовёте его готовым. Урок 23.8 показывает, как выполнить каждый пункт; здесь — список, чтобы вы планировали его с самого начала.

| Область | Минимум |
|---|---|
| Гигиена сборки | `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` и `cargo test` проходят в CI при каждой отправке |
| Тесты | модульные тесты ядра, хотя бы один тест на основе свойств или на основе модели, сквозные тесты для каждой вехи, хотя бы один тест на сбой (падение, тайм-аут или потерянное соединение) |
| Фаззинг | одна фаззинг-цель для каждого парсера внешнего ввода (сетевые кадры, файлы конфигурации, запросы) |
| Производительность | повторяемый бенчмарк с записанным оборудованием и нагрузкой и числа задержки p50/p99 (медиана и 99-й перцентиль, Урок 19.1) или пропускной способности в `docs/results.md` |
| Наблюдаемость | структурированные логи через `tracing`; для сервисов ещё метрики и эндпоинт проверки работоспособности |
| Устойчивость | тайм-ауты на каждом сетевом вызове, лимиты на каждой очереди и буфере, корректное завершение (graceful shutdown) |
| Безопасность | никаких `unwrap` на внешнем вводе, `cargo deny check` или `cargo audit` в CI, у каждого блока `unsafe` есть комментарий `// SAFETY:` |
| Документация | `README.md`, `docs/design.md`, записи о решениях в `docs/adr/`, `docs/results.md` |

**Критерии готовности** всего итогового проекта короткие: проверки «Готово, когда» каждой вехи проходят в CI, планка качества достигнута, документы написаны, и вы представили проект.

> 📏 **Соглашение:** впишите планку качества в README как чек-лист и отмечайте пункты, только когда CI их подтверждает. Утверждение без теста или числа — это пожелание.

## 5. Репозиторий и ходячий скелет

Каждый итоговый проект живёт в своей папке `code/p23-<name>`, например `code/p23-kv` или `code/p23-proxy`. В отличие от прежних проектов, у каждого итогового проекта **свой репозиторий Git**, потому что в Уроке 23.9 вы опубликуете его отдельно. Примеры этого урока используют учебный скелет `code/p23-skeleton`, который можно скопировать для обоих проектов.

Структура следует гексагональной идее из [Урока 08.14](../08-software-design/14-layers-and-hexagonal-architecture.md): логика — в крейте ядра без сети и файлов, вокруг него — тонкие бинарные крейты.

```text
code/p23-skeleton/
├── Cargo.toml            ← рабочее пространство (без [package])
├── README.md             ← пишется в Уроке 23.9, начните сейчас
├── docs/
│   ├── design.md         ← Урок 23.2
│   ├── adr/              ← записи о решениях
│   ├── log.md            ← ваш журнал работы
│   └── results.md        ← бенчмарки, Урок 23.8
└── crates/
    ├── skel-core/        ← только логика: легко покрыть модульными тестами
    └── skel/             ← бинарник: аргументы, сеть, файлы
        └── tests/acceptance.rs
```

**Ходячий скелет** — это веха M0 любого итогового проекта. Он почти ничего не делает, но весь путь уже существует: рабочее пространство, крейт ядра, бинарник, который его использует, один приёмочный тест, запускающий настоящий бинарник, и CI. Следующие вехи наращивают «мясо» на кости, которые уже соединены. Создайте его:

```bash
cd ~/projects/rust
mkdir -p code/p23-skeleton/crates
cd code/p23-skeleton
cargo new --lib crates/skel-core
cargo new crates/skel
mkdir -p crates/skel/tests docs
```

Корневой `Cargo.toml` (создайте его):

```toml
[workspace]
resolver = "3"
members = ["crates/*"]

[workspace.package]
version = "0.1.0"
edition = "2024"

[workspace.dependencies]
skel-core = { path = "crates/skel-core" }
```

`crates/skel-core/Cargo.toml` и `crates/skel/Cargo.toml` (замените сгенерированные):

```toml
[package]
name = "skel-core"
version.workspace = true
edition.workspace = true

[dependencies]
```

```toml
[package]
name = "skel"
version.workspace = true
edition.workspace = true

[dependencies]
skel-core.workspace = true
```

`crates/skel-core/src/lib.rs`:

```rust
//! The core of the capstone: logic only, no network and no files.

/// The name and version that `skel --version` prints.
pub fn version_line() -> String {
    format!("skel {}", env!("CARGO_PKG_VERSION"))
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn version_line_starts_with_the_name() {
        assert!(version_line().starts_with("skel "));
    }
}
```

`crates/skel/src/main.rs`:

```rust
use std::process::ExitCode;

fn main() -> ExitCode {
    let args: Vec<String> = std::env::args().skip(1).collect();
    match args.first().map(String::as_str) {
        Some("--version") => {
            println!("{}", skel_core::version_line());
            ExitCode::SUCCESS
        }
        _ => {
            eprintln!("usage: skel --version");
            ExitCode::from(2)
        }
    }
}
```

**Что происходит:**

1. В рабочем пространстве два участника. `skel-core` — библиотека; `skel` — бинарник, который зависит от неё через `skel-core.workspace = true`.
2. `env!("CARGO_PKG_VERSION")` Cargo подставляет при компиляции из версии в `Cargo.toml`, поэтому бинарник всегда печатает настоящую версию.
3. `main` возвращает `ExitCode`: `SUCCESS` (0) для `--version` и 2 для всего остального. Код 2 — обычный код для «неправильного использования».
4. Сообщение об использовании идёт в стандартный поток ошибок через `eprintln!`, чтобы скрипт, читающий стандартный вывод, его не увидел.

## 6. «Готово, когда» в виде тестов

Каждая веха в Уроках 23.3–23.7 заканчивается проверками **«Готово, когда:»**. Превращайте каждую проверку в приёмочный тест **до** начала вехи. Сначала тест падает (красный); веха готова, когда он проходит (зелёный). Это разработка через тестирование из [Урока 09.6](../09-testing-debugging-benchmarking/06-tdd-in-practice.md), применённая к целой вехе.

`crates/skel/tests/acceptance.rs`:

```rust
//! Acceptance tests: one test per "Done when" line of the milestones.
use std::process::Command;

/// Runs the `skel` binary that Cargo built for this test.
fn skel(args: &[&str]) -> (i32, String) {
    let out = Command::new(env!("CARGO_BIN_EXE_skel"))
        .args(args)
        .output()
        .expect("the skel binary should start");
    let code = out.status.code().unwrap_or(-1);
    (code, String::from_utf8_lossy(&out.stdout).into_owned())
}

#[test]
fn m0_prints_its_version() {
    let (code, stdout) = skel(&["--version"]);
    assert_eq!(code, 0);
    assert_eq!(stdout, "skel 0.1.0\n");
}

#[test]
fn m0_unknown_arguments_exit_with_code_2() {
    let (code, _) = skel(&["--frobnicate"]);
    assert_eq!(code, 2);
}

#[test]
#[ignore = "M1 is not started yet"]
fn m1_a_value_survives_a_restart() {
    todo!("write this test at the start of M1");
}
```

**Что происходит:**

1. `env!("CARGO_BIN_EXE_skel")` — путь к бинарнику `skel`. Cargo собирает бинарники пакета до его интеграционных тестов и передаёт каждому тесту эту переменную, поэтому тест запускает настоящую программу.
2. Вспомогательная функция `skel` запускает программу с аргументами и возвращает код возврата и стандартный вывод.
3. Имена тестов начинаются с вехи (`m0_`, `m1_`). Тогда список тестов читается как отчёт о прогрессе.
4. `#[ignore = "…"]` оставляет в файле тест следующей вехи, но не запускает его. Причина печатается в выводе тестов.

Запустите всё из `code/p23-skeleton`:

```bash

```


> 🧪 **Тестирование:** добавьте приёмочные тесты в CI начиная с M0, с конвейером из [Урока 09.12](../09-testing-debugging-benchmarking/12-continuous-integration.md). Веха считается готовой, только когда CI зелёный, а не когда всё работает на вашем ноутбуке.

**Один шаг Git: репозиторий на каждый итоговый проект и тег на каждую веху.** Папка курса уже является репозиторием Git. Репозиторий внутри другого называется *встроенным* (embedded), и внешний репозиторий должен его игнорировать. Сначала скажите репозиторию курса игнорировать все папки итоговых проектов, затем создайте собственный репозиторий проекта и отметьте M0 тегом:

```bash
cd ~/projects/rust
echo 'code/p23-*/' >> .gitignore
git add .gitignore && git commit -m "Ignore capstone repositories (they have their own Git)"
cd code/p23-skeleton
git init
printf '/target\n' > .gitignore
git add .
git commit -m "M0: walking skeleton"
git tag -a m0 -m "M0 done: the walking skeleton builds and its tests pass"
git log --oneline --decorate
```

```text

```

`git tag -a` создаёт аннотированный тег с сообщением. В конце каждой вехи вы создаёте следующий (`m1`, `m2`, …). Потом любой может получить ровно то состояние, которое было у каждой вехи, командой `git switch --detach m2`.

## 7. Планирование времени и движение по плану

План превращает «4–7 недель» в числа, которые можно проверять каждую неделю. Для итогового проекта на 60 часов (6 недель × 10 часов):

| Часть | Доля | Часы |
|---|---|---|
| Выбор и проектирование | 10% | 6 |
| Вехи M0–M5 | 55% | 33 |
| Укрепление | 15% | 9 |
| Презентация | 10% | 6 |
| Запас | 10% | 6 |
| **Всего** | 100% | **60** |

Дайте каждой вехе тайм-бокс, например «M2: 7 часов». Ведите **журнал работы** в `docs/log.md` и после каждого занятия пишите три строки:

```markdown
## 2026-12-03 (2 h)
- Done: M2 leader election works with three nodes on localhost.
- Blocked: the election test is flaky, about 1 in 20 runs fails.
- Next: make the election timeout come from a seeded random generator.
```

Журнал помогает трижды: вы рано замечаете, что веха затягивается; вы помните, почему приняли решение; а в Уроке 23.9 он даёт историю для статьи в блоге (самая трудная ошибка обычно записана в журнале).

**Когда веха заняла вдвое больше своего тайм-бокса**, остановитесь и выберите одно из этого, в таком порядке:

1. Уменьшите веху. Перенесите менее важную часть в дополнительные цели.
2. Используйте часть запаса.
3. Перенесите более позднюю необязательную веху в дополнительные цели.

Никогда не снижайте планку качества ради времени. Проект поменьше, но с тестами и числами — хороший итоговый проект; проект побольше без них — нет.

**Когда вы застряли** (в итоговом проекте нет готовых ответов, которые можно открыть):

1. Перечитайте контракт и свой проектный документ. Часто проблема в нечётком требовании.
2. Уменьшите проблему: напишите самый маленький падающий тест, который её показывает.
3. Перечитайте урок, где объяснялась идея (каждый урок с вариантом перечисляет их).
4. Посмотрите, как задачу решает настоящая система (каждый урок с вариантом перечисляет системы для изучения).
5. Спросите: на форуме, в чате сообщества, у опытного инженера или у ИИ-ассистента в роли рецензента. Просите подсказку, а не код.

> ⚠️ **Частая ошибка:** начать второй итоговый проект, пока первый не закончен, «чтобы было интереснее». Два наполовину сделанных проекта показывают меньше, чем один законченный. Закончите, поставьте тег, представьте и только потом начинайте следующий.

## Частые ошибки

**1. Добавить репозиторий итогового проекта в репозиторий курса.** Если вы забыли строку игнорирования и выполнили `git add code` в `~/projects/rust`, Git предупреждает:

```text
warning: adding embedded git repository: code/p23-demo
hint: You've added another git repository inside your current repository.
hint: Clones of the outer repository will not contain the contents of
hint: the embedded repository and will not know how to obtain it.
```

Тогда внешний репозиторий хранит только указатель, а не ваши файлы. Исправление: `git rm --cached code/p23-demo`, добавьте `code/p23-*/` в `.gitignore` и закоммитьте.

**2. Писать код до проектирования.** Две недели кода, а потом выясняется, что формат данных не поддерживает репликацию. Несколько часов проектирования (Урок 23.2) находят такие проблемы, пока их ещё дёшево исправить.

**3. Гигантская первая веха.** «M1: всё хранилище с репликацией». Она никогда не кончается, и вы никогда не видите зелёного теста. Исправление: M1 должна быть такой, чтобы её можно было закончить за одну-две недели вечеров, а ходячий скелет M0 — за один вечер.

**4. Писать приёмочные тесты в конце.** Тогда они проверяют то, что вы построили, а не то, что обещали. Исправление: пишите тесты вехи заранее — как заглушки с `#[ignore]` в начале проекта и как настоящие тесты в начале вехи.

**5. «Позолота»** (gold-plating). Неделями полировать M1 (красивый CLI, цвета, много параметров), пока трудная часть ждёт. Исправление: тайм-бокс. Когда он кончился, двигайтесь дальше.

**6. Скрыть зависимость.** Использовать крейт для главной идеи и не сказать об этом. Рецензенты это замечают. Исправление: правило 7 из раздела 2 — назовите его в README и постройте другое, такой же глубины.

### Упражнение 2 — Напишите тест: справка идёт в стандартный поток ошибок (средне)

Добавьте в `crates/skel/tests/acceptance.rs` приёмочный тест `m0_no_arguments_print_usage_to_stderr`. Он запускает `skel` без аргументов и проверяет три вещи: код возврата равен 2, в стандартный вывод ничего не напечатано, а стандартный поток ошибок содержит `usage: skel`.

<details>
<summary>Подсказка</summary>

Вспомогательная функция `skel` возвращает только стандартный вывод. Вызовите `Command::new(env!("CARGO_BIN_EXE_skel")).output()` напрямую: у результата есть поля `status`, `stdout` и `stderr` (оба `Vec<u8>`).

</details>

<details>
<summary>Ответ</summary>

```rust
#[test]
fn m0_no_arguments_print_usage_to_stderr() {
    let out = Command::new(env!("CARGO_BIN_EXE_skel"))
        .output()
        .expect("the skel binary should start");
    assert_eq!(out.status.code(), Some(2));
    assert!(out.stdout.is_empty(), "nothing should go to stdout");
    let stderr = String::from_utf8_lossy(&out.stderr);
    assert!(stderr.contains("usage: skel"), "stderr was: {stderr}");
}
```

Почему это работает: `status.code()` равен `Some(2)`, потому что `main` вернула `ExitCode::from(2)`. Текст справки напечатан через `eprintln!`, поэтому он в `stderr`, а `stdout` пуст. Сообщения после условий делают падение легко читаемым.

</details>

### Упражнение 3 — Бюджет времени (средне)

Вы можете работать 8 часов в неделю и хотите закончить первый итоговый проект за 6 недель. Разделите часы по долям из раздела 7 (округлите до целых часов). Затем: у вашей M1 был тайм-бокс 5 часов, а заняла она 10. Что вы делаете?

<details>
<summary>Подсказка</summary>

6 × 8 = 48 часов. Используйте 10%, 55%, 15%, 10%, 10%. Для второго вопроса посмотрите на упорядоченный список «Когда веха заняла вдвое больше своего тайм-бокса».

</details>

<details>
<summary>Ответ</summary>

48 часов: проектирование 5, вехи 26, укрепление 7, презентация 5, запас 5 (5 + 26 + 7 + 5 + 5 = 48).

M1 заняла на 5 часов больше. Сначала проверьте, можно ли уменьшить M1 (перенести часть в дополнительные цели). Если 5 часов уже потрачены, возьмите их из запаса, который теперь равен 0, и сразу решите, какая необязательная веха станет дополнительной целью, если ещё что-то задержится. Не берите время у укрепления или презентации.

</details>

### Упражнение 4 — Флаг `--help`, сначала тест (сложно)

Добавьте `skel --help`: он печатает строку справки в **стандартный вывод** и завершается с кодом 0. Работайте «тест вперёд»: напишите приёмочный тест `m0_help_prints_usage_and_succeeds`, посмотрите, как он падает, затем измените `main.rs`. Держите текст справки в одной константе, чтобы оба места печатали одну и ту же строку.

<details>
<summary>Подсказка</summary>

Падающий тест показывает `left: 2, right: 0`: сейчас `--help` попадает в ветку `_`. Добавьте ветку `Some("--help")` перед `_` и `const USAGE: &str = "…";` в начале `main.rs`.

</details>

<details>
<summary>Ответ</summary>

Тест (в `acceptance.rs`):

```rust
#[test]
fn m0_help_prints_usage_and_succeeds() {
    let (code, stdout) = skel(&["--help"]);
    assert_eq!(code, 0);
    assert!(stdout.starts_with("usage: skel"), "stdout was: {stdout}");
}
```

До изменения он падает так:

```text
thread 'm0_help_prints_usage_and_succeeds' (6457531) panicked at crates/skel/tests/acceptance.rs:47:5:
assertion `left == right` failed
  left: 2
 right: 0
```

Новый `crates/skel/src/main.rs`:

```rust
use std::process::ExitCode;

const USAGE: &str = "usage: skel --version | --help";

fn main() -> ExitCode {
    let args: Vec<String> = std::env::args().skip(1).collect();
    match args.first().map(String::as_str) {
        Some("--version") => {
            println!("{}", skel_core::version_line());
            ExitCode::SUCCESS
        }
        Some("--help") => {
            println!("{USAGE}");
            ExitCode::SUCCESS
        }
        _ => {
            eprintln!("{USAGE}");
            ExitCode::from(2)
        }
    }
}
```

Почему это работает: просьба о справке — не ошибка, поэтому справка идёт в стандартный вывод с кодом 0; неправильное использование — в стандартный поток ошибок с кодом 2. Теперь проходят все четыре приёмочных теста (`4 passed; 0 failed; 1 ignored`), включая тест из Упражнения 2, потому что справка по-прежнему начинается с `usage: skel`.

</details>

## Вопросы для самопроверки

1. Чем итоговый проект отличается от прежних проектов курса?

<details>
<summary>Ответ</summary>

Это законченная система, которую вы проектируете сами; она использует сразу много этапов, занимает недели, а не занятия, и должна достичь полной планки качества (тесты всех уровней, бенчмарки, документы, CI). Это проект для портфолио, который вы представляете другим.

</details>

2. Почему этот этап требует ровно два итоговых проекта разных видов?

<details>
<summary>Ответ</summary>

Два законченных проекта ценнее многих незаконченных. Один углубляется в вашу специализацию, другой показывает широту в другой области.

</details>

3. Что такое ходячий скелет и почему это веха M0?

<details>
<summary>Ответ</summary>

Самая маленькая версия всей системы, которая собирается, запускается и проверяется сквозным тестом, с CI. Он сначала соединяет все части, поэтому следующие вехи только добавляют поведение к пути, который уже работает и уже протестирован.

</details>

4. Когда веха готова?

<details>
<summary>Ответ</summary>

Когда все её проверки «Готово, когда» проходят как приёмочные тесты в CI, а работа закоммичена и отмечена тегом (например, `m2`). «Работает на моём ноутбуке» — недостаточно.

</details>

5. Что даёт интеграционному тесту `env!("CARGO_BIN_EXE_skel")`?

<details>
<summary>Ответ</summary>

Путь к бинарнику `skel`, который Cargo собрал для запуска тестов. Тест может запустить настоящую программу через `std::process::Command`.

</details>

6. Веха заняла вдвое больше своего тайм-бокса. Какая реакция неправильная: уменьшить веху, использовать запас или пропустить тесты ради экономии времени?

<details>
<summary>Ответ</summary>

Пропустить тесты. Планку качества никогда не снижают; вместо этого сокращают объём (меньшая веха, запас, необязательная веха — в дополнительные цели).

</details>

7. Почему у каждого итогового проекта свой репозиторий Git и что должен сделать репозиторий курса?

<details>
<summary>Ответ</summary>

Потому что каждый итоговый проект вы публикуете отдельно. Репозиторий курса должен игнорировать эти папки (`code/p23-*/` в `.gitignore`); иначе `git add` создаёт встроенный репозиторий, который хранит только указатель, а не файлы.

</details>

## Итоги

- Итоговый проект — законченная система, которую вы проектируете, строите по вехам, тестируете, измеряете, документируете и представляете. Вы строите **два** разных вида, по 4–7 недель каждый.
- Сначала проектирование (Урок 23.2). Главная идея должна быть вашим кодом; крейты подходят для обвязки, а каждая заимствованная идея называется.
- Каждый итоговый проект начинается с **ходячего скелета** (M0): рабочее пространство, крейт ядра, бинарник, приёмочный тест, запускающий настоящий бинарник, и CI.
- Каждое «Готово, когда» становится приёмочным тестом до начала вехи; `#[ignore = "…"]` держит будущие тесты на виду; веха заканчивается зелёным CI и тегом Git.
- **Планка качества** (тесты всех уровней, фаззинг, бенчмарки, наблюдаемость, устойчивость, безопасность, документы) планируется с самого начала и никогда не снижается.
- Планируйте с тайм-боксами и запасом, ведите журнал работы, а когда не успеваете, сокращайте объём, а не качество.
