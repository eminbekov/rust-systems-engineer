## Новые слова

| Слово | Значение |
|---|---|
| **лог** (log) | Запись о том, что делала программа, сделанная во время работы, чтобы её можно было прочитать позже. |
| **уровень логирования** (log level) | Насколько важно сообщение: `ERROR`, `WARN`, `INFO`, `DEBUG` или `TRACE`. Вы выбираете, какие уровни показывать. |
| **событие** (event) | Одно происшествие в один момент: «заказ получен». В `tracing` `info!(...)` создаёт событие. |
| **поле** (field) | Именованное значение, прикреплённое к событию или спану, например `total=2500`. Поля делают логи пригодными для поиска. |
| **спан** (span) | Период времени с началом и концом, у которого есть имя и поля, например «обработка заказа 2». Каждое событие внутри него печатается вместе со спаном. |
| **подписчик** (subscriber) | Часть программы, которая получает события и спаны и решает, что с ними делать: напечатать, записать JSON, посчитать. |
| **`tracing`** | Крейт с макросами (`info!`, `#[instrument]`, …), которые вызывает ваш код. Сам он ничего не печатает. |
| **`tracing-subscriber`** | Крейт с готовыми подписчиками, например тем, который печатает строки в терминал. |
| **переменная окружения** (environment variable) | Именованная настройка, которую командная оболочка передаёт программе, например `RUST_LOG=debug`. |
| **структурированное логирование** (structured logging) | Логирование, где каждое событие — это данные (поля), а не только текст, так что инструмент может их фильтровать и считать. |
| **JSON** (JavaScript Object Notation, запись объектов JavaScript) | Текстовый формат данных из пар `{"имя": значение}`, который умеют читать многие инструменты. |

## 1. Почему не просто `println!`?

`println!` годится для десятиминутной ошибки. Для программы, работающей месяцами, у него есть проблемы:

1. **Его нельзя выключить.** Каждый отладочный `println!` остаётся для всех и всегда, а вывод вашей настоящей программы смешивается с ним.
2. **Нет важности.** Строка «диск заполнен» и строка «x = 3» выглядят одинаково.
3. **Нет контекста.** Если сервер обрабатывает 100 заказов одновременно, строка «списано» не говорит, *какой* это заказ.
4. **Только текст.** Инструмент не может спросить «покажи все строки с `order_id=2`», если вы не отформатировали строку очень аккуратно.

Библиотека **логирования** решает все четыре проблемы. Главная идея крейта `tracing`: код только *описывает*, что происходит, с помощью макросов. *Подписчик*, выбранный один раз в `main`, решает, как это показать.

```text
 your code and libraries                 chosen once, in main
 ┌─────────────────────────┐   events   ┌──────────────────────────┐
 │ info!(total = 2500, ..) │ ─────────▶ │ subscriber               │ ──▶ terminal lines
 │ #[instrument] fn charge │   spans    │  + filter (RUST_LOG)     │ ──▶ JSON for a tool
 └─────────────────────────┘            └──────────────────────────┘
```

Пять уровней, от самого важного к наименее важному:

| Уровень | Для чего | Пример |
|---|---|---|
| `ERROR` | Что-то не удалось, и работу выполнить не получилось | «не удалось открыть базу данных» |
| `WARN` | Что-то не так, но программа продолжает | «диск заполнен на 91%» |
| `INFO` | Обычные важные события, история программы | «сервер запущен» |
| `DEBUG` | Подробности для разработчиков | «сумма вычислена» |
| `TRACE` | Очень подробные шаги, их, вероятно, слишком много | «вход в цикл, i = 3» |

## 2. Ваши первые события

Создайте проект и добавьте два крейта. Фича `env-filter` крейта `tracing-subscriber` даёт фильтр `RUST_LOG`, который использует раздел 5:

```bash
cd ~/projects/rust/code
cargo new p09-tracing
cd p09-tracing
cargo add tracing@0.1
cargo add tracing-subscriber@0.3 --features env-filter
```

Теперь `Cargo.toml` содержит:

```toml
[dependencies]
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter"] }
```

Поместите в `src/main.rs`:

```rust
use tracing::{debug, error, info, trace, warn};

fn main() {
    tracing_subscriber::fmt().without_time().with_ansi(false).init();

    trace!("very detailed step");
    debug!("a value for developers");
    info!("server started");
    warn!("disk is 91% full");
    error!("could not open the database");
}
```

```bash
cargo run
```

```text
 INFO p09_tracing: server started
 WARN p09_tracing: disk is 91% full
ERROR p09_tracing: could not open the database
```

**Что происходит:**

1. `tracing_subscriber::fmt()` создаёт строитель подписчика «печатать строки», а `.init()` устанавливает его подписчиком всей программы. Это нужно сделать один раз, в начале `main`.
2. `.without_time()` убирает метку времени, а `.with_ansi(false)` убирает цвета, чтобы вывод в уроке был коротким и простым. В настоящем терминале нужны оба: и время, и цвета.
3. Макросы `trace!`, `debug!`, `info!`, `warn!` и `error!` создают события с указанным уровнем.
4. Показаны только `INFO` и выше. Строитель начинает с максимального уровня `INFO`, поэтому `trace!` и `debug!` ничего не делают (они стоят почти ничего, см. раздел 8). `p09_tracing` — это **цель** (target): модуль, написавший событие.

Чтобы увидеть всё, можно поднять уровень в коде через `.with_max_level(tracing::Level::TRACE)`. Лучше, как покажет раздел 5, менять его снаружи без перекомпиляции.

> ⚡ **Производительность:** событие с выключенным уровнем пропускается очень рано: значения в `info!(total = expensive(), ...)` **не вычисляются**, когда `INFO` выключен. Поэтому строки `debug!` и `trace!` можно оставлять в коде навсегда, в отличие от `println!`.

## 3. Поля: данные вместо текста

Не собирайте предложение через `format!`. Передавайте значения как **поля** после сообщения или перед ним:

```rust
use tracing::info;

fn main() {
    tracing_subscriber::fmt().with_ansi(false).without_time().init();
    let name = "Ada";
    let list = vec![1, 2];
    info!(name, "plain value");
    info!(name = %name, "display");
    info!(name = ?name, list = ?list, "debug");
}
```

```text
 INFO p09_tracing: plain value name="Ada"
 INFO p09_tracing: display name=Ada
 INFO p09_tracing: debug name="Ada" list=[1, 2]
```

**Что происходит:**

1. `info!(name, "...")` записывает переменную `name` как поле с тем же именем. Обычный `&str` записывается как текст и показывается в кавычках.
2. `name = %name` записывает значение в форме **`Display`** (форма `{}` в `println!`, Урок 05.2): без кавычек.
3. `name = ?name` записывает значение в форме **`Debug`** (форма `{:?}`). У типов вроде `Vec` или вашей `struct` нет `Display`, поэтому для них используют `?`.
4. Сообщение — последний аргумент, обычная строка. Делайте его **постоянным** предложением: «order received». Изменяющиеся части идут в поля. Тогда инструмент логов может посчитать все события с сообщением «order received».

> 📏 **Соглашение:** сообщение — что произошло, строчными буквами, без значений. Поля — значения: `info!(order_id, total_cents, "order accepted")`. Используйте одни и те же имена полей везде (`order_id`, а не `id` в одном месте и `orderId` в другом).

## 4. Спаны и `#[instrument]`

Событие говорит «что-то произошло». **Спан** говорит «на время этой работы помни эти поля». Все события внутри спана несут их с собой.

Самый простой способ создать спан — атрибут `#[instrument]` на функции: он создаёт спан с именем функции, живущий на время вызова, и записывает аргументы как поля. Вот программа, которой мы будем пользоваться до конца урока. Замените `src/main.rs`:

```rust
use tracing::{debug, info, instrument, warn};
use tracing_subscriber::EnvFilter;

#[derive(Debug)]
struct Order {
    id: u32,
    customer: String,
    prices_cents: Vec<u64>,
}

#[instrument(skip(order), fields(order_id = order.id), err)]
fn charge(order: &Order, limit_cents: u64) -> Result<u64, String> {
    let total: u64 = order.prices_cents.iter().sum();
    debug!(total, items = order.prices_cents.len(), "computed total");
    if total > limit_cents {
        warn!(total, limit_cents, "total is over the limit");
        return Err(format!("order {} is over the limit", order.id));
    }
    info!(total, "charged");
    Ok(total)
}

#[instrument(skip_all, fields(order_id = order.id))]
fn process(order: Order) {
    info!(customer = %order.customer, "order received");
    match charge(&order, 5_000) {
        Ok(total) => info!(total, "order done"),
        Err(_) => info!("order rejected"),
    }
}

fn main() {
    tracing_subscriber::fmt()
        .with_env_filter(EnvFilter::from_default_env())
        .with_ansi(false)
        .without_time()
        .init();

    process(Order {
        id: 1,
        customer: "Ada".to_string(),
        prices_cents: vec![1_000, 1_500],
    });
    process(Order {
        id: 2,
        customer: "Bob".to_string(),
        prices_cents: vec![4_000, 2_500],
    });
}
```

**Что происходит:**

1. `#[instrument]` оборачивает функцию: при вызове входит в спан с именем функции, а при возврате выходит из него. Каждое событие внутри функции и внутри вызываемых ею функций печатается с именами и полями окружающих спанов.
2. По умолчанию `#[instrument]` записывает **каждый аргумент** через `Debug`. `skip(order)` исключает `order`, потому что весь `Order` большой (и может содержать закрытые данные, см. раздел 8). `skip_all` исключает все аргументы. `fields(order_id = order.id)` добавляет одно выбранное нами поле.
3. `err` означает: если функция возвращает `Err`, записать ошибку как событие `ERROR` автоматически. Работает для функций, возвращающих `Result`, у ошибки которых есть `Display`.
4. `.with_env_filter(EnvFilter::from_default_env())` делает уровень зависящим от переменной `RUST_LOG` (следующий раздел). Без `RUST_LOG` показывается только `ERROR`.

Запустите с `RUST_LOG=info`. Запись `ИМЯ=значение команда` задаёт переменную только для этой одной команды:

```bash
RUST_LOG=info cargo run
```

```text
 INFO process{order_id=1}: p09_tracing: order received customer=Ada
 INFO process{order_id=1}:charge{limit_cents=5000 order_id=1}: p09_tracing: charged total=2500
 INFO process{order_id=1}: p09_tracing: order done total=2500
 INFO process{order_id=2}: p09_tracing: order received customer=Bob
 WARN process{order_id=2}:charge{limit_cents=5000 order_id=2}: p09_tracing: total is over the limit total=6500 limit_cents=5000
ERROR process{order_id=2}:charge{limit_cents=5000 order_id=2}: p09_tracing: error=order 2 is over the limit
 INFO process{order_id=2}: p09_tracing: order rejected
```

**Как это читать:**

1. Текст до второго двоеточия — это **путь спанов**: `process{order_id=2}:charge{limit_cents=5000 order_id=2}` означает «внутри `process` для заказа 2, внутри `charge`». В фигурных скобках — поля каждого спана.
2. Благодаря спанам строка `total is over the limit` говорит нам, **какого заказа** она касается, хотя сам `warn!` его не упоминает. Это была проблема 3 из раздела 1.
3. Строку `ERROR` создал `err`, мы её не писали. После неё программа продолжает работу (`order rejected`).
4. Строки заказа 1 показывают счастливый путь: три строки `INFO`, без предупреждений.

## 5. Выбор того, что видеть, через `RUST_LOG`

`EnvFilter` читает переменную `RUST_LOG` при запуске программы. Вы меняете количество логов, не меняя код:

```bash
cargo run                     # no RUST_LOG: only ERROR
RUST_LOG=warn cargo run       # WARN and ERROR
RUST_LOG=debug cargo run      # everything from DEBUG up
```

```text
ERROR p09_tracing: error=order 2 is over the limit
```

```text
 WARN p09_tracing: total is over the limit total=6500 limit_cents=5000
ERROR p09_tracing: error=order 2 is over the limit
```

С `RUST_LOG=debug` появляются дополнительные строки `DEBUG`, например:

```text
DEBUG process{order_id=1}:charge{limit_cents=5000 order_id=1}: p09_tracing: computed total total=2500 items=2
```

(Обратите внимание: при `RUST_LOG=warn` имена спанов из строк пропали. Спаны, созданные `#[instrument]`, имеют уровень `INFO`, поэтому `warn` их выключает, и они больше не входят в печатаемый контекст. Используйте как минимум `info`, когда нужно знать, к какому заказу относится строка.)

Значение `RUST_LOG` — список **директив** через запятую. Директива — это `уровень` или `цель=уровень`:

| `RUST_LOG` | Значение |
|---|---|
| `info` | Всё на уровне `INFO` и выше, из всех крейтов |
| `warn,p09_tracing=debug` | `WARN` для всего, но `DEBUG` для нашего собственного крейта |
| `p09_tracing=trace` | Только наш крейт, на всех уровнях; зависимости остаются на уровне по умолчанию (`ERROR`) |
| `debug,hyper=warn` | `DEBUG` везде, но тихо для крейта `hyper` |

В этом и состоит главное применение целей: когда библиотека (зависимость) слишком болтлива, вы глушите её одной директивой и сохраняете полную подробность для собственного кода.

> 💡 **Совет:** задайте хорошее значение по умолчанию на случай, когда `RUST_LOG` не установлена. Вместо `EnvFilter::from_default_env()` напишите `EnvFilter::try_from_default_env().unwrap_or_else(|_| EnvFilter::new("info"))`. Тогда программа по умолчанию показывает `INFO`, а переменная лишь переопределяет это.

## 6. Сколько это заняло? Спаны как секундомеры

У спана есть начало и конец, поэтому подписчик может измерить его длительность. Добавьте `.with_span_events(FmtSpan::CLOSE)` в строитель (и импорт `use tracing_subscriber::fmt::format::FmtSpan;`). Тогда каждый спан при закрытии печатает одно дополнительное событие. На этот раз оставьте метку времени, потому что поля времени показываются вместе с ней:

```text
2026-11-18T06:40:57.072353Z  INFO process{order_id=2}:charge{limit_cents=5000 order_id=2}: p09_tracing: close time.busy=13.4µs time.idle=1.50µs
2026-11-18T06:40:57.072364Z  INFO process{order_id=2}: p09_tracing: close time.busy=32.7µs time.idle=1.54µs
```

(Пример вывода; ваши числа будут другими.) `time.busy` — время, пока код работал внутри спана, а `time.idle` — время, когда спан был открыт, но код ждал (это важно для асинхронного кода, [Урок 06.9](../06-rust-advanced/09-async-await-introduction.md)). Здесь `charge` заняла 13,4 микросекунды, а весь `process` — 32,7 микросекунды. Это дешёвый способ увидеть, какая часть программы медленная, прежде чем браться за бенчмарк (Урок 09.11).

Для машин вместо людей те же события можно печатать как один объект **JSON** на строку, который умеют искать инструменты логов. Добавьте фичу `json` (`cargo add tracing-subscriber@0.3 --features env-filter,json`) и вызовите `.json()` вместо `.with_ansi(false)`:

```text
{"level":"WARN","fields":{"message":"total is over the limit","total":6500,"limit_cents":5000},"target":"p09_tracing","span":{"limit_cents":5000,"order_id":2,"name":"charge"},"spans":[{"order_id":2,"name":"process"},{"limit_cents":5000,"order_id":2,"name":"charge"}]}
```

Каждое поле — отдельный ключ, поэтому инструмент может ответить на «покажи все события `WARN` для `order_id` 2», не разбирая предложение. Это и есть **структурированное логирование**.

## 7. Логи в тестах

Когда тест падает, лог того, что произошло внутри, часто — самое быстрое объяснение. У `tracing-subscriber` есть `with_test_writer()`, который отправляет строки через перехват вывода тестовой обвязки, поэтому они показываются только для упавших тестов (или с `--nocapture`). Добавьте это в конец `src/main.rs`:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    fn init_logs() {
        // `try_init` returns an error if a subscriber already exists; ignore it,
        // because every test calls this function.
        let _ = tracing_subscriber::fmt()
            .with_env_filter(EnvFilter::from_default_env())
            .with_ansi(false)
            .with_test_writer()
            .without_time()
            .try_init();
    }

    #[test]
    fn small_order_is_charged() {
        init_logs();
        let order = Order {
            id: 7,
            customer: "Test".to_string(),
            prices_cents: vec![100, 200],
        };
        assert_eq!(charge(&order, 1_000), Ok(300));
    }

    #[test]
    fn big_order_is_rejected() {
        init_logs();
        let order = Order {
            id: 8,
            customer: "Test".to_string(),
            prices_cents: vec![9_000],
        };
        assert!(charge(&order, 1_000).is_err());
    }
}
```

**Что происходит:**

1. Подписчика можно установить **только один раз** на процесс. Все тесты крейта выполняются в одном процессе (в разных потоках), поэтому каждый тест вызывает `init_logs()`, а `try_init()` тихо ничего не делает, когда подписчик уже установлен.
2. `with_test_writer()` делает так, что строки принадлежат тесту, который их напечатал.
3. Обычный `cargo test` не показывает ничего лишнего. `RUST_LOG=debug cargo test -- --nocapture` показывает логи всех тестов:

```bash
cargo test
```

```text
test tests::small_order_is_charged ... ok
test tests::big_order_is_rejected ... ok
test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

> 🧪 **Тестирование:** положите в свой набор инструментов `RUST_LOG=debug cargo test имя_падающего_теста`. Когда тест падает, его лог печатается вместе с отчётом о падении, и вы видите шаги, которые к нему привели, не добавив ни одного `println!`.

## 8. Что логировать и что не логировать никогда

1. **Библиотеки используют только макросы; приложения устанавливают подписчика.** Если бы библиотека сама вызывала `tracing_subscriber::fmt().init()`, она нарушила бы выбор программы, которая её использует. `init` вызывает только `main` (или тест).
2. **Логируйте решения и границы**, а не каждую строку: пришёл запрос, заказ принят, случилась повторная попытка, соединение оборвалось. Если логировать всё на уровне `INFO`, важные строки потеряются в шуме.
3. **Выбирайте уровень честно.** `ERROR` — для сбоев, на которые должен посмотреть человек. Если каждый отклонённый заказ — `ERROR`, `ERROR` больше никто не читает.
4. **Не логируйте один сбой дважды.** В нашей программе `err` уже записывает ошибку, поэтому `process` лишь говорит «order rejected» на уровне `INFO`.
5. **Не заменяйте логами метрики**: «сколько заказов в секунду?» — это число, которое нужно считать, а не строка для поиска через grep (метрики разбирает один из следующих этапов).

> 🔒 **Безопасность:** **никогда не логируйте секреты и персональные данные**: пароли, токены, API-ключи (API, Application Programming Interface, программный интерфейс), номера карт, тела запросов целиком. Логи копируются во многие места, хранятся месяцами и читаются многими людьми. Помните, что `#[instrument]` без `skip` записывает **каждый аргумент** через `Debug`: функция `login(user: &str, password: &str)` напечатает пароль. Используйте `skip` или `skip_all` и называйте безопасные поля сами. Будьте осторожны и с текстом извне: пользователь может прислать перевод строки и подделать строку лога. Со структурированными полями (`name = %input`) значение остаётся внутри своего поля, а формат JSON его экранирует.

> ⚡ **Производительность:** *включённое* логирование стоит реального времени: форматирование, блокировка и запись. Не логируйте во внутреннем цикле горячего пути на уровне `INFO`. Используйте там `trace!`, который по умолчанию выключен.

## Частые ошибки

**1. Подписчик не установлен.** Если `main` никогда не вызывает `.init()`, все события молча отбрасываются, и вы ничего не видите. Добавьте строку в начало `main`.

**2. Двойной вызов `init()`.** `.init()` паникует, если подписчик уже установлен (например, один раз в `main` и один раз в библиотечной функции). В тестах используйте `try_init()`.

**3. `RUST_LOG` задана, но ничего не меняется.** `EnvFilter` применяется, только если вы передали его через `.with_env_filter(...)`. Без этого вызова (как в разделе 2) `RUST_LOG` игнорируется.

**4. Значение внутри сообщения.** `info!("charged {total} cents")` — просто текст, и инструмент не может по нему фильтровать. Пишите `info!(total, "charged")`.

**5. `#[instrument]` на функции с большим или секретным аргументом.** Используйте `skip` или `skip_all`.

## Упражнения

### Упражнение 1 — Директива (легко)

Какое значение `RUST_LOG` показывает события `WARN` и `ERROR` для всех крейтов, но события `DEBUG` (и выше) только для крейта `p09_tracing`? Запишите его и запустите программу с ним. Сколько строк она печатает?

<details>
<summary>Подсказка</summary>

Директива — это `цель=уровень`; несколько директив разделяются запятыми. Директива без цели задаёт уровень по умолчанию.

</details>

<details>
<summary>Ответ</summary>

```bash
RUST_LOG=warn,p09_tracing=debug cargo run
```

Она печатает полный вывод `DEBUG`, 9 строк. Наш крейт на уровне `debug`, поэтому показываются все его события; `warn` применяется ко всему остальному, а других крейтов, которые бы что-то логировали, в этой программе нет.

Почему это работает: фильтр выбирает наиболее конкретную директиву, подходящую к цели события. У наших событий цель `p09_tracing`, она подходит к `p09_tracing=debug`.

</details>

### Упражнение 2 — Тест границы (средне)

Напишите тест, что заказ, сумма которого **ровно** равна лимиту, принимается (`charge(&order, 1_000)` с ценами `[400, 600]` должна вернуть `Ok(1000)`). Какое сравнение в `charge` защищает этот тест?

<details>
<summary>Подсказка</summary>

Поставьте тест рядом с остальными в `mod tests` и сначала вызовите `init_logs()`. В коде написано `if total > limit_cents`.

</details>

<details>
<summary>Ответ</summary>

```rust
    #[test]
    fn order_exactly_at_the_limit_is_charged() {
        init_logs();
        let order = Order {
            id: 9,
            customer: "Test".to_string(),
            prices_cents: vec![400, 600],
        };
        assert_eq!(charge(&order, 1_000), Ok(1_000));
    }
```

Почему это работает: сумма равна 1000, а `1000 > 1000` ложно, поэтому заказ принимается. Тест защищает `>` от ошибочной замены на `>=` (ошибка на единицу). Если кто-то сделает такую замену, этот тест упадёт, и в его логе будет строка `WARN`.

</details>

### Упражнение 3 — Спан, который выдаёт лишнее (сложно)

Коллега пишет `#[instrument]` (без аргументов) на `fn process(order: Order)`. Запустите программу с `RUST_LOG=info` и посмотрите на первую строку. Что утекает и что нужно написать вместо этого?

<details>
<summary>Подсказка</summary>

`#[instrument]` записывает каждый аргумент через `Debug`, а `Order` выводит `Debug`. Сравните с `skip_all`.

</details>

<details>
<summary>Ответ</summary>

Первая строка становится такой:

```text
 INFO process{order=Order { id: 1, customer: "Ada", prices_cents: [1000, 1500] }}: p09_tracing: order received customer=Ada
```

Весь заказ (имя клиента и каждая цена) печатается в каждой строке каждого события внутри `process`. Вместо этого напишите:

```rust
#[instrument(skip_all, fields(order_id = order.id))]
```

и спан станет коротким `process{order_id=1}`. Почему это работает: `skip_all` останавливает автоматическую запись аргументов, а `fields(...)` добавляет только те значения, которые вы сочли безопасными и полезными.

</details>

## Вопросы для самопроверки

1. В чём разница между событием и спаном?

<details>
<summary>Ответ</summary>

Событие — один момент («заказ получен»). Спан — период времени с именем и полями; события внутри него печатаются с его контекстом, а его длительность можно измерить.

</details>

2. Почему строки `debug!` безопасно оставлять в коде?

<details>
<summary>Ответ</summary>

Когда уровень выключен, макрос пропускает событие рано, до вычисления значений полей и до форматирования, поэтому цена мизерная. Позже строки можно включить через `RUST_LOG=debug` без перекомпиляции.

</details>

3. Чем `info!(total = ?x, "done")` отличается от `info!(total = %x, "done")`?

<details>
<summary>Ответ</summary>

`?` записывает значение в форме `Debug` (у `&str` будут кавычки); `%` — в форме `Display` (без кавычек). Типам без `Display` нужен `?`.

</details>

4. Кто должен вызывать `.init()`, чтобы установить подписчика: библиотека или программа?

<details>
<summary>Ответ</summary>

Программа (`main` или тест). Библиотека только использует макросы, а куда пойдёт вывод, решает программа.

</details>

5. `RUST_LOG=warn` скрывает имена спанов в строках. Почему?

<details>
<summary>Ответ</summary>

Спаны, созданные `#[instrument]`, имеют уровень `INFO`. При `warn` они выключены, поэтому не входят в печатаемый контекст.

</details>

6. Назовите две вещи, которые нельзя записывать в лог.

<details>
<summary>Ответ</summary>

Пароли, токены, API-ключи, номера карт или другие персональные данные. Также будьте осторожны с непроверенным вводом, который может подделать строки лога; структурированные поля удерживают его внутри своего поля.

</details>

## Итоги

- Логи нужны, когда нельзя подключить отладчик: релизная сборка, долгая работа, сервер. `tracing` позволяет коду описывать события и спаны; `tracing-subscriber` решает, как их печатать.
- Пять уровней: `ERROR`, `WARN`, `INFO`, `DEBUG`, `TRACE`. Выключенные уровни почти бесплатны.
- Кладите значения в поля (`info!(total, "charged")`), а не в сообщение. `%` значит `Display`, `?` значит `Debug`.
- `#[instrument]` создаёт спан для функции; используйте `skip`, `skip_all`, `fields(...)` и `err`.
- `EnvFilter` с `RUST_LOG` усиливает и ослабляет логирование без перекомпиляции: `warn,p09_tracing=debug`.
- События закрытия спанов дают тайминги; вывод JSON даёт данные для инструментов; `with_test_writer()` показывает логи упавших тестов.
- Подписчика устанавливает только программа. Никогда не логируйте секреты.
