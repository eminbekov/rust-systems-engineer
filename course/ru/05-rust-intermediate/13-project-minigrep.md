## Новые слова

| Слово | Значение |
|---|---|
| **grep** (Global Regular Expression Print, «глобальная печать по регулярному выражению») | Классическая программа Unix, которая печатает строки файла, соответствующие образцу. `minigrep` — её маленькая версия. |
| **образец** (pattern) | Текст, который вы ищете. В `minigrep` это обычный текст, а не регулярное выражение. |
| **стандартный ввод** (standard input, stdin) | Поток данных, который программа читает по умолчанию: клавиатура или вывод другой программы. |
| **стандартный вывод** (standard output, stdout) | Поток, куда программа записывает свои обычные результаты. |
| **стандартный поток ошибок** (standard error, stderr) | Второй поток вывода для сообщений об ошибках, отдельный от результатов. |
| **конвейер** (pipe, `\|`) | Возможность оболочки, которая соединяет stdout одной программы со stdin следующей: `cat file \| minigrep word`. |
| **перенаправление** (redirect, `>`) | Возможность оболочки, которая отправляет stdout в файл: `minigrep word file > result.txt`. |
| **статус завершения** (exit status) | Число, которое возвращается при завершении программы; `0` означает успех. Также называется кодом возврата. |
| **переменная окружения** (environment variable) | Именованная настройка, которую оболочка передаёт программе, например `HOME` или `MINIGREP_IGNORE_CASE`. |
| **буфер** (buffer) | Кусок памяти, который накапливает данные перед отправкой дальше, чтобы требовалось меньше медленных операций. |
| **системный вызов** (system call, syscall) | Запрос программы к операционной системе, например «запиши эти байты». У каждого есть цена. |
| **приёмочный тест** (acceptance test) | Тест, который проверяет, что программа делает то, что обещает контракт, если смотреть снаружи. Здесь это команды «Готово, когда». |
| **крейт-библиотека / крейт-бинарник** (library crate / binary crate) | Крейт с `src/lib.rs` (код для использования другими) / крейт с `src/main.rs` (программа, которую вы запускаете). В пакете могут быть оба. |
| **TDD** (Test-Driven Development, разработка через тестирование) | Способ работы: сначала пишется падающий тест, затем код, который его проходит, затем наводится порядок. |
| **README** | Текстовый файл в корне проекта, который объясняет, что это и как этим пользоваться. |
| **тег** (tag, Git) | Фиксированная именованная метка на одном коммите, часто для релиза, например `v0.1.0`. |
| **I/O** (Input/Output, ввод-вывод) | Чтение из внешнего мира и запись в него: файлы, клавиатура, экран, сеть. |
| **CLI** (Command-Line Interface, интерфейс командной строки) | Программа, которой пользуются, набирая команду в терминале. |

## Разминка: познакомьтесь с настоящим grep

Прежде чем создавать инструмент, воспользуйтесь настоящим. Создайте папку с двумя небольшими файлами (используйте точно эти тексты, как в примерах урока, чтобы ваш вывод совпадал):

```bash
mkdir -p ~/projects/rust/code/p05-minigrep-data && cd ~/projects/rust/code/p05-minigrep-data
cat > poem.txt <<'EOF'
Rust is a language
that cares about memory.
Every value has an owner,
and the owner decides its fate.
RUST is loved by many,
but the compiler is strict.
EOF
cat > notes.txt <<'EOF'
todo: read the chapter about rust
todo: write the tests
done: install the toolchain
EOF
```

Теперь попробуйте системный `grep` (на вашем Mac `grep` может оказаться современной заменой, но приведённые ниже параметры работают так же):

```bash
grep Rust poem.txt        # строки, содержащие "Rust"
grep -i rust poem.txt     # без учёта регистра
grep -n owner poem.txt    # показать номера строк
grep -c the poem.txt      # только посчитать строки
grep -v the poem.txt      # строки, которые НЕ содержат "the"
echo $?                   # статус завершения последней команды
```

Заметьте две вещи: когда `grep` ничего не находит, он ничего не печатает, но его статус завершения равен `1`; и `grep` читает стандартный ввод, если файл не указан: `cat poem.txt | grep -n memory`. Ваш инструмент повторит это поведение.

## Проект

### Что вы создадите

`minigrep` — инструмент командной строки, который печатает строки файлов (или стандартного ввода), содержащие заданный текст. Он поддерживает четыре опции (`-i`, `-v`, `-n`, `-c`), несколько файлов, переменную окружения и правильные коды возврата. Он построен как **библиотека** (`src/lib.rs`) со всей логикой и **тонкий бинарник** (`src/main.rs`), который общается с терминалом.

Работать вы будете в таком порядке: подготовка и разбор аргументов, функция поиска с тестами заранее, чтение файлов и вывод, опции, тестирование всей программы снаружи, документация, затем измерения и ускорение.

```text
p05-minigrep/
├── Cargo.toml
├── README.md
├── benches/
│   └── search.rs        ← бенчмарк criterion (веха M7)
├── src/
│   ├── lib.rs           ← логика: search, run, ошибки
│   └── main.rs          ← терминал: clap, коды возврата
└── tests/
    └── cli.rs           ← интеграционные тесты (веха M5)
```

### Контракт

Это точное поведение, которое должна иметь ваша программа. Все проверки «Готово, когда» следуют из него.

**Использование**

```text
minigrep [OPTIONS] <PATTERN> [FILES]...
```

| Часть | Значение |
|---|---|
| `<PATTERN>` | Обязателен. Текст для поиска. Обычный текст, не регулярное выражение. Строка *выбирается*, когда содержит образец. Пустой образец выбирает каждую строку. |
| `[FILES]...` | Ноль или больше файлов. Если файлов нет, читается стандартный ввод. |
| `-i`, `--ignore-case` | Заглавные и строчные буквы считаются равными. |
| `-v`, `--invert-match` | Выбирать строки, которые **не** содержат образец. |
| `-n`, `--line-number` | Печатать номер строки (считая с 1) и двоеточие перед каждой строкой. |
| `-c`, `--count` | Не печатать строки; печатать только число выбранных строк для каждого входа. |
| `-h`, `--help`, `-V`, `--version` | Справка и версия (создаются `clap`). |

**Окружение.** Если переменная `MINIGREP_IGNORE_CASE` задана (с любым значением), она работает как `-i`.

**Вывод (stdout)**

| Ситуация | Формат выбранной строки |
|---|---|
| один вход | `text` |
| один вход, `-n` | `12:text` |
| больше одного файла | `file:text` |
| больше одного файла, `-n` | `file:12:text` |
| `-c`, один вход | `3` |
| `-c`, больше одного файла | `file:3` (по строке на файл) |

Строки печатаются в порядке появления, файл за файлом, в порядке, указанном в командной строке. Перевод строки не входит в текст строки.

**Ошибки (stderr)**

- Файл, который нельзя прочитать, даёт одну строку в stderr: `minigrep: <file>: <reason>` (например, `minigrep: missing.txt: No such file or directory (os error 2)`). Остальные файлы всё равно обрабатываются.
- Неверная командная строка (нет образца, неизвестная опция) даёт обычное сообщение `clap` в stderr.
- В stdout попадают только результаты.

**Статус завершения**

| Статус | Когда |
|---|---|
| `0` | Выбрана хотя бы одна строка, и все входы удалось прочитать. |
| `1` | Не выбрано ни одной строки, и все входы удалось прочитать. |
| `2` | Любая ошибка: файл не удалось прочитать или командная строка неверна. |

**Правила для кода**

- Логика находится в `src/lib.rs`. `src/main.rs` только разбирает аргументы, вызывает библиотеку и превращает результат в статус завершения.
- Функция, которая выполняет сопоставление, возвращает **заимствованные** строки (`&str` из входного текста), а не новые `String`. Ей нужна аннотация времени жизни: `fn search<'a>(pattern: &str, contents: &'a str, ...) -> Vec<...<'a>>`.
- Ошибки — это перечисление `thiserror`. Никаких `unwrap()` и `expect()` вне тестов.
- Зависимости: `clap` и `thiserror`; dev-зависимости `tempfile` и `criterion`.
- `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` и `cargo test` должны проходить без предупреждений.

#### M1 — Подготовьте проект и разберите командную строку

**Цель:** проект, который собирается, находится под Git и понимает командную строку из контракта.

**Руководство:**

1. Создайте ветку для проекта и пакет: `cd ~/projects/rust && git switch -c project/05-minigrep && cargo new code/p05-minigrep`. Поскольку вы внутри своего учебного репозитория, Cargo не создаёт новый репозиторий Git. В `Cargo.toml` измените `name` пакета на `minigrep` (тогда бинарник будет называться `minigrep`).
2. Добавьте зависимости: `clap` с фичей `derive`, `thiserror` и (как dev-зависимости, с `--dev`) `tempfile` и `criterion`. См. [Урок 05.8](08-cargo-dependencies-and-versions.md) и [Урок 05.11](11-practical-crates-serde-clap-errors.md).
3. Создайте `src/lib.rs` (пока он может быть пустым или содержать только комментарий).
4. В `src/main.rs` опишите структуру командной строки с `#[derive(Parser)]` и аргументами из контракта. Дайте каждому аргументу doc-комментарий. На этой вехе `main` только разбирает аргументы и печатает их через `{:?}` (добавьте `Debug` в derive).
5. Сделайте коммит (сообщение смотрите ниже).

<details>
<summary>Подсказка 1 — поля</summary>

`pattern: String`, `files: Vec<PathBuf>` и четыре поля `bool` с `#[arg(short, long)]`. Поле `Vec<PathBuf>` означает «ноль или больше» аргументов. Флагу `-v` для инверсии нужен `#[arg(short = 'v', long)]`, если поле называется `invert_match`, потому что один `short` берёт первую букву имени поля (`i`, которая уже занята `ignore_case`). Посмотрите, какие короткие опции вам нужны, и назовите поля так, чтобы они не конфликтовали.

</details>

<details>
<summary>Подсказка 2 — длинные имена</summary>

`long` превращает имя поля в опцию с дефисами: `ignore_case` становится `--ignore-case`, `line_number` — `--line-number`, `invert_match` — `--invert-match`. Они перечислены в контракте.

</details>

**Готово, когда:**


печатает строку использования, которая содержит `minigrep [OPTIONS] <PATTERN> [FILES]...`, и перечисляет четыре опции, а также `-h`, `-V`. (Тексты описаний ваши.) Например:



#### M2 — Функция поиска, сначала тест

**Цель:** протестированная функция в `src/lib.rs`, которая выбирает строки. Пока без файлов и терминала.

**Руководство:** Это TDD ([Урок 05.6](06-testing-in-depth.md)): красный, зелёный, рефакторинг.

1. В `lib.rs` определите `pub struct Options { pub ignore_case: bool, pub invert: bool }` (добавьте `Debug`, `Default`, `Clone`, `Copy`, `PartialEq`, `Eq`) и `pub struct Match<'a> { pub line_number: usize, pub text: &'a str }` (добавьте `Debug`, `PartialEq`, `Eq`). Время жизни `'a` говорит: `Match` не может пережить текст, на который указывает.
2. Напишите **тесты сначала** (они пока даже не скомпилируются). Используйте общую константу:

```rust
const TEXT: &str = "Rust is fast\nrust is safe\nPython is nice";
```

Проверьте такие поведения, по одному тесту на каждое:
   - По умолчанию поиск учитывает регистр: `"Rust"` выбирает только строку 1.
   - С `ignore_case` образец `"RUST"` выбирает строки 1 и 2.
   - С `invert` образец `"fast"` выбирает две строки, а `"is"` — ни одной.
   - Пустой образец выбирает каждую строку.
   - Пустой текст ничего не выбирает.
3. Напишите `pub fn search<'a>(pattern: &str, contents: &'a str, options: Options) -> Vec<Match<'a>>`, чтобы тесты проходили. Используйте адаптеры итераторов (`lines`, `enumerate`, `filter`, `map`, `collect`) вместо цикла `for` с изменяемым вектором ([Урок 05.5](05-iterators.md)).
4. Запустите `cargo clippy --all-targets -- -D warnings` и `cargo fmt`. Можно сделать два коммита: один для тестов, один для кода.

<details>
<summary>Подсказка 1 — сопоставление без учёта регистра</summary>

Преобразуйте и образец, и строку через `to_lowercase()` и сравнивайте через `contains`. Образец преобразуйте один раз, вне цикла, а не для каждой строки. (Сначала сделайте эту простую версию. В вехе M7 вас попросят её измерить.)

</details>

<details>
<summary>Подсказка 2 — как учесть инверсию</summary>

Вычислите `found` (содержит ли строка образец?) и оставляйте строку, когда `found != options.invert`. Это одно сравнение покрывает оба режима.

</details>

<details>
<summary>Подсказка 3 — номера строк</summary>

`lines().enumerate()` считает с 0. Используйте `index + 1` для `line_number`. Помните, что фильтровать нужно сначала, а преобразовывать потом, либо хранить индекс в паре, чтобы номера оставались верными для пропущенных строк.

</details>

<details>
<summary>Подсказка 4 — зачем `<'a>`?</summary>

У функции два ссылочных параметра (`pattern` и `contents`), и она возвращает ссылки. Компилятор не может знать, из какого входа заимствован результат, поэтому нужно сказать: результат живёт столько же, сколько `contents` (`'a`), а `pattern` с ним не связан. Если вы напишете неправильное время жизни, сообщение об ошибке на него укажет ([Урок 05.3](03-lifetimes.md)).

</details>

**Готово, когда:** `cargo test` показывает, что ваши тесты проходят (не меньше пяти для `search`), например:

```text
running 5 tests
test tests::case_sensitive_by_default ... ok
test tests::empty_pattern_selects_every_line ... ok
test tests::empty_text_has_no_lines ... ok
test tests::ignore_case_finds_both ... ok
test tests::invert_selects_the_other_lines ... ok

test result: ok. 5 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

(Имена ваши. Порядок может отличаться.) Коммит: `git add . && git commit -m "feat(minigrep): add the search function with tests"`.

#### M3 — Чтение файлов и печать результатов

**Цель:** `minigrep Rust poem.txt` работает для одного или нескольких файлов, а ошибки чтения обрабатываются.

**Руководство:**

1. Определите `pub struct Config` в `lib.rs`: образец, список файлов, `Options` и переключатели вывода (`line_numbers`, `count`). `main` собирает её из структуры `clap`.
2. Определите `pub enum GrepError` с помощью `thiserror`. Ему нужен как минимум вариант «не удаётся прочитать этот файл», хранящий имя файла и исходный `io::Error` (используйте `#[source]`), и вариант для ошибки при записи вывода.
3. Напишите `pub fn run(...)` в `lib.rs`. Чтобы её можно было тестировать, она не должна напрямую использовать `println!`. Дайте ей **writer** для результатов и writer для ошибок (обобщённые параметры `W: Write`, `E: Write`), а также reader для стандартного ввода (`&mut dyn Read`). В тестах вы передаёте `Vec<u8>` как writer; в `main` вы передаёте `stdout` и `stderr`.
4. Для каждого файла: прочитайте его через `std::fs::read_to_string`, вызовите `search` и запишите выбранные строки. Когда файлов больше одного, ставьте `file:` перед каждой строкой. Если чтение не удалось, запишите `minigrep: <error>` в writer ошибок, запомните, что что-то пошло не так, и **переходите к следующему файлу**.
5. `run` возвращает общий результат (`Matched`, `NoMatch`, `Failed`). `main` превращает его в `ExitCode::SUCCESS`, `ExitCode::from(1)` или `ExitCode::from(2)` ([Урок 05.11](11-practical-crates-serde-clap-errors.md) показал `main`, возвращающий статус).
6. Пока не поддерживайте опции, кроме образца и файлов (разобранные поля уже можно передавать). Добавьте тесты для `run`, использующие writer в памяти.

<details>
<summary>Подсказка 1 — обобщённый writer</summary>

`pub fn run<W: Write, E: Write>(config: &Config, stdin: &mut dyn Read, out: &mut W, err: &mut E) -> Result<Outcome, GrepError>`. Используйте `writeln!(out, "{}", line)?;` вместо `println!`. В тесте: `let mut out = Vec::new();`, а потом `String::from_utf8(out).unwrap()`. `&[u8]` (например, `"text".as_bytes()`) реализует `Read`, поэтому может играть роль stdin.

</details>

<details>
<summary>Подсказка 2 — продолжать после ошибки</summary>

Используйте `match` по `fs::read_to_string(path)`. В ветке `Err` запишите сообщение и установите переменную `failed = true`, а `?` там не используйте (`?` остановил бы всю функцию). В конце: `if failed { Outcome::Failed } else if selected > 0 { Outcome::Matched } else { Outcome::NoMatch }`.

</details>

<details>
<summary>Подсказка 3 — метка</summary>

Вычислите `let label_files = config.files.len() > 1;` один раз перед циклом. Имя файла можно превратить в текст через `path.display()`.

</details>

<details>
<summary>Подсказка 4 — функция main</summary>

`fn main() -> ExitCode`. Заблокируйте stdout один раз (`let stdout = io::stdout(); let mut out = stdout.lock();`). Если `run` возвращает `Err`, напечатайте `minigrep: {error}` в stderr и верните `ExitCode::from(2)`.

</details>

**Готово, когда:** (выполняйте в папке `~/projects/rust/code/p05-minigrep-data`; путь к бинарнику при необходимости замените, здесь это `$B`: `B=~/projects/rust/code/p05-minigrep/target/debug/minigrep` после `cargo build`)

```bash
$B Rust poem.txt notes.txt
```

#### M7 — Измерьте, найдите медленное место, исправьте

**Цель:** применить [Урок 05.12](12-benchmarking-basics.md) к своему инструменту. Вы найдёте настоящую медлительность с помощью `hyperfine`, исправите её и докажете это числами.

**Руководство:**

1. **Микробенчмарк `search`.** Добавьте в `Cargo.toml` `[[bench]] name = "search"` с `harness = false` и создайте `benches/search.rs` с `criterion`. Постройте текст из 100 000 строк (например, циклом, повторяющим строку `"line {i}: the quick brown fox jumps over the lazy dog, again and again"`) вне измеряемого кода и замерьте два случая: с учётом регистра и без. Используйте `black_box`. Запустите `cargo bench`.
2. **Измерьте всю программу.** Соберите через `cargo build --release`. Сделайте большой тестовый файл, в котором совпадает каждая строка (около 74 МБ):

```bash
yes 'the quick brown fox jumps over the lazy dog, again and again' | head -n 1000000 > /tmp/big.txt
```

   Установите `hyperfine` (`cargo install hyperfine`) и измерьте: `hyperfine --warmup 2 --runs 10 "./target/release/minigrep 'lazy dog' /tmp/big.txt"`. Сохраните результат.
3. **Посмотрите на числа.** Программа должна напечатать миллион строк. Подумайте: сколько раз она просит операционную систему выполнить запись? (Подсказка ниже.)
4. **Сделайте изменение в ветке.** `git switch -c perf/buffered-output` (от ветки вашего проекта). Измените **одну** вещь. Запустите тесты. Измерьте снова той же командой `hyperfine`. Запишите числа «до» и «после» в сообщение коммита, например `perf(minigrep): buffer the output (734 ms -> 45 ms)`.
5. Если числа явно улучшились, слейте в ветку проекта: `git switch project/05-minigrep && git merge perf/buffered-output`, затем удалите ветку эксперимента командой `git branch -d perf/buffered-output`. Если числа не улучшились, удалите ветку командой `git branch -D perf/buffered-output` и запишите, чему вы научились.
6. Добавьте в README раздел «Performance» с двумя числами и описанием вашего компьютера.
7. Поставьте тег версии: `git tag minigrep-v0.1.0` (префикс помогает отличать теги вашего учебного репозитория). Когда вы довольны, слейте ветку проекта в `main` (`git switch main && git merge project/05-minigrep`); основная ветка на вашем компьютере может называться `master`, проверьте через `git branch`.

<details>
<summary>Подсказка 1 — где уходит время?</summary>

Стандартный вывод Rust **буферизуется построчно**: он отправляет данные операционной системе в конце каждой строки. Миллион строк — это миллион системных вызовов. Один системный вызов дёшев, а миллион — нет.

</details>

<details>
<summary>Подсказка 2 — исправление</summary>

Оберните вывод в `std::io::BufWriter::new(stdout.lock())` в `main`. `BufWriter` накапливает байты в буфере (по умолчанию 8 КиБ; КиБ — кибибайт: 1 024 байта) и записывает их большими кусками. Помните две вещи: вызовите `flush()` в конце и сообщите об ошибке, если он не удался (при уничтожении буфер тоже пытается сбросить данные, но сообщить об ошибке не может), и заметьте, что сообщения об ошибках в stderr теперь могут появляться *раньше* результатов в stdout, потому что stdout ждёт в буфере. Это нормально для таких инструментов, как `grep`, когда их вывод идёт не в терминал.

</details>

<details>
<summary>Подсказка 3 — чего ожидать</summary>

На компьютере автора (Apple M4 Pro), 1 000 000 совпавших строк: до — около 734 мс, после — около 45 мс, то есть более чем в 16 раз быстрее. Ваши числа будут другими, но улучшение должно быть в несколько раз. Использование памяти (около 97 МиБ, где МиБ — мебибайт: 1 048 576 байт) не изменилось, потому что программа по-прежнему читает весь файл в память: это одна из дополнительных целей.

</details>

### Дополнительные цели

Делайте их в ветках (`git switch -c <name>`), по одной, с тестами и с измерением, когда цель — скорость. Сливайте только то, чем гордитесь.

1. **Чтение по строкам.** Используйте `BufReader` и `lines()`, чтобы читать файл потоком, и файлу в 10 ГБ не требовалось 10 ГБ памяти. Сравните столбец памяти в `hyperfine` до и после. (Осторожно: `search` теперь работает с одной строкой за раз или с reader.)
2. **Рекурсивный поиск.** Добавьте `-r`/`--recursive`: когда путь — папка, искать во всех файлах внутри неё (используйте `std::fs::read_dir`). Пропускайте файлы, которые не являются корректным UTF-8 (стандартным способом хранить текст в виде байтов; `str` и `String` в Rust — всегда UTF-8), с понятным сообщением.
3. **Параллельный поиск.** Используйте `std::thread::scope` ([Урок 05.10](10-threads-channels-and-shared-state.md)), чтобы читать и обрабатывать несколько файлов одновременно, но печатать результаты в порядке, указанном в командной строке. Измерьте на многих файлах: правда ли быстрее? У потоков есть цена.
4. **Более быстрый поиск без учёта регистра.** Избегайте выделения новой `String` на каждую строку: сравнивайте без создания копии строки в нижнем регистре (для текста в ASCII, то есть простых латинских букв из American Standard Code for Information Interchange, — `eq_ignore_ascii_case` на окнах байтов; для полного Unicode подумайте о цене и корректности). Используйте базовую линию criterion из M7, чтобы доказать выигрыш.
5. **Строки контекста.** Добавьте `-C N`, чтобы печатать `N` строк до и после каждой выбранной строки, с `--` между группами, как в `grep`.
6. **Цвета.** Подсвечивайте найденный текст красным, только когда stdout — терминал (`std::io::IsTerminal`).
7. **Регулярные выражения.** Добавьте крейт `regex` ([Урок 05.8](08-cargo-dependencies-and-versions.md) показывает, как читать его документацию и фичи) и опцию `-E`. Поиск по обычному тексту оставьте по умолчанию.
8. **Релиз.** Выполните `cargo build --release`, скопируйте бинарник в папку из `PATH` и пользуйтесь своим инструментом каждый день. Запишите в учебные заметки, что бы вы изменили дальше.

## Частые ошибки

1. **Логика в `main.rs`.** Тогда её нельзя протестировать модульно. Держите `main.rs` тонким.
2. **`println!` в библиотеке.** Тогда функцию трудно тестировать, и она не может писать в другие места. Принимайте параметр `Write`.
3. **`?` в цикле по файлам для ошибок чтения.** Первый же отсутствующий файл останавливает весь запуск, а контракт требует продолжать. Обрабатывайте ошибку через `match`.
4. **Ошибка времени жизни в `search`.** Например:

```text
error[E0106]: missing lifetime specifier
```

   Компилятор не знает, откуда берутся возвращаемые ссылки: из `pattern` или из `contents`. Добавьте `'a` к `contents` и к результату ([Урок 05.3](03-lifetimes.md)).
5. **Преобразование образца в нижний регистр внутри цикла.** Одна и та же работа повторяется для каждой строки. Делайте это один раз.
6. **Забыли про статус завершения.** Инструмент, который всегда возвращает 0, нельзя использовать в скриптах (`if minigrep -q ...`). Проверяйте через `echo $?` и интеграционные тесты.
7. **Забыли сбросить `BufWriter`.** Последние строки вывода могут потеряться. Сбрасывайте в конце и проверяйте ошибку.
8. **Коммитите `target/`, `big.txt` или вывод бенчмарка.** Проверяйте `git status` перед каждым коммитом. `/target` уже есть в `.gitignore`.
9. **Верите бенчмарку в режиме debug.** Всегда используйте `--release` или `cargo bench`.
10. **Меняете много вещей до измерения.** Меняйте одну вещь на коммит.

## Вопросы для самопроверки

1. Почему функция сопоставления объявлена как `fn search<'a>(pattern: &str, contents: &'a str, ...) -> Vec<Match<'a>>`?

<details>
<summary>Ответ</summary>

Она возвращает ссылки в `contents`, а не в `pattern`. Время жизни `'a` говорит, что результат действителен, пока действителен `contents`. Без него компилятор не может знать, из какого аргумента заимствован результат.

</details>

2. Почему `run` принимает параметр-writer, а не вызывает `println!`?

<details>
<summary>Ответ</summary>

Чтобы тесты могли передать буфер в памяти (`Vec<u8>`) и проверить вывод, и чтобы одна и та же функция могла писать в stdout, в файл или куда угодно ещё.

</details>

3. Каковы три статуса завершения `minigrep` и почему они важны?

<details>
<summary>Ответ</summary>

`0` (что-то выбрано и ничего не сломалось), `1` (ничего не выбрано), `2` (ошибка). Скрипты и другие программы используют статус, чтобы решить, что делать дальше, например `if minigrep ERROR log.txt; then ...`.

</details>

4. Зачем интеграционный тест использует `env!("CARGO_BIN_EXE_minigrep")`?

<details>
<summary>Ответ</summary>

Cargo собирает бинарник до запуска интеграционных тестов и кладёт его путь в эту переменную времени компиляции, поэтому тест запускает настоящую программу точно так, как это сделал бы пользователь.

</details>

5. Почему печать миллиона строк была медленной и как это исправили?

<details>
<summary>Ответ</summary>

Стандартный вывод буферизуется построчно, поэтому каждая строка вызывала отдельный системный вызов. Обёртка в `BufWriter` накапливает вывод в буфере и записывает его большими кусками, что сделало программу более чем в 16 раз быстрее по измерению автора.

</details>

6. Почему переменную окружения читают в `main`, а не в библиотеке?

<details>
<summary>Ответ</summary>

Чтение окружения — побочный эффект, зависящий от внешнего мира. Если оставить его в `main`, библиотека остаётся обычной функцией своих входных данных, которую легко и надёжно тестировать.

</details>

7. Почему изменение скорости должно быть отдельным коммитом с числами в сообщении?

<details>
<summary>Ответ</summary>

Он документирует доказательство и причину и позволяет легко найти или откатить изменение позже ([Урок 05.12](12-benchmarking-basics.md)).

</details>

8. Коллега говорит: «Я добавил потоки, значит, должно быть быстрее». О чём вы спросите?

<details>
<summary>Ответ</summary>

«Что вы измерили?» Потоки стоят времени на запуск и координацию. Измерьте через `hyperfine` или `criterion` на реалистичных данных, с потоками и без, в режиме release, и сравните.

</details>

## Итоги

- Хороший инструмент состоит из тонкого бинарника и библиотеки с логикой, чтобы логику можно было тестировать без терминала.
- Письменный контракт (использование, форматы вывода, ошибки, статусы завершения) превращает «работает» в проверки, которые можно запустить.
- TDD, модульные тесты, интеграционные тесты с настоящим бинарником и doc-тесты защищают от разных видов ошибок.
- Времена жизни позволяют `search` возвращать заимствованные строки без копирования.
- Ошибки идут в stderr, результаты — в stdout, а статус завершения сообщает скриптам, что произошло.
- Сначала измеряйте: `criterion` для функций, `hyperfine` для всей программы. Настоящая медлительность здесь была не в поиске, а в выводе, и `BufWriter` её исправил.
- Один коммит на веху, один коммит на оптимизацию с числами, ветка для каждого эксперимента, тег для каждого релиза.
