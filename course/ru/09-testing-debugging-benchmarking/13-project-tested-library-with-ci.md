## Новые слова

| Слово | Значение |
|---|---|
| **страховочная сетка** (safety net) | Все автоматические проверки вокруг фрагмента кода (тесты, свойства, снапшоты, фаззинг, CI), которые ловят ошибку, когда кто-то его меняет. |
| **веха** (milestone) | Один шаг проекта со своей целью и своей проверкой «Готово, когда». |
| **каноническая форма** (canonical form) | Единственный стандартный способ записать значение, например `1h30m`, а не `90m` для той же длительности. |
| **публичный API** (Application Programming Interface, программный интерфейс) | Функции и типы крейта, которыми может пользоваться другой код (`pub`). Интеграционные и документационные тесты используют только их. |
| **регрессионный тест** (regression test) | Тест, добавленный после ошибки, с входом, который её вызвал, чтобы ошибка не вернулась незамеченной. |
| **UTF-8** (Unicode Transformation Format, 8-bit) | Способ, которым Rust хранит текст в виде байтов. `&str` всегда является корректным UTF-8. |
| **README** | Первый файл, который читатель открывает в проекте: что это и как запустить. |

## Проект

### Что вы создадите

Небольшой библиотечный крейт `p09-durparse`, который читает и записывает **длительности** в компактном текстовом виде — виде, принятом в файлах конфигурации и параметрах командной строки:

```text
1h30m      →  one hour and thirty minutes
2d         →  two days
1s500ms    →  one and a half seconds
```

Функциональность намеренно мала. Смысл проекта не в парсере, а в **страховочной сетке** вокруг него. Когда вы закончите, посторонний человек сможет изменить код, и сетка скажет ему, не сломал ли он что-нибудь.

### Контракт

Библиотека предоставляет ровно такой публичный API (имена важны, потому что тесты в этом уроке их используют):

```rust
use std::time::Duration;

pub fn parse_duration(input: &str) -> Result<Duration, ParseError>;
pub fn format_duration(duration: Duration) -> String;
pub fn render_error(input: &str, error: &ParseError) -> String;

pub struct ParseError {
    pub kind: ErrorKind,
    pub position: usize, // byte index in the input
}

pub enum ErrorKind {
    Empty,
    UnexpectedChar(char),
    MissingNumber,
    MissingUnit,
    UnknownUnit(String),
    UnitOrder,
    Overflow,
}
```

`ParseError` и `ErrorKind` выводят `Debug`, `Clone`, `PartialEq` и `Eq`. `ParseError` реализует `std::fmt::Display` и `std::error::Error`.

**Формат.** Длительность — это одна или несколько *частей*, записанных подряд, без пробелов: *число* (одна или несколько десятичных цифр, без знака, без десятичной точки), за которым идёт *единица*. Единицы записываются строчными: `d` (день, 24 часа), `h` (час), `m` (минута), `s` (секунда) и `ms` (миллисекунда). Единицы должны идти **от большей к меньшей, каждая не более одного раза**. У числа могут быть ведущие нули (`007s` — это 7 секунд), и числа больше 59 разрешены (`90m` — это 90 минут). Значение — сумма частей.

**`parse_duration`** возвращает сумму как `Duration` с точностью до миллисекунды или первую найденную ошибку при просмотре слева направо. Поля `kind` и `position` ошибки подчиняются таким правилам:

| Вид | Когда | `position` |
|---|---|---|
| `Empty` | вход равен `""` | `0` |
| `MissingNumber` | буква там, где должно начинаться число | индекс этой буквы |
| `UnexpectedChar(c)` | любой другой символ там, где должно начинаться число (пробел, `-`, не-ASCII буква: ASCII, American Standard Code for Information Interchange, американский стандартный код для обмена информацией, — базовый набор из 128 символов с английскими буквами и цифрами…) | индекс `c` |
| `MissingUnit` | цифры, за которыми не следует ASCII-буква (конец текста или другой символ) | индекс сразу после цифр |
| `UnknownUnit(text)` | буквы после цифр — не одна из пяти единиц; `text` — все эти буквы | индекс первой буквы |
| `UnitOrder` | единица не меньше предыдущей (включая повторённую единицу) | индекс первой буквы единицы |
| `Overflow` | число не помещается в `u64` или сумма в миллисекундах не помещается в `u64` | индекс первой цифры части |

**Примеры (ваши тесты должны содержать по меньшей мере их):**

| Вход | Результат `parse_duration` | Затем `format_duration` даёт |
|---|---|---|
| `"90s"` | `Ok(90 s)` | `"1m30s"` |
| `"5m"` | `Ok(5 min)` | `"5m"` |
| `"250ms"` | `Ok(250 ms)` | `"250ms"` |
| `"0s"` | `Ok(0)` | `"0s"` |
| `"1h30m"` | `Ok(5400 s)` | `"1h30m"` |
| `"1d2h3m4s5ms"` | `Ok(93 784 005 ms)` | `"1d2h3m4s5ms"` |
| `"90m"` | `Ok(5400 s)` | `"1h30m"` |
| `"007s"` | `Ok(7 s)` | `"7s"` |
| `"18446744073709551615ms"` | `Ok(u64::MAX ms)` | `"213503982334d14h25m51s615ms"` |
| `""` | `Err(Empty, 0)` | |
| `"90"` | `Err(MissingUnit, 2)` | |
| `"h"` | `Err(MissingNumber, 0)` | |
| `"5x"` | `Err(UnknownUnit("x"), 1)` | |
| `"1H"` | `Err(UnknownUnit("H"), 1)` | |
| `"1h-5m"` | `Err(UnexpectedChar('-'), 2)` | |
| `" 1h"` | `Err(UnexpectedChar(' '), 0)` | |
| `"1.5h"` | `Err(MissingUnit, 1)` | |
| `"30m1h"` | `Err(UnitOrder, 4)` | |
| `"1h1h"` | `Err(UnitOrder, 3)` | |
| `"99999999999999999999s"` | `Err(Overflow, 0)` | |
| `"18446744073709551615d"` | `Err(Overflow, 0)` | |

**`format_duration`** записывает *каноническую* запись: части с ненулевым количеством, от большей к меньшей, причём каждая единица хранит остаток (поэтому `90s` становится `1m30s`, а не `90s`). Нулевая длительность — это `"0s"`. Всё, что меньше миллисекунды, отбрасывается (`1500 µs` — это `"1ms"`). Для `Duration` из целого числа миллисекунд `parse_duration(&format_duration(d))` должна вернуть `d`.

**`render_error`** возвращает сообщение для людей такого вида (формулировка первой строки ваша; строка с кареткой — нет):

```text
error: unknown unit `x` at position 1
  5x
   ^
```

Вторая строка — вход с отступом в два пробела; в третьей строке два пробела плюс ещё `position` пробелов, затем `^`.

**Правила качества для всего проекта:** никаких `unwrap()` и `expect()` для пользовательского ввода в `src/` (код никогда не должен паниковать, каким бы ни был вход), `cargo fmt --check` и `cargo clippy --all-targets -- -D warnings` чисты, у каждой публичной функции есть doc-комментарий и есть короткий `README.md`.

#### M1 — Первые тесты: красный, затем зелёный

**Цель:** `parse_duration` обрабатывает **одну часть** (`90s`, `5m`, `250ms`, `0s`).

**Указания:** работайте как в Уроке 09.6. Сначала напишите в комментарии *список* тестов. Затем напишите один тест, увидьте, что он падает по верной причине (сначала `todo!()`, потом неверный ответ), пройдите его простейшим кодом и повторяйте. Определите `ParseError` и `ErrorKind` сейчас (контракт их перечисляет), но на этом этапе возвращайте только случаи `Ok`. Используйте `Duration::from_millis` и работайте в миллисекундах как `u64`.

<details>
<summary>Подсказка</summary>

Пока не пишите хитрый цикл. Первая проходящая версия может обрабатывать только цифры и единицу `s`. Следующий тест (`5m`) потребует `match` по единице. Тест для `250ms` потребует прочитать две буквы. Каждый тест должен вынуждать написать одну новую строку кода.

</details>

**Готово, когда:** вы видели, как каждый новый тест падал, прежде чем вы его прошли, и:

```bash
cargo test
```

```text
test result: ok. 4 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

(не менее 4 тестов, по одному на каждую из первых четырёх строк таблицы примеров). Коммит: `parse a single part`.

#### M2 — Полный парсер, ошибки, три вида тестов

**Цель:** `parse_duration` следует контракту целиком.

**Указания:**

1. Добавьте остальной парсер: несколько частей, правило порядка единиц, все виды ошибок и проверяемую арифметику. Используйте `u64::checked_mul` и `checked_add`, никогда не обычные `*` и `+` для чисел, пришедших из входа (Урок 02.2: отладочная сборка паникует при переполнении, релизная молча «заворачивается», и то и другое здесь — ошибки).
2. Поместите примеры из таблицы в **табличный модульный тест** в `src/lib.rs` (цикл по парам `(input, expected)` с понятным сообщением проверки, содержащим вход).
3. Добавьте **интеграционный тест** в `tests/public_api.rs`, использующий только публичный API: разберите значение, выведите ошибку через `to_string()`, сравните `error.kind`.
4. Добавьте **документационный тест**: комментарий `//!` в начале `src/lib.rs` с примером `parse_duration("1h30m")`.
5. Напишите `impl Display for ParseError` и `impl std::error::Error for ParseError`. Сообщение должно содержать позицию.

<details>
<summary>Подсказка</summary>

Проще всего сканер с индексом: `pos` движется по байтам (`input.as_bytes()`); сначала `while` по ASCII-цифрам, затем `while` по ASCII-буквам. Работайте с байтовым индексом, потому что контракт говорит о байтовых позициях. Не забудьте вызвать `parse::<u64>()` для цифр и превратить её ошибку в `Overflow` (строка цифр может провалиться только из-за слишком большого значения, потому что вы проверили, что все символы — цифры). Храните `last_unit: Option<Unit>` и сравнивайте единицы через выведенный `PartialOrd` (самая большая единица первой в `enum`).

</details>

**Готово, когда:**

```bash
cargo test
cargo clippy --all-targets -- -D warnings
cargo fmt --check
```

```text
     Running unittests src/lib.rs (...)
test result: ok. N passed; 0 failed; ...
     Running tests/public_api.rs (...)
test result: ok. 2 passed; 0 failed; ...
   Doc-tests p09_durparse
test result: ok. 1 passed; 0 failed; ...
```

Вы видите три блока результатов (модульные, интеграционные, документационные), clippy и fmt ничего не печатают, и каждая строка таблицы примеров есть в каком-либо тесте. Коммит: `full parser with errors`.

#### M3 — Форматирование и тесты свойств

**Цель:** `format_duration` и три свойства.

**Указания:** реализуйте `format_duration` (снова TDD: сначала напишите тестами четыре канонических примера). Затем создайте `tests/properties.rs` с тремя свойствами `proptest`:

1. **Круговое преобразование:** для любого `u64` числа миллисекунд `ms` `parse_duration(&format_duration(Duration::from_millis(ms)))` равно `Ok(Duration::from_millis(ms))`.
2. **Без паники:** для любого текста из стратегии `"\\PC*"` (любые печатаемые символы) `parse_duration` возвращает результат без паники (результат может быть ошибкой).
3. **Алфавит:** `format_duration(Duration::from_millis(ms))` содержит только ASCII-цифры и буквы `d`, `h`, `m`, `s`.

<details>
<summary>Подсказка</summary>

Форма теста свойства:

```rust
use proptest::prelude::*;

proptest! {
    #[test]
    fn name_of_the_property(ms in any::<u64>()) {
        // arrange, then prop_assert_eq!(left, right);
    }
}
```

`format_duration` получает `Duration`, у которого `as_millis()` возвращает `u128`: число дней может быть больше `u64` (см. последнюю строку таблицы), поэтому арифметику там делайте в `u128`. Чтобы увидеть сжатие (shrinking), намеренно сломайте функцию (например, отбросьте часть `ms`) и прочитайте минимальный провальный пример, который напечатает `proptest`, затем исправьте.

</details>

**Готово, когда:**

```bash
cargo test --test properties
```

```text
test format_then_parse_round_trips ... ok
test parse_never_panics ... ok
test formatted_text_has_only_digits_and_units ... ok
test result: ok. 3 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.02s
```

(имена могут отличаться). Также: вы один раз намеренно сломали форматирование, увидели сжатый провальный вход вроде `ms = 1` и восстановили код. Коммит: `format_duration and property tests`.

#### M4 — Снапшот сообщений об ошибках

**Цель:** `render_error` и один снапшот-тест.

**Указания:** напишите `render_error` как описано в контракте. Затем создайте `tests/snapshots.rs`: для списка плохих входов (`""`, `"90"`, `"h"`, `"5x"`, `"1h-5m"`, `"30m1h"`, `"1h1h"`, `"99999999999999999999s"`) соберите отрисованные сообщения в одну `String` (пустая строка между ними) и сравните её через `insta::assert_snapshot!`. Первый запуск падает и записывает файл `.snap.new`: прочитайте его, убедитесь, что сообщения такие, как вы хотите, затем примите.

<details>
<summary>Подсказка</summary>

```bash

cargo insta review              # or: cargo insta accept
cargo test --test snapshots     # passes
```

Откройте `tests/snapshots/snapshots__*.snap` и прочитайте его как человек: стоит ли каретка под нужным символом в каждом случае? Закоммитьте файл `.snap`. Затем измените одно сообщение (например, «unknown unit» на «bad unit»), посмотрите, как тест падает с разницей, и верните.

</details>

**Готово, когда:**

```bash
cargo test --test snapshots
git status --short
```

```text
test error_messages_with_carets ... ok
test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

и файлов, оканчивающихся на `.snap.new`, нет (`git status --short` один раз показывает файл `.snap` как новый). Коммит: `snapshot test of error messages`.

#### M5 — Фаззинг

**Цель:** цель фаззинга, которая работает не менее 60 секунд без находки падения.

**Указания:** следуйте Уроку 09.8. Выполните `cargo fuzz init` в папке проекта. Цель превращает байты в текст (если это не корректный UTF-8, возвращается досрочно), вызывает `parse_duration` и, **если вызов успешен**, проверяет свойство «всё, что мы приняли, переживает запись и чтение»: `parse_duration(&format_duration(d)) == Ok(d)`. Запустите: `cargo +nightly fuzz run fuzz_target_1 -- -max_total_time=60`.

Если фаззер находит падение, это *победа*: воспроизведите его, минимизируйте (`cargo +nightly fuzz tmin`), напишите регрессионный модульный тест с падающим входом, исправьте библиотеку и запустите снова.

<details>
<summary>Подсказка</summary>

```rust
#![no_main]

use libfuzzer_sys::fuzz_target;

fuzz_target!(|data: &[u8]| {
    let Ok(text) = std::str::from_utf8(data) else {
        return;
    };
    // call parse_duration(text); when it is Ok(duration), assert the round trip
});
```

Если ваш парсер использовал `unwrap()`, обычные `+` или `*` либо срезы вроде `&input[a..b]` на позиции, не являющейся границей символа, здесь это проявится. Регрессионные тесты кладите в `src/lib.rs` или `tests/`, а не в игнорируемую папку `fuzz/artifacts`.

</details>

**Готово, когда:**

```bash
cargo +nightly fuzz run fuzz_target_1 -- -max_total_time=60
```

```text
...
#32935622	DONE   cov: ...
Done 32935622 runs in 61 second(s)
```

В выводе не должно быть `Failing input` (числа будут другими). У каждого найденного ранее падения есть регрессионный тест. Коммит: `fuzz target` (папка `fuzz/`, но не её `corpus`, `artifacts` и `target`).

#### M6 — Цели по покрытию и мутациям

**Цель:** не менее **95% покрытия строк** `src/lib.rs` и **ни одного пропущенного мутанта**.

**Указания:** измерьте через `cargo llvm-cov --summary-only`. Посмотрите непокрытые строки через `cargo llvm-cov --text` и решите: достижима ли строка? Если да, напишите тест, который до неё доходит. Затем запустите `cargo mutants`. Для каждого `MISSED`-мутанта прочитайте изменённую строку, спросите «какой тест должен был упасть?» и добавьте этот тест. Тайм-аут или «unviable» мутант допустимы (см. Урок 09.7). Покрытие — карта того, что было *выполнено*; мутанты показывают, что на самом деле *проверяется*.

<details>
<summary>Подсказка</summary>

Типичные выжившие в таком парсере: `>=`, которое могло бы быть `>` (проверка порядка единиц: есть ли тест с **повторённой** единицей, вроде `1h1h`?); `+`, заменённый на `-` или `*` в сумме (проверяете ли вы **несколько** частей и сумму, не равную произведению?); позиция со смещением на единицу (проверяют ли ваши тесты `position`, а не только `kind`?); обработка `0` в середине форматирования (`1h5s`: есть ли `0m`, которое нужно пропустить?); сообщения `Display` (их проверяет только снапшот, поэтому сохраните его).

</details>

**Готово, когда:**

```bash
cargo llvm-cov --summary-only
cargo mutants
```

```text
TOTAL     ...     98.60%     ...        (the Lines "Cover" column must be 95% or more)
```

```text
Found 48 mutants to test
ok       Unmutated baseline in 8s build + 1s test
48 mutants tested in 88s: 44 caught, 2 unviable, 2 timeouts
```

(Пример: у вас будет другое число мутантов, но в выводе не должно быть `missed`.) Коммит: `tests for surviving mutants`.

#### M7 — Один честный бенчмарк

**Цель:** бенчмарк `criterion` для `parse_duration` и `format_duration` на одном и том же входе с сохранённой базовой линией.

**Указания:** создайте `benches/parse.rs` и запись `[[bench]]` с `harness = false`. Применяйте `black_box` ко входу. Берите самый длинный реалистичный вход (`"1d2h3m4s5ms"`), а `Duration` для бенчмарка форматирования стройте вне цикла. Следуйте контрольному списку Урока 09.11: релизная сборка (`cargo bench` делает её), тихий компьютер, тест корректности рядом (он у вас есть), а широкий интервал означает «повторите». Сохраните базовую линию: `cargo bench --bench parse -- --save-baseline main`.

<details>
<summary>Подсказка</summary>

```rust
c.bench_function("parse 1d2h3m4s5ms", |b| {
    b.iter(|| parse_duration(black_box("1d2h3m4s5ms")))
});
```

На ноутбуке Apple M4 разбор занимает около 19 наносекунд, а форматирование около 200 наносекунд (форматировщик выделяет строки). Если ваш результат отличается в тысячу раз, проверьте, что вы не измеряли отладочную сборку или то, что компилятор убрал.

</details>

**Готово, когда:**

```bash
cargo bench --bench parse -- --warm-up-time 1 --measurement-time 2
```

```text
parse 1d2h3m4s5ms       time:   [18.564 ns 19.009 ns 19.488 ns]
format 1d2h3m4s5ms      time:   [201.97 ns 204.27 ns 207.25 ns]
```

(Ваши числа будут другими.) Базовая линия сохранена, а `cargo bench --no-run` собирается без ошибок. Коммит: `benchmark`.

#### M8 — CI и README

**Цель:** рабочий процесс, который при каждой отправке запускает всю сетку, и README, объясняющий, как её запускать.

**Указания:** создайте `.github/workflows/ci.yml` в репозитории (см. Урок 09.12): checkout, тулчейн с `rustfmt` и `clippy`, `Swatinem/rust-cache@v2`, затем `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test --all-targets` и `cargo test --doc`. Добавьте задание, которое собирает бенчмарки (`cargo bench --no-run`). Добавьте **второй рабочий процесс** `fuzz.yml`, который раз в неделю запускает цель фаззинга на пять минут. Проверьте оба через `actionlint`. Затем выполните четыре команды «контроля качества» в чистом контейнере из Урока 09.12 (`rust:1.100`), чтобы доказать, что проект не зависит от вашего Mac. Допишите раздел «Development» в `README.md` с командами для каждого инструмента: тесты, свойства, снапшоты (`cargo insta review`), фаззинг, покрытие, мутанты и бенчмарки.

Если репозитория на GitHub ещё нет, рабочий процесс запустить нельзя; не переживайте. Запуск в контейнере — ваше доказательство, а файл проверяет `actionlint`.

Либо задайте на уровне задания `defaults: run: working-directory: code/p09-durparse`, либо добавьте `working-directory:` к каждому шагу `run`. Действию `Swatinem/rust-cache` в блоке `with:` тоже нужен `workspaces: code/p09-durparse`. Запускайте `actionlint` из корня репозитория.

</details>

Снапшот-тестам нужны `tests/snapshots/*.snap` в Git, и они входят в подключённую папку.) Коммит: `CI workflows and README`, и поставьте тег Git: `git tag p09-durparse-v0.1.0`.

### Дополнительные цели

1. **Программа командной строки.** Добавьте `src/bin/dur.rs`, которая читает один аргумент (`dur 1h30m` печатает `5400` секунд, `dur 5x` печатает отрисованную ошибку в стандартный поток ошибок и завершается с кодом 2), и протестируйте её сквозным тестом с `assert_cmd`, как в Уроке 09.2.
2. **Более быстрое форматирование.** `format_duration` выделяет `String` для каждой части через `format!`. Напишите версию, которая дописывает напрямую в одну `String` (`write!` с `std::fmt::Write` или `push_str` и вспомогательная функция числа в текст). Сохраните старый бенчмарк, сравните с `--baseline main` и укажите число в сообщении коммита. Проходят ли по-прежнему тесты свойств?
3. **Пробелы и заглавные буквы.** Добавьте вторую функцию `parse_duration_lenient`, принимающую пробелы между частями и заглавные буквы (`"1H 30M"`). Строгую не меняйте. Добавьте её тесты, свойство («мягкий разбор строгого текста даёт тот же ответ») и цель фаззинга.
4. **Дроби.** Поддержите `1.5h`. Это меняет контракт (`"1.5h"` теперь допустимо, и строка примера меняется): обновите все тесты, снапшот и свойства. Заметьте, какие тесты подсказывают, что менять. Это сетка делает свою работу.
5. **Трассировка в логах.** Добавьте события `tracing` уровня `DEBUG` для каждой разобранной части (Урок 09.10) и тест, проверяющий, что по умолчанию библиотека ничего не выводит.
6. **Задание мутационного тестирования.** Добавьте еженедельное задание CI, которое запускает `cargo mutants` и загружает `mutants.out` как артефакт, если есть пропущенные мутанты.

## Частые ошибки

**1. Сначала код, «тесты потом».** Тогда тесты описывают существующий код, вместе с его ошибками. Делайте M1 и M2 «тест вперёд».

**2. Тест свойства, повторяющий код.** Если свойство вычисляет ответ тем же алгоритмом, что и функция, оно не может с ней разойтись. Используйте *другую* идею: круговое преобразование, инварианты, простую модель.

**3. Снапшоты, принятые без чтения.** `cargo insta accept` делает истиной любой вывод. Прочитайте файл `.snap` как пользователь.

**4. Погоня за 100% покрытия.** Цель — 95% и мутанты. Тест без проверок повышает покрытие и ничего не проверяет; мутанты это обнажают.

**5. `unwrap()` в библиотеке «потому что выше ввод проверен».** Фаззер найдёт случай, о котором вы не подумали. Используйте `get`, `?` и `ok_or`.

**6. Рабочие процессы не в той папке.** GitHub читает только `.github/workflows/` в **корне** репозитория. Рабочий процесс внутри `code/p09-durparse/.github/` не запустится никогда.

## Вопросы для самопроверки

1. В каком порядке выполнять вехи, если придётся остановиться после M4? Какие части сетки у вас будут?

<details>
<summary>Ответ</summary>

В заданном порядке. После M4 у вас есть модульные, интеграционные и документационные тесты, свойства и снапшот. Не будет фаззинга, проверки покрытия и мутантов, бенчмарка и CI. Правило «самое дешёвое и ценное первым»: тесты раньше инструментов, которые оценивают тесты.

</details>

2. Покрытие 100%, но один мутант пропущен. О чём это говорит?

<details>
<summary>Ответ</summary>

Каждая строка выполняется во время тестов, но тесты недостаточно строго проверяют результат этой строки: какой-то проверки не хватает или она слишком слаба. Покрытие измеряет то, что выполнялось, мутанты — то, что проверяется.

</details>

3. Почему цель фаззинга досрочно возвращается, когда байты не являются корректным UTF-8?

<details>
<summary>Ответ</summary>

`parse_duration` принимает `&str`, а он всегда корректный UTF-8. Некорректные байты находятся вне контракта функции, поэтому проверять нечего.

</details>

4. Почему бенчмарки в CI только собираются, но не запускаются?

<details>
<summary>Ответ</summary>

Числа на общем раннере — шум. Сборка в CI не даёт коду гнить; скорость оценивают на тихом компьютере с базовой линией.

</details>

## Итоги

- Страховочная сетка строится слоями: тесты на примерах, свойства, снапшоты, фаззинг, затем инструменты, оценивающие тесты (покрытие и мутанты), бенчмарк и CI.
- Основу делайте «тест вперёд», добавьте тест свойств с круговым преобразованием и «никогда не паникует», снимайте снапшоты с читаемого людьми вывода и превращайте каждую находку фаззера в регрессионный тест.
- Цели делают работу конечной: 95% покрытия и ни одного пропущенного мутанта; «готово» значит, что команды печатают ожидаемый результат.
- Докажите, что проект не зависит от вашей машины: запустите «контроль качества» в чистом контейнере и проверьте рабочий процесс через `actionlint`.
