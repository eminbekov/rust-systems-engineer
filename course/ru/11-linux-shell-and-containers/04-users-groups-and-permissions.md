## Новые слова

| Слово | Значение |
|---|---|
| **пользователь** (user) | Учётная запись, которая владеет файлами и запускает программы. Каждый процесс работает ровно от одного пользователя. |
| **UID** (User ID, идентификатор пользователя) | Число, которое идентифицирует пользователя. Ядро работает с числами; имена нужны только людям. |
| **группа** (group) | Именованный набор пользователей. У пользователя есть одна *основная* группа и могут быть дополнительные. |
| **GID** (Group ID, идентификатор группы) | Число, которое идентифицирует группу. |
| **root** | Администратор, пользователь с UID 0. Ядро не проверяет права доступа для root. |
| **sudo** | Программа, которая выполняет одну команду от имени другого пользователя, обычно root, если вам это разрешено. |
| **биты прав** (permission bits) | Девять переключателей у каждого файла: чтение, запись и выполнение — для владельца, группы и всех остальных. |
| **восьмеричный режим** (octal mode) | Биты прав, записанные тремя цифрами, например `755` или `640`. |
| **umask** | Маска, которая убирает биты прав у каждого нового файла и каталога. |
| **sticky-бит** (sticky bit) | У каталога: удалять файл может только его владелец, даже если другие могут писать в каталог. |
| **setuid / setgid** | Бит, из-за которого программа запускается от имени *владельца* / *группы* файла; у каталога `setgid` заставляет новые файлы наследовать группу каталога. |
| **наименьшие привилегии** (least privilege) | Правило безопасности: давать каждому пользователю и программе только нужные права и не больше. |
| **системный пользователь** (system user) | Пользователь без входа в систему, созданный для запуска одной службы. Его UID меньше 1000. |

## 1. Пользователи и группы

Каждый процесс работает **от имени пользователя**, а каждый файл принадлежит **одному пользователю и одной группе**. Спросите, кто вы:

```bash
whoami
id
id root
```

```text
student
uid=1000(student) gid=1000(student) groups=1000(student),27(sudo)
uid=0(root) gid=0(root) groups=0(root)
```

**Что происходит:**

1. `whoami` печатает имя вашего пользователя.
2. `id` печатает ваши числа. `uid=1000`: ваш идентификатор пользователя. `gid=1000`: ваша основная группа. `groups=...`: все группы; `27(sudo)` означает, что вы можете использовать `sudo`. (В ВМ Lima ваш UID совпадает с UID вашего пользователя на Mac, часто 501, а группы немного другие.)
3. `id root` показывает администратора: **UID 0**.

Ядро знает только числа. Имена хранятся в обычных текстовых файлах:

```bash
head -n 3 /etc/passwd
grep '^student' /etc/passwd
getent group sudo
```

```text
root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
bin:x:2:2:bin:/bin:/usr/sbin/nologin
student:x:1000:1000::/home/student:/bin/bash
sudo:x:27:student
```

Каждая строка `/etc/passwd` состоит из семи полей, разделённых двоеточиями:

| Поле | Пример | Значение |
|---|---|---|
| 1 | `student` | имя для входа |
| 2 | `x` | пароля здесь нет (он в `/etc/shadow`) |
| 3 | `1000` | UID |
| 4 | `1000` | GID основной группы |
| 5 | (пусто) | комментарий, часто полное имя |
| 6 | `/home/student` | домашний каталог |
| 7 | `/bin/bash` | оболочка входа; `/usr/sbin/nologin` означает «интерактивный вход запрещён» |

`/etc/group` перечисляет группы так же (`name:x:GID:members`). `getent` («get entries», получить записи) обращается к базе пользователей системы, в которой могут быть
и учётные записи, которых нет в файле (например, корпоративный каталог). Хешированные пароли лежат в `/etc/shadow`, который может читать только `root`:

```bash
cat /etc/shadow
ls -l /etc/passwd /etc/shadow
```

```text
cat: /etc/shadow: Permission denied
-rw-r--r-- 1 root root   884 Nov 18 06:27 /etc/passwd
-rw-r----- 1 root shadow 503 Nov 18 06:27 /etc/shadow
```

**Что происходит:** `/etc/passwd` должен читаться всеми, потому что программы ищут в нём имена пользователей. Секреты вынесли в `/etc/shadow` с
режимом `rw-r-----`: root может читать и писать, группа `shadow` может читать, у остальных нет ничего. Запомните эту схему: **открытые и секретные данные — в разных файлах с разными правами**.

У номеров пользователей есть соглашения: **0** — root, **от 1 до 999** — *системные пользователи* (для служб), **1000 и выше** — обычные люди.

## 2. `root` и `sudo`

`root` игнорирует права доступа: он может читать, менять и удалять всё. Поэтому под root не работают. Вы работаете как обычный пользователь и просите
права root только для одной команды, которой они нужны:

```bash
whoami
sudo whoami
sudo -u nobody whoami
```

```text
student
root
nobody
```

**Что происходит:**

1. `sudo command` выполняет `command` от имени root, проверив, что вам это разрешено (файл `/etc/sudoers`). На настоящем сервере он спросит **ваш** пароль; в ВМ Lima — не спросит (Урок 11.1).
2. `sudo -u nobody whoami` выполняет команду от имени другого пользователя (`-u`), здесь `nobody` — пользователя без каких-либо прав.
3. Чтобы изменить правила, используйте `sudo visudo`, который проверяет синтаксис перед сохранением. Испорченный файл sudoers может закрыть вам доступ.

> 💡 **Совет:** в Ubuntu 26.04 команда `sudo` — это *sudo-rs*, переписанный на Rust `sudo`. Проверьте: `sudo --version`.
> Команды этого урока работают так же.

> 🔒 **Безопасность:** применяйте правило **наименьших привилегий**. Не входите как root, не запускайте службу от root, не выполняйте через `sudo` команду, которую не понимаете.
> Ошибка в программе, работающей от root, может уничтожить всю машину; та же ошибка в программе с маленьким собственным пользователем ограничена файлами этого пользователя.

## 3. Создание пользователей и групп

Управление учётными записями требует прав root, поэтому эти команды начинаются с `sudo`. Создадим двух людей и группу:

```bash
sudo useradd -m -s /bin/bash alice
sudo useradd -m -s /bin/bash bob
sudo groupadd team
sudo usermod -aG team alice
sudo usermod -aG team bob
id alice
getent group team
```

```text
uid=1001(alice) gid=1001(alice) groups=1001(alice),1003(team)
team:x:1003:alice,bob
```

**Что происходит:**

1. `useradd -m -s /bin/bash alice` создаёт пользователя с домашним каталогом (`-m`, make home) и оболочкой входа `bash` (`-s`). Система берёт следующий свободный UID (здесь 1001) и создаёт также группу с именем `alice`.
2. `groupadd team` создаёт группу.
3. `usermod -aG team alice` добавляет (`-a`, append) alice в дополнительную группу (`-G`) `team`. **Всегда используйте `-a` вместе с `-G`**: без `-a` пользователь будет удалён из всех остальных групп.
4. `id alice` подтверждает результат. (Числа в вашей ВМ могут отличаться.) Пользователь, который уже вошёл в систему, должен войти заново, чтобы увидеть новую группу.

> ⚠️ **Частая ошибка:** `sudo usermod -G team alice` без `-a` заменяет весь список групп. Если alice была в `sudo`, она только что её потеряла.

В Debian и Ubuntu есть также `adduser` — более дружелюбная интерактивная обёртка, которая спрашивает пароль и имя. Низкоуровневая
`useradd` одинакова во всех дистрибутивах и лучше подходит для скриптов.

**Пользователь для службы.** Веб-сервер или ваша программа на Rust не должны работать от вашего имени и тем более от root. Дайте ей **системного пользователя**:

```bash
sudo useradd --system --no-create-home --shell /usr/sbin/nologin heartbeat
id heartbeat
sudo -u heartbeat whoami
```

```text
uid=999(heartbeat) gid=999(heartbeat) groups=999(heartbeat)
heartbeat
```

**Что происходит:** `--system` берёт UID меньше 1000; `--no-create-home` не создаёт домашнюю папку; `--shell /usr/sbin/nologin` означает, что никто не сможет войти под этим пользователем, он может только
запускать свою службу. [Урок 11.6](06-services-with-systemd.md) создаёт именно такого пользователя для службы на Rust. Теперь удалите демонстрационного пользователя:

```bash
sudo userdel heartbeat
```

## 4. Права доступа: файлы и каталоги

`ls -l` показывает в начале строки десять символов: тип и три группы по три бита.

```text
-rwxr-xr-x  1  student  student  ...  name
│└┬┘└┬┘└┬┘     │        │
│ │  │  │      │        └ group
│ │  │  │      └ owner
│ │  │  └ other (everybody else)
│ │  └ group bits
│ └ owner bits
└ type: - file, d directory, l symlink
```

Ядро проверяет правила в таком порядке: если вы **владелец**, решают биты владельца; иначе, если вы в **группе** файла, решают биты группы;
иначе решают биты **остальных** (other). Для файлов и каталогов биты означают разное:

| Бит | У файла | У каталога |
|---|---|---|
| `r` чтение | читать содержимое | просматривать имена внутри |
| `w` запись | менять содержимое | создавать, переименовывать и удалять записи внутри |
| `x` выполнение | запускать как программу | входить в него (`cd`) и обращаться к записям по имени |

Каталоги — самое неожиданное. Попробуйте:

```bash
cd ~
mkdir perm-lab
cd perm-lab
mkdir box
echo secret > box/file.txt
chmod -x box
ls box
ls -l box
cat box/file.txt
```

```text
file.txt
total 0
-????????? ? ? ? ?            ? file.txt
cat: box/file.txt: Permission denied
```

**Что происходит:** без `x` у каталога вы всё ещё можете увидеть *имена* (у вас есть `r`), но не можете получить сведения о записях и не можете открыть файл внутри, хотя сам файл доступен для чтения. Теперь наоборот:

```bash
chmod +x box
chmod -r box
ls box
cat box/file.txt
chmod +r box
```

```text
ls: cannot open directory 'box': Permission denied
secret
```

**Что происходит:** с `x`, но без `r` нельзя просмотреть каталог, зато можно открыть файл, если знать его точное имя. В конце ничего не изменено: `chmod +r box` вернул бит.

### `chmod`: символьная и восьмеричная записи

`chmod` («change mode», изменить режим) имеет две записи. **Символьная** говорит, для кого (`u` владелец, `g` группа, `o` остальные, `a` все), что сделать (`+` добавить, `-` убрать, `=` задать) и какие биты:

```bash
touch notes.txt
ls -l notes.txt
chmod u+x,g-w,o-r notes.txt
ls -l notes.txt
chmod a=r notes.txt
ls -l notes.txt
```

```text
-rw-rw-r-- 1 student student 0 Nov 18 06:50 notes.txt
-rwxr--r-- 1 student student 0 Nov 18 06:50 notes.txt
-r--r--r-- 1 student student 0 Nov 18 06:50 notes.txt
```

(Первая строка показывает, что ваш новый файл доступен для записи группе. Раздел 5 объясняет почему.)

**Восьмеричная** запись пишет каждую группу битов одной цифрой: чтение = 4, запись = 2, выполнение = 1, и они складываются. `rwx` = 4+2+1 = 7, `rw-` = 6, `r-x` = 5, `r--` = 4, `---` = 0.

| Режим | Биты | Типичное применение |
|---|---|---|
| `644` | `rw-r--r--` | обычный файл, доступный всем для чтения |
| `600` | `rw-------` | приватный файл: секреты, ключи SSH (Secure Shell, Урок 11.10), токены |
| `755` | `rwxr-xr-x` | программа или общедоступный каталог |
| `700` | `rwx------` | приватный каталог |
| `640` | `rw-r-----` | владелец пишет, группа читает (как `/etc/shadow`) |

```bash
chmod 755 notes.txt
stat -c '%a %A %n' notes.txt
```

```text
755 -rwxr-xr-x notes.txt
```

**Что происходит:** `stat -c` печатает выбранные поля (`%a` восьмеричный режим, `%A` буквы, `%n` имя).

> ⚠️ **Частая ошибка:** `chmod 777`. Он позволяет любому на машине менять файл и часто используется как попытка «заставить ошибку исчезнуть». Выясните, кому какой доступ нужен, и дайте ровно его.
> Будьте осторожны и с `chmod -R` (рекурсивно): файлам и каталогам нужны разные режимы (`x` у каталогов, у файлов обычно не нужен).

Когда вы встречаете «Permission denied» на глубоком пути, `namei -l` показывает права **каждого каталога по пути** и тот, который вас блокирует:

```bash
mkdir -p a/b
touch a/b/c
chmod 700 a
namei -l ~/perm-lab/a/b/c
```

```text
f: /home/student/perm-lab/a/b/c
drwxr-xr-x root    root    /
drwxr-xr-x root    root    home
drwxr-x--- student student student
drwxrwxr-x student student perm-lab
drwx------ student student a
drwxrwxr-x student student b
-rw-rw-r-- student student c
```

**Что происходит:** каждая строка — одна часть пути с её режимом, владельцем и группой. Все, кроме `student`, останавливаются на `a` (`drwx------`) или на домашнем каталоге. (У вас список выглядит так же, с вашим именем пользователя.)

## 5. Владелец, группа и `umask`

`chown` («change owner», сменить владельца) меняет владельца и группу; `chgrp` меняет только группу. Передать файл другому владельцу может только root:

```bash
sudo chown alice notes.txt
sudo chown alice:team notes.txt
ls -l notes.txt
sudo chown student:student notes.txt
```

```text
-rwxr-xr-x 1 alice team 0 Nov 18 06:50 notes.txt
```

**Что происходит:** `owner:group` задаёт обоих. После последней команды файл снова ваш. `chown -R` делает это для всего дерева.

Новый файл получает режим из запроса программы (обычно `666` для файлов, `777` для каталогов) **минус** **umask**:

```bash
umask
touch u1
umask 077
touch u2
mkdir d2
umask 002
ls -ld u1 u2 d2
```

```text
0002
drwx------ 2 student student 4096 Nov 18 06:50 d2
-rw-rw-r-- 1 student student    0 Nov 18 06:50 u1
-rw------- 1 student student    0 Nov 18 06:50 u2
```

**Что происходит:**

1. `umask` печатает текущую маску: `0002` убирает только бит «запись для остальных», поэтому `666` становится `664` (`rw-rw-r--`). Ubuntu использует `002` для обычных пользователей, потому что у каждого пользователя своя группа; в других системах обычное значение — `022`.
2. После `umask 077` у группы и остальных убирается всё: файлы получают `600`, каталоги `700`.
3. Изменение действует только для текущей оболочки. Последняя команда `umask 002` возвращает всё назад.

> 🔒 **Безопасность:** программа, которая записывает секрет (ключ, токен, файл паролей), должна создавать его **приватным с самого начала**, с режимом `600`.
> Если она сначала записывает, а потом вызывает `chmod`, то на какое-то мгновение другие пользователи могут его прочитать. Раздел 7 показывает, как сделать это в Rust.

## 6. Особые биты и общий каталог

Существуют ещё три бита, они показываются на месте `x`:

| Бит | Восьмеричное | Где | Эффект |
|---|---|---|---|
| sticky `t` | `1000` | каталог | удалять или переименовывать записи может только владелец файла (или root) |
| setgid `s` | `2000` | каталог | новые файлы получают группу каталога |
| setuid `s` | `4000` | файл программы | программа запускается от имени владельца файла |

Вы уже встречали все три:

```bash
ls -ld /tmp
ls -l /usr/bin/passwd
```

```text
drwxrwxrwt 1 root root 4096 Nov 18 06:35 /tmp
-rwsr-xr-x 1 root root 142552 Feb  2  2026 /usr/bin/passwd
```

**Что происходит:** `/tmp` доступен всем для записи, а `t` (sticky) не даёт одному пользователю удалить файлы другого. У `passwd` стоит `s` в битах владельца: когда его запускает любой пользователь, он работает от root, поэтому может менять `/etc/shadow`. Программы с setuid опасны при наличии ошибок, поэтому их очень мало.

**Общий каталог.** Alice и bob работают вместе; никто другой не должен видеть файлы. Создайте каталог с группой `team` и битом `setgid` (`2770`):

```bash
sudo mkdir /srv/team-share
sudo chown root:team /srv/team-share
sudo chmod 2770 /srv/team-share
ls -ld /srv/team-share
sudo -u alice touch /srv/team-share/a.txt
sudo ls -l /srv/team-share
sudo -u bob bash -c 'echo hi >> /srv/team-share/a.txt'
ls /srv/team-share
```

```text
drwxrws--- 2 root team 4096 Nov 18 06:50 /srv/team-share
total 0
-rw-r--r-- 1 alice team 0 Nov 18 06:50 a.txt
bash: line 1: /srv/team-share/a.txt: Permission denied
ls: cannot open directory '/srv/team-share': Permission denied
```

**Что происходит:**

1. `2770` = setgid (`2`) + `rwx` для владельца (`7`), `rwx` для группы (`7`), ничего для остальных (`0`). `ls` показывает `s` в битах группы. Ваш пользователь `student` не владелец и не состоит в `team`, поэтому последний `ls` отклонён: это и есть цель.
2. У файла, созданного alice, группа `team`: это работа бита `setgid`; без него группой была бы собственная группа alice.
3. Но bob не может в него писать: `umask` alice дал файлу `644`, поэтому у группы нет `w`. Каталог общий, а файлы — нет, пока umask создателя этого не разрешит. Попробуйте ещё раз с `umask 002`:

```bash
sudo -u alice bash -c 'umask 002; touch /srv/team-share/b.txt'
sudo -u bob bash -c 'echo hi >> /srv/team-share/b.txt'
sudo cat /srv/team-share/b.txt
```

```text
hi
```

**Что происходит:** `b.txt` получил `664` (`rw-rw-r--`) и группу `team`, поэтому bob может дописывать. Поэтому участники команды обычно задают `umask 002` в настройках своей оболочки.

Уберите всё, что создали в этом уроке (`-r` у `userdel` удаляет и домашний каталог):

```bash
sudo rm -r /srv/team-share
sudo userdel -r alice
sudo userdel -r bob
sudo groupdel team
rm -r ~/perm-lab
```

(Сообщение вроде `userdel: alice mail spool (/var/mail/alice) not found` безобидно: эти пользователи никогда не получали почту.)

## 7. Права доступа из Rust

Откройте вкладку терминала **Mac** (права доступа работают так же и в macOS). Программа, которая хранит секрет, должна создавать файл с нужным режимом **в момент создания**. В системах Unix у Rust для этого есть
`std::os::unix::fs::OpenOptionsExt`:

```bash
cd ~/projects/rust
cargo new code/p11-secretfile
```

Замените `code/p11-secretfile/src/main.rs`:

```rust
use std::fs::OpenOptions;
use std::io::{self, Write};
use std::os::unix::fs::{OpenOptionsExt, PermissionsExt};
use std::path::Path;

/// Creates a NEW file that only the owner can read and write (mode 600).
fn write_secret(path: &Path, text: &str) -> io::Result<()> {
    let mut file = OpenOptions::new()
        .write(true)
        .create_new(true) // fail if the file already exists
        .mode(0o600) // rw------- (the umask can only remove bits)
        .open(path)?;
    file.write_all(text.as_bytes())
}

fn main() -> io::Result<()> {
    let path = Path::new("token.txt");
    write_secret(path, "not-a-real-token\n")?;
    let mode = std::fs::metadata(path)?.permissions().mode();
    println!("created {} with mode {:o}", path.display(), mode & 0o777);
    Ok(())
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn secret_file_is_private_and_not_overwritten() {
        let path = std::env::temp_dir().join(format!("p11-secretfile-{}", std::process::id()));
        write_secret(&path, "x").unwrap();

        let mode = std::fs::metadata(&path).unwrap().permissions().mode();
        assert_eq!(mode & 0o777, 0o600);
        assert!(write_secret(&path, "y").is_err(), "second write must fail");

        std::fs::remove_file(&path).unwrap();
    }
}
```

**Что происходит:**

1. `OpenOptions` описывает, как открыть файл. `.create_new(true)` означает «создай, и завершись ошибкой, если файл уже существует», поэтому программа никогда не перезапишет и не пойдёт по файлу, который заранее подготовил злоумышленник.
2. `.mode(0o600)` задаёт биты прав нового файла в том же системном вызове. Префикс `0o` записывает в Rust восьмеричное число. Umask может только убирать биты, поэтому результат никогда не шире `600`.
3. `mode & 0o777` оставляет девять битов прав и скрывает биты типа файла, которые тоже возвращает `mode()`. `{:o}` печатает в восьмеричном виде.
4. Тест создаёт файл во временном каталоге (с идентификатором процесса в имени), проверяет режим, проверяет, что второй вызов `write_secret` завершается ошибкой, и удаляет файл.

```bash
cargo run -q
ls -l token.txt
cargo run -q
cargo test
```

```text
created token.txt with mode 600
-rw------- 1 student staff 17 Nov 18 11:46 token.txt
Error: Os { code: 17, kind: AlreadyExists, message: "File exists" }
```

(Вывод `cargo test` заканчивается строкой `test result: ok. 1 passed`. `ls -l` показывает имена вашего пользователя и группы.) Второй запуск завершается ошибкой намеренно: файл уже существовал. Удалите `token.txt`, когда закончите. [Урок 10.8](../10-security-fundamentals/08-secrets-management.md) объясняет, как управлять секретами; здесь вы увидели часть про права доступа.

## Частые ошибки

1. **`chmod 777`, чтобы исправить «Permission denied».** Теперь любой может менять файл. *Исправление:* найдите настоящую причину через `ls -l` и `namei -l`; дайте нужный доступ только одному пользователю или группе.
2. **`usermod -G` без `-a`.** Пользователь теряет все остальные группы. *Исправление:* `usermod -aG group user`.
3. **Забыли `x` у каталога.** `cd: Permission denied`, или существующие файлы не открываются. *Исправление:* каталогам нужен `x`; для каталогов используйте `chmod 755` / `750` / `700`, а не `644`.
4. **Новая группа не действует.** Вы добавили себя в группу, но по-прежнему получаете «Permission denied». *Исправление:* выйдите и войдите заново (или снова войдите в ВМ); работающая оболочка хранит старый список групп.
5. **Служба работает от root.** Одна ошибка отдаёт злоумышленнику всю машину. *Исправление:* создайте для неё системного пользователя (Урок 11.6).
6. **Секреты созданы с режимом по умолчанию.** Файл токена с `644` может прочитать любой пользователь. *Исправление:* создавайте его с `600` с самого начала.

Выполняйте шаги по порядку; у каждого указан ожидаемый результат.

1. Выполните `id` и `groups`. В каких группах вы состоите?
2. Создайте `mkdir ~/perm-lab && cd ~/perm-lab && touch report.txt`. Сделайте файл доступным для чтения и записи только вам и покажите `ls -l report.txt`. Ожидается: `-rw-------`.

## Упражнения

### Упражнение 1 — Приватный каталог (средне)

Создайте `~/private-notes`, в который можете войти и который можете просмотреть только вы, и файл `idea.txt` внутри. Покажите командой `sudo -u nobody cat ~/private-notes/idea.txt`, что другой пользователь не может его прочитать. Уберите за собой.

<details>
<summary>Подсказка</summary>

Каталогу нужен `rwx` для владельца и ничего для остальных: режим `700`. Если задать его до создания файла, файл защищён с самого начала.

</details>

<details>
<summary>Ответ</summary>

```bash
mkdir ~/private-notes
chmod 700 ~/private-notes
echo "an idea" > ~/private-notes/idea.txt
sudo -u nobody cat ~/private-notes/idea.txt
rm -r ~/private-notes
```

```text
cat: /home/student/private-notes/idea.txt: Permission denied
```

Почему это работает: пользователь `nobody` для этого каталога — «остальные». Без бита `x` для остальных он не может даже добраться до файла; права самого файла не играют роли. (Ваш домашний каталог, возможно, уже блокирует других пользователей, но защита внутреннего каталога защищает и на случай, если домашний когда-нибудь откроют.)

</details>

### Упражнение 2 — Напишите проверку прав (средне)

**Проверка** — это команда, код возврата которой говорит «да» или «нет». Напишите shell-проверку, которая успешна, только если у `~/perm-lab/report.txt` ровно режим `600`, и печатает `ok` или `FAIL`. Проверьте её для режима `600` и для режима `644`.

<details>
<summary>Подсказка</summary>

`stat -c '%a' file` печатает восьмеричный режим. Сравните его через `[ "$(stat -c '%a' file)" = 600 ]`.

</details>

<details>
<summary>Ответ</summary>

```bash
mkdir -p ~/perm-lab && cd ~/perm-lab && touch report.txt
chmod 600 report.txt
[ "$(stat -c '%a' report.txt)" = 600 ] && echo ok || echo FAIL
chmod 644 report.txt
[ "$(stat -c '%a' report.txt)" = 600 ] && echo ok || echo FAIL
cd ~ && rm -r ~/perm-lab
```

```text
ok
FAIL
```

Почему это работает: `$(...)` подставляет вывод `stat` в строку, `[ a = b ]` сравнивает две строки и задаёт код возврата, а `&&` / `||` выбирают сообщение. Урок 11.8 превращает такие проверки в скрипты.

</details>

### Упражнение 3 — Расширьте тест на Rust (сложно)

В `p11-secretfile` добавьте второй тест: у нового файла **не должно** быть битов прав для группы и для остальных (`mode & 0o077 == 0`). Менять umask внутри теста неудобно, поэтому проверяйте только результат.

<details>
<summary>Подсказка</summary>

`0o077` — маска шести битов группы и остальных. Если режим, к которому применено «И» с ней, равен нулю, ни один из этих битов не установлен.

</details>

<details>
<summary>Ответ</summary>

```rust
    #[test]
    fn secret_file_has_no_group_or_other_bits() {
        let path = std::env::temp_dir().join(format!("p11-secretfile-bits-{}", std::process::id()));
        write_secret(&path, "x").unwrap();

        let mode = std::fs::metadata(&path).unwrap().permissions().mode();
        assert_eq!(
            mode & 0o077,
            0,
            "group/other bits must be empty, got {:o}",
            mode & 0o777
        );

        std::fs::remove_file(&path).unwrap();
    }
```

Добавьте его внутрь `mod tests`; `cargo test` должен показать `2 passed`. Почему это работает: `& 0o077` выделяет шесть младших битов; сообщение утверждения печатает настоящий режим, если тест когда-нибудь упадёт.

</details>

## Вопросы для самопроверки

1. Каков UID у `root` и что в нём особенного?

<details>
<summary>Ответ</summary>

Ноль. Ядро не применяет к нему проверки прав доступа.

</details>

2. Где хранятся пользователи и где хеши паролей?

<details>
<summary>Ответ</summary>

Пользователи — в `/etc/passwd` (читается всеми), группы — в `/etc/group`, хеши паролей — в `/etc/shadow` (читается только root и группой `shadow`).

</details>

3. Что означает бит `x` у каталога?

<details>
<summary>Ответ</summary>

Разрешение входить в него и обращаться к его записям по имени. Без него файлы внутри нельзя открыть, даже если они доступны для чтения.

</details>

4. Почему `usermod -aG`, а не `usermod -G`?

<details>
<summary>Ответ</summary>

`-a` дописывает. Без него `-G` заменяет весь список дополнительных групп пользователя.

</details>

5. Почему у `/tmp` есть sticky-бит?

<details>
<summary>Ответ</summary>

Создавать там файлы может любой, а sticky-бит не даёт пользователям удалять файлы друг друга.

</details>

6. Почему служба должна работать от собственного системного пользователя?

<details>
<summary>Ответ</summary>

Наименьшие привилегии: если в службе ошибка или её атакуют, злоумышленник получает только права этого маленького пользователя, а не root и не человека.

</details>

## Итоги

- Каждый процесс работает от пользователя; у каждого файла есть владелец и группа. Ядро использует числа UID и GID; имена лежат в `/etc/passwd` и `/etc/group`.
- `root` (UID 0) не проверяется. Работайте как обычный пользователь и используйте `sudo` для отдельных команд. Следуйте принципу наименьших привилегий.
- `useradd`, `groupadd`, `usermod -aG` и `userdel` управляют учётными записями. Службы получают системного пользователя с `nologin`.
- Права — это `rwx` для владельца, группы и остальных. У каталогов `x` означает «войти». Восьмеричная запись: r=4, w=2, x=1.
- `chmod` (символьно или восьмерично), `chown`, `umask` меняют, кто что может. `namei -l` объясняет «Permission denied».
- Особые биты: sticky (`/tmp`), setuid (`passwd`), setgid (общий каталог команды).
- Секреты нужно создавать приватными с самого начала: в Rust это `OpenOptions` с `.create_new(true)` и `.mode(0o600)`.
