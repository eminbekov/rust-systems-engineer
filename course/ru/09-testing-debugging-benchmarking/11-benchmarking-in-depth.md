# Урок 09.11 — Бенчмарки подробно

> **Этап 09 — Тестирование, отладка и бенчмарки** · Урок 11 из 14 · ⏱ около 120 минут

## Что вы узнаете

- Как измерять одну функцию на входах нескольких размеров и читать число **пропускной способности** (throughput).
- Как не включать подготовительную работу в измерение с помощью `iter_batched`.
- Как сохранить **базовую линию** (baseline) в `criterion`, изменить код и дать `criterion` сказать, стал ли он быстрее или медленнее, и как читать его вердикт.
- Как сравнивать целые программы с помощью `hyperfine`: списки параметров, прогрев, экспорт таблицы.
- Как честно измерять на ноутбуке, который занят другими делами, и как отличить настоящее изменение от шума.

## Перед началом

- Вы прошли [Урок 09.10 — Логирование и трассировка](10-logging-and-tracing.md). Тайминги спанов из того урока — быстрый взгляд; этот урок — аккуратное измерение.

Не пропускайте тамошние правила («сначала измерьте», «режим release», «держите тест корректности»); этот урок на них опирается.

- Код лежит в `~/projects/rust/code/p09-bench`.

## Новые слова

| Слово | Значение |
|---|---|
| **пропускная способность** (throughput) | Сколько работы делается в секунду, например мегабайт текста в секунду. Лучше, чем «время», когда размер входа меняется. |
| **базовая линия** (baseline) | Сохранённый набор результатов более ранней версии кода. Более поздний запуск сравнивается с ним. |
| **регрессия** (regression, производительности) | Изменение, которое делает программу медленнее. |
| **шум** (noise) | Случайный разброс измерения, не вызванный вашим кодом: другие программы, операционная система, температура чипа. |
| **порог шума** (noise threshold) | Размер изменения (в `criterion` по умолчанию 2%), меньше которого разница считается шумом. |
| **p-значение** (p-value) | Число от 0 до 1 из статистики. Малое (меньше 0,05) значит «разница вряд ли случайна». Оно говорит, что изменение *настоящее*, а не что оно *большое*. |
| **стандартное отклонение** (σ, «сигма») | Насколько разбросаны повторные измерения. Большая σ означает ненадёжные результаты. |
| **прогрев** (warm-up) | Запуски, которые выполняются и выбрасываются перед измерением, чтобы кэши и скорость CPU (Central Processing Unit, центральный процессор — микросхема, которая выполняет программу) установились. |
| **подготовка** (setup) | Работа, нужная перед каждым измеряемым вызовом, например копирование входа. Её время измерять не нужно. |
| **закон Амдала** (Amdahl's law) | Ускорение всей программы ограничено частью, которую вы не улучшили. Ускорение в десять раз части, занимающей 5% времени, даёт не больше 4,5%. |

## 1. Функция, которую стоит измерять

Нам нужно что-то настоящее для сравнения. Задача: превратить текст вроде `"3,14,15"` в числа `[3, 14, 15]`. Есть два честных способа: воспользоваться `split` и `parse` из стандартной библиотеки или один раз пройти по байтам и собрать числа вручную.

```bash
cd ~/projects/rust/code
cargo new --lib p09-bench
cd p09-bench
cargo add --dev criterion@0.8
mkdir benches src/bin
```

`src/lib.rs`:

```rust
/// Parses numbers separated by commas, for example `"3,14,15"`.
/// Version 1: the standard way, `split` + `parse`.
pub fn parse_split(text: &str) -> Vec<u32> {
    text.split(',').map(|part| part.parse().unwrap()).collect()
}

/// Version 2: one pass over the bytes, no intermediate strings.
pub fn parse_bytes(text: &str) -> Vec<u32> {
    let mut numbers = Vec::new();
    let mut current: u32 = 0;
    for &byte in text.as_bytes() {
        if byte == b',' {
            numbers.push(current);
            current = 0;
        } else {
            current = current * 10 + u32::from(byte - b'0');
        }
    }
    numbers.push(current);
    numbers
}

/// Builds a test text with `count` numbers, for example `"0,7,14,..."`.
pub fn make_text(count: usize) -> String {
    let numbers: Vec<String> = (0..count).map(|i| ((i * 7) % 100_000).to_string()).collect();
    numbers.join(",")
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn both_parsers_agree() {
        for count in [1, 2, 10, 1000] {
            let text = make_text(count);
            assert_eq!(parse_split(&text), parse_bytes(&text), "count = {count}");
        }
    }

    #[test]
    fn parses_a_small_example() {
        assert_eq!(parse_bytes("3,14,15"), vec![3, 14, 15]);
        assert_eq!(parse_split("3,14,15"), vec![3, 14, 15]);
    }
}
```

**Что происходит:**

1. `parse_split` — версия, которую пишет большинство. `parse_bytes` читает каждый байт: запятая завершает текущее число; цифра добавляет ещё один десятичный разряд (`current * 10 + digit`). `b'0'` — значение байта символа `0`, поэтому `byte - b'0'` — это цифра.
2. `make_text` создаёт тестовый вход любого размера. Числа всегда меньше 100 000, поэтому помещаются в `u32`.
3. Тест корректности идёт **первым**. Более быстрая функция, дающая другой ответ, бесполезна (Урок 05.12).
4. Предупреждение о честности: `parse_bytes` быстрее отчасти потому, что делает **меньше**. Он не проверяет, что символы — цифры, поэтому принимает `"1x,2"` и возвращает мусор, тогда как `parse_split` паникует. Сравнение честно, только если обе функции делают одну и ту же работу. Здесь мы сравниваем их только на корректном входе и знаем это ограничение.

```bash
cargo test
```

```text
test tests::parses_a_small_example ... ok
test tests::both_parsers_agree ... ok
test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

## 2. `criterion` с несколькими размерами входа

Один размер входа может ввести в заблуждение: функция, выигрывающая на 10 числах, может проиграть на 100 000. Измеряйте **диапазон**. Добавьте в конец `Cargo.toml` (в Уроке 05.12 вы объявляли `harness = false` для одного бенчмарка; теперь файлов два):

```toml
[[bench]]
name = "parse"
harness = false

[[bench]]
name = "sort"
harness = false
```

`benches/parse.rs`:

```rust
use criterion::{BenchmarkId, Criterion, Throughput, criterion_group, criterion_main};
use p09_bench::{make_text, parse_bytes, parse_split};
use std::hint::black_box;

fn bench_parse(c: &mut Criterion) {
    let mut group = c.benchmark_group("parse");
    for count in [10, 1_000, 100_000] {
        let text = make_text(count);
        group.throughput(Throughput::Bytes(text.len() as u64));
        group.bench_with_input(BenchmarkId::new("split", count), &text, |b, text| {
            b.iter(|| parse_split(black_box(text)))
        });
        group.bench_with_input(BenchmarkId::new("bytes", count), &text, |b, text| {
            b.iter(|| parse_bytes(black_box(text)))
        });
    }
    group.finish();
}

criterion_group!(benches, bench_parse);
criterion_main!(benches);
```

**Что происходит:**

1. Цикл создаёт по одному входу для каждого размера. Вход строится **вне** измеряемого замыкания, поэтому его построение не измеряется.
2. `group.throughput(Throughput::Bytes(n))` сообщает `criterion`, сколько байтов обрабатывает каждый вызов, чтобы он мог показывать мегабайты в секунду наряду со временем.
3. `bench_with_input(BenchmarkId::new("split", count), &text, |b, text| ...)` регистрирует бенчмарк с именем `parse/split/10` (группа / функция / параметр) и передаёт `&text` в замыкание. `black_box` прячет значение входа от оптимизатора; результат `criterion` прячет сам.

Запустите. Параметры после `--` идут в `criterion`; здесь они сокращают прогрев и время измерения, чтобы весь запуск занял около половины минуты вместо нескольких минут (для настоящих решений используйте значения по умолчанию):

```bash
cargo bench --bench parse -- --warm-up-time 1 --measurement-time 2
```

```text

Found 8 outliers among 100 measurements (8.00%)

                        thrpt:  [419.47 MiB/s 490.03 MiB/s 558.04 MiB/s]
```

(Сокращено: часть строк про выбросы опущена, а ваши числа будут другими. Единица `MiB/s` — мебибайты в секунду, 1 MiB = 1 048 576 байтов. `GiB/s` — гибибайты в секунду.)

**Как это читать:**

1. Строка `time` — интервал `[нижняя лучшая верхняя]`. Для `bytes/1000` это `[1.8176 µs 1.8207 µs 1.8243 µs]`: очень узкий интервал, надёжное число.
2. `split/1000` — это `[8.27 µs 9.42 µs 11.0 µs]`: интервал шириной около 30%, и 17% выборок — выбросы. На Mac работало что-то ещё. **Не** доверяйте этому числу; запустите снова, когда компьютер свободен (раздел 6). `criterion` показывает сомнение; читать его — ваша работа.
3. `thrpt` (пропускная способность) делает размеры сравнимыми. `bytes` обрабатывает около 2,5–3 гибибайт в секунду на больших размерах, `split` — около 0,5–0,7. То есть `bytes` примерно в 4–5 раз быстрее для 1000 и 100 000 чисел и примерно в 1,8 раза быстрее для 10 чисел, где фиксированная стоимость старта (выделение вектора) важнее.
4. Вывод, который мы вправе сделать: на **корректном входе** таких размеров ручной цикл в несколько раз быстрее. Мы *не* вправе заключить, что ручной код всегда лучше: он менее безопасен, а для программы, которая один раз разбирает 100 чисел, разницу никто не измерит (закон Амдала: ускоряйте то, что занимает время).

> ⚠️ **Частая ошибка:** если ваш пакет — библиотека, обычный `cargo bench -- --warm-up-time 1` падает:
>
> ```text
> error: Unrecognized option: 'warm-up-time'
> error: bench failed, to rerun pass `--lib`
> ```
>
> `cargo bench` запускает как бенчмарк также **собственную тестовую обвязку библиотеки**, а она не знает параметров `criterion`. Назовите нужный бенчмарк: `cargo bench --bench parse -- ...`. (Или добавьте в `Cargo.toml` секцию `[lib]` с `bench = false`.)

Чтобы запустить только некоторые бенчмарки, задайте фильтр. Это регулярное выражение, сопоставляемое с полным именем; `$` означает «конец имени»:

```bash
cargo bench --bench parse -- "bytes/1000$"
```

## 3. Подготовка вне измерения

Сортировка меняет свой вход. Если бенчмарк сортирует один и тот же вектор снова и снова, второй запуск сортирует уже отсортированный вектор, и вы измеряете другое. Нужна **свежая копия для каждого вызова**, но копирование измерять не нужно. Именно это делает `iter_batched`: первое замыкание готовит вход (не измеряется), второе замыкание измеряется. Создайте `benches/sort.rs`:

```rust
use criterion::{BatchSize, Criterion, criterion_group, criterion_main};
use std::hint::black_box;

fn data() -> Vec<u32> {
    (0..10_000u32)
        .map(|i| i.wrapping_mul(2_654_435_761) % 100_000)
        .collect()
}

fn bench_sort(c: &mut Criterion) {
    let input = data();
    let mut group = c.benchmark_group("sort 10_000");
    group.bench_function("sort", |b| {
        b.iter_batched(|| input.clone(), |mut v| v.sort(), BatchSize::SmallInput)
    });
    group.bench_function("sort_unstable", |b| {
        b.iter_batched(
            || input.clone(),
            |mut v| v.sort_unstable(),
            BatchSize::SmallInput,
        )
    });
    group.bench_function("clone only", |b| b.iter(|| black_box(input.clone())));
    group.finish();
}

criterion_group!(benches, bench_sort);
criterion_main!(benches);
```

**Что происходит:**

1. `data()` создаёт 10 000 чисел, выглядящих случайными. `wrapping_mul` умножает и «заворачивается» при переполнении вместо паники (Урок 02.2), поэтому числа перемешаны, а не отсортированы.
2. `iter_batched(setup, routine, size)` вызывает `setup`, чтобы получить свежий вектор, затем измеряет только `routine`. `BatchSize::SmallInput` сообщает `criterion`, что входы маленькие, поэтому он может готовить много сразу.
3. `v.sort()` — **устойчивая** сортировка (равные элементы сохраняют порядок). `v.sort_unstable()` может переставлять равные элементы и часто быстрее.
4. `"clone only"` измеряет только подготовку, чтобы вы знали, что скрывает `iter_batched`. Хорошая привычка: измерьте то, что убрали, чтобы увидеть, насколько оно велико.

```bash
cargo bench --bench sort -- --warm-up-time 1 --measurement-time 2
```

```text
sort 10_000/sort        time:   [54.373 µs 54.736 µs 55.242 µs]
sort 10_000/sort_unstable
                        time:   [54.742 µs 54.868 µs 55.005 µs]
sort 10_000/clone only  time:   [522.97 ns 533.53 ns 544.20 ns]
```

**Что мы узнаём:** обе сортировки занимают 54–55 микросекунд. Интервалы пересекаются, поэтому на этом входе **разницы нет**. Результат «разницы нет» — настоящий результат: он говорит не переписывать код ради этого. Клон стоит 0,5 µs — один процент от сортировки, так что его исключение здесь мало что изменило; для более дешёвой функции это было бы очень важно.

## 4. Базовые линии: помогло ли моё изменение?

Вы меняете код и хотите число, которое скажет «на 20% быстрее» или «без изменений». `criterion` сохраняет каждый запуск на диске (в `target/criterion/`) и сравнивает новый запуск с предыдущим. Для намеренного сравнения дайте сохранённому результату имя — **базовая линия**:

```bash
cargo bench --bench parse -- --save-baseline before "split/1000$"
```

Теперь запустите тот же код ещё раз, на этот раз **сравнивая** с этой базовой линией через `--baseline before`:

```bash
cargo bench --bench parse -- --baseline before "split/1000$"
```

```text
parse/split/1000        time:   [7.6437 µs 7.6855 µs 7.7342 µs]
                        thrpt:  [596.67 MiB/s 600.46 MiB/s 603.74 MiB/s]
                 change:
                        time:   [+0.8594% +1.5051% +2.1350%] (p = 0.00 < 0.05)
                        thrpt:  [−2.0904% −1.4827% −0.8521%]
                        Change within noise threshold.
```

**Как это читать:**

1. Код не менялся, а запуск говорит `+1.5%`: так выглядит шум. `p = 0.00` говорит, что разница «статистически реальна» (два набора выборок различаются), но `Change within noise threshold` говорит, что она меньше 2%, которые `criterion` в любом случае считает шумом. **Малое p-значение не означает большого изменения.** Читайте также размер изменения.
2. Теперь намеренно замедлите `parse_split`: сначала постройте `Vec<String>` из частей (одно лишнее выделение памяти на число), затем разберите их:

```rust
pub fn parse_split(text: &str) -> Vec<u32> {
    let parts: Vec<String> = text.split(',').map(|part| part.to_string()).collect();
    parts.iter().map(|part| part.parse().unwrap()).collect()
}
```

Запустите сравнение снова:

```text
parse/split/1000        time:   [31.982 µs 36.966 µs 43.755 µs]
                        thrpt:  [105.47 MiB/s 124.84 MiB/s 144.29 MiB/s]
                 change:
                        time:   [+593.53% +733.49% +897.03%] (p = 0.00 < 0.05)
                        thrpt:  [−89.970% −88.002% −85.581%]
                        Performance has regressed.
```

`criterion` сообщает `Performance has regressed`: новый код работает в 7–10 раз дольше. Три возможных вердикта: `No change in performance detected`, `Change within noise threshold` и `Performance has improved` / `Performance has regressed`. Верните исходный код, прежде чем продолжать.

> 💡 **Совет:** создайте базовую линию перед началом оптимизации (`--save-baseline before`) и сравнивайте после каждого изменения. Коммитьте изменение, которое помогло, вместе с числами в сообщении коммита («parse: single pass over the bytes, 4x faster at 100k numbers on M4, see benches/parse.rs»). Позже вы сможете выяснить, *почему* код выглядит именно так (Урок 01.4).

## 5. `hyperfine` для целых программ

`criterion` измеряет функцию внутри процесса. Иногда вопрос касается **всей программы**: чтение файла, запуск процесса, всё вместе. Для этого используют `hyperfine`, который запускает команду много раз и сообщает время. Сделайте небольшую программу, использующую оба парсера. `src/bin/sumfile.rs`:

```rust
use p09_bench::{parse_bytes, parse_split};
use std::{env, fs, process};

fn main() {
    let args: Vec<String> = env::args().collect();
    if args.len() != 3 || (args[1] != "split" && args[1] != "bytes") {
        eprintln!("usage: sumfile <split|bytes> <file>");
        process::exit(2);
    }
    let text = fs::read_to_string(&args[2]).expect("cannot read the file");
    let text = text.trim();
    let numbers = if args[1] == "split" {
        parse_split(text)
    } else {
        parse_bytes(text)
    };
    let sum: u64 = numbers.iter().map(|&n| u64::from(n)).sum();
    println!("{} numbers, sum {}", numbers.len(), sum);
}
```

Сделайте входной файл с миллионом чисел (7,8 МБ, мегабайта: миллионов байтов). `seq -f %.0f` печатает простые цифры (иначе `seq` в macOS печатает большие числа вроде `1e+06`, которые наши парсеры не прочитают), а `paste -sd,` соединяет строки запятыми:

```bash
seq -f %.0f 0 7 6999993 | paste -sd, - > numbers.txt
cargo build --release --bin sumfile
./target/release/sumfile split numbers.txt
./target/release/sumfile bytes numbers.txt
```

```text
1000000 numbers, sum 3499996500000
1000000 numbers, sum 3499996500000
```

Обе программы дают один ответ (проверка корректности до измерения времени). Теперь сравните их:

```bash
hyperfine -N --warmup 3 --runs 20 -L impl split,bytes --command-name 'parse with {impl}' './target/release/sumfile {impl} numbers.txt'
```

```text
Benchmark 1: parse with split (20 runs)
                mean     ±       σ          min     …     max
  Wall Time     12.3 ms  ±     0.3 ms      11.8 ms  …    13.0 ms
  Memory        15.3 MiB ±     0.0 MiB     15.3 MiB …    15.3 MiB
 
Benchmark 2: parse with bytes (20 runs)
                mean     ±       σ          min     …     max
  Wall Time      5.8 ms  ±     0.2 ms       5.3 ms  …     6.3 ms           -53.2%  (2.1x faster)
  Memory        15.3 MiB ±     0.0 MiB     15.3 MiB …    15.4 MiB            0.0%
```

(Формат вывода — у `hyperfine` 2.0; старые версии печатают немного иначе.)

**Что происходит:**

1. `-N` запускает программу напрямую, без промежуточной командной оболочки. Без него `hyperfine` запускает оболочку для каждого запуска и вычитает время её старта; для программ, работающих всего несколько миллисекунд, эта поправка — источник шума, поэтому `-N` лучше.
2. `--warmup 3` делает три запуска, которые выбрасываются, чтобы файл оказался в кэше операционной системы, а CPU работал на полной скорости. `--runs 20` делает 20 измеряемых запусков.
3. `-L impl split,bytes` — **список параметров**: команда запускается по разу для каждого значения, с подстановкой `{impl}`. `--command-name` даёт читаемую метку.
4. Читайте `mean ± σ`: `12.3 ± 0.3 ms` говорит «около 12,3 мс, и запуски различаются примерно на 0,3 мс». Разница между двумя командами (12,3 против 5,8) во много раз больше σ, поэтому вывод надёжен.
5. Обратите внимание на разницу в размере: тест на уровне функции говорил, что `bytes` примерно в 4 раза быстрее, тест на уровне программы — что в 2,1 раза. Остальное время программы (чтение 7,8 МБ из дискового кэша, запуск процесса, суммирование) одинаково для обеих. Это закон Амдала в действии. **Число на уровне программы — то, что чувствует пользователь.**

Чтобы сохранить таблицу для pull request или отчёта, добавьте `--export-markdown result.md`; hyperfine запишет такое:

```text
| Command | Mean Wall Time [ms] | Change | Factor |
|:---|---:|---:|:---|
| `parse with split` | 12.3 ± 0.3 |  |  |
| `parse with bytes` | 5.8 ± 0.2 | -53.2% | (2.1x faster) |
```

`--export-json result.json` записывает все отдельные измерения — для ваших скриптов и графиков.

Когда какой инструмент использовать:

| Вопрос | Инструмент |
|---|---|
| Насколько быстра эта функция на входах разных размеров? | `criterion` |
| Сделал ли мой последний коммит эту функцию медленнее? | `criterion` с базовой линией |
| Сколько занимает вся команда, включая старт и I/O (Input/Output, ввод-вывод: чтение и запись)? | `hyperfine` |
| Какая из двух программ или двух версий программы быстрее? | `hyperfine` |
| *Почему* медленно, какая строка? | Профилировщик (инструмент, который выборочно смотрит, куда уходит время, например `cargo flamegraph` или `samply`; здесь не разбираются) |

## 6. Честные измерения на настоящем компьютере

Ваш Mac — не лаборатория. Всё ниже меняет числа.

1. **Шум от другой работы.** В фоне работают браузеры, сборки и синхронизация. Чтобы увидеть эффект, мы запустили 14 прожорливых фоновых программ и измерили ту же команду снова:

```text
quiet:   Wall Time   5.8 ms  ±   0.2 ms      5.3 ms  …    6.3 ms
loaded:  Wall Time   6.9 ms  ±   0.8 ms      5.7 ms  …    8.7 ms
```

(Пример; ваши значения будут другими.) Среднее сдвинулось на 19%, а σ выросла в четыре раза. Лучший запуск (`min`) близок к спокойному: *минимум* часто самое стабильное число, потому что шум только добавляет время. Но за минимумом не спрячешься, когда настоящая программа работает на занятом сервере.

2. **Нагрев и питание.** Ноутбук на батарее или горячий чип сам себя замедляет. Подключите зарядку, подождите минуту между большими запусками и не сравнивайте утренний запуск с вечерним.
3. **Прогрев.** Первый запуск медленнее: файлы не в кэше, предсказатели ветвлений пусты. Поэтому оба инструмента выбрасывают первые запуски.
4. **Смотрите на разброс, а не только на среднее.** Широкий интервал `criterion`, много выбросов или большая `σ` означают: пока не решайте. Закройте другие программы и запустите снова.
5. **Сравнивайте в одном сеансе.** Запускайте старый и новый код друг за другом (базовая линия), а не в разные дни и не на разных машинах. Числа с другого компьютера ничего не говорят о вашем.
6. **Берите реалистичный вход.** Бенчмарк с крошечным идеально упорядоченным входом может вести себя иначе, чем реальные данные. Пробуйте размеры от малых до превышающих ваш кэш (раздел 2).
7. **Держите проверку корректности** рядом с каждым бенчмарком (раздел 1) и сравнивайте одинаковую работу.
8. **Не оптимизируйте то, что не медленное.** Сначала выясните, куда уходит время (закон Амдала). Функция, занимающая 2% времени работы, не даст выигрыша больше 2%.

> ⚡ **Производительность:** бенчмарки на общей машине CI (continuous integration, непрерывной интеграции; Урок 09.12) шумные: соседи меняются от запуска к запуску. Используйте их, чтобы ловить крупные регрессии (в 2 раза медленнее), а не 3%-ные. Мелкие изменения оценивайте на своём тихом компьютере.

> 🧪 **Тестирование:** бенчмарк — не тест, но медленный бенчмарк, который ни разу не запускали, — ошибка, ждущая своего часа. Как минимум убедитесь, что `cargo bench --no-run` (сборка всех бенчмарков) успешно выполняется в CI, чтобы ваши бенчмарки не гнили.

## Частые ошибки

**1. `cargo bench -- --some-criterion-option` падает с `Unrecognized option`.** Добавьте `--bench <имя>` (раздел 2).

**2. Измерение отладочной сборки.** `cargo bench` и `cargo build --release` оптимизируют; `cargo run` — нет. `hyperfine` на `target/debug/...` не измеряет ничего полезного.

**3. Подготовка внутри `b.iter`.** `b.iter(|| { let mut v = input.clone(); v.sort(); })` измеряет клонирование и сортировку вместе. Используйте `iter_batched`.

**4. Забытый `black_box` на входе.** Компилятор может вычислить ответ для константы на этапе компиляции, и вы ничего не измерите (Урок 05.12).

**5. Вера одному шумному числу.** Если интервал широк или выбросов много, повторите запуск, прежде чем писать вывод.

**6. Сравнение двух разных задач.** Более быстрая программа, пропускающая проверки, — не более быстрое решение той же задачи.

## Упражнения

### Упражнение 1 — Фильтр и чтение пропускной способности (легко)

Запустите только бенчмарк `bytes/100000`. Сколько байтов обрабатывает один вызов и примерно сколько гибибайт в секунду?

<details>
<summary>Подсказка</summary>

Фильтр — регулярное выражение: `"bytes/100000$"`. В тексте 100 000 чисел, после каждого запятая; у большинства чисел по 5 цифр. Строка пропускной способности начинается с `thrpt`.

</details>

<details>
<summary>Ответ</summary>

```bash
cargo bench --bench parse -- --warm-up-time 1 --measurement-time 2 "bytes/100000$"
```

```text
parse/bytes/100000      time:   [178.46 µs 180.59 µs 183.53 µs]
                        thrpt:  [2.9883 GiB/s 3.0370 GiB/s 3.0732 GiB/s]
```

Около 3 GiB/s. Текст имеет длину 588 889 байтов (100 000 чисел до 5 цифр и запятые), а `3.04 GiB/s * 180.6 µs` — около 0,59 МБ, что сходится.

Почему это работает: пропускная способность — это число байтов, переданное в `Throughput::Bytes`, делённое на время.

</details>

### Упражнение 2 — Тест граничных случаев (средне)

Напишите в `src/lib.rs` тест, проверяющий, что оба парсера согласны на единственном числе `"0"` и на `"99999,0,5"`. Почему хорошо иметь его рядом с бенчмарком?

<details>
<summary>Подсказка</summary>

Используйте `assert_eq!` с `vec![...]`. Поместите тест в существующий `mod tests`.

</details>

<details>
<summary>Ответ</summary>

```rust
    #[test]
    fn parsers_agree_on_edge_cases() {
        for text in ["0", "99999,0,5"] {
            assert_eq!(parse_split(text), parse_bytes(text), "text = {text}");
        }
        assert_eq!(parse_bytes("99999,0,5"), vec![99_999, 0, 5]);
    }
```

```text
test tests::parsers_agree_on_edge_cases ... ok
```

Почему это работает: обеим функциям даются одни и те же входы, и они должны дать один и тот же вектор; последняя строка ещё и фиксирует ожидаемый ответ. Тест защищает бенчмарк: если кто-то ускорит `parse_bytes` и сломает ответ, тест упадёт, и никто не будет праздновать ложное ускорение.

</details>

### Упражнение 3 — Третья версия (сложно)

Добавьте `parse_split_with_capacity` (сначала зарезервируйте место вектора через `Vec::with_capacity(text.matches(',').count() + 1)`, затем `push` в цикле по `text.split(',')`). Добавьте её в `benches/parse.rs` под именем `split_cap`, проверьте тестом согласованность, измерьте на 1000 числах и решите: быстрее ли она, чем `split`?

<details>
<summary>Подсказка</summary>

`matches(',').count()` один раз проходит по всему тексту, чтобы сосчитать запятые, а это тоже стоит времени. Сравните интервалы `split` и `split_cap` и повторите запуск, если интервалы широкие.

</details>

<details>
<summary>Ответ</summary>

```rust
/// Version 3: like version 1, but the vector gets its room first.
pub fn parse_split_with_capacity(text: &str) -> Vec<u32> {
    let mut numbers = Vec::with_capacity(text.matches(',').count() + 1);
    for part in text.split(',') {
        numbers.push(part.parse().unwrap());
    }
    numbers
}
```

Поместите функцию в `src/lib.rs` выше `mod tests` (Clippy ругается на элементы, стоящие после тестового модуля). В `benches/parse.rs` добавьте импорт `parse_split_with_capacity` и рядом с `split`:

```rust
        group.bench_with_input(BenchmarkId::new("split_cap", count), &text, |b, text| {
            b.iter(|| parse_split_with_capacity(black_box(text)))
        });
```

Результат на спокойном запуске: `split/1000` около 7,6 µs, `split_cap/1000` около 8,0 µs. Разница в пределах нескольких процентов: подсчёт запятых стоит примерно столько же, сколько экономит рост вектора, а разбор каждого числа в любом случае преобладает. Честный вывод — «полезного улучшения нет». (Если на вашем компьютере вы видите большую разницу, сначала проверьте шум: на занятом Mac значение `split` скакало в наших запусках между 7,6 и 31 µs.)

Почему это работает: `Vec` растёт удвоением (Урок 04.7), поэтому копирование составляет лишь несколько процентов работы по сравнению с разбором текста.

</details>

## Вопросы для самопроверки

1. Зачем измерять несколько размеров входа?

<details>
<summary>Ответ</summary>

Потому что более быстрая версия на одном размере может быть более медленной на другом. На малых входах преобладают фиксированные затраты, на больших — стоимость на элемент.

</details>

2. Что значит `p = 0.00 < 0.05` вместе с `Change within noise threshold`?

<details>
<summary>Ответ</summary>

Два набора выборок статистически различаются, но разница меньше порога шума `criterion` (2%). Она реальна, но слишком мала, чтобы о ней заботиться; не сообщайте её как улучшение или регрессию.

</details>

3. Зачем использовать `iter_batched` в бенчмарке сортировки?

<details>
<summary>Ответ</summary>

Сортировка изменяет свой вход. `iter_batched` даёт каждому вызову свежий вход и не считает время его создания, так что каждый измеряемый вызов сортирует одинаковые данные.

</details>

4. Почему `hyperfine` показывает меньшее ускорение (2,1x), чем `criterion` (около 4x), для тех же двух функций?

<details>
<summary>Ответ</summary>

Целая программа ещё читает файл, запускает процесс и суммирует числа; эта часть одинакова для обеих и не ускоряется (закон Амдала).

</details>

5. Какое число шумного измерения часто самое стабильное?

<details>
<summary>Ответ</summary>

Минимум, потому что шум только добавляет время. Но типичный пользователь чувствует среднее, поэтому сообщайте оба вместе с разбросом.

</details>

6. Что делает параметр `-N` у `hyperfine`?

<details>
<summary>Ответ</summary>

Запускает команду напрямую, без командной оболочки для каждого запуска, что убирает время старта оболочки и шум от поправки на него.

</details>

## Итоги

- Измеряйте диапазон размеров входа и читайте пропускную способность. Узкий интервал — надёжный результат; широкий или много выбросов означают «повторите, когда компьютер свободен».
- `iter_batched` выводит подготовку из измерения; измерьте подготовку отдельно, чтобы знать её размер.
- Сохраняйте базовую линию через `--save-baseline` и сравнивайте через `--baseline`. Читайте вердикт и размер изменения, а не только p-значение.
- `hyperfine` измеряет целые программы: `-N`, `--warmup`, `--runs`, списки параметров `-L`, `--export-markdown`. Он показывает то, что чувствует пользователь; `criterion` показывает, как стоят дела у функции.
- Будьте честны (та же задача, корректный вход, тест корректности рядом с бенчмарком), терпеливы (питание подключено, тихий компьютер, повтор) и оптимизируйте только то, что занимает время.
- Результат «разницы нет» — тоже результат. Записывайте числа в сообщение коммита.
