# Урок 24.2 — Ваше портфолио

> **Этап 24 — Карьера и open source** · Урок 2 из 9 · ⏱ около 120 минут

## Что вы узнаете

- Что такое портфолио, кто его читает и сколько времени на него тратит.
- Как выбрать два-три проекта из этого курса и сделать их понятными.
- Из каких разделов состоит README проекта, который отвечает на вопросы читателя, и как честно показывать результаты бенчмарков.
- Как написать техническую статью и подготовить короткий доклад.
- Как автоматически проверять свои README небольшой программой на Rust с тестами.

  `code/p24-career`.

## Новые слова

| Слово | Значение |
|---|---|
| **портфолио** (portfolio) | Небольшая публичная подборка ваших лучших работ с короткими пояснениями, которую могут посмотреть другие люди. |
| **README** | Файл `README.md` в корне репозитория. Сайты хостинга кода показывают его на главной странице проекта. Название означает «прочитай меня сначала». |
| **страница профиля** (profile page) | Ваша личная страница на GitHub или GitLab. Оба сайта умеют показывать на ней README из специального репозитория. |
| **статья о проекте** (write-up) | Статья, которая объясняет одну вещь, которую вы построили или изучили: задачу, устройство, цифры и ошибки. |
| **блиц-доклад** (lightning talk) | Очень короткий доклад, обычно на пять минут, об одной идее. |
| **воспроизводимый** (reproducible) | Другой человек может повторить ваши шаги и получить тот же результат. |
| **лицензия** (licence) | Юридический текст, который говорит, что другим людям можно делать с вашим кодом. Без него никто не вправе законно использовать код повторно. |
| **лицензия MIT** (MIT licence) | Короткая разрешительная open-source-лицензия, названная по Массачусетскому технологическому институту (Massachusetts Institute of Technology), где её написали. |
| **Apache-2.0** | Apache License версии 2.0: разрешительная лицензия от Apache Software Foundation, которая также касается патентов. |
| **строка статуса** (status line) | Одна строка в начале README о том, насколько проект готов, например «Status: milestone 3 of 4». |
| **CI** (Continuous Integration, непрерывная интеграция) | Сервис, который автоматически собирает и тестирует каждое изменение (Урок 09.12). *Значок CI* (CI badge) — маленькая картинка в README, которая показывает, прошёл ли последний запуск. |
| **TCP** (Transmission Control Protocol, протокол управления передачей) | Протокол, который даёт программам надёжный поток байтов по сети (Урок 15.3). Встречается в шаблоне README ниже. |
| **SRE** (Site Reliability Engineering, инженерия надёжности сайтов) | Эксплуатация продакшен-систем методами программной инженерии; так же называется и роль (Урок 24.1). |
| **ASCII** (American Standard Code for Information Interchange, американский стандартный код для обмена информацией) | Базовый набор из 128 текстовых символов (английские буквы, цифры, знаки препинания). *ASCII-схема* — рисунок из этих символов. |
| **код возврата** (exit code) | Число, которое программа возвращает командной оболочке при завершении: 0 означает успех, другие значения — неудачу (Урок 11.5). |

## 1. Что такое портфолио и кто его читает

**Портфолио** — это публичное доказательство ваших навыков. В Уроке 24.1 такое доказательство называлось
*подтверждением*. Когда вы откликаетесь на вакансию или предлагаете pull request проекту, люди с другой
стороны не видят ваш журнал обучения и ваши личные папки. Они видят репозиторий, README, статью или видео.

Кто его читает и как?

- **Инженер, который просматривает отклики.** Часто у него несколько минут на человека. Он открывает ваш
  профиль, щёлкает по одному проекту, читает первый экран README и, может быть, один файл с кодом.
- **Интервьюер.** Перед собеседованием он читает глубже и спрашивает «почему вы выбрали именно это?».
- **Мейнтейнер open-source-проекта.** Он смотрит на ваши прошлые работы, чтобы решить, насколько внимательно
  проверять ваш первый pull request.

Отсюда главное правило: **первый экран должен объяснять проект.** Что это, зачем оно существует, как это
запустить и работает ли оно. Всё остальное может идти ниже в файле.

Второе правило: **качество важнее количества.** Два законченных, протестированных, хорошо объяснённых проекта
говорят больше, чем двадцать недоделанных. Читатель, который открыл репозиторий без README и с упавшей сборкой,
дальше не пойдёт.

## 2. Выберите два-три проекта

За курс вы построили много проектов. Выберите два-три, которые **закончены**, **протестированы**, **ваши**
и **связаны с ролью**, которую вы выбрали в Уроке 24.1.

| Кандидат | Откуда | Подходит для ролей |
|---|---|---|
| Ваш итоговый проект | Этап 23 | Для всех; это ваша самая сильная работа |
| Проект вашей специализации | Этап 22 (один из проектов направлений) | Роль этого направления |
| Мини-среда выполнения контейнеров | Урок 13.17 | Инфраструктура, платформа, ядро |
| Балансировщик нагрузки TCP | Урок 15.15 | Сети, инфраструктура, SRE |
| Собственное хранилище «ключ-значение» | Урок 17.14 | Базы данных, системное ПО |
| Реплицированное хранилище «ключ-значение» | Урок 18.14 | Базы данных, распределённые системы |
| Сервис в Kubernetes | Урок 21.13 | Платформа, инфраструктура, SRE |

Для каждого выбранного проекта составьте короткий список того, чего не хватает: раздела README, теста,
бенчмарка, исправления предупреждений. Исправьте это раньше, чем добавлять что-то новое. Уже существующий
проект, доведённый до отличного состояния, стоит больше нового.

> 📏 **Соглашение:** один проект — один репозиторий. Дайте ему понятное имя (`minikv`, а не `p17-project-final2`)
> и описание в одно предложение в настройках репозитория. Репозиторий курса оставьте журналом обучения;
> законченный проект копируйте в отдельный репозиторий, когда он готов.

## 3. README, который отвечает на вопросы читателя

Читатель приходит с вопросами в определённом порядке. Хороший README отвечает на них в том же порядке:

1. *Что это?* — один абзац.
2. *Это закончено?* — строка статуса.
3. *Как это устроено?* — небольшая схема.
4. *Как это запустить?* — точные команды.
5. *Это работает?* — как это протестировано.
6. *Это быстро?* — цифры, с машиной и командами.
7. *Чего это не умеет?* — ограничения.
8. *Чему научился автор?* — два-три честных предложения.

Вот шаблон. Скопируйте его в каждый проект портфолио и заполните:

````markdown
# minikv

A small key-value store with a write-ahead log and crash recovery, written in Rust.

Status: complete for the goals below; not used in production.

## What it is

Two or three sentences: the problem, who would use it, what is special about it.

## Architecture

```text
client --TCP--> server --> memtable --> SSTables on disk
                   \--> write-ahead log (fsync before reply)
```

## How to run

```bash
cargo run --release -- --data ./data --port 7000
```

## How it is tested

- Unit tests: `cargo test`
- A crash test that kills the server during writes and checks that no
  acknowledged write is lost: `cargo test --test crash -- --ignored`

## Benchmarks (M4 Mac, release build)

Machine: Apple M4, 24 GB memory, macOS, Rust 1.100.0, `--release`.
Command: `cargo bench --bench put_get`

| Operation | Median latency |
|---|---|
| put (with fsync) | (your number) |
| get (from memtable) | (your number) |

## Limitations

- One node only; no replication.
- Keys and values must fit in memory during compaction.

## What I learned

Two or three sentences about the hardest problem and how you solved it.

## License

MIT OR Apache-2.0
````

Некоторые детали важнее, чем кажется:

- **Команды должны быть точными.** Читатель их копирует. Проверьте их сами на свежем клоне.
- **Схема может быть ASCII.** Она не обязана быть красивой; она должна показывать части и поток данных.
- **Раздел ограничений — сила, а не слабость.** Он показывает, что вы знаете, где заканчиваются возможности вашего решения.
- **Лицензия.** Большинство проектов на Rust используют сразу две лицензии, `MIT OR Apache-2.0`: пользователь
  может выбрать любую. Положите оба текста лицензий в `LICENSE-MIT` и `LICENSE-APACHE` и напишите
  `license = "MIT OR Apache-2.0"` в `Cargo.toml`. Тексты можно скопировать с choosealicense.com (см.
  источники).
- **README ваших итоговых проектов.** В Уроке 23.9 у README итоговых проектов другие заголовки («Quick start»,
  «Guarantees and non-goals», «How it works», «Results», «Limits and next steps», «Licence»). Обе структуры
  отвечают на одни и те же вопросы. Выберите один набор заголовков для всех своих публичных репозиториев; если
  оставляете заголовки из Урока 23.9, поменяйте список `REQUIRED` в программе проверки из раздела 4 под них
  (Упражнение 1 показывает, как его менять).

> ⚡ **Производительность:** число из бенчмарка без контекста ничего не значит. Всегда пишите машину, версию
> Rust, профиль сборки и точную команду и предпочитайте медиану или перцентили среднему значению
> (Урок 19.1). Никогда не утверждайте, что ваш проект «быстрее X», по одному микробенчмарку; опишите, что вы
> измеряли и где границы этого измерения.

> 🔒 **Безопасность:** прежде чем сделать репозиторий публичным, прочитайте всю его историю через `git log -p`
> и поищите пароли, токены, закрытые ключи и внутренние имена хостов. Удаление файла в новом коммите **не**
> убирает его из истории. Если настоящий секрет когда-либо попал в коммит, считайте его утёкшим: отзовите
> его и создайте новый (Урок 10.8). Никогда не публикуйте код, конфигурацию или данные работодателя.

## 4. Проверяйте README программой

У вас будет несколько репозиториев, и README со временем устаревают. Небольшая программа проверки находит
пропущенные разделы за секунду. Создайте `src/bin/readme-check.rs` в `code/p24-career`:

```rust
// Checks that a project README has the sections a reader expects.
use std::process::ExitCode;

const REQUIRED: &[&str] = &[
    "what it is",
    "architecture",
    "how to run",
    "how it is tested",
    "benchmarks",
    "limitations",
];

/// Returns the level-2 headings (`## ...`) of a Markdown text, in lowercase.
/// Lines inside fenced code blocks are ignored.
fn headings(markdown: &str) -> Vec<String> {
    let mut in_code = false;
    let mut found = Vec::new();
    for line in markdown.lines() {
        if line.starts_with("```") {
            in_code = !in_code;
        } else if !in_code && let Some(title) = line.strip_prefix("## ") {
            found.push(title.trim().to_lowercase());
        }
    }
    found
}

/// Returns the required sections that the README does not have.
/// A heading counts if it starts with the required words, e.g. "Benchmarks (M4 Mac)".
fn missing_sections(markdown: &str) -> Vec<&'static str> {
    let found = headings(markdown);
    REQUIRED
        .iter()
        .copied()
        .filter(|required| !found.iter().any(|h| h.starts_with(required)))
        .collect()
}

fn main() -> ExitCode {
    let Some(path) = std::env::args().nth(1) else {
        eprintln!("usage: readme-check <path/to/README.md>");
        return ExitCode::from(2);
    };
    let text = match std::fs::read_to_string(&path) {
        Ok(text) => text,
        Err(err) => {
            eprintln!("cannot read {path}: {err}");
            return ExitCode::from(2);
        }
    };

    let missing = missing_sections(&text);
    if missing.is_empty() {
        println!("{path}: all {} sections present", REQUIRED.len());
        return ExitCode::SUCCESS;
    }
    println!(
        "{path}: missing {} of {} sections:",
        missing.len(),
        REQUIRED.len()
    );
    for section in missing {
        println!("  - ## {section}");
    }
    ExitCode::FAILURE
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn finds_level_two_headings_in_lowercase() {
        let md = "# Title\n## What it is\ntext\n### Detail\n## How To Run\n";
        assert_eq!(headings(md), vec!["what it is", "how to run"]);
    }

    #[test]
    fn ignores_headings_inside_code_blocks() {
        let md = "```text\n## not a heading\n```\n## Limitations\n";
        assert_eq!(headings(md), vec!["limitations"]);
    }

    #[test]
    fn heading_may_have_extra_words() {
        let md = "## Benchmarks (M4 Mac, release build)\n";
        assert!(!missing_sections(md).contains(&"benchmarks"));
    }

    #[test]
    fn complete_readme_has_nothing_missing() {
        let md: String = REQUIRED.iter().map(|s| format!("## {s}\n")).collect();
        assert!(missing_sections(&md).is_empty());
    }
}
```

**Что происходит:**

1. `REQUIRED` перечисляет названия разделов строчными буквами. Сравнение текста в нижнем регистре означает, что
   засчитываются и `## How To Run`, и `## How to run`.
2. `headings` проходит по строкам. Строка, начинающаяся с трёх обратных кавычек, открывает или закрывает блок кода,
   поэтому `in_code` переключается. Вне блоков кода `strip_prefix("## ")` возвращает остаток строки для
   заголовка второго уровня и `None` для всего остального. Часть `&& let` — это *let-цепочка* (let chain, Урок 04.5).
3. `missing_sections` оставляет каждое обязательное название, с которого не начинается ни один заголовок.
   `starts_with` разрешает лишние слова, поэтому `## Benchmarks (M4 Mac, release build)` засчитывается как «benchmarks».
4. `main` возвращает `ExitCode`. `let ... else` обрабатывает отсутствующий аргумент; код возврата 2 означает
   «неправильный вызов», 1 — «README неполный», 0 — «всё в порядке». Скрипты и CI могут пользоваться этими кодами.
5. Тесты проверяют правила разбора на крошечных строках. Последний собирает README из самого `REQUIRED`, поэтому
   остаётся верным, если вы меняете список.

Попробуйте на черновике README. Сохраните шаблон из раздела 3 как `demo/README.md` в папке пакета, затем удалите
три его раздела: «Architecture», «How it is tested» и «Limitations».

Запустите проверку, затем напечатайте код возврата через `echo $?` (оболочка хранит последний код возврата в `$?`):

```bash
cargo run -q --bin readme-check -- demo/README.md; echo "exit code: $?"
```

```text
demo/README.md: missing 3 of 6 sections:
  - ## architecture
  - ## how it is tested
  - ## limitations
exit code: 1
```

`-q` скрывает собственные строки Cargo «Compiling…», а `--` отделяет параметры Cargo от аргументов программы.
Без аргумента программа печатает строку с подсказкой по использованию и возвращает код 2; случай «cannot read»
вы увидите в частых ошибках ниже.

И тесты:

```bash
cargo test --bin readme-check
```

```text
running 4 tests
test tests::complete_readme_has_nothing_missing ... ok
test tests::finds_level_two_headings_in_lowercase ... ok
test tests::ignores_headings_inside_code_blocks ... ok
test tests::heading_may_have_extra_words ... ok

test result: ok. 4 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

> 🧪 **Тестирование:** у каждого правила парсера есть свой тест с самым маленьким входом, который его показывает.
> Когда настоящий README сбивает программу с толку, сначала скопируйте сбивающие строки в новый тест, убедитесь,
> что он падает, и только потом исправляйте код (привычка регрессионных тестов из Урока 05.6).

## 5. Статьи: хорошо объясните одну вещь

**Статья о проекте** показывает, что вы понимаете то, что построили. Это ещё и лучший способ проверить, так ли
это: пробелы в понимании становятся видны, когда пытаешься объяснить их письменно.

Структура, которая хорошо работает для системных тем:

| Часть | Содержание | Объём |
|---|---|---|
| Задача | Что вы хотели построить или выяснить, простыми словами. | 1 абзац |
| Предыстория | Каждый термин, который нужен читателю, простым языком. | 2–4 абзаца |
| Устройство | Части, схема и почему вы выбрали это устройство, а не другое. | основная часть |
| Измерения | Таблица с настоящими цифрами, машиной и командами. | 1 таблица |
| Ошибки | Что пошло не так и чему это научило. | 1–3 абзаца |
| Дальше | Что бы вы сделали, будь у вас больше времени. | короткий список |

Хорошие темы берутся из журнала: «Что на самом деле гарантирует `fsync`: проверено убийством моего хранилища
„ключ-значение“», «Как моя оболочка запускает конвейер: `fork`, `exec` и `pipe` шаг за шагом», «Три ошибки, которые
нашла моя симуляция Raft». Выбирайте тему, где у вас есть **цифры или неожиданный результат**.

Где публиковать: достаточно небольшого статического сайта, которым вы управляете. **mdBook** (инструмент, которым
собрана Rust Book) и **Zola** (генератор статических сайтов) написаны на Rust, и их можно бесплатно разместить на
GitHub Pages или GitLab Pages. Для начала подойдёт и Markdown-файл в репозитории проекта.

> 💡 **Совет:** пишите для себя такого, каким вы были год назад. Если тот человек смог бы прочитать статью от начала до конца,
> уровень выбран правильно.

## 6. Доклады: пять минут, одна идея

**Блиц-доклад** — самый простой способ начать выступать: пять минут, одна идея, от трёх до шести слайдов.
Местные и онлайн-митапы часто рады коротким докладам от новых докладчиков.

Простая форма: **задача** (один слайд), **что вы построили** (один-два слайда со схемой), **одно число или один
сюрприз** (один слайд), **чему вы научились** (один слайд). Прорепетируйте вслух три раза с таймером. Запишите один
прогон и посмотрите его; вы заметите, что нужно вырезать.
Выступать не на родном языке на технических мероприятиях — нормально.

## 7. Страница профиля

Ваш профиль на GitHub или GitLab — это точка входа. Держите его коротким:

1. **Три предложения** о себе: над чем вы работаете, что изучаете, какую роль ищете.
2. **Ссылки на два-три проекта**, у каждой — одна строка описания.
3. **Ссылки на принятые pull request** в open-source-проектах (Уроки 24.4 и 24.5) и на ваши статьи.

Закрепите репозитории портфолио в профиле, чтобы они показывались первыми. Удалите или архивируйте эксперименты,
которые запутают читателя, или дайте им строку статуса «experiment».

## Частые ошибки

**README, который начинается с подробностей установки.** Читатель ещё не знает, что это за проект. Начните с одного
абзаца о том, что это и зачем оно существует.

**Красный значок CI.** Значок, показывающий упавшую сборку, сообщает каждому посетителю, что проект сломан.
Почините сборку или уберите значок.

**Запуск проверки из другой папки.** Относительный путь вроде `demo/README.md` ищется от папки, где вы запускаете
команду, а не от папки пакета. Из `src/` это не сработает:

```bash
cd src
cargo run -q --bin readme-check -- demo/README.md; echo "exit code: $?"
```

```text
cannot read demo/README.md: No such file or directory (os error 2)
exit code: 2
```

Вернитесь через `cd ..` или передайте полный путь, например `~/projects/rust/code/p24-career/demo/README.md`.

**Копирование рабочих материалов.** Даже «очищенный» код или конфигурация с работы могут нарушить ваш договор
и раскрыть внутренние детали. В портфолио — только то, что вы построили в своё время на своих данных.

## Попробуйте сами

1. Выберите два-три проекта для портфолио и запишите список в `notes/career.md`, указав для каждого одну
   недостающую вещь.
2. Скопируйте шаблон README в первый проект и заполните каждый раздел настоящим содержанием.
3. Запустите на нём проверку: `cargo run -q --bin readme-check -- <path>/README.md`. Повторяйте, пока она не
   напечатает «all 6 sections present».
4. Попросите знакомого, который не знает проект, прочитать только первый экран README и сказать, что делает
   проект. Если он не может, перепишите первый абзац.
5. Спланируйте одну статью в `notes/writeup-plan.md`: заголовок, по одному предложению для каждой из шести частей
   раздела 5 и точную команду, которая даёт ваше главное число.

## Упражнения

### Упражнение 1 — Ещё один обязательный раздел (легко)

Сделайте так, чтобы проверка требовала и раздел `## License`. Что она теперь напечатает для `demo/README.md`? Почему?

<details>
<summary>Подсказка</summary>

Добавьте одну строку в `REQUIRED`, строчными буквами. Тест `complete_readme_has_nothing_missing` менять не нужно.
Почему?

</details>

<details>
<summary>Ответ</summary>

Добавьте `"license",` после `"limitations",` в `REQUIRED`. Вывод станет таким:

```text
demo/README.md: missing 3 of 7 sections:
  - ## architecture
  - ## how it is tested
  - ## limitations
```

В шаблоне уже есть раздел `## License`, поэтому меняется только общее число — с 6 на 7. Удалите этот раздел из
`demo/README.md`, и строка `- ## license` появится четвёртой.

Почему это работает: и программа, и тест читают список из `REQUIRED`, поэтому тест теперь собирает README с семью
заголовками и по-прежнему проходит.

</details>

### Упражнение 2 — В «How to run» нужна команда (средне)

Раздел «How to run» без команды бесполезен. Напишите `section_has_code(markdown: &str, name: &str) -> bool`,
которая возвращает `true`, если в разделе, заголовок которого начинается с `name`, есть огороженный блок кода.
Сначала напишите тест. Затем пусть `main` печатает строку-предупреждение, если раздел «how to run» есть, но блока
кода в нём нет.

<details>
<summary>Подсказка</summary>

Проходите по строкам и держите флаг `inside`. Каждый заголовок `## ` выставляет флаг: true, если этот заголовок
начинается с `name`, иначе false. Пока `inside` равен true, строка, начинающаяся с трёх обратных кавычек, означает
«нашли».

</details>

<details>
<summary>Ответ</summary>

```rust
/// Returns true if the section whose heading starts with `name` contains a fenced code block.
fn section_has_code(markdown: &str, name: &str) -> bool {
    let mut inside = false;
    for line in markdown.lines() {
        if let Some(title) = line.strip_prefix("## ") {
            inside = title.trim().to_lowercase().starts_with(name);
        } else if inside && line.starts_with("```") {
            return true;
        }
    }
    false
}

#[test]
fn finds_code_only_in_the_named_section() {
    let md = "## How to run\n```bash\ncargo run\n```\n## Limitations\nnone\n";
    assert!(section_has_code(md, "how to run"));
    assert!(!section_has_code(md, "limitations"));
    assert!(!section_has_code("## How to run\njust run it\n", "how to run"));
}
```

Тест помещается в `mod tests`. В `main` сразу после `let missing = missing_sections(&text);`:

```rust
    if !missing.contains(&"how to run") && !section_has_code(&text, "how to run") {
        println!("{path}: the \"how to run\" section has no code block");
    }
```

Для файла `demo/bad.md` с текстом `## What it is`, `x`, `## How to run`, `Just run it.` (четыре строки):

```text
demo/bad.md: the "how to run" section has no code block
demo/bad.md: missing 4 of 6 sections:
  - ## architecture
  - ## how it is tested
  - ## benchmarks
  - ## limitations
```

Почему это работает: флаг меняется только на заголовках `## `, поэтому блок кода засчитывается только тому разделу,
в котором он находится. Проверка `!missing.contains(...)` убирает второе сообщение, когда раздела нет вовсе.

</details>

### Упражнение 3 — Закрепите правило тестом (легко)

В Markdown строка `##Architecture` (без пробела после решёток) — **не** заголовок, а обычная строка текста.
Напишите тест, который документирует, как программа обрабатывает такую строку. Предскажите результат до запуска.

<details>
<summary>Подсказка</summary>

`strip_prefix("## ")` требует пробела. Значит, `headings` ничего не вернёт, и все обязательные разделы будут
отсутствовать.

</details>

<details>
<summary>Ответ</summary>

```rust
#[test]
fn a_heading_needs_a_space_after_the_hashes() {
    assert!(headings("##Architecture\n").is_empty());
    assert_eq!(missing_sections("##Architecture\n").len(), REQUIRED.len());
}
```

Почему это работает: тест записывает правило в коде. Если кто-то потом изменит парсер так, что `##Architecture`
станет считаться заголовком, тест упадёт и заставит принять решение сознательно. Автор README увидит раздел как
отсутствующий, и это правильно: большинство программ просмотра Markdown тоже не покажут его как заголовок.

</details>

## Вопросы для самопроверки

1. Что должно быть на первом экране README?

<details>
<summary>Ответ</summary>

Что это за проект и зачем он существует, его статус и, в идеале, как он устроен и как его запустить. На первом
экране читатель решает, читать ли дальше.

</details>

2. Что нужно написать рядом с числом из бенчмарка?

<details>
<summary>Ответ</summary>

Машину (процессор, память, операционная система), версию Rust, профиль сборки и точную команду, а также какая это
статистика (например, медиана).

</details>

3. Год назад вы закоммитили токен доступа и удалили его в следующем коммите. Теперь это безопасно?

<details>
<summary>Ответ</summary>

Нет. Он всё ещё в истории Git. Отзовите токен и создайте новый; после этого можно и почистить историю, но
безопасным его делает именно отзыв.

</details>

4. Что означает `MIT OR Apache-2.0` в `Cargo.toml`?

<details>
<summary>Ответ</summary>

Код предлагается под двумя лицензиями, и каждый пользователь может выбрать любую из них. Это самый распространённый
выбор лицензии в экосистеме Rust.

</details>

5. Какие коды возврата использует `readme-check` и почему они важны?

<details>
<summary>Ответ</summary>

0, когда все разделы на месте, 1, когда некоторых нет, 2 при неправильном вызове или нечитаемом файле. Скрипты
и задания CI определяют успех или неудачу по коду возврата, поэтому программа, всегда возвращающая 0, не смогла бы
остановить конвейер.

</details>

## Итоги

- Портфолио — это публичное подтверждение: два-три законченных, протестированных, объяснённых проекта, несколько
  статей и, может быть, доклад.
- Первый экран README решает, будут ли читать дальше: что это, статус, схема, как запустить.
- Результаты бенчмарков всегда идут вместе с машиной, версией Rust, профилем сборки и командой.
- Разделы об ограничениях и о том, «чему я научился», показывают зрелость.
- Не допускайте секреты и материалы работодателя в публичные репозитории; проверяйте историю перед публикацией.
- Небольшая программа проверки с тестами (`readme-check`) следит, чтобы README оставались полными, пока проекты меняются.
