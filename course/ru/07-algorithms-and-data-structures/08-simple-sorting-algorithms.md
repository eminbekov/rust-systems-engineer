## Новые слова

| Слово | Значение |
|---|---|
| **сортировка** (sorting) | Расстановка элементов списка по порядку, например чисел от меньшего к большему. |
| **сортировка сравнениями** (comparison sort) | Алгоритм сортировки, который узнаёт порядок только сравнением двух элементов за раз (`a < b`). Все алгоритмы этого урока — сортировки сравнениями. |
| **на месте** (in place) | Алгоритм, который переставляет элементы внутри того же среза и использует лишь несколько дополнительных переменных, а не вторую копию данных. |
| **устойчивая** (stable) | Сортировка устойчива, если элементы, которые считаются равными, сохраняют исходный порядок. |
| **адаптивная** (adaptive) | Сортировка адаптивна, если работает быстрее, когда вход уже (почти) отсортирован. |
| **проход** (pass) | Один полный обход среза (или его части) внутри алгоритма сортировки. |
| **обмен** (swap) | Перестановка двух элементов местами. Метод среза: `v.swap(i, j)`. |
| **инверсия** (inversion) | Пара элементов в неправильном порядке: левый больше правого. В отсортированном срезе 0 инверсий. |
| **инвариант** (invariant) | Утверждение, которое истинно при каждом повторении цикла. Оно помогает доказать, что алгоритм верен. |
| **`Ord`** | Стандартный трейт для типов с полным порядком: любые два значения можно сравнить. Его реализуют числа, `String` и `char`. |
| **`std`** | Сокращение от «standard»: имя стандартной библиотеки Rust, например в `std::collections`. «Сравнить со `std`» значит «сравнить с версией из стандартной библиотеки». |

## 1. Что такое сортировка и зачем она нужна

С **отсортированным** списком проще работать: элемент можно найти быстрее (как — покажет Урок 07.10), одинаковые значения
оказываются рядом, наименьший и наибольший элементы лежат по краям, а два списка легко слить. Многие другие
алгоритмы начинаются со слов «сначала отсортируем данные».

В этом уроке мы напишем три простые сортировки. В настоящих программах их не используют (в стандартной
библиотеке есть лучшие), но они учат важным идеям, а одна из них, сортировка вставками, — настоящий строительный блок.

Три свойства помогают сравнивать алгоритмы сортировки:

| Свойство | На какой вопрос отвечает |
|---|---|
| **на месте** (in place) | Нужна ли вторая копия данных или хватит нескольких переменных? |
| **устойчивость** (stable) | Если два элемента равны, остаётся ли первым тот, что был первым? |
| **адаптивность** (adaptive) | Становится ли алгоритм быстрее, когда данные почти отсортированы? |

**Зачем нужна устойчивость.** Представьте список студентов, уже отсортированный по имени. Теперь вы сортируете его по оценке. Если
сортировка устойчива, студенты с одинаковой оценкой остаются в алфавитном порядке. Если нет, они могут
оказаться в любом порядке.

## 2. Сортировка пузырьком

**Идея.** Идите вдоль среза и сравнивайте каждую пару соседей. Если левый больше, поменяйте их местами.
После одного прохода самый большой элемент «всплывает» в конец. Повторите для оставшейся части среза.

**Картинка** для `[4, 2, 5, 1]` (в скобках — сравниваемая пара; `|` отмечает часть, которая уже окончательная):

```text
start:   4  2  5  1
pass 1:  [4 2] 5  1   4 > 2  swap  ->  2  4  5  1
          2 [4  5] 1  4 < 5  keep
          2  4 [5  1] 5 > 1  swap  ->  2  4  1 | 5
pass 2:  [2 4] 1 | 5  keep
          2 [4  1] | 5 swap  ->  2  1 | 4  5
pass 3:  [2 1] | 4  5 swap  ->  1 | 2  4  5
result:  1  2  4  5
```

**Код.** Поместите это в `src/sorting.rs`:

```rust
//! Simple sorting algorithms: bubble, selection and insertion sort.

/// Bubble sort: repeatedly swaps neighbours that are in the wrong order.
pub fn bubble_sort<T: Ord>(v: &mut [T]) {
    // `end` is the index of the last item that is still not in its final place.
    for end in (1..v.len()).rev() {
        let mut swapped = false;
        for i in 0..end {
            if v[i] > v[i + 1] {
                v.swap(i, i + 1);
                swapped = true;
            }
        }
        if !swapped {
            break; // a whole pass without swaps: the slice is sorted
        }
    }
}
```

**Что происходит:**

1. `T: Ord` означает: подходит любой тип, который можно сравнивать через `<` и `>`. `&mut [T]` — изменяемый срез:
   функция меняет данные там, где они лежат, поэтому она работает *на месте* и ничего не возвращает.
2. `(1..v.len()).rev()` считает от `len - 1` вниз до `1`. Для пустого среза или среза из одного элемента диапазон пуст,
   цикл ничего не делает, так что такие входы безопасны.
3. Внутренний цикл делает один проход по `v[0..=end]`, сравнивая `v[i]` и `v[i + 1]`. Так как `i < end`,
   значение `i + 1` не больше `end`, а это допустимый индекс.
4. После прохода с наибольшим `end` самый большой элемент стоит на последнем месте, поэтому следующий проход может закончиться
   на один элемент раньше. Это и есть **инвариант**: *после прохода элементы после `end` окончательные*.
5. `swapped` — ускорение. Проход без единого обмена доказывает, что все пары соседей в порядке, и мы останавливаемся.
   Благодаря этому сортировка пузырьком *адаптивна*: отсортированному срезу нужен только один проход.

**Стоимость.** В худшем случае (обратный порядок) проходы делают `(n−1) + (n−2) + … + 1 = n(n−1)/2`
сравнений. Для n = 1000 это 499 500. Это записывают как **O(n²)** («порядка n в квадрате»: если вход вырос вдвое,
работа вырастает примерно вчетверо). Лучший случай (уже отсортировано) — **O(n)**: один проход. Нужно лишь несколько
переменных, поэтому дополнительная память — **O(1)**. Сортировка устойчива, потому что обмен происходит только при
`v[i] > v[i + 1]`, но никогда для равных элементов.

## 3. Сортировка выбором

**Идея.** Найдите наименьший элемент неотсортированной части и обменяйте его с первым элементом этой части. Затем сделайте то же
для остатка. Отсортированная часть растёт слева.

```text
start:   4  2  5  1
i = 0:   smallest of [4 2 5 1] is 1 (index 3)  swap v[0], v[3]  ->  1 | 2  5  4
i = 1:   smallest of [2 5 4]   is 2 (index 1)  already there    ->  1  2 | 5  4
i = 2:   smallest of [5 4]     is 4 (index 3)  swap v[2], v[3]  ->  1  2  4 | 5
result:  1  2  4  5
```

```rust
/// Selection sort: finds the smallest item of the rest and puts it next in line.
pub fn selection_sort<T: Ord>(v: &mut [T]) {
    for i in 0..v.len() {
        let mut min = i;
        for j in (i + 1)..v.len() {
            if v[j] < v[min] {
                min = j;
            }
        }
        v.swap(i, min);
    }
}
```

**Что происходит:**

1. `min` — индекс наименьшего элемента, виденного до сих пор в неотсортированной части; он начинается с `i`.
2. Внутренний цикл просматривает каждый следующий элемент и запоминает индекс меньшего.
3. Один `swap` за раунд ставит наименьший элемент на позицию `i`. (Если `min == i`, обмен ничего не меняет.)
4. **Инвариант:** перед раундом `i` элементы `v[0..i]` — это `i` наименьших элементов по порядку.

**Стоимость.** Внутренний цикл всегда выполняется полностью, какими бы ни были данные: ровно `n(n−1)/2` сравнений, так что время —
**O(n²) в лучшем, среднем и худшем случае**. Алгоритм не адаптивен. Он делает не более `n − 1` обменов — в этом его
единственное достоинство: если перемещение элемента очень дорого, сортировка выбором перемещает меньше всех. Она **не
устойчива**: обмен на большом расстоянии может перебросить элемент через равный ему (тесты ниже это докажут).

## 4. Сортировка вставками

**Идея.** Так многие сортируют игральные карты в руке. Левая часть всегда отсортирована. Берём следующий элемент
и сдвигаем его влево, пока он не встретит меньший или равный элемент.

```text
start:   4 | 2  5  1          (the part before | is sorted)
i = 1:   take 2, slide left past 4         ->  2  4 | 5  1
i = 2:   take 5, 4 < 5, it stays           ->  2  4  5 | 1
i = 3:   take 1, slide past 5, 4 and 2     ->  1  2  4  5 |
result:  1  2  4  5
```

```rust
/// Insertion sort: grows a sorted prefix by sliding each new item into place.
pub fn insertion_sort<T: Ord>(v: &mut [T]) {
    for i in 1..v.len() {
        let mut j = i;
        while j > 0 && v[j - 1] > v[j] {
            v.swap(j - 1, j);
            j -= 1;
        }
    }
}
```

**Что происходит:**

1. `i` — индекс вставляемого элемента. **Инвариант:** перед раундом `i` срез `v[0..i]` отсортирован.
2. `j` — текущее место элемента. Пока левый сосед больше, мы меняем их местами и сдвигаем `j` на шаг влево.
3. Проверка `j > 0` стоит **первой**. При `&&` Rust останавливается на первом `false`, поэтому `v[j - 1]` не
   вычисляется при `j == 0`. (Частая ошибка 2 показывает, что будет при другом порядке.)
4. Сравнение — `>`, а не `>=`, поэтому элемент останавливается перед равным: равные элементы никогда не обгоняют друг друга,
   и сортировка **устойчива**.

**Стоимость.** Объём работы зависит от входа, потому что цикл `while` выполняется, лишь пока элементы стоят не по порядку.
Каждый обмен убирает ровно одну *инверсию* (одну пару в неправильном порядке), поэтому число обменов равно
числу инверсий во входе:

- отсортированный вход: 0 инверсий, около `n` сравнений: **O(n)**. Сортировка вставками *адаптивна*.
- обратный порядок: `n(n−1)/2` инверсий: **O(n²)** (худший случай).
- случайный вход: примерно половина пар — инверсии, поэтому около `n²/4` обменов: **O(n²)** в среднем.

Память: **O(1)**, на месте, устойчива.

| Алгоритм | Лучший | Средний | Худший | Доп. память | Устойчива | Адаптивна |
|---|---|---|---|---|---|---|
| сортировка пузырьком (с ранним выходом) | O(n) | O(n²) | O(n²) | O(1) | да | да |
| сортировка выбором | O(n²) | O(n²) | O(n²) | O(1) | нет | нет |
| сортировка вставками | O(n) | O(n²) | O(n²) | O(1) | да | да |

> 💡 **Совет:** из трёх только сортировка вставками применяется в настоящем коде. Она очень быстра на *коротких* срезах
> (десяток элементов) и на почти отсортированных данных, потому что почти не тратит время на служебные действия. Урок 07.9 использует её как
> «финальный шаг» более быстрых алгоритмов. Сортировка пузырьком нужна только для обучения.

## 5. Тестирование сортировки

Функцию сортировки легко хорошо протестировать, потому что стандартная библиотека даёт правильный ответ для сравнения:
`slice.sort()`. План:

1. **Граничные случаи:** пустой срез, один элемент, уже отсортированный, в обратном порядке.
2. **Много сгенерированных входов:** сравните ваш результат со `std` на сотнях входов: разной длины, с
   большим и малым числом повторов.
3. **Устойчивость:** тест с элементами, которые считаются равными, но на самом деле различны.

Нам нужны «случайные» числа, но тест должен давать одинаковый результат при каждом запуске. Именно это делает **генератор
псевдослучайных чисел** `Rng`, который вы написали в `src/testutil.rs` в Уроке 07.3: его числа похожи на случайные, но
полностью определяются начальным числом — *зерном* (seed). Его используют все тесты этого этапа.

Добавьте это в конец `src/sorting.rs`:

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use crate::testutil::Rng;
    use std::cmp::Ordering;

    /// `len` pseudo-random numbers from 0 to `max - 1`. Same seed, same numbers.
    fn random_vec(seed: u64, len: usize, max: u64) -> Vec<i32> {
        let mut rng = Rng::new(seed);
        (0..len).map(|_| (rng.next_u64() % max) as i32).collect()
    }

    /// Runs one sorting function on many inputs and compares with the standard library.
    fn check(sort: fn(&mut [i32])) {
        for len in 0..=40 {
            for seed in 1..=5 {
                // `max` = 5 gives many duplicates, 1000 gives few.
                for max in [5, 1000] {
                    let mut actual = random_vec(seed, len, max);
                    let mut expected = actual.clone();
                    expected.sort();
                    sort(&mut actual);
                    assert_eq!(actual, expected, "len {len}, seed {seed}, max {max}");
                }
            }
        }
    }

    #[test]
    fn all_sorts_match_std() {
        check(bubble_sort::<i32>);
        check(selection_sort::<i32>);
        check(insertion_sort::<i32>);
    }

    #[test]
    fn edge_cases() {
        for case in [vec![], vec![7], vec![1, 2, 3, 4], vec![4, 3, 2, 1]] {
            let mut v = case.clone();
            insertion_sort(&mut v);
            let mut expected = case;
            expected.sort();
            assert_eq!(v, expected);
        }
    }

    /// A card that is compared by `rank` only. The `tag` shows the original order.
    #[derive(Debug, Clone, Copy, PartialEq, Eq)]
    struct Card {
        rank: u8,
        tag: char,
    }

    impl PartialOrd for Card {
        fn partial_cmp(&self, other: &Self) -> Option<Ordering> {
            Some(self.cmp(other))
        }
    }

    impl Ord for Card {
        fn cmp(&self, other: &Self) -> Ordering {
            self.rank.cmp(&other.rank)
        }
    }

    /// Sorts the cards 2a, 2b, 1c and returns the tags in the sorted order.
    fn sorted_tags(sort: fn(&mut [Card])) -> String {
        let mut v = vec![
            Card { rank: 2, tag: 'a' },
            Card { rank: 2, tag: 'b' },
            Card { rank: 1, tag: 'c' },
        ];
        sort(&mut v);
        v.iter().map(|c| c.tag).collect()
    }

    #[test]
    fn bubble_and_insertion_are_stable() {
        assert_eq!(sorted_tags(bubble_sort), "cab");
        assert_eq!(sorted_tags(insertion_sort), "cab");
    }

    #[test]
    fn selection_sort_is_not_stable() {
        // The two cards of rank 2 swapped places: "b" now comes before "a".
        assert_eq!(sorted_tags(selection_sort), "cba");
    }
}
```

**Что происходит:**

1. `random_vec` строит по зерну список из `len` чисел, меньших `max`, с помощью `Rng` из Урока 07.3. Одно и то же
   зерно даёт один и тот же список, поэтому падение теста можно повторить.
2. `check` принимает любую функцию типа `fn(&mut [i32])`. Вызов `check(bubble_sort::<i32>)` передаёт
   обобщённую функцию с `T`, равным `i32` («турбофиш» `::<i32>` из Урока 05.1). Циклы проверяют
   длины от 0 до 40, 5 зёрен и 2 диапазона значений: 410 входов на каждый алгоритм. При `max = 5` много
   равных элементов — именно там прячутся ошибки.
3. `edge_cases` перебирает четыре маленьких входа: пустой, один элемент, отсортированный и в обратном порядке.
4. `Card` реализует `Ord` вручную и сравнивает только `rank`. Две карты с одинаковым рангом для
   сортировки «равны», но их буквы `tag` различаются, поэтому мы *видим*, изменился ли их порядок. (`PartialOrd` и
   `Ord` идут парой; трейты объяснялись в Уроке 05.2.)
5. Вход `[2a, 2b, 1c]` при устойчивой сортировке должен дать `c a b`. Сортировки пузырьком и вставками это делают. Сортировка выбором
   меняет `v[0]` (карту `2a`) с картой `1c` в конце, и `2a` оказывается за `2b`: получается `c b a`. Мы
   *проверяем неустойчивость тестом*, чтобы задокументировать её.

## 6. Подсчёт шагов

«O(n²)» — это утверждение. Давайте его проверим. Мы хотим посчитать сравнения, не меняя наши функции сортировки.
Приём: сортируем тип, который сам считает свои сравнения. Создайте `examples/e08_count_steps.rs`:

```rust
use p07_algorithms::sorting::{bubble_sort, insertion_sort, selection_sort};
use std::cell::Cell;
use std::cmp::Ordering;

/// A number that counts how many times it is compared.
struct Counted<'a> {
    value: i32,
    counter: &'a Cell<u64>,
}

impl PartialEq for Counted<'_> {
    fn eq(&self, other: &Self) -> bool {
        self.value == other.value
    }
}

impl Eq for Counted<'_> {}

impl PartialOrd for Counted<'_> {
    fn partial_cmp(&self, other: &Self) -> Option<Ordering> {
        Some(self.cmp(other))
    }
}

impl Ord for Counted<'_> {
    fn cmp(&self, other: &Self) -> Ordering {
        self.counter.set(self.counter.get() + 1);
        self.value.cmp(&other.value)
    }
}

/// Sorts a copy of `data` with `sort` and returns the number of comparisons.
fn count<'a>(sort: fn(&mut [Counted<'a>]), data: &[i32], counter: &'a Cell<u64>) -> u64 {
    counter.set(0);
    let mut items: Vec<Counted> = data
        .iter()
        .map(|&value| Counted { value, counter })
        .collect();
    sort(&mut items);
    counter.get()
}

fn pseudo_random(len: usize) -> Vec<i32> {
    let mut x: u64 = 12345;
    (0..len)
        .map(|_| {
            x ^= x << 13;
            x ^= x >> 7;
            x ^= x << 17;
            (x % 1_000_000) as i32
        })
        .collect()
}

fn main() {
    let counter = Cell::new(0);
    println!(
        "{:>6} {:>12} {:>12} {:>12} {:>14}",
        "n", "bubble", "selection", "insertion", "insertion/sorted"
    );
    for n in [100, 200, 400, 800] {
        let data = pseudo_random(n);
        let sorted: Vec<i32> = (0..n as i32).collect();
        println!(
            "{:>6} {:>12} {:>12} {:>12} {:>14}",
            n,
            count(bubble_sort::<Counted>, &data, &counter),
            count(selection_sort::<Counted>, &data, &counter),
            count(insertion_sort::<Counted>, &data, &counter),
            count(insertion_sort::<Counted>, &sorted, &counter),
        );
    }
}
```

**Что происходит:**

1. `Counted` хранит число и общую ссылку на `Cell<u64>` (внутренняя изменяемость, Урок 06.4: `Cell` можно
   менять через общую ссылку). Время жизни `'a` говорит, что счётчик должен жить не меньше, чем числа.
2. Каждое сравнение проходит через `Ord::cmp`, и наш `cmp` прибавляет единицу к счётчику перед сравнением
   значений. Операторы `<` и `>` вызывают `partial_cmp`, который вызывает `cmp`, поэтому каждое сравнение внутри
   `bubble_sort`, `selection_sort` и `insertion_sort` учитывается без каких-либо изменений в них.
3. `count` оборачивает каждое число в `Counted`, запускает сортировку и возвращает счётчик. Обобщённые функции
   применяются с `T = Counted`: для этого обобщения и нужны.
4. `main` каждый раз удваивает `n` и печатает счётчики. В последнем столбце сортируется уже отсортированный список.

```bash
cargo run --example e08_count_steps
```

```text
     n       bubble    selection    insertion insertion/sorted
   100         4845         4950         2376             99
   200        19600        19900         9981            199
   400        77784        79800        38651            399
   800       318654       319600       157250            799
```

**Как это читать:**

1. Когда `n` удваивается, счётчики всех трёх сортировок растут примерно **вчетверо** (4950, 19900, 79800, 319600 для
   сортировки выбором): это признак O(n²).
2. Сортировке выбором нужно ровно `n(n−1)/2` сравнений (для 100: 100·99/2 = 4950), каковы бы ни были данные.
3. Сортировке вставками на случайных данных нужно примерно вдвое меньше (2376 при n = 100), потому что в среднем она сдвигает
   элемент лишь на полпути.
4. На отсортированном входе сортировке вставками нужно лишь `n − 1` сравнений (99, 199, …): это лучший случай **O(n)**.

> ⚡ **Производительность:** при n = 1 000 000 сортировка вставками на случайных данных делает около n²/4 = 2,5·10¹¹ сравнений —
> минуты работы. Сортировке O(n log n) нужно около 2·10⁷ сравнений, это малая доля секунды. В этом разница, которую даёт
> алгоритм, и никакая настройка компилятора её не закроет. Урок 07.9 измеряет реальное время.

## 7. Что использовать в настоящем коде

В стандартной библиотеке есть две сортировки для срезов и `Vec`:

| Метод | Устойчивая | Дополнительная память | Когда использовать |
|---|---|---|---|
| `v.sort()` | да | может выделить буфер | вариант по умолчанию; нужно, чтобы равные элементы сохраняли порядок |
| `v.sort_unstable()` | нет | нет (на месте) | вариант по умолчанию для обычных чисел и других типов, где равные элементы неразличимы; обычно чуть быстрее |

Варианты: `sort_by(|a, b| …)` принимает замыкание сравнения, возвращающее `Ordering`; `sort_by_key(|x| …)` сортирует
по ключу, вычисленному для каждого элемента; `sort_unstable_by` и `sort_unstable_by_key` — их неустойчивые двойники.
`is_sorted()` за O(n) проверяет, отсортирован ли срез. Для чисел с плавающей точкой используйте
`sort_by(|a, b| a.total_cmp(b))`, потому что `f32` и `f64` не реализуют `Ord` (значению NaN, «не число»,
нет места в порядке).

Обе сортировки в худшем случае работают за O(n log n). Пишите собственную простую сортировку только ради обучения или в очень редком случае,
когда нужно сортировать крошечные срезы в горячем цикле и вы измерили, что это помогает.

## Частые ошибки

**1. Обмен через кортежи индексированных элементов.** В обобщённой функции элементы могут не быть `Copy`, поэтому
их нельзя вынуть из среза:

```rust
pub fn swap_pair<T: Ord>(v: &mut [T], i: usize, j: usize) {
    (v[i], v[j]) = (v[j], v[i]);
}
```

```text
error[E0508]: cannot move out of type `[T]`, a non-copy slice
 --> src/lib.rs:2:21
  |
2 |     (v[i], v[j]) = (v[j], v[i]);
  |                     ^^^^
  |                     |
  |                     cannot move out of here
  |                     move occurs because `v[_]` has type `T`, which does not implement the `Copy` trait
```

Компилятор говорит: нельзя переместить `T` из среза и оставить дыру. Исправление — метод среза
`v.swap(i, j)`, который безопасно меняет два элемента местами без всякого `Copy`.

**2. Слишком поздняя проверка `j > 0`.** Два условия цикла сортировки вставками записаны в неправильном порядке:

```rust
while v[j - 1] > v[j] && j > 0 {
```

Если `j` имеет тип `usize` (беззнаковое число), то `j - 1` при `j == 0` — переполнение. Тест с обратным
входом `[3, 2, 1]` падает в отладочной сборке:

```text
thread 'reversed' panicked at src/lib.rs:4:17:
attempt to subtract with overflow
```

Исправление: сначала проверяйте `j > 0`. `&&` не вычисляет правую часть, если левая — `false`.

**3. `>=` в сортировке вставками.** `v[j - 1] >= v[j]` тоже меняет местами равные элементы. Результат по-прежнему отсортирован,
но сортировка перестаёт быть устойчивой и делает лишнюю работу. Используйте строгое `>`.

### Упражнение 1 — Трассировка вручную (легко)

Запишите список после каждого раунда сортировки вставками для `[3, 1, 4, 1, 5]`. Сколько всего сделано обменов
и сколько инверсий во входе?

<details>
<summary>Подсказка</summary>

Инверсия — это пара `(левый, правый)`, где `левый > правый`, а `левый` стоит в списке раньше. Посчитайте
пары. Каждый обмен сортировки вставками исправляет ровно одну такую пару.

</details>

<details>
<summary>Ответ</summary>

```text
start:   3  1  4  1  5
i = 1:   1  3  4  1  5     (1 slides past 3: 1 swap)
i = 2:   1  3  4  1  5     (4 stays)
i = 3:   1  1  3  4  5     (the second 1 slides past 4 and 3: 2 swaps, stops in front of the first 1)
i = 4:   1  1  3  4  5     (5 stays)
```

Всего: 3 обмена. Инверсии: (3, 1), (3, 1) и (4, 1) — три пары в неправильном порядке, то есть 3. Эти два числа
равны, как и говорит урок. Вторая `1` останавливается перед первой `1`, потому что сравнение строгое, поэтому
равные элементы сохраняют порядок.

</details>

<details>
<summary>Подсказка</summary>

Склонируйте вектор перед сортировкой, отсортируйте клон через `.sort()` и сравните оба через `assert_eq!`.
Поместите тест в модуль `tests`.

</details>

<details>
<summary>Ответ</summary>

```rust
#[test]
fn sorts_words() {
    let mut words = vec![
        "pear".to_string(),
        "apple".to_string(),
        "fig".to_string(),
        "apple".to_string(),
    ];
    let mut expected = words.clone();
    expected.sort();

    assert_eq!(words, expected);
    assert!(words.is_sorted());
}
```

Почему это работает: `String` реализует `Ord`, поэтому `T = String` удовлетворяет ограничению. Строки сравниваются

### Упражнение 3 — Назовите сложность (средне)

Назовите временную сложность (в нотации Big-O, через `n`) каждого случая и примерно сколько сравнений он делает:

1. сортировка вставками уже отсортированного списка из 1 000 000 чисел;
2. сортировка выбором уже отсортированного списка из 1 000 000 чисел;
3. сортировка пузырьком (с ранним выходом) списка из 1 000 чисел в обратном порядке: сколько сравнений и сколько обменов?

<details>
<summary>Подсказка</summary>

Для (1) и (2) подумайте, что делает каждый внутренний цикл, когда ничего не нужно двигать. Для (3) сложите длины
проходов: `999 + 998 + … + 1`.

</details>

<details>
<summary>Ответ</summary>

1. **O(n)**: цикл `while` делает одно сравнение на элемент и сразу останавливается. Около 999 999 сравнений.
2. **O(n²)**: сортировка выбором не замечает, что данные отсортированы; она всегда делает `n(n−1)/2`, около
   5·10¹¹ (500 миллиардов) сравнений.
3. **O(n²)**: 999 + 998 + … + 1 = 499 500 сравнений. В списке в обратном порядке каждая сравниваемая пара стоит не по порядку,
   поэтому обменов тоже 499 500.

Почему это работает: лучший случай адаптивного алгоритма зависит от данных; у неадаптивного — нет.

</details>

### Упражнение 4 — Обмены равны инверсиям (сложно)

Напишите `inversions<T: Ord>(v: &[T]) -> usize`, которая считает пары в неправильном порядке двумя вложенными циклами, и
`insertion_sort_counting_swaps<T: Ord>(v: &mut [T]) -> usize`, которая сортирует и возвращает число сделанных обменов.
Напишите тест, проверяющий, что они равны на многих сгенерированных входах, и тест, что у списка из 1000 чисел в обратном порядке
499 500 инверсий. Какова временная сложность `inversions`?

<details>
<summary>Подсказка</summary>

Для каждого `i` посчитайте `j > i`, для которых `v[i] > v[j]`. Для счётчика обменов прибавляйте единицу в цикле `while` после
каждого `swap`. Используйте помощник `random_vec` из модуля `tests` (возьмите малое `max`, например 20, чтобы были повторы).

</details>

<details>
<summary>Ответ</summary>

```rust
pub fn inversions<T: Ord>(v: &[T]) -> usize {
    let mut count = 0;
    for i in 0..v.len() {
        for j in (i + 1)..v.len() {
            if v[i] > v[j] {
                count += 1;
            }
        }
    }
    count
}

pub fn insertion_sort_counting_swaps<T: Ord>(v: &mut [T]) -> usize {
    let mut swaps = 0;
    for i in 1..v.len() {
        let mut j = i;
        while j > 0 && v[j - 1] > v[j] {
            v.swap(j - 1, j);
            swaps += 1;
            j -= 1;
        }
    }
    swaps
}

#[test]
fn swaps_equal_inversions() {
    assert_eq!(inversions(&[3, 1, 4, 1, 5]), 3);
    for len in 0..30 {
        for seed in 1..=5 {
            let v = random_vec(seed, len, 20);
            let expected = inversions(&v);
            let mut w = v.clone();
            assert_eq!(insertion_sort_counting_swaps(&mut w), expected);
        }
    }
    let reversed: Vec<i32> = (0..1000).rev().collect();
    assert_eq!(inversions(&reversed), 499_500);
}
```

Почему это работает: каждый обмен двух соседей исправляет ровно одну неправильную пару и не создаёт новых, поэтому число обменов
не может быть ничем иным, кроме числа инверсий. `inversions` работает за **O(n²)** из-за двух вложенных
циклов по примерно `n²/2` парам. (Более быстрый способ, O(n log n), появляется после сортировки слиянием из Урока 07.9.)

</details>

## Вопросы для самопроверки

1. Что значит «устойчивая» для алгоритма сортировки?

<details>
<summary>Ответ</summary>

Элементы, которые считаются равными, сохраняют тот же взаимный порядок, что и во входе. Сортировки пузырьком и вставками
устойчивы. Сортировка выбором — нет.

</details>

2. Почему сортировка вставками работает за O(n) на отсортированном списке, а сортировка выбором — за O(n²)?

<details>
<summary>Ответ</summary>

Сортировка вставками прекращает сдвигать элемент, как только левый сосед не больше него, поэтому на отсортированных данных каждый элемент
стоит одного сравнения. Сортировка выбором всегда просматривает всю неотсортированную часть в поисках наименьшего элемента, как бы ни
выглядели данные.

</details>

3. Во сколько раз больше работы делает алгоритм O(n²), когда `n` становится в 10 раз больше?

<details>
<summary>Ответ</summary>

Примерно в 100 раз (10² = 100).

</details>

4. Какой метод нужно использовать, чтобы отсортировать `Vec<u32>` в настоящей программе?

<details>
<summary>Ответ</summary>

`sort_unstable()` (равные числа неразличимы, поэтому устойчивость не важна) или `sort()`, если вам больше нравится устойчивая.
Но никогда — самодельную сортировку за O(n²).

</details>

## Итоги

- Сортировка расставляет элементы по порядку; сортировка сравнениями узнаёт порядок только сравнением пар.
- Три свойства позволяют сравнивать алгоритмы: на месте (мало дополнительной памяти), устойчивость (равные элементы сохраняют порядок)
  и адаптивность (быстрее на почти отсортированных данных).
- Сортировки пузырьком, выбором и вставками в худшем случае работают за O(n²) и используют O(1) дополнительной памяти.
- Сортировка вставками — лучшая из них: устойчива, адаптивна (O(n) на отсортированных данных) и быстра на коротких срезах.
  Число её обменов равно числу инверсий.
- Тестируйте сортировку против `std` на многих сгенерированных входах, с большим числом повторов, и добавляйте граничные случаи и тест
  устойчивости.
- Подсчёт сравнений показывает, что при удвоении `n` сортировка O(n²) делает примерно вчетверо больше работы.
- В настоящем коде используйте `sort`, `sort_unstable`, `sort_by_key` и им подобные.
