## Новые слова

| Слово | Значение |
|---|---|
| **конкуренция за блокировку** (contention) | Несколько потоков хотят одну и ту же блокировку одновременно. Блокировка *нагружена* (contended), когда за неё борются, и *свободна от конкуренции* (uncontended), когда ею пользуется только один поток. |
| **быстрый путь / медленный путь** (fast path / slow path) | Быстрый случай (блокировка свободна: взять её одной атомарной операцией) и дорогой случай (блокировка занята: попросить OS усыпить поток). |
| **futex** (fast user-space mutex, быстрый мьютекс пространства пользователя) | Системный вызов Linux, который позволяет потоку спать, пока не изменится число в памяти, и потом будит его. Блокировки Rust используют его в Linux. |
| **POSIX** (Portable Operating System Interface, переносимый интерфейс операционных систем) | Стандартный набор системных функций, который предлагают Unix-подобные системы (Linux, macOS). |
| **pthread** (POSIX threads, потоки POSIX) | Стандартная библиотека потоков и блокировок Unix-подобных систем. В macOS `Mutex` из Rust использует мьютекс pthread. |
| **нс** (ns, nanosecond, наносекунда) | Одна миллиардная доля секунды. Взять свободную блокировку стоит несколько наносекунд. |
| **временное значение** (temporary) | Значение, которое создаётся посреди выражения и не имеет имени, например guard в `m.lock().unwrap().pop()`. |
| **проверяемое выражение** (scrutinee) | Выражение, которое рассматривает `match` или `if let`: в `match x.pop() { … }` это `x.pop()`. |
| **`try_lock`** | Метод, который берёт блокировку, только если она свободна прямо сейчас, а иначе сразу возвращает ошибку вместо ожидания. |
| **блокировка чтения-записи** (read-write lock, `RwLock`) | Блокировка, которая пускает **многих читателей сразу или одного писателя**, но никогда тех и других вместе. |
| **голодание писателя** (writer starvation) | Читатели всё время держат блокировку занятой, и писатель ждёт очень долго. |
| **честность** (fairness) | Отдаёт ли блокировка себя ожидающим потокам в порядке их прихода. Стандартные блокировки Rust честность не обещают. |
| **гранулярность блокировок** (lock granularity) | Сколько данных защищает одна блокировка. *Крупная*: одна блокировка на всё. *Мелкая*: много блокировок, каждая на небольшую часть. |
| **шардирование** (sharding, lock striping) | Разделение данных на несколько частей, у каждой своя блокировка, чтобы потоки, работающие с разными частями, не ждали друг друга. |

## 1. Что происходит внутри мьютекса

Мьютекс — это небольшое число в памяти плюс способ ждать. У захвата блокировки два случая:

```text
 lock():
   is the number "unlocked"?  ── yes ──▶ set it to "locked" with ONE atomic operation   (fast path, a few ns)
              │
              no
              ▼
   ask the OS: "put me to sleep until the lock is released"                            (slow path)
   ...sleep...
   the owner calls unlock() and the OS wakes one sleeping thread, which tries again
```

Быстрый путь никогда не обращается к OS. Это одна атомарная инструкция (Урок 14.5 покажет такие инструкции). Медленный путь стоит намного дороже: **системный вызов** ([Урок 13.3](../13-operating-systems/03-system-calls.md)), переключение контекста с этого потока и позже переключение обратно.

Как OS усыпляет поток, зависит от системы. В Linux стандартная библиотека Rust использует системный вызов **futex**: «спать, пока это число всё ещё имеет это значение». В macOS она использует мьютекс **pthread** из системной библиотеки, который делает ту же работу с ядром macOS. Сами вы их никогда не вызываете — это делает `Mutex::lock`.

Измерим разницу. Создайте `src/bin/lock_cost.rs`:

```rust
use std::sync::{Arc, Mutex};
use std::thread;
use std::time::Instant;

const TOTAL: u64 = 4_000_000;

fn main() {
    // 1. One thread: nobody else wants the lock (uncontended).
    let counter = Mutex::new(0u64);
    let start = Instant::now();
    for _ in 0..TOTAL {
        *counter.lock().unwrap() += 1;
    }
    let one = start.elapsed().as_nanos() as f64 / TOTAL as f64;
    println!("1 thread : {one:>5.1} ns per lock");

    // 2. Four threads fight for the same lock (contended).
    let counter = Arc::new(Mutex::new(0u64));
    let start = Instant::now();
    let handles: Vec<_> = (0..4)
        .map(|_| {
            let counter = Arc::clone(&counter);
            thread::spawn(move || {
                for _ in 0..TOTAL / 4 {
                    *counter.lock().unwrap() += 1;
                }
            })
        })
        .collect();
    for handle in handles {
        handle.join().unwrap();
    }
    let four = start.elapsed().as_nanos() as f64 / TOTAL as f64;
    println!("4 threads: {four:>5.1} ns per lock");
    println!("total = {}", *counter.lock().unwrap());
}
```

Всегда измеряйте в релизном режиме: `cargo run --release --bin lock_cost`.

```text
1 thread :   4.2 ns per lock
4 threads:  10.7 ns per lock
total = 4000000
```

**Что происходит:**

1. Обе части делают одну и ту же работу: 4 миллиона увеличений, каждое внутри своей пары «заблокировать — разблокировать».
2. С одним потоком блокировка всегда свободна, поэтому каждый `lock()` идёт по быстрому пути: около 4 нс.
3. С четырьмя потоками работа разделена, но блокировка пускает внутрь только один поток за раз. Значит, работа всё равно выполняется одно увеличение за другим, *плюс* потоки теперь ждут друг друга, будят друг друга и перегоняют *кэш-линию* блокировки (небольшой блок памяти, 128 байт на чипах Apple M, который ядро копирует в свой кэш, [Урок 12.9](../12-computer-systems/09-memory-hierarchy-and-caches.md)) между ядрами CPU (Central Processing Unit, центральный процессор). С четырьмя потоками вся работа заняла примерно **в 2,5 раза больше времени**, чем с одним.
4. Ваши числа будут другими (они зависят от машины и от того, что ещё запущено), но картина останется: горячая общая блокировка не становится быстрее от добавления потоков.

> ⚡ **Производительность:** свободная блокировка дешёвая, *нагруженная* — дорогая. Когда профиль показывает, что потоки ждут блокировку, не добавляйте потоки. Сделайте критическую секцию короче (готовьте данные до захвата блокировки), берите блокировку реже (накапливайте локально, потом обновляйте один раз) или разделите блокировку (раздел 5).

## 2. Сколько живёт guard-объект?

Guard-объект снимает блокировку, когда его **уничтожают** (drop). Guard с именем (`let guard = m.lock().unwrap();`) уничтожается в конце своего блока или раньше, через `drop(guard)`. Guard без имени — это **временное значение**, и в правилах для временных значений есть ловушка.

Эта программа берёт задание из списка и хочет добавить следующее задание. Создайте `src/bin/match_lock.rs`:

```rust
use std::sync::Mutex;

fn main() {
    let jobs = Mutex::new(vec![1, 2, 3]);

    match jobs.lock().unwrap().pop() {
        Some(job) => {
            println!("got job {job}, adding a follow-up job");
            jobs.lock().unwrap().push(job * 10); // hangs here
        }
        None => println!("no jobs"),
    }
    println!("jobs: {:?}", jobs.lock().unwrap());
}
```

```text
got job 3, adding a follow-up job
```

И дальше ничего. Программа висит вечно (остановите её через `Ctrl+C`).

**Что происходит:**

1. `jobs.lock().unwrap()` создаёт guard без имени. Через него вызывается `.pop()`.
2. Guard — часть **проверяемого выражения** `match` (выражения после `match`). Rust держит временные значения проверяемого выражения живыми **до конца всего `match`**, потому что образец ещё может заимствовать из них.
3. Поэтому внутри ветки `Some(job)` первый guard ещё жив и мьютекс всё ещё заблокирован. Второй `jobs.lock()` ждёт блокировку, которую держит этот же поток: взаимная блокировка с самим собой, как в Уроке 14.1.
4. У `if let Some(job) = jobs.lock().unwrap().pop() { … }` та же проблема: в редакции 2024 временное значение уничтожается перед блоком `else`, но внутри блока `if` оно ещё живо. Попробуйте: программа зависает в том же месте.

Исправление — закончить жизнь guard-объекта инструкцией `let`. Временное значение в `let` живёт только до `;`:

```rust
use std::sync::Mutex;

fn main() {
    let jobs = Mutex::new(vec![1, 2, 3]);

    let next = jobs.lock().unwrap().pop(); // the guard is dropped at the `;`
    match next {
        Some(job) => {
            println!("got job {job}, adding a follow-up job");
            jobs.lock().unwrap().push(job * 10);
        }
        None => println!("no jobs"),
    }
    println!("jobs: {:?}", jobs.lock().unwrap());
}
```

```text
got job 3, adding a follow-up job
jobs: [1, 2, 30]
```

> ⚠️ **Частая ошибка:** `match m.lock().unwrap().something() { … }` и `if let … = m.lock().unwrap()…` держат блокировку весь блок. Компилятор не предупреждает. Сначала вынесите вызов под блокировкой в отдельный `let`.

> 📏 **Соглашение:** делайте время жизни каждого guard-объекта очевидным. Либо дайте ему имя и держите блок коротким, либо вызовите `drop(guard)` там, где заканчивается критическая секция.

## 3. `try_lock`, отравление и блокировка без блокировки

Иногда ждать нельзя: поток, который рисует экран, или запрос с крайним сроком. `try_lock` берёт блокировку, только если она свободна **сейчас**. Если блокировка занята, он сразу возвращает `Err(TryLockError::WouldBlock)`.

**Отравление** вы уже знаете из Урока 05.10: если поток паникует, держа guard, мьютекс помечается как отравленный, и следующие вызовы `lock()` возвращают `Err`. Эта ошибка — не тупик. Внутри неё лежит guard, и его можно достать, если вы решите, что данные ещё пригодны. Создайте `src/bin/try_and_poison.rs`:

```rust
use std::sync::{Arc, Mutex, TryLockError};
use std::thread;

fn main() {
    let data = Arc::new(Mutex::new(vec![1, 2, 3]));

    // try_lock: do not wait if the lock is busy.
    let guard = data.lock().unwrap();
    match data.try_lock() {
        Ok(_) => println!("try_lock: got it"),
        Err(TryLockError::WouldBlock) => println!("try_lock: busy, do something else"),
        Err(TryLockError::Poisoned(_)) => println!("try_lock: poisoned"),
    }
    drop(guard); // end the critical section early

    // A worker panics in the middle of an update.
    let worker_data = Arc::clone(&data);
    let result = thread::spawn(move || {
        let mut v = worker_data.lock().unwrap();
        v.push(4);
        panic!("worker crashed after push");
    })
    .join();
    println!("worker failed: {}", result.is_err());

    // Recover: take the data out of the PoisonError and look at it.
    let v = data.lock().unwrap_or_else(|poisoned| poisoned.into_inner());
    println!("data after the crash: {:?}", *v);
    drop(v);

    data.clear_poison();
    println!("poisoned now: {}", data.is_poisoned());
}
```

```text
try_lock: busy, do something else

thread '<unnamed>' (5404093) panicked at src/bin/try_and_poison.rs:21:9:
worker crashed after push
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
worker failed: true
data after the crash: [1, 2, 3, 4]
poisoned now: false
```

**Что происходит:**

1. Главный поток держит `guard`, поэтому `try_lock` на том же мьютексе не может пройти. Он не зависает (в отличие от `lock()` в Уроке 14.1): он сразу возвращает `WouldBlock`.
2. `drop(guard)` отпускает блокировку до запуска рабочего потока. Без этого рабочий поток ждал бы вечно.
3. Рабочий поток добавляет `4` и паникует, держа guard. Сообщение о панике идёт в стандартный поток ошибок; число в скобках — идентификатор потока, у вас оно будет другим.
4. Теперь `lock()` возвращает `Err(PoisonError)`. `unwrap_or_else(|poisoned| poisoned.into_inner())` достаёт guard из ошибки. Мы видим `[1, 2, 3, 4]`: добавление успело произойти до паники.
5. `clear_poison()` снимает пометку после того, как вы проверили или починили данные.

Когда восстановление правильно? Когда каждое отдельное изменение оставляет данные корректными (добавление в список, запись счётчика). Когда неправильно? Когда паника могла прервать многошаговое обновление на середине, как в банке из Урока 14.1. Тогда данным доверять нельзя, и `unwrap()` (передать панику дальше) — честный выбор.

Два метода вообще не блокируют, потому что компилятор может доказать, что никто другой мьютексом пользоваться не может:

- `mutex.get_mut()` принимает `&mut self` и возвращает `&mut T`. Если у вас есть `&mut Mutex<T>`, ни у какого другого потока не может быть ссылки на него, поэтому блокировка не нужна.
- `mutex.into_inner()` поглощает мьютекс и возвращает данные, например после того как все потоки дождались через `join`.

> 💡 **Совет:** `try_lock` полезен для работы вида «сделай, если можешь, пропусти, если нет», например для необязательного обновления статистики. Не стройте из него цикл повторов без случайной паузы — так начинается активная блокировка (Урок 14.1).

## 4. Блокировки чтения-записи

Многие программы читают общие данные гораздо чаще, чем меняют: конфигурацию, таблицу маршрутов, кэш. Мьютекс пускает только одного читателя за раз, хотя читатели не могут навредить друг другу. **Блокировка чтения-записи** это исправляет:

```text
 RwLock state         who may enter
 ─────────────        ─────────────────────────────
 free                 one writer OR any number of readers
 N readers inside     more readers; writers wait
 1 writer inside      nobody else
```

У `std::sync::RwLock<T>` вместо `lock` два метода: `read()` возвращает guard, дающий `&T`, а `write()` — guard, дающий `&mut T`. Много guard-объектов чтения могут существовать одновременно; guard записи — исключительный. Отравление работает как у `Mutex` (блокировку отравляет только паникующий *писатель*).

Всегда ли это быстрее? Измерим. Восемь потоков каждый по 20 000 раз читают вектор и суммируют его — один раз под `Mutex`, другой раз под `RwLock`; пробуем короткий вектор (10 чисел) и длинный (10 000 чисел). Создайте `src/bin/rw_vs_mutex.rs`:

```rust
use std::hint::black_box;
use std::sync::{Mutex, RwLock};
use std::thread;
use std::time::{Duration, Instant};

const THREADS: usize = 8;
const READS: usize = 20_000;

/// Runs `read_once` READS times in each of THREADS threads; returns the time.
fn time_readers(read_once: impl Fn() -> u64 + Sync) -> Duration {
    let start = Instant::now();
    thread::scope(|s| {
        for _ in 0..THREADS {
            s.spawn(|| {
                for _ in 0..READS {
                    black_box(read_once());
                }
            });
        }
    });
    start.elapsed()
}

fn main() {
    for len in [10, 10_000] {
        let data: Vec<u64> = (0..len).collect();
        let mutex = Mutex::new(data.clone());
        let rwlock = RwLock::new(data);

        let m = time_readers(|| mutex.lock().unwrap().iter().sum());
        let r = time_readers(|| rwlock.read().unwrap().iter().sum());
        println!("vector of {len:>6}: Mutex {m:>9.2?}   RwLock {r:>9.2?}");
    }
}
```

`cargo run --release --bin rw_vs_mutex`, два запуска:

```text
vector of     10: Mutex    2.08ms   RwLock   27.00ms
vector of  10000: Mutex  234.56ms   RwLock   24.57ms
vector of     10: Mutex    2.16ms   RwLock   23.99ms
vector of  10000: Mutex  183.26ms   RwLock   21.55ms
```

**Что происходит:**

1. `time_readers` принимает замыкание, которое делает одно чтение, запускает его в 8 scoped-потоках ([Урок 05.10](../05-rust-intermediate/10-threads-channels-and-shared-state.md)) и измеряет время. Замыкание должно быть `Sync`, потому что его делят все потоки. `black_box` (из Урока 05.12) не даёт компилятору удалить результат, которым никто не пользуется.
2. **Длинные чтения** (10 000 чисел): с `Mutex` 8 потоков суммируют по очереди; с `RwLock` — одновременно. `RwLock` примерно **в 8–10 раз быстрее**: близко к числу потоков.
3. **Короткие чтения** (10 чисел): `RwLock` примерно **в 10 раз медленнее**! Каждый `read()` должен менять общий *счётчик читателей* (на одного читателя больше, на одного меньше) атомарными операциями. Когда работа внутри крошечная, все потоки борются за этот счётчик, и его кэш-линия всё время прыгает между ядрами. Простой мьютекс выигрывает.
4. Вывод: `RwLock` окупается, когда чтения **длинные** и **частые**, а записи **редкие**. Для крошечных критических секций обычно лучше `Mutex`. Измеряйте свой случай.

Ещё два факта из документации `RwLock`:

- **Политика зависит от OS.** Не обещается, блокируют ли ожидающие писатели новых читателей (это защищает от голодания писателя). На некоторых системах непрерывный поток читателей может заставить писателя ждать долго.
- **Не берите блокировку чтения дважды в одном потоке.** Если между вашими двумя вызовами `read()` начнёт ждать писатель, блокировка, отдающая предпочтение писателям, задержит ваш второй `read()`, писатель будет ждать ваш первый — и получится взаимная блокировка.

> 🧪 **Тестирование:** с `RwLock` легко обновлять **несколько значений как одно целое**: измените их все под одним guard-объектом записи, и читатели никогда не увидят половину изменения. Именно это проверяет Упражнение 2.

## 5. Одна блокировка или много: гранулярность и шардирование

**Гранулярность блокировок** — это сколько данных защищает одна блокировка. Одна блокировка вокруг всего `HashMap` проста и корректна, но каждый поток ждёт каждый другой, даже если они работают с разными ключами.

**Шардирование** (его ещё называют *lock striping*) делит данные на N частей — *шардов*, у каждого своя блокировка. Ключ всегда попадает в один и тот же шард, выбранный по его хешу:

```text
               hash("apple") % 4 = 1
 key "apple" ───────────────────────────▶ shard 1: Mutex<HashMap>
 key "pear"  ──── hash % 4 = 3 ─────────▶ shard 3: Mutex<HashMap>
 key "plum"  ──── hash % 4 = 1 ─────────▶ shard 1: Mutex<HashMap>  (waits only for "apple")

 shard 0: Mutex<HashMap>   shard 2: Mutex<HashMap>   (free for other keys)
```

Потоки, работающие с ключами из разных шардов, никогда не ждут друг друга. С 16 шардами и 8 потоками большинство вызовов `lock` идут по быстрому пути. Вы напишете такой счётчик в Упражнении 3. Цена: операция, которой нужны *все* данные (например «посчитать все ключи»), должна заблокировать каждый шард, а если ей нужна согласованная картина — держать все блокировки сразу, в фиксированном порядке (Урок 14.1).

> 💡 **Совет:** крейт `parking_lot` (версия `"0.13"`) предлагает типы `Mutex` и `RwLock`, которые чуть меньше, не имеют отравления (`lock()` сразу возвращает guard) и добавляют возможности вроде честного снятия блокировки. Стандартных блокировок хватает большинству программ, и этот курс использует их.

## Частые ошибки

1. **Guard в проверяемом выражении `match` или `if let`.** Блокировка остаётся взятой весь блок; повторный захват внутри зависает. Сначала вынесите вызов в `let` (раздел 2).
2. **Медленная работа внутри критической секции.** Чтение файла, сетевой запрос или обильная печать под блокировкой заставляют ждать все остальные потоки. Подготовьте всё снаружи, заблокируйте, измените, разблокируйте.
3. **`RwLock` для крошечных чтений.** Он может быть намного медленнее `Mutex` (раздел 4). Измерьте, прежде чем переходить на него.
4. **Восстановление после отравления не задумываясь.** `into_inner()` на `PoisonError` даёт данные, которые могут быть обновлены наполовину. Восстанавливайтесь, только если каждое изменение оставляет данные корректными.
5. **Цикл повторов `try_lock` без паузы.** Потоки могут раз за разом проигрывать в одном ритме (активная блокировка). Используйте `lock()` или добавьте короткую случайную паузу между попытками.

## Упражнения

### Упражнение 1 — Два guard-объекта в одной строке (легко)

Эта функция должна перенести последний элемент `a` в конец `b`. Приведённый ниже `main` работает, но функция зависает, если вызвать её как `move_last(&a, &a)`, и может попасть во взаимную блокировку с другим потоком, который одновременно выполняет `move_last(&b, &a)`. Объясните обе проблемы, а затем перепишите функцию так, чтобы она никогда не держала две блокировки сразу.

```rust
use std::sync::Mutex;

fn move_last(a: &Mutex<Vec<i32>>, b: &Mutex<Vec<i32>>) {
    if let Some(x) = a.lock().unwrap().pop() {
        b.lock().unwrap().push(x);
    }
}

fn main() {
    let a = Mutex::new(vec![1, 2, 3]);
    let b = Mutex::new(vec![]);
    move_last(&a, &b);
    println!("a = {:?}, b = {:?}", a.lock().unwrap(), b.lock().unwrap());
}
```

<details>
<summary>Подсказка</summary>

Внутри блока `if let` guard-объект `a` ещё жив (раздел 2). Что, если функция сначала достанет элемент, закончит эту критическую секцию и только потом заблокирует `b`?

</details>

<details>
<summary>Ответ</summary>

Внутри блока `if let` временный guard `a` ещё жив, поэтому функция держит `a`, пока блокирует `b`. Если `a` и `b` — один и тот же мьютекс, она блокирует его дважды и зависает. Если другой поток в это же время выполняет `move_last(&b, &a)`, два потока берут блокировки в противоположном порядке: взаимная блокировка. Элементу не нужны обе блокировки одновременно:

```rust
use std::sync::Mutex;

fn move_last(a: &Mutex<Vec<i32>>, b: &Mutex<Vec<i32>>) {
    let item = a.lock().unwrap().pop(); // guard of `a` dropped here
    if let Some(x) = item {
        b.lock().unwrap().push(x);
    }
}

fn main() {
    let a = Mutex::new(vec![1, 2, 3]);
    let b = Mutex::new(vec![]);
    move_last(&a, &b);
    println!("a = {:?}, b = {:?}", a.lock().unwrap(), b.lock().unwrap());
}
```

```text
a = [1, 2], b = [3]
```

Почему это работает: каждая блокировка удерживается в одиночку, поэтому ни один поток не ждёт вторую блокировку, держа первую: условие 2 из Урока 14.1 («удержание и ожидание») нарушено. Обратите внимание на компромисс: между двумя критическими секциями другой поток может не найти элемент ни в одном из векторов. Если для вашего инварианта это важно, нужны обе блокировки в фиксированном порядке.

</details>

### Упражнение 2 — Читатели никогда не видят половину обновления (средне)

Напишите `src/bin/config.rs` с типом `Config`, который хранит `RwLock<HashMap<String, String>>` и имеет методы `get(&self, key) -> Option<String>` и `set_many(&self, pairs: &[(&str, &str)])`, задающий все пары под **одним** guard-объектом записи. Затем напишите тест: один поток-писатель присваивает `a` и `b` одно и то же значение (`"1"`, `"2"`, …, `"1000"`), а четыре потока-читателя 1000 раз проверяют под одним guard-объектом чтения, что `a == b`. В конце `a` должно быть `"1000"`.

<details>
<summary>Подсказка</summary>

Используйте `thread::scope`, чтобы потоки могли заимствовать `config` без `Arc`. В читателе возьмите `let map = config.values.read().unwrap();` один раз и сравнивайте `map["a"]` с `map["b"]` через один и тот же guard. Два отдельных вызова `get` были бы двумя критическими секциями.

</details>

<details>
<summary>Ответ</summary>

```rust
use std::collections::HashMap;
use std::sync::RwLock;

struct Config {
    values: RwLock<HashMap<String, String>>,
}

impl Config {
    fn new() -> Self {
        Config {
            values: RwLock::new(HashMap::new()),
        }
    }

    fn get(&self, key: &str) -> Option<String> {
        self.values.read().unwrap().get(key).cloned()
    }

    /// Sets several keys in ONE write lock: readers see all or nothing.
    fn set_many(&self, pairs: &[(&str, &str)]) {
        let mut map = self.values.write().unwrap();
        for (k, v) in pairs {
            map.insert(k.to_string(), v.to_string());
        }
    }
}

fn main() {
    let config = Config::new();
    config.set_many(&[("host", "localhost"), ("port", "8080")]);
    println!("{:?} {:?}", config.get("host"), config.get("port"));
}

#[cfg(test)]
mod tests {
    use super::*;
    use std::thread;

    #[test]
    fn readers_never_see_half_an_update() {
        let config = Config::new();
        config.set_many(&[("a", "0"), ("b", "0")]);
        thread::scope(|s| {
            s.spawn(|| {
                for i in 1..=1000 {
                    let v = i.to_string();
                    config.set_many(&[("a", &v), ("b", &v)]);
                }
            });
            for _ in 0..4 {
                s.spawn(|| {
                    for _ in 0..1000 {
                        let map = config.values.read().unwrap(); // one read lock
                        assert_eq!(map["a"], map["b"]);
                    }
                });
            }
        });
        assert_eq!(config.get("a").as_deref(), Some("1000"));
    }
}
```

```text
running 1 test
test tests::readers_never_see_half_an_update ... ok
```

`cargo run --bin config` печатает `Some("localhost") Some("8080")`.

Почему это работает: писатель меняет `a` и `b` внутри одного guard-объекта записи, а читатель смотрит на оба значения внутри одного guard-объекта чтения. Эти две критические секции никогда не пересекаются, поэтому читатель видит либо старую пару, либо новую, но никогда не смесь. Паника в потоке-читателе заставила бы запаниковать и `thread::scope`, поэтому упавший `assert_eq!` проваливает тест.

</details>

### Упражнение 3 — Шардированный счётчик (сложно)

Напишите `src/bin/sharded.rs` с типом `ShardedCounter`, который считает, сколько раз добавлялся каждый ключ. Он хранит `Vec<Mutex<HashMap<String, u64>>>`; методы `new(shards)`, `add(&self, key)` и `get(&self, key) -> u64` (0 для неизвестных ключей). Шард выбирайте с помощью `DefaultHasher`. Тест: 8 потоков каждый по 1000 раз добавляют 10 ключей `key0`…`key9`; затем у каждого ключа должно быть значение 8000.

<details>
<summary>Подсказка</summary>

```rust
let mut hasher = DefaultHasher::new();
key.hash(&mut hasher);                    // needs `use std::hash::{Hash, Hasher};`
let index = (hasher.finish() as usize) % self.shards.len();
```

Напишите приватный помощник `shard_for(&self, key) -> &Mutex<HashMap<String, u64>>` и используйте его в `add` и `get`.

</details>

<details>
<summary>Ответ</summary>

```rust
use std::collections::HashMap;
use std::collections::hash_map::DefaultHasher;
use std::hash::{Hash, Hasher};
use std::sync::Mutex;

struct ShardedCounter {
    shards: Vec<Mutex<HashMap<String, u64>>>,
}

impl ShardedCounter {
    fn new(shards: usize) -> Self {
        ShardedCounter {
            shards: (0..shards).map(|_| Mutex::new(HashMap::new())).collect(),
        }
    }

    fn shard_for(&self, key: &str) -> &Mutex<HashMap<String, u64>> {
        let mut hasher = DefaultHasher::new();
        key.hash(&mut hasher);
        let index = (hasher.finish() as usize) % self.shards.len();
        &self.shards[index]
    }

    fn add(&self, key: &str) {
        let mut map = self.shard_for(key).lock().unwrap();
        *map.entry(key.to_string()).or_insert(0) += 1;
    }

    fn get(&self, key: &str) -> u64 {
        self.shard_for(key)
            .lock()
            .unwrap()
            .get(key)
            .copied()
            .unwrap_or(0)
    }
}

fn main() {
    let counter = ShardedCounter::new(16);
    counter.add("apple");
    counter.add("apple");
    counter.add("pear");
    println!(
        "apple = {}, pear = {}, plum = {}",
        counter.get("apple"),
        counter.get("pear"),
        counter.get("plum")
    );
}

#[cfg(test)]
mod tests {
    use super::*;
    use std::thread;

    #[test]
    fn counts_are_exact_with_many_threads() {
        let counter = ShardedCounter::new(16);
        let keys: Vec<String> = (0..10).map(|i| format!("key{i}")).collect();
        thread::scope(|s| {
            for _ in 0..8 {
                s.spawn(|| {
                    for _ in 0..1000 {
                        for key in &keys {
                            counter.add(key);
                        }
                    }
                });
            }
        });
        for key in &keys {
            assert_eq!(counter.get(key), 8000, "wrong count for {key}");
        }
    }
}
```

```text
apple = 2, pear = 1, plum = 0
```

`cargo test --bin sharded` проходит: `test tests::counts_are_exact_with_many_threads ... ok`.

Почему это работает: один и тот же ключ всегда даёт один и тот же хеш, поэтому всегда попадает в один и тот же шард, а `HashMap` каждого шарда защищён своим мьютексом. Каждый `add` — одна критическая секция в одном шарде, поэтому ни одно обновление не теряется, а потоки, работающие с ключами из разных шардов, не ждут друг друга.

</details>

## Вопросы для самопроверки

1. Чем быстрый путь `lock()` отличается от медленного?

<details>
<summary>Ответ</summary>

Быстрый путь: блокировка свободна, и поток берёт её одной атомарной операцией в пространстве пользователя, за несколько наносекунд. Медленный путь: блокировка занята, поэтому поток просит OS усыпить его (futex в Linux, мьютекс pthread в macOS), и его будят позже: системные вызовы и переключения контекста, намного медленнее.

</details>

2. Почему `match m.lock().unwrap().pop() { Some(x) => m.lock().unwrap().push(x), None => {} }` зависает?

<details>
<summary>Ответ</summary>

Guard — временное значение в проверяемом выражении `match`, а такие временные значения живут до конца всего `match`. Внутри ветки мьютекс всё ещё заблокирован, поэтому второй `lock()` вечно ждёт тот же самый поток.

</details>

3. Когда правильно восстанавливаться после отравленного мьютекса через `into_inner()`?

<details>
<summary>Ответ</summary>

Когда каждое изменение данных оставляет их корректными, и паника посередине не может их сломать (например, счётчик или список, в который только добавляют). Если паника может прервать многошаговое обновление, инвариант может быть нарушен, и лучше остановиться через `unwrap()`.

</details>

4. Почему `RwLock` может быть медленнее `Mutex`, даже если все потоки только читают?

<details>
<summary>Ответ</summary>

Каждый `read()` и каждое уничтожение guard-объекта чтения меняют общий счётчик читателей атомарными операциями. Когда работа под блокировкой крошечная, потоки тратят большую часть времени на борьбу за кэш-линию этого счётчика. `RwLock` помогает, когда сами чтения длинные.

</details>

5. Что даёт шардирование словаря и чего оно стоит?

<details>
<summary>Ответ</summary>

Потоки, работающие с ключами из разных шардов, не ждут друг друга, поэтому конкуренция за блокировки падает. Цена: операции над всеми ключами должны блокировать все шарды (в фиксированном порядке, если нужна согласованная картина), а код становится сложнее.

</details>

## Итоги

- Взять свободную блокировку дёшево (одна атомарная операция). Нагруженная блокировка медленная: потоки засыпают и просыпаются через OS, а работа всё равно идёт по одному потоку за раз.
- Больше потоков не делают горячую блокировку быстрее. Сокращайте критическую секцию, блокируйте реже или разделяйте блокировку.
- Guard в проверяемом выражении `match` или `if let` живёт весь блок. Выносите вызов под блокировкой в `let` или вызывайте `drop(guard)`, когда закончили.
- `try_lock` никогда не ждёт. Отравленная блокировка всё ещё хранит свои данные: `into_inner()` возвращает их, когда им можно доверять. `get_mut` и `into_inner` вообще не требуют блокировки.
- `RwLock` пускает многих читателей одновременно. Он выигрывает при длинных чтениях и редких записях и может сильно проиграть при крошечных чтениях. Его политика по отношению к писателям зависит от OS.
- Шардирование даёт каждой части данных свою блокировку, поэтому потоки, работающие с разными частями, не ждут друг друга.
