## Новые слова

| Слово | Значение |
|---|---|
| **фаззинг** (fuzzing) | Запуск вашего кода снова и снова с автоматически сгенерированным, часто странным вводом в поисках падений. |
| **фаззер** (fuzzer) | Программа, которая генерирует входы и следит за сбоями. |
| **цель фаззинга** (fuzz target) | Крошечная функция, которую вы пишете: «возьми эти байты и передай их моему коду». Фаззер вызывает её миллионы раз. |
| **управляемый покрытием** (coverage-guided) | Фаззер следит, какие строки вашего кода затрагивает каждый вход. Вход, дошедший до новой строки, сохраняется и мутируется дальше. |
| **корпус** (corpus) | Папка с интересными входами, которые собрал фаззер. Растёт, пока фаззер работает. |
| **мутация** (mutation) | Небольшое случайное изменение сохранённого входа: перевернуть бит, вставить байт, скопировать кусок. |
| **артефакт падения** (crash artifact) | Файл с точным входом, на котором программа упала. |
| **libFuzzer** | Движок фаззинга из проекта LLVM (набор компиляторных инструментов, которым пользуется Rust). `cargo-fuzz` управляет им. |
| **санитайзер** (sanitizer) | Инструмент, встроенный в компилятор: он добавляет в программу проверки во время работы. `cargo-fuzz` включает AddressSanitizer, который ловит неверное использование памяти. |
| **минимизация** (`tmin`) | Уменьшение падающего входа до минимально возможного, чтобы его было легко понять. |
| **структурированный фаззинг** (structured fuzzing) | Фаззинг с типизированным вводом (например, структурой) вместо сырых байтов. |
| **круговое преобразование** (round trip) | Превращение значения в другую форму и обратно (закодировать, затем раскодировать). Результат должен совпасть с началом. |

## 1. Зачем нужен фаззинг?

Вы пишете функцию, которая читает данные снаружи: файл, сетевое сообщение, текст, набранный человеком. Вы проверяете её пятью входами, которые можете представить. Потом пользователь присылает пять тысяч первый вход, который вы не могли вообразить, и программа паникует.

**Фаззинг** автоматизирует этот «невообразимый» ввод. *Фаззер* генерирует от тысяч до миллионов входов в секунду, запускает на каждом ваш код и сообщает первый вход, который вызывает панику, переполнение, нехватку памяти или зависание.

Одни только случайные байты тратили бы время зря: большинство случайных байтов не проходит уже первую проверку вашего парсера. Современные фаззеры **управляются покрытием** (coverage-guided): компилятор добавляет в код маленькие счётчики, и фаззер видит, какие части кода затронул каждый вход. Цикл выглядит так:

```text
  ┌──────────────┐  pick one   ┌───────────────┐  change a few   ┌──────────────┐
  │   corpus     │ ──────────▶ │ stored input  │ ──────────────▶ │ new mutation │
  │ (saved files)│             └───────────────┘   bytes         └──────┬───────┘
  └──────▲───────┘                                                      │ run your code
         │ reached a NEW line?                                          ▼
         └───────────────── yes: keep it ◀──────────────  ┌────────────────────────┐
                                                          │ crash? save the input  │
                                                          └────────────────────────┘
```

Поскольку фаззер хранит каждый вход, открывающий новую ветку, он постепенно «узнаёт» форму корректного ввода: находит правильный первый байт, затем правильный второй и так далее.

> 🔒 **Безопасность:** фаззинг — один из главных способов, которыми находят серьёзные ошибки в настоящих парсерах (декодерах изображений, сетевых протоколах, форматах файлов). Любой код, читающий байты извне вашей программы, — хороший кандидат для фаззинга, потому что злоумышленник может прислать именно тот странный вход, который найдёт фаззер.

Фаззинг отличается от тестов, которые вы писали раньше. Модульный тест говорит: «для этого входа ответ X». Цель фаззинга говорит только: «для **любого** входа не падай» (а с проверками внутри — «и сохраняй это правило истинным»). Она не знает правильных ответов, она знает только правила.

## 2. Установка и начало работы

Для фаззинга в Rust нужны две вещи: инструмент `cargo-fuzz` и компилятор **nightly**. `cargo-fuzz` использует параметры компилятора, которые есть только в nightly Rust. Ваш обычный код остаётся на stable; nightly используют только команды фаззинга.

```bash
cargo install --locked cargo-fuzz
cargo fuzz --version
```

```text
cargo-fuzz 0.13.2
```

Теперь создадим библиотеку, которую будем «атаковать». Она читает крошечный двоичный формат: один байт с длиной имени, затем само имя как текст UTF-8 (UTF-8, Unicode Transformation Format 8-bit, формат преобразования Юникода, — стандартный способ хранить текст в байтах, Урок 03.6), затем один байт `count`. Например, `[3, b'a', b'b', b'c', 7]` означает имя `"abc"` и счётчик `7`.

```bash
cd ~/projects/rust/code
cargo new --lib p09-fuzzing
cd p09-fuzzing
```

Поместите в `src/lib.rs`:

```rust
/// One record of a tiny binary format:
/// byte 0 = length of the name, then the name (UTF-8), then one byte `count`.
#[derive(Debug, PartialEq, Eq)]
pub struct Record {
    pub name: String,
    pub count: u8,
}

#[derive(Debug, PartialEq, Eq)]
pub enum ParseError {
    Empty,
    BadUtf8,
}

pub fn parse_record(data: &[u8]) -> Result<Record, ParseError> {
    if data.is_empty() {
        return Err(ParseError::Empty);
    }
    let len = data[0] as usize;
    let name_bytes = &data[1..1 + len];
    let name = std::str::from_utf8(name_bytes).map_err(|_| ParseError::BadUtf8)?;
    let count = data[1 + len];
    Ok(Record {
        name: name.to_string(),
        count,
    })
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn parses_a_valid_record() {
        let data = [3, b'a', b'b', b'c', 7];
        assert_eq!(
            parse_record(&data),
            Ok(Record { name: "abc".to_string(), count: 7 })
        );
    }

    #[test]
    fn empty_input_is_an_error() {
        assert_eq!(parse_record(&[]), Err(ParseError::Empty));
    }
}
```

**Что происходит:**

1. `parse_record` читает длину из байта 0, берёт столько байтов как имя, превращает их в текст через `std::str::from_utf8` (она возвращает ошибку, если байты не являются корректным UTF-8) и читает байт после имени как `count`.
2. Функция возвращает `Result`, то есть обещает сообщать о проблемах ошибками и никогда не паниковать. Именно это обещание мы и хотим проверить.
3. Оба теста проходят. Внимательный человек написал бы ещё несколько тестов. Посмотрим, что найдёт фаззер.

```bash
cargo test
```

```text
running 2 tests
test tests::empty_input_is_an_error ... ok
test tests::parses_a_valid_record ... ok

test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Создайте окружение для фаззинга:

```bash
cargo fuzz init
```

Появится новая папка `fuzz/`. Это отдельный пакет Cargo, зависящий от вашей библиотеки, со своим `Cargo.toml` и папкой `fuzz_targets/`. Также создаётся файл `fuzz/.gitignore`, который говорит Git игнорировать папки `target`, `corpus`, `artifacts` и `coverage` внутри `fuzz/`.

```text
p09-fuzzing/
├── Cargo.toml
├── src/lib.rs
└── fuzz/
    ├── Cargo.toml              ← the fuzz package (depends on your crate)
    ├── .gitignore
    └── fuzz_targets/
        └── fuzz_target_1.rs    ← the fuzz target (the generated name)
```

## 3. Цель фаззинга

Откройте `fuzz/fuzz_targets/fuzz_target_1.rs` и замените его содержимое:

```rust
#![no_main]

use libfuzzer_sys::fuzz_target;

fuzz_target!(|data: &[u8]| {
    let _ = p09_fuzzing::parse_record(data);
});
```

**Что происходит:**

1. `#![no_main]` говорит Rust не создавать собственную функцию `main`. У `libFuzzer` есть своя `main`, которая запускает цикл фаззинга.
2. `fuzz_target!` — макрос из крейта `libfuzzer-sys`. Замыкание после него вызывается по одному разу на каждый сгенерированный вход. `data` — срез байтов: сам вход.
3. Мы вызываем нашу функцию и игнорируем результат (`let _ =`). Нас не интересует, что она вернёт, только то, что она не паникует.
4. В коде крейт называется `p09_fuzzing`: дефисы превращаются в подчёркивания.

Если сейчас запустить `cargo fuzz run fuzz_target_1` с обычным компилятором stable, вы получите ошибку (сокращено):

```text
error: failed to run `rustc` to learn about target-specific information
  ...
  error: the option `Z` is only accepted on the nightly compiler
```

Исправление — выбрать nightly для одной этой команды через `+nightly`:

```bash
cargo +nightly fuzz run fuzz_target_1
```

```text
INFO: Seed: 398044694
INFO: Loaded 1 modules   (408 inline 8-bit counters): 408 [0x102805560, 0x1028056f8), 
INFO: A corpus is not provided, starting from an empty corpus

thread '<unnamed>' (4597100) panicked at src/lib.rs:20:27:
range end index 11 out of range for slice of length 1
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
==23035== ERROR: libFuzzer: deadly signal
...
Failing input:

	fuzz/artifacts/fuzz_target_1/crash-adc83b19e793491b1c6ea0fd8b46cd9f32e592fc

Output of `std::fmt::Debug`:

	[10]

Reproduce with:

	cargo fuzz run fuzz_target_1 fuzz/artifacts/fuzz_target_1/crash-adc83b19e793491b1c6ea0fd8b46cd9f32e592fc

Minimize test case with:

	cargo fuzz tmin fuzz_target_1 fuzz/artifacts/fuzz_target_1/crash-adc83b19e793491b1c6ea0fd8b46cd9f32e592fc
```

(Первая сборка занимает время. Ваше начальное число, номера процессов и имена файлов будут другими. Строки, начинающиеся с `#` и числа, — длинная трассировка стека, мы её опустили.)

**Как это читать:**

1. Первые строки — стартовый отчёт libFuzzer: его случайное начальное число (seed), сколько счётчиков кода он нашёл (`408` в нашей маленькой библиотеке) и что корпуса пока нет.
2. Строка `panicked at src/lib.rs:20:27` — то же сообщение о панике, которое вы знаете из Урока 02.9. Фаззер нашёл её за долю секунды.
3. `Failing input` — это **артефакт падения**: файл с точными байтами. `Output of std::fmt::Debug` показывает их как массив Rust: `[10]`. Один байт, `10`.
4. Затем печатаются две команды: одна воспроизводит падение, другая его минимизирует.

Объяснение ошибки: первый байт говорит «имя занимает 10 байтов», но других байтов нет. `&data[1..1 + len]` — это `&data[1..11]` для среза длиной 1, поэтому Rust паникует. Функция, возвращающая `Result`, только что запаниковала на входе из одного байта, и ни один из наших двух тестов об этом не подумал.

> 💡 **Совет:** самая полезная привычка: как только фаззер что-то нашёл, **воспроизведите** это напечатанной командой, чтобы убедиться, что падение настоящее и повторяемое, и только потом исправляйте.

## 4. Исправляем, запускаем снова, находим следующую ошибку

Добавьте новый вариант ошибки и используйте `get` вместо индексации. `slice.get(range)` возвращает `None` вместо паники, если диапазон выходит за пределы среза, а `ok_or(error)` превращает `None` в `Err`:

```rust
#[derive(Debug, PartialEq, Eq)]
pub enum ParseError {
    Empty,
    BadUtf8,
    Truncated,
}
```

и в `parse_record` замените строку, создающую `name_bytes`:

```rust
    let name_bytes = data.get(1..1 + len).ok_or(ParseError::Truncated)?;
```

Запустите фаззер снова:

```bash
cargo +nightly fuzz run fuzz_target_1
```

```text
#2	INITED cov: 26 ft: 26 corp: 1/1b exec/s: 0 rss: 36Mb
#39	NEW    cov: 29 ft: 29 corp: 2/3b lim: 4 exec/s: 0 rss: 36Mb L: 2/2 MS: 2 CrossOver-CMP- DE: "\000\000"-

thread '<unnamed>' (4598175) panicked at src/lib.rs:23:17:
index out of bounds: the len is 1 but the index is 1
...
	[0]
```

**Как это читать:** строки, начинающиеся с `#`, — отчёты о ходе работы. `cov: 29` — число достигнутых точек кода, `corp: 2/3b` означает, что в корпусе хранятся два входа общим размером три байта, а `NEW` говорит, что вход дошёл до нового кода. Новое падение — вход `[0]`: длина имени 0, пустое имя допустимо, но байта после имени, `data[1 + len]`, не существует. Исправьте и эту строку:

```rust
    let count = *data.get(1 + len).ok_or(ParseError::Truncated)?;
```

(`get` возвращает `Option<&u8>`, а `*` копирует байт из ссылки.) Запустите фаззер на десять секунд. Всё после `--` передаётся прямо в libFuzzer; `-max_total_time=10` означает «остановись через 10 секунд»:

```bash
cargo +nightly fuzz run fuzz_target_1 -- -max_total_time=10
```

```text
#2	INITED cov: 27 ft: 27 corp: 1/2b exec/s: 0 rss: 36Mb
#3	NEW    cov: 29 ft: 29 corp: 2/4b lim: 4 exec/s: 0 rss: 36Mb L: 2/2 MS: 1 ChangeBit-
#6	NEW    cov: 31 ft: 31 corp: 3/6b lim: 4 exec/s: 0 rss: 36Mb L: 2/2 MS: 3 ChangeBit-CopyPart-CopyPart-
...
#16513067	DONE   cov: 37 ft: 37 corp: 6/17b lim: 4096 exec/s: 1501187 rss: 611Mb
Done 16513067 runs in 11 second(s)
```

Шестнадцать миллионов запусков за одиннадцать секунд, падений нет. Число покрытия остановилось на `37`: фаззер дошёл до каждой ветки этой небольшой функции, поэтому дополнительное время не поможет. Это признак того, что цель «насыщена». (Значения вроде `exec/s` зависят от вашего Mac.)

Корпус лежит в `fuzz/corpus/fuzz_target_1/`: шесть маленьких файлов, которые вместе доходят до всего кода. При следующем запуске цели фаззер начнёт с них, а не с пустого места.

## 5. Превращаем каждое падение в регрессионный тест

Папка `fuzz/artifacts` игнорируется Git, как и корпус. Поэтому исправленные падения должны жить в постоянном месте: в обычных тестах. Добавьте это в модуль `tests` в `src/lib.rs`:

```rust
    #[test]
    fn crash_found_by_the_fuzzer_length_longer_than_data() {
        assert_eq!(parse_record(&[10]), Err(ParseError::Truncated));
    }

    #[test]
    fn crash_found_by_the_fuzzer_count_byte_missing() {
        assert_eq!(parse_record(&[0]), Err(ParseError::Truncated));
    }
```

Теперь `cargo test` при каждом запуске защищает от обеих ошибок меньше чем за секунду, без nightly и без фаззера.

> 🧪 **Тестирование:** правило «каждая найденная ошибка становится тестом» (*регрессионный тест*, Урок 05.6) действует и для находок фаззера. Называйте тест по тому, что произошло, чтобы читатель знал, откуда он взялся. Если падающий вход большой, сохраните файл артефакта в папку `tests/data/` и загрузите его через `include_bytes!("data/crash-1.bin")`.

Для такого маленького формата можно даже попробовать *каждый* вход длиной до двух байтов в обычном тесте (Упражнение 2). Для длинных входов число вариантов взрывается: три байта уже дают 16,7 миллиона входов. Тут в дело вступает фаззинг: он исследует огромное пространство *умно*, а не полностью.

## 6. Структурированный фаззинг и свойства

Сырые байты — правильный вход для парсера. Но иногда нужно протестировать код, который принимает типизированное значение, или проверить *правило* о результате. Крейт `arbitrary` строит значения Rust из байтов фаззера.

Проверим правило «**круговое преобразование**: если я записал запись и прочитал её обратно, я получаю ту же запись». Сначала добавим в `src/lib.rs` запись с небольшой ошибкой, которую легко допустить:

```rust
/// Writes a record in the format that `parse_record` reads.
pub fn encode_record(record: &Record) -> Vec<u8> {
    let mut bytes = Vec::new();
    bytes.push(record.name.len() as u8);
    bytes.extend_from_slice(record.name.as_bytes());
    bytes.push(record.count);
    bytes
}
```

(`as u8` отрезает число до младших 8 бит без всякого предупреждения, Урок 02.2. Имя в 256 байтов получило бы длину `0`.)

Добавьте крейт `arbitrary` в пакет **fuzz** (его `Cargo.toml` — это `fuzz/Cargo.toml`) с фичей `derive`, которая позволяет писать `#[derive(Arbitrary)]`, и зарегистрируйте вторую цель в конце этого файла:

```toml
[dependencies]
libfuzzer-sys = "0.4"
arbitrary = { version = "1", features = ["derive"] }

[[bin]]
name = "roundtrip"
path = "fuzz_targets/roundtrip.rs"
test = false
doc = false
bench = false
```

(Оставьте остальные строки, которые создал `cargo fuzz init`. Добавьте только показанное. Команда `cargo fuzz add roundtrip` сама создаёт файл цели и запись `[[bin]]`, и вам останется добавить только строку `arbitrary`.)

Создайте `fuzz/fuzz_targets/roundtrip.rs`:

```rust
#![no_main]

use arbitrary::Arbitrary;
use libfuzzer_sys::fuzz_target;
use p09_fuzzing::{Record, encode_record, parse_record};

#[derive(Debug, Arbitrary)]
struct Input {
    name: String,
    count: u8,
}

fuzz_target!(|input: Input| {
    let record = Record {
        name: input.name,
        count: input.count,
    };
    let bytes = encode_record(&record);
    assert_eq!(parse_record(&bytes), Ok(record));
});
```

**Что происходит:**

1. `#[derive(Arbitrary)]` создаёт код, который собирает `Input` из сырых байтов libFuzzer: первые байты становятся `String`, следующий — `u8`. Фаззер по-прежнему работает с байтами, но ваша цель видит типизированное значение.
2. `fuzz_target!(|input: Input| ...)` принимает типизированное значение напрямую. Тип `Input` должен реализовывать `Arbitrary` и `Debug` (для отчёта).
3. Тело создаёт `Record`, кодирует его, разбирает обратно и проверяет, что результат равен началу. Эта одна строка и есть всё **свойство**.

```bash
cargo +nightly fuzz run roundtrip -- -max_total_time=20
```

```text

...
thread '<unnamed>' (4603635) panicked at fuzz_targets/roundtrip.rs:19:5:
assertion `left == right` failed
```

Фаззеру нужно было имя длиннее 255 байтов, и он нашёл его за десятки тысяч запусков. Вход сохранён, но сырые байты трудно читать. Попросите фаззер минимизировать его:

```bash
cargo +nightly fuzz tmin roundtrip fuzz/artifacts/roundtrip/crash-ef395ca4346fca40e3f833914fa81130824a2213
```

```text
Minimized artifact:

	fuzz/artifacts/roundtrip/minimized-from-b00c2ee4af8e0c729b8811209a33618e5a2b9a57

Output of `std::fmt::Debug`:

	Input {
	    name: "\0\0\0\u{7}\0\u{8}\u{8}\u{8}\u{8}\u{8}\u{8}\u{8}\u{8}\u{8}\u{8}\u{8}\u{8}...",
	    count: 255,
	}
```

(У вас будет другое имя файла и имя длиной 256 байтов или больше; длинную строку мы обрезали.) Отчёт показывает настоящее значение `Input`. Это та самая ошибка, которую мы подложили: имя слишком длинное для одного байта длины.

**Исправление** должно быть в библиотеке, а не в цели фаззинга. Имя, которое не помещается, нельзя закодировать; скажем это в типе: вернём `None`. Замените `encode_record` на:

```rust
/// Writes a record in the format that `parse_record` reads.
/// Returns `None` when the name is longer than 255 bytes (the length must fit in one byte).
pub fn encode_record(record: &Record) -> Option<Vec<u8>> {
    let len = u8::try_from(record.name.len()).ok()?;
    let mut bytes = vec![len];
    bytes.extend_from_slice(record.name.as_bytes());
    bytes.push(record.count);
    Some(bytes)
}
```

**Что происходит:** `u8::try_from(usize)` возвращает `Err`, если число не помещается в `u8`; `.ok()` превращает `Result` в `Option`, а `?` досрочно возвращает `None`. Теперь обновите цель: имена, которые нельзя закодировать, просто пропускаются (это правило библиотеки, а не ошибка):

```rust
fuzz_target!(|input: Input| {
    let record = Record {
        name: input.name,
        count: input.count,
    };
    let Some(bytes) = encode_record(&record) else {
        return; // name too long: nothing to round-trip
    };
    assert_eq!(parse_record(&bytes), Ok(record));
});
```

Добавьте регрессионный тест в библиотеку, запустите `cargo test` и запустите фаззер на 15 секунд:

```rust
    #[test]
    fn names_longer_than_255_bytes_cannot_be_encoded() {
        let record = Record { name: "x".repeat(256), count: 1 };
        assert_eq!(encode_record(&record), None);
    }
```

```bash
cargo test
cargo +nightly fuzz run roundtrip -- -max_total_time=15
```

```text

...
#9045772	DONE   cov: 99 ft: 99 corp: 10/1313b lim: 4096 exec/s: 565360 rss: 527Mb
Done 9045772 runs in 16 second(s)
```

Девять миллионов круговых преобразований, и всё в порядке.

## 7. Что фаззинг умеет и чего не умеет

| Хорошо находит | Слабо находит |
|---|---|
| Паники, переполнение (сборка для фаззинга оставляет debug-проверки включёнными), выход индекса за границы | Логические ошибки, когда код возвращает *неверный, но допустимый* ответ, если вы не написали проверку (свойство) |
| Парсеры, декодеры, всё, что принимает байты или текст | Код со сложной подготовкой (базы данных, сети) |
| Ошибки памяти в `unsafe`-коде (AddressSanitizer включён) | Очень длинные «магические» значения и контрольные суммы, которые фаззер не может угадать |
| Зависания и огромное потребление памяти (у libFuzzer есть тайм-аут и лимит памяти) | Программы, медленные на каждом входе: фаззеру нужны тысячи запусков в секунду |

Практические правила:

1. **Делайте цель быстрой и детерминированной.** Никаких пауз, чтения часов, случайных чисел, файлов и сети. Одни и те же байты всегда должны давать один и тот же результат, иначе падение не воспроизвести.
2. **Ограничивайте время.** Фаззер никогда не «заканчивает». Запускайте его на фиксированное время: пять минут перед слиянием изменения в парсере, дольше — по расписанию. Это делает `-max_total_time=СЕКУНДЫ`. В Уроке 09.12 вы увидите, как задание CI (continuous integration, непрерывная интеграция: сервер, который автоматически проверяет каждое изменение) запускает короткий сеанс фаззинга.
3. **Фаззите в фоне вашей обычной работы.** Запустите перед обедом, прочитайте результат после.
4. **Коммитьте цели, а не корпус** (`.gitignore` по умолчанию правильный). Коммитьте *регрессионные тесты*, сделанные из находок.
5. **Фаззинг и тесты свойств дружат.** Тест свойств (Урок 09.4) выполняет несколько сотен случаев в `cargo test` при каждой сборке. Фаззинг работает минуты или часы и учится по покрытию. При желании используйте одно и то же свойство в обоих.

> ⚡ **Производительность:** `cargo fuzz` собирает проект в режиме release с оптимизацией и одновременно с debug-проверками, поэтому он быстрый, но всё же ловит переполнение целых чисел. Один запуск цели должен занимать микросекунды. Если один вход обрабатывается секунду, фаззинг становится бесполезным.

> 📏 **Соглашение:** называйте цели фаззинга по тому, что они проверяют (`parse_record`, `roundtrip`), храните их в `fuzz/fuzz_targets/` и пишите сверху комментарий со свойством.

## Частые ошибки

**1. Запуск `cargo fuzz` на тулчейне stable.** Вы получаете `error: the option Z is only accepted on the nightly compiler` (показано в разделе 3). Используйте `cargo +nightly fuzz run …`.

**2. Забытый `#![no_main]`.** Тогда в бинарном файле фаззинга две функции `main`: ваша и libFuzzer. Сборка падает или фаззер не стартует. Всегда оставляйте первой строкой файла цели `#![no_main]`.

**3. Фаззинг не того.** Цель, которая вызывает `parse_record(data).unwrap()`, падает на каждой обычной ошибке разбора и ничего полезного не показывает. Игнорируйте ожидаемые ошибки (`let _ = …`) и падайте только на настоящих нарушениях, например на неудачном `assert_eq!`.

**4. Ошибку исправили, а тест не добавили.** Файл артефакта лежит в игнорируемой папке. Без регрессионного теста ошибка может вернуться незамеченной.

### Упражнение 1 — Прочитать файл падения (легко)

Файлы падений в `fuzz/artifacts/fuzz_target_1/` — это сырые байты, в редакторе их не прочитать. Одной подкомандой `cargo fuzz` выведите содержимое артефакта с входом `[0]` (из раздела 4) в читаемом виде Rust.

<details>
<summary>Подсказка</summary>

Подкоманда называется `fmt` (сокращение от «format», форматировать). Она принимает имя цели и путь к файлу артефакта.

</details>

<details>
<summary>Ответ</summary>

```bash
cargo +nightly fuzz fmt fuzz_target_1 fuzz/artifacts/fuzz_target_1/crash-5ba93c9db0cff93f52b521d7420e43f6eda2784f
```

```text
Output of `std::fmt::Debug`:

[0]
```

Почему это работает: `fmt` запускает декодер входа цели на файле и печатает результат через `Debug` — тот же текст, что печатает отчёт о падении. Используйте имя вашего файла из вывода `ls fuzz/artifacts/fuzz_target_1`.

</details>

### Упражнение 2 — Перебрать все маленькие входы (средне)

Напишите обычный тест в `tests/small_inputs.rs`, который вызывает `parse_record` на **каждом** входе длиной до двух байтов и проверяет только то, что паники нет. Сколько это вызовов? Нужен ли этому тесту компилятор nightly?

<details>
<summary>Подсказка</summary>

Используйте два вложенных цикла `for a in 0..=255u8` и `for b in 0..=255u8`. Нужен `use p09_fuzzing::parse_record;`. Не забудьте пустой вход и входы из одного байта.

</details>

<details>
<summary>Ответ</summary>

```rust
use p09_fuzzing::parse_record;

#[test]
fn never_panics_on_any_input_of_up_to_two_bytes() {
    let _ = parse_record(&[]);
    for a in 0..=255u8 {
        let _ = parse_record(&[a]);
        for b in 0..=255u8 {
            let _ = parse_record(&[a, b]);
        }
    }
}
```

```text
test never_panics_on_any_input_of_up_to_two_bytes ... ok
test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Почему это работает: вызовов 1 + 256 + 65 536 = 65 793. Любой вызов с паникой провалил бы тест, поэтому успех означает отсутствие паник. Это обычный тест: без nightly и без фаззера. Он работает, только пока пространство входов крошечное.

</details>

### Упражнение 3 — Второе свойство (сложно)

Напишите третью цель `reencode` со свойством: «если `parse_record(data)` успешна, то кодирование разобранной записи даёт ровно первые байты `data`». Зарегистрируйте её, запустите на десять секунд и скажите, нашла ли она ошибку. Что свойство говорит о лишних байтах в конце?

<details>
<summary>Подсказка</summary>

Используйте форму с сырыми байтами `|data: &[u8]|`. Закодированная запись имеет длину `bytes.len()`, поэтому сравнивайте `bytes[..]` с `data[..bytes.len()]`. Добавьте запись `[[bin]]` в `fuzz/Cargo.toml`.

</details>

<details>
<summary>Ответ</summary>

`fuzz/fuzz_targets/reencode.rs`:

```rust
#![no_main]

use libfuzzer_sys::fuzz_target;
use p09_fuzzing::{encode_record, parse_record};

fuzz_target!(|data: &[u8]| {
    if let Ok(record) = parse_record(data) {
        let bytes = encode_record(&record).expect("a parsed name is at most 255 bytes");
        assert_eq!(bytes[..], data[..bytes.len()]);
    }
});
```

В `fuzz/Cargo.toml`:

```toml
[[bin]]
name = "reencode"
path = "fuzz_targets/reencode.rs"
test = false
doc = false
bench = false
```

```bash
cargo +nightly fuzz run reencode -- -max_total_time=10
```

```text
#13250496	DONE   cov: 58 ft: 58 corp: 6/17b lim: 4096 exec/s: 1204590 rss: 686Mb
Done 13250496 runs in 11 second(s)
```

Почему это работает: падений нет, значит, свойство выполняется. Обратите внимание: мы сравниваем только с *началом* `data`: `parse_record` игнорирует байты после записи, поэтому вход может быть длиннее закодированной записи. Если ваш парсер должен отвергать лишние байты в конце, это свойство показало бы, что он этого не делает.

</details>

## Вопросы для самопроверки

1. Почему фаззер сохраняет вход, дошедший до новой строки кода?

<details>
<summary>Ответ</summary>

Потому что этот вход открыл новую ветку (например, верный первый байт). Мутации такого входа дают входы, которые проникают в код глубже. Это и значит «управляемый покрытием», и поэтому фаззинг лучше чисто случайных байтов.

</details>

2. Почему `cargo fuzz` требует `+nightly`?

<details>
<summary>Ответ</summary>

Он использует параметры компилятора (санитайзер и инструментирование покрытия, передаваемые через `-Z`), которые есть только в компиляторе nightly. Сам ваш код может оставаться на stable.

</details>

3. Цель фаззинга выполняет `parse_record(data).unwrap()`. В чём проблема?

<details>
<summary>Ответ</summary>

Каждая обычная ошибка разбора (`Err`) превращается в панику, поэтому фаззер сообщает «падения», которые на самом деле корректное поведение. Игнорируйте `Result` и проверяйте только настоящие правила.

</details>

4. Что нужно добавить в проект после того, как фаззер нашёл ошибку и вы её исправили?

<details>
<summary>Ответ</summary>

Регрессионный тест в обычный набор тестов с падающим входом, потому что артефакты и корпус не коммитятся.

</details>

5. Может ли фаззер найти функцию, которая возвращает неверный ответ, но не падает?

<details>
<summary>Ответ</summary>

Только если вы скажете ему, что такое «верно», проверкой в цели фаззинга, как свойство кругового преобразования в разделе 6. Без проверки он находит только падения, зависания и ошибки памяти.

</details>

## Итоги

- Фаззинг запускает ваш код на огромном числе сгенерированных входов и сообщает первый, на котором код падает. Управление покрытием делает поиск умным.
- `cargo-fuzz` требует компилятор nightly: `cargo +nightly fuzz run <target>`. Цель — маленькая функция `fuzz_target!(|data: &[u8]| { … })` в файле с `#![no_main]`.
- Отчёт называет артефакт падения с точным входом; воспроизведите его, минимизируйте через `cargo fuzz tmin`, исправьте код и добавьте обычный регрессионный тест.
- С крейтом `arbitrary` цель может принимать типизированное значение и проверять свойство, например «закодировали и раскодировали — получили исходное».
- Цели должны быть быстрыми и детерминированными. Запускайте их с ограничением по времени: `-- -max_total_time=СЕКУНДЫ`.
- Коммитьте цели и регрессионные тесты; корпус и артефакты по умолчанию игнорируются.
