# Урок 08.1 — Хороший дизайн: KISS, DRY и YAGNI

> **Этап 08 — Проектирование ПО: принципы, паттерны и соглашения** · Урок 1 из 17 · ⏱ около 135 минут

## Что вы узнаете

- Почему код читают гораздо чаще, чем пишут, и что на практике значит «хороший дизайн».
- **KISS**: почему самый простой код, который работает, обычно лучший.
- **DRY**: как убрать повторяющиеся *знания* и почему не каждую повторяющуюся строку нужно объединять.
- **YAGNI**: почему не стоит строить что-то «на всякий случай».
- Что делать, когда эти три принципа противоречат друг другу.

## Новые слова

| Слово | Значение |
|---|---|
| **дизайн** (design) программы | Решения о том, как код делится на части, как эти части называются и как они работают вместе. У любой программы есть дизайн, хороший или плохой. |
| **принцип проектирования** (design principle) | Практическое правило, которое помогает выбрать между двумя способами написать код. Это совет, основанный на опыте, а не закон, и у него бывают исключения. |
| **сопровождаемость** (maintainability) | Насколько легко читать, менять и чинить программу спустя месяцы, часто — другому человеку. |
| **KISS** (Keep It Simple, Stupid, «делай проще») | Выбирайте самое простое решение, которое справляется с задачей. Слово «stupid» не про вас: оно говорит, что *простой* дизайн трудно сломать. |
| **DRY** (Don't Repeat Yourself, «не повторяйся») | У каждого знания должно быть одно-единственное место в коде. |
| **YAGNI** (You Aren't Gonna Need It, «тебе это не понадобится») | Не добавляйте функциональность или гибкость, пока у вас нет настоящей потребности в них. |
| **дублирование** (duplication) | Одна и та же идея, записанная в нескольких местах. |
| **абстракция** (abstraction) | Имя (функция, тип, трейт), которое скрывает детали, чтобы можно было говорить об идее, не повторяя её шаги. |
| **рефакторинг** (refactoring) | Изменение структуры кода без изменения того, что он делает. Подробно его разбирает Урок 08.13. |
| **правило трёх** (rule of three) | Ориентир: один раз можно скопировать, но когда тот же код появляется в третий раз, выделяйте общую абстракцию. |

## 1. Что значит «хороший дизайн»

Представьте, что вы открыли программу, которую написали три месяца назад. Нужно поменять одно правило: «заказы от 10 штук получают скидку». Сколько времени уйдёт на поиск нужного места? Насколько вы уверены, что изменение ничего не сломает?

Именно об этом и говорит дизайн. Опыт многих команд одинаков: программисты тратят гораздо больше времени на **чтение** кода, чем на его написание. Поэтому хороший дизайн — это не хитрые трюки. Это возможность сделать следующее изменение **дешёвым и безопасным**.

**Принцип проектирования** — это короткое правило, которое в этом помогает. В этом уроке мы изучим три принципа, с которыми каждый инженер сталкивается в первые недели работы:

| Принцип | Одной строкой | Против чего |
|---|---|---|
| KISS | Предпочитайте простое решение. | Хитрости, лишняя сложность |
| DRY | Одно место для каждого знания. | Копирование и вставка |
| YAGNI | Стройте только то, что нужно сейчас. | Гадание о будущем |

Принципы — не заповеди. Для каждого мы посмотрим на типичную проблему («до»), на лучшую версию («после») и на случаи, когда его применять НЕ нужно.

> 💡 **Совет:** весь код этого этапа лежит в `code/p08-<тема>`, по одному пакету Cargo на урок (в этом уроке — `code/p08-kiss-dry`). Примеры показаны так, как будто это `src/main.rs`. Чтобы хранить несколько примеров в одном пакете, сохраняйте каждый как `src/bin/<имя>.rs` и запускайте через `cargo run --bin <имя>`; тогда в сообщениях компилятора будет этот путь вместо `src/main.rs`. Сообщения в уроках получены в пакете с именем `demo`; у вас там будет имя вашего пакета (например, `p08-kiss-dry`).

## 2. KISS: делайте проще

Небольшой расчёт для магазина. Цена заказа — это `цена за штуку × количество`. Заказ от 10 штук получает скидку 10 %, а члены клуба получают ещё 5 %. Деньги считаются в **центах** (целых числах), так что числа с плавающей точкой нам не нужны.

Первую версию написал человек, который любил гибкость:

```rust
type Rule = Box<dyn Fn(u64) -> u64>;

fn make_rules(quantity: u32, is_member: bool) -> Vec<Rule> {
    let mut rules: Vec<Rule> = Vec::new();
    if quantity >= 10 {
        rules.push(Box::new(|cents| cents - cents / 10));
    }
    if is_member {
        rules.push(Box::new(|cents| cents - cents / 20));
    }
    rules
}

fn total_cents(unit_cents: u64, quantity: u32, is_member: bool) -> u64 {
    make_rules(quantity, is_member)
        .iter()
        .fold(unit_cents * u64::from(quantity), |sum, rule| rule(sum))
}

fn main() {
    println!("{}", total_cents(250, 4, false));
    println!("{}", total_cents(250, 12, true));
}
```

**Что происходит:**

1. `type Rule = Box<dyn Fn(u64) -> u64>` даёт имя «замыканию в коробке (Box), которое принимает цену и возвращает новую цену» (Уроки 05.4 и 06.1).
2. `make_rules` собирает `Vec` с одним замыканием на каждую подходящую скидку. Каждое замыкание размещается в куче вызовом `Box::new`.
3. `total_cents` берёт `unit_cents * quantity` и с помощью `fold` пропускает цену через правила, одно за другим.
4. `main` печатает сумму заказа без скидок и заказа с обеими скидками.

```text
1000
2565
```

Работает. Так что же плохо? Чтобы ответить на вопрос «сколько платит член клуба за 12 штук?», нужно прочитать псевдоним типа, функцию, возвращающую вектор замыканий, и `fold`. Новому читателю приходится сначала понять *механизм* и лишь потом он видит *правила*, а важны здесь только правила.

Простая версия:

```rust
fn total_cents(unit_cents: u64, quantity: u32, is_member: bool) -> u64 {
    let mut total = unit_cents * u64::from(quantity);
    if quantity >= 10 {
        total -= total / 10; // bulk discount: 10 %
    }
    if is_member {
        total -= total / 20; // member discount: 5 %
    }
    total
}

fn main() {
    println!("{}", total_cents(250, 4, false));
    println!("{}", total_cents(250, 12, true));
}
```

Она снова печатает `1000` и `2565`. Правила (10 % и 5 %) видны с первого взгляда, ничего не выделяется в куче, и у каждой скидки своя строка, куда можно вставить `println!`.

> 📏 **Соглашение:** простое — не значит «меньше всего строк» или «без абстракций». Это значит, что читателю нужно держать в голове как можно меньше идей. Обычный `if`, понятный всем, лучше хитрого `fold`, над которым надо думать минуту.

**Когда KISS НЕ применять.** Оставьте гибкую версию, если правила действительно должны меняться во время работы программы, например когда владелец магазина редактирует скидки в файле настроек. Тогда список правил *и есть* требование, а обычный `if` его выразить не может. KISS говорит «не платите за гибкость, которая вам не нужна», а не «никогда не будьте гибкими». (Урок 08.9 показывает паттерн *стратегия* — аккуратный способ построить такую гибкость, когда она нужна.)

> ⚡ **Производительность:** простая версия ещё и быстрее, потому что ничего не выделяет в куче. Но это побочный эффект. Не выбирайте дизайн ради скорости, пока ничего не измерили (как измерять, учит Этап 19).

## 3. DRY: одно место для каждого знания

Название DRY пришло из книги *The Pragmatic Programmer*. Идея о **знании**: каждый факт или правило вашей программы должны быть записаны ровно в одном месте. Правило *не* звучит как «никогда не пишите две похожие строки».

Типичная проблема. Две формы программы проверяют, что имя не пустое и не длиннее 20 букв. Вторую проверку сделали копированием:

```rust
fn check_username(name: &str) -> Result<(), String> {
    if name.is_empty() {
        return Err("username is empty".to_string());
    }
    if name.len() > 20 {
        return Err("username is too long".to_string());
    }
    Ok(())
}

fn check_project_name(name: &str) -> Result<(), String> {
    if name.is_empty() {
        return Err("project name is empty".to_string());
    }
    if name.len() >= 20 {
        return Err("project name is too long".to_string());
    }
    Ok(())
}

fn main() {
    let name = "abcdefghijklmnopqrst"; // exactly 20 letters
    println!("{:?}", check_username(name));
    println!("{:?}", check_project_name(name));
}
```

**Что происходит:**

1. Две функции — копии друг друга; различаются только слова в сообщениях.
2. В `check_project_name` стоит `>=`, а в `check_username` — `>`. Кто-то ошибся при наборе или «исправил» одну копию и забыл про другую.
3. `main` проверяет имя ровно из 20 букв. По правилу 20 допустимо.

```text
Ok(())
Err("project name is too long")
```

Одно и то же правило даёт **два разных ответа**. В этом настоящая опасность дублирования: когда знание («в имени не больше 20 символов») меняется, нужно помнить обо всех копиях, и однажды вы забудете одну. У обеих копий есть и ещё одна общая ошибка: `len()` считает *байты*, а не символы (Урок 04.8), поэтому имя «Ünal» считается как 5.

Исправление — одна функция, которая хранит знание, и одна константа для предела:

```rust
const MAX_NAME_CHARS: usize = 20;

fn check_name(kind: &str, name: &str) -> Result<(), String> {
    if name.is_empty() {
        return Err(format!("{kind} is empty"));
    }
    if name.chars().count() > MAX_NAME_CHARS {
        return Err(format!("{kind} is too long"));
    }
    Ok(())
}

fn main() {
    let name = "abcdefghijklmnopqrst"; // exactly 20 letters
    println!("{:?}", check_name("username", name));
    println!("{:?}", check_name("project name", name));
}
```

```text
Ok(())
Ok(())
```

**Что происходит:**

1. `MAX_NAME_CHARS` — единственное место, где живёт предел.
2. `check_name` принимает то, что различается (`kind` — вид имени, он нужен для сообщения), как параметр.
3. `name.chars().count()` считает символы, поэтому ошибка с байтами исправлена один раз для всех.
4. Имя из 20 букв теперь принимается везде.

> 🔒 **Безопасность:** дублированные *проверки* — это риск для безопасности. Если проверка прав скопирована в пять мест, а ошибку исправили в четырёх, пятое место — дыра. Держите важные правила (кто что может делать, какой ввод допустим) ровно в одной функции.

### DRY — про знание, а не про внешний вид

Иногда код выглядит одинаково, но это не одно и то же знание. Возьмём `format_price` (печатает `1999` центов как `$19.99`) и `format_weight` (печатает `2500` граммов как `2.500 kg`). Обе делят число и печатают две части. Внимательный программист видит повтор и объединяет их:

```rust
fn format_fixed(value: u64, divisor: u64, width: usize, prefix: &str, suffix: &str) -> String {
    format!(
        "{prefix}{}.{:0width$}{suffix}",
        value / divisor,
        value % divisor
    )
}

fn main() {
    println!("{}", format_fixed(1999, 100, 2, "$", ""));
    println!("{}", format_fixed(2500, 1000, 3, "", " kg"));
}
```

```text
$19.99
2.500 kg
```

Работает, но прочитайте вызовы: что такое `100` и `2` в `format_fixed(1999, 100, 2, "$", "")`? В следующем месяце цены должны показывать разделитель тысяч («$1,999.00»), а вес — округляться до одного знака. Каждое изменение заставляет добавлять в `format_fixed` новый параметр или флаг, и это затрагивает всех, кто её вызывает. Цены и вес меняются по **разным причинам**, значит, это разные знания. «Дублирование» было случайностью первой версии.

Это называется **неправильной абстракцией**. Опытный инженер Санди Мец выразила это одной фразой: дублирование намного дешевле неправильной абстракции.

> 📏 **Соглашение:** используйте **правило трёх**. В первый раз напишите код. Во второй раз скопируйте, если нужно, и запомните это. В третий раз вы уже видите, что на самом деле отличается у копий, и тогда выделяйте функцию или тип. До третьей копии вы только гадаете.

**Когда DRY НЕ применять:**

- части похожи, но меняются по разным причинам (пример выше);
- общей функции понадобились бы параметры-флаги вроде `fn run(kind: bool, extra: bool)`: это две функции, склеенные в одну;
- копии живут в разных крейтах или сервисах, которые должны меняться независимо.

## 4. YAGNI: не стройте ради воображаемого будущего

YAGNI пришёл из подхода к работе, который называется экстремальным программированием (Extreme Programming). Идея: возможность, добавленная потому, что «она точно понадобится позже», часто оказывается неверной или так и остаётся неиспользованной. А сегодня она уже стоит вам: больше кода читать, тестировать и поддерживать в рабочем состоянии.

Хранилище настроек, которое построил программист, представлявший много будущих применений:

```rust
use std::collections::HashMap;

trait Storage {
    fn save(&mut self, key: &str, value: &str);
    fn load(&self, key: &str) -> Option<String>;
}

impl Storage for HashMap<String, String> {
    fn save(&mut self, key: &str, value: &str) {
        self.insert(key.to_string(), value.to_string());
    }
    fn load(&self, key: &str) -> Option<String> {
        self.get(key).cloned()
    }
}

struct Settings<S: Storage> {
    storage: S,
    retry_count: u32,
    on_change: Option<Box<dyn Fn(&str)>>,
}

impl<S: Storage> Settings<S> {
    fn set(&mut self, key: &str, value: &str) {
        self.storage.save(key, value);
    }
    fn get(&self, key: &str) -> Option<String> {
        self.storage.load(key)
    }
}

fn main() {
    let mut settings = Settings {
        storage: HashMap::new(),
        retry_count: 3,
        on_change: None,
    };
    settings.set("theme", "dark");
    println!("{:?}", settings.get("theme"));
}
```

**Что происходит:**

1. `trait Storage` означает «что-то, что сохраняет и загружает текст». Единственный реализующий его тип — `HashMap<String, String>`.
2. `Settings<S: Storage>` обобщена по хранилищу, чтобы когда-нибудь можно было подключить файл или базу данных.
3. `retry_count` и `on_change` добавили «на потом». Их никто не читает.
4. `main` использует весь этот механизм, чтобы сохранить одну строку.

Программа печатает `Some("dark")`. Даже компилятор относится к этому коду с подозрением. Когда он собирает его, он говорит:

```text
warning: fields `retry_count` and `on_change` are never read
  --> src/main.rs:19:5
   |
17 | struct Settings<S: Storage> {
   |        -------- fields in this struct
18 |     storage: S,
19 |     retry_count: u32,
   |     ^^^^^^^^^^^
20 |     on_change: Option<Box<dyn Fn(&str)>>,
   |     ^^^^^^^^^
   |
   = note: `#[warn(dead_code)]` (part of `#[warn(unused)]`) on by default

warning: `demo` (bin "demo") generated 1 warning
```

Сравните с версией, которая решает сегодняшнюю задачу:

```rust
use std::collections::HashMap;

fn main() {
    let mut settings: HashMap<String, String> = HashMap::new();
    settings.insert("theme".to_string(), "dark".to_string());
    println!("{:?}", settings.get("theme"));
}
```

Она тоже печатает `Some("dark")`. Она втрое короче, и все понимают её с первого прочтения. Если в следующем году появится второй вид хранилища, вы *тогда* узнаете, что ему нужно (может ли сохранение завершиться ошибкой? медленное ли оно?), и сможете написать трейт с нужными методами. Маленький понятный код легко менять. Неправильную абстракцию, которая разошлась по программе, — нет.

> 💡 **Совет:** компилятор Rust помогает применять YAGNI. Предупреждения вроде `dead_code` и `unused` указывают на поля, функции и импорты, которые никто не использует. Читайте их как «удалите это» и держите сборку без предупреждений.

**Когда YAGNI НЕ применять.** Кое-что очень дорого менять позже. Думать об этом заранее — не гадание, а проектирование:

- **Публичные интерфейсы.** Когда другие программы или люди зависят от имён ваших функций или формата файла, любое изменение их ломает.
- **Форматы хранимых данных.** Данные на диске живут дольше кода. Номер версии в формате файла стоит одно поле сегодня и спасает от болезненной миграции потом.
- **Безопасность и корректность.** Никогда не откладывайте проверку ввода фразой «добавим позже».
- **Точки для тестирования.** Маленький трейт, позволяющий тесту подменить часы или сеть, часто оправдан ещё до появления второй настоящей реализации (Урок 08.9).

YAGNI также не значит «без проектирования» или «без тестов». Он значит: не создавайте возможности, о которых никто не просил.

## 5. Когда принципы расходятся

Три принципа тянут в разные стороны, и это нормально. Если вы не уверены, задавайте эти вопросы в таком порядке:

1. Код работает и протестирован? Если нет, сначала исправьте это. Всё остальное требует тестов как страховки.
2. Не записано ли одно и то же *знание* дважды? Объедините (DRY), помня о правиле трёх.
3. Нет ли здесь чего-то, что никто не использует и что пока не нужно? Удалите (YAGNI).
4. Сможет ли новый читатель быстро это понять? Если нет, упростите (KISS).

> 🧪 **Тестирование:** обкладывайте код тестами **до** рефакторинга. Рефакторинг не должен менять поведение, и только тест скажет вам, что оно не изменилось. Вы потренируетесь в этом в следующем разделе.

## Частые ошибки

**Ошибка 1: делать код обобщённым «на всякий случай».** Функция, принимающая «что угодно», часто ничего с этим сделать не может:

```rust
fn describe<T>(item: T) -> String {
    format!("item: {}", item)
}

fn main() {
    println!("{}", describe(42));
}
```

```text
error[E0277]: `T` doesn't implement `std::fmt::Display`
 --> src/main.rs:2:25
  |
2 |     format!("item: {}", item)
  |                    --   ^^^^ `T` cannot be formatted with the default formatter
  |                    |
  |                    required by this formatting parameter
  |
  = note: in format strings you may be able to use `{:?}` (or `{:#?}` for pretty-print) instead
help: consider restricting type parameter `T` with trait `Display`
  |
1 | fn describe<T: std::fmt::Display>(item: T) -> String {
  |              +++++++++++++++++++

For more information about this error, try `rustc --explain E0277`.
error: could not compile `demo` (bin "demo") due to 1 previous error
```

Компилятор прав: `T` может быть любым типом, а не любой тип можно напечатать через `{}`. Чтобы `describe` заработала, нужно добавить ограничение (`T: std::fmt::Display`). Если функцию вызывают только с числами, проще `fn describe(item: i32)`. Добавляйте обобщения, когда появится *второе* настоящее применение, а не раньше.

**Ошибка 2: объединять код только потому, что он похож.** Сначала спросите, меняются ли части по одной и той же причине (раздел 3).

**Ошибка 3: «просто» значит «коротко».** Цепочка итераторов в 200 символов коротка, но не проста. Если строку нужно пояснять комментарием, разбейте её на именованные шаги.

**Ошибка 4: YAGNI как оправдание небрежности.** «Тесты пока не нужны» или «обработка ошибок пока не нужна» — это не YAGNI. Тесты и обработка ошибок — часть возможности, которую вы строите сегодня.

## Упражнения

### Упражнение 1 — Назовите принцип (легко)

Для каждой ситуации скажите, какой принцип (KISS, DRY или YAGNI) нарушен:

1. В программе есть `trait Plugin` и реестр плагинов, но существует только один плагин и других никто не планирует.
2. Правило «PIN (Personal Identification Number, личный идентификационный номер — короткий секретный код) состоит из 4 цифр» записано в восьми разных функциях.
3. Функция, складывающая два числа, использует макрос, три обобщённых параметра и строитель.

<details>
<summary>Подсказка</summary>

Спросите себя: не построено ли то, что никому не нужно (YAGNI)? Не записано ли одно знание много раз (DRY)? Не сложнее ли решение, чем задача (KISS)?

</details>

<details>
<summary>Ответ</summary>

1. YAGNI: система плагинов для одного плагина — гибкость, о которой никто не просил.
2. DRY: правило про PIN — знание, которое должно жить в одной функции или константе.
3. KISS: простое решение — `a + b`.

Почему это работает: принципы — это вопросы, которые вы задаёте коду. Ситуация может нарушать сразу несколько (реестр плагинов в пункте 1 ещё и не прост); вам нужно лишь увидеть проблему.

</details>

### Упражнение 2 — Уберите дублирование и проверьте тестом (средне)

Эти две функции повторяют логику «обрезать пробелы и сделать первую букву заглавной». Выделите её в функцию `capitalize` и сделайте так, чтобы обе функции её использовали. **Напишите тест** для `capitalize`, который охватывает обычное имя, пустую строку и имя, начинающееся с не-ASCII буквы (ASCII — базовый набор английских букв, цифр и символов), например `"élan"`.

```rust
fn welcome(name: &str) -> String {
    let mut chars = name.trim().chars();
    let fixed = match chars.next() {
        Some(first) => first.to_uppercase().collect::<String>() + chars.as_str(),
        None => String::new(),
    };
    format!("Welcome, {fixed}!")
}

fn goodbye(name: &str) -> String {
    let mut chars = name.trim().chars();
    let fixed = match chars.next() {
        Some(first) => first.to_uppercase().collect::<String>() + chars.as_str(),
        None => String::new(),
    };
    format!("Goodbye, {fixed}. See you soon!")
}

fn main() {
    println!("{}", welcome("  ana "));
    println!("{}", goodbye("bo"));
}
```

<details>
<summary>Подсказка</summary>

Общее знание — только «как превратить `  ana ` в `Ana`». Сообщения («Welcome» и «Goodbye») разные и остаются каждое в своей функции.

</details>

<details>
<summary>Ответ</summary>

```rust
fn capitalize(text: &str) -> String {
    let mut chars = text.trim().chars();
    match chars.next() {
        Some(first) => first.to_uppercase().collect::<String>() + chars.as_str(),
        None => String::new(),
    }
}

fn welcome(name: &str) -> String {
    format!("Welcome, {}!", capitalize(name))
}

fn goodbye(name: &str) -> String {
    format!("Goodbye, {}. See you soon!", capitalize(name))
}

fn main() {
    println!("{}", welcome("  ana "));
    println!("{}", goodbye("bo"));
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn capitalize_handles_normal_empty_and_non_ascii_text() {
        assert_eq!(capitalize("  ana "), "Ana");
        assert_eq!(capitalize(""), "");
        assert_eq!(capitalize("élan"), "Élan");
    }
}
```

Почему это работает: `capitalize` хранит единственное знание, а `welcome` и `goodbye` лишь выбирают формулировку. Тест вызывает `capitalize` напрямую, поэтому все три случая проверяются без печати. `cargo test` сообщает, что 1 тест пройден.

</details>

### Упражнение 3 — Объединять или нет? (сложно)

Две функции, `valid_for_signup` и `valid_for_newsletter`, сегодня делают совершенно одну и ту же проверку адреса электронной почты (часть до `@` не пуста, а часть после содержит точку). В следующем квартале при регистрации нужно отклонять адреса, оканчивающиеся на `@example.com`, а рассылка по-прежнему должна их принимать. Нужно ли объединить две функции в одну? Покажите дизайн, который соблюдает DRY и не создаёт неправильную абстракцию.

<details>
<summary>Подсказка</summary>

Отделите то, что *действительно* общее (как выглядит адрес электронной почты), от того, что относится к каждому применению (правило для регистрации).

</details>

<details>
<summary>Ответ</summary>

Две публичные функции объединять не нужно. Выделите только общее знание и оставьте по маленькой функции на каждую цель:

```rust
// The one piece of knowledge that is really shared.
fn looks_like_email(text: &str) -> bool {
    match text.split_once('@') {
        Some((user, host)) => !user.is_empty() && host.contains('.'),
        None => false,
    }
}

// Each rule can now change on its own.
fn valid_for_signup(text: &str) -> bool {
    looks_like_email(text) && !text.ends_with("@example.com")
}

fn valid_for_newsletter(text: &str) -> bool {
    looks_like_email(text)
}

fn main() {
    println!("{}", valid_for_signup("ana@mail.org"));
    println!("{}", valid_for_signup("ana@example.com"));
    println!("{}", valid_for_newsletter("ana@example.com"));
}
```

Почему это работает: `looks_like_email` — общее знание, определённое один раз. `valid_for_signup` и `valid_for_newsletter` могут меняться независимо, и флаг `bool` не нужен. Объединённая `fn valid(text, for_signup: bool)` была бы неправильной абстракцией.

</details>

## Вопросы для самопроверки

1. Что должно быть уникальным по DRY: строки кода или знания?

<details>
<summary>Ответ</summary>

Знания. Две похожие строки, которые меняются по разным причинам, DRY не нарушают.

</details>

2. Почему в первом примере про DRY (`check_username` и `check_project_name`) две проверки дали разные ответы?

<details>
<summary>Ответ</summary>

Правило скопировали, и одну копию изменили (`>=` вместо `>`). Дублированные знания расходятся.

</details>

3. Назовите две вещи, которые дорого менять позже, поэтому YAGNI к ним не применяется.

<details>
<summary>Ответ</summary>

Любые две из: публичные интерфейсы, форматы хранимых данных, проверки безопасности, точки подмены для тестов.

</details>

4. Что говорит правило трёх?

<details>
<summary>Ответ</summary>

Подождите, пока тот же код появится в третий раз, и только потом выделяйте абстракцию: к этому моменту видно, что на самом деле отличается.

</details>

5. Функцию `fn render(kind: bool, flag: bool, ...)` получили, объединив две функции. Какой принцип это нарушает и почему?

<details>
<summary>Ответ</summary>

DRY, применённый неправильно. Параметры-флаги показывают, что склеили две разные вещи: это неправильная абстракция.

</details>

## Итоги

- Хороший дизайн делает следующее изменение дешёвым и безопасным; код читают гораздо чаще, чем пишут.
- **KISS**: выбирайте простое решение. Обычный `if` лучше хитрого конвейера из замыканий в коробках, если только гибкость во время работы не является настоящим требованием.
- **DRY**: у каждого *знания* один дом. Дублированные правила расходятся и порождают ошибки.
- DRY не значит «объединяй всё, что похоже». Неправильная абстракция стоит дороже небольшого дублирования; используйте правило трёх.
- **YAGNI**: не стройте ради воображаемого будущего. Предупреждения компилятора о неиспользуемом коде часто на него указывают.
- Публичные интерфейсы, форматы хранимых данных и безопасность — исключения: думайте о них заранее.
- Принципы — это эвристики, а не законы. Сначала обложите код тестами, потом делайте рефакторинг.
