# Урок 16.1 — Что такое бэкенд-сервис

> **Этап 16 — Бэкенд-сервисы** · Урок 1 из 16 · ⏱ около 2,5 часа (2 занятия)

## Что вы узнаете

- Что такое бэкенд-сервис и чем он отличается от программ командной строки, которые вы писали до сих пор.

- Почему сервис не должен хранить важные данные в своей памяти и куда эти данные деваются вместо этого.

## Новые слова

| Слово | Значение |
|---|---|
| **бэкенд** (backend) | Часть программной системы, которая работает на серверах: хранит данные, применяет правила и отвечает на запросы. Пользователь не видит её напрямую. |
| **фронтенд** (frontend) | Часть, которую пользователь видит и трогает: веб-страница, приложение на телефоне, программа на компьютере. Она отправляет запросы бэкенду. |
| **сервис** (service) | Программа, которая работает долго, ждёт запросов по сети и отвечает на них. *Бэкенд-сервис* — сервис, который входит в бэкенд. |
| **клиент** (client) | Программа, которая отправляет запросы сервису: браузер, приложение на телефоне, `curl` или другой сервис. |
| **API** (Application Programming Interface, программный интерфейс) | Согласованный список запросов, которые понимает сервис, и ответов, которые он даёт. Это контракт между сервисом и его клиентами. |
| **эндпоинт** (endpoint) | Один вид запроса, на который отвечает сервис; записывается как HTTP-метод плюс путь, например `GET /health`. |
| **обработчик** (handler) | Функция в сервисе, которая выполняется для одного эндпоинта и строит ответ. |
| **маршрутизатор** (router) | Часть веб-фреймворка, которая смотрит на метод и путь запроса и выбирает обработчик. |
| **веб-фреймворк** (web framework) | Библиотека, которая делает общую работу HTTP-сервера (разбор, маршрутизацию, построение ответов), так что вы пишете только обработчики. `axum` — один из них. |
| **экземпляр** (instance) | Одна запущенная копия сервиса. Сервис может работать в виде многих экземпляров одновременно. |
| **сервис без состояния** (stateless service) | Сервис, который не хранит важных данных в своей памяти между запросами. Любой экземпляр может ответить на любой запрос. |
| **горизонтальное масштабирование** (horizontal scaling) | Обработка большей нагрузки за счёт запуска большего числа экземпляров вместо покупки более мощной машины. |
| **балансировщик нагрузки** (load balancer) | Программа перед экземплярами, которая распределяет входящие запросы между ними (Урок 15.14). |
| **база данных** (database) | Отдельная программа, которая надёжно хранит данные на диске и отвечает на вопросы о них. На этом этапе используется PostgreSQL. |
| **кэш** (cache) | Быстрое хранилище копий часто читаемых данных, чтобы реже обращаться к базе данных. На этом этапе используется Redis. |
| **брокер сообщений** (message broker) | Программа, которая принимает сообщения от одного сервиса и доставляет их другим, чтобы им не приходилось вызывать друг друга напрямую. На этом этапе используется NATS. |
| **проверка работоспособности** (health check) | Запрос (часто `GET /health`), который отвечает только «я жив». Его используют балансировщики нагрузки и контейнерные платформы. |
| **блокирующий вызов** (blocking call) | Вызов, который держит поток занятым, пока ждёт (времени, файла, сети), так что поток не может делать ничего другого. |

## 1. От программы к сервису

Программы, которые вы писали до сих пор, запускаются, делают одну работу и завершаются. `minigrep` читает
файл, печатает подходящие строки и выходит. **Сервис** устроен иначе: он запускается, открывает сетевой порт
и затем **ждёт**. Каждый раз, когда приходит запрос, он делает небольшую работу, отправляет ответ и снова
ждёт. Он останавливается, только когда ему скажут остановиться.

Хорошая бытовая картинка — кухня ресторана. Кухня не готовит одно блюдо и не закрывается. Она открывается
утром, принимает заказы от многих официантов одновременно, хранит продукты в холодильнике (а не в руках
повара) и закрывается вечером, когда готовы последние заказы.

| | Программа командной строки | Сервис |
|---|---|---|
| Сколько работает | Секунды, одна работа | Дни или месяцы, пока не остановят |
| Кто начинает работу | Пользователь, с аргументами | Клиенты, с запросами по сети |
| Сколько пользователей одновременно | Один | Много одновременно |
| Откуда приходит ввод | Аргументы, файлы, стандартный ввод | HTTP-запросы (или сообщения) |
| Куда уходит вывод | Стандартный вывод, файлы | HTTP-ответы (или сообщения) |
| Что происходит при ошибке | Напечатать её и выйти с кодом | Ответить ошибкой на этот один запрос и продолжать работу |

Последняя строка важна. Программа может завершиться, если что-то пошло не так. Сервис не должен: один
плохой запрос никогда не должен останавливать сервис для всех остальных клиентов.

## 2. Фронтенд, бэкенд и API между ними

Представьте банковское приложение на телефоне. Приложение (**фронтенд**) показывает ваш баланс. Само оно
вашего баланса не знает. Оно отправляет запрос через интернет на серверы банка (**бэкенд**), и бэкенд
отвечает числом.

```text
 phone app (frontend)                         bank servers (backend)
 ┌──────────────────┐   GET /accounts/42      ┌──────────────────────┐
 │ shows "1 250.00" │ ──────────────────────▶ │ checks who you are,  │
 │                  │                          │ reads the database,  │
 │                  │ ◀────────────────────── │ builds the answer    │
 └──────────────────┘   200 OK {"balance":…}  └──────────────────────┘
```

Список запросов, которые понимает бэкенд, и ответов, которые он даёт, — это **API**. Это контракт: команда
фронтенда и команда бэкенда могут работать отдельно, пока обе соблюдают контракт. Урок 16.2 показывает,
как спроектировать хороший API.

Бэкенду принадлежат две вещи:

1. **Данные.** Счета, заказы, сообщения. Фронтенд показывает только копии.
2. **Правила.** «Вы можете видеть только свой счёт». «Перевод не может быть отрицательным». Бэкенд должен
   сам проверять каждое правило, потому что кто угодно может отправить ему любой запрос, а не только ваше
   приложение. Вы изучали это как «никогда не доверяйте вводу» в [Уроке 10.4](../10-security-fundamentals/04-input-validation.md).

> 🔒 **Безопасность:** проверка, которая есть только во фронтенде, — это не проверка. Злоумышленник обходит
> ваше приложение и отправляет запросы через `curl`. Каждая проверка прав и каждая проверка ввода должны
> выполняться и в бэкенде.

## 3. Части бэкенд-системы

Настоящий бэкенд обычно состоит из нескольких программ, которые общаются друг с другом по сети:

```text
                ┌──────────────┐
  clients ────▶ │ load balancer│ ───┬─────────────┬───────────────┐
  (apps, curl,  └──────────────┘    ▼             ▼               ▼
   other                       ┌─────────┐   ┌─────────┐     ┌─────────┐
   services)                   │service  │   │service  │ ... │service  │   instances of
                               │instance1│   │instance2│     │instanceN│   YOUR program
                               └────┬────┘   └────┬────┘     └────┬────┘
                                    │             │               │
                  ┌─────────────────┼─────────────┼───────────────┤
                  ▼                 ▼             ▼               ▼
            ┌──────────┐      ┌──────────┐   ┌───────────┐  ┌─────────────────┐
            │PostgreSQL│      │  Redis   │   │   NATS    │  │ logs, metrics,  │
            │(database)│      │ (cache)  │   │ (messages)│  │ traces collector│
            └──────────┘      └──────────┘   └───────────┘  └─────────────────┘
```

| Часть | Её работа | Где вы её изучите |

| Балансировщик нагрузки | Распределяет запросы между экземплярами | Урок 15.14 |

| Вход и права доступа | Кто обращается и что ему можно | Урок 16.8 |
| Кэш | Быстрые копии горячих данных | Урок 16.10 |

## 4. Ваш первый сервис

В Уроке 06.11 вы читали байты из `TcpStream`, разбивали текст на строки, находили путь и писали ответ
вручную. Это был хороший способ учиться, но каждому настоящему сервису снова и снова нужны одни и те же
части: правильный разбор HTTP, выбор обработчика, построение заголовков, работа со многими соединениями.
**Веб-фреймворк** делает эту работу за вас. В этом курсе используется **`axum`** — веб-фреймворк,
построенный на Tokio и на `hyper` (HTTP-библиотеке из Урока 15.9).

**Как организован код этого этапа.** Каждый урок говорит, какую папку использовать. Этот и следующий урок
используют небольшой пакет `code/p16-hello`. С Урока 16.3 по Урок 16.8 вы шаг за шагом выращиваете один
сервис — `code/p16-tasks`.

Создайте пакет и добавьте два крейта:

```bash
cd ~/projects/rust
cargo new code/p16-hello
cd code/p16-hello
cargo add axum@0.8
cargo add tokio@1 --features full
```

Теперь в `Cargo.toml` есть:

```toml
[dependencies]
axum = "0.8"
tokio = { version = "1", features = ["full"] }
```

Замените `src/main.rs` на:

```rust
use std::sync::atomic::{AtomicU64, Ordering};
use std::time::Duration;

use axum::{Router, routing::get};

// Живёт в памяти одного этого процесса. Пропадает, когда процесс останавливается.
static VISITS: AtomicU64 = AtomicU64::new(0);

async fn health() -> &'static str {
    "ok\n"
}

async fn slow() -> &'static str {
    tokio::time::sleep(Duration::from_secs(1)).await;
    "done after 1 second\n"
}

async fn visits() -> String {
    let n = VISITS.fetch_add(1, Ordering::Relaxed) + 1;
    format!("visit number {n}\n")
}

#[tokio::main]
async fn main() {
    let port = std::env::args().nth(1).unwrap_or_else(|| "3000".to_string());
    let addr = format!("127.0.0.1:{port}");

    let app = Router::new()
        .route("/health", get(health))
        .route("/slow", get(slow))
        .route("/visits", get(visits));

    let listener = tokio::net::TcpListener::bind(&addr).await.unwrap();
    println!("listening on http://{addr}");
    axum::serve(listener, app).await.unwrap();
}
```

**Что происходит:**

1. `health`, `slow` и `visits` — **обработчики**: обычные `async fn`. axum вызывает один из них на каждый
   запрос. То, что возвращает обработчик, становится ответом. `&'static str` или `String` становится ответом
   со статусом `200 OK` и текстом в теле.
2. `slow` ждёт одну секунду через `tokio::time::sleep(...).await`. Пока он ждёт, поток свободен и может
   работать над другими запросами (раздел 5 это показывает).
3. `VISITS` — глобальный атомарный счётчик (Урок 14.5). `fetch_add(1, …)` прибавляет единицу и возвращает
   старое значение, безопасно, даже если много запросов выполняется одновременно. Для простого счётчика
   достаточно порядка `Relaxed`.
4. В `main` первый аргумент командной строки — это порт; без него используем `3000`.
5. `Router::new().route("/health", get(health))` означает: «для запроса `GET` к пути `/health` вызвать
   `health`». Каждый `.route` добавляет один эндпоинт. Это и есть **маршрутизатор**.
6. `TcpListener::bind` открывает порт — точно как в Уроке 06.11, но в асинхронной версии из Tokio.
   `127.0.0.1` означает, что подключиться могут только программы на этом компьютере.
7. `axum::serve(listener, app)` работает бесконечно: принимает соединения, разбирает HTTP, просит у
   маршрутизатора обработчик, запускает его и записывает ответ. Он возвращается, только если случилось
   что-то очень плохое.

Запустите сервис в одном терминале:

```bash
cargo run
```

```text
listening on http://127.0.0.1:3000
```

Программа не завершается. Она ждёт. Откройте **второй** терминал и станьте её первым клиентом. `-i` просит
`curl` напечатать ещё и строку статуса и заголовки:

```bash
curl -i http://127.0.0.1:3000/health
```

```text
HTTP/1.1 200 OK
content-type: text/plain; charset=utf-8
content-length: 3
date: Wed, 18 Nov 2026 06:55:24 GMT

ok
```

Вы не написали ни одного заголовка, но axum построил правильный HTTP-ответ: статус, `content-type`
(потому что обработчик вернул текст), длину и дату. Теперь попробуйте несуществующий путь и метод, который
эндпоинт не принимает:

```bash
curl -i http://127.0.0.1:3000/nothing-here
curl -i -X POST http://127.0.0.1:3000/health
```

```text
HTTP/1.1 404 Not Found
content-length: 0
date: Wed, 18 Nov 2026 06:55:24 GMT

HTTP/1.1 405 Method Not Allowed
allow: GET,HEAD
content-length: 0
date: Wed, 18 Nov 2026 06:55:24 GMT
```

**Что происходит:**

1. Ни один маршрут не подходит к `/nothing-here`, поэтому маршрутизатор сам отвечает `404 Not Found`.
2. `/health` существует, но только для `GET`. `-X POST` отправляет `POST`, поэтому маршрутизатор отвечает
   `405 Method Not Allowed` и даже перечисляет разрешённые методы в заголовке `allow`. (`HEAD` — то же, что
   `GET`, только без тела; axum добавляет его бесплатно.)

Когда закончите, остановите сервис клавишами `Ctrl+C` в первом терминале.

> 💡 **Совет:** держите на протяжении всего этапа два терминала: в одном работает сервис, в другом — `curl`.
> В RustRover можно разделить окно терминала или открыть в нём вторую вкладку.

## 5. Много клиентов одновременно

У сервиса много клиентов, и они не ждут вежливо друг друга. Снова запустите сервис (`cargo run`) и во
втором терминале отправьте **три** запроса к `/slow` одновременно. `&` в конце команды запускает её в фоне,
`wait` ждёт их все, а `time` измеряет всю группу:

```bash
time (curl -s http://127.0.0.1:3000/slow & curl -s http://127.0.0.1:3000/slow & curl -s http://127.0.0.1:3000/slow & wait)
```

```text
done after 1 second
done after 1 second
done after 1 second
( curl -s http://127.0.0.1:3000/slow & curl -s http://127.0.0.1:3000/slow &  )  0.01s user 0.01s system 1% cpu 1.013 total
```

Три запроса, каждому нужна одна секунда, завершились примерно за **1 секунду в сумме**, а не за три.
(`-s` означает «тихо»: без индикатора прогресса.)

**Что происходит:**

1. `axum::serve` запускает новую **задачу** Tokio на каждое соединение (задачи вы знаете из Урока 14.13).
   Задача дешёвая: их у сервиса могут быть многие тысячи.
2. Каждый запрос доходит до `slow`, который вызывает `sleep(...).await`. `.await` говорит рантайму: «мне
   нечего делать одну секунду, выполняй другие задачи». Поэтому все три задачи ждут одновременно.
3. Через секунду рантайм будит все три, и каждая отправляет свой ответ.

Именно поэтому бэкенд-сервисы на Rust почти всегда асинхронные: большую часть времени запрос **ждёт** —
базу данных, другой сервис, сеть. Пока он ждёт, поток обслуживает другие запросы.

Теперь посмотрите, что происходит, когда обработчик блокирует поток. Создайте `src/bin/blocking.rs`. Он
использует `std::thread::sleep`, который блокирует поток, и рантайм только с **одним** потоком
(`flavor = "current_thread"`), чтобы эффект было легко увидеть:

```rust
use std::time::Duration;

use axum::{Router, routing::get};

async fn slow() -> &'static str {
    // НЕПРАВИЛЬНО: это блокирует весь поток, а не только этот запрос.
    std::thread::sleep(Duration::from_secs(1));
    "done after 1 second\n"
}

#[tokio::main(flavor = "current_thread")]
async fn main() {
    let app = Router::new().route("/slow", get(slow));
    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000").await.unwrap();
    println!("listening on http://127.0.0.1:3000");
    axum::serve(listener, app).await.unwrap();
}
```

Остановите первый сервис, запустите этот через `cargo run --bin blocking` и отправьте те же три запроса:

```text
done after 1 second
done after 1 second
done after 1 second
( curl -s http://127.0.0.1:3000/slow & curl -s http://127.0.0.1:3000/slow &  )  0.01s user 0.01s system 0% cpu 3.025 total
```

**3 секунды.** `std::thread::sleep` не возвращает управление рантайму, поэтому единственный поток не мог
начать второй запрос, пока первый не закончился полностью. Запросы выполнились один за другим.

> ⚡ **Производительность:** никогда не вызывайте блокирующие функции внутри асинхронного обработчика:
> `std::thread::sleep`, чтение больших файлов через `std::fs`, тяжёлые вычисления на много миллисекунд.
> С многопоточным рантаймом по умолчанию вред сначала скрыт (другие потоки продолжают работать), но под
> нагрузкой каждый заблокированный поток — это на один поток меньше для всех клиентов. Используйте
> асинхронную версию (`tokio::time::sleep`, `tokio::fs`) или переносите работу в
> `tokio::task::spawn_blocking` (Урок 06.9, раздел «Не блокируйте рантайм»).

## 6. Где живут данные?

Остановите блокирующий сервис и снова запустите обычный через `cargo run`. Вызовите `/visits` несколько раз:

```bash
curl -s http://127.0.0.1:3000/visits
curl -s http://127.0.0.1:3000/visits
```

```text
visit number 1
visit number 2
```

Считает. Теперь остановите сервис (`Ctrl+C`), запустите снова и вызовите `/visits` ещё раз: он опять
говорит `visit number 1`. Счётчик жил в памяти процесса, а эта память пропадает, когда процесс
останавливается. Сервисы останавливают постоянно: ради новой версии, при замене машины, при падении.

Есть и вторая проблема. Настоящие сервисы работают как **несколько экземпляров** за балансировщиком
нагрузки. Запустите второй экземпляр на порту 3001 в третьем терминале (`cargo run -- 3001`). Затем
вызывайте оба по очереди, как сделал бы балансировщик:

```bash
curl -s http://127.0.0.1:3000/visits
curl -s http://127.0.0.1:3000/visits
curl -s http://127.0.0.1:3001/visits
curl -s http://127.0.0.1:3000/visits
```

```text
visit number 1
visit number 2
visit number 1
visit number 3
```

У каждого экземпляра свой счётчик, и клиенты видят бессмысленные числа. Решение — главное правило
проектирования бэкенда и фактор VI приложения двенадцати факторов (Урок 08.15):

> **Сервис должен быть без состояния.** Все данные, которые должны пережить перезапуск или должны быть
> одинаковыми для всех экземпляров, живут **вне** процесса: в базе данных (Уроки 16.5–16.7), в кэше
> (Урок 16.10) или в брокере сообщений (Урок 16.11).

```text
   stateful (bad)                         stateless (good)
 ┌───────────┐ ┌───────────┐          ┌───────────┐ ┌───────────┐
 │instance 1 │ │instance 2 │          │instance 1 │ │instance 2 │
 │ visits=3  │ │ visits=1  │          │ no data   │ │ no data   │
 └───────────┘ └───────────┘          └─────┬─────┘ └─────┬─────┘
   two different answers                    └──────┬──────┘
                                                   ▼
                                            ┌────────────┐
                                            │ database   │
                                            │ visits = 4 │
                                            └────────────┘
```

У сервиса без состояния большие преимущества: любой экземпляр можно перезапустить в любой момент, а
большую нагрузку можно выдержать, просто запустив больше экземпляров (**горизонтальное масштабирование**).
Память внутри процесса по-прежнему подходит для того, что можно потерять: пула соединений, небольшого кэша
настроек, счётчика для метрик.

Когда закончите, остановите оба экземпляра.

## 7. Что ещё должен делать настоящий сервис

Отвечать на `GET /health` — простая часть. Сервис, от которого зависят настоящие люди, должен также:

- **Проверять каждый ввод** и отвечать понятными ошибками вместо падения (Урок 16.4).
- **Надёжно хранить данные** и менять несколько вещей сразу, не оставляя работу сделанной наполовину (Уроки 16.5–16.7).
- **Знать, кто обращается** и что ему разрешено (Урок 16.8).
- **Быть наблюдаемым:** писать структурированные логи, отдавать метрики и трассировки, чтобы вы видели, что
  он делает в продакшене (Урок 16.12, на основе [Урока 09.10 — Логирование и трассировка](../09-testing-debugging-benchmarking/10-logging-and-tracing.md)).
- **Читать конфигурацию из окружения** и сообщать о своей работоспособности (Урок 16.13).
- **Корректно завершаться:** перестать принимать новые запросы, закончить текущие, затем выйти (Урок 14.14).
- **Быть протестированным** на всех уровнях, в том числе с настоящей базой данных (Урок 16.14).

> 📏 **Соглашение:** почти у каждого сервиса есть дешёвый эндпоинт `GET /health`, который не делает
> настоящей работы и отвечает `200 OK`, пока процесс жив. Делайте его быстрым и никогда не кладите секреты
> в его ответ.

## Частые ошибки

**1. Порт уже занят.** Вы запускаете сервис, пока ещё работает старая копия (может быть, в другом
терминале или в RustRover):

```text
thread 'main' (4882234) panicked at src/main.rs:33:63:
called `Result::unwrap()` on an `Err` value: Os { code: 48, kind: AddrInUse, message: "Address already in use" }
```

Слушать порт может только одна программа. Найдите старую и остановите её (`Ctrl+C`) или запустите эту на
другом порту: `cargo run -- 3002`. Число в скобках после `main` — идентификатор потока; у вас оно другое.

**2. Ожидание, что `cargo run` закончится.** Сервис никогда «не заканчивается». Если терминал будто завис
после `listening on …`, это правильно: он ждёт запросов. Для `curl` используйте второй терминал.

**3. Блокировка внутри обработчика.** `std::thread::sleep`, медленные циклы или `std::fs::read` большого
файла внутри обработчика `async fn` останавливают один поток рантайма для всех (раздел 5). Используйте
асинхронную версию или `spawn_blocking`.

**4. Хранение важных данных в глобальной переменной или в `Vec` в памяти.** Это работает на вашем ноутбуке
с одним экземпляром и ломается при перезапуске или с двумя экземплярами (раздел 6). Используйте это только
для данных, которые можно потерять.

## Упражнения

### Упражнение 1 — Тест обработчика (легко)

Обработчик — это просто `async fn`, поэтому его можно вызвать из теста. Напишите тест `health_says_ok` в
`src/main.rs`, который проверяет, что `health()` возвращает `"ok\n"`. Тесты асинхронных функций используют
`#[tokio::test]` вместо `#[test]`.

<details>
<summary>Подсказка</summary>

Внутри асинхронного теста можно написать `health().await`. Поместите тест в `#[cfg(test)] mod tests` с
`use super::*;`.

</details>

<details>
<summary>Ответ</summary>

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[tokio::test]
    async fn health_says_ok() {
        assert_eq!(health().await, "ok\n");
    }
}
```

`cargo test` печатает `test tests::health_says_ok ... ok`.

Почему это работает: `#[tokio::test]` запускает для теста маленький рантайм Tokio, поэтому внутри можно
писать `.await`. Обработчику не нужен работающий сервер: это обычная функция, которая возвращает значение.

</details>

### Упражнение 2 — Эндпоинт версии (средне)

Добавьте эндпоинт `GET /version`, который отвечает версией из `Cargo.toml` и переводом строки (`0.1.0\n`).
Не набирайте число в коде: Cargo передаёт его вам во время компиляции через `env!("CARGO_PKG_VERSION")`.
Добавьте тест для нового обработчика.

<details>
<summary>Подсказка</summary>

`concat!(env!("CARGO_PKG_VERSION"), "\n")` строит `&'static str` во время компиляции. Добавьте ещё одну
строку `.route(...)`.

</details>

<details>
<summary>Ответ</summary>

```rust
async fn version() -> &'static str {
    concat!(env!("CARGO_PKG_VERSION"), "\n")
}

// в main:
//     .route("/version", get(version))

#[cfg(test)]
mod tests {
    use super::*;

    #[tokio::test]
    async fn version_matches_cargo_toml() {
        assert_eq!(version().await, "0.1.0\n");
    }
}
```

`curl -s http://127.0.0.1:3000/version` печатает `0.1.0`.

Почему это работает: `env!` читает переменную окружения **во время компиляции**, а Cargo задаёт
`CARGO_PKG_VERSION` при каждой сборке. Когда вы меняете версию в `Cargo.toml`, ответ меняется без правки
кода. У многих настоящих сервисов есть такой эндпоинт, чтобы было видно, какая версия развёрнута.

</details>

### Упражнение 3 — Тест настоящего сервера (сложно)

Упражнение 1 проверяло обработчик отдельно. Теперь проверьте **весь** сервис вместе с маршрутизатором.
Перенесите маршрутизатор в функцию `fn app() -> Router`, чтобы его могли использовать и `main`, и тест.
В тесте привяжите слушатель к `127.0.0.1:0` (порт 0 означает «любой свободный порт»), запустите
`axum::serve` в отдельной задаче, подключитесь через `tokio::net::TcpStream`, запишите «сырой» HTTP-запрос
(вы делали это вручную в Уроке 06.11) и проверьте, что ответ начинается с `HTTP/1.1 200 OK` и
заканчивается на `ok\n`.

<details>
<summary>Подсказка</summary>

`listener.local_addr()` сообщает, какой порт выбрала система. Отправьте
`b"GET /health HTTP/1.1\r\nHost: test\r\nConnection: close\r\n\r\n"`; с `Connection: close` сервер
закрывает соединение после ответа, поэтому `read_to_string` знает, где конец. Понадобится
`use tokio::io::{AsyncReadExt, AsyncWriteExt};`.

</details>

<details>
<summary>Ответ</summary>

```rust
// Строки `use`, VISITS, health, slow и visits остаются как были.

fn app() -> Router {
    Router::new()
        .route("/health", get(health))
        .route("/slow", get(slow))
        .route("/visits", get(visits))
}

#[tokio::main]
async fn main() {
    let port = std::env::args().nth(1).unwrap_or_else(|| "3000".to_string());
    let addr = format!("127.0.0.1:{port}");
    let listener = tokio::net::TcpListener::bind(&addr).await.unwrap();
    println!("listening on http://{addr}");
    axum::serve(listener, app()).await.unwrap();
}

#[cfg(test)]
mod tests {
    use super::*;
    use tokio::io::{AsyncReadExt, AsyncWriteExt};

    #[tokio::test]
    async fn real_server_answers_health() {
        // Порт 0 просит у операционной системы любой свободный порт.
        let listener = tokio::net::TcpListener::bind("127.0.0.1:0").await.unwrap();
        let addr = listener.local_addr().unwrap();
        tokio::spawn(async move {
            axum::serve(listener, app()).await.unwrap();
        });

        let mut stream = tokio::net::TcpStream::connect(addr).await.unwrap();
        stream
            .write_all(b"GET /health HTTP/1.1\r\nHost: test\r\nConnection: close\r\n\r\n")
            .await
            .unwrap();
        let mut response = String::new();
        stream.read_to_string(&mut response).await.unwrap();

        assert!(response.starts_with("HTTP/1.1 200 OK"), "got: {response}");
        assert!(response.ends_with("ok\n"), "got: {response}");
    }
}
```

```text
running 1 test
test tests::real_server_answers_health ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Почему это работает: порт 0 позволяет каждому тесту получить свой свободный порт, поэтому тесты никогда не
спорят за порт 3000 и могут идти параллельно. Запущенная задача обслуживает запросы, а тест выступает
клиентом. Это маленький **интеграционный тест** всего пути HTTP. Урок 16.14 покажет более удобные
инструменты для этого, но идея останется той же.

</details>

## Вопросы для самопроверки

1. Назовите два отличия программы командной строки от сервиса.

<details>
<summary>Ответ</summary>

Сервис работает долго и ждёт запросов; программа командной строки делает одну работу и завершается. Сервис
обслуживает многих клиентов одновременно; у программы командной строки один пользователь. Сервис отвечает
ошибкой на один запрос и продолжает работу; программа командной строки может завершиться при ошибке.

</details>

2. Почему бэкенд должен проверять правила, которые уже проверяет приложение-фронтенд?

<details>
<summary>Ответ</summary>

Потому что кто угодно может отправлять запросы бэкенду напрямую (через `curl`, скрипт, изменённое
приложение). Проверка во фронтенде нужна только для удобства пользователя; проверка в бэкенде — настоящая
защита.

</details>

3. Три запроса к `/slow` (по одной секунде каждый) завершились за одну секунду. Почему?

<details>
<summary>Ответ</summary>

axum выполняет каждое соединение в отдельной задаче Tokio. `tokio::time::sleep(...).await` возвращает
управление рантайму, поэтому три задачи ждали одновременно, а не одна за другой.

</details>

4. Что изменится, если обработчик использует `std::thread::sleep`?

<details>
<summary>Ответ</summary>

Он блокирует поток. С одним потоком рантайма запросы выполняются один за другим (3 секунды на три
запроса). С большим числом потоков проблема меньше, но реальна: каждый заблокированный поток никого не
может обслужить.

</details>

5. Что значит «сервис без состояния» и чем это полезно?

<details>
<summary>Ответ</summary>

Сервис не хранит важных данных в своей памяти; такие данные живут в базе данных, кэше или брокере. Любой
экземпляр можно перезапустить в любой момент, можно запустить больше экземпляров для большей нагрузки
(горизонтальное масштабирование), и каждый экземпляр даёт одинаковые ответы.

</details>

6. Что означают `404` и `405` и кто их выдал в этом уроке?

<details>
<summary>Ответ</summary>

`404 Not Found`: ни у одного эндпоинта нет такого пути. `405 Method Not Allowed`: путь есть, но не для
этого метода. Оба ответа автоматически выдал маршрутизатор axum; ни один обработчик не выполнялся.

</details>

## Итоги

- Бэкенд-сервис — долго работающая программа, которая ждёт запросов по сети, отвечает многим клиентам
  одновременно и продолжает работу, когда один запрос завершается ошибкой.
- Фронтенд показывает данные; бэкенду принадлежат данные и правила, и он должен сам проверять каждое правило.
- Бэкенд-система состоит из частей: балансировщик нагрузки, экземпляры сервиса, база данных, кэш, брокер
  сообщений и инструменты наблюдаемости. Этот этап учит каждой из них.
- `axum` превращает асинхронные функции-обработчики в HTTP-сервис: `Router::new().route(path, get(handler))`,
  затем `axum::serve(listener, app)`.
- Каждое соединение выполняется в своей задаче Tokio; `.await` позволяет одному потоку обслуживать много
  ждущих запросов. Блокирующий вызов внутри обработчика это разрушает.
- Делайте сервисы без состояния: данные, которые должны пережить перезапуск или быть общими для
  экземпляров, живут вне процесса.
