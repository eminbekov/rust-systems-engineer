## Новые слова

| Слово | Значение |
|---|---|
| **конечный автомат состояния** (replicated state machine) | Часть, которая хранит данные (здесь — ваш движок «ключ-значение»). Каждый узел применяет одни и те же закоммиченные записи журнала в одном порядке, поэтому все автоматы приходят в одно состояние. |
| **контрактный тест** (contract test) | Тестовая функция, написанная для трейта, а не для типа. Каждая реализация (в памяти, один узел, кластер) должна пройти один и тот же тест. |
| **идентификатор запроса** (request ID; ID — identifier, идентификатор) | Пара (номер клиента, порядковый номер), которую клиент ставит на каждую запись, чтобы хранилище распознало повтор и применило его только один раз. |
| **таблица дедупликации** (deduplication table) | Часть конечного автомата, которая помнит для каждого клиента последний применённый порядковый номер и его результат. |
| **read index** (индекс чтения) | Способ выполнить линеаризуемое чтение без записи в журнал: лидер запоминает свой индекс коммита, одним раундом heartbeat-сообщений подтверждает, что он всё ещё лидер, ждёт применения этого индекса и читает. |
| **устаревшее чтение** (stale read) | Чтение, которое может вернуть немного старые данные, например с ведомого узла. Оно дешевле, но не линеаризуемо. |
| **снапшот** (snapshot) | Копия всего конечного автомата на одном индексе журнала. Со снапшотом записи журнала до этого индекса можно удалить. |
| **компакция журнала** (log compaction) | Удаление старых записей журнала после снапшота, чтобы журнал не рос бесконечно. |
| **`InstallSnapshot`** | Сообщение Raft, которое отправляет снапшот ведомому узлу, отставшему настолько, что у лидера уже нет нужных ему записей. |
| **пакетная запись** (batching, group commit) | Запись многих предложений в журнал одним `fsync` вместо `fsync` на каждое. Сильно повышает пропускную способность. |
| **конвейерная отправка** (pipelining) | Отправка следующего `AppendEntries` ведомому до того, как пришёл ответ на предыдущий. |
| **изменение состава** (membership change) | Добавление или удаление узла из работающего кластера без его остановки. |
| **307 Temporary Redirect** | Статус HTTP (HyperText Transfer Protocol, протокол передачи гипертекста), который говорит: «отправь тот же запрос, тем же методом и с тем же телом, по адресу из заголовка `Location`». |
| **UTF-8** (Unicode Transformation Format, 8-bit, формат преобразования Юникода, 8 бит) | Обычная кодировка текста в байты; `String` и `&str` в Rust всегда корректный UTF-8. |
| **URL** (Uniform Resource Locator, унифицированный указатель ресурса) | Веб-адрес, например `https://example.test/v1/kv/color`. |
| **RPC** (Remote Procedure Call, удалённый вызов процедуры) | Вызов функции на другой машине по сети, например `AppendEntries` в Raft. |
| **ADR** (Architecture Decision Record, запись об архитектурном решении) | Короткий файл с одним важным решением: контекст, решение, последствия (Урок 23.2). |
| **SSD** (Solid-State Drive, твердотельный накопитель) | Накопитель на флеш-памяти без движущихся частей. |
| **CI** (Continuous Integration, непрерывная интеграция) | Сервер, который автоматически запускает ваши проверки при каждой отправке (Урок 09.12). |

## 1. Что вы строите и почему это важно

Вы строите `kvd` — маленькое хранилище в духе etcd: базу данных «ключ-значение», которая работает на трёх машинах и остаётся **корректной**, пока одна из них падает, перезапускается или отрезана от сети. Каждая запись проходит через Raft, поэтому подтверждённая запись переживает потерю любого одного узла. Клиенты общаются с ним по HTTP через `curl` или маленький клиент командной строки `kv`.

Обе половины вы уже построили. `p17-kv` надёжно хранит данные на одной машине. `p18-kv` реплицирует журнал через Raft и проходит хаос-тесты в симуляции. Этот итоговый проект превращает их в систему, которую команда действительно могла бы эксплуатировать:

- настоящий **HTTP API** с понятными кодами статуса и перенаправлениями;
- **идемпотентные записи**, чтобы клиент мог безопасно повторить запрос после тайм-аута;
- **быстрые линеаризуемые чтения** через read index и дешёвые устаревшие чтения;
- **снапшоты и компакция журнала**, чтобы журнал не рос без предела;
- **пакетная запись**, чтобы один `fsync` покрывал много записей;
- **эксплуатация**: метрики, логи, проверки работоспособности, кластер из трёх узлов в Docker Compose и числа бенчмарков.

Почему это важно: почти каждая большая система зависит от такого хранилища. Kubernetes хранит всё своё состояние в etcd; базы данных вроде TiKV и CockroachDB построены из многих групп Raft. На собеседованиях на позиции в инфраструктуре и базах данных часто задают те вопросы, на которые отвечает этот проект: что происходит, когда лидер умирает посреди записи, как чтение может быть линеаризуемым, как журнал остаётся маленьким. После этого итогового проекта вы ответите на них своим кодом и своими результатами тестов.

## 2. Эталонная архитектура

```text
            kv CLI, curl, contract tests, oha
                      |
                      |  HTTP/JSON: PUT, GET, DELETE /v1/kv/{key}, GET /v1/status
                      v
 +-------------------------------------------+   Raft RPC: AppendEntries,
 | kvd node 1 (leader)                       |   RequestVote, InstallSnapshot
 |                                           |<-------------------+
 |  +-------------+      +----------------+  |                    |
 |  | HTTP API    |----->| driver task    |  |          +-------------------+
 |  | (axum)      |<-----| (owns the core)|  |<-------->| kvd node 2        |
 |  +-------------+      +--+----------+--+  |          | (follower)        |
 |                          |          |     |          +-------------------+
 |              step, tick, |          | committed,     +-------------------+
 |              propose     |          | in order  <--->| kvd node 3        |
 |                          v          v     |          | (follower)        |
 |  +------------------+  +----------------+ |          +-------------------+
 |  | Raft core        |  | state machine: | |
 |  | (pure, no I/O)   |  | KV engine +    | |
 |  +--------+---------+  | dedup table    | |
 |           |            +-------+--------+ |
 |           v                    v          |
 |  +------------------+  +----------------+ |
 |  | Raft log (WAL,   |  | snapshots      | |
 |  | fsync, batches)  |  | (atomic files) | |
 |  +------------------+  +----------------+ |
 +-------------------------------------------+
```

Части и их задачи:

1. **HTTP API** превращает запросы в предложения (proposals) и ждёт их результатов. Он никогда не трогает состояние Raft напрямую.
2. **Задача-драйвер** (из Проекта 18.14) владеет ядром Raft. Она передаёт ему тики, сообщения и предложения, сохраняет жёсткое состояние (hard state) *до* отправки сообщений и отдаёт закоммиченные записи конечному автомату.
3. **Ядро Raft** — чистая логика без сети и диска, поэтому его можно тестировать точными повторяемыми шагами.
4. **Журнал Raft** — журнал упреждающей записи (Урок 17.4) с пакетной записью: много записей, один `fsync`.
5. **Конечный автомат** — ваш движок «ключ-значение» плюс таблица дедупликации. Оба меняются только применением закоммиченных записей.
6. **Снапшоты** позволяют узлу удалять старые записи журнала и помогают медленному ведомому догнать остальных.

> 📏 **Соглашение:** держите ядро Raft свободным от ввода-вывода (I/O, input/output) и от `tokio`. Каждую ошибку, найденную позже, проще воспроизвести в чистой функции, которую можно вызвать с точными входными данными. Это гексагональная архитектура из Урока 08.14, применённая к консенсусу.

### Контракт

**Командная строка сервера:**

```text
kvd --id <N> --listen <ADDR> --peers <ID=ADDR,...> --data <DIR>
    [--election-timeout-ms 300..600] [--heartbeat-ms 50] [--snapshot-every 10000]
```

Пример для локального кластера из трёх узлов: `kvd --id 1 --listen 127.0.0.1:7001 --peers 2=127.0.0.1:7002,3=127.0.0.1:7003 --data data/1`. Один адрес обслуживает и клиентский API, и трафик Raft (под `/raft/…`), либо выберите два порта и опишите это.

**HTTP API** (все тела — JSON, JavaScript Object Notation):

| Метод и путь | Тело запроса | Успех | Ошибки |
|---|---|---|---|
| `PUT /v1/kv/{key}` | `{"value":"blue","client":7,"seq":42}` | `200 {"index":17}` | `307`, `400`, `413`, `503` |
| `GET /v1/kv/{key}?read=linearizable` (по умолчанию) | – | `200 {"value":"blue","index":17}` | `404`, `307`, `503` |
| `GET /v1/kv/{key}?read=stale` | – | `200 {"value":"blue","index":15}` | `404` |
| `DELETE /v1/kv/{key}` | `{"client":7,"seq":43}` | `200 {"deleted":true,"index":18}` | `307`, `400`, `503` |
| `GET /v1/status` | – | `200 {"id":1,"role":"leader","term":3,"leader":1,"commit_index":18,"applied_index":18,"log_first_index":1}` | – |
| `GET /healthz`, `GET /readyz` | – | `200 ok` | `503` (готовность — только при известном лидере) |
| `GET /metrics` | – | текстовый формат Prometheus | – |

**Правила:**

1. Ключи — 1–1 024 байта текста UTF-8 (в URL — с процентным кодированием); значения — не больше 1 МиБ. Всё остальное — `400` или `413` с `{"error":"…"}`.
2. На запись отвечают `200` только после того, как её запись журнала **закоммичена** (сохранена на большинстве узлов, каждая копия после `fsync`) и **применена**. `index` — её индекс в журнале.
3. Ведомый узел отвечает на записи и линеаризуемые чтения `307 Temporary Redirect`, заголовком `Location` с URL лидера и `{"error":"not leader","leader":1}`. Без известного лидера (во время выборов) ответ — `503 {"error":"no leader"}`.
4. **Линеаризуемые** чтения видят каждую запись, подтверждённую до начала чтения. **Устаревшие** чтения может обслужить любой узел, и они могут отставать; они возвращают применённый индекс узла, чтобы клиент видел, насколько ответ стар.
5. **Идемпотентность:** запись с `(client, seq)`, которая уже применена, возвращает исходный результат и ничего не меняет. Таблица дедупликации — часть конечного автомата: она реплицируется, входит в снапшоты и переживает перезапуски.
6. Запрос, который не закоммичен за 2 секунды, получает `503 {"error":"timeout"}`. Клиент может повторить его с тем же `(client, seq)`.

**Командная строка клиента** (печатает в стандартный вывод; ошибки — в стандартный поток ошибок с кодом возврата 1):

```text
kv [--server URL] put <KEY> <VALUE>      ->  OK (index 17)
kv [--server URL] get <KEY> [--stale]    ->  blue            (or "not found", exit 1)
kv [--server URL] delete <KEY>           ->  deleted (index 18)
kv [--server URL] status                 ->  node 1: leader, term 3, commit 18, applied 18
```

Клиент следует перенаправлениям, повторяет запросы после тайм-аутов с задержкой и джиттером (Урок 18.3) и хранит свой номер `client` и растущий `seq`.

**Трейт хранилища.** Сделайте контракт исполняемым: один трейт, который предлагает каждая реализация, и контрактные тесты, написанные для трейта. Вот отправная точка с самой простой реализацией. Чтобы попробовать, положите её в учебный пакет `code/p23-kv-contract` (в итоговом проекте она попадёт в `kv-api` и модуль тестовых утилит):

```rust
use std::collections::HashMap;

/// Identifies one client request, so that a retry can be recognised.
#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash)]
pub struct RequestId {
    pub client: u64,
    pub seq: u64,
}

/// The errors every implementation may return.
#[derive(Debug, PartialEq)]
pub enum KvError {
    /// The key is empty or longer than 1,024 bytes.
    InvalidKey,
    /// This node is not the leader; `leader` is a hint where to go.
    NotLeader { leader: Option<String> },
}

/// What every version of the store offers, from a toy in memory to a 3-node cluster.
pub trait KvStore {
    fn put(&mut self, key: &str, value: &str, id: RequestId) -> Result<(), KvError>;
    fn get(&mut self, key: &str) -> Result<Option<String>, KvError>;
    fn delete(&mut self, key: &str, id: RequestId) -> Result<bool, KvError>;
}

fn check_key(key: &str) -> Result<(), KvError> {
    if key.is_empty() || key.len() > 1024 {
        return Err(KvError::InvalidKey);
    }
    Ok(())
}

/// The simplest store that meets the contract: one HashMap in memory.
#[derive(Default)]
pub struct MemStore {
    map: HashMap<String, String>,
}

impl KvStore for MemStore {
    fn put(&mut self, key: &str, value: &str, _id: RequestId) -> Result<(), KvError> {
        check_key(key)?;
        self.map.insert(key.to_string(), value.to_string());
        Ok(())
    }

    fn get(&mut self, key: &str) -> Result<Option<String>, KvError> {
        check_key(key)?;
        Ok(self.map.get(key).cloned())
    }

    fn delete(&mut self, key: &str, _id: RequestId) -> Result<bool, KvError> {
        check_key(key)?;
        Ok(self.map.remove(key).is_some())
    }
}

/// The basic contract. Every implementation must pass it.
pub fn check_basic_contract(store: &mut impl KvStore) {
    let id = |seq| RequestId { client: 1, seq };
    assert_eq!(store.get("color"), Ok(None));
    store.put("color", "blue", id(1)).unwrap();
    assert_eq!(store.get("color"), Ok(Some("blue".to_string())));
    store.put("color", "green", id(2)).unwrap();
    assert_eq!(store.get("color"), Ok(Some("green".to_string())));
    assert_eq!(store.delete("color", id(3)), Ok(true));
    assert_eq!(store.delete("color", id(4)), Ok(false));
    assert_eq!(store.put("", "x", id(5)), Err(KvError::InvalidKey));
    let long_key = "k".repeat(1025);
    assert_eq!(store.get(&long_key), Err(KvError::InvalidKey));
}

fn main() {
    let mut store = MemStore::default();
    check_basic_contract(&mut store);
    println!("MemStore passes the basic contract");
}
```

**Что происходит:**

1. `RequestId` — пара из правила 5. Она выводит (derive) `Hash` и `Eq`, поэтому позже может быть ключом в множестве или словаре.
2. `KvError` перечисляет ошибки, которые вызывающий код должен обработать. `NotLeader` несёт подсказку, как `307` из правила 3.
3. `KvStore` — это контракт в виде трейта. `get` принимает `&mut self`, потому что настоящему клиенту может понадобиться обновить своё представление о том, кто лидер.
4. `MemStore` — **эталонная реализация**: очевидно корректная и крошечная. Пока она игнорирует идентификатор запроса — Упражнение 2 показывает, почему этого недостаточно.
5. `check_basic_contract` принимает `&mut impl KvStore`, поэтому та же функция позже будет тестировать один узел `kvd` через HTTP и кластер из трёх узлов через клиентскую библиотеку `kv`.

```

```

### Пошаговый план

Каждая веха заканчивается проверками «Готово, когда». Показанные выводы — **часть контракта**: это то, что должна печатать ваша законченная программа, а не вывод, полученный курсом. Превратите каждую проверку в приёмочный тест (Урок 23.1) до начала вехи и ставьте тег на коммит, когда CI зелёный.

#### M0 — Ходячий скелет

**Цель.** Рабочее пространство из таблицы выше вместе с CI компилируется; `kvd --version` и `kv --version` работают; контрактные тесты из этого урока проходят на `MemStore`; приёмочные тесты M1–M6 существуют как заглушки с `#[ignore]`.

**Готово, когда:** `cargo test` показывает прошедший контрактный тест и по одному пропущенному тесту на каждую следующую веху; CI запускает `fmt`, `clippy` и `test`.

#### M1 — Один узел за HTTP

**Цель.** Кластер из одного узла: ядро Raft без соседей коммитит каждую запись сразу (большинство из одного — это один). HTTP API и клиент `kv` работают от начала до конца, данные хранятся надёжно.

<details>
<summary>Подсказка</summary>

Не стройте особый «режим одного узла»: запускайте обычный драйвер с пустым списком соседей. Тогда M2 меняет конфигурацию, а не пути в коде. Для теста надёжности запустите `kvd` из теста как дочерний процесс, пишите в цикле, убейте его через `Child::kill` (это `SIGKILL`, то же, что `kill -9`) в случайный момент, перезапустите и проверьте, что каждая запись, получившая `200`, читается.

</details>

**Готово, когда:**

```bash
kvd --id 1 --listen 127.0.0.1:7001 --data data/1 &
kv --server http://127.0.0.1:7001 put color blue
kv --server http://127.0.0.1:7001 get color
```

```text
OK (index 2)
blue
```

(Индекс 1 — это no-op-запись нового лидера.) Также: `check_basic_contract` проходит через HTTP-клиент для одного узла, а тест `m1_acknowledged_writes_survive_kill` (1 000 записей, убийство в случайный момент, перезапуск) проходит 20 раз подряд.

#### M2 — Три узла, перенаправления и идемпотентные записи

**Цель.** Три узла на localhost. Ведомые перенаправляют. Записи несут `(client, seq)`, а таблица дедупликации делает повторы безопасными, в том числе при смене лидера.

<details>
<summary>Подсказка</summary>

Храните в таблице только **последний** применённый `seq` и его результат для каждого клиента. Запрос с меньшим или равным `seq` — повтор: верните сохранённый результат (для `seq` старше последнего можно вернуть ошибку — правильный клиент никогда его не отправит). Поскольку таблица меняется только применением закоммиченных записей, каждый узел строит одинаковую таблицу.

</details>

**Готово, когда:**

```bash
curl -si -X PUT http://127.0.0.1:7002/v1/kv/color -H 'content-type: application/json' -d '{"value":"blue","client":7,"seq":1}'
```

```text
HTTP/1.1 307 Temporary Redirect
location: http://127.0.0.1:7001/v1/kv/color
content-type: application/json

{"error":"not leader","leader":1}
```

(Один `-d` отправляет тело как веб-форму; заголовок `content-type` сообщает серверу, что это JSON. Без него экстрактор `Json` из `axum` отвечает `415 Unsupported Media Type`.)

Также: `kv --server http://127.0.0.1:7002 put color blue` следует перенаправлению и печатает `OK (index …)`; контрактный тест повторов (Упражнение 2) проходит на кластере; тест на `turmoil` отправляет запись, теряет ответ, убивает лидера и повторяет тот же запрос на новом лидере — ключ записан один раз, и более поздняя запись того же ключа не перезаписывается повтором.

#### M3 — Линеаризуемые чтения через read index и устаревшие чтения

**Цель.** Чтения больше не проходят через журнал. Линеаризуемые чтения используют read index; чтения с `?read=stale` берутся из локального конечного автомата любого узла.

<details>
<summary>Подсказка</summary>

Лидер, отрезанный от остальных, всё ещё *считает* себя лидером, пока не услышит больший терм. Поэтому read index нужен один раунд heartbeat-сообщений, подтверждённый большинством **после** прихода чтения. Новый лидер также сначала должен закоммитить свою no-op-запись, иначе его индекс коммита может отставать.

</details>

**Готово, когда:** после 1 000 линеаризуемых `GET` значения `log_first_index` и последнего индекса журнала в `/v1/status` не сдвинулись; тест на `turmoil` отрезает старого лидера от двух других, даёт им выбрать нового лидера и записать новое значение и проверяет, что старый лидер отвечает на линеаризуемое чтение `307` или `503`, но никогда не старым значением; тот же старый лидер может ответить на `?read=stale` старым значением и своим применённым индексом.

#### M4 — Снапшоты и компакция журнала

**Цель.** Каждые `--snapshot-every` применённых записей узел атомарно пишет снапшот конечного автомата (движка **и** таблицы дедупликации), затем удаляет журнал до него. Ведомый, отставший слишком сильно, получает `InstallSnapshot`.

<details>
<summary>Подсказка</summary>

Пишите снапшот во временный файл, делайте `fsync`, переименовывайте, делайте `fsync` каталога (шаблон из Урока 17.2); только после этого удаляйте записи журнала. Храните последний индекс и терм снапшота: проверке согласованности `AppendEntries` нужен терм записи прямо перед первой оставшейся.

</details>

**Готово, когда:** в тесте с 1 миллионом записей по 1 000 ключам каталог журнала никогда не вырастает выше предела, указанного в проектном документе (например, 64 МиБ); ведомый, остановленный на время 100 000 записей, догоняет остальных после перезапуска, а его метрики показывают один `InstallSnapshot`; узел, перезапущенный после снапшота, имеет те же данные, что и раньше (снапшот плюс хвост журнала).

#### M5 — Пропускная способность: пакетная запись и конвейерная отправка

**Цель.** Сначала измерить, потом ускорить: много предложений делят одну запись в журнал и один `fsync`, а лидер держит у каждого ведомого несколько `AppendEntries` в полёте.

<details>
<summary>Подсказка</summary>

Измерьте базовую линию с `oha` и фиксированной нагрузкой, прежде чем что-то менять, и добавьте метрики «вызовов fsync» и «записей на fsync». Group commit в драйвере делается просто: возьмите все предложения, ждущие в канале (до предела), добавьте их все, сделайте один `fsync`.

</details>

**Готово, когда:** `docs/results.md` содержит таблицу с записями в секунду и задержкой p50/p99 (медиана и 99-й перцентиль, Урок 19.1) для трёх узлов до и после пакетной записи, измеренными одинаково (записаны оборудование, размер значения, число соединений, длительность); метрика «записей на fsync» под нагрузкой больше 1; все прежние тесты по-прежнему проходят.

#### M6 — Эксплуатация и доказательство

**Цель.** Хранилище можно запускать, наблюдать и ему можно доверять: метрики, структурированные логи, корректное завершение, кластер в Docker Compose и хаос-симуляция с проверкой истории в CI.

<details>
<summary>Подсказка</summary>

Начните с хаос-теста и простой проверки из Проекта 18.14 и расширьте их на HTTP API, устаревшие чтения и идемпотентные повторы. Держите в репозитории список фиксированных начальных значений (seed), чтобы CI каждый раз запускал одни и те же, а много случайных начальных значений запускайте в отдельном, более медленном задании.

</details>

**Готово, когда:** `docker compose up` запускает три узла, и `kv status` на каждом показывает одного лидера; `/metrics` сообщает как минимум терм, роль, индекс коммита, применённый индекс, отставание применения и гистограммы задержек запросов; остановка контейнера лидера через `docker compose stop` даёт нового лидера в пределах тайм-аута выборов плюс одна секунда; хаос-тест проходит для 200 фиксированных начальных значений в CI и для 2 000 случайных начальных значений в локальном релизном запуске; README формулирует гарантии одним предложением: «linearizable reads and writes; tolerates the failure of 1 of 3 nodes».

### Планка качества

Общая планка — в Уроке 23.1. Для этого варианта она означает:

| Область | Что это значит здесь |
|---|---|
| Модульные тесты и тесты на модели | ядро Raft протестировано шаг за шагом; тест на основе свойств сравнивает конечный автомат с моделью на `HashMap` на случайных последовательностях команд |
| Контрактные тесты | `check_basic_contract` и контракт повторов проходят на `MemStore`, одном узле и кластере |
| Тесты на сбои | надёжность при `kill -9` (M1), падение лидера во время записей (M2), разделение сети (M3), медленный ведомый (M4), хаос с начальными значениями (seed, M6) |
| Фаззинг | фаззинг-цели для декодера записей журнала и декодера снапшотов: испорченные байты должны давать ошибку, а не панику и не огромное выделение памяти |
| Бенчмарки | `oha` для `PUT` и `GET` плюс бенчмарк `criterion` для пути добавления в журнал |
| Наблюдаемость | спаны `tracing` на каждый запрос с индексом журнала; метрики из M6 |
| Устойчивость | тайм-ауты на каждом RPC, ограниченная очередь предложений (`503`, когда она полна), лимит размера тела |

### Дополнительные цели

- **Изменения состава:** добавить четвёртый узел как неголосующего ученика (learner), дать ему догнать остальных по снапшоту, затем сделать голосующим; удалить узел, не останавливая записи.
- **Передача лидерства** при корректном завершении, чтобы плановый перезапуск не ждал тайм-аута выборов.
- **`Watch(prefix)`**: потоковый эндпоинт, который отправляет каждое изменение ключей с префиксом, как это делает etcd.
- **Аренды** (leases) для более быстрых чтений, с записанным допущением о дрейфе часов (Урок 18.4).
- Полная **проверка линеаризуемости** для небольших историй (поиск из Урока 18.7) для каждого начального значения хаос-теста.
- **Multi-Raft:** разделить пространство ключей на диапазоны, каждый со своей группой Raft.

## Частые ошибки

**1. Отвечать до `fsync`.** Запись лежит в страничном кэше операционной системы, машина теряет питание, подтверждённая запись пропала. Правило 2 гласит: закоммичено — значит сохранено на большинстве, каждая копия после `fsync`.

**2. Применить запись дважды после перезапуска.** Узел воспроизводит журнал с начала поверх конечного автомата, в котором часть записей уже есть. Исправление: храните последний применённый индекс вместе с данными, атомарно (в том же снапшоте или в той же записи движка), и пропускайте записи с индексом не больше него.

**3. Таблица дедупликации только в памяти лидера.** После смены лидера новый лидер не знает, какие запросы применены, и повтор применяется дважды. Исправление: правило 5 — таблица является частью реплицируемого конечного автомата.

**4. Отдавать «линеаризуемые» чтения из локального состояния лидера без проверки.** Отрезанный старый лидер возвращает старые данные. Исправление: read index (M3).

**5. Реальное время в тестах.** Тайм-ауты выборов из `std::time` и `rand::rng()` делают падения невоспроизводимыми. Исправление: время и случайность приходят из драйвера; в тестах — из `turmoil` и начального значения.

**6. Неограниченные очереди.** Под нагрузкой предложения копятся в памяти, пока процесс не убьют. Исправление: ограниченный канал и `503`, когда он полон (Урок 20.8).

## Упражнения

Эти упражнения готовят проектный документ и первые контрактные тесты. Сделайте их в `code/p23-kv-contract` до M0.

### Упражнение 1 — Неоднозначная запись (легко)

Лидер добавляет запись, реплицирует её на большинство, применяет и падает **до** того, как отправил клиенту `200`. Клиент видит тайм-аут. Что знает клиент? Что ему делать и какое правило контракта делает это безопасным? Запишите ответ строкой таблицы режимов отказов.

<details>
<summary>Подсказка</summary>

Со стороны клиента «запись не удалась» и «запись удалась, но ответ потерялся» выглядят одинаково. Посмотрите на правила 5 и 6.

</details>

<details>
<summary>Ответ</summary>

Клиент не знает, произошла ли запись. Он повторяет **тот же** запрос с **тем же** `(client, seq)` на новом лидере. Правило 5 делает это безопасным: если запись была применена, таблица дедупликации возвращает исходный результат и ничего не меняет; если нет — она применяется сейчас.

| Компонент | Отказ | Как мы замечаем | Что видит пользователь | Что мы делаем |
|---|---|---|---|---|
| Лидер | падает после коммита, до ответа | тайм-аут у клиента; новые выборы | одна медленная запись (тайм-аут + повтор), затем `200` | клиент повторяет запрос с тем же идентификатором; дедупликация возвращает сохранённый результат |

</details>

### Упражнение 2 — Напишите тест: повтор применяется один раз (средне)

Добавьте в конец `src/main.rs` контрактную функцию `check_retry_contract`: запишите `color = blue` с `(7, 1)`, затем `color = green` с `(7, 2)`, затем снова отправьте первый запрос `(7, 1)` (его ответ «потерялся»). Значение должно остаться `green`. Добавьте тестовый модуль, который запускает обе контрактные функции на `MemStore`. Запустите, прочитайте ошибку и исправьте `MemStore`.

<details>
<summary>Подсказка</summary>

Для исправления нужен `std::collections::HashSet<RequestId>` в `MemStore`. `HashSet::insert` возвращает `false`, если значение уже было в множестве.

</details>

<details>
<summary>Ответ</summary>

```rust
/// A retried request must be applied at most once.
pub fn check_retry_contract(store: &mut impl KvStore) {
    let first = RequestId { client: 7, seq: 1 };
    let second = RequestId { client: 7, seq: 2 };
    store.put("color", "blue", first).unwrap();
    store.put("color", "green", second).unwrap();
    // The answer to `first` was lost, so the client sends it again.
    store.put("color", "blue", first).unwrap();
    assert_eq!(store.get("color"), Ok(Some("green".to_string())));
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn mem_store_passes_the_basic_contract() {
        check_basic_contract(&mut MemStore::default());
    }

    #[test]
    fn mem_store_applies_a_retry_once() {
        check_retry_contract(&mut MemStore::default());
    }
}
```

С `MemStore` из этого урока `cargo test` падает:

```text
thread 'tests::mem_store_applies_a_retry_once' (6562892) panicked at src/main.rs:86:5:
assertion `left == right` failed
  left: Ok(Some("blue"))
 right: Ok(Some("green"))
```

Повтор перезаписал более новое значение — ровно та ошибка, которая теряет данные в настоящем кластере. Исправление (поменяйте строку `use` на `use std::collections::{HashMap, HashSet};`):

```rust
/// The simplest store that meets the contract: one HashMap in memory.
#[derive(Default)]
pub struct MemStore {
    map: HashMap<String, String>,
    seen: HashSet<RequestId>,
}

impl KvStore for MemStore {
    fn put(&mut self, key: &str, value: &str, id: RequestId) -> Result<(), KvError> {
        check_key(key)?;
        if !self.seen.insert(id) {
            return Ok(()); // a retry: already applied, do nothing
        }
        self.map.insert(key.to_string(), value.to_string());
        Ok(())
    }

    fn get(&mut self, key: &str) -> Result<Option<String>, KvError> {
        check_key(key)?;
        Ok(self.map.get(key).cloned())
    }

    fn delete(&mut self, key: &str, _id: RequestId) -> Result<bool, KvError> {
        check_key(key)?;
        Ok(self.map.remove(key).is_some())
    }
}
```

```text
running 2 tests
..
test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Почему это работает: второй `put` с `(7, 1)` находит идентификатор в `seen` и возвращается без записи. Множество *всех* идентификаторов растёт бесконечно; в итоговом проекте вы храните только последний `seq` для каждого клиента (подсказка к M2), и этого достаточно, потому что клиент отправляет свои запросы по порядку.

</details>

### Упражнение 3 — Зачем реплицировать таблицу дедупликации? (средне)

Друг предлагает: «Храни таблицу дедупликации только на лидере. Записи всё равно получает только он». Опишите последовательность событий, при которой это теряет или портит данные.

<details>
<summary>Подсказка</summary>

Объедините Упражнение 1 (ответ потерян после коммита) со сменой лидера.

</details>

<details>
<summary>Ответ</summary>

1. Клиент 7 пишет `color = blue` с `(7, 1)`; лидер A коммитит и применяет запись, затем падает до ответа.
2. Лидером становится узел B. Его таблица пуста, потому что таблица жила только в памяти A.
3. Другой клиент, 8, пишет `color = green` с `(8, 1)` на B; запись применена и подтверждена ответом `200`. Затем клиент 7 после своего тайм-аута повторяет `(7, 1)` на B.
4. B не знает `(7, 1)` и применяет его снова: `color` снова `blue`, и более новая подтверждённая запись клиента 8 потеряна.

Если таблица внутри реплицируемого конечного автомата, B тоже применил `(7, 1)` из журнала и поэтому узнаёт повтор.

</details>

### Упражнение 4 — Оцените стоимость `fsync` (сложно)

Вашему SSD нужно около 2 мс на один `fsync`. (a) Если каждой записи нужен свой `fsync` на лидере, сколько записей в секунду максимум может сделать один лидер? (b) При пакетах по 50 записей на `fsync`? (c) Почему настоящий предел в кластере из трёх узлов обычно ниже, чем (b)? Добавьте маленькую функцию для (a) и (b) в `code/p23-estimate` из Урока 23.2, с тестом.

<details>
<summary>Подсказка</summary>

Один `fsync` за раз: 1 000 мс / 2 мс на `fsync`. Для (c) подумайте, что ещё должно произойти, прежде чем запись будет закоммичена.

</details>

<details>
<summary>Ответ</summary>

(a) 1 000 / 2 = 500 записей в секунду. (b) 500 × 50 = 25 000 записей в секунду. (c) Запись закоммичена только тогда, когда большинство сделало ей `fsync`, поэтому добавляются сетевой круговой путь до ведомого и собственный `fsync` ведомого; время CPU (Central Processing Unit, центральный процессор) на HTTP и JSON тоже считается. Конвейерная отправка (M5) скрывает часть кругового пути.

```rust
/// Upper bound of writes per second when one fsync covers `batch` writes.
fn max_writes_per_second(fsync_ms: f64, batch: u64) -> f64 {
    1000.0 / fsync_ms * batch as f64
}

#[test]
fn batching_multiplies_the_fsync_limit() {
    assert_eq!(max_writes_per_second(2.0, 1), 500.0);
    assert_eq!(max_writes_per_second(2.0, 50), 25_000.0);
}
```

Точное сравнение чисел с плавающей точкой здесь допустимо, потому что 1000 / 2 и произведения точно представимы в `f64`. В бинарнике `p23-estimate` вызовите функцию ещё и из `main` (например, в `println!`); иначе обычная сборка предупредит, что она нигде не используется. Это верхние границы для проектного документа; M5 измеряет настоящие числа.

</details>

## Вопросы для самопроверки

1. Почему этот итоговый проект — хороший проект для портфолио на позиции в инфраструктуре и базах данных?

<details>
<summary>Ответ</summary>

Многие большие системы зависят от такого реплицированного хранилища (Kubernetes — от etcd, базы данных построены из групп Raft), и на собеседованиях задают ровно его вопросы: падение лидера во время записи, линеаризуемые чтения, рост журнала, идемпотентные повторы. Проект отвечает на них вашим кодом и результатами тестов.

</details>

2. Когда `kvd` может ответить на `PUT` кодом `200`?

<details>
<summary>Ответ</summary>

Только после того, как запись журнала закоммичена (сохранена и прошла `fsync` на большинстве узлов) и применена к конечному автомату.

</details>

3. Что ведомый отвечает на запись и почему `307`, а не `302`?

<details>
<summary>Ответ</summary>

`307 Temporary Redirect` с лидером в `Location` (или `503`, если лидер ему неизвестен). `307` требует от клиента повторить запрос тем же методом и с тем же телом, поэтому `PUT` остаётся `PUT`.

</details>

4. Как read index делает чтение линеаризуемым без записи в журнал?

<details>
<summary>Ответ</summary>

Лидер запоминает свой индекс коммита, раундом heartbeat-сообщений, подтверждённым большинством, проверяет, что он всё ещё лидер, ждёт, пока конечный автомат применит как минимум этот индекс, и затем читает локально.

</details>

5. Почему снапшот должен содержать таблицу дедупликации, а не только данные «ключ-значение»?

<details>
<summary>Ответ</summary>

Потому что записи журнала до снапшота удаляются. Узел, восстановленный из снапшота, иначе не знал бы, какие запросы уже применены, и повтор мог бы примениться дважды.

</details>

6. Чем пакетная запись отличается от конвейерной отправки?

<details>
<summary>Ответ</summary>

Пакетная запись помещает много записей в одну запись журнала и один `fsync`. Конвейерная отправка шлёт следующий `AppendEntries` ведомому до того, как вернулся ответ на предыдущий. Первая экономит время диска, вторая скрывает сетевые круговые пути.

</details>

7. Почему выводы из «Готово, когда» нужно превращать в приёмочные тесты до начала вехи?

<details>
<summary>Ответ</summary>

Чтобы тест проверял обещание, а не то, что у вас случайно получилось; сначала он падает (красный), а веха готова, когда он проходит в CI (зелёный).

</details>

## Итоги

- Вариант 1 превращает ваш движок `p17-kv` и кластер Raft `p18-kv` в хранилище, которое команда могла бы эксплуатировать: HTTP API, идемпотентные записи, read index, снапшоты, пакетная запись и эксплуатация.
- Архитектура разделяет чистое ядро Raft, драйвер, который им владеет, журнал упреждающей записи, конечный автомат с таблицей дедупликации и снапшоты.
- Контракт фиксирует командные строки, HTTP API, коды статуса и шесть правил; трейт хранилища и контрактные тесты делают его исполняемым с M0.
- Вехи: M0 скелет, M1 один узел через HTTP, M2 три узла с перенаправлениями и идемпотентностью, M3 read index, M4 снапшоты, M5 пакетная запись, M6 эксплуатация и хаос в CI.
- Планка качества добавляет контрактные тесты на каждом слое, тесты на сбои для каждой вехи, фаззинг каждого декодера и числа бенчмарков до и после оптимизации.
- Изучайте etcd, TiKV, raft-rs, openraft, FoundationDB и Jepsen после того, как сами спроектировали каждую часть.
