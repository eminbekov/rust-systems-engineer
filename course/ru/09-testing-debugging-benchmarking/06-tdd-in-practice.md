# Урок 09.6 — Разработка через тестирование на практике

> **Этап 09 — Тестирование, отладка и бенчмарки** · Урок 6 из 14 · ⏱ около 135 минут

## Что вы узнаете

- Как проходит настоящая сессия TDD (test-driven development, разработка через тестирование: сначала падающий тест, потом код): список тестов, один падающий тест за раз, маленькие шаги, рефакторинг на зелёном.
- Три способа перейти от красного к зелёному: *подделка* (fake it), *триангуляция* и *очевидная реализация*.
- Как писать табличные тесты с крейтом `rstest`.
- Как исправлять ошибку через TDD и когда TDD — *не* тот инструмент.

## Перед началом

- Вы прошли [Урок 09.5 — Снапшот-тестирование](05-snapshot-testing.md).
- Вы знаете цикл «красный, зелёный, рефакторинг» из [Урока 02.8](../02-programming-basics/08-your-first-tests.md) (раздел 9) и [Урока 05.6](../05-rust-intermediate/06-testing-in-depth.md) (раздел 2): напишите падающий тест, сделайте так, чтобы он проходил, наведите порядок. Этот урок не учит циклу заново. Он показывает, как *работать* с ним целый час: что писать первым, насколько большим делать шаг и что делать, когда цикл вас удивляет.
- Вы знаете `Result`, ошибки-перечисления и `match` ([Урок 04.10](../04-structs-enums-collections-errors/10-error-handling.md)) и методы `push` и `pop` у `Vec` ([Урок 04.7](../04-structs-enums-collections-errors/07-vectors.md)).

## Новые слова

| Слово | Значение |
|---|---|
| **список тестов** (test list) | Короткий список, написанный до первого теста, желаемых поведений. Вы берёте по одному пункту. |
| **маленький шаг** (baby step) | Очень маленькое изменение: один тест, затем минимум кода, чтобы он проходил. |
| **подделка** (fake it) | Заставить тест проходить самым простым, даже глупым способом (например, вернуть константу). Следующий тест вынудит написать настоящий код. |
| **триангуляция** (triangulation) | Добавление второго теста с другими данными, чтобы «вернуть константу» больше не работало и пришлось появиться общему коду. |
| **очевидная реализация** (obvious implementation) | Когда вы уверены в настоящем коде, напишите его сразу, а не подделывайте. |
| **табличный тест** (table-driven test) | Одна тестовая функция, запускаемая со многими строками (вход, ожидаемый результат). |
| **`rstest`** | Крейт, который превращает одну тестовую функцию во многие с помощью атрибутов `#[case]`. |
| **RPN** (Reverse Polish Notation, обратная польская запись) | Способ записи вычислений, где оператор стоит *после* чисел: `3 4 +` значит 3 + 4. |
| **стек** (stack) | Стопка, где добавляют и убирают только сверху (`push` добавляет, `pop` убирает последнее добавленное). |
| **регрессионный тест** (regression test) | Тест, написанный для ошибки, чтобы она не вернулась незамеченной (Урок 05.6). |
| **спайк** (spike) | Быстрый эксперимент, написанный, чтобы узнать, как что-то работает, а потом выброшенный. |

## 1. Что мы строим: калькулятор RPN

В RPN вы пишете `3 4 +` вместо `3 + 4` и `5 1 2 + 4 * + 3 -` вместо `5 + (1 + 2) * 4 - 3`. Нет скобок и нет правил о том, какой оператор первый,
потому что работу делает **стек**: читайте токены (слова) слева направо; число кладётся в стек; оператор снимает два числа,
вычисляет и кладёт результат. В конце в стеке должно быть ровно одно число: ответ.

```text
tokens:   3     4     +
stack:   [3]  [3,4]  [7]      <- "+" popped 4 and 3 and pushed 7
```

Это хороший размер для тренировки: небольшой, с ясными правилами и с достаточным числом ошибок, чтобы подумать. Создайте пакет:

```bash
cd ~/projects/rust
git switch main
git switch -c lesson/09-06-tdd
cargo new --lib code/p09-tdd
cd code/p09-tdd
cargo add --dev rstest@0.28
```

## 2. Начните со списка тестов

Прежде чем писать код, запишите, что должна делать программа, короткими предложениями. Это занимает две минуты и освобождает голову, потому что не нужно
помнить всё. Наш список:

```text
- an empty input is an error
- a single number gives that number
- 3 4 +  gives 7
- the other operators: - * /
- longer expressions use the stack: 2 3 4 * +  gives 14
- errors: too few operands, too many operands, a word that is not a number, division by zero
```

Вы будете вычёркивать пункты и добавлять новые по мере узнавания. Правило сессии: **берите один пункт, пишите для него один падающий тест и добивайтесь, чтобы он проходил. Никогда
не держите два падающих теста.**

## 3. Цикл 1: первый тест и «подделка»

Сначала напишите тест. Положите в `src/lib.rs` *только* это:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn empty_input_is_an_error() {
        assert_eq!(evaluate(""), Err(RpnError::Empty));
    }
}
```

`cargo test` даже не компилируется, и это первый красный:

```text
error[E0425]: cannot find function `evaluate` in this scope
 --> src/lib.rs:7:20
  |
7 |         assert_eq!(evaluate(""), Err(RpnError::Empty));
  |                    ^^^^^^^^ not found in this scope
```

(Есть и вторая ошибка про `RpnError`.) Ошибка компиляции — законный красный. Она говорит, что нужно создать. Напишите самый маленький каркас с `todo!()` в теле,
чтобы тест компилировался и падал *по правильной причине*:

```rust
#[derive(Debug, PartialEq, Eq)]
pub enum RpnError {
    Empty,
}

pub fn evaluate(_input: &str) -> Result<i64, RpnError> {
    todo!()
}
```

```text
thread 'tests::empty_input_is_an_error' panicked at src/lib.rs:7:5:
not yet implemented
```

Теперь **подделка**: самый простой код, который проходит. Замените `todo!()` на `Err(RpnError::Empty)`. Тест проходит. Выглядит глупо: калькулятор, который
всегда говорит «пусто»! Но это намеренный маленький шаг: тест проходит, структура компилируется, а следующие тесты вынудят написать настоящее
поведение. Не пишите больше, чем требует тест.

> 💡 **Совет:** «красный по правильной причине» важен. Если тест падает из-за опечатки или неверного импорта, он ничего не доказывает про код. Всегда читайте
> сообщение о падении и спрашивайте: *то ли это падение, которого я ждал?*

## 4. Цикл 2: следующий тест вынуждает написать настоящий код

Добавьте второй пункт списка:

```rust
    #[test]
    fn a_single_number_is_its_own_result() {
        assert_eq!(evaluate("5"), Ok(5));
    }
```

```text
thread 'tests::a_single_number_is_its_own_result' panicked at src/lib.rs:21:9:
assertion `left == right` failed
  left: Err(Empty)
 right: Ok(5)
```

Это тот красный, который мы хотели: подделанная константа больше не работает. Два теста вместе *триангулируют*: «всегда `Err(Empty)`» не может удовлетворить оба, поэтому код должен смотреть на
свой вход. Напишите минимум кода:

```rust
pub fn evaluate(input: &str) -> Result<i64, RpnError> {
    if input.trim().is_empty() {
        return Err(RpnError::Empty);
    }
    Ok(input.trim().parse().unwrap())
}
```

Оба теста проходят. Обратите внимание на `unwrap()`: если текст не число, программа паникует. Для готовой программы это неверно, но
**пока нормально**: никакой тест ещё не требует правильного поведения. Это есть в нашем списке («слово, не являющееся числом»), и когда мы напишем этот тест, он вынудит нас
заменить `unwrap`. TDD значит писать код, которого требуют тесты, и не больше; отсутствующий тест — это отсутствующее требование.

## 5. Цикл 3: сложение и первый настоящий алгоритм

```rust
    #[test]
    fn adds_two_numbers() {
        assert_eq!(evaluate("3 4 +"), Ok(7));
    }
```

```text
thread 'tests::adds_two_numbers' panicked at src/lib.rs:10:29:
called `Result::unwrap()` on an `Err` value: ParseIntError { kind: InvalidDigit }
```

Красный: `"3 4 +"` — не число. Теперь мы уверены в алгоритме (стек, из раздела 1), поэтому используем **очевидную реализацию** и не подделываем:

```rust
pub fn evaluate(input: &str) -> Result<i64, RpnError> {
    if input.trim().is_empty() {
        return Err(RpnError::Empty);
    }
    let mut stack: Vec<i64> = Vec::new();
    for token in input.split_whitespace() {
        if token == "+" {
            let b = stack.pop().unwrap();
            let a = stack.pop().unwrap();
            stack.push(a + b);
        } else {
            stack.push(token.parse().unwrap());
        }
    }
    Ok(stack.pop().unwrap())
}
```

**Что происходит:**

1. `input.split_whitespace()` делит текст по любым пробелам, табуляциям или переводам строк.
2. `+` снимает два числа со стека. Второе снятое (`b`) — правый операнд, первое (`a`) — левый: для `-` и `/` это важно.
3. Любой другой токен разбирается как число и кладётся в стек. В конце последнее число в стеке — ответ.

Все три теста проходят. **Какой размер шага правильный?** Если вы уверены и код короткий, делайте шаг побольше (очевидная реализация). Если последний шаг вас удивил,
делайте поменьше (подделка). Размер меняется в течение сессии; это нормально.

## 6. Цикл 4: таблица случаев с `rstest`

Дальше в списке `-`, `*` и `/`. Ещё три почти одинаковых теста — много копирования. Крейт `rstest` позволяет одной тестовой функции
запускаться со многими строками. Замените `adds_two_numbers` таблицей (и добавьте `use rstest::rstest;` в `mod tests`):

```rust
    #[rstest]
    #[case("3 4 +", 7)]
    #[case("10 4 -", 6)]
    #[case("3 4 *", 12)]
    #[case("20 4 /", 5)]
    fn applies_an_operator(#[case] input: &str, #[case] expected: i64) {
        assert_eq!(evaluate(input), Ok(expected));
    }
```

**Что происходит:** `#[rstest]` заменяет `#[test]`. Каждая строка `#[case(...)]` — одна строка таблицы: её значения передаются параметрам с пометкой `#[case]` по порядку.
`rstest` генерирует по одному тесту на строку с именами `applies_an_operator::case_1`, `case_2` и так далее, поэтому вывод точно говорит, какая строка упала:

```text
test tests::applies_an_operator::case_1 ... ok
test tests::applies_an_operator::case_3 ... FAILED
test tests::applies_an_operator::case_2 ... FAILED
test tests::applies_an_operator::case_4 ... FAILED
---- tests::applies_an_operator::case_3 stdout ----
thread 'tests::applies_an_operator::case_3' panicked at src/lib.rs:17:38:
called `Result::unwrap()` on an `Err` value: ParseIntError { kind: InvalidDigit }
```

(Мы сделали сразу три новые строки. Наше правило — один падающий тест за раз; три строки *одной* таблицы, падающие по *одной* причине, считаются одним шагом.) Самое
быстрое изменение, чтобы они проходили, — `match` с веткой на каждый оператор:

```rust
        match token {
            "+" => {
                let b = stack.pop().unwrap();
                let a = stack.pop().unwrap();
                stack.push(a + b);
            }
            "-" => {
                let b = stack.pop().unwrap();
                let a = stack.pop().unwrap();
                stack.push(a - b);
            }
            // ...and the same for "*" and "/"
            number => stack.push(number.parse().unwrap()),
        }
```

Все шесть тестов зелёные. Теперь посмотрите на этот код: одни и те же четыре строки скопированы четыре раза. **Это шаг рефакторинга**, и тесты делают его безопасным. Вынесите
повторяющуюся часть в функцию:

```rust
pub fn evaluate(input: &str) -> Result<i64, RpnError> {
    if input.trim().is_empty() {
        return Err(RpnError::Empty);
    }
    let mut stack: Vec<i64> = Vec::new();
    for token in input.split_whitespace() {
        match token {
            "+" | "-" | "*" | "/" => {
                let b = stack.pop().unwrap();
                let a = stack.pop().unwrap();
                stack.push(apply(token, a, b));
            }
            number => stack.push(number.parse().unwrap()),
        }
    }
    Ok(stack.pop().unwrap())
}

fn apply(operator: &str, a: i64, b: i64) -> i64 {
    match operator {
        "+" => a + b,
        "-" => a - b,
        "*" => a * b,
        "/" => a / b,
        _ => unreachable!(),
    }
}
```

Запустите тесты: всё ещё зелёные, значит, поведение не изменилось. (`unreachable!()` паникует, если до него дойдёт управление; здесь внешний `match` гарантирует, что не дойдёт.)
**Рефакторьте только на зелёном и запускайте тесты после каждого маленького изменения.** Если тест стал красным, отмените последнее изменение, и вы точно знаете, что его сломало.

Теперь добавьте две строки для более длинных выражений:

```rust
    #[case("2 3 4 * +", 14)]
    #[case("5 1 2 + 4 * + 3 -", 14)]
```

Они проходят **сразу**. Это допустимо, но будьте осторожны: тест, который никогда не был красным, возможно, ничего не проверяет. Здесь всё хорошо, потому что эти строки проверяют
реальное (стек работает для более глубоких выражений), а первые четыре строки уже доказали, что таблица может упасть. Если сомневаетесь, сломайте код
нарочно (например, замените `a - b` на `b - a`) и посмотрите, как тест покраснеет.

## 7. Цикл 5: ошибки и что обнаружили тесты

Последние пункты списка — ошибки. Напишите все строки сразу, второй таблицей:

```rust
    #[rstest]
    #[case("+", RpnError::NotEnoughOperands)]
    #[case("1 +", RpnError::NotEnoughOperands)]
    #[case("1 2", RpnError::TooManyOperands)]
    #[case("1 x +", RpnError::BadToken("x".to_string()))]
    #[case("1 0 /", RpnError::DivisionByZero)]
    fn reports_errors(#[case] input: &str, #[case] expected: RpnError) {
        assert_eq!(evaluate(input), Err(expected));
    }
```

Первый красный — ошибка компиляции, потому что вариантов ошибок ещё нет:

```text
error[E0599]: no variant, associated function, or constant named `NotEnoughOperands` found for enum `RpnError` in the current scope
  --> src/lib.rs:61:27
```

Добавьте в перечисление варианты `NotEnoughOperands`, `TooManyOperands`, `BadToken(String)` и `DivisionByZero`, и получите настоящий красный:

```text
---- tests::reports_errors::case_3 stdout ----
assertion `left == right` failed
  left: Ok(2)
 right: Err(TooManyOperands)
---- tests::reports_errors::case_2 stdout ----
called `Option::unwrap()` on a `None` value
---- tests::reports_errors::case_5 stdout ----
attempt to divide by zero
---- tests::reports_errors::case_4 stdout ----
called `Result::unwrap()` on an `Err` value: ParseIntError { kind: InvalidDigit }
```

Прочитайте это внимательно, потому что тут сказано важное. Случай 3 показывает, что `"1 2"` **вернул `Ok(2)`** — неверный ответ без всякого
предупреждения: наш калькулятор молча выбросил `1`. Без теста мы бы этого не заметили. Остальные случаи — паники от `unwrap`, которые мы оставили нарочно. Теперь
замените каждый `unwrap` настоящей ошибкой:

```rust
pub fn evaluate(input: &str) -> Result<i64, RpnError> {
    if input.trim().is_empty() {
        return Err(RpnError::Empty);
    }
    let mut stack: Vec<i64> = Vec::new();
    for token in input.split_whitespace() {
        match token {
            "+" | "-" | "*" | "/" => {
                let b = stack.pop().ok_or(RpnError::NotEnoughOperands)?;
                let a = stack.pop().ok_or(RpnError::NotEnoughOperands)?;
                stack.push(apply(token, a, b)?);
            }
            number => {
                let value = number
                    .parse()
                    .map_err(|_| RpnError::BadToken(number.to_string()))?;
                stack.push(value);
            }
        }
    }
    match stack.as_slice() {
        [result] => Ok(*result),
        _ => Err(RpnError::TooManyOperands),
    }
}

fn apply(operator: &str, a: i64, b: i64) -> Result<i64, RpnError> {
    match operator {
        "+" => Ok(a + b),
        "-" => Ok(a - b),
        "*" => Ok(a * b),
        "/" if b == 0 => Err(RpnError::DivisionByZero),
        "/" => Ok(a / b),
        _ => unreachable!(),
    }
}
```

**Что происходит:** `ok_or(error)` превращает `Option` в `Result`, поэтому недостающий операнд становится `NotEnoughOperands`, а `?` досрочно возвращает его.
`map_err` преобразует ошибку разбора в наш `BadToken` с проблемным словом. `stack.as_slice()`, сопоставленный с `[result]`, означает «ровно один элемент»; любая другая
длина (включая пустой стек) — `TooManyOperands`. (У ветки `"/" if b == 0` есть *охранное условие* (guard): она применяется, только когда условие истинно.) Все 13 тестов проходят.

## 8. Цикл 6: сообщение об ошибке и TDD

Пользователь пишет: *«`9223372036854775807 1 +` роняет программу»*. (9223372036854775807 — наибольшее `i64`.) Ответ TDD на сообщение об ошибке всегда один: **сначала
тест, который её воспроизводит.**

```rust
    #[test]
    fn adding_past_the_largest_number_is_an_error() {
        assert_eq!(evaluate("9223372036854775807 1 +"), Err(RpnError::Overflow));
    }
```

Добавьте в перечисление вариант `Overflow` (чтобы компилировалось) и запустите:

```text
---- tests::adding_past_the_largest_number_is_an_error stdout ----
thread 'tests::adding_past_the_largest_number_is_an_error' panicked at src/lib.rs:39:19:
attempt to add with overflow
```

Ошибка воспроизведена: в отладочной сборке `a + b` паникует, когда результат не помещается. Теперь исправление: методы `checked_…` возвращают `None` вместо переполнения
(Урок 05.6):

```rust
fn apply(operator: &str, a: i64, b: i64) -> Result<i64, RpnError> {
    let result = match operator {
        "+" => a.checked_add(b),
        "-" => a.checked_sub(b),
        "*" => a.checked_mul(b),
        "/" if b == 0 => return Err(RpnError::DivisionByZero),
        "/" => a.checked_div(b),
        _ => unreachable!(),
    };
    result.ok_or(RpnError::Overflow)
}
```

Все 14 тестов проходят, и у ошибки теперь постоянная защита.

> 🔒 **Безопасность:** в *релизной* сборке (`cargo build --release`) переполнение целых по умолчанию не паникует: число молча заворачивается. Калькулятор,
> который отвечает `-9223372036854775808` на `9223372036854775807 1 +`, неверен без каких-либо признаков. Код, который делает арифметику над входом извне, должен использовать методы `checked_…`,
> а тест выше гарантирует, что это так.

Закоммитьте готовую работу; сейчас подходящий момент, потому что все тесты зелёные:

```bash
cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test
git add code/p09-tdd
git commit -m "Add p09-tdd: an RPN calculator built test-first"
```

## 9. Привычки и когда TDD — не ответ

Что сделало сессию рабочей:

- **Один падающий тест за раз.** Когда красных два, вы не знаете, какое изменение что исправило.
- **Читайте каждый красный.** Он должен падать по ожидаемой вами причине. Красный в Цикле 5 даже выявил неверный ответ.
- **Минимум кода, который проходит**, затем наведение порядка на зелёном. Тесты просят поведения, рефакторинг улучшает структуру; не смешивайте их в одном шаге.
- **Коммитьте на зелёном.** Каждый зелёный — безопасная точка, куда можно вернуться. В настоящем проекте вы бы коммитили после большинства циклов.
- **Держите список тестов живым.** Вычёркивайте, добавляйте, переставляйте. Новая идея во время цикла идёт в список, а не в код.
- **Слушайте тесты.** Тест, который трудно написать, — это сообщение: у кода слишком много зависимостей или он делает слишком много (Урок 09.3).

TDD — инструмент, а не религия. Он плохо подходит, когда:

- **Вы ещё не знаете, что строить.** Исследуйте *спайком*: напишите грубый код, чтобы научиться, потом удалите его и напишите настоящий через тест с тем, что узнали.
- **Вывод в основном визуальный или исследовательский:** разметка, диаграмма. Используйте ручные проверки и снапшоты (Урок 09.5) постфактум.
- **Код уже существует без тестов** (унаследованный код). Сначала зафиксируйте, что он делает, *характеризационными тестами* (снапшоты идеальны), затем меняйте его.
- **Стоимость теста больше его ценности:** однострочная обёртка вокруг вызова библиотеки.

> 📏 **Соглашение:** называйте тесты по поведению (`adding_past_the_largest_number_is_an_error`), а табличный тест — по группе поведений
> (`reports_errors`). Отчёт о падающей строке `reports_errors::case_4` плюс таблица в исходнике говорят, какой вход сломался.

## Частые ошибки

**1. Сначала код, потом тест.** Тест тогда следует за кодом, а не за требованием, и вы ни разу не видели его падения. Даже для
крошечной функции увидьте красный.

**2. Слишком большие шаги.** Написать пять тестов и весь алгоритм, а потом час отлаживать. Если вы застряли, удалите последнее изменение и сделайте шаг поменьше.

**3. Тестирование реализации.** Тест, который проверяет содержимое приватного `stack`, сломался бы при смене структуры данных, хотя калькулятор по-прежнему работает.
Тестируйте только то, что возвращает `evaluate`.

**4. Пропуск шага рефакторинга.** Зелёный — ещё не конец. В коде раздела 6 было четыре копии одних и тех же строк; без рефакторинга каждый новый оператор добавлял бы ещё одну копию.

**5. Таблица, которая скрывает слишком многое.** `rstest` с 40 строками загадочных чисел трудно читать. Группируйте строки (одна таблица для результатов, одна для ошибок) и выбирайте строки, каждая из которых
чему-то учит.

## Попробуйте сами

1. Создайте пакет. Пройдите разделы 3–8 по порядку. После каждого цикла запускайте `cargo test` и убеждайтесь, что видите красный *до* того, как пишете код.
2. После Цикла 4 сломайте код нарочно (`a - b` на `b - a`), посмотрите на падение `applies_an_operator::case_2` и отмените.
3. Выполните `cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test`. Закоммитьте, как показано в разделе 8.

## Упражнения

### Упражнение 1 — Предскажите цвет (легко)

Для каждого нового теста предскажите, красный он или зелёный с готовым калькулятором, а затем запустите: (а) `evaluate("-3 4 +")` равно `Ok(1)`; (б) `evaluate("  3   4\t+\n")` равно `Ok(7)`.

<details>
<summary>Подсказка</summary>

Для (а): `"-3"` — тот же токен, что оператор `"-"`? Для (б): что делает `split_whitespace` с несколькими пробелами?

</details>

<details>
<summary>Ответ</summary>

```rust
    #[test]
    fn negative_numbers_are_numbers() {
        assert_eq!(evaluate("-3 4 +"), Ok(1));
    }

    #[test]
    fn extra_whitespace_is_ignored() {
        assert_eq!(evaluate("  3   4\t+\n"), Ok(7));
    }
```

Оба зелёные сразу: `"-3"` — это другой токен, чем `"-"`, поэтому он попадает в ветку чисел и разбирается как -3; а `split_whitespace` игнорирует любое количество пробельных символов.
Поскольку они ни разу не были красными, проверьте, что второй тест *может* упасть: замените `split_whitespace()` на `split(" ")` и запустите его. Он падает с `Err(BadToken(""))`, значит,
тест настоящий. Затем отмените изменение.

</details>

### Упражнение 2 — Новый оператор, сначала тест (средне)

Добавьте оператор остатка `%` (`7 3 %` равно `1`; `7 0 %` равно `Err(DivisionByZero)`). Работайте циклом: сначала напишите таблицу, увидьте красный, затем пишите код.

<details>
<summary>Подсказка</summary>

Без кода `%` разбирается как число, и вы получаете `BadToken("%")`. Метод `checked_rem` у `i64` возвращает `None` при переполнении (и при делителе 0), поэтому для деления на ноль нужна отдельная ветка перед ним.

</details>

<details>
<summary>Ответ</summary>

Тест:

```rust
    #[rstest]
    #[case("7 3 %", Ok(1))]
    #[case("7 0 %", Err(RpnError::DivisionByZero))]
    fn remainder(#[case] input: &str, #[case] expected: Result<i64, RpnError>) {
        assert_eq!(evaluate(input), expected);
    }
```

Оба случая красные (`BadToken("%")`). Код: добавьте `"%"` в ветку операторов в `evaluate` (`"+" | "-" | "*" | "/" | "%" =>`) и измените `apply`:

```rust
        "/" | "%" if b == 0 => return Err(RpnError::DivisionByZero),
        "/" => a.checked_div(b),
        "%" => a.checked_rem(b),
```

Почему это работает: охранное условие `if b == 0` относится к обеим альтернативам образца `"/" | "%"`, поэтому одна строка покрывает оба деления на ноль. Все 18 тестов зелёные.

</details>

### Упражнение 3 — Ошибка из практики (сложно)

Пользователь сообщает: *«`1 2 + 3` возвращает ошибку, а я ожидал список из двух результатов, `3 3`»*. Это ошибка? Решите и напишите тест, который
документирует ваше решение. Затем объясните, что должен говорить пункт списка тестов, когда требование неясно.

<details>
<summary>Подсказка</summary>

Проверьте требование из раздела 1: в конце в стеке должно быть ровно одно число. Пользователь хочет то, что калькулятор никогда не должен был делать.

</details>

<details>
<summary>Ответ</summary>

Это не ошибка: спецификация говорит, что выражение оставляет ровно одно число, а калькулятор сообщает `TooManyOperands`. Сообщение — это *запрос новой возможности* (или
недоразумение). Тест документирует решение:

```rust
    #[test]
    fn several_results_are_not_allowed() {
        assert_eq!(evaluate("1 2 + 3"), Err(RpnError::TooManyOperands));
    }
```

Он зелёный сразу и защищает правило. Когда требование неясно, поставьте в список тестов *вопрос* («должен ли `1 2 3` быть списком?»), спросите того, кто решает, и пишите тест только
после ответа. Тест — это исполняемое решение; не гадайте.

</details>

## Вопросы для самопроверки

1. Каков первый шаг цикла TDD и что нужно в нём проверить?

<details>
<summary>Ответ</summary>

Написать падающий тест (красный). Проверьте, что он падает по ожидаемой причине, прочитав сообщение, потому что тест, падающий по неверной причине, ничего не доказывает.

</details>

2. Что такое «подделывай, пока не получится» (fake it) и чем это полезно?

<details>
<summary>Ответ</summary>

Сделать так, чтобы тест проходил самым простым кодом, даже константой. Это быстро приводит к зелёному, а следующий тест с другими данными (триангуляция) вынуждает написать настоящий
код.

</details>

3. Когда в TDD делают рефакторинг?

<details>
<summary>Ответ</summary>

Только когда все тесты зелёные, маленькими шагами, запуская тесты после каждого. Если тест стал красным, отмените последнее изменение.

</details>

4. Что вы делаете первым делом после получения сообщения об ошибке?

<details>
<summary>Ответ</summary>

Пишете тест, который воспроизводит ошибку, на самом низком возможном уровне, и видите, как он падает. Затем исправляете код. Тест остаётся как регрессионный.

</details>

5. Что делает `#[case(...)]` в `rstest`?

<details>
<summary>Ответ</summary>

Каждая строка `#[case]` — одна строка таблицы: `rstest` генерирует отдельный тест (с именем `case_1`, `case_2`, …), который запускает функцию со значениями этой строки.

</details>

6. Назовите две ситуации, где TDD — не лучший инструмент.

<details>
<summary>Ответ</summary>

Например: вы ещё не знаете, что строить (используйте спайк); вывод в основном визуальный; код уже существует без тестов (сначала характеризационные тесты); тест стоит дороже, чем
приносит пользы.

</details>

## Итоги

- Начинайте со **списка тестов**. Берите один пункт, пишите один падающий тест, добивайтесь прохождения, наводите порядок. Только один красный за раз.
- **Читайте каждый красный:** он должен падать по правильной причине. Ошибки компиляции — законные красные.
- Три пути к зелёному: *подделка* (константа), *триангуляция* (второй тест с другими данными), *очевидная реализация* (когда вы уверены). Делайте большие шаги, когда уверены, и маленькие, когда удивлены.
- **Рефакторьте только на зелёном**, с тестами как страховочной сеткой. Выносите дублирование, затем снова запускайте тесты.
- `rstest` делает табличные тесты: `#[rstest]` и один `#[case(...)]` на строку; каждая строка — отдельный тест.
- Сообщение об ошибке начинается с воспроизводящего теста. Для входа извне используйте арифметику `checked_…`, потому что релизные сборки заворачиваются молча.
- TDD — инструмент: используйте спайк при исследовании и характеризационные тесты для унаследованного кода.
