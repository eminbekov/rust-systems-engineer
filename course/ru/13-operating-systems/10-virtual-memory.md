# Урок 13.10 — Виртуальная память

## Что вы узнаете

- Почему каждый процесс получает своё собственное *адресное пространство* и как ядро и CPU (Central Processing Unit, центральный процессор) создают для каждого процесса иллюзию, что вся память принадлежит ему.

- Что на самом деле означает ошибка сегментации.

## Новые слова

| Слово | Значение |
|---|---|
| **физическая память** (physical memory) | Настоящие микросхемы RAM (Random Access Memory, оперативная память). У каждого байта один *физический адрес*. |
| **виртуальный адрес** (virtual address) | Адрес, которым пользуется программа, например в указателе. CPU переводит его в физический адрес при каждом обращении. |
| **адресное пространство** (address space) | Весь диапазон виртуальных адресов, которыми может пользоваться один процесс. У каждого процесса оно своё. |
| **страница** (page) | Блок виртуальной памяти фиксированного размера, обычно 4 КиБ (4096 байт). Память отображается постранично. |
| **кадр** (frame) | Блок физической памяти размером со страницу. Страница хранится в кадре. |
| **таблица страниц** (page table) | Таблица, которую ядро ведёт для каждого процесса: в каком кадре лежит каждая страница и что процессу с ней можно делать (читать, писать, исполнять). |
| **MMU** (Memory Management Unit, блок управления памятью) | Часть CPU, которая переводит виртуальные адреса в физические, читая таблицу страниц. |
| **TLB** (Translation Lookaside Buffer, буфер ассоциативной трансляции) | Маленький кэш внутри CPU, который помнит недавние переводы, чтобы MMU не читал таблицу страниц каждый раз. |
| **страничный сбой** (page fault) | CPU останавливает программу, потому что страница не отображена или доступ запрещён. Затем ядро исправляет это (отображает кадр) или убивает программу. |
| **малый / большой сбой** (minor / major fault) | Малый сбой исправляется без диска (например, выдаётся новая нулевая страница). Для большого сначала нужно прочитать данные с диска. |
| **подкачка по требованию** (demand paging) | Ядро выдаёт кадр только при первом обращении к странице, а не в момент запроса памяти. |
| **RSS** (Resident Set Size, резидентный размер) | Сколько памяти процесса прямо сейчас действительно находится в RAM. |
| **копирование при записи** (copy-on-write, CoW) | После `fork` родитель и потомок делят одни и те же кадры. Кадр копируется, только когда один из них в него пишет. |
| **ошибка сегментации** (segmentation fault, SIGSEGV) | Сигнал, который ядро посылает, когда программа обращается к адресу, которым ей пользоваться нельзя. |
| **ASLR** (Address Space Layout Randomization, рандомизация размещения адресного пространства) | Ядро при каждом запуске кладёт стек, кучу и код по случайным адресам, что усложняет атаки. |
| **OOM killer** (Out Of Memory killer, убийца при нехватке памяти) | Часть ядра, которая убивает процесс, когда RAM и swap заполнены. |

## 1. Зачем нужна виртуальная память

Представьте гостиницу. Каждый гость получает ключ-карту с надписью «номер 12». В одной гостинице номер 12
гостя A и номер 12 гостя B — разные настоящие комнаты: администратор ведёт для каждого гостя личный список,
где написано «ваш номер 12 — это на самом деле комната 304 на третьем этаже». Гости никогда не видят
настоящих номеров комнат. Они не могут войти в чужую комнату, потому что в их списке её нет.

Виртуальная память устроена так же:

- Каждый **процесс** получает своё **адресное пространство**: огромный диапазон адресов, которые как будто
  все принадлежат ему.
- Адреса внутри вашей программы (каждый указатель, каждый `&x`) — это **виртуальные адреса**.
- Ядро ведёт для каждого процесса личную **таблицу страниц**. При каждом обращении к памяти **MMU** в CPU
  по этой таблице переводит виртуальный адрес в **физический адрес** в RAM.

Это даёт три больших преимущества:

1. **Изоляция.** Процесс не может прочитать или испортить память другого процесса: в его таблице просто нет
   записей об этих кадрах. Ошибка в одной программе не роняет остальные.
2. **Простая картина для каждой программы.** Любую программу можно скомпоновать и загрузить так, будто она
   одна в памяти ([Урок 12.12](../12-computer-systems/12-linking-and-loading.md)).
3. **Гибкость.** Ядро может выдать RAM позже, разделить её между процессами или перенести на диск, а
   программа этого не заметит.

## 2. Страницы и таблицы страниц

Отображать каждый байт отдельно — значит держать огромную таблицу. Поэтому память отображается блоками
одного размера: **страницами** (виртуальная) и **кадрами** (физическая). В Linux на большинстве процессоров
страница занимает **4 КиБ**. Тогда виртуальный адрес делится на две части:

```text
virtual address 0x0000_aaaa_db09_bd60   (page size 4096 = 0x1000)

  page number = address / 4096 = 0xaaaadb09b   -> looked up in the page table
  offset      = address % 4096 = 0xd60 (3424)  -> copied unchanged

  page table of this process
  +-------------+--------------+-------------+
  | page number | frame number | permissions |
  +-------------+--------------+-------------+
  | 0xaaaadb09b | 0x3f2a1      | rw-         |
  | ...         | ...          | ...         |
  +-------------+--------------+-------------+

physical address = frame 0x3f2a1 * 4096 + 0xd60
```

Смещение в обоих адресах одинаковое. Заменяется только номер страницы — на номер кадра. Настоящие таблицы
страниц — это деревья из нескольких уровней (обычно четырёх на arm64 и x86-64), чтобы пустым частям адресного
пространства вообще не нужна была таблица, но идея — именно такой поиск.

Читать таблицу страниц из памяти при каждом обращении было бы медленно. CPU хранит недавние переводы в
**TLB** — крошечном кэше, похожем на кэши данных из [Урока 12.9](../12-computer-systems/09-memory-hierarchy-and-caches.md).
Большинство обращений попадает в TLB и ничего лишнего не стоит.

Посмотрим на настоящие адреса. Создайте `src/bin/pages.rs`:

```rust
use nix::unistd::{SysconfVar, sysconf};

fn main() {
    let page = sysconf(SysconfVar::PAGE_SIZE)
        .expect("sysconf failed")
        .expect("page size is unknown") as usize;
    println!("page size: {page} bytes");

    let on_stack: u64 = 42;
    let on_heap = Box::new(7u64);
    let places = [
        ("stack", &on_stack as *const u64 as usize),
        ("heap", &*on_heap as *const u64 as usize),
        ("code", main as fn() as usize),
    ];
    for (name, addr) in places {
        println!(
            "{name:>5}: address {addr:#014x} -> page {:#011x}, offset {:4}",
            addr / page,
            addr % page
        );
    }
}
```

**Что происходит:**

1. `sysconf(SysconfVar::PAGE_SIZE)` спрашивает у системы размер страницы. Возвращается `Result<Option<_>>`:
   вызов может завершиться ошибкой, а некоторые значения могут быть «неизвестны». Никогда не пишите `4096`
   вручную.
2. `&on_stack as *const u64 as usize` превращает ссылку в сырой указатель, а затем в обычное число —
   виртуальный адрес. Это безопасно: мы только смотрим на число и никогда не используем его как указатель.
3. `main as fn() as usize` — адрес машинного кода самой функции `main`.
4. Для каждого адреса мы печатаем номер страницы (`/`) и смещение внутри страницы (`%`).

Запустите дважды командой `cargo run --bin pages`:

```text
page size: 4096 bytes
stack: address 0xffffc5b538d0 -> page 0xffffc5b53, offset 2256
 heap: address 0xaaaadb09bd60 -> page 0xaaaadb09b, offset 3424
 code: address 0xaaaab6319ec8 -> page 0xaaaab6319, offset 3784
page size: 4096 bytes
stack: address 0xffffc6a6e620 -> page 0xffffc6a6e, offset 1568
 heap: address 0xaaaacc550d60 -> page 0xaaaacc550, offset 3424
 code: address 0xaaaac2ef9ec8 -> page 0xaaaac2ef9, offset 3784
```

Адреса меняются при каждом запуске. Это **ASLR**: ядро выбирает случайные места для стека, кучи и
программы, чтобы атакующий не мог угадать, где что лежит. Заметьте, что *смещения* значения в куче и
функции `main` остаются прежними: сдвигаются только целые страницы.

> 🔒 **Безопасность:** ASLR — одна из защит, которые затрудняют эксплуатацию ошибок работы с памятью. Саму
> ошибку она не исправляет; безопасный Rust вообще не допускает большинства таких ошибок ([Урок 10.12](../10-security-fundamentals/12-memory-safety-and-reviewing-unsafe.md)).

## 3. Карта процесса: `/proc/self/maps`

Адресное пространство почти пустое. Используются только некоторые диапазоны — **отображения** (mappings,
их ещё называют областями). Ядро показывает их в файле `/proc/<pid>/maps`; `/proc/self` всегда означает
«процесс, который читает этот файл». Создайте `src/bin/maps.rs`:

```rust
use std::fs;

fn main() {
    let maps = fs::read_to_string("/proc/self/maps").expect("cannot read /proc/self/maps");
    for line in maps.lines() {
        println!("{line}");
    }
}
```

`cargo run --bin maps` печатает около 25 строк. Вот вывод, где середина сокращена (строка `...` —
наша):

```text
aaaad19e0000-aaaad1a2f000 r-xp 00000000 00:34 316190                     /work/target/debug/maps
aaaad1a3d000-aaaad1a40000 r--p 0005d000 00:34 316190                     /work/target/debug/maps
aaaad1a40000-aaaad1a41000 rw-p 00060000 00:34 316190                     /work/target/debug/maps
aaab075f9000-aaab0761a000 rw-p 00000000 00:00 0                          [heap]
ffff9e240000-ffff9e3dc000 r-xp 00000000 00:57 951780                     /usr/lib/aarch64-linux-gnu/libc.so.6
ffff9e3dc000-ffff9e3ed000 ---p 0019c000 00:57 951780                     /usr/lib/aarch64-linux-gnu/libc.so.6
...
ffff9e47b000-ffff9e47d000 r-xp 00000000 00:00 0                          [vdso]
ffffc2483000-ffffc24a4000 rw-p 00000000 00:00 0                          [stack]
```

(Путь к вашей программе будет внутри папки вашего проекта, а не `/work`.) Каждая строка — одно отображение:

| Столбец | Пример | Значение |
|---|---|---|
| диапазон адресов | `aaaad19e0000-aaaad1a2f000` | начальный и конечный виртуальный адрес (конец не включается), в шестнадцатеричном виде |
| права | `r-xp` | **r** — чтение, **w** — запись, **x** — исполнение; `p` = приватное (копирование при записи), `s` = общее |
| смещение | `0005d000` | с какого места файла начинается это отображение |
| устройство, inode | `00:34 316190` | какой это файл (inode объясняет Урок 13.12); `0` для памяти без файла |
| путь | `[heap]` | файл или имя в квадратных скобках для особых областей |

**Что происходит**, если читать карту сверху вниз:

1. Три отображения файла программы: машинный код (`r-x`, можно исполнять, но нельзя менять), константные
   данные (`r--`) и глобальные переменные (`rw-`). Это сегменты ELF из Урока 12.12.
2. `[heap]`: классическая куча, которая растёт вверх. Здесь живут небольшие значения `Box` и `Vec`.
3. Библиотека C `libc.so.6` (и, в скрытых строках, динамический загрузчик `ld-linux-aarch64.so.1`),
   отображённые так же. Строка `---p` — промежуток вообще без прав: обращение к нему роняет программу.
4. `[vdso]` — крошечная библиотека, которую само ядро кладёт в каждый процесс, чтобы некоторые вызовы,
   например «который час?», не требовали настоящего системного вызова.
5. `[stack]`: стек главного потока, ближе к верху адресного пространства.

> 💡 **Совет:** можно прочитать карту любого вашего процесса: `cat /proc/$$/maps` показывает карту текущей
> командной оболочки (`$$` — это PID, Process Identifier, идентификатор процесса оболочки). `pmap <pid>`
> печатает более короткую версию.

## 4. Подкачка по требованию: память выдаётся при обращении

Когда программа просит память, ядро **не** ищет сразу свободную RAM. Оно только отмечает в списке
отображений процесса: «этот диапазон адресов теперь разрешён». Таблица страниц остаётся пустой. Дальше:

1. Программа впервые обращается к адресу в новом диапазоне.
2. MMU не находит кадра для этой страницы и вызывает **страничный сбой**: CPU приостанавливает программу и
   переходит в ядро.
3. Ядро видит, что адрес разрешён, берёт свободный кадр, заполняет его нулями, записывает в таблицу страниц
   и продолжает программу с той же инструкции.

Программа ничего не замечает, кроме короткой задержки. Это и есть **подкачка по требованию**. Сбой,
исправленный вот так, из RAM, — **малый сбой**. Если бы данные сначала пришлось взять с диска (например,
страницу файла программы, которой не было в памяти, Урок 13.11), это был бы **большой сбой**.

Посмотрим на это. Создайте `src/bin/lazy.rs`:

```rust
use std::fs;
use std::hint::black_box;

use nix::sys::resource::{UsageWho, getrusage};
use nix::unistd::{SysconfVar, sysconf};

/// Resident set size of this process in KiB, read from /proc/self/status.
fn rss_kib() -> u64 {
    let status = fs::read_to_string("/proc/self/status").expect("cannot read status");
    let line = status
        .lines()
        .find(|l| l.starts_with("VmRSS:"))
        .expect("no VmRSS line");
    line.split_whitespace().nth(1).unwrap().parse().unwrap()
}

fn report(when: &str) {
    let faults = getrusage(UsageWho::RUSAGE_SELF)
        .expect("getrusage failed")
        .minor_page_faults();
    println!(
        "{when:<28} RSS = {:>7} KiB, minor faults = {faults:>6}",
        rss_kib()
    );
}

fn main() {
    const SIZE: usize = 256 * 1024 * 1024; // 256 MiB
    let page = sysconf(SysconfVar::PAGE_SIZE).unwrap().unwrap() as usize;

    report("start");
    let mut buffer = vec![0u8; SIZE];
    report("after vec![0u8; 256 MiB]");

    for i in (0..SIZE).step_by(page) {
        buffer[i] = 1; // one write per page
    }
    report("after one write per page");

    black_box(&buffer);
}
```

**Что происходит:**

1. `rss_kib` читает `/proc/self/status` — текстовый файл, который ядро пишет для каждого процесса, — и
   берёт число из строки `VmRSS:  1660 kB`. RSS — это память, которая действительно лежит в RAM.
2. `getrusage(UsageWho::RUSAGE_SELF)` спрашивает у ядра расход ресурсов этим процессом;
   `minor_page_faults()` — число малых сбоев с момента запуска.
3. `vec![0u8; SIZE]` просит 256 МиБ нулей. Для такого большого блока аллокатор напрямую просит у ядра новое
   отображение, а ядро обещает, что новые страницы заполнены нулями, поэтому пока ничего писать не нужно.
4. Цикл записывает по одному байту в каждую страницу: `step_by(page)` прыгает сразу на 4096 байт.
5. `black_box(&buffer)` говорит компилятору «считай, что это значение используется», чтобы оптимизатор не
   удалил цикл.

Запустите командой `cargo run --bin lazy`:

```text
start                        RSS =    1660 KiB, minor faults =    102
after vec![0u8; 256 MiB]     RSS =    1668 KiB, minor faults =    105
after one write per page     RSS =  263808 KiB, minor faults =  65640
```

Выделение 256 МиБ изменило RSS всего на 8 КиБ. Затем цикл вызвал около 65 536 страничных сбоев:
256 МиБ / 4 КиБ = 65 536 страниц, по одному сбою на каждую, и RSS вырос на 256 МиБ. Память стала
настоящей только тогда, когда к ней обратились.

> ⚡ **Производительность:** страничный сбой стоит примерно микросекунду. Один раз — это ничто, но программа,
> которая трогает миллионы новых страниц, проводит заметное время в ядре. Переиспользовать буфер дешевле, чем
> каждый раз выделять новый.

Ваши числа будут немного отличаться. В некоторых системах ядро использует **прозрачные огромные страницы**
(transparent huge pages): когда вы трогаете большой выровненный диапазон, оно отображает сразу одну страницу
в 2 МиБ вместо 512 маленьких, и сбоев становится меньше. Настройку можно посмотреть командой
`cat /sys/kernel/mm/transparent_hugepage/enabled`.

Само выделение видно через `strace` ([Урок 13.3](03-system-calls.md)), из папки `~/p13-vmem` в ВМ:

```bash
strace -e trace=mmap,munmap ./target/debug/lazy
```

Последние строки:

```text
start                        RSS =    1664 KiB, minor faults =     84
mmap(NULL, 268439552, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0) = 0xffffacbcf000
after vec![0u8; 256 MiB]     RSS =    1672 KiB, minor faults =     87
after one write per page     RSS =  263812 KiB, minor faults =  64089
munmap(0xffffacbcf000, 268439552)       = 0
+++ exited with 0 +++
```

`mmap` создал новое отображение на 256 МиБ плюс одна страница для служебных данных аллокатора, а `munmap`
удалил его, когда `buffer` был уничтожен. Вызову `mmap` посвящён весь следующий урок: [Урок 13.11](11-memory-mapped-files.md).

## 5. `fork` и копирование при записи

В [Уроке 13.5](05-fork-exec-and-wait.md) вы узнали, что `fork` делает копию процесса. Копировать всю его
память было бы медленно. Вместо этого ядро использует **копирование при записи**:

```text
right after fork                   after the child writes to page B
parent table    child table        parent table    child table
  A -> frame 7    A -> frame 7       A -> frame 7    A -> frame 7
  B -> frame 8    B -> frame 8       B -> frame 8    B -> frame 21 (new copy)
  (both marked read-only)
```

1. Обе таблицы страниц указывают на одни и те же кадры, а все записываемые страницы помечены «только для
   чтения».
2. Когда один из процессов пишет, MMU вызывает страничный сбой. Ядро копирует только этот один кадр, отдаёт
   пишущему его личную копию с правом записи и продолжает его работу.

У потомка **те же виртуальные адреса**, что и у родителя, но после записи — другие данные. Создайте
`src/bin/cow.rs`:

```rust
use nix::sys::wait::waitpid;
use nix::unistd::{ForkResult, fork};

fn main() {
    let mut value: i32 = 1;

    // SAFETY: the program has only one thread, so the child is a full copy.
    match unsafe { fork() }.expect("fork failed") {
        ForkResult::Child => {
            value = 100;
            println!("child : value = {value:3} at {:p}", &value);
            std::process::exit(0);
        }
        ForkResult::Parent { child } => {
            waitpid(child, None).expect("waitpid failed");
            println!("parent: value = {value:3} at {:p}", &value);
        }
    }
}
```

**Что происходит:**

1. `fork` в `nix` помечен `unsafe`, потому что `fork` программы с несколькими потоками может оставить
   блокировки у потомка в сломанном состоянии (Урок 13.5). В нашей программе один поток.
2. Потомок записывает `100`. Эта запись вызывает сбой копирования при записи, и потомок получает
   собственную копию страницы с `value`.
3. Родитель ждёт потомка, затем печатает своё `value`.
4. `{:p}` печатает адрес `value`.

```text
child : value = 100 at 0xfffff99f2e64
parent: value =   1 at 0xfffff99f2e64
```

По одному и тому же адресу видны два разных значения. Это возможно только потому, что у двух процессов два
разных адресных пространства, и один и тот же виртуальный адрес переводится в два разных кадра.

## 6. Когда обращение к памяти идёт не так

Если ядро разбирает страничный сбой и видит, что адрес **не разрешён** (не входит ни в одно отображение или
это запись в страницу только для чтения), исправить его нельзя. Ядро посылает процессу сигнал **SIGSEGV**
(ошибка сегментации), и по умолчанию процесс умирает. Создайте `src/bin/crash.rs`:

```rust
fn main() {
    let address = 0x10 as *const u8;
    println!("reading address {address:p} ...");
    // SAFETY: none! Nothing is mapped at this address. This is a deliberate crash.
    let byte = unsafe { std::ptr::read_volatile(address) };
    println!("never printed: {byte}");
}
```

`read_volatile` читает ровно по этому адресу (компилятор не может убрать или изменить это чтение).
Запустите программу, затем напечатайте код завершения последней команды:

```bash
cargo run --bin crash
echo "exit=$?"
```

```text
reading address 0x10 ...
Segmentation fault
exit=139
```

Оболочка сообщает о сигнале (некоторые системы добавляют `(core dumped)`). Код завершения 139 — это
128 + 11, а 11 — номер SIGSEGV ([Урок 11.5](../11-linux-shell-and-containers/05-processes-and-signals.md)).
Первую страницу адресного пространства никогда не отображают намеренно, чтобы использование нулевого или
почти нулевого указателя громко роняло программу, а не читало мусор.

Безопасный Rust не может так упасть: каждая ссылка указывает на корректную память. Сюда можно попасть только
через `unsafe`-код или из-за ошибки в коде на C, вызванном через FFI ([Урок 06.10](../06-rust-advanced/10-ffi-calling-c.md)).

**Когда память кончается.** Благодаря подкачке по требованию Linux обычно позволяет программам запросить
больше памяти, чем есть на самом деле (это называется *overcommit*, избыточное выделение). Если программы
действительно всё это тронут, ядро сначала переносит редко используемые страницы в *swap* (область подкачки)
на диске. Когда не остаётся ничего, **OOM killer** выбирает процесс, чаще всего самый большой, и убивает его
сигналом SIGKILL. Вы ограничите память и безопасно посмотрите на это в [Уроке 13.16](16-cgroups.md).

## Частые ошибки

1. **Не тот столбец принимают за «использованную память».** `ps -o pid,vsz,rss,comm` показывает VSZ
   (виртуальный размер, все отображения) и RSS. Программа с VSZ 2 ГБ может занимать всего 5 МБ RAM.
   *Исправление:* смотрите на RSS (а для контейнеров — на числа cgroup из Урока 13.16).

2. **Размер страницы зашит в код.** `4096` работает на большинстве Linux-компьютеров, но macOS на Apple
   silicon использует страницы по 16 КиБ, а некоторые системы Linux на arm64 — по 16 или 64 КиБ.
   *Исправление:* спрашивайте через `sysconf(SysconfVar::PAGE_SIZE)`.

3. **Ожидание одного и того же адреса при каждом запуске.** Тесты или логи, сравнивающие сырые адреса,
   падают из-за ASLR. *Исправление:* сравнивайте смещения или значения, никогда — абсолютные адреса.

4. **Переполнение стека принимают за другую ошибку.** Под стеком лежит *сторожевая страница* (guard page):
   отображение без каких-либо прав. Очень глубокая рекурсия в неё упирается. Эта программа тратит 8 КиБ стека
   на вызов:

   ```rust
   fn depth(n: u64) -> u64 {
       let big = [n; 1024]; // 8 KiB on the stack in every call
       if n == 0 { 0 } else { big[0] + depth(n - 1) }
   }

   fn main() {
       println!("{}", depth(1_000_000));
   }
   ```

   ```text
   thread 'main' (551) has overflowed its stack
   fatal runtime error: stack overflow, aborting
   Aborted
   ```

   Rust замечает, что адрес сбоя попал в сторожевую страницу, и перед аварийным завершением печатает понятное
   сообщение (код завершения 134 = 128 + 6, SIGABRT). *Исправление:* используйте цикл или храните большие
   данные в куче (`vec!`, `Box`).

## Упражнения

Вспомогательные функции упражнений 1 и 2 положите в `src/lib.rs` пакета `code/p13-vmem` (создайте этот
файл). Бинарники в `src/bin/` могут вызывать их как `p13_vmem::<имя>`.

### Упражнение 1 — Страница и смещение (легко)

Напишите `pub fn page_and_offset(addr: usize, page_size: usize) -> (usize, usize)`. Функция должна
паниковать с сообщением, содержащим «power of two», если `page_size` не степень двойки. Напишите тесты:
`0x1234` при 4096 даёт `(1, 0x234)`; `4096` даёт `(1, 0)`; `0x1234` при 16 384 даёт `(0, 0x1234)`; размер
страницы 1000 вызывает панику.

<details>
<summary>Подсказка</summary>

У `usize` есть метод `is_power_of_two()`. Для степени двойки `addr % page_size` равно
`addr & (page_size - 1)` ([Урок 12.4](../12-computer-systems/04-bitwise-operations.md)). Для последнего
теста используйте `#[should_panic(expected = "power of two")]`.

</details>

<details>
<summary>Ответ</summary>

```rust
/// Splits an address into (page number, offset inside the page).
/// `page_size` must be a power of two.
pub fn page_and_offset(addr: usize, page_size: usize) -> (usize, usize) {
    assert!(
        page_size.is_power_of_two(),
        "page size must be a power of two"
    );
    (addr / page_size, addr & (page_size - 1))
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn splits_address_into_page_and_offset() {
        assert_eq!(page_and_offset(0x1234, 4096), (1, 0x234));
        assert_eq!(page_and_offset(4096, 4096), (1, 0));
        assert_eq!(page_and_offset(4095, 4096), (0, 4095));
        assert_eq!(page_and_offset(0x1234, 16384), (0, 0x1234));
    }

    #[test]
    #[should_panic(expected = "power of two")]
    fn rejects_bad_page_size() {
        page_and_offset(10, 1000);
    }
}
```

Почему это работает: степень двойки минус один — это маска из единиц (`0xfff` для 4096), поэтому `&`
оставляет ровно младшие биты, то есть смещение. Деление отбрасывает эти биты и оставляет номер страницы.

</details>

### Упражнение 2 — Разбор RSS с тестом (средне)

`rss_kib` в `lazy.rs` читает настоящий файл, поэтому её трудно тестировать. Напишите
`pub fn parse_rss_kib(status: &str) -> Option<u64>`, которая принимает *текст* файла status. Проверьте её
коротким образцом текста со строкой `VmRSS:\t    1684 kB` и текстом без строки `VmRSS` (у потоков ядра её
нет).

<details>
<summary>Подсказка</summary>

Используйте `lines().find(...)`, затем `split_whitespace().nth(1)`, затем `parse().ok()`. Оператор `?`
работает и с `Option`.

</details>

<details>
<summary>Ответ</summary>

```rust
/// Finds the `VmRSS:` line in the text of /proc/<pid>/status and returns the value in KiB.
pub fn parse_rss_kib(status: &str) -> Option<u64> {
    let line = status.lines().find(|l| l.starts_with("VmRSS:"))?;
    line.split_whitespace().nth(1)?.parse().ok()
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn finds_rss_line() {
        let text = "Name:\tlazy\nVmSize:\t  264000 kB\nVmRSS:\t    1684 kB\nThreads:\t1\n";
        assert_eq!(parse_rss_kib(text), Some(1684));
    }

    #[test]
    fn missing_rss_line_gives_none() {
        assert_eq!(parse_rss_kib("Name:\tkthreadd\n"), None);
    }
}
```

Почему это работает: если отделить «прочитать файл» от «понять текст», логика становится чистой функцией,
которую легко проверить на любом входе. Настоящая программа просто вызывает
`parse_rss_kib(&fs::read_to_string("/proc/self/status")?)`.

</details>

### Упражнение 3 — Измерьте копирование при записи (сложно)

Выделите 64 МиБ через `vec![1u8; SIZE]` (так записывается каждый байт, и все страницы оказываются в RAM).
Затем вызовите `fork`. В потомке запишите по одному байту в каждую страницу и напечатайте, сколько малых
сбоев это вызвало. В родителе после `waitpid` напечатайте `buffer[0]`. Предскажите числа до запуска.

<details>
<summary>Подсказка</summary>

Прочитайте `getrusage(UsageWho::RUSAGE_SELF)` в потомке до и после цикла. У каждого процесса свои
счётчики.

</details>

<details>
<summary>Ответ</summary>

```rust
use std::hint::black_box;

use nix::sys::resource::{UsageWho, getrusage};
use nix::sys::wait::waitpid;
use nix::unistd::{ForkResult, SysconfVar, fork, sysconf};

fn minor_faults() -> i64 {
    getrusage(UsageWho::RUSAGE_SELF)
        .unwrap()
        .minor_page_faults()
}

fn main() {
    const SIZE: usize = 64 * 1024 * 1024;
    let page = sysconf(SysconfVar::PAGE_SIZE).unwrap().unwrap() as usize;
    let mut buffer = vec![1u8; SIZE]; // vec![1; …] writes every byte: all pages are in RAM

    // SAFETY: single-threaded program.
    match unsafe { fork() }.expect("fork failed") {
        ForkResult::Child => {
            let before = minor_faults();
            for i in (0..SIZE).step_by(page) {
                buffer[i] = 2; // the first write to each shared page copies it
            }
            let after = minor_faults();
            black_box(&buffer);
            println!("pages in the buffer : {}", SIZE / page);
            println!("faults while writing: {}", after - before);
            std::process::exit(0);
        }
        ForkResult::Parent { child } => {
            waitpid(child, None).unwrap();
            println!("parent still sees   : {}", buffer[0]);
        }
    }
}
```

```text
pages in the buffer : 16384
faults while writing: 16385
parent still sees   : 1
```

Почему это работает: после `fork` все 16 384 страницы общие и доступны только для чтения. Первая запись в
каждую — это сбой копирования при записи (ещё один сбой даёт сама программа, например стек). Родитель
сохраняет свои исходные кадры, поэтому по-прежнему видит `1`.

</details>

## Вопросы для самопроверки

1. Что делает MMU?

<details>
<summary>Ответ</summary>

При каждом обращении к памяти он переводит виртуальный адрес, которым пользуется программа, в физический
адрес по таблице страниц текущего процесса (с помощью кэша TLB). Если подходящей записи нет, он вызывает
страничный сбой.

</details>

2. Программа вызывает `vec![0u8; 1 << 30]` (1 ГиБ) и засыпает. Почему RSS остаётся маленьким?

<details>
<summary>Ответ</summary>

Из-за подкачки по требованию: ядро только создало отображение. Кадры выдаются при первом обращении к каждой
странице, а программа их ещё не трогала. Нулевые страницы не нужно заранее заполнять.

</details>

3. Чем малый страничный сбой отличается от большого?

<details>
<summary>Ответ</summary>

Малый сбой исправляется без диска (новая нулевая страница, копия при записи, страница, которая уже есть в
RAM). При большом сбое данные сначала нужно прочитать с диска, поэтому он намного медленнее.

</details>

4. После `fork` родитель и потомок печатают адрес одной и той же переменной. Почему адреса равны, а значения
   могут различаться?

<details>
<summary>Ответ</summary>

Адресное пространство потомка — копия родительского, поэтому виртуальные адреса совпадают. Но у каждого
процесса своя таблица страниц; после записи копирование при записи даёт пишущему собственный кадр, и один и
тот же виртуальный адрес ведёт в разную физическую память.

</details>

5. Программа завершилась с кодом 139. Что случилось?

<details>
<summary>Ответ</summary>

Её убил сигнал 11 (139 = 128 + 11), SIGSEGV: она обратилась к неотображённому адресу или записала в
страницу, которую можно только читать.

</details>

## Итоги

- У каждого процесса своё виртуальное адресное пространство; MMU переводит виртуальные адреса в физические по таблице страниц процесса, а TLB кэширует эти переводы.
- Память управляется страницами (в Linux обычно по 4 КиБ); адрес — это номер страницы плюс смещение. Размер страницы узнавайте через `sysconf`.
- `/proc/self/maps` перечисляет отображения процесса: программа, куча, библиотеки, vdso, стек, у каждого свои права.
- Подкачка по требованию выдаёт кадр только при первом обращении; это обращение — (малый) страничный сбой. RSS показывает, что действительно лежит в RAM.
- `fork` делит все кадры через копирование при записи; страница копируется только тогда, когда в неё кто-то пишет.
- Сбой на неразрешённом адресе превращается в SIGSEGV; глубокая рекурсия упирается в сторожевую страницу стека. Когда RAM кончается, OOM killer завершает процесс.
