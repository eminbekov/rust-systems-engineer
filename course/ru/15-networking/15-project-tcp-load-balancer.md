## Новые слова

| Слово | Значение |
|---|---|
| **переключение при отказе** (failover) | Отправка клиента на другой бэкенд, когда выбранный не справился. |
| **активная / пассивная проверка работоспособности** (active / passive health check) | Проверка, которую балансировщик делает сам (тестовое подключение через каждый интервал) / вывод, сделанный из настоящего трафика (клиентское подключение к бэкенду не удалось). |
| **ограничение числа соединений** (connection limit) | Максимальное число клиентских соединений, которые программа обслуживает одновременно. Лишние клиенты получают отказ, а не перегружают всё. |
| **осушение** (draining) | Во время завершения: новые соединения больше не принимаются, а открытым дают закончиться. |
| **тайм-аут осушения** (drain timeout) | Самое долгое время, которое программа при завершении ждёт открытые соединения, прежде чем оборвать их. |
| **`CancellationToken`** | Тип из `tokio-util`: одна сторона вызывает `cancel()`, и просыпается каждая задача, ждущая `cancelled()`. Используется, чтобы сказать фоновым задачам остановиться. |
| **`TaskTracker`** | Тип из `tokio-util`, который считает запущенные задачи и позволяет ждать через `wait()`, пока все они не завершатся. |
| **SIGINT / SIGTERM** (signal interrupt / signal terminate, сигнал прерывания / сигнал завершения) | Сигналы Unix, которые посылают `Ctrl+C` и менеджеры сервисов вроде systemd, Docker и Kubernetes, когда хотят остановить программу (Урок 11.5). |
| **TCP** (Transmission Control Protocol, протокол управления передачей) | Надёжный поток байтов, который пересылает ваш балансировщик (Урок 15.3). |
| **HTTP, TLS, SNI** (HyperText Transfer Protocol, Transport Layer Security, Server Name Indication — протокол передачи гипертекста, протокол защиты транспортного уровня, указание имени сервера) | Протокол, на котором говорят тестовые бэкенды; слой шифрования из Урока 15.12; имя хоста, которое клиент TLS отправляет в своём первом, незашифрованном сообщении (используется в дополнительной цели). |

## 1. Устройство

В балансировщике три вида задач, которые разделяют два элемента состояния:

```text
                         ┌──────────────────────── Pool ─────────────────────────┐
                         │ backends: [(addr, healthy: AtomicBool)], next: AtomicUsize │
                         └───────▲───────────────────────▲──────────────────────────┘
                                 │ candidates()          │ set_healthy()
  clients ──► accept loop ───────┤                       │
              │  Semaphore       │                       │
              │  (max conns)     │                health-check task
              ▼                  │                (every interval: connect to each backend)
        connection task ─────────┘
        (try healthy backends in turn, copy_bidirectional, record failures)

  shutdown signal ──► accept loop stops ──► TaskTracker waits for connection tasks
                                            (at most the drain timeout)
```

- **Пул** (pool) знает бэкенды и здоров ли каждый из них. `AtomicBool` и `AtomicUsize` позволяют каждой задаче читать и обновлять его без блокировки.
- **Цикл приёма** берёт для каждого клиента разрешение у `Semaphore` (или отказывает клиенту, если разрешений не осталось) и запускает **задачу соединения**.
- Задача соединения просит у пула здоровые бэкенды, начиная со следующего по очереди, и пробует их один за другим, пока подключение не удастся. Это round robin плюс переключение при отказе.
- **Задача проверки работоспособности** с фиксированным интервалом подключается к каждому бэкенду и обновляет пул, поэтому вернувшийся бэкенд снова используется.
- По **SIGINT или SIGTERM** цикл приёма останавливается, слушающий сокет закрывается, и программа ждёт открытые соединения (не дольше тайм-аута осушения).

Логика решений лежит в библиотеке (`src/lib.rs`) с функцией `run`, которая принимает слушающий сокет и *future завершения* (shutdown future) как аргументы. Исполняемый файл только разбирает командную строку и передаёт `Ctrl+C` в роли этого future; тесты передают канал, которым управляют сами. Именно это делает возможными тесты в M6.

## Проект

### Что вы создадите

```text
$ lb --backend 127.0.0.1:9001 --backend 127.0.0.1:9002
lb listening on 127.0.0.1:8080, 2 backend(s)
127.0.0.1:61334 -> 127.0.0.1:9001: 77 bytes up, 99 bytes down
127.0.0.1:61340 -> 127.0.0.1:9002: 77 bytes up, 100 bytes down
127.0.0.1:61388: cannot reach 127.0.0.1:9002: Connection refused (os error 61)
backend 127.0.0.1:9002 is DOWN
127.0.0.1:61388 -> 127.0.0.1:9001: 77 bytes up, 99 bytes down
backend 127.0.0.1:9002 is UP
shutting down, waiting for 0 connection(s)

```

(Во время этого запуска один бэкенд останавливали и снова запускали; последние две строки появляются после `Ctrl+C`.)

### Контракт

**Командная строка** (через `clap`; исполняемый файл называется `lb`):

```text
lb [--listen <addr>] --backend <addr> [--backend <addr> …]
   [--max-conns <n>] [--health-interval-ms <ms>] [--connect-timeout-ms <ms>] [--drain-timeout-ms <ms>]
```

| Параметр | По умолчанию | Значение |
|---|---|---|
| `--listen` | `127.0.0.1:8080` | адрес, на котором принимать клиентов |
| `--backend` | обязателен, повторяется | по одному адресу бэкенда на параметр |
| `--max-conns` | `100` | число одновременно обслуживаемых клиентских соединений |
| `--health-interval-ms` | `1000` | время между двумя раундами проверок; первый раунд выполняется при запуске |
| `--connect-timeout-ms` | `1000` | предел для каждой попытки подключения к бэкенду |
| `--drain-timeout-ms` | `5000` | сколько при завершении ждать открытые соединения |

Добавьте в `Cargo.toml` `[[bin]] name = "lb"` с `path = "src/main.rs"`. При отсутствующих или неверных параметрах `clap` печатает строку использования и завершается с кодом 2.

**Поведение.**

1. Каждый принятый клиент получает **здоровые** бэкенды в порядке round robin (каждый новый клиент начинает на одну позицию дальше) и подключается к первому, который примет соединение в пределах тайм-аута подключения. Затем байты копируются в обе стороны, пока обе стороны не закроются.
2. Бэкенд, попытка подключения к которому не удалась или превысила тайм-аут (от клиента или при проверке работоспособности), помечается как **down**; успешная проверка помечает его как **up**. В лог пишутся только изменения: `backend <addr> is DOWN` / `backend <addr> is UP`.
3. Если ни один здоровый бэкенд не принял соединение, соединение клиента закрывается и в лог пишется `<peer>: no healthy backend, closing`.
4. Если уже обслуживается `--max-conns` клиентов, новый клиент сразу закрывается и в лог пишется `<peer>: connection limit (<n>) reached, closing`.
5. После завершённого соединения: `<peer> -> <backend>: <up> bytes up, <down> bytes down`. После неудачной попытки: `<peer>: cannot reach <backend>: <error>`.
6. По SIGINT (`Ctrl+C`) или SIGTERM: перестать принимать и закрыть слушающий сокет, записать в лог `shutting down, waiting for <n> connection(s)`, дождаться открытых соединений и записать `all connections closed, bye` либо, после тайм-аута осушения, `drain timeout: <n> connection(s) cut`. Затем выйти с кодом 0.

**API библиотеки** (`src/lib.rs`, крейт `p15_lb`), которым пользуются исполняемый файл и тесты:

```text
pub struct Config {
    pub backends: Vec<SocketAddr>,
    pub max_conns: usize,
    pub health_interval: Duration,
    pub connect_timeout: Duration,
    pub drain_timeout: Duration,
}

pub async fn run(listener: TcpListener, config: Config, shutdown: impl Future<Output = ()>);
```

`run` возвращается только после завершения работы. Остальное решаете вы (например, тип `Pool` со своими модульными тестами).

**Качество.** `cargo test` проходит (модульные тесты пула и интеграционные тесты из M6), `cargo clippy --all-targets` чист, `cargo fmt --check` чист, `README.md` объясняет использование, и на каждую веху приходится один коммит Git.

#### M1 — Аргументы и один бэкенд

**Цель:** `lb` разбирает параметры из контракта и пересылает каждого клиента на **первый** бэкенд.

**Как делать:**

1. Напишите структуру `Args` с `#[derive(Parser)]`. `SocketAddr` реализует `FromStr`, поэтому `clap` сам разберёт и проверит адреса. Повторяющийся параметр — это `Vec<SocketAddr>` с `#[arg(long = "backend", required = true)]`.
2. Преобразуйте `Args` в `Config` (миллисекунды — в `Duration::from_millis`).
3. В `lib.rs` напишите первую версию `run` с циклом приёма и `copy_bidirectional` из Урока 15.14. Пока не обращайте внимания на `shutdown` (из `main` можно передать `std::future::pending()`).

<details>
<summary>Подсказка</summary>

`#[arg(long, default_value_t = 100)] max_conns: usize` даёт `--max-conns` со значением по умолчанию. `#[command(name = "lb")]` заставляет строку использования говорить `lb`. Добавьте секцию исполняемого файла в `Cargo.toml` до того, как запускать `cargo run --bin lb`.

</details>

#### M2 — Round robin по всем бэкендам

**Цель:** клиенты по очереди распределяются по всем бэкендам.

**Как делать:**

1. Создайте в `lib.rs` тип `Pool` с бэкендами и счётчиком `AtomicUsize`, как `RoundRobin` в Уроке 15.14.
2. Дайте ему метод, который возвращает **все** бэкенды в порядке очереди, начиная со следующей позиции: для трёх бэкендов `[1, 2, 3]`, затем `[2, 3, 1]`, затем `[3, 1, 2]`. В M3 вы будете фильтровать этот список и пробовать его элементы один за другим.
3. Напишите модульный тест на вращение.
4. Разделите пул с задачами соединений через `Arc`.

<details>
<summary>Подсказка</summary>

`let start = self.next.fetch_add(1, Ordering::Relaxed);`, затем `(0..n).map(|i| backends[(start + i) % n])`.

</details>

**Готово, когда:**

#### M3 — Здоровье, переключение при отказе и тайм-ауты подключения

**Цель:** мёртвый бэкенд ничего не стоит клиентам: их сразу отправляют на другой, мёртвый пропускается, пока не вернётся, а от бэкенда, который вообще не отвечает, отказываются после тайм-аута подключения.

**Как делать:**

1. Добавьте каждому бэкенду `AtomicBool` «здоров» (в начале `true`). Метод вращения теперь возвращает только здоровые бэкенды. Метод `set_healthy(addr, bool)` использует `swap`, который возвращает старое значение, поэтому в лог можно писать только настоящие изменения.
2. Оборачивайте каждую попытку подключения в `tokio::time::timeout(config.connect_timeout, TcpStream::connect(addr))`. Тайм-аут считайте такой же неудачей, как любую другую.
3. В задаче соединения пробуйте кандидатов по порядку. При неудаче запишите это в лог, пометьте бэкенд как down и пробуйте следующий. Если не удались все, запишите `no healthy backend` и выйдите (удаление клиента закрывает его соединение).
4. Запустите в `run` задачу проверки работоспособности: `tokio::time::interval(config.health_interval)`, и на каждом такте пытайтесь подключиться к каждому бэкенду (здоровому или нет) и записывайте результат. Обратите внимание: первый `tick()` завершается сразу, поэтому первая проверка выполняется при запуске.
5. Расширьте модульные тесты: бэкенд в состоянии down пропускается; после `set_healthy(addr, true)` он снова используется.

<details>
<summary>Подсказка</summary>

Из `timeout(…, connect(…)).await` выходят два слоя `Result`: внешний говорит «время вышло», внутренний — это ошибка подключения. Маленький помощник `async fn connect(addr, limit) -> io::Result<TcpStream>`, который превращает тайм-аут в `io::Error::new(io::ErrorKind::TimedOut, "connect timed out")`, упрощает остальной код. Для проверки тайм-аута используйте `192.0.2.1:9`: адрес для документации, где никто никогда не отвечает.

</details>

#### M4 — Ограничение числа соединений

**Цель:** одновременно обслуживается не больше `--max-conns` клиентов; лишние клиенты сразу получают отказ.

**Как делать:**

1. Создайте в `run` `Arc<Semaphore>` с `max_conns` разрешениями.
2. В цикле приёма используйте `Arc::clone(&limit).try_acquire_owned()`: он никогда не ждёт. Если не получилось, запишите отказ в лог и удалите клиента.
3. Переместите разрешение (`OwnedSemaphorePermit`) в задачу соединения, чтобы оно возвращалось, когда задача заканчивается, как бы она ни закончилась.

<details>
<summary>Подсказка</summary>

Разрешение — guard-объект RAII (Resource Acquisition Is Initialization, «получение ресурса есть инициализация»), как аренда из Упражнения 3 Урока 15.14. Вызов `drop(permit)` в конце задачи делает намерение видимым, но разрешение вернулось бы и без него.

</details>

**Готово, когда:** запустите `lb -- --backend 127.0.0.1:9001 --max-conns 1`, займите единственное место через `nc 127.0.0.1 8080` в другом терминале (ничего не набирайте) и попробуйте `curl`; затем завершите `nc` через `Ctrl+C` и попробуйте снова:

```bash
curl -sS http://127.0.0.1:8080/
curl -sS http://127.0.0.1:8080/      # after nc has ended
git commit -am "M4: connection limit"
```

```text
curl: (56) Recv failure: Connection reset by peer
hello from blue, you are 127.0.0.1:62699
```

Лог `lb`:

```text
127.0.0.1:62687: connection limit (1) reached, closing
127.0.0.1:62684 -> 127.0.0.1:9001: 0 bytes up, 99 bytes down
127.0.0.1:62698 -> 127.0.0.1:9001: 77 bytes up, 99 bytes down
```

(`nc` ничего не отправлял, поэтому вверх ушло 0 байт; приветствие бэкенда ушло вниз.)

#### M5 — Корректное завершение

**Цель:** `Ctrl+C` и SIGTERM останавливают балансировщик, не обрывая ещё открытые соединения, но и не ожидая дольше тайм-аута осушения.

**Как делать:**

1. В `main` соберите future завершения из `tokio::signal::ctrl_c()` и `tokio::signal::unix::signal(SignalKind::terminate())`, объединённых через `tokio::select!`, и передайте его в `run`.
2. В `run` закрепите future (`tokio::pin!(shutdown)`) и в цикле делайте `select!` между ним и `listener.accept()`. Когда он завершится, выйдите из цикла и сделайте `drop(listener)`: с этого момента попытки подключения отвергает операционная система.
3. Запускайте задачи соединений через `TaskTracker` (`tracker.spawn(…)`). После цикла: `tracker.close()`, запись `tracker.len()` в лог, затем `timeout(config.drain_timeout, tracker.wait())`.
4. Останавливайте задачу проверки работоспособности через `CancellationToken`: `select!` по `token.cancelled()` и такту интервала, а при завершении вызывайте `token.cancel()`.

<details>
<summary>Подсказка</summary>

`TaskTracker::wait()` завершается, только когда был вызван `close()` **и** все задачи закончились; `close()` не останавливает задачи, он лишь говорит «больше задач не будет». Задачи, ещё работающие, когда истекает тайм-аут осушения, останавливаются, когда `run` возвращается и рантайм Tokio завершает работу.

</details>

**Готово, когда:** запустите `lb -- --backend 127.0.0.1:9001`, откройте соединение, которое длится несколько секунд (`sleep 3 | nc 127.0.0.1 8080` в другом терминале), и нажмите `Ctrl+C` в терминале `lb`, пока оно открыто. `curl` во время завершения получает отказ:

```bash
curl -sS http://127.0.0.1:8080/
```

```text
curl: (7) Failed to connect to 127.0.0.1 port 8080 after 0 ms: Couldn't connect to server
```

Лог `lb`, который заканчивается сам, когда `nc` завершается:

```text
lb listening on 127.0.0.1:8080, 1 backend(s)
shutting down, waiting for 1 connection(s)
127.0.0.1:62600 -> 127.0.0.1:9001: 0 bytes up, 99 bytes down
all connections closed, bye
```

С `--drain-timeout-ms 1000` и соединением, которое длится пять секунд (`sleep 5 | nc …`), остановленным через `pkill -TERM -f target/debug/lb` (SIGTERM, как отправил бы `docker stop`):

```text
lb listening on 127.0.0.1:8080, 1 backend(s)
shutting down, waiting for 1 connection(s)
drain timeout: 1 connection(s) cut
```

```bash
git commit -am "M5: graceful shutdown"
```

#### M6 — Сквозные тесты, README, контроль качества

**Цель:** тесты, которые запускают настоящие бэкенды и настоящий балансировщик внутри тестового процесса, на случайных портах, и проверяют весь контракт.

**Как делать:**

1. В `tests/lb.rs` напишите три помощника: **тестовый бэкенд** на `127.0.0.1:0`, который пишет однобуквенное имя и затем ждёт, пока клиент закроет соединение (так тест может держать соединение открытым); **мёртвый бэкенд** (привяжите слушающий сокет к порту 0, запомните его адрес, удалите его); и **`start_lb(backends, max_conns)`**, который привязывается к `127.0.0.1:0`, создаёт канал `tokio::sync::oneshot` и запускает `run(listener, config, async { let _ = rx.await; })`. Верните адрес, отправителя («кнопку остановки») и `JoinHandle`. Используйте короткие интервалы (проверки каждые 100 мс, тайм-аут подключения 200 мс), чтобы тесты оставались быстрыми.
2. Напишите четыре теста: соединения идут по очереди (`a, b, a, b`); мёртвый бэкенд пропускается; при `max_conns = 1` и одном удерживаемом соединении лишний клиент читает 0 байт; после сигнала остановки новые соединения не проходят, `run` не завершён, пока соединение удерживается, и завершается вскоре после того, как это соединение удалено.
3. Напишите `README.md` (что это, использование, таблица параметров, как тестировать) и пройдите контроль качества.

<details>
<summary>Подсказка</summary>

Помощник теста, который читает имя бэкенда через балансировщик:

```rust
async fn ask(lb: SocketAddr) -> (TcpStream, String) {
    let mut s = TcpStream::connect(lb).await.unwrap();
    let mut name = [0u8; 1];
    s.read_exact(&mut name).await.unwrap();
    (s, String::from_utf8_lossy(&name).into_owned())
}
```

Он возвращает и поток: сохраните его в переменной, чтобы держать соединение открытым, или проигнорируйте (`ask(lb).await.1`), чтобы сразу закрыть. `JoinHandle::is_finished()` говорит, вернулась ли `run`.

</details>

**Готово, когда:**

```bash
cargo fmt --check && cargo clippy --all-targets && cargo test
git add . && git commit -m "M6: end-to-end tests and README"
```

```text

...

test the_connection_limit_refuses_extra_clients ... ok
```

(Первый результат — два модульных теста пула; порядок четырёх интеграционных тестов меняется от запуска к запуску. Запустите `cargo test` несколько раз: тесты должны проходить каждый раз, а не только иногда.)

### Дополнительные цели

1. **Пороги подъёма и падения.** Помечайте бэкенд как down только после 2 неудачных проверок подряд, а как up — только после 2 успешных, чтобы один потерянный пакет не переключал его туда-сюда. Пишите счётчики в лог.
2. **Least connections.** Замените round robin арендой `LeastConnections` из Упражнения 3 Урока 15.14 с выбором только среди здоровых бэкендов.
3. **Тайм-аут простоя.** Закрывайте соединения, по которым за `--idle-timeout-ms` не прошло ни одного байта. `copy_bidirectional` так не умеет; копируйте два направления сами двумя вызовами `tokio::io::copy` на разделённых половинах с общим временем «последней активности».
4. **Метрики.** Считайте принятые, отклонённые и неудачные соединения и байты на каждый бэкенд в атомарных переменных и печатайте их каждые 10 секунд (или отдавайте по HTTP через `hyper` из Урока 15.9; настоящие метрики показывает Урок 16.12).
5. **Сквозная передача TLS по SNI.** Подсмотрите первые байты TLS ClientHello (`TcpStream::peek`), прочитайте имя SNI и выбирайте группу бэкендов по имени, ничего не расшифровывая.
6. **Запустите его в контейнере** с Dockerfile, как в [Уроке 11.13](../11-linux-shell-and-containers/13-dockerfiles-for-rust.md), и проверьте через `docker stop`, что SIGTERM осушает соединения.

## Частые ошибки

**1. Держать блокировку через `.await`.** Если бы пул жил в `Mutex<Vec<…>>`, а задача держала guard, пока подключается к бэкенду, каждая другая задача ждала бы этой попытки подключения — вплоть до тайм-аута. Храните состояние в атомарных переменных (или копируйте нужное из-под блокировки) и никогда не делайте `.await`, держа guard от `std::sync::Mutex`.

**2. Забыть вернуть разрешение при ошибках.** Если разрешение возвращается вручную в конце «счастливого пути», каждое соединение, закончившееся ошибкой, теряет одно разрешение, и после `max_conns` ошибок балансировщик отказывает всем. Перемещайте владеющее разрешение в задачу: его удаление происходит автоматически на любом пути.

**3. Завершение, которое никогда не кончается.** Ожидание `tracker.wait()` без тайм-аута зависает навсегда, если один клиент держит соединение открытым. Ожидание с тайм-аутом, но без закрытия слушающего сокета, пускает новых клиентов во время осушения. Делайте и то и другое, в таком порядке: перестать принимать, затем ждать со сроком.

**4. Нестабильные сквозные тесты.** Фиксированные порты (`8080`) сталкиваются с работающими программами; вызовы `sleep` гадают, сколько что-то займёт. Привязывайте каждый тестовый сервер к порту `0`, читайте настоящий адрес и ждите *событий* (ответа, закрытого соединения, завершённой задачи) с `timeout` в роли страховки, а не спите.

> 🔒 **Безопасность:** балансировщик смотрит в интернет, поэтому и обращайтесь с ним соответственно: запускайте его от обычного пользователя (привязка к порту ниже 1024 за контейнером или файрволом не нужна), держите `--max-conns` конечным, а тайм-аут подключения коротким, чтобы медленные или вредоносные клиенты и мёртвые бэкенды не могли исчерпать его ресурсы.

## Вопросы для самопроверки

1. Почему неудачная попытка подключения от клиента сразу помечает бэкенд как down, а не ждёт следующей проверки?

<details>
<summary>Ответ</summary>

Это пассивная проверка работоспособности: настоящий трафик только что доказал, что бэкенд не принимает соединения. Если сразу пометить его как down, следующие клиенты сразу его пропустят, а не будут каждый платить за неудачную попытку до следующей активной проверки.

</details>

2. Почему задача соединения пробует **все** здоровые бэкенды по порядку и почему такой повтор здесь всегда безопасен?

<details>
<summary>Ответ</summary>

Чтобы бэкенд, умерший после последней проверки, ничего не стоил клиенту: его место занимает следующий бэкенд в списке (переключение при отказе). Это безопасно, потому что неудачный `connect` означает, что ни один байт данных клиента не дошёл ни до одного бэкенда; ещё не произошло ничего, что могло бы повториться.

</details>

3. Чем `try_acquire_owned()` отличается от `acquire_owned().await` у семафора и какое поведение требует контракт?

<details>
<summary>Ответ</summary>

`try_acquire_owned()` возвращается сразу, с ошибкой, если свободного разрешения нет; `acquire_owned().await` ждёт, пока разрешение освободится. Контракт требует немедленного отказа, значит, `try_acquire_owned()`. (Ожидание тоже было бы допустимым решением: тогда лишние клиенты вставали бы в очередь, а не получали отказ.)

</details>

4. В каком порядке выполняется корректное завершение и что пошло бы не так, если поменять шаги местами?

<details>
<summary>Ответ</summary>

Сначала перестать принимать и закрыть слушающий сокет, затем ждать открытые соединения со сроком. Если сначала ждать, новые клиенты продолжали бы приходить, и ожидание могло бы никогда не закончиться; без срока один клиент, который никогда не уходит, мог бы держать программу живой вечно.

</details>

5. Почему `run` принимает слушающий сокет и future завершения как параметры, а не привязывает порт и не слушает `Ctrl+C` сама?

<details>
<summary>Ответ</summary>

Чтобы тесты могли дать ей слушающий сокет на порту 0 и сигнал завершения, которым управляют сами (канал oneshot), а исполняемый файл передавал настоящий порт и сигналы Unix. Это внедрение зависимостей: функция не решает, откуда берутся её входные данные, и поэтому её можно тестировать.

</details>

## Итоги

- Полезный балансировщик L4 — это небольшой набор взаимодействующих задач: цикл приёма, по задаче на соединение и проверка работоспособности, разделяющие пул атомарных переменных.
- Round robin по здоровым бэкендам плюс «попробуй следующий, если connect не удался» дают переключение при отказе, которого клиенты не замечают.
- Каждой попытке подключения нужен тайм-аут; бэкенд, который не отвечает, так же плох, как бэкенд, который отказывает.
- Владеющее разрешение семафора на каждое соединение обеспечивает ограничение числа соединений на любом пути выполнения.
- Корректное завершение: сигнал → перестать принимать → `TaskTracker` ждёт открытые соединения → сдаться по тайм-ауту осушения.
- `run(listener, config, shutdown)` делает всю программу тестируемой от начала до конца с бэкендами внутри процесса на порту 0.
