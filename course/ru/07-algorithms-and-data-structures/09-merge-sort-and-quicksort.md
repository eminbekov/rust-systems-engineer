## Новые слова

| Слово | Значение |
|---|---|
| **разделяй и властвуй** (divide and conquer) | Способ решения задачи: разбить её на меньшие части того же вида, решить каждую часть и объединить ответы. |
| **логарифм** (logarithm, log₂ n) | Сколько раз можно разделить `n` пополам, пока не получится 1. log₂ 8 = 3, log₂ 1 000 000 ≈ 20. Растёт очень медленно. |
| **O(n log n)** | Время «n log n»: около `n` шагов на каждый из примерно log₂ n уровней. Для больших `n` намного быстрее O(n²). |
| **слияние** (merge) | Объединение двух отсортированных списков в один отсортированный: повторно берётся меньший из передних элементов. |
| **временный буфер** (scratch buffer) | Временный блок памяти, который алгоритм использует для работы, а затем забывает. |
| **опорный элемент** (pivot) | Элемент, который быстрая сортировка использует как разделительную линию: меньшие элементы идут слева от него, большие — справа. |
| **разбиение** (partition) | Перестановка среза вокруг опорного элемента так, чтобы он разделился на группы (меньшие, равные, большие). |
| **медиана** (median) | Среднее значение группы после её сортировки. Медиана чисел 5, 9 и 4 равна 5. |
| **медиана трёх** (median-of-three) | Способ выбрать опорный элемент: взять медиану первого, среднего и последнего элементов. |
| **глубина рекурсии** (recursion depth) | Сколько вызовов одновременно ждёт в стеке вызовов (Урок 07.7). |
| **быстрый выбор** (quickselect) | Алгоритм, который находит k-й по величине элемент по одному шагу разбиения, не сортируя всё. |

## 1. Разделяй и властвуй и откуда берётся n log n

Простые сортировки из Урока 07.8 медленны, потому что сравнивают почти каждую пару элементов: около `n²/2`
сравнений. Лучшая идея — **разделяй и властвуй**: разрезать срез на две половины, отсортировать каждую половину
(тем же алгоритмом: это рекурсия) и дёшево объединить две отсортированные половины.

Посмотрите, как срез разрезается пополам. Каждая строка — *уровень*:

```text
level 0:            [5 2 8 1 9 3 7 4]           1 slice  of 8
level 1:        [5 2 8 1]     [9 3 7 4]         2 slices of 4
level 2:      [5 2] [8 1]   [9 3] [7 4]         4 slices of 2
level 3:     [5][2] [8][1] [9][3] [7][4]        8 slices of 1   (nothing left to sort)
```

Деление 8 элементов пополам занимает 3 шага, потому что 2³ = 8. Говорят: log₂ 8 = 3. Для миллиона элементов хватает 20 делений
(2²⁰ ≈ миллион). Если работа по объединению частей на одном уровне — около `n` шагов в сумме, то
весь алгоритм требует около `n × log₂ n` шагов: **O(n log n)**. Для n = 1 000 000 это около 20
миллионов шагов, а для сортировки O(n²) — 500 миллиардов.

## 2. Сортировка слиянием

Сортировка слиянием выполняет настоящую работу, когда *поднимается обратно* по уровням. Ключевая операция — **слияние** двух
отсортированных списков: смотрим на передний элемент каждого списка, берём меньший и повторяем. Каждый элемент просматривается
один раз, поэтому слияние `n` элементов стоит O(n).

Слияние `[1, 4, 6]` и `[2, 3, 9]`:

```text
left = [1 4 6]   right = [2 3 9]    out = []
1 vs 2  take 1                      out = [1]
4 vs 2  take 2                      out = [1 2]
4 vs 3  take 3                      out = [1 2 3]
4 vs 9  take 4                      out = [1 2 3 4]
6 vs 9  take 6                      out = [1 2 3 4 6]
left is empty: copy the rest        out = [1 2 3 4 6 9]
```

Подъём обратно для наших 8 элементов:

```text
level 3:     [5][2] [8][1] [9][3] [7][4]
merge:       [2 5]  [1 8]  [3 9]  [4 7]
merge:         [1 2 5 8]     [3 4 7 9]
merge:             [1 2 3 4 5 7 8 9]
```

Добавьте эту строку в начало `src/sorting.rs`, под комментарием `//!` (она понадобится и для быстрой сортировки):

```rust
use std::cmp::Ordering;
```

и этот код ниже `insertion_sort` (выше модуля `tests`):

```rust
/// Merge sort: split in two halves, sort each half, merge the sorted halves.
pub fn merge_sort<T: Ord + Clone>(v: &mut [T]) {
    let mut buf = v.to_vec(); // one scratch buffer, allocated once
    merge_sort_rec(v, &mut buf);
}

fn merge_sort_rec<T: Ord + Clone>(v: &mut [T], buf: &mut [T]) {
    let n = v.len();
    if n <= 1 {
        return;
    }
    let mid = n / 2;
    merge_sort_rec(&mut v[..mid], &mut buf[..mid]);
    merge_sort_rec(&mut v[mid..], &mut buf[mid..]);

    // Merge the sorted halves v[..mid] and v[mid..] into buf, then copy back.
    let (mut i, mut j, mut k) = (0, mid, 0);
    while i < mid && j < n {
        if v[j] < v[i] {
            buf[k] = v[j].clone();
            j += 1;
        } else {
            buf[k] = v[i].clone(); // on a tie take the left one: this keeps the sort stable
            i += 1;
        }
        k += 1;
    }
    while i < mid {
        buf[k] = v[i].clone();
        i += 1;
        k += 1;
    }
    while j < n {
        buf[k] = v[j].clone();
        j += 1;
        k += 1;
    }
    v.clone_from_slice(&buf[..n]);
}
```

**Что происходит:**

1. `merge_sort` — публичная функция. Она создаёт **один** временный буфер той же длины (`to_vec`
   копирует срез) и передаёт оба рекурсивной вспомогательной функции. Одно выделение памяти гораздо дешевле, чем выделение при каждом вызове.
2. *Базовый случай* (Урок 07.7) — `n <= 1`: пустой срез или срез из одного элемента уже отсортирован.
3. Иначе срез разрезается в точке `mid`. Два рекурсивных вызова получают `&mut v[..mid]` и `&mut v[mid..]`
   (и те же части `buf`). Они выполняются один за другим, поэтому два изменяемых заимствования никогда не пересекаются.
4. Слияние: `i` идёт по левой половине `v[..mid]`, `j` — по правой `v[mid..]`, `k` — следующее свободное место в `buf`. Цикл
   берёт меньший передний элемент. Правый элемент берётся первым, только если он **строго** меньше (`v[j] < v[i]`);
   при равенстве побеждает левый. Именно это делает сортировку слиянием **устойчивой**.
5. Когда одна половина закончилась, два небольших цикла `while` копируют остаток другой половины.
6. `clone_from_slice` копирует результат слияния из `buf` обратно в `v`. Ограничение `Clone` нужно,
   потому что мы копируем элементы, а не вынимаем их из среза (в срезе не может быть «дыр»).

**Стоимость.** Уровней около log₂ n, и на каждом уровне слияния вместе затрагивают `n` элементов:
**O(n log n) в лучшем, среднем и худшем случае**. Дополнительная память: буфер, **O(n)**. Сортировка **устойчива**.
Она не работает на месте. Глубина рекурсии — всего около log₂ n, поэтому стек вызовов остаётся небольшим.

## 3. Быстрая сортировка

Быстрая сортировка выполняет настоящую работу, когда *спускается вниз* по уровням. Идея:

1. Выбрать один элемент, **опорный** (pivot).
2. **Разбить** срез: переместить все меньшие элементы налево от опорного, а все большие — направо.
   Теперь опорный элемент стоит на своём окончательном месте.
3. Отсортировать левую и правую части тем же способом.

Потом ничего сливать не нужно: когда части отсортированы, отсортирован и весь срез.

Есть две ловушки, и наш код обходит обе:

- **Равные элементы.** Если много элементов равны опорному, обычное двустороннее разбиение складывает их все на одну сторону,
  и части получаются очень неравными. Мы используем **трёхстороннее разбиение** с тремя группами: меньшие, равные, большие. Группа равных
  завершается сразу.
- **Плохой опорный элемент.** Если опорный элемент всегда самый маленький или самый большой (например, первый элемент уже отсортированного среза),
  части имеют размеры 0 и `n − 1`, и быстрой сортировке нужно `n` уровней: **O(n²)**. Мы выбираем опорный элемент по
  **медиане трёх**: медиана первого, среднего и последнего элементов. Отсортированные, обратные и состоящие из равных элементов входы тогда не проблема.

Разбиение `[4, 7, 2, 4, 9, 1]` с опорным элементом `4`. Три маркера делят срез: `[..lt]` меньше
опорного, `[lt..i]` равно ему, `[gt..]` больше, а `[i..gt]` ещё не просмотрено:

```text
start (pivot 4 at the front):  4 7 2 4 9 1      lt=0 i=1 gt=6
7 > 4  send it right           4 1 2 4 9 | 7    gt=5
1 < 4  send it left            1 4 2 4 9 | 7    lt=1 i=2
2 < 4  send it left            1 2 4 4 9 | 7    lt=2 i=3
4 = 4  leave it                1 2 4 4 9 | 7    i=4
9 > 4  send it right           1 2 4 4 | 9 7    gt=4, i == gt: stop
result:                        [1 2] [4 4] [9 7]   sort the two outer parts
```

Добавьте этот код ниже `merge_sort_rec`:

```rust
/// Slices shorter than this are finished with insertion sort.
const SMALL: usize = 16;

/// Quicksort: pick a pivot, move smaller items left and bigger items right, repeat on both sides.
pub fn quicksort<T: Ord>(mut v: &mut [T]) {
    while v.len() > SMALL {
        let pivot = median_of_three(v);
        let (lt, gt) = partition3(v, pivot);
        let (left, rest) = v.split_at_mut(lt);
        let right = &mut rest[gt - lt..];
        // Recurse into the smaller part, loop on the bigger one: the depth stays O(log n).
        if left.len() < right.len() {
            quicksort(left);
            v = right;
        } else {
            quicksort(right);
            v = left;
        }
    }
    insertion_sort(v);
}

/// Returns the index of the median of the first, middle and last item.
fn median_of_three<T: Ord>(v: &[T]) -> usize {
    let (a, b, c) = (0, v.len() / 2, v.len() - 1);
    if v[a] < v[b] {
        if v[b] < v[c] {
            b
        } else if v[a] < v[c] {
            c
        } else {
            a
        }
    } else if v[a] < v[c] {
        a
    } else if v[b] < v[c] {
        c
    } else {
        b
    }
}

/// Rearranges `v` around the pivot `v[pivot]`. Returns `(lt, gt)` such that
/// `v[..lt]` is smaller than the pivot, `v[lt..gt]` equals it, `v[gt..]` is bigger.
fn partition3<T: Ord>(v: &mut [T], pivot: usize) -> (usize, usize) {
    v.swap(0, pivot); // keep the pivot at the front while we work
    let (mut lt, mut i, mut gt) = (0, 1, v.len());
    while i < gt {
        match v[i].cmp(&v[lt]) {
            Ordering::Less => {
                v.swap(lt, i);
                lt += 1;
                i += 1;
            }
            Ordering::Greater => {
                gt -= 1;
                v.swap(i, gt);
            }
            Ordering::Equal => i += 1,
        }
    }
    (lt, gt)
}
```

**Что происходит:**

1. `partition3` сначала переставляет опорный элемент в начало. Затем она поддерживает такой **инвариант**: `v[..lt]` меньше
   опорного, `v[lt..i]` равно ему (поэтому `v[lt]` всегда копия значения опорного), `v[i..gt]` неизвестно, `v[gt..]` больше.
2. Для следующего неизвестного элемента `v[i]` решение принимает `match` по `cmp` (он возвращает `Ordering`: `Less`, `Equal` или `Greater`):
   *меньше*: обменять его на место `lt` и сдвинуть оба маркера вправо; *больше*: обменять его с концом неизвестной части (`gt` сдвигается
   влево, `i` остаётся, потому что пришедший на место `i` элемент ещё не просмотрен); *равно*: просто сдвинуть `i`.
3. Когда `i` встречает `gt`, неизвестных элементов не остаётся, и функция возвращает две границы. Каждый элемент просматривается один раз: **O(n)**.
4. `median_of_three` сравнивает три элемента и возвращает *индекс* среднего. Она никогда не паникует при
   `len >= 1`, потому что для среза из одного элемента все три индекса равны 0.
5. В `quicksort` метод `split_at_mut(lt)` разрезает срез на две **непересекающиеся** изменяемые части. `rest[gt - lt..]` пропускает
   группу равных. Теперь `left` и `right` — две части, которые нужно отсортировать.
6. `if` сортирует **меньшую** часть рекурсией, а затем снова идёт циклом по **большей**. Каждый рекурсивный вызов работает не более чем с половиной элементов, поэтому глубина рекурсии не больше
   примерно log₂ n даже на плохих входах. (Если бы обе части обрабатывались рекурсией, плохой опорный элемент мог бы сделать стек вызовов
   глубиной в `n` вызовов, и программа упала бы с переполнением стека, Урок 07.7.)
7. Срез не длиннее 16 элементов завершается через `insertion_sort` из Урока 07.8. На коротких срезах она быстрее,
   чем дальнейшее разбиение. Число 16 — типичный выбор; настоящие библиотеки подбирают его измерениями.

**Стоимость.** В среднем **O(n log n)**: каждый уровень разбивает `n` элементов, а хорошие опорные элементы дают около log₂ n уровней. С
медианой трёх худший случай на естественных данных встречается редко, но всё же существует (какой-нибудь особый вход всегда может сломать любое простое правило выбора опорного элемента): **O(n²)**
в худшем случае. Дополнительная память: только стек вызовов, **O(log n)**. **Неустойчива**: разбиение обменивает элементы на больших расстояниях.

| Алгоритм | Лучший | Средний | Худший | Доп. память | Устойчива |
|---|---|---|---|---|---|
| сортировка слиянием | O(n log n) | O(n log n) | O(n log n) | O(n) | да |
| быстрая сортировка (наша версия) | O(n) (все элементы равны) | O(n log n) | O(n²) | O(log n) | нет |

```rust
    fn check_long(sort: fn(&mut [i32])) {
        // The lengths around 16 test the switch to insertion sort.
        for len in [0, 1, 2, 15, 16, 17, 18, 31, 32, 33, 100, 1000, 5000] {
            for seed in 1..=3 {

                    let mut actual = random_vec(seed, len, max);
                    let mut expected = actual.clone();
                    expected.sort();
                    sort(&mut actual);
                    assert_eq!(actual, expected, "len {len}, seed {seed}, max {max}");
                }
            }
        }
    }

    #[test]
    fn merge_sort_and_quicksort_match_std() {
        check(merge_sort::<i32>);
        check(quicksort::<i32>);
        check_long(merge_sort::<i32>);
        check_long(quicksort::<i32>);
    }

    #[test]
    fn quicksort_handles_sorted_reversed_and_equal_input() {
        let n = 100_000;
        let sorted: Vec<i32> = (0..n).collect();
        let reversed: Vec<i32> = (0..n).rev().collect();
        let equal = vec![7; n as usize];

            let mut actual = input.clone();
            quicksort(&mut actual);
            let mut expected = input;
            expected.sort();
            assert_eq!(actual, expected);
        }
    }

    #[test]
    fn merge_sort_is_stable() {
        assert_eq!(sorted_tags(merge_sort), "cab");
    }
```

   `quicksort` переключается на `insertion_sort`. **На границах живут ошибки на единицу.**

> 🧪 **Тестирование:** прошедший тест не доказывает, что алгоритм верен; он доказывает, что алгоритм верен *для тех
> входов, которые вы попробовали*. Поэтому тесты используют много длин, много диапазонов значений и граничные длины. Этап 09 показывает
> инструменты, которые сами генерируют входы.

## 5. Насколько они быстры на самом деле

Создайте `benches/fast_sorts.rs` и зарегистрируйте его в `Cargo.toml`, как в Уроке 05.12:

```toml
[[bench]]
name = "fast_sorts"
harness = false
```

```rust
use criterion::{BatchSize, BenchmarkId, Criterion, criterion_group, criterion_main};
use p07_algorithms::sorting::{insertion_sort, merge_sort, quicksort};

type SortFn = fn(&mut [i32]);

fn pseudo_random(len: usize) -> Vec<i32> {
    let mut x: u64 = 12345;
    (0..len)
        .map(|_| {
            x ^= x << 13;
            x ^= x >> 7;
            x ^= x << 17;
            (x % 1_000_000) as i32
        })
        .collect()
}

fn bench_fast_sorts(c: &mut Criterion) {
    let n = 10_000;
    let random = pseudo_random(n);
    let sorted: Vec<i32> = (0..n as i32).collect();
    let inputs = [("random", random), ("sorted", sorted)];
    let sorts: [(&str, SortFn); 5] = [
        ("insertion", insertion_sort::<i32>),
        ("merge", merge_sort::<i32>),
        ("quick", quicksort::<i32>),
        ("std sort", <[i32]>::sort),
        ("std sort_unstable", <[i32]>::sort_unstable),
    ];

    let mut group = c.benchmark_group("sort 10_000");
    for (input_name, data) in &inputs {
        for (name, sort) in sorts {
            group.bench_with_input(BenchmarkId::new(name, input_name), data, |b, data| {
                b.iter_batched(
                    || data.clone(),
                    |mut v| {
                        sort(&mut v);
                        v
                    },
                    BatchSize::SmallInput,
                )
            });
        }
    }
    group.finish();
}

criterion_group!(benches, bench_fast_sorts);
criterion_main!(benches);
```

**Что происходит:** тот же шаблон, что и в бенчмарке Урока 05.12. `iter_batched` клонирует вход на подготовительном шаге, который не измеряется,
потому что сортировка портит свой вход. Каждый алгоритм получает одни и те же 10 000 чисел дважды: один раз случайные и один раз
уже отсортированные. `pseudo_random` использует маленькую формулу xorshift (сдвиги и исключающее ИЛИ, как в `Rng`):
бенчмарк не может взять `Rng` из `src/testutil.rs`, потому что этот модуль компилируется только для `cargo test`
(`#[cfg(test)]`). Запустите (около двух минут):

```bash
cargo bench --bench fast_sorts -- --warm-up-time 1 --measurement-time 3
```

Лучшие оценки из одного запуска на Mac с Apple M4 Pro, релизная сборка, 2026-11-18 (ваши числа будут другими):

| Алгоритм | случайный вход | отсортированный вход |
|---|---|---|
| сортировка вставками | 7,41 мс | 2,64 мкс |
| сортировка слиянием (наша) | 354 мкс | 96,3 мкс |
| быстрая сортировка (наша) | 274 мкс | 511 мкс |
| `sort` (std) | 54,9 мкс | 2,66 мкс |
| `sort_unstable` (std) | 56,8 мкс | 2,55 мкс |

**Как это читать:**

1. На случайных данных сортировка слиянием и быстрая сортировка примерно **в 20–27 раз быстрее** сортировки вставками уже для 10 000 элементов (7,41 мс против 0,35 и 0,27 мс).
   Разрыв растёт с `n`, потому что O(n log n) побеждает O(n²).
2. Быстрая сортировка чуть быстрее сортировки слиянием на случайных данных: она не копирует элементы в буфер.
3. На **отсортированном** входе сортировка вставками — чемпион среди наших четырёх (2,6 мкс, один проход: лучший случай O(n) из Урока 07.8). Наши сортировка слиянием и быстрая сортировка
   не замечают, что данные отсортированы, и проходят все свои уровни. Наша быстрая сортировка на отсортированном входе даже медленнее, чем на случайном
   (511 мкс); обмены на шаге разбиения перемещают много элементов.
4. Сортировки стандартной библиотеки примерно **в 5–6 раз быстрее** наших на случайных данных и обрабатывают отсортированный вход так же быстро, как сортировка вставками
   (2,6 мкс): они обнаруживают в данных уже упорядоченный участок и останавливаются. У них гораздо больше приёмов (например, особая обработка крошечных
   срезов), отточенных годами. Наши версии учат идеям; они не конкурируют.

> ⚡ **Производительность:** алгоритм с лучшей скоростью роста (n log n) выигрывает в разы уже на 10 000 элементах.
> Только после этого начинают иметь значение детали: аккуратная реализация стандартной библиотеки ещё в 5 раз быстрее учебной
> версии. Поэтому «используйте стандартную библиотеку» — верное правило по умолчанию.

## 6. Что использовать в настоящем коде

- `sort()` **устойчива**. В документации стандартной библиотеки сказано, что текущая реализация основана на *driftsort*, который
  сочетает быстрый средний случай быстрой сортировки с быстрым худшим случаем сортировки слиянием и требует лишь линейного времени на отсортированном и обратном входах.
- `sort_unstable()` работает на месте и неустойчива. В документации сказано, что она основана на *ipnsort*, который сочетает быстрый средний случай быстрой сортировки
  с быстрым худшим случаем пирамидальной сортировки (heapsort; её объясняет Урок 07.12), поэтому O(n log n) выполняется для любого входа.
- Чтобы найти только k-й по величине элемент (медиану, десять лучших), полная сортировка не нужна:
  `v.select_nth_unstable(k)` работает за O(n). Это быстрый выбор (quickselect) стандартной библиотеки (в Упражнении 4 вы построите простой).

В настоящем проекте вы не будете писать алгоритм сортировки. Но «разделяй и властвуй» и «разбиение» вам ещё встретятся в
деревьях, в поиске и во многих других алгоритмах.

## Частые ошибки

**1. Два `&mut` среза одного среза одновременно.** Кажется естественным взять сначала обе половины, а использовать потом:

```rust
pub fn sort_halves<T: Ord>(v: &mut [T]) {
    let mid = v.len() / 2;
    let left = &mut v[..mid];
    let right = &mut v[mid..];
    left.sort();
    right.sort();
}
```

```text
error[E0499]: cannot borrow `*v` as mutable more than once at a time
 --> src/lib.rs:4:22
  |
3 |     let left = &mut v[..mid];
  |                     - first mutable borrow occurs here
4 |     let right = &mut v[mid..];
  |                      ^ second mutable borrow occurs here
5 |     left.sort();
  |     ---- first borrow later used here
  |
  = help: use `.split_at_mut(position)` to obtain two mutable non-overlapping sub-slices
```

Компилятор не видит, что `..mid` и `mid..` не пересекаются. Строка help подсказывает исправление: `let (left, right) = v.split_at_mut(mid);` —
безопасная функция, которая доказывает, что части раздельны. (Наша `merge_sort_rec` в порядке, потому что каждое заимствование заканчивается до начала следующего.)

**2. Наивный опорный элемент.** Простейшая быстрая сортировка берёт последний элемент как опорный и двустороннее разбиение:

```rust
fn naive_quicksort<T: Ord>(v: &mut [T]) {
    if v.len() <= 1 {
        return;
    }
    let last = v.len() - 1; // the last item is the pivot
    let mut store = 0;
    for i in 0..last {
        if v[i] < v[last] {
            v.swap(i, store);
            store += 1;
        }
    }
    v.swap(store, last);
    naive_quicksort(&mut v[..store]);
    naive_quicksort(&mut v[store + 1..]);
}
```

Она верна и быстра на случайных данных. Но на **уже отсортированном** входе опорный элемент всегда самый большой,
поэтому в одной части `n − 1` элементов, а в другой нет ни одного. Измерение на `0..n` в релизной сборке через `Instant` (Урок 05.12):

```text
n = 10000: 31.741333ms
n = 20000: 78.712625ms
n = 40000: 295.459708ms
```

Удвоение `n` замедляет примерно вчетверо: это O(n²). Отсортированные данные в настоящих программах встречаются очень часто, поэтому эта «простая»
версия — ловушка. Медиана трёх, трёхстороннее разбиение и рекурсия только в меньшую часть — три дешёвых исправления,
которые использует наша `quicksort`.

### Упражнение 1 — Слияние вручную (легко)

Слейте отсортированные списки `[2, 5, 8]` и `[1, 5, 9, 10]` так, как это делает `merge_sort_rec`. Запишите каждое сравнение. В каком порядке выйдут две
пятёрки (первая `5` — из левого списка)? Сколько сравнений сделано?

<details>
<summary>Подсказка</summary>

Берите из правого списка только если его передний элемент строго меньше переднего элемента левого списка. Когда один список пуст, сравнивать больше не нужно.

</details>

<details>
<summary>Ответ</summary>

```text
2 vs 1  take 1     out = [1]
2 vs 5  take 2     out = [1 2]
5 vs 5  take 5 (left, tie)   out = [1 2 5]
8 vs 5  take 5 (right)       out = [1 2 5 5]
8 vs 9  take 8     out = [1 2 5 5 8]
left is empty: copy 9, 10    out = [1 2 5 5 8 9 10]
```

5 сравнений. При равенстве `5 vs 5` первой берётся левая `5`, поэтому равные элементы сохраняют исходный порядок. Это
правило устойчивости сортировки слиянием.

</details>

### Упражнение 3 — Назовите сложность (средне)

Ответьте для каждого случая Big-O и одним предложением обоснования:

1. Время `merge_sort` на 1 000 000 уже отсортированных элементов.
2. Дополнительная память `merge_sort` и `quicksort` для `n` элементов.
3. Глубина рекурсии `merge_sort_rec` для 1 000 000 элементов.
4. Время наивной быстрой сортировки из раздела «Частые ошибки» для списка из `n` равных чисел.

<details>
<summary>Подсказка</summary>

Спросите себя: сколько уровней и сколько работы делает один уровень? Для (4): что делает наивное разбиение, когда ни один элемент не меньше опорного?

</details>

<details>
<summary>Ответ</summary>

1. **O(n log n)** (около 20 миллионов шагов). Сортировка слиянием не смотрит на порядок входа; каждый уровень сливает все `n` элементов.
2. Сортировка слиянием: **O(n)** на временный буфер. Быстрая сортировка: **O(log n)** на стек вызовов, потому что наша версия рекурсивно заходит только в меньшую часть.
3. Около **20**: деление 1 000 000 элементов пополам доходит до 1 за 20 шагов (2²⁰ = 1 048 576), поэтому в стеке одновременно ждёт не более 20 вызовов.
4. **O(n²)**: ни один элемент не меньше опорного, поэтому каждое разбиение оставляет `n − 1` элементов с одной стороны: `n + (n−1) + … + 1` шагов. (Наша `quicksort` с трёхсторонним
   разбиением обрабатывает этот вход за O(n): все элементы попадают в группу «равных» за один проход.)

</details>

### Упражнение 4 — Быстрый выбор (сложно)

Напишите в `sorting.rs` функцию `nth_smallest<T: Ord + Clone>(v: &mut [T], k: usize) -> T` (где `k = 0` — наименьший элемент), используя
`median_of_three` и `partition3`, но **без** сортировки всего: после каждого разбиения оставляйте только ту часть, где лежит позиция `k`. Напишите тест,
сравнивающий результат с отсортированным вектором для каждого `k` и для многих длин. Какова средняя временная сложность?

<details>
<summary>Подсказка</summary>

Храните два числа `lo` и `hi` так, чтобы ответ всегда лежал внутри `v[lo..hi]`. Разбивайте `&mut v[lo..hi]`; возвращаемые ею границы
отсчитываются от `lo`. Если `k` левее группы равных, положите `hi = lo + lt`. Если правее, положите `lo = lo + gt`. Иначе значение опорного элемента и есть ответ.

</details>

<details>
<summary>Ответ</summary>

```rust
/// The k-th smallest item (k = 0 is the smallest), found with partitioning only.
pub fn nth_smallest<T: Ord + Clone>(v: &mut [T], k: usize) -> T {
    assert!(k < v.len(), "k must be smaller than the length");
    let (mut lo, mut hi) = (0, v.len()); // the answer is inside v[lo..hi]
    loop {
        let part = &mut v[lo..hi];
        let pivot = median_of_three(part);
        let (lt, gt) = partition3(part, pivot);
        let (lt, gt) = (lo + lt, lo + gt);
        if k < lt {
            hi = lt;
        } else if k >= gt {
            lo = gt;
        } else {
            return v[k].clone();
        }
    }
}
```

Тест внутри модуля `tests`:

```rust
    #[test]
    fn nth_smallest_matches_sorting() {
        for len in 1..60 {
            let data = random_vec(len as u64, len, 20);
            let mut sorted = data.clone();
            sorted.sort();
            for (k, expected) in sorted.iter().enumerate() {
                let mut copy = data.clone();
                assert_eq!(&nth_smallest(&mut copy, k), expected, "len {len}, k {k}");
            }
        }
    }
```

Почему это работает: после `partition3` позиции `lt..gt` содержат значение опорного элемента на их окончательных отсортированных местах. Если `k` попадает
туда, мы закончили. Если нет, ответ только с одной стороны, и мы отбрасываем другую. При хороших опорных элементах часть каждый раз примерно вдвое
меньше: `n + n/2 + n/4 + … ≈ 2n`, поэтому среднее время — **O(n)**, меньше, чем O(n log n) полной сортировки.

</details>

## Вопросы для самопроверки

1. В чём главное различие в том, как работают сортировка слиянием и быстрая сортировка?

<details>
<summary>Ответ</summary>

Сортировка слиянием вслепую делит пополам и делает работу при слиянии на обратном пути вверх. Быстрая сортировка делает работу
при спуске вниз (разбиение вокруг опорного элемента), а потом ей нечего объединять.

</details>

2. Почему сортировка слиянием устойчива, а наша быстрая сортировка — нет?

<details>
<summary>Ответ</summary>

При слиянии при равенстве первым берётся левый элемент, поэтому равные элементы сохраняют порядок. Разбиение обменивает элементы на больших
расстояниях и может перебросить элемент через равный ему.

</details>

3. Какой вход заставляет быструю сортировку с плохим правилом выбора опорного элемента работать за O(n²)?

<details>
<summary>Ответ</summary>

Такой, где опорный элемент всегда самый маленький или самый большой, например уже отсортированный или обратный список, если опорным берётся первый или последний элемент.
Части получаются размеров 0 и `n − 1`.

</details>

4. Почему `quicksort` рекурсивно заходит в меньшую часть, а по большей идёт циклом?

<details>
<summary>Ответ</summary>

Тогда каждый рекурсивный вызов работает не более чем с половиной элементов, поэтому стек вызовов никогда не растёт глубже примерно log₂ n, даже при плохих опорных элементах.

</details>

5. Какой метод стандартной библиотеки даёт медиану большого среза без его полной сортировки?

<details>
<summary>Ответ</summary>

`select_nth_unstable(k)` при `k = len / 2`. Он работает за O(n).

</details>

## Итоги

- «Разделяй и властвуй» разбивает задачу на меньшие копии самой себя. Деление пополам даёт около log₂ n уровней, поэтому сортировка, которая делает O(n) работы на уровень, стоит O(n log n).
- Сортировка слиянием: отсортировать обе половины, слить их, повторно беря меньший передний элемент. Всегда O(n log n), O(n) дополнительной памяти, устойчива.
- Быстрая сортировка: выбрать опорный элемент, разбить вокруг него, отсортировать обе стороны. В среднем O(n log n), в худшем случае O(n²), O(log n) дополнительной памяти, неустойчива.
- Хорошей быстрой сортировке нужны хороший опорный элемент (медиана трёх), трёхстороннее разбиение для равных элементов, рекурсия только в меньшую часть и сортировка вставками для коротких срезов.
- Тестируйте с граничными длинами, множеством повторов и отсортированными, обратными и состоящими из равных элементов входами и сравнивайте со `std`.
- Результат измерений: на 10 000 элементов обе быстрее сортировки вставками более чем в 20 раз, а стандартная `sort` ещё в 5 раз быстрее наших версий.
- В настоящем коде используйте `sort`, `sort_unstable` и `select_nth_unstable`.

- [Rust standard library — slice::select_nth_unstable](https://doc.rust-lang.org/std/primitive.slice.html#method.select_nth_unstable) — поиск k-го элемента за O(n).
- [Rust standard library — slice::split_at_mut](https://doc.rust-lang.org/std/primitive.slice.html#method.split_at_mut) — два непересекающихся изменяемых среза.
