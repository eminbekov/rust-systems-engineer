## Новые слова

| Слово | Значение |
|---|---|
| **прокси** (proxy) | Программа, которая стоит между клиентом и сервером и передаёт их трафик дальше, возможно, просматривая или изменяя его. |
| **прямой прокси** (forward proxy) | Прокси, который работает на **клиентов**: они отправляют через него все свои запросы (например, прокси компании). |
| **обратный прокси** (reverse proxy) | Прокси, который работает на **серверы**: клиенты думают, что это и есть сервер; он передаёт запросы настоящим серверам позади себя. |
| **балансировщик нагрузки** (load balancer) | Обратный прокси, который распределяет запросы или соединения по нескольким одинаковым серверам (**бэкендам**). |
| **бэкенд** (backend) / **upstream** | Один из настоящих серверов позади прокси. |
| **L4 / L7** (layer 4 / layer 7, уровень 4 / уровень 7) | Номера уровней из модели OSI (Open Systems Interconnection, взаимодействие открытых систем): 4 — транспорт (TCP, Transmission Control Protocol, протокол управления передачей), 7 — приложение (HTTP, HyperText Transfer Protocol, протокол передачи гипертекста). Прокси L4 копирует байты; прокси L7 понимает запросы. |
| **завершение TLS** (TLS termination) | Прокси держит сертификат, расшифровывает трафик TLS (Transport Layer Security, протокол защиты транспортного уровня) и говорит с бэкендами открытым текстом или по новому TLS. |
| **сквозная передача TLS** (TLS passthrough) | Прокси не расшифровывает; он передаёт зашифрованные байты, выбирая бэкенд только по имени SNI (Server Name Indication, указание имени сервера) из первого сообщения. |
| **проверка работоспособности** (health check) | Регулярная проверка, которая говорит прокси, может ли бэкенд принимать трафик. |
| **round robin** (по кругу) | Бэкенды берутся по очереди: 1, 2, 3, 1, 2, 3, … |
| **least connections** (наименьшее число соединений) | Выбор бэкенда с наименьшим числом открытых соединений. |
| **идемпотентный** (idempotent) | Запрос, результат которого одинаков, выполнится ли он один раз или несколько (`GET`, `PUT`), поэтому его можно безопасно повторять. |
| **`X-Forwarded-For`** | HTTP-заголовок, в который прокси записывают IP-адрес (Internet Protocol, межсетевой протокол) исходного клиента. |
| **QUIC, RFC** | Транспорт из Урока 15.13, построенный поверх UDP (User Datagram Protocol, протокол пользовательских датаграмм); его название не сокращение; Request for Comments («запрос комментариев») — документы, которые определяют интернет-стандарты. |

## 1. Прямые и обратные прокси

Прокси — это посредник. Важно, **на кого** он работает:

```text
 forward proxy (works for clients)          reverse proxy (works for servers)

 laptop ─┐                                                    ┌─► app server 1
 laptop ─┼─► company proxy ──► the internet     client ──► proxy ──┼─► app server 2
 laptop ─┘   (filters, logs, caches)          (looks like       └─► app server 3
                                               "the server")
```

- **Прямой прокси** настраивается на клиентах (`HTTPS_PROXY=…`). Он решает, куда им можно ходить, а внешний мир видит адрес прокси вместо их адресов.
- **Обратный прокси** стоит перед серверами. Клиенты подключаются к нему так, будто это и есть сервис. Он может завершать TLS, направлять `/api` одной группе серверов, а `/static` — другой, кэшировать, ограничивать частоту запросов и скрывать, сколько серверов за ним. Распространённые — nginx, HAProxy, Envoy и Traefik; в Kubernetes эти роли играют Service и Ingress-контроллер.
- **Балансировщик нагрузки** — обратный прокси, главная задача которого — распределять нагрузку по одинаковым бэкендам и перестать отправлять трафик на неработающие.

С одним вы уже работали: в Уроке 15.13 HTTP/3-сервер `cloudflare-quic.com` — обратный прокси, который общается с собственными серверами позади себя.

## 2. Уровень 4 и уровень 7

Прокси может работать на двух уровнях:

| | Прокси L4 (TCP) | Прокси L7 (HTTP) |
|---|---|---|
| Видит | адреса, порты, поток байтов | методы, пути, заголовки, тела |
| Выбирает бэкенд | один раз на **соединение** | на каждый **запрос** (одно соединение может нести много) |
| Может маршрутизировать по | IP и порту (и SNI при сквозной передаче TLS) | хосту, пути, заголовку, cookie |
| Может менять трафик | нет | да: добавлять заголовки, переписывать пути, сжимать, кэшировать |
| Подходит для | любого протокола поверх TCP: базы данных, SSH (Secure Shell), MQTT (Message Queuing Telemetry Transport, протокол обмена сообщениями для небольших устройств), HTTP | только протокола, который он понимает |
| Цена за байт | очень мала | разбор и буферизация |
| Примеры | HAProxy `mode tcp`, nginx `stream`, Service в Kubernetes | nginx `http`, Envoy, Traefik, Ingress |

TLS добавляет ещё один выбор. При **завершении TLS** прокси держит сертификат и закрытый ключ (Урок 15.12), расшифровывает и затем может работать на L7. При **сквозной передаче TLS** прокси передаёт зашифрованные байты; он всё ещё может прочитать имя SNI в первом сообщении клиента, которое не зашифровано, и выбрать бэкенд по имени, но больше ничего не видит. (Более новое расширение TLS, Encrypted Client Hello, скрывает даже это имя от всех, кроме оператора сервера; с ним выбор по SNI работает только у прокси, который держит соответствующий ключ.) Сквозная передача держит ключи только на бэкендах; завершение позволяет прокси заглядывать в запросы.

> 🔒 **Безопасность:** прокси, завершающий TLS, видит каждый пароль и токен открытым текстом, поэтому он — часть вашей самой чувствительной инфраструктуры. Если сети между прокси и бэкендами нельзя полностью доверять, используйте TLS и там (часто взаимный TLS, Урок 15.12).

## 3. TCP-прокси в 30 строк

Прокси L4 делает совсем немного: принимает соединение, открывает соединение с бэкендом и копирует байты в обе стороны, пока обе стороны не закончат. В Tokio есть ровно такая функция: `tokio::io::copy_bidirectional`.

Сначала бэкенд для проверки. Он отвечает на каждый HTTP-запрос своим именем и адресом, с которого, как он видит, пришёл клиент. Создайте `src/bin/backend.rs`:

```rust
use tokio::io::{AsyncReadExt, AsyncWriteExt};
use tokio::net::TcpListener;

/// A tiny HTTP backend: `backend <port> <name>` answers every request with its name.
#[tokio::main]
async fn main() -> std::io::Result<()> {
    let mut args = std::env::args().skip(1);
    let port = args.next().unwrap_or_else(|| "9001".to_string());
    let name = args.next().unwrap_or_else(|| "backend".to_string());
    let listener = TcpListener::bind(format!("127.0.0.1:{port}")).await?;
    println!("{name} listening on {}", listener.local_addr()?);

    loop {
        let (mut stream, peer) = listener.accept().await?;
        let name = name.clone();
        tokio::spawn(async move {
            let mut buf = [0u8; 1024];
            let _ = stream.read(&mut buf).await; // the request; we ignore its content
            let body = format!("hello from {name}, you are {peer}\n");
            let reply = format!(
                "HTTP/1.1 200 OK\r\ncontent-length: {}\r\nconnection: close\r\n\r\n{body}",
                body.len()
            );
            let _ = stream.write_all(reply.as_bytes()).await;
        });
    }
}
```

Прокси должен выбирать бэкенд для каждого соединения. Положите выбор в библиотеку, `src/lib.rs`:

```rust
use std::net::SocketAddr;
use std::sync::atomic::{AtomicUsize, Ordering};

/// A list of backends, chosen in turn: round robin.
pub struct RoundRobin {
    backends: Vec<SocketAddr>,
    next: AtomicUsize,
}

impl RoundRobin {
    pub fn new(backends: Vec<SocketAddr>) -> Self {
        assert!(!backends.is_empty(), "need at least one backend");
        RoundRobin {
            backends,
            next: AtomicUsize::new(0),
        }
    }

    /// Returns the next backend. Safe to call from many tasks at once.
    pub fn pick(&self) -> SocketAddr {
        let n = self.next.fetch_add(1, Ordering::Relaxed);
        self.backends[n % self.backends.len()]
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn takes_turns_and_wraps_around() {
        let a: SocketAddr = "127.0.0.1:9001".parse().unwrap();
        let b: SocketAddr = "127.0.0.1:9002".parse().unwrap();
        let rr = RoundRobin::new(vec![a, b]);
        let picks: Vec<_> = (0..5).map(|_| rr.pick()).collect();
        assert_eq!(picks, [a, b, a, b, a]);
    }
}
```

**Что происходит:**

1. `next` считает, сколько бэкендов уже выдано. `fetch_add(1)` увеличивает его и возвращает старое значение **атомарно**: две задачи, вызвавшие `pick` в один и тот же момент, всегда получают разные числа, без блокировки (Урок 14.5).
2. `n % len` превращает постоянно растущий счётчик в индекс: 0, 1, 0, 1, … Порядка `Relaxed` достаточно, потому что никакие другие данные от этого счётчика не зависят (Урок 14.6).
3. Когда счётчик дойдёт до `usize::MAX`, `fetch_add` перейдёт через ноль, а не запаникует, так что прокси может работать вечно. (На 64-битной машине до этого всё равно не дойдёт и за много человеческих жизней.)
4. Тест фиксирует точный порядок, включая переход через начало.

Теперь прокси, `src/bin/l4proxy.rs`:

```rust
use std::net::SocketAddr;
use std::sync::Arc;

use p15_proxy::RoundRobin;
use tokio::io::copy_bidirectional;
use tokio::net::{TcpListener, TcpStream};

/// `l4proxy <backend> [<backend> …]`: listens on 127.0.0.1:8080 and forwards every
/// connection to the next backend, byte for byte.
#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let backends: Vec<SocketAddr> = std::env::args()
        .skip(1)
        .map(|a| a.parse())
        .collect::<Result<_, _>>()?;
    let pool = Arc::new(RoundRobin::new(backends));
    let listener = TcpListener::bind("127.0.0.1:8080").await?;
    println!("proxy listening on {}", listener.local_addr()?);

    loop {
        let (mut client, peer) = listener.accept().await?;
        let backend = pool.pick();
        tokio::spawn(async move {
            match TcpStream::connect(backend).await {
                Ok(mut server) => match copy_bidirectional(&mut client, &mut server).await {
                    Ok((up, down)) => {
                        println!("{peer} -> {backend}: {up} bytes up, {down} bytes down")
                    }
                    Err(err) => eprintln!("{peer} -> {backend}: {err}"),
                },
                Err(err) => eprintln!("{peer}: cannot reach {backend}: {err}"),
            }
        });
    }
}
```

**Что происходит:**

1. Адреса бэкендов берутся из командной строки; `collect::<Result<_, _>>()?` останавливает программу с ошибкой, если какой-то из них не разбирается.
2. Для каждого принятого клиента `pool.pick()` выбирает бэкенд, и задача подключается к нему.
3. `copy_bidirectional(&mut client, &mut server)` копирует клиент → сервер и сервер → клиент **одновременно**, пока не закончатся оба направления. Когда одна сторона закрывает свою пишущую половину, функция передаёт это дальше (вызывает `shutdown` на другой стороне) и продолжает копировать другое направление: полузакрытие (half-close) работает правильно. Функция возвращает, сколько байт прошло в каждую сторону.
4. Если до бэкенда не достучаться, задача пишет это в лог и закрывает соединение клиента.

Запустите два бэкенда и прокси, каждый в своём терминале (или с `&` в конце строки), и отправьте четыре запроса через прокси и один — напрямую бэкенду:

```bash
cargo run -q --bin backend -- 9001 blue
cargo run -q --bin backend -- 9002 green
cargo run -q --bin l4proxy -- 127.0.0.1:9001 127.0.0.1:9002
```

```bash
for i in 1 2 3 4; do curl -s http://127.0.0.1:8080/; done
curl -s http://127.0.0.1:9001/
```

```text
hello from blue, you are 127.0.0.1:58455
hello from green, you are 127.0.0.1:58457
hello from blue, you are 127.0.0.1:58459
hello from green, you are 127.0.0.1:58461
hello from blue, you are 127.0.0.1:58462
```

Прокси пишет в лог по строке на соединение:

```text
proxy listening on 127.0.0.1:8080
127.0.0.1:58454 -> 127.0.0.1:9001: 77 bytes up, 99 bytes down
127.0.0.1:58456 -> 127.0.0.1:9002: 77 bytes up, 100 bytes down
127.0.0.1:58458 -> 127.0.0.1:9001: 77 bytes up, 99 bytes down
127.0.0.1:58460 -> 127.0.0.1:9002: 77 bytes up, 100 bytes down
```

**Что происходит:** запросы чередуются между `blue` и `green`. Посмотрите на порты: `curl` подключился к прокси с порта 58454, а `blue` увидел клиента на порту 58455 — это собственное исходящее соединение прокси. **Бэкенд больше не видит настоящего клиента.** (77 байт — это запрос `curl`; ответ `green` на байт длиннее, потому что длиннее его имя.)

> 🧪 **Тестирование:** выбор бэкенда — обычный библиотечный тип, поэтому `cargo test` проверяет его без всякой сети. Держите логику решений (какой бэкенд, здоров ли он, можно ли начать это соединение) отдельно от кода ввода-вывода (I/O, input/output) и тестируйте её саму по себе; затем тестируйте весь прокси с несколькими локальными бэкендами на порту 0, как вы сделаете в Уроке 15.15.

## 4. Выбор бэкенда

Round robin прост и справедлив, когда все запросы стоят примерно одинаково. Для других ситуаций подходят другие алгоритмы:

| Алгоритм | Как выбирает | Хорош, когда |
|---|---|---|
| **round robin** | по очереди | бэкенды одинаковы, запросы похожи |
| **взвешенный round robin** | по очереди, но бэкенд с весом 3 получает три хода против одного | бэкенды разного размера (Упражнение 2) |
| **least connections** | бэкенд с наименьшим числом открытых соединений | соединения живут очень разное время (Упражнение 3) |
| **случайный** (random) | любой бэкенд, выбранный случайно | много независимых прокси; общее состояние не нужно |
| **power of two choices** (выбор из двух) | выбрать два случайно и взять менее загруженный | почти так же хорош, как least connections, но гораздо дешевле при большом масштабе |
| **хеширование** (по IP клиента, ключу или пути) | один и тот же вход всегда идёт на один и тот же бэкенд | кэши и *липкие сессии* (sticky sessions); согласованное хеширование (Урок 18.8) оставляет бо́льшую часть ключей на месте при смене бэкендов |

> ⚡ **Производительность:** выбор бэкенда выполняется на каждое соединение или запрос, поэтому он должен быть дешёвым и неблокирующим: атомарный счётчик, а не `Mutex<Vec<…>>`, которого ждёт каждая задача. Измеряйте, прежде чем выбирать «более умный» алгоритм; round robin плюс хорошие проверки работоспособности достаточно на удивление часто.

## 5. Что добавляет настоящий балансировщик

Прокси выше работает, но ставить его перед настоящими пользователями ещё небезопасно. Остановите бэкенд `green` (`Ctrl+C`), перезапустите прокси с несуществующим бэкендом (`9003`) и отправьте два запроса:

```bash
cargo run -q --bin l4proxy -- 127.0.0.1:9001 127.0.0.1:9003
```

```bash
curl -s http://127.0.0.1:8080/
curl -sS http://127.0.0.1:8080/
```

```text
hello from blue, you are 127.0.0.1:58465
curl: (56) Recv failure: Connection reset by peer
```

В логе прокси видно `127.0.0.1:58466: cannot reach 127.0.0.1:9003: Connection refused (os error 61)` (в Linux номер ошибки — 111). Каждый второй пользователь получает ошибку — и так навсегда. Балансировщик в продакшене избегает этого с помощью:

- **Проверок работоспособности.** *Активных*: каждые несколько секунд попробовать подключиться (L4) или сделать `GET /health` (L7) к каждому бэкенду и пометить его как *down* после нескольких неудач и снова как *up* после нескольких успехов. *Пассивных*: считать настоящие отказы и выводить бэкенд из работы, когда их накопилось много. Тогда выбор пропускает неработающие бэкенды.
- **Тайм-аутов** везде: на подключение к бэкенду (выключенная машина часто вообще не отвечает, и `connect` ждал бы минутами), на простаивающие соединения и, на L7, на запрос целиком.
- **Повторных попыток** — осторожно. Если `connect` к бэкенду не удался, ещё ничего не отправлено, поэтому попробовать следующий бэкенд всегда безопасно. На L7 повторяйте запрос, только если он **идемпотентный**: повтор `POST /payments`, который, возможно, уже обработан, может списать деньги дважды.
- **Ограничений.** Максимум соединений всего и на каждый бэкенд, чтобы всплеск трафика вставал в очередь или отклонялся, а не заваливал всё (обратное давление, Урок 14.13).
- **Корректного завершения.** При перезапуске перестать принимать новые соединения, дать открытым закончиться (со сроком) и затем выйти (Урок 14.14).
- **Адреса клиента.** Поскольку бэкенд видит только прокси, прокси L7 добавляет `X-Forwarded-For: <IP клиента>` (или стандартный заголовок `Forwarded: for=…`, RFC 7239); прокси L4 может отправить перед данными строку *PROXY protocol*, если бэкенд её ожидает.

Проверки работоспособности, ограничения и корректное завершение вы встроите в настоящий балансировщик L4 в Уроке 15.15 — Проект: балансировщик нагрузки TCP.

## Частые ошибки

**1. Доверять `X-Forwarded-For` от кого угодно.** Любой клиент может сам прислать этот заголовок с любым адресом. Ставить его может только ваш собственный прокси: прокси должен **удалять** входящие заголовки `X-Forwarded-For` от клиентов (или осознанно дописывать к ним), а бэкенд должен доверять заголовку, только если соединение пришло от этого прокси. Иначе ограничения частоты и правила доступа по IP клиента обходятся элементарно.

**2. Нет тайм-аута подключения.** Выключенная машина-бэкенд не отказывает в соединении: она просто не отвечает. Тогда `TcpStream::connect` ждёт до предела операционной системы, часто больше минуты, а клиенты тем временем копятся. Оборачивайте его в `tokio::time::timeout` (Урок 14.14).

**3. Копировать по одному направлению за раз.** Прокси, который сначала читает весь запрос и только потом передаёт его, или который копирует клиент → сервер, а только затем сервер → клиент, попадает во взаимную блокировку с протоколами, где обе стороны говорят одновременно, и добавляет задержку всем остальным. Копируйте оба направления одновременно, как делает `copy_bidirectional`.

**4. Повторять всё подряд.** Прокси L7, который повторяет каждый неудачный запрос, превращает один медленный бэкенд в шторм дублирующихся запросов и повторяет неидемпотентные операции. Повторяйте только безопасные случаи, с ограничением и желательно на другом бэкенде.

## Попробуйте сами

1. Запустите два бэкенда и прокси, как в разделе 3.
2. Выполните `for i in $(seq 1 6); do curl -s http://127.0.0.1:8080/; done`. Посчитайте, сколько раз вы видите `blue` и `green`.
3. Остановите `green` через `Ctrl+C` и снова запустите цикл. Каждый второй запрос падает с `Connection reset by peer`, а в логе прокси видно `cannot reach 127.0.0.1:9002`. Именно эту проблему решают проверки работоспособности в Уроке 15.15.
4. Снова запустите `green`: без перезапуска прокси следующие запросы опять работают, потому что прокси подключается заново для каждого клиента.

## Упражнения

### Упражнение 1 — Не только HTTP (легко)

Покажите, что прокси L4 передаёт любой протокол. Используйте `nc -l 9005` как единственный бэкенд, направьте на него прокси, отправьте через прокси одну строку обычного текста с помощью `nc` и посмотрите, что получил бэкенд и что записал в лог прокси.

<details>
<summary>Подсказка</summary>

Запустите `nc -l 9005` в одном терминале (он печатает то, что получает), прокси с `127.0.0.1:9005` — во втором, затем `printf 'not HTTP at all\n' | nc -w 1 127.0.0.1 8080` — в третьем (`-w 1` закрывает соединение через секунду).

</details>

<details>
<summary>Ответ</summary>

Терминал бэкенда печатает:

```text
not HTTP at all
```

Прокси пишет в лог (ваш порт будет другим):

```text
127.0.0.1:58917 -> 127.0.0.1:9005: 16 bytes up, 0 bytes down
```

Почему это работает: прокси никогда не смотрит на байты, поэтому ему всё равно, к какому протоколу они относятся. 16 байт — это текст плюс перевод строки; обратно ничего не пришло, поэтому клиенту ушло 0 байт. HTTP-прокси L7 отверг бы такой ввод как некорректный запрос.

</details>

### Упражнение 2 — Взвешенный round robin (средне)

Напишите `Weighted` в новом модуле `src/weighted.rs` (добавьте `pub mod weighted;` в `src/lib.rs`): `Weighted::new(&[(addr, weight)])` и `pick()`, где бэкенд с весом 3 получает три хода на каждый ход бэкенда с весом 1, а вес 0 означает «никогда». Напишите тесты для обоих правил.

<details>
<summary>Подсказка</summary>

Самое простое правильное решение повторяет каждый адрес `weight` раз в списке (`std::iter::repeat_n(addr, weight)` внутри `flat_map`), а затем делает обычный round robin по этому списку.

</details>

<details>
<summary>Ответ</summary>

```rust
use std::net::SocketAddr;
use std::sync::atomic::{AtomicUsize, Ordering};

/// Round robin where a backend with weight 3 gets three turns for every one turn of weight 1.
pub struct Weighted {
    slots: Vec<SocketAddr>,
    next: AtomicUsize,
}

impl Weighted {
    pub fn new(backends: &[(SocketAddr, usize)]) -> Self {
        let slots: Vec<SocketAddr> = backends
            .iter()
            .flat_map(|&(addr, weight)| std::iter::repeat_n(addr, weight))
            .collect();
        assert!(
            !slots.is_empty(),
            "need at least one backend with weight > 0"
        );
        Weighted {
            slots,
            next: AtomicUsize::new(0),
        }
    }

    pub fn pick(&self) -> SocketAddr {
        let n = self.next.fetch_add(1, Ordering::Relaxed);
        self.slots[n % self.slots.len()]
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn a_heavier_backend_gets_more_turns() {
        let a: SocketAddr = "127.0.0.1:9001".parse().unwrap();
        let b: SocketAddr = "127.0.0.1:9002".parse().unwrap();
        let w = Weighted::new(&[(a, 3), (b, 1)]);
        let picks: Vec<_> = (0..8).map(|_| w.pick()).collect();
        assert_eq!(picks, [a, a, a, b, a, a, a, b]);
    }

    #[test]
    fn weight_zero_means_never() {
        let a: SocketAddr = "127.0.0.1:9001".parse().unwrap();
        let b: SocketAddr = "127.0.0.1:9002".parse().unwrap();
        let w = Weighted::new(&[(a, 0), (b, 2)]);
        assert!((0..10).all(|_| w.pick() == b));
    }
}
```

Почему это работает: после развёртывания `[(a, 3), (b, 1)]` становится списком `a, a, a, b`, и round robin по нему даёт ровно нужное соотношение. `assert!` защищает от списка из одних нулевых весов, на котором `% 0` вызвал бы панику. (Настоящие балансировщики распределяют ходы тяжёлого бэкенда равномернее, `a, b, a, a` вместо `a, a, a, b`, чтобы избежать всплесков; это хорошее расширение.)

</details>

### Упражнение 3 — Least connections с арендой (сложно)

Напишите `LeastConnections` в `src/least.rs`. `LeastConnections::pick(&pool)` выбирает бэкенд с наименьшим числом открытых соединений и возвращает `Lease` (аренду); пока аренда существует, соединение считается открытым, а удаление аренды его завершает. Тест: при двух свободных бэкендах первый выбор получает первый из них, второй выбор — другой, а после удаления первой аренды снова выбирается первый бэкенд.

<details>
<summary>Подсказка</summary>

Храните `Vec<(SocketAddr, AtomicUsize)>` в `Arc`. Аренда хранит `Arc` на пул и индекс, а `impl Drop for Lease` делает `fetch_sub(1)`. `iter().enumerate().min_by_key(...)` находит наименее загруженный элемент (при равенстве возвращает первый).

</details>

<details>
<summary>Ответ</summary>

```rust
use std::net::SocketAddr;
use std::sync::Arc;
use std::sync::atomic::{AtomicUsize, Ordering};

/// Picks the backend with the fewest open connections.
pub struct LeastConnections {
    backends: Vec<(SocketAddr, AtomicUsize)>,
}

/// Proof that one connection to `addr` is open. Dropping it closes the count.
pub struct Lease {
    pool: Arc<LeastConnections>,
    index: usize,
    pub addr: SocketAddr,
}

impl LeastConnections {
    pub fn new(addrs: Vec<SocketAddr>) -> Arc<Self> {
        assert!(!addrs.is_empty(), "need at least one backend");
        let backends = addrs
            .into_iter()
            .map(|a| (a, AtomicUsize::new(0)))
            .collect();
        Arc::new(LeastConnections { backends })
    }

    /// Chooses the least busy backend and counts the new connection.
    pub fn pick(pool: &Arc<Self>) -> Lease {
        let (index, (addr, open)) = pool
            .backends
            .iter()
            .enumerate()
            .min_by_key(|(_, (_, open))| open.load(Ordering::Relaxed))
            .expect("not empty");
        open.fetch_add(1, Ordering::Relaxed);
        Lease {
            pool: Arc::clone(pool),
            index,
            addr: *addr,
        }
    }

    pub fn open_connections(&self, addr: SocketAddr) -> usize {
        self.backends
            .iter()
            .find(|(a, _)| *a == addr)
            .map_or(0, |(_, open)| open.load(Ordering::Relaxed))
    }
}

impl Drop for Lease {
    fn drop(&mut self) {
        self.pool.backends[self.index]
            .1
            .fetch_sub(1, Ordering::Relaxed);
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn a_busy_backend_is_avoided_until_its_connection_ends() {
        let a: SocketAddr = "127.0.0.1:9001".parse().unwrap();
        let b: SocketAddr = "127.0.0.1:9002".parse().unwrap();
        let pool = LeastConnections::new(vec![a, b]);

        let first = LeastConnections::pick(&pool); // both idle: the first one wins
        assert_eq!(first.addr, a);
        let second = LeastConnections::pick(&pool); // a is busy, b is idle
        assert_eq!(second.addr, b);
        assert_eq!(pool.open_connections(a), 1);

        drop(first); // the connection to a ends
        assert_eq!(pool.open_connections(a), 0);
        assert_eq!(LeastConnections::pick(&pool).addr, a);
        drop(second);
    }
}
```

С `pub mod least;` и `pub mod weighted;` в `src/lib.rs` `cargo test` печатает для библиотеки `test result: ok. 4 passed`.

Почему это работает: аренда — это guard-объект RAII (Resource Acquisition Is Initialization, «получение ресурса есть инициализация»), как `MutexGuard`: счётчик увеличивается при её создании и уменьшается в `Drop`, поэтому забыть это невозможно, даже если задача соединения завершится ошибкой или паникой. В прокси вы держали бы аренду внутри задачи соединения, пока не вернётся `copy_bidirectional`. Чтение минимума и последующее прибавление — не один атомарный шаг, поэтому при большой нагрузке две задачи могут в один и тот же момент выбрать один бэкенд; для балансировки такая небольшая неточность допустима.

</details>

## Вопросы для самопроверки

1. Чем прямой прокси отличается от обратного?

<details>
<summary>Ответ</summary>

Прямой прокси работает на клиентов: они настроены отправлять свой трафик через него, и серверы видят прокси вместо них. Обратный прокси работает на серверы: клиенты подключаются к нему как к сервису, а он передаёт запросы настоящим серверам позади себя.

</details>

2. Почему прокси L4 не может направить `/api` и `/static` на разные бэкенды и чем он может пользоваться вместо этого?

<details>
<summary>Ответ</summary>

Прокси L4 видит только поток байтов и выбирает бэкенд один раз на соединение, ещё до чтения какого-либо запроса; он не разбирает HTTP и ничего не знает о путях. Он может маршрутизировать по адресу и порту, а при сквозной передаче TLS — по имени SNI в первом сообщении TLS.

</details>

3. В демонстрации `curl` использовал порт 58454, а бэкенд сообщил о клиенте на порту 58455. Почему и почему это важно?

<details>
<summary>Ответ</summary>

TCP-соединение бэкенда приходит от прокси, который открыл новое соединение со своего порта 58455. Бэкенд никогда не видит настоящего клиента, поэтому журналированию, ограничению частоты или правилам доступа по адресу клиента нужна дополнительная помощь: заголовки `X-Forwarded-For`/`Forwarded` на L7 или PROXY protocol на L4.

</details>

4. Почему при неудачном `connect` всегда безопасно попробовать другой бэкенд, а повторять неудачный HTTP-запрос — не всегда?

<details>
<summary>Ответ</summary>

Если `connect` не удался, ни один байт запроса не дошёл ни до одного бэкенда, то есть ещё ничего не произошло. Неудачный HTTP-запрос мог уже быть обработан (потерялся ответ, а не запрос); повтор неидемпотентного запроса, например платежа, мог бы выполнить его дважды.

</details>

5. Почему `RoundRobin::pick` использует `AtomicUsize::fetch_add`, а не `Mutex<usize>`?

<details>
<summary>Ответ</summary>

`fetch_add` увеличивает значение и возвращает старое за одну атомарную операцию процессора (CPU, Central Processing Unit, центральный процессор), поэтому каждая задача получает своё число, не ожидая блокировки. Это корректно и дешевле мьютекса для того, что выполняется на каждое соединение.

</details>

## Итоги

- Прямой прокси работает на клиентов; обратный прокси стоит перед серверами; балансировщик нагрузки — обратный прокси, который распределяет трафик по одинаковым бэкендам.
- Прокси L4 копируют байты и выбирают бэкенд один раз на соединение; прокси L7 понимают HTTP и могут маршрутизировать, менять и повторять каждый запрос.
- Завершение TLS кладёт ключи на прокси и позволяет ему видеть запросы; сквозная передача пересылает зашифрованные байты, маршрутизируя самое большее по SNI.
- `tokio::io::copy_bidirectional` — сердце прокси L4: оба направления одновременно, с правильным полузакрытием.
- Round robin на атомарном счётчике дёшев и безопасен; взвешенный вариант, least connections, power of two choices и хеширование подходят для других ситуаций.
- Балансировщики в продакшене добавляют проверки работоспособности, тайм-ауты, осторожные повторы, ограничения, корректное завершение и способ передать адрес клиента.
