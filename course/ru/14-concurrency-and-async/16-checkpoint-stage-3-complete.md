## Вопросы для самопроверки

**Этап 12: компьютерные системы**

1. Как значение −1 типа `i8` хранится в памяти и что происходит с `127_i8 + 1` в отладочной сборке и в сборке release?

<details>
<summary>Ответ</summary>

В дополнительном коде −1 — это все единичные биты: `0b1111_1111` (`0xFF`). `127_i8 + 1` переполняется: отладочная сборка паникует с «attempt to add with overflow»; сборка release переходит через край к −128 (если проверки переполнения не включены). Используйте `checked_add`, `wrapping_add` или `saturating_add`, чтобы явно сказать, чего вы хотите.

</details>

2. Почему `0.1 + 0.2 == 0.3` ложно для `f64` и как сравнивать числа с плавающей точкой?

<details>
<summary>Ответ</summary>

У `0.1`, `0.2` и `0.3` нет точного двоичного представления, поэтому каждое округляется, и ошибки округления не компенсируют друг друга. Сравнивайте с допуском: `(a - b).abs() < 1e-9` (допуск выбирайте под свою задачу).

</details>

3. Что такое ложное разделение (false sharing) и как его избежать?

<details>
<summary>Ответ</summary>

Два потока пишут в *разные* переменные, которые лежат в *одной* кэш-линии. Каждая запись забирает всю линию у другого ядра, поэтому линия скачет между ядрами, и оба потока замедляются, хотя общих данных у них нет. Исправление: поместите каждую «горячую» переменную в свою кэш-линию (дополните или выровняйте её, например через `crossbeam_utils::CachePadded`). Кэш-линии занимают 64 байта на большинстве процессоров x86-64 и 128 байтов на процессорах Apple серии M (`sysctl hw.cachelinesize` печатает `128` на Mac с M4).

</details>

4. Почему структура с полями `u8`, `u32`, `u16` в Rust занимает 8 байтов, а с `#[repr(C)]` — 12?

<details>
<summary>Ответ</summary>

Каждое поле должно начинаться с адреса, кратного его выравниванию (`u32`: 4). С `#[repr(C)]` поля остаются в написанном порядке: `u8` + 3 байта заполнения + `u32` + `u16` + 2 байта заполнения, чтобы размер был кратен 4, = 12. Обычный Rust может переставить поля (`u32`, `u16`, `u8`, 1 байт заполнения) = 8. Практическое задание 1 проверяет это тестом.

</details>

**Этап 13: операционные системы**

5. Что такое системный вызов? Назовите три.

<details>
<summary>Ответ</summary>

Просьба программы к ядру о том, что программа не может сделать сама: открыть файл, прочитать, записать, создать процесс, отобразить память. Примеры: `openat`, `read`, `write`, `clone`/`fork`, `execve`, `mmap`. На время вызова процессор переходит в режим ядра и затем обратно, и это стоит времени.

</details>

6. Что такое файловый дескриптор и что такое 0, 1 и 2?

<details>
<summary>Ответ</summary>

Небольшое целое число, которым процесс обозначает открытый файл, конвейер или сокет; это индекс в таблице открытых файлов процесса, которую ведёт ядро. 0 — стандартный ввод, 1 — стандартный вывод, 2 — стандартный вывод ошибок.

</details>

7. Что делают `fork`, `exec` и `wait` и что такое процесс-зомби?

<details>
<summary>Ответ</summary>

`fork` создаёт копию текущего процесса. `exec` заменяет программу в текущем процессе другой программой. `wait` позволяет родителю забрать код завершения закончившегося потомка. Зомби — это потомок, который закончился, но чей код завершения ещё никто не забрал; он занимает запись в таблице процессов, пока родитель его не дождётся.

</details>

8. Что такое страничный сбой (page fault) и всегда ли это ошибка?

<details>
<summary>Ответ</summary>

Процессор вызывает его, когда программа обращается к виртуальному адресу, чья страница (ещё) не отображена в физическую память. Обычно это не ошибка: ядро загружает страницу (из файла, из подкачки или выдаёт новую нулевую страницу), и программа продолжает работу. Только обращение к адресу, которым процессу пользоваться нельзя, приводит к падению (ошибке сегментации).

</details>

9. Какую проблему решает epoll?

<details>
<summary>Ответ</summary>

Сервер с тысячами соединений не может блокироваться на каждом, а опрашивать каждое по очереди («данные уже есть?») — пустая трата CPU. epoll позволяет одному потоку зарегистрировать множество файловых дескрипторов и спать, пока **какой-нибудь** из них не станет готов, а затем сообщает, какие именно. Асинхронные рантаймы вроде Tokio строят на нём свой реактор (в macOS — на kqueue).

</details>

10. Чем пространство имён (namespace) отличается от cgroup?

<details>
<summary>Ответ</summary>

Пространство имён меняет то, что процесс может **видеть** (свои идентификаторы процессов, сеть, точки монтирования, имя хоста). Cgroup ограничивает то, что процесс может **использовать** (время CPU, память, число процессов). Контейнер использует и то и другое.

</details>

**Этап 14: конкурентность и асинхронность**

11. Чем гонка данных отличается от состояния гонки и что из этого предотвращает безопасный Rust?

<details>
<summary>Ответ</summary>

Гонка данных: два потока одновременно обращаются к одной памяти, хотя бы один пишет, и синхронизации нет; это неопределённое поведение. Безопасный Rust предотвращает её при компиляции (`Send`, `Sync`, правила заимствования). Состояние гонки: результат зависит от времени, например потерянное обновление между `load` и `store`; оно возможно и в совершенно безопасном коде, и поймать его помогают только проектирование и тестирование (loom).

</details>

12. Что гарантируют `Release` при записи и `Acquire` при загрузке и почему это важно на вашем Mac?

<details>
<summary>Ответ</summary>

Если загрузка с `Acquire` видит значение, записанное записью с `Release`, то всё, что пишущий поток сделал до записи, видно читающему потоку после загрузки. Процессоры arm64 слабо упорядочены: без этой пары другое ядро может увидеть флаг раньше данных. Тест с `Relaxed` на Mac с M4 действительно иногда падает, а на другой машине может не упасть никогда.

</details>

13. Что делает loom и почему тесты loom должны быть маленькими?

<details>
<summary>Ответ</summary>

Он прогоняет тест по одному разу на каждое возможное чередование потоков loom (и моделирует модель памяти для атомарных типов), поэтому находит ошибки, которые проявляются только при редких расписаниях. Число расписаний очень быстро растёт с каждым новым потоком или операцией (4 итерации для двух потоков, 253 для трёх в Уроке 14.9), поэтому модели должны быть крошечными или использовать `LOOM_MAX_PREEMPTIONS`.

</details>

14. Что future обязан сделать, прежде чем вернуть `Poll::Pending`?

<details>
<summary>Ответ</summary>

Позаботиться, чтобы waker из `cx.waker()` был разбужен, когда станет возможен прогресс: сохранить клон там, где его найдёт источник события (а проверку и сохранение сделать без промежутка, чтобы пробуждение не потерялось). Исполнитель опрашивает задачу снова только после пробуждения.

</details>

15. Почему `poll` принимает `self: Pin<&mut Self>`?

<details>
<summary>Ответ</summary>

Future из `async fn` после первого опроса могут содержать ссылки на собственные поля (локальная переменная, заимствованная через `.await`). Перемещение такого future сделало бы эти ссылки висячими. `Pin` обещает, что future больше не переместится, поэтому опрашивать его безопасно.

</details>

16. Цикл с `select!` устраивает гонку `read_pair(&mut rx)` и таймера. Почему он может терять сообщения и какие есть два исправления?

<details>
<summary>Ответ</summary>

Когда побеждает таймер, `select!` выбрасывает future `read_pair` вместе с первым сообщением, которое тот, возможно, уже получил: `read_pair` небезопасен при отмене. Исправления: класть в `select!` только безопасные при отмене future (вроде `rx.recv()`) и хранить частичное состояние в цикле; или создать future один раз, закрепить его и передавать в `select!` ссылку `&mut`, чтобы он не выбрасывался.

</details>

17. Чем `token.cancel()` отличается от `handle.abort()`?

<details>
<summary>Ответ</summary>

`cancel()` у `CancellationToken` — просьба: задачи, которые следят за `cancelled()`, останавливаются по-своему и могут прибраться. `abort()` принуждает одну задачу: её future выбрасывается на следующем `.await`. Корректное завершение сначала просит, ждёт с ограничением времени и прерывает только оставшееся.

</details>

18. Назовите два способа предотвратить взаимную блокировку двух мьютексов.

<details>
<summary>Ответ</summary>

Брать блокировки в одном общем порядке (например, всегда сначала счёт с меньшим id) или никогда не держать одну блокировку, беря другую (скопировать нужные данные, освободить, потом взять следующую блокировку). Помогают и более короткие критические секции, и `try_lock` с запасным путём. Пропущенные взаимные блокировки находит loom.

</details>

### Задание 1 — Предскажите размещение в памяти (Этап 12)

В `tests/layout.rs` определите структуры `Reordered { a: u8, b: u32, c: u16 }` и такую же с `#[repr(C)]` под именем `InOrder`, а также перечисление `Shape { Dot(u8), Line(u64) }`. **Сначала** запишите свои предсказания `size_of` для: `Reordered`, `InOrder`, `Option<Box<u8>>`, `Option<u32>`, `Shape`, `&str`, `String` (на вашем 64-битном Mac). Затем превратите предсказания в один тест с `assert_eq!` и запустите `cargo test --test layout`.

<details>
<summary>Подсказка</summary>

Подумайте о выравнивании и заполнении (Урок 12.11) и о *нише* `Box`: `Box` никогда не бывает нулевым, поэтому `Option` может использовать нулевое значение для `None` без лишнего байта. У `u32` такого запрещённого значения нет. `&str` — это указатель и длина; `String` — указатель, ёмкость и длина.

</details>

<details>
<summary>Ответ</summary>

```rust
use std::mem::size_of;

#[allow(dead_code)]
struct Reordered {
    a: u8,
    b: u32,
    c: u16,
}

#[allow(dead_code)]
#[repr(C)]
struct InOrder {
    a: u8,
    b: u32,
    c: u16,
}

#[allow(dead_code)]
enum Shape {
    Dot(u8),
    Line(u64),
}

#[test]
fn layout_matches_my_predictions() {
    assert_eq!(size_of::<Reordered>(), 8);
    assert_eq!(size_of::<InOrder>(), 12);
    assert_eq!(size_of::<Option<Box<u8>>>(), 8);
    assert_eq!(size_of::<Option<u32>>(), 8);
    assert_eq!(size_of::<Shape>(), 16);
    assert_eq!(size_of::<&str>(), 16);
    assert_eq!(size_of::<String>(), 24);
}
```

`cargo test --test layout` показывает `test result: ok. 1 passed`. Почему это работает: компилятор переставляет поля `Reordered` в 4 + 2 + 1 + 1 байт заполнения = 8; `InOrder` сохраняет порядок — 12 (вопрос 4). `Option<Box<u8>>` использует нулевую нишу: 8. `Option<u32>` нужен отдельный тег, дополненный до выравнивания `u32`: 8. У `Shape` есть тег и `u64`, выровненный по 8: 16. `&str` — 2 × 8, `String` — 3 × 8.

</details>

### Задание 2 — Команда с ограничением времени (Этапы 13 и 14)

Напишите `async fn run_limited(program: &str, args: &[&str], limit: Duration) -> String` в `src/bin/run_limited.rs`. Она запускает программу как дочерний процесс через `tokio::process::Command`, перехватывает стандартный вывод и ждёт не дольше `limit`. Она возвращает строку с кодом возврата и выводом или «gave up after … ms, child killed». Попробуйте `echo hello`, `sh -c "exit 3"` и `sleep 5` с пределом 500 мс. Убедитесь, что процесс `sleep` действительно завершается.

<details>
<summary>Подсказка</summary>

`Command::new(program).args(args).stdout(Stdio::piped()).kill_on_drop(true).spawn()` даёт `Child`; `child.wait_with_output()` — это future. Оберните его в `tokio::time::timeout`. При тайм-ауте future (а вместе с ним и `Child`) выбрасывается; тогда `kill_on_drop(true)` посылает процессу сигнал завершения (Урок 13.7). Проверьте через `pgrep -f "sleep 5"` сразу после окончания программы.

</details>

<details>
<summary>Ответ</summary>

```rust
use std::process::Stdio;
use std::time::Duration;
use tokio::process::Command;
use tokio::time::timeout;

/// Runs `program` with `args`, but at most for `limit`.
async fn run_limited(program: &str, args: &[&str], limit: Duration) -> String {
    let child = Command::new(program)
        .args(args)
        .stdout(Stdio::piped())
        .kill_on_drop(true) // dropping the future kills the child
        .spawn()
        .expect("could not start the program");
    match timeout(limit, child.wait_with_output()).await {
        Ok(Ok(output)) => format!(
            "exit code {:?}, output {:?}",
            output.status.code(),
            String::from_utf8_lossy(&output.stdout).trim()
        ),
        Ok(Err(error)) => format!("error: {error}"),
        Err(_) => format!("gave up after {} ms, child killed", limit.as_millis()),
    }
}

#[tokio::main]
async fn main() {
    let limit = Duration::from_millis(500);
    println!("{}", run_limited("echo", &["hello"], limit).await);
    println!("{}", run_limited("sh", &["-c", "exit 3"], limit).await);
    println!("{}", run_limited("sleep", &["5"], limit).await);
}
```

```text
exit code Some(0), output "hello"
exit code Some(3), output ""
gave up after 500 ms, child killed
```

Почему это работает: отмена — это выбрасывание (Урок 14.14), а `kill_on_drop(true)` связывает выбрасывание значения Rust с процессом операционной системы. Без него `pgrep -f "sleep 5"` всё ещё находит процесс `sleep` после окончания программы: потомок продолжает работать сам по себе, его усыновляет первый процесс системы (Урок 13.5).

</details>

### Задание 3 — Одна сумма, три вида параллелизма (Этап 14)

В `src/bin/parallel_sum.rs` просуммируйте числа от 1 до 1 000 000 (`u64`) четырьмя способами: обычным итератором; через `std::thread::scope` с 4 потоками, каждый из которых суммирует свой кусок; через `par_iter().sum()` из `rayon`; и той же суммой rayon внутри `tokio::task::spawn_blocking` из асинхронного `main`. Напечатайте четыре результата и проверьте через `assert!`, что они равны.

<details>
<summary>Подсказка</summary>

`numbers.chunks(n)` делит срез на куски; `div_ceil` вычисляет размер куска так, чтобы 4 куска покрыли всё. Scoped-потоки могут заимствовать `numbers` (Урок 14.4). `spawn_blocking` нужно замыкание `'static`, поэтому переместите `Vec` в него.

</details>

<details>
<summary>Ответ</summary>

```rust
use rayon::prelude::*;
use std::thread;

fn sum_sequential(numbers: &[u64]) -> u64 {
    numbers.iter().sum()
}

fn sum_scoped_threads(numbers: &[u64], threads: usize) -> u64 {
    let chunk = numbers.len().div_ceil(threads);
    thread::scope(|scope| {
        let handles: Vec<_> = numbers
            .chunks(chunk)
            .map(|part| scope.spawn(move || part.iter().sum::<u64>()))
            .collect();
        handles.into_iter().map(|h| h.join().unwrap()).sum()
    })
}

fn sum_rayon(numbers: &[u64]) -> u64 {
    numbers.par_iter().sum()
}

#[tokio::main]
async fn main() {
    let numbers: Vec<u64> = (1..=1_000_000).collect();
    let a = sum_sequential(&numbers);
    let b = sum_scoped_threads(&numbers, 4);
    let c = sum_rayon(&numbers);
    // spawn_blocking needs owned data ('static), so the Vec is moved in.
    let d = tokio::task::spawn_blocking(move || sum_rayon(&numbers))
        .await
        .unwrap();
    println!("sequential {a}, scoped {b}, rayon {c}, rayon in spawn_blocking {d}");
    assert!(a == b && b == c && c == d);
}
```

```text
sequential 500000500000, scoped 500000500000, rayon 500000500000, rayon in spawn_blocking 500000500000
```

Почему это работает: сложению безразличен порядок, поэтому любое разбиение даёт ту же сумму. Scoped-потоки заимствуют данные, и их дожидаются в конце `thread::scope`; rayon сам делит работу и перераспределяет её между своими потоками (кража задач); `spawn_blocking` держит тяжёлую для CPU работу подальше от рабочих потоков Tokio (Урок 14.13).

</details>

### Задание 4 — Обобщённая повторная попытка с остановленными часами (Этап 14)

В `src/lib.rs` напишите

```rust
pub async fn retry<T, E, F, Fut>(max_attempts: u32, backoff: Duration, operation: F) -> Result<T, E>
```

которая вызывает `operation(attempt)` (попытка 1, 2, …), пока та не вернёт `Ok`, но не больше `max_attempts` раз, и между попытками ждёт `backoff`, затем вдвое дольше и так далее. Если все попытки неудачны, она возвращает последнюю ошибку. Напишите два `#[tokio::test(start_paused = true)]`: операция, которая дважды падает, при задержке 100 мс завершается успехом ровно через 300 мс; операция, которая всегда падает, возвращает ошибку попытки 3, когда `max_attempts` равно 3.

<details>
<summary>Подсказка</summary>

Ограничения такие: `F: FnMut(u32) -> Fut` и `Fut: Future<Output = Result<T, E>>`: `operation` вызывается заново на каждую попытку и каждый раз возвращает новый future. В тестах замыкание может выглядеть как `|attempt| async move { … }`.

</details>

<details>
<summary>Ответ</summary>

```rust
//! Stage 3 checkpoint tasks.

use std::future::Future;
use std::time::Duration;

/// Calls `operation(attempt)` until it succeeds, at most `max_attempts` times.
/// Waits `backoff`, then twice as long, … between attempts.
pub async fn retry<T, E, F, Fut>(
    max_attempts: u32,
    backoff: Duration,
    mut operation: F,
) -> Result<T, E>
where
    F: FnMut(u32) -> Fut,
    Fut: Future<Output = Result<T, E>>,
{
    let mut delay = backoff;
    let mut attempt = 1;
    loop {
        match operation(attempt).await {
            Ok(value) => return Ok(value),
            Err(error) if attempt >= max_attempts => return Err(error),
            Err(_) => {
                tokio::time::sleep(delay).await;
                delay *= 2;
                attempt += 1;
            }
        }
    }
}

#[cfg(test)]
mod tests {
    use super::*;
    use tokio::time::Instant;

    #[tokio::test(start_paused = true)]
    async fn retry_succeeds_on_the_third_attempt() {
        let start = Instant::now();
        let result: Result<&str, String> =
            retry(5, Duration::from_millis(100), |attempt| async move {
                if attempt < 3 {
                    Err(format!("attempt {attempt} failed"))
                } else {
                    Ok("done")
                }
            })
            .await;
        assert_eq!(result, Ok("done"));
        assert_eq!(start.elapsed(), Duration::from_millis(300)); // 100 + 200
    }

    #[tokio::test(start_paused = true)]
    async fn retry_returns_the_last_error() {
        let result: Result<(), String> = retry(3, Duration::from_secs(1), |attempt| async move {
            Err(format!("failure {attempt}"))
        })
        .await;
        assert_eq!(result, Err("failure 3".to_string()));
    }
}
```

`cargo test --lib` показывает `test result: ok. 2 passed; 0 failed`. Почему это работает: каждый вызов `operation` создаёт новый future, поэтому неудачная попытка ничего после себя не оставляет. Остановленные часы делают 100 мс + 200 мс ожидания бесплатными по реальному времени и точными для `assert_eq!` (Урок 14.14). Это часть вашей очереди заданий, отвечающая за повторные попытки, вынесенная в переиспользуемую функцию.

</details>
