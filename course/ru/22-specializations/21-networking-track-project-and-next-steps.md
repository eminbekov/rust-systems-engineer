# Урок 22.21 — Трек сетей: проект и следующие шаги

> **Этап 22 — Специализации** · Урок 21 из 30 · ⏱ около 20 часов (10 занятий)

## Что вы узнаете

- Как соединить части направления (параметры сокетов, разбор без копирования, ограничения, балансировку нагрузки) в один работающий обратный HTTP/1.1-прокси.
- Как обрабатывать сбои, которые прокси встречает каждый день: неверные запросы, слишком большие заголовочные части, мёртвые бэкенды, медленные бэкенды.
- Как тестировать прокси сквозными тестами внутри одного процесса с фейковыми бэкендами.
- Куда двигаться дальше в сетях: книги, документация, проекты с открытым кодом и сообщества.

## Новые слова

| Слово | Значение |
|---|---|
| **код статуса** (status code) | Трёхзначное число в начале HTTP-ответа (HTTP — Hypertext Transfer Protocol, протокол передачи гипертекста): `200` — OK, `400` — неверный запрос, `502` — ошибка шлюза и так далее. |
| **`502 Bad Gateway`** | Статус, который прокси возвращает, если не смог получить правильный ответ ни от одного бэкенда. |
| **`504 Gateway Timeout`** | Статус, который прокси возвращает, если бэкенд не ответил вовремя. |
| **`431 Request Header Fields Too Large`** | Статус для заголовочной части запроса, которая больше, чем принимает сервер. |
| **переключение при отказе** (failover) | Автоматическая попытка обратиться к другому бэкенду, когда выбранный не отвечает. |
| **пассивная проверка работоспособности** (passive health checking) | Когда о том, что бэкенд не работает, узнают по неудачным настоящим запросам, а не по отдельным тестовым соединениям (активные проверки, Урок 22.20). |
| **журнал доступа** (access log) | Одна строка на запрос: метод, путь, статус, бэкенд, длительность. |
| **тест внутри процесса** (in-process test) | Тест, который запускает сервер внутри тестовой программы (на порту 0), а не отдельным процессом. |

**Другие сокращения в этом уроке:** ВМ (виртуальная машина; Linux-ВМ `dev`), CLI (command-line interface, интерфейс
командной строки: как запускается программа и какие аргументы принимает), TCP (Transmission Control Protocol, протокол
управления передачей), TLS (Transport Layer Security, протокол защиты транспортного уровня — слой шифрования HTTPS) и
URL (Uniform Resource Locator, веб-адрес).

## 1. Проект на одной картинке

```text
  curl / load generator
          │  HTTP/1.1 (keep-alive)
          ▼
 ┌────────────────────────────── p22-relay ───────────────────────────────┐
 │ listener (TCP_NODELAY, connection cap)                                 │
 │   └─ one task per client connection                                    │
 │        1. read_head (zero-copy parser, MAX_HEAD)  ── bad → 400 / 431   │
 │        2. read the body (Content-Length)                               │
 │        3. /__relay/stats? answer it here                               │
 │        4. rewrite the head (X-Forwarded-For, drop Connection)          │
 │        5. pick a backend: round robin, failover ── none → 502          │
 │        6. send, read the response head + body  ── too slow → 504      │
 │        7. add X-Relay, write to the client, log one line               │
 └────────────────────────────────────────────────────────────────────────┘
          │                         │
          ▼                         ▼
   backend 127.0.0.1:8001     backend 127.0.0.1:8002
```

Урок 23.4 (вариант итогового проекта 2) требует гораздо большего, высокопроизводительного обратного
прокси. Этот проект — маленькая честная версия: каждая часть ваша, и каждый случай сбоя обработан
намеренно.

## Проект

### Что вы создадите

`p22-relay` — обратный HTTP/1.1-прокси на Tokio из частей этого направления. Он пересылает запросы
списку бэкендов по кругу (round robin), переключается при отказе бэкенда, соблюдает ограничения,
сообщает простую статистику и пишет журнал доступа.

```bash
cd ~/projects/rust
cargo new code/p22-relay
cd code/p22-relay
cargo add tokio@1 --features full
cargo add bytes@1
cargo add socket2@0.6
cargo add clap@4 --features derive
git init   # skip if code/ is already one repository
```

Скопируйте `parse.rs` из `code/p22-net/src/` в `src/parse.rs`, а `backend.rs` из
`code/p22-proxy/src/bin/` в `src/bin/backend.rs`.

### Контракт

**Командная строка:**

```text
Usage: p22-relay [OPTIONS] --backend <BACKENDS>

Options:
      --listen <LISTEN>              Address to listen on [default: 127.0.0.1:7400]
      --backend <BACKENDS>           A backend address; repeat for several backends
      --max-conns <MAX_CONNS>        Maximum number of client connections served at the same time [default: 1000]
      --timeout-secs <TIMEOUT_SECS>  Seconds to wait for a backend's answer [default: 5]
  -h, --help                         Print help
```

**API библиотеки** (в `src/lib.rs`, чтобы тесты могли запускать прокси внутри процесса):

```rust
pub struct Config {
    pub backends: Vec<std::net::SocketAddr>,
    pub max_conns: usize,
    pub upstream_timeout: std::time::Duration,
}

pub async fn run(listener: tokio::net::TcpListener, config: Config) -> std::io::Result<()>;
```

**Поведение:**

1. Запросы — HTTP/1.1 с необязательным телом, длина которого задана `Content-Length`. Клиентские
   соединения постоянные (keep-alive): одно соединение может нести много запросов один за другим.
2. Прокси отправляет каждый запрос следующему бэкенду по кругу. Он заменяет любой заголовок
   `X-Forwarded-For` IP-адресом клиента (IP — Internet Protocol, межсетевой протокол) и удаляет
   заголовок `Connection`.
3. Каждый ответ клиенту содержит заголовок `X-Relay: p22-relay`.
4. Если бэкенд отказывает в соединении (или не принимает его за 1 секунду), прокси пробует следующий.
   Если не работает ни один: `502 Bad Gateway` с телом `no backend available\n`, затем закрытие.
5. Если выбранный бэкенд не прислал полный ответ за `--timeout-secs`: `504 Gateway Timeout` с телом
   `backend timed out\n`, затем закрытие.
6. Заголовочная часть запроса больше 8 КиБ (8192 байта): `431 Request Header Fields Too Large`, тело
   `request head too large\n`. Любой другой неразбираемый запрос: `400 Bad Request`, тело
   `bad request\n`. Оба закрывают соединение.
7. На `GET /__relay/stats` отвечает сам прокси: `200` с телом `requests=<N> errors=<M>\n` (все
   увиденные запросы и запросы, на которые ответили 400, 431, 502 или 504).
8. Одновременно обслуживается не больше `--max-conns` клиентских соединений; лишние ждут (обратное
   давление, Урок 22.18).
9. Одна строка журнала доступа на запрос в стандартный вывод:
   `<method> <path> <status> <backend or -> <ms>ms`.

**Вне рамок проекта** (дополнительные цели): тела с порционной передачей
(`Transfer-Encoding: chunked`), HTTP/2, TLS, пул соединений с бэкендами.

### Пошаговый план

#### M1 — Каркас: слушать и вежливо отказывать

**Цель:** командная строка из контракта, слушающий сокет, цикл приёма с одной задачей на соединение и
ответ `502` на каждый запрос (пересылки пока нет).

**Указания:** используйте `clap` с `#[derive(Parser)]` (Урок 05.11); повторяющиеся флаги `--backend`
собираются в `Vec<SocketAddr>` через `#[arg(long = "backend", required = true)]`. Поместите `Config` и
`run` в `src/lib.rs`, а в `main.rs` оставьте только разбор аргументов и вызов `run`. Задавайте
`TCP_NODELAY` на принятых соединениях (Урок 22.18). Для чтения каждой заголовочной части запроса
используйте `read_head` из Урока 22.19.

<details>
<summary>Подсказка</summary>

Напишите вспомогательную функцию `fn simple(status: &str, body: &str) -> String`, которая строит
полный ответ с `Content-Length`, `Connection: close` и `X-Relay: p22-relay`. Она пригодится для каждого
статуса ошибки.

</details>

**Готово, когда:**

```bash
cargo run -- --backend 127.0.0.1:8001     # in terminal 1
curl -si http://127.0.0.1:7400/hello      # in terminal 2
```

```text
HTTP/1.1 502 Bad Gateway
Content-Length: 21
Connection: close
X-Relay: p22-relay

no backend available
```

Коммит: `git commit -am "M1: listener and 502 skeleton"`.

#### M2 — Переслать один запрос

**Цель:** переслать запрос первому бэкенду и скопировать ответ обратно.

**Указания:** подключитесь к бэкенду через `TcpStream::connect`. Напишите новую заголовочную часть
запроса: строку запроса, все заголовки, кроме `X-Forwarded-For` и `Connection`, затем
`X-Forwarded-For: <client ip>` и пустую строку. Затем прочитайте ответ: его заголовочная часть
заканчивается на `\r\n\r\n`; код статуса — три цифры после `HTTP/1.1 `; длина тела берётся из
`Content-Length`. Вставьте `X-Relay: p22-relay` прямо перед пустой строкой заголовочной части ответа.

<details>
<summary>Подсказка</summary>

Читайте ответ в `BytesMut`, пока не найдёте `\r\n\r\n`, отрежьте заголовочную часть через `split_to`,
затем читайте, пока в буфере не будет `Content-Length` байтов. Соберите ответ клиенту в один буфер и
отправьте одним `write_all` (вспомните урок про 40 мс).

</details>

**Готово, когда:** при запущенном `cargo run --bin backend -- 8001`

```bash
cargo run -- --backend 127.0.0.1:8001
curl -si http://127.0.0.1:7400/hello
```

```text
HTTP/1.1 200 OK
Content-Length: 43
Content-Type: text/plain
X-Relay: p22-relay

hello from backend 8001 (client 127.0.0.1)
```

а relay печатает `GET /hello 200 127.0.0.1:8001 0ms`. Коммит.

#### M3 — Постоянные соединения и тела

**Цель:** обслуживать много запросов в одном клиентском соединении и пересылать тела запросов.

**Указания:** сделайте цикл в задаче соединения: после одного ответа разбирайте следующую
заголовочную часть из того же буфера (она может уже лежать там, Урок 22.19). После заголовочной части
прочитайте ровно `Content-Length` байтов тела (0, если заголовка нет) и отправьте их после
переписанной заголовочной части.

<details>
<summary>Подсказка</summary>

`curl` переиспользует одно соединение, если дать ему несколько URL в одной команде. Тогда журнал
доступа показывает два запроса, а `curl` печатает оба тела.

</details>

**Готово, когда:**

```bash
cargo run -- --backend 127.0.0.1:8001
curl -s http://127.0.0.1:7400/a http://127.0.0.1:7400/b
```

```text
hello from backend 8001 (client 127.0.0.1)
hello from backend 8001 (client 127.0.0.1)
```

а журнал доступа показывает `GET /a ...` и `GET /b ...` от одной команды `curl`. Коммит.

#### M4 — Распределение по кругу и переключение при отказе

**Цель:** распределять запросы по всем бэкендам и пропускать неработающие.

**Указания:** храните следующий индекс в `AtomicUsize`, общем для всех соединений (`fetch_add`, затем
`% backends.len()`). Если `connect` не удался или занял больше секунды (`tokio::time::timeout`),
пробуйте следующий бэкенд, не больше одного раза на бэкенд. Если не удались все, ответьте `502` и
посчитайте ошибку.

<details>
<summary>Подсказка</summary>

Вынесите цикл по бэкендам в отдельную
`async fn forward(...) -> std::io::Result<(SocketAddr, u16, Bytes)>`, которая возвращает бэкенд, статус
и полный ответ. Тогда задача соединения только решает, какой ответ отправить.

</details>

**Готово, когда:** при запущенных бэкендах 8001 и 8002 и только что запущенном relay

```bash
cargo run -- --backend 127.0.0.1:8001 --backend 127.0.0.1:8002
for i in 1 2 3 4; do curl -s http://127.0.0.1:7400/; done
```

```text
hello from backend 8001 (client 127.0.0.1)
hello from backend 8002 (client 127.0.0.1)
hello from backend 8001 (client 127.0.0.1)
hello from backend 8002 (client 127.0.0.1)
```

Остановите бэкенд 8002 (Ctrl+C) и снова запустите цикл: все четыре ответа приходят от 8001 со статусом
200. Остановите и 8001: `curl -si http://127.0.0.1:7400/` печатает ответ `502` из M1. Коммит.

#### M5 — Ограничения, тайм-ауты и статистика

**Цель:** пункты 5–8 контракта.

**Указания:** оберните весь обмен с бэкендом (`forward`) в
`tokio::time::timeout(config.upstream_timeout, ...)`. Сопоставьте `ParseError::TooLarge` статусу `431`, а
остальные ошибки разбора — `400`. Считайте запросы и ошибки в двух `AtomicU64` внутри общего состояния
в `Arc`. Добавьте в цикл приёма `Semaphore` из упражнения 3 Урока 22.18.

<details>
<summary>Подсказка</summary>

«Бэкенд», который принимает соединения и никогда не отвечает: `sleep 60 | nc -l 8009` (`sleep`
держит вход `nc` открытым, поэтому тот не закрывает соединение). Слишком большая заголовочная часть:
`python3 -c "print('GET / HTTP/1.1\r\nX-Big: ' + 'a'*9000 + '\r\n\r\n', end='')" | nc 127.0.0.1 7400`.
Убедитесь, что 431 возвращается и тогда, когда вся большая заголовочная часть приходит за одно чтение.

</details>

**Готово, когда:** каждая из этих команд даёт показанный результат.

```bash
printf 'GARBAGE\r\n\r\n' | nc 127.0.0.1 7400
```

```text
HTTP/1.1 400 Bad Request
Content-Length: 12
Connection: close
X-Relay: p22-relay

bad request
```

```bash
python3 -c "print('GET / HTTP/1.1\r\nX-Big: ' + 'a'*9000 + '\r\n\r\n', end='')" | nc 127.0.0.1 7400 | head -1
```

```text
HTTP/1.1 431 Request Header Fields Too Large
```

При запущенном в другом терминале `sleep 60 | nc -l 8009`:

```bash
cargo run -- --listen 127.0.0.1:7401 --backend 127.0.0.1:8009 --timeout-secs 2
curl -si http://127.0.0.1:7401/slow
```

```text
HTTP/1.1 504 Gateway Timeout
Content-Length: 18
Connection: close
X-Relay: p22-relay

backend timed out
```

Команда `curl` завершается примерно через 2 секунды, а relay пишет в журнал `GET /slow 504 - 2002ms`.
`curl -s http://127.0.0.1:7400/__relay/stats` печатает строку вроде `requests=13 errors=3`.
Наконец, запустите relay с `--max-conns 1`, удерживайте одно соединение открытым через
`sleep 5 | nc 127.0.0.1 7400` и выполните `curl -s --max-time 2 http://127.0.0.1:7400/`: он сдаётся с
кодом возврата 28 (тайм-аут), потому что единственное место занято. После закрытия соединения `nc` та
же команда `curl` проходит успешно. Коммит.


### Дополнительные цели

- **Пул соединений с бэкендами:** храните простаивающие соединения с бэкендами в пуле для каждого
  бэкенда и переиспользуйте их. Измерьте разницу нагрузочным тестом.
- **Порционные тела:** поддержите `Transfer-Encoding: chunked` в обоих направлениях (RFC 9112,
  раздел 7).
- **Режим «поток на ядро»:** флаг `--workers N`, который запускает N потоков со слушающими сокетами
  `SO_REUSEPORT` и рантаймами текущего потока (Урок 22.18). Сравните с рантаймом по умолчанию.
- **Активные проверки работоспособности:** проверяйте каждый бэкенд раз в секунду в фоновой задаче и
  пропускайте мёртвые бэкенды до того, как запрос завершится ошибкой.
- **Корректное завершение:** по Ctrl+C перестаньте принимать соединения, завершите открытые запросы и
  выйдите (Урок 14.14).
- **Фаззинг пути запроса** через `cargo fuzz` (Урок 09.8): подавайте случайные байты в обработчик
  соединения через `tokio::io::duplex`.

## Частые ошибки

**Читать ответ, пока бэкенд не закроет соединение.** Бэкенды держат соединения открытыми
(keep-alive), поэтому «читать до конца файла» ждёт вечно. Всегда используйте `Content-Length` (или, в
дополнительной цели, порционную передачу), чтобы знать, где кончается ответ.

**Забыть про байты, которые уже лежат в буфере.** После одного запроса следующий (или его часть) уже
может лежать в буфере клиента. Разбирайте до того, как читать снова, иначе запросы, пришедшие
конвейером, зависнут (Урок 22.19, упражнение 3).

**Держать разрешение на соединение слишком долго или слишком мало.** Разрешение `Semaphore` должно
жить ровно столько, сколько клиентское соединение: переместите его в задачу соединения. Если удалить
его сразу после `accept`, лимит выключится; если держать его в цикле приёма, сервер заблокируется после
первого соединения.

**Писать в журнал тело или секретные заголовки.** Журнал доступа не должен содержать тела запросов,
заголовки `Authorization` или cookie (Урок 10.8). Записывайте только метод, путь, статус, бэкенд и
длительность.

## Вопросы для самопроверки

1. Почему прокси должен разобрать следующий запрос из буфера до того, как снова читать из сокета?

<details>
<summary>Ответ</summary>

Клиент мог отправить несколько запросов сразу (конвейером), поэтому следующий может уже лежать в
буфере. Если прокси сначала ждёт чтения, он ждёт байтов, которые никогда не придут, а клиент ждёт
ответа: зависают оба.

</details>

2. Какие коды статуса возвращает `p22-relay` для: запроса, который нельзя разобрать, заголовочной части
   в 9000 байтов, отсутствия доступного бэкенда, бэкенда, который никогда не отвечает?

<details>
<summary>Ответ</summary>

`400 Bad Request`, `431 Request Header Fields Too Large`, `502 Bad Gateway`, `504 Gateway Timeout`.

</details>

3. Чем переключение при отказе в M4 отличается от проверок работоспособности из Урока 22.20?

<details>
<summary>Ответ</summary>

Переключение при отказе пассивное: прокси замечает мёртвый бэкенд, только когда настоящий запрос не
смог подключиться, и тогда пробует следующий. Активные проверки тестируют каждый бэкенд в фоне,
поэтому мёртвый бэкенд пропускается ещё до того, как к нему обратится какой-либо запрос.

</details>

4. Почему `run` принимает `TcpListener`, а не адрес?

<details>
<summary>Ответ</summary>

Тест может привязать слушающий сокет к порту `0`, прочитать настоящий порт через `local_addr()` и
затем запустить прокси. С адресом тесту понадобился бы фиксированный свободный порт, из-за чего тесты
сталкиваются и случайно падают.

</details>

## Итоги

- Обратный прокси — это цикл маленьких чётко определённых шагов: прочитать заголовочную часть,
  прочитать тело, выбрать бэкенд, переслать, прочитать ответ, ответить, записать в журнал.
- Большая часть кода настоящего прокси посвящена сбоям: неверный ввод (400), слишком большой ввод (431),
  нет бэкенда (502), медленный бэкенд (504), слишком много клиентов (обратное давление).
- Держите `run` в библиотеке, чтобы тесты могли запускать прокси внутри процесса на порту 0 с
  фейковыми бэкендами.
- Измеряйте до и после каждой идеи по производительности; сравнивайте с прямым соединением и с
  прокси для продакшена, например Pingora.
- Дальше: читайте hyper, Pingora и Tokio, следите за RFC и сделайте первый небольшой вклад.
