# Урок 15.1 — Как работает интернет: уровни и пакеты

> **Этап 15 — Сети** · Урок 1 из 16 · ⏱ около 135 минут

## Что вы узнаете

- Почему данные идут по сети множеством маленьких независимых **пакетов**.
- Четыре уровня интернета (канальный, сетевой, транспортный, прикладной) и за что отвечает каждый.
- Как работает **инкапсуляция**: каждый уровень заворачивает данные уровня выше в свой заголовок.
- Как захватывать настоящие пакеты с помощью `tcpdump` в Linux-контейнере и читать их байт за байтом.
- Как разобрать заголовок IPv4 маленькой программой на Rust.

## Новые слова

| Слово | Значение |
|---|---|
| **сеть** (network) | Компьютеры, соединённые так, что могут передавать друг другу данные. **Интернет** — это сеть сетей. |
| **протокол** (protocol) | Набор правил, которым следуют обе стороны: какие байты отправлять, в каком порядке и что они означают. |
| **пакет** (packet) | Небольшой кусок данных (обычно не больше примерно 1500 байт) с заголовком, который говорит, куда его доставить. |
| **заголовок** (header) | Байты в начале пакета с информацией для одного уровня: адреса, длины, флаги. |
| **полезная нагрузка** (payload) | Данные, которые несёт заголовок: всё, что идёт после него. |
| **уровень** (layer) | Одна ступень устройства сети. Каждый уровень решает одну задачу и пользуется уровнем ниже. |
| **инкапсуляция** (encapsulation) | Заворачивание: каждый уровень кладёт данные уровня выше внутрь своего заголовка, как письмо в конверт. |
| **IP** (Internet Protocol, межсетевой протокол) | Протокол, который доставляет пакеты от одного компьютера к другому через множество сетей. Используются версии 4 (IPv4) и 6 (IPv6). |
| **IP-адрес** (IP address) | Число, которое обозначает сетевой интерфейс компьютера, например `127.0.0.1`. |
| **маршрутизатор** (router) | Устройство, которое принимает пакеты и пересылает каждый в сторону его получателя. |
| **TCP** (Transmission Control Protocol, протокол управления передачей) | Протокол поверх IP, который даёт программам надёжный поток байтов. Его объясняет Урок 15.3. |
| **UDP** (User Datagram Protocol, протокол пользовательских датаграмм) | Более простой протокол поверх IP, который отправляет отдельные сообщения без гарантий. Урок 15.3. |
| **порт** (port) | Число от 0 до 65535, которое говорит, какой программе на компьютере предназначен пакет, например 80 для веб-сервера. |
| **HTTP** (HyperText Transfer Protocol, протокол передачи гипертекста) | Протокол веба. Вы встречали его в Уроке 06.11. |
| **DNS** (Domain Name System, система доменных имён) | Система, которая превращает имена вроде `example.com` в IP-адреса. Урок 15.10. |
| **Ethernet** | Самая распространённая технология канального уровня для кабелей. Wi-Fi работает почти так же, только по радио. |
| **MAC-адрес** (Media Access Control address, адрес управления доступом к среде) | Аппаратный адрес сетевого интерфейса длиной 6 байт, записывается как `42:9a:88:e7:5c:d9`. Используется только внутри одной локальной сети. |
| **кадр / пакет / сегмент / датаграмма** (frame / packet / segment / datagram) | Названия одной порции данных на разных уровнях: *кадр* Ethernet, *пакет* IP, *сегмент* TCP, *датаграмма* UDP. |
| **MTU** (Maximum Transmission Unit, максимальный размер передаваемого блока) | Самый большой пакет, который может передать один канал. Для Ethernet это 1500 байт. |
| **сетевой интерфейс** (network interface) | Точка подключения компьютера к сети: сетевая карта, Wi-Fi или виртуальный интерфейс `lo`. |
| **сокет** (socket) | Объект, который программа получает от операционной системы, чтобы отправлять и принимать данные по сети. Подробно его объясняет Урок 15.4. |
| **loopback** (петлевой интерфейс) | Виртуальный интерфейс (`lo`) с адресом `127.0.0.1`. Пакеты, отправленные на него, никогда не покидают компьютер. |
| **TTL** (Time To Live, время жизни) | Счётчик в заголовке IP. Каждый маршрутизатор уменьшает его на единицу; при нуле пакет выбрасывается, поэтому потерявшийся пакет не может кружить вечно. |
| **контрольная сумма** (checksum) | Небольшое число, вычисленное по данным и отправленное вместе с ними, чтобы получатель заметил повреждённые байты. |
| **capability** (Linux, привилегия) | Отдельная часть власти root, которую процесс может получить сам по себе. `NET_RAW` разрешает читать и отправлять «сырые» пакеты; `NET_ADMIN` разрешает настраивать сетевые интерфейсы. |
| **захват пакетов** (packet capture) | Запись пакетов, проходящих через интерфейс. `tcpdump` — классический инструмент командной строки для этого. |
| **модель OSI** (Open Systems Interconnection model, модель взаимодействия открытых систем) | Более старое описание сетей из семи уровней. Её номера уровней используются до сих пор: «L4» означает транспортный уровень, «L7» — прикладной. |
| **SSH** (Secure Shell, защищённая оболочка) | Протокол для входа на другой компьютер по сети и выполнения там команд, с шифрованием. |
| **TLS** (Transport Layer Security, протокол защиты транспортного уровня) и **HTTPS** (HTTP Secure, защищённый HTTP) | TLS шифрует соединение, чтобы никто по пути не мог его прочитать или изменить (Уроки 10.11 и 15.12); HTTPS — это HTTP, передаваемый внутри TLS. |
| **ICMP** (Internet Control Message Protocol, протокол межсетевых управляющих сообщений) | Небольшие служебные сообщения и сообщения об ошибках межсетевого уровня, например «этот хост недоступен»; их использует `ping`. |
| **QUIC** | Более новый транспортный протокол поверх UDP, на котором работает HTTP/3 (Урок 15.13). Название не является сокращением. |
| **ВМ** (VM, virtual machine, виртуальная машина) | Целый компьютер, который имитирует программа; здесь — Linux-ВМ `dev` из Этапа 11. |
| **ASCII** (American Standard Code for Information Interchange, американский стандартный код для обмена информацией) | Классическая таблица из 128 символов, в которой, например, `h` — это байт `0x68` (Урок 12.5). |
| **МБ** (MB, megabyte, мегабайт) | Около миллиона байтов. |

## 1. Данные путешествуют множеством маленьких писем

Представьте, что вы хотите отправить другу в другой город целую книгу, но почта принимает только
открытки. Вы режете книгу на маленькие куски, пишете каждый кусок на открытке, нумеруете открытки и
пишете адрес на каждой. Открытки едут отдельно. Одни проходят через одно сортировочное отделение,
другие — через другое. Друг собирает их и раскладывает страницы по порядку.

Интернет работает так же:

- Данные режутся на **пакеты**, каждый не больше примерно 1500 байт.
- У каждого пакета есть **заголовок** с адресом получателя, как адрес на открытке.
- **Маршрутизаторы** — это сортировочные отделения. Маршрутизатор смотрит только на адрес получателя
  и отправляет пакет на один шаг ближе. Ни один маршрутизатор не знает весь путь.
- Пакеты могут теряться, дублироваться или приходить в другом порядке. Если программе это важно,
  исправлять это должен кто-то на концах пути.

Почему не отправить всё одним куском? Потому что сеть общая. Если одна большая передача заняла бы
кабель на минуту, все остальные ждали бы. Маленькие пакеты позволяют миллионам разговоров делить
одни и те же кабели, а потеря пакета стоит лишь небольшой повторной отправки.

## 2. Четыре уровня, у каждого одна задача

Передать данные через весь мир — большая задача, поэтому её делят на задачи поменьше. Каждый
**уровень** решает одну задачу и доверяет уровню ниже решить свою.

| Уровень | Его задача | Какие адреса использует | Примеры | Номер в OSI |
|---|---|---|---|---|
| **Прикладной** (application) | Что данные *означают* | имена, пути (`/index.html`) | HTTP, DNS, SSH, TLS | L7 |
| **Транспортный** (transport) | Какой *программе*; надёжность, если нужна | порты (`80`, `9000`) | TCP, UDP, QUIC | L4 |
| **Сетевой** (internet) | Какому *компьютеру*, через множество сетей | IP-адреса (`104.20.23.154`) | IPv4, IPv6, ICMP | L3 |
| **Канальный** (link) | *Следующий шаг* внутри одной локальной сети | MAC-адреса (`42:9a:88:e7:5c:d9`) | Ethernet, Wi-Fi | L2 (и L1, сам кабель) |

Такая четырёхуровневая картина называется **моделью TCP/IP**. В модели OSI семь уровней; вам нужны
только её номера, потому что инженеры говорят «балансировщик L4» (он смотрит на IP-адреса и порты)
или «прокси L7» (он понимает HTTP). Балансировщик нагрузки L4 вы напишете в Уроке 15.15.

Главная мысль: **каждый уровень разговаривает только с тем же уровнем на другой стороне**. Ваш код
HTTP разговаривает с кодом HTTP сервера. Ему всё равно, шли байты по Wi-Fi, по кабелю или через
петлевой интерфейс. А маршрутизатор посередине читает только канальный и сетевой заголовки; в ваш
HTTP-запрос он никогда не заглядывает.

```text
 your computer                                                  server
┌──────────────┐                                           ┌──────────────┐
│ application  │ ◄─────────── HTTP request/response ─────► │ application  │
│ transport    │ ◄─────────── TCP segments ──────────────► │ transport    │
│ internet     │ ◄── IP ──► ┌────────┐ ◄── IP ──► ┌──────┐ │ internet     │
│ link         │ ◄─ Wi-Fi ─►│ router │ ◄─ fibre ─►│router│►│ link         │
└──────────────┘            └────────┘            └──────┘ └──────────────┘
                        routers use only the two lowest layers
```

## 3. Инкапсуляция: конверты в конвертах

Когда ваша программа отправляет `hello\n` по TCP, каждый уровень добавляет свой заголовок перед
данными:

```text
                                          ┌──────────┐
 application data                         │ hello\n  │   6 bytes
                                          └──────────┘
                              ┌──────────┐┌──────────┐
 TCP segment                  │TCP header││ hello\n  │   32 + 6 bytes
                              └──────────┘└──────────┘
                  ┌──────────┐┌──────────┐┌──────────┐
 IP packet        │IP header ││TCP header││ hello\n  │   20 + 32 + 6 = 58 bytes
                  └──────────┘└──────────┘└──────────┘
      ┌──────────┐┌──────────┐┌──────────┐┌──────────┐
 frame│ Ethernet ││IP header ││TCP header││ hello\n  │   14 + 58 = 72 bytes
      └──────────┘└──────────┘└──────────┘└──────────┘
```

На принимающей стороне уровни работают в обратном порядке. Сетевая карта проверяет заголовок
Ethernet и снимает его, операционная система проверяет заголовок IP и снимает его, затем заголовок
TCP, и ваша программа получает просто `hello\n`.

Обратите внимание на цену: 6 байтов данных потребовали 66 байтов заголовков. Поэтому отправлять по
одному байту расточительно, и поэтому важен **MTU**. При MTU Ethernet в 1500 байт один IP-пакет
может нести не больше 1500 − 20 − 20 = 1460 байт данных TCP (с самым маленьким заголовком TCP).
Программа, которая отправляет 1 МБ, порождает примерно 720 пакетов.

## 4. Смотрим на настоящие пакеты с tcpdump

`tcpdump` записывает пакеты на интерфейсе и печатает их. Ему нужно право читать *весь* трафик,
поэтому он работает от root внутри контейнера с двумя привилегиями Linux (capabilities): `NET_RAW`
(открывать «сырые» сокеты) и `NET_ADMIN` (настраивать интерфейсы). Запустите контейнер из своего
образа:

```bash
docker run --rm -it --cap-add NET_RAW --cap-add NET_ADMIN p15-nettools bash
```

Внутри контейнера запустите крошечный сервер через `nc` (netcat), запустите `tcpdump` на петлевом
интерфейсе и отправьте серверу `hello`:

```bash
nc -l 127.0.0.1 9000 > /dev/null &
tcpdump -i lo -n -X -c 8 tcp port 9000 &
sleep 1
printf "hello\n" | nc -q 1 127.0.0.1 9000
```

**Что происходит:**

1. `nc -l 127.0.0.1 9000` слушает порт 9000 и выбрасывает всё, что получает (`> /dev/null`).
   `&` запускает его в фоне.
2. `tcpdump -i lo` захватывает пакеты на петлевом интерфейсе. `-n` печатает числа вместо имён. `-X`
   печатает каждый пакет в шестнадцатеричном виде и как текст. `-c 8` останавливается после 8
   пакетов. `tcp port 9000` — это *фильтр*: только TCP-пакеты к порту 9000 или от него.
3. Второй `nc` подключается к серверу, отправляет `hello\n`, ждёт одну секунду (`-q 1`) и закрывает
   соединение.

Разговор порождает 8 пакетов. Семь из них открывают и закрывают соединение (вы прочитаете их в
Уроке 15.3). Вот тот, который несёт наши данные (вывод сокращён до этого пакета):

```text
06:51:54.219945 IP 127.0.0.1.36932 > 127.0.0.1.9000: Flags [P.], seq 1:7, ack 1, win 64, options [nop,nop,TS val 2778587979 ecr 1523372706], length 6
	0x0000:  4500 003a 9332 4000 4006 a989 7f00 0001  E..:.2@.@.......
	0x0010:  7f00 0001 9044 2328 f1e7 d90f a4e3 8284  .....D#(........
	0x0020:  8018 0040 fe2e 0000 0101 080a a59d e34b  ...@...........K
	0x0030:  5acc d2a2 6865 6c6c 6f0a                 Z...hello.
```

Как это читать:

1. Первая строка — сводка tcpdump: время, `IP` (пакет IPv4), от `127.0.0.1` с порта `36932` к
   `127.0.0.1` на порт `9000`, и `length 6`: шесть байтов данных TCP. Клиентский порт `36932`
   выбрала операционная система; у вас он будет другим.
2. Остальные строки — байты пакета. `0x0000` — смещение первого байта строки. Каждая группа из
   четырёх шестнадцатеричных цифр — это два байта. Справа печатаемые байты показаны как текст.
3. Байты начинаются с заголовка IP (`45 00 ...`). На петлевом интерфейсе tcpdump не показывает
   заголовок Ethernet. Наше `hello.` в самом конце: `68 65 6c 6c 6f 0a` — это `h e l l o \n` в
   ASCII.

Теперь та же идея на настоящем интерфейсе контейнера, `eth0`, пока `curl` загружает публичную
веб-страницу. Параметр `-e` добавляет к каждой строке заголовок канального уровня (Ethernet):

```bash
tcpdump -i eth0 -n -e -c 3 tcp port 80 &
sleep 1
curl -s -o /dev/null http://example.com/
```

```text

06:52:07.268295 3a:71:10:41:e3:23 > 42:9a:88:e7:5c:d9, ethertype IPv4 (0x0800), length 74: 104.20.23.154.80 > 172.17.0.5.39170: Flags [S.], seq 943654894, ack 3088817597, win 65408, options [mss 65495,sackOK,TS val 183731092 ecr 1288958365,nop,wscale 7], length 0
06:52:07.268316 42:9a:88:e7:5c:d9 > 3a:71:10:41:e3:23, ethertype IPv4 (0x0800), length 66: 172.17.0.5.39170 > 104.20.23.154.80: Flags [.], ack 1, win 64, options [nop,nop,TS val 1288958462 ecr 183731092], length 0
```

В одной строке видны все уровни:

| Часть строки | Уровень | Значение |
|---|---|---|
| `42:9a:88:e7:5c:d9 > 3a:71:10:41:e3:23` | канальный | от MAC-адреса контейнера к MAC-адресу следующего шага (виртуального маршрутизатора Docker) |
| `ethertype IPv4 (0x0800)` | канальный | «полезная нагрузка этого кадра — пакет IPv4» |
| `172.17.0.5 > 104.20.23.154` | сетевой | от IP-адреса контейнера к IP-адресу веб-сервера |
| `.39170 > .80` | транспортный | со случайного клиентского порта на порт 80, порт HTTP |
| `Flags [S]` | транспортный | запрос на TCP-соединение (Урок 15.3) |

Посмотрите на отметки времени: ответ пришёл примерно через 97 мс после запроса. Столько времени
пакету понадобилось, чтобы дойти до сервера и вернуться. Ваши числа и адреса будут другими. Выйдите
из контейнера командой `exit`.

Если `tcpdump` ничего не печатает, вы, скорее всего, захватываете не тот интерфейс: трафик к
`127.0.0.1` идёт через `lo`, трафик в интернет — через `eth0`. `ip -brief addr` показывает список
интерфейсов, а `-i any` захватывает на всех сразу.

> 🔒 **Безопасность:** захват пакетов может содержать пароли, cookie и личные сообщения, отправленные
> без шифрования. Захватывайте только свой трафик на своих машинах и удаляйте файлы захвата, которые
> больше не нужны. Именно поэтому веб перешёл на HTTPS (Урок 10.11): с TLS захват показывает только
> зашифрованные байты.

## 5. Читаем заголовок IPv4 на Rust

Первые 20 байтов пакета выше — это заголовок IPv4. Его формат задан в RFC 791 (RFC — Request for
Comments, «запрос комментариев»: документы, которые определяют стандарты интернета):

```text
 byte:  0         1         2         3
      ┌────┬────┬─────────┬───────────────────┐
  0   │ver │IHL │  TOS    │   total length    │   45 00 | 00 3a
      ├────┴────┴─────────┼───┬───────────────┤
  4   │  identification   │flg│ fragment off. │   93 32 | 40 00
      ├─────────┬─────────┼───┴───────────────┤
  8   │   TTL   │protocol │  header checksum  │   40 06 | a9 89
      ├─────────┴─────────┴───────────────────┤
 12   │          source IP address            │   7f 00 00 01
      ├───────────────────────────────────────┤
 16   │        destination IP address         │   7f 00 00 01
      └───────────────────────────────────────┘
```

- `ver` (4 бита) — версия, 4. `IHL` (Internet Header Length, длина заголовка, 4 бита) — длина
  заголовка в 32-битных словах: 5 слов = 20 байтов.
- `total length` — размер всего пакета: заголовок плюс полезная нагрузка.
- `TOS` (Type of Service, тип обслуживания) может пометить пакет как срочный; `identification`,
  `flg` (флаги) и `fragment off.` (смещение фрагмента) нужны, когда пакет приходится делить на
  меньшие. Мы их пропускаем.
- `protocol` говорит, что лежит в полезной нагрузке: 6 — TCP, 17 — UDP, 1 — ICMP (Internet Control
  Message Protocol, протокол управляющих сообщений интернета, его использует `ping`).
- Многобайтовые числа передаются в порядке **big-endian** (старший байт первым). В сетях это
  называют **сетевым порядком байтов** (network byte order). Поэтому `00 3a` означает 0x003a = 58.

Сохраните эту программу как `src/bin/ipv4_header.rs`. В ней байты захваченного пакета:

```rust
use std::net::Ipv4Addr;

/// The bytes of one real packet, copied from the tcpdump output above.
const PACKET: [u8; 58] = [
    0x45, 0x00, 0x00, 0x3a, 0x93, 0x32, 0x40, 0x00, 0x40, 0x06, 0xa9, 0x89, 0x7f, 0x00, 0x00, 0x01,
    0x7f, 0x00, 0x00, 0x01, 0x90, 0x44, 0x23, 0x28, 0xf1, 0xe7, 0xd9, 0x0f, 0xa4, 0xe3, 0x82, 0x84,
    0x80, 0x18, 0x00, 0x40, 0xfe, 0x2e, 0x00, 0x00, 0x01, 0x01, 0x08, 0x0a, 0xa5, 0x9d, 0xe3, 0x4b,
    0x5a, 0xcc, 0xd2, 0xa2, 0x68, 0x65, 0x6c, 0x6c, 0x6f, 0x0a,
];

fn main() {
    let p = &PACKET;
    let version = p[0] >> 4;
    let header_len = (p[0] & 0x0f) as usize * 4;
    let total_len = u16::from_be_bytes([p[2], p[3]]);
    let ttl = p[8];
    let protocol = p[9];
    let src = Ipv4Addr::new(p[12], p[13], p[14], p[15]);
    let dst = Ipv4Addr::new(p[16], p[17], p[18], p[19]);

    println!("version:       {version}");
    println!("header length: {header_len} bytes");
    println!("total length:  {total_len} bytes");
    println!("TTL:           {ttl}");
    println!("protocol:      {protocol} (6 means TCP)");
    println!("source:        {src}");
    println!("destination:   {dst}");
    println!("IP payload:    {} bytes", p.len() - header_len);
}
```

**Что происходит:**

1. `PACKET` — константный массив с 58 байтами из шестнадцатеричного дампа, в том же порядке.
2. `p[0] >> 4` сдвигает первый байт вправо на четыре бита и оставляет старшую половину:
   `0x45 >> 4 = 4`.
3. `p[0] & 0x0f` оставляет младшие четыре бита, `5`. Поле считает 32-битные слова, поэтому умножаем
   на 4.
4. `u16::from_be_bytes([p[2], p[3]])` собирает 16-битное число из двух байтов в порядке big-endian.
5. `Ipv4Addr::new` из `std::net` строит адрес из четырёх байтов. Его `Display` печатает привычную
   запись через точки.
6. Полезная нагрузка — всё после заголовка: 58 − 20 = 38 байтов (заголовок TCP и наши данные).

Запустите командой `cargo run --bin ipv4_header`:

```text
version:       4
header length: 20 bytes
total length:  58 bytes
TTL:           64
protocol:      6 (6 means TCP)
source:        127.0.0.1
destination:   127.0.0.1
IP payload:    38 bytes
```

TTL равен 64 — обычное начальное значение в Linux. Пакет не проходил через маршрутизатор, поэтому
никто его не уменьшил.

> 🧪 **Тестирование:** захваченные пакеты — отличные тестовые данные. Один раз скопируйте байты
> настоящего пакета в тест, и ваш парсер навсегда проверяется на реальности, без сети. Это делает
> Упражнение 3.

## 6. Где живёт каждый уровень

Кто выполняет всю эту работу? Не ваша программа.

```text
 your program         │  application layer: you decide what the bytes mean
 ─────────────────────┼─────────────── socket API (Lesson 15.4) ──────────────
 operating system     │  transport (TCP, UDP) and internet (IP) layers
 kernel               │  routing table, checksums, resending lost packets
 ─────────────────────┼──────────────────────────────────────────────────────
 network card, driver │  link layer: Ethernet / Wi-Fi frames
```

TCP, UDP и IP реализует ядро. Ваша программа видит только верх: она просит у ядра **сокет** и
читает и пишет байты. `TcpStream` из Урока 06.11 — именно это. На этом этапе вы узнаете, что ядро
делает под сокетом (Уроки 15.2 и 15.3), как хорошо пользоваться сокетами (15.4–15.6) и как самому
проектировать прикладной уровень (15.7 и дальше).

## Частые ошибки

> ⚠️ **Частая ошибка: чтение сетевого числа как little-endian.** Процессор вашего Mac работает в
> порядке little-endian, а сетевые заголовки — в big-endian. С `u16::from_le_bytes([p[2], p[3]])`
> общая длина становится 14848 вместо 58. Сообщения об ошибке нет, просто неверное число. Для полей
> заголовков всегда используйте `from_be_bytes`.

> ⚠️ **Частая ошибка: поле длины заголовка как байты.** `IHL` считает 32-битные слова. Если забыть
> `* 4`, вы обрежете пакет на 5-м байте и прочитаете заголовок TCP не с того места. Помните также,
> что заголовок с опциями бывает длиннее 20 байтов: всегда используйте `IHL`, а не фиксированное `20`.

> ⚠️ **Частая ошибка: запуск tcpdump без нужного права.** В контейнере без привилегии `NET_RAW`
> (или без `sudo` в ВМ) вы получите:
>
> ```text
> tcpdump: lo: You don't have permission to perform this capture on that device
> (Attempt to create packet socket failed - CAP_NET_RAW may be required)
> ```
>
> Запускайте контейнер с `--cap-add NET_RAW --cap-add NET_ADMIN`, как показано выше.

### Упражнение 2 — Порты и данные из заголовка TCP (средне)

Напишите `src/bin/tcp_ports.rs`, который использует тот же `PACKET` и печатает порт отправителя,
порт получателя и данные. Заголовок TCP начинается сразу после заголовка IP. Его первые два байта —
порт отправителя, следующие два — порт получателя, а старшие четыре бита байта 12 — длина
заголовка TCP в 32-битных словах. Ожидаемый вывод:

```text
source port:      36932
destination port: 9000
TCP header:       32 bytes
data:             "hello\n"
```

<details>
<summary>Подсказка</summary>

Сделайте срез `let tcp = &PACKET[ip_header_len..];` и обращайтесь к нему по индексам. Длина
заголовка — `(tcp[12] >> 4) as usize * 4`. `String::from_utf8_lossy` превращает байты в текст.

</details>

<details>
<summary>Ответ</summary>

```rust
const PACKET: [u8; 58] = [
    0x45, 0x00, 0x00, 0x3a, 0x93, 0x32, 0x40, 0x00, 0x40, 0x06, 0xa9, 0x89, 0x7f, 0x00, 0x00, 0x01,
    0x7f, 0x00, 0x00, 0x01, 0x90, 0x44, 0x23, 0x28, 0xf1, 0xe7, 0xd9, 0x0f, 0xa4, 0xe3, 0x82, 0x84,
    0x80, 0x18, 0x00, 0x40, 0xfe, 0x2e, 0x00, 0x00, 0x01, 0x01, 0x08, 0x0a, 0xa5, 0x9d, 0xe3, 0x4b,
    0x5a, 0xcc, 0xd2, 0xa2, 0x68, 0x65, 0x6c, 0x6c, 0x6f, 0x0a,
];

fn main() {
    let ip_header_len = (PACKET[0] & 0x0f) as usize * 4;
    let tcp = &PACKET[ip_header_len..];
    let src_port = u16::from_be_bytes([tcp[0], tcp[1]]);
    let dst_port = u16::from_be_bytes([tcp[2], tcp[3]]);
    let tcp_header_len = (tcp[12] >> 4) as usize * 4;
    let data = &tcp[tcp_header_len..];
    println!("source port:      {src_port}");
    println!("destination port: {dst_port}");
    println!("TCP header:       {tcp_header_len} bytes");
    println!("data:             {:?}", String::from_utf8_lossy(data));
}
```

Почему это работает: инкапсуляция означает, что каждый заголовок просто идёт следом за предыдущим.
Зная длину заголовка IP, вы знаете, где начинается заголовок TCP; зная длину заголовка TCP — где
начинаются данные. Здесь заголовок TCP занимает 32 байта, потому что несёт 12 байтов опций (отметки
времени `TS val ... ecr ...` в строке tcpdump).

</details>

### Упражнение 3 — Парсер IPv4 с тестами (средне)

Напишите `src/bin/parse_ipv4.rs` со структурой `Ipv4Header` (длина заголовка, общая длина, TTL,
протокол, отправитель, получатель) и функцией
`fn parse_ipv4(bytes: &[u8]) -> Result<Ipv4Header, &'static str>`. Она должна отклонять вход короче
20 байтов, версию, отличную от 4, и длину заголовка меньше 20 или больше входа. Напишите тест с
настоящими байтами заголовка и тесты хотя бы для двух ошибок. Запускайте их командой
`cargo test --bin parse_ipv4`.

<details>
<summary>Подсказка</summary>

Проверяйте длину **до** обращения по индексу, иначе короткий вход вызовет панику. Чтобы получить в
тесте испорченный пакет, скопируйте хороший массив (`let mut bytes = HEADER;`) и измените один байт.

</details>

<details>
<summary>Ответ</summary>

```rust
use std::net::Ipv4Addr;

#[derive(Debug, PartialEq)]
struct Ipv4Header {
    header_len: usize,
    total_len: u16,
    ttl: u8,
    protocol: u8,
    src: Ipv4Addr,
    dst: Ipv4Addr,
}

fn parse_ipv4(bytes: &[u8]) -> Result<Ipv4Header, &'static str> {
    if bytes.len() < 20 {
        return Err("too short for an IPv4 header");
    }
    if bytes[0] >> 4 != 4 {
        return Err("not IPv4");
    }
    let header_len = (bytes[0] & 0x0f) as usize * 4;
    if header_len < 20 || bytes.len() < header_len {
        return Err("bad header length");
    }
    Ok(Ipv4Header {
        header_len,
        total_len: u16::from_be_bytes([bytes[2], bytes[3]]),
        ttl: bytes[8],
        protocol: bytes[9],
        src: Ipv4Addr::new(bytes[12], bytes[13], bytes[14], bytes[15]),
        dst: Ipv4Addr::new(bytes[16], bytes[17], bytes[18], bytes[19]),
    })
}

fn main() {
    let header = [
        0x45, 0x00, 0x00, 0x3a, 0x93, 0x32, 0x40, 0x00, 0x40, 0x06, 0xa9, 0x89, 0x7f, 0x00, 0x00,
        0x01, 0x7f, 0x00, 0x00, 0x01,
    ];
    println!("{:?}", parse_ipv4(&header));
    println!("{:?}", parse_ipv4(&header[..10]));
}

#[cfg(test)]
mod tests {
    use super::*;

    const HEADER: [u8; 20] = [
        0x45, 0x00, 0x00, 0x3a, 0x93, 0x32, 0x40, 0x00, 0x40, 0x06, 0xa9, 0x89, 0x7f, 0x00, 0x00,
        0x01, 0x7f, 0x00, 0x00, 0x01,
    ];

    #[test]
    fn parses_a_real_header() {
        let h = parse_ipv4(&HEADER).unwrap();
        assert_eq!(h.header_len, 20);
        assert_eq!(h.total_len, 58);
        assert_eq!(h.ttl, 64);
        assert_eq!(h.protocol, 6);
        assert_eq!(h.src, Ipv4Addr::LOCALHOST);
    }

    #[test]
    fn rejects_short_input() {
        assert_eq!(
            parse_ipv4(&HEADER[..19]),
            Err("too short for an IPv4 header")
        );
    }

    #[test]
    fn rejects_a_header_length_below_20() {
        let mut bytes = HEADER;
        bytes[0] = 0x44; // версия 4, длина заголовка 4 * 4 = 16 байтов
        assert_eq!(parse_ipv4(&bytes), Err("bad header length"));
    }
}
```

`cargo run --bin parse_ipv4` печатает:

```text
Ok(Ipv4Header { header_len: 20, total_len: 58, ttl: 64, protocol: 6, src: 127.0.0.1, dst: 127.0.0.1 })
Err("too short for an IPv4 header")
```

а `cargo test --bin parse_ipv4` заканчивается строкой
`test result: ok. 3 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out`.

Почему это работает: каждый индекс сверяется с длиной до использования, поэтому никакой вход не
может вызвать панику парсера. Байты из сети — это недоверенный ввод (Урок 10.4): парсер должен
возвращать ошибку на любой мусор, а не падать.

</details>

## Вопросы для самопроверки

1. Почему данные режут на пакеты, а не отправляют одним длинным куском?

<details>
<summary>Ответ</summary>

Чтобы множество разговоров могли честно делить одни и те же кабели и чтобы повреждённый или
потерянный кусок стоил лишь небольшой повторной отправки. Каждый пакет маршрутизируется сам по себе.

</details>

2. Маршрутизатор пересылает ваш пакет. Какие заголовки он читает, а какие игнорирует?

<details>
<summary>Ответ</summary>

Он читает канальный заголовок (чтобы принять кадр) и заголовок IP (чтобы выбрать следующий шаг и
уменьшить TTL). Данные транспортного и прикладного уровней он игнорирует.

</details>

3. В строке tcpdump вы видите `10.0.0.5.51000 > 10.0.0.9.443`. Что такое `51000` и `443`?

<details>
<summary>Ответ</summary>

Порты. `51000` — порт клиента (его выбрала операционная система клиента), `443` — порт сервера
(обычный порт для HTTPS).

</details>

4. Что означает «L4» и что означает «L7»?

<details>
<summary>Ответ</summary>

Номера уровней из модели OSI: L4 — транспортный уровень (TCP, UDP, порты), L7 — прикладной уровень
(HTTP, DNS).

</details>

5. Байты `00 3a` — это 16-битное поле длины. Какое это число и почему?

<details>
<summary>Ответ</summary>

58. Сетевые заголовки используют big-endian (сетевой порядок байтов): первый байт старший, поэтому
значение — 0x003a.

</details>

## Итоги

- Сети передают данные маленькими независимыми **пакетами**; **маршрутизаторы** пересылают каждый на
  шаг ближе к получателю.
- У интернета четыре уровня: **канальный** (следующий шаг, MAC-адреса), **сетевой** (какой компьютер,
  IP-адреса), **транспортный** (какая программа, порты; TCP или UDP), **прикладной** (что означают
  байты).
- **Инкапсуляция**: каждый уровень заворачивает уровень выше в свой заголовок, а получатель
  разворачивает в обратном порядке.
- Заголовки маленькие, но стоят байтов в каждом пакете; **MTU** (1500 байт в Ethernet) ограничивает
  размер пакета.
- `tcpdump -i <interface> -n -X` показывает настоящие пакеты; запускайте его в контейнере с
  `--cap-add NET_RAW --cap-add NET_ADMIN`.
- Поля заголовков записаны в **big-endian**; разбирайте их через `from_be_bytes`, проверяйте каждую
  длину до обращения по индексу и используйте захваченные пакеты как тестовые данные.
