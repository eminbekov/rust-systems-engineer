# Урок 01.1 — Что такое контроль версий

> **Этап 01 — Git и контроль версий** · Урок 1 из 10 · ⏱ около 105 минут

## Что вы узнаете

- Какую проблему решает контроль версий и почему копирование папок («`project_final_v2_REAL`») — это не решение.
- Что такое репозиторий, коммит, история и удалённый репозиторий — простыми словами.
- Три вида систем контроля версий и почему Git называют «распределённым».
- Чем отличаются Git, GitHub и GitLab.
- Почему каждый системный инженер и каждый проект на Rust ежедневно используют Git.

## Перед началом

- Вы прошли [Урок 00.4 — Терминал: первые команды](../00-getting-started/04-terminal-basics.md). Вы умеете открыть терминал, переходить между папками и смотреть список файлов.
- Вы прошли [Урок 00.8 — Режим занятий, заметки в Markdown и контрольная точка](../00-getting-started/08-study-routine-notes-and-checkpoint.md).
- Git вам пока не нужен. В этом уроке вы сделаете контроль версий **вручную**, чтобы почувствовать боль, которую Git устраняет. Git вы установите в следующем уроке.

## Новые слова

| Слово | Значение |
|---|---|
| **версия** (version) | Одно состояние ваших файлов в один момент времени. «Эссе в том виде, как оно было в понедельник» — это одна версия. |
| **контроль версий** (version control) | Способ записывать каждую версию файлов, чтобы видеть, что изменилось, кто это изменил и зачем, и уметь вернуться назад. Ещё говорят *система управления исходным кодом* или VC. |
| **VCS** (Version Control System, система контроля версий) | Программа, которая выполняет контроль версий. Git — это VCS. |
| **репозиторий** (repository, repo) | Папка, историю которой записывает VCS. В нём лежат ваши файлы и все их сохранённые версии. |
| **коммит** (commit) | Одна сохранённая версия в истории вместе с короткым сообщением о том, зачем вы её сохранили. |
| **история** (history) | Список всех коммитов от первого до последнего. |
| **снимок** (snapshot) | «Фотография» всех файлов проекта в один момент. Коммит — это снимок. |
| **diff** (difference, разница) | Список строк, которые были добавлены, удалены или изменены между двумя версиями. |
| **хеш** (hash) | Короткий «отпечаток», вычисленный по содержимому файла. Одинаковое содержимое даёт одинаковый хеш; любое изменение даёт совершенно другой хеш. |
| **SHA** (Secure Hash Algorithm, безопасный алгоритм хеширования) | Семейство хеш-функций. Git по умолчанию использует SHA-1 (и умеет использовать SHA-256). |
| **удалённый репозиторий** (remote) | Копия вашего репозитория на другом компьютере, например на GitHub. |
| **ветка** (branch) | Отдельная линия работы внутри репозитория. Вы изучите её в [Уроке 01.6](06-branches-and-merging.md). |
| **SVN** (Subversion) | Более старая *централизованная* система контроля версий. |
| **CLI** (Command-Line Interface, интерфейс командной строки) | Способ работать с программой, вводя команды в терминале. |
| **GUI** (Graphical User Interface, графический интерфейс) | Способ работать с программой через окна, кнопки и мышь. |
| **IDE** (Integrated Development Environment, интегрированная среда разработки) | Программа для написания кода со множеством встроенных помощников. RustRover — это IDE. |

## 1. Проблема: файлы меняются

Представьте, что вы пишете эссе о Rust. В понедельник в нём один абзац. Во вторник вы добавляете второй. В среду вы переписываете первый и замечаете, что понедельничная версия была лучше.

Без инструментов остаётся только копировать файл перед каждым изменением. Скоро ваша папка выглядит так:

```text
essay.txt
essay-v2.txt
essay-v2-final.txt
essay-v2-final-REAL.txt
essay-v2-final-REAL-fixed-monday-version.txt
```

Какой файл самый новый? Чем они отличаются? Зачем вы создали четвёртый? Через неделю вы этого не вспомните.

Теперь представьте настоящий программный проект. В нём сотни файлов. Пять человек меняют их одновременно. Появляется ошибка, и никто не знает, какое изменение её вызвало. Копирование папок тут не работает.

Система контроля версий отвечает на эти вопросы:

| Вопрос | Что даёт инструмент |
|---|---|
| Как выглядел проект в прошлый вторник? | Вернуться к любой сохранённой версии. |
| Что именно изменилось в этом файле? | *diff* между двумя версиями. |
| Кто изменил эту строку и зачем? | Автор, дата и сообщение каждого коммита. |
| Я всё сломал. Можно отменить? | Вернуться к последней рабочей версии. |
| Двое правят один файл. Чья работа победит? | Средства, чтобы объединить оба изменения. |
| Как поделиться работой с командой? | Отправить историю в удалённый репозиторий и получить работу других. |

> 💡 **Совет:** представляйте контроль версий как «неограниченные точки сохранения» в видеоигре плюс лабораторный журнал, который помнит, кто что сделал и зачем.

## 2. Сначала сделаем это вручную

Сделаем контроль версий вручную. Вы будете использовать команды терминала из [Урока 00.4](../00-getting-started/04-terminal-basics.md) и две новые.

Создайте папку для практики и файл:

```bash
mkdir -p ~/projects/vc-by-hand
cd ~/projects/vc-by-hand
echo "Rust is a systems language." > essay.txt
```

**Что происходит:**

1. `mkdir -p ~/projects/vc-by-hand` создаёт папку. Флаг `-p` означает «создай и недостающие родительские папки и не ругайся, если папка уже есть».
2. `cd` переводит вас в неё.
3. `echo "..." > essay.txt` печатает текст, но `>` перенаправляет его в файл `essay.txt` вместо экрана. Если файл существует, `>` **заменяет** его содержимое. (`>>` **добавило бы** текст в конец.)

Теперь сохраните «версию 1» копированием, измените файл и сохраните «версию 2»:

```bash
cp essay.txt essay-v1.txt
echo "It has no garbage collector." >> essay.txt
cp essay.txt essay-v2.txt
echo "Rust is a fast systems language." > essay.txt
echo "It has no garbage collector." >> essay.txt
ls -1
```

**Что происходит:**

1. `cp essay.txt essay-v1.txt` копирует файл. Эта копия — «версия 1».
2. `>>` добавляет вторую строку в `essay.txt`.
3. Ещё одна копия — «версия 2».
4. Последние две команды `echo` переписывают файл: первая строка меняется, вторая остаётся. Это «текущая» версия.
5. `ls -1` выводит список файлов по одному в строке.

```text
essay-v1.txt
essay-v2.txt
essay.txt
```

Чтобы увидеть, что изменилось, используйте программу `diff`. Она сравнивает два файла построчно.

```bash
diff essay-v1.txt essay.txt
```

```text
1c1,2
< Rust is a systems language.
---
> Rust is a fast systems language.
> It has no garbage collector.
```

**Что происходит:** `diff` печатает изменения, которые нужны, чтобы превратить первый файл во второй. `1c1,2` значит «строка 1 первого файла была **и**зменена (**c**hanged) на строки 1–2 второго». Строки с `<` взяты из первого файла, строки с `>` — из второго.

Более распространённый формат — *унифицированный diff* (unified diff). В Git вы будете видеть его постоянно:

```bash
diff -u essay-v1.txt essay.txt
```

```text
--- essay-v1.txt	2026-11-17 16:21:22
+++ essay.txt	2026-11-17 16:21:22
@@ -1 +1,2 @@
-Rust is a systems language.
+Rust is a fast systems language.
+It has no garbage collector.
```

**Что происходит:** строки с `-` удалены, строки с `+` добавлены. Строка `@@ -1 +1,2 @@` говорит, где изменение: «со строки 1 старого файла» и «со строки 1, две строки, нового файла».

Ваши даты будут другими. Это нормально.

### Почему это не масштабируется

Вы только что выполнили работу системы контроля версий и уже видите проблемы:

- **Смысл спрятан в именах.** `essay-v2` не говорит, *зачем* появилась версия. Никто не записал «добавили предложение про сборщик мусора».
- **Место.** Каждая версия — полная копия, даже если изменилась одна строка.
- **Легко сломать.** Вы можете случайно затереть `essay-v1.txt`. Ничто не предупредит.
- **Нет авторов и дат**, которым можно доверять.
- **Нет безопасного способа объединить** работу двух людей.

Git решает всё это. Посмотрим на первую идею, которую он использует.

## 3. Отпечатки: как инструмент узнаёт, что файл изменился

Как инструменту убедиться, что два файла одинаковы или что файл повреждён? Он вычисляет **хеш**. Хеш-функция читает все байты файла и выдаёт короткую строку. В macOS для этого есть программа `shasum`:

```bash
shasum -a 256 essay-v1.txt essay.txt
cp essay.txt essay-copy.txt
shasum -a 256 essay-copy.txt
```

```text
39331024fe2fc799466a9aef292914d32b5c788ba2e63f09e42bdd227f641031  essay-v1.txt
a59be4c9143e0cae7f2748fe2f3191ab0306a020528fc896ed95a8c540f5f542  essay.txt
a59be4c9143e0cae7f2748fe2f3191ab0306a020528fc896ed95a8c540f5f542  essay-copy.txt
```

**Что происходит:**

1. `shasum -a 256` вычисляет хеш SHA-256 каждого файла и печатает его, а после него — имя файла.
2. У `essay.txt` и его копии `essay-copy.txt` **абсолютно одинаковый** хеш, потому что содержимое одинаково. Имя не важно.
3. У `essay-v1.txt` **совершенно другой** хеш, потому что содержимое другое.

Даже крошечное изменение даёт совсем другой результат. Сравните хеши SHA-1 текста `abc` и текста `abc ` (с пробелом в конце):

```bash
printf 'abc' | shasum -a 1
printf 'abc ' | shasum -a 1
```

```text
a9993e364706816aba3e25717850c26c9cd0d89d  -
eeca658f56ce50a4f36605aaf93e29e87c12009a  -
```

(`printf` печатает текст без перевода строки; `|` передаёт его в `shasum`; `-` значит «данные пришли из канала, а не из файла».)

Git использует хеши везде. Каждая сохранённая версия получает имя, которое **является** хешем её содержимого, например `4fb5aafe1d1ebe8ae283f983329fbd147d8307bb`. Поэтому Git быстро находит изменения, а повреждённую или тайно изменённую историю замечает сразу. Пока достаточно запомнить: **коммит называется длинным хешем, а на практике используют его первые 7 символов.**

> 📏 **Соглашение:** по умолчанию Git использует SHA-1 и постепенно переходит на SHA-256. В этом курсе хеши в выводе Git — это 40 шестнадцатеричных символов (SHA-1).

## 4. Три вида систем контроля версий

Системы контроля версий развивались в три шага.

**1. Локальные.** История хранится в скрытой папке на вашем компьютере. Просто, но работать с другими людьми нельзя.

**2. Централизованные.** Один **сервер** хранит единственную настоящую историю. Разработчики *забирают* (check out) файлы с сервера, меняют их и *коммитят* обратно на сервер. Примеры: **CVS** (Concurrent Versions System, система одновременных версий), **Subversion (SVN)**, Perforce. Слабое место: если сервер недоступен или вы без сети, сохранить историю нельзя, а если диск сервера умрёт, историю можно потерять.

**3. Распределённые.** У *каждого* разработчика есть **полная копия всей истории**. Сервер (например, GitHub) — просто ещё одна копия, о которой все договорились. Примеры: **Git**, Mercurial.

```text
 Centralized                            Distributed

 Alice   Bob   Carol                    Alice          Bob
   \      |     /                      [full history] [full history]
    \     |    /                           \            /
   [ one server ]                           [ shared server ]
   (only copy of history)                       |
                                           Carol [full history]
```

Поскольку каждая копия полная, в Git можно:

- сохранять историю, смотреть её и возвращаться назад **без интернета**;
- работать быстро, потому что почти все команды затрагивают только ваш диск;
- потерять сервер и всё равно восстановить всё из копии любого разработчика.

## 5. Что такое Git?

**Git** — бесплатная распределённая система контроля версий с открытым исходным кодом. Её начал в 2005 году Линус Торвальдс, создатель Linux, чтобы управлять разработкой ядра Linux (центральной части операционной системы Linux). Сегодня это стандартный инструмент почти для любого программного обеспечения.

Как Git «думает» о вашем проекте? Он хранит **снимки**. Каждый коммит — это картина *всех* отслеживаемых файлов в один момент, с сообщением и автором. (Внутри Git умён: если файл не менялся, новый снимок просто указывает на старую сохранённую копию, поэтому место не тратится зря.)

```text
commit 1          commit 2          commit 3
[A1] [B1] [C1] -> [A2] [B1] [C1] -> [A2] [B2] [C1]
 file A, B, C      A changed         B changed
                   (B, C reused)     (A, C reused)
```

Каждый коммит помнит и своего **родителя** (коммит перед ним). Если идти по родителям, получается история.

## 6. Git, GitHub и GitLab — это не одно и то же

Это самая частая путаница у новичков.

| Название | Что это |
|---|---|
| **Git** | Программа на вашем компьютере. Она записывает историю. Работает без интернета и без аккаунта. |
| **GitHub** | Сайт и сервис, который хранит Git-репозитории онлайн и добавляет инструменты для командной работы: pull request, задачи (issues), автоматические проверки. Принадлежит Microsoft. |
| **GitLab** | Другой такой сервис. Можно пользоваться сайтом компании или установить GitLab на собственные серверы. |
| **Другие** | Bitbucket, Codeberg, Gitea и другие. Все они «говорят» на Git. |

Аналогия: Git — как текстовый редактор, GitHub — как облачный диск, где вы храните документы и делитесь ими. Редактировать документы можно и без облака. С GitHub и GitLab вы поработаете в [Уроке 01.8](08-remotes-github-and-gitlab.md) и [Уроке 01.9](09-teamwork-pull-requests-and-conventions.md).

## 7. Карта слов, которые вам встретятся

Вот картинка для всего этапа. Не страшно, если пока всё ново: у каждой части будет свой урок.

```text
 your computer                                               another computer
┌──────────────────────────────────────────────────┐        ┌───────────────┐
│  working tree        staging area     repository │        │    remote     │
│  (your files)  --->  (next commit) ---> (history)│ <----> │ (GitHub etc.) │
│   edit files         git add           git commit│  push/ │               │
│                                                  │  pull  │               │
└──────────────────────────────────────────────────┘        └───────────────┘
```

- **Рабочее дерево** (working tree): настоящие файлы, которые вы редактируете.
- **Область подготовки** (staging area, «индекс»): комната ожидания, где вы выбираете, какие изменения попадут в следующий коммит.
- **Репозиторий** (repository): скрытая база данных всех коммитов (папка `.git`).
- **Удалённый репозиторий** (remote): копия на сервере. *Push* отправляет туда ваши коммиты, *pull* приносит коммиты других.

## 8. Зачем системному инженеру это нужно

- **Git используют все команды.** Код-ревью, релизы и автоматические тесты начинаются с истории Git.
- **Rust живёт на Git.** Компилятор Rust, Cargo и почти все крейты (библиотеки Rust) разрабатываются в открытых Git-репозиториях. Cargo даже может взять зависимость прямо по Git-адресу.
- **Страховка.** С историей можно экспериментировать без страха: плохая идея отменяется одной командой.
- **Отладка.** Когда появляется ошибка, история подскажет, *какое изменение* её внесло (вы сделаете это в [Уроке 01.4](04-viewing-history-and-changes.md)).
- **Доказательство вашей работы.** Хорошая история — ваше портфолио. Работодатели её читают.

## Частые ошибки

> ⚠️ **Частая ошибка:** «Git — это GitHub». Это не так. Git полностью работает на вашем ноутбуке. GitHub — лишь одно из мест, где можно хранить копию.

> ⚠️ **Частая ошибка:** «Контроль версий — это резервная копия». История внутри одной папки пропадёт, если умрёт диск. Настоящая резервная копия — это копия на **другой** машине. Удалённый репозиторий в этом помогает, но это не одно и то же.

> ⚠️ **Частая ошибка:** «Выучу Git потом, когда проект вырастет». Новички чаще всего теряют работу именно в первых маленьких проектах. Начните сейчас.

> 🔒 **Безопасность:** история хранится вечно. Если вы сохранили пароль или секретный ключ в файле и закоммитили его, он останется в истории, даже если потом удалить файл. Как этого избежать, вы узнаете в [Уроке 01.3](03-your-first-repository-and-commits.md) и [Уроке 01.8](08-remotes-github-and-gitlab.md).

## Попробуйте сами

Выполните это в терминале. Это повтор ручного процесса с небольшим поворотом.

1. Перейдите в папку для практики: `cd ~/projects/vc-by-hand`.
2. Создайте второй файл: `echo "Cargo is the Rust build tool." > tools.txt`.
3. «Сохраните версию» файла: `cp tools.txt tools-v1.txt`.
4. Измените его: `echo "rustup installs Rust." >> tools.txt`.
5. Выполните `diff -u tools-v1.txt tools.txt`. Вы должны увидеть одну строку с `+`.
6. Выполните `shasum -a 256 tools-v1.txt tools.txt`. Два хеша должны отличаться.
7. Теперь отмените изменение **вручную**: `cp tools-v1.txt tools.txt`. Снова выполните `shasum -a 256 tools-v1.txt tools.txt`. Теперь хеши равны.

Вы только что увидели три базовые возможности контроля версий: **увидеть изменение**, **обнаружить изменение**, **вернуться назад**. Git делает все три для каждого файла автоматически — с сообщением и автором.

## Упражнения

### Упражнение 1 — Классифицируйте инструмент (легко)

Для каждого пункта скажите, чем он является: **VCS**, **сервисом хостинга** или **ни тем ни другим**: Git, GitHub, Subversion, GitLab, RustRover, Mercurial.

<details>
<summary>Подсказка</summary>

VCS записывает историю на вашем компьютере. Сервис хостинга — это сайт, который хранит репозитории.

</details>

<details>
<summary>Ответ</summary>

- VCS: Git, Subversion, Mercurial.
- Сервис хостинга: GitHub, GitLab.
- Ни то ни другое: RustRover (это IDE, редактор кода; он может *использовать* Git, но сам не является VCS).

Почему это работает: VCS — инструмент, который записывает версии. Сервис хостинга хранит общие копии и добавляет инструменты для командной работы.

</details>

### Упражнение 2 — Найдите изменение (легко)

В `~/projects/vc-by-hand` у вас есть `essay-v2.txt` и `essay.txt`. Покажите разницу между ними командой и одним предложением скажите, что изменилось.

<details>
<summary>Подсказка</summary>

Используйте `diff -u`, сначала более старый файл.

</details>

<details>
<summary>Ответ</summary>

```bash
diff -u essay-v2.txt essay.txt
```

```text
--- essay-v2.txt	2026-11-17 16:21:22
+++ essay.txt	2026-11-17 16:21:22
@@ -1,2 +1,2 @@
-Rust is a systems language.
+Rust is a fast systems language.
 It has no garbage collector.
```

Изменилась первая строка: добавлено слово «fast». Вторая строка такая же (она начинается с пробела — это значит «неизменённый контекст»).

Почему это работает: `diff -u` показывает удалённые строки с `-`, добавленные с `+`, а неизменённые строки вокруг — с пробелом.

</details>

### Упражнение 3 — Заметьте изменение в один символ (средне)

Создайте файл `a.txt` с текстом `hello`. Скопируйте его в `b.txt`. Докажите хешами, что файлы равны. Затем добавьте `!` в конец `b.txt` и докажите, что теперь они различаются.

<details>
<summary>Подсказка</summary>

`echo "hello" > a.txt`, затем `cp`, затем `shasum -a 256 a.txt b.txt`. Чтобы добавить символ, используйте `>>` — но `echo` добавляет перевод строки, поэтому в файле появится ещё одна строка. Ничего страшного: достаточно любого изменения.

</details>

<details>
<summary>Ответ</summary>

```bash
echo "hello" > a.txt
cp a.txt b.txt
shasum -a 256 a.txt b.txt
echo "!" >> b.txt
shasum -a 256 a.txt b.txt
```

Первый `shasum` печатает два одинаковых хеша. Второй печатает два разных.

Почему это работает: хеш вычисляется только по содержимому. Одинаковое содержимое даёт одинаковый хеш; любое изменение даёт другой. Git использует именно эту идею, чтобы узнать, что изменилось.

</details>

### Упражнение 4 — Зачем нужен Git? (сложно)

Ваша команда из трёх человек пользуется одной сетевой папкой и копирует файлы в подпапки с датами (`2026-11-01`, `2026-11-02`, …). Запишите **четыре** конкретные проблемы, которые решил бы Git. Используйте таблицу из раздела 1.

<details>
<summary>Подсказка</summary>

Подумайте о том, как двое правят один файл; как найти, кто изменил строку; сколько места занято; как вернуть один файл из прошлого месяца; как работать в поезде без сети.

</details>

<details>
<summary>Ответ</summary>

Примеры (любые четыре верны):

1. Двое правят один файл в один день: один затирает работу другого. Git это обнаруживает и помогает *слить* оба изменения.
2. Причина изменения нигде не записана. В Git у каждого коммита есть сообщение и автор.
3. Полные копии всего каждый день тратят место на диске. Git хранит неизменённые файлы один раз.
4. Чтобы найти, какое изменение внесло ошибку, нужно вручную открывать много папок. Git умеет показать diff и даже искать по истории автоматически.
5. Без сети сетевая папка недоступна. В Git полная история есть у вас локально.

Почему это работает: в ручном процессе нет сообщений, авторов, безопасного слияния и экономного хранения. Именно эти четыре проблемы Git и создавался решать.

</details>

## Вопросы для самопроверки

1. Что такое *коммит*?

<details>
<summary>Ответ</summary>

Сохранённая версия проекта (снимок всех отслеживаемых файлов) в истории, с автором, датой и сообщением.

</details>

2. Назовите одно преимущество *распределённой* VCS перед *централизованной*.

<details>
<summary>Ответ</summary>

У каждого разработчика есть полная история, поэтому можно коммитить и смотреть историю без сети, работать быстро, а проект переживает потерю любого одного компьютера, включая сервер.

</details>

3. Git — это то же самое, что GitHub?

<details>
<summary>Ответ</summary>

Нет. Git — программа, записывающая историю. GitHub — сайт, который хостит Git-репозитории и добавляет инструменты для командной работы.

</details>

4. Если у двух файлов одинаковый хеш SHA-256, что вы о них знаете?

<details>
<summary>Ответ</summary>

Их содержимое одинаково (имена могут быть разными).

</details>

5. Что из этого *не* входит в картинку раздела 7: рабочее дерево, область подготовки, репозиторий, компилятор?

<details>
<summary>Ответ</summary>

Компилятор. Остальные три — места, где живут ваши изменения до коммита и после него.

</details>

6. Почему закоммиченный пароль — проблема, даже если потом удалить файл?

<details>
<summary>Ответ</summary>

История хранит каждую версию. Любой, у кого есть доступ к репозиторию, всё ещё может прочитать старую версию с паролем.

</details>

## Итоги

- Контроль версий записывает каждую версию файлов с сообщением и автором, чтобы вы могли сравнивать и возвращаться назад.
- Ручное копирование папок не масштабируется: нет причин, нет авторов, место тратится зря, слияние небезопасно.
- *Хеш* — отпечаток содержимого; Git называет им каждый коммит.
- Распределённая VCS даёт каждому разработчику полную копию истории; Git — стандартная такая система.
- Коммит — это снимок; коммиты указывают на родителей и образуют историю.
- Git — инструмент; GitHub и GitLab — сервисы, которые хостят репозитории.
- Ключевые места: рабочее дерево, область подготовки, репозиторий и удалённый репозиторий.
