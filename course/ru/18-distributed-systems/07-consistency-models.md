# Урок 18.7 — Модели согласованности

> **Этап 18 — Распределённые системы** · Урок 7 из 15 · ⏱ около 135 минут

- Что такое модель согласованности: контракт, который говорит, какие ответы реплицируемой системе разрешено давать.

## Новые слова

| Слово | Значение |
|---|---|
| **модель согласованности** (consistency model) | Контракт между хранилищем данных и его клиентами: правила, которые говорят, какие значения может вернуть чтение. |
| **регистр** (register) | Простейший вид данных: одно значение, которое можно записать и прочитать. Ключ в хранилище «ключ-значение» — это регистр. |
| **история** (history) | Запись того, что делали клиенты: каждый вызов с временем начала, временем окончания, видом (чтение или запись) и значением. |
| **линеаризуемость** (linearizability) | Самая сильная из распространённых моделей: система ведёт себя так, будто копия данных **одна**, и каждая операция срабатывает в один момент между своим началом и концом. |
| **последовательная согласованность** (sequential consistency) | Все клиенты видят операции в одном порядке, который сохраняет порядок каждого клиента, но может не совпадать с реальным временем. |
| **причинная согласованность** (causal consistency) | Причинно связанные операции («произошло раньше») все видят в этом порядке; конкурентные можно видеть в разном порядке. |
| **согласованность в конечном счёте** (eventual consistency) | Если новых записей нет, все реплики со временем вернут одно и то же значение. О промежутке ничего не обещается. |
| **гарантия сессии** (session guarantee) | Обещание для вызовов одного клиента, например «вы всегда видите свои записи». |
| **теорема CAP** (CAP theorem) | При сетевом разделении (**P**artition) система не может быть одновременно согласованной (**C**onsistent, линеаризуемой) и доступной (**A**vailable, отвечающей на каждый запрос). |
| **устаревшее чтение** (stale read) | Чтение, вернувшее значение, которое уже было перезаписано. |

## 1. Что такое модель согласованности

В Уроке 18.6 клиент записал `x = 2`, а потом прочитал `x = 1` с отстающего последователя. Это ошибка? Зависит от
того, что система **обещала**. **Модель согласованности** — это и есть обещание: набор правил, который говорит,
какие значения разрешено вернуть чтению с учётом произошедших записей.

Житейская картинка. Вы отправили другу письмо, а потом звоните ему. «Строгая» согласованность значит, что письмо
точно уже у него, когда вы звоните. Согласованность «в конечном счёте» значит, что письмо когда-нибудь дойдёт. Оба
обещания честные; просто это разные обещания с разной ценой.

С более сильными моделями проще программировать, потому что они ведут себя больше как один компьютер. Более слабые
модели позволяют строить более быстрые и доступные системы, потому что репликам нужно меньше договариваться. Пойдём
от сильных к слабым.

## 2. Линеаризуемость: иллюзия одной копии

Система **линеаризуема**, если каждая её история могла бы получиться у **одной-единственной копии** данных, где каждая
операция срабатывает в **один момент** между тем, как клиент её отправил, и тем, как клиент получил ответ.

Главное — во второй части: реальное время имеет значение. Если запись **закончилась** до того, как чтение **началось**,
чтение обязано увидеть эту запись (или более новую). Если две операции **перекрываются** во времени, они могут
сработать в любом порядке.

Вот четыре истории одного регистра, который начинается с 0. Каждая строка — один клиент; прямоугольник `[....]` —
вызов от его начала до конца, один символ на миллисекунду; `r→0` — чтение, вернувшее 0:

```text
ms    0         10        20        30
1 write, then read: linearizable
  A   [.write 1.]
  B                       [.read → 1]
2 stale read: NOT linearizable: the write had finished
  A   [.write 1.]
  B                       [.read → 0]
3 reads during a write: linearizable: the write took effect between the reads
  A   [...........write 1...........]
  B        [r→0.]
  C                  [r→1.]
4 new, then old: NOT linearizable: once 1 was seen, 0 is gone
  A   [...........write 1...........]
  B        [r→1.]
  C                  [r→0.]
```

История 4 удивляет многих: оба чтения перекрываются с записью, и каждое по отдельности было бы допустимо. Но чтение B
**закончилось** до того, как чтение C **началось**, поэтому чтение B сработало первым. Если B уже увидело новое значение,
значит, запись уже произошла, и C больше не может увидеть старое. Система, которая читает с реплик с разным
отставанием, выдаёт именно такую историю.

### Крошечная программа проверки

Линеаризуемость можно определить поиском: попробовать расставить вызовы по порядку, один за другим, так чтобы (1) вызов
мог идти следующим, только если ни один другой ожидающий вызов **не обязан** идти раньше него, и (2) каждое чтение
возвращало значение регистра на своём месте в порядке. Если какой-то порядок подходит, история линеаризуема. Это поиск
с возвратом ([Урок 07.7](../07-algorithms-and-data-structures/07-recursion.md)): попробовать вызов, углубиться и
отменить выбор, если он ведёт в тупик. Поместите это в `src/lib.rs`:

```rust
//! Consistency models (Lesson 18.7).

/// What one call did to the register. A read carries the value it returned.
#[derive(Debug, Clone, Copy, PartialEq)]
pub enum Op {
    Write(u32),
    Read(u32),
}

/// One call in a history: which client made it, when it started and ended (in ms), and what it did.
#[derive(Debug, Clone, Copy)]
pub struct Call {
    pub client: char,
    pub start: u32,
    pub end: u32,
    pub op: Op,
}

/// A rule `must_precede(a, b)`: call `a` has to take effect before call `b`.
pub type Rule = fn(&Call, &Call) -> bool;

/// Linearizability: a call that ended before another started must take effect first.
fn real_time(a: &Call, b: &Call) -> bool {
    a.end < b.start
}

/// Searches for an order of the calls that a single copy of the register (starting at 0)
/// could have produced, where each call takes effect at one instant between its start and
/// end. Returns that order (as indexes into `history`), or `None` if there is none.
pub fn linearize(history: &[Call]) -> Option<Vec<usize>> {
    find_order(history, real_time)
}

/// Finds an order of all calls that respects `must_precede` and that a single register
/// starting at 0 could have produced.
pub fn find_order(history: &[Call], must_precede: Rule) -> Option<Vec<usize>> {
    let mut order = Vec::new();
    if search(history, must_precede, &mut order, 0) {
        Some(order)
    } else {
        None
    }
}

fn search(history: &[Call], must_precede: Rule, order: &mut Vec<usize>, value: u32) -> bool {
    if order.len() == history.len() {
        return true; // every call has found its place
    }
    for i in 0..history.len() {
        if order.contains(&i) {
            continue;
        }
        // Call i may take effect next only if no waiting call must come before it.
        let waiting = |j: &usize| !order.contains(j) && *j != i;
        if (0..history.len())
            .filter(waiting)
            .any(|j| must_precede(&history[j], &history[i]))
        {
            continue;
        }
        let next_value = match history[i].op {
            Op::Write(v) => v,
            Op::Read(v) if v == value => value,
            Op::Read(_) => continue, // this read cannot happen now
        };
        order.push(i);
        if search(history, must_precede, order, next_value) {
            return true;
        }
        order.pop(); // a dead end: try another call in this place
    }
    false
}
```

**Что происходит:**

1. `Call` записывает одну операцию истории. Для чтения `Op::Read(v)` хранит значение, которое чтение **вернуло**.
2. `Rule` — *тип указателя на функцию*: любую функцию с сигнатурой `fn(&Call, &Call) -> bool` можно использовать как
   значение этого типа. Отдельное правило позволяет Упражнению 3 повторно использовать весь поиск для другой модели.
3. Для линеаризуемости правило — реальное время: `a.end < b.start` значит «a закончилось до начала b, поэтому a должно
   идти первым».
4. `search` строит порядок в векторе `order`. На каждом шаге он пробует каждый ещё не поставленный вызов. Вызов
   пропускается, если какой-то ожидающий вызов обязан идти раньше него или если это чтение, чьё значение не совпадает
   с текущим значением регистра. Иначе вызов ставится, и поиск углубляется с новым значением.
5. Когда более глубокий поиск не удался, `order.pop()` отменяет выбор, и цикл пробует следующий вызов. Если поставлены
   все вызовы, допустимый порядок найден.

Поиск перебирает много порядков, поэтому годится только для маленьких историй. Настоящие программы проверки (например,
в инструменте тестирования Jepsen) гораздо умнее, но отвечают на тот же вопрос.

Теперь проверим наши четыре истории, `src/bin/histories.rs`:

```rust
use p18_consistency::{Call, Op, linearize};

fn call(client: char, start: u32, end: u32, op: Op) -> Call {
    Call {
        client,
        start,
        end,
        op,
    }
}

fn main() {
    let histories = [
        (
            "1 write, then read",
            vec![
                call('A', 0, 10, Op::Write(1)),
                call('B', 20, 30, Op::Read(1)),
            ],
        ),
        (
            "2 stale read",
            vec![
                call('A', 0, 10, Op::Write(1)),
                call('B', 20, 30, Op::Read(0)),
            ],
        ),
        (
            "3 reads during a write",
            vec![
                call('A', 0, 30, Op::Write(1)),
                call('B', 5, 10, Op::Read(0)),
                call('C', 15, 20, Op::Read(1)),
            ],
        ),
        (
            "4 new, then old",
            vec![
                call('A', 0, 30, Op::Write(1)),
                call('B', 5, 10, Op::Read(1)),
                call('C', 15, 20, Op::Read(0)),
            ],
        ),
    ];
    for (name, history) in &histories {
        match linearize(history) {
            Some(order) => println!("{name:24} linearizable, order {order:?}"),
            None => println!("{name:24} NOT linearizable"),
        }
    }
}
```

`cargo run --bin histories`:

```text
1 write, then read       linearizable, order [0, 1]
2 stale read             NOT linearizable
3 reads during a write   linearizable, order [1, 0, 2]
4 new, then old          NOT linearizable
```

Для истории 3 программа нашла порядок «B читает 0, A пишет 1, C читает 1»: запись сработала где-то между 10 и 15 мс.
Это разрешено, потому что запись всё ещё шла.

> 🧪 **Тестирование:** записать историю тестового прогона и проверить её — так на самом деле тестируют распределённые
> базы данных на ошибки согласованности. Добавьте два ключевых случая как модульные тесты в конец `src/lib.rs`:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    fn call(client: char, start: u32, end: u32, op: Op) -> Call {
        Call {
            client,
            start,
            end,
            op,
        }
    }

    #[test]
    fn a_stale_read_after_the_write_finished_is_not_linearizable() {
        let history = [
            call('A', 0, 10, Op::Write(1)),
            call('B', 20, 30, Op::Read(0)),
        ];
        assert_eq!(linearize(&history), None);
    }

    #[test]
    fn a_read_during_the_write_may_see_the_old_value() {
        let history = [
            call('A', 0, 30, Op::Write(1)),
            call('B', 5, 10, Op::Read(0)),

    }

```

`cargo test --lib`:

```text

```

Как настоящие системы становятся линеаризуемыми? Системы с одним лидером могут читать и писать **только на лидере**
(и проверять, что он всё ещё лидер); так делают системы консенсуса вроде Raft (Уроки 18.9–18.11). Чтение с
асинхронных последователей не линеаризуемо, как показывает история 2. Кворумы без лидера с `R + W > N` тоже **не**
линеаризуемы автоматически: история 4 всё ещё может случиться, пока запись доходит до реплик одна за другой.

## 3. Более слабые модели

Линеаризуемость требует координации: кто-то должен гарантировать, что каждое чтение видит каждую законченную запись, а
это стоит обменов сообщениями и не работает, когда сеть разрезана. Более слабые модели отказываются от части обещания:

| Модель | Обещание | Пример того, что разрешено |
|---|---|---|
| **Линеаризуемая** | одна копия, порядок реального времени | ничего неожиданного |
| **Последовательная** | один порядок для всех, сохраняющий порядок каждого клиента, но не реальное время | история 2: чтение B можно поставить до записи A, потому что это разные клиенты |
| **Причинная** | «произошло раньше» соблюдается везде (Урок 18.5); конкурентные записи можно видеть в разном порядке | два пользователя видят два несвязанных комментария в разном порядке, но ответ никогда не появляется раньше комментария, на который он отвечает |
| **В конечном счёте** | если записи прекратились, реплики сходятся | что угодно устаревшее на время, даже метания между старым и новым |

Между ними есть полезные обещания для **сессии одного клиента**, которые могут дать даже слабо согласованные системы:

| Гарантия сессии | Смысл | Какую проблему Урока 18.6 она решает |
|---|---|---|
| **Читай свои записи** (read your writes) | после вашей записи ваши чтения её видят | пользователь, сменивший имя и увидевший старое |
| **Монотонные чтения** (monotonic reads) | увидев значение, вы никогда не увидите более старое | чтение с последователя 0, а потом с сильнее отстающего последователя 1 |
| **Монотонные записи** (monotonic writes) | ваши записи применяются в том порядке, в котором вы их сделали | — |
| **Согласованный префикс** (consistent prefix) | вы видите записи в осмысленном порядке (ответ никогда раньше вопроса) | — |

Частый способ получить первые две: клиент запоминает позицию в журнале, которую он видел (Упражнение 3 Урока 18.6), и
принимает только реплики, продвинувшиеся как минимум так же далеко, или всегда общается с одной и той же репликой
(«липкие» сессии).

## 4. Теорема CAP

Теорему CAP часто пересказывают как «выберите два из трёх: согласованность, доступность, устойчивость к разделению».
Это вводит в заблуждение. Сетевые разделения — не выбор; они случаются (Урок 18.2). Настоящее утверждение такое:

> **Когда сеть разделена**, система должна выбрать: либо она остаётся **линеаризуемой**, и часть узлов отказывает в
> запросах (не доступна), либо каждый узел продолжает отвечать, и часть ответов может устареть (не линеаризуема).

```text
           partition
  client ── node 1  ║  node 2 ── client
   writes x = 2     ║     reads x
                    ║
  CP choice: node 2 refuses to answer ("I cannot reach the others") → consistent, not available
  AP choice: node 2 answers with what it has (x = 1)                  → available, not consistent
```

Эти две метки взяты из букв CAP: **CP** значит «остаётся согласованной (**C**onsistent) во время разделения сети
(**P**artition)», **AP** — «остаётся доступной (**A**vailable) во время разделения сети». Кластер Raft делает выбор CP: сторона с большинством продолжает работать, сторона меньшинства отказывает в записях и
линеаризуемых чтениях. Корзина покупок в хранилище без лидера делает выбор AP: каждая реплика принимает записи, а
конфликты объединяются позже (Урок 18.5).

Есть и второй компромисс, который важен, даже когда разделения **нет**: более сильная согласованность стоит задержки,
потому что репликам нужно переговорить, прежде чем ответить. Формулировка PACELC (если **P**artition — **A** или
**C**; иначе, **E**lse, — **L**atency или **C**onsistency, задержка или согласованность) называет оба компромисса.

> 💡 **Совет:** ярлыки вроде «CP-база данных» или «AP-база данных» грубы. Большинство настоящих баз данных предлагают
> несколько режимов, и одна и та же база может быть линеаризуемой для одних операций и нет для других. Спрашивайте
> «какая гарантия у этого конкретного чтения?».

## 5. Выбор модели

| Возможность | Что ей нужно | Почему |
|---|---|---|
| Имя пользователя должно быть уникальным | линеаризуемость | два пользователя, одновременно регистрирующие «anna», не должны оба преуспеть |
| Баланс счёта и переводы | линеаризуемость (и транзакции) | деньги не должны появляться или исчезать |
| «Кто лидер?» или блокировка | линеаризуемость (консенсус) | иначе разделение мозга (Урок 18.6) |
| Страница собственного профиля пользователя | читай свои записи | пользователь должен видеть своё изменение |
| Комментарии к посту | причинная | ответы после комментария, на который они отвечают |
| Счётчик лайков, время «был в сети» | в конечном счёте | немного устаревшее число никому не вредит |

## Частые ошибки

> ⚠️ **Частая ошибка: «кворумы делают систему линеаризуемой».** `R + W > N` заставляет группы чтения и записи
> пересекаться, но история 4 всё ещё может случиться, пока запись выполнена наполовину. Линеаризуемым системам на
> кворумах нужны дополнительные шаги (например, чтение, нашедшее разные версии, должно записать самую новую обратно в
> кворум **до** того, как ответит).

> ⚠️ **Частая ошибка: тестировать согласованность на одной машине.** На ноутбуке без отставания любая система выглядит
> линеаризуемой. Ошибки согласованности появляются только при задержках, разделениях и переключениях, поэтому тесты
> должны их создавать; Урок 18.12 делает это с помощью симулятора.

> ⚠️ **Частая ошибка: забыть о реальном времени.** «Все реплики согласны о порядке» — это последовательная
> согласованность, а не линеаризуемость. Разница проявляется именно тогда, когда один клиент говорит другому: «я
> записал, иди читай».

## Попробуйте сами

1. Добавьте в `histories.rs` пятую историю: A пишет 1 с 0 до 10 мс, затем B пишет 2 с 20 до 30 мс, затем C читает 1 с
   40 до 50 мс. Предскажите ответ и запустите (не линеаризуема: C прочитал перезаписанное значение).
2. Сдвиньте чтение C в этой истории на 25–35 мс, во время записи B. Теперь история линеаризуема, с порядком
   `[0, 2, 1]`: чтение сработало до второй записи.
3. В истории 4 пусть чтение B заканчивается в 16 мс, а не в 10. Теперь два чтения перекрываются, и история
   линеаризуема.

## Упражнения

### Упражнение 1 — Когда «новое, потом старое» допустимо (легко)

Напишите интеграционный тест `tests/overlap.rs` с историей 4 и вариантом, в котором чтение C начинается в 8 мс, так
что два чтения **перекрываются**. Проверьте, что история 4 не линеаризуема, а вариант линеаризуем с порядком
`[2, 0, 1]`.

<details>
<summary>Подсказка</summary>

Скопируйте маленькую вспомогательную функцию `call` в файл теста. Когда два чтения перекрываются, ни одно не обязано
идти раньше другого, поэтому чтение 0 может сработать первым, ещё до записи.

</details>

<details>
<summary>Ответ</summary>

```rust
use p18_consistency::{Call, Op, linearize};

fn call(client: char, start: u32, end: u32, op: Op) -> Call {
    Call {
        client,
        start,
        end,
        op,
    }
}

#[test]
fn new_then_old_is_wrong_only_if_the_reads_do_not_overlap() {
    let one_after_the_other = [
        call('A', 0, 30, Op::Write(1)),
        call('B', 5, 10, Op::Read(1)),
        call('C', 15, 20, Op::Read(0)),
    ];
    assert_eq!(linearize(&one_after_the_other), None);

    let overlapping = [
        call('A', 0, 30, Op::Write(1)),
        call('B', 5, 10, Op::Read(1)),
        call('C', 8, 20, Op::Read(0)),
    ];
    assert_eq!(linearize(&overlapping), Some(vec![2, 0, 1]));
}
```

`cargo test --test overlap`:

```text
test new_then_old_is_wrong_only_if_the_reads_do_not_overlap ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Почему это работает: в варианте чтение C (8–20 мс) началось до того, как закончилось чтение B (5–10 мс), поэтому
порядок «C читает 0, A пишет 1, B читает 1» соблюдает все ограничения реального времени. Линеаризуемость — о том, что
клиенты могли наблюдать, а здесь они не могли отличить.

</details>

### Упражнение 2 — Монотонные чтения (средне)

Клиент делает несколько чтений, возможно, с разных реплик. Для каждого чтения известно, сколько записей журнала применила
ответившая реплика. Создайте `src/session.rs` (и `pub mod session;`) с
`pub fn first_backwards_read(positions: &[usize]) -> Option<usize>`, которая возвращает индекс первого чтения,
увидевшего **меньше** записей, чем чтение перед ним, или `None`, если чтения ни разу не вернулись в прошлое.
Проверьте на `[3, 5, 5, 4, 6]` (ответ 3), `[1, 2, 2, 3]` и пустом списке (оба `None`).

<details>
<summary>Подсказка</summary>

`positions.windows(2)` даёт каждую пару соседей; `.position(...)` находит первую пару, в которой второе число меньше.
Вернувшееся в прошлое чтение — **второе** в паре, поэтому прибавьте 1.

</details>

<details>
<summary>Ответ</summary>

```rust
//! Exercise 2: monotonic reads.

/// `positions[k]` is how many log entries the replica had applied when it answered the
/// client's k-th read. Returns the index of the first read that went back in time.
pub fn first_backwards_read(positions: &[usize]) -> Option<usize> {
    positions
        .windows(2)
        .position(|pair| pair[1] < pair[0])
        .map(|i| i + 1)
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn switching_to_a_lagging_replica_goes_back_in_time() {
        assert_eq!(first_backwards_read(&[3, 5, 5, 4, 6]), Some(3));
        assert_eq!(first_backwards_read(&[1, 2, 2, 3]), None);
        assert_eq!(first_backwards_read(&[]), None);
    }
}
```

Почему это работает: монотонные чтения запрещают только движение **назад**; одинаковые позиции (одна и та же реплика
дважды или две одинаково актуальные реплики) допустимы. Клиент, который передаёт свою наибольшую позицию с каждым
чтением, позволяет системе отклонять реплики, нарушающие это правило.

</details>

### Упражнение 3 — Последовательная согласованность (сложно)

Создайте `src/sequential.rs` (и `pub mod sequential;`) с
`pub fn sequentialize(history: &[Call]) -> Option<Vec<usize>>`, которая повторно использует `find_order` с другим
правилом: раньше обязан идти только **более ранний вызов того же клиента**; реальное время между разными клиентами не
важно. Проверьте два случая: история 2 (устаревшее чтение другим клиентом) не линеаризуема, но последовательно
согласована, с порядком `[1, 0]`; а история, в которой клиент A пишет 1, а затем **сам** читает 0, не является
последовательно согласованной.

<details>
<summary>Подсказка</summary>

Правило — `a.client == b.client && a.start < b.start`. Напишите его как обычную `fn` с сигнатурой `Rule` и передайте её
имя в `find_order`.

</details>

<details>
<summary>Ответ</summary>

```rust
//! Exercise 3: sequential consistency.

use crate::{Call, find_order};

/// Sequential consistency: only the order of each client's own calls must be kept.
fn same_client_earlier(a: &Call, b: &Call) -> bool {
    a.client == b.client && a.start < b.start
}

pub fn sequentialize(history: &[Call]) -> Option<Vec<usize>> {
    find_order(history, same_client_earlier)
}

#[cfg(test)]
mod tests {
    use super::*;
    use crate::{Op, linearize};

    fn call(client: char, start: u32, end: u32, op: Op) -> Call {
        Call {
            client,
            start,
            end,
            op,
        }
    }

    #[test]
    fn another_clients_stale_read_is_allowed() {
        let history = [
            call('A', 0, 10, Op::Write(1)),
            call('B', 20, 30, Op::Read(0)),
        ];
        assert_eq!(linearize(&history), None);
        assert_eq!(sequentialize(&history), Some(vec![1, 0]));
    }

    #[test]
    fn a_client_must_see_its_own_write() {
        let history = [
            call('A', 0, 10, Op::Write(1)),
            call('A', 20, 30, Op::Read(0)),
        ];
        assert_eq!(sequentialize(&history), None);
    }
}
```

`cargo test --lib`:

```text
test result: ok. 5 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Почему это работает: последовательная согласованность разрешает порядок «B читает 0, затем A пишет 1», потому что B и
A — разные клиенты, а значение имеет только собственный порядок каждого клиента. Но она всё равно не позволяет
клиенту пропустить собственную запись. То, что две программы проверки отличаются одним маленьким правилом,
показывает, насколько близки определения.

</details>

## Вопросы для самопроверки

1. Что такое модель согласованности?

<details>
<summary>Ответ</summary>

Контракт между хранилищем данных и его клиентами, который говорит, какие значения могут вернуть чтения с учётом
произошедших записей.

</details>

2. Запись закончилась в 10 мс. Чтение другого клиента началось в 20 мс и вернуло старое значение. Какие модели нарушает
   эта история: линеаризуемость, последовательную, в конечном счёте?

<details>
<summary>Ответ</summary>

Она нарушает линеаризуемость (реальное время). Она может быть последовательно согласованной (чтение ставится до
записи) и согласованной в конечном счёте.

</details>

3. Почему история 4 («новое, потом старое») не линеаризуема, хотя оба чтения перекрываются с записью?

<details>
<summary>Ответ</summary>

Чтения не перекрываются друг с другом: чтение B закончилось до начала чтения C, поэтому B должно сработать первым. B
увидело новое значение, значит, запись уже сработала, и C больше не может увидеть старое значение.

</details>

4. Сформулируйте теорему CAP правильно.

<details>
<summary>Ответ</summary>

При сетевом разделении система должна выбрать между линеаризуемостью и доступностью: либо часть запросов
отклоняется, либо часть ответов может быть устаревшей.

</details>

5. Какая согласованность нужна для «имя пользователя должно быть уникальным», а какая — для «числа лайков»?

<details>
<summary>Ответ</summary>

Уникальности нужна линеаризуемость (или транзакция на одном лидере), иначе два пользователя могут в один момент занять
одно имя. Счётчику лайков достаточно согласованности в конечном счёте.

</details>

## Итоги

- Модель согласованности — контракт о том, какие значения могут вернуть чтения. С более сильными моделями проще
  работать; более слабые позволяют строить более быстрые и доступные системы.
- Линеаризуемость: система ведёт себя как одна копия, и каждая операция срабатывает в один момент между своим началом
  и концом. Реальное время имеет значение.
- Маленький поиск с возвратом может проверить историю на линеаризуемость; с другим правилом он проверяет
  последовательную согласованность.
- Последовательная, причинная согласованность и согласованность в конечном счёте слабее; гарантии сессии («читай свои
  записи», монотонные чтения) защищают опыт одного клиента.
- CAP: при разделении выбирайте линеаризуемость или доступность. Без разделения компромисс — задержка против
  согласованности.
- Выбирайте для каждой возможности: уникальности, деньгам и лидерству нужна линеаризуемость; счётчикам и лентам — нет.
