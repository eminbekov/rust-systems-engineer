## Новые слова

| Слово | Значение |
|---|---|
| **профилировщик** (profiler) | Инструмент, который показывает, на что работающая программа тратит время. |
| **семплирующий профилировщик** (sampling profiler) | Профилировщик, который много раз в секунду (например, 1000 раз) останавливает программу и каждый раз записывает стек вызовов. Функции, которые попадают во многие замеры, — это то, куда уходит время. |
| **замер** (sample) | Один снимок: «в этот момент этот поток выполнял вот эту цепочку функций». |
| **стек вызовов** (call stack) | Цепочка функций, которые выполняются прямо сейчас: `main` вызвала `count_words`, та вызвала `normalize`, а та — `to_lowercase`. |
| **собственное время** (self time) | Замеры, в которых функция выполнялась сама (была на вершине стека). |
| **общее время** (total time) | Замеры, в которых функция была где угодно в стеке: её собственная работа плюс всё, что она вызвала. Ещё называется *running time* или *включающее время* (inclusive time). |
| **горячая точка** (hot spot) | Небольшая часть кода, которая забирает большую долю времени. |
| **флеймграф** (flame graph) | Картинка из множества стеков: каждая функция — прямоугольник, его ширина показывает долю замеров, прямоугольники над ним — функции, которые она вызвала. |
| **отладочная информация** (debug info) | Дополнительные данные в бинарнике, которые связывают машинный код с именами функций, файлами и номерами строк. |
| **символ / символизация** (symbol / symbolication) | Символ — имя функции в бинарнике. Символизация превращает сырые адреса кода из профиля в эти имена. |
| **встраивание** (inlining) | Оптимизация: компилятор копирует маленькую функцию в вызывающую, и во время работы отдельного вызова нет. |
| **искажённое имя** (mangled name) | Закодированная форма имени функции Rust внутри бинарника, например `_RNvCs7wEbHSVyFlW_12p19_wordfreq9normalize`. **Деманглинг** (demangling) превращает его обратно в `p19_wordfreq::normalize`. |

## 1. Как работает семплирующий профилировщик

Представьте, что вы хотите узнать, на что коллега тратит рабочий день. Можно ходить за ним с секундомером и записывать каждую задачу (это **инструментирование**, instrumentation, как спаны из Урока 09.10). А можно раз в десять минут заглядывать к нему в экран и записывать, что там. Через неделю, если «почта» встречается в 40% записей, он тратит на почту около 40% дня. Второй способ — **семплирование**: дёшево и достаточно точно, когда замеров много.

Семплирующий профилировщик делает то же с вашей программой. Примерно 1000 раз в секунду он на мгновение останавливает поток и записывает весь **стек вызовов**:

```text
sample 1:  main > count_words > normalize > to_lowercase
sample 2:  main > count_words > normalize > collect > grow > malloc
sample 3:  main > count_words > free
sample 4:  main > count_words > normalize > to_lowercase
...
```

Из тысяч таких строк профилировщик вычисляет два числа для каждой функции:

- **Собственное время:** в скольких замерах функция стояла в *конце* строки (делала свою работу). В четырёх замерах выше у `to_lowercase` собственное время 2.
- **Общее время:** в скольких замерах функция была *где угодно* в строке. У `normalize` общее время 3, у `count_words` — 4.

Функция с большим общим и маленьким собственным временем — «менеджер»: она медленная из-за того, что вызывает. Функция с большим собственным временем сама делает дорогую работу.

> ⚡ **Производительность:** профилировщик измеряет, *куда* уходит время, а не *насколько быстра* программа. Профилирование немного замедляет программу, а числа приблизительны (функция на 2% может показаться как 1% или 3%). Для сравнения скорости «до и после» используйте `hyperfine` или `criterion`; профилировщик нужен, чтобы решить, *что* менять.

## 2. Сборка для профилирования

Профилировщику нужны от бинарника две вещи:

1. **Оптимизированный код.** Отладочная сборка тратит время там, где release-сборка не тратит никогда. Профилируйте то, что поставляете.
2. **Отладочная информация** — чтобы профилировщик мог превратить адреса кода в имена функций, файлов и номера строк, включая функции, которые оптимизатор **встроил** в вызывающие.

В release-сборке по умолчанию отладочной информации нет. Вместо того чтобы менять `release`, добавьте в `Cargo.toml` отдельный **профиль** (profile), который наследует всё от `release` и добавляет отладочную информацию:

```toml
[profile.profiling]
inherits = "release"
debug = true
```

Собирайте командой `cargo build --profile profiling`; бинарники попадают в `target/profiling/`. Машинный код тот же, что в `target/release/`, добавлена только отладочная информация.

> 💡 **Совет:** чтобы быстро пройти по стеку вызовов, профилировщики идут по цепочке **указателей кадра** (frame pointers), которые каждая функция хранит в стеке. На Mac с Apple Silicon платформа требует указатели кадра, поэтому всё работает сразу. В Linux их часто нет; что делать там, показывает Урок 19.4.

## 3. Программа для профилирования

Мы будем профилировать счётчик частоты слов: он читает большой текстовый файл, превращает каждое слово в строчные буквы и цифры, пропускает частые «стоп-слова», считает остальные в `HashMap` и печатает десять самых частых. Он правильный — и медленнее, чем мог бы быть. Этот пакет растёт с Урока 19.3 по 19.5.

```bash
cd ~/projects/rust/code
cargo new p19-wordfreq
cd p19-wordfreq
mkdir src/bin
echo "words.txt" >> .gitignore
```

Последняя строка не пускает большой тестовый файл в Git. Теперь добавьте в `Cargo.toml` раздел `[profile.profiling]` из раздела 2.

Сначала генератор тестовых данных, `src/bin/gen.rs`. Он пишет выдуманные слова из слогов — при одинаковых аргументах всегда один и тот же файл:

```rust
//! Writes a big test file of pseudo-random English-like words.
//! Usage: cargo run --release --bin gen -- words.txt 25000000
use std::env;
use std::fs::File;
use std::io::{BufWriter, Write};

/// A tiny pseudo-random number generator (xorshift). Same seed, same file.
struct Rng(u64);

impl Rng {
    fn next(&mut self) -> u64 {
        self.0 ^= self.0 << 13;
        self.0 ^= self.0 >> 7;
        self.0 ^= self.0 << 17;
        self.0
    }
}

fn main() -> std::io::Result<()> {
    let args: Vec<String> = env::args().collect();
    let path = args.get(1).map(String::as_str).unwrap_or("words.txt");
    let count: usize = args.get(2).map(|s| s.parse().unwrap()).unwrap_or(3_000_000);

    let syllables = [
        "ka", "lo", "mi", "ne", "ru", "sta", "the", "an", "is", "or", "pre", "ing",
    ];
    let mut rng = Rng(0x2545_F491_4F6C_DD1D);
    let mut out = BufWriter::new(File::create(path)?);
    for i in 0..count {
        // Short words are much more common than long ones.
        let len = 1 + (rng.next() % 4) as usize * (rng.next() % 2) as usize;
        let mut word = String::new();
        for _ in 0..len {
            word.push_str(syllables[(rng.next() % syllables.len() as u64) as usize]);
        }
        if rng.next().is_multiple_of(10) {
            word = word.to_uppercase(); // some words are in capitals
        }
        let end = match rng.next() % 20 {
            0 => ". ",
            1 => ", ",
            _ => " ",
        };
        write!(out, "{word}{end}")?;
        if i % 15 == 14 {
            writeln!(out)?;
        }
    }
    out.flush()
}
```

Затем сам счётчик, `src/main.rs`:

```rust
//! Counts how often each word appears in text files and prints the top 10.
//! Usage: p19-wordfreq <file>...
use std::collections::HashMap;
use std::env;
use std::fs;

/// Words that are too common to be interesting.
const STOP_WORDS: [&str; 24] = [
    "a", "an", "and", "are", "as", "at", "be", "by", "for", "from", "has", "in", "is", "it", "its",
    "of", "on", "or", "that", "the", "to", "was", "were", "with",
];

/// Lowercase letters and digits only: "The," -> "the".
#[inline(never)]
fn normalize(word: &str) -> String {
    word.to_lowercase()
        .chars()
        .filter(|c| c.is_alphanumeric())
        .collect()
}

#[inline(never)]
fn is_stop_word(word: &str) -> bool {
    STOP_WORDS.contains(&word)
}

#[inline(never)]
fn count_words(text: &str, counts: &mut HashMap<String, usize>) {
    for raw in text.split_whitespace() {
        let word = normalize(raw);
        if word.is_empty() || is_stop_word(&word) {
            continue;
        }
        *counts.entry(word).or_insert(0) += 1;
    }
}

fn top(counts: &HashMap<String, usize>, n: usize) -> Vec<(String, usize)> {
    let mut all: Vec<(String, usize)> = counts.iter().map(|(w, c)| (w.clone(), *c)).collect();
    // Most frequent first; equal counts in alphabetical order.
    all.sort_by(|a, b| b.1.cmp(&a.1).then(a.0.cmp(&b.0)));
    all.truncate(n);
    all
}

fn main() {
    let paths: Vec<String> = env::args().skip(1).collect();
    assert!(!paths.is_empty(), "usage: p19-wordfreq <file>...");
    let mut counts = HashMap::new();
    for path in &paths {
        let text = fs::read_to_string(path).expect("cannot read the file");
        count_words(&text, &mut counts);
    }
    println!("{} different words", counts.len());
    for (word, count) in top(&counts, 10) {
        println!("{count:>8} {word}");
    }
}
```

**Что происходит:**

1. `main` читает каждый файл в один `String` и передаёт его в `count_words`.
2. `count_words` делит текст по пробельным символам. Для каждого куска вызывает `normalize`, пропускает пустые слова и стоп-слова и прибавляет 1 в словаре. `entry(word).or_insert(0)` вставляет 0 для нового слова и возвращает изменяемую ссылку на счётчик.
3. `normalize` переводит всё слово в нижний регистр (`to_lowercase` создаёт новый `String`), затем оставляет только буквы и цифры и собирает их в *ещё один* новый `String`.
4. `top` копирует словарь в вектор, сортирует его и оставляет первые `n`.
5. `#[inline(never)]` просит компилятор не встраивать эти маленькие функции. Оптимизированный код обычно растворил бы их в `count_words`. `samply` благодаря отладочной информации всё равно показывает встроенные функции, а более простые инструменты, такие как `sample` (раздел 6), — нет, поэтому, пока мы изучаем профиль, оставляем их настоящими функциями.

Сгенерируйте 25 миллионов слов (около 130 МБ, мегабайт) и запустите счётчик:

```bash
cargo run --release --bin gen -- words.txt 25000000
cargo build --release
time ./target/release/p19-wordfreq words.txt
```


## 4. Записываем профиль с samply

`samply` — семплирующий профилировщик для macOS и Linux. Он записывает профиль и показывает его в **Firefox Profiler** — веб-странице, которая работает в вашем браузере и читает данные с маленького локального веб-сервера, запущенного `samply`. Данные остаются на вашем компьютере, пока вы не нажмёте кнопку загрузки.

```bash
cargo install --locked samply
samply --version
```

```text
samply 0.13.1
```

Соберите бинарник для профилирования и запишите профиль. `--save-only` пишет файл и пока не открывает браузер:

```bash
cargo build --profile profiling
samply record --save-only -o profile.json.gz ./target/profiling/p19-wordfreq words.txt
```

Программа работает как обычно и печатает свой привычный вывод. Теперь откройте профиль:

```bash
samply load profile.json.gz
```

Браузер открывает Firefox Profiler. Вот что вы видите (словами, потому что это интерактивная страница):

- **Наверху — временная шкала:** одна дорожка для нашего потока с графиком загрузки CPU (Central Processing Unit, центральный процессор) за две секунды. Можно выделить мышью часть шкалы и смотреть только этот отрезок времени.
- **Ниже — вкладки:** *Call Tree*, *Flame Graph*, *Stack Chart* и *Marker Chart*. Начните с *Call Tree*.
- **Call Tree** (дерево вызовов) — дерево функций, начиная со `start` и `main`. В каждой строке есть *Running Time* (общее число замеров, в миллисекундах) и *Self* (собственные замеры). Раскрывайте дерево маленькими треугольниками. Идя за самыми большими числами, вы доберётесь до `p19_wordfreq::count_words` (около 97% времени работы), а под ней — до `p19_wordfreq::normalize` (около 50%).
- **Внутри `normalize`** вы найдёте `<str>::to_lowercase` (около 15%) и сборку символов в `String`, где большая часть времени уходит в `RawVecInner::finish_grow` и функции аллокатора из `libsystem_malloc.dylib` (около 27%). Это строка, которая снова и снова растёт, пока в неё кладут символы.
- **Рядом с `normalize`**, прямо под `count_words`, есть большой блок в `libsystem_malloc.dylib` (около 15–20%): это `free`, который возвращает память только что созданных строк. На macOS он даже вызывает внутри аллокатора `mach_absolute_time` — функцию часов.
- Работа `HashMap` (`rustc_entry`, `hash_one`) — всего около 4%, а чтение файла (`read_to_string`) — около 3%.
- **Флажок «Invert call stack»** переворачивает дерево: наверху оказываются функции с наибольшим *собственным* временем. Это самый быстрый способ ответить на вопрос «какой код на самом деле выполняется?».
- **Двойной щелчок по функции** открывает её исходный код с числом замеров рядом с каждой строкой.

Значит, догадка «в `HashMap`» была неверной. Около **трёх четвертей** времени уходит на создание и уничтожение маленьких строк в `normalize`. Это типично: медленная часть очень часто не там, где её ждёшь. Поэтому мы профилируем, прежде чем оптимизировать.

> 🔒 **Безопасность:** профиль содержит имена функций, пути к файлам, а иногда и аргументы командной строки. Firefox Profiler умеет загружать профиль, чтобы поделиться им по ссылке. Никогда не загружайте профили закрытого кода или программ, работающих с секретными данными.

## 5. Читаем флеймграф

Щёлкните вкладку *Flame Graph*. Те же данные теперь стали картинкой. Упрощённый рисунок нашего:

```text
          | malloc |                               |
          | grow   |                               |
    |to_lowercase| collect into String  |          |
    |          normalize                | free     |hash|
    |                 count_words                       |read|
    |                        main                            |
     <---------------------- 100% of samples ---------------->
```

Правила:

1. **Каждый прямоугольник — функция.** Прямоугольник прямо над другим — функция, которую тот вызвал.
2. **Ширина — доля замеров** (общее время). `normalize` примерно вдвое уже всей картинки, значит, она выполнялась примерно в половине замеров.
3. **Ось x — не время.** Прямоугольники отсортированы по алфавиту (или по размеру), а не по тому, когда они выполнялись. Чтобы увидеть порядок во времени, используйте вкладку *Stack Chart*.
4. **Верхние края — собственное время.** Где над прямоугольником ничего нет, выполнялась сама функция. Широкие «плато» наверху — горячие точки.
5. **Цвета нужны только для различения.** В некоторых инструментах они обозначают вид кода (ваш код, стандартная библиотека, система), но никогда не «горячо» или «холодно».

Читайте наш граф снизу: почти всё внутри `count_words`; внутри неё две широкие башни — `normalize` и `free`; внутри `normalize` две широкие части — `to_lowercase` и растущая строка. `HashMap` — тонкий прямоугольник.

## 6. Файл с флеймграфом: sample и inferno

Для исследования лучше всего вид в браузере. Чтобы вставить флеймграф в отчёт, pull request или чат, нужен файл. На macOS его можно сделать тремя небольшими инструментами:

- `sample` входит в macOS. Он подключается к работающему процессу на несколько секунд и пишет текстовый отчёт о его стеках вызовов.
- `inferno` (порт на Rust исходных скриптов FlameGraph) превращает такие отчёты в «свёрнутый» (collapsed) формат — одна строка на стек, с количеством — и рисует изображение SVG (Scalable Vector Graphics, масштабируемая векторная графика).
- `rustfilt` выполняет деманглинг имён Rust.

```bash
cargo install --locked inferno rustfilt
```

## 7. Исправить одно, проверить, измерить

Профиль говорит: `normalize` создаёт слишком много короткоживущих строк. `to_lowercase` строит один `String`, затем `collect` строит второй и наращивает его по шагам. Наши входные данные почти всегда в ASCII (American Standard Code for Information Interchange, американский стандартный код для обмена информацией: 128 базовых латинских букв, цифр и символов), а у ASCII гораздо более простое правило нижнего регистра. План:

- Для слов в ASCII: один `String` нужной ёмкости, заполняемый байт за байтом.
- Для всех остальных слов: в точности старый код, чтобы вывод не изменился.

Сначала сохраните старую программу, чтобы было с чем сравнивать: `cp src/main.rs src/bin/slow.rs`. Затем замените `normalize` в `src/main.rs`:

```rust
fn normalize(word: &str) -> String {
    if word.is_ascii() {
        // Fast path: one allocation of the right size, byte by byte.
        let mut out = String::with_capacity(word.len());
        for byte in word.bytes().filter(u8::is_ascii_alphanumeric) {
            out.push(char::from(byte.to_ascii_lowercase()));
        }
        out
    } else {
        // Rare path: the full Unicode rules, exactly as before.
        word.to_lowercase()
            .chars()
            .filter(|c| c.is_alphanumeric())
            .collect()
    }
}
```

(Оставьте над ней `#[inline(never)]` и doc-комментарий.) Для слова в ASCII оба пути дают одинаковый результат: строчная форма ASCII-буквы — это её строчная ASCII-форма, а `is_alphanumeric` истинно ровно для ASCII-букв и цифр. Упражнение 2 превращает это утверждение в тест.

**Сначала проверьте вывод**, потом измеряйте. Более быстрая программа с другим ответом — это ошибка:

```bash
cargo build --release
./target/release/slow words.txt > before.txt
./target/release/p19-wordfreq words.txt > after.txt
diff before.txt after.txt && echo "identical output"
hyperfine --warmup 1 --runs 10 './target/release/slow words.txt' './target/release/p19-wordfreq words.txt'
```

```text
identical output
Benchmark 1: ./target/release/slow words.txt (10 runs)
                mean     ±       σ          min     …     max
  Wall Time    1.745 s   ±   0.077 s      1.626 s   …   1.879 s
  Memory       130.6 MiB ±     0.8 MiB    129.1 MiB …   131.5 MiB
 
Benchmark 2: ./target/release/p19-wordfreq words.txt (10 runs)
                mean     ±       σ          min     …     max
  Wall Time    1.179 s   ±   0.047 s      1.134 s   …   1.280 s            -32.5%  (1.5x faster)
  Memory       131.1 MiB ±     0.5 MiB    130.4 MiB …   131.5 MiB           +0.4%
```

Одна маленькая функция — и вся программа в 1,5 раза быстрее при том же выводе. Теперь **профилируйте снова**: `cargo build --profile profiling`, запишите и откройте профиль, как в разделе 4. В новом профиле `normalize` занимает около трети времени, большой блок `free` сжимается до нескольких процентов, а `HashMap` (хеширование в `hash_one` и `write` от SipHash плюс `rustc_entry`) стал одной из самых больших частей — около 18%. Каждое исправление переносит горячую точку в другое место. Останавливайтесь, когда программа достаточно быстра для своей задачи, а не когда профиль стал «плоским».

> 🧪 **Тестирование:** перед каждой оптимизацией имейте тест, который закрепляет текущее поведение, и сохраняйте старую версию как эталон. Сравнение выводов старой и новой версий на множестве входов — один из самых сильных тестов для оптимизации.

## Частые ошибки

1. **Профилировать отладочную сборку.** Профиль тогда показывает адаптеры итераторов, проверки границ и другой код, который release-сборка убирает. Всегда профилируйте оптимизированный код (`--profile profiling`).
2. **Нет отладочной информации.** Без неё вы видите сырые адреса (`p19-wordfreq+0x1a2b4`) или только те немногие функции, которые не были встроены. Добавьте `debug = true` в профиль, которым пользуетесь для профилирования.
3. **Оптимизировать без профиля.** Мы думали на `HashMap`; на самом деле виновато выделение памяти под строки. Упражнение 3 показывает «умное» изменение, которое сделало программу медленнее.
4. **Читать ось x флеймграфа как время.** Она отсортирована по именам. Прямоугольник слева не выполнялся первым.
5. **Более быстрая версия с другими ответами.** Заманчивая однопроходная версия `normalize` переводит каждый символ в нижний регистр отдельно: `out.extend(c.to_lowercase())`. Она быстрая, но `str::to_lowercase` знает, что греческая заглавная сигма `Σ` в конце слова становится `ς`, а `char::to_lowercase` не может знать, где кончается слово. С этой версией тест из Упражнения 2 падает:

   ```text
   thread 'tests::fast_normalize_matches_the_reference' (6204647) panicked at src/main.rs:89:13:
   assertion `left == right` failed: input: "ΟΔΟΣ"
     left: "οδοσ"
    right: "οδος"
   ```

   Наши тестовые данные — ASCII, так что `diff` бы этого не заметил. Поэтому быстрый путь в разделе 7 обрабатывает только ASCII, а всё остальное оставляет старому коду.

## Упражнения

### Упражнение 1 — Прочитайте флеймграф (легко)

Флеймграф другой программы, упрощённо (ширина в % от всех замеров):

```text
                 | sha256 30% |
| parse_json 25% | hash_password 32% |  render 38%                |
|                         handle_request 95%                       | log 5% |
|                                main 100%                                  |
```

(а) У какой функции после `main` наибольшее общее время? (б) У какой — наибольшее собственное? (в) Над `render` ничего нет. Что это значит? (г) Вызывается ли `hash_password` раньше `render`?

<details>
<summary>Подсказка</summary>

Собственное время = ширина минус ширина прямоугольников прямо над ним. Ось x — не время.

</details>

<details>
<summary>Ответ</summary>

(а) `handle_request`, 95%. (б) `render`: 38% собственного, потому что над ним ничего нет. У `sha256` 30% собственного; у `parse_json` 25%; у `hash_password` всего 32 − 30 = 2% собственного. (в) Во всех своих замерах выполнялся сам `render` (или встроенный в него код): это отдельная горячая точка. (г) Узнать нельзя: прямоугольники отсортированы по имени или размеру, а не по времени. Чтобы увидеть порядок, используйте stack chart (вид по времени).

</details>

### Упражнение 2 — Тест, который охраняет оптимизацию (средне)

Добавьте в `src/main.rs` тестовый модуль, который хранит исходную `normalize` под именем `normalize_reference` и проверяет, что новая `normalize` даёт ровно тот же результат для таких входов: `"The,"`, `"HELLO"`, `"it's"`, `"--"`, `""`, `"a1b2"`, `"Straße"`, `"ÉCOLE"`, `"ΟΔΟΣ"`, `"日本語"`, `"🦀rust"`. Запустите его.

<details>
<summary>Подсказка</summary>

Положите входы в массив и пройдите по нему циклом. Добавьте вход в сообщение проверки (`"input: {word:?}"`), чтобы при падении было видно, *какой* вход сломался.

</details>

<details>
<summary>Ответ</summary>

```rust
#[cfg(test)]
mod tests {
    use super::*;

    /// The first, slow version: our reference for correct answers.
    fn normalize_reference(word: &str) -> String {
        word.to_lowercase()
            .chars()
            .filter(|c| c.is_alphanumeric())
            .collect()
    }

    #[test]
    fn fast_normalize_matches_the_reference() {
        let words = [
            "The,",
            "HELLO",
            "it's",
            "--",
            "",
            "a1b2",
            "Straße",
            "ÉCOLE",
            "ΟΔΟΣ",
            "日本語",
            "🦀rust",
        ];
        for word in words {
            assert_eq!(
                normalize(word),
                normalize_reference(word),
                "input: {word:?}"
            );
        }
    }
}
```

`cargo test` запускает тесты каждого бинарника в пакете; строка для `src/main.rs` показывает:

```text
test tests::fast_normalize_matches_the_reference ... ok
test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Почему это работает: входы покрывают ASCII-пунктуацию, цифры, пустую строку и слова не в ASCII, которые идут по медленному пути (немецкая `ß`, заглавная буква с ударением, греческое слово с конечной сигмой, японский текст, эмодзи). С однопроходной версией из «Частых ошибок» этот тест падает на `"ΟΔΟΣ"`.

</details>

### Упражнение 3 — Амдал и «умное» изменение (сложно)

В профиле быстрой версии `is_stop_word` и вызовы `memcmp`, которые она делает, занимают около 10% замеров. `STOP_WORDS` отсортирован, поэтому линейный `contains` можно заменить на `STOP_WORDS.binary_search(&word).is_ok()` (не больше 5 сравнений вместо 24). (а) По закону Амдала, каково *наилучшее* возможное ускорение всей программы? (б) Сделайте изменение в копии, измерьте его через `hyperfine` против текущей версии и объясните результат.

<details>
<summary>Подсказка</summary>

Если часть занимает 10% и становится бесконечно быстрой, вся программа занимает 90% времени. Для (б) подумайте, что первым делом делает `==` для двух `&str` и насколько предсказуемы ветвления двоичного поиска (Урок 12.6).

</details>

<details>
<summary>Ответ</summary>

(а) Не больше 1 ÷ 0,9 ≈ 1,11, то есть примерно на 11% быстрее — и то, только если проверка стоп-слов станет бесплатной.

(б) Сначала сохраните текущий бинарник (`cp target/release/p19-wordfreq ascii-wordfreq`), измените `is_stop_word`, пересоберите, скопируйте новый в `bsearch-wordfreq` и сравните:

```text
Benchmark 1: ./ascii-wordfreq words.txt (10 runs)
                mean     ±       σ          min     …     max
  Wall Time    2.339 s   ±   0.385 s      1.721 s   …   2.948 s
  Memory       129.6 MiB ±     0.1 MiB    129.4 MiB …   129.7 MiB
 
Benchmark 2: ./bsearch-wordfreq words.txt (10 runs)
                mean     ±       σ          min     …     max
  Wall Time    3.164 s   ±   0.433 s      2.641 s   …   3.889 s            +35.3%  (1.4x slower)
  Memory       129.7 MiB ±     0.2 MiB    129.5 MiB …   130.4 MiB           +0.1%
```

(Во время этого запуска Mac был занят, поэтому оба времени выше, чем в разделе 7; сравнивайте две строки между собой.) Двоичный поиск сделал программу *медленнее*. Сравнение двух `&str` через `==` сначала сравнивает их длины, а это сразу отсекает большинство стоп-слов и очень предсказуемо для предсказателя ветвлений. Двоичный поиск сравнивает строки буква за буквой (`"ka"` и `"for"`), а то, в какую половину он пойдёт, для каждого слова своё, и процессор часто ошибается в догадке. Меньше сравнений — не то же самое, что меньше времени. Оставьте линейную проверку, а измерение сохраните в заметках.

</details>

## Вопросы для самопроверки

1. Чем собственное время отличается от общего?

<details>
<summary>Ответ</summary>

Собственное время считает замеры, где выполнялась сама функция (вершина стека). Общее время считает замеры, где она была где угодно в стеке, включая время в функциях, которые она вызвала.

</details>

2. Почему мы добавляем `debug = true` в отдельный профиль `profiling`, а не профилируем отладочную сборку?

<details>
<summary>Ответ</summary>

Нам нужен оптимизированный машинный код release-сборки (именно он работает в продакшене) плюс имена и номера строк из отладочной информации. Отладочная сборка не оптимизирована и тратит время в других местах.

</details>

3. Во флеймграфе над широким прямоугольником ничего нет. О чём это говорит?

<details>
<summary>Ответ</summary>

Функция во многих замерах выполняла собственный код: у неё большое собственное время. Это горячая точка, на которую стоит посмотреть.

</details>

4. Показывает ли порядок слева направо во флеймграфе, что произошло раньше?

<details>
<summary>Ответ</summary>

Нет. Прямоугольники отсортированы (обычно по имени). Порядок во времени показывает stack chart или вид временной шкалы.

</details>

5. Функция занимает 4% замеров. Вы ускорили её вдвое. Насколько быстрее стала вся программа?

<details>
<summary>Ответ</summary>

Примерно на 2%: часть в 4% стала 2%, и программа занимает около 98% прежнего времени. Маленькие части профиля дают только маленький выигрыш (закон Амдала).

</details>

6. Почему профиль показал так много времени в `malloc` и `free` у программы, которая «просто считает слова»?

<details>
<summary>Ответ</summary>

Потому что `normalize` создавала два новых `String` для каждого из 25 миллионов слов (один в `to_lowercase`, другой в `collect`, который ещё и приходилось наращивать) и снова их удаляла. Каждое выделение и освобождение памяти стоит времени в аллокаторе.

</details>

## Итоги

- **Семплирующий профилировщик** записывает стек вызовов около 1000 раз в секунду; функции, которые попадают во многие замеры, — это то, куда уходит время.
- **Общее время** включает вызываемые функции; **собственное время** — работа самой функции. Ищите широкие прямоугольники, над которыми ничего нет.
- Профилируйте **оптимизированный код с отладочной информацией**: `[profile.profiling]`, который наследует `release` и задаёт `debug = true`.
- На macOS `samply record` + `samply load` открывают Firefox Profiler с деревом вызовов, перевёрнутым видом, флеймграфом и видом исходного кода.
- `sample` + `inferno-collapse-sample` + `rustfilt` + `inferno-flamegraph` делают SVG-флеймграф, которым можно поделиться.
- Цикл: профилировать, найти горячую точку, изменить одну вещь, **проверить, что вывод тот же**, измерить через `hyperfine`, профилировать снова.
- Догадки о производительности часто неверны, а «более умный» код может быть медленнее. Измеряйте.
