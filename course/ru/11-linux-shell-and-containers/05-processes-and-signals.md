## Новые слова

| Слово | Значение |
|---|---|
| **процесс** (process) | Работающий экземпляр программы со своей памятью, своим пользователем и своим номером. |
| **PID** (Process ID, идентификатор процесса) | Число, которое идентифицирует процесс. Ядро выдаёт следующее свободное число каждому новому процессу. |
| **PPID** (Parent PID, PID родителя) | PID процесса, который запустил данный. |
| **дерево процессов** (process tree) | У каждого процесса (кроме первого) есть родитель, поэтому процессы образуют дерево. |
| **PID 1** | Первый процесс, который запускает ядро. Он предок всех остальных. В нашей ВМ это `systemd` (Урок 11.6). |
| **передний план / фон** (foreground / background) | Задание на переднем плане удерживает терминал, пока не закончится. Фоновое задание работает, пока вы продолжаете печатать. |
| **задание** (job) | Команда (или конвейер), которую запустила ваша оболочка и за которой она следит. |
| **сигнал** (signal) | Небольшое сообщение, которое ядро или другой процесс посылает процессу, например «остановись». |
| **SIGTERM / SIGKILL** | Сигнал 15, «пожалуйста, завершись» (программа может отреагировать), и сигнал 9, «завершить немедленно» (ядро убивает процесс, реакция невозможна). |
| **код возврата** (exit status, exit code) | Число от 0 до 255, которое процесс оставляет, когда завершается. 0 означает успех; всё остальное — неудачу. |
| **зомби** (zombie) | Процесс, который завершился, но родитель ещё не прочитал его код возврата. Памяти не занимает, только запись в таблице процессов. |
| **сирота** (orphan) | Процесс, родитель которого завершился. Его усыновляет PID 1. |
| **демон** (daemon) | Процесс, который долго работает в фоне, обычно служба (Урок 11.6). |

## 1. Процессы: список и осмотр

Когда вы запускаете `ls`, оболочка просит у ядра новый процесс, программа выполняется, и процесс завершается. Долго работающая программа — то же самое, только дольше. Запустите один
процесс в фоне и посмотрите на него:

```bash
sleep 300 &
ps -o pid,ppid,user,stat,etime,cmd -p $!
```

```text
    PID    PPID USER     STAT     ELAPSED CMD
   4643    4640 student  S          00:00 sleep 300
```

(Ваши PID будут другими.) **Что происходит:**

1. `sleep 300` ждёт 300 секунд и ничего не делает. Символ `&` в конце запускает её в фоне (раздел 2), и оболочка продолжает работу.
2. `$!` — переменная оболочки, в которой хранится PID последнего фонового задания. `ps -p` выбирает именно этот процесс.
3. `-o` выбирает столбцы: `PID`, `PPID` (родитель: ваша оболочка), `USER`, `STAT` (состояние), `ELAPSED` (время с запуска) и `CMD` (командная строка).
4. `STAT` `S` означает *спит*: процесс чего-то ждёт (здесь таймер) и не использует процессор. Другие буквы: `R` работает, `T` остановлен, `Z` зомби, `D` ждёт диск. Знак `+` после буквы отмечает процесс переднего плана.

Обычно вы выводите сразу много процессов. Две классические формы (вывод длинный, поэтому фильтруем наш `sleep`):

```bash
ps aux | grep '[s]leep 300'
```

```text
student     4643  0.0  0.0  17096  6344 ?        S    07:00   0:00 sleep 300
```

**Что происходит:** `ps aux` выводит все процессы всех пользователей (`a`), со столбцом пользователя (`u`), включая процессы без терминала (`x`). Столбцы: `USER PID %CPU %MEM VSZ RSS TTY STAT START TIME COMMAND`: `%CPU` и `%MEM` — доли процессора и памяти, `VSZ` — размер виртуальной памяти, а `RSS` — реальная память в килобайтах, `TTY` — терминал (`?` означает, что его нет), `TIME` — использованное процессорное время.
Шаблон `'[s]leep 300'` находит процесс, но не сам `grep`, в чьей командной строке тоже есть `sleep 300`: скобки делают так, что шаблон не совпадает со своим собственным текстом.

Другие способы посмотреть:

| Команда | Что показывает |
|---|---|
| `ps -ef` | все процессы в «полном формате», включая PPID |
| `ps -o pid,ppid,stat,cmd --forest` | процессы в виде ASCII-дерева (нарисованного простыми символами ASCII, American Standard Code for Information Interchange; родители выше детей) |
| `pstree -p` | компактно нарисованное дерево с PID |
| `top` | живая таблица, отсортированная по процессору; выход по `q` (`top -b -n 1` печатает один снимок) |
| `pgrep -a sleep` | PID (и командные строки, с `-a`) процессов, в имени которых есть `sleep` |
| `ps aux --sort=-%mem \| head -n 5` | пять процессов, использующих больше всего памяти |

**Всё о процессе лежит в `/proc/<PID>/`** ([Урок 11.2](02-the-linux-file-system.md)):

```bash
P=$(pgrep -n -x sleep)
grep -E '^(Name|State|Pid|PPid|Uid)' /proc/$P/status
tr '\0' ' ' < /proc/$P/cmdline; echo
ls -l /proc/$P/cwd | cut -d' ' -f9-
```

```text
Name:	sleep
State:	S (sleeping)
Pid:	4643
PPid:	4640
Uid:	1000	1000	1000	1000
sleep 300 
/proc/4643/cwd -> /home/student
```

**Что происходит:** `pgrep -n -x sleep` возвращает самый новый процесс с именем ровно `sleep`. В `status` лежат имя, состояние, PID и идентификаторы пользователя; в `cmdline` — аргументы, разделённые нулевыми байтами (которые `tr` превращает в пробелы); `cwd` — символическая ссылка на текущий каталог процесса. `ps` и `top` просто читают эти файлы и форматируют их.

**Родители и дети.** Оболочка запустила `sleep`, поэтому оболочка — его родитель. Если родитель завершается первым, ребёнок становится **сиротой**, и его усыновляет PID 1. Если ребёнок завершился, а родитель не забрал его код возврата, ребёнок остаётся **зомби** (`Z` в `STAT`, `<defunct>` в `CMD`). Зомби почти ничего не стоит, но программа, которая создаёт их много, содержит ошибку: она никогда не вызывает `wait`.

## 2. Задания на переднем плане и в фоне

Обычная команда — это задание **переднего плана**: оболочка ждёт её, и терминал принадлежит ей. Сочетания клавиш обращаются к заданию переднего плана:

- `Ctrl + C` посылает сигнал **SIGINT** («прерывание»). Большинство программ останавливаются.
- `Ctrl + Z` посылает **SIGTSTP** («приостановка»). Задание ставится на паузу, и вы получаете приглашение обратно.
- `Ctrl + D` — не сигнал: это *конец ввода* (stdin закрыт). Оболочка на него завершается.

Настоящий сеанс выглядит так (`$ ` — приглашение, `^Z` и `^C` показывают, что выводит терминал при сочетании):

```text
$ sleep 300
^Z
[1]+  Stopped                    sleep 300
$ jobs
[1]+  Stopped                    sleep 300
$ bg
[1]+ sleep 300 &
$ jobs
[1]+  Running                    sleep 300 &
$ fg
sleep 300
^C
$ jobs
```

**Что происходит:**

1. `Ctrl + Z` приостанавливает `sleep`. Оболочка печатает `[1]+  Stopped`: задание номер 1, состояние Stopped (остановлено).
2. `jobs` перечисляет задания **этой** оболочки. `+` отмечает текущее задание, `-` — предыдущее.
3. `bg` («background», фон) возобновляет задание в фоне. Теперь оно работает, пока вы заняты своим.
4. `fg` («foreground», передний план) возвращает его, и оно снова удерживает терминал. `Ctrl + C` завершило его. Последний `jobs` ничего не печатает: заданий не осталось.

Можно сразу запустить задание в фоне через `&`: `sleep 300 &` печатает `[1] 4643` (номер задания и PID). Оболочка называет задания `%1`, `%2`, ...: `kill %1` останавливает задание 1, `fg %2` выводит задание 2 на передний план. `wait` ждёт завершения всех фоновых заданий.

> ⚠️ **Частая ошибка:** фоновое задание всё ещё привязано к вашему терминалу. Когда вы закрываете терминал, оболочка посылает своим заданиям `SIGHUP` («положили трубку»), и большинство из них останавливаются. Чтобы команда жила после вашего ухода, используйте `nohup command &` (он игнорирует SIGHUP и пишет вывод в `nohup.out`), а лучше **службу** (Урок 11.6) или мультиплексор терминала вроде `tmux`. Не полагайтесь на один `&` для того, что должно пережить выход.

## 3. Сигналы

**Сигнал** — это способ ядра тронуть процесс за плечо. У каждого есть номер и имя. Выведите их список:

```bash
kill -l | head -n 4
```

```text
 1) SIGHUP	 2) SIGINT	 3) SIGQUIT	 4) SIGILL	 5) SIGTRAP
 6) SIGABRT	 7) SIGBUS	 8) SIGFPE	 9) SIGKILL	10) SIGUSR1
11) SIGSEGV	12) SIGUSR2	13) SIGPIPE	14) SIGALRM	15) SIGTERM
16) SIGSTKFLT	17) SIGCHLD	18) SIGCONT	19) SIGSTOP	20) SIGTSTP
```

Те, что нужны каждый день:

| Сигнал | № | Значение | Может ли программа его перехватить? |
|---|---|---|---|
| `SIGHUP` | 1 | терминал закрыт; по соглашению многие службы используют его как «перечитай настройки» | да |
| `SIGINT` | 2 | прерывание (`Ctrl + C`) | да |
| `SIGKILL` | 9 | убить немедленно | **нет** |
| `SIGSEGV` | 11 | программа обратилась к недопустимой памяти (сбой) | да (редко полезно) |
| `SIGTERM` | 15 | вежливая просьба завершиться; значение `kill` по умолчанию | да |
| `SIGSTOP` | 19 | приостановить процесс | **нет** |
| `SIGCONT` | 18 | продолжить приостановленный процесс | да |

«Перехватить» значит: программа устанавливает **обработчик** — функцию, которая выполняется при получении сигнала вместо действия по умолчанию (для большинства сигналов это завершение). В обработчике программа может прибраться: закончить запись, закрыть соединения, удалить временный файл.
`SIGKILL` и `SIGSTOP` нельзя перехватить, игнорировать или заблокировать: ядро обрабатывает их само.

Команда `kill` посылает сигнал по PID или заданию (название историческое: она не всегда убивает):

```bash
sleep 300 &
kill $!
wait $!
echo "status: $?"
sleep 300 &
kill -9 $!
wait $!
echo "status: $?"
```

```text
status: 143
status: 137
```

**Что происходит:** `kill PID` посылает `SIGTERM` (15). `kill -9 PID` (то же, что `kill -KILL PID`) посылает `SIGKILL`. `wait $!` ждёт это задание и возвращает его код возврата, который мы печатаем (раздел 4 объясняет 143 и 137). Оболочка может также напечатать строку вроде `Killed  sleep 300` для второго задания.

Чтобы поставить процесс на паузу и возобновить, не завершая его:

```bash
sleep 300 &
kill -STOP $!
ps -o pid,stat,cmd -p $!
kill -CONT $!
ps -o pid,stat,cmd -p $!
kill $!
```

```text
    PID STAT CMD
   4713 T    sleep 300
    PID STAT CMD
   4713 S    sleep 300
```

**Что происходит:** `STAT` `T` означает остановлен; после `SIGCONT` снова `S`, и процесс продолжает с того места, где остановился.

По имени вместо PID:

```bash
sleep 301 & sleep 302 &
pkill -f 'sleep 30[12]'
pgrep -c -f 'sleep 30[12]'
```

```text
0
```

**Что происходит:** `pkill` посылает `SIGTERM` каждому подходящему процессу (`-f` сопоставляет всю командную строку, а не только имя). `pgrep -c` считает совпадения: осталось 0. `pkill` — мощная команда; сначала выполните `pgrep -a` с тем же шаблоном, чтобы увидеть, что она заденет.

> 🔒 **Безопасность:** посылать сигналы можно только своим процессам; для чужих нужен `sudo`. Правила хорошего тона: сначала `SIGTERM` (подождите несколько секунд), затем `SIGKILL`.
> `kill -9` не оставляет программе шанса прибраться: файлы могут остаться недописанными, блокировки — повиснуть, дочерние процессы — осиротеть. Это крайняя мера, а не привычка.

## 4. Код возврата

Когда процесс завершается, он оставляет родителю число — **код возврата**. Оболочка хранит последний в `$?`:

```bash
true; echo "true -> $?"
false; echo "false -> $?"
ls /nope 2>/dev/null; echo "ls /nope -> $?"
bash -c 'exit 3'; echo "exit 3 -> $?"
nosuchcommand 2>/dev/null; echo "nosuchcommand -> $?"
```

```text
true -> 0
false -> 1
ls /nope -> 2
exit 3 -> 3
nosuchcommand -> 127
```

**Что происходит:** по соглашению **0 = успех, всё остальное = неудача**. Команды `true` и `false` ничего не делают, только возвращают 0 и 1. `ls` возвращает 2, если файла нет. `127` — код оболочки для «команда не найдена». Каждая программа документирует свои коды (см. руководство: `man grep` говорит, что 0 = найдено совпадение, 1 = нет, 2 = ошибка).

Если процесс завершён сигналом, оболочка сообщает **128 + номер сигнала**:

| Код | Значение |
|---|---|
| 130 | завершён SIGINT (128 + 2): вы нажали `Ctrl + C` |
| 137 | завершён SIGKILL (128 + 9) |
| 143 | завершён SIGTERM (128 + 15) |

В Rust программа завершается с кодом 0, когда `main` возвращается нормально (или возвращает `Ok`), с кодом 1, когда `main` возвращает `Err`, с кодом 101 при панике и с любым числом по вашему выбору через `std::process::exit(code)`; Урок 11.3 использовал `exit(2)` для ошибки использования. Инструменты вроде `systemd` и скрипты решают, что делать дальше, по этим числам.

## 5. Программа на Rust, которая обрабатывает сигналы

Программы на Rust получают сигналы, как любой другой процесс. По умолчанию `SIGTERM` просто убивает программу. Служба, которая хранит данные, должна вместо этого **корректно завершаться**. Крейт `signal-hook` (версия 0.4) доставляет сигналы безопасным способом. Мы напишем небольшую программу `p11-heartbeat`, которую вы запустите и как службу в следующем уроке.

Создайте проект на вашем **Mac** (откройте вкладку терминала Mac):

```bash
cd ~/projects/rust
cargo new code/p11-heartbeat
cd code/p11-heartbeat
cargo add signal-hook@0.4
```

Замените `src/main.rs`:

```rust
use std::error::Error;
use std::thread;
use std::time::Duration;

use signal_hook::consts::{SIGHUP, SIGINT, SIGTERM};
use signal_hook::iterator::Signals;

/// What the program does when a signal arrives.
#[derive(Debug, PartialEq)]
enum Action {
    Reload,
    Stop,
}

/// Maps a signal number to an action. Other signals are ignored.
fn action_for(signal: i32) -> Option<Action> {
    match signal {
        SIGHUP => Some(Action::Reload),
        SIGTERM | SIGINT => Some(Action::Stop),
        _ => None,
    }
}

fn main() -> Result<(), Box<dyn Error>> {
    let name = std::env::var("HEARTBEAT_NAME").unwrap_or_else(|_| "world".to_string());
    let seconds: u64 = std::env::var("HEARTBEAT_SECONDS")
        .ok()
        .and_then(|text| text.parse().ok())
        .unwrap_or(2);

    println!(
        "starting: pid {}, greeting {name}, every {seconds} s",
        std::process::id()
    );

    // The worker thread prints one line per interval, forever.
    thread::spawn(move || {
        let mut count = 0;
        loop {
            count += 1;
            println!("heartbeat {count} from {name}");
            thread::sleep(Duration::from_secs(seconds));
        }
    });

    // The main thread waits for signals.
    let mut signals = Signals::new([SIGTERM, SIGINT, SIGHUP])?;
    for signal in signals.forever() {
        match action_for(signal) {
            Some(Action::Reload) => println!("got SIGHUP: pretend to reload the configuration"),
            Some(Action::Stop) => {
                println!("got signal {signal}: shutting down");
                break;
            }
            None => {}
        }
    }
    println!("bye");
    Ok(())
}

#[cfg(test)]
mod tests {
    use super::*;
    use signal_hook::consts::SIGUSR1;

    #[test]
    fn maps_signals_to_actions() {
        assert_eq!(action_for(SIGHUP), Some(Action::Reload));
        assert_eq!(action_for(SIGTERM), Some(Action::Stop));
        assert_eq!(action_for(SIGINT), Some(Action::Stop));
        assert_eq!(action_for(SIGUSR1), None);
    }
}
```

**Что происходит:**

1. `Signals::new([...])` просит ядро доставлять эти три сигнала программе как события вместо действия по умолчанию. `signals.forever()` ждёт (блокируется) и выдаёт номер каждого сигнала по мере прихода.
2. Рабочий **поток** (потоки изучают Урок 06.11 и Этап 14) печатает «heartbeat» каждые `seconds` секунд. Главный поток только ждёт сигналов.
3. `action_for` — чистая функция: число на входе, действие на выходе. Побочных эффектов нет, поэтому тест может проверить её без отправки настоящих сигналов. Это привычка из [Этапа 08](../08-software-design/README.md): отделять решение от ввода-вывода.
4. `SIGHUP` только печатает (настоящая служба перечитала бы настройки). `SIGTERM` и `SIGINT` печатают и выходят из цикла через `break`, поэтому `main` возвращает `Ok(())`, а код возврата равен 0.
5. Настройки берутся из **переменных окружения** (`HEARTBEAT_NAME`, `HEARTBEAT_SECONDS`) со значениями по умолчанию. Тогда службу можно настраивать без изменения кода ([Урок 08.15](../08-software-design/15-the-twelve-factor-app.md)).
6. `println!` буферизуется построчно, поэтому каждая строка появляется сразу; в том числе когда вывод идёт в файл или в журнал.

🧪 **Тестирование:** выполните `cargo test` на Mac. Ожидается `test tests::maps_signals_to_actions ... ok` и `test result: ok. 1 passed`.

Теперь соберите и запустите её **в ВМ**. В ВМ ещё нет Rust, а файлы Mac там доступны только для чтения, поэтому мы делаем три шага.

**Шаг 1 — инструменты для сборки.** Rust нужен *компоновщик* (linker), который поставляется с пакетом компилятора C `build-essential`. (`apt` — менеджер пакетов; Урок 11.7 объясняет его.)

```bash
sudo apt-get update
sudo apt-get install -y build-essential curl
```

**Шаг 2 — установите Rust в ВМ.** Используйте тот же установщик, что в [Уроке 00.5](../00-getting-started/05-install-rust-and-rustrover.md). Он ставит Rust в `~/.cargo` пользователя ВМ:

```bash
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y --profile minimal
. "$HOME/.cargo/env"
cargo --version
```

Пример вывода последней команды (у вас будет текущая версия):

```text

```

(`-s -- -y` передаёт установщику `-y`, чтобы принять значения по умолчанию; `--profile minimal` пропускает документацию. `. "$HOME/.cargo/env"` добавляет `~/.cargo/bin` в `PATH` этой оболочки; новые оболочки делают это сами.)

**Шаг 3 — скопируйте проект и соберите.** Замените `student` на имя, которое показывает `ls /Users`:

```bash
mkdir -p ~/code/p11-heartbeat
cd /Users/student/projects/rust/code/p11-heartbeat
cp -r Cargo.toml Cargo.lock src ~/code/p11-heartbeat/
cd ~/code/p11-heartbeat
cargo build --release
```

Мы копируем только `Cargo.toml`, `Cargo.lock` и `src`, но не папку `target/`, которую создала сборка на вашем Mac: в ней программы для macOS, которые Linux не запустит. Пример вывода (у вас будет похоже; первая сборка скачивает крейты и занимает от нескольких секунд до минуты):

```text

   Compiling signal-hook v0.4.6
   Compiling errno v0.3.15
   Compiling signal-hook-registry v1.4.8
   Compiling p11-heartbeat v0.1.0 (/home/student/code/p11-heartbeat)
    Finished `release` profile [optimized] target(s) in 3.64s
```

Программа — это `target/release/p11-heartbeat`. Запустите её в фоне, пошлите сигналы и посмотрите на код возврата (программа печатает каждые две секунды):

```bash
./target/release/p11-heartbeat &
sleep 4.5
kill -HUP $!
sleep 0.5
kill -TERM $!
wait $!
echo "exit status: $?"
```

```text
starting: pid 4750, greeting world, every 2 s
heartbeat 1 from world
heartbeat 2 from world
heartbeat 3 from world
got SIGHUP: pretend to reload the configuration
got signal 15: shutting down
bye
exit status: 0
```

**Что происходит:** `SIGHUP` не остановил программу, а только напечатал строку. `SIGTERM` (сигнал 15) завершил цикл, `main` напечатала `bye` и вернулась: **код возврата 0, корректное завершение**. Попробуйте `SIGKILL` и сравните:

```bash
./target/release/p11-heartbeat &
sleep 1
kill -KILL $!
wait $!
echo "exit status: $?"
```

```text
starting: pid 4754, greeting world, every 2 s
heartbeat 1 from world
exit status: 137
```

**Что происходит:** нет ни `got signal`, ни `bye`: после убийства программа не выполнила ни одной строки кода. Код равен 137 = 128 + 9. Посмотрите также, как работают переменные окружения:

```bash
HEARTBEAT_NAME=Alice HEARTBEAT_SECONDS=1 ./target/release/p11-heartbeat > hb.log &
sleep 2.5
kill $!
wait $!
cat hb.log
rm hb.log
```

```text
starting: pid 4763, greeting Alice, every 1 s
heartbeat 1 from Alice
heartbeat 2 from Alice
heartbeat 3 from Alice
got signal 15: shutting down
bye
```

**Что происходит:** настройки берутся из двух переменных, записанных перед командой (они существуют только для этого процесса). `> hb.log` отправляет stdout в файл, как в [Уроке 11.3](03-text-tools-pipes-and-redirection.md). Бинарный файл мы оставляем для Урока 11.6.

## Частые ошибки

1. **Начинать с `kill -9`.** Программа не может прибраться. *Исправление:* сначала `kill PID`, подождите, и `kill -9` только если она не завершилась.
2. **`pkill` с коротким шаблоном.** `pkill ssh` может остановить больше, чем вы хотели. *Исправление:* сначала проверьте `pgrep -a pattern`, используйте `-x` для точного имени.
3. **Расчёт на то, что `&` переживёт выход.** Задание получает `SIGHUP`, когда терминал закрывается. *Исправление:* `nohup`, `tmux` или служба (Урок 11.6).
4. **Слишком поздно читать `$?`.** `echo $?` показывает код *предыдущей* команды; любая команда между ними его заменяет. *Исправление:* сохраните сразу: `status=$?`.
5. **Игнорирование кода возврата в своих программах.** Программа на Rust, которая терпит неудачу, но завершается с 0, прячет сбой от скриптов и systemd. *Исправление:* верните `Err` из `main` или вызовите `std::process::exit` с ненулевым кодом.
6. **Забыли `. "$HOME/.cargo/env"`** после установки Rust: `cargo: command not found`. *Исправление:* выполните его или откройте новую оболочку через `exit` и `limactl shell dev`.

## Попробуйте сами

1. Дважды запустите `sleep 500 &`. Выведите их через `jobs` и через `pgrep -a sleep`. Остановите задание 1 командой `kill %1` и проверьте `jobs`.
2. Выполните `sleep 500`, нажмите `Ctrl + Z`, затем `bg`, затем `fg`, затем `Ctrl + C`. Напечатайте `$?`. Ожидается: `130`.
3. В `/proc/$$` (PID вашей оболочки лежит в `$$`) найдите файл `status` и напечатайте строки `Name` и `PPid`. Кто родитель вашей оболочки? Проверьте командой `ps -o pid,cmd -p <тот PPid>`.
4. Запустите программу heartbeat в фоне. Пошлите `SIGHUP`, затем `SIGTERM` и напечатайте код возврата. Повторите с `SIGKILL`.
5. Уберите за собой: завершите оставленные `sleep` (`pkill -x sleep`) и проверьте `pgrep -a sleep`.

## Упражнения

### Упражнение 1 — Найти и остановить (легко)

Запустите три задания `sleep 600 &`. Одной командой остановите их все по имени, затем убедитесь, что ни одного не осталось.

<details>
<summary>Подсказка</summary>

`pkill` принимает имя. `-x` означает точное совпадение имени. `pgrep -c` считает совпадения.

</details>

<details>
<summary>Ответ</summary>

```bash
sleep 600 & sleep 600 & sleep 600 &
pkill -x sleep
pgrep -c -x sleep
```

```text
0
```

Почему это работает: `pkill -x sleep` посылает SIGTERM каждому процессу с именем ровно `sleep`; действие SIGTERM по умолчанию — завершение. `pgrep -c` печатает 0 совпадений.

</details>

### Упражнение 2 — Расшифруйте код (средне)

Скрипт завершился, и `echo $?` напечатал `143`. Другой напечатал `130`, третий — `127`. Что случилось с каждым? Проверьте ответ настоящими командами для 143 и 127.

<details>
<summary>Подсказка</summary>

Числа больше 128 означают «128 + номер сигнала». `kill -l 15` печатает имя сигнала 15.

</details>

<details>
<summary>Ответ</summary>

- `143` = 128 + 15: процесс завершил `SIGTERM`.
- `130` = 128 + 2: завершён `SIGINT` (`Ctrl + C`).
- `127`: оболочка не нашла команду.

```bash
sleep 300 &
kill $!
wait $!; echo $?
nosuchcommand; echo $?
```

```text
143
bash: nosuchcommand: command not found
127
```

Почему это работает: оболочка превращает «убит сигналом N» в код `128 + N` и использует 127 для «команда не найдена» (126 — «найдена, но не исполняема»).

</details>

### Упражнение 3 — Добавьте SIGUSR1 и тест (сложно)

Научите `p11-heartbeat` новому сигналу: по `SIGUSR1` печатать `status: running`. Напишите **тест сначала**: расширьте тест проверкой, что `action_for(SIGUSR1)` возвращает новый `Action::Status`, посмотрите, как он падает, затем сделайте так, чтобы он прошёл.

<details>
<summary>Подсказка</summary>

Добавьте в перечисление вариант `Status`, добавьте `SIGUSR1` в `Signals::new([...])` и в `match` внутри `action_for`. Импортируйте `SIGUSR1` из `signal_hook::consts` в основном коде; тестовый модуль видит его через `use super::*;`.

</details>

<details>
<summary>Ответ</summary>

Сначала измените тест: замените последнее утверждение на `assert_eq!(action_for(SIGUSR1), Some(Action::Status));` (программа пока не компилируется: красный). Затем сделайте так, чтобы он прошёл:

```rust
use signal_hook::consts::{SIGHUP, SIGINT, SIGTERM, SIGUSR1};

#[derive(Debug, PartialEq)]
enum Action {
    Reload,
    Status,
    Stop,
}

fn action_for(signal: i32) -> Option<Action> {
    match signal {
        SIGHUP => Some(Action::Reload),
        SIGUSR1 => Some(Action::Status),
        SIGTERM | SIGINT => Some(Action::Stop),
        _ => None,
    }
}
```

В `main` зарегистрируйте сигнал через `Signals::new([SIGTERM, SIGINT, SIGHUP, SIGUSR1])?` и добавьте в `match` ветку `Some(Action::Status) => println!("status: running"),`. Тестовый модуль теперь выглядит так (`use super::*;` уже приносит `SIGUSR1`; `SIGUSR2` — сигнал, который остаётся неизвестным):

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use signal_hook::consts::SIGUSR2;

    #[test]
    fn maps_signals_to_actions() {
        assert_eq!(action_for(SIGHUP), Some(Action::Reload));
        assert_eq!(action_for(SIGTERM), Some(Action::Stop));
        assert_eq!(action_for(SIGINT), Some(Action::Stop));
        assert_eq!(action_for(SIGUSR1), Some(Action::Status));
        assert_eq!(action_for(SIGUSR2), None);
    }
}
```

`cargo test` сообщает `1 passed`. Проверьте вручную в ВМ: `kill -USR1 $!` печатает `status: running`, и программа продолжает работать.

Почему это работает: чистую функцию `action_for` легко тестировать, а новое поведение добавляется ровно в одном месте на каждом слое: в перечислении, в сопоставлении, в регистрации и в обработчике.

</details>

## Вопросы для самопроверки

1. Чем отличается программа от процесса?

<details>
<summary>Ответ</summary>

Программа — это файл на диске. Процесс — её работающий экземпляр со своим PID, памятью и пользователем. У одной программы может быть много процессов.

</details>

2. Что означает `STAT` `T` в `ps`?

<details>
<summary>Ответ</summary>

Процесс остановлен (поставлен на паузу), например после `Ctrl + Z` или `SIGSTOP`.

</details>

3. Какие два сигнала процесс никогда не может перехватить?

<details>
<summary>Ответ</summary>

`SIGKILL` (9) и `SIGSTOP` (19).

</details>

4. Почему сначала пробуют `SIGTERM`, а потом `SIGKILL`?

<details>
<summary>Ответ</summary>

`SIGTERM` позволяет программе прибраться (закончить запись, закрыть соединения). `SIGKILL` завершает её сразу, без возможности прибраться.

</details>

5. Команда завершилась с кодом 137. Что это значит?

<details>
<summary>Ответ</summary>

128 + 9: её убил `SIGKILL`.

</details>

6. Что хранит `$!` и что хранит `$?`?

<details>
<summary>Ответ</summary>

`$!` — PID последнего фонового задания. `$?` — код возврата последней команды.

</details>

## Итоги

- Процесс — работающая программа с PID, родителем (PPID), пользователем и состоянием. Процессы образуют дерево с PID 1 в корне.
- `ps`, `pgrep`, `top` и `/proc/<PID>` показывают, что работает. `&`, `jobs`, `fg`, `bg` управляют заданиями вашей оболочки.
- Сигналы — сообщения процессам. `kill` их посылает (по умолчанию `SIGTERM`). `SIGKILL` и `SIGSTOP` перехватить нельзя.
- Будьте вежливы: сначала `SIGTERM`, `SIGKILL` в последнюю очередь. `pkill` ищет по имени; сначала проверьте через `pgrep -a`.
- Код возврата 0 означает успех; `128 + N` значит «завершён сигналом N» (130, 137, 143); 127 — «команда не найдена».
- Служба на Rust перехватывает `SIGTERM` (например, через `signal-hook`), заканчивает работу и возвращается из `main` с кодом 0.
- Отделяйте решение (`action_for`) от ввода-вывода, чтобы его можно было тестировать.
