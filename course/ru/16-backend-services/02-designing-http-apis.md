## Новые слова

| Слово | Значение |
|---|---|
| **REST** (REpresentational State Transfer, передача состояния представления) | Стиль проектирования HTTP API: API — это набор *ресурсов*, у каждого свой URL, и с ними работают стандартными HTTP-методами. |
| **ресурс** (resource) | Вещь, с которой API позволяет работать: задача, пользователь, список задач. У неё есть URL. |
| **представление** (representation) | Форма, в которой ресурс передаётся в запросе или ответе, обычно JSON. |
| **URL** (Uniform Resource Locator, единый указатель ресурса) | Полный адрес ресурса: `http://127.0.0.1:3000/tasks/7?done=true`. *Путь* — `/tasks/7`; *строка запроса* — `done=true`. |
| **JSON** (JavaScript Object Notation, нотация объектов JavaScript) | Текстовый формат данных, который использует почти каждый веб-API: `{"id": 7, "done": false}`. |
| **безопасный метод** (safe method) | Метод, который только читает и никогда ничего не меняет на сервере (`GET`, `HEAD`). |
| **идемпотентный метод** (idempotent method) | Метод, который даёт одинаковый эффект, отправить его один раз или десять (`GET`, `PUT`, `DELETE`). Клиент может безопасно повторить его после сетевой ошибки. |
| **код статуса** (status code) | Трёхзначное число в первой строке каждого ответа, которое говорит, чем закончился запрос (`200`, `404`, …). |
| **контракт** (contract) | Точное согласованное описание API: пути, методы, тела, коды статуса. На него опираются обе стороны. |
| **пагинация** (pagination) | Выдача длинного списка страницами (например, по 50 элементов), а не целиком. |
| **ломающее изменение** (breaking change) | Изменение API, из-за которого существующие клиенты перестают работать, например переименование поля JSON. |

## 1. Что такое REST

Урок 15.8 показал, что HTTP — это просто текст: метод, путь, заголовки и тело. Сам HTTP не говорит,
**какие** пути и методы должны быть у вашего API. Можно спроектировать API так:

```text
POST /createTask        POST /getTask?id=7        POST /deleteTaskNow
```

Это работает, но каждый такой API устроен по-своему, и клиентам приходится изучать каждый с нуля. **REST** —
распространённый стиль, который делает API предсказуемыми. Его главные идеи простыми словами:

1. **Всё — ресурс с URL.** Список задач — `/tasks`. Задача номер 7 — `/tasks/7`. URL — это
   **существительные**, никогда не глаголы.
2. **Метод — это глагол.** `GET /tasks/7` читает задачу 7. `DELETE /tasks/7` удаляет её. Вы не
   придумываете новые глаголы, а используете те немногие, что уже есть в HTTP.
3. **Ресурсы передаются в виде представлений,** обычно JSON. Сервер отправляет
   `{"id":7,"title":"Buy milk","done":false}`; неважно, как он хранит задачу внутри.
4. **Каждый запрос самостоятелен.** Запрос несёт всё, что нужно серверу (в том числе, кто вы, Урок 16.8).
   Сервер не помнит «предыдущий запрос» клиента. Это подходит к сервисам без состояния из Урока 16.1.
5. **Коды статуса сообщают результат.** `200` — получилось, `404` — не найдено и так далее (раздел 3).

Клиент, который знает эти правила, может угадать большую часть вашего API, ничего не читая. В этом весь смысл.

## 2. Методы: глаголы HTTP

| Метод | Значение | Тело в запросе? | Безопасный | Идемпотентный | Типичный успех |
|---|---|---|---|---|---|
| `GET` | Прочитать ресурс или список | нет | да | да | `200 OK` |
| `POST` | Создать новый ресурс в коллекции (или выполнить действие) | да | нет | **нет** | `201 Created` |
| `PUT` | Полностью заменить ресурс | да | нет | да | `200 OK` |
| `PATCH` | Изменить некоторые поля ресурса | да | нет | обычно нет\* | `200 OK` |
| `DELETE` | Удалить ресурс | нет | нет | да | `204 No Content` |

\* `PATCH`, который присваивает поля (`{"done": true}`), на практике идемпотентен; тот, что прибавляет к значению, — нет.

**Безопасный** значит «только читает». Браузеры, кэши и поисковые роботы могут отправлять запросы `GET`
когда угодно, поэтому `GET` **никогда** не должен менять данные. Ссылка вида `GET /tasks/7/delete` — настоящая
ошибка: программа, которая проверяет все ссылки на странице, удалит ваши задачи.

**Идемпотентный** значит «сделать дважды — то же самое, что сделать один раз». Это важно, потому что сети
дают сбои. Представьте: клиент отправляет `DELETE /tasks/7`, задача удалена, но ответ потерялся по дороге
назад. Клиент не знает, что произошло, и отправляет запрос снова. Второй `DELETE` не находит, что удалять,
и итоговое состояние то же: задачи 7 нет. Повтор был безвреден.

Теперь представьте то же самое с `POST /tasks` (создать задачу). Первый запрос создал задачу 8, ответ
потерялся, и повтор создаёт задачу 9: **две** одинаковые задачи. `POST` не идемпотентен, поэтому клиенты не
должны повторять его вслепую. (Настоящие API решают это ключом идемпотентности — уникальным значением,
которое клиент отправляет с запросом, чтобы сервер узнал повтор. Этапы 18 и 20 возвращаются к повторным
попыткам.)

Метод и тело, которые отправляет `curl`, видно с `-v` («подробно»). `-d` задаёт тело (и заставляет `curl`
использовать `POST`), `-H` добавляет заголовок. Запустите `code/p16-hello` из Урока 16.1 и выполните:

```bash
curl -v -H 'content-type: application/json' -d '{"title":"Buy milk"}' http://127.0.0.1:3000/health
```

```text
*   Trying 127.0.0.1:3000...
* Connected to 127.0.0.1 (127.0.0.1) port 3000
> POST /health HTTP/1.1
> Host: 127.0.0.1:3000
> User-Agent: curl/8.7.1
> Accept: */*
> content-type: application/json
> Content-Length: 20
>
* upload completely sent off: 20 bytes
< HTTP/1.1 405 Method Not Allowed
< allow: GET,HEAD
< content-length: 0
< date: Wed, 18 Nov 2026 07:02:39 GMT
<
* Connection #0 to host 127.0.0.1 left intact
```

**Что происходит:**

1. Строки со `*` — собственные заметки `curl`: он подключается к порту.
2. Строки с `>` — то, что `curl` **отправляет**: строку запроса `POST /health HTTP/1.1`, заголовки и 20 байт
   JSON-тела (`-v` его не печатает). `content-type: application/json` сообщает серверу, что лежит в теле.
3. Строки с `<` — то, что **отвечает** сервер. `/health` разрешает только `GET`, поэтому `405`.

Именно в такой форме вы будете вызывать `curl`, чтобы создавать задачи в следующем уроке.

## 3. Коды статуса

Первая цифра задаёт класс:

| Класс | Значение | Чья «вина» |
|---|---|---|
| `2xx` | Успех | — |
| `3xx` | Идите в другое место (перенаправление) | — |
| `4xx` | Запрос неверный; повтор без изменений снова не сработает | клиента |
| `5xx` | Сервер дал сбой; тот же запрос может сработать позже | сервера |

Коды, которые нужны почти любому API:

| Код | Название | Когда использовать |
|---|---|---|
| `200` | OK | Чтение или изменение прошло успешно; в теле результат. |
| `201` | Created | `POST` создал ресурс. Добавьте заголовок `location` с его URL, например `location: /tasks/8`. |
| `204` | No Content | Получилось, и отправлять в ответ нечего (типично для `DELETE`). |
| `301` / `308` | Moved Permanently / Permanent Redirect | Ресурс навсегда живёт по другому URL (заголовок `location`). |
| `302` / `307` | Found / Temporary Redirect | В этот раз перейдите на другой URL. Сервис коротких ссылок (Урок 16.15) отвечает одним из них. |
| `400` | Bad Request | Запрос нельзя прочитать: сломанный JSON, неверный тип в строке запроса. |
| `401` | Unauthorized | Мы не знаем, кто вы: нет входа или неверный токен (Урок 16.8). |
| `403` | Forbidden | Мы знаем, кто вы, и вам это делать нельзя. |
| `404` | Not Found | Ресурса не существует (или вам не положено знать, что он существует). |
| `409` | Conflict | Запрос противоречит текущему состоянию, например «это имя уже занято». |
| `415` | Unsupported Media Type | Тело не в том формате, который принимает сервер (например, JSON без `content-type: application/json`). |
| `422` | Unprocessable Content | JSON корректен, но значения нарушают правило: пустой заголовок, отрицательная сумма. |
| `429` | Too Many Requests | Клиент отправил слишком много запросов; он должен притормозить (ограничение частоты запросов). |
| `500` | Internal Server Error | Ошибка в коде или неожиданный сбой в сервере. |
| `503` | Service Unavailable | Сервер сейчас не может работать (перегружен, база данных недоступна, идёт завершение). |

> ⚠️ **Частая ошибка:** отвечать `200 OK` с телом вроде `{"success": false}`. Клиенты, прокси, инструменты
> мониторинга и логика повторов сначала смотрят на код статуса. Если запрос не удался, код статуса должен
> об этом сказать.

> 🔒 **Безопасность:** для вещей, принадлежащих другим пользователям, `404` часто лучше, чем `403`. «Задача 7
> запрещена» сообщает злоумышленнику, что задача 7 существует; «не найдено» не сообщает ничего. В Уроке 10.3
> это называлось нарушением контроля доступа.

### Единое тело ошибки

Когда что-то не получилось, код статуса говорит, **какого рода** сбой, а тело объясняет, **какой именно**.
Выберите один формат ошибки и используйте его для **каждой** ошибки API, чтобы клиенты могли написать один
кусок кода для обработки ошибок. API задач использует:

```json
{"code": "validation_failed", "message": "title must not be empty"}
```

`code` — короткое стабильное слово, которое могут проверять программы (`not_found`, `validation_failed`,
`bad_request`, `internal`). `message` — для людей и может меняться. Для этого есть и стандартный формат —
*Problem Details for HTTP APIs* (RFC 9457, отправляется как `application/problem+json`); большие API часто
используют его. RFC (Request for Comments, «запрос комментариев») — так называются документы, которые
определяют стандарты интернета.

> 🔒 **Безопасность:** ответ `500` никогда не должен содержать внутренних подробностей: ни текста SQL (Structured Query Language, язык структурированных запросов), ни
> путей к файлам, ни трассировок стека. Пишите их в логи (Урок 16.12), а отправляйте только
> `{"code":"internal","message":"internal error"}`.

## 4. Проектирование URL и тел

Правила, которым следуют большинство хорошо спроектированных API:

- **Существительные во множественном числе для коллекций, идентификатор для одного элемента:** `/tasks`,
  `/tasks/7`. Не `/task/7` и не `/getTask`.
- **Пути строчными буквами, слова через `-`:** `/password-resets`, а не `/passwordResets`.
- **Вкладывайте, только когда вещь действительно принадлежит другой:** `/tasks/7/comments` перечисляет
  комментарии задачи 7. Ограничьтесь одним уровнем; глубокие пути вроде
  `/users/1/projects/2/tasks/7/comments` неудобны.
- **Строки запроса фильтруют, сортируют и разбивают списки на страницы:** `/tasks?done=false&limit=50`.
  Они никогда не обозначают один отдельный ресурс.
- **Один стиль имён для полей JSON.** `serde` в Rust использует имена полей вашей структуры, поэтому
  естественный выбор — `snake_case` (`created_at`). Не смешивайте `createdAt` и `created_at`.
- **Даты и время — текстом в формате RFC 3339,** всегда с часовым поясом: `"2026-11-18T07:02:39Z"`.
- **Идентификаторы непрозрачны.** Клиенты должны считать `7` именем и не заниматься с ним арифметикой.

**Пагинация.** `GET /tasks` не должен возвращать миллион строк. Верните страницу и дайте клиенту запросить
следующую: `GET /tasks?limit=50&offset=100` (пропустить 100, вернуть 50) — простейшая форма. Большие API
предпочитают *курсор*: `GET /tasks?limit=50&after_id=150` («50 задач после задачи 150»), который остаётся
быстрым и правильным, даже когда строки добавляются, пока клиент листает страницы.

**Версионирование.** Когда клиенты уже используют ваш API, ломающее изменение (переименование поля,
удаление эндпоинта, смена типа) ломает их. Добавить новое необязательное поле или новый эндпоинт безопасно.
Когда вам действительно нужно нарушить контракт, опубликуйте новую версию рядом со старой, часто с
префиксом: `/v1/tasks` и `/v2/tasks`, и удаляйте `v1`, только когда им больше не пользуется ни один клиент.

## 5. API задач

Вот контракт сервиса, который вы построите в следующих уроках. Запишите его **до** написания кода: изменить
таблицу гораздо дешевле, чем работающий API.

Задача передаётся так:

```json
{"id": 1, "title": "Buy milk", "done": false}
```

| Эндпоинт | Тело запроса | Успех | Ошибки |
|---|---|---|---|
| `GET /tasks` | — | `200`, JSON-массив задач, от старых к новым | — |
| `GET /tasks?done=false` | — | `200`, только задачи с этим значением `done` | `400`, если `done` не `true`/`false` |
| `POST /tasks` | `{"title": "Buy milk"}` | `201`, новая задача, заголовок `location: /tasks/{id}` | `400` сломанный JSON, `415` неверный тип содержимого, `422` нет поля или неверный заголовок |
| `GET /tasks/{id}` | — | `200`, задача | `404` |
| `PATCH /tasks/{id}` | `{"title": "…"}` и/или `{"done": true}` | `200`, изменённая задача | `404`, `422` |
| `DELETE /tasks/{id}` | — | `204`, без тела | `404` |
| `GET /health` | — | `200`, `ok` | — |

Правила: у заголовка обрезаются пробелы с обоих концов, и в нём должно быть от 1 до 200 символов. `{id}` —
положительное целое число. У каждой ошибки тело `{"code": "...", "message": "..."}`.

`{id}` в таблице — это **параметр пути**: изменяемая часть пути. В следующем уроке вы увидите, что axum
использует ровно такую запись.

Полный разговор с API будет выглядеть так (в Уроке 16.3 вы получите его сами):

```text
POST /tasks  {"title":"Buy milk"}      →  201  location: /tasks/1   {"id":1,"title":"Buy milk","done":false}
PATCH /tasks/1  {"done":true}          →  200  {"id":1,"title":"Buy milk","done":true}
GET /tasks?done=false                  →  200  []
DELETE /tasks/1                        →  204
GET /tasks/1                           →  404  {"code":"not_found","message":"task 1 not found"}
```

> 📏 **Соглашение:** храните контракт в репозитории рядом с кодом (например, в `API.md`) и обновляйте его в
> том же коммите, что и код. Большие команды пишут его в формате OpenAPI — стандартном машиночитаемом
> описании REST API; тогда инструменты могут генерировать по нему документацию и клиентский код.

> 🧪 **Тестирование:** каждая строка таблицы контракта — тестовый случай: один запрос, ожидаемый статус,
> ожидаемое тело. Урок 16.3 начинает писать такие тесты, а Урок 16.14 запускает их с настоящей базой данных.

## Частые ошибки

**1. Глаголы в URL.** `POST /tasks/7/delete` или `GET /deleteTask?id=7`. Используйте `DELETE /tasks/7`.
Версия с `GET` ещё и опасна (раздел 2).

**2. `200` на всё.** Ошибка со статусом `200` выглядит как успех для любого инструмента. Используйте
правильный код `4xx` или `5xx`.

**3. Разные формы ошибок.** Один эндпоинт отвечает `{"error":"..."}`, другой — простым текстом, третий —
`{"msg":"..."}`. Выберите один формат и используйте его везде.

**4. Незаметное изменение JSON.** Во время рефакторинга вы переименовываете поле структуры `title` в
`name`. `serde` послушно следует за ним, и все клиенты ломаются. Тест, который сравнивает точный JSON
(упражнение 3), это ловит.

**5. Возврат всего сразу.** `GET /tasks` без ограничения работает с десятью задачами и падает с десятью
миллионами. Планируйте пагинацию с самого начала.

## Упражнения

### Упражнение 1 — Выберите метод, путь и статус (легко)

Для каждого действия с API задач укажите метод, путь и код статуса при успехе:
(a) перечислить выполненные задачи; (b) отметить задачу 4 выполненной; (c) удалить задачу 9; (d) создать
задачу «Call mom»; (e) прочитать задачу 12, которой не существует.

<details>
<summary>Подсказка</summary>

Коллекции — `/tasks`, один элемент — `/tasks/{id}`. Изменение одного поля — это `PATCH`.

</details>

<details>
<summary>Ответ</summary>

(a) `GET /tasks?done=true` → `200`. (b) `PATCH /tasks/4` с `{"done": true}` → `200`.
(c) `DELETE /tasks/9` → `204`. (d) `POST /tasks` с `{"title": "Call mom"}` → `201` и заголовок
`location`. (e) `GET /tasks/12` → `404` с `{"code":"not_found",…}`.

Почему это работает: метод говорит, что сделать, путь — с чем, а код статуса — чем закончилось. (e) — вовсе
не «успех»: правильный ответ на отсутствующий ресурс — `4xx`, а не `200` с пустым телом.

</details>

### Упражнение 2 — Комментарии к задачам (средне)

Пользователи хотят писать комментарии к задаче. Спроектируйте эндпоинты, чтобы перечислить комментарии
задачи, добавить комментарий и удалить один комментарий. Приведите JSON комментария, коды статуса и скажите,
что происходит, если задачи не существует.

<details>
<summary>Подсказка</summary>

Комментарий принадлежит ровно одной задаче, поэтому один уровень вложенности разумен. Нужен ли
идентификатор задачи в пути, чтобы удалить комментарий?

</details>

<details>
<summary>Ответ</summary>

Комментарий: `{"id": 3, "task_id": 7, "text": "Use the oat milk", "created_at": "2026-11-18T07:02:39Z"}`.

| Эндпоинт | Успех | Ошибки |
|---|---|---|
| `GET /tasks/{id}/comments` | `200`, массив | `404`, если задачи не существует |
| `POST /tasks/{id}/comments` с `{"text": "…"}` | `201`, `location: /comments/{comment_id}` | `404` нет задачи, `422` пустой текст |
| `DELETE /comments/{comment_id}` | `204` | `404` |

Почему это работает: перечислять и создавать комментарии имеет смысл только *внутри* задачи, поэтому они
вложены. У комментария свой идентификатор, поэтому к нему можно обратиться напрямую как
`/comments/{comment_id}`, не повторяя задачу. (`DELETE /tasks/{id}/comments/{comment_id}` тоже допустимо;
выберите один стиль и придерживайтесь его.) Отсутствующая задача даёт `404`, а не пустой список, чтобы
клиент мог отличить «нет комментариев» от «нет такой задачи».

</details>

### Упражнение 3 — Тест контракта (средне)

Создайте библиотеку `cargo new --lib code/p16-contract`, добавьте `serde` (с фичей `derive`) и
`serde_json`. Напишите структуру `Task` (`id: u64`, `title: String`, `done: bool`), которая сериализуется в
JSON из раздела 5, и структуру `NewTask` для тела `POST /tasks`. Напишите три теста:

1. `Task` сериализуется ровно в `{"id":1,"title":"Buy milk","done":false}`;
2. тело `{"title":"Buy milk"}` десериализуется в `NewTask`;
3. поле с опечаткой, `{"titel":"Buy milk"}`, **отклоняется**.

<details>
<summary>Подсказка</summary>

По умолчанию `serde` игнорирует неизвестные поля, и тогда тест 3 падает не так, как вы ожидаете (он сообщает
об отсутствующем `title`, но молча принял бы `{"title":"a","titel":"b"}`). Атрибут
`#[serde(deny_unknown_fields)]` на структуре делает неизвестные поля ошибкой.

</details>

<details>
<summary>Ответ</summary>

```rust
use serde::{Deserialize, Serialize};

/// Задача в том виде, в каком API отправляет её клиентам.
#[derive(Debug, Serialize, Deserialize, PartialEq)]
pub struct Task {
    pub id: u64,
    pub title: String,
    pub done: bool,
}

/// Тело `POST /tasks`.
#[derive(Debug, Deserialize, PartialEq)]
#[serde(deny_unknown_fields)]
pub struct NewTask {
    pub title: String,
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn task_json_matches_the_contract() {
        let task = Task {
            id: 1,
            title: "Buy milk".to_string(),
            done: false,
        };
        let json = serde_json::to_string(&task).unwrap();
        assert_eq!(json, r#"{"id":1,"title":"Buy milk","done":false}"#);
    }

    #[test]
    fn new_task_reads_the_documented_body() {
        let body: NewTask = serde_json::from_str(r#"{"title":"Buy milk"}"#).unwrap();
        assert_eq!(
            body,
            NewTask {
                title: "Buy milk".to_string()
            }
        );
    }

    #[test]
    fn misspelled_field_is_rejected() {
        let error = serde_json::from_str::<NewTask>(r#"{"titel":"Buy milk"}"#).unwrap_err();
        println!("{error}");
        assert!(error.to_string().contains("unknown field `titel`"));
    }
}
```

`cargo test -- --nocapture` (показывает вывод `println!`) печатает:

```text
running 3 tests
unknown field `titel`, expected `title` at line 1 column 8
test tests::new_task_reads_the_documented_body ... ok
test tests::misspelled_field_is_rejected ... ok
test tests::task_json_matches_the_contract ... ok

test result: ok. 3 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Почему это работает: тест 1 сравнивает **точный** текст, поэтому переименование или перестановка поля
проваливает тест раньше, чем это увидит какой-либо клиент. `r#"…"#` — «сырая» строка, поэтому кавычкам
внутри не нужны обратные слеши. `deny_unknown_fields` превращает опечатку в запросе клиента в понятную
ошибку `422` позже, вместо молча проигнорированного поля.

</details>

## Вопросы для самопроверки

1. Что должен содержать URL в REST: существительные или глаголы? Где находится глагол?

<details>
<summary>Ответ</summary>

Существительные (ресурсы: `/tasks/7`). Глагол — это HTTP-метод (`GET`, `POST`, `PATCH`, `DELETE`).

</details>

2. Чем *безопасный* метод отличается от *идемпотентного*? Назовите метод, который идемпотентен, но не
   безопасен.

<details>
<summary>Ответ</summary>

Безопасный никогда ничего не меняет (`GET`, `HEAD`). Идемпотентный при многократной отправке даёт тот же
эффект, что и при однократной. `DELETE` (и `PUT`) идемпотентны, но не безопасны: они меняют данные, но
повтор ничего больше не меняет.

</details>

3. Почему опасно автоматически повторять `POST /tasks` после тайм-аута?

<details>
<summary>Ответ</summary>

Первый запрос мог выполниться, а потерялся только ответ. `POST` не идемпотентен, поэтому повтор создаёт
вторую, дублирующую задачу.

</details>

4. Какой код статуса подходит: (a) JSON-тело оборвано посередине; (b) JSON в порядке, но заголовок пустой;
   (c) запрос к базе данных падает из-за ошибки в коде?

<details>
<summary>Ответ</summary>

(a) `400 Bad Request`. (b) `422 Unprocessable Content`. (c) `500 Internal Server Error`, без внутренних
подробностей в теле.

</details>

5. Чем отличаются `401` и `403`?

<details>
<summary>Ответ</summary>

`401`: сервер не знает, кто вы (учётных данных нет или они неверны). `403`: он знает, кто вы, и вам это
делать нельзя.

</details>

6. Какие из этих изменений ломают существующих клиентов: (a) добавление необязательного поля `due_date` в
   JSON задачи; (b) переименование `done` в `completed`; (c) добавление эндпоинта `GET /tasks/{id}/comments`?

<details>
<summary>Ответ</summary>

Только (b). Старые клиенты по-прежнему читают `done` и теперь ничего не находят. Добавить поле или эндпоинт
безопасно, потому что старые клиенты просто игнорируют то, чего не знают.

</details>

## Итоги

- REST проектирует API как ресурсы с URL (существительные) и действует над ними HTTP-методами (глаголами).
- `GET` читает (безопасный), `POST` создаёт (не идемпотентный), `PUT` заменяет, `PATCH` меняет некоторые
  поля, `DELETE` удаляет (идемпотентный).
- Коды статуса сообщают результат: `2xx` — успех, `4xx` — ошибка клиента, `5xx` — сбой сервера. Никогда не
  отвечайте на ошибку кодом `200`.
- Используйте один формат JSON-ошибок везде; никогда не кладите внутренние подробности в ответ `500`.
- Существительные во множественном числе, пути строчными буквами, строки запроса для фильтров и страниц,
  один стиль имён полей JSON, даты в RFC 3339.
- Пишите контракт до кода и защищайте его тестами, которые сравнивают точный JSON.

## Источники и что почитать

- [RFC 9110 — HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110) — официальное определение методов (раздел 9), безопасных и идемпотентных методов и кодов статуса (раздел 15).
- [RFC 9457 — Problem Details for HTTP APIs](https://www.rfc-editor.org/rfc/rfc9457) — стандартный JSON-формат ошибок.
- [MDN — HTTP response status codes](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status) — понятный список всех кодов статуса.
- [Microsoft REST API Guidelines](https://github.com/microsoft/api-guidelines) — длинный практичный свод правил проектирования API, которым пользуется большая компания.
- [OpenAPI Specification](https://spec.openapis.org/oas/latest.html) — стандартный формат описания REST API.
- [serde — container attributes](https://serde.rs/container-attrs.html) — `deny_unknown_fields`, `rename_all` и другие атрибуты для структур.
