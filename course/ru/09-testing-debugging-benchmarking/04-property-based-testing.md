# Урок 09.4 — Тестирование на основе свойств

> **Этап 09 — Тестирование, отладка и бенчмарки** · Урок 4 из 14 · ⏱ около 135 минут

## Что вы узнаете

- Почему тесты с подобранными вручную примерами пропускают ошибки и что такое *свойство*.
- Как писать тесты свойств с крейтом `proptest`: стратегии, `proptest!`, `prop_assert!`.
- Как `proptest` находит падающий вход и *сжимает* (shrink) его до самого маленького, который всё ещё падает.
- Пять приёмов поиска хороших свойств и как избегать слишком слабых свойств.

## Новые слова

| Слово | Значение |
|---|---|
| **свойство** (property) | Утверждение, которое должно быть истинным для *каждого* допустимого входа, например «доли всегда в сумме дают итог». |
| **тест на основе свойств** (property-based test) | Тест, проверяющий свойство на многих автоматически сгенерированных входах вместо нескольких подобранных вручную. |
| **тест на примерах** (example-based test) | Обычный тест: один выбранный вручную вход и один ожидаемый выход. |
| **`proptest`** | Крейт для тестирования на основе свойств в Rust. |
| **стратегия** (strategy) | Рецепт, который говорит `proptest`, как генерировать значения некоторого типа (например, «любой `u64`» или «текст из 0–60 букв a или b»). |
| **случай** (case) | Один набор сгенерированных входов и один запуск тела теста с ним. По умолчанию `proptest` запускает 256 случаев на тест. |
| **сжатие** (shrinking) | После падения — попытки найти меньшие и более простые входы, чтобы получить *минимальный падающий вход*, который легко читать. |
| **минимальный падающий вход** (minimal failing input) | Самый простой найденный вход, при котором тест всё ещё падает. |
| **круговой путь** (round trip) | Выполнить операцию и обратную ей (закодировать, затем раскодировать) и ожидать исходное значение. |
| **оракул** (oracle) | Надёжный, более простой (или более медленный) способ получить верный ответ для сравнения, например `sort` стандартной библиотеки. |
| **инвариант** (invariant) | Факт, остающийся истинным при любых изменениях входа, например «длина результата равна длине входа». |
| **идемпотентный** (idempotent) | Операция, дающая при двукратном применении тот же результат, что и при однократном (сортировка отсортированного списка ничего не меняет). |
| **файл регрессий** (regression file) | Файл, в который `proptest` сохраняет падающий вход, чтобы при следующем запуске сначала пробовать его. |

## 1. Предел примеров, подобранных вручную

Тест на примерах выглядит так:

```rust
assert_eq!(split_bill(1000, 3), vec![334, 333, 333]);
```

Он ясный и быстрый, но проверяет **один** вход из миллиардов. Входы выбираете вы, значит, вы выбираете те, о которых
уже подумали, а ошибки любят те, о которых вы не подумали: огромное число, один человек, текст из десяти одинаковых
букв.

**Тест на основе свойств** переворачивает вопрос. Вместо «для 1000 и 3 ответ — `[334, 333, 333]`» вы формулируете
правило, верное для всех входов: «для **любого** итога и **любого** числа людей доли в сумме дают итог». Затем библиотека
генерирует сотни входов, включая неприятные, и проверяет правило на каждом.
Если находит контрпример, она упрощает его и показывает самый маленький.

Два вида дополняют друг друга. Примеры документируют поведение («вот как выглядит 10.00, разделённые на троих») и легко
читаются. Свойства ищут сюрпризы.

## 2. Подготовка и первые свойства

```bash
cd ~/projects/rust
git switch main
git switch -c lesson/09-04-property-tests
cargo new --lib code/p09-proptest
cd code/p09-proptest
cargo add --dev proptest@1
```

Пусть `src/lib.rs` содержит список модулей. Модули мы напишем в этом и следующих разделах:

```rust
pub mod rle;
pub mod sorting;
pub mod split;
```

Создайте `src/split.rs`:

```rust
/// Splits `total_cents` between `people` (at least 1). The shares add up to the total
/// exactly; the first `total_cents % people` people pay one cent more than the others.
pub fn split_bill(total_cents: u64, people: u64) -> Vec<u64> {
    let base = total_cents / people;
    let extra = total_cents % people;
    (0..people)
        .map(|i| if i < extra { base + 1 } else { base })
        .collect()
}

#[cfg(test)]
mod tests {
    use super::*;
    use proptest::prelude::*;

    #[test]
    fn example_ten_dollars_between_three() {
        assert_eq!(split_bill(1000, 3), vec![334, 333, 333]);
    }

    proptest! {
        #[test]
        fn shares_add_up_to_the_total(total in any::<u64>(), people in 1u64..=1000) {
            let shares = split_bill(total, people);
            prop_assert_eq!(shares.iter().sum::<u64>(), total);
        }

        #[test]
        fn there_is_one_share_per_person(total in any::<u64>(), people in 1u64..=1000) {
            prop_assert_eq!(split_bill(total, people).len() as u64, people);
        }

        #[test]
        fn nobody_pays_more_than_one_cent_above_anybody_else(
            total in any::<u64>(),
            people in 1u64..=1000,
        ) {
            let shares = split_bill(total, people);
            let max = shares.iter().max().unwrap();
            let min = shares.iter().min().unwrap();
            prop_assert!(max - min <= 1, "max {} and min {}", max, min);
        }
    }
}
```

Чтобы остальные модули компилировались, пока создайте пустые файлы `src/rle.rs` и `src/sorting.rs`. Запустите:

```bash
cargo test --lib split
```

```text
running 4 tests
test split::tests::example_ten_dollars_between_three ... ok
test split::tests::there_is_one_share_per_person ... ok
test split::tests::shares_add_up_to_the_total ... ok
test split::tests::nobody_pays_more_than_one_cent_above_anybody_else ... ok

test result: ok. 4 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.01s
```

**Что происходит:**

1. `use proptest::prelude::*` подключает `proptest!`, `prop_assert!` и функции-стратегии.
2. Макрос `proptest! { … }` оборачивает обычно выглядящие тестовые функции. Каждый параметр имеет вид `имя in стратегия`:
   `total in any::<u64>()` значит «`total` — любое `u64`, от 0 до 18 446 744 073 709 551 615», а `people in 1u64..=1000` значит
   «число от 1 до 1000» (диапазон тоже является стратегией).
3. Тело — тест о свойстве. `prop_assert_eq!` и `prop_assert!` подобны `assert_eq!` и `assert!`, но
   сообщают о падении так, что `proptest` может использовать это для сжатия и читаемого сообщения. Третье свойство
   показывает, что `prop_assert!`, как и `assert!`, принимает сообщение с аргументами форматирования.
4. Для каждого теста `proptest` генерирует **256 случаев** и запускает тело с каждым. 256 × 4 теста завершаются примерно
   за 10 миллисекунд, потому что `split_bill` быстрая.
5. Мы написали четыре теста и ни одного фиксированного числа, кроме одного примера. Мы сказали, *что должно выполняться всегда*: сумма верна,
   количество верно, а разброс — не больше одного цента. Вместе эти три свойства почти определяют функцию.

> 💡 **Совет:** держите тест-пример рядом с тестами свойств. Когда свойство падает, пример показывает, что функция
> должна была делать.

## 3. Находим настоящую ошибку

Допустим, коллега «оптимизирует» деление и записывает его на числах с плавающей точкой:

```rust
    let base = (total_cents as f64 / people as f64).floor() as u64;
```

Замените строку `let base = total_cents / people;` на эту и снова запустите тесты. Тест-пример всё ещё проходит, потому что
1000 / 3 прекрасно работает в плавающей точке. Тест свойств находит проблему:

```text
---- split::tests::shares_add_up_to_the_total stdout ----
proptest: Saving this and future failures in …/proptest-regressions/split.txt
proptest: If this test was run on a CI system, you may wish to add the following line to your copy of the file. (You may need to create it.)
cc 902a0585c76884d24a6dc54991b0019277c5eef93e5d9803f997808069671741
thread 'split::tests::shares_add_up_to_the_total' (4769191) panicked at src/split.rs:21:5:
Test failed: assertion failed: `(left == right)`
  left: `2519100732292684288`,
 right: `2519100732292684033` at src/split.rs:25.
minimal failing input: total = 2519100732292684033, people = 1
	successes: 0
	local rejects: 0
	global rejects: 0
```

**Что это значит:**

1. `proptest` пробовал случайные значения и сразу нашёл падающий случай. Числа на вашем экране будут другими:
   `proptest` каждый раз стартует со случайного начального значения генератора.
2. Затем он **сжал** падение. Он пытался сделать `total` и `people` меньше и проще, пока тест
   всё ещё падал, и остановился на `people = 1` и всё ещё огромном `total`. Результат — *минимальный падающий вход*, напечатанный
   в строке, которая начинается с `minimal failing input`.
3. Почему тест падает? 64-битное число с плавающей точкой (`f64`) хранит только 53 бита точности, поэтому целые числа выше
   примерно 9 × 10¹⁵ округляются: `…033` превратилось в `…288`. Доли больше не дают в сумме итог. На обычных примерах (малые суммы) вы бы
   этого никогда не увидели.
4. `proptest` сохранил падающий случай в файле `proptest-regressions/split.txt`. При каждом следующем запуске он пробует
   сохранённые случаи **первыми**, поэтому исправленная ошибка остаётся исправленной. **Закоммитьте эту папку в Git.**
5. Отчёт *воспроизводим*: хотя генерация случайна, вход в строке `minimal failing input` точный, поэтому вы можете скопировать его в
   обычный тест-пример: `assert_eq!(split_bill(2519100732292684033, 1).iter().sum::<u64>(), 2519100732292684033);`.

Верните целочисленное деление (`let base = total_cents / people;`), удалите файл `proptest-regressions/split.txt`
и запустите снова, чтобы увидеть, что все тесты проходят.

> 🔒 **Безопасность:** переполнение целых чисел и ошибки округления в деньгах, размерах и длинах — частый источник ошибок безопасности.
> Свойства над `any::<u64>()` — дешёвый способ их искать.

> ⚡ **Производительность:** деление в `u64` ещё и быстрее, чем преобразование в `f64` и обратно. «Умная» версия была и медленнее, и неверна.

## 4. Стратегии: описываем входы

Стратегия решает, какие значения генерируются. Чаще всего вам понадобятся эти:

| Стратегия | Генерирует |
|---|---|
| `any::<T>()` | любое значение типа `T` (`u8`, `i32`, `bool`, `String`, `char`, …) |
| `0u32..10`, `1u64..=1000` | число из диапазона (`..` исключает конец, `..=` включает) |
| `"[a-z]{1,8}"` | текст, подходящий под небольшое регулярное выражение (здесь: от 1 до 8 строчных букв) |
| `(s1, s2)` | кортеж с одним значением от каждой стратегии |
| `prop::collection::vec(s, 0..5)` | `Vec` из 0–4 значений, каждое от стратегии `s` |
| `s.prop_map(\|x\| x * 2)` | значения `s`, преобразованные функцией |
| `prop_oneof![Just("yes"), Just("no")]` | одна из нескольких стратегий; `Just(x)` всегда даёт `x` |

Добавьте этот тест внутрь блока `proptest! { … }` в `src/split.rs`, чтобы увидеть их в работе. Тест проверяет, что каждая стратегия даёт
обещанное:

```rust
        #[test]
        fn a_tour_of_strategies(
            n in 0u32..10,
            text in "[a-z]{1,8}",
            pair in (any::<bool>(), 1u8..=6),
            list in prop::collection::vec(0u8..=9, 0..5),
            even in (0u32..100).prop_map(|x| x * 2),
            word in prop_oneof![Just("yes"), Just("no")],
        ) {
            prop_assert!(n < 10);
            prop_assert!((1..=8).contains(&text.len()));
            prop_assert!((1..=6).contains(&pair.1));
            prop_assert!(list.len() < 5);
            prop_assert!(even % 2 == 0);
            prop_assert!(word == "yes" || word == "no");
        }
```

**Что происходит:** каждый параметр генерируется независимо. `prop_map` — способ построить собственные значения из простых: здесь
каждое чётное число меньше 200.

Иногда случай не имеет смысла для свойства. `prop_assume!(условие)` отбрасывает случай (он считается «локальным отказом»,
local reject), и `proptest` пробует другой. Добавьте и этот:

```rust
        #[test]
        fn an_inexact_split_gives_two_different_amounts(total in any::<u64>(), people in 2u64..=1000) {
            prop_assume!(total % people != 0);
            let shares = split_bill(total, people);
            prop_assert_ne!(shares.first(), shares.last());
        }
```

Если итог делится нацело, все доли равны и свойство было бы неверным, поэтому мы такие случаи пропускаем. Используйте
`prop_assume!` только для редких исключений: если он отбрасывает большинство случаев, `proptest` сдаётся с ошибкой («too many
rejects»). В таком случае лучше построить нужный вход лучшей стратегией.

> 💡 **Совет:** по умолчанию 256 случаев. Для быстрого запуска используйте `PROPTEST_CASES=10 cargo test`; перед релизом попробуйте
> `PROPTEST_CASES=10000 cargo test`. В коде можно задать `#![proptest_config(ProptestConfig::with_cases(1000))]` первой
> строкой внутри блока `proptest!`.

## 5. Пять приёмов поиска свойств

Трудно не с библиотекой, а с пониманием, что утверждать. Эти приёмы покрывают большинство случаев:

| Приём | Идея | Пример |
|---|---|---|
| **Круговой путь** | выполнить операцию, затем обратную, и ожидать исходное | `decode(encode(x)) == x` |
| **Инвариант** | то, что остаётся истинным для любого входа | длина результата равна длине входа |
| **Оракул** | сравнить с надёжным, более простым способом | наша сортировка равна сортировке стандартной библиотеки |
| **Идемпотентность** | дважды — то же, что один раз | сортировка отсортированного списка ничего не меняет |
| **Границы / без падений** | результат остаётся в пределах, или код не паникует | `x.clamp(low, high)` лежит между `low` и `high` |

### Круговой путь: кодирование длин серий

*Кодирование длин серий* (run-length encoding, RLE) сокращает текст с повторяющимися буквами: `"aaabcc"` превращается в `"3a1b2c"` (3 раза `a`, 1 раз `b`, 2 раза
`c`). Создайте `src/rle.rs`, сначала с декодером, в котором есть тонкая ошибка:

```rust
/// Run-length encoding: `"aaabcc"` becomes `"3a1b2c"`.
pub fn encode(text: &str) -> String {
    let mut result = String::new();
    let mut chars = text.chars().peekable();
    while let Some(c) = chars.next() {
        let mut count = 1;
        while chars.peek() == Some(&c) {
            chars.next();
            count += 1;
        }
        result.push_str(&count.to_string());
        result.push(c);
    }
    result
}

/// The reverse of `encode`: `"3a1b2c"` becomes `"aaabcc"`.
pub fn decode(encoded: &str) -> String {
    let mut result = String::new();
    let mut chars = encoded.chars();
    while let (Some(count), Some(c)) = (chars.next(), chars.next()) {
        let Some(count) = count.to_digit(10) else {
            break;
        };
        for _ in 0..count {
            result.push(c);
        }
    }
    result
}

#[cfg(test)]
mod tests {
    use super::*;
    use proptest::prelude::*;

    #[test]
    fn encodes_runs() {
        assert_eq!(encode("aaabcc"), "3a1b2c");
        assert_eq!(encode(""), "");
    }

    #[test]
    fn decodes_runs() {
        assert_eq!(decode("3a1b2c"), "aaabcc");
    }

    proptest! {
        #[test]
        fn decoding_an_encoded_text_gives_the_original(text in "[ab]{0,60}") {
            prop_assert_eq!(decode(&encode(&text)), text);
        }
    }
}
```

**Что происходит:**

1. `encode` идёт по символам; для каждого считает, сколько одинаковых символов следует за ним (`peekable` и
   `peek` смотрят на следующий символ, не забирая его), и записывает число и символ.
2. `decode` берёт символы парами: число, затем символ для повторения. (`while let (Some(count), Some(c)) = …`
   останавливается, когда во входе нет полной пары.)
3. Два теста-примера проходят. Свойство — круговой путь: для любого текста из букв `a` и `b` (от 0 до 60 штук)
   `decode(encode(text))` должно быть исходным. Мы используем только две буквы, чтобы длинные серии одинаковых букв встречались часто.

```bash
cargo test --lib rle
```

```text
---- rle::tests::decoding_an_encoded_text_gives_the_original stdout ----
proptest: Saving this and future failures in …/proptest-regressions/rle.txt
cc 25e7af3a55e5cd185e8cfce5beb83edb9a54a99eadb85d54fb8d10d4d65050a4
thread 'rle::tests::decoding_an_encoded_text_gives_the_original' (4755197) panicked at src/rle.rs:48:5:
Test failed: assertion failed: `(left == right)`
  left: `"0"`,
 right: `"bbbbbbbbbb"` at src/rle.rs:51.
minimal failing input: text = "bbbbbbbbbb"
	successes: 56
	local rejects: 0
	global rejects: 0
```

**Что это значит:** минимальный падающий вход — десять одинаковых букв (у вас может быть десять `a`). `encode` пишет `"10b"` (число состоит из двух
цифр), а `decode` читает ровно один символ как число: `'1'`, затем повторяет символ `'0'` один раз, и результат — `"0"`.
Два примера использовали числа от 1 до 3, поэтому никогда этого не показали. Сжатие полезно: падающий текст из 57 букв было бы трудно
понять; десять одинаковых букв указывают прямо на «числа 10 и больше».

Исправьте `decode` так, чтобы он собирал все цифры числа:

```rust
/// The reverse of `encode`: `"3a1b2c"` becomes `"aaabcc"`.
pub fn decode(encoded: &str) -> String {
    let mut result = String::new();
    let mut digits = String::new();
    for c in encoded.chars() {
        if c.is_ascii_digit() {
            digits.push(c);
        } else {
            let count: usize = digits.parse().unwrap_or(0);
            result.extend(std::iter::repeat_n(c, count));
            digits.clear();
        }
    }
    result
}
```

**Что происходит:** цифры накапливаются в `digits`; когда приходит не цифра, это символ для повторения, а `digits`
хранит его число (`"10"` разбирается как 10). `repeat_n(c, count)` производит `c` ровно `count` раз. Удалите `proptest-regressions/rle.txt`
(или оставьте: он гарантирует, что «bbbbbbbbbb» теперь пробуется первым), и свойство проходит.

### Инвариант, оракул, идемпотентность: сортировка

Создайте `src/sorting.rs`. Сортировка вставками проста, а стандартная библиотека даёт нам надёжный оракул:

```rust
/// Sorts numbers from the smallest to the largest with insertion sort.
pub fn insertion_sort(numbers: &[i32]) -> Vec<i32> {
    let mut result = numbers.to_vec();
    for i in 1..result.len() {
        let mut j = i;
        while j > 0 && result[j - 1] > result[j] {
            result.swap(j - 1, j);
            j -= 1;
        }
    }
    result
}

#[cfg(test)]
mod tests {
    use super::*;
    use proptest::prelude::*;

    fn is_sorted(numbers: &[i32]) -> bool {
        numbers.windows(2).all(|pair| pair[0] <= pair[1])
    }

    proptest! {
        #[test]
        fn the_result_is_sorted(numbers in prop::collection::vec(any::<i32>(), 0..100)) {
            prop_assert!(is_sorted(&insertion_sort(&numbers)));
        }

        #[test]
        fn the_result_has_the_same_elements(numbers in prop::collection::vec(any::<i32>(), 0..100)) {
            let mut expected = numbers.clone();
            expected.sort();
            // The oracle: the standard library's sort must agree with ours.
            prop_assert_eq!(insertion_sort(&numbers), expected);
        }

        #[test]
        fn sorting_twice_changes_nothing(numbers in prop::collection::vec(any::<i32>(), 0..100)) {
            let once = insertion_sort(&numbers);
            prop_assert_eq!(insertion_sort(&once), once);
        }
    }
}
```

**Что происходит:** `windows(2)` даёт каждую пару соседей (Урок 05.5), поэтому `is_sorted` проверяет, что ни одна пара не нарушает
порядок. Второй тест использует приём **оракула**: он ничего не говорит о том, *как* сортировать, лишь требует тот же ответ, что и функция,
которой мы доверяем. Третий использует **идемпотентность**. Запустите `cargo test`, чтобы увидеть, что все тесты проходят. (Стратегия `vec` даёт от 0 до 99 чисел,
а `any::<i32>()` включает `i32::MIN`, `i32::MAX` и много дубликатов.)

## 6. Слишком слабые свойства

Слишком слабое свойство проходит для неверного кода. Посмотрите: добавьте в тестовый модуль сломанную «сортировку» со свойством «результат
отсортирован» и более сильным свойством:

```rust
    /// A broken "sort" that returns nothing.
    fn broken_sort(_numbers: &[i32]) -> Vec<i32> {
        Vec::new()
    }

    proptest! {
        #[test]
        fn a_weak_property_accepts_the_broken_sort(numbers in prop::collection::vec(any::<i32>(), 0..100)) {
            prop_assert!(is_sorted(&broken_sort(&numbers)));
        }

        #[test]
        fn a_stronger_property_rejects_it(numbers in prop::collection::vec(any::<i32>(), 0..100)) {
            let result = broken_sort(&numbers);
            prop_assert!(is_sorted(&result));
            prop_assert_eq!(result.len(), numbers.len());
        }
    }
```

```text
test sorting::tests::a_stronger_property_rejects_it ... FAILED
test sorting::tests::a_weak_property_accepts_the_broken_sort ... ok
…
minimal failing input: numbers = [
    0,
]
```

**Что это значит:** пустой список «отсортирован», поэтому слабое свойство удовлетворяется функцией, которая ничего не делает. Более сильное свойство
требует ещё и той же длины и падает с самым маленьким возможным контрпримером — списком из одного числа `0`.
Каждый раз, когда пишете свойство, спрашивайте: *«Какая самая глупая функция всё равно его пройдёт?»* Если такая есть, добавьте свойство, которое
её отвергает. (Потом удалите два экспериментальных теста, чтобы набор тестов оставался зелёным.)

## Частые ошибки

**1. Написание кода заново внутри свойства.** `prop_assert_eq!(split_bill(t, p), my_own_copy_of_split_bill(t, p))` не проверяет
ничего: у обеих сторон одна и та же ошибка. Формулируйте *другой* факт о результате: сумма, количество, разброс.

**2. Стратегия, которая никогда не доходит до ошибки.** С `"[a-z]{0,40}"` десять одинаковых букв подряд почти не встречаются, и ошибочный
`decode` прошёл бы. Выбирайте стратегии так, чтобы интересные случаи были *вероятны*: маленький алфавит, маленькие диапазоны и несколько
крайних значений.

**3. Свойства со скрытым предусловием.** Круговой путь `decode(encode(text)) == text` ложен для текста с цифрами (`"1"`
кодируется как `"11"`, а это неоднозначно). Если расширить стратегию до `"[ab1]{0,30}"`, тест упадёт с минимальным входом `text = "1"`.
Решите: ограничить входы (и задокументировать это) или изменить формат. Падение показывает пробел в *спецификации*, а не только в коде.

**4. `assert!` вместо `prop_assert!`.** Обычный `assert!` тоже роняет тест (`proptest` перехватывает панику), но
варианты с `prop_` быстрее, потому что нет паники, которую нужно раскручивать, и дают более чистый отчёт. Используйте их внутри `proptest!`.

**5. Ожидание одних и тех же чисел при каждом запуске.** Начальное значение генератора случайно, поэтому падающий вход различается между запусками. Если нужно
воспроизвести падение, используйте строку `minimal failing input` или сохранённый файл в `proptest-regressions/`.

## Упражнения

### Упражнение 1 — Ещё одно свойство (легко)

Добавьте в `src/split.rs` свойство: доли не возрастают слева направо (каждая доля больше или равна следующей).

<details>
<summary>Подсказка</summary>

Используйте `shares.windows(2)` и проверьте `pair[0] >= pair[1]` для всех пар, как `is_sorted` делает для сортировки.

</details>

<details>
<summary>Ответ</summary>

```rust
        #[test]
        fn shares_never_increase(total in any::<u64>(), people in 1u64..=1000) {
            let shares = split_bill(total, people);
            prop_assert!(shares.windows(2).all(|pair| pair[0] >= pair[1]));
        }
```

Почему это работает: первые `total % people` долей равны `base + 1`, остальные — `base`, поэтому список убывает не более одного раза.
Это свойство поймало бы ошибку, которая отдавала бы лишние центы последним людям.

</details>

### Упражнение 2 — Свойства `clamp` (средне)

`x.clamp(low, high)` возвращает `x`, ограниченный диапазоном от `low` до `high`. Напишите тест свойств с двумя фактами: результат
всегда лежит между `low` и `high`, а если `x` уже в диапазоне, результат равен `x`. Сгенерируйте `low` и `high` так, чтобы `low <= high`
выполнялось всегда, без `prop_assume!`.

<details>
<summary>Подсказка</summary>

Сгенерируйте `low` и неотрицательную `width`, затем используйте `high = low + width`. Держите числа небольшими (например,
`-1000..1000`), чтобы сложение не могло переполниться. Проверяйте через `(low..=high).contains(&x)`.

</details>

<details>
<summary>Ответ</summary>

```rust
        #[test]
        fn clamp_stays_inside_the_limits(x in any::<i32>(), low in -1000i32..1000, width in 0i32..1000) {
            let high = low + width;
            let result = x.clamp(low, high);
            prop_assert!(low <= result && result <= high);
            if (low..=high).contains(&x) {
                prop_assert_eq!(result, x);
            }
        }
```

Почему это работает: построение `high` из `low` и ширины делает недопустимый случай (`low > high`, где `clamp` паникует) невозможным по
построению. Это лучше, чем отбрасывать случаи, потому что ни один сгенерированный случай не пропадает впустую.

</details>

### Упражнение 3 — Цифры в тексте (сложно)

Измените стратегию теста кругового пути для RLE на `"[ab1]{0,30}"` и запустите его. Каков минимальный падающий вход и почему тест падает?
Затем решите, как исправить проблему, и запишите исправление в виде теста.

<details>
<summary>Подсказка</summary>

Закодируйте текст `"1"` вручную, затем раскодируйте результат. Два выхода: запретить цифры во входе (документированное предусловие) или сделать
формат однозначным (например, кодировать цифру escape-последовательностью).

</details>

<details>
<summary>Ответ</summary>

Минимальный падающий вход — `text = "1"`. `encode("1")` даёт `"11"` (число 1, символ `'1'`), а `decode("11")` читает обе
цифры как одно число и не находит символа для повторения, поэтому возвращает `""`.

Самое простое исправление — документированное предусловие «текст не должен содержать цифр»: напишите это в doc-комментарии к `encode` и оставьте
стратегию только из букв. Как тест предусловия зафиксируйте, что функция предназначена для букв:

```rust
        #[test]
        fn round_trip_for_letters(text in "[a-c]{0,40}") {
            prop_assert_eq!(decode(&encode(&text)), text);
        }
```

Более полное исправление сделало бы `encode` возвращающей `Result<String, EncodeError>` и отказывающейся принимать цифры, с тестом, что
`encode("a1")` — это `Err`. Тест свойств сделал своё дело: он показал, что у формата есть пробел.

</details>

## Вопросы для самопроверки

1. Чем тест на примерах отличается от теста на основе свойств?

<details>
<summary>Ответ</summary>

Тест на примерах проверяет один выбранный вручную вход против одного ожидаемого выхода. Тест на основе свойств формулирует правило, которое должно выполняться для всех
допустимых входов, а библиотека проверяет его на многих сгенерированных входах.

</details>

2. Что такое сжатие (shrinking)?

<details>
<summary>Ответ</summary>

После нахождения падающего входа `proptest` пробует меньшие и более простые входы, которые всё ещё падают, и сообщает минимальный падающий вход, который
намного легче понять, чем первый случайный.

</details>

3. Почему папку `proptest-regressions` нужно коммитить?

<details>
<summary>Ответ</summary>

В ней хранятся найденные падающие входы. При каждом следующем запуске, вашем, коллеги или CI (continuous integration, непрерывной интеграции — сервера, который тестирует каждое изменение), они пробуются первыми, поэтому исправленная
ошибка не сможет вернуться незамеченной.

</details>

4. Назовите три приёма поиска свойства.

<details>
<summary>Ответ</summary>

Например: круговой путь (`decode(encode(x)) == x`), инвариант (длина остаётся прежней), оракул (сравнение со стандартной библиотекой),
идемпотентность (двукратное применение равно однократному), границы / без падений.

</details>

5. Свойство гласит: «результат `sort` упорядочен». Почему оно слишком слабое?

<details>
<summary>Ответ</summary>

Ему удовлетворяет функция, возвращающая пустой список. Хороший набор свойств требует ещё, чтобы результат содержал те же элементы, что и вход (ту же
длину или равенство с оракулом).

</details>

6. Что делает `prop_assume!` и когда это плохая идея?

<details>
<summary>Ответ</summary>

Он отбрасывает текущий случай, если условие ложно. Это плохая идея, когда он отбрасывает большинство случаев, потому что `proptest` сдаётся. Постройте нужные
входы лучшей стратегией.

</details>

## Итоги

- Свойство — правило, которое должно выполняться для каждого допустимого входа. Тест на основе свойств проверяет его на многих сгенерированных входах и находит случаи, о которых вы не подумали.
- С `proptest`: `proptest! { #[test] fn name(x in strategy) { prop_assert!(…); } }`. Стратегии: `any::<T>()`, диапазоны, регулярные выражения,
  кортежи, `vec`, `prop_map`, `prop_oneof!`.
- Когда случай падает, `proptest` сжимает его до минимального падающего входа и сохраняет в `proptest-regressions/`; коммитьте эту папку.
- По умолчанию 256 случаев; `PROPTEST_CASES` это меняет.
- Приёмы: круговой путь, инвариант, оракул, идемпотентность, границы / без падений. Спрашивайте «какая самая глупая функция пройдёт?», чтобы избежать слабых свойств.
- Примеры документируют поведение, свойства ищут сюрпризы. Используйте оба вида.
