# Урок 13.1 — Что делает операционная система

> **Этап 13 — Операционные системы изнутри** · Урок 1 из 18 · ⏱ около 135 минут

## Что вы узнаете

- Три задачи операционной системы: спрятать железо за простыми понятиями, разделить машину между программами и защитить программы друг от друга.
- Что такое ядро и чем пространство пользователя отличается от пространства ядра.
- Три способа, которыми процессор входит в ядро: системные вызовы, прерывания и исключения.
- Как заглянуть внутрь работающего ядра Linux через `/proc` — вручную и из программы на Rust.
- Как на этом этапе устроен код и как запускать его в вашей ВМ `dev`.

## Перед началом

- У вас есть Linux-ВМ `dev` из [Урока 11.1 — Linux и виртуальная машина на вашем Mac](../11-linux-shell-and-containers/01-linux-and-a-virtual-machine.md), и вы умеете работать с командной оболочкой, файлами, процессами и сигналами (Этап 11).

- Вы знаете, что означает `unsafe` ([Урок 06.6 — Небезопасный Rust и Miri](../06-rust-advanced/06-unsafe-rust-and-miri.md)). Здесь мы используем его один раз и намеренно — чтобы нарушить правило.

## Новые слова

| Слово | Значение |
|---|---|
| **CPU** (Central Processing Unit, центральный процессор) / **RAM** (Random Access Memory, оперативная память) | Микросхема, которая выполняет инструкции / основная память (Этап 12). |
| **VM** (Virtual Machine, виртуальная машина, ВМ) | Компьютер, смоделированный программой; ваша Linux-ВМ называется `dev` (Урок 11.1). |
| **ОС** (operating system, OS, операционная система) | Программное обеспечение, которое управляет железом компьютера и даёт программам безопасно им пользоваться: Linux, macOS, Windows. |
| **ядро** (kernel) | Центральная часть ОС. Оно работает с полной властью над железом; всё остальное просит его о помощи. |
| **пространство пользователя** (user space) | Мир, где работают обычные программы (ваши программы на Rust, командная оболочка, `ls`). У кода здесь ограниченные права. |
| **пространство ядра** (kernel space) | Память и режим процессора, в которых работает ядро. Пользовательские программы не могут их читать или менять. |
| **уровень привилегий** (privilege level) | Режим процессора, который определяет, какие инструкции и какая память разрешены. На arm64 он называется **EL** (Exception Level, уровень исключений): EL0 для программ, EL1 для ядра. На x86-64 он называется **кольцом** (ring): кольцо 3 для программ, кольцо 0 для ядра. |
| **системный вызов** (system call, syscall) | Запрос программы к ядру: «открой этот файл», «дай мне память», «запусти процесс». Урок 13.3 разбирает его подробно. |
| **прерывание** (interrupt) | Сигнал от устройства (таймера, диска, сетевой карты), который заставляет процессор прервать текущую работу и выполнить код ядра. |
| **исключение** (exception, у процессора) | Событие, вызванное выполняемой инструкцией: плохой адрес памяти, деление на ноль, запрещённая инструкция. Процессор переходит в ядро, чтобы его обработать. |
| **драйвер** (driver) | Код ядра, который умеет общаться с одним видом устройств. |
| **абстракция** (abstraction) | Простое понятие, которое скрывает сложную вещь: «файл» скрывает блоки диска, «процесс» — переключения процессора. |
| **PID** (Process IDentifier, идентификатор процесса) | Номер, который ядро даёт каждому работающему процессу (Этап 11). |
| **procfs** (process file system, файловая система процессов) | Папка `/proc`. Её файлов нет на диске: ядро создаёт их содержимое при каждом чтении. |
| **POSIX** (Portable Operating System Interface, переносимый интерфейс операционных систем) | Стандарт, описывающий системные вызовы и утилиты, которые должны быть у Unix-подобной ОС. Linux и macOS следуют большей его части. |
| **КиБ / МиБ** (KiB / MiB, кибибайт / мебибайт) | 1 КиБ = 1024 байта, 1 МиБ = 1024 КиБ (Урок 12.1). |

## 1. Какую задачу решает операционная система

Представьте офисное здание, где много компаний делят одну линию электричества и один набор лифтов. У здания есть
**управляющий**: компании просят у него комнату или ключ, а он не пускает их в чужие комнаты.

У компьютера та же задача: один процессор с несколькими ядрами, одна оперативная память, один диск и одна сетевая
карта, но сотни программ, которым всё это нужно одновременно. **Операционная система** — это управляющий зданием. У неё три задачи:

1. **Абстракция — спрятать железо за простыми понятиями.** Ваша программа не знает, какая у вас модель диска.
   Она говорит «открой файл `notes.txt`», а ОС превращает это в команды для именно этого диска.
   *Файл*, *процесс*, *сокет* и *виртуальная память* — всё это абстракции, созданные ОС.
2. **Разделение — поделить машину между программами.** ОС даёт каждой программе короткие отрезки времени на процессоре
   (Урок 13.9), часть памяти (Урок 13.10) и её долю диска и сети.
3. **Защита — держать программы раздельно.** Ошибка в браузере не должна ронять ваш редактор, а программа обычного
   пользователя не должна читать файлы другого пользователя или менять саму ОС.

Результаты этих задач вы уже видели на Этапе 11: процессы с PID, пользователи и права доступа, сигналы, службы.
На этом этапе вы смотрите на них **изнутри**: что на самом деле делает ядро и как программа на Rust с ним разговаривает.

## 2. Ядро, пространство пользователя и пространство ядра

Самая важная часть ОС — **ядро**. Это одна большая программа, которую компьютер запускает первой (после прошивки)
и которая работает, пока вы не выключите компьютер. Всё остальное — командная оболочка, `systemd`, ваши программы
на Rust — работает **поверх** ядра, в **пространстве пользователя**.

```text
 user space (EL0 on arm64, ring 3 on x86-64)
 +-------------------------------------------------------------+
 |  your Rust program     bash      systemd      sshd    ...   |
 |        |                 |                                   |
 |  Rust standard library (std)                                 |
 |        |                                                     |
 |  C library (libc): small functions that make system calls    |
 +--------|----------------------------------------------------+
          |  system call: the only door into the kernel
 +--------v----------------------------------------------------+
 |  kernel space (EL1 on arm64, ring 0 on x86-64)              |
 |  processes and scheduler | memory manager | file systems    |
 |  network stack           | drivers                          |
 +--------|----------------------------------------------------+
          v
   hardware: CPU cores, RAM, disk, network card, timer
```

Эту границу охраняет сам процессор. Он всегда работает на каком-то **уровне привилегий**:

- На **низком** уровне (EL0 на arm64, кольцо 3 на x86-64) процессор отказывается выполнять некоторые инструкции,
  например те, что меняют защиту памяти или напрямую обращаются к устройствам, и отказывается трогать память,
  принадлежащую ядру.
- На **высоком** уровне (EL1 на arm64, кольцо 0 на x86-64) разрешено всё. Там работает только ядро.

Ядро настраивает карту памяти каждой программы (как — объясняет Урок 13.10) так, что собственная память ядра помечена
«только для ядра». Если программа пытается её прочитать, процессор останавливает инструкцию и передаёт управление
ядру, а ядро наказывает программу. Посмотрим, как это происходит.

### Смотрим, как работает защита

Эта маленькая программа пытается прочитать один байт по адресу в верхней половине адресного пространства, которая
в Linux принадлежит ядру (`src/bin/poke-kernel.rs`, о структуре папок — в разделе 5):

```rust
fn main() {
    // An address in the upper half of the address space: on Linux, that half belongs to the kernel.
    let kernel_address = 0xffff_8000_0000_0000_usize as *const u8;
    println!("trying to read kernel memory at {kernel_address:p} ...");
    // SAFETY: none! This is deliberately wrong code, to watch the kernel stop us.
    let value = unsafe { std::ptr::read_volatile(kernel_address) };
    println!("read {value}"); // never printed
}
```

```bash
cargo run -q --bin poke-kernel
echo "exit code: $?"
```

```text
trying to read kernel memory at 0xffff800000000000 ...
bash: line 1:   150 Segmentation fault      cargo run -q --bin poke-kernel
exit code: 139
```

**Что происходит:**

1. `0xffff_8000_0000_0000_usize as *const u8` превращает число в сырой указатель (Урок 06.6). Создавать его можно;
   опасно читать через него, поэтому для чтения нужен `unsafe`.
2. `read_volatile` действительно выполняет чтение (компилятор не может его убрать). Процессор, работающий на низком
   уровне привилегий, проверяет карту памяти, видит «только для ядра» и генерирует **исключение**.
3. Обработчик исключений в ядре видит, что пользовательская программа тронула память, которую трогать нельзя. Он
   посылает программе сигнал `SIGSEGV` (сигнал 11, «segmentation violation», нарушение сегментации), действие которого
   по умолчанию — убить процесс.
4. Командная оболочка сообщает `Segmentation fault`, а код возврата равен 139 = 128 + 11 — знакомое вам по Этапу 11
   правило для «убит сигналом». Второй `println!` так и не выполняется.

Точный текст зависит от командной оболочки: в интерактивном bash вы увидите `Segmentation fault (core dumped)`.

> 🔒 **Безопасность:** именно эта граница делает многопользовательскую машину безопасной. Ваша программа может уронить
> саму себя, но не может прочитать память ядра, память других программ или файлы, на которые у неё нет прав. Любая
> атака на ОС ищет дыру именно в этой границе, поэтому ядра пишут очень аккуратно.

## 3. Три двери в ядро

Ядро не работает «рядом» с вашей программой всё время. Процессор выполняет инструкции вашей программы, пока не
случится одно из трёх событий, и только тогда переходит в код ядра:

| Дверь | Кто её открывает | Пример |
|---|---|---|
| **системный вызов** | ваша программа, намеренно | «прочитай 4 КиБ из этого файла», «выведи этот текст в терминал» |
| **исключение** | выполняемая инструкция, случайно или по замыслу | плохой адрес (как выше), деление на ноль на некоторых процессорах, страница памяти, которая ещё не загружена (Урок 13.10) |
| **прерывание** | устройство, в любой момент | тикнул таймер, пришёл сетевой пакет, диск закончил чтение |

Все двери работают одинаково. Процессор сохраняет, где была программа, переключается на высокий уровень привилегий
и переходит по адресу в ядре, который ядро выбрало при загрузке. Ядро делает свою работу и затем либо возвращается в ту
же программу, либо, если решит, что сейчас должна работать другая программа, переключается на неё.

**Прерывание таймера** — причина, по которой один бесконечный цикл не может заморозить машину. Много раз в секунду
аппаратный таймер прерывает процессор, и у ядра появляется шанс отдать процессор кому-то другому. Вы увидите это в
[Уроке 13.9 — Потоки и планирование](09-threads-and-scheduling.md).

## 4. Linux: ядро, в которое можно заглянуть

**Linux** — это ядро. **Дистрибутив**, например Ubuntu, — это ядро Linux плюс тысячи программ пространства пользователя
(Урок 11.1). Ядро Linux *монолитное*: планировщик, менеджер памяти, файловые системы, сетевой стек и большинство драйверов
живут в одной большой программе в пространстве ядра. Дополнительные драйверы можно подгружать на ходу — как
**модули ядра** (kernel modules).

Команда `uname` (Unix name) сообщает, какое ядро работает. Попробуйте в вашей ВМ:

```bash
uname -r
uname -m
```

Настоящий вывод из Linux-контейнера, в котором проверялся этот урок (в вашей ВМ версия заканчивается на `-generic`):

```text
7.0.14-linuxkit
aarch64
```

`-r` печатает версию ядра, `-m` — тип машины: `aarch64` — так Linux называет arm64.

### `/proc`: окно в ядро

Ядро показывает большую часть своего внутреннего состояния как **файлы** в папке `/proc`. Эти файлы не хранятся ни на
каком диске: когда вы читаете файл, ядро пишет ответ в этот самый момент. Это и есть **procfs**.

```bash
cat /proc/version
cat /proc/uptime
cat /proc/loadavg
head -3 /proc/meminfo
ls /proc | head -5
```

Настоящий вывод (у вас будут другие числа):

```text
Linux version 7.0.14-linuxkit (root@buildkitsandbox) (gcc (Alpine 15.2.0) 15.2.0, GNU ld (GNU Binutils) 2.45.1) #1 SMP PREEMPT Fri Oct 30 13:45:20 UTC 2026
63588.65 746910.25
0.52 0.91 0.51 2/492 183
MemTotal:        8124192 kB
MemFree:          355980 kB
MemAvailable:    7084184 kB
1
185
186
buddyinfo
bus
```

**Что происходит:**

1. `/proc/version` — версия ядра и компилятор, которым оно собрано. `SMP` (Symmetric MultiProcessing, симметричная
   многопроцессорность) означает, что ядро умеет использовать много ядер процессора; `PREEMPT` — что даже собственный код
   ядра можно приостановить на середине, чтобы раньше запустить более срочную задачу (программы в пространстве
   пользователя приостановить можно всегда).
2. `/proc/uptime` — секунды с момента загрузки, затем суммарное время простоя всех ядер процессора.
3. `/proc/loadavg` — среднее число готовых к работе процессов за 1, 5 и 15 минут, затем «работают сейчас / всего
   задач», затем последний выданный PID.
4. `/proc/meminfo` — память в КиБ (ядро пишет `kB`, но имеет в виду КиБ). `MemAvailable` — сколько могла бы получить
   новая программа, не вытесняя другие.
5. `ls /proc` — каждая папка с числом вместо имени — это **работающий процесс**: `/proc/1` — это PID 1. Остальные
   записи описывают систему целиком. [Урок 13.2 — Процессы изнутри](02-processes-from-the-inside.md) открывает эти папки.

> 💡 **Совет:** `man 5 proc` описывает каждый файл в `/proc`. Раздел 5 справочника посвящён форматам файлов; когда урок
> пишет `proc(5)`, это значит «страница справки `proc` в разделе 5».

## 5. Как на этом этапе устроен код и где его запускать

Большинство программ этого этапа используют возможности ядра, которые есть только в Linux. Вы пишете их на Mac в
RustRover, но **собираете и запускаете в ВМ `dev`**, и никогда — от root на вашем Mac.

**Структура кода.** Все небольшие примеры Уроков 13.1–13.7 и 13.9 живут в одном пакете, `code/p13-os`. Каждый пример —
отдельный бинарник в `src/bin/`: файл `src/bin/os-info.rs` становится программой `os-info`, которую вы запускаете
командой `cargo run --bin os-info`. Проекты (командная оболочка в Уроке 13.8) получают собственный пакет. Создайте пакет
на Mac:

```bash
cd ~/projects/rust
cargo new code/p13-os
rm code/p13-os/src/main.rs
mkdir code/p13-os/src/bin
```

Мы удаляем `src/main.rs`, потому что у пакета, где есть только файлы в `src/bin/`, нет бинарника по умолчанию; вы
всегда называете нужный через `--bin`.

**Rust внутри ВМ.** Если вы не установили Rust в ВМ на Этапе 11, сделайте это сейчас, один раз. Войдите в ВМ командой
`limactl shell dev` и выполните:

```bash
sudo apt-get update
sudo apt-get install -y build-essential strace rsync
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y
source "$HOME/.cargo/env"
rustc --version
```

Пример вывода последней команды (у вас будет похожий):

```text
rustc 1.100.0 (0ef1bc386 2026-11-09)
```

`build-essential` приносит компилятор C и компоновщик, которые нужны Rust в Linux (Урок 12.12), `strace` — инструмент
из [Урока 13.3 — Системные вызовы](03-system-calls.md), а `rsync` копирует папки.

**Скопировать, затем запустить.** Папка вашего Mac видна в ВМ, но только для чтения (Урок 11.1), поэтому скопируйте пакет
в домашнюю папку ВМ и собирайте его там. Выполняйте это внутри ВМ каждый раз, когда изменили код (замените `student` на
имя пользователя вашего Mac):

```bash
rsync -a --delete --exclude target /Users/student/projects/rust/code/p13-os/ ~/p13-os/
cd ~/p13-os
cargo run --bin os-info
```

`--exclude target` пропускает результаты сборки на Mac, которые в Linux бесполезны; `--delete` удаляет из копии файлы,
которые вы удалили на Mac. Косая черта в конце `p13-os/` означает «содержимое этой папки».

> 💡 **Совет:** каждая программа этого этапа проверена в Linux-контейнере, собранном из официального образа `rust:1.100`
> (Debian, arm64). Выводы в уроках взяты оттуда, поэтому версии ядра, PID и размеры в вашей ВМ будут другими. Поведение
> такое же.

## 6. Первый взгляд на ядро из Rust

Чтение `/proc` из Rust — обычное чтение файлов (Урок 04.10). Создайте `src/bin/os-info.rs`:

```rust
use std::fs;

/// Returns the first number in the text of /proc/uptime: seconds since boot.
fn parse_uptime(text: &str) -> Option<f64> {
    text.split_whitespace().next()?.parse().ok()
}

/// Finds a line like "MemTotal:  8000000 kB" and returns the number (in KiB).
fn meminfo_kib(text: &str, key: &str) -> Option<u64> {
    for line in text.lines() {
        if let Some(rest) = line.strip_prefix(key).and_then(|r| r.strip_prefix(':')) {
            return rest.split_whitespace().next()?.parse().ok();
        }
    }
    None
}

fn main() -> std::io::Result<()> {
    let version = fs::read_to_string("/proc/version")?;
    let uptime = fs::read_to_string("/proc/uptime")?;
    let meminfo = fs::read_to_string("/proc/meminfo")?;

    println!("kernel:    {}", version.trim());
    if let Some(secs) = parse_uptime(&uptime) {
        println!("uptime:    {secs:.0} seconds");
    }
    let total_mib = meminfo_kib(&meminfo, "MemTotal").unwrap_or(0) / 1024;
    let avail_mib = meminfo_kib(&meminfo, "MemAvailable").unwrap_or(0) / 1024;
    println!("memory:    {total_mib} MiB total, {avail_mib} MiB available");
    println!("this PID:  {}", std::process::id());
    Ok(())
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn uptime_takes_the_first_number() {
        assert_eq!(parse_uptime("350735.47 234388.90\n"), Some(350735.47));
        assert_eq!(parse_uptime(""), None);
    }

    #[test]
    fn meminfo_finds_the_exact_key() {
        let text = "MemTotal:        8131124 kB\nMemFree:          912000 kB\n";
        assert_eq!(meminfo_kib(text, "MemTotal"), Some(8131124));
        assert_eq!(meminfo_kib(text, "MemFree"), Some(912000));
        assert_eq!(meminfo_kib(text, "Mem"), None);
    }
}
```

Скопируйте пакет в ВМ (строка с `rsync` выше), затем:

```bash
cargo run -q --bin os-info
cargo test -q --bin os-info
```

```text
kernel:    Linux version 7.0.14-linuxkit (root@buildkitsandbox) (gcc (Alpine 15.2.0) 15.2.0, GNU ld (GNU Binutils) 2.45.1) #1 SMP PREEMPT Fri Oct 30 13:45:20 UTC 2026
uptime:    63802 seconds
memory:    7933 MiB total, 6822 MiB available
this PID:  62

running 2 tests
..
test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

**Что происходит:**

1. `fs::read_to_string("/proc/version")` открывает и читает файл, как любой другой. Ядро генерирует его текст на месте.
2. `parse_uptime` берёт первое слово и разбирает его как `f64`. `?` внутри функции, возвращающей `Option`, досрочно
   возвращает `None`, если первого слова нет (Урок 04.10).
3. `meminfo_kib` ищет строку, которая начинается с ключа, **за которым идёт двоеточие**, поэтому `"Mem"` случайно не
   совпадёт с `"MemTotal"`. Тест `meminfo_finds_the_exact_key` проверяет именно этот граничный случай.
4. `std::process::id()` спрашивает у ядра PID этого процесса. За этим вызовом стоит системный вызов `getpid`; Урок 13.3
   покажет, как его увидеть.
5. Функции разбора отделены от `main` и принимают `&str`, поэтому тестам вообще не нужен `/proc`, и они работают даже на Mac.

> 🧪 **Тестирование:** держите код, который *разговаривает с ядром*, тонким, а код, который *понимает ответ*, — в чистых
> функциях, принимающих текст или числа. Чистую часть можно тестировать где угодно, на фиксированных входах, скопированных
> с настоящей машины, включая странные случаи, которые ваша машина показывает редко.

Когда всё работает, сделайте коммит на Mac: `git add code/p13-os` и `git commit -m "feat(p13): os-info reads /proc"`.

## Частые ошибки

> ⚠️ **Частая ошибка:** запускать программы этого этапа на macOS. Там нет `/proc`, поэтому `os-info` падает с ошибкой:
>
> ```text
> Error: Os { code: 2, kind: NotFound, message: "No such file or directory" }
> ```
>
> Код 2 — это `ENOENT`, «нет такого файла». Запускайте программу в ВМ.

> ⚠️ **Частая ошибка:** собирать прямо в папке Mac, доступной в ВМ только для чтения. `cargo build` в
> `/Users/student/projects/rust/code/p13-os` падает, потому что Cargo не может создать там `target/`; ошибка
> заканчивается на `Read-only file system (os error 30)`. Сначала скопируйте пакет в `~/p13-os`.

> ⚠️ **Частая ошибка:** думать, что у файлов в `/proc` есть размер. `ls -l /proc/uptime` показывает размер 0, а `cat`
> печатает текст. Всегда читайте такие файлы до конца, а не по указанной длине.

## Попробуйте сами

1. В ВМ выполните `cat /proc/uptime` дважды с паузой в несколько секунд. Первое число растёт: файл каждый раз новый.
2. Выполните `cat /proc/self/status | head -5`. `self` всегда означает «процесс, который читает». Какая это программа?
   (Это сам `cat`, поэтому строка `Name:` говорит `cat`.)
3. Выполните `cargo run -q --bin os-info` дважды. PID каждый раз меняется, потому что каждый запуск — новый процесс.
4. Выполните `cargo run -q --bin poke-kernel`, затем `echo $?`. Объясните число 139 своими словами.

## Упражнения

### Упражнение 1 — Сколько процессоров? (легко)

Напишите `src/bin/cpus.rs`. Посчитайте строки `/proc/cpuinfo`, которые начинаются с `processor`, и напечатайте число.
Напечатайте также, что говорит `std::thread::available_parallelism()`. Пример вывода:

```text
/proc/cpuinfo lists 12 CPUs
available_parallelism says 12
```

<details>
<summary>Подсказка</summary>

`text.lines().filter(|line| line.starts_with("processor")).count()`. `available_parallelism` возвращает
`io::Result<NonZero<usize>>`, который можно напечатать через `{}`.

</details>

<details>
<summary>Ответ</summary>

```rust
use std::fs;

fn count_processors(cpuinfo: &str) -> usize {
    cpuinfo
        .lines()
        .filter(|line| line.starts_with("processor"))
        .count()
}

fn main() -> std::io::Result<()> {
    let text = fs::read_to_string("/proc/cpuinfo")?;
    println!("/proc/cpuinfo lists {} CPUs", count_processors(&text));
    let std_count = std::thread::available_parallelism()?;
    println!("available_parallelism says {std_count}");
    Ok(())
}
```

Почему это работает: ядро пишет в `/proc/cpuinfo` по одному блоку на каждое ядро процессора, и каждый блок начинается
со строки `processor : N`. Числа могут различаться, если контейнер или ограничение на процессор сужает вашу программу
(Урок 13.16): `available_parallelism` учитывает такие ограничения, а `/proc/cpuinfo` — нет.

</details>

### Упражнение 2 — Разбор `/proc/loadavg`, сначала тест (средне)

Четвёртое поле `/proc/loadavg` выглядит как `2/492`: готовые к работе задачи сейчас и все задачи. Напишите
`src/bin/loadavg.rs` с функцией `parse_tasks(loadavg: &str) -> Option<(u32, u32)>`. Тесты напишите **первыми**: один с
настоящей строкой `"0.52 0.91 0.51 2/492 183\n"` (ожидается `Some((2, 492))`) и один, который проверяет, что `""`,
`"0.52 0.91 0.51 2-492 183"` и `"0.52 0.91 0.51 x/492 183"` дают `None`. Затем пусть `main` печатает строку вида
`runnable now: 2 of 491 tasks`.

<details>
<summary>Подсказка</summary>

`split_whitespace().nth(3)` даёт четвёртое слово (счёт с 0). `split_once('/')` возвращает `None`, если `/` нет, а
`parse().ok()?` возвращает `None`, если часть — не число.

</details>

<details>
<summary>Ответ</summary>

```rust
use std::fs;

/// Reads the fourth field of /proc/loadavg, "running/total", as two numbers.
fn parse_tasks(loadavg: &str) -> Option<(u32, u32)> {
    let field = loadavg.split_whitespace().nth(3)?;
    let (running, total) = field.split_once('/')?;
    Some((running.parse().ok()?, total.parse().ok()?))
}

fn main() -> std::io::Result<()> {
    let text = fs::read_to_string("/proc/loadavg")?;
    match parse_tasks(&text) {
        Some((running, total)) => println!("runnable now: {running} of {total} tasks"),
        None => eprintln!("could not parse {text:?}"),
    }
    Ok(())
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn parses_a_real_line() {
        assert_eq!(parse_tasks("0.52 0.91 0.51 2/492 183\n"), Some((2, 492)));
    }

    #[test]
    fn rejects_broken_input() {
        assert_eq!(parse_tasks(""), None);
        assert_eq!(parse_tasks("0.52 0.91 0.51 2-492 183"), None);
        assert_eq!(parse_tasks("0.52 0.91 0.51 x/492 183"), None);
    }
}
```

```text
runnable now: 2 of 491 tasks
test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Почему это работает: каждый `?` превращает отсутствующее слово, отсутствующий `/` или неудачный разбор в `None`, поэтому
сломанный ввод никогда не вызывает панику. Тесты используют фиксированный текст, поэтому проходят на любой машине, даже на Mac.

</details>

### Упражнение 3 — Крошечный `ps` (сложно)

Напишите `src/bin/mini-ps.rs`, который выводит все процессы: прочитайте папку `/proc`, оставьте записи, чьё имя — число,
отсортируйте PID и для каждого напечатайте PID и содержимое `/proc/<pid>/comm` (короткое имя программы). Процесс может
завершиться, пока вы читаете; ваша программа не должна при этом падать.

<details>
<summary>Подсказка</summary>

`fs::read_dir("/proc")?` даёт записи; `entry?.file_name()` — это `OsString`, используйте `.to_str()` и
`.parse::<u32>().ok()`. Для каждого PID `if let Ok(comm) = fs::read_to_string(...)` просто пропускает исчезнувший процесс.

</details>

<details>
<summary>Ответ</summary>

```rust
use std::fs;

fn main() -> std::io::Result<()> {
    let mut pids: Vec<u32> = Vec::new();
    for entry in fs::read_dir("/proc")? {
        let name = entry?.file_name();
        // Only folders whose name is a number are processes.
        if let Some(pid) = name.to_str().and_then(|s| s.parse().ok()) {
            pids.push(pid);
        }
    }
    pids.sort();
    println!("{:>6}  COMMAND", "PID");
    for pid in pids {
        // A process can exit between read_dir and read_to_string: skip it then.
        if let Ok(comm) = fs::read_to_string(format!("/proc/{pid}/comm")) {
            println!("{pid:>6}  {}", comm.trim_end());
        }
    }
    Ok(())
}
```

Вывод в маленьком контейнере (в вашей ВМ строк будет гораздо больше):

```text
   PID  COMMAND
     1  bash
   189  mini-ps
```

Почему это работает: настоящий `ps` делает то же самое, только читает больше файлов на процесс. Пропустить ошибку чтения
здесь правильно, потому что список процессов всё время меняется. Два события, порядок которых вы не контролируете,
называют **гонкой** (race; гонки изучает Этап 14); здесь это нормально, а не ошибка.

</details>

## Вопросы для самопроверки

1. Назовите три задачи операционной системы.

<details>
<summary>Ответ</summary>

Абстракция (простые понятия вроде файлов и процессов вместо голого железа), разделение (распределение процессорного
времени, памяти, диска и сети между программами) и защита (программы, пользователи и ядро отделены друг от друга).

</details>

2. Чем пространство пользователя отличается от пространства ядра?

<details>
<summary>Ответ</summary>

Пространство пользователя — это место, где работают обычные программы, а процессор находится на низком уровне привилегий
(EL0 или кольцо 3): некоторые инструкции и память ядра запрещены. Пространство ядра — это память ядра и высокий уровень
привилегий (EL1 или кольцо 0), где разрешено всё.

</details>

3. Ваша программа делит на ноль, приходит сетевой пакет, и ваша программа просит открыть файл. Какая дверь в ядро в каждом случае?

<details>
<summary>Ответ</summary>

Деление на ноль — исключение (его вызывает выполняемая инструкция; на arm64 целочисленное деление на ноль просто
возвращает 0, а Rust сам проверяет делитель и паникует). Пакет — прерывание (его вызывает устройство). Открытие файла —
системный вызов (намеренный запрос).

</details>

4. Почему бесконечный цикл в одной программе не может заморозить всю машину?

<details>
<summary>Ответ</summary>

Из-за прерывания таймера: аппаратный таймер регулярно прерывает процессор, запускается ядро, и оно может отдать процессор
другой программе. Зациклившаяся программа приостанавливается и продолжает позже.

</details>

5. `ls -l /proc/meminfo` показывает размер 0, но `cat` печатает много строк. Почему?

<details>
<summary>Ответ</summary>

`/proc` — это procfs: её файлы нигде не хранятся. Ядро создаёт содержимое, когда вы читаете файл, поэтому сохранённого
размера, который можно было бы показать, нет.

</details>

6. `poke-kernel` завершилась с кодом 139. Какой сигнал её убил и кто его послал?

<details>
<summary>Ответ</summary>

139 − 128 = 11, сигнал `SIGSEGV`. Его послало ядро: процессор сгенерировал исключение на запрещённом чтении, а обработчик
исключений ядра превратил его в сигнал для процесса.

</details>

## Итоги

- ОС прячет железо за абстракциями, делит машину между программами и защищает их друг от друга.
- Ядро — часть ОС, которая работает на высоком уровне привилегий (EL1 на arm64, кольцо 0 на x86-64); программы работают в пространстве пользователя (EL0, кольцо 3).
- Процессор входит в ядро только через системные вызовы, исключения и прерывания; прерывание таймера позволяет ядру забрать процессор обратно.
- Linux — монолитное ядро; дистрибутив добавляет вокруг него программы пространства пользователя.
- `/proc` — окно в ядро: его файлы создаются при каждом чтении, а каждая папка с номером — это процесс.
- На этом этапе вы пишете код на Mac в `code/p13-os` (один бинарник на файл в `src/bin/`), копируете его в ВМ через `rsync` и запускаете там.
