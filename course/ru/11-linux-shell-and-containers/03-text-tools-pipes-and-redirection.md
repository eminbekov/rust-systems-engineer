## Новые слова

| Слово | Значение |
|---|---|
| **стандартный поток** (standard stream) | Один из трёх каналов, которые получает каждая программа при запуске: *стандартный ввод* (stdin), *стандартный вывод* (stdout) и *стандартный вывод ошибок* (stderr). |
| **файловый дескриптор** (file descriptor, fd) | Небольшое число, которым операционная система называет открытый файл или поток. stdin — 0, stdout — 1, stderr — 2. |
| **перенаправление** (redirection) | Отправка потока в файл (или чтение его из файла) вместо терминала. |
| **конвейер** (pipe) | Оператор `\|`: вывод левой программы становится вводом правой. |
| **цепочка конвейера** (pipeline) | Несколько команд, соединённых конвейерами. |
| **фильтр** (filter) | Программа, которая читает текст из stdin, изменяет или отбирает его часть и пишет результат в stdout. `grep`, `sort` и `cut` — фильтры. |
| **регулярное выражение** (regular expression, regex) | Краткий язык шаблонов для текста, например `[0-9]+` означает «одна или больше цифр». Его понимают `grep -E` и `sed`. |
| **поле / разделитель** (field / delimiter) | *Поле* — один столбец строки; *разделитель* — символ, который разделяет столбцы (пробел, запятая, двоеточие). |
| **файл журнала** (log file) | Текстовый файл, в который программа пишет, что произошло, по одному событию на строку. |
| **подстановка команды** (command substitution) | `$(command)`: оболочка выполняет команду и подставляет её вывод в строку. |

## 1. Три потока

Каждая программа стартует с тремя открытыми каналами:

```text
                 +-----------+
  keyboard  ---> | 0 stdin   |
                 |  program  | ---> 1 stdout ---> terminal screen
                 |           | ---> 2 stderr ---> terminal screen
                 +-----------+
```

- **stdin (0)** — откуда программа читает ввод. По умолчанию: клавиатура.
- **stdout (1)** — куда она пишет результаты. По умолчанию: терминал.
- **stderr (2)** — куда она пишет сообщения об ошибках и ходе работы. По умолчанию тоже терминал.

Два выходных канала существуют, чтобы *результаты* и *сообщения для человека* не смешивались. Экран показывает оба,
поэтому разницы не видно, пока вы не перенаправите. Сначала — небольшой файл с данными. Это выдуманный журнал веб-сервера с пятью полями в строке:
IP-адрес (IP, Internet Protocol, межсетевой протокол), метод, путь, код статуса и отправленные байты. Адреса взяты из диапазонов, зарезервированных для примеров.

```bash
mkdir ~/text-lab
cd ~/text-lab
cat > access.log <<'EOF'
203.0.113.5 GET /index.html 200 512
198.51.100.7 GET /api/items 200 1280
203.0.113.5 GET /missing.png 404 0
192.0.2.44 POST /api/items 201 64
203.0.113.5 GET /api/items 200 1280
198.51.100.7 GET /index.html 200 512
192.0.2.44 GET /admin 403 0
203.0.113.9 GET /api/items 500 0
198.51.100.7 GET /api/items 200 1280
203.0.113.5 GET /index.html 304 0
192.0.2.44 GET /missing.png 404 0
203.0.113.5 DELETE /api/items/7 204 0
EOF
wc -l access.log
```

```text
12 access.log
```

**Что происходит:**

1. `cat > access.log <<'EOF'` — это *here-document* (как в Уроке 00.4): всё до строки `EOF` попадает в файл. Кавычки вокруг `'EOF'` не дают оболочке менять знаки `$` внутри.
2. `wc -l` («word count», строки) считает строки: 12.

## 2. Перенаправление

Выполните `ls` для одного существующего файла и одного несуществующего:

```bash
ls access.log /nope
```

```text
ls: cannot access '/nope': No such file or directory
access.log
```

Первая строка — stderr, вторая — stdout. (Порядок на вашем экране может отличаться.) Теперь перенаправим:

| Оператор | Значение |
|---|---|
| `> file` | записать stdout в `file`; **заменить** файл, если он существует |
| `>> file` | **дописать** stdout в конец `file` |
| `< file` | читать stdin из `file` |
| `2> file` | записать stderr (поток 2) в `file` |
| `2>&1` | отправить stderr туда же, куда идёт stdout |
| `&> file` | отправить оба потока в `file` (короткая форма в bash) |

```bash
ls access.log /nope > out.txt
```

```text
ls: cannot access '/nope': No such file or directory
```

**Что происходит:** stdout ушёл в `out.txt` (там лежит `access.log`); ошибка не была перенаправлена, поэтому она по-прежнему
появляется на экране. Перенаправьте ошибку и вывод по отдельности, затем вместе:

```bash
ls access.log /nope 2> err.txt
cat err.txt
ls access.log /nope > both.txt 2>&1
cat both.txt
```

```text
access.log
ls: cannot access '/nope': No such file or directory
ls: cannot access '/nope': No such file or directory
access.log
```

**Что происходит:**

1. Первая команда `ls` напечатала `access.log` (stdout, не перенаправлен) и записала ошибку в `err.txt`, которую показал `cat`.
2. Во второй `> both.txt` направляет stdout в файл, а `2>&1` затем говорит «поток 2 идёт туда, куда сейчас идёт поток 1»: оба оказываются в `both.txt`.

> ⚠️ **Частая ошибка:** важен **порядок**. `cmd > file 2>&1` отправляет оба потока в файл. `cmd 2>&1 > file` сначала
> направляет stderr туда, где *сейчас* stdout (на экран), и только потом переносит stdout в файл, поэтому ошибки по-прежнему
> появляются на экране. Читайте перенаправления слева направо.

`>` уничтожает прежнее содержимое файла; `>>` дописывает. Оба создают файл, если его нет:

```bash
echo one > l.txt
echo two >> l.txt
cat l.txt
echo three > l.txt
cat l.txt
```

```text
one
two
three
```

**Что происходит:** после `echo three > l.txt` в файле только `three`; `one` и `two` исчезли.

Особый файл `/dev/null` ([Урок 11.2](02-the-linux-file-system.md)) выбрасывает данные, поэтому `2>/dev/null` означает
«я не хочу видеть ошибки». Используйте `<`, чтобы подать файл программе, читающей stdin:

```bash
wc -l < access.log
ls access.log /nope 2>/dev/null
```

```text
12
access.log
```

> 💡 **Совет:** `wc -l access.log` печатает имя файла, а `wc -l < access.log` — только число, потому что `wc` не знает
> имени своего stdin. Это удобно в скриптах.

> 🔒 **Безопасность:** `>` может за секунду затереть важный файл. Прежде чем набрать `> something`, проверьте, что
> имя именно то, которое вы имеете в виду. В скриптах держите выходные файлы в отдельном каталоге. Bash умеет отказываться затирать существующий файл: после `set -o noclobber` команда `echo x > old.txt` завершается ошибкой `cannot overwrite existing file`, а `>|` принудительно перезаписывает.

## 3. Конвейеры

**Конвейер** соединяет stdout одной команды со stdin следующей, без файла посередине:

```text
  access.log --> [ cut ] --pipe--> [ sort ] --pipe--> [ uniq -c ] --> terminal
```

Команды работают **одновременно**; данные идут дальше, как только появляются. Если читатель медленный, писатель
ждёт. Временный файл не нужен, и огромный файл никогда не загружается в память целиком. По конвейеру передаётся только stdout;
stderr по-прежнему идёт на экран, если только вы не напишете `2>&1` перед конвейером.

```bash
ls /usr/bin | wc -l
(echo out; echo err >&2) | wc -l
```

```text
444
err
1
```

**Что происходит:** первое число (количество файлов в `/usr/bin`) зависит от вашей системы. Вторая команда печатает `out` в stdout (в конвейер)
и `err` в stderr (на экран), поэтому `wc -l` насчитал **одну** строку. С `2>&1` внутри скобок `wc` насчитал бы 2.

Эта идея — маленькие программы, делающие одно дело и соединяемые конвейерами — называется *философией Unix*. Выучите маленькие утилиты, и вы сможете
отвечать на многие вопросы, не написав ни одной программы.

## 4. Набор текстовых утилит

Во всех примерах используется `access.log` из раздела 1.

### Начало, конец, размер

```bash
head -n 3 access.log
tail -n 2 access.log
wc access.log
```

```text
203.0.113.5 GET /index.html 200 512
198.51.100.7 GET /api/items 200 1280
203.0.113.5 GET /missing.png 404 0
192.0.2.44 GET /missing.png 404 0
203.0.113.5 DELETE /api/items/7 204 0
 12  60 419 access.log
```

**Что происходит:** `head -n 3` показывает первые 3 строки, `tail -n 2` — последние 2. `wc` без параметров печатает строки, слова и байты.
`tail -f file` («follow», следить) продолжает работать и печатает новые строки по мере того, как программа их дописывает; это стандартный способ смотреть
журнал вживую. Остановите его клавишами `Ctrl + C`. Чтобы читать длинный файл постранично, используйте `less file` (стрелки, `/word` — поиск, `q` — выход).

### Вырезаем столбцы, сортируем, считаем

```bash
cut -d' ' -f1 access.log | sort | uniq -c
```

```text
      3 192.0.2.44
      3 198.51.100.7
      5 203.0.113.5
      1 203.0.113.9
```

**Что происходит:**

1. `cut -d' ' -f1` берёт пробел как **разделитель** (`-d`) и оставляет поле номер 1 (`-f1`): IP-адрес.
2. `sort` упорядочивает строки. По умолчанию порядок алфавитный, строка за строкой.
3. `uniq -c` схлопывает **соседние** одинаковые строки в одну и пишет, сколько их было (`-c`, count — количество).

`uniq` сравнивает только соседей, поэтому почти всегда перед ним ставят `sort`. Без `sort` одинаковые строки, стоящие не рядом, не объединяются.
Теперь расположим результат по убыванию частоты:

```bash
cut -d' ' -f1 access.log | sort | uniq -c | sort -rn | head -n 2
```

```text
      5 203.0.113.5
      3 198.51.100.7
```

**Что происходит:** `sort -rn` сортирует **чи**сленно (`-n`, numeric) в **обратном** порядке (`-r`, reverse). Без `-n` `10` идёт раньше `9`,
потому что текст сравнивается посимвольно:

```bash
printf '10\n9\n100\n' | sort
printf '10\n9\n100\n' | sort -n
```

```text
10
100
9
9
10
100
```

`sort -u` оставляет по одной копии каждой строки (unique, уникальные). `printf` похож на `echo`, но понимает `\n` как перевод строки.

### Поиск: `grep`

```bash
grep 404 access.log
grep -c GET access.log
grep -v GET access.log
grep -n admin access.log
grep -E ' (4|5)[0-9][0-9] ' access.log
```

```text
203.0.113.5 GET /missing.png 404 0
192.0.2.44 GET /missing.png 404 0
10
192.0.2.44 POST /api/items 201 64
203.0.113.5 DELETE /api/items/7 204 0
7:192.0.2.44 GET /admin 403 0
203.0.113.5 GET /missing.png 404 0
192.0.2.44 GET /admin 403 0
203.0.113.9 GET /api/items 500 0
192.0.2.44 GET /missing.png 404 0
```

**Что происходит:**

1. `grep 404 access.log` печатает строки, содержащие `404`.
2. `-c` считает подходящие строки вместо того, чтобы печатать их: 10 строк содержат `GET`.
3. `-v` инвертирует: строки, которые **не** содержат `GET`.
4. `-n` добавляет номер строки (`7:`). `-i` игнорирует регистр, а `-r` ищет во всех файлах каталога рекурсивно (`grep -r admin .`).
5. `-E` включает *расширенные регулярные выражения*. `(4|5)[0-9][0-9]` означает: `4` или `5`, затем две цифры, то есть находит коды статуса от 400 до 599. Пробелы вокруг гарантируют, что мы не совпадём внутри других чисел.

> ⚠️ **Частая ошибка:** `grep 404` находит также `1404` или путь `/page404`. Сделайте шаблон точнее (`' 404 '`) или сначала вырежьте нужное поле.

### Изменяем текст: `tr`, `sed`

```bash
echo "Hello World" | tr a-z A-Z
echo "a,b,c" | tr ',' '\n'
sed 's/GET/get/' access.log | head -n 2
sed -n '2,3p' access.log
```

```text
HELLO WORLD
a
b
c
203.0.113.5 get /index.html 200 512
198.51.100.7 get /api/items 200 1280
198.51.100.7 GET /api/items 200 1280
203.0.113.5 GET /missing.png 404 0
```

**Что происходит:**

1. `tr` («translate», преобразовать) заменяет отдельные **символы**: строчные буквы на заглавные, запятые на переводы строк. `tr -s ' '` сжимает повторяющиеся пробелы в один.
2. `sed` — «потоковый редактор». `s/GET/get/` — команда подстановки: заменить первое `GET` в каждой строке на `get`. Добавьте `g` в конце (`s/a/b/g`), чтобы заменить все вхождения в строке.
3. `sed -n '2,3p'` означает: по умолчанию не печатать (`-n`), напечатать (`p`) строки с 2 по 3.

`sed -i 's/old/new/' file` правит **сам файл**; сделайте сначала копию, потому что отмены нет.

### Работаем со столбцами: `awk`

`awk` читает строку, делит её на поля `$1`, `$2` … и выполняет вашу маленькую программу для каждой строки:

```bash
awk '{print $1, $4}' access.log | head -n 3
awk '{sum += $5} END {print sum}' access.log
awk '$4 >= 400 {print $2, $3, $4}' access.log
```

```text
203.0.113.5 200
198.51.100.7 200
203.0.113.5 404
4928
GET /missing.png 404
GET /admin 403
GET /api/items 500
GET /missing.png 404
```

**Что происходит:**

1. `{print $1, $4}` печатает поле 1 и поле 4 каждой строки.
2. `{sum += $5}` прибавляет поле 5 (байты) к переменной для каждой строки; `END {...}` выполняется один раз после последней строки. Итого 4928 байт.
3. `$4 >= 400 {...}` — *условие* перед фигурными скобками: действие выполняется только для строк, где статус 400 или больше.

Одинарные кавычки не дают оболочке трогать `$1`. `awk` — небольшой язык; двух-трёх шаблонов вроде этих хватает на большинство повседневных задач.

### Утилиты-соединители: `tee`, `xargs`, `$( )`

```bash
ls /etc | wc -l | tee count.txt
printf 'x.txt\ny.txt\n' | xargs touch
find . -name '*.txt' | xargs wc -l | tail -n 1
echo "the log has $(wc -l < access.log) lines"
```

```text
96
  6 total
the log has 12 lines
```

**Что происходит:**

1. `tee` копирует stdin в файл **и** в stdout, как Т-образный разветвитель. Вы видите число `96` (у вас будет другое) и оно же сохранено в `count.txt`.
2. `xargs` превращает строки со своего stdin в **аргументы** другой команды. Здесь он выполнил `touch x.txt y.txt`. Отличие от конвейера: `touch` не читает stdin, поэтому `... | touch` не сработает; `xargs` делает так, что работает. В третьей команде `xargs` собирает `wc -l file1 file2 ...` из найденных имён; `tail -n 1` оставляет строку `total`.
3. `$(command)` — **подстановка команды**: оболочка выполняет команду и подставляет её вывод в строку перед запуском `echo`.

> ⚠️ **Частая ошибка:** `find ... | xargs rm` ломается на именах с пробелами (он делит по пробелам). Безопасная форма разделяет имена нулевым байтом:
> `find . -name '*.tmp' -print0 | xargs -0 rm`. Сначала запустите её с `echo` (`xargs -0 echo rm`), чтобы увидеть, что она сделает.

## 5. Настоящий вопрос одной строкой

«Какие пути запросов чаще всего приводят к ошибкам?» Разбейте задачу на шаги и проверяйте каждый шаг, прежде чем добавлять следующий конвейер:

```bash
awk '$4 >= 400 {print $3}' access.log | sort | uniq -c | sort -rn
```

```text
      2 /missing.png
      1 /api/items
      1 /admin
```

**Что происходит:**

1. `awk` оставляет путь (поле 3) в строках со статусом 400 или больше.
2. `sort | uniq -c` считает одинаковые пути. `sort -rn` ставит самые частые первыми.

Проверим всё вместе: сумма отправленных байтов по каждому IP-адресу.

```bash
awk '{b[$1] += $5} END {for (ip in b) print ip, b[ip]}' access.log | sort
```

```text
192.0.2.44 64
198.51.100.7 3072
203.0.113.5 1792
203.0.113.9 0
```

**Что происходит:** `b[$1] += $5` использует *ассоциативный массив* (таблицу с текстовыми ключами): для каждого IP прибавляются байты. После последней строки `for (ip in b)` печатает каждый ключ и итог. `sort` делает порядок стабильным, потому что `awk` не гарантирует никакого порядка.

> 📏 **Соглашение:** стройте конвейеры **по шагам**: запустите первую команду отдельно, посмотрите вывод, добавьте `| next`, посмотрите снова.
> Если конвейер вырос больше чем до трёх-четырёх шагов или нужен вам не один раз, он становится скриптом ([Урок 11.8](08-bash-scripting-basics.md)).

## 6. Ваши программы на Rust и потоки

Программы на Rust используют те же три потока: `println!` пишет в stdout, `eprintln!` пишет в stderr, а `std::io::stdin()` читает stdin.
Программа, следующая этому правилу, работает в конвейерах с `grep` и `sort` без дополнительных усилий. (Поэтому программы
пишут свои *журналы* в stderr или stdout и оставляют файлы оболочке; [Урок 08.15](../08-software-design/15-the-twelve-factor-app.md) называет это привычкой 12-факторного приложения, а [Урок 09.10](../09-testing-debugging-benchmarking/10-logging-and-tracing.md) посвящён логированию.)

Откройте вкладку терминала **Mac**. Напишем крошечный фильтр `p11-streams`: он считает строки своего stdin, содержащие слово.

```bash
cd ~/projects/rust
cargo new code/p11-streams
```

Замените `code/p11-streams/src/main.rs`:

```rust
use std::io::{self, BufRead};

/// Counts how many lines contain `word`.
fn count_matching<I>(lines: I, word: &str) -> usize
where
    I: Iterator<Item = String>,
{
    lines.filter(|line| line.contains(word)).count()
}

fn main() {
    let Some(word) = std::env::args().nth(1) else {
        eprintln!("usage: p11-streams WORD < input");
        std::process::exit(2);
    };

    eprintln!("reading standard input...");
    let stdin = io::stdin();
    let lines = stdin
        .lock()
        .lines()
        .map(|line| line.expect("cannot read a line"));
    println!("{}", count_matching(lines, &word));
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn counts_only_lines_with_the_word() {
        let lines = ["a 404", "b 200", "c 404"].iter().map(|s| s.to_string());
        assert_eq!(count_matching(lines, "404"), 2);
    }
}
```

**Что происходит:**

1. `std::env::args().nth(1)` — первый аргумент после имени программы. Без аргумента программа печатает сообщение об использовании в **stderr** и завершается со статусом 2 (ненулевой статус означает неудачу; Урок 11.5).
2. Сообщение о ходе работы `reading standard input...` уходит в stderr через `eprintln!`, поэтому никогда не загрязняет результат.
3. `stdin.lock().lines()` даёт строки stdin в виде итератора. `count_matching` считает те, что содержат слово. Результат уходит в stdout через `println!`.
4. Сама функция не читает stdin: она принимает любой итератор строк, поэтому тест может передать готовый список. (Это идея тестируемого проектирования из [Этапа 08](../08-software-design/README.md).)

Создайте небольшой вход и попробуйте все виды перенаправления (`-q` делает сам Cargo тихим):

```bash
printf 'a 404\nb 200\nc 404\n' > in.txt
cargo run -q -- 404 < in.txt
cat in.txt | cargo run -q -- 404
cargo run -q -- 404 < in.txt > count.txt
cat count.txt
cargo run -q -- 404 < in.txt 2>/dev/null
cargo run -q
echo "status: $?"
```

```text
reading standard input...
2
reading standard input...
2
reading standard input...
2
2
usage: p11-streams WORD < input
status: 2
```

**Что происходит:** строки 1–2 даёт первая команда (stderr, затем stdout). Строки 3–4 — то же самое с конвейером от `cat`.
Третья команда отправила stdout в `count.txt`, поэтому на экране появилось только сообщение о ходе работы; `cat count.txt` печатает результат `2`.
С `2>/dev/null` виден только результат `2`. У последней команды нет аргумента: сообщение об использовании и статус 2.

🧪 **Тестирование:**

```bash

```

```text

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Когда закончите, уберите за собой: `rm in.txt count.txt` в папке проекта, а в ВМ — `rm -r ~/text-lab`.

## Частые ошибки

1. **Забыли `sort` перед `uniq -c`.** Счётчики неверны, потому что объединяются только соседние строки. *Исправление:* `... | sort | uniq -c`.
2. **`>` вместо `>>`.** Старое содержимое журнала потеряно. *Исправление:* используйте `>>`, чтобы дописывать; дважды проверяйте имя перед `>`.
3. **`2>&1` не на своём месте.** `cmd 2>&1 > file` не кладёт ошибки в файл. *Исправление:* `cmd > file 2>&1`.
4. **Чтение и запись в один и тот же файл.** `sort access.log > access.log` сначала опустошает файл (оболочка открывает его на запись до запуска `sort`). *Исправление:* пишите в другой файл: `sort access.log > sorted.log`.
5. **Шаблоны без кавычек.** `grep ' 404 ' file` нормально, а `awk {print $1}` без кавычек оболочка изменит. *Исправление:* берите программу awk в одинарные кавычки.
6. **Числа отсортированы как текст.** `10` раньше `9`. *Исправление:* `sort -n`.

## Упражнения

### Упражнение 1 — Считаем конвейером (легко)

Сколько запросов сделал IP-адрес `203.0.113.5`? Используйте `grep` и `wc`, затем попробуйте короче — только с `grep`.

<details>
<summary>Подсказка</summary>

`grep` печатает подходящие строки; `wc -l` считает строки. У `grep` есть и параметр, который считает.

</details>

<details>
<summary>Ответ</summary>

```bash
grep '^203.0.113.5 ' access.log | wc -l
grep -c '^203.0.113.5 ' access.log
```

Обе печатают `5`.

Почему это работает: `^` привязывает шаблон к началу строки, а пробел после адреса не даёт совпасть с `203.0.113.55` (точки тоже совпадают с любым символом, но для этих данных это неважно). `-c` считает подходящие строки.

</details>

### Упражнение 2 — Добавьте тесты к фильтру на Rust (средне)

В `code/p11-streams` добавьте два теста для `count_matching`: один для **пустого ввода** (результат 0) и один для слова, которого **нет** (тоже 0).

<details>
<summary>Подсказка</summary>

Для пустого случая передайте `std::iter::empty()`. Функция принимает любой итератор `String`, поэтому у итератора должен быть конкретный тип элементов: `std::iter::empty::<String>()`.

</details>

<details>
<summary>Ответ</summary>

Добавьте внутрь `mod tests`:

```rust
    #[test]
    fn empty_input_counts_zero() {
        assert_eq!(count_matching(std::iter::empty::<String>(), "404"), 0);
    }

    #[test]
    fn missing_word_counts_zero() {
        let lines = ["a 200", "b 200"].iter().map(|s| s.to_string());
        assert_eq!(count_matching(lines, "404"), 0);
    }
```

```text
running 3 tests
test tests::counts_only_lines_with_the_word ... ok
test tests::missing_word_counts_zero ... ok
test tests::empty_input_counts_zero ... ok

test result: ok. 3 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

(Порядок строк `test` у вас может отличаться: тесты выполняются параллельно.)

Почему это работает: функции нужен только итератор строк, поэтому тестам не нужны настоящий stdin или файл. Граничные случаи (пустой ввод, нет совпадений) — именно там прячутся ошибки.

</details>

### Упражнение 3 — Байты по IP, сначала самые большие (сложно)

Напечатайте сумму байтов по каждому IP-адресу, сначала самую большую, в виде `198.51.100.7 3072`.

<details>
<summary>Подсказка</summary>

Программа на `awk` есть в разделе 5. Порядок — дело `sort`: сортируйте численно (`-n`), в обратном порядке, по **второму** полю (`-k2`).

</details>

<details>
<summary>Ответ</summary>

```bash
awk '{b[$1] += $5} END {for (ip in b) print ip, b[ip]}' access.log | sort -k2 -rn
```

```text
198.51.100.7 3072
203.0.113.5 1792
192.0.2.44 64
203.0.113.9 0
```

Почему это работает: `awk` выдаёт строки `IP итог` в произвольном порядке; `sort -k2 -rn` упорядочивает их по второму столбцу, как числа, от большего к меньшему.

</details>

## Вопросы для самопроверки

1. Какие номера у stdin, stdout и stderr?

<details>
<summary>Ответ</summary>

0, 1 и 2.

</details>

2. Чем отличаются `>` и `>>`?

<details>
<summary>Ответ</summary>

`>` заменяет содержимое файла; `>>` дописывает в конец.

</details>

3. Почему `cmd 2>&1 > file` всё равно печатает ошибки на экран?

<details>
<summary>Ответ</summary>

Перенаправления применяются слева направо. `2>&1` направляет stderr туда, где в этот момент stdout (на экран); только потом stdout переходит в файл.

</details>

4. Почему `sort` должен идти раньше `uniq`?

<details>
<summary>Ответ</summary>

`uniq` объединяет только соседние одинаковые строки. `sort` ставит одинаковые строки рядом.

</details>

5. Почему программа на Rust печатает сообщения о ходе работы через `eprintln!`, а не `println!`?

<details>
<summary>Ответ</summary>

Чтобы результат в stdout оставался чистым для следующей программы в конвейере или для файла; сообщения для человека идут в stderr.

</details>

## Итоги

- У каждой программы есть stdin (0), stdout (1) и stderr (2). В Rust: `stdin()`, `println!`, `eprintln!`.
- `>` заменяет, `>>` дописывает, `<` читает из файла, `2>` перенаправляет ошибки, `2>&1` объединяет ошибки с выводом; порядок читается слева направо.
- Конвейер `|` соединяет stdout со следующим stdin; команды работают одновременно.
- Основные утилиты: `head`, `tail`, `wc`, `sort` (`-n`, `-r`, `-u`), `uniq -c`, `cut`, `tr`, `grep` (`-c -v -n -i -E`), `sed 's/a/b/'`, `awk`, `tee`, `xargs`.
- `$(command)` подставляет вывод одной команды в другую.
- Стройте конвейеры по шагам; когда конвейер становится длинным или нужен снова, превращайте его в скрипт.
