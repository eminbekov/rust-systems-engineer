## Новые слова

| Слово | Значение |
|---|---|
| **кадр вызова** (call frame) | Переменные одного выполняющегося вызова функции. Каждый вызов получает новый кадр; он исчезает, когда вызов возвращается. |
| **глубина рекурсии** (recursion depth) | Сколько вызовов активны одновременно, один внутри другого. |
| **статическая проверка типов** (static type checker) | Проход компилятора, который даёт каждому выражению тип (`int` или `bool`) и сообщает о несовпадениях *до* запуска программы. «Статическая» значит «по исходному тексту, без запуска». |
| **проход компилятора** (compiler pass) | Один обход синтаксического дерева, выполняющий одну задачу: проверку типов, генерацию кода и так далее. |
| **бэкенд** (back end) | Часть реализации языка, которая выполняет или переводит проверенное дерево; у Pebble будет два бэкенда — интерпретатор и компилятор в WebAssembly. |
| **импорт (функция хоста)** (import, host function) | Функция, которую модуль WebAssembly вызывает, а предоставляет хост, например `print_int`. |
| **`Linker`** | Тип из `wasmtime`, который связывает импорты модуля с функциями хоста перед созданием экземпляра модуля. |
| **семантика** (semantics) | Что *означают* программы языка: что вычисляет каждая операция и что происходит при ошибках. |
| **дифференциальный тест** (differential test) | Тест, который запускает две реализации на одних и тех же входах и проверяет, что результаты равны. |

**Сокращения из Урока 22.24:** WAT (WebAssembly Text format, текстовый формат WebAssembly — читаемая форма модуля) и
WASI (WebAssembly System Interface, системный интерфейс WebAssembly — стандартные импорты для файлов, часов и вывода).

## 1. Законченный язык

В конце проекта у Pebble появятся функции. Вот программа, которую вы запустите обоими способами:

```text
// Fibonacci numbers, the slow recursive way.
fn fib(n) {
    if n < 2 {
        return n;
    }
    return fib(n - 1) + fib(n - 2);
}

print fib(10);
print fib(20);
```

Реализация становится конвейером с двумя бэкендами:

```text
 source ─▶ lexer ─▶ parser ─▶ type checker ─┬─▶ interpreter ──────────────────▶ output
                                            │
                                            └─▶ code generator ─▶ WAT ─▶ Wasmtime ─▶ output
                                                                         (print_int, print_bool
                                                                          are host functions)
                     the differential test checks that both outputs are equal
```

## Проект

### Что вы создадите

`p22-pebble` — законченный маленький язык с одной программой командной строки и четырьмя командами:
`check` (только проверка типов), `run` (интерпретатор), `compile` (печать текста WebAssembly) и `wasm`
(компиляция и запуск во встроенном Wasmtime).

### Контракт

**Командная строка:** `p22-pebble <run|check|compile|wasm> <file.pb>`. Код возврата 0 при успехе, 1 при
любой ошибке (синтаксической, типов или выполнения), 2 при неправильном использовании.

**Дополнения языка:**

```text
statement := ...
           | "fn" IDENT "(" (IDENT ("," IDENT)*)? ")" block      (only at the top level)
           | "return" expr ";"                                    (only inside a function)
expr      := ... | IDENT "(" (expr ("," expr)*)? ")"              (a call)
```

**Семантика (оба бэкенда должны следовать ей точно):**

1. Параметры функций и возвращаемые значения — `int`. Функция, которая заканчивается без `return`,
   возвращает `0`.
2. Функция видит только свои параметры и свои переменные `let`, но не переменные вызывающего кода и не
   переменные верхнего уровня. Функции могут вызывать друг друга и себя в любом порядке определения.
3. Целочисленные `+ - *` и префиксный `-` при переполнении **переносят значение по модулю**
   (дополнительный код, Урок 12.2).
4. Деление или остаток от деления на ноль — ошибка выполнения `division by zero`; `i64::MIN / -1` —
   `integer overflow`.
5. Больше 200 активных вызовов — ошибка выполнения `call stack too deep`.
6. `print` пишет `int` как десятичное число, а `bool` — как `true` или `false`, по одному значению на
   строку.
7. Ошибки идут в стандартный поток ошибок: `<file>:<line>:<col>: type error: <message>` от `check` (все,
   по одной на строку) и `<file>: runtime error: <message>` от `run` и `wasm`. Вывод, напечатанный до
   ошибки выполнения, остаётся напечатанным.

**Вне рамок проекта** (дополнительные цели): типы, кроме `int` и `bool`, строки, массивы, замыкания.

### Пошаговый план

#### M1 — Функции в парсере

**Цель:** разбирать определения функций, `return` и вызовы.

**Указания:** три новых токена (`Fn`, `Return`, `Comma`), `Stmt::Fn(name, params, body, pos)`,
`Stmt::Return(expr, pos)` и `Expr::Call(name, args, pos)`. Вызов — это имя, за которым идёт `(`:
проверьте следующий токен в `prefix` так же, как `statement` делает это для присваивания. Печатайте их
как S-выражения: `(fn fib (n) (block ...))`, `(return ...)`, `(call fib (- n 1))`.

<details>
<summary>Подсказка</summary>

Напишите вспомогательную функцию `fn ident(&mut self, what: &str) -> Result<String, ParseError>`,
которая забирает один идентификатор или падает с «expected <what>». Списки параметров и аргументов — это
«ноль или больше, через запятую»: разберите один, затем повторяйте, пока следующий токен — запятая.

</details>

**Готово, когда:** тест парсера проверяет, что `fn add(a, b) { return a + b; } print add(1, 2);`
печатается как `(fn add (a b) (block (return (+ a b))))` и `(print (call add 1 2))`, а старые тесты
по-прежнему проходят. Коммит.

#### M2 — Функции в интерпретаторе

**Цель:** вызовы с новыми кадрами, рекурсия, `return`, ограничение глубины.

**Указания:** перед запуском соберите все `Stmt::Fn` в `HashMap<String, Rc<...>>` (чтобы вызовы могли
стоять раньше определений). `return` должен сразу покинуть все охватывающие блоки и циклы: пусть `exec`
возвращает `Result<Flow, RuntimeError>` с `enum Flow { Normal, Return(Value) }`, и выполнение блока
прекращается, как только инструкция вернула `Flow::Return`. Для вызова вычислите аргументы в
вызывающем коде, затем подмените `self.scopes` новым стеком, в котором только параметры, выполните тело
и верните стек обратно. Переведите `+ - *` на `wrapping_*` (пункт 3 семантики).

<details>
<summary>Подсказка</summary>

`std::mem::replace(&mut self.scopes, vec![frame])` возвращает вам области видимости вызывающего кода как
значение, которое потом нужно восстановить. Считайте глубину в поле и проверяйте её *до* вызова.
Держите предел умеренным: интерпретатор рекурсивно вызывает функции Rust для каждого вызова Pebble, а у
тестовых потоков стек меньше, чем у `main` (по умолчанию 2 МиБ); с пределом 1000 дифференциальный тест
из M5 переполнил свой стек в отладочной сборке.

</details>

**Готово, когда:**

```bash
cargo run -- run programs/fib.pb
```

```text
55
6765
```

а `programs/deep.pb`

```text
fn down(n) {
    return down(n + 1);
}
print down(0);
```

даёт в стандартном потоке ошибок `programs/deep.pb: runtime error: call stack too deep` с кодом
возврата 1. Коммит.

#### M3 — Статическая проверка типов

**Цель:** `check` сообщает об ошибках типов с позициями до любого запуска; `run`, `compile` и `wasm`
отказываются от программ с ошибками типов.

**Указания:** новый модуль `src/check.rs` с
`pub fn check(program: &[Stmt]) -> Result<(), Vec<String>>`. Обойдите дерево со стеком областей
видимости, который сопоставляет имена с `Type::Int` или `Type::Bool`. Правила: арифметике и
`< <= > >=` нужны два int; `&&`, `||`, `!` нужны bool; `==` и `!=` нужны два операнда одного типа;
условия — bool; аргументы и значения `return` — int; вызовам нужна известная функция с правильным
числом аргументов. Собирайте *все* ошибки, а не останавливайтесь на первой.

<details>
<summary>Подсказка</summary>

Пусть метод для выражений возвращает `Option<Type>`: `None` значит «ошибка внутри этого выражения уже
сообщена». Тогда одна ошибка не порождает каскад последующих. Проверьте также правила «`fn` только на
верхнем уровне» и «`return` только внутри функции».

</details>

**Готово, когда:** с `programs/bad_types.pb`

```text
let ready = true;
print ready + 1;
let n = 5;
if n {
    print n;
}
```

`cargo run -- check programs/bad_types.pb` печатает

```text
programs/bad_types.pb:2:13: type error: `+` cannot combine bool and int
programs/bad_types.pb:4:4: type error: expected bool, found int
```

и завершается с кодом 1, а `cargo run -- check programs/fib.pb` печатает `programs/fib.pb: ok`. Коммит.

#### M4 — Компиляция целых программ в WebAssembly

**Цель:** `compile` печатает модуль WAT; `wasm` запускает его в Wasmtime с двумя функциями хоста.

**Указания:** расширьте генератор кода из Урока 22.24 в `src/compile.rs`:

- Каждая функция Pebble становится `(func $f_<name> (param $<p> i64)... (result i64) ...)` и
  заканчивается `i64.const 0` для случая «нет `return`». Инструкции верхнего уровня становятся
  `(func (export "main") ...)`.
- Каждый `let` становится новой локальной переменной с уникальным именем (`$x_0`, `$x_1`, ...),
  объявленной в начале её функции как `(local $x_0 i64)`. Стек областей видимости сопоставляет имена
  Pebble с локальными переменными WAT, поэтому затенение работает.
- `print` вызывает импорт `$print_int` или `$print_bool` в зависимости от типа выражения; объявите их в
  начале: `(import "env" "print_int" (func $print_int (param i64)))`.
- Для `if` и `while` нужно условие `i32`: `i32.wrap_i64` перед `if`; для `while` используйте
  `block $exit loop $again <cond> i64.eqz br_if $exit <body> br $again end end`.
- `&&` и `||` вычисляются по короткой схеме через `if (result i64) ... else ... end`.
- Инструкция-выражение заканчивается `drop`; `return` — это `<expr> return`.

Для `wasm` напишите `src/runwasm.rs`: `wasmtime::Linker<String>` с двумя функциями хоста, которые дописывают
текст в `String` в хранилище (`func_wrap("env", "print_int", |mut caller: Caller<'_, String>, v: i64| ...)`),
топливо и вызов `main`. Переводите ловушки в сообщения контракта через
`error.downcast_ref::<wasmtime::Trap>()`: `IntegerDivisionByZero`, `IntegerOverflow`, `StackOverflow`.

<details>
<summary>Подсказка</summary>

Сначала сгенерируйте тело функции (в `String`), собирая её локальные переменные, и только потом
запишите заголовок `(func ...)` со списком `(local ...)`. Чтобы знать тип выражения для `print`,
генератор кода может вычислять его по ходу: литералы, сравнения и логика дают bool, арифметика и вызовы
дают int, у переменных тип хранится в таблице областей видимости.

</details>

**Готово, когда:**

```bash
cargo run -- compile programs/fib.pb | head -12
cargo run -- wasm programs/fib.pb
```

```text
(module
  (import "env" "print_int" (func $print_int (param i64)))
  (import "env" "print_bool" (func $print_bool (param i64)))
  (func $f_fib (param $n i64) (result i64)
    local.get $n
    i64.const 2
    i64.lt_s
    i64.extend_i32_u
    i32.wrap_i64
    if
    local.get $n
    return
55
6765
```

(Ваши инструкции могут отличаться в деталях; вывод `wasm` — нет.) Коммит.

#### M5 — Добиться совпадения бэкендов и доказать его

**Цель:** оба бэкенда следуют семантике контракта, и это проверяет дифференциальный тест.

**Указания:** добавьте в `programs/` программы, которые проверяют каждое правило: циклы, рекурсию,
логику по короткой схеме, перенос по модулю (`9223372036854775807 + 1`), деление на ноль после
некоторого вывода, предел глубины. Затем напишите `tests/differential.rs`: для каждого файла в
`programs/`, который проходит проверку типов, запустите интерпретатор и скомпилированный модуль и
сравните их результаты через `assert_eq!`, включая вывод, напечатанный до ошибки, и сообщение об ошибке.

<details>
<summary>Подсказка</summary>

Дайте обоим бэкендам одинаковый тип результата, например `Result<String, (String, String)>` (вывод
или вывод до ошибки плюс сообщение). Тогда тест — это один
`assert_eq!(interpreted, compiled, "{}", path.display())`. Ловушка исчерпанного стека Wasm играет роль
«call stack too deep» в скомпилированном бэкенде.

</details>

**Готово, когда:** `cargo test --test differential` проходит, например

```text
test interpreter_and_compiler_agree_on_every_program ... ok
```

а `programs/zero.pb`

```text
fn ratio(a, b) {
    return a / b;
}
print ratio(10, 3);
print ratio(1, 0);
print 99;
```

печатает `3`, а затем `programs/zero.pb: runtime error: division by zero` — **и** через `run`, **и**
через `wasm`. Коммит.

### Дополнительные цели

- **Виртуальная машина байт-кода:** третий бэкенд, который компилирует дерево в плоский список
  инструкций для вашей собственной стековой машины и выполняет его в цикле; часть III *Crafting
  Interpreters* показывает идею. Добавьте его в дифференциальный тест.
- **Оператор `**`** из упражнения 2 Урока 22.22 во всех бэкендах (в WebAssembly нет инструкции степени:
  сгенерируйте цикл или вызовите вспомогательную функцию, которую вы вставляете в каждый модуль).
- **Лучшие ошибки:** показывайте строку исходного текста и `^` под позицией, как это делает компилятор
  Rust.
- **Сгенерированные программы:** с `proptest` генерируйте случайные выражения и проверяйте, что оба
  бэкенда совпадают (Урок 09.4). Так находятся ошибки, которые пропускают написанные вручную программы.
- **Двоичный вывод:** пишите `.wasm` вместо WAT с крейтом `wasm-encoder` и запускайте его инструментом
  командной строки `wasmtime`.

## Частые ошибки

**`return`, который покидает только самый внутренний блок.** Если `exec` возвращает `()`, у `return`
внутри `while` внутри `if` нет способа остановить цикл и функцию. Возвращайте значение `Flow` и
проверяйте его после каждой инструкции.

**Функции, которые видят переменные вызывающего кода.** Если положить параметры ещё одной областью
видимости на стек вызывающего кода, переменные вызывающего станут видны внутри функции (динамическая
область видимости). Контракт говорит, что их не видно; бэкенд WebAssembly тоже их не видит, поэтому
дифференциальный тест падает. Подставляйте новый стек для каждого вызова.

**Разная семантика, скрытая тестами, которые согласны сами с собой.** Тесты интерпретатора проверяют
интерпретатор; они не могут заметить, что `9223372036854775807 + 1` даёт ошибку в одном бэкенде и
перенос по модулю в другом. Только дифференциальный тест с программой на каждое правило контракта ловит
это.

**Локальные переменные с именем переменной Pebble.** Два `let x` в разных блоках одной функции оба
стали бы `$x`, и внутренний блок перезаписал бы внешнюю переменную. Давайте каждому `let` свою
локальную переменную.

## Вопросы для самопроверки

1. Почему `exec` возвращает значение `Flow`, как только в языке появляется `return`?

<details>
<summary>Ответ</summary>

`return` должен сразу остановить текущий блок, все охватывающие блоки и циклы и функцию. Возврат
`Flow::Return(value)` позволяет каждому уровню увидеть это и остановиться, пока значение не получит сам
вызов.

</details>

2. Что даёт статическая проверка типов такого, чего не дают проверки интерпретатора во время
   выполнения?

<details>
<summary>Ответ</summary>

Она находит ошибки типов во *всех* частях программы до запуска, включая ветки, до которых конкретный
запуск никогда не доходит. А ещё она позволяет генератору кода знать тип каждого выражения (для
`print`).

</details>

3. Почему локальные переменные WebAssembly получают уникальные имена вроде `$x_0` и `$x_1`?

<details>
<summary>Ответ</summary>

У функции WebAssembly один плоский список локальных переменных, а Pebble разрешает несколько
переменных с одним именем в разных областях видимости (затенение). Уникальные имена разделяют их.

</details>

4. Почему контракт выбрал арифметику с переносом по модулю, а не ошибку переполнения?

<details>
<summary>Ответ</summary>

Потому что `i64.add` в WebAssembly переносит значение по модулю, и скомпилированный бэкенд получает это
поведение бесплатно. Ошибка переполнения потребовала бы дополнительных проверок вокруг каждой операции
в сгенерированном коде. Это решение при проектировании; важно, чтобы оба бэкенда делали одно и то же.

</details>

5. Что ловит дифференциальный тест такого, что пропускают обычные модульные тесты?

<details>
<summary>Ответ</summary>

Расхождения между реализациями: случаи, когда каждый бэкенд проходит собственные тесты, но они
вычисляют разные результаты, например по-разному ведут себя при переполнении или ошибках.

</details>

## Итоги

- Функциям нужны кадры вызова (новый стек областей видимости на каждый вызов), способ для `return`
  покинуть вложенные инструкции (`Flow`) и предел глубины.
- Статическая проверка типов один раз обходит дерево, даёт каждому выражению тип и сообщает обо всех
  несовпадениях до запуска программы.
- Компиляция целых программ в WebAssembly — это локальные переменные с уникальными именами,
  `block`/`loop`/`br_if` для циклов, `if` для ветвлений и функции хоста для вывода.
- Запишите семантику; затем заставьте каждый бэкенд следовать ей и проверьте это дифференциальным
  тестом.

  Wasmtime или другой языковой проект.
