# Урок 13.2 — Процессы изнутри

> **Этап 13 — Операционные системы изнутри** · Урок 2 из 18 · ⏱ около 135 минут

## Что вы узнаете

- Чем программа отличается от процесса и что ядро помнит о каждом процессе.
- Как устроена память процесса (код, данные, куча, стек) и как увидеть её в `/proc/self/maps`.
- Состояния процесса R, S, D, T и Z и как увидеть, что процесс меняет состояние.
- Как процессы образуют дерево с PID 1 в корне.
- Как читать сведения о любом процессе из `/proc/<pid>/` на Rust с помощью `std` и крейта `nix`.

## Перед началом

- Вы прошли [Урок 13.1 — Что делает операционная система](01-what-an-operating-system-does.md), и пакет `code/p13-os` скопирован в вашу ВМ.
- С Этапа 11 вы знаете `ps`, `kill`, фоновые задачи с `&` и сигналы вроде `SIGSTOP` и `SIGCONT`.
- Из [Урока 12.12 — Компоновка и загрузка программ](../12-computer-systems/12-linking-and-loading.md) вы знаете, что программа — это ELF-файл с секциями вроде `.text` и `.data` и что загрузчик отображает их в память.

## Новые слова

| Слово | Значение |
|---|---|
| **процесс** (process) | Программа во время работы: её память, открытые файлы, регистры процессора и записи ядра о ней. |
| **дескриптор процесса** (process descriptor) | Запись, которую ядро хранит о каждом процессе. В Linux это структура на C под названием `task_struct`. |
| **PPID** (Parent Process IDentifier, идентификатор родительского процесса) | PID процесса, который создал данный. |
| **UID** (User IDentifier, идентификатор пользователя) | Номер пользователя, от имени которого работает процесс; 0 — это `root` (Урок 11.4). |
| **адресное пространство** (address space) | Все адреса памяти, которые может использовать процесс. У каждого процесса оно своё. |
| **область памяти** (memory region, mapping) | Непрерывный диапазон адресов с одинаковыми правами и одним источником, например «код программы» или «стек». |
| **стек** / **куча** (stack / heap) | Память для локальных переменных выполняющихся функций / память для значений, чей размер или время жизни определяется во время работы (`Box`, `Vec`), из Урока 03.1. |
| **ASLR** (Address Space Layout Randomization, рандомизация размещения адресного пространства) | Ядро размещает код, кучу и стек по случайным адресам при каждом запуске, чтобы атакующий не мог их угадать. |
| **RSS** (Resident Set Size, размер резидентного набора) | Сколько памяти процесса прямо сейчас действительно находится в RAM. В `/proc` это называется `VmRSS`. |
| **состояние процесса** (process state) | Что делает процесс: работает (R), спит (S), ждёт устройство (D), остановлен (T) или завершился, но не собран (Z). |
| **зомби** (zombie) | Процесс, который завершился, но чей родитель ещё не прочитал его код возврата. Урок 13.5 объясняет это. |
| **NUL-байт** (NUL byte) | Байт со значением 0. Linux использует его, чтобы разделять строки в некоторых файлах. |
| **CPU**, **RAM**, **ELF**, **КиБ**/**МиБ**/**ГиБ**/**ТиБ**, **UTF-8** | Известны из прошлых уроков: Central Processing Unit, центральный процессор; Random Access Memory, оперативная память; Executable and Linkable Format, формат файлов программ Linux (Урок 12.12); кибибайт, мебибайт, гибибайт, тебибайт (каждый в 1024 раза больше предыдущего); Unicode Transformation Format, 8-bit, кодировка текста (Урок 12.5). |

## 1. Программа — это файл, процесс — это работающая программа

**Программа** — это файл на диске, например `/usr/bin/sleep`, ELF-файл, полный инструкций (Урок 12.12). Сама по себе она
ничего не делает. **Процесс** — это то, что получается, когда ядро *запускает* программу: ядро загружает файл в память,
даёт ему стек, PID и место в очереди планировщика и запускает его первую инструкцию.

Представьте рецепт и саму готовку. Рецепт — это программа. Два повара, которые готовят по одному рецепту на двух кухнях, —
это два процесса: одни и те же инструкции, но разные кастрюли и разный ход работы. Так же вы можете запустить `sleep 100`
три раза и получить три процесса из одного файла.

Для каждого процесса ядро хранит **дескриптор процесса** (в Linux он называется `task_struct`). Его главные части:

```text
 task_struct (one per process, inside kernel memory)
 +---------------------------------------------------------------+
 | PID 4630, parent PID 4629, state S (sleeping)                 |
 | credentials: UID 501, GID 1000                                |
 | memory map: code, data, heap, stack, libraries   -> Section 2 |
 | open files: 0, 1, 2, 3 ...                       -> Lesson 13.4|
 | current directory, root directory                             |
 | signal handlers and blocked signals              -> Lesson 13.7|
 | saved CPU registers (while it is not running)    -> Lesson 13.9|
 | scheduling priority, CPU time used                            |
 +---------------------------------------------------------------+
```

GID (Group IDentifier, идентификатор группы) — номер основной группы пользователя (Урок 11.4). Почти каждый файл в
`/proc/<pid>/` показывает одну часть этой записи.

### Спросим у ядра, кто мы

Добавьте в пакет крейт `nix`. `nix` даёт безопасные функции Rust для системных вызовов Unix; его части включаются фичами
(features) Cargo (Урок 05.8):

```bash
cargo add nix@0.32 --features process,user
```

Теперь в `Cargo.toml` есть строка `nix = { version = "0.32", features = ["process", "user"] }`. Создайте
`src/bin/who-am-i.rs`:

```rust
use nix::unistd::{getpid, getppid, getuid};
use std::fs;

fn main() -> std::io::Result<()> {
    println!("PID  (std): {}", std::process::id());
    println!("PID  (nix): {}", getpid());
    println!("PPID:       {}", getppid());
    println!("UID:        {}", getuid());
    println!("directory:  {}", std::env::current_dir()?.display());

    // The kernel's own summary of this process.
    let status = fs::read_to_string("/proc/self/status")?;
    for line in status.lines() {
        let key = line.split(':').next().unwrap_or("");
        if ["Name", "State", "PPid", "Threads", "VmRSS"].contains(&key) {
            println!("  {line}");
        }
    }
    Ok(())
}
```

```text
PID  (std): 154
PID  (nix): 154
PPID:       1
UID:        0
directory:  /work
  Name:	who-am-i
  State:	R (running)
  PPid:	1
  VmRSS:	    1744 kB
  Threads:	1
```

**Что происходит:**

1. `std::process::id()` и `nix::unistd::getpid()` задают ядру один и тот же вопрос. `std` возвращает `u32`; `nix` —
   тип `Pid`, который нельзя случайно перепутать с другими числами.
2. `getppid()` возвращает родителя. В проверочном контейнере родитель — PID 1, первый процесс контейнера. В вашей ВМ
   это PID вашего `bash`.
3. `getuid()` здесь равен 0, потому что контейнер работает от root. В ВМ вы увидите свой UID, например 501.
4. `/proc/self/status` — текстовая сводка ядра по дескриптору процесса. `State: R (running)` верно в момент чтения:
   программа, конечно, работает.
5. Строки идут не в порядке нашего списка: цикл печатает их в том порядке, в котором их пишет ядро.

> 📏 **Соглашение:** предпочитайте `std`, если там есть нужная функция (`std::process::id`, `std::env::current_dir`).
> Используйте `nix` для вызовов Unix, которых в `std` нет. Оба обращаются к одному и тому же ядру.

## 2. Память процесса

Каждый процесс получает своё **адресное пространство**: огромный диапазон адресов (в Linux на arm64 — 2⁴⁸ байт = 256 ТиБ),
из которого реально используются лишь небольшие куски. Каждый используемый кусок — это **область памяти** со своими правами.
Типичное размещение, младшие адреса внизу:

```text
 high addresses  0xffff_ffff_ffff
 +----------------------------------+
 | stack  (grows down)              |  local variables, function calls
 |   ...                            |
 | shared libraries (libc ...)      |  mapped files
 |   ...                            |
 | heap   (grows up)                |  Box, Vec, String
 | .data / .bss   rw-               |  writable statics
 | read-only data r--               |  constants
 | .text code     r-x               |  your compiled functions
 +----------------------------------+
 low addresses   0x0000_0000_0000
```

`r`, `w`, `x` означают «чтение», «запись», «выполнение». Код никогда не доступен для записи, данные никогда не выполняются:
простая защита от многих атак. Найдём настоящие адреса. Создайте `src/bin/memory-map.rs`:

```rust
use std::fs;
use std::sync::atomic::AtomicU64;

static GREETING: &str = "hello";
static COUNTER: AtomicU64 = AtomicU64::new(1);

fn main() -> std::io::Result<()> {
    let on_stack = 42_u64;
    let on_heap = Box::new(7_u64);

    println!("code   (fn main)   {:p}", main as *const ());
    println!("rodata (\"hello\")   {:p}", GREETING.as_ptr());
    println!("data   (COUNTER)   {:p}", &COUNTER);
    println!("heap   (Box)       {:p}", &*on_heap);
    println!("stack  (local)     {:p}", &on_stack);
    println!();

    // The kernel's list of memory regions of this process: one line per region.
    let maps = fs::read_to_string("/proc/self/maps")?;
    for line in maps.lines() {
        if line.contains("memory-map") || line.contains("[heap]") || line.contains("[stack]") {
            println!("{line}");
        }
    }
    Ok(())
}
```

```text
code   (fn main)   0xaaaae09598a0
rodata ("hello")   0xaaaae0994f37
data   (COUNTER)   0xaaaae09c0008
heap   (Box)       0xaaaaf5c06d60
stack  (local)     0xffffd68a6ee0

aaaae0950000-aaaae09a5000 r-xp 00000000 00:34 319762                     /work/target/debug/memory-map
aaaae09bd000-aaaae09c0000 r--p 0005d000 00:34 319762                     /work/target/debug/memory-map
aaaae09c0000-aaaae09c1000 rw-p 00060000 00:34 319762                     /work/target/debug/memory-map
aaaaf5c06000-aaaaf5c27000 rw-p 00000000 00:00 0                          [heap]
ffffd6887000-ffffd68a8000 rw-p 00000000 00:00 0                          [stack]
```

**Что происходит:**

1. `{:p}` печатает адрес. `main as *const ()` — адрес первой инструкции функции. `AtomicU64` (атомарные типы: Урок 05.10) — это static,
   который может меняться, поэтому он живёт в памяти для записи и не требует `unsafe`.
2. Каждая строка `/proc/self/maps` — одна область: `начало-конец`, права (`p` = private, личная для этого процесса),
   смещение в файле, устройство и inode (Урок 13.4) файла и его путь.
3. `main` (…598a0) находится внутри первой области, `r-xp`: код нашей программы, только чтение и выполнение. Строка
   `"hello"` здесь в той же области: компоновщик положил константы только для чтения рядом с кодом.
4. Область `r--p` содержит данные, которые загрузчик поправил при старте, а потом сделал доступными только для чтения.
5. `COUNTER` (…c0008) лежит внутри области `rw-p` файла: записываемые static.
6. `Box` находится внутри `[heap]`, а `on_stack` — внутри `[stack]`, по гораздо большему адресу.

Запустите ещё раз — адреса изменятся:

```text
code   (fn main)   0xaaaacb3598a0
rodata ("hello")   0xaaaacb394f37
data   (COUNTER)   0xaaaacb3c0008
heap   (Box)       0xaaaad1d9dd60
stack  (local)     0xffffd71d1db0
```

Последние три шестнадцатеричные цифры адреса кода остаются прежними (`8a0`), а остальное сдвигается. Это **ASLR**: ядро
выбирает случайное начало для каждой области при каждом запуске.

> 🔒 **Безопасность:** многим атакам нужно знать, где в памяти находится функция или буфер. ASLR делает эти адреса разными
> при каждом запуске, поэтому атака, сработавшая в одном запуске, проваливается в следующем. Никогда не отключайте его на
> настоящих машинах.

### Настоящая память: RSS

Адресное пространство — в основном пустые обещания. Память становится настоящей RAM только тогда, когда программа в неё
**пишет** (почему — объясняет Урок 13.10). `VmRSS` в `/proc/self/status` показывает настоящую часть. В упражнении 1 вы
увидите, как она растёт.

## 3. Состояния процесса

Процесс работает не всё время. На машине с 12 ядрами одновременно работают не больше 12 процессов; сотни остальных ждут.
`/proc/<pid>/status` и `ps` показывают **состояние** одной буквой:

| Буква | Название | Значение |
|---|---|---|
| `R` | работает или готов | сейчас на процессоре или готов и ждёт своей очереди |
| `S` | спит | ждёт чего-то: таймера, нажатия клавиши, данных из сети |
| `D` | непрерываемый сон | ждёт устройство (часто диск); даже сигналам приходится ждать |
| `T` | остановлен | приостановлен `SIGSTOP` или Ctrl-Z до `SIGCONT` |
| `Z` | зомби | завершился; родитель ещё не забрал код возврата (Урок 13.5) |

Посмотрите в ВМ, как процесс меняет состояние:

```bash
sleep 100 &
ps -o pid,ppid,stat,comm
kill -STOP $!
grep State /proc/$!/status
kill -CONT $!
grep State /proc/$!/status
kill $!
```

Настоящий вывод из проверочного контейнера (в вашей ВМ родитель — ваш `bash`, а не PID 1):

```text
    PID    PPID STAT COMMAND
      1       0 Ss   bash
      7       1 S    sleep
      9       1 R    ps
State:	T (stopped)
State:	S (sleeping)
```

**Что происходит:**

1. `sleep 100 &` запускает дочерний процесс в фоне; `$!` — его PID (Урок 11.5).
2. `ps` показывает `sleep` в состоянии `S`: он спит, пока не кончится его таймер. Сам `ps` в состоянии `R`, потому что
   работает, пока печатает. `s` после `S` у `bash` отмечает *лидера сеанса* (session leader, Урок 13.7).
3. `kill -STOP` посылает `SIGSTOP`; ядро убирает процесс из очереди процессора: состояние `T`.
4. `kill -CONT` позволяет ему продолжить, и он снова спит: `S`.

> ⚡ **Производительность:** программа, которая ждёт диск или сеть, находится в состоянии `S` или `D` и **не** тратит
> процессорное время. Высокая загрузка процессора означает много процессов в состоянии `R`. Именно их считает четвёртое
> поле `/proc/loadavg` из Урока 13.1.

## 4. Дерево процессов

Каждый процесс, кроме самого первого, создан другим процессом — своим **родителем**. Поэтому процессы образуют дерево.
В корне — **PID 1**, первая программа пространства пользователя, которую ядро запускает при загрузке. В вашей ВМ это
`systemd` (Урок 11.6); в контейнере — та команда, которую запускает контейнер.

```text
systemd (1)
 ├── sshd (912)
 │    └── sshd-session (4629)
 │         └── bash (4630)
 │              ├── sleep (4700)
 │              └── ps (4701)
 └── cron (870)
```

Своё дерево можно нарисовать командой `ps -ef --forest` или `pstree -p`. Когда родитель умирает раньше ребёнка, ребёнок не
остаётся один: ядро даёт ему нового родителя, обычно PID 1. Такого *сироту* (orphan) вы создадите в Уроке 13.5.

Rust получает родителя через `getppid()`, а `/proc/<pid>/status` даёт `PPid` любого процесса. Упражнение 3 использует это,
чтобы подняться от вашей программы до PID 1.

## 5. Смотрим на любой процесс через `/proc/<pid>/`

В папке каждого процесса много файлов. Самые полезные:

| Файл | Содержимое |
|---|---|
| `status` | понятная человеку сводка, которую вы видели выше |
| `cmdline` | аргументы, с которыми запущен процесс, разделённые NUL-байтами |
| `environ` | его переменные окружения, разделённые NUL-байтами |
| `cwd` | символическая ссылка на его текущую папку |
| `exe` | символическая ссылка на файл его программы |
| `maps` | его области памяти |
| `fd/` | его открытые файлы (Урок 13.4) |

```bash
ls -l /proc/self/exe /proc/self/cwd
```

```text
lrwxrwxrwx 1 root root 0 Nov 18 07:02 /proc/self/cwd -> /work
lrwxrwxrwx 1 root root 0 Nov 18 07:02 /proc/self/exe -> /usr/bin/ls
```

`self` здесь — это `ls`, потому что именно `ls` читает папку.

В `cmdline` между аргументами стоят NUL-байты, а не пробелы. Так ядро отличает `echo "a b"` (два аргумента: `echo` и
`a b`) от `echo a b` (три аргумента). Упражнение 2 разбирает этот файл.

> 🔒 **Безопасность:** `status` и `cmdline` процессов других пользователей читать можно, а их `environ`, `maps` и `fd/` —
> нет: обычный пользователь на `cat /proc/1/environ` получит `cat: /proc/1/environ: Permission denied`. Переменные
> окружения часто содержат секреты, поэтому никогда не передавайте пароль в командной строке: `cmdline` может прочитать
> любой пользователь машины.

## Частые ошибки

> ⚠️ **Частая ошибка:** включить слишком мало фич `nix`. Если вызвать `getuid` только с фичей `process`, компилятор скажет:
>
> ```text
> error[E0432]: unresolved import `nix::unistd::getuid`
>  --> src/main.rs:1:5
>   |                  no `getuid` in `unistd`
> note: found an item that was configured out
>   |    ---------------- the item is gated behind the `user` feature
> ```
>
> «Configured out» означает, что функция в `nix` есть, но не была скомпилирована. Добавьте фичу командой
> `cargo add nix@0.32 --features user`.

> ⚠️ **Частая ошибка:** считать адрес, напечатанный через `{:p}`, постоянным. С ASLR он разный при каждом запуске, поэтому
> никогда не сохраняйте адреса в файлы и не сравнивайте их между запусками.

> ⚠️ **Частая ошибка:** делить `cmdline` по пробелам. Аргумент может содержать пробелы; делите по NUL-байту.

3. Нажмите Ctrl-Z, пока `sleep 300` работает на переднем плане. Проверьте его состояние через `ps -o pid,stat,comm`,
   затем продолжите его командой `fg` и остановите через Ctrl-C.
4. Выполните в ВМ `pstree -p $$`. `$$` — это PID вашей командной оболочки.

## Упражнения

### Упражнение 1 — Смотрим, как растёт RSS (легко)

Напишите `src/bin/rss.rs` с функцией `vm_rss_kib() -> u64`, которая читает `VmRSS` из `/proc/self/status`. Напечатайте
значение четыре раза: в начале, после `Vec::with_capacity(100 * 1024 * 1024)` (100 МиБ типа `u8`), после заполнения
вектора через `resize(100 * 1024 * 1024, 1_u8)` и после `drop`. Объясните числа.

<details>
<summary>Подсказка</summary>

`status.lines().find_map(|line| line.strip_prefix("VmRSS:"))` даёт остаток строки, например `"    1680 kB"`. Возьмите
первое слово и разберите его.

</details>

<details>
<summary>Ответ</summary>

```rust
use std::fs;

fn vm_rss_kib() -> u64 {
    let status = fs::read_to_string("/proc/self/status").unwrap_or_default();
    status
        .lines()
        .find_map(|line| line.strip_prefix("VmRSS:"))
        .and_then(|rest| rest.split_whitespace().next())
        .and_then(|n| n.parse().ok())
        .unwrap_or(0)
}

fn main() {
    println!("before:          {} KiB", vm_rss_kib());
    let mut big = Vec::with_capacity(100 * 1024 * 1024);
    println!("after reserving: {} KiB", vm_rss_kib());
    big.resize(100 * 1024 * 1024, 1_u8);
    println!("after writing:   {} KiB", vm_rss_kib());
    drop(big);
    println!("after drop:      {} KiB", vm_rss_kib());
}
```

```text
before:          1680 KiB
after reserving: 1688 KiB
after writing:   104088 KiB
after drop:      1684 KiB
```

Почему это работает: резервирование 100 МиБ только создаёт область памяти; RAM не используется, пока программа не пишет.
Запись каждого байта заставляет ядро выдавать настоящую память страница за страницей, поэтому RSS растёт примерно на
100 МиБ. После `drop` аллокатор сразу возвращает такой большой блок ядру, и RSS снова падает.

</details>

### Упражнение 2 — Разбор `cmdline` с тестами (средне)

Напишите `src/bin/cmdline.rs` с функцией `fn split_cmdline(raw: &[u8]) -> Vec<String>`. `main` принимает необязательный
аргумент PID (по умолчанию `self`), читает `/proc/<pid>/cmdline` через `fs::read` (байты, не текст) и печатает каждый
аргумент. Напишите три теста: `b"sleep\x00100\x00"` даёт `["sleep", "100"]`, `b"echo\x00a b\x00"` даёт
`["echo", "a b"]`, а пустой вход не даёт аргументов.

<details>
<summary>Подсказка</summary>

У срезов есть `split(|&b| b == 0)`. Данные заканчиваются NUL-байтом, из-за чего в конце получается один пустой кусок;
отфильтруйте пустые куски. `String::from_utf8_lossy` превращает байты в текст, даже если это не корректный UTF-8.

</details>

<details>
<summary>Ответ</summary>

```rust
use std::fs;

/// /proc/<pid>/cmdline holds the arguments separated (and ended) by zero bytes.
fn split_cmdline(raw: &[u8]) -> Vec<String> {
    raw.split(|&b| b == 0)
        .filter(|part| !part.is_empty())
        .map(|part| String::from_utf8_lossy(part).into_owned())
        .collect()
}

fn main() -> std::io::Result<()> {
    let pid = std::env::args()
        .nth(1)
        .unwrap_or_else(|| "self".to_string());
    let raw = fs::read(format!("/proc/{pid}/cmdline"))?;
    for (i, arg) in split_cmdline(&raw).iter().enumerate() {
        println!("argv[{i}] = {arg:?}");
    }
    Ok(())
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn splits_on_zero_bytes() {
        assert_eq!(split_cmdline(b"sleep\x00100\x00"), vec!["sleep", "100"]);
    }

    #[test]
    fn keeps_spaces_inside_one_argument() {
        assert_eq!(split_cmdline(b"echo\x00a b\x00"), vec!["echo", "a b"]);
    }

    #[test]
    fn empty_cmdline_gives_no_arguments() {
        assert!(split_cmdline(b"").is_empty());
    }
}
```

```bash
cargo build -q
sleep 100 &
./target/debug/cmdline $!
```

```text
argv[0] = "sleep"
argv[1] = "100"
```

Почему это работает: ядро хранит строки аргументов ровно такими, какими их получила программа, и каждая заканчивается
NUL-байтом. Деление по этому байту возвращает исходные аргументы. (Фильтр отбрасывает и пустые аргументы вроде `""`;
идеальная версия отбрасывала бы только самый последний кусок.)

</details>

### Упражнение 3 — Поднимаемся до PID 1 (сложно)

Напишите `src/bin/ancestors.rs`, который начинает со своего PID и печатает `PID  имя` для себя, своего родителя, родителя
родителя и так далее, пока не дойдёт до PID 1 (его `PPid` равен 0). Напишите вспомогательную функцию
`fn name_and_parent(pid: u32) -> Option<(String, u32)>`.

<details>
<summary>Подсказка</summary>

Прочитайте `/proc/<pid>/status`, возьмите строки, которые начинаются с `Name:` и `PPid:`. Цикл — `while pid != 0`.
Используйте `let Some(...) = ... else { break };`, чтобы исчезнувший процесс завершал цикл, а не вызывал панику.

</details>

<details>
<summary>Ответ</summary>

```rust
use std::fs;

/// Returns (name, parent PID) of a process, read from /proc/<pid>/status.
fn name_and_parent(pid: u32) -> Option<(String, u32)> {
    let status = fs::read_to_string(format!("/proc/{pid}/status")).ok()?;
    let mut name = String::new();
    let mut ppid = None;
    for line in status.lines() {
        if let Some(v) = line.strip_prefix("Name:") {
            name = v.trim().to_string();
        } else if let Some(v) = line.strip_prefix("PPid:") {
            ppid = v.trim().parse().ok();
        }
    }
    Some((name, ppid?))
}

fn main() {
    let mut pid = std::process::id();
    while pid != 0 {
        let Some((name, parent)) = name_and_parent(pid) else {
            break;
        };
        println!("{pid:>6}  {name}");
        pid = parent;
    }
}
```

В проверочном контейнере цепочка короткая:

```text
   545  ancestors
     1  bash
```

Пример вывода в ВМ (у вас будет похожий):

```text
  5012  ancestors
  4630  bash
  4629  sshd-session
  4580  sshd-session
   912  sshd
     1  systemd
```

Почему это работает: каждый дескриптор процесса хранит PID родителя, а у PID 1 родитель равен 0, что означает «нет
родителя». `cargo run` заменяет себя вашей программой, поэтому `cargo` в цепочке не появляется.

</details>

## Вопросы для самопроверки

1. Чем программа отличается от процесса?

<details>
<summary>Ответ</summary>

Программа — это файл с инструкциями. Процесс — это работающий экземпляр программы со своей памятью, открытыми файлами,
PID и состоянием. Одна программа может одновременно работать как много процессов.

</details>

2. В `/proc/self/maps` у одной области права `r-xp`, а у другой `rw-p`. Что живёт в каждой?

<details>
<summary>Ответ</summary>

`r-xp` (чтение, выполнение, личная) — это код: его можно выполнять, но нельзя менять. `rw-p` (чтение, запись, личная) — это
изменяемые данные, например static, куча или стек: их можно менять, но нельзя выполнять.

</details>

3. Почему адрес `main` меняется между двумя запусками?

<details>
<summary>Ответ</summary>

Из-за ASLR: ядро загружает программу и её области по случайному базовому адресу при каждом запуске, чтобы атаки, которым
нужны фиксированные адреса, не срабатывали.

</details>

4. Программа ждёт нажатия клавиши. В каком она состоянии и тратит ли процессорное время?

<details>
<summary>Ответ</summary>

В состоянии `S` (спит). Процессорное время она не тратит; ядро разбудит её, когда придёт нажатие клавиши.

</details>

5. Ваша программа зарезервировала 1 ГиБ через `Vec::with_capacity`, но `VmRSS` вырос совсем немного. Почему?

<details>
<summary>Ответ</summary>

Резервирование создаёт область памяти, но настоящую RAM ядро выдаёт только при первой записи в страницу. RSS считает
только ту память, которая действительно находится в RAM.

</details>

6. Почему опасно передавать пароль как аргумент командной строки?

<details>
<summary>Ответ</summary>

`/proc/<pid>/cmdline` может прочитать любой пользователь машины, а утилиты вроде `ps` его показывают. Секретам место в файлах
со строгими правами или в переменных окружения, которые другие пользователи прочитать не могут.

</details>

## Итоги

- Процесс — это работающая программа; ядро хранит дескриптор процесса (`task_struct`) с его PID, родителем, состоянием, картой памяти, открытыми файлами и многим другим.
- У каждого процесса своё адресное пространство с областями для кода (`r-x`), констант (`r--`), данных и кучи (`rw-`) и стека; `/proc/<pid>/maps` перечисляет их.
- ASLR размещает области по случайным адресам при каждом запуске.
- RSS — часть памяти, которая действительно находится в RAM; память становится настоящей только при записи.
- Состояния: R (работает или готов), S (спит), D (ждёт устройство), T (остановлен), Z (зомби).
- Процессы образуют дерево с PID 1 в корне; сирот усыновляет PID 1.
- `nix::unistd` даёт безопасные обёртки вроде `getpid`, `getppid` и `getuid`; нужные части включаются фичами Cargo.
