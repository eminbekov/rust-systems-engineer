## Новые слова

| Слово | Значение |
|---|---|
| **брокер** (broker) | Сервер, который получает сообщения от производителей, хранит их и отдаёт потребителям. |
| **производитель** (producer) / **потребитель** (consumer) | Программа, которая отправляет сообщения брокеру / которая читает их из него. |
| **топик** (topic) | Именованный поток сообщений, например `orders`. |
| **партиция** (partition) | Один упорядоченный журнал только для добавления внутри топика. У топика с 3 партициями 3 независимых журнала; порядок сохраняется только *внутри* партиции. |
| **смещение** (offset) | Позиция записи в её партиции: 0, 1, 2, … Оно никогда не меняется и никогда не используется повторно. |
| **смещение конца журнала** (log end offset) | Смещение, которое получит следующая добавленная запись. |
| **сегмент** (segment) | Один файл журнала партиции. Когда сегмент заполнен, начинается новый; старые сегменты удаляются целиком. |
| **разреженный индекс** (sparse index) | Индексный файл с записью только для каждой *n*-й записи (смещение → позиция в байтах), чтобы чтение могло перепрыгнуть близко к нужному месту и досканировать остальное. |
| **хранение** (retention) | Правило, сколько времени хранить записи: по возрасту или по общему размеру. |
| **группа потребителей** (consumer group) | Набор потребителей, которые делят партиции топика: каждую партицию читает ровно один член группы. |
| **закоммиченное смещение** (committed offset) | Смещение, которое группа потребителей сохранила как «обработано до этого места». После перезапуска чтение продолжается с него. |
| **перебалансировка** (rebalance) | Повторная раздача партиций членам группы после того, как член присоединился или ушёл. |
| **отставание потребителя** (consumer lag) | Насколько группа отстаёт: смещение конца журнала минус закоммиченное смещение. |
| **длинный опрос** (long polling) | Чтение, которое ждёт на брокере, пока не придут данные или не истечёт лимит времени, вместо того чтобы сразу вернуть пустой ответ. |
| **acks** | Выбор производителя, как долго ждать: `0` (не ждать), `1` (лидер записал), `all` (запись есть у каждой синхронной реплики). |
| **ISR** (In-Sync Replicas, синхронные реплики) | Реплики партиции, которые не отстают от лидера дольше лимита времени. |
| **верхняя отметка** (high watermark) | Первое смещение, которого ещё нет хотя бы у одной синхронной реплики: каждая запись ниже него есть на всех синхронных репликах. Потребители могут читать только ниже неё. |
| **идемпотентный производитель** (idempotent producer) | Производитель, повторённые пакеты которого брокер распознаёт (идентификатор производителя и порядковый номер) и сохраняет только один раз. |
| **CRC-32C** (Cyclic Redundancy Check, 32 bits, Castagnoli, циклический избыточный код) | 32-битная контрольная сумма; другое значение после чтения значит, что байты повреждены (Урок 17.3). |
| **CI** (Continuous Integration, непрерывная интеграция) | Сервер, который автоматически запускает ваши проверки при каждой отправке (Урок 09.12). |

## 1. Что вы строите и почему это важно

Вы строите `brokerd` — маленький брокер на основе журнала в духе Kafka: производители добавляют записи в **топики**, каждый топик разделён на **партиции**, каждая партиция — **журнал** только для добавления на диске, а потребители читают с любого смещения, как быстро или медленно им угодно. Записи не удаляются при чтении; их удаляет **хранение** (retention). Группы потребителей делят партиции и запоминают свой прогресс как **закоммиченные смещения**. В поздних вехах каждая партиция **реплицируется** на другие брокеры.

Журнал только для добавления — одна из самых важных идей в системах. Вы встречали его как журнал упреждающей записи базы данных (Урок 17.4) и как журнал Raft (Урок 18.11). Брокер делает продуктом сам журнал: многие сервисы пишут в него события, а многие другие читают их независимо, каждый в своём темпе. Так многие организации соединяют свои сервисы, строят конвейеры данных и заново проигрывают историю после ошибки.

Почему это важно для вас: брокер объединяет хранение (файлы сегментов, индексы, `fsync`, восстановление после сбоя), сети (двоичный протокол, пакеты, длинный опрос) и распределённые системы (репликация, верхняя отметка, переключение при отказе, идемпотентные производители). «Как Kafka гарантирует порядок и надёжность?» — частый вопрос на собеседованиях; после этого итогового проекта вы ответите на него по своему коду.

## 2. Эталонная архитектура

```text
 producers                                         consumers (group "billing")
 bk produce orders --key k                         member A: partitions 0, 1
    |  Produce(topic, partition, batch, acks)      member B: partition 2
    v                                                  ^  Fetch(topic, part, offset,
 +-----------------------------------------------+     |        max_wait_ms, min_bytes)
 | brokerd 1                                     |-----+
 |  +--------------+   +-----------------------+ |     |  CommitOffset(group, part, off)
 |  | protocol     |-->| partition orders/0    | |<----+
 |  | (frames)     |   |  segments:            | |
 |  +--------------+   |  00000000.log  .index | |   group coordinator:
 |                     |  00004096.log  .index | |   members, assignment,
 |                     |  log end offset: 5120 | |   offsets in __offsets
 |                     |  high watermark: 5118 | |
 |                     +-----------^-----------+ |
 +---------------------------------|-------------+
                                   | followers fetch from the leader
                     +-------------+-------------+
                     | brokerd 2, brokerd 3      |
                     | (replicas of orders/0)    |
                     +---------------------------+
```

Части и их задачи:

1. **Слой протокола** читает кадры с префиксом длины, декодирует запросы и пишет ответы с тем же идентификатором корреляции.
2. **Каждая партиция** — каталог файлов сегментов. У сегмента есть файл `.log` с пакетами записей и файл `.index` с разреженным индексом от смещения к позиции в байтах. Имя сегмента — его первое смещение.
3. **Координатор групп** хранит членов каждой группы потребителей, назначает им партиции и хранит закоммиченные смещения — сам во внутреннем топике `__offsets`.
4. **Репликация** (M5): у каждой партиции есть брокер-лидер и ведомые; ведомые читают у лидера, как потребители; лидер сдвигает верхнюю отметку, когда запись есть у всех синхронных реплик.

> 📏 **Соглашение:** держите хранение одной партиции (`PartitionLog`) библиотекой без сетевого кода. Тогда тест на основе модели (M1), тесты на сбои и бенчмарки работают с ней напрямую, а брокер — только тонкий слой, который превращает кадры в вызовы.

## Проект

### Что вы создадите

Рабочее пространство Cargo `code/p23-broker`:

| Крейт | Вид | Задача |
|---|---|---|
| `broker-log` | библиотека | одна партиция: сегменты, разреженный индекс, восстановление, хранение; плюс эталонная модель |
| `broker-proto` | библиотека | кодирование и декодирование кадров и сообщений (без ввода-вывода, I/O, input/output) |

| `bk` | бинарник | инструмент командной строки: создавать топики, производить, потреблять, описывать группы |
| `broker-tests` | только тесты | сквозные тесты, тесты на сбои и тесты симуляцией |

**Не-цели:** никаких транзакций между партициями, никакой компакции журнала по ключу (дополнительная цель), никакой аутентификации, никакой совместимости с настоящим протоколом Kafka (ваш протокол — ваш собственный и описан в `docs/protocol.md`).

### Контракт

**Командные строки:**

```text
brokerd --id <N> --listen <ADDR> --data <DIR> [--peers <ID=ADDR,...>]
        [--segment-bytes 1048576] [--flush every-batch|interval-ms=<N>]

bk [--broker ADDR] topic create <TOPIC> --partitions <N> [--replicas <R>] [--retention-bytes <B>] [--retention-ms <MS>]
bk [--broker ADDR] produce <TOPIC> [--key <KEY>] [--acks 0|1|all] <VALUE>    ->  orders/1@42
bk [--broker ADDR] consume <TOPIC> --group <GROUP> [--from-beginning]       ->  orders/1@42 key=k value
bk [--broker ADDR] groups describe <GROUP>                                  ->  one line per partition with lag
```

`orders/1@42` значит «топик `orders`, партиция 1, смещение 42». `consume` печатает по строке на запись и работает, пока не нажат `Ctrl+C`.

**Сетевой протокол.** Каждый запрос и ответ — кадр. Все целые числа — в порядке байтов big-endian:

| Поле | Размер | Значение |
|---|---|---|
| length | 4 байта, `u32` | число байтов **после** этого поля |
| api key | 2 байта, `u16` | 1 Produce, 2 Fetch, 3 ListOffsets, 4 CommitOffset, 5 FetchOffset, 6 Metadata, 7 JoinGroup, 8 Heartbeat, 9 LeaveGroup |
| api version | 2 байта, `u16` | начинается с 0; позволяет позже изменить сообщение, не ломая старых клиентов |
| correlation ID | 4 байта, `u32` | выбирается клиентом; ответ несёт то же значение |
| body | length − 8 байтов | само сообщение, описанное в `docs/protocol.md` |

Тестовый вектор (он пойдёт в тест в Упражнении 3): кадр Produce, версия 0, идентификатор корреляции 7, тело `hi` — это ровно `00 00 00 0a 00 01 00 00 00 00 00 07 68 69`.

Записи передаются и хранятся **пакетами** (batches): заголовок пакета (базовое смещение, число записей, контрольная сумма CRC-32C пакета, идентификатор производителя, базовый порядковый номер), затем записи (длина ключа, ключ, длина значения, значение). Брокер пишет пакет на диск в том виде, в каком получил, не перекодируя каждую запись.

**Правила:**

1. **Смещения:** в каждой партиции они начинаются с 0, растут ровно на 1 на запись и никогда не используются повторно, в том числе после удаления по хранению.
2. **Партиционирование:** запись с ключом идёт в `hash(key) % partitions` (назовите свою хеш-функцию в проектном документе и не меняйте её никогда); записи без ключа производитель распределяет по кругу.
3. **Порядок:** записи одной партиции читаются в порядке смещений. Между партициями порядка нет.
4. **Надёжность:** с `--flush every-batch` пакет проходит `fsync` до ответа на `acks=1`; с `interval-ms=N` при отключении питания может потеряться не больше N мс подтверждённых данных — README должен это сказать. `acks=all` (M5) отвечает, только когда пакет есть у каждой синхронной реплики.
5. **Чтение (Fetch):** возвращает записи с запрошенного смещения; на смещении конца журнала ждёт до `max_wait_ms`, пока не наберётся хотя бы `min_bytes` (длинный опрос); смещение ниже начала журнала или выше его конца — ошибка `OffsetOutOfRange` с обеими границами.
6. **Видимость** (M5): потребители видят только записи ниже верхней отметки.
7. **Доставка:** хотя бы один раз (at-least-once). Потребитель коммитит смещение **после** того, как обработал записи до него; после сбоя он продолжает с закоммиченного смещения и может увидеть часть записей снова.
8. **Хранение:** по общему размеру и по возрасту для каждого топика; удаляются только целые закрытые сегменты.
9. **Восстановление:** после сбоя последний сегмент проверяется пакет за пакетом; оборванный или испорченный пакет в конце отрезается; всё до него сохраняется.

**Эталонная модель.** До того как писать файлы сегментов, напишите модель одной партиции, с которой будут сравниваться все последующие тесты. Попробуйте её в учебном пакете `code/p23-broker-model`:

```rust
/// One record as the broker stores it.
#[derive(Clone, Debug, PartialEq)]
pub struct Record {
    pub offset: u64,
    pub value: Vec<u8>,
}

#[derive(Debug, PartialEq)]
pub enum FetchError {
    /// The offset is before the oldest kept record or after the end.
    OffsetOutOfRange { log_start: u64, log_end: u64 },
}

/// The reference model of one partition: in memory, slow, obviously correct.
#[derive(Default)]
pub struct ModelLog {
    log_start: u64,
    records: Vec<Record>,
}

impl ModelLog {
    /// Appends a record and returns its offset.
    pub fn append(&mut self, value: &[u8]) -> u64 {
        let offset = self.log_end();
        self.records.push(Record {
            offset,
            value: value.to_vec(),
        });
        offset
    }

    /// The offset that the next appended record will get.
    pub fn log_end(&self) -> u64 {
        self.log_start + self.records.len() as u64
    }

    /// Up to `max` records, starting at offset `from`.
    pub fn fetch(&self, from: u64, max: usize) -> Result<Vec<Record>, FetchError> {
        if from < self.log_start || from > self.log_end() {
            return Err(FetchError::OffsetOutOfRange {
                log_start: self.log_start,
                log_end: self.log_end(),
            });
        }
        let skip = (from - self.log_start) as usize;
        Ok(self.records.iter().skip(skip).take(max).cloned().collect())
    }

    /// Retention: forget every record with an offset below `offset`.
    pub fn delete_before(&mut self, offset: u64) {
        let offset = offset.min(self.log_end());
        if offset > self.log_start {
            let n = (offset - self.log_start) as usize;
            self.records.drain(..n);
            self.log_start = offset;
        }
    }
}

fn main() {
    let mut log = ModelLog::default();
    for value in ["a", "b", "c"] {
        let offset = log.append(value.as_bytes());
        println!("appended {value:?} at offset {offset}");
    }
    let from_one: Vec<u64> = log.fetch(1, 10).unwrap().iter().map(|r| r.offset).collect();
    println!("fetch(1, 10) -> offsets {from_one:?}");
    log.delete_before(2);
    println!("after retention: fetch(0, 10) -> {:?}", log.fetch(0, 10));
    println!("next append gets offset {}", log.append(b"d"));
    println!("fetch(4, 10) -> {:?}", log.fetch(4, 10));
}
```

**Что происходит:**

1. `log_start` — смещение самой старой сохранённой записи; `log_end()` — смещение, которое получит следующая запись. Всё, что брокер обещает о смещениях (правила 1 и 5), выражается этими двумя числами.
2. `append` даёт новой записи смещение `log_end()` и возвращает его, поэтому смещения идут подряд.
3. `fetch` принимает любое смещение от `log_start` до `log_end()` **включительно**. Чтение ровно на конце — не ошибка: оно значит «я всё прочитал», и в настоящем брокере именно здесь ждёт длинный опрос.
4. `delete_before` — это хранение. Оно сдвигает `log_start` вперёд, но никогда за конец, и никогда не меняет `log_end()`, поэтому смещения не используются повторно.

```bash
cargo run
```

```text
appended "a" at offset 0
appended "b" at offset 1
appended "c" at offset 2
fetch(1, 10) -> offsets [1, 2]
after retention: fetch(0, 10) -> Err(OffsetOutOfRange { log_start: 2, log_end: 3 })
next append gets offset 3
fetch(4, 10) -> Ok([])
```

Модель не знает о файлах, пакетах и времени. В этом и смысл: она настолько проста, что очевидно верна, и в M1 тест на основе свойств выполняет тысячи случайных операций над вашим настоящим `PartitionLog` и над `ModelLog` и проверяет, что они всегда согласны.

### Пошаговый план

Выводы ниже — **часть контракта**: то, что должен печатать ваш законченный брокер. Курс их не производил. Напишите каждую проверку как приёмочный тест до начала вехи.

#### M0 — Ходячий скелет

**Цель.** Рабочее пространство с CI; `ModelLog` и его тесты в `broker-log`; кодировщик и декодер заголовка кадра в `broker-proto` с тестовым вектором; заглушки `#[ignore]` для M1–M6.

**Готово, когда:** `cargo test` проходит тесты модели и тест тестового вектора; `brokerd --version` и `bk --version` работают.

#### M1 — Одна партиция на диске

**Цель.** `PartitionLog` с файлами сегментов, разреженным индексом, переходом на новый сегмент при `--segment-bytes`, хранением по размеру и возрасту и восстановлением (правило 9).

При восстановлении читайте пакеты с начала последнего сегмента; остановитесь на первом пакете, длина которого выходит за конец файла или контрольная сумма которого неверна, и обрежьте файл в этом месте. Перестройте разреженный индекс последнего сегмента по прочитанным пакетам; не доверяйте индексному файлу, который мог быть записан после данных.

</details>

**Готово, когда:** тест на основе модели с `proptest` со случайными добавлениями, чтениями со случайных смещений, хранением и *повторным открытием* (закрыть и снова открыть журнал) всегда согласен с `ModelLog`; тест на сбой, который обрезает последний сегмент на каждой позиции байта внутри последнего пакета, восстанавливает каждый полный пакет и ничего больше; чтение из середины партиции в 1 ГиБ читает меньше одного интервала индекса данных до первой возвращаемой записи (посчитайте байты в тесте).

#### M2 — Сетевой протокол

**Цель.** `brokerd` с одним топиком и одной партицией: Produce, Fetch с длинным опросом, ListOffsets. `bk produce` и `bk consume` без групп (`--from-beginning`).

<details>
<summary>Подсказка</summary>

Фрейминг делает `tokio_util::codec` с кодеком с разделением по длине (length-delimited); тело декодируете вы. Длинный опрос: у каждой партиции есть `tokio::sync::Notify` (или канал `watch` со смещением конца журнала); ждущее чтение спит, пока его не разбудят или не пройдёт `max_wait_ms`.

</details>

**Готово, когда:**

```bash
bk produce orders hello
bk consume orders --from-beginning
```

```text
orders/0@0
orders/0@0 value=hello
```

Также: производитель отправляет 1 миллион записей пакетами, а потребитель читает ровно те же записи в том же порядке; потребитель, ждущий на конце журнала, получает новую запись в пределах 10 мс после её производства; фаззинг-цель для декодирования кадров и сообщений работает 10 минут без паники и без выделения памяти больше размера кадра.

#### M3 — Топики, партиции и хранение

**Цель.** `topic create`, Metadata, несколько партиций на топик, партиционирование по ключу (правило 2) и хранение для каждого топика.

<details>
<summary>Подсказка</summary>

Один каталог на партицию: `<data>/orders-0/`, `<data>/orders-1/`. Настройки топика храните в маленьком файле на топик, записанном атомарно (временный файл, `fsync`, переименование). Сначала протестируйте функцию партиционирования отдельно: один ключ → одна партиция, а ключи распределяются примерно равномерно.

</details>

**Готово, когда:** 10 000 записей со 100 разными ключами ложатся так, что все записи одного ключа оказываются в одной партиции в порядке производства; топик с `--retention-bytes 10485760` (10 МиБ) никогда не хранит больше 10 МиБ плюс один сегмент на партицию, пока вы производите 100 МиБ; `bk topic create orders --partitions 3` дважды даёт ошибку `topic orders already exists`.

#### M4 — Группы потребителей и закоммиченные смещения

**Цель.** JoinGroup, Heartbeat, LeaveGroup, простое назначение (например, диапазонами), перебалансировка, когда члены присоединяются, уходят или перестают присылать heartbeat, CommitOffset и FetchOffset, надёжно хранимые в `__offsets`.

<details>
<summary>Подсказка</summary>

Дайте группе номер *поколения* (generation), который растёт с каждой перебалансировкой, и отклоняйте коммиты из более старого поколения: член, который был слишком медленным и потерял свои партиции, не должен перезаписать смещения нового владельца. Пишите коммит записью в `__offsets` с ключом (группа, топик, партиция); при старте читайте топик, чтобы восстановить последние смещения.

</details>

**Готово, когда:**

```bash
bk groups describe billing
```

```text
orders/0  member=A  committed=1200  end=1250  lag=50
orders/1  member=A  committed=980   end=980   lag=0
orders/2  member=B  committed=1105  end=1190  lag=85
```

Также: с двумя потребителями в одной группе и тремя партициями каждую партицию читает ровно один из них; когда один потребитель убит, другой забирает его партиции в пределах тайм-аута сессии и продолжает с закоммиченного смещения; проверка, которая записывает каждую обработанную пару (партиция, смещение), не показывает **пропусков** (повторы разрешены — правило 7).

#### M5 — Репликация

**Цель.** У каждой партиции есть лидер и ведомые на других брокерах; ведомые читают у лидера; лидер ведёт ISR и верхнюю отметку; `acks=all`; простой контроллер выбирает нового лидера из ISR, когда лидер отказывает.

<details>
<summary>Подсказка</summary>

Контроллер — самая трудная для правильной реализации часть. Два хороших варианта: один брокер — фиксированный контроллер (просто, но это единая точка отказа — скажите об этом в README), или метаданные контроллера живут в вашем хранилище Raft из варианта 1 или Проекта 18.14. Ведомый, который возвращается, сначала должен обрезать свой журнал до последней известной ему верхней отметки, потому что записи выше неё могли так и не быть закоммичены.

</details>

**Готово, когда:** симуляция на `turmoil` убивает лидера партиции во время нагрузки производства с `acks=all` — каждая подтверждённая запись читается после переключения, по порядку, и ни один потребитель никогда не получил запись, которая потом исчезла; при одном из трёх остановленных брокеров `acks=all` по-прежнему выполняется (ISR уменьшается); метрики показывают недостаточно реплицированные партиции, пока брокер недоступен.

#### M6 — Идемпотентные производители, производительность и эксплуатация

**Цель.** Идентификаторы производителей и порядковые номера (повторённый пакет сохраняется один раз), бенчмарки, метрики и установка из трёх брокеров в Docker Compose.

<details>
<summary>Подсказка</summary>

Брокер хранит для каждой пары (идентификатор производителя, партиция) последний сохранённый порядковый номер как часть состояния партиции; оно должно переживать перезапуски и смену лидера, как таблица дедупликации из варианта 1. Делайте бенчмарки с фиксированным размером сообщения (например, 1 КиБ) и записывайте размер пакета, `acks`, число партиций и политику сброса на диск.

</details>

**Готово, когда:** тест заставляет брокер потерять ответ на запрос производства, производитель повторяет, а партиция содержит пакет ровно один раз; `docs/results.md` сообщает МБ/с (мегабайты в секунду) и задержку производства p50/p99 (медиана и 99-й перцентиль, Урок 19.1) для `acks=1` и `acks=all` с `--flush every-batch` и с `interval-ms=10` и объясняет разницу; отставание потребителей по группам видно в `/metrics`; `docker compose up` запускает три брокера, и команды из M4 работают с ними.

### Планка качества

| Область | Что это значит здесь |
|---|---|
| Тесты на основе модели | `PartitionLog` против `ModelLog` (M1); координатор групп против простой модели назначений |
| Тесты на сбои | обрезка на каждом байте последнего пакета (M1); `kill -9` для `brokerd` во время производства; перезапуск с диска |
| Симуляция | переключение лидера с `acks=all` (M5) со многими начальными значениями (seed) |
| Фаззинг | декодеры кадров и сообщений, декодер пакетов, восстановление сегмента из случайных байтов |
| Бенчмарки | МБ/с и задержка для каждого `acks` и политики сброса; `criterion` для пути добавления и декодера пакетов |
| Наблюдаемость | метрики смещения конца журнала, верхней отметки, размера ISR, отставания потребителей, задержки `fsync` |
| Устойчивость | максимальный размер кадра проверяется **до** выделения памяти; лимиты на размер пакета, соединения и ждущие чтения |

> 🔒 **Безопасность:** поле длины из сети — это внешний ввод. Проверьте его на максимальный размер кадра до того, как выделять буфер такого размера; иначе один 4-байтовый заголовок кадра (`ff ff ff ff`) заставит брокер попытаться выделить 4 ГиБ.

### Дополнительные цели

- **Компакция журнала по ключу:** хранить в старых сегментах только новейшую запись каждого ключа (это со временем нужно `__offsets`).
- **Чтение без копирования** (zero-copy) через системный вызов Linux `sendfile`, который копирует данные файла из страничного кэша в сокет внутри ядра, не пропуская их через вашу программу (идея избегать копий — в Уроке 22.19).
- **Обработка ровно один раз** (exactly-once) для схемы «прочитать — преобразовать — записать» с транзакциями между партициями.
- **Push-потребители** в стиле NATS JetStream рядом с чтением по запросу (pull).
- **Многоуровневое хранение** (tiered storage): переносить старые сегменты в объектное хранилище (локальный контейнер MinIO) и читать их по требованию.

## Частые ошибки

**1. Показывать записи выше верхней отметки.** Потребитель читает смещение 500 у лидера, лидер падает, у нового лидера смещения 500 никогда не было — потребитель увидел запись, которой больше нет. Правило 6: только ниже верхней отметки.

**2. Коммитить до обработки.** Потребитель коммитит смещение 100, падает во время обработки записи 99 и больше её не увидит: случайная доставка «не больше одного раза». Правило 7: сначала обработать, потом коммитить.

**3. Доверять индексу после сбоя.** Запись индекса записана, данные — нет. Исправление: при восстановлении перестраивайте индекс последнего сегмента по данным.

**4. Один `fsync` на запись.** Пропускная способность падает до числа `fsync` в секунду (около 500 по 2 мс). Исправление: пакеты и описанная политика сброса (правило 4).

**5. Перебалансировка, после которой одну партицию читают два члена.** Старый владелец медленный, не замечает перебалансировки и продолжает коммитить. Исправление: номера поколений (подсказка к M4).

**6. Неограниченные ждущие чтения.** Десять тысяч потребителей в длинном опросе, каждый держит буфер. Исправление: лимит ждущих чтений на соединение и в сумме, и `max_wait_ms` всегда соблюдается.

## Упражнения

Сделайте их в `code/p23-broker-model` до M0.

### Упражнение 1 — «Хотя бы один раз» на практике (легко)

Потребитель из группы `billing` читает записи 40–49 партиции 0, отправляет счёт по каждой и коммитит смещение 50. Он падает после отправки счёта по записи 45, но до коммита. Что происходит после перезапуска и что должен с этим делать сервис счетов?

<details>
<summary>Подсказка</summary>

Последнее закоммиченное смещение — из предыдущего круга. Посмотрите на правило 7.

</details>

<details>
<summary>Ответ</summary>

Закоммиченное смещение по-прежнему 40, поэтому после перезапуска потребитель снова читает записи 40–49 и отправляет счета 40–45 **второй** раз. Это доставка «хотя бы один раз». Поэтому сервис счетов должен быть идемпотентным: например, он использует (топик, партиция, смещение) или идентификатор счёта внутри записи как уникальный ключ и пропускает повторы. Коммит *до* обработки избавил бы от повторов, но мог бы терять счета («не больше одного раза»).

</details>

### Упражнение 2 — Напишите тесты для правил смещений (средне)

Добавьте в `src/main.rs` тестовый модуль с двумя тестами: (a) после `delete_before(2)` на журнале с двумя записями следующий `append` возвращает 2, а `fetch(0, 10)` возвращает `OffsetOutOfRange` с `log_start: 2, log_end: 3`; (b) на журнале с одной записью `fetch(1, 10)` — это `Ok` без записей, а `fetch(2, 10)` — ошибка.

<details>
<summary>Подсказка</summary>

`FetchError` выводит `PartialEq`, поэтому можно сравнить целый `Err(…)` через `assert_eq!`. Для (b) `Ok(vec![])` работает, потому что `Record` тоже выводит `PartialEq`.

</details>

<details>
<summary>Ответ</summary>

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn offsets_are_never_reused_after_retention() {
        let mut log = ModelLog::default();
        log.append(b"a");
        log.append(b"b");
        log.delete_before(2);
        assert_eq!(log.append(b"c"), 2);
        assert_eq!(
            log.fetch(0, 10),
            Err(FetchError::OffsetOutOfRange {
                log_start: 2,
                log_end: 3
            })
        );
    }

    #[test]
    fn fetching_at_the_end_is_empty_and_beyond_is_an_error() {
        let mut log = ModelLog::default();
        log.append(b"a");
        assert_eq!(log.fetch(1, 10), Ok(vec![]));
        assert!(log.fetch(2, 10).is_err());
    }
}
```

```text
running 2 tests
..
test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Почему это работает: (a) закрепляет правило 1 (нет повторного использования) и ошибку из правила 5; (b) закрепляет разницу между «всё прочитано» и «вне диапазона», от которой зависит ваш длинный опрос.

</details>

### Упражнение 3 — Тестовый вектор (средне)

Напишите `pub fn encode_frame(api_key: u16, version: u16, correlation_id: u32, body: &[u8]) -> Vec<u8>`, начиная с теста: тест сравнивает `encode_frame(1, 0, 7, b"hi")` с 14 байтами тестового вектора из контракта.

<details>
<summary>Подсказка</summary>

`u32::to_be_bytes` и `u16::to_be_bytes` дают байты в порядке big-endian (Урок 12.1). Длина считает 8 байтов заголовка после поля длины плюс тело.

</details>

<details>
<summary>Ответ</summary>

```rust
/// Encodes one frame: length, api key, version, correlation ID, body (all big-endian).
pub fn encode_frame(api_key: u16, version: u16, correlation_id: u32, body: &[u8]) -> Vec<u8> {
    let length = (8 + body.len()) as u32;
    let mut frame = Vec::with_capacity(4 + length as usize);
    frame.extend_from_slice(&length.to_be_bytes());
    frame.extend_from_slice(&api_key.to_be_bytes());
    frame.extend_from_slice(&version.to_be_bytes());
    frame.extend_from_slice(&correlation_id.to_be_bytes());
    frame.extend_from_slice(body);
    frame
}
```

Тест внутри `mod tests`:

```rust
#[test]
fn a_produce_frame_matches_the_protocol_document() {
    let frame = encode_frame(1, 0, 7, b"hi");
    let expected = [
        0x00, 0x00, 0x00, 0x0a, // length = 10 bytes after this field
        0x00, 0x01, // api key 1 = Produce
        0x00, 0x00, // version 0
        0x00, 0x00, 0x00, 0x07, // correlation ID 7
        b'h', b'i', // body
    ];
    assert_eq!(frame, expected);
}
```

Почему это работает: тестовый вектор, записанный в документе протокола и проверяемый тестом, держит документ и код согласованными. Если кто-то по ошибке поменяет порядок байтов или правило длины, тест упадёт. (Приведение `as u32` здесь безопасно только потому, что кадры ограничены намного меньше 4 ГиБ; настоящий кодировщик должен проверять лимит.)

</details>

### Упражнение 4 — Тест на основе свойств для модели (сложно)

С `proptest` (Урок 09.4; `cargo add --dev proptest@1`) напишите тест на основе свойств: для любой последовательности до 100 случайных операций, каждая из которых либо `Append(value)`, либо `DeleteBefore(offset)`, (a) смещения, которые возвращает `append`, идут 0, 1, 2, … по порядку и (b) после каждой операции чтение с `log_start` возвращает ровно `log_end() - log_start` записей.

<details>
<summary>Подсказка</summary>

Опишите операцию через `enum Op` и постройте стратегию с `prop_oneof!` и `prop_map`, как в тесте на основе модели из Проекта 17.14. Дайте добавлениям больший вес, чем удалениям (`3 => …, 1 => …`), иначе журнал большую часть времени пуст. Тестовый модуль может читать приватное поле `log_start`, потому что он дочерний модуль.

</details>

<details>
<summary>Ответ</summary>

```rust
use proptest::prelude::*;

#[derive(Debug, Clone)]
enum Op {
    Append(Vec<u8>),
    DeleteBefore(u64),
}

fn op() -> impl Strategy<Value = Op> {
    prop_oneof![
        3 => prop::collection::vec(any::<u8>(), 0..8).prop_map(Op::Append),
        1 => (0u64..50).prop_map(Op::DeleteBefore),
    ]
}

proptest! {
    #[test]
    fn appended_offsets_are_consecutive(ops in prop::collection::vec(op(), 0..100)) {
        let mut log = ModelLog::default();
        let mut expected_next = 0;
        for op in ops {
            match op {
                Op::Append(value) => {
                    prop_assert_eq!(log.append(&value), expected_next);
                    expected_next += 1;
                }
                Op::DeleteBefore(offset) => log.delete_before(offset),
            }
            let kept = log.fetch(log.log_start, usize::MAX).unwrap();
            prop_assert_eq!(kept.len() as u64, log.log_end() - log.log_start);
        }
    }
}
```

Поместите эти строки внутрь `mod tests`. С четырьмя тестами из Упражнений 2–4 `cargo test -q` печатает:

```text
running 4 tests
....
test result: ok. 4 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.07s
```

Почему это работает: proptest по умолчанию выполняет тело для 256 случайных последовательностей и уменьшает (shrinking) упавшую до минимального примера. `DeleteBefore` со смещениями до 50 иногда указывает за конец, что проверяет `min` в `delete_before`. В M1 то же `enum Op` получит новые варианты (`Fetch`, `Reopen`) и будет управлять вашим настоящим `PartitionLog` рядом с моделью.

</details>

## Вопросы для самопроверки

1. Зачем у топика партиции и какой порядок получает потребитель?

<details>
<summary>Ответ</summary>

Партиции позволяют писать и читать топик параллельно (несколькими брокерами и несколькими потребителями). Порядок гарантирован только внутри одной партиции; записи с одним ключом идут в одну партицию, поэтому остаются по порядку.

</details>

2. Что означают смещения начала и конца журнала и что происходит при чтении ровно на конце?

<details>
<summary>Ответ</summary>

Начало журнала — смещение самой старой сохранённой записи; конец — смещение, которое получит следующая запись. Чтение на конце — не ошибка: потребитель всё прочитал, и брокер ждёт (длинный опрос), пока не придут новые данные или не пройдёт `max_wait_ms`.

</details>

3. Почему достаточно разреженного индекса?

<details>
<summary>Ответ</summary>

Потому что записи в сегменте отсортированы по смещению. Индекс перепрыгивает к ближайшей предыдущей записи индекса, а брокер сканирует вперёд на маленькое, ограниченное расстояние. Полный индекс был бы гораздо больше и дал бы мало.

</details>

4. Что такое верхняя отметка и почему потребители могут читать только ниже неё?

<details>
<summary>Ответ</summary>

Первое смещение, которого ещё нет хотя бы у одной синхронной реплики; каждая запись ниже него есть на всех синхронных репликах. Записи на этой отметке и выше могут быть только на части реплик и могут исчезнуть при переключении; чтение их позволило бы потребителю увидеть данные, которые потом будут потеряны.

</details>

5. Какую проблему решают номера поколений в группах потребителей?

<details>
<summary>Ответ</summary>

Медленный член, пропустивший перебалансировку, мог бы продолжать коммитить смещения партиций, которые ему больше не принадлежат. С номером поколения на каждом коммите координатор отклоняет коммиты старого поколения.

</details>

6. Что обещает `acks=all` и чего это стоит?

<details>
<summary>Ответ</summary>

Производитель получает ответ, только когда пакет есть у каждой синхронной реплики, поэтому пакет переживает потерю лидера. Это стоит задержки (круговой путь до ведомых и их записи) и требует, чтобы ISR оставался здоровым.

</details>

7. Почему стоит писать эталонную модель вроде `ModelLog`, хотя она никогда не используется в продакшене?

<details>
<summary>Ответ</summary>

Она настолько проста, что очевидно верна, поэтому может быть судьёй в тестах на основе модели: тысячи случайных операций над настоящим, сложным журналом сравниваются с моделью, и каждое расхождение — ошибка.

</details>

## Итоги

- Вариант 3 — брокер на основе журнала: топики разделены на партиции, каждая партиция — журнал только для добавления из файлов сегментов с разреженным индексом, потребители читают по смещениям, а вместо удаления при чтении действует хранение.
- Группы потребителей делят партиции и хранят закоммиченные смещения; доставка — «хотя бы один раз», поэтому потребители должны справляться с повторами.
- Репликация добавляет лидеров, ведомых, ISR и верхнюю отметку; `acks` позволяет производителям выбирать между задержкой и надёжностью; идемпотентные производители убирают повторы от повторных отправок.
- Контракт фиксирует командные строки, версионированный двоичный формат кадров с тестовым вектором и девять правил о смещениях, порядке, надёжности, чтении, видимости, доставке, хранении и восстановлении.
- Вехи: M0 модель и фрейминг, M1 партиция на диске, M2 протокол, M3 топики и хранение, M4 группы потребителей, M5 репликация, M6 идемпотентные производители, производительность и эксплуатация.
- `ModelLog` — судья для тестов на основе модели начиная с M1; изучайте Kafka, KIP-98, NATS JetStream и Apache Iggy после того, как сами спроектировали каждую часть.
