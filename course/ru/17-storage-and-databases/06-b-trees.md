## Новые слова

| Слово | Значение |
|---|---|
| **BST** (Binary Search Tree, двоичное дерево поиска) | Дерево, в котором у каждого узла не больше двух потомков: меньшие ключи слева, большие справа (Урок 07.11). |
| **B-дерево** (B-tree) | Сбалансированное дерево поиска, узлы которого содержат много отсортированных ключей и имеют много потомков. Устроено так, что один узел помещается в одну страницу диска. |
| **ветвистость** (fanout) | Сколько потомков у узла. У узла B-дерева их могут быть сотни, у узла двоичного дерева — два. |
| **минимальная степень** (minimum degree, `t`) | Число, задающее размер узла в нашем B-дереве: каждый узел, кроме корня, содержит от `t - 1` до `2t - 1` ключей. |
| **разделение** (split) | Когда узел полон, его разрезают на два наполовину полных узла, а средний ключ поднимают в родителя. |
| **внутренний узел** (internal node) | Узел, у которого есть потомки (не лист). |
| **B+-дерево** (B+ tree) | Вариант, которым пользуются настоящие базы данных: все значения лежат в листьях, внутренние узлы только направляют поиск, а листья связаны по порядку ключей. |
| **страница** (page) | Блок файла базы данных фиксированного размера (часто 4 КиБ или 8 КиБ; КиБ, кибибайт, — это 1024 байта), который читают и пишут целиком. Здесь одна страница содержит один узел дерева. |
| **страница со слотами** (slotted page) | Раскладка страницы, в начале которой небольшой массив смещений указывает на записи разного размера внутри страницы. |

## 1. Почему не двоичное дерево поиска на диске?

В Уроке 07.11 сбалансированное двоичное дерево поиска (BST, binary search tree) находило любой из `n` ключей примерно за
`log₂ n` шагов. Для миллиона ключей это 20 шагов. В памяти каждый шаг — несколько наносекунд. На диске каждый шаг — переход
к другому узлу где-то в файле: случайное чтение в десятки микросекунд на SSD (твердотельном накопителе) и в миллисекунды на HDD — жёстком диске (Урок 17.1). Двадцать
случайных чтений на один поиск — слишком много.

Хуже того, каждое чтение приносит целый блок в 4 КиБ (Урок 17.1), а узел BST с одним ключом и двумя указателями занимает,
скажем, 30 байт. 99 % каждого чтения пропадает впустую.

Решение — сделать каждый узел **шириной со страницу**: положить в один узел сотни отсортированных ключей и сотни указателей
на потомков. Тогда одно чтение страницы даёт много информации, а дереву нужно лишь несколько уровней:

```text
 fanout (children per node)    levels for 1,000,000 keys    levels for 1,000,000,000 keys
            2  (a BST)                    20                            30
          100                              3                             5
          500                              3                             4
```

Это и есть **B-дерево**. При 500 потомках на узел поиск среди миллиарда ключей читает четыре страницы, а один-два верхних
уровня используются так часто, что всё равно остаются в RAM. (Число уровней — это `log` по основанию, равному
ветвистости; упражнение 1 его вычисляет.)

## 2. Правила

У нашего B-дерева есть **минимальная степень** `t` (не меньше 2). Тогда:

1. Каждый узел хранит свои ключи **отсортированными**. Узел с `k` ключами либо не имеет потомков (**лист**), либо имеет
   ровно `k + 1` потомков (**внутренний узел**).
2. Потомок номер `i` хранит ключи, которые лежат *между* ключом `i - 1` и ключом `i` своего родителя:

```text
                 [ 20 | 50 ]
                /     |     \
      [ 5 | 10 ]  [ 30 | 40 ]  [ 60 | 70 | 80 ]
       keys < 20   20 < keys < 50   keys > 50
```

3. Каждый узел, кроме корня, содержит от `t - 1` до `2t - 1` ключей. Он никогда не бывает переполнен и никогда не бывает
   заполнен меньше чем наполовину. (При `t = 2`, как на рисунке, узел содержит от 1 до 3 ключей.)
4. **Все листья находятся на одной глубине.** Именно это здесь значит «сбалансированное», и поэтому никакой порядок вставки,
   даже отсортированный, не может сделать дерево высоким.

**Поиск** следует из правила 2. Начните с корня. Сделайте двоичный поиск по ключам узла. Если ключ там — готово. Иначе
поиск подскажет, между какими двумя ключами он оказался бы; спуститесь в этого потомка. Если в листе ключа нет, ключ не
существует.

**Вставка** всегда добавляет ключ в **лист**, на его место по порядку. Проблема — полный лист (`2t - 1` ключей). Тогда узел
**разделяется**: его средний ключ поднимается в родителя, а ключи слева и справа от него становятся двумя узлами по
`t - 1` ключей. Здесь `t = 2`, и мы вставляем 40 в полный лист:

```text
before:      [ 20 ]                   after:        [ 20 | 30 ]
            /      \                               /     |     \
      [ 10 ]    [ 25 | 30 | 35 ]             [ 10 ]  [ 25 ]  [ 35 | 40 ]
                     full!                                         40 goes here
```

А если родитель тоже полон? Наш код обходит этот вопрос простым приёмом: на пути **вниз** он разделяет каждый полный узел, в
который собирается войти. Поэтому, когда разделение поднимает ключ, в родителе всегда есть место. Если полон **корень**,
сначала над ним ставится новый корень. Только так дерево становится выше: оно растёт сверху, никогда снизу, и все листья
остаются на одной глубине.

## 3. B-дерево на Rust

Создайте `src/btree.rs` и добавьте `pub mod btree;` в `src/lib.rs`. Типы:

```rust
use std::cmp::Ordering;

/// A B-tree in memory. Every node except the root holds between t-1 and 2t-1 keys,
/// and all leaves are at the same depth.
pub struct BTree<K, V> {
    root: Node<K, V>,
    t: usize,
    len: usize,
}

struct Node<K, V> {
    keys: Vec<K>,              // sorted
    vals: Vec<V>,              // vals[i] belongs to keys[i]
    children: Vec<Node<K, V>>, // empty for a leaf, otherwise keys.len() + 1
}

impl<K, V> Node<K, V> {
    fn new() -> Self {
        Node {
            keys: Vec::new(),
            vals: Vec::new(),
            children: Vec::new(),
        }
    }

    fn is_leaf(&self) -> bool {
        self.children.is_empty()
    }
}
```

Узел владеет своими потомками напрямую, в `Vec<Node>`; потомок не может пережить родителя, поэтому `Box` или `Rc` не нужны.
Дерево обобщено по типу ключа `K` (он должен быть `Ord`, чтобы его можно было сортировать) и типу значения `V` (Урок 05.1).

Поиск и мелкие вспомогательные методы:

```rust
impl<K: Ord, V> BTree<K, V> {
    /// Creates an empty tree with minimum degree `t` (a node holds at most 2t-1 keys).
    pub fn new(t: usize) -> Self {
        assert!(t >= 2, "minimum degree must be at least 2");
        BTree {
            root: Node::new(),
            t,
            len: 0,
        }
    }

    pub fn len(&self) -> usize {
        self.len
    }

    pub fn is_empty(&self) -> bool {
        self.len == 0
    }

    /// Number of levels: 1 for a tree that is only a root.
    pub fn height(&self) -> usize {
        let mut height = 1;
        let mut node = &self.root;
        while !node.is_leaf() {
            node = &node.children[0];
            height += 1;
        }
        height
    }

    pub fn get(&self, key: &K) -> Option<&V> {
        let mut node = &self.root;
        loop {
            match node.keys.binary_search(key) {
                Ok(i) => return Some(&node.vals[i]),
                Err(_) if node.is_leaf() => return None,
                Err(i) => node = &node.children[i],
            }
        }
    }
```

**Что происходит:**

1. `height` спускается по самым левым потомкам. Правило 4 говорит, что все листья на одной глубине, поэтому любой путь даёт
   высоту.
2. `binary_search` возвращает `Ok(i)`, когда `keys[i]` — искомый ключ, и `Err(i)` с позицией, где ключ *был бы*. Эта позиция
   — ровно номер потомка, в которого надо спуститься (правило 2). Это поиск из раздела 2 в четыре строки.
3. `Err(_) if node.is_leaf()` — ветка `match` с **условием** (guard, Урок 04.5): она подходит, только если условие истинно.

Вставка, конец `impl BTree`:

```rust
    /// Inserts or overwrites. Returns the old value if the key was already there.
    pub fn insert(&mut self, key: K, value: V) -> Option<V> {
        if self.root.keys.len() == 2 * self.t - 1 {
            // The root is full: put a new, empty root above it and split the old root.
            let old_root = std::mem::replace(&mut self.root, Node::new());
            self.root.children.push(old_root);
            self.root.split_child(0, self.t);
        }
        let old = self.root.insert_non_full(key, value, self.t);
        if old.is_none() {
            self.len += 1;
        }
        old
    }
}
```

`std::mem::replace(&mut self.root, Node::new())` ставит новый пустой узел на место корня и возвращает старый корень. Он
нужен потому, что Rust не позволяет вынести значение из поля и оставить поле пустым даже на мгновение. Старый корень
становится единственным потомком нового, и его разделение даёт новому корню первый ключ.

Методы узла, которые делают настоящую работу:

```rust
impl<K: Ord, V> Node<K, V> {
    /// Splits the full child `i` (2t-1 keys) into two nodes of t-1 keys
    /// and moves its middle key up into `self`.
    fn split_child(&mut self, i: usize, t: usize) {
        let child = &mut self.children[i];
        let right = Node {
            keys: child.keys.split_off(t),
            vals: child.vals.split_off(t),
            children: if child.is_leaf() {
                Vec::new()
            } else {
                child.children.split_off(t)
            },
        };
        let middle_key = child.keys.pop().expect("a full node has a middle key");
        let middle_val = child.vals.pop().expect("a full node has a middle value");
        self.keys.insert(i, middle_key);
        self.vals.insert(i, middle_val);
        self.children.insert(i + 1, right);
    }

    /// Inserts into a node that is known not to be full.
    fn insert_non_full(&mut self, key: K, value: V, t: usize) -> Option<V> {
        let mut i = match self.keys.binary_search(&key) {
            Ok(i) => return Some(std::mem::replace(&mut self.vals[i], value)),
            Err(i) => i,
        };
        if self.is_leaf() {
            self.keys.insert(i, key);
            self.vals.insert(i, value);
            return None;
        }
        if self.children[i].keys.len() == 2 * t - 1 {
            self.split_child(i, t);
            // The middle key of the child is now keys[i]: choose the side to go down.
            match key.cmp(&self.keys[i]) {
                Ordering::Equal => return Some(std::mem::replace(&mut self.vals[i], value)),
                Ordering::Greater => i += 1,
                Ordering::Less => {}
            }
        }
        self.children[i].insert_non_full(key, value, t)
    }
}
```

**Что происходит:**

1. В `split_child` у потомка `2t - 1` ключей на позициях `0 .. 2t-1`. `split_off(t)` отрезает позиции `t ..` (это `t - 1`
   ключей) в новый правый узел. У потомка остаётся `t` ключей; `pop` убирает последний из них, позицию `t - 1`, —
   **средний ключ**. У потомка остаётся `t - 1` ключей. У внутреннего потомка `2t` детей, и `split_off(t)` отдаёт каждой
   стороне по `t`.
2. Средний ключ и его значение идут в родителя на позицию `i`, а правый узел становится потомком `i + 1` — ровно как на
   рисунке в разделе 2.
3. `insert_non_full` сначала проверяет, нет ли ключа уже в этом узле; тогда перезаписывает значение и возвращает старое,
   так же как `HashMap::insert`.
4. В листе `Vec::insert` ставит ключ на его место по порядку. Во внутреннем узле код разделяет потомка **до** спуска, если
   этот потомок полон. После разделения средний ключ потомка оказывается в `keys[i]`, поэтому новый ключ может относиться к
   правой половине (`i += 1`) или даже совпасть с этим средним ключом.
5. Рекурсия спускается на один уровень за вызов, поэтому её глубина равна высоте дерева.

> ⚡ **Производительность:** `Vec::insert` в середину узла сдвигает ключи после него, это O(ветвистость) работы. Звучит
> плохо, но узел маленький и лежит в нескольких кэш-линиях (Урок 12.9); сдвинуть несколько сотен байт дешевле, чем
> пройти ещё по одному указателю. Поэтому и `BTreeMap` стандартной библиотеки — B-дерево.

## 4. Тестируем против `BTreeMap`

Лучший тест для собственной структуры данных — проверенная структура, которая делает ту же работу:
`std::collections::BTreeMap`. Подайте обеим одни и те же операции и сравните каждый ответ. Добавьте в конец
`src/btree.rs`:

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use std::collections::BTreeMap;

    #[test]
    fn small_tree_by_hand() {
        let mut tree = BTree::new(2); // at most 3 keys per node
        for k in [10, 20, 30, 40, 50] {
            tree.insert(k, k * 100);
        }
        assert_eq!(tree.height(), 2); // the root was split once
        assert_eq!(tree.get(&40), Some(&4000));
        assert_eq!(tree.get(&35), None);
        assert_eq!(tree.insert(40, 1), Some(4000)); // overwrite
        assert_eq!(tree.len(), 5);
    }

    #[test]
    fn behaves_like_std_btreemap() {
        for t in [2, 3, 8] {
            let mut ours = BTree::new(t);
            let mut std_map = BTreeMap::new();
            let mut x: u64 = 7;
            for _ in 0..10_000 {
                x ^= x << 13;
                x ^= x >> 7;
                x ^= x << 17;
                let key = x % 5_000; // many repeated keys: overwrites
                assert_eq!(ours.insert(key, x), std_map.insert(key, x));
            }
            assert_eq!(ours.len(), std_map.len());
            for key in 0..5_000 {
                assert_eq!(ours.get(&key), std_map.get(&key), "t = {t}, key = {key}");
            }
        }
    }
}
```

**Что происходит:**

1. Первый тест достаточно мал, чтобы проследить его на бумаге: 10, 20, 30 заполняют корень; вставка 40 разделяет его на
   `[20]` с потомками `[10]` и `[30]`; 40 и 50 присоединяются к `[30]`. Высота 2.
2. Второй тест берёт генератор xorshift из Урока 17.1 и делает 10 000 ключей в `0..5000`, поэтому многие ключи
   повторяются, и перезапись тоже проверяется. Маленькие `t` вроде 2 и 3 вызывают много разделений — именно там прячутся
   ошибки.
3. `insert` должен возвращать тот же `Option`, что и `BTreeMap::insert`, и каждый `get` должен совпадать.

`cargo test --lib btree`:

```text
running 2 tests
test btree::tests::small_tree_by_hand ... ok
test btree::tests::behaves_like_std_btreemap ... ok

test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 21 filtered out; finished in 0.03s
```

> 🧪 **Тестирование:** сравнение с простой проверенной реализацией (*моделью*) — один из самых сильных тестов для структур
> данных. Тестирование на основе свойств из Урока 09.4 делает это автоматически: операции генерирует инструмент.

## 5. Насколько высоким оно становится?

В Уроке 07.11 обычное BST, построенное из **отсортированных** ключей, имело высоту, равную числу ключей. Дадим нашему
B-дереву тот же худший случай. Поместите это в `src/bin/btree_heights.rs`:

```rust
use p17_storage::btree::BTree;

const N: u64 = 1_000_000;

fn main() {
    println!("{:>4} {:>14} {:>7}", "t", "max keys/node", "height");
    for t in [2, 16, 128] {
        let mut tree = BTree::new(t);
        for key in 0..N {
            tree.insert(key, key); // sorted input: the worst case for a plain BST
        }
        assert_eq!(tree.len(), N as usize);
        assert_eq!(tree.get(&777_777), Some(&777_777));
        println!("{:>4} {:>14} {:>7}", t, 2 * t - 1, tree.height());
    }
}
```

`cargo run --release --bin btree_heights`:

```text
   t  max keys/node  height
   2              3      19
  16             31       5
 128            255       3
```

Миллион отсортированных ключей, и высота 19 даже при крошечных узлах; при 255 ключах на узел — 3. Если хранить его на
диске по одному узлу на страницу, поиск прочитал бы 3 страницы. BST из Урока 07.11 на том же вводе потребовало бы до
миллиона шагов.

## 6. B-деревья на диске

Дерево выше живёт в памяти. База данных хранит его в файле, и это работает благодаря трём идеям:

**Один узел — одна страница.** Файл — это массив страниц фиксированного размера (в SQLite по умолчанию 4 КиБ, в PostgreSQL
8 КиБ). Страница номер `n` начинается со смещения `n × page_size`. «Указатель» на потомка — это просто номер страницы.
Чтение узла — одно чтение одной страницы по смещению (Урок 17.1), а кэш страниц в RAM, *пул буферов*, — тема Урока 17.9.

**Страницы со слотами.** Ключи и значения бывают разного размера, поэтому страница не может быть простым массивом. У
**страницы со слотами** есть небольшой заголовок с массивом смещений («слотов») в начале, а записи растут от конца страницы к
середине:

```text
 ┌────────┬────────┬────────┬───────────── free ─────────────┬──────────┬──────────┐
 │ header │ slot 0 │ slot 1 │                                 │ record 1 │ record 0 │
 │ count=2│ → 4000 │ → 3950 │                                 │ (50 B)   │ (96 B)   │
 └────────┴────────┴────────┴─────────────────────────────────┴──────────┴──────────┘
 0                                                                                4095
```

Чтобы держать ключи отсортированными, двигают только маленькие слоты; записи остаются на месте. Упражнение 3 кодирует
страницу попроще, с записями фиксированного размера.

**B+-деревья.** Настоящие базы данных используют вариант — **B+-дерево**. Внутренние узлы содержат только ключи и номера
страниц (без значений), поэтому их помещается в страницу больше, и дерево ещё более плоское. Все значения живут в
**листьях**, и каждый лист указывает на следующий. Запрос по диапазону («все ключи от `b` до `d`») находит первый лист, а
затем просто идёт по цепочке вправо, читая страницы по порядку. Тип индекса PostgreSQL по умолчанию (`CREATE INDEX` из
Урока 16.5) — именно такое дерево.

**Обновления на месте требуют WAL.** В отличие от журналов из Уроков 17.4 и 17.5, B-дерево **меняет страницы на месте**:
вставка переписывает лист, а разделение — три страницы. Сбой посередине может оставить разорванную страницу (Урок 17.2) или
наполовину сделанное разделение, и дерево было бы сломано. Поэтому базы данных на B-деревьях сначала пишут каждое изменение
страницы в WAL, а восстановление его воспроизводит. Вот почему у каждой базы данных на B-деревьях, которую вы встретите, есть
WAL.

Удаление из B-дерева тоже возможно: это зеркальное отражение вставки, со слиянием или перебалансировкой узлов, которые стали
заполнены меньше чем наполовину. Случаев в нём больше, чем во вставке, и в этот урок оно не вошло; многие настоящие системы
просто позволяют страницам оставаться частично пустыми и убирают их позже.

## Частые ошибки

1. **Разделять не по тому индексу.** При `2t - 1` ключах средний находится на индексе `t - 1`. Ошибка на единицу даёт узлы
   с `t` и `t - 2` ключами, что позже нарушает правило 3. Сравнительный тест с `BTreeMap` при `t = 2` быстро это ловит.
2. **Забыть перенести потомков при разделении.** Потомков внутреннего узла нужно разделять вместе с его ключами
   (`children.split_off(t)`), иначе дерево указывает не на те поддеревья.
3. **Спуститься не в ту сторону после разделения.** После `split_child(i)` ключ может теперь относиться к потомку `i + 1`.
   Сравните с новым `keys[i]`, прежде чем спускаться.
4. **Тестировать только со случайными ключами.** Отсортированный и обратный порядок разделяют узлы по-разному; проверяйте и
   их.

## Упражнения

### Упражнение 1 — Сколько уровней? (легко)

Создайте `src/page.rs` (и добавьте `pub mod page;` в `src/lib.rs`) с функцией
`pub fn levels_needed(items: u64, fanout: u64) -> u32`: наименьшее число уровней `h`, при котором `fanout^h >= items`.
Напишите тест: миллиону элементов с ветвистостью 100 нужно 3 уровня; миллиарду с ветвистостью 200 — 4; 100 элементам с
ветвистостью 100 — 1, а 101 — уже 2.

<details>
<summary>Подсказка</summary>

Начните с `levels = 1` и `capacity = fanout`; пока `capacity < items`, умножайте `capacity` на `fanout` и добавляйте
уровень. Используйте `saturating_mul`, чтобы большие числа не переполнялись (Урок 12.2).

</details>

<details>
<summary>Ответ</summary>

```rust
/// Exercise 1: the smallest number of levels such that `fanout`^levels >= `items`.
pub fn levels_needed(items: u64, fanout: u64) -> u32 {
    assert!(fanout >= 2);
    let mut levels = 1;
    let mut capacity = fanout;
    while capacity < items {
        capacity = capacity.saturating_mul(fanout);
        levels += 1;
    }
    levels
}
```

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn levels() {
        assert_eq!(levels_needed(1_000_000, 100), 3);
        assert_eq!(levels_needed(1_000_000_000, 200), 4);
        assert_eq!(levels_needed(100, 100), 1);
        assert_eq!(levels_needed(101, 100), 2);
        assert_eq!(levels_needed(u64::MAX, 2), 64);
    }
}
```

Почему это работает: каждый уровень умножает число достижимых элементов на ветвистость, поэтому `h` уровней достигают
`fanout^h` элементов. `200^4 = 1,6 × 10⁹ ≥ 10⁹`, а `200^3 = 8 × 10⁶` недостаточно. Последняя проверка показывает, что
`saturating_mul` останавливается на `u64::MAX`, а не переполняется.

</details>

### Упражнение 2 — Запрос по диапазону (средне)

Добавьте в `BTree` метод `pub fn range(&self, lo: &K, hi: &K) -> Vec<(&K, &V)>`. Он возвращает все записи с
`lo <= key < hi` в порядке ключей. Заходите только в тех потомков, которые могут содержать такие ключи. Проверьте его
против `BTreeMap::range(lo..hi)` на нескольких диапазонах, включая пустой (`50..50`) и такой, в котором нет ни одного
ключа.

<details>
<summary>Подсказка</summary>

Напишите рекурсивный вспомогательный метод у `Node`, который обходит узел по порядку: для каждого ключа `i` сначала потомок
`i` (только если `keys[i] > lo`), затем сам ключ (если он в диапазоне); остановитесь, как только ключ `>= hi`. После цикла
зайдите в последнего потомка. Методу нужно время жизни `'a`, связывающее возвращаемые ссылки с `&'a self` (Урок 05.3).

</details>

<details>
<summary>Ответ</summary>

В `impl<K: Ord, V> BTree<K, V>`:

```rust
    /// All entries with `lo <= key < hi`, in key order.
    pub fn range(&self, lo: &K, hi: &K) -> Vec<(&K, &V)> {
        let mut out = Vec::new();
        self.root.range_into(lo, hi, &mut out);
        out
    }
```

В `impl<K: Ord, V> Node<K, V>`:

```rust
    /// Appends the entries of this subtree with `lo <= key < hi` to `out`, in order.
    fn range_into<'a>(&'a self, lo: &K, hi: &K, out: &mut Vec<(&'a K, &'a V)>) {
        for (i, key) in self.keys.iter().enumerate() {
            if !self.is_leaf() && key > lo {
                self.children[i].range_into(lo, hi, out); // keys smaller than `key`
            }
            if key >= hi {
                return; // everything further right is too big
            }
            if key >= lo {
                out.push((key, &self.vals[i]));
            }
        }
        if let Some(last) = self.children.last() {
            last.range_into(lo, hi, out); // keys bigger than the last key
        }
    }
```

Тест:

```rust
    #[test]
    fn range_matches_std() {
        let mut ours = BTree::new(3);
        let mut std_map = BTreeMap::new();
        for k in (0..1_000).rev() {
            ours.insert(k * 3, k);
            std_map.insert(k * 3, k);
        }
        for (lo, hi) in [(0, 10), (100, 200), (2_990, 5_000), (50, 50), (7, 8)] {
            let expected: Vec<_> = std_map.range(lo..hi).collect();
            assert_eq!(ours.range(&lo, &hi), expected, "range {lo}..{hi}");
        }
    }
```

`cargo test --lib btree` теперь показывает `3 passed`. Почему это работает: потомок `i` содержит только ключи меньше
`keys[i]`, поэтому если `keys[i] <= lo`, весь потомок ниже диапазона и пропускается. Как только ключ дошёл до `hi`, каждый
ключ и потомок справа от него больше, и обход останавливается. Это отсечение и делает диапазоны дешёвыми: посещаются только
пути к двум концам диапазона и ключи внутри него. Ключи вставлялись в обратном порядке, так что проверяется и такой шаблон
ввода.

</details>

### Упражнение 3 — Лист в странице (сложно)

В `src/page.rs` напишите `pub fn encode_leaf(entries: &[(u64, u64)]) -> [u8; 4096]` и
`pub fn decode_leaf(page: &[u8; 4096]) -> Option<Vec<(u64, u64)>>`. Раскладка страницы: счётчик `u16` в little-endian,
затем записи (8 байт ключа, 8 байт значения), затем нули. Определите `LEAF_CAPACITY` — сколько записей помещается.
`decode_leaf` должен возвращать `None`, если счётчик больше вместимости. Тест: вместимость равна 255; полный лист проходит
круговой путь; повреждённый счётчик отвергается.

<details>
<summary>Подсказка</summary>

Вместимость: `(4096 - 2) / 16`. Запись `i` начинается с байта `2 + i * 16`. Используйте `to_le_bytes`, `from_le_bytes` и
`try_into` ровно как в Уроке 17.3.

</details>

<details>
<summary>Ответ</summary>

```rust
pub const PAGE_SIZE: usize = 4096;
/// How many (u64 key, u64 value) entries fit after the 2-byte count.
pub const LEAF_CAPACITY: usize = (PAGE_SIZE - 2) / 16;

/// Exercise 3: writes a leaf into one page: a u16 count, then the entries, then zeros.
pub fn encode_leaf(entries: &[(u64, u64)]) -> [u8; PAGE_SIZE] {
    assert!(
        entries.len() <= LEAF_CAPACITY,
        "too many entries for one page"
    );
    let mut page = [0u8; PAGE_SIZE];
    page[0..2].copy_from_slice(&(entries.len() as u16).to_le_bytes());
    for (i, (key, value)) in entries.iter().enumerate() {
        let at = 2 + i * 16;
        page[at..at + 8].copy_from_slice(&key.to_le_bytes());
        page[at + 8..at + 16].copy_from_slice(&value.to_le_bytes());
    }
    page
}

/// Exercise 3: reads the entries back; `None` if the count does not fit.
pub fn decode_leaf(page: &[u8; PAGE_SIZE]) -> Option<Vec<(u64, u64)>> {
    let count = u16::from_le_bytes([page[0], page[1]]) as usize;
    if count > LEAF_CAPACITY {
        return None;
    }
    let mut entries = Vec::with_capacity(count);
    for i in 0..count {
        let at = 2 + i * 16;
        let key = u64::from_le_bytes(page[at..at + 8].try_into().unwrap());
        let value = u64::from_le_bytes(page[at + 8..at + 16].try_into().unwrap());
        entries.push((key, value));
    }
    Some(entries)
}
```

Тесты, рядом с тестом из упражнения 1:

```rust
    #[test]
    fn a_full_leaf_round_trips() {
        assert_eq!(LEAF_CAPACITY, 255);
        let entries: Vec<(u64, u64)> = (0..255).map(|k| (k * 10, k * k)).collect();
        let page = encode_leaf(&entries);
        assert_eq!(decode_leaf(&page), Some(entries));
    }

    #[test]
    fn a_damaged_count_is_rejected() {
        let mut page = encode_leaf(&[(1, 2)]);
        page[0..2].copy_from_slice(&1000u16.to_le_bytes());
        assert_eq!(decode_leaf(&page), None);
    }
```

`cargo test --lib page`:

```text

test page::tests::levels ... ok
```

Почему это работает: каждая запись фиксированного размера, поэтому запись `i` лежит по вычисляемому смещению, и слоты не
нужны. Проверка вместимости в `decode_leaf` — это идея `MAX_LEN` из Урока 17.3: счётчик, прочитанный с диска, — это ввод, и
его проверяют до использования. При 255 записях на лист и `levels_needed(10⁹, 255)` = 4 миллиарду таких записей нужно
дерево из четырёх уровней.

</details>

## Вопросы для самопроверки

1. Почему сбалансированное двоичное дерево поиска — плохой индекс на диске?

<details>
<summary>Ответ</summary>

Его высота около `log₂ n` (20 для миллиона ключей), и каждый уровень — случайное чтение с диска. Каждое чтение приносит
целую страницу, но использует лишь несколько её байтов.

</details>

2. Сколько ключей может содержать узел при `t = 3` и сколько потомков может быть у внутреннего узла?

<details>
<summary>Ответ</summary>

От `t - 1 = 2` до `2t - 1 = 5` ключей (у корня может быть меньше) и на одного потомка больше, чем ключей: от 3 до 6.

</details>

3. Что происходит при вставке в полный лист?

<details>
<summary>Ответ</summary>

Лист разделяется: его средний ключ поднимается в родителя, а ключи слева и справа от него становятся двумя листьями по
`t - 1` ключей. Новый ключ затем идёт в нужный из двух.

</details>

4. Как B-дерево становится выше и почему при этом все листья остаются на одной глубине?

<details>
<summary>Ответ</summary>

Только разделением корня: над ним создаётся новый корень. Новый уровень добавляется сверху, поэтому каждый лист опускается
на один уровень одновременно со всеми остальными.

</details>

5. В чём главное отличие B-дерева от B+-дерева?

<details>
<summary>Ответ</summary>

В B+-дереве все значения в листьях, и листья связаны по порядку ключей; внутренние узлы содержат только ключи и номера
страниц потомков. Поэтому внутренние узлы меньше (ветвистость выше), а просмотр диапазона — это проход по листьям.

</details>

6. Почему базе данных с B-деревом нужен WAL, а журнал из Урока 17.5 мог обойтись без него?

<details>
<summary>Ответ</summary>

B-дерево меняет страницы на месте, и сбой может оставить разорванную страницу или наполовину сделанное разделение. WAL
сначала записывает каждое изменение, чтобы восстановление могло его повторить. Журнал, в который только дописывают,
никогда не меняет старые байты, и единственный вред от сбоя для него — разорванный хвост.

</details>

## Итоги

- B-дерево — сбалансированное дерево поиска с широкими узлами: сотни отсортированных ключей на узел, один узел на страницу
  диска.
- Его высота — это `log` по основанию, равному ветвистости: три-четыре чтения страниц находят ключ среди миллиардов.
- Поиск: двоичный поиск в узле, затем спуск в потомка между двумя соседними ключами.
- Вставка добавляет в лист; полные узлы разделяются, их средний ключ поднимается; дерево растёт только у корня, поэтому
  остаётся сбалансированным даже при отсортированном вводе.
- Проверка против `BTreeMap` (модели) ловит ошибки на единицу при разделении.
- На диске узлы — это страницы, часто страницы со слотами; настоящие базы данных используют B+-деревья со связанными
  листьями для просмотра диапазонов.
- B-деревья меняют страницы на месте, поэтому для устойчивости к сбоям им нужен WAL.
