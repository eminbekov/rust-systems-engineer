## Новые слова

| Слово | Значение |
|---|---|
| **оболочка ядра** (kernel shell) | Крошечный цикл команд внутри самого ядра: прочитать строку из последовательной консоли, выполнить встроенную команду. |
| **кольцевой буфер** (ring buffer) | Очередь фиксированного размера, конец которой переходит в начало; ей не нужна куча. |
| **критическая секция** (critical section) | Участок кода, который нельзя прерывать, пока он работает с общими данными. На одном ядре — маскировать прерывания. |
| **куча** (heap) ядра | Область памяти, из которой аллокатор ядра выдаёт блоки для `Box`, `Vec` и `String`. |
| **`#[global_allocator]`** | Атрибут, который говорит Rust, какой аллокатор использует `alloc` (Урок 12.13). |
| **SPI** (Shared Peripheral Interrupt, общее прерывание периферии) | Прерывание GIC от устройства, которое может обработать любое ядро процессора, например UART (INTID 33 на `virt`). |
| **дымовой тест** (smoke test) | Быстрый сквозной тест, который проверяет, что вся система вообще запускается и отвечает. |
| **semihosting** | Способ для программы внутри QEMU попросить сам QEMU о сервисе, например «завершиться с кодом 1». |

**Сокращения из прошлых уроков:** ОС (операционная система), QEMU (Quick Emulator, быстрый эмулятор), UART
(Universal Asynchronous Receiver-Transmitter, универсальный асинхронный приёмопередатчик — последовательный порт;
PL011 — его модель на `virt`), MMU (Memory Management Unit, блок управления памятью), GIC (Generic Interrupt
Controller, универсальный контроллер прерываний), INTID (interrupt ID, номер прерывания), IRQ (Interrupt Request,
запрос прерывания), PSCI (Power State Coordination Interface, интерфейс управления состояниями питания), RAM (Random
Access Memory, оперативная память), ВМ (виртуальная машина) и CI (continuous integration, непрерывная интеграция,
Урок 09.12). Новые в подсказках: FIFO (First In, First Out, «первым пришёл — первым ушёл»: аппаратная очередь байтов)
и `IMSC` (Interrupt Mask Set/Clear, регистр установки и сброса маски прерываний UART).

## 1. Где вы сейчас

Ваше ядро уже умеет многое: оно загружается на «голом железе», печатает, обрабатывает исключения и прерывания и
управляет своей таблицей страниц. Чего оно пока не умеет — это **слушать**. В этом проекте оно получает клавиатуру
(приёмную сторону UART), цикл команд и кучу. Это настоящий рубеж: та же структура (прерывание ввода, буфер,
обработчик команд, аллокатор) есть внутри любого ядра.

Проект — ваша собственная работа; этот урок даёт контракт, план с вехами, небольшие подсказки и приёмочные проверки.
Полного решения нет — каждая часть использует только то, что вы изучили в Уроках 22.2–22.4, плюс сведения о регистрах
из подсказок.

## Проект

### Что вы создадите

`p22-kernel` v1: ядро, которое загружается в QEMU, печатает приглашение и выполняет команды, которые вы вводите:

```text
p22-kernel ready. Type `help`.
p22-kernel> help
commands: help, ticks, mem, history, fault, off
p22-kernel> ticks
ticks: 13
p22-kernel> mem
kernel: 0x40080000..0x400a1000, heap free: 1023 KiB
p22-kernel> history
  1 help
  2 ticks
  3 mem
  4 history
p22-kernel> off
bye
```

Этот вывод получен от эталонного решения; ваши адреса и числа будут другими.

### Контракт

| Входная строка | Вывод |
|---|---|
| `help` | `commands: help, ticks, mem, history, fault, off` |
| `ticks` | `ticks: <n>`, где таймер прибавляет 1 каждые 100 мс |
| `mem` | `kernel: 0x40080000..<stack top>, heap free: <n> KiB` |
| `history` | все непустые команды до сих пор, с номерами: `{:>3} <command>` |
| `fault` | читает `0xC000_0000`; обработчик страничного сбоя паникует (запуск заканчивается) |
| `off` | `bye`, затем PSCI `SYSTEM_OFF` |
| пустая строка | ничего; новое приглашение |
| что-то другое | `unknown command: <the word>` |

Правила:

- После загрузки ядро один раз печатает `` p22-kernel ready. Type `help`. ``. Приглашение — ровно `p22-kernel> `
  (с пробелом). Вводимые символы отображаются (эхо). Backspace (байт `0x7f`) удаляет последний символ.
  Строку заканчивает и `\r` (от терминала), и `\n` (от `printf`).
- Строки длиннее 64 символов обрезаются до 64; ничего не падает.
- Чистая логика (разбор, редактирование строки, кольцевой буфер) живёт в `src/lib.rs` и покрыта модульными тестами.
- `cargo clippy` проходит чисто, `cargo fmt --check` проходит, есть `README.md` и по одному коммиту Git на каждую
  веху.

### Пошаговый план

#### M1 — Читаем клавиатуру опросом

**Цель:** ядро читает байты из UART, отображает их и по Enter печатает `you typed: <line>`. Строка `off` печатает
`bye` и выключает машину.

**Указания:** добавьте `Uart::read_byte(&mut self) -> Option<u8>` в `src/uart.rs`. Храните строку в массиве
фиксированного размера (`[u8; 64]` плюс длина): кучи пока нет. Уберите демонстрационный код Урока 22.4 из
`kernel_main` (оставьте `exceptions::init()`, `mmu::init()` и `timer::init()`). Контракт требует тик каждые
100 мс: если вы не делали Упражнение 1 Урока 22.4, замените сейчас оба вызова `arm(200)` на `arm(100)`.

<details>
<summary>Подсказка</summary>

Бит 4 регистра флагов PL011 (`0x18`) — `RXFE`, «очередь приёма пуста». Пока он равен 0, байт ждёт: прочитайте регистр
данных (`0x00`) через `read_volatile` и оставьте младшие 8 битов. `core::str::from_utf8(&buf[..len])` превращает байты
в `&str`.

</details>

**Готово, когда:** ввод через конвейер работает (конвейер идёт в последовательную линию QEMU):

```bash
printf 'hello\noff\n' | cargo run -q
```

```text
p22-kernel ready. Type `help`.
p22-kernel> hello
you typed: hello
p22-kernel> off
bye
```

Коммит: `git commit -am "p22-kernel: M1 polling input"`.

#### M2 — Редактор строки и разбор команд с тестами на Mac

**Цель:** команды из контракта (пока без `history`), а логика разбора и редактирования — в `src/lib.rs`.

**Указания:** спроектируйте два маленьких типа. `parse(line: &str) -> Result<Command, &str>` возвращает перечисление
`Command` или неизвестное слово. `LineEditor<const N: usize>` принимает один байт через `push(byte)` и говорит, что
должен показать терминал (отобразить байт, стереть один символ, ничего или «строка готова»). Константные обобщения
(`<const N: usize>`) позволяют тестам использовать крошечный редактор на 2 байта.

<details>
<summary>Подсказка</summary>

Перечисление вроде `enum Echo { Byte(u8), Erase, Nothing, Line }` избавляет редактор от печати, поэтому его можно
тестировать. Чтобы стереть символ в терминале, ядро печатает `"\x08 \x08"`: назад, пробел, назад. Игнорируйте байты
вне `b' '..=b'~'`.

</details>

**Готово, когда:** `cargo host-test` запускает минимум шесть тестов (разбор: известная команда, неизвестное слово,
пустая строка; редактор: Backspace, слишком длинная строка, Enter) и они проходят, а

```bash
printf 'help\nwhat\noff\n' | cargo run -q
```

```text
p22-kernel ready. Type `help`.
p22-kernel> help
commands: help, ticks, mem, history, fault, off
p22-kernel> what
unknown command: what
p22-kernel> off
bye
```

#### M3 — Ввод по прерываниям

**Цель:** ядро спит в `wfi`, пока не придёт клавиша. Обработчик прерывания UART перекладывает принятые байты в
кольцевой буфер; `kernel_main` забирает их оттуда.

**Указания:** напишите `RingBuffer<const N: usize>` в `src/lib.rs` с `push(byte) -> bool` (false, когда буфер полон) и
`pop() -> Option<u8>` и протестируйте его, включая переход через конец. Буфер общий для обработчика и `kernel_main`, а
это гонка данных, если её не предотвратить. На одном ядре решение — **критическая секция**: маскировать IRQ, пока
`kernel_main` работает с буфером.

<details>
<summary>Подсказка 1: оборудование</summary>

- Прерывание UART — INTID **33** (это SPI). Разрешите его в распределителе GIC битом 1 регистра по адресу
  `GICD + 0x104` (второй регистр разрешения: INTID 32–63) и запишите в его байт назначения `GICD + 0x800 + 33` значение
  `0x01` (ядро 0) volatile-записью типа `u8`.
- В UART включите прерывания приёма регистром маски прерываний `IMSC` по смещению `0x38`: бит 4 (приём) и бит 6
  (тайм-аут приёма).
- В `handle_irq`, когда INTID равен 33, читайте байты, пока `read_byte` не вернёт `None`. Чтение регистра данных
  сбрасывает прерывание. Затем запишите `EOIR`, как для таймера.

</details>

<details>
<summary>Подсказка 2: безопасное разделение</summary>

Хорошо работает тип-обёртка: `struct IrqCell<T>(UnsafeCell<T>)` с `unsafe impl<T> Sync for IrqCell<T> {}` и методом
`with(&self, f: impl FnOnce(&mut T) -> R) -> R`, который сохраняет `DAIF` (`mrs {}, daif`), маскирует IRQ
(`msr daifset, #2`), вызывает `f` и восстанавливает сохранённый `DAIF` (`msr daif, {}`). Напишите комментарий
`// SAFETY:`, объясняющий, почему это корректно: одно ядро, и прерывания замаскированы, пока работает `f`. Тогда
`static INPUT: IrqCell<RingBuffer<64>>` можно использовать с обеих сторон. Никогда не ждите блокировку внутри
обработчика прерывания.

</details>

**Готово, когда:** в главном цикле есть `wfi` и нет активного опроса UART, тесты кольцевого буфера проходят, а
счётчик тиков идёт, пока ядро ждёт ввода (около 10 тиков в секунду):

```bash
(sleep 1; printf 'ticks\n'; sleep 1; printf 'ticks\noff\n') | cargo run -q
```

```text
p22-kernel ready. Type `help`.
p22-kernel> ticks
ticks: 6
p22-kernel> ticks
ticks: 16
p22-kernel> off
bye
```

Первое число зависит от того, как быстро запускается контейнер; разница между двумя должна быть около 10.

#### M4 — Куча, `Vec` и `String`

**Цель:** `history` и `mem` из контракта, с `alloc::vec::Vec<String>` для истории.

**Указания:** зарезервируйте 1 МиБ под кучу в `linker.ld` после стека, с двумя символами `__heap_start` и
`__heap_end` (выровняйте начало по 4096). Используйте свой аллокатор из Урока 12.14 как `#[global_allocator]` или
крейт `linked_list_allocator = "0.10"`. Инициализируйте кучу в `kernel_main` после `mmu::init()` и до первого
выделения памяти. Добавьте `extern crate alloc;` в `src/main.rs` (в крейте `no_std` `alloc` нужно назвать явно).

<details>
<summary>Подсказка</summary>

С крейтом: `static ALLOCATOR: LockedHeap = LockedHeap::empty();` с пометкой `#[global_allocator]`, затем
`unsafe { ALLOCATOR.lock().init(start as *mut u8, end - start) }`. `ALLOCATOR.lock().free()` даёт свободные байты для
`mem`. Аллокатор использует атомарные инструкции — ещё одна причина сначала включить MMU (и обычную память).

</details>

**Готово, когда:**

```bash
printf 'ticks\nmem\nhistory\noff\n' | cargo run -q
```

```text
p22-kernel ready. Type `help`.
p22-kernel> ticks
ticks: 0
p22-kernel> mem
kernel: 0x40080000..0x400a1000, heap free: 1023 KiB
p22-kernel> history
  1 ticks
  2 mem
  3 history
p22-kernel> off
bye
```

(`ticks: 0` здесь нормально: ввод через конвейер приходит сразу после загрузки.)

#### M5 — Автоматический тест в QEMU и завершение

**Цель:** скрипт `test.sh`, который загружает ядро со сценарием ввода и проверяет ответы, плюс README.

**Указания:** сохраните весь вывод в переменную командной оболочки, затем проверяйте ожидаемые строки через
`grep -q`. Завершайтесь с кодом 1 при первой ошибке, чтобы потом это мог запускать конвейер CI (Урок 09.12).

<details>
<summary>Подсказка</summary>

```sh
out=$(printf 'help\nwhat\nticks\nhistory\noff\n' | cargo run -q 2>&1)
check() {
  if printf '%s\n' "$out" | grep -q "$1"; then echo "ok:   $1"; else echo "FAIL: $1"; exit 1; fi
}
check 'commands: help'
```

</details>

**Готово, когда:**

```bash
./test.sh
```

```text
ok:   commands: help
ok:   unknown command: what
ok:   ticks: 
ok:     2 ticks
ok:   bye
all checks passed
```

и `cargo host-test`, `cargo clippy` и `cargo fmt --check` проходят чисто, README объясняет, как собрать, запустить и
протестировать ядро, а `git log --oneline` показывает по одному коммиту на веху.

### Дополнительные цели

- **`fault`, который не убивает ядро.** Для data abort из команды `fault` напечатайте подробности и вернитесь в
  оболочку вместо паники. (Подсказка: обработчик может записать в `frame.elr` адрес функции «восстановления».)
- **Страницы по 4 КиБ.** Замените блок оперативной памяти таблицей уровня 2 и таблицами уровня 3 и отобразите код ядра
  только для чтения, а его данные — без права выполнения.
- **Второе ядро процессора.** Запустите ядро 1 вызовом PSCI `CPU_ON` (`0xC400_0003`), дайте ему свой стек и пусть оно
  что-нибудь считает. Теперь вам нужны настоящие блокировки (Урок 14.7) вместо маскирования прерываний.
- **Пользовательский режим.** Запустите крошечную функцию на EL0 через `eret` и дайте ей попросить ядро о сервисе
  через `svc` — ваш первый системный вызов, увиденный со стороны ядра (Урок 13.3).
- **Настоящие результаты тестов.** Запускайте QEMU с `-semihosting` и используйте вызов semihosting «exit», чтобы
  упавший тест ядра заставлял QEMU завершаться с ненулевым кодом.

## 2. Следующие шаги

Вы построили основу ядра с нуля на arm64. Вот куда двигаться глубже.

**Читать и проходить:**

- *Writing an OS in Rust* Филиппа Оппермана (Philipp Oppermann, os.phil-opp.com) — тот же путь на x86-64, с крейтом
  `bootloader` (0.11), крейтом `x86_64` (0.15) и крейтом `uart_16550` (0.9). Если пройти его после этого
  направления, вы увидите, что одинаково на любой машине (стек, таблицы страниц, прерывания), а что зависит от
  конкретной.
- *Operating Systems: Three Easy Pieces* (OSTEP) — бесплатная книга об идеях, лежащих в основе любого ядра:
  планирование, виртуальная память, конкурентность, файловые системы.
- *The Embedonomicon* — руководство команды Rust Embedded о программах `no_std`, скриптах компоновщика и коде запуска.
- *Operating System development tutorials in Rust on the Raspberry Pi* — длинная серия уроков о ядре для arm64 на
  Rust, от первой инструкции до виртуальной памяти и исключений.
- *Arm Architecture Reference Manual* и руководства *Learn the architecture* — первоисточник для каждого регистра,
  которого вы касались.

**Проекты с открытым кодом, в которые можно вносить вклад:**

|---|---|---|
| Rust for Linux | Поддержка Rust внутри ядра Linux: драйверы и безопасные абстракции. | Прочитать документацию, собрать ядро с включённым Rust в своей ВМ, следить за списком рассылки и Zulip. |

Redox и каналы о разработке ОС в сообществах Rust. Когда задаёте вопрос, указывайте, какая машина, какая версия QEMU и
какой точно вывод вы видите, — ровно так, как в Уроке 00.7.

**Этап 24** показывает, как выбрать задачу, общаться с мейнтейнерами и отправить свой первый вклад.

> 💡 **Совет:** заведите в журнале обучения страницу «факты о ядре»: каждый регистр, смещение и бит, которые вы
> использовали, с источником. Работа над ядром полна таких фактов, и собственный список быстрее любого руководства.

## Частые ошибки

> ⚠️ **Частая ошибка:** выделять память до инициализации кучи (например, `Vec::new()`, который растёт в
> `exceptions::init`). Аллокатор возвращает нулевой указатель, и `alloc` сообщает об ошибке выделения, что приводит к
> панике. Инициализируйте кучу сразу после MMU.

> ⚠️ **Частая ошибка:** брать спин-блокировку в `kernel_main` и ту же блокировку в обработчике прерывания. Если
> прерывание придёт, пока `kernel_main` держит блокировку, обработчик будет вечно ждать блокировку, которую можно
> отпустить только после его возврата: взаимная блокировка на одном ядре. Вместо этого маскируйте прерывания в обычном
> коде.

> ⚠️ **Частая ошибка:** забыть запись `u8` в регистр назначения UART (`GICD + 0x821`) или включать бит 33 в первом
> регистре разрешения. Прерывания 32–63 — во *втором* регистре (`0x104`), в бите `33 - 32 = 1`.

> ⚠️ **Частая ошибка:** тестировать только через `printf`. Настоящий терминал посылает `\r` для Enter и `0x7f` для
> Backspace; введите несколько команд и вручную через `cargo run` (выход из QEMU — Ctrl-A X).

## Вопросы для самопроверки

1. Зачем оболочке ядра кольцевой буфер между прерыванием UART и `kernel_main`?

<details>
<summary>Ответ</summary>

Обработчик прерывания должен заканчиваться быстро и не может сам выполнять команду, а байты могут приходить быстрее,
чем `kernel_main` их обрабатывает. Кольцевой буфер хранит их по порядку в фиксированной памяти без кучи.

</details>

2. Почему на одном ядре маскирование IRQ — правильная критическая секция для данных, общих с обработчиком прерывания?

<details>
<summary>Ответ</summary>

Единственный другой код, который может коснуться данных, — обработчик, а он запускается только при приходе IRQ. Пока
IRQ замаскированы, ничего другого не выполнится до снятия маски. На нескольких ядрах этого недостаточно; нужны ещё и
блокировки.

</details>

3. Что нужно ядру, чтобы заработал `Vec::push`?

<details>
<summary>Ответ</summary>

`extern crate alloc;`, `#[global_allocator]` и область памяти, которой инициализирован аллокатор (здесь 1 МиБ,
зарезервированный скриптом компоновщика).

</details>

4. Почему проект использует `printf '...' | cargo run -q` для приёмочных тестов?

<details>
<summary>Ответ</summary>

Конвейер подаёт данные на последовательный вход ядра, `-q` скрывает собственные строки Cargo, а `off` завершает
запуск, так что всё ядро можно проверить скриптом, без человека за клавиатурой.

</details>

5. Назовите два ядра с открытым кодом на Rust и один способ начать вносить вклад.

<details>
<summary>Ответ</summary>

Например, Redox OS и Theseus (а также Hermit и Rust for Linux внутри Linux). Начните с того, чтобы собрать и
запустить проект, прочитать руководство для участников и выбрать маленькую задачу для новичков или исправление
документации.

</details>

## Итоги

- Проект превращает ядро в интерактивную систему: ввод через UART, цикл команд, куча и автоматический тест в QEMU.
- Обработчики прерываний остаются короткими: они перекладывают байты в кольцевой буфер; главный цикл спит в `wfi` и
  выполняет работу.
- На одном ядре критическая секция — это «замаскировать IRQ, поработать с данными, восстановить маску».
- `extern crate alloc` и `#[global_allocator]` над зарезервированной областью дают `Vec` и `String`.
- Чистая логика проверяется через `cargo host-test`; всё ядро — загрузкой со сценарием ввода.
- Дальше: *Writing an OS in Rust* для x86-64, OSTEP для теории, а Rust for Linux, Redox, Theseus и Hermit — для
  настоящего вклада.
