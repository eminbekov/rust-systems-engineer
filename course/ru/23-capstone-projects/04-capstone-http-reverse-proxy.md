# Урок 23.4 — Итоговый проект 2: высокопроизводительный обратный HTTP-прокси

> **Этап 23 — Итоговые проекты** · Урок 4 из 10 · ⏱ около 50 часов (25 занятий)

## Что вы узнаете

- Что делает обратный HTTP-прокси в продакшене между клиентами и бэкендами и почему это сильный проект для портфолио.

- Семь вех — от проверки конфигурации до TLS, горячей перезагрузки, ограничения частоты и измеренного, профилированного прокси.

## Новые слова

| Слово | Значение |
|---|---|
| **вышестоящий сервер** (upstream) / **бэкенд** (backend) | Сервер за прокси, который на самом деле отвечает на запрос. Группа одинаковых бэкендов — **пул** (pool; в Envoy он называется *cluster*). |
| **нижестоящая сторона** (downstream) | Клиентская сторона прокси: браузер, `curl` или другой сервис, который отправляет запрос. |
| **маршрут** (route) | Правило, которое говорит, какой пул получает запрос, по имени хоста и пути. |
| **hop-by-hop-заголовок** (hop-by-hop header) | Заголовок, предназначенный только для одного соединения, например `Connection` или `Transfer-Encoding`. Прокси удаляет его и никогда не пересылает. |
| **`X-Forwarded-For`** | Заголовок, в который прокси записывают IP-адрес (Internet Protocol, межсетевой протокол) клиента, чтобы бэкенд знал, кто на самом деле прислал запрос. |
| **активная проверка здоровья** (active health check) | Прокси сам с интервалом отправляет каждому бэкенду запрос (например, `GET /healthz`). |
| **пассивная проверка здоровья** (passive health check) / **обнаружение выбросов** (outlier detection) | Прокси следит за настоящим трафиком и на время убирает бэкенд после нескольких ошибок подряд. |
| **бюджет повторов** (retry budget) | Ограничение повторов долей от всех запросов (например, 10%), чтобы во время сбоя повторы не умножали нагрузку. |
| **идемпотентный метод** (idempotent method) | Метод HTTP, повторение которого даёт тот же эффект, что и один вызов: `GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE`. `POST` — нет. |
| **SNI** (Server Name Indication, указание имени сервера) | Имя хоста, которое клиент TLS (Transport Layer Security, протокол защиты транспортного уровня) отправляет в первом сообщении, чтобы один адрес мог обслуживать несколько сертификатов. |
| **ALPN** (Application-Layer Protocol Negotiation, согласование протокола прикладного уровня) | Расширение TLS, в котором клиент и сервер договариваются о HTTP/1.1 или HTTP/2. |
| **горячая перезагрузка** (hot reload) | Применение новой конфигурации во время работы прокси без потери соединений и запросов. |
| **`ArcSwap`** | Тип из крейта `arc-swap`: `Arc`, который можно атомарно заменить, пока его читают многие потоки, без блокировки. Идеален для «текущей конфигурации». |
| **ведро токенов** (token bucket) | Ограничитель частоты: ведро пополняется токенами с постоянной скоростью; каждый запрос забирает один; при пустом ведре запрос отклоняется (`429`). |
| **slowloris** | Атака, которая открывает много соединений и очень медленно присылает заголовки, чтобы исчерпать соединения сервера. Её останавливает тайм-аут чтения заголовков. |
| **HTTP** (HyperText Transfer Protocol, протокол передачи гипертекста) | Протокол запросов и ответов веба; HTTPS — это HTTP поверх зашифрованного соединения. |
| **JSON** (JavaScript Object Notation, нотация объектов JavaScript) | Текстовый формат структурированных данных, например `{"error":"no route"}`. |
| **CI** (Continuous Integration, непрерывная интеграция) | Сервер, который автоматически запускает ваши проверки при каждой отправке (Урок 09.12). |
| **RFC** (Request for Comments, запрос комментариев) | Здесь: пронумерованный интернет-стандарт, например RFC 9110 о семантике HTTP. |
| **ВМ** (виртуальная машина, VM — Virtual Machine) | Целый компьютер, имитируемый программой; Linux-ВМ курса называется `dev` (Урок 11.1). |

## 1. Что вы строите и почему это важно

Вы строите `proxy` — обратный HTTP-прокси в духе Envoy или Pingora. Он принимает от клиентов HTTP/1.1 и HTTP/2, с TLS или без, выбирает пул по хосту и пути, выбирает здоровый бэкенд алгоритмом балансировки, пересылает запрос и возвращает ответ. Вокруг этого ядра он защищает бэкенды и себя: тайм-ауты, безопасные повторы, проверки здоровья, ограничение частоты, лимиты соединений и конфигурация, которую можно заменить, не потеряв ни одного запроса.

Основу вы уже построили. `p15-lb` копировал байты между соединениями TCP (Transmission Control Protocol, протокол управления передачей); `p22-relay` (в направлении сетей) пересылал HTTP/1.1 по кругу (round robin). Итоговый проект добавляет то, что делает прокси пригодным перед настоящими сервисами:

- **HTTP/2 и TLS** с несколькими сертификатами на одном адресе (SNI) и выбором протокола (ALPN);
- **маршрутизация** по хосту и пути к нескольким пулам с разными алгоритмами;
- **здоровье**: активные проверки и обнаружение выбросов;
- **безопасные повторы** с бюджетом и понятные коды ошибок (`502`, `503`, `504`);
- **горячая перезагрузка** конфигурации, ограничение частоты и API администрирования;
- **числа**: накладные расходы прокси в задержке p50/p99/p99.9 (медиана, 99-й и 99,9-й перцентили, Урок 19.1) и флеймграф, который их объясняет.

Почему это важно: большинство запросов к веб-сервису проходит через несколько прокси — балансировщики нагрузки, API-шлюзы (API, Application Programming Interface, программный интерфейс), sidecar-прокси сервисной сетки. Именно там добавляется задержка, распространяются или останавливаются сбои, применяются правила безопасности. Прокси, который вы построили, измерили и объяснили, показывает, что вы одновременно понимаете сети, конкурентность и производительность.

## 2. Эталонная архитектура

```text
                       proxy.toml --(SIGHUP / file change)--> config loader
                                                                  | validate
                                                                  v
 clients                                                  ArcSwap<Config>
 HTTP/1.1, HTTP/2                                                 | read per request
 TLS (SNI, ALPN)                                                  |
    |      +---------------+    +-------------+    +--------------v----------+
    +----->| listeners     |--->| limits:     |--->| router: host + prefix   |
           | accept, TLS,  |    | conns, rate,|    |   -> route -> pool      |
           | header timeout|    | body size   |    +--------------+----------+
           +---------------+    +-------------+                   |
                                                                  v
                     +-------------------------------------------------------+
                     | upstream pool "api"   algorithm: least_requests        |
                     |   backend A (up)   backend B (up)   backend C (ejected)|
                     |   connection pool per backend, timeouts, retries      |
                     +--------------------------+----------------------------+
                                                ^
                health checker: GET /healthz ---+   outlier detector: errors in a row
 admin API (127.0.0.1:9900): GET /pools, GET /metrics, POST /reload
```

Части и их задачи:

1. **Слушатели** (listeners) принимают соединения, выполняют рукопожатие TLS (выбирая сертификат по SNI и протокол по ALPN) и ограничивают, сколько времени клиент может присылать заголовки.
2. **Лимиты** стоят до любой настоящей работы: максимальное число соединений, ведро токенов на адрес клиента, максимальный размер тела.
3. **Маршрутизатор** находит первый маршрут, чьи хост и префикс пути подходят, а значит и пул.
4. **Пул** выбирает здоровый бэкенд своим алгоритмом, переиспользует соединения с ним, применяет тайм-аут маршрута и повторяет запрос, только когда правила это разрешают.
5. **Проверка здоровья и детектор выбросов** хранят состояние «работает» / «исключён» для каждого бэкенда.
6. **Конфигурация** живёт за `ArcSwap`. Каждый запрос один раз в начале загружает текущую версию и пользуется ею до конца, поэтому перезагрузка никогда не меняет правила посреди запроса.

> ⚡ **Производительность:** задача прокси — добавлять как можно меньше. Измеряйте *накладные расходы*: запустите один и тот же нагрузочный тест один раз напрямую на бэкенд и один раз через прокси и сообщите разницу на p50, p99 и p99.9. Никогда не измеряйте прокси без базовой линии.

## Проект

### Что вы создадите

Рабочее пространство Cargo `code/p23-proxy`:

| Крейт | Вид | Задача |
|---|---|---|
| `proxy-config` | библиотека | типы конфигурации, `load` и проверка (контрактный код ниже) |
| `proxy-core` | библиотека | маршрутизатор, алгоритмы балансировки, логика повторов и здоровья — чистая, без ввода-вывода (I/O, input/output) |
| `proxy` | бинарник | слушатели, TLS, пересылка через `hyper`, API администрирования, сигналы |
| `test-backend` | бинарник | маленький бэкенд для тестов: отвечает своим именем, по команде может быть медленным или падать |

**Не-цели:** никакого кэширования ответов, никаких WebSocket, никакого HTTP/3, никакого динамического обнаружения сервисов (бэкенды берутся из файла конфигурации), никаких скриптовых плагинов в стиле `Lua`.

### Контракт

**Командная строка:**

```text
proxy --config <FILE>            run the proxy
proxy check --config <FILE>      validate the file, print "config ok: …", exit 0; or print the error, exit 1
proxy --version
```

**Файл конфигурации** (TOML, Tom's Obvious Minimal Language — формат `Cargo.toml`). Минимальная форма, которую уже читает M0:

```toml
[[listener]]
address = "127.0.0.1:8080"

[[route]]
host = "api.example.test"
path_prefix = "/v1/"
pool = "api"
timeout_ms = 2000
retries = 1

[[route]]
path_prefix = "/"
pool = "web"

[[pool]]
name = "api"
algorithm = "least_requests"
backends = ["127.0.0.1:9001", "127.0.0.1:9002"]

[[pool]]
name = "web"
algorithm = "round_robin"
backends = ["127.0.0.1:9101"]
```

Следующие вехи добавляют (каждое нужно описать в справочнике по конфигурации в README): записи `tls = { cert = "…", key = "…" }` для слушателя и имени хоста (M4), `[pool.health_check]` с `path`, `interval_ms`, `unhealthy_after`, `healthy_after` (M3), `rate_limit_per_second` для маршрута (M5) и таблицу `[limits]` с `max_connections`, `header_timeout_ms`, `max_body_bytes`, `drain_timeout_ms`.

**Правила пересылки:**

1. **Маршрутизация:** маршруты проверяются в порядке файла; первый маршрут подходит, когда его `host` (если задан) равен хосту запроса без порта, а его `path_prefix` — префикс пути. Нет совпадения: `404`.
2. **Заголовки:** hop-by-hop-заголовки (`Connection`, `Keep-Alive`, `Proxy-Connection`, `TE`, `Trailer`, `Transfer-Encoding`, `Upgrade` и каждый заголовок, названный в `Connection`) удаляются в обоих направлениях. Прокси дописывает адрес клиента в `X-Forwarded-For`, ставит `X-Forwarded-Proto` в `http` или `https` и добавляет `x-request-id`, если у запроса его нет.
3. **Ошибки** имеют маленькое тело JSON `{"error":"…"}`: нет здорового бэкенда — `503`; соединение с бэкендом не удалось после всех повторов — `502`; тайм-аут маршрута — `504`; слишком большое тело — `413`; ограничение частоты — `429` с `Retry-After`; слишком много соединений — соединение закрывается.
4. **Повторы:** только для `GET`, `HEAD` и `OPTIONS`, только если ни один байт ответа ещё не дошёл до клиента, не больше `retries` раз, всегда на *другой* бэкенд и только пока это позволяет бюджет повторов пула (10% его запросов за последние 10 с). (`PUT` и `DELETE` идемпотентны по стандарту HTTP, но прокси не может знать, действительно ли каждый бэкенд реализует их так, поэтому их он тоже не повторяет.)
5. **Здоровье:** бэкенд *недоступен* после `unhealthy_after` неудачных активных проверок и снова *доступен* после `healthy_after` удачных. Пять неудачных запросов подряд исключают его на 30 с. Трафик получают только *доступные* бэкенды.
6. **Перезагрузка:** по `SIGHUP`, изменению файла или `POST /reload` новый файл проверяется. Если он неверен, старая конфигурация остаётся, а ошибка пишется в лог и возвращается. Если верен, новые запросы используют его; запросы в полёте завершаются со старой. Состояние здоровья сохраняется для бэкендов, которые есть в обеих версиях.
7. **Завершение:** по `SIGTERM` или `Ctrl+C` прекратить приём, завершить запросы в полёте (не дольше `drain_timeout_ms`), затем выйти с кодом 0.

**API администрирования** на отдельном адресе (по умолчанию `127.0.0.1:9900`): `GET /pools` → JSON с состоянием каждого бэкенда, запросами в полёте и недавними ошибками; `GET /metrics` → текст Prometheus; `POST /reload` → `200 {"reloaded":true}` или `400 {"error":"…"}`.

**Контракт конфигурации в коде.** M0 начинается с части, от которой зависит всё остальное: чтения и проверки файла. Попробуйте это в учебном пакете:

```bash
cd ~/projects/rust
cargo new code/p23-proxy-config
cd code/p23-proxy-config
cargo add serde@1 --features derive
cargo add toml@1
```

Сохраните файл выше как `proxy.toml` в папке пакета. `src/main.rs`:

```rust
use serde::Deserialize;
use std::collections::HashSet;
use std::net::SocketAddr;

#[derive(Debug, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct Config {
    pub listener: Vec<Listener>,
    pub route: Vec<Route>,
    pub pool: Vec<Pool>,
}

#[derive(Debug, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct Listener {
    pub address: SocketAddr,
}

#[derive(Debug, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct Route {
    /// `None` matches every host.
    pub host: Option<String>,
    pub path_prefix: String,
    pub pool: String,
    #[serde(default = "default_timeout_ms")]
    pub timeout_ms: u64,
    #[serde(default)]
    pub retries: u32,
}

fn default_timeout_ms() -> u64 {
    5_000
}

#[derive(Debug, Deserialize)]
#[serde(rename_all = "snake_case")]
pub enum Algorithm {
    RoundRobin,
    LeastRequests,
    ConsistentHash,
}

#[derive(Debug, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct Pool {
    pub name: String,
    pub algorithm: Algorithm,
    pub backends: Vec<SocketAddr>,
}

/// Parses and checks a configuration. Every error names what is wrong.
pub fn load(text: &str) -> Result<Config, String> {
    let config: Config = toml::from_str(text).map_err(|e| e.to_string())?;
    let pools: HashSet<&str> = config.pool.iter().map(|p| p.name.as_str()).collect();
    for route in &config.route {
        if !pools.contains(route.pool.as_str()) {
            return Err(format!(
                "route {:?} uses unknown pool {:?}",
                route.path_prefix, route.pool
            ));
        }
        if route.timeout_ms == 0 {
            return Err(format!(
                "route {:?}: timeout_ms must be > 0",
                route.path_prefix
            ));
        }
    }
    for pool in &config.pool {
        if pool.backends.is_empty() {
            return Err(format!("pool {:?} has no backends", pool.name));
        }
    }
    Ok(config)
}

fn main() {
    let path = std::env::args().nth(1).unwrap_or_else(|| "proxy.toml".to_string());
    let text = std::fs::read_to_string(&path).expect("cannot read the config file");
    match load(&text) {
        Ok(c) => println!(
            "config ok: {} listener(s), {} route(s), {} pool(s)",
            c.listener.len(),
            c.route.len(),
            c.pool.len()
        ),
        Err(e) => {
            eprintln!("invalid config {path}: {e}");
            std::process::exit(1);
        }
    }
}
```

**Что происходит:**

1. Каждая таблица `[[listener]]`, `[[route]]` и `[[pool]]` в файле становится одним элементом `Vec`. `#[derive(Deserialize)]` из `serde` пишет код чтения за нас.
2. `#[serde(deny_unknown_fields)]` превращает опечатку в ошибку, а не молча пропускает строку. Для прокси это важно: пропущенный `timeout_ms` означал бы, что используется значение по умолчанию, и никто этого не заметит.
3. Адреса читаются сразу в `SocketAddr`, поэтому `"127.0.0.1:99999"` отклоняется ещё при чтении. *Разбирай, а не проверяй* (parse, don't validate; Урок 08.5): после `load` типы гарантируют формат.
4. `#[serde(default = "default_timeout_ms")]` подставляет 5 секунд, если у маршрута нет тайм-аута; `#[serde(default)]` даёт `retries` значение 0.
5. `rename_all = "snake_case"` сопоставляет `"least_requests"` в файле с `Algorithm::LeastRequests`.
6. Затем `load` проверяет то, чего не могут гарантировать одни типы: каждый маршрут называет существующий пул, тайм-ауты положительны, у пулов есть бэкенды.

### Планка качества

| Область | Что это значит здесь |
|---|---|
| Модульные тесты и тесты на основе свойств | табличные тесты маршрутизатора; тесты на основе свойств для балансировки (круговой обход честен при любом числе запросов; исключённые бэкенды никогда не получают трафик) |
| Интеграционные тесты | настоящие процессы `proxy` и `test-backend` на свободных портах для каждой вехи |
| Тесты на сбои | бэкенд убит, медленный, возвращает `500`, закрывает соединение посреди ответа; клиент медленно присылает заголовки |
| Фаззинг | загрузчик конфигурации (`load` никогда не должна паниковать) и ваш код переписывания заголовков |
| Бенчмарки | накладные расходы прокси на фиксированных частотах с `oha`; `criterion` для маршрутизатора и балансировщика |
| Наблюдаемость | журнал доступа с идентификатором запроса, маршрутом, бэкендом, статусом и длительностью; метрики по маршрутам и бэкендам |
| Безопасность | тайм-аут чтения заголовков (slowloris), лимиты на размер заголовков, размер тела и соединения; hop-by-hop-заголовки никогда не пересылаются; API администрирования только на `127.0.0.1` |

> 🔒 **Безопасность:** прокси — первая программа, с которой говорит злоумышленник. Никогда не доверяйте `X-Forwarded-For` от клиента как адресу клиента (его может отправить кто угодно); дописывайте в него, а для ограничения частоты используйте настоящий адрес соседа. Отклоняйте запросы, которые `hyper` считает неверно сформированными, а не пытайтесь их «починить».

### Дополнительные цели

- **Обновление бинарника без простоя:** запустить новую версию, передать ей слушающие сокеты (или использовать `SO_REUSEPORT`), дать старой завершить работу.

## Частые ошибки

**1. Повторять `POST`.** Бэкенд мог обработать его до обрыва соединения; повтор создаёт второй заказ. Правило 4 разрешает повторы только для `GET`, `HEAD` и `OPTIONS`.

**2. Повторы без бюджета.** Во время сбоя каждый запрос пробуют два или три раза, и оставшиеся бэкенды получают в два-три раза больше нагрузки — сбой распространяется. Исправление: бюджет повторов.

**3. Пересылать hop-by-hop-заголовки.** Пересланные `Connection: close` или `Transfer-Encoding` путают соединение с бэкендом и могут открыть дорогу контрабанде запросов (request smuggling). Исправление: правило 2, с тестом.

**4. Держать блокировку через `.await`.** `std::sync::Mutex` вокруг списка бэкендов, удерживаемый во время пересылки запроса, выстраивает весь трафик в одну очередь. Исправление: читайте снимок состояния через `Arc` и отпускайте все guard-объекты до ожидания.

**5. Все проверки здоровья в один момент.** Сто бэкендов, проверяемых ровно в одно и то же время каждую секунду, создают всплески. Исправление: добавьте к интервалу джиттер.

**6. Измерять без базовой линии.** «p99 равно 4 мс» ничего не говорит о прокси, если у самого бэкенда p99 уже 3,9 мс. Исправление: всегда сравнение с прямым обращением к бэкенду.

### Упражнение 1 — Какой пул? (легко)

С `proxy.toml` из этого урока и правилом 1: какой пул (или какой код статуса) получает каждый запрос? (a) `GET http://api.example.test/v1/users` (b) `GET http://api.example.test:8080/health` (c) `GET http://shop.example.test/v1/users` (d) `POST http://api.example.test/v1` (без косой черты в конце).

<details>
<summary>Подсказка</summary>

Хост сравнивается без порта. У префикса `/v1/` в конце есть косая черта. У второго маршрута нет хоста, поэтому он подходит для любого хоста.

</details>

<details>
<summary>Ответ</summary>

(a) `api`: хост совпадает, а `/v1/users` начинается с `/v1/`. (b) `web`: хост (без `:8080`) совпадает, но `/health` не начинается с `/v1/`; второй маршрут подходит для всего. (c) `web`: первый маршрут требует хост `api.example.test`. (d) `web`: `/v1` не начинается с `/v1/`. ### Упражнение 2 — Напишите тесты для проверки (средне)

Добавьте в `src/main.rs` тестовый модуль с тремя тестами: маршрут к неизвестному пулу отклоняется с точным сообщением, пул без бэкендов отклоняется, а маршрут без `timeout_ms` получает 5 000 мс. Собирайте текст TOML внутри тестов.

<details>
<summary>Подсказка</summary>

Сырая строка `r#"…"#` может содержать кавычки. Держите слушатель и маршрут в одной константе, а пулы добавляйте маленькой вспомогательной функцией, чтобы каждый тест показывал только то, что в нём особенного. Помните, что `pool` — обязательное поле: файл без единого `[[pool]]` падает ещё при разборе, а не в вашей проверке.

</details>

<details>
<summary>Ответ</summary>

```rust
#[cfg(test)]
mod tests {
    use super::*;

    /// A listener and one route to the pool "web"; each test adds pools.
    const ROUTE_TO_WEB: &str = r#"
[[listener]]
address = "127.0.0.1:8080"

[[route]]
path_prefix = "/"
pool = "web"
"#;

    fn pool(name: &str, backends: &str) -> String {
        format!(
            "[[pool]]\nname = \"{name}\"\nalgorithm = \"round_robin\"\nbackends = [{backends}]\n"
        )
    }

    #[test]
    fn a_route_to_an_unknown_pool_is_rejected() {
        let text = format!("{ROUTE_TO_WEB}{}", pool("api", r#""127.0.0.1:9001""#));
        assert_eq!(
            load(&text).unwrap_err(),
            r#"route "/" uses unknown pool "web""#
        );
    }

    #[test]
    fn a_pool_without_backends_is_rejected() {
        let text = format!("{ROUTE_TO_WEB}{}", pool("web", ""));
        assert_eq!(load(&text).unwrap_err(), r#"pool "web" has no backends"#);
    }

    #[test]
    fn the_default_timeout_is_five_seconds() {
        let text = format!("{ROUTE_TO_WEB}{}", pool("web", r#""127.0.0.1:9101""#));
        let config = load(&text).unwrap();
        assert_eq!(config.route[0].timeout_ms, 5_000);
    }
}
```

```text
running 3 tests
...
test result: ok. 3 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Почему это работает: каждый тест собирает самый маленький файл, который показывает одно правило, и сравнивает сообщение об ошибке целиком, поэтому изменённое сообщение будет замечено (эти сообщения читают пользователи и скрипты).

</details>

### Упражнение 3 — Повторяющиеся имена пулов, сначала тест (средне)

Две таблицы `[[pool]]` с одинаковым `name` сейчас принимаются, и никто не знает, какую использует маршрут. Напишите тест `two_pools_with_the_same_name_are_rejected` (ожидаемое сообщение: `pool "web" is defined twice`), посмотрите, как он падает, затем измените `load`.

<details>
<summary>Подсказка</summary>

`HashSet::insert` возвращает `false`, если значение уже было. Стройте множество имён пулов циклом вместо `collect` и остановитесь на первом повторе.

</details>

<details>
<summary>Ответ</summary>

Тест, в модуле из Упражнения 2:

```rust
#[test]
fn two_pools_with_the_same_name_are_rejected() {
    let web = pool("web", r#""127.0.0.1:9101""#);
    let text = format!("{ROUTE_TO_WEB}{web}{web}");
    assert_eq!(load(&text).unwrap_err(), r#"pool "web" is defined twice"#);
}
```

До изменения `load` возвращает `Ok`, и тест падает с:

```text
called `Result::unwrap_err()` on an `Ok` value: Config { listener: [Listener { address: 127.0.0.1:8080 }], route: [Route { host: None, path_prefix: "/", pool: "web", timeout_ms: 5000, retries: 0 }], pool: [Pool { name: "web", algorithm: RoundRobin, backends: [127.0.0.1:9101] }, Pool { name: "web", algorithm: RoundRobin, backends: [127.0.0.1:9101] }] }
```

В `load` замените строку, которая строит `pools`, на:

```rust
let mut pools = HashSet::new();
for pool in &config.pool {
    if !pools.insert(pool.name.as_str()) {
        return Err(format!("pool {:?} is defined twice", pool.name));
    }
}
```

Почему это работает: цикл строит то же множество, что и раньше, но замечает момент, когда имя вставляется второй раз. Все четыре теста проходят.

</details>

### Упражнение 4 — Повторы и бюджет (сложно)

Пул из трёх бэкендов получает 1 000 запросов `GET` в секунду; у каждого маршрута `retries = 2`. Один бэкенд начинает отвечать ошибкой на каждый запрос. (a) Без бюджета повторов сколько запросов в секунду получают два здоровых бэкенда вместе, пока обнаружение выбросов не исключило плохой? (b) С бюджетом 10%? (c) Почему бюджет ещё важнее, когда перегружены *все* бэкенды?

<details>
<summary>Подсказка</summary>

Примерно треть запросов сначала попадает на плохой бэкенд. Каждый из них повторяется на другом бэкенде. При перегрузке повтор — ещё один запрос к серверу, который и так слишком медленный.

</details>

<details>
<summary>Ответ</summary>

(a) Около 667 запросов в секунду идут прямо на два хороших бэкенда, около 333 — сначала на плохой; каждый из них падает и повторяется на *другом* бэкенде (правило 4), то есть на хорошем. Поэтому хорошие бэкенды получают около 667 + 333 = 1 000 запросов в секунду, а плохой — 333; общая нагрузка на бэкенды — 1 333 (на треть больше). Если бы повтор мог снова попасть на плохой бэкенд, часть запросов использовала бы и второй повтор. (b) С бюджетом 10% разрешено не больше 100 повторов в секунду: хорошие бэкенды получают около 767 в секунду, а около 233 запросов в секунду падают с `502`, пока плохой бэкенд не исключён. (c) Когда все бэкенды медленные из-за перегрузки, повторы добавляют нагрузку именно там, где нет запаса мощности; это делает их ещё медленнее, что вызывает больше тайм-аутов и больше повторов — *шторм повторов* (retry storm). Бюджет ограничивает эту петлю обратной связи. Поэтому Envoy и другие прокси используют бюджеты повторов, и поэтому ваш проектный документ должен назвать свой.

</details>

## Вопросы для самопроверки

1. Что такое нижестоящая (downstream) и вышестоящая (upstream) стороны прокси?

<details>
<summary>Ответ</summary>

Нижестоящая — сторона клиентов (кто отправляет запросы прокси); вышестоящая — сторона бэкендов (серверы, которым прокси пересылает запросы).

</details>

2. Почему прокси удаляет hop-by-hop-заголовки?

<details>
<summary>Ответ</summary>

Они описывают только одно соединение (например, `Connection` или `Transfer-Encoding`). Пересланные, они описывали бы не то соединение, путали бы бэкенд и могли бы сделать возможной контрабанду запросов.

</details>

3. Какие запросы прокси может повторять и при каких условиях?

<details>
<summary>Ответ</summary>

Только `GET`, `HEAD` и `OPTIONS`; только если ни один байт ответа ещё не дошёл до клиента; не больше `retries` раз; на другой бэкенд; и только пока это разрешает бюджет повторов.

</details>

4. Что делают SNI и ALPN в M4?

<details>
<summary>Ответ</summary>

SNI говорит прокси, какое имя хоста нужно клиенту, чтобы на общем адресе выбрать правильный сертификат. ALPN позволяет клиенту и прокси договориться о HTTP/2 или HTTP/1.1 во время рукопожатия TLS.

</details>

5. Почему каждый запрос загружает конфигурацию из `ArcSwap` один раз, в начале?

<details>
<summary>Ответ</summary>

Чтобы перезагрузка никогда не меняла правила посреди запроса. Запрос держит свой `Arc` на старую конфигурацию до конца; новые запросы видят новую.

</details>

6. Почему результаты производительности должны сравнивать «через прокси» и «напрямую на бэкенд»?

<details>
<summary>Ответ</summary>

Потому что собственная стоимость прокси — это разница. Число для всего пути смешивает задержку бэкенда с задержкой прокси.

</details>

7. Почему `#[serde(deny_unknown_fields)]` важен для конфигурации прокси?

<details>
<summary>Ответ</summary>

Без него ключ с опечаткой пропускается и молча используется значение по умолчанию, например отсутствующий тайм-аут. С ним `proxy check` и перезагрузки отклоняют файл и говорят, какой ключ неверен.

</details>

## Итоги

- Вариант 2 — обратный прокси HTTP/1.1 и HTTP/2 с TLS (SNI, ALPN), маршрутизацией, пулами с балансировкой, проверками здоровья, безопасными повторами, ограничением частоты, горячей перезагрузкой и API администрирования.
- Архитектура разделяет слушатели, лимиты, чистый маршрутизатор и балансировщик, пулы бэкендов, состояние здоровья и конфигурацию за `ArcSwap`.
- Контракт фиксирует командную строку, файл конфигурации, семь правил пересылки и API администрирования; загрузчик конфигурации со строгим разбором и проверкой — первый код, который вы пишете.
- Вехи: M0 `proxy check`, M1 пересылка HTTP/1.1, M2 маршрутизация и HTTP/2, M3 здоровье, тайм-ауты и повторы, M4 TLS, M5 перезагрузка и ограничение частоты, M6 производительность и эксплуатация.

## Источники и что почитать

- [RFC 9110 — HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110) — методы и идемпотентность, коды статуса, `Connection` и правила для посредников вроде прокси.
- [RFC 9112 — HTTP/1.1](https://www.rfc-editor.org/rfc/rfc9112) — границы сообщений, `Content-Length` и `Transfer-Encoding` и почему неоднозначные границы нужно отклонять.
- [hyper](https://hyper.rs/) — библиотека HTTP под большинством прокси на Rust; руководства для клиентов и серверов.
- [Документация rustls](https://docs.rs/rustls/latest/rustls/) — конфигурация сервера, резолверы сертификатов и ALPN.
- [Документация arc-swap](https://docs.rs/arc-swap/latest/arc_swap/) — шаблон «очень часто читать текущую конфигурацию, редко заменять».
- [Атрибуты serde](https://serde.rs/attributes.html) и [документация toml](https://docs.rs/toml/latest/toml/) — `deny_unknown_fields`, значения по умолчанию и переименование, использованные в коде конфигурации.
