# Урок 17.1 — Как работают диски и файлы

> **Этап 17 — Как устроены хранилища и базы данных** · Урок 1 из 15 · ⏱ около 120 минут

## Что вы узнаете

- Какие слои лежат между вашим вызовом `write` и устройством хранения и где данные ждут по пути.
- Как жёсткий диск и SSD хранят данные и почему оба работают с целыми блоками, а не с отдельными байтами.
- Что такое задержка и пропускная способность и почему *случайный* доступ намного медленнее *последовательного*.
- Как измерить настоящий SSD из Rust так, чтобы страничный кэш не мешал.
- Почему движки хранения дописывают данные в журналы, используют страницы фиксированного размера и пишут большими кусками.

## Новые слова

| Слово | Значение |
|---|---|
| **устройство хранения** (storage device) | Оборудование, которое хранит данные при выключенном питании: жёсткий диск или SSD. |
| **HDD** (Hard Disk Drive, жёсткий диск) | Устройство хранения с вращающимися магнитными пластинами и подвижным рычагом, который их читает и записывает. |
| **SSD** (Solid-State Drive, твердотельный накопитель) | Устройство хранения из микросхем флеш-памяти, без движущихся частей. В вашем Mac стоит именно он. |
| **NVMe** (Non-Volatile Memory Express) | Быстрый способ, которым современные SSD общаются с компьютером, через PCIe (Peripheral Component Interconnect Express, внутреннюю скоростную шину). «Non-volatile» значит «энергонезависимая»: хранит данные без питания. |
| **сектор / блок** (sector / block) | Самая маленькая единица, которую устройство читает или записывает: обычно 512 байт или 4 КиБ. Файловая система тоже использует блоки, обычно по 4 КиБ. |
| **флеш-страница / блок стирания** (flash page / erase block) | Внутри SSD данные записываются флеш-страницами (несколько КиБ), а стереть их можно только гораздо более крупными блоками стирания (много страниц). |
| **FTL** (Flash Translation Layer, слой трансляции флеш-памяти) | Программа внутри SSD, которая сопоставляет номера блоков, которыми пользуется компьютер, с реальными местами в микросхемах флеш-памяти. |
| **задержка** (latency) | Сколько длится одна операция, от запроса до ответа. Измеряется в микросекундах (мкс) или миллисекундах (мс). |
| **пропускная способность** (throughput) | Сколько данных проходит за секунду, например 2000 МиБ/с (мебибайт в секунду). |
| **IOPS** (Input/Output Operations Per Second, операций ввода-вывода в секунду) | Сколько отдельных чтений или записей устройство выполняет за секунду. |
| **последовательный / случайный доступ** (sequential / random access) | Чтение или запись соседних блоков один за другим / переходы к блокам по всему устройству. |
| **чтение-изменение-запись** (read-modify-write) | Чтобы изменить часть блока, система должна прочитать весь блок, изменить его в памяти и записать весь блок обратно. |
| **усиление записи** (write amplification) | Когда устройство записывает больше байтов, чем попросила программа, например целый блок 4 КиБ ради одного изменённого байта. |

## 1. Путь от `write` до устройства

Когда программа вызывает `write`, байты не летят прямо в SSD. Они проходят несколько слоёв, и в большинстве
из них могут подождать:

```text
 your program      Vec<u8>, String        ← your memory
      │
 BufWriter         8 KiB buffer           ← still your memory (Rust std)
      │  write() system call
 kernel            page cache             ← RAM owned by the kernel
      │  later, or on fsync
 file system       blocks, inodes, journal
      │
 device driver     NVMe commands
      │
 SSD controller    small RAM write cache  ← inside the device!
      │
 flash chips       data survives power loss
```

Среднюю часть вы уже знаете. Из Урока 13.11: `write` возвращается, как только данные оказались в страничном кэше.
Из Урока 13.12: ядро записывает «грязные» страницы на устройство позже, а `fsync` ждёт, пока они там окажутся.

Два слоя новые. Наверху `BufWriter` (из стандартной библиотеки Rust) собирает мелкие записи в вашей собственной
памяти, чтобы программа делала меньше системных вызовов. Внизу у самого устройства есть небольшой кэш. Что это
значит для надёжности, покажет следующий урок. Этот урок — о **скорости**: каждый слой существует потому, что слой
под ним медленный.

Первый слой легко измерить. Поместите это в `src/bin/small_writes.rs`:

```rust
use std::fs::File;
use std::io::{BufWriter, Write};
use std::time::Instant;

const COUNT: usize = 100_000;
const RECORD: &[u8] = b"key=value;12345\n"; // 16 bytes

fn main() -> std::io::Result<()> {
    // 1. One write system call per record.
    let start = Instant::now();
    let mut file = File::create("direct.log")?;
    for _ in 0..COUNT {
        file.write_all(RECORD)?;
    }
    println!("unbuffered: {:?}", start.elapsed());

    // 2. BufWriter collects records in an 8 KiB buffer and writes it in big pieces.
    let start = Instant::now();
    let mut file = BufWriter::new(File::create("buffered.log")?);
    for _ in 0..COUNT {
        file.write_all(RECORD)?;
    }
    file.flush()?;
    println!("buffered:   {:?}", start.elapsed());

    std::fs::remove_file("direct.log")?;
    std::fs::remove_file("buffered.log")?;
    Ok(())
}
```

**Что происходит:**

1. У `File` нет собственного буфера: каждый `write_all` превращается в один системный вызов `write`, всего 100 000.
2. `BufWriter::new` оборачивает файл буфером на 8 КиБ. `write_all` копирует 16 байт в буфер; только когда буфер
   заполнен, делается один системный вызов на 8 КиБ. Это около 200 системных вызовов вместо 100 000.
3. `flush` записывает то, что осталось в буфере. Без него последняя часть записалась бы только при удалении
   `BufWriter` (drop), а ошибка в этот момент была бы проигнорирована.
4. Обе версии доходят только до страничного кэша. Данные пока не обязаны быть на SSD.

Запустите `cargo run --release --bin small_writes`:

```text
unbuffered: 470.717958ms
buffered:   1.537375ms
```

Те же 1,6 МБ (мегабайта) данных, примерно в 300 раз быстрее. Здесь каждый системный вызов стоит около 4–5 мкс (ядро должно
проверить дескриптор, найти страницы в страничном кэше и скопировать данные), и буферизованная версия платит эту цену в
500 раз реже. Ваши числа будут другими, но соотношение будет похожим.

> ⚡ **Производительность:** системный вызов дёшев по сравнению с диском, но дорог по сравнению с копированием 16 байт.
> Если программа пишет много мелких кусков, оберните файл в `BufWriter`. Движки хранения идут дальше и
> собирают в памяти целые блоки, прежде чем что-то записать.

## 2. Два вида устройств

**Жёсткий диск (HDD)** похож на проигрыватель пластинок. Данные лежат по кругам (дорожкам) на вращающихся пластинах, а
рычаг с головкой чтения-записи движется над ними. Чтобы прочитать блок, рычаг сначала должен переместиться на нужную
дорожку (*поиск*, seek), а затем подождать, пока пластина повернёт блок под головку. И то, и другое — механика, поэтому
занимает миллисекунды. После этого следующие блоки на той же дорожке читаются быстро: они просто проходят под головкой.

**У SSD** нет движущихся частей. Он хранит биты как электрический заряд в микросхемах флеш-памяти. До любого блока можно
добраться за десятки микросекунд. Но у флеш-памяти два странных правила:

1. Записать **флеш-страницу** (несколько КиБ) можно, только когда она пуста. Перезаписать её нельзя.
2. Очищать страницы можно только большими группами, **блоками стирания** (часто по несколько МиБ), и каждый блок
   выдерживает ограниченное число стираний.

Поэтому SSD никогда не меняет данные на месте. Когда вы перезаписываете блок 1000, **FTL** (слой трансляции флеш-памяти),
маленькая программа внутри SSD, пишет новые данные в какую-нибудь пустую страницу и запоминает: «блок 1000 теперь живёт
здесь». Старая страница становится мусором. Позже SSD копирует ещё нужные страницы из блока стирания, где почти всё —
мусор, и стирает его. Это копирование — разновидность **усиления записи**: устройство записывает больше, чем вы просили.

```text
                        HDD                          SSD (NVMe)
smallest unit           sector, 512 B or 4 KiB       flash page, 4–16 KiB
random 4 KiB read       5–10 ms (seek + rotation)    20–200 µs
sequential throughput   100–250 MB/s                 2,000–7,000 MB/s
overwrite in place      yes                          no (FTL writes elsewhere)
```

Это типичные значения, а не точные. Важна форма: HDD примерно в 100 раз быстрее при последовательном доступе, чем при
случайном, а SSD всё ещё в несколько раз быстрее при последовательном, что вы измерите в разделе 4.

## 3. Всё происходит блоками

Ни одно устройство не умеет хранить один байт. Устройство работает **секторами** (512 байт или 4 КиБ), а файловая система
поверх него — **блоками**, обычно по 4 КиБ. Файл всегда занимает целые блоки. Поместите это в `src/bin/blocks.rs`:

```rust
use std::fs;
use std::os::unix::fs::MetadataExt;

fn main() -> std::io::Result<()> {
    fs::write("one-byte.txt", b"x")?;
    fs::write("five-thousand.txt", vec![b'a'; 5000])?;

    for name in ["one-byte.txt", "five-thousand.txt"] {
        let meta = fs::metadata(name)?;
        println!(
            "{name}: len = {} bytes, on disk = {} bytes, block size = {}",
            meta.len(),
            meta.blocks() * 512,
            meta.blksize()
        );
    }

    fs::remove_file("one-byte.txt")?;
    fs::remove_file("five-thousand.txt")?;
    Ok(())
}
```

**Что происходит:**

1. `MetadataExt` (только Unix) даёт сырые поля `stat`, с которыми вы познакомились в Уроке 13.12.
2. `blocks()` считает единицы по 512 байт, каким бы ни был настоящий размер блока, поэтому мы умножаем на 512.
3. `blksize()` — размер блока, который файловая система рекомендует для эффективного чтения и записи.

`cargo run --release --bin blocks` на Mac (файловая система APFS, Apple File System):

```text
one-byte.txt: len = 1 bytes, on disk = 4096 bytes, block size = 4096
five-thousand.txt: len = 5000 bytes, on disk = 8192 bytes, block size = 4096
```

Один байт занимает целый блок 4 КиБ; 5000 байт занимают два блока. Файловая система ext4 на Linux даёт ту же картину.

Блоки объясняют и один дорогой сценарий. Если программа меняет 10 байт в середине файла, ядру нужна вся страница
4 КиБ в страничном кэше. Если страницы там нет, ядро сначала **читает** её с устройства, затем **изменяет** 10 байт в
памяти и позже **записывает** всю страницу обратно. Это **чтение-изменение-запись**:

```text
want: change bytes 5000..5010

  device block 1 (bytes 4096..8191)
  ┌──────────────────────────────┐
  │ read all 4096 bytes  ────────┼──► page cache: change 10 bytes
  │ write all 4096 bytes ◄───────┼─── (later, or on fsync)
  └──────────────────────────────┘
```

База данных, которая меняет мелкие записи на месте, постоянно платит эту цену. Поэтому все подходы на этом
этапе либо дописывают в конец (никогда не меняют старые байты), либо держат данные в страницах, размер которых равен
размеру блока.

## 4. Последовательное и случайное чтение: измеряем

Измерить устройство непросто: страничный кэш отвечает из RAM (Random Access Memory, оперативная память) всякий раз, когда может. Файл, который вы только что
записали, всё ещё в кэше, и его чтение ничего не говорит об SSD. В macOS есть флаг для одного файлового дескриптора,
`F_NOCACHE`, который говорит ядру не держать данные файла в страничном кэше. В стандартной библиотеке Rust для него нет
метода, поэтому мы вызываем функцию C `fcntl` (file control, управление файлом) из крейта `libc`. Поместите это в
`src/bin/seq_vs_random.rs`:

```rust
use std::fs::{self, File};
use std::io::Write;
use std::os::unix::fs::FileExt;
use std::time::Instant;

const FILE_SIZE: u64 = 256 * 1024 * 1024; // 256 MiB
const BLOCK: usize = 4096; // read 4 KiB at a time
const READS: u64 = 4096; // 4096 reads x 4 KiB = 16 MiB

/// A tiny pseudo-random number generator (xorshift). Good enough to pick offsets.
fn next_random(state: &mut u64) -> u64 {
    *state ^= *state << 13;
    *state ^= *state >> 7;
    *state ^= *state << 17;
    *state
}

/// Asks macOS not to keep this file's data in the page cache, so that reads go to the SSD.
#[cfg(target_os = "macos")]
fn bypass_page_cache(file: &File) {
    use std::os::fd::AsRawFd;
    // SAFETY: fcntl with F_NOCACHE only sets a flag on a descriptor that we own and that is open.
    let result = unsafe { libc::fcntl(file.as_raw_fd(), libc::F_NOCACHE, 1) };
    assert_ne!(result, -1, "F_NOCACHE failed");
}

#[cfg(not(target_os = "macos"))]
fn bypass_page_cache(_file: &File) {
    eprintln!("note: page cache not bypassed on this system; reads may come from RAM");
}

fn main() -> std::io::Result<()> {
    // 1. Create the test file once: 256 MiB of bytes.
    let mut out = File::create("big.bin")?;
    bypass_page_cache(&out);
    let chunk = vec![7u8; 1024 * 1024];
    for _ in 0..FILE_SIZE / chunk.len() as u64 {
        out.write_all(&chunk)?;
    }
    out.sync_all()?;
    drop(out);

    let file = File::open("big.bin")?;
    bypass_page_cache(&file);
    let mut buf = vec![0u8; BLOCK];
    let blocks_in_file = FILE_SIZE / BLOCK as u64;

    // 2. Sequential: block 0, 1, 2, ...
    let start = Instant::now();
    for i in 0..READS {
        file.read_exact_at(&mut buf, i * BLOCK as u64)?;
    }
    let seq = start.elapsed();

    // 3. Random: blocks in a random order all over the file.
    let mut state = 42;
    let start = Instant::now();
    for _ in 0..READS {
        let block = next_random(&mut state) % blocks_in_file;
        file.read_exact_at(&mut buf, block * BLOCK as u64)?;
    }
    let random = start.elapsed();

    println!("sequential: {READS} reads in {seq:?} ({:?} per read)", seq / READS as u32);
    println!("random:     {READS} reads in {random:?} ({:?} per read)", random / READS as u32);
    fs::remove_file("big.bin")?;
    Ok(())
}
```

**Что происходит:**

1. `next_random` — это *xorshift*, классический генератор из трёх строк. Для безопасности он не годится, но хорошо
   разбрасывает смещения и при каждом запуске даёт одну и ту же последовательность, так что запуски можно сравнивать.
   Крейт не нужен.
2. `#[cfg(target_os = "macos")]` компилирует первую `bypass_page_cache` только на macOS; на других системах
   компилируется вторая версия, которая лишь печатает замечание. На Linux вы бы использовали `O_DIRECT`, которому нужны
   особым образом выровненные буферы; это за рамками урока.
3. Блок `unsafe` нужен потому, что `fcntl` — функция C: компилятор не может её проверить. Наше обещание (оно записано в
   комментарии `SAFETY:`) — дескриптор открыт, а эта команда `fcntl` не трогает память.
4. Мы ставим `F_NOCACHE` уже **во время записи** файла. Иначе его страницы остались бы в кэше после записи, и чтения
   всё равно шли бы из RAM.
5. `read_exact_at` (из `FileExt`) читает по заданному смещению, не сдвигая смещение файла: это системный вызов `pread`.
   Он удобен, когда вы прыгаете по файлу.
6. Последовательные чтения берут блоки 0, 1, 2, … Случайные выбирают 4096 случайных блоков из всех 65 536.

`cargo run --release --bin seq_vs_random` (программа записывает и удаляет файл на 256 МиБ):

```text
sequential: 4096 reads in 182.11775ms (44.462µs per read)
random:     4096 reads in 502.914791ms (122.781µs per read)
```

Второй запуск на том же Mac дал 57 мкс и 223 мкс. Измерения устройства зашумлены, потому что им пользуются и другие
программы. Но результат ясен: на SSD случайное чтение стоит примерно **в три раза** дороже последовательного. SSD и
операционная система замечают последовательный шаблон и читают наперёд; случайные чтения предсказать нельзя. На HDD
разница была бы ближе к сотне раз, потому что каждое случайное чтение требует поиска.

Размер каждого чтения важен ещё больше. Программа `src/bin/block_sizes.rs` из упражнения 3 читает 32 МиБ в случайном
порядке кусками разного размера. Один запуск дал:

```text
random reads of    4096 bytes:     11 MiB/s
random reads of   16384 bytes:    100 MiB/s
random reads of   65536 bytes:    359 MiB/s
random reads of 1048576 bytes:   2341 MiB/s
```

У каждого чтения есть постоянная цена (системный вызов, команда устройству, ожидание флеш-памяти), поэтому прочитать
1 МиБ за раз в пересчёте на байт более чем в сто раз быстрее, чем читать его кусками по 4 КиБ.

> ⚠️ **Частая ошибка:** измерять файл, который всё ещё в страничном кэше. Если убрать оба вызова `bypass_page_cache`,
> каждое чтение займёт меньше 1 мкс, и «случайное» будет выглядеть почти таким же быстрым, как «последовательное». Это
> скорость RAM, а не SSD (упражнение 2).

## 5. Что из этого следует для движков хранения

Всё дальнейшее на этом этапе вытекает из четырёх фактов, которые вы сейчас увидели:

| Факт | Что делают движки хранения |
|---|---|
| Системные вызовы стоят микросекунды | Собирают много мелких изменений в памяти, затем записывают их одним вызовом. |
| Устройства работают блоками | Хранят данные в **страницах** по 4, 8 или 16 КиБ и читают или пишут целые страницы (B-деревья, Урок 17.6). |
| Случайный доступ медленный, последовательный быстрый | **Дописывают** в конец файла, вместо того чтобы менять старые байты (WAL, журнал упреждающей записи, в Уроке 17.4, журналы в Уроках 17.5 и 17.7). |
| Большие чтения и записи дешевле в пересчёте на байт | Записывают большие отсортированные файлы за один раз и сливают их большими кусками (Уроки 17.7 и 17.8). |

Есть ещё один факт, самый важный, и скоростью его не измерить: данные в любом кэше могут пропасть. Об этом
Урок 17.2.

## Частые ошибки

1. **Бенчмарк отладочной сборки.** `cargo run` без `--release` собирает код без оптимизаций. Для программ ввода-вывода
   (I/O, Input/Output) лишнее время уходит в основном на ваш код, а не на устройство, поэтому числа врут.
2. **Измерять кэш, а не устройство.** См. предупреждение в разделе 4. Файл, который вы только что записали или
   прочитали, лежит в страничном кэше.
3. **Забыть `flush` у `BufWriter`.** Последние байты остаются в буфере, пока `BufWriter` не удалён, а ошибка во время
   этого удаления игнорируется. Вызывайте `flush()` (или `into_inner()`) и обрабатывайте его `Result`.
4. **Доверять одному запуску.** Тем же SSD пользуются другие программы. Запускайте измерение несколько раз и смотрите
   на разброс, как в [Уроке 09.11 — Бенчмарки подробно](../09-testing-debugging-benchmarking/11-benchmarking-in-depth.md).

## Упражнения

### Упражнение 1 — Сколько страниц затрагивает запись? (легко)

Напишите `pub fn pages_touched(offset: u64, len: u64, page_size: u64) -> u64` в `src/lib.rs`. Функция возвращает,
сколько страниц по `page_size` байт затрагивает запись `len` байт по смещению `offset` (каждая из них — возможное
чтение-изменение-запись). Напишите тест хотя бы с такими случаями: запись 4096 байт по смещению 0 затрагивает
1 страницу; 2 байта по смещению 4095 — 2 страницы; 10 000 байт по смещению 100 — 3 страницы; 0 байт — 0 страниц.

<details>
<summary>Подсказка</summary>

Вычислите номер первой страницы (`offset / page_size`) и страницы, где лежит *последний* байт
(`(offset + len - 1) / page_size`). Случай `len == 0` обработайте отдельно, иначе `len - 1` уйдёт ниже нуля.

</details>

<details>
<summary>Ответ</summary>

```rust
/// Returns how many pages of `page_size` bytes a write of `len` bytes at `offset` touches.
pub fn pages_touched(offset: u64, len: u64, page_size: u64) -> u64 {
    if len == 0 {
        return 0;
    }
    let first = offset / page_size;
    let last = (offset + len - 1) / page_size;
    last - first + 1
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn counts_pages() {
        assert_eq!(pages_touched(0, 4096, 4096), 1);
        assert_eq!(pages_touched(4095, 2, 4096), 2);
        assert_eq!(pages_touched(100, 10_000, 4096), 3);
        assert_eq!(pages_touched(8192, 1, 4096), 1);
        assert_eq!(pages_touched(5, 0, 4096), 0);
    }
}
```

`cargo test --lib`:

```text
running 1 test
test tests::counts_pages ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Почему это работает: последний байт записи находится по смещению `offset + len - 1`. Затронута каждая страница от
первой до страницы этого байта. Байты 100..10 100 лежат в страницах 0, 1 и 2.

</details>

### Упражнение 2 — Измерьте вместо этого кэш (средне)

Скопируйте `seq_vs_random.rs` в `src/bin/cached.rs` и удалите оба вызова `bypass_page_cache` (и обе функции, чтобы
`cargo clippy` не предупреждал о неиспользуемом коде). Предскажите результат, затем запустите. Что вы теперь измеряете?

<details>
<summary>Подсказка</summary>

Файл только что записан, поэтому все 256 МиБ, скорее всего, всё ещё в страничном кэше.

</details>

<details>
<summary>Ответ</summary>

Один запуск на тестовом Mac:

```text
sequential: 4096 reads in 2.272916ms (554ns per read)
random:     4096 reads in 3.391375ms (827ns per read)
```

Оба варианта быстрее 1 мкс на чтение, примерно в сто раз быстрее SSD. Каждый `read_exact_at` теперь — это системный
вызов плюс копирование 4 КиБ из страничного кэша, то есть из RAM. SSD вообще не используется. Поэтому бенчмарки баз
данных всегда указывают, помещались ли данные в память.

</details>

### Упражнение 3 — Чтения покрупнее (сложно)

Напишите `src/bin/block_sizes.rs`: программа создаёт тот же файл на 256 МиБ в обход кэша, затем для каждого размера
чтения 4 КиБ, 16 КиБ, 64 КиБ и 1 МиБ читает 32 МиБ по случайным смещениям, выровненным по блоку, и печатает пропускную
способность в МиБ/с. Объясните результат.

<details>
<summary>Подсказка</summary>

Оставьте `next_random`, обе функции `bypass_page_cache` и код, создающий файл. Для каждого размера число чтений равно
`32 MiB / size`, а число блоков в файле — `FILE_SIZE / size`. Пропускная способность — `32.0 / seconds`.

</details>

<details>
<summary>Ответ</summary>

Замените всё в `main` после `drop(out);` и до `fs::remove_file` этим циклом (и удалите константы `BLOCK` и `READS`):

```rust
    let file = File::open("big.bin")?;
    bypass_page_cache(&file);
    let total: u64 = 32 * 1024 * 1024; // read 32 MiB in every test
    for block in [4096usize, 16 * 1024, 64 * 1024, 1024 * 1024] {
        let mut buf = vec![0u8; block];
        let reads = total / block as u64;
        let blocks_in_file = FILE_SIZE / block as u64;
        let mut state = 42;
        let start = Instant::now();
        for _ in 0..reads {
            let n = next_random(&mut state) % blocks_in_file;
            file.read_exact_at(&mut buf, n * block as u64)?;
        }
        let secs = start.elapsed().as_secs_f64();
        let mib_per_sec = total as f64 / (1024.0 * 1024.0) / secs;
        println!("random reads of {:>7} bytes: {:>6.0} MiB/s", block, mib_per_sec);
    }
```

Вывод показан в разделе 4 (второй запуск дал 21, 120, 435 и 1515 МиБ/с). Почему это работает: у каждого чтения есть
постоянная цена в десятки микросекунд, каким бы ни был его размер. При чтениях по 4 КиБ вы платите её 8192 раза за
32 МиБ, при чтениях по 1 МиБ — только 32 раза, а SSD может читать для одного большого запроса многие микросхемы
флеш-памяти параллельно.

</details>

## Вопросы для самопроверки

1. Программа вызывает `write` и получает `Ok`. Назовите два места, кроме микросхем флеш-памяти, где данные ещё могут
   находиться.

<details>
<summary>Ответ</summary>

В страничном кэше ядра (RAM) и в собственном кэше записи SSD. (Если вы использовали `BufWriter` без `flush`, данные
могут быть даже ещё в буфере вашей программы.)

</details>

2. Почему SSD не может перезаписать блок на месте и что он делает вместо этого?

<details>
<summary>Ответ</summary>

Флеш-страницу можно записать, только когда она пуста, а очищаются страницы лишь целым блоком стирания. Поэтому FTL
пишет новые данные в пустую страницу, обновляет своё соответствие номера блока физическому месту, а старые страницы
убирает позже.

</details>

3. Программа меняет 1 байт в середине файла на 1 ГиБ, которого нет в страничном кэше. Примерно сколько байтов нужно
   прочитать и записать?

<details>
<summary>Ответ</summary>

Один блок: прочитать 4 КиБ, изменить 1 байт в памяти и записать 4 КиБ обратно (чтение-изменение-запись). Внутри SSD
может записаться ещё больше из-за усиления записи.

</details>

4. Чем задержка отличается от пропускной способности? Приведите по одному примеру из этого урока.

<details>
<summary>Ответ</summary>

Задержка — время одной операции, например около 45 мкс на одно последовательное чтение 4 КиБ. Пропускная способность —
данные в секунду, например 2341 МиБ/с для случайных чтений по 1 МиБ.

</details>

5. Почему измерение с кэшем в упражнении 2 почти не показало разницы между последовательным и случайным чтением?

<details>
<summary>Ответ</summary>

Все данные были в RAM (в страничном кэше), а в RAM нет ни поиска дорожки, ни флеш-страниц. Время (меньше 1 мкс) —
это в основном цена системного вызова и копирования.

</details>

6. К какой идее проектирования ведёт результат «случайный доступ медленный, последовательный быстрый»?

<details>
<summary>Ответ</summary>

Дописывать новые данные в конец файла (журнал), а не менять старые данные на месте, и записывать большими кусками.

</details>

## Итоги

- По пути к микросхемам флеш-памяти данные проходят несколько слоёв: ваш буфер, страничный кэш, файловую систему,
  драйвер и собственный кэш устройства. Каждый слой существует потому, что следующий медленнее.
- `BufWriter` превращает много мелких записей в несколько системных вызовов; здесь это дало ускорение примерно в 300 раз.
- Устройства и файловые системы работают блоками (обычно по 4 КиБ). Изменение нескольких байтов стоит
  чтения-изменения-записи целого блока.
- HDD платит миллисекунды за каждый поиск; SSD никогда не перезаписывает на месте, и его FTL перемещает данные.
- На SSD этого Mac случайные чтения были примерно в три раза медленнее последовательных, а большие чтения в пересчёте
  на байт были намного дешевле мелких.
- Чтобы измерить устройство, убедитесь, что отвечает не страничный кэш (`F_NOCACHE` на macOS).
- Поэтому движки хранения группируют записи, дописывают в конец, используют страницы и пишут большие отсортированные
  куски.
