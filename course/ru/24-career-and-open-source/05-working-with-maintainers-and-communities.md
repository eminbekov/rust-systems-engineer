# Урок 24.5 — Работа с мейнтейнерами и сообществом

> **Этап 24 — Карьера и open source** · Урок 5 из 9 · ⏱ около 120 минут

## Что вы узнаете

- Как проект выглядит со стороны мейнтейнера и почему это меняет то, как вы им пишете.
- Как написать отчёт об ошибке с минимальным воспроизводимым примером и собрать сведения об окружении небольшой
  программой на Rust.
- Как задавать хорошие вопросы, отвечать на комментарии ревью, терпеливо ждать и пережить закрытый pull request.
- Где общается сообщество Rust, как там себя вести и как вырасти из новичка в постоянного участника, не выгорев.

## Новые слова

| Слово | Значение |
|---|---|
| **сообщество** (community) | Люди вокруг проекта: пользователи, участники, мейнтейнеры, и места, где они общаются. |
| **отчёт об ошибке** (bug report) | Issue, которая описывает проблему так точно, что кто-то другой может увидеть, как она происходит. |
| **MRE** (Minimal Reproducible Example, минимальный воспроизводимый пример) | Самая маленькая законченная программа, которая всё ещё показывает проблему. Ещё говорят «minimal repro». |
| **окружение** (environment) | Сведения о том, где выполнялся код: версии Rust и библиотеки, операционная система, тип процессора. |
| **комментарий ревью** (review comment) | Замечание, которое ревьюер прикрепляет к строке или ко всему pull request. |
| **nit** (придирка) | Мелкое необязательное замечание ревью («nitpick»), например об имени. Ревьюеры часто начинают его с `nit:`. |
| **пинг** (ping) | Короткое вежливое напоминание в обсуждении, которое давно молчит. |
| **триаж** (triage) | Разбор новых issue: проверить, воспроизводятся ли они, поставить метки, спросить недостающие сведения. |
| **выгорание** (burnout) | Истощение от слишком большой работы или давления слишком долго. Частая беда мейнтейнеров. |
| **ID** (identifier, идентификатор) | Число или имя, которое обозначает что-то одно, например ID потока в сообщении паники. |
| **ИИ** (AI, Artificial Intelligence, искусственный интеллект) | Инструменты, которые генерируют текст или код (Урок 24.3). |
| **ОС** (OS, Operating System, операционная система) | Программа, которая управляет оборудованием и запускает другие программы; `bug-report` печатает её имя, например `macos`. |

## 1. Взгляд мейнтейнера

Представьте, что вы ведёте библиотеку, которой пользуются несколько тысяч проектов. Вы работаете над ней по вечерам.
Каждую неделю приходит тридцать новых уведомлений: отчёты об ошибках, вопросы, pull request и люди, спрашивающие
«есть новости?».

С этой стороны следуют три факта:

1. **Время — дефицитный ресурс.** Отчёт, который можно понять за две минуты, получает внимание. Тот, что требует пяти
   уточняющих вопросов туда-обратно, ждёт.
2. **Принятое изменение — это обещание.** Мейнтейнер годами будет поддерживать этот код рабочим, отвечать на вопросы
   о нём и исправлять его ошибки. Поэтому он осторожен в том, *что* принимает, а не только в том, *как* это написано.
3. **Большинство мейнтейнеров доброжелательны, но устали.** Короткий ответ обычно не грубость; это десятый ответ за вечер.

Поэтому у всего в этом уроке одна цель: **облегчить мейнтейнеру следующий шаг.** Точный отчёт, маленький pull request,
ясный ответ на комментарий ревью.

## 2. Отчёт об ошибке, который исправят

Хороший отчёт об ошибке отвечает на четыре вопроса. Во многих проектах есть шаблон issue ровно с этими частями:

| Часть | Вопрос | Пример |
|---|---|---|
| Что я сделал | Какие шаги, какой код, какой вход? | «Я вызвал `first_word("hello")`». |
| Что я ожидал | Что должно было произойти и почему вы так думаете? | «Весь текст, `"hello"`, как для любого одного слова». |
| Что произошло | Точный вывод, ошибка или паника — скопированные, а не пересказанные. | сообщение паники |
| Окружение | Версии и платформа. | версия Rust, версия крейта, операционная система |

Самая ценная часть — **MRE**, минимальный воспроизводимый пример. Допустим, большая ваша программа падает, и вы подозреваете
вспомогательную функцию из библиотеки. Вы шаг за шагом убираете всё, что не нужно для падения, и после каждого шага
проверяете, что падение по-прежнему происходит. В итоге получается вот что:

```rust
fn first_word(text: &str) -> &str {
    let end = text.find(' ').unwrap();
    &text[..end]
}

fn main() {
    println!("{}", first_word("hello world"));
    println!("{}", first_word("hello"));
}
```

```text
hello

thread 'main' (6656315) panicked at src/main.rs:2:30:
called `Option::unwrap()` on a `None` value
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

**Что происходит:**

1. Первый вызов работает и печатает `hello`: пробел есть, поэтому `find` возвращает `Some(5)`.
2. Во втором вызове пробела нет; `find` возвращает `None`, и `unwrap()` паникует (Урок 04.10).
3. Программа — девять строк, без зависимостей, и показывает ожидаемый результат (`hello`) рядом с ошибкой. Мейнтейнер
   может вставить её в Rust Playground или новый проект и увидеть ошибку за секунды. (Число после `'main'` — ID потока,
   его идентификатор; оно меняется при каждом запуске.)

Уменьшение программы часто показывает ошибку вам самим. Это нормально: тогда в отчёте можно написать «причина, похоже,
в `unwrap` в строке 2» или даже прислать исправление.

> 💡 **Совет:** прежде чем писать новую issue, поищите сообщение об ошибке в трекере. Если issue уже есть, добавьте туда
> свой MRE и окружение вместо комментария «+1»; дополнительные факты помогают, «+1» — нет.

## 3. Соберите окружение программой

Часть об окружении легко забыть, и набирать её скучно. Добавьте в `code/p24-career` небольшой помощник,
`src/bin/bug-report.rs`:

```rust
// Prints the facts that every bug report needs, ready to paste into an issue.
use std::process::Command;

/// Runs `program --version` and returns the first line it prints,
/// or a short note if the program cannot be run.
fn version_of(program: &str) -> String {
    match Command::new(program).arg("--version").output() {
        Ok(out) if out.status.success() => String::from_utf8_lossy(&out.stdout)
            .lines()
            .next()
            .unwrap_or("")
            .to_string(),
        _ => format!("{program}: not found"),
    }
}

/// Formats the environment part of a bug report as Markdown.
fn environment(rustc: &str, cargo: &str, os: &str, arch: &str) -> String {
    format!("### Environment\n\n- {rustc}\n- {cargo}\n- OS: {os} ({arch})\n")
}

fn main() {
    let report = environment(
        &version_of("rustc"),
        &version_of("cargo"),
        std::env::consts::OS,
        std::env::consts::ARCH,
    );
    print!("{report}");
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn environment_is_a_markdown_list() {
        let text = environment("rustc 1.0.0", "cargo 1.0.0", "linux", "x86_64");
        assert_eq!(
            text,
            "### Environment\n\n- rustc 1.0.0\n- cargo 1.0.0\n- OS: linux (x86_64)\n"
        );
    }

    #[test]
    fn a_missing_program_is_reported_not_panicked() {
        assert_eq!(
            version_of("no-such-program-24-5"),
            "no-such-program-24-5: not found"
        );
    }

    #[test]
    fn rustc_reports_its_version() {
        assert!(version_of("rustc").starts_with("rustc "));
    }
}
```

**Что происходит:**

1. `Command::new(program).arg("--version").output()` запускает программу, ждёт её и собирает то, что она напечатала
   (Урок 13.5). Если программы нет, возвращается `Err`.
2. У `match` есть **охранное условие** (guard) `if out.status.success()`: первая ветка срабатывает, только если программа
   запустилась *и* завершилась с кодом 0. Все остальные случаи попадают в `_` и дают пометку вместо паники.
3. `String::from_utf8_lossy` превращает байты вывода в текст, заменяя недопустимые байты, а не падая; `.lines().next()`
   оставляет первую строку.
4. `std::env::consts::OS` и `ARCH` — константы, которые Rust заполняет при компиляции целевой операционной системой
   и типом процессора.
5. `environment` только форматирует текст, поэтому её легко точно протестировать. Второй тест проверяет путь неудачи,
   третий — настоящий `rustc` на вашей машине.

```bash
cargo run -q --bin bug-report
cargo test --bin bug-report
```

```text
### Environment

- rustc 1.100.0 (0ef1bc386 2026-11-09)
- cargo 1.100.0 (3acc79c0c 2026-11-05)
- OS: macos (aarch64)
```

```text
running 3 tests
test tests::environment_is_a_markdown_list ... ok
test tests::a_missing_program_is_reported_not_panicked ... ok
test tests::rustc_reports_its_version ... ok

test result: ok. 3 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.04s
```

`aarch64` — так Rust называет процессоры arm64 в Mac на чипах Apple серии M (Урок 12.6). Для ошибки в библиотеке добавьте
и версию библиотеки: её печатает `cargo tree -p <crate> --depth 0`.

> 🔒 **Безопасность:** прежде чем вставлять логи, конфигурацию или трассировку стека в публичную issue, уберите пароли,
> токены, внутренние имена хостов и персональные данные. Если вы нашли проблему **безопасности** (например, падение,
> которое может вызвать злоумышленник), не открывайте публичную issue: найдите в репозитории `SECURITY.md` или «security
> policy» и сообщите о проблеме приватно, как там описано. После исправления такие проблемы публикуются как бюллетени
> безопасности (Урок 10.13).

## 4. Как задавать вопросы

Если вы застряли во время работы над вкладом, спрашивайте; но делайте вопрос лёгким для ответа:

1. **Сначала поищите**: документация, трекер задач, история чата.
2. **Скажите, чего хотите добиться**, а не только какой шаг не получается. Иногда есть путь лучше.
3. **Покажите, что вы пробовали**, и точную ошибку — в блоке кода.
4. **Спрашивайте в правильном месте.** Вопросы об *использовании* Rust — на Rust Users Forum. Вопросы об *одном проекте* —
   в его чате или форуме обсуждений или в issue, над которой вы работаете. Не пишите мейнтейнерам в личные сообщения,
   если они сами не пригласили.

Хороший вопрос в issue, над которой вы работаете:

```text
I am working on this issue. I added the check in `parse_pair` (commit 12cc175),
but `cargo test --doc` now fails in `README.md` line 14, because the example
there uses an empty key on purpose. Should I change the example, or should
empty keys stay allowed in that case?
```

В нём сказано, что сделано, что падает, где, и предложены два конкретных варианта. Мейнтейнер может ответить одной строкой.

## 5. Код-ревью: ответы на комментарии

Ваш pull request получит комментарии. Это нормально и это самая ценная часть вклада: опытный инженер бесплатно читает
ваш код.

- **Отвечайте на каждый комментарий.** Либо измените код и ответьте «Done in <commit>», либо объясните, почему думаете
  иначе. Молчание выглядит так, будто вы не заметили.
- **Спрашивайте, если комментарий непонятен.** «Do you mean the check should move into `split_once`'s caller, or the
  whole function should return a `Result`?» — хороший ответ.
- **Возражайте с доводами — и только один раз.** Коротко изложите аргумент. Если мейнтейнер всё равно предпочитает свой
  вариант, следуйте ему: поддерживать код будет он, а не вы.
- **Отличайте придирки от настоящих проблем.** Комментарий, начинающийся с `nit:`, необязателен; выполните его, если это
  дёшево.
- **Следуйте стилю проекта для обновлений.** Одни проекты хотят новых коммитов во время ревью и объединяют их в конце;
  другие хотят, чтобы вы переписывали свои коммиты интерактивным rebase (Урок 01.9). Скажет `CONTRIBUTING.md` или ревьюер.
- **Не принимайте на свой счёт.** Комментарий — о коде. «This allocates on every call» не значит «вы плохой инженер».

Короткие ответы, которые хорошо работают:

```text
Good catch, done in 4f2a9c1.
I kept the `unwrap` here because `split_once` already checked for `=`; is a comment enough?
I am not sure I understand. Do you mean X or Y?
Thanks for the review! I pushed the changes; ready for another look.
```

> 📏 **Соглашение:** будьте конкретны и доброжелательны в обе стороны. Пишите «This loop is quadratic for long input;
> a `HashSet` would make it linear» вместо «This is slow». То же правило действует, когда ревью делаете вы.

## 6. Ожидание, пинги и закрытые pull request

**Ожидание.** Ревью в волонтёрских проектах может занимать дни или недели. Если около двух недель ничего не происходит,
один вежливый пинг уместен: «Friendly ping: is there anything I should change here?» Не пингуйте каждый день и не
упоминайте много людей.

**Когда ответа нет совсем.** Иногда проект молчит месяцами. Перейти к другому проекту — нормально. Если вы взяли issue
и прекращаете над ней работать, скажите об этом коротким комментарием, чтобы её мог взять кто-то другой.

**Когда ваш pull request закрыли.** Это случается со всеми. Частые причины: мейнтейнеры хотят другого устройства,
проблему решили иначе, или изменение не подходит к целям проекта. Прочитайте причину, поблагодарите за потраченное время
и сохраните то, чему научились. Вежливая реакция на закрытый pull request повышает шансы следующего в том же проекте.

## 7. Сообщества и как себя в них вести

Официальные места общения Rust, перечисленные на странице сообщества rust-lang.org:

- **Rust Users Forum** (`users.rust-lang.org`) — для вопросов об использовании Rust;
- чат **Rust Zulip**, где работают и обсуждают дела команды, развивающие сам Rust;
- чаты проектов (многие проекты держат пространство в Zulip, Discord или Matrix; README даёт ссылку);
- **This Week in Rust**, еженедельная рассылка, а также местные или онлайн-**митапы**.

У каждого из них есть кодекс поведения. Основные правила просты: будьте доброжелательны, исходите из добрых намерений,
держите обсуждение в техническом русле и никого не оскорбляйте, даже когда раздражены.

Писать не на родном языке в этих пространствах — нормально. Короткие ясные предложения легко читать всем. Если вы
используете инструмент ИИ, чтобы перевести или отшлифовать текст, следуйте политике проекта об ИИ (Урок 24.3): некоторые
проекты просят писать своими словами и помечать машинный перевод как таковой.

## 8. От новичка к постоянному участнику

После первого принятого изменения лучший следующий шаг обычно — **тот же проект**. Вы уже знаете, как его собирать
и тестировать, а мейнтейнеры знают вас. Типичный рост:

1. второе и третье небольшое исправление;
2. **триаж**: воспроизвести новые отчёты об ошибках, попросить у авторов недостающие сведения, написать для них MRE;
3. **ревью** чужих pull request: «I tried this branch and it fixes the issue for me» сильно помогает мейнтейнерам;
4. более крупное изменение, сначала обсуждённое в issue.

Держите темп, который можно выдержать. Вклад добровольный; выберите ритм, который вы сохраните год, например два часа
в неделю. Сказать «у меня сейчас нет на это времени» — нормально. Выгорают мейнтейнеры, выгорают и участники.

## Частые ошибки

**Пересказ ошибки вместо копирования.** «Там что-то про unwrap» нельзя ни найти поиском, ни проверить. Скопируйте точный
текст в блок кода.

**MRE, который не компилируется.** Если мейнтейнеру приходится угадывать недостающие строки `use` или типы, пример
не воспроизводим. Запустите его сами в новом проекте, прежде чем публиковать.

**Спор с каждым комментарием ревью.** Объясните один раз; затем примите решение мейнтейнера или вежливо закройте
pull request.

**Слишком частые пинги или пинги во многих местах.** Один пинг примерно через две недели, в самом pull request.

**Публикация секретов.** Логи и конфигурация часто содержат токены или внутренние имена. Читайте каждую строку, которую
вставляете.

## Попробуйте сами

1. Добавьте `bug-report` в `code/p24-career`, запустите его и его тесты.
2. Возьмите панику или неверный результат из одного из своих проектов курса, уменьшите до MRE не длиннее пятнадцати
   строк и напишите полный отчёт об ошибке (четыре части из раздела 2) в `notes/oss-log.md`.
3. Прочитайте десять недавних issue в проекте, которым пользуетесь. Отметьте, по каким легко действовать, а по каким
   нет, и запишите почему.
4. Прочитайте кодекс поведения этого проекта.

## Упражнения

### Упражнение 1 — Шаблон всего отчёта (средне)

Расширьте `bug-report`, чтобы перед окружением печатались пустые разделы «What I did», «What I expected» и «What happened
instead» (после каждого — `(fill in)`). Напишите тест, который проверяет, что четыре заголовка идут в этом порядке.

<details>
<summary>Подсказка</summary>

Напишите функцию `report_template(environment: &str) -> String`, которая строит текст в цикле по трём заголовкам. В тесте
используйте `text.find("### …")` для каждого заголовка и сравните позиции.

</details>

<details>
<summary>Ответ</summary>

```rust
/// The empty sections that the reporter fills in by hand, followed by the environment.
fn report_template(environment: &str) -> String {
    let mut text = String::new();
    for heading in ["What I did", "What I expected", "What happened instead"] {
        text.push_str(&format!("### {heading}\n\n(fill in)\n\n"));
    }
    text.push_str(environment);
    text
}

fn main() {
    let env = environment(
        &version_of("rustc"),
        &version_of("cargo"),
        std::env::consts::OS,
        std::env::consts::ARCH,
    );
    print!("{}", report_template(&env));
}

#[test]
fn template_has_the_sections_in_order() {
    let text = report_template("### Environment\n");
    let did = text.find("### What I did").unwrap();
    let expected = text.find("### What I expected").unwrap();
    let happened = text.find("### What happened instead").unwrap();
    let env = text.find("### Environment").unwrap();
    assert!(did < expected && expected < happened && happened < env);
}
```

Тест помещается в `mod tests`. Вывод `cargo run -q --bin bug-report`:

```text
### What I did

(fill in)

### What I expected

(fill in)

### What happened instead

(fill in)

### Environment

- rustc 1.100.0 (0ef1bc386 2026-11-09)
- cargo 1.100.0 (3acc79c0c 2026-11-05)
- OS: macos (aarch64)
```

Почему это работает: `report_template` получает окружение параметром, а не вызывает `rustc` сама, поэтому тест может
передать фиксированный текст и не зависит от машины.

</details>

### Упражнение 2 — Уменьшите (средне)

Эта программа должна печатать сводку с одним предупреждением для строки `verbose` (настройка без значения), но паникует.
Уменьшите её до MRE не длиннее десяти строк, который показывает ту же панику, и одним предложением назовите причину.

```rust
use std::collections::HashMap;

struct Config {
    values: HashMap<String, String>,
    warnings: Vec<String>,
}

fn command_name(line: &str) -> &str {
    let end = line.find(' ').unwrap();
    &line[..end]
}

fn load(text: &str) -> Config {
    let mut config = Config {
        values: HashMap::new(),
        warnings: Vec::new(),
    };
    for (number, line) in text.lines().enumerate() {
        let line = line.trim();
        if line.is_empty() || line.starts_with('#') {
            continue;
        }
        let name = command_name(line);
        let rest = line[name.len()..].trim();
        if rest.is_empty() {
            config
                .warnings
                .push(format!("line {}: {name} has no value", number + 1));
        }
        config.values.insert(name.to_string(), rest.to_string());
    }
    config
}

fn main() {
    let text = "# server settings\nport 8080\nhost localhost\nverbose\n";
    let config = load(text);
    println!(
        "{} values, {} warnings",
        config.values.len(),
        config.warnings.len()
    );
}
```

```text

thread 'main' (6656547) panicked at src/main.rs:9:30:
called `Option::unwrap()` on a `None` value
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

<details>
<summary>Подсказка</summary>

Паника — в строке 9, внутри `command_name`. Какая входная строка доходит до неё без пробела? Оставьте только эту функцию
и один работающий вызов рядом с одним падающим.

</details>

<details>
<summary>Ответ</summary>

```rust
fn command_name(line: &str) -> &str {
    let end = line.find(' ').unwrap();
    &line[..end]
}

fn main() {
    println!("{}", command_name("port 8080"));
    println!("{}", command_name("verbose"));
}
```

```text
port

thread 'main' (6656974) panicked at src/main.rs:2:30:
called `Option::unwrap()` on a `None` value
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

Причина: `command_name` предполагает, что после имени в каждой строке есть пробел, поэтому строка `verbose` вызывает
панику раньше, чем код предупреждений вообще выполняется. Почему это работает как MRE: `HashMap`, структура `Config`,
комментарии и номера строк не имели отношения к панике; после их удаления осталось только ошибочное предположение
и один удачный вызов, показывающий, что функция должна делать.

</details>

### Упражнение 3 — Ответьте на ревью (легко, без кода)

Мейнтейнер оставил три комментария к вашему pull request: (a) «nit: rename k to key». (b) «This adds a new public
function. Could it be private instead?» (c) «I think this belongs in a separate pull request.» Напишите ответ на каждый.

<details>
<summary>Подсказка</summary>

Для каждого комментария решите: сделать и подтвердить, задать вопрос или один раз объяснить. Каждый ответ — одно-два
предложения.

</details>

<details>
<summary>Ответ</summary>

Примеры ответов:

```text
(a) Done in 7c1e0b2.
(b) Good point. Nothing outside the module uses it, so I made it private in 7c1e0b2.
(c) Agreed. I removed that part from this pull request and opened a separate issue for it.
```

Каждый ответ подтверждает действие коммитом или показывает, что вы поняли причину. Ни один не спорит о придирке, а
замечание о границах изменения решается тем, что pull request становится меньше, — именно этого просил мейнтейнер.

</details>

## Вопросы для самопроверки

1. Почему минимальный воспроизводимый пример — самая ценная часть отчёта об ошибке?

<details>
<summary>Ответ</summary>

Мейнтейнер может запустить его за секунды и увидеть проблему, не угадывая вашу настройку. Уменьшение примера часто ещё
и показывает, где ошибка.

</details>

2. Куда сообщать о проблеме безопасности, найденной в библиотеке?

<details>
<summary>Ответ</summary>

Приватно, по политике безопасности проекта (часто в `SECURITY.md`), а не в публичной issue.

</details>

3. Ревьюер просит изменение, с которым вы не согласны. Что делать?

<details>
<summary>Ответ</summary>

Один раз коротко объяснить свои доводы. Если он всё равно предпочитает свой вариант, следовать ему, потому что
поддерживать код будет он; или вежливо закрыть pull request, если вы не можете принять изменение.

</details>

4. На ваш pull request две недели нет реакции. Какой хороший следующий шаг?

<details>
<summary>Ответ</summary>

Один короткий вежливый пинг в самом pull request («Friendly ping: is there anything I should change?»). Не каждый день
и не во многих местах.

</details>

5. Зачем в `version_of` в `match` стоит охранное условие `if out.status.success()`?

<details>
<summary>Ответ</summary>

`output()` возвращает `Ok`, даже когда программа запустилась, но завершилась неудачей. Охранное условие заставляет
первую ветку срабатывать только при успешном запуске, поэтому для неудачно завершившейся программы тоже получается
пометка «not found», а не её вывод об ошибке вместо версии.

</details>

## Итоги

- У мейнтейнеров мало времени, и им поддерживать то, что они принимают: облегчайте им следующий шаг.
- Хороший отчёт об ошибке состоит из четырёх частей (что я сделал, что ожидал, что произошло, окружение) и MRE, который
  компилируется и показывает проблему в нескольких строках.
- Собирайте окружение автоматически и убирайте секреты, прежде чем что-либо вставлять.
- О проблемах безопасности сообщайте приватно, по политике безопасности проекта.
- Отвечайте на каждый комментарий ревью, возражайте с доводами только один раз и не принимайте комментарии на свой счёт.
- Терпеливо ждите, пингуйте один раз, достойно принимайте закрытый pull request и растите в одном проекте в посильном темпе.
