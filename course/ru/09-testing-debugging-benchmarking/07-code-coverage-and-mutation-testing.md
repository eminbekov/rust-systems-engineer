# Урок 09.7 — Покрытие кода и мутационное тестирование

> **Этап 09 — Тестирование, отладка и бенчмарки** · Урок 7 из 14 · ⏱ около 120 минут

## Что вы узнаете

- Что такое покрытие кода, как измерять его с помощью `cargo llvm-cov` и как читать отчёт.
- Почему 100 % покрытия не означает, что тесты хороши.
- Что такое мутационное тестирование и как `cargo mutants` показывает тесты, которые ничего не проверяют.
- Как превратить «пропущенного мутанта» в лучший тест и как пользоваться обоими инструментами, не гоняясь за цифрами.

## Новые слова

| Слово | Значение |
|---|---|
| **покрытие кода** (code coverage) | Измерение того, какие части вашего кода выполнялись, пока работали тесты. |
| **покрытие строк** (line coverage) | Доля строк исходного кода, выполненных хотя бы один раз, в процентах. |
| **регион** (region) | Участок кода, который компилятор считает для покрытия отдельно: например, одна ветка `if`. Покрытие регионов строже покрытия строк. |
| **инструментирование** (instrumentation) | Дополнительный код-счётчик, который компилятор добавляет в программу, чтобы она записывала, что выполнялось. |
| **LLVM** (название историческое) | Бэкенд компилятора, который Rust использует для получения машинного кода; он же предоставляет счётчики покрытия. |
| **LCOV** (название инструмента покрытия `lcov`) | Текстовый формат файла с данными о покрытии (обычно файл `lcov.info`). Назван по инструменту `lcov`; его умеют читать многие редакторы и сервисы покрытия. |
| **`cargo-llvm-cov`** | Инструмент, используемый как `cargo llvm-cov`, который запускает ваши тесты с инструментированием и печатает отчёт о покрытии. |
| **мутационное тестирование** (mutation testing) | Намеренное изменение вашего кода мелкими способами (*мутация*) и проверка того, что хотя бы один тест падает. |
| **мутант** (mutant) | Одна изменённая копия вашей программы, например с `+`, заменённым на `-`. |
| **пойманный / убитый мутант** (caught / killed mutant) | Мутант, из-за которого падает тест. Хорошо: ваши тесты заметили изменение. |
| **пропущенный / выживший мутант** (missed / surviving mutant) | Мутант, при котором все тесты по-прежнему проходят. Плохо: ваши тесты не замечают это изменение. |
| **эквивалентный мутант** (equivalent mutant) | Мутант, который меняет код, но не поведение, поэтому никакой тест не может его поймать. |
| **`cargo-mutants`** | Инструмент, используемый как `cargo mutants`, который создаёт мутантов и запускает на каждом ваши тесты. |
| **тайм-аут теста** (test timeout) | Ограничение времени запуска тестов; мутант, из-за которого программа зацикливается навсегда, им останавливается. |
| **граничное значение** (boundary value) | Значение прямо на границе двух случаев, например вес 500, когда предел — «до 500». |

## 1. Два вопроса о тестах

Вы написали тесты. Остаются два открытых вопроса:

1. **Какой код запускают мои тесты?** Код, который не запускает ни один тест, заведомо не протестирован. На это отвечает *покрытие*.
2. **Если бы я сломал код, заметил бы это какой-нибудь тест?** Тест может выполнить строку и при этом ничего о ней не проверить. На это отвечает *мутационное тестирование*.

У первого вопроса простой и быстрый ответ, но его легко прочитать неверно. Второй медленнее, но он измеряет то, что вам действительно нужно: способность тестов находить ошибки.

## 3. Тестируемый код и слабый тест

Замените `src/lib.rs`:

```rust
/// Price of sending a parcel, in cents. Express delivery costs twice as much.
pub fn shipping_cost(weight_grams: u32, express: bool) -> u32 {
    let base = if weight_grams <= 500 {
        500
    } else if weight_grams <= 2_000 {
        900
    } else {
        1_500
    };
    if express { base * 2 } else { base }
}

/// Orders of 5,000 cents or more ship for free.
pub fn shipping_for_order(order_cents: u32, weight_grams: u32, express: bool) -> u32 {
    if order_cents >= 5_000 {
        0
    } else {
        shipping_cost(weight_grams, express)
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn it_runs() {
        shipping_cost(100, false);
        shipping_cost(1_000, true);
        shipping_cost(3_000, false);
        shipping_for_order(6_000, 100, false);
        shipping_for_order(100, 100, false);
    }
}
```

**Что происходит:** у `shipping_cost` три весовых класса (до 500 г стоит 500 центов, до 2000 г — 900, больше — 1500), а для экспресс-доставки цена удваивается.
`shipping_for_order` делает большие заказы бесплатными. Тест `it_runs` вызывает функции со входами для каждой ветки, но **никогда не смотрит на результат**: нет ни одного
`assert`. Так пишет уставший программист или программа, которая хочет «дойти до 100 %». Запустите `cargo test`: один тест проходит.

## 4. Измерение покрытия

```bash
cargo llvm-cov
```

Команда компилирует ваши тесты с инструментированием, запускает их и печатает обычный вывод тестов, а затем таблицу. Настоящая таблица широкая; вот
важные столбцы (столбцы *Branches*, которые на стабильном Rust показывают `-`, опущены):

```text
Filename       Regions  Missed Regions  Cover     Functions  Missed Functions  Executed   Lines  Missed Lines  Cover
…/src/lib.rs        30               0  100.00%           3                 0  100.00%      20             0  100.00%
TOTAL               30               0  100.00%           3                 0  100.00%      20             0  100.00%
```

**Что это значит:**

- **Lines** (строки): 20 строк могут выполняться, и все 20 выполнены. Покрытие строк 100 %.
- **Functions** (функции): 3 функции (`shipping_cost`, `shipping_for_order` и сам тест), все вызваны.
- **Regions** (регионы): 30 регионов (участки вроде каждой ветки `if` и каждой стороны `&&`), ни один не пропущен.

Всё выполнено, и всё равно тесты ничего не доказывают: вы могли бы заменить тело `shipping_cost` на `0`, и `cargo test` остался бы зелёным. **Покрытие говорит, что выполнялось, а не что проверялось.**

Другие формы отчёта:

| Команда | Что она даёт |
|---|---|
| `cargo llvm-cov --text` | исходный код со счётчиком выполнений перед каждой строкой (лучше всего для поиска дыр) |
| `cargo llvm-cov --html` | папку `target/llvm-cov/html/` с отчётом, который можно просматривать; добавьте `--open`, чтобы открыть его в браузере |
| `cargo llvm-cov --lcov --output-path lcov.info` | файл в формате LCOV, который читают многие инструменты и сервисы |
| `cargo llvm-cov --summary-only` | только таблицу, без исходного кода |
| `cargo llvm-cov --fail-under-lines 90` | завершиться с кодом ошибки, если покрытие строк ниже 90 % (для CI, continuous integration, непрерывной интеграции: сервера, который проверяет каждое изменение, Урок 09.12) |
| `cargo llvm-cov --ignore-filename-regex 'tests/'` | исключить файлы, путь которых подходит под шаблон |

Чтобы увидеть, как помогает вид `--text`, замените `it_runs` двумя небольшими настоящими тестами (они нам всё равно понадобятся в следующих разделах):

```rust
    #[test]
    fn a_light_parcel_costs_500() {
        assert_eq!(shipping_cost(100, false), 500);
    }

    #[test]
    fn a_big_order_ships_free() {
        assert_eq!(shipping_for_order(6_000, 100, false), 0);
    }
```

```bash
cargo llvm-cov --text
```

```text
    1|       |/// Price of sending a parcel, in cents. Express delivery costs twice as much.
    2|      1|pub fn shipping_cost(weight_grams: u32, express: bool) -> u32 {
    3|      1|    let base = if weight_grams <= 500 {
    4|      1|        500
    5|      0|    } else if weight_grams <= 2_000 {
    6|      0|        900
    7|       |    } else {
    8|      0|        1_500
    9|       |    };
   10|      1|    if express { base * 2 } else { base }
                               ^0
   11|      1|}
   12|       |
   13|       |/// Orders of 5,000 cents or more ship for free.
   14|      1|pub fn shipping_for_order(order_cents: u32, weight_grams: u32, express: bool) -> u32 {
   15|      1|    if order_cents >= 5_000 {
   16|      1|        0
   17|       |    } else {
   18|      0|        shipping_cost(weight_grams, express)
   19|       |    }
```

**Что происходит:** число перед `|` — номер строки; второе число говорит, сколько раз строка выполнялась. `0` отмечает код, который не выполнил ни один тест: средний и тяжёлый
классы (строки 5, 6, 8) и вызов в строке 18. `^0` под строкой 10 — это *регион*, который никогда не выполнялся: экспресс-ветка `base * 2`. Итоговая строка теперь говорит:
79,31 % регионов и 78,95 % строк. Отчёт показывает ровно, каких тестов не хватает.

Обратите внимание, что произошло: после того как мы заменили один бесполезный тест двумя настоящими, **покрытие упало** (со 100 % до 79 %), а качество тестов выросло. Поэтому один лишь процент —
плохая мера.

> 💡 **Совет:** используйте покрытие, чтобы находить *дыры*, а не чтобы достигать числа. Откройте отчёт `--html` после новой возможности и посмотрите на красные строки: каждая — вопрос «нормально ли, что
> это ничто не тестирует?». Иногда ответ «да» (код, печатающий сообщение об использовании), иногда это пропущенный тест.

## 5. Мутационное тестирование

Мутационное тестирование измеряет силу тестов напрямую. Инструмент меняет вашу программу мелкими механическими способами, по одному изменению за раз, и запускает тесты на каждой изменённой копии
(**мутанте**). Если тесты всё равно проходят, изменение осталось незамеченным: **пропущенный** мутант, указывающий на отсутствующий или слабый тест. Типичные мутации: заменить тело функции константой
(`0`, `1`, `true`, `false`, пустой `Vec`) и подменить оператор (`+` на `-` или `*`, `<` на `>`, `==` на `!=`).

Верните слабый тест `it_runs` (код из раздела 3) и посмотрите, что сделал бы инструмент:

```bash
cargo mutants --list
```

```text
src/lib.rs:3:5: replace shipping_cost -> u32 with 0
src/lib.rs:3:5: replace shipping_cost -> u32 with 1
src/lib.rs:3:32: replace <= with > in shipping_cost
src/lib.rs:5:28: replace <= with > in shipping_cost
src/lib.rs:10:23: replace * with + in shipping_cost
src/lib.rs:10:23: replace * with / in shipping_cost
src/lib.rs:15:5: replace shipping_for_order -> u32 with 0
src/lib.rs:15:5: replace shipping_for_order -> u32 with 1
src/lib.rs:15:20: replace >= with < in shipping_for_order
```

Каждая строка — один мутант: *файл:строка:столбец: что заменяется*. Теперь запустите их. `cargo mutants` копирует проект во временную папку, применяет каждую мутацию, собирает и запускает `cargo test`:

```bash
cargo mutants
```

```text

MISSED   src/lib.rs:3:5: replace shipping_cost -> u32 with 1 in 0s build + 0s test
```

**Что это значит:**

1. Сначала инструмент запускает тесты на *немутированном* коде («базовый уровень», baseline). Они должны проходить, иначе результат ничего бы не значил.
2. **Все 9 мутантов пропущены**, хотя покрытие строк 100 %. Каждая мутация, даже «функция всегда возвращает 0», невидима для тестов, потому что тест ничего не проверяет. Это доказательство того,
   что покрытие и качество тестов — разные вещи.
3. Инструмент также записывает подробности в папку `mutants.out/` (`missed.txt`, `caught.txt` и лог для каждого мутанта). Папка есть в вашем `.gitignore`.

## 6. Убиваем мутантов

Замените `it_runs` двумя настоящими тестами из раздела 4 и снова запустите `cargo mutants`:

```text
Found 9 mutants to test
ok       Unmutated baseline in 0s build + 0s test
 INFO Auto-set test timeout to 20s
MISSED   src/lib.rs:5:28: replace <= with > in shipping_cost in 0s build + 0s test
MISSED   src/lib.rs:10:23: replace * with + in shipping_cost in 0s build + 0s test
MISSED   src/lib.rs:10:23: replace * with / in shipping_cost in 0s build + 0s test
MISSED   src/lib.rs:15:5: replace shipping_for_order -> u32 with 0 in 0s build + 0s test
9 mutants tested in 4s: 4 missed, 5 caught
```

Пять мутантов теперь **пойманы**. Каждый из четырёх пропущенных говорит, чего не хватает:

| Пропущенный мутант | Почему тесты не замечают | Тест, который его убивает |
|---|---|---|
| строка 5: `<=` на `>` | ни один тест не использует вес от 501 до 2000 | средняя посылка |
| строка 10: `*` на `+` или `/` | ни один тест не использует `express = true` | экспресс-посылка |
| строка 15: `shipping_for_order` всегда `0` | единственный тест ожидает `0` | заказ, который *не* бесплатный |

Напишите эти тесты (и для тяжёлого класса, который покрытие тоже отметило), а также граничные тесты, о которых дальше:

```rust
    #[test]
    fn a_medium_parcel_costs_900() {
        assert_eq!(shipping_cost(1_000, false), 900);
    }

    #[test]
    fn a_heavy_parcel_costs_1500() {
        assert_eq!(shipping_cost(3_000, false), 1_500);
    }

    #[test]
    fn express_costs_twice_as_much() {
        assert_eq!(shipping_cost(100, true), 1_000);
    }

    #[test]
    fn a_small_order_pays_for_shipping() {
        assert_eq!(shipping_for_order(100, 100, false), 500);
    }

    #[test]
    fn the_weight_limits_belong_to_the_cheaper_class() {
        assert_eq!(shipping_cost(500, false), 500);
        assert_eq!(shipping_cost(501, false), 900);
        assert_eq!(shipping_cost(2_000, false), 900);
        assert_eq!(shipping_cost(2_001, false), 1_500);
    }

    #[test]
    fn five_thousand_cents_is_enough_for_free_shipping() {
        assert_eq!(shipping_for_order(4_999, 100, false), 500);
        assert_eq!(shipping_for_order(5_000, 100, false), 0);
    }
```

```bash
cargo test && cargo llvm-cov --summary-only && cargo mutants
```

```text

Filename       Regions  Missed Regions  Cover     Functions  Missed Functions  Executed   Lines  Missed Lines  Cover
…/src/lib.rs        84               0  100.00%          10                 0  100.00%      41             0  100.00%

 INFO Auto-set test timeout to 20s
```

Теперь оба показателя равны 100 %, и на этот раз 100 % что-то значит: каждая строка выполняется **и** каждая мутация замечена.

**Граничные тесты.** `the_weight_limits_belong_to_the_cheaper_class` проверяет значения ровно на границах: 500 и 501, 2000 и 2001, а также 4999 и 5000. Ошибки любят границы
(«до 500» или «меньше 500»?). Обратите внимание, что `cargo mutants` не создал мутанта «`<=` становится `<`», поэтому даже 9 пойманных мутантов не доказали, что граница верна. Если изменить
`weight_grams <= 500` на `< 500`, упадёт только граничный тест. Инструменты находят дыры; **думать о граничных случаях всё равно ваша работа**.

## 7. Разумное использование инструментов

**Покрытие**

- Это *отрицательный* сигнал: низкое покрытие важного модуля — предупреждение, высокое покрытие доказывает немногое.
- Не ставьте цель 100 %. Погоня за числом порождает тесты вроде `it_runs`. Командная цель вроде «не менее 80 % строк и без падения в pull request» лучше работает как страховочная сетка в CI:
  `cargo llvm-cov --fail-under-lines 80` (Урок 09.12 строит конвейер CI).
- Исключайте то, что не должно считаться: вспомогательный код тестов, сгенерированный код (`--ignore-filename-regex`).

**Мутационное тестирование**

- Оно медленное: каждому мутанту нужна сборка и запуск тестов. На большом проекте это может занять часы. Запускайте его на **небольшой важной части** (`cargo mutants -f src/lib.rs`), или только на том, что изменила ветка
  (`cargo mutants --in-diff changes.diff`, где `changes.diff` — вывод `git diff`), или ночью в CI.
- Не каждый пропущенный мутант — проблема. **Эквивалентный мутант** меняет код, но не поведение (например, замена `x * 1` на `x / 1`), поэтому никакой тест его не поймает. Читайте каждого выжившего
  и решайте: пропущенный тест или неважно? Код, который вы решили оставить, можно пометить атрибутом `#[mutants::skip]` из крейта `mutants` (см. его документацию).
- Мутант, из-за которого программа зацикливается навсегда, останавливается *тайм-аутом* (`cargo mutants` в нашем запуске автоматически поставил 20 секунд) и считается отдельно как «timeout».
- Сначала убедитесь, что тесты проходят без мутации («базовый уровень»). Нестабильный тест (Урок 05.6) делает результаты ненадёжными.

**Слепые пятна обоих инструментов** (одно показывает упражнение): они не видят *отсутствующий тест для требования, которого нет в коде*, например минимум страховки, который никогда не мутируется, и они
не придумывают граничные случаи. Три подхода вместе — примеры, подобранные вручную, свойства (Урок 09.4) и эти инструменты — дополняют друг друга.

> 🧪 **Тестирование:** хороший порядок для важного модуля: сначала напишите тесты (TDD, test-driven development, разработка через тестирование, Урок 09.6), посмотрите в `cargo llvm-cov --html`, какой код не протестирован, запустите `cargo mutants` на этом модуле и
> превратите каждого значимого выжившего в тест.

> ⚡ **Производительность:** инструментирование для покрытия замедляет тесты (часто в 1,5–3 раза), а мутационное тестирование умножает время тестов на число мутантов. Запускайте оба в отдельных заданиях CI, а не
> в быстром цикле «правка — тест».

## Частые ошибки

**1. Считать процент целью.** Тесты без проверок, как `it_runs`, дают 100 % и ничего не защищают. Измеряйте мутантами и читайте красные строки.

**2. Забыть компонент.** Без `llvm-tools-preview` инструмент останавливается с ошибкой, которая просит выполнить `rustup component add llvm-tools-preview`. Выполните команду и повторите.

**3. Запускать `cargo mutants` при красных тестах.** Базовый уровень падает, и инструмент останавливается с `ERROR cargo test failed in an unmutated tree, so no mutants were tested`, потому что каждый мутант «упал» бы по неверной причине. Сначала сделайте тесты зелёными.

**4. Коммитить `mutants.out` или `target/llvm-cov`.** Это результаты сборки, часто большие. Держите их в `.gitignore`.

**5. Игнорировать каждого выжившего.** «Инструмент слишком строгий». Иногда так и есть, но каждый выживший — это заявление «я изменил ваш код, и никто не пожаловался». Прочитайте его, прежде чем отмахнуться.

## Упражнения

### Упражнение 1 — Найдите дыры (легко)

Имея только два теста `a_light_parcel_costs_500` и `a_big_order_ships_free`, запустите `cargo llvm-cov --summary-only --show-missing-lines`. Какие строки он перечисляет как непокрытые и какому поведению они принадлежат?

<details>
<summary>Подсказка</summary>

Список появляется под `Uncovered Lines:`. Сравните его с видом `--text` из раздела 4.

</details>

<details>
<summary>Ответ</summary>

```text
Uncovered Lines:
…/src/lib.rs: 5-6, 8, 18
```

Строки 5 и 6 — средний класс (больше 500 г, до 2000 г), строка 8 — тяжёлый класс, а строка 18 — вызов `shipping_cost` из `shipping_for_order` для заказа, который не бесплатный. Каждая из них —
отсутствующий тест. (Вид `--text` также показывает никогда не выполнявшуюся экспресс-ветку строки 10 как `^0`.)

</details>

### Упражнение 2 — Убейте одного мутанта (средне)

После двух настоящих тестов `cargo mutants` сообщает `MISSED src/lib.rs:5:28: replace <= with > in shipping_cost`. Объясните одним предложением, почему тесты его пропускают, напишите самый маленький тест, который его убивает, и проверьте это через `cargo mutants`.

<details>
<summary>Подсказка</summary>

Строка 5 — условие `weight_grams <= 2_000`. Какие веса до него доходят и какие из них дают другой ответ при инвертированном условии?

</details>

<details>
<summary>Ответ</summary>

Единственный проверяемый вес — 100 г, и он решается первым условием (`<= 500`), поэтому строка 5 никогда не вычисляется. Вес 1000 г доходит до второго условия, где исходный код отвечает 900, а
мутант — 1500:

```rust
    #[test]
    fn a_medium_parcel_costs_900() {
        assert_eq!(shipping_cost(1_000, false), 900);
    }
```

С этим тестом `cargo mutants` показывает на одного мутанта меньше: `replace <= with > in shipping_cost` (строка 5) пойман, потому что мутант заставляет `shipping_cost(1_000, false)` возвращать 1500.

</details>

### Упражнение 3 — Слепое пятно (сложно)

Добавьте в библиотеку эту функцию с тестом `big_orders_pay_two_percent`, который проверяет `insurance(10_000) == 200`:

```rust
/// Insurance costs 2% of the order (one fiftieth, rounded down), but at least 100 cents.
pub fn insurance(order_cents: u32) -> u32 {
    (order_cents / 50).max(100)
}
```

Запустите `cargo mutants` и `cargo llvm-cov --summary-only`. Оба довольны. Теперь удалите `.max(100)` из функции: заметят ли это тесты? Что это показывает и какой тест вы добавите?

<details>
<summary>Подсказка</summary>

`cargo mutants --list` показывает, какие мутанты существуют для `insurance`. Есть ли мутант для вызова `max`? Подумайте, при каких входах `max(100)` имеет значение.

</details>

<details>
<summary>Ответ</summary>

```rust
    #[test]
    fn big_orders_pay_two_percent() {
        assert_eq!(insurance(10_000), 200);
    }
```

`cargo mutants` перечисляет для `insurance` четыре мутанта (функция, заменённая на `0` или `1`, и `/`, заменённое на `%` или `*`) и ловит их все; покрытие 100 %. Если удалить `.max(100)`, тесты всё равно
проходят: правило минимума **не протестировано**, а у `cargo mutants` нет мутанта, который убирает вызов метода вроде `.max(100)`. Инструменты не могут проверить требования, о которых не говорят ваши тесты. Добавьте тест
на это правило со входом, где минимум имеет значение:

```rust
    #[test]
    fn small_orders_pay_the_minimum_insurance() {
        assert_eq!(insurance(0), 100);
        assert_eq!(insurance(5_000), 100);
    }
```

Если убрать `.max(100)`, то `insurance(0)` возвращает 0, и тест падает. Урок: используйте инструменты, чтобы находить дыры, а список требований — чтобы решать, что должны говорить тесты.

</details>

## Вопросы для самопроверки

1. Что покрытие строк 100 % говорит вам и чего не говорит?

<details>
<summary>Ответ</summary>

Оно говорит, что каждая строка была выполнена хотя бы раз, пока работали тесты. Оно не говорит, что результаты проверялись: тест без проверок может дать 100 %.

</details>

2. Что такое мутант и что значит, что он «пропущен»?

<details>
<summary>Ответ</summary>

Мутант — копия вашей программы с одним небольшим намеренным изменением (например, `+`, заменённый на `-`). Если он пропущен, все тесты по-прежнему проходят с этим изменением, значит, ни один тест не замечает это поведение.

</details>

3. Почему `cargo mutants` сначала запускает тесты на неизменённом коде?

<details>
<summary>Ответ</summary>

Чтобы убедиться, что тесты в начале проходят (базовый уровень). Если они падают без мутации, падение на мутанте ничего бы не доказывало.

</details>

4. Почему покрытие может падать, пока тесты становятся лучше?

<details>
<summary>Ответ</summary>

Слабый тест может выполнять много строк, ничего не проверяя. Замена его настоящим тестом, выполняющим меньше строк, снижает покрытие, но новый тест действительно проверяет результаты.

</details>

5. Назовите два способа ускорить мутационное тестирование на большом проекте.

<details>
<summary>Ответ</summary>

Запускать только на части (`-f src/file.rs` или пакет), только на изменениях ветки (`--in-diff`), запускать мутантов параллельно через `-j` или запускать в отдельном ночном задании CI.

</details>

6. Какой инструмент показывает «строки, которые не запускает ни один тест», а какой — «тесты, которые ничего не проверяют»?

<details>
<summary>Ответ</summary>

`cargo llvm-cov` показывает строки, которые не запускает ни один тест. `cargo mutants` показывает изменения, которых не замечает ни один тест, то есть тесты, ничего не проверяющие об этом коде.

</details>

## Итоги

- Покрытие (`cargo llvm-cov`) говорит, какой код выполнялся во время тестов: используйте `--text` или `--html`, чтобы находить дыры, и `--fail-under-lines N` как страховочную сетку в CI.
- 100 % покрытия не значит хорошие тесты: тест без проверок выполняет всё и ничего не проверяет.
- Мутационное тестирование (`cargo mutants`) меняет код мелкими способами и проверяет, что тест падает. Пропущенный мутант — отсутствующий или слабый тест; пойманный — работающий тест.
- Превращайте каждого значимого выжившего в тест. Некоторые выжившие — эквивалентные мутанты, их можно игнорировать.
- Граничные тесты добавляйте сами: инструменты их не придумывают. У обоих инструментов есть слепые пятна.
- Мутационное тестирование медленное; запускайте его на важном или изменённом коде. Держите `mutants.out*` вне Git.
