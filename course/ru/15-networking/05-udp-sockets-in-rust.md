## Новые слова

| Слово | Значение |
|---|---|
| **собеседник** (peer) | Программа на другой стороне разговора. В UDP каждая датаграмма может прийти от другого собеседника. |
| **усечение** (truncation) | Обрезание конца датаграммы, потому что буфер приёма был слишком мал. Остаток теряется. |
| **фрагментация** (fragmentation) | Деление одного IP-пакета, который больше MTU, на несколько пакетов поменьше. Если теряется один фрагмент, теряется вся датаграмма. |
| **идентификатор запроса** (request ID) | Число, которое клиент кладёт в каждый запрос, а сервер копирует в ответ, чтобы клиент мог сопоставить ответы с запросами. |
| **повторная попытка** (retry) | Повторная отправка запроса после тайм-аута, потому что ответ не пришёл. |
| **идемпотентный** (idempotent) | Об операции, которая даёт один и тот же результат, выполнена ли она один раз или несколько. Вслепую повторять безопасно только идемпотентные запросы. |
| **атака с усилением** (amplification attack) | Атака, в которой маленький запрос с поддельным адресом отправителя заставляет сервер отправить большой ответ жертве. |
| **подмена IP-адреса** (IP spoofing) | Отправка пакетов с ложным адресом отправителя. С UDP это просто, потому что нет рукопожатия. |
| **UDP / TCP / IP / MTU** (User Datagram Protocol / Transmission Control Protocol / Internet Protocol / Maximum Transmission Unit — протокол пользовательских датаграмм / протокол управления передачей / межсетевой протокол / максимальный размер передаваемого блока) | Из Уроков 15.1 и 15.3: протокол датаграмм этого урока, потоковый протокол, протокол под ними обоими и самый большой пакет, который может перенести один канал (1500 байт в Ethernet). |
| **DNS, ICMP, QUIC, FIN** | Domain Name System (система доменных имён, классический протокол на UDP); Internet Control Message Protocol (протокол межсетевых управляющих сообщений: ошибки вроде «port unreachable»); QUIC (более новый транспорт поверх UDP, Урок 15.13); флаг TCP «finish» (завершение, Урок 15.3). |

## 1. `UdpSocket`: ни listen, ни accept

У UDP-сервера нет ни `listen`, ни `accept`, потому что нет соединений. Он привязывает сокет и
принимает датаграммы; каждая приходит с адресом своего отправителя. Сохраните как
`src/bin/udp_echo.rs`:

```rust
use std::net::UdpSocket;

fn main() -> std::io::Result<()> {
    let socket = UdpSocket::bind("127.0.0.1:7100")?;
    println!("UDP echo server on {}", socket.local_addr()?);
    let mut buf = [0u8; 1500];
    loop {
        let (n, peer) = socket.recv_from(&mut buf)?;
        println!(
            "{peer}: {n} bytes: {:?}",
            String::from_utf8_lossy(&buf[..n])
        );
        socket.send_to(&buf[..n], peer)?;
    }
}
```

**Что происходит:**

1. `UdpSocket::bind` выполняет системные вызовы `socket` и `bind`. С этого момента ядро доставляет этому
   сокету каждую датаграмму для порта 7100.
2. `recv_from` ждёт следующую датаграмму, копирует её в `buf` и возвращает её длину и адрес
   отправителя (`peer`).
3. `send_to` отправляет одну датаграмму на адрес. Мы отвечаем тому собеседнику, от которого только что
   получили сообщение.
4. Один поток и один сокет обслуживают **всех** клиентов: в ядре нет состояния для каждого клиента.

Запустите его (`cargo run --bin udp_echo`) и во втором терминале отправьте две датаграммы:

```bash
printf "hello\n" | nc -u -w 1 127.0.0.1 7100
printf "second\n" | nc -u -w 1 127.0.0.1 7100
```

Каждый `nc` печатает свою строку обратно (`hello`, затем `second`), а сервер показывает двух разных
собеседников, потому что каждый `nc` получил собственный эфемерный порт:

```text
UDP echo server on 127.0.0.1:7100
127.0.0.1:60033: 6 bytes: "hello\n"
127.0.0.1:50304: 7 bytes: "second\n"
```

`-u` выбирает UDP, а `-w 1` велит `nc` сдаться после секунды тишины (в UDP он не может узнать, что
разговор окончен, ведь FIN нет).

| | TCP (`TcpListener` + `TcpStream`) | UDP (`UdpSocket`) |
|---|---|---|
| Сокеты на сервере | один слушающий + по одному на клиента | один для всех |
| Приём | `read`: несколько байтов потока | `recv_from`: одна целая датаграмма + отправитель |
| Отправка | `write_all`: байты в поток | `send_to`: одна датаграмма на адрес |
| Конец разговора | EOF (`Ok(0)`) | не существует; решайте сами (тайм-аут) |

## 2. Границы, маленькие буферы и большие датаграммы

Датаграммы сохраняют свои границы, но сколько вы получите от каждой, решает буфер, переданный в
`recv_from`. Эта самодостаточная программа отправляет четыре датаграммы и принимает их в буфер из
8 байтов. Сохраните как `src/bin/datagrams.rs`:

```rust
use std::net::UdpSocket;

fn main() -> std::io::Result<()> {
    let server = UdpSocket::bind("127.0.0.1:0")?;
    let client = UdpSocket::bind("127.0.0.1:0")?;
    let server_addr = server.local_addr()?;

    for msg in ["one", "two", "three", "a much longer fourth message"] {
        client.send_to(msg.as_bytes(), server_addr)?;
    }

    let mut buf = [0u8; 8]; // нарочно слишком мал для последнего сообщения
    for _ in 0..4 {
        let (n, from) = server.recv_from(&mut buf)?;
        println!(
            "{n} bytes from {from}: {:?}",
            String::from_utf8_lossy(&buf[..n])
        );
    }

    // Датаграмму больше предела IPv4 вообще нельзя отправить.
    let huge = vec![0u8; 70_000];
    if let Err(e) = client.send_to(&huge, server_addr) {
        println!("70000 bytes: {e} (kind: {:?})", e.kind());
    }
    Ok(())
}
```

`cargo run --bin datagrams`:

```text
3 bytes from 127.0.0.1:51287: "one"
3 bytes from 127.0.0.1:51287: "two"
5 bytes from 127.0.0.1:51287: "three"
8 bytes from 127.0.0.1:51287: "a much l"
70000 bytes: Message too long (os error 40) (kind: Uncategorized)
```

**Что происходит:**

1. Четыре отправки дают ровно четыре приёма. Сравните с `chunks.rs` из Урока 15.4, где две записи TCP
   вышли одним чтением.
2. В четвёртой датаграмме было 28 байтов, а в буфере — 8. Ядро скопировало 8 байтов и **выбросило
   остаток**, без всякой ошибки. Это **усечение**. Всегда используйте буфер размером с самую большую
   датаграмму, которую допускает ваш протокол.
3. Датаграмма UDP поверх IPv4 может нести не больше 65 507 байтов (65 535 минус заголовки IP и UDP).
   Более крупные отправки сразу завершаются ошибкой «Message too long» (в Linux это `os error 90`).

Даже 65 507 байтов на практике слишком много. Датаграмму больше MTU (1500 байтов в Ethernet) IP делит
на **фрагменты**, и если теряется *один* фрагмент, теряется вся датаграмма. Многие сети к тому же
намеренно отбрасывают фрагменты. Поэтому настоящие протоколы на UDP держат датаграммы маленькими:
классические ответы DNS — не больше 512 байтов, а QUIC использует около 1200 байтов.

## 3. `connect` для UDP

`UdpSocket::connect` ничего не отправляет. Он лишь запоминает в ядре **собеседника по умолчанию**.
После этого:

- `send` и `recv` работают без адреса;
- датаграммы с любого *другого* адреса ядро отбрасывает;
- ICMP-ошибки для этого собеседника, например «port unreachable» из Урока 15.3, сообщаются вашей
  программе.

Последний пункт полезен. Сохраните как `src/bin/udp_connect.rs`:

```rust
use std::net::UdpSocket;
use std::time::Duration;

fn main() -> std::io::Result<()> {
    // Находим свободный порт и сразу закрываем его, чтобы там никто не слушал.
    let closed_port = UdpSocket::bind("127.0.0.1:0")?.local_addr()?;

    let socket = UdpSocket::bind("127.0.0.1:0")?;
    socket.set_read_timeout(Some(Duration::from_millis(500)))?;
    socket.connect(closed_port)?; // только задаёт собеседника по умолчанию: пакет не отправляется
    socket.send(b"anybody there?")?;

    let mut buf = [0u8; 64];
    match socket.recv(&mut buf) {
        Ok(n) => println!("got {n} bytes"),
        Err(e) => println!("recv: {e} (kind: {:?})", e.kind()),
    }
    Ok(())
}
```

```text
recv: Connection refused (os error 61) (kind: ConnectionRefused)
```

**Что происходит:**

1. Временный сокет из первой строки уничтожается в конце инструкции, поэтому его порт снова свободен
   и никто его не слушает.
2. `send` завершается успешно: датаграмма уходит. Принимающее ядро отвечает ICMP «port unreachable».
3. Поскольку сокет подключён, ядро передаёт нам это ICMP-сообщение, и `recv` возвращает
   `ConnectionRefused`, а не ждёт до тайм-аута. Неподключённый сокет просто подождал бы 500 мс и
   сообщил `WouldBlock`.

Не полагайтесь на это сообщение: в настоящей сети файрволы часто отбрасывают ICMP. Это быстрая
подсказка, а не гарантия.

## 4. Надёжность — ваша задача

В UDP запрос или ответ на него может потеряться, и никто вам об этом не скажет. Стандартный рецепт:

1. Установите **тайм-аут чтения**.
2. Если ответ не пришёл вовремя, сделайте **повторную попытку**, ограниченное число раз.
3. Кладите в каждый запрос **идентификатор запроса**. Сервер копирует его в ответ. Игнорируйте ответы,
   чей идентификатор не совпадает: это могут быть поздние ответы на прежнюю попытку или чужие
   сообщения.

Эта программа изображает плохую сеть с помощью сервера, который «теряет» каждую вторую датаграмму.
Сохраните как `src/bin/retry.rs`:

```rust
use std::io::{Error, ErrorKind};
use std::net::{SocketAddr, UdpSocket};
use std::thread;
use std::time::{Duration, Instant};

/// A test server that "loses" every second datagram and answers the others.
fn lossy_server(socket: UdpSocket) {
    let mut buf = [0u8; 512];
    let mut count = 0;
    while let Ok((n, peer)) = socket.recv_from(&mut buf) {
        count += 1;
        if count % 2 == 1 {
            continue; // делаем вид, что эта датаграмма потерялась по дороге
        }
        let mut answer = buf[..2].to_vec(); // сохраняем идентификатор запроса
        answer.extend(buf[2..n].to_ascii_uppercase());
        let _ = socket.send_to(&answer, peer);
    }
}

/// Sends `body` with a 2-byte id and waits for the answer with the same id, up to 3 times.
fn request(
    socket: &UdpSocket,
    server: SocketAddr,
    id: u16,
    body: &[u8],
) -> std::io::Result<Vec<u8>> {
    let mut packet = id.to_be_bytes().to_vec();
    packet.extend_from_slice(body);
    let mut buf = [0u8; 512];
    for attempt in 1..=3 {
        socket.send_to(&packet, server)?;
        match socket.recv_from(&mut buf) {
            Ok((n, from)) if from == server && n >= 2 && buf[..2] == id.to_be_bytes() => {
                return Ok(buf[2..n].to_vec());
            }
            Ok(_) => println!("  attempt {attempt}: unexpected datagram, ignored"),
            Err(e) if matches!(e.kind(), ErrorKind::WouldBlock | ErrorKind::TimedOut) => {
                println!("  attempt {attempt}: no answer within the timeout");
            }
            Err(e) => return Err(e),
        }
    }
    Err(Error::new(
        ErrorKind::TimedOut,
        "no answer after 3 attempts",
    ))
}

fn main() -> std::io::Result<()> {
    let server = UdpSocket::bind("127.0.0.1:0")?;
    let server_addr = server.local_addr()?;
    thread::spawn(move || lossy_server(server));

    let socket = UdpSocket::bind("127.0.0.1:0")?;
    socket.set_read_timeout(Some(Duration::from_millis(200)))?;
    for (id, word) in [(1, "hello"), (2, "world")] {
        let start = Instant::now();
        let answer = request(&socket, server_addr, id, word.as_bytes())?;
        println!(
            "id {id}: {:?} after {:?}",
            String::from_utf8_lossy(&answer),
            start.elapsed()
        );
    }
    Ok(())
}
```

`cargo run --bin retry`:

```text
  attempt 1: no answer within the timeout
id 1: "HELLO" after 201.307583ms
  attempt 1: no answer within the timeout
id 2: "WORLD" after 201.188333ms
```

**Что происходит:**

1. Каждый запрос — это 2 байта идентификатора (big-endian, Урок 15.1), за которыми идёт тело. Сервер
   отвечает тем же идентификатором и телом в верхнем регистре.
2. Первая попытка каждого запроса «теряется», поэтому `recv_from` упирается в тайм-аут 200 мс. Клиент
   отправляет тот же пакет ещё раз, и на вторую попытку приходит ответ.
3. Условие ветки проверяет три вещи, прежде чем принять ответ: он пришёл от сервера, он достаточно
   длинный и его идентификатор совпадает. Всё остальное игнорируется.
4. После трёх неудачных попыток `request` возвращает собственную ошибку `TimedOut`, чтобы вызывающий
   код не ждал вечно.

Каждая повторная попытка стоит одного тайм-аута ожидания. Поэтому настоящие клиенты начинают с
короткого тайм-аута и увеличивают его с каждой попыткой (*экспоненциальная задержка*, exponential
backoff), а также ограничивают общее время. К этому вернётся Урок 18.3 (повторные попытки, задержка и
идемпотентность).

> ⚠️ **Частая ошибка: повторять неидемпотентные запросы.** Если потерялся *ответ*, сервер уже один раз
> выполнил работу. Повторить «какой адрес у example.com?» безвредно; повторить «переведи 10 евро» —
> значит, возможно, сделать это дважды. Делайте запросы идемпотентными или пусть сервер помнит
> недавние идентификаторы запросов и отвечает на дубликаты из памяти.

> 🔒 **Безопасность:** UDP-сервер не может знать, настоящий ли адрес отправителя у датаграммы
> (**подмена IP-адреса**). Если крошечный запрос заставляет ваш сервер отправить большой ответ,
> атакующий может подделать адрес жертвы и использовать ваш сервер, чтобы завалить жертву трафиком
> (**атака с усилением**). Правила: для незнакомых собеседников ответы не должны быть больше запросов,
> ограничивайте частоту запросов с каждого адреса и проверяйте каждую датаграмму, прежде чем на неё
> реагировать.

> 🧪 **Тестирование:** тесты UDP легко сделать детерминированными. Привязывайте каждый сокет к
> `127.0.0.1:0`, изображайте потери в тестовом сервере (как `lossy_server`) и держите тайм-ауты
> короткими (50 мс), чтобы тест, который ждёт тайм-аута, всё равно заканчивался быстро. Именно это
> делает Упражнение 2.

## Частые ошибки

> ⚠️ **Частая ошибка: слишком маленький буфер приёма.** Усечённые датаграммы теряют свой конец без
> ошибки. Выбирайте размер буфера под самую большую датаграмму, которую допускает ваш протокол
> (например, 1500 байтов или 65 535, если вы не знаете).

> ⚠️ **Частая ошибка: забыть тайм-аут.** Без `set_read_timeout` клиент, чей запрос потерялся, ждёт в
> `recv_from` вечно. Каждому UDP-клиенту нужен тайм-аут.

> ⚠️ **Частая ошибка: доверять адресу отправителя.** `recv_from` сообщает, откуда датаграмма
> *утверждает*, что пришла. Используйте его, чтобы отправить ответ, а не как доказательство личности.

## Попробуйте сами

1. Запустите `udp_echo` и выполните `nc -u 127.0.0.1 7100` в интерактивном режиме. Введите несколько
   строк. Каждая строка — одна датаграмма, и каждая возвращается.
2. Остановите сервер и введите ещё одну строку в тот же `nc`. Ничего не возвращается. В зависимости от
   версии `nc` либо продолжает ждать, либо молча завершается после ICMP-ошибки из раздела 3; ясного
   сообщения о том, что получателя больше нет, он не получает никогда.
3. В `datagrams.rs` замените буфер на `[0u8; 64]` и проверьте, что четвёртое сообщение приходит
   целиком.
4. В `retry.rs` замените `count % 2 == 1` на `count % 3 != 0` (отвечают только на каждую третью
   датаграмму) и посмотрите, как запросам понадобится по три попытки.

## Упражнения

### Упражнение 1 — UDP-сервер времени (легко)

Напишите `src/bin/time_server.rs`: сервер на `127.0.0.1:7101`, который на любую датаграмму, что бы в
ней ни было, отвечает текущим временем в секундах с 1 января 1970 года (*Unix-время*) и переводом
строки. Проверьте его командой `echo x | nc -u -w 1 127.0.0.1 7101`.

<details>
<summary>Подсказка</summary>

`SystemTime::now().duration_since(UNIX_EPOCH)` из `std::time` даёт `Duration`; `.as_secs()` превращает
его в число. Содержимое запроса можно проигнорировать через `let (_, peer) = ...`.

</details>

<details>
<summary>Ответ</summary>

```rust
use std::net::UdpSocket;
use std::time::{SystemTime, UNIX_EPOCH};

fn main() -> std::io::Result<()> {
    let socket = UdpSocket::bind("127.0.0.1:7101")?;
    let mut buf = [0u8; 64];
    loop {
        let (_, peer) = socket.recv_from(&mut buf)?; // содержимое неважно
        let seconds = SystemTime::now()
            .duration_since(UNIX_EPOCH)
            .expect("the clock is after 1970")
            .as_secs();
        socket.send_to(format!("{seconds}\n").as_bytes(), peer)?;
    }
}
```

`echo x | nc -u -w 1 127.0.0.1 7101` напечатал `1794986824`; ваше число будет больше. Сравните его с
`date +%s` в терминале.

Почему это работает: ответ маленький, а повторный вопрос ничему не вредит, поэтому этому протоколу
вообще не нужны идентификаторы запросов. (Публичный сервер такого рода всё равно был бы небольшим
риском усиления: его ответ длиннее запроса в один байт.)

</details>

### Упражнение 2 — Протестируйте логику повторов (средне)

Добавьте в `retry.rs` модуль `tests` с тремя тестами: (a) `request` успешен, когда первая датаграмма
потерялась (используйте `lossy_server`); (b) он возвращает ошибку вида `TimedOut`, когда никто не
отвечает; (c) он игнорирует ответ с неверным идентификатором и принимает следующий, с верным. Держите
каждый тест быстрым с помощью коротких тайм-аутов.

<details>
<summary>Подсказка</summary>

Для (b) привяжите сокет и просто никогда из него не читайте: датаграммы на него ядро принимает, но
никто на них не отвечает. Для (c) напишите в потоке теста крошечный сервер, который сначала отвечает
байтами `b"\x00\x09stale"` (идентификатор 9), а затем без изменений возвращает повторную попытку.

</details>

<details>
<summary>Ответ</summary>

Добавьте это в конец `retry.rs`:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    fn client(timeout_ms: u64) -> UdpSocket {
        let socket = UdpSocket::bind("127.0.0.1:0").unwrap();
        socket
            .set_read_timeout(Some(Duration::from_millis(timeout_ms)))
            .unwrap();
        socket
    }

    #[test]
    fn retries_after_a_lost_datagram() {
        let server = UdpSocket::bind("127.0.0.1:0").unwrap();
        let addr = server.local_addr().unwrap();
        thread::spawn(move || lossy_server(server));

        let answer = request(&client(50), addr, 7, b"abc").unwrap();
        assert_eq!(answer, b"ABC");
    }

    #[test]
    fn gives_up_when_nobody_answers() {
        let silent = UdpSocket::bind("127.0.0.1:0").unwrap(); // привязан, но никогда не читает
        let addr = silent.local_addr().unwrap();

        let err = request(&client(50), addr, 1, b"hi").unwrap_err();
        assert_eq!(err.kind(), ErrorKind::TimedOut);
    }

    #[test]
    fn ignores_an_answer_with_another_id() {
        let server = UdpSocket::bind("127.0.0.1:0").unwrap();
        let addr = server.local_addr().unwrap();
        thread::spawn(move || {
            let mut buf = [0u8; 64];
            let (_, peer) = server.recv_from(&mut buf).unwrap();
            server.send_to(b"\x00\x09stale", peer).unwrap(); // неверный идентификатор
            let (n, peer) = server.recv_from(&mut buf).unwrap(); // повторная попытка
            server.send_to(&buf[..n], peer).unwrap(); // верный идентификатор
        });

        let answer = request(&client(200), addr, 3, b"fresh").unwrap();
        assert_eq!(answer, b"fresh");
    }
}
```

`cargo test --bin retry` сообщает `test result: ok. 3 passed; ... finished in 0.15s`.

Почему это работает: каждый тест создаёт ровно то поведение сети, которое ему нужно: потерю, тишину,
устаревший ответ. Ничто не зависит от настоящей сети, а самый медленный тест ждёт всего 3 × 50 мс.

</details>

### Упражнение 3 — Ретранслятор чата (сложно)

Напишите `src/bin/relay.rs`: UDP-сервер на `127.0.0.1:7102`, который запоминает каждый адрес, от
которого получил датаграмму, и пересылает каждую датаграмму всем *остальным* известным собеседникам.
Напишите тест с тремя клиентскими сокетами: когда `c` отправляет `hi from c`, её получают и `a`, и
`b`, а сам `c` не получает ничего.

<details>
<summary>Подсказка</summary>

Храните `HashSet<SocketAddr>` собеседников. В тесте подключите (`connect`) каждый клиентский сокет к
ретранслятору, чтобы пользоваться `send` и `recv`, и дайте каждому короткий тайм-аут чтения, чтобы
«не получает ничего» превращалось в ошибку `WouldBlock` после тайм-аута.

</details>

<details>
<summary>Ответ</summary>

```rust
use std::collections::HashSet;
use std::net::{SocketAddr, UdpSocket};

/// Forwards every datagram to all other peers that have ever sent something.
fn relay(socket: UdpSocket) -> std::io::Result<()> {
    let mut peers: HashSet<SocketAddr> = HashSet::new();
    let mut buf = [0u8; 1500];
    loop {
        let (n, from) = socket.recv_from(&mut buf)?;
        peers.insert(from);
        for &peer in peers.iter().filter(|&&p| p != from) {
            socket.send_to(&buf[..n], peer)?;
        }
    }
}

fn main() -> std::io::Result<()> {
    let socket = UdpSocket::bind("127.0.0.1:7102")?;
    println!("relay on {}", socket.local_addr()?);
    relay(socket)
}

#[cfg(test)]
mod tests {
    use super::*;
    use std::thread;
    use std::time::Duration;

    fn peer() -> UdpSocket {
        let s = UdpSocket::bind("127.0.0.1:0").unwrap();
        s.set_read_timeout(Some(Duration::from_millis(300)))
            .unwrap();
        s
    }

    fn recv_text(s: &UdpSocket) -> Option<String> {
        let mut buf = [0u8; 100];
        let n = s.recv(&mut buf).ok()?;
        Some(String::from_utf8_lossy(&buf[..n]).into_owned())
    }

    #[test]
    fn messages_reach_everybody_else() {
        let server = UdpSocket::bind("127.0.0.1:0").unwrap();
        let addr = server.local_addr().unwrap();
        thread::spawn(move || relay(server));

        let (a, b, c) = (peer(), peer(), peer());
        for s in [&a, &b, &c] {
            s.connect(addr).unwrap();
        }
        a.send(b"a joined").unwrap(); // других собеседников ещё не знают
        b.send(b"b joined").unwrap();
        assert_eq!(recv_text(&a).as_deref(), Some("b joined"));
        c.send(b"hi from c").unwrap();
        assert_eq!(recv_text(&a).as_deref(), Some("hi from c"));
        assert_eq!(recv_text(&b).as_deref(), Some("hi from c"));
        assert_eq!(recv_text(&c), None); // отправитель копию не получает
    }
}
```

`cargo test --bin relay` сообщает `1 passed`. Можно попробовать и вручную: запустите ретранслятор и
подключите два-три окна `nc -u 127.0.0.1 7102`; каждое должно сначала ввести строку, чтобы
ретранслятор узнал его адрес.

Почему это работает: один сокет и один цикл обслуживают всех собеседников, потому что UDP не хранит
состояния для собеседника; программа хранит своё состояние (множество собеседников). В настоящем
чате вы бы ещё удаляли собеседников, которые долго молчат, ведь UDP никогда не сообщает, что
собеседник ушёл.

</details>

## Вопросы для самопроверки

1. Почему UDP-серверу не нужны ни `listen`, ни `accept`?

<details>
<summary>Ответ</summary>

В UDP нет соединений. Сокет получает каждую датаграмму, отправленную на его порт, и каждая
датаграмма несёт адрес отправителя, поэтому один сокет может обслуживать всех собеседников.

</details>

2. Собеседник отправляет датаграмму в 2000 байтов, а вы вызываете `recv_from` с буфером на 1500 байтов.
   Что произойдёт?

<details>
<summary>Ответ</summary>

Вы получите первые 1500 байтов; оставшиеся 500 байтов выбрасываются без ошибки (усечение).

</details>

3. Что `UdpSocket::connect` отправляет по сети?

<details>
<summary>Ответ</summary>

Ничего. Он только сохраняет в ядре собеседника по умолчанию; ядро отбрасывает входящие датаграммы с
других адресов и пропускает к программе ICMP-ошибки для этого собеседника.

</details>

4. Зачем UDP-клиент кладёт в каждый запрос идентификатор?

<details>
<summary>Ответ</summary>

Чтобы сопоставлять ответы с запросами. После повторной попытки может прийти поздний ответ на прежнюю
попытку (или чужая датаграмма); идентификатор позволяет клиенту распознать и проигнорировать его.

</details>

5. Почему настоящие датаграммы UDP обычно держат меньше примерно 1200–1400 байтов?

<details>
<summary>Ответ</summary>

Более крупные датаграммы превышают MTU и фрагментируются; потеря любого фрагмента означает потерю
всей датаграммы, а многие сети отбрасывают фрагменты. Маленькие датаграммы идут одним пакетом.

</details>

6. Что такое атака с усилением и почему она хорошо работает с UDP?

<details>
<summary>Ответ</summary>

Атакующий отправляет маленькие запросы, подделав адрес жертвы как адрес отправителя; сервер
отправляет жертве большие ответы. В UDP нет рукопожатия, поэтому сервер не может проверить, что адрес
отправителя настоящий.

</details>

## Итоги

- `UdpSocket::bind`, `recv_from` и `send_to` — всё, что нужно UDP-серверу; один сокет обслуживает всех
  собеседников.
- Каждая отправка — одна датаграмма, каждый приём возвращает одну датаграмму: границы сохраняются, но
  слишком маленький буфер молча усекает данные, а датаграммы больше 65 507 байтов отправить нельзя.
- Держите датаграммы маленькими (заметно меньше MTU), чтобы избежать фрагментации.
- `connect` задаёт собеседника по умолчанию, отсеивает других отправителей и показывает ICMP-ошибки;
  он ничего не отправляет.
- Надёжность — ваша задача: тайм-ауты чтения, ограниченное число повторных попыток, идентификаторы
  запросов и идемпотентные запросы.
- Никогда не доверяйте адресу отправителя; защищайте публичные UDP-сервисы от атак с усилением.
