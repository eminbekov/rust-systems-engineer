# Урок 19.7 — SIMD: одна инструкция, много данных

> **Этап 19 — Производительность и профилирование** · Урок 7 из 11 · ⏱ около 135 минут

## Что вы узнаете

- Что такое SIMD, что такое векторные регистры и линии (lanes) и какой они ширины на вашем Mac и на компьютерах x86-64.
- Как компилятор сам превращает обычные циклы в SIMD-код (автовекторизация) и как проверить это в ассемблере.

- Как безопасно пользоваться интринсиками NEON из `std::arch::aarch64` — с проверкой во время выполнения и тестом против простой версии.

## Новые слова

| Слово | Значение |
|---|---|
| **SIMD** (Single Instruction, Multiple Data, одна инструкция — много данных) | Вид инструкций CPU (Central Processing Unit, центральный процессор), которые выполняют одну и ту же операцию сразу над несколькими значениями, например четыре сложения за одну инструкцию. |
| **скаляр** (scalar) | Одно отдельное значение или код, который работает с одним значением за раз. Противоположность вектору. |
| **векторный регистр** (vector register) | Широкий регистр процессора, в котором рядом лежат несколько значений. На arm64 их 32 — `v0`–`v31`, каждый шириной 128 бит. |
| **линия** (lane) | Одна ячейка векторного регистра. В 128-битном регистре 4 линии по 32 бита или 16 линий по 8 бит. |
| **NEON** | Набор SIMD-инструкций процессоров arm64, в том числе чипов Apple серии M. Он всегда есть на 64-битных Arm. |
| **SSE / AVX** (Streaming SIMD Extensions / Advanced Vector Extensions, потоковые SIMD-расширения / расширенные векторные расширения) | Наборы SIMD-инструкций процессоров x86-64. SSE2 использует 128-битные регистры и есть всегда; AVX2 использует 256-битные регистры и есть только на более новых процессорах. |
| **автовекторизация** (auto-vectorization) | Компилятор сам превращает обычный цикл в SIMD-код, без изменений в вашем исходнике. |
| **интринсик** (intrinsic) | Функция, которую компилятор заменяет одной конкретной инструкцией процессора. `vaddq_f32` становится одной инструкцией NEON `fadd` над четырьмя числами. |
| **целевая возможность** (target feature) | Необязательная часть набора инструкций (например, `neon` или `avx2`), которую компилятор может использовать, только если знает, что она есть у процессора. |
| **свёртка** (reduction) | Объединение всех значений в один результат: сумма, максимум, количество. |
| **горизонтальная операция** (horizontal operation) | Операция между линиями одного регистра, например сложение его четырёх линий друг с другом. |

## 1. Одна инструкция, четыре сложения

Представьте кассира, который сканирует товары по одному. У SIMD-кассира широкий сканер, который считывает четыре товара за одно движение. Работы на каждый товар столько же, а движений вчетверо меньше.

Обычный регистр (`x0`, `w0`) хранит одно число. **Векторный регистр** хранит несколько чисел рядом, в **линиях**. В процессоре arm64 вашего Mac 32 векторных регистра, от `v0` до `v31`, каждый шириной 128 бит. Имена в ассемблере говорят, как регистр разделён:

```text
  v0 as .16b : 16 lanes of 8 bits   (u8, i8)
  v0 as .8h  :  8 lanes of 16 bits  (u16, i16)
  v0 as .4s  :  4 lanes of 32 bits  (u32, i32, f32)
  v0 as .2d  :  2 lanes of 64 bits  (u64, i64, f64)

  add.4s v0, v1, v2      one instruction, four additions:

  v1:  [  1 |  2 |  3 |  4 ]
  v2:  [ 10 | 20 | 30 | 40 ]
        +    +    +    +
  v0:  [ 11 | 22 | 33 | 44 ]
```

Тот же регистр может хранить и одно скалярное значение: тогда в ассемблере он называется `s0` (одно 32-битное число с плавающей точкой) или `d0` (одно 64-битное). Поэтому, читая ассемблер, помните: `fadd s0, s0, s1` складывает **одно** число, а `fadd.4s v0, v0, v1` — **четыре**.

Ширина зависит от семейства процессоров:

| Семейство процессоров | Набор инструкций | Ширина регистра | Значений `f32` за инструкцию |
|---|---|---|---|
| arm64 (ваш Mac, большинство телефонов, многие серверы) | NEON | 128 бит | 4 |
| x86-64, любой процессор | SSE2 | 128 бит | 4 |
| x86-64, более новые процессоры | AVX2 | 256 бит | 8 |
| x86-64, некоторые серверные процессоры | AVX-512 | 512 бит | 16 |

NEON и SSE2 есть всегда, поэтому компилятор использует их по умолчанию. AVX2 и AVX-512 — это **целевые возможности**: компилятор использует их, только если вы скажете ему, что они есть у процессора (это вы сделаете в [Уроке 19.8](08-build-settings-for-speed.md)).

## 2. Автовекторизация: компилятор делает это за вас

SIMD вручную пишут редко. В режиме release компилятор смотрит на каждый цикл и спрашивает: «могу ли я выполнить несколько итераций сразу?» Если да, он сам пишет SIMD-код. Это **автовекторизация**. Поместите это в `src/lib.rs` пакета `code/p19-simd`:

```rust
/// Adds all values. Wraps around on overflow instead of panicking.
#[inline(never)]
pub fn sum_u32(values: &[u32]) -> u32 {
    let mut total = 0u32;
    for &v in values {
        total = total.wrapping_add(v);
    }
    total
}

/// Adds all values one by one, from left to right.
#[inline(never)]
pub fn sum_f32(values: &[f32]) -> f32 {
    let mut total = 0.0;
    for &v in values {
        total += v;
    }
    total
}
```

**Что происходит:**

1. `#[inline(never)]` оставляет каждую функцию настоящей функцией, чтобы `cargo asm` мог её показать (Урок 12.7).
2. `wrapping_add` говорит, что делать при переполнении: заворачиваться (Урок 12.2). Так результат одинаков в сборках debug и release.
3. Обе функции делают одно и то же: **свёртку** среза в одно число.

Теперь посмотрите ассемблер целочисленной версии (здесь и дальше строки-директивы, начинающиеся с `.`, опущены):

```bash
cd ~/projects/rust/code/p19-simd
cargo asm --lib p19_simd::sum_u32
```

Важная часть — основной цикл:

```text
LBB3_7:
	ldp q4, q5, [x8, #-32]
	ldp q6, q7, [x8], #64
	add.4s v0, v4, v0
	add.4s v1, v5, v1
	add.4s v2, v6, v2
	add.4s v3, v7, v3
	subs x14, x14, #16
	b.ne LBB3_7
	add.4s v0, v1, v0
	add.4s v0, v2, v0
	add.4s v0, v3, v0
	addv.4s s0, v0
```

**Что происходит:**

1. `ldp q4, q5, [x8, #-32]` загружает из памяти *пару* 128-битных регистров (`q4` и `q5` — 128-битные имена `v4` и `v5`): 8 чисел. Следующая строка загружает ещё 8. Значит, один проход цикла читает 16 чисел.
2. Каждая из четырёх строк `add.4s` прибавляет 4 числа к векторной промежуточной сумме. Сумм четыре, `v0`–`v3`, поэтому четыре сложения не ждут друг друга. Это идея «четырёх цепочек» из Урока 12.6, только сделанная компилятором, и каждая цепочка шириной в 4 линии.
3. `subs x14, x14, #16` уменьшает счётчик на 16 чисел, а `b.ne` прыгает назад, пока числа остаются.
4. После цикла три строки `add.4s` объединяют четыре суммы в один регистр. `addv.4s s0, v0` — **горизонтальное** сложение: оно складывает 4 линии `v0` в одно число.
5. Код, который здесь не показан, обрабатывает последние несколько чисел, если длина не кратна 16.

(Номера меток вроде `LBB3_7` и номера регистров у вас могут отличаться, как и в Уроке 12.7.)

В исходнике один простой цикл. Машинный код делает 16 сложений за проход. Вы получили это бесплатно.

Теперь версия с числами с плавающей точкой:

```bash
cargo asm --lib p19_simd::sum_f32
```

(Позже, когда с `sum_f32` будут начинаться и другие имена, `cargo asm` вместо этого покажет нумерованный список совпадений; тогда добавьте номер, например `cargo asm --lib p19_simd::sum_f32 0`.) Основной цикл:

```text
LBB2_3:
	ldp s1, s2, [x12, #-8]
	ldp s3, s4, [x12], #16
	fadd s0, s0, s1
	fadd s0, s0, s2
	fadd s0, s0, s3
	fadd s0, s0, s4
	subs x14, x14, #4
	b.ne LBB2_3
```

**Что происходит:**

1. Загрузки используют `s1`…`s4`: по одному числу. Нигде нет `.4s`.
2. Все четыре строки `fadd` пишут в `s0` и читают `s0`. Каждое сложение должно ждать предыдущего: одна длинная цепочка зависимостей.
3. Компилятор развернул цикл (четыре сложения за проход, чтобы меньше тратить на счётчик), но **не** векторизовал его.

Почему такая разница? Вы узнали это в Уроке 12.3: для чисел с плавающей точкой `(a + b) + c` не всегда равно `a + (b + c)`. SIMD-сумма складывает числа в *другом порядке* (линия 0 получает значения 0, 4, 8, …, линия 1 — 1, 5, 9, …). Для целых чисел порядок не важен, и компилятор может так сделать. Для чисел с плавающей точкой это изменило бы результат, а компилятор никогда не меняет ваш результат только ради скорости.

## 3. Помогаем компилятору: напишите нужный порядок

Если *вы* согласны на другой порядок, напишите его в коде. Держите 8 отдельных промежуточных сумм («линий») и сложите их в конце. Добавьте в `src/lib.rs`:

```rust
/// Adds the values in 8 separate running totals ("lanes"), then adds the lanes.
#[inline(never)]
pub fn sum_f32_lanes(values: &[f32]) -> f32 {
    let mut lanes = [0.0f32; 8];
    let (chunks, rest) = values.as_chunks::<8>();
    for chunk in chunks {
        for (lane, &v) in lanes.iter_mut().zip(chunk) {
            *lane += v;
        }
    }
    let mut total: f32 = lanes.iter().sum();
    for &v in rest {
        total += v;
    }
    total
}
```

**Что происходит:**

1. `values.as_chunks::<8>()` делит срез на две части: срез массивов `[f32; 8]` (столько полных групп по 8, сколько поместится) и `rest` — обычный срез с оставшимися 0–7 значениями.
2. В каждой группе значение номер `i` попадает в `lanes[i]`. Линия 0 получает значения 0, 8, 16, …; линия 1 — значения 1, 9, 17, …. Это тот порядок, который использует SIMD-сумма, и теперь он записан в исходнике.
3. Группа — это массив фиксированной длины 8, поэтому компилятор знает, что во внутреннем цикле ровно 8 шагов и проверки границ не нужны.
4. В конце 8 линий складываются вместе, а потом добавляется остаток.

Проверьте ассемблер командой `cargo asm --lib p19_simd::sum_f32_lanes`:

```text
LBB1_2:
	ldp q2, q3, [x11], #32
	fadd.4s v0, v3, v0
	fadd.4s v1, v2, v1
	subs x10, x10, #32
	b.ne LBB1_2
```

Восемь сложений за проход, в двух независимых векторных цепочках (`v0` и `v1`, по 4 линии). Массив `lanes` живёт в двух векторных регистрах и никогда не попадает в память.

> 📏 **Соглашение:** Clippy (Урок 05.6) предупреждает о `chunks_exact(8)` с постоянным размером и предлагает `as_chunks::<8>()`. Если размер постоянный, предпочитайте `as_chunks`: вы получаете настоящие массивы, и компилятор знает длину.

### Результат тот же?

Не всегда, и это нужно знать. Поместите это в `examples/order.rs`:

```rust
use p19_simd::{sum_f32, sum_f32_lanes};

fn main() {
    let values = vec![0.1f32; 1_000_000];
    println!("one by one: {}", sum_f32(&values));
    println!("8 lanes:    {}", sum_f32_lanes(&values));
    println!("exact:      {}", 0.1f64 * 1_000_000.0);
}
```

Запустите `cargo run --release --example order`:

```text
one by one: 100958.34
8 lanes:    99910.32
exact:      100000
```

**Что происходит:**

1. Миллион раз `0.1`. Точный ответ — 100 000.
2. Сумма по одному ошибается почти на 1 000. Когда `total` становится большим, каждое маленькое `0.1` при сложении с ним сильно округляется.
3. Сумма по 8 линиям ошибается примерно на 90. Каждая линия вырастает лишь примерно до 12 500, поэтому каждое сложение теряет меньше. Версия с линиями быстрее *и* здесь точнее, но она **другая**. Если программа должна печатать в точности те же числа, что и раньше (в Уроке 19.10 есть такой тест), изменённый порядок суммирования может это сломать.

## 4. Измеряем разницу

Поместите это в `src/main.rs`. Здесь используется идея `black_box` из Урока 05.12 и берётся лучший из пяти запусков, чтобы уменьшить шум:

```rust
use std::hint::black_box;
use std::time::{Duration, Instant};

use p19_simd::{sum_f32, sum_f32_lanes, sum_f32_neon, sum_u32};

const LEN: usize = 4096; // 16 KiB of data: it stays in the L1 cache
const ROUNDS: u32 = 20_000;

/// Runs `f` ROUNDS times, five times over, and prints the fastest time per call.
fn time<T: std::fmt::Display>(name: &str, mut f: impl FnMut() -> T) {
    let mut best = Duration::MAX;
    let mut result = None;
    for _ in 0..5 {
        let start = Instant::now();
        for _ in 0..ROUNDS {
            result = Some(black_box(f()));
        }
        best = best.min(start.elapsed() / ROUNDS);
    }
    println!("{name:<14} {best:>9.2?} per call  (result {})", result.unwrap());
}

fn main() {
    let ints: Vec<u32> = (0..LEN as u32).collect();
    let floats: Vec<f32> = (0..LEN).map(|i| (i % 10) as f32 * 0.5).collect();

    time("sum_u32", || sum_u32(black_box(&ints)));
    time("sum_f32", || sum_f32(black_box(&floats)));
    time("sum_f32_lanes", || sum_f32_lanes(black_box(&floats)));
    time("sum_f32_neon", || sum_f32_neon(black_box(&floats)));
}
```

`sum_f32_neon` появится в разделе 5; добавьте её перед запуском. Вывод `cargo run --release` на M4 (ваши числа будут другими):

```text
sum_u32         139.00ns per call  (result 8386560)
sum_f32           2.90µs per call  (result 9210)
sum_f32_lanes   304.00ns per call  (result 9210)
sum_f32_neon    625.00ns per call  (result 9210)
```

**Что происходит:**

1. 4 096 чисел по одному занимают около 2,9 мкс (микросекунды): около 0,7 нс на сложение — это задержка одного сложения с плавающей точкой на этом процессоре. Скорость определяет цепочка.
2. Версия с 8 линиями примерно в **9 раз быстрее** с тем же результатом. Причин две сразу: 4 значения за инструкцию (SIMD) и две независимые цепочки вместо одной.
3. Целочисленная сумма быстрее всех: четыре векторные цепочки, 16 значений за проход.
4. Данные — небольшие числа вроде 0.5 и 4.5, поэтому каждая сумма точна и все версии печатают одинаковые 9210.

> ⚡ **Производительность:** SIMD помогает больше всего, когда данные уже в кэше. Когда данные идут из основной памяти, пределом может стать **пропускная способность памяти** (сколько байтов в секунду выдаёт память, Урок 12.9), и тогда более широкая инструкция не ускорит работу. Всегда измеряйте на данных реалистичного размера.

## 5. Пишем SIMD вручную: интринсики NEON

Иногда компилятор не находит SIMD-версию, а вы точно знаете, какие инструкции вам нужны. Тогда используют **интринсики**: функции из `std::arch`, каждая из которых становится одной инструкцией процессора. Интринсики NEON лежат в `std::arch::aarch64`. Их имена — короткие коды; например, `vaddq_f32` означает «**v**ector **add** (векторное сложение), **q** — полный 128-битный регистр, значения **f32**». Добавьте в `src/lib.rs`:

```rust
#[cfg(target_arch = "aarch64")]
#[target_feature(enable = "neon")]
fn sum_f32_neon_inner(values: &[f32]) -> f32 {
    use std::arch::aarch64::{vaddq_f32, vaddvq_f32, vdupq_n_f32, vld1q_f32};

    let (chunks, rest) = values.as_chunks::<4>();
    let mut acc = vdupq_n_f32(0.0);
    for chunk in chunks {
        // SAFETY: `chunk` is a [f32; 4], so reading 4 values (16 bytes) stays in bounds.
        let v = unsafe { vld1q_f32(chunk.as_ptr()) };
        acc = vaddq_f32(acc, v);
    }
    let mut total = vaddvq_f32(acc);
    for &v in rest {
        total += v;
    }
    total
}

/// Adds the values with NEON instructions, 4 at a time.
#[cfg(target_arch = "aarch64")]
#[inline(never)]
pub fn sum_f32_neon(values: &[f32]) -> f32 {
    if std::arch::is_aarch64_feature_detected!("neon") {
        // SAFETY: we have just checked that this CPU supports NEON.
        unsafe { sum_f32_neon_inner(values) }
    } else {
        sum_f32(values)
    }
}
```

**Что происходит:**

1. `#[cfg(target_arch = "aarch64")]` компилирует эти функции только для arm64. На других процессорах их нет (программе для x86-64 понадобилась бы своя версия или никакой).
2. `#[target_feature(enable = "neon")]` говорит: «внутри этой функции компилятор может использовать NEON». Внутри такой функции интринсики, которые только вычисляют над значениями, можно вызывать безопасно.
3. `vdupq_n_f32(0.0)` создаёт вектор с `0.0` во всех 4 линиях. Его тип — `float32x4_t`: четыре `f32` в одном регистре.
4. `vld1q_f32(ptr)` загружает 4 числа из памяти. Она принимает сырой указатель, поэтому она `unsafe`: Rust не может проверить, что там можно прочитать 16 байт. Комментарий `// SAFETY:` объясняет, почему всё в порядке: кусок — массив ровно из 4 элементов.
5. `vaddq_f32` складывает 4 линии с 4 линиями. `vaddvq_f32` — горизонтальная сумма 4 линий.
6. Публичная функция сначала спрашивает процессор во время выполнения, есть ли у него NEON (`is_aarch64_feature_detected!`). Только после этого она вызывает внутреннюю функцию, вызов которой из кода без этой возможности — `unsafe`: вызвать её на процессоре без NEON было бы неопределённым поведением.

На arm64 проверка всегда истинна, и компилятор это знает: в release-ассемблере `sum_f32_neon` проверки нет, а цикл состоит просто из `ldr q1` (загрузить 4 числа) и `fadd.4s v0, v0, v1`. Схему «проверить во время выполнения, затем вызвать функцию с `#[target_feature]`» всё равно стоит выучить, потому что на x86-64 она нужна по-настоящему: AVX2 есть не на каждом процессоре (`is_x86_feature_detected!("avx2")`).

Посмотрите ещё раз на замеры в разделе 4: написанная вручную версия NEON (625 нс) **медленнее** простой версии с линиями на Rust (304 нс). У неё только одна векторная цепочка, `acc`, поэтому каждая `fadd.4s` ждёт предыдущую. SIMD, написанный вручную, не становится быстрым автоматически; Упражнение 3 это исправит.

> 🧪 **Тестирование:** каждой SIMD-функции нужен тест, который сравнивает её с простой версией на **многих длинах**, включая 0, 1, кратную ширине и на единицу больше кратной. Большинство ошибок SIMD живёт в части `rest`.

Добавьте этот модуль тестов в конец `src/lib.rs`:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    fn close(a: f32, b: f32) -> bool {
        (a - b).abs() <= 1e-4 * a.abs().max(b.abs()).max(1.0)
    }

    #[test]
    fn every_length_from_0_to_40_gives_the_same_sum() {
        for len in 0..=40 {
            let values: Vec<f32> = (0..len).map(|i| i as f32 * 0.25).collect();
            let expected = sum_f32(&values);
            assert!(close(sum_f32_lanes(&values), expected), "lanes, len {len}");
            #[cfg(target_arch = "aarch64")]
            assert!(close(sum_f32_neon(&values), expected), "neon, len {len}");
        }
    }

    #[test]
    fn integer_sum_wraps_instead_of_panicking() {
        assert_eq!(sum_u32(&[u32::MAX, 2]), 1);
    }
}
```

`close` сравнивает числа с допуском относительно их величины (Урок 12.3), потому что разный порядок суммирования может округлять по-разному. Цикл покрывает случаи «ни одной полной группы», «ровно полные группы» и все возможные размеры `rest`. `cargo test`:

```text
test tests::every_length_from_0_to_40_gives_the_same_sum ... ok
test tests::integer_sum_wraps_instead_of_panicking ... ok

test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

### Переносимый SIMD ещё не стабилен

Интринсики привязаны к одному семейству процессоров. В стандартной библиотеке есть и **переносимый** модуль SIMD, `std::simd`, с типами вроде `f32x4`, которые работают на любом процессоре. В Rust 1.100 он всё ещё **только в nightly**. На стабильном Rust:

```rust
use std::simd::f32x4;

fn main() {
    let a = f32x4::from_array([1.0, 2.0, 3.0, 4.0]);
    println!("{:?}", a + a);
}
```

```text
error[E0658]: use of unstable library feature `portable_simd`
 --> src/main.rs:1:5
  |
1 | use std::simd::f32x4;
  |     ^^^^^^^^^^^^^^^^
  |
  = note: see issue #86656 <https://github.com/rust-lang/rust/issues/86656> for more information
```

На стабильном Rust пишите простые циклы, которые компилятор может векторизовать (разделы 2–3), используйте интринсики за `#[cfg]` или берите крейт, в котором SIMD-код уже написан: например, `memchr` (быстрый поиск байтов, его используют `regex` и многие другие).

## 6. Что мешает автовекторизации

Прежде чем писать интринсики, проверьте, почему компилятор не векторизовал цикл. Обычные причины:

| Причина | Пример | Что делать |
|---|---|---|
| Порядок сложения чисел с плавающей точкой | `total += v` для `f32`/`f64` | Напишите линии сами (раздел 3), если другой порядок допустим. |
| Ранний выход | `values.iter().position(\|&b\| b == 0)` | Цикл может остановиться на любом элементе. Используйте крейт (`memchr`) или интринсики. |
| Каждый шаг нужен следующему | промежуточная сумма, записываемая в массив: `out[i] = out[i - 1] + a[i]` | Обычно просто так не векторизуется; выберите другой алгоритм. |
| Вызов внутри цикла | вызов функции, которая не встраивается | Сделайте так, чтобы её можно было встроить (маленькая, в том же крейте или `#[inline]`). |
| Разные или неизвестные длины | индексация `a[i]`, `b[i]`, `out[i]` одним `i` | Идите по `zip` или сначала обрежьте все срезы до одной длины; тогда компилятор уберёт проверки границ. |

Каждый случай можно проверить в ассемблере: ищите в цикле `.4s`, `.16b`, `.2d` и регистры `q`.

На x86-64 та же `sum_u32` по умолчанию использует 128-битный SSE2 (`paddd xmm0, xmm1`), а 256-битный AVX2 — только если вы разрешите эту целевую возможность. Оба варианта можно увидеть прямо на Mac (нужна целевая платформа x86-64 из Урока 12.7). `RUSTFLAGS` — переменная окружения с дополнительными параметрами компилятора (её объясняет Урок 19.8):

```bash
cargo asm --lib --target x86_64-unknown-linux-gnu p19_simd::sum_u32 | grep padd
RUSTFLAGS="-C target-cpu=x86-64-v3" cargo asm --lib --target x86_64-unknown-linux-gnu p19_simd::sum_u32 | grep padd
```

```text
	paddd xmm1, xmm2
	paddd xmm0, xmm2
	...
	vpaddd ymm0, ymm0, ymmword ptr [rdi + 4*rax]
	vpaddd ymm1, ymm1, ymmword ptr [rdi + 4*rax + 32]
	...
```

Регистры `xmm` — 128 бит, регистры `ymm` — 256 бит. Тот же исходник, вдвое большая ширина, но такая программа упадёт с ошибкой «illegal instruction» (недопустимая инструкция) на старом процессоре x86-64 без AVX2.

> 🔒 **Безопасность:** `unsafe`-код с SIMD читает память через сырые указатели. Ошибка в расчёте длины приводит к чтению за концом среза: это неопределённое поведение, и оно может раскрыть чужие данные. Загружайте через указатель только куски фиксированного размера (`as_chunks`), как в разделе 5, и тестируйте все длины.

## Частые ошибки

> ⚠️ **Частая ошибка:** вызов интринсика в обычной функции. Без `#[target_feature(enable = "neon")]` на функции каждый интринсик NEON вызывать `unsafe`, хотя на вашем Mac NEON всегда включён:
>
> ```text
> error[E0133]: call to function `vaddq_f32` with `#[target_feature]` is unsafe and requires unsafe block
>   --> src/lib.rs:46:15
>    |
> 46 |         acc = vaddq_f32(acc, v);
>    |               ^^^^^^^^^^^^^^^^^ call to function with `#[target_feature]`
>    |
>    = help: in order for the call to be safe, the context requires the following additional target feature: neon
>    = note: the neon target feature being enabled in the build configuration does not remove the requirement to list it in `#[target_feature]`
> ```
>
> Исправление: вынесите SIMD-цикл в отдельную функцию с `#[target_feature(enable = "neon")]`, как в разделе 5, и вызывайте её из обёртки после проверки во время выполнения.

> ⚠️ **Частая ошибка:** забыть про `rest`. Цикл по `as_chunks::<4>()` молча пропускает последние 1–3 значения. Тест с длинами 0..=40 сразу это находит.

> ⚠️ **Частая ошибка:** ждать в точности того же результата с плавающей точкой. SIMD-сумма складывает в другом порядке, поэтому последние цифры могут отличаться. Сравнивайте с допуском или сохраняйте старый порядок там, где важен точный вывод.

## Упражнения

### Упражнение 1 — Векторизуется ли `max`? (легко)

Добавьте `pub fn max_i32(values: &[i32]) -> Option<i32>`, которая возвращает `values.iter().copied().max()`, пометьте её `#[inline(never)]` и посмотрите её ассемблер. Векторизована ли она? Какая инструкция находит максимум сразу по 4 линиям?

<details>
<summary>Подсказка</summary>

Ищите в основном цикле инструкцию с `.4s`, а после цикла — инструкцию, оканчивающуюся на `v` (как `addv`).

</details>

<details>
<summary>Ответ</summary>

```rust
#[inline(never)]
pub fn max_i32(values: &[i32]) -> Option<i32> {
    values.iter().copied().max()
}
```

Да, она векторизована. Основной цикл `cargo asm --lib p19_simd::max_i32`:

```text
	smax.4s v0, v0, v4
	smax.4s v1, v1, v5
	smax.4s v2, v2, v6
	smax.4s v3, v3, v7
	...
	smaxv.4s s0, v0
```

Почему это работает: `smax.4s` («signed maximum», знаковый максимум) берёт большее значение в каждой линии; `smaxv.4s` — горизонтальный максимум 4 линий. Максимум целых чисел не зависит от порядка, поэтому компилятор может свободно его векторизовать, как и целочисленную сумму.

</details>

### Упражнение 2 — Скалярное произведение по линиям, с тестом (средне)

Скалярное произведение двух срезов — это `a[0]*b[0] + a[1]*b[1] + …`. Напишите `dot(a, b)` простым способом (через `zip`, `map`, `sum`) и `dot_lanes(a, b)` с 8 линиями, как `sum_f32_lanes`. Используйте только первые `min(a.len(), b.len())` значений. Затем напишите тест, который сравнивает их на всех длинах от 0 до 40.

<details>
<summary>Подсказка</summary>

Сначала обрежьте оба среза до одной длины: `let (a, b) = (&a[..len], &b[..len]);`. Потом вызовите `as_chunks::<8>()` у обоих и объедините куски через `zip`.

</details>

<details>
<summary>Ответ</summary>

```rust
pub fn dot(a: &[f32], b: &[f32]) -> f32 {
    a.iter().zip(b).map(|(x, y)| x * y).sum()
}

pub fn dot_lanes(a: &[f32], b: &[f32]) -> f32 {
    let len = a.len().min(b.len());
    let (a, b) = (&a[..len], &b[..len]);
    let (a_chunks, a_rest) = a.as_chunks::<8>();
    let (b_chunks, b_rest) = b.as_chunks::<8>();
    let mut lanes = [0.0f32; 8];
    for (ca, cb) in a_chunks.iter().zip(b_chunks) {
        for ((lane, x), y) in lanes.iter_mut().zip(ca).zip(cb) {
            *lane += x * y;
        }
    }
    let mut total: f32 = lanes.iter().sum();
    for (x, y) in a_rest.iter().zip(b_rest) {
        total += x * y;
    }
    total
}

#[cfg(test)]
mod dot_tests {
    use super::*;

    #[test]
    fn dot_lanes_matches_simple_dot_for_many_lengths() {
        for len in 0..=40 {
            let a: Vec<f32> = (0..len).map(|i| i as f32 * 0.5).collect();
            let b: Vec<f32> = (0..len).map(|i| 3.0 - i as f32 * 0.25).collect();
            let expected = dot(&a, &b);
            let got = dot_lanes(&a, &b);
            assert!((got - expected).abs() <= 1e-3, "len {len}: {got} vs {expected}");
        }
    }
}
```

```text
test dot_tests::dot_lanes_matches_simple_dot_for_many_lengths ... ok
```

Почему это работает: оба среза одной длины, поэтому и части `rest` у них одной длины. В режиме release цикл становится `fmul.4s` и `fadd.4s` в двух векторных цепочках. Тест покрывает все возможные размеры остатка.

</details>

### Упражнение 3 — Две цепочки NEON (сложно)

Версия NEON из раздела 5 имеет одну цепочку и медленнее `sum_f32_lanes`. Напишите `sum_f32_neon2`, которая за проход обрабатывает 8 чисел в два аккумулятора, `acc0` и `acc1`, и складывает их в конце. Сохраните проверку во время выполнения и комментарии `// SAFETY:`, добавьте функцию в тест из раздела 5, затем измерьте время.

<details>
<summary>Подсказка</summary>

Используйте `as_chunks::<8>()`. Загрузите первые 4 значения через `vld1q_f32(chunk.as_ptr())`, а следующие 4 — через `vld1q_f32(chunk.as_ptr().add(4))`. В конце: `vaddvq_f32(vaddq_f32(acc0, acc1))`.

</details>

<details>
<summary>Ответ</summary>

```rust
#[cfg(target_arch = "aarch64")]
#[target_feature(enable = "neon")]
fn sum_neon2_inner(values: &[f32]) -> f32 {
    use std::arch::aarch64::{vaddq_f32, vaddvq_f32, vdupq_n_f32, vld1q_f32};

    let (chunks, rest) = values.as_chunks::<8>();
    let mut acc0 = vdupq_n_f32(0.0);
    let mut acc1 = vdupq_n_f32(0.0);
    for chunk in chunks {
        // SAFETY: `chunk` is a [f32; 8]; we read values 0..4 and 4..8, both in bounds.
        let (v0, v1) = unsafe { (vld1q_f32(chunk.as_ptr()), vld1q_f32(chunk.as_ptr().add(4))) };
        acc0 = vaddq_f32(acc0, v0);
        acc1 = vaddq_f32(acc1, v1);
    }
    let mut total = vaddvq_f32(vaddq_f32(acc0, acc1));
    for &v in rest {
        total += v;
    }
    total
}

#[cfg(target_arch = "aarch64")]
#[inline(never)]
pub fn sum_f32_neon2(values: &[f32]) -> f32 {
    if std::arch::is_aarch64_feature_detected!("neon") {
        // SAFETY: we have just checked that this CPU supports NEON.
        unsafe { sum_neon2_inner(values) }
    } else {
        values.iter().sum()
    }
}
```

Почему это работает: `acc0` и `acc1` не зависят друг от друга, поэтому процессор выполняет их сложения параллельно. Время падает примерно до времени `sum_f32_lanes` (около 300 нс на M4), потому что теперь это тот же машинный код, который компилятор сделал из простой версии с линиями. Вот настоящий урок: простая версия на Rust была так же быстра и не требует `unsafe`.

</details>

## Вопросы для самопроверки

1. Что такое линия и сколько линий `u8` в 128-битном регистре?

<details>
<summary>Ответ</summary>

Линия — одна ячейка векторного регистра. В 128-битном регистре 16 линий по 8 бит, то есть 16 значений `u8`.

</details>

2. Почему компилятор векторизует сумму `u32`, но не сумму `f32`?

<details>
<summary>Ответ</summary>

SIMD-сумма складывает значения в другом порядке. Для целых чисел (с заворачиванием) результат одинаков при любом порядке. Для чисел с плавающей точкой из-за округления результат зависит от порядка, а компилятор не должен менять ваши результаты.

</details>

3. Почему `sum_f32_lanes` и быстрее, и отличается в последних цифрах?

<details>
<summary>Ответ</summary>

Быстрее: компилятор кладёт 8 линий в два векторных регистра и делает 8 сложений за проход в двух независимых цепочках. Отличается: сложения идут в другом порядке и поэтому округляются по-другому.

</details>

4. Что разрешает `#[target_feature(enable = "neon")]` и почему такую функцию тогда `unsafe` вызывать из обычного кода?

<details>
<summary>Ответ</summary>

Внутри функции компилятор может использовать инструкции NEON, а интринсики, работающие только со значениями, можно вызывать безопасно. Если бы такая функция выполнилась на процессоре без этой возможности, процессор встретил бы неизвестную инструкцию: неопределённое поведение. Поэтому вызывающий код должен гарантировать наличие возможности — обычно через `is_aarch64_feature_detected!` или `is_x86_feature_detected!`.

</details>

5. Почему `vld1q_f32` — `unsafe` даже внутри функции с `#[target_feature]`?

<details>
<summary>Ответ</summary>

Она читает 16 байт через сырой указатель. Компилятор не может проверить, что эти байты лежат внутри допустимого среза; это должен гарантировать программист.

</details>

6. Можно ли использовать `std::simd` на стабильном Rust 1.100?

<details>
<summary>Ответ</summary>

Нет. Переносимый SIMD (`std::simd`, фича `portable_simd`) всё ещё только в nightly. На стабильном Rust пишите векторизуемые циклы, используйте интринсики `std::arch` или крейты вроде `memchr`.

</details>

## Итоги

- SIMD-инструкции выполняют одну операцию сразу над несколькими значениями. На arm64 (NEON) векторный регистр — 128 бит: 4 `f32`, 16 `u8`. На x86-64 SSE2 — 128 бит, AVX2 — 256 бит.
- В режиме release компилятор **автовекторизует** простые циклы. Проверяйте это в `cargo asm`: ищите в цикле `.4s`, `.16b` и регистры `q`.
- Свёртки чисел с плавающей точкой не векторизуются, потому что другой порядок даёт другой результат. Напишите линии сами (`as_chunks::<8>()` и массив сумм), если другой результат допустим.
- Несколько независимых цепочек важны так же, как ширина SIMD: одна векторная цепочка оказалась медленнее двух.
- Интринсики из `std::arch::aarch64` помещают в функцию с `#[target_feature(enable = "neon")]`, которую вызывают после проверки во время выполнения; загрузкам через указатель нужен `unsafe` с комментарием `// SAFETY:`.
- Тестируйте каждую SIMD-функцию против простой версии на многих длинах, с допуском для чисел с плавающей точкой.
- `std::simd` (переносимый SIMD) в Rust 1.100 всё ещё только в nightly.

## Источники и что почитать

- [Модуль `std::arch`](https://doc.rust-lang.org/std/arch/index.html) — официальная документация по интринсикам для конкретных процессоров, проверке во время выполнения и `#[target_feature]`.
- [`core::arch::aarch64`](https://doc.rust-lang.org/core/arch/aarch64/index.html) — список всех интринсиков NEON в Rust (`std::arch::aarch64` — тот же модуль).
- [The Rust Reference — The `target_feature` attribute](https://doc.rust-lang.org/reference/attributes/codegen.html) — точные правила для `#[target_feature]` и того, когда вызовы безопасны.
- [Arm C Language Extensions — Advanced SIMD (Neon) intrinsics](https://arm-software.github.io/acle/neon_intrinsics/advsimd.html) — спецификация Arm для каждого интринсика NEON и инструкции, в которую он превращается.
- [`slice::as_chunks`](https://doc.rust-lang.org/std/primitive.slice.html) — метод среза из этого урока (найдите на странице `as_chunks`).
- [`std::simd` (nightly)](https://doc.rust-lang.org/std/simd/index.html) — модуль переносимого SIMD, который ещё не стабилен.
- [The Rust Performance Book](https://nnethercote.github.io/perf-book/) — практические советы, как ускорять программы на Rust.
