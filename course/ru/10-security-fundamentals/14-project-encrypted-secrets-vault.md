# Урок 10.14 — Проект: зашифрованное хранилище секретов

> **Этап 10 — Основы безопасности** · Урок 14 из 15 · ⏱ около 8 часов (4 занятия)

## Что вы узнаете

- Как объединить хеш пароля (Argon2id), аутентифицированное шифрование (XChaCha20-Poly1305), безопасную случайность и затирание памяти в один работающий инструмент.
- Как спроектировать небольшой двоичный формат файла с версией, солью, nonce и параметрами и как безопасно читать его, когда файлу нельзя доверять.
- Как тестировать свойства безопасности: неверный пароль, подмену любого байта, мусорный ввод.
- Как не пускать секреты в логи, командные строки, сообщения об ошибках и (насколько это позволяет Rust) в память.
- Как написать краткую модель угроз и README для инструмента безопасности.

Это **проектный урок**. Он не даёт готовую программу. Он даёт цель (контракт), план с вехами, подсказки и команды, которые доказывают, что веха выполнена.

## Новые слова

| Слово | Значение |
|---|---|
| **хранилище** (vault) | Файл, хранящий именованные секреты в зашифрованном виде. |
| **мастер-пароль** (master password) | Единственный пароль, из которого получают ключ шифрования. Если его забыть, данные не восстановить. |
| **параметры KDF** (KDF parameters; KDF, key derivation function, функция формирования ключа: превращает пароль в ключ) | Настройки стоимости Argon2: память (`m_cost`, в KiB, кибибайтах), проходы (`t_cost`) и параллелизм (`p_cost`). Чем выше стоимость, тем медленнее перебор у атакующего и тем медленнее разблокировка у вас. |
| **заголовок файла** (file header) | Первые байты файла, описывающие его формат (здесь: магические байты, версия, параметры KDF, соль). |
| **магические байты** (magic bytes) | Фиксированная последовательность в начале файла, которая говорит, какого он типа (здесь `VLT1`). |
| **атомарная запись** (atomic write) | Запись файла, при которой сбой оставляет либо полный старый файл, либо полный новый, но не наполовину записанный. Делается через временный файл и `rename`. |
| **модель угроз** (threat model) | Короткий список того, что вы защищаете, от кого, и от чего **не** защищаете (Урок 10.2). |
| **`Zeroizing<T>`** | Обёртка из крейта `zeroize`, которая перезаписывает значение нулями при освобождении. |
| **права `0600`** (permissions) | Режим файла Unix: читать и писать файл может только владелец. Права объясняются в Уроке 11.4; здесь вам нужно лишь выставить этот один режим. |

## Проект

### Что вы создадите

`vault` — инструмент командной строки, хранящий именованные секреты (токены API, Application Programming Interface; пароли) в одном зашифрованном файле:

```text
vault init                 create an empty vault, asking for a master password
vault add github-token     read the secret from standard input, store it under that name
vault get github-token     print the secret
vault list                 print the names of all secrets (never the values)
vault remove github-token  delete a secret
```

Всё защищено одним мастер-паролем: **Argon2id** превращает его (со случайной солью) в 32-байтовый ключ, а **XChaCha20-Poly1305** шифрует весь список секретов и обнаруживает любое изменение файла.

### Контракт

**Командная строка**

```text
vault [--file <PATH>] <COMMAND>
```

| Команда | Поведение | Вывод при успехе |
|---|---|---|
| `init` | Создаёт файл хранилища. Завершается ошибкой, если он существует. | `Created <path>` |
| `add <NAME>` | Читает секрет со стандартного ввода (одно значение; завершающий перевод строки удаляется). Если `NAME` существует, он заменяется. | `Added <name>` или `Updated <name>` |
| `get <NAME>` | Печатает секрет и перевод строки. | секрет |
| `list` | Печатает имена, отсортированные, по одному в строке. | имена |
| `remove <NAME>` | Удаляет секрет. | `Removed <name>` |

- `--file` (или переменная окружения `VAULT_FILE`) — путь к хранилищу. По умолчанию — `vault.bin` в текущей папке.
- **Пароль:** если задана переменная окружения `VAULT_PASSWORD`, используйте её (это для скриптов и тестов, и это более слабый способ: Урок 10.8). Иначе спросите в терминале **без эха** (крейт `rpassword`). `init` спрашивает дважды и отказывается, если ответы различаются.
- **Значение секрета для `add`:** если стандартный ввод — терминал, спросите без эха; иначе прочитайте из конвейера. Секреты никогда не берутся из аргументов командной строки (они попали бы в `ps` — команду, которая показывает запущенные программы с их аргументами, — и в историю командной оболочки).
- **Коды возврата:** `0` — успех; `1` — любая ошибка инструмента; `2` — неверное использование командной строки (так по умолчанию делает `clap`). Ошибки идут в стандартный поток ошибок как `error: <message>`.
- **Имена:** от 1 до 64 символов из `A-Z a-z 0-9 . _ -`.
- **Сообщения** (используйте именно их, команды «Готово, когда» их показывают):

| Ситуация | Сообщение в стандартный поток ошибок |
|---|---|
| Неверный пароль **или** изменённый файл | `error: wrong password, or the vault file was modified` |
| Первые четыре байта не `VLT1` | `error: not a vault file (bad magic bytes)` |
| Неизвестный байт версии | `error: unsupported vault version 7` |
| Файл короче минимума или больше лимита | `error: the vault file is too short or too large` |
| Нет такого секрета | `error: no secret named "x"` |
| `init`, а файл существует | `error: <path> already exists` |
| Плохое имя | `error: invalid secret name "bad name!" (use 1-64 characters from A-Z a-z 0-9 . _ -)` |

(Почему одно сообщение для «неверный пароль» и «изменён»? Метка аутентификации не может их различить, а программа, которая попыталась бы это сделать, лишь помогла бы атакующему.)

**Формат файла, версия 1** (все числа в порядке big-endian)

| Байты | Размер | Содержимое |
|---|---|---|
| 0..4 | 4 | магические байты `VLT1` |
| 4 | 1 | версия формата `1` |
| 5..9 | 4 | `m_cost` Argon2 в KiB |
| 9..13 | 4 | `t_cost` Argon2 |
| 13..17 | 4 | `p_cost` Argon2 |
| 17..33 | 16 | соль (случайная) |
| 33..57 | 24 | nonce XChaCha20-Poly1305 (случайный) |
| 57.. | n + 16 | шифртекст секретов, за которым идёт 16-байтовая метка |

- **Открытый текст:** JSON-объект (JavaScript Object Notation) `{"name": "value", ...}` (используйте `serde_json`). Пустое хранилище — это `{}`, поэтому файл пустого хранилища занимает `33 + 24 + 2 + 16 = 75` байт.
- **Присоединённые данные:** байты `0..33` (заголовок). Поэтому метка покрывает также версию, параметры и соль.
- **Значения по умолчанию:** `m_cost = 19456` (19 MiB), `t_cost = 2`, `p_cost = 1` (обычно рекомендуемый минимум для Argon2id). В тестах можно использовать дешёвые параметры (`8`, `1`, `1`), чтобы они работали быстро.
- **Новая случайная соль и новый случайный nonce при каждом сохранении.** Ключ вычисляется заново при каждом сохранении из того же пароля и новой соли.
- **Лимиты** (Урок 10.12): файл хранилища больше 1 MiB отвергается до чтения; секрет больше 64 KiB отвергается; при чтении параметры Argon2 из файла должны быть разумными (`m_cost` не больше 1 048 576 KiB, `t_cost` не больше 20, `p_cost` не больше 16), потому что они приходят из **недоверенного файла** и иначе могли бы заставить программу использовать гигабайты памяти.

**Требования безопасности**

1. Мастер-пароль, полученный ключ, расшифрованный открытый текст и секрет, прочитанный со стандартного ввода, находятся в контейнерах `Zeroizing` (или затираются вручную) и не копируются без нужды.
2. Значения секретов появляются в выводе только для `get`. Они никогда не попадают в сообщения об ошибках, вывод `Debug` или логи.
3. Файл создаётся с правами `0600` и заменяется **атомарно** (временный файл в той же папке, `sync_all`, `rename`).
4. Никакой ввод не может вызвать панику в программе: отсутствующий, пустой, обрезанный, случайный или изменённый файл всегда даёт ошибку с сообщением и кодом возврата `1`.
5. Зависимости проверяются через `cargo audit` и `cargo deny check` (Урок 10.13), а `deny.toml` закоммичен.

**Крейты:** `clap` (фичи `derive`, `env`), `argon2`, `chacha20poly1305`, `getrandom`, `zeroize`, `serde_json`, `thiserror`, `rpassword`; dev-зависимости `assert_cmd`, `predicates`, `tempfile`. Добавляйте каждый через `cargo add`, который выбирает текущую версию.

**Предлагаемая структура** (можно изменить): библиотека `src/lib.rs` для логики и тонкий `src/main.rs` для терминала, как в Уроке 05.13.

```text
src/lib.rs        pub mod error; pub mod kdf; pub mod format; pub mod vault; pub mod fileio;
src/main.rs       clap definition, password prompts, calls into the library
tests/format.rs   tests of key derivation and the file format
tests/cli.rs      end-to-end tests with assert_cmd
```

**Предлагаемые сигнатуры** (тесты ниже ссылаются на них):

```rust
pub struct KdfParams { pub m_cost: u32, pub t_cost: u32, pub p_cost: u32 }
pub fn derive_key(password: &[u8], salt: &[u8; 16], params: KdfParams) -> Result<Zeroizing<[u8; 32]>, VaultError>;
pub fn seal(vault: &Vault, password: &[u8], params: KdfParams) -> Result<Vec<u8>, VaultError>;
pub fn open(bytes: &[u8], password: &[u8]) -> Result<Vault, VaultError>;
```

**Модель угроз** (запишите её и в README)

| Хранилище защищает от | Хранилище **не** защищает от |
|---|---|
| Того, кто скопирует файл хранилища и попытается его прочитать | Вредоносной программы или кейлоггера на вашем компьютере, пока вы вводите пароль |
| Того, кто изменит файл (любое изменение обнаруживается) | Слабого мастер-пароля (Argon2 замедляет перебор, но не может его остановить) |
| Подбора пароля офлайн (замедляется Argon2id) | Того, кто читает память работающей программы или файл подкачки |
| Утечки секретов через командную строку и логи | Удалённого файла без резервной копии (восстановления нет) |

#### M1 — Каркас: командная строка, ошибки, пока без логики

**Цель:** пакет, который собирается, разбирает командную строку из контракта и содержит тип ошибки.

**Указания:**

1. Создайте пакет: `cargo new --lib code/p10-vault` (библиотека) и добавьте `src/main.rs` сами. Добавьте зависимости через `cargo add`.

#### M2 — Получение ключа

**Цель:** `derive_key` превращает пароль и соль в 32-байтовый ключ с помощью Argon2id, а ключ затирается при освобождении.

**Указания:**

1. Прочитайте `argon2::Params::new`, `Argon2::new` и `hash_password_into` в документации используемой версии. Выберите `Algorithm::Argon2id` и `Version::V0x13`.
2. Верните ключ как `Zeroizing<[u8; 32]>`. Преобразуйте ошибки Argon2 в `VaultError::BadParams` (добавьте этот вариант с сообщением на ваш выбор).
3. Напишите тесты (дешёвые параметры `8, 1, 1`). Назовите их так, чтобы в каждом имени было слово `kdf`: тот же пароль и соль дают тот же ключ; другая соль даёт другой ключ; другой пароль даёт другой ключ; другой `m_cost` даёт другой ключ.
4. Сделайте коммит.

<details>
<summary>Подсказка 1 — форма API</summary>

`let params = Params::new(m, t, p, Some(32))?; let argon = Argon2::new(Algorithm::Argon2id, Version::V0x13, params); argon.hash_password_into(password, salt, &mut key[..])?;`, где `key` — `Zeroizing<[u8; 32]>` (он разыменовывается в массив).

</details>

<details>
<summary>Подсказка 2 — сравнение ключей в тестах</summary>

`assert_eq!(*key_a, *key_b)` сравнивает массивы внутри обёрток. В тестах `==` допустим; в самой программе ключи вы не сравниваете — проверку делает метка AEAD.

</details>

**Готово, когда:**

```bash
cargo test kdf
```

печатает не менее четырёх тестов, в чьих именах есть `kdf`, все `ok`, и заканчивается `test result: ok.`.

#### M3 — Запечатанный формат файла и тесты на подмену

**Цель:** `seal` и `open` реализуют формат файла из контракта; любое повреждение — это ошибка.

**Указания:**

1. `seal`: создайте случайную 16-байтовую соль и случайный 24-байтовый nonce через `getrandom`; получите ключ; соберите 33-байтовый заголовок; зашифруйте JSON-открытый текст с заголовком в качестве присоединённых данных; верните `header || nonce || ciphertext+tag`. Пока храните секреты в памяти в типе `Vault` (внутри `BTreeMap<String, String>`).
2. `open`: **сначала** проверьте ограничения длины, затем магические байты, затем версию, затем границы параметров. Только после этого получайте ключ и расшифровывайте. Неудачное расшифрование преобразуйте в единую ошибку «wrong password, or modified». Никогда не используйте `unwrap` и индексацию без проверки.
3. Напишите приведённые ниже тесты; дайте каждому имя, содержащее показанное в скобках слово.
4. Сделайте коммит.

Тесты, которые нужно написать:

- круговой путь: `open(seal(v)) == v` (`round_trip`);
- неверный пароль даёт ровно ошибку «wrong password» (`wrong_password`);
- **переверните каждый байт** запечатанного хранилища по очереди и проверьте, что `open` каждый раз возвращает ошибку и не паникует (`tamper`);
- обрезанные файлы нескольких длин и пустой ввод — ошибки (`truncated`);
- два запечатывания одного хранилища с одним паролем дают разные байтовые строки (`fresh_nonce`);
- заголовок с `m_cost`, равным `u32::MAX`, отвергается без попытки выделить память (`absurd_params`).

<details>
<summary>Подсказка 1 — сборка заголовка</summary>

Собирайте части в `Vec<u8>`: `extend_from_slice(b"VLT1")`, `push(1)`, затем `m_cost.to_be_bytes()`, `t_cost.to_be_bytes()`, `p_cost.to_be_bytes()`, затем соль. Его длина должна быть 33. Числа читайте обратно через `u32::from_be_bytes([b0, b1, b2, b3])`.

</details>

<details>
<summary>Подсказка 2 — присоединённые данные</summary>

Используйте `Payload { msg: &plaintext, aad: &header }` и для шифрования, и для расшифрования (Урок 10.10, Упражнение 2). `split_at` даёт заголовок, nonce и шифртекст без индексации.

</details>

<details>
<summary>Подсказка 3 — тест «переверните каждый байт»</summary>

`for i in 0..bytes.len() { let mut bad = bytes.clone(); bad[i] ^= 1; assert!(open(&bad, pw).is_err(), "byte {i}"); }`. Переворот в магических байтах, версии или частях, связанных с длиной, ловят ранние проверки; переворот в любом другом месте ловит метка. Все они должны быть ошибками.

</details>

**Готово, когда:**

```bash
cargo test tamper && cargo test wrong_password && cargo test absurd_params
```

все проходят, а `cargo test` целиком заканчивается `test result: ok.`.

#### M4 — Команды и файл на диске

**Цель:** пять команд работают с настоящим файлом.

**Указания:**

1. Напишите `write_file(path, bytes)`: создайте `<path>.tmp` с режимом `0o600` (`std::os::unix::fs::OpenOptionsExt::mode`), запишите, вызовите `sync_all`, затем `rename` поверх конечного пути. Напишите `read_file(path)`, которая проверяет размер файла по лимиту 1 MiB **до** чтения.
2. Добавьте `Vault::set`, `get`, `remove` и `names` (отсортированные: `BTreeMap` делает это за вас) с проверкой имён и размеров из контракта.
3. В `main.rs` реализуйте команды. `load` = прочитать файл, спросить пароль, `open`. `save` = `seal` с `KdfParams::default()` (значения из контракта), затем `write_file`.
4. Читайте пароль через `rpassword::prompt_password`, если не задан `VAULT_PASSWORD`. Секрет для `add` читайте со стандартного ввода, как в контракте (запрос без эха, если это терминал).
5. Сделайте коммит.

<details>
<summary>Подсказка 1 — терминал или конвейер?</summary>

`use std::io::IsTerminal; std::io::stdin().is_terminal()`. Для конвейера читайте через `Read::take(MAX_VALUE as u64 + 1)`, чтобы огромный ввод не мог заполнить память, и отвергайте его, если он длиннее лимита.

</details>

<details>
<summary>Подсказка 2 — один и тот же код для всех команд</summary>

`get` и `list` только читают; `add` и `remove` читают, изменяют и сохраняют. Пара небольших функций `load` и `save` сводит каждую команду к нескольким строкам.

</details>

**Готово, когда:** (соберите через `cargo build`; в листинге программа называется `vault`, а запускаете вы `./target/debug/vault`. Первые три строки готовят одноразовую демонстрацию; `VAULT_PASSWORD` экспортируется **только для этого эксперимента**: сама команда `export` сохраняется в истории вашей командной оболочки, поэтому никогда не делайте так с настоящим паролем.)

```bash

export VAULT_FILE=/tmp/vault-demo/vault.bin VAULT_PASSWORD='correct horse battery staple'

```

#### M5 — Укрепление

**Цель:** инструмент переживает враждебные файлы и враждебный ввод и не пускает секреты в неожиданные места.

**Указания:**

1. **Мусорный ввод.** Проверьте отсутствующий файл, пустой файл, текстовый файл, 200 случайных байтов, корректный файл с изменённым байтом версии (`unsupported vault version`). Каждый должен давать чистую строку `error:` и код возврата `1`, без сообщения о панике.
2. **Аудит затирания.** Поищите в коде: `grep -n "Zeroizing\|zeroize" src/*.rs`. Пароль, ключ, байты расшифрованного открытого текста и секрет, прочитанный со стандартного ввода, должны находиться в значениях `Zeroizing`. Значения внутри карты `Vault` должны затираться в `Drop` для `Vault` и при удалении секрета (`String::zeroize`).
3. **Никаких утечек.** Проверьте, что ни один `println!`, `format!` или сообщение об ошибке не содержит секрет или пароль; что `Vault` не выводит `Debug` через derive (или у него ручной `Debug`, печатающий только имена).
4. **Лимиты.** Имя длиннее 64 символов, секрет больше 64 KiB (используйте `head -c 70000 /dev/zero | tr '\0' a | vault add big`) и файл больше 1 MiB отвергаются до какой-либо тяжёлой работы.
5. **Зависимости.** Запустите `cargo audit` и создайте `deny.toml` для `cargo deny check` (Урок 10.13) с лицензиями, которые реально используются в вашем дереве.
6. Сделайте коммит.

<details>
<summary>Подсказка 1 — тест со случайным мусором</summary>

Заполните буфер через `getrandom::fill` для длин `0..300` и вызовите `open`; каждый вызов должен вернуть `Err`. Это маленький самодельный фаззинг-тест (настоящий фаззинг: Урок 09.8). Шанс, что случайные байты начнутся с `VLT1` и будут иметь верную метку, нулевой.

</details>

<details>
<summary>Подсказка 2 — затирание при удалении</summary>

`BTreeMap::remove` возвращает `Some(String)`: вызовите `zeroize()` для этой строки до того, как она будет освобождена. В `Drop for Vault` пройдитесь циклом по `self.entries.values_mut()`. Не забудьте импортировать трейт `Zeroize`, чтобы вызывать `.zeroize()`.

</details>

**Готово, когда:**

```bash
echo 'x' > not-a-vault.txt; head -c 200 /dev/urandom > random.bin
vault --file not-a-vault.txt list; echo "exit: $?"
vault --file random.bin list; echo "exit: $?"
vault --file does-not-exist.bin list; echo "exit: $?"
```

(при всё ещё экспортированном `VAULT_PASSWORD` из M4; иначе инструмент сначала спросит пароль) печатают по строке `error:` (первые две — `the vault file is too short or too large` и `not a vault file (bad magic bytes)`, третья упоминает отсутствующий файл; её формулировка ваша), все с `exit: 1`, и ни одна не печатает слово `panicked`. `cargo audit` не печатает уязвимостей, а `cargo deny check` заканчивается строкой `advisories ok, bans ok, licenses ok, sources ok`.

### Дополнительные цели

- **`vault passwd`**: смена мастер-пароля (откройте со старым, сохраните с новым; новая соль создаётся автоматически).
- **Файл-ключ**: разрешите `--key-file <path>` в дополнение к паролю (смешайте оба в вход Argon2) как второй фактор.
- **Версионирование**: добавьте версию формата `2` (например, с другим шифром) и продолжайте читать версию `1`; напишите тест с сохранённым файлом версии 1.
- **`vault export` / `import`**: зашифрованная резервная копия всего хранилища с другим паролем.
- **`secrecy`**: используйте `SecretString` для пароля и секретов, чтобы их нельзя было случайно напечатать (`Debug` показывает `[REDACTED]`).
- **Фаззинг**: добавьте цель `cargo fuzz` для `open` (Урок 09.8) и запустите её на несколько минут.
- **Защита от подкачки**: прочитайте про `mlock` и о том, почему затирание не убирает копии, которые операционная система уже сделала.
- **Проверка времени**: измерьте, сколько длится `init`, с помощью `hyperfine` (Урок 09.11), и обсудите, как выбрать `m_cost` и `t_cost` для вашего компьютера.

## Частые ошибки

**1. Повторное использование nonce.** Один фиксированный nonce для каждого сохранения — ошибка из Урока 10.10. Новый случайный nonce **и** новая соль при каждом сохранении её избегают.

**2. Аутентификация только шифртекста.** Без заголовка в присоединённых данных атакующий мог бы изменить параметры Argon2 или версию незаметно. Передавайте заголовок как `aad`.

**3. Доверие параметрам из файла.** `m_cost` из враждебного файла может запросить терабайты памяти. Проверяйте границы до вызова Argon2.

**4. Паники на плохих файлах.** `bytes[33..57]` на 10-байтовом файле паникует. Используйте `split_at` после проверки длины или `get`.

**5. Секрет в командной строке.** `vault add token hunter2` сохранил бы секрет в истории командной оболочки и в `ps`. Поэтому значение берётся со стандартного ввода.

**6. Запись файла «на месте».** Сбой посреди `std::fs::write` уничтожает единственную копию ваших секретов. Пишите временный файл и переименовывайте его.

**7. Печать пароля в сообщении о панике или логе.** Никогда не печатайте через `{:?}` структуру с секретами, не проверив её реализацию `Debug`.

## Вопросы для самопроверки

1. Зачем хранилищу случайная соль и где она хранится?

<details>
<summary>Ответ</summary>

Соль делает ключ уникальным для каждого файла, поэтому атакующий не может использовать заранее вычисленные данные для разных хранилищ или пользователей, а одинаковые пароли дают разные ключи. Она не секретна, поэтому хранится в заголовке файла.

</details>

2. Что защищают присоединённые данные и что случилось бы без них?

<details>
<summary>Ответ</summary>

Заголовок (магические байты, версию, параметры KDF, соль). Без них атакующий мог бы изменить параметры или версию файла, не сделав метку недействительной.

</details>

3. Почему «неверный пароль» и «файл изменён» — это одно сообщение об ошибке?

<details>
<summary>Ответ</summary>

Проверка метки AEAD в обоих случаях не проходит, и их нельзя различить. Более конкретное сообщение было бы догадкой и подсказкой для атакующих.

</details>

4. Почему секрет читается со стандартного ввода, а не из аргумента?

<details>
<summary>Ответ</summary>

Аргументы видны другим пользователям через `ps` и сохраняются в истории командной оболочки. Стандартный ввод не виден и не сохраняется.

</details>

5. Гарантирует ли `Zeroizing`, что в памяти не останется ни одной копии секрета? Что он делает?

<details>
<summary>Ответ</summary>

Нет. Он перезаписывает именно это значение при освобождении, и компилятору не дают выбросить запись как лишнюю. Он не может стереть копии, сделанные в других местах (перемещения, буферы других библиотек, подкачка, дампы памяти). Он уменьшает риск, но не убирает его.

</details>

## Итоги

- Хранилище объединяет инструменты этого этапа: Argon2id получает ключ из пароля и случайной соли, XChaCha20-Poly1305 шифрует и аутентифицирует данные, а заголовок аутентифицируется как присоединённые данные.
- У хорошего формата файла есть магическое число, версия, параметры, с которыми он создан, соль и nonce, а разбирается он с явными проверками длины и лимитами.
- Тестируйте свойства безопасности напрямую: неверный пароль, каждый перевёрнутый байт, обрезанный и случайный ввод, абсурдные параметры.
- Секреты не попадают в аргументы, логи, сообщения об ошибках и вывод `Debug` и затираются там, где Rust это позволяет; знайте пределы этой защиты.
- Заменяйте файл атомарно с ограничительными правами и проверяйте зависимости через `cargo audit` и `cargo deny`.
- Запишите модель угроз: она говорит, что инструмент делает, а что нет.
