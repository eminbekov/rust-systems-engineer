## Новые слова

| Слово | Значение |
|---|---|
| **REPL** (Read–Eval–Print Loop, цикл «прочитать — выполнить — напечатать») | Программа, которая раз за разом читает строку, выполняет её, показывает результат и спрашивает снова. Любая интерактивная оболочка — REPL. |
| **приглашение** (prompt) | Короткий текст, который оболочка печатает, когда ждёт команду, здесь `rsh> `. |
| **токен** (token) | Один осмысленный кусок входной строки: слово вроде `ls` или оператор вроде `\|` или `>`. |
| **лексер** (tokenizer, lexer) | Функция, которая режет строку на токены, учитывая пробелы и кавычки. |
| **парсер** (parser) | Функция, которая превращает список токенов в структуру, которую программа может выполнить: команды, аргументы, перенаправления. |
| **встроенная команда** (built-in) | Команда, которую оболочка выполняет в собственном процессе, например `cd`. Она обязана быть встроенной, потому что меняет саму оболочку. |
| **интеграционный тест** (integration test) | Тест, который запускает готовый бинарник снаружи (Урок 05.6). |
| **`assert_cmd`** | Крейт для интеграционных тестов программ командной строки: запустить бинарник, подать стандартный ввод, проверить вывод и код возврата. |
| **ВМ**, **ОС** | Известны из прошлых уроков: виртуальная машина (ваша ВМ `dev`); операционная система. |

## Проект

### Что вы создадите

`rsh` — небольшую, но настоящую командную оболочку Unix. Она читает командные строки, запускает программы через `fork` и
`exec`, соединяет их конвейерами, перенаправляет ввод и вывод в файлы, имеет встроенные команды `cd`, `exit` и `export` и
переживает Ctrl-C, тогда как запущенная ею программа — нет. Сеанс в терминале выглядит так:

```text
rsh> echo hello
hello
rsh> sleep 30
^C
rsh> cat /etc/passwd | cut -d: -f1 | sort | head -3 > /tmp/users.txt
rsh> cat < /tmp/users.txt
_apt
backup
bin
rsh> exit
```

(Этот и все последующие выводы получены от эталонного решения, проверенного в Linux-контейнере. Имена пользователей у вас
могут отличаться.) Готового решения вы не получите: ваш ориентир — контракт, вехи, небольшие подсказки и приёмочные тесты
(«Готово, когда»).

```text
 one line  ──>  tokenize  ──>  parse  ──>  built-in?  ──yes──>  run in the shell (cd, exit, export)
                (parse.rs)    (parse.rs)       │
                                               no
                                               v
                               for each command: pipe2, fork; in the child: reset signals,
                               dup2 pipes and files onto 0/1, execvp  (exec.rs)
                                               │
                                               v
                               parent: close pipe ends, waitpid all, remember the last status
```

### Контракт

**Пакет и файлы.** Бинарный пакет `code/p13-rsh` с именем `rsh`:

```text
code/p13-rsh/
├── Cargo.toml
├── README.md          ← что умеет rsh, как его собрать, запустить и протестировать
├── src/
│   ├── main.rs        ← цикл REPL: приглашение, чтение строки, вызов parse и exec
│   ├── parse.rs       ← tokenize() и parse() с модульными тестами
│   ├── builtins.rs    ← cd, exit, export
│   └── exec.rs        ← fork, exec, конвейеры, перенаправления, ожидание
└── tests/
    └── cli.rs         ← интеграционные тесты на assert_cmd
```

Зависимости (версии с crates.io проверены 2026-11-17):

```toml
[dependencies]
nix = { version = "0.32", features = ["fs", "process", "signal"] }

[dev-dependencies]
assert_cmd = "2.2"
predicates = "3.1"
```

**Ввод.** `rsh` не принимает аргументов. Он читает строки со стандартного ввода до конца файла. Приглашение `rsh> ` он
печатает в **стандартный поток ошибок** и только когда стандартный ввод — терминал: тогда тесты, подающие ввод через конвейер,
видят чистый вывод.

**Синтаксис одной строки.**

| Правило | Пример | Значение |
|---|---|---|
| слова разделяются пробелами или табуляциями | `ls   -l` | `["ls", "-l"]` |
| `'...'` и `"..."` сохраняют пробелы и операторы внутри одного слова; кавычки убираются | `echo 'a  b' "c\|d"` | `["echo", "a  b", "c\|d"]` |
| кавычки могут быть частью слова | `x"y z"` | `"xy z"` |
| `\|`, `<`, `>` — операторы, с пробелами вокруг или без | `ls\|wc` | две команды |
| `< file` / `> file` | `sort < in > out` | stdin из `in`, stdout в `out` (создать или обрезать, права 644) |
| конвейер — команды, соединённые `\|` | `a \| b \| c` | stdout каждой идёт в stdin следующей |
| пустая строка или строка из одних пробелов ничего не делает | | |

Без переменных (`$X`), без `;`, `&&`, `&`, `>>` и `2>` — это дополнительные цели.

**Встроенные команды** (выполняются внутри оболочки, только когда команда одна в строке):

| Команда | Поведение | Статус |
|---|---|---|
| `cd DIR` | сменить текущую папку оболочки | 0 или 1 с `rsh: cd: DIR: No such file or directory` (текст ошибки ОС) |
| `cd` | перейти в `$HOME` | 0 |
| `exit [N]` | завершить оболочку со статусом N (по умолчанию — статус последней команды) | — |
| `export NAME=VALUE` | задать переменную окружения, которую унаследуют следующие программы | 0 |

**Статусы завершения и ошибки.** После каждой строки оболочка запоминает статус: код возврата последней команды конвейера
или 128 + номер сигнала, если её убили. В конце файла `rsh` завершается с последним статусом.

| Ситуация | Сообщение в стандартный поток ошибок | Статус |
|---|---|---|
| программа не найдена | `rsh: NAME: command not found` | 127 |
| файл перенаправления не открывается | `rsh: FILE: No such file or directory` (текст ошибки ОС) | 1 |
| незакрытая кавычка | `rsh: unclosed quote` | 2 |
| `\|` в начале или конце, или `>`/`<` без файла | `rsh: syntax error ...` (любой текст после `syntax error`) | 2 |

**Сигналы.** Ctrl-C во время работы программы завершает эту программу (статус 130), а **не** оболочку; оболочка затем печатает
новую строку и новое приглашение. Ctrl-C в приглашении не завершает оболочку. Программы, запущенные `rsh`, получают настройки
сигналов по умолчанию: `SIGINT` и `SIGPIPE` сбрасываются на действие по умолчанию в каждом ребёнке до `exec`.

**Качество.** `cargo test` проходит (модульные тесты в `parse.rs`, интеграционные — в `tests/cli.rs`), `cargo clippy` не даёт
предупреждений, `cargo fmt --check` чист, и на каждую веху — один коммит Git.

#### M1 — Цикл: запустить одну программу

**Цель.** REPL, который читает строки, делит их по пробелам, запускает программу через `fork` + `execvp`, ждёт и печатает
`command not found` для неизвестных программ.

**Указания.**

1. В `main` один раз решите, печатать ли приглашение: `std::io::stdin().is_terminal()` (трейт `std::io::IsTerminal`).
   Печатайте приглашение через `eprint!` и сбрасывайте буфер стандартного потока ошибок.
2. Читайте через `read_line`. Результат `Ok(0)` означает конец файла: выйдите из цикла и вызовите
   `std::process::exit(last_status)`.
3. Пока что ваш парсер — `line.split_whitespace()`. Пустые строки пропускайте.
4. Напишите `run(argv: &[String]) -> i32` в `exec.rs`: соберите `CString` **до** `fork`, `execvp` в ребёнке, `waitpid` в
   родителе. Превратите `WaitStatus` в число (Урок 13.5, упражнение 2).
5. Если `execvp` падает с `ENOENT`, ребёнок печатает `rsh: NAME: command not found` и завершается с кодом 127.

<details>
<summary>Подсказка</summary>

У `rsh` только один поток, поэтому после `fork` ребёнок может использовать `eprintln!` и `std::process::exit` (Урок 13.5).
Оставьте комментарий `// SAFETY:`, который это объясняет. `execvp` возвращает `Err(e)` только при неудаче; сравните его с
`nix::errno::Errno::ENOENT`.

</details>

Добавьте первый интеграционный тест в `tests/cli.rs` уже сейчас; он образец для всех следующих:

```rust
use assert_cmd::cargo::cargo_bin_cmd;

#[test]
fn runs_a_program() {
    cargo_bin_cmd!("rsh")
        .write_stdin("echo hello world\n")
        .assert()
        .success()
        .stdout("hello world\n");
}
```

`cargo_bin_cmd!("rsh")` создаёт команду для вашего собранного бинарника, `write_stdin` подаёт ей ввод через конвейер (поэтому
приглашение не печатается), а `assert()` проверяет результат. `.code(127)` и `.stderr("...")` проверяют код возврата и
стандартный поток ошибок.

**Готово, когда:**

```bash
cargo build -q
printf 'echo hello world\nls /no-such-dir\nno-such-cmd\n' | ./target/debug/rsh; echo "status $?"
cargo test -q --test cli
```

```text
hello world
ls: cannot access '/no-such-dir': No such file or directory
rsh: no-such-cmd: command not found
status 127
```

и `test result: ok` для ваших тестов. Добавьте ещё тест `unknown_command`, который проверяет код 127 и точное сообщение.
Коммит: `git commit -m "feat(p13-rsh): M1 run one program"`.

#### M2 — Лексер и парсер, сначала тесты

**Цель.** Заменить `split_whitespace` на `tokenize` и `parse` в `parse.rs`, полностью покрытые модульными тестами, ещё до того,
как они будут подключены к чему-либо, что делает fork.

**Указания.** Предлагаемые типы (можете выбрать другие):

```rust
#[derive(Debug, PartialEq)]
pub enum Token {
    Word(String),
    Pipe,
    Less,
    Greater,
}

#[derive(Debug, PartialEq, Default)]
pub struct Command {
    pub argv: Vec<String>,
    pub stdin: Option<String>,
    pub stdout: Option<String>,
}

pub fn tokenize(line: &str) -> Result<Vec<Token>, String> {
    todo!()
}

pub fn parse(line: &str) -> Result<Vec<Command>, String> {
    todo!()
}
```

`parse` возвращает конвейер: по одной `Command` на каждую часть между `|`. Сначала напишите тесты (Урок 05.6), по одному на
каждую строку таблицы синтаксиса из контракта, плюс случаи ошибок: `"echo 'oops"`, `"ls |"`, `"| ls"`, `"ls >"`. Затем пустая
строка: `parse("")` возвращает пустой `Vec`.

<details>
<summary>Подсказка</summary>

Идите по `line.chars()`, храня `String` для текущего слова и `bool` «я внутри слова?». Пробел заканчивает слово; оператор
заканчивает слово **и** добавляет собственный токен; символ кавычки начинает маленький внутренний цикл, который копирует
символы, пока не встретится та же кавычка (или пока не кончится строка: ошибка). Помните, что `""` — тоже слово (пустое),
поэтому нужен `bool`, а не просто проверка `word.is_empty()`.

</details>

**Готово, когда:** `cargo test -q parse` показывает, что все ваши тесты парсера проходят, и парсер используется в REPL:

```bash
printf '%s\n' "echo 'a   b' \"c|d\" x\"y z\"" "echo 'oops" | ./target/debug/rsh; echo "status $?"
```

```text
a   b c|d xy z
rsh: unclosed quote
status 2
```

Коммит: `feat(p13-rsh): M2 tokenizer and parser`.

#### M3 — Встроенные команды: `cd`, `exit`, `export`

**Цель.** Команды, которые должны менять саму оболочку, выполняются внутри оболочки.

**Указания.** До fork проверьте, состоит ли строка из одной команды, чей `argv[0]` — встроенная команда. `cd` использует
`std::env::set_current_dir`; `cd` без аргумента использует переменную `HOME`. `export NAME=VALUE` использует
`std::env::set_var`, которая в редакции 2024 — `unsafe`, потому что другой поток может в тот же момент читать окружение; у
`rsh` один поток, так что объясните это в комментарии `// SAFETY:`. Дети наследуют окружение и текущую папку автоматически
через `fork` и `exec`.

<details>
<summary>Подсказка</summary>

Почему `cd` не может быть обычной программой? Дочерний процесс, меняющий собственную папку, никак не влияет на родителя:
ребёнок завершается, а оболочка остаётся там, где была. Для сообщения об ошибке: `Display` у `io::Error` заканчивается на
` (os error 2)`; отрежьте это или соберите текст из `e.kind()`.

</details>

**Готово, когда:**

```bash
./target/debug/rsh <<'EOF'
cd /tmp
pwd
cd /nope
export GREETING=hi
printenv GREETING
exit 3
echo never printed
EOF
echo "status $?"
```

```text
/tmp
rsh: cd: /nope: No such file or directory
hi
status 3
```

Добавьте интеграционный тест для этого скрипта (проверьте `.code(3)` и `.stdout("/tmp\nhi\n")`). Коммит:
`feat(p13-rsh): M3 built-ins`.

#### M4 — Перенаправление: `<` и `>`

**Цель.** Работает `cmd < in > out`.

**Указания.** В ребёнке, после `fork` и до `execvp`: если задан `stdin`, откройте файл только для чтения и сделайте
`dup2_stdin`; если задан `stdout`, откройте с `O_WRONLY | O_CREAT | O_TRUNC` и правами `0o644`, затем `dup2_stdout`
(Урок 13.6, раздел 4). Если `open` не удался, напечатайте `rsh: FILE: <текст ошибки>` и завершите ребёнка с кодом 1.

<details>
<summary>Подсказка</summary>

Открывайте файлы **в ребёнке**, а не в оболочке: тогда неудачный `open` касается только этой команды, а собственные
дескрипторы оболочки никогда не меняются. Открывайте их с `O_CLOEXEC`: копии, сделанные `dup2` на 0 и 1, остаются открытыми,
а оригиналы закрываются при `exec`.

</details>

**Готово, когда:**

```bash
./target/debug/rsh <<'EOF'
echo saved > /tmp/rsh-out.txt
cat < /tmp/rsh-out.txt
wc -c < /tmp/rsh-out.txt > /tmp/rsh-count.txt
cat /tmp/rsh-count.txt
cat < /nope
EOF
echo "status $?"
```

```text
saved
6
rsh: /nope: No such file or directory
status 1
```

Добавьте интеграционный тест, который пишет в файл в `std::env::temp_dir()` и читает его обратно. Коммит:
`feat(p13-rsh): M4 redirection`.

#### M5 — Конвейеры

**Цель.** `a | b | c` любой длины; статус — это статус последней команды.

**Указания.** Это Урок 13.6 (раздел 3 и упражнение 3), но для N команд. Создайте конвейер для каждого `|`, запустите **всех**
детей и только потом ждите их всех. У команды могут быть и конвейер, и перенаправление (`sort < in | uniq > out`): сначала
применяйте конвейер, потом файл, чтобы файл побеждал, как в bash.

<details>
<summary>Подсказка</summary>

Храните `previous_read_end: Option<OwnedFd>`. Для команды `i`: если она не последняя, создайте `pipe2(O_CLOEXEC)`; запустите
ребёнка с `previous_read_end` в качестве stdin и новым концом для записи в качестве stdout; затем в родителе **закройте** (drop)
оба этих дескриптора (теперь они живут в ребёнке) и сохраните новый конец для чтения для следующей команды. Если конвейер
зависает, какой-то процесс всё ещё держит конец для записи: посмотрите `ls -l /proc/<pid>/fd` зависшего процесса.

</details>

**Готово, когда:**

```bash
./target/debug/rsh <<'EOF'
cat /etc/passwd | cut -d: -f1 | sort | head -3
yes | head -2
printf 'b\na\n' | sort > /tmp/rsh-pipe.txt
cat /tmp/rsh-pipe.txt
EOF
echo "status $?"
printf 'ls |\n' | ./target/debug/rsh; echo "status $?"
```

```text
_apt
backup
bin
y
y
a
b
status 0
rsh: syntax error near `|`
status 2
```

`yes | head -2` должен завершиться сразу и **ничего** не напечатать в стандартный поток ошибок. Если вы видите
`yes: standard output: Broken pipe`, ребёнок унаследовал игнорируемый `SIGPIPE` от рантайма Rust (Урок 13.7): это веха M6.
Добавьте интеграционный тест с конвейером из трёх команд. Коммит: `feat(p13-rsh): M5 pipelines`.

#### M6 — Ctrl-C: ребёнок останавливается, оболочка остаётся

**Цель.** Поведение из раздела «Сигналы» контракта.

**Указания.** В начале `main` поставьте игнорирование `SIGINT` через `nix::sys::signal::signal(Signal::SIGINT,
SigHandler::SigIgn)`. В каждом ребёнке до `execvp` верните `SIGINT` и `SIGPIPE` к `SigHandler::SigDfl`. Все процессы остаются
в одной группе процессов, поэтому терминал посылает Ctrl-C и оболочке, и работающей программе; оболочка его игнорирует, а
программа умирает со статусом 130. Если последний статус равен 130 и оболочка интерактивна, напечатайте пустую строку в
стандартный поток ошибок перед следующим приглашением.

<details>
<summary>Подсказка</summary>

Вспомните таблицу «Настройки сигналов при `fork` и `exec`» из Урока 13.7: игнорируемый сигнал остаётся игнорируемым после
`exec`, поэтому без сброса в ребёнке Ctrl-C не остановил бы и `sleep 30`. В автоматическом тесте Ctrl-C не нажать, но
программа может сама послать `SIGINT`: `kill -INT $PPID` из ребёнка посылает его оболочке, а `kill -INT $$` заставляет `sh`
убить самого себя.

</details>

**Готово, когда** (автоматическая часть):

```bash
./target/debug/rsh <<'EOF'
sh -c 'kill -INT $PPID'
echo still here
sh -c 'kill -INT $$'
EOF
echo "status $?"
```

```text
still here
status 130
```

и вручную в терминале ВМ: запустите `./target/debug/rsh`, выполните `sleep 30`, нажмите Ctrl-C. Вы увидите `^C`, новую строку и
новое приглашение, а `echo alive` по-прежнему работает. Оформите скрипт выше как интеграционный тест (`.code(130)` и
`.stdout(predicates::str::contains("still here"))`). Коммит: `feat(p13-rsh): M6 signals`.

#### M7 — Завершение: тесты, линтер, README

**Цель.** Проект, который не стыдно показать.

**Указания.** Интеграционные тесты для каждой строки таблицы ошибок из контракта; `cargo clippy --all-targets` без
предупреждений; `cargo fmt`; `README.md` с тем, что `rsh` умеет, чего не умеет, как его собрать, запустить и протестировать
(в ВМ, потому что он использует системные вызовы Linux). Проверьте, нет ли зомби: пока работает `rsh`,
`ps -o pid,stat,comm --ppid <pid rsh>` не должен показывать `Z` после завершения команд.

<details>
<summary>Подсказка</summary>

Интеграционные тесты запускают много процессов `rsh` в параллельных потоках; у каждого теста свой процесс, поэтому они друг
другу не мешают — но для каждого теста, который пишет файлы, используйте свои имена файлов в `temp_dir()`.

</details>

**Готово, когда:**

```bash
cargo fmt --check && cargo clippy -q --all-targets && cargo test -q
```

печатает только результаты тестов, все `ok`, например (у эталонного решения 2 модульных и 7 интеграционных тестов; у вас
числа будут другими):

```text
running 2 tests
..
test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s


running 7 tests
.......
test result: ok. 7 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.01s
```

Коммит: `feat(p13-rsh): M7 tests, lint and README`.

### Дополнительные цели

- `>>` (дозапись) и `2>` / `2>&1` для стандартного потока ошибок.
- Подстановка `$NAME` и `$?` вне одинарных кавычек.
- `;` и `&&` между командами.
- Настоящее управление заданиями: помещайте каждый конвейер в собственную группу процессов через `setpgid`, отдавайте ему
  терминал через `tcsetpgrp`, забирайте терминал обратно после (Урок 13.7, раздел 5); затем `&`, `jobs` и `fg`.
- Редактирование строки и история с крейтом `rustyline` (версия 19, проверено 2026-11-17).

## Частые ошибки

> ⚠️ **Частая ошибка:** конвейер зависает после того, как первая команда завершилась. Где-то ещё открыт конец для записи: в
> самой оболочке или в следующем ребёнке, который его унаследовал. Создавайте конвейеры с `O_CLOEXEC` и закрывайте копии
> родителя сразу после каждого `fork` (Урок 13.6).

> ⚠️ **Частая ошибка:** выполнять `cd` в ребёнке. Это «работает» без ошибки, но папка оболочки так и не меняется.

> ⚠️ **Частая ошибка:** печатать приглашение в стандартный вывод. Тогда `printf 'echo hi\n' | rsh | wc -l` посчитает и
> приглашение, и каждому интеграционному тесту придётся его вырезать. Контракт отправляет его в стандартный поток ошибок и
> только для терминалов.

> ⚠️ **Частая ошибка:** забыть дождаться каждого ребёнка конвейера. Тогда оболочка наполняется зомби, а статус строки может
> взяться не от той команды.

## Вопросы для самопроверки

1. Почему `cd`, `exit` и `export` должны быть встроенными командами?

<details>
<summary>Ответ</summary>

Они меняют сам процесс оболочки: его текущую папку, его жизнь, его окружение. Дочерний процесс может изменить только свою
копию, которая исчезает вместе с ним.

</details>

2. В каком процессе вызывать `dup2` и `open` для `cmd < in > out` и почему?

<details>
<summary>Ответ</summary>

В ребёнке, между `fork` и `exec`. Тогда меняются только дескрипторы новой программы, а неудачный `open` касается только этой
команды; собственные стандартный ввод и вывод оболочки остаются нетронутыми.

</details>

3. Почему `rsh` сбрасывает `SIGINT` и `SIGPIPE` на действие по умолчанию в ребёнке?

<details>
<summary>Ответ</summary>

Потому что игнорируемые сигналы остаются игнорируемыми после `exec`. Оболочка игнорирует `SIGINT` (чтобы пережить Ctrl-C), а
рантайм Rust игнорирует `SIGPIPE`; без сброса запущенные ею программы тоже игнорировали бы Ctrl-C и разрыв конвейера.

</details>

4. Почему приглашение идёт в стандартный поток ошибок и только когда стандартный ввод — терминал?

<details>
<summary>Ответ</summary>

Чтобы стандартный вывод оболочки содержал только вывод команд. Скрипты и тесты, которые подают ввод в `rsh` через конвейер,
получают чистый вывод; человек за терминалом всё равно видит приглашение.

</details>

5. Зачем лексер и парсер вынесены в отдельный модуль с модульными тестами?

<details>
<summary>Ответ</summary>

Это чистые функции из текста в данные, поэтому их можно тестировать быстро и тщательно, не запуская ни одного процесса. Часть,
которая делает fork и exec, остаётся маленькой и покрывается несколькими интеграционными тестами.

</details>

## Итоги

- Командная оболочка — это REPL: прочитать строку, разбить на токены, разобрать, выполнить встроенные команды в оболочке, а всё остальное — в детях, дождаться, повторить.
- Встроенные команды существуют, потому что только собственный процесс оболочки может менять её папку, окружение или жизнь.
- Перенаправления и конвейеры готовятся в ребёнке между `fork` и `exec` через `open`, `pipe2` и `dup2`; родитель закрывает свои концы конвейеров и ждёт каждого ребёнка.
- Оболочка игнорирует `SIGINT`; дети сбрасывают `SIGINT` и `SIGPIPE` на действие по умолчанию до `exec`.
- Чистый парсер с модульными тестами плюс интеграционные тесты на `assert_cmd` делают системную программу безопасной для изменений.
