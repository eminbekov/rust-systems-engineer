## Новые слова

| Слово | Значение |
|---|---|
| **ошибка** (bug) | Недочёт в программе, из-за которого она делает не то, что задумано. |
| **отладка** (debugging) | Поиск причины ошибки и её исправление. |
| **воспроизвести** (reproduce) | Заставить ошибку проявиться снова, надёжно, теми же шагами. |
| **backtrace** (трассировка стека) | Список функций, которые работали в момент паники, от новейшей к самой старой. |
| **отладчик** (debugger) | Инструмент, который запускает вашу программу под контролем: её можно приостановить, посмотреть переменные и идти по шагам. |
| **LLDB** | Отладчик проекта LLVM (Low Level Virtual Machine). Используется в macOS, в том числе внутри RustRover. |
| **точка останова** (breakpoint) | Метка на строке кода: отладчик приостанавливает программу, когда она доходит до этой строки. |
| **шаг с обходом / с заходом / с выходом** (step over / into / out) | Команды отладчика: выполнить текущую строку целиком / зайти внутрь вызываемой функции / выполнять до возврата из текущей функции. |
| **наблюдение** (watch) | Следить за значением переменной или выражения, пока вы идёте по коду. |
| **отладочное утверждение** (debug assertion) | Проверка (`debug_assert!`), которая работает только в отладочных сборках и исчезает в релизных. |
| **линт** (lint) | Автоматическая проверка подозрительного или неидиоматичного кода. Clippy — набор линтов. |
| **бисекция** (bisect) | Найти первую плохую версию, многократно деля диапазон версий пополам (двоичный поиск). |
| **регрессионный тест** (regression test) | Тест, написанный, чтобы зафиксировать исправленную ошибку, чтобы она не вернулась незаметно. |

## 1. Метод, а не магия

Новички часто отлаживают, меняя всё подряд и надеясь на удачу. Это тратит время и добавляет новые ошибки. Профессионалы следуют простому циклу:

```mermaid
flowchart LR
    A[1. Воспроизвести] --> B[2. Изолировать]
    B --> C[3. Предположить причину]
    C --> D[4. Проверить предположение]
    D -- неверно --> C
    D -- верно --> E[5. Исправить]
    E --> F[6. Добавить тест]
    F --> G[7. Сделать коммит]
```

1. **Воспроизведите.** Найдите точные входные данные и шаги, при которых ошибка появляется каждый раз. Без этого вы не узнаете, что исправили её.
2. **Изолируйте.** Сделайте задачу маленькой. Какая функция неверна? Отрежьте код, который не участвует. Идеальный результат — упавший тест для одной функции.
3. **Предположите причину.** Сформулируйте одну ясную мысль: «Кажется, цикл останавливается на шаг раньше».
4. **Проверьте предположение.** Напечатайте или изучите значения (разделы 3–5). Пока не меняйте код; сначала подтвердите.
5. **Исправьте** причину, а не симптом.
6. **Добавьте тест** (**регрессионный тест**), который падает без исправления и проходит с ним.
7. **Сделайте коммит** с сообщением, говорящим, что было не так (`fix: …`).

Два помощника: объясните проблему вслух другу или резиновой уточке («отладка резиновой уточкой») — ответ часто находится в процессе объяснения; и **сделайте перерыв** — отдохнувший ум видит опечатку.

## 2. Читайте то, что говорит Rust

Rust даёт много информации. Научитесь читать три вещи.

**Ошибка компилятора** (Урок 00.7): код ошибки, строка, текст `help` и `rustc --explain EXXXX`.

**Сообщение о панике.** При ошибке во время работы первые строки говорят почти всё:

```text
thread 'main' (4149505) panicked at src/main.rs:2:5:
attempt to divide by zero
```

В нём есть: поток (`main`), **файл и строка** (`src/main.rs:2:5`) и **причина** (`attempt to divide by zero`). Сначала откройте эту строку.

**Backtrace.** Строка паники говорит, *где* всё упало, но настоящая причина часто в коде, который *вызвал* эту функцию. Установите переменную окружения `RUST_BACKTRACE=1`, чтобы увидеть все активные функции:

```rust
fn divide(a: i32, b: i32) -> i32 {
    a / b
}

fn average(total: i32, count: i32) -> i32 {
    divide(total, count)
}

fn main() {
    println!("{}", average(10, 2));
    println!("{}", average(10, 0));
}
```

```bash
RUST_BACKTRACE=1 cargo run
```

```text
5

thread 'main' (4149505) panicked at src/main.rs:2:5:
attempt to divide by zero
stack backtrace:
   0: __rustc::rust_begin_unwind
   1: core::panicking::panic_fmt
   2: core::panicking::panic_const::panic_const_div_by_zero
   3: b_backtrace::divide
             at ./src/main.rs:2:5
   4: b_backtrace::average
             at ./src/main.rs:6:5
   5: b_backtrace::main
             at ./src/main.rs:11:20
   6: <fn() as core::ops::function::FnOnce<()>>::call_once
note: Some details are omitted, run with `RUST_BACKTRACE=full` for a verbose backtrace.
```

(Я убрал строки `at /rustc/...` стандартной библиотеки, чтобы вывод был короче.) Как это читать:

1. Кадры 0–2 — механизм паники внутри Rust. **Игнорируйте их**; ищите первый кадр с именем *вашего* крейта: `b_backtrace::divide`.
2. Чтение вниз идёт от новейшего вызова к старейшему: `divide` вызвала `average` на строке 6, а `average` вызвала `main` на строке 11, столбец 20.
3. Значит, ошибка на самом деле не в `divide`: `main` запросила `average(10, 0)`, из-за чего счётчик равен `0`. Вопрос превращается в «кому разрешено передавать ноль?». Это картина стека вызовов из Урока 02.4, ставшая видимой.

## 3. Отладка печатью

Самый простой инструмент — напечатать значения в интересных местах. `println!("{x}")` вы знаете. Три привычки делают его лучше:

- Используйте `{:?}`, чтобы видеть точное значение, включая кавычки и скрытые символы (Урок 02.6).
- Печатайте в **stderr** через `eprintln!`, чтобы отладочный вывод не смешивался с настоящим.
- Подписывайте каждое значение: `eprintln!("i = {i}, total = {total}")`, а не просто числа.

### Макрос `dbg!`

`dbg!(expression)` создан для этого. Он печатает в stderr **файл, строку, текст выражения и его значение** в форме Debug, а затем **возвращает значение**, поэтому его можно обернуть вокруг любого выражения, не меняя программу:

```rust
fn main() {
    let a = 2;
    let b = dbg!(a * 3) + 1;
    dbg!(b);
    let pair = (a, b);
    dbg!(pair);
}
```

```text
[src/main.rs:3:13] a * 3 = 6
[src/main.rs:4:5] b = 7
[src/main.rs:6:5] pair = (
    2,
    7,
)
```

Что происходит: `dbg!(a * 3)` печатает `a * 3 = 6` и возвращает `6`, поэтому `b` по-прежнему равно `7`. Красивый вывод (в стиле `{:#?}`) встроен. Когда ошибка устранена, **удалите строки с `dbg!`**; `cargo clippy` может предупредить об оставшихся (линт `dbg_macro` необязателен).

### Отладочные утверждения

Проверки `assert!` остаются в итоговой программе. Проверки `debug_assert!` работают **только в отладочных сборках** и убираются из релизных, поэтому вы можете писать проверки, которые были бы слишком медленными для итоговой программы:

```rust
fn show_percent(p: u32) -> u32 {
    debug_assert!(p <= 100, "percent out of range: {p}");
    p
}

fn main() {
    println!("{}", show_percent(50));
    println!("{}", show_percent(150));
}
```

Отладочная сборка (`cargo run`):

```text
50

thread 'main' (4150421) panicked at src/main.rs:2:5:
percent out of range: 150
```

Релизная сборка (`cargo run --release`):

```text
50
150
```

В релизной сборке проверка исчезает, и неверное значение проходит дальше. Отладочное утверждение — **инструмент для поиска ошибок во время разработки**, а не защита пользователей; для правил, которые должны выполняться всегда, используйте `assert!` или возвращайте `Result`.

> 🔒 **Безопасность:** разница между отладочной и релизной сборками важна. Проверки переполнения (Урок 02.2) и `debug_assert!` существуют только в отладочных сборках. Всегда запускайте тесты в отладочном режиме (по умолчанию для `cargo test`), чтобы получить эти проверки, и также думайте о том, что делает релизная сборка, когда данные неверны.

## 4. Отладчик

Отладка печатью означает: остановить, изменить, пересобрать, запустить, прочитать, повторить. **Отладчик** позволяет приостановить *работающую* программу и осмотреться. Отладчик для Rust в macOS — **LLDB**. Cargo собирает отладочную версию с отладочной информацией (`Finished dev profile [unoptimized + debuginfo]`), поэтому LLDB может показывать имена ваших переменных и строки.

Отладим функцию с ошибкой. Она должна возвращать `1² + 2² + … + n²`, то есть для `n = 3` — `14`:

```rust
fn sum_of_squares(n: u32) -> u32 {
    let mut total = 0;
    for i in 1..n {
        total += i * i;
    }
    total
}

fn main() {
    println!("sum of squares up to 3 = {}", sum_of_squares(3));
    assert_eq!(sum_of_squares(3), 14);
}
```

```text
sum of squares up to 3 = 5

thread 'main' (4149754) panicked at src/main.rs:11:5:
assertion `left == right` failed
  left: 5
 right: 14
```

У нас есть **воспроизведение** (тест падает) и задача поменьше (`sum_of_squares(3)` даёт 5; должно быть 14). Пора проверить предположение.

### В RustRover (графический отладчик)

1. **Поставьте точку останова.** Щёлкните в сером поле слева от номера строки `total += i * i;`. Появится красная точка.
2. **Запустите отладчик.** Нажмите зелёный значок *жука* рядом с функцией `main` (или кнопку Debug на панели инструментов). RustRover соберёт программу с отладочной информацией и запустит её под LLDB.
3. Программа **остановится** на точке останова, до выполнения строки. Панель *Debug* показывает:
   - **Frames**: стек вызовов (тот же список, что в backtrace);
   - **Variables**: `n = 3`, `total = 0`, `i = 1`;
   - **Watches**: выражения, которые вы добавляете сами, например `i * i`.
4. Двигайтесь дальше кнопками пошагового выполнения (названия одинаковы во всех IDE JetBrains; сочетания клавиш macOS показаны в меню *Run*):

| Команда | Что делает |
|---|---|
| **Resume** | Выполнять до следующей точки останова или до конца. |
| **Step Over** | Выполнить текущую строку целиком и остановиться на следующей. Вызовы функций в строке выполняются целиком. |
| **Step Into** | Если строка вызывает функцию, зайти внутрь. |
| **Step Out** | Выполнять, пока текущая функция не вернётся в вызывающую. |
| **Run to Cursor** | Выполнять до строки, где стоит текстовый курсор. |
| **Evaluate Expression** | Введите любое выражение (например, `i * i + total`) и увидите его значение сейчас. |

5. Нажмите **Resume** и следите за переменными: `i` становится 2, а `total` становится 1. Нажмите **Resume** ещё раз: программа больше не останавливается, а просто завершается. Тело цикла выполнилось только **дважды**, а мы ожидали три раза (для 1, 2 и 3).

Это ответ на наш вопрос: цикл `1..n` не включает `n`. Наше предположение оказалось верным: это ошибка на единицу из Урока 02.5.

### С LLDB в терминале

Тот же сеанс можно провести в терминале, что полезно, когда вы работаете на сервере или через SSH (Secure Shell, способ войти на другой компьютер). Соберите программу, затем запустите LLDB с программой и несколькими командами:

```bash

```

### Исправление и его тест

Цикл должен включать `n`: напишите `1..=n`. Перед исправлением мы пишем тест, который сейчас падает и проходит после исправления (регрессионный тест), с крайними случаями `n = 1` и `n = 0`:

```rust
fn sum_of_squares(n: u32) -> u32 {
    let mut total = 0;
    for i in 1..=n {
        total += i * i;
    }
    total
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn sums_squares_including_n() {
        assert_eq!(sum_of_squares(3), 14);
        assert_eq!(sum_of_squares(1), 1);
        assert_eq!(sum_of_squares(0), 0);
    }
}
```

> 💡 **Совет:** когда какой инструмент использовать? **`println!`/`dbg!`** — для быстрого взгляда на одно-два значения. **Отладчик** — когда нужно проследить длинную цепочку событий, увидеть много переменных сразу или когда ошибка исчезает при добавлении печати. **Тест** — всегда, чтобы ошибка не вернулась.

## 5. Пусть инструменты ищут ошибки за вас

Прежде чем отлаживать, спросите инструменты.

- **`cargo check`** — быстрые ошибки компиляции без сборки программы.
- **`cargo clippy`** — сотни дополнительных проверок. Вот что он говорит о коде, который компилируется, но нехорош:

```rust
fn clamp_score(x: i32) -> i32 {
    if x >= 0 && x <= 100 {
        return x;
    }
    return 100;
}

fn main() {
    let v = [1, 2, 3];
    for i in 0..v.len() {
        println!("{}", v[i]);
    }
    println!("{}", clamp_score(150));
}
```

```text
warning: unneeded `return` statement
 --> src/main.rs:5:5
  |
5 |     return 100;
  |     ^^^^^^^^^^
  |
  = note: `#[warn(clippy::needless_return)]` on by default
help: remove `return`

warning: manual `RangeInclusive::contains` implementation
 --> src/main.rs:2:8
  |
2 |     if x >= 0 && x <= 100 {
  |        ^^^^^^^^^^^^^^^^^^ help: use: `(0..=100).contains(&x)`

warning: the loop variable `i` is only used to index `v`
  --> src/main.rs:10:14
   |
10 |     for i in 0..v.len() {
   |              ^^^^^^^^^^
```

Clippy не понимает логику вашей программы, но находит формы, в которых любят прятаться ошибки (цикл по диапазону, нужный только для индексации, — там и живут ошибки на единицу). **Относитесь к предупреждениям Clippy как к части работы**: запускайте `cargo clippy` перед каждым коммитом.

- **`cargo test`** — ваши тесты, всегда.
- **RustRover** — красные и жёлтые пометки в редакторе — это компилятор и Clippy, работающие пока вы печатаете. Наведите курсор, чтобы прочитать сообщение.

## 6. Git как инструмент отладки

Контроль версий помнит каждое состояние вашего кода. Три команды помогают находить ошибки:

**Что я изменил?** Когда что-то работало час назад, а сейчас не работает:

```bash
git status            # which files changed
git diff              # the exact lines changed since the last commit
git diff HEAD~3       # the changes compared with three commits ago
git log -p -n 3       # the last three commits with their changes
```

**Вернуться и попробовать.** `git stash` откладывает ваши незакоммиченные изменения в сторону, чтобы вы могли проверить, работает ли последний коммит ([Урок 01.5](../01-git-and-version-control/05-undoing-changes-safely.md)); `git stash pop` возвращает их.

**Какой коммит всё сломал? `git bisect`.** Если у вас много коммитов и вы знаете, что старый был хорошим, а текущий плохой, `git bisect` находит первый плохой коммит **двоичным поиском**: он переключается на коммит из середины, вы говорите «хороший» или «плохой», и он снова делит диапазон пополам. Для 1000 коммитов нужно всего около 10 проверок. Ещё лучше, он может запускать команду за вас: команда, которая завершается успехом для хорошего коммита и неудачей для плохого, — это тест!

Вот настоящий пример. В небольшом проекте 8 коммитов. Функция `average` была верной, затем один коммит её «упростил» до `a + b / 2` (неверный приоритет операторов — Урок 02.3), и тест `average(4, 6) == 5` начал падать:

```text
$ git log --oneline
840d9ae docs: add note 6
bea4b60 docs: add note 5
1e352c0 docs: add note 4
fa9e438 refactor: simplify average
058a626 docs: add note 3
d91fb94 docs: add note 2
b999561 docs: add note 1
50cf810 feat: add average
```

Мы пишем маленький скрипт `check.sh`, который запускает тесты и возвращает успех или неудачу, затем:

```bash
git bisect start
git bisect bad HEAD                 # the current version is broken
git bisect good 50cf810             # the first commit was fine
git bisect run ./check.sh           # let Git test the commits in the middle
```

```text
Bisecting: 3 revisions left to test after this (roughly 2 steps)
[058a6268025c0964fd3c294476c5cce69679d5cc] docs: add note 3
...
fa9e438f585e485a161d5e24b5f8f12150c49835 is the first bad commit
commit fa9e438f585e485a161d5e24b5f8f12150c49835
Author: Demo <demo@example.com>

    refactor: simplify average

 calc/src/lib.rs | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
bisect found first bad commit
```

```bash
git bisect reset                    # go back to where you were
git show fa9e438                    # read the change that caused the bug
```

Git проверил только 3 коммита из 8 и назвал виновника вместе с его сообщением и изменением. **Маленькие коммиты с понятными сообщениями** (привычка с Этапа 01) — то, что делает `bisect` полезным: он указывает на коммит в 5 строк вместо коммита в 500.

## 7. Семейства частых ошибок

| Ошибка | Типичный признак | Где искать |
|---|---|---|
| Ошибка на единицу | Пропал последний (или первый) элемент; паника индекса | Концы диапазонов `..` и `..=`; `len()` и `len() - 1`; `<` и `<=` |
| Целочисленное деление | Результат «округлён вниз» | `/` для целых чисел (Урок 02.3) |
| Переполнение | Паника `attempt to add with overflow` или завёрнутый результат в релизе | Слишком маленькие типы (Урок 02.2) |
| Неверный приоритет операторов | Формула, выглядящая верной, даёт неверные числа | Добавьте скобки (Урок 02.3) |
| Забытый `trim()` | «invalid digit found in string» для ввода, который выглядит верным | Обработка ввода (Урок 02.7) |
| Сюрприз затенения | У переменной старое значение после блока | `let x` внутри блока создаёт новый `x` (Урок 02.1) |
| Бесконечный цикл | Программа зависла, вентилятор шумит | Переменная цикла никогда не меняется |
| Смешанные единицы | Результаты отличаются в разы | Числа с плавающей точкой и целые, секунды и миллисекунды |

## Частые ошибки

**1. Менять код, не поняв ошибку.** Сначала воспроизведите и подтвердите причину.

**2. Исправлять симптом.** Добавление особого случая, чтобы «этот ввод заработал», оставляет настоящую ошибку на месте.

**3. Оставлять `dbg!` и отладочную печать в коде.** Удаляйте их до коммита.

**4. Отладка релизной сборки.** В оптимизированной сборке нет отладочной информации и значений переменных; отлаживайте с `cargo build` / `cargo run` (профиль dev).

**5. Не написать регрессионный тест.** Ошибка вернётся.

**6. Менять много вещей сразу.** Меняйте одну вещь, запускайте, смотрите.

**7. Отлаживать уставшим.** Сначала сделайте перерыв.

> 🧪 **Тестирование:** хороший отчёт об ошибке — это упавший тест. Когда кто-то говорит «ваша функция даёт неверный ответ для 3», первое, что вы делаете, — пишете `assert_eq!(f(3), expected)` и смотрите, как он падает. После исправления сохраните тест навсегда.

> ⚡ **Производительность:** `dbg!` и `println!` в горячем цикле могут замедлить программу в сто раз, потому что печать медленная (Урок 02.6). Когда вы отлаживаете медленную программу, не доверяйте измерениям времени сборки с печатью и никогда не измеряйте скорость в отладочной сборке (Этап 05, Урок 12).

## Упражнения

### Упражнение 1 — Найдите ошибку с помощью `dbg!` (легко)

Эта программа должна напечатать `average of 4 and 6 = 5`, но печатает `7`. С помощью `dbg!` посмотрите на части выражения, найдите проблему и исправьте её. Среднее `1` и `2` должно быть `1.5`.

```rust
fn average(a: i32, b: i32) -> f64 {
    (a + b / 2) as f64
}

fn main() {
    println!("average of 4 and 6 = {}", average(4, 6));
    assert_eq!(average(4, 6), 5.0);
}
```

<details>
<summary>Подсказка</summary>

Напишите `dbg!(b / 2)` и `dbg!(a + b / 2)`. Какой оператор вычисляется первым? (Урок 02.3: приоритет.) Помните также, что целочисленное деление отбрасывает дробную часть.

</details>

<details>
<summary>Ответ</summary>

```rust
fn average(a: i32, b: i32) -> f64 {
    (a + b) as f64 / 2.0
}

fn main() {
    println!("average of 4 and 6 = {}", average(4, 6));
    assert_eq!(average(4, 6), 5.0);
    assert_eq!(average(1, 2), 1.5);
}
```

```text
average of 4 and 6 = 5
```

Почему это работает: у `/` приоритет выше, чем у `+`, поэтому старый код вычислял `4 + (6 / 2) = 7`. Исправление сначала складывает числа, преобразует в `f64`, чтобы сохранить дробную часть, и делит на `2.0`. Второе утверждение проверяет случай с дробью.

</details>

### Упражнение 2 — Прочитайте backtrace (легко)

Вот часть backtrace программы, которая запаниковала:

```text
thread 'main' panicked at src/main.rs:2:5:
attempt to divide by zero
stack backtrace:
   2: core::panicking::panic_const::panic_const_div_by_zero
   3: b_backtrace::divide
             at ./src/main.rs:2:5
   4: b_backtrace::average
             at ./src/main.rs:6:5
   5: b_backtrace::main
             at ./src/main.rs:11:20
```

Ответьте: (a) В какой функции и на какой строке произошла паника? (b) Кто вызвал эту функцию и с какой строки? (c) Какую строку `main` нужно изменить или проверить?

<details>
<summary>Подсказка</summary>

Игнорируйте кадры стандартной библиотеки. Идите вниз по списку: каждый кадр — это *вызывающий* для кадра выше.

</details>

<details>
<summary>Ответ</summary>

(a) В `divide`, строка 2, столбец 5 (выражение `a / b`). (b) Её вызвала `average` на строке 6; `average` вызвала `main` на строке 11, столбец 20. (c) Строку 11 в `main`: `average(10, 0)` передаёт счётчик, равный нулю. Нужно либо не вызывать с нулём, либо сделать так, чтобы `average` проверяла `count == 0` и решала, что делать.

Почему это работает: строка паники показывает, где программа *упала*; backtrace показывает *путь*, который к этому привёл, и причина часто на несколько кадров выше.

</details>

### Упражнение 3 — Исправление с регрессионным тестом (средне)

Возьмите ошибочную `sum_of_squares` из раздела 4. Сначала напишите `#[test]`, который падает (проверьте `3 → 14`, `1 → 1`, `0 → 0`), и прочитайте сообщение о падении. Затем исправьте функцию. Затем снова запустите тест.

<details>
<summary>Подсказка</summary>

Падение показывает `left: 5`, `right: 14`: это `1 + 4`. Значения `3 * 3 = 9` не хватает, поэтому цикл не доходит до `n`. Замените `1..n` на `1..=n`.

</details>

<details>
<summary>Ответ</summary>

```rust
fn sum_of_squares(n: u32) -> u32 {
    let mut total = 0;
    for i in 1..=n {
        total += i * i;
    }
    total
}

fn main() {
    println!("sum of squares up to 3 = {}", sum_of_squares(3));
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn sums_squares_including_n() {
        assert_eq!(sum_of_squares(3), 14);
        assert_eq!(sum_of_squares(1), 1);
        assert_eq!(sum_of_squares(0), 0);
    }
}
```

Почему это работает: для `n = 0` диапазон `1..=0` пуст, и сумма равна `0` — верный крайний случай. Теперь тест документирует все три случая и защищает от возвращения ошибки.

</details>

### Упражнение 4 — Две ошибки в одной функции (средне)

Функция должна считать чётные цифры числа (`2468 → 4`, `1357 → 0`, `4 → 1`, `1020 → 3`). Тест падает. Найдите **обе** ошибки с помощью `dbg!` или отладчика и исправьте их.

```rust
fn count_even_digits(mut n: u32) -> u32 {
    let mut count = 0;
    while n > 10 {
        if n % 10 % 2 == 0 {
            count += 1;
        }
        n = n / 100;
    }
    count
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn counts_even_digits() {
        assert_eq!(count_even_digits(2468), 4);
        assert_eq!(count_even_digits(1357), 0);
        assert_eq!(count_even_digits(4), 1);
        assert_eq!(count_even_digits(1020), 3);
    }
}
```

<details>
<summary>Подсказка</summary>

Первое падение показывает `left: 2`, `right: 4` для `2468`: половина цифр пропущена. Напечатайте `n` в начале каждой итерации. Затем проверьте условие цикла на однозначном числе вроде `4`.

</details>

<details>
<summary>Ответ</summary>

```rust
fn count_even_digits(mut n: u32) -> u32 {
    let mut count = 0;
    while n > 0 {
        if n % 10 % 2 == 0 {
            count += 1;
        }
        n = n / 10;
    }
    count
}
```

Почему это работает: ошибка 1 — `n / 100` убирает **две** цифры за раз, поэтому каждая вторая цифра пропускается (`2468` → `24` → `0`, считаются только `8` и `4`); нужно `n / 10`. Ошибка 2 — условие `n > 10` останавливается раньше последней цифры, когда `n` однозначное (`4` не больше 10); нужно `n > 0`. После исправления проходят все четыре утверждения. (У числа `0` одна цифра, но эта функция возвращает для него `0`; решение, что верно для `0`, — вопрос проектирования для нового теста.)

</details>

### Упражнение 5 — Найдите плохой коммит с помощью `git bisect` (сложно)

Выполните этот скрипт во временной папке (не в вашем учебном репозитории). Он создаёт репозиторий с 8 коммитами; файл `value.txt` корректен, пока его значение меньше 50.

```bash
mkdir /tmp/bisect-demo && cd /tmp/bisect-demo && git init -q -b main .
for n in 10 20 30 40 50 60 70 80; do echo $n > value.txt; git add value.txt; git commit -q -m "set value to $n"; done
git log --oneline
```

С помощью `git bisect` и `git bisect run` найдите первый коммит, в котором значение равно 50 или больше. Проверяющая команда — `sh -c 'test "$(cat value.txt)" -lt 50'` (она успешна, когда значение меньше 50). Затем наведите порядок командой `git bisect reset`.

<details>
<summary>Подсказка</summary>

Начните с `git bisect start`, отметьте `HEAD` как плохой, а `HEAD~7` (первый коммит) как хороший, затем используйте `git bisect run` с командой.

</details>

<details>
<summary>Ответ</summary>

```bash
git bisect start
git bisect bad HEAD
git bisect good HEAD~7
git bisect run sh -c 'test "$(cat value.txt)" -lt 50'
git bisect reset
```

Вывод заканчивается так:

```text
aa6339cdc8ee7db17485442f0dc3ca6c19fb4109 is the first bad commit
commit aa6339cdc8ee7db17485442f0dc3ca6c19fb4109
Author: Demo <demo@example.com>

    set value to 50

 value.txt | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
bisect found first bad commit
```

(Хеш коммита и автор у вас будут другими.) Почему это работает: Git проверил только коммиты `40` и `50` — каждый раз он делил диапазон пополам — и обнаружил, что коммит `set value to 50` первый, для которого команда падает. `git bisect reset` возвращает вас в `main`.

</details>

## Вопросы для самопроверки

1. Каковы первые два шага отладки?

<details>
<summary>Ответ</summary>

Надёжно воспроизвести ошибку и изолировать её (сделать задачу как можно меньше, в идеале — упавший тест).

</details>

2. Что печатает `dbg!(x * 2)` и что возвращает?

<details>
<summary>Ответ</summary>

Он печатает в stderr файл, строку, текст `x * 2` и его значение, а возвращает значение, так что программа продолжает работать без изменений.

</details>

3. Как получить backtrace для паники и как его читать?

<details>
<summary>Ответ</summary>

Запустить с `RUST_BACKTRACE=1`. Пропустите кадры стандартной библиотеки, найдите первый кадр вашего крейта и читайте вниз: каждый кадр — это вызывающий для кадра выше.

</details>

4. Чем отличаются *Step Over* и *Step Into* в отладчике?

<details>
<summary>Ответ</summary>

*Step Over* выполняет текущую строку, не останавливаясь внутри вызываемых функций. *Step Into* заходит в вызываемую функцию и останавливается на её первой строке.

</details>

5. Почему `debug_assert!` может проходить в релизном режиме, когда то же условие падает в отладочном?

<details>
<summary>Ответ</summary>

`debug_assert!` удаляется из релизных сборок, поэтому проверка вообще не выполняется.

</details>

6. Что делает `git bisect run ./check.sh`?

<details>
<summary>Ответ</summary>

Автоматически переключается на коммиты между хорошим и плохим, запускает скрипт на каждом и с помощью двоичного поиска находит первый коммит, на котором скрипт падает.

</details>

7. Что нужно сделать после исправления ошибки, кроме коммита?

<details>
<summary>Ответ</summary>

Написать (или сохранить) регрессионный тест, который падает без исправления и проходит с ним, чтобы ошибка не вернулась незаметно.

</details>

## Итоги

- Отлаживайте методично: воспроизвести, изолировать, предположить, проверить, исправить, добавить тест, коммит.
- Читайте сообщение о панике (файл, строка, причина) и backtrace (путь вызовов; ищите кадры вашего крейта).
- `println!`/`eprintln!` с `{:?}` и подписями, `dbg!` для быстрого взгляда, `debug_assert!` для проверок только в отладочных сборках.
- Отладчик (RustRover или `lldb`) позволяет приостанавливаться на точках останова, идти с обходом/заходом/выходом и наблюдать переменные.
- `cargo check`, `cargo clippy` и `cargo test` находят много ошибок до начала отладки.
- Git помогает: `git diff` показывает, что изменилось, `git stash` откладывает изменения, `git bisect` находит коммит, внёсший ошибку.
- Маленькие коммиты и регрессионный тест для каждой ошибки облегчают поиск следующей.
