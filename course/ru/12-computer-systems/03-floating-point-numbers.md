# Урок 12.3 — Числа с плавающей точкой

> **Этап 12 — Компьютерные системы** · Урок 3 из 15 · ⏱ около 120 минут

## Новые слова

| Слово | Значение |
|---|---|
| **плавающая точка** (floating point) | Способ хранить вещественные числа как «цифры × 2 в какой-то степени». Точка «плавает»: те же биты могут хранить 0,000001 или 1 000 000. |
| **IEEE 754** | Стандарт (от IEEE, Institute of Electrical and Electronics Engineers, Институт инженеров электротехники и электроники), который задаёт форматы и правила для чисел с плавающей точкой. `f32` — его формат *binary32*, `f64` — формат *binary64*. |
| **знак / порядок / дробная часть** (sign / exponent / fraction) | Три поля числа: один бит под знак, степень двойки (порядок) и цифры после двоичной точки (дробная часть, её называют ещё *мантиссой*). |
| **смещение порядка** (bias) | Число, которое прибавляют к настоящему порядку, чтобы хранить его без знака: 127 для `f32`, 1023 для `f64`. |
| **скрытый бит** (hidden bit) | Ведущая `1.` нормального числа. Она есть всегда, поэтому её не хранят. |
| **ULP** (Unit in the Last Place, единица последнего разряда) | Промежуток между числом и следующим большим числом с плавающей точкой. Он растёт вместе с величиной числа. |
| **машинный эпсилон** (machine epsilon) | ULP числа 1.0: самый маленький шаг, который можно прибавить к 1.0. `f32::EPSILON` ≈ 1,19 × 10⁻⁷, `f64::EPSILON` ≈ 2,22 × 10⁻¹⁶. |
| **NaN** (Not a Number, «не число») | Особое значение для результатов без смысла, например 0/0. Оно ничему не равно, даже самому себе. |
| **субнормальное число** (subnormal number) | Крошечное число ниже нормального диапазона, без скрытого бита. Позволяет числам плавно уменьшаться до нуля. |
| **ошибка округления** (rounding error) | Небольшая разница между точным результатом операции и ближайшим числом, которое компьютер может сохранить. |
| **допуск** (tolerance) | Какую разницу вы готовы принять при сравнении двух чисел («равны с точностью до 10⁻⁹»). |

## 1. Научная запись, но в двоичной системе

Вы, возможно, знаете научную запись из школы: скорость света — 2,998 × 10⁸ м/с. Число записывается как **несколько цифр**, умноженных на **степень десяти**. Так одними и теми же несколькими цифрами можно записать и огромные, и крошечные числа.

Число с плавающей точкой делает ровно это, но по основанию 2:

```text
value = (-1)^sign × 1.fraction × 2^exponent
```

Сначала нужны двоичные *дроби*. После двоичной точки веса разрядов — это половины: ½, ¼, ⅛, 1/16 и так далее.

```text
place value:   4   2   1  .  1/2  1/4  1/8
5.75 =         1   0   1  .   1    1    0     (4 + 1 + 0.5 + 0.25)
```

Значит, 5.75 в двоичной системе — это `101.11`. Сдвиньте точку так, чтобы перед ней стояла ровно одна `1`, как в научной записи: `101.11` = `1.0111 × 2²`. Это **нормальная форма**: часть до точки всегда `1`, поэтому число её даже не хранит (**скрытый бит**). Хранятся только знак, порядок 2 и биты дробной части `0111…`.

### Устройство `f32`

```text
 bit 31   bits 30..23        bits 22..0
┌──────┬──────────────┬───────────────────────────┐
│ sign │ exponent (8) │       fraction (23)       │
└──────┴──────────────┴───────────────────────────┘
value = (-1)^sign × 1.fraction × 2^(exponent - 127)
```

Поле порядка хранится со **смещением** 127: записанное число — это настоящий порядок + 127, чтобы отрицательным порядкам не нужен был знак. Для 5.75 записанный порядок равен 2 + 127 = 129. У `f64` то же устройство: 1 бит знака, 11 битов порядка (смещение 1023) и 52 бита дробной части.

Проверим это на настоящих значениях. `to_bits()` возвращает 32 бита `f32` как `u32`. Чтобы вырезать поля, используем сдвиг (`>>`) и **маску** с `&`: `x & 0xff` оставляет только младшие 8 битов. Урок 12.4 подробно учит маскам; здесь достаточно читать их как «вырежи эти биты».

```rust
fn show(x: f32) {
    let bits = x.to_bits();
    let sign = bits >> 31;
    let exponent = (bits >> 23) & 0xff;
    let fraction = bits & 0x7f_ffff;
    println!(
        "{x:>10}: {sign} {exponent:08b} {fraction:023b}  (exponent {exponent} - 127 = {})",
        exponent as i32 - 127
    );
}

fn main() {
    for x in [1.0f32, 2.0, 5.75, -5.75, 0.1, 0.5] {
        show(x);
    }
}
```

**Что происходит:**

1. `bits >> 31` переносит старший бит вниз: это знак.
2. `(bits >> 23) & 0xff` переносит поле порядка вниз и оставляет его 8 битов.
3. `bits & 0x7f_ffff` оставляет младшие 23 бита (`0x7fffff` — это 23 единицы): дробную часть.

```text
         1: 0 01111111 00000000000000000000000  (exponent 127 - 127 = 0)
         2: 0 10000000 00000000000000000000000  (exponent 128 - 127 = 1)
      5.75: 0 10000001 01110000000000000000000  (exponent 129 - 127 = 2)
     -5.75: 1 10000001 01110000000000000000000  (exponent 129 - 127 = 2)
       0.1: 0 01111011 10011001100110011001101  (exponent 123 - 127 = -4)
       0.5: 0 01111110 00000000000000000000000  (exponent 126 - 127 = -1)
```

Читайте вывод так:

- 1.0 — это `1.0 × 2⁰`: дробная часть — все нули, порядок 0. 2.0 отличается только порядком: `1.0 × 2¹`.
- У 5.75 ровно та дробная часть `0111`, которую мы нашли вручную. −5.75 отличается только знаковым битом. (Отрицательные числа с плавающей точкой **не** используют дополнительный код; знак — отдельный бит.)
- У 0.1 дробная часть повторяет `1001 1001 1001 …` и заканчивается на `…1101`. Этот конец округлён. Следующий раздел объясняет почему.

## 2. Почему 0.1 не хранится точно

В десятичной системе 1/3 = 0,3333… никогда не кончается. В двоичной то же происходит с 1/10: 0.1 — это `0.000110011001100110011…` бесконечно, потому что 1/10 нельзя сложить из нескольких половин, четвертей и восьмых. У числа всего 23 (или 52) бита дробной части, поэтому компьютер хранит **ближайшее** число, которое может. Напечатайте больше цифр, чем обычно, — и вы это увидите:

```rust
fn main() {
    println!("0.1f32 is really {:.30}", 0.1f32);
    println!("0.1f64 is really {:.30}", 0.1f64);
    println!("0.5f64 is really {:.30}", 0.5f64);
    let mut sum = 0.0f64;
    for _ in 0..10 {
        sum += 0.1;
    }
    println!("0.1 added ten times = {sum}");
    println!("{:.20}", 0.1 + 0.2);
}
```

**Что происходит:**

1. `{:.30}` печатает 30 цифр после точки. Значение `f32` ошибается в 9-й цифре, значение `f64` — в 18-й.
2. 0.5 — это ½, одна двоичная цифра, поэтому оно хранится точно. Числа, составленные из половин, четвертей, восьмых… (0.25, 0.375, 5.75), точны; большинство «красивых» десятичных чисел — нет.
3. Каждое сложение немного округляет; десять маленьких ошибок складываются в заметную разницу.

```text
0.1f32 is really 0.100000001490116119384765625000
0.1f64 is really 0.100000000000000005551115123126
0.5f64 is really 0.500000000000000000000000000000
0.1 added ten times = 0.9999999999999999
0.30000000000000004441
```

> ⚠️ **Частая ошибка:** думать, что Rust печатает «настоящее» значение. По умолчанию `{}` печатает **самый короткий** десятичный текст, который превращается обратно в то же самое число. Поэтому `0.1` печатается как `0.1`, хотя хранится не ровно 0.1.

### Промежутки растут с величиной

У числа фиксированное количество битов дробной части. Для чисел от 1 до 2 они описывают шаги по 2⁻²³; от 2 до 4 те же биты описывают шаги вдвое крупнее, и так далее. Поэтому **промежуток между соседними числами (ULP) растёт вместе с числом**:

```rust
fn main() {
    let big = 16_777_216.0f32; // 2^24
    println!("{} + 1 = {}", big, big + 1.0);
    println!("{} + 2 = {}", big, big + 2.0);
    println!("16777217 as f32 = {}", 16_777_217u32 as f32);
    let huge = 9_007_199_254_740_992.0f64; // 2^53
    println!("{} + 1 = {}", huge, huge + 1.0);

    for x in [1.0f64, 1000.0, 1_000_000.0, 1e15] {
        println!("gap after {x:>16}: {:e}", x.next_up() - x);
    }
    println!("f32::EPSILON = {:e}, f64::EPSILON = {:e}", f32::EPSILON, f64::EPSILON);
}
```

**Что происходит:**

1. Начиная с 2²⁴ = 16 777 216, `f32` может хранить только **чётные** целые числа: промежуток равен 2. Прибавленная 1 теряется при округлении. У целого 16 777 217 вообще нет представления в `f32`.
2. Для `f64` то же происходит на 2⁵³: до этой границы каждое целое число точно, выше — нет.
3. `next_up()` возвращает следующее большее число. Промежуток после 1.0 — это **машинный эпсилон**; после 10¹⁵ он уже 0,125.

```text
16777216 + 1 = 16777216
16777216 + 2 = 16777218
16777217 as f32 = 16777216
9007199254740992 + 1 = 9007199254740992
gap after                1: 2.220446049250313e-16
gap after             1000: 1.1368683772161603e-13
gap after          1000000: 1.1641532182693481e-10
gap after 1000000000000000: 1.25e-1
f32::EPSILON = 1.1920929e-7, f64::EPSILON = 2.220446049250313e-16
```

> ⚠️ **Частая ошибка:** использовать `f32` для счётчика, идентификатора или метки времени. После 16 777 216 счётчик на `f32` перестаёт считать: `x + 1.0 == x`. Для всего, что вы считаете, используйте целые числа.

## 3. Особые значения

Два варианта поля порядка зарезервированы. **Все нули** означают ноль или *субнормальное* число. **Все единицы** означают бесконечность или NaN.

```rust
fn main() {
    let values = [0.0f32, -0.0, f32::INFINITY, f32::NEG_INFINITY, f32::NAN, f32::MIN_POSITIVE, f32::from_bits(1), f32::MAX];
    for x in values {
        println!("{x:>14e}  bits {:#010x}  normal? {:<5} nan? {}", x.to_bits(), x.is_normal(), x.is_nan());
    }
    println!("0.0 == -0.0 : {}", 0.0f32 == -0.0);
    let nan = f32::NAN;
    println!("nan == nan  : {}", nan == nan);
    println!("1/-0.0      : {}", 1.0f32 / -0.0);
    println!("f32::MAX * 2: {}", f32::MAX * 2.0);
    println!("nan as i32 = {}, 1e20 as i32 = {}, -1e20 as u8 = {}", nan as i32, 1e20f32 as i32, -1e20f32 as u8);
}
```

**Что происходит:**

1. **Ноль** — это все нулевые биты. У **отрицательного нуля** установлен только знаковый бит (`0x80000000`). При сравнении они равны, но биты у них разные, и `1 / -0.0` даёт `-inf`.
2. У **бесконечности** порядок — все единицы, дробная часть — ноль (`0x7f800000`). Она появляется, когда результат слишком велик: `f32::MAX * 2.0`.
3. У **NaN** порядок — все единицы, а дробная часть не нулевая. `nan == nan` равно `false`: по стандарту NaN ничему не равен. Для проверки используйте `is_nan()`.
4. `f32::MIN_POSITIVE` (около 1,18 × 10⁻³⁸) — самое маленькое **нормальное** число. Ниже идут **субнормальные** числа: поле порядка равно 0, скрытого бита нет. `from_bits(1)`, самое маленькое из них, — это около 1,4 × 10⁻⁴⁵ (печатается как `1e-45` — самый короткий текст, который даёт те же биты).
5. Превращение числа с плавающей точкой в целое через `as` в Rust определено: оно **насыщается** на границах целого типа, а NaN становится 0. Оно никогда не заворачивается и никогда не роняет программу.

```text
           0e0  bits 0x00000000  normal? false nan? false
          -0e0  bits 0x80000000  normal? false nan? false
           inf  bits 0x7f800000  normal? false nan? false
          -inf  bits 0xff800000  normal? false nan? false
           NaN  bits 0x7fc00000  normal? false nan? true
 1.1754944e-38  bits 0x00800000  normal? true  nan? false
         1e-45  bits 0x00000001  normal? false nan? false
  3.4028235e38  bits 0x7f7fffff  normal? true  nan? false
0.0 == -0.0 : true
nan == nan  : false
1/-0.0      : -inf
f32::MAX * 2: inf
nan as i32 = 0, 1e20 as i32 = 2147483647, -1e20 as u8 = 0
```

Поскольку NaN не равен самому себе, числа с плавающей точкой нарушают правило, которое обещает трейт `Eq` («каждое значение равно самому себе»). Поэтому `f32` и `f64` реализуют только `PartialEq` и `PartialOrd`, но не `Eq` и `Ord`. Вы почувствуете это при сортировке (см. «Частые ошибки»).

> 🔒 **Безопасность:** NaN из плохого ввода распространяется молча: любое вычисление с NaN даёт NaN, и любое сравнение с ним — `false`. Проверка вроде `if amount > limit { reject }` пропустит NaN. Когда вы разбираете числа, пришедшие извне, отбрасывайте NaN и бесконечность через `x.is_finite()`.

## 4. Округление: порядок важен

Каждая операция с плавающей точкой округляет свой точный результат до ближайшего числа. Одна ошибка округления крошечная, но у неё странное следствие: **порядок сложений меняет результат**. В обычной математике (a + b) + c = a + (b + c). Для чисел с плавающей точкой это не всегда так:

```rust
fn main() {
    let a = 1e16f64;
    let b = -1e16f64;
    let c = 1.0f64;
    println!("(a + b) + c = {}", (a + b) + c);
    println!("a + (b + c) = {}", a + (b + c));

    let mut v = vec![2.5f64, -1.0, f64::NAN, 0.0, -0.0, 10.0];
    v.sort_by(|x, y| x.total_cmp(y));
    println!("sorted with total_cmp: {v:?}");
    println!("max of 1.0 and NaN: {}", 1.0f64.max(f64::NAN));
}
```

**Что происходит:**

1. `(a + b) + c`: `a + b` — ровно 0, затем + 1 даёт 1.
2. `a + (b + c)`: около 10¹⁶ промежуток между числами равен 2, поэтому `b + c` = −10¹⁶ + 1 округляется обратно до −10¹⁶. Единица теряется, и результат — 0.
3. `total_cmp` — это **полный порядок** для чисел с плавающей точкой: он ставит каждое значение, даже NaN и −0.0, на определённое место (−0.0 перед 0.0, положительный NaN в конце). Используйте его для сортировки.
4. `max` и `min` игнорируют аргумент NaN и возвращают другое число.

```text
(a + b) + c = 1
a + (b + c) = 0
sorted with total_cmp: [-1.0, -0.0, 0.0, 2.5, 10.0, NaN]
max of 1.0 and NaN: 1
```

Из-за округления компилятору **не** разрешено переставлять сложения чисел с плавающей точкой ради скорости (это изменило бы ваши результаты). Как это влияет на скорость, вы увидите в Уроке 12.6.

> ⚡ **Производительность:** `f64` выбран по умолчанию не зря: на вашем Mac для отдельных значений он примерно так же быстр, как `f32`. `f32` оправдан, когда значений миллионы (он вдвое уменьшает память и вдвое увеличивает число значений, помещающихся в кэш-линию и в регистр SIMD — SIMD, Single Instruction, Multiple Data, «одна инструкция, много данных», означает инструкцию, которая работает сразу с несколькими значениями; Уроки 12.9 и 19.7 вернутся к этому), а меньшая точность допустима.

> 🧪 **Тестирование:** никогда не используйте `assert_eq!` для вычисленных чисел с плавающей точкой. Сравнивайте с допуском (Упражнение 3). Явно проверяйте особые значения: `0.0`, `-0.0`, `NaN`, `INFINITY`, субнормальное число и очень большое число. А для кода, который превращает числа в биты и обратно, тест туда-обратно через `to_bits()` сравнивает точные биты, так что там `assert_eq!` безопасен.

## Частые ошибки

> ⚠️ **Частая ошибка: сортировать числа с плавающей точкой как целые.** Для `sort()` нужен `Ord`, которого у них нет:

```rust
fn main() {
    let mut v = vec![2.5f64, 1.0];
    v.sort();
    println!("{v:?}");
}
```

```text
error[E0277]: the trait bound `f64: Ord` is not satisfied
 --> src/main.rs:3:7
  |
3 |     v.sort();
  |       ^^^^ the trait `Ord` is not implemented for `f64`
```

Частое «исправление» — `sort_by(|a, b| a.partial_cmp(b).unwrap())`. Оно компилируется, но паникует, как только в данных появляется NaN, потому что `partial_cmp` возвращает `None` для NaN:

```rust
fn main() {
    let mut v = vec![2.5f64, f64::NAN, 1.0];
    v.sort_by(|a, b| a.partial_cmp(b).unwrap());
    println!("{v:?}");
}
```

```text

thread 'main' (5505498) panicked at src/main.rs:3:39:
called `Option::unwrap()` on a `None` value
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

Настоящее исправление: `v.sort_by(|a, b| a.total_cmp(b))`.

> ⚠️ **Частая ошибка: абсолютный допуск для любых величин.** `(a - b).abs() < 1e-9` работает для чисел около 1, но около 10²⁰ промежуток между числами намного больше 10⁻⁹, и два «равных» результата никогда не пройдут проверку. Для чисел любой величины используйте **относительный** допуск (Упражнение 3).

> ⚠️ **Частая ошибка: деньги в числах с плавающей точкой.** Даже 0,10 доллара нельзя сохранить точно. Храните деньги целым числом самых мелких единиц (центов, `i64`).

2. Напечатайте `f64::MAX`, `f64::MIN_POSITIVE` и `f64::EPSILON` через `{:e}` (через `{}` первые два печатаются сотнями цифр). Сравните их со значениями `f32` выше.
3. Найдите циклом первое целое число, которое `f32` не может сохранить: начните с `0u32` и остановитесь на первом `n`, для которого `(n as f32) as u32 != n`. (Должно получиться 16 777 217.)

## Упражнения

### Упражнение 1 — Разбор вручную (легко)

Какое число означают биты `f32` `0x40a00000`? И какие биты у −2.5? Решите на бумаге, затем проверьте через `f32::from_bits` и `to_bits`.

<details>
<summary>Подсказка</summary>

`0x40a00000` в двоичной системе — `0100 0000 1010 0000 …`. Разделите на 1 + 8 + 23 бита. Для −2.5: 2.5 = `10.1` в двоичной системе = `1.01 × 2¹`.

</details>

<details>
<summary>Ответ</summary>

```rust
fn main() {
    println!("{}", f32::from_bits(0x40a0_0000));
    println!("{:#010x}", (-2.5f32).to_bits());
}
```

```text
5
0xc0200000
```

Почему это работает: `0x40a00000` = знак `0`, порядок `10000001` = 129 → 2, дробная часть `0100…` → `1.01₂ × 2²` = 1,25 × 4 = 5. Для −2.5: знак `1`, порядок 1 + 127 = 128 = `10000000`, дробная часть `0100…`; биты `1100 0000 0010 0000 …` — это `0xc0200000`.

</details>

### Упражнение 2 — Разбор и сборка в коде (средне)

В `src/lib.rs` напишите `pub fn decode_f32(x: f32) -> (u32, i32, u32)`, которая возвращает знаковый бит, порядок **без смещения** и 23 бита дробной части. Напишите `pub fn encode_f32(sign: u32, exponent: i32, fraction: u32) -> f32`, которая делает обратное для нормальных чисел. Проверьте известные значения (1.0, 5.75, −0.5) и путь туда-обратно для нескольких значений.

<details>
<summary>Подсказка</summary>

Используйте сдвиги и маски из раздела 1 и вычтите смещение 127. Для сборки прибавьте смещение, верните каждую часть на место через `<<`, объедините их через `|` (побитовое ИЛИ) и вызовите `f32::from_bits`.

</details>

<details>
<summary>Ответ</summary>

```rust
/// Splits an f32 into its sign bit, unbiased exponent and 23 fraction bits.
pub fn decode_f32(x: f32) -> (u32, i32, u32) {
    let bits = x.to_bits();
    let sign = bits >> 31;
    let exponent = ((bits >> 23) & 0xff) as i32 - 127;
    let fraction = bits & 0x7f_ffff;
    (sign, exponent, fraction)
}

/// Builds a normal f32 back from its parts: (-1)^sign * 1.fraction * 2^exponent.
pub fn encode_f32(sign: u32, exponent: i32, fraction: u32) -> f32 {
    let biased = (exponent + 127) as u32;
    f32::from_bits((sign << 31) | (biased << 23) | fraction)
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn decodes_known_values() {
        assert_eq!(decode_f32(1.0), (0, 0, 0));
        assert_eq!(decode_f32(5.75), (0, 2, 0b0111 << 19));
        assert_eq!(decode_f32(-0.5), (1, -1, 0));
    }

    #[test]
    fn round_trip_for_many_values() {
        for x in [1.0f32, -2.5, 0.1, 3.14159, 1e30, -1e-30, f32::MAX] {
            let (s, e, f) = decode_f32(x);
            assert_eq!(encode_f32(s, e, f), x, "value {x}");
        }
    }
}
```

Почему это работает: поля не пересекаются, поэтому `|` просто ставит их рядом. Для 5.75 дробная часть `0111` стоит в начале 23 битов, то есть `0b0111 << 19`. Сравнивать числа после пути туда-обратно через `assert_eq!` здесь можно, потому что никакой арифметики не было: биты идентичны.

</details>

### Упражнение 3 — Сравнение с относительным допуском (средне)

Напишите `pub fn approx_eq(a: f64, b: f64, rel: f64) -> bool`, которая возвращает `true`, когда разница не больше `rel`, умноженного на большее из `|a|` и `|b|`. Тесты: `0.1 + 0.2` ≈ `0.3`; `1e20 + 1e5` ≈ `1e20`; `1.0` не ≈ `1.001`; `0.0` ≈ `-0.0`; NaN не ≈ NaN (везде `rel = 1e-12`).

<details>
<summary>Подсказка</summary>

Сначала обработайте `a == b` (это покрывает `0.0` и `-0.0`, а также бесконечности одного знака). Затем сравните `(a - b).abs()` с `a.abs().max(b.abs()) * rel`. Любое сравнение с NaN даёт `false`, поэтому случай NaN работает сам собой.

</details>

<details>
<summary>Ответ</summary>

```rust
/// True if a and b differ by at most `rel` times the larger of their sizes.
pub fn approx_eq(a: f64, b: f64, rel: f64) -> bool {
    if a == b {
        return true;
    }
    let diff = (a - b).abs();
    let largest = a.abs().max(b.abs());
    diff <= largest * rel
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn approx_eq_cases() {
        assert!(approx_eq(0.1 + 0.2, 0.3, 1e-12));
        assert!(approx_eq(1e20 + 1e5, 1e20, 1e-12));
        assert!(!approx_eq(1.0, 1.001, 1e-12));
        assert!(approx_eq(0.0, -0.0, 1e-12));
        assert!(!approx_eq(f64::NAN, f64::NAN, 1e-12));
    }
}
```

Почему это работает: относительный допуск масштабируется вместе с величиной чисел — так же, как промежутки между ними. Обратите внимание на одно ограничение: сравнение ровно с `0.0` (`approx_eq(1e-300, 0.0, …)`) даёт `false`, потому что относительная величина разницы — 100%. Около нуля нужен дополнительный абсолютный допуск.

</details>

### Упражнение 4 — Суммирование Кэхэна (сложно)

Если десять миллионов раз прибавить 0.1, должно получиться 1 000 000, но простая сумма ошибается примерно на 10⁻⁴. Суммирование Кэхэна (Kahan summation) хранит ошибку округления каждого шага во второй переменной и прибавляет её обратно. Напишите `pub fn kahan_sum(values: &[f64]) -> f64` и тест, который показывает, что она точнее, чем `values.iter().sum()`, и отличается от точного ответа не больше чем на 10⁻⁶.

<details>
<summary>Подсказка</summary>

Храните `sum` и `lost` (накопленную ошибку, вначале 0). Для каждого `x`: `y = x - lost` (поправить новое значение), `t = sum + y` (округлённая новая сумма), `lost = (t - sum) - y` (что отбросило округление), `sum = t`.

</details>

<details>
<summary>Ответ</summary>

```rust
/// Kahan summation: keeps the rounding error of each addition and adds it back.
pub fn kahan_sum(values: &[f64]) -> f64 {
    let mut sum = 0.0;
    let mut lost = 0.0;
    for &x in values {
        let y = x - lost;
        let t = sum + y;
        lost = (t - sum) - y;
        sum = t;
    }
    sum
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn kahan_is_more_accurate() {
        let values = vec![0.1; 10_000_000];
        let naive: f64 = values.iter().sum();
        let careful = kahan_sum(&values);
        let exact = 1_000_000.0;
        println!("naive error = {:e}, kahan error = {:e}", (naive - exact).abs(), (careful - exact).abs());
        assert!((careful - exact).abs() < (naive - exact).abs());
        assert!((careful - exact).abs() < 1e-6);
    }
}
```

С `cargo test kahan -- --nocapture` вы увидите напечатанную строку:

```text
naive error = 1.610246254131198e-4, kahan error = 0e0
```

Почему это работает: `(t - sum)` — это та часть `y`, которая действительно попала в сумму; вычитание `y` оставляет часть, потерянную при округлении. Следующий шаг прибавляет её обратно. Это работает только потому, что компилятор сохраняет порядок операций с плавающей точкой ровно таким, как написано (раздел 4); при перестановке `lost` всегда был бы 0.

</details>

## Вопросы для самопроверки

1. Какие три поля у `f32` и сколько битов в каждом?

<details>
<summary>Ответ</summary>

Знак (1 бит), порядок (8 битов, смещение 127), дробная часть (23 бита). У `f64` — 1, 11 (смещение 1023) и 52.

</details>

2. Почему нормальное число не хранит `1` перед двоичной точкой?

<details>
<summary>Ответ</summary>

В нормальной форме там всегда `1`, поэтому хранить её — значит тратить бит впустую. Этот «скрытый бит» бесплатно даёт один лишний бит точности.

</details>

3. Почему 0.5 хранится точно, а 0.1 — нет?

<details>
<summary>Ответ</summary>

0.5 — это ½, один двоичный разряд. 0.1 — бесконечная периодическая двоичная дробь (`0.000110011…`), поэтому её приходится округлять до ближайшего числа.

</details>

4. Чему равно `16_777_216.0f32 + 1.0` и почему?

<details>
<summary>Ответ</summary>

`16777216`. На 2²⁴ промежуток между значениями `f32` равен 2, поэтому точный результат 16 777 217 округляется до соседа.

</details>

5. Почему `f64` не реализует `Ord`?

<details>
<summary>Ответ</summary>

Из-за NaN: он не равен самому себе и не упорядочен ни с каким значением, поэтому полный порядок с `==` и `<` невозможен. Для сортировки используйте `total_cmp`.

</details>

6. Что даёт `f64::NAN as i32` в Rust и что даёт `1e20 as i32`?

<details>
<summary>Ответ</summary>

0 и `i32::MAX` (2147483647). Преобразование числа с плавающей точкой в целое через `as` насыщается на границах и превращает NaN в 0.

</details>

7. Почему `(a + b) + c` и `a + (b + c)` могут различаться для чисел с плавающей точкой?

<details>
<summary>Ответ</summary>

Каждое сложение округляет свой результат. При другом порядке округляются другие промежуточные результаты, поэтому маленькое значение может потеряться в одном порядке и сохраниться в другом.

</details>

## Итоги

- Число с плавающей точкой — это `(-1)^sign × 1.fraction × 2^(exponent − bias)`: у `f32` 1 + 8 + 23 бита (смещение 127), у `f64` 1 + 11 + 52 бита (смещение 1023).
- Точны только суммы степеней двойки; 0.1 округляется. `{}` печатает самый короткий текст, который даёт то же число, а не точное хранимое значение.
- Промежуток между числами (ULP) растёт вместе с числом: `f32` хранит каждое целое только до 2²⁴, `f64` — до 2⁵³.
- Особые значения: ±0, ±бесконечность, NaN (не равен самому себе) и субнормальные числа. `as` из числа с плавающей точкой в целое насыщается, NaN становится 0.
- Каждая операция округляет, поэтому порядок операций важен; компилятор сохраняет ваш порядок.
- Сравнивайте с относительным допуском, сортируйте через `total_cmp`, отбрасывайте NaN из ввода через `is_finite`, а деньги и счётчики храните в целых числах.
