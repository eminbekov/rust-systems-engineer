## Новые слова

| Слово | Значение |
|---|---|
| **IP-адрес** (Internet Protocol address) | Число, которое идентифицирует сетевой интерфейс, например `172.30.0.2` (IPv4: четыре числа) или `::1` (IPv6: длиннее). |
| **интерфейс** (interface) | Сетевое подключение компьютера, например `eth0` (кабель или виртуальный кабель) или `lo` (петля). |
| **префикс** (prefix: `/24`, `/16`) | Сколько начальных бит адреса задают сеть. `172.30.0.2/16` значит: сеть — `172.30.0.0`, и все адреса `172.30.x.y` находятся в той же локальной сети. |
| **шлюз** (gateway, роутер) | Компьютер, который пересылает пакеты в другие сети. *Маршрут по умолчанию* говорит: «всё остальное — на шлюз». |
| **DNS** (Domain Name System, система доменных имён) | Система, которая превращает имена вроде `example.com` в IP-адреса. Программа-*резолвер* спрашивает *сервер имён*. |
| **TCP** (Transmission Control Protocol, протокол управления передачей) | Протокол, дающий надёжное двустороннее соединение между двумя программами. Его используют HTTP и SSH. |
| **UDP** (User Datagram Protocol, протокол пользовательских датаграмм) | Более простой протокол, который отправляет отдельные сообщения без соединения. DNS обычно использует его. |
| **сокет** (socket) | Один конец сетевого соединения, заданный адресом и портом. Программа, которая *слушает*, имеет сокет, ожидающий соединений. |
| **привязка** (bind) | Присоединение слушающего сокета к адресу и порту. *Адрес привязки* определяет, какие сети могут достучаться до программы. |
| **HTTP** (HyperText Transfer Protocol, протокол передачи гипертекста) | Текстовый протокол веба: запрос (`GET /`) и ответ (код состояния вроде `200`, заголовки, тело). |
| **код состояния** (status code) | Число в ответе HTTP: `200` — хорошо, `404` — не найдено, `500` — ошибка сервера. |
| **TLS** (Transport Layer Security, защита транспортного уровня) | Слой шифрования за `https://` ([Урок 10.11](../10-security-fundamentals/11-tls-and-certificates.md)). |
| **ICMP** (Internet Control Message Protocol, протокол управляющих сообщений) | Небольшие сообщения, которые используют `ping` и `traceroute`. |

## 1. Лестница для сломанных соединений

«Служба не отвечает» может иметь шесть разных причин. Команды этого урока проверяют их снизу вверх. Всегда поднимайтесь по лестнице в этом порядке; первый шаг, который не прошёл, и есть ваша проблема:

| Шаг | Вопрос | Команда | Типичный сбой |
|---|---|---|---|
| 1 | Есть ли у этой машины адрес? | `ip -br addr` | на `eth0` нет адреса |
| 2 | Знает ли она путь наружу? | `ip route` | нет маршрута `default` |
| 3 | Превращается ли имя в адрес? | `getent hosts ИМЯ`, `dig` | `Could not resolve host` |
| 4 | Достижима ли другая машина? | `ping`, `traceroute` | `100% packet loss` |
| 5 | Слушает ли порт какая-нибудь программа? | `nc -zv ХОСТ ПОРТ`, `ss -ltn` | `Connection refused` |
| 6 | Правильно ли отвечает программа? | `curl -v URL` | неверный код состояния, пустой ответ |

Два сбоя выглядят по-разному и означают разное. **Connection refused** (отказ в соединении) возвращается сразу: машина на месте, но на этом порту никто не слушает. **Тайм-аут** означает тишину: пакеты теряются по дороге или файрвол (фильтр, отбрасывающий пакеты) их выбрасывает.

## 2. Адреса и маршруты

```bash
ip -br addr show up
ip route
```

Пример вывода:

```text
lo               UNKNOWN        127.0.0.1/8 ::1/128
eth0@if3158      UP             172.30.0.2/16
default via 172.30.0.1 dev eth0
172.30.0.0/16 dev eth0 proto kernel scope link src 172.30.0.2
```

**Что происходит:**

1. `ip` — инструмент для просмотра и изменения сети в Linux. `-br` («brief», кратко) печатает по одной строке на интерфейс; `show up` скрывает выключенные интерфейсы.
2. `lo` — это **петля** (loopback). Её адрес `127.0.0.1` (и `::1` в IPv6) всегда означает «именно этот компьютер». Трафик к нему никогда не покидает машину.
3. `eth0` — настоящее соединение. `172.30.0.2/16` — его адрес и префикс. В вашей ВМ будут другие числа (Lima обычно использует `192.168.5.x`).
4. `ip route` — таблица маршрутизации: `172.30.0.0/16 dev eth0` говорит, что адреса своей сети достигаются напрямую через `eth0`; `default via 172.30.0.1` говорит *всё остальное идёт на шлюз* `172.30.0.1`.

Спросите, каким путём пойдёт пакет к определённому адресу:

```bash
ip route get 1.1.1.1
```

```text
1.1.1.1 via 172.30.0.1 dev eth0 src 172.30.0.2 uid 0
    cache
```

## 3. Имена: `/etc/hosts`, `/etc/resolv.conf`, `dig`

Программы работают с именами; сеть работает с адресами. Linux разрешает имя в таком порядке: сначала файл `/etc/hosts` (небольшой список, который вы контролируете), затем сервер имён, указанный в `/etc/resolv.conf`.

```bash
getent hosts example.com
dig +short example.com
```

```text
172.66.147.243  example.com
104.20.23.154   example.com
172.66.147.243
104.20.23.154
```

`getent hosts` спрашивает систему так же, как ваши программы (он читает и `/etc/hosts`). `dig` — диагностический инструмент: он напрямую спрашивает сервер имён. `+short` печатает только ответы. У одного имени может быть несколько адресов.

Полный ответ смотрите в `dig example.com A` (сокращённо):

```text
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 2327
;; QUESTION SECTION:
;example.com.			IN	A

;; ANSWER SECTION:
example.com.		307	IN	A	172.66.147.243
example.com.		307	IN	A	104.20.23.154

;; Query time: 2 msec
;; SERVER: 127.0.0.11#53(127.0.0.11) (UDP)
```

**Что происходит:** `A` — тип записи «адрес IPv4» (`AAAA` — IPv6, `MX` — почтовые серверы, `NS` — серверы имён домена). `307` — число секунд, в течение которых ответ можно кэшировать (TTL, time to live, время жизни). `SERVER:` — сервер имён, который ответил; он берётся из `/etc/resolv.conf`. `status: NOERROR` — успех; для несуществующего имени вы увидите `status: NXDOMAIN`, а `getent hosts` ничего не напечатает и вернёт код 2.

Имя для этой машины можно переопределить через `/etc/hosts` (нужен `sudo`):

```bash
echo "127.0.0.1 myservice.test" | sudo tee -a /etc/hosts
getent hosts myservice.test
```

```text
127.0.0.1       myservice.test
```

(Имя заканчивается на `.test` — домен, зарезервированный для таких опытов. Удалите строку обратно в редакторе или командой `sudo sed -i '/myservice.test/d' /etc/hosts`.)

## 4. Достижимо ли? `ping` и `traceroute`

```bash
ping -c 3 localhost
ping -c 2 example.com
```

```text
PING example.com (172.66.147.243) 56(84) bytes of data.
64 bytes from 172.66.147.243: icmp_seq=1 ttl=63 time=82.1 ms
64 bytes from 172.66.147.243: icmp_seq=2 ttl=63 time=80.5 ms

--- example.com ping statistics ---
2 packets transmitted, 2 received, 0% packet loss, time 1006ms
rtt min/avg/max/mdev = 80.496/81.277/82.059/0.781 ms
```

`ping` отправляет маленькие «эхо»-сообщения ICMP и ждёт ответов. `-c 2` означает два пакета (без этого `ping` работает до `Ctrl + C`). `time` — время кругового пути в миллисекундах. `ttl` — счётчик «времени жизни» пакета: каждый маршрутизатор уменьшает его на единицу. `ping localhost` проверяет только вашу собственную машину.

> ⚠️ **Частая ошибка:** считать неудачный `ping` признаком того, что «сервер не работает». Многие серверы и файрволы намеренно игнорируют ICMP. Лучшее доказательство — работающий `curl` или `nc` на настоящий порт; один неудавшийся `ping` ничего не доказывает.

`traceroute -n example.com` перечисляет маршрутизаторы на пути (`-n` пропускает поиск имён). Строки с `*` — маршрутизаторы, которые не отвечают. Это полезно, чтобы увидеть, *где* останавливаются пакеты, но сегодня многие сети скрывают путь, так что считайте результат подсказкой.

## 5. Порты и сокеты: `ss` и `nc`

**Порт** позволяет одной машине запускать много сетевых программ: адрес находит машину, порт — программу. Программа, которая хочет принимать соединения, *слушает* порт. `ss` (socket statistics, статистика сокетов) выводит список сокетов:

```bash
ss -ltn
```

```text
State  Recv-Q Send-Q Local Address:Port  Peer Address:Port
LISTEN 0      128          0.0.0.0:8080       0.0.0.0:*
```

| Опция | Значение |
|---|---|
| `-l` | только слушающие сокеты (**l**istening) |
| `-t` / `-u` | **t**CP / **u**DP |
| `-n` | числа (**n**umbers), без поиска имён (быстрее, яснее) |
| `-p` | показать процесс (**p**rocess), которому принадлежит сокет (процессы других пользователей видны только с `sudo`) |

Прочитайте строку: `0.0.0.0:8080` значит «слушает порт 8080 на **всех** адресах IPv4». Добавьте `-p`, чтобы увидеть программу:

```text
LISTEN 0      128          0.0.0.0:8080       0.0.0.0:*    users:(("p11-bind",pid=129,fd=3))
```

`ss -tn state established` показывает открытые соединения. Для соединения одной программы с другой на той же машине вы видите две строки, по одной на каждый конец:

```text
Recv-Q Send-Q Local Address:Port  Peer Address:Port
0      0          127.0.0.1:60338    127.0.0.1:9000
0      0          127.0.0.1:9000     127.0.0.1:60338
```

Клиентский конец использует случайный высокий порт (`60338`, *эфемерный* порт, выбранный системой); серверный конец — порт, который он слушает (`9000`). `ss -lun` показывает сокеты UDP.

**`nc`** (netcat) открывает простые соединения. С `-z` он только проверяет, открыт ли порт, `-v` печатает результат, а `-w 2` ждёт не дольше двух секунд:

```bash
nc -zv 127.0.0.1 8080
nc -zv -w 2 127.0.0.1 9
echo "status: $?"
```

```text
Connection to 127.0.0.1 8080 port [tcp/http-alt] succeeded!
nc: connect to 127.0.0.1 port 9 (tcp) failed: Connection refused
status: 1
```

Можно и сделать `nc` слушателем для экспериментов: `nc -l 9000` ждёт соединения на порту 9000 и печатает всё, что приходит. Код возврата (0 — открыт, 1 — нет) делает `nc -z` удобным в скриптах, как в Упражнении 1.

## 6. HTTP с `curl`

`curl` отправляет запрос и печатает ответ. Для веб-сервера это самый полезный инструмент этого урока. Сначала нужен сервер, с которым можно говорить: программа на Rust из раздела 7 отвечает на каждый запрос одной строкой. Вот что показывает `curl` (сервер слушает порт 8080):

```bash
curl -s http://127.0.0.1:8080/
curl -i -s http://127.0.0.1:8080/
curl -s -o /dev/null -w "code=%{http_code} size=%{size_download}\n" http://127.0.0.1:8080/
```

```text
hello from p11-bind
HTTP/1.1 200 OK
Content-Length: 20
Connection: close

hello from p11-bind
code=200 size=20
```

| Опция | Значение |
|---|---|
| `-s` | тихий режим (**s**ilent): без индикатора прогресса (но и без текста ошибок; добавьте `-S`, чтобы ошибки всё же показывались) |
| `-i` | включить заголовки ответа в вывод (`-I` отправляет запрос `HEAD`: только заголовки) |
| `-o файл` | записать тело в файл (`-o /dev/null` выбрасывает его) |
| `-w 'формат'` | напечатать значения после передачи, например `%{http_code}` и `%{time_total}` |
| `-m 2` | сдаться через 2 секунды (в скриптах всегда задавайте лимит) |
| `-f` | сбой (**f**ail): завершиться с ошибкой при коде 400 и выше вместо печати страницы ошибки |
| `-v` | подробный режим (**v**erbose): показать каждый шаг, включая DNS, рукопожатие TLS и запрос |

`-v` на настоящем сайте с `https` показывает всю цепочку этого урока в нескольких строках (выборка из вывода `curl -sv https://example.com -o /dev/null 2>&1`):

```text
* Host example.com:443 was resolved.
* IPv4: 172.66.147.243, 104.20.23.154
* TLSv1.3 (OUT), TLS handshake, Client hello (1):
* TLSv1.3 (IN), TLS handshake, Server hello (2):
* Server certificate:
*   subject: CN=example.com
*   subjectAltName: "example.com" matches cert's "example.com"
> GET / HTTP/2
> Host: example.com
```

Строки с `*` — собственные заметки `curl`, `>` — то, что он отправил, `<` — то, что пришло. Вы видите, как имя разрешилось в адреса (шаг 3), TCP-соединение (шаг 5), рукопожатие TLS с проверкой сертификата, а затем запрос.

**Коды возврата.** `curl` говорит, *где* именно произошёл сбой, что соответствует лестнице:

```bash
curl -sS http://127.0.0.1:9/;            echo "exit: $?"
curl -sS http://no-such-name.invalid/;   echo "exit: $?"
curl -sS -m 2 http://10.255.255.1/;      echo "exit: $?"
```

```text
curl: (7) Failed to connect to 127.0.0.1 port 9 after 0 ms: Could not connect to server
exit: 7
curl: (6) Could not resolve host: no-such-name.invalid
exit: 6
curl: (28) Connection timed out after 2003 milliseconds
exit: 28
```

| Код возврата | Значение | Шаг лестницы |
|---|---|---|
| 6 | не удалось разрешить имя хоста | 3 (DNS) |
| 7 | в соединении отказано (никто не слушает или нет пути) | 5 (порт) |
| 28 | тайм-аут (тишина: файрвол, потерянные пакеты) | 2, 4 или 5 |
| 22 | с `-f`: сервер ответил кодом 400 или выше | 6 |

(`10.255.255.1` — частный адрес, на котором никто не отвечает, поэтому соединение зависает до лимита. Безвредно, но не используйте его как сервер.)

## 7. Ваш сервер на Rust и адрес привязки

Каждая сетевая программа должна сказать, **на каком адресе** она слушает. Эта одна настройка вызывает значительную долю проблем «у меня работает», а Docker в следующих уроках делает её ещё важнее. Создайте небольшой сервер на Mac:

```bash
cd ~/projects/rust
cargo new code/p11-bind
```

Замените `src/main.rs` (файл использует только стандартную библиотеку, поэтому `Cargo.toml` остаётся как есть):

```rust
use std::io::{Read, Write};
use std::net::{TcpListener, TcpStream};

/// Reads the request (and ignores it), then answers with a fixed page.
fn handle(mut stream: TcpStream) -> std::io::Result<()> {
    let mut buffer = [0u8; 1024];
    let _ = stream.read(&mut buffer)?;
    let body = "hello from p11-bind\n";
    write!(
        stream,
        "HTTP/1.1 200 OK\r\nContent-Length: {}\r\nConnection: close\r\n\r\n{}",
        body.len(),
        body
    )
}

fn main() -> std::io::Result<()> {
    // The address to listen on, for example 127.0.0.1:8080 or 0.0.0.0:8080.
    let addr = std::env::args()
        .nth(1)
        .unwrap_or_else(|| "127.0.0.1:8080".to_string());
    let listener = TcpListener::bind(&addr)?;
    println!("listening on {}", listener.local_addr()?);

    for stream in listener.incoming() {
        // A broken connection must not stop the server.
        if let Err(error) = stream.and_then(handle) {
            eprintln!("connection error: {error}");
        }
    }
    Ok(())
}
```

**Что происходит:**

1. `TcpListener::bind(&addr)` создаёт слушающий сокет для адреса, заданного текстом первого аргумента командной строки (по умолчанию `127.0.0.1:8080`). `local_addr()` показывает, что система выбрала на самом деле.
2. `listener.incoming()` выдаёт каждое новое соединение. `handle` читает байты запроса, игнорирует их и пишет ответ HTTP: строку состояния, заголовки, пустую строку (`\r\n\r\n`), затем тело. `Content-Length` сообщает клиенту, сколько байтов тела следует.
3. Клиент вроде `nc -z` подключается и сразу закрывает соединение, поэтому запись ответа завершается ошибкой `Broken pipe`. `if let Err` печатает ошибку и продолжает работу; при простом `?` в `main` один такой клиент остановил бы весь сервер.

Скопируйте проект в ВМ и соберите его, как в Уроке 11.5 (замените `student` на имя вашего пользователя Mac):

```bash
mkdir -p ~/code/p11-bind
cp -r /Users/student/projects/rust/code/p11-bind/Cargo.toml /Users/student/projects/rust/code/p11-bind/src ~/code/p11-bind/
cd ~/code/p11-bind && cargo build --release
```

Запустите его **только на петле** в фоне и посмотрите на сокет:

```bash
./target/release/p11-bind 127.0.0.1:8080 &
sleep 1
ss -ltn | grep 8080
curl -s http://127.0.0.1:8080/
```

```text
listening on 127.0.0.1:8080
LISTEN 0      128        127.0.0.1:8080       0.0.0.0:*
hello from p11-bind
```

Теперь важный эксперимент с **двумя отдельными компьютерами** в одной сети. У серверной машины адрес `172.30.0.2`, а `curl` запускается на другой машине. Пример вывода для такой пары (позже вы сможете повторить это с двумя контейнерами). Когда сервер привязан к `127.0.0.1`, другой компьютер получает:

```text
$ curl -sS -m 3 http://172.30.0.2:8080/
curl: (7) Failed to connect to 172.30.0.2 port 8080 after 0 ms: Could not connect to server
```

После остановки сервера и запуска с `0.0.0.0:8080` (**все** адреса машины) `ss` показывает `0.0.0.0:8080`, и тот же запрос с другого компьютера работает:

```text
$ curl -sS -m 3 http://172.30.0.2:8080/
hello from p11-bind
```

| Адрес привязки | Кто может подключиться |
|---|---|
| `127.0.0.1:8080` | только программы на этой же машине |
| `0.0.0.0:8080` | любой, кто может достучаться до любого адреса машины (другие компьютеры, контейнеры, Mac через перенаправление портов Lima) |
| `192.168.5.15:8080` | только через этот один адрес |

> 🔒 **Безопасность:** по умолчанию привязывайтесь к `127.0.0.1`, а `0.0.0.0` открывайте только для служб, которые должны быть доступны, лучше всего за файрволом или обратным прокси. База данных или админ-страница на `0.0.0.0` — один из самых частых способов утечки данных. В Docker (Урок 11.12) встречается обратная ошибка: сервер внутри контейнера, слушающий `127.0.0.1`, недоступен снаружи контейнера, даже если порт опубликован.

Ещё три вещи, с которыми вы встретитесь:

- **Address already in use** (адрес уже используется). Две программы не могут слушать один и тот же адрес и порт. Вторая завершится на `bind` с `Error: Os { code: 98, kind: AddrInUse, message: "Address already in use" }`. Найдите владельца командой `ss -ltnp | grep 8080`.
- **Permission denied на низком порту.** В Linux по умолчанию только root может слушать порты ниже 1024. Обычный пользователь для порта 80 получает `Error: Os { code: 13, kind: PermissionDenied, message: "Permission denied" }`. Используйте высокий порт (`8080`) и позвольте прокси или платформе контейнеров отобразить его, вместо запуска службы от root.
- **`localhost` — не всегда `127.0.0.1`.** `p11-bind localhost:8081` печатает `listening on [::1]:8081`: система выдала сначала IPv6, и `curl http://127.0.0.1:8081/` получил бы отказ. В службах пишите числовые адреса.

Остановите сервер, когда закончите: `kill %1` (или `pkill p11-bind`).

🧪 **Тестирование:** чтобы тестировать сетевую программу без фиксированных портов, привязывайтесь к **порту 0**. Система выбирает свободный порт, а `local_addr()` сообщает его. Такой тест пишется в Упражнении 3.

## Частые ошибки

1. **Проверка не с той стороны.** Работающий `curl http://127.0.0.1:8080` на сервере ничего не говорит о других компьютерах. *Исправление:* проверьте адрес привязки через `ss -ltn` и проверяйте со второй машины.
2. **Принимать `ping` за истину** (ICMP может быть заблокирован) или тайм-аут за «отказ». *Исправление:* используйте `nc -zv` и `curl` и помните разницу между отказом (ответили «нет») и тайм-аутом (тишина).
3. **Забыть `-m` в скриптах.** `curl` или `nc` без лимита времени может на минуты повесить скрипт развёртывания. *Исправление:* `curl -m 5`, `nc -w 2`, `ssh -o ConnectTimeout=5`.
4. **Использовать `0.0.0.0` для всего.** *Исправление:* по умолчанию петля.
5. **Править `/etc/resolv.conf` вручную.** В Ubuntu им управляет `systemd-resolved`, и ваше изменение будет перезаписано. *Исправление:* `resolvectl status` показывает настоящую конфигурацию, а для локальных имён есть `/etc/hosts`.

## Попробуйте сами

2. Выполните `getent hosts example.com` и `dig +short example.com`. Добавьте в `/etc/hosts` строку для `myservice.test` и разрешите это имя. Затем удалите строку.
3. Соберите `p11-bind` в ВМ. Запустите его на `127.0.0.1:8080`, найдите его через `ss -ltnp` и вызовите через `curl -i`. Затем попробуйте запустить вторую копию и прочитайте ошибку.
4. Выполните `curl -sv https://example.com -o /dev/null 2>&1 | head -20` и найдите: разрешённые адреса, версию TLS, строку запроса.

## Упражнения

### Упражнение 1 — Проверка порта и её тест (средне)

Напишите `check-port.sh HOST PORT` в `code/p11-scripts`: он использует `nc -z -w 2`, печатает `HOST:PORT is open` и завершается с кодом 0, либо печатает `HOST:PORT is closed or filtered` в стандартный поток ошибок и завершается с кодом 1. При нехватке аргументов он должен остановиться с сообщением об использовании. Затем напишите `test-check-port.sh`, который запускает в фоне `nc -l 127.0.0.1 9099` и проверяет код 0 для порта 9099 и код 1 для порта 9 (слушателя завершите через `trap`).

<details>
<summary>Подсказка</summary>

`host=${1:?usage: check-port.sh HOST PORT}` останавливает скрипт с сообщением. В тесте `nc -l ... &` и `server=$!`. Подождите полсекунды (`sleep 0.5`), чтобы слушатель был готов. Код сохраняйте так: `rc=0; command || rc=$?`.

</details>

<details>
<summary>Ответ</summary>

```bash
#!/usr/bin/env bash
# check-port.sh HOST PORT - exit 0 if a TCP connection to HOST:PORT works, 1 if not.
set -u

host=${1:?usage: check-port.sh HOST PORT}
port=${2:?usage: check-port.sh HOST PORT}

if nc -z -w 2 "$host" "$port" 2> /dev/null; then
    echo "$host:$port is open"
else
    echo "$host:$port is closed or filtered" >&2
    exit 1
fi
```

```bash
#!/usr/bin/env bash
# test-check-port.sh - needs nc (netcat-openbsd) and check-port.sh in the same folder
set -u
here=$(cd "$(dirname "$0")" && pwd)
failures=0

nc -l 127.0.0.1 9099 > /dev/null &     # a listener on port 9099
server=$!
trap 'kill "$server" 2> /dev/null' EXIT
sleep 0.5

rc=0; bash "$here/check-port.sh" 127.0.0.1 9099 > /dev/null 2>&1 || rc=$?
if (( rc == 0 )); then echo "ok   - open port"; else echo "FAIL - open port (status $rc)"; failures=$((failures + 1)); fi

rc=0; bash "$here/check-port.sh" 127.0.0.1 9 > /dev/null 2>&1 || rc=$?
if (( rc == 1 )); then echo "ok   - closed port"; else echo "FAIL - closed port (status $rc)"; failures=$((failures + 1)); fi

(( failures == 0 ))
```

Запуск `bash test-check-port.sh` печатает:

```text
ok   - open port
ok   - closed port
```

Почему это работает: `nc -l` принимает ровно одно соединение, которое использует первая проверка; вторая проверка обращается к порту, где никто не слушает, поэтому `nc -z` завершается с «Connection refused». Тесту не нужна сеть за пределами машины.

</details>

### Упражнение 2 — Исправьте недоступный сервер (легко)

Коллега говорит: «Моя служба на Rust в контейнере слушает `127.0.0.1:3000`, я опубликовал порт 3000, а снаружи всё равно получаю ошибку». Объясните причину и что должна изменить служба. (Вы воспроизведёте это с Docker в Уроке 11.13.)

<details>
<summary>Подсказка</summary>

Посмотрите на раздел 7: кто может подключиться к сокету, привязанному к `127.0.0.1`? Где находится эта петля, когда программа работает в контейнере?

</details>

<details>
<summary>Ответ</summary>

Внутри контейнера петля `127.0.0.1` принадлежит только контейнеру. Опубликованный порт приходит на сетевой интерфейс контейнера (`eth0`), а не на его петлю, поэтому служба, привязанная к `127.0.0.1`, никогда не видит соединения. Служба должна привязаться к `0.0.0.0:3000` (лучше всего читать адрес из переменной окружения, например `BIND`: по умолчанию `127.0.0.1` для локальной работы, а в контейнере `0.0.0.0`).

Почему это работает: адрес привязки выбирает, какие интерфейсы принимают соединения; `0.0.0.0` означает все интерфейсы машины, включая тот, через который Docker подключается наружу.

</details>

### Упражнение 3 — Проверьте сервер на порту 0 (сложно)

Добавьте в `p11-bind` тест: привяжите слушатель к `127.0.0.1:0`, примите одно соединение в потоке и выполните на нём `handle`, подключитесь как клиент, отправьте запрос, прочитайте весь ответ и проверьте, что он начинается с `HTTP/1.1 200 OK` и заканчивается на `hello from p11-bind\n`.

<details>
<summary>Подсказка</summary>

`TcpListener::bind("127.0.0.1:0")`, затем `listener.local_addr()` для порта. Серверная часть работает в `std::thread::spawn(move || ...)`. Клиент вызывает `write_all` и `read_to_string`, что работает, потому что ответ содержит `Connection: close`. В конце вызовите `join()` для потока.

</details>

<details>
<summary>Ответ</summary>

Добавьте в `src/main.rs`:

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use std::thread;

    #[test]
    fn answers_with_the_fixed_page() {
        // Port 0 asks the system for any free port, so tests never collide.
        let listener = TcpListener::bind("127.0.0.1:0").unwrap();
        let addr = listener.local_addr().unwrap();
        let server = thread::spawn(move || {
            let (stream, _) = listener.accept().unwrap();
            handle(stream).unwrap();
        });

        let mut client = TcpStream::connect(addr).unwrap();
        client.write_all(b"GET / HTTP/1.1\r\n\r\n").unwrap();
        let mut reply = String::new();
        client.read_to_string(&mut reply).unwrap();
        server.join().unwrap();

        assert!(reply.starts_with("HTTP/1.1 200 OK"));
        assert!(reply.ends_with("hello from p11-bind\n"));
    }
}
```

`cargo test` печатает:

```text
running 1 test
test tests::answers_with_the_fixed_page ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Почему это работает: тест — это полноценные клиент и сервер в одном процессе. Поскольку порт выбирает система, он никогда не конфликтует с работающей службой или параллельным тестом. `use super::*` приносит в модуль тестов `handle`, `TcpListener` и `TcpStream`, а вместе с ними и трейты `Read` и `Write`.

</details>

## Вопросы для самопроверки

1. В чём разница между «connection refused» и тайм-аутом?

<details>
<summary>Ответ</summary>

Отказ возвращается сразу: машина достижима, но на этом порту никто не слушает (или машина отклонила соединение). Тайм-аут — это тишина: пакеты теряются или файрвол их отбрасывает.

</details>

2. О чём говорит строка `0.0.0.0:8080` в `ss -ltn`?

<details>
<summary>Ответ</summary>

Программа слушает порт 8080 на всех адресах IPv4 машины, так что подключаться могут и другие компьютеры. `127.0.0.1:8080` означало бы только эту же машину.

</details>

3. Какой файл читается первым при разрешении имени программой: `/etc/hosts` или сервер имён?

<details>
<summary>Ответ</summary>

`/etc/hosts`. Только если имени там нет, система спрашивает сервер имён из `/etc/resolv.conf`.

</details>

4. Что означают коды возврата `curl` 6, 7 и 28?

<details>
<summary>Ответ</summary>

6: не удалось разрешить имя хоста. 7: в соединении отказано (никто не слушает или нет маршрута). 28: истекло время операции.

</details>

5. Почему тест из Упражнения 3 привязывается к порту 0?

<details>
<summary>Ответ</summary>

Порт 0 заставляет систему выбрать любой свободный порт. Тест никогда не конфликтует с другой программой или другим тестом, работающим одновременно; `local_addr()` возвращает выбранный порт.

</details>

6. Чем может вводить в заблуждение неудавшийся `ping`?

<details>
<summary>Ответ</summary>

Многие серверы и файрволы отбрасывают ICMP, поэтому `ping` не проходит, хотя веб-служба работает. Проверяйте настоящий порт службы через `nc -zv` или `curl`.

</details>

## Итоги

- Поднимайтесь по лестнице: адрес (`ip -br addr`), маршрут (`ip route`), имя (`getent hosts`, `dig`), достижимость (`ping`), порт (`nc -zv`, `ss -ltn`), приложение (`curl -v`).
- Отказ значит «ответили нет»; тайм-аут значит тишину. Коды `curl` 6, 7 и 28 указывают на DNS, закрытый порт и тайм-аут.
- `ss -ltnp` показывает, какая программа что слушает; локальный адрес в этой строке — адрес привязки.
- `127.0.0.1` доступен только с той же машины, `0.0.0.0` — из каждой сети машины. По умолчанию привязывайтесь к петле, а адрес открывайте осознанно.
- Rust: `TcpListener::bind(addr)`, обрабатывайте оборванное соединение, не останавливая сервер, и тестируйте с портом 0.
- В скриптах всегда задавайте лимиты времени (`curl -m`, `nc -w`).
