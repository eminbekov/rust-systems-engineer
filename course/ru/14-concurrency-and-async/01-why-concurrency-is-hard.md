# Урок 14.1 — Почему конкурентность сложна: гонки и взаимные блокировки

> **Этап 14 — Конкурентность и асинхронность подробно** · Урок 1 из 16 · ⏱ около 135 минут

## Что вы узнаете

- Почему порядок выполнения потоков вам не подвластен и что такое *чередование* (interleaving).
- Чем гонка данных (Rust останавливает её при компиляции) отличается от состояния гонки (его Rust остановить не может).
- Два классических состояния гонки: *потерянное обновление* и *«проверить, затем действовать»*.
- Что такое взаимная блокировка, какие четыре условия ей нужны и простейшее лекарство — фиксированный порядок захвата блокировок.
- Почему ошибки конкурентности прячутся от обычных тестов и что с этим делать.

- Вы знаете, как OS (Operating System, операционная система) запускает потоки на ядрах CPU (Central Processing Unit, центральный процессор) и переключается между ними: [Урок 13.9 — Потоки и планирование](../13-operating-systems/09-threads-and-scheduling.md).

## Новые слова

| Слово | Значение |
|---|---|
| **чередование** (interleaving) | Один из возможных порядков, в котором шаги нескольких потоков перемешиваются во времени. |
| **общее состояние** (shared state) | Данные, которые может читать или менять больше одного потока. |
| **гонка данных** (data race) | Два потока обращаются к одной и той же памяти одновременно, хотя бы один из них пишет, и ничто не упорядочивает эти обращения. В безопасном Rust такое не компилируется. |
| **состояние гонки** (race condition) | Ошибка, при которой результат зависит от того, как по времени выполнились потоки. Возможна и в безопасном Rust. |
| **потерянное обновление** (lost update) | Состояние гонки: два потока читают одно и то же старое значение, оба записывают новое, и одна из записей теряется. |
| **чтение-изменение-запись** (read-modify-write) | Операция из трёх шагов: прочитать значение, вычислить новое, записать его обратно. `x += 1` — именно такая операция. |
| **«проверить, затем действовать»** (check-then-act) | Состояние гонки: поток проверяет условие, а действует позже, но за это время условие изменилось. |
| **критическая секция** (critical section) | Код, который выполняется, пока удерживается блокировка. |
| **инвариант** (invariant) | Правило о ваших данных, которое должно быть верно всегда, например «общая сумма денег в банке не меняется». |
| **взаимная блокировка** (deadlock) | Два или больше потоков вечно ждут друг друга. |
| **порядок захвата блокировок** (lock ordering) | Правило, по которому каждый поток берёт несколько блокировок в одном и том же фиксированном порядке. Не даёт возникнуть взаимной блокировке. |
| **активная блокировка** (livelock) | Потоки всё время реагируют друг на друга и заняты делом, но ни один не продвигается. |
| **голодание** (starvation) | Один поток ждёт очень долго (или вечно), потому что ресурс всегда первыми получают другие потоки. |
| **гейзенбаг** (heisenbug) | Ошибка, которая исчезает или меняется, когда вы пытаетесь её наблюдать (например, добавляете `println!`). Ошибки конкурентности часто бывают гейзенбагами. |
| **сторож** (watchdog) | Небольшой кусок кода, который следит за продвижением работы и сообщает, когда его нет. |
| **OS** (Operating System, операционная система) | Программа (macOS, Linux), которая запускает другие программы и решает, какой поток на каком ядре выполняется. |
| **CPU** (Central Processing Unit, центральный процессор) | Микросхема, которая выполняет инструкции программ. У неё несколько *ядер*; каждое ядро в каждый момент выполняет один поток. |
| **TOCTOU** (Time Of Check To Time Of Use, «время проверки — время использования») | Ошибка «проверить, затем действовать» в безопасности: что-то проверили, а до использования это изменил кто-то другой. |

## 1. Порядок вам не подвластен

Однопоточная программа похожа на рецепт, который читает один повар: шаг 1, шаг 2, шаг 3, всегда в одном и том же порядке. Программа с двумя потоками похожа на двух поваров на одной маленькой кухне, которые делят ножи и плиту. Каждый повар выполняет свой рецепт по порядку, но *как перемешаются их шаги*, зависит от того, кто в данный момент быстрее.

Из Урока 13.9 вы знаете, что *планировщик* OS (часть операционной системы, которая выбирает, какой поток выполнять следующим) решает, когда выполняется каждый поток, и что он может приостановить поток между любыми двумя машинными инструкциями. Поэтому если у потока A есть шаги `A1 A2`, а у потока B — шаги `B1 B2`, возможны все эти порядки:

```text
A1 A2 B1 B2
A1 B1 A2 B2
A1 B1 B2 A2
B1 A1 A2 B2
B1 A1 B2 A2
B1 B2 A1 A2
```

Каждая строка — одно **чередование**. Для двух потоков по два шага их 6. Для двух потоков по 10 шагов — уже 184 756. Проверить их все, запустив программу несколько раз, невозможно, а то чередование, которое ломает программу, может случиться один раз на миллион запусков, в загруженный день, на компьютере клиента.

Конкурентный код корректен, только если он корректен для **каждого** чередования. В этом и состоит вся сложность этого этапа.

## 2. Гонка данных и состояние гонки

Два понятия звучат похоже, но означают разное.

**Гонка данных** — проблема низкого уровня, проблема памяти: два потока обращаются к одной памяти одновременно, хотя бы один пишет, и нет ни блокировки, ни атомарной операции, которая бы их упорядочила. Результат — *неопределённое поведение* ([Урок 06.6](../06-rust-advanced/06-unsafe-rust-and-miri.md)): может случиться что угодно. Безопасный Rust **не компилирует** гонку данных. Здесь два потока пытаются изменить одну локальную переменную:

```rust
use std::thread;

fn main() {
    let mut count = 0;
    thread::scope(|s| {
        s.spawn(|| count += 1);
        s.spawn(|| count += 1);
    });
    println!("{count}");
}
```

```text
error[E0499]: cannot borrow `count` as mutable more than once at a time
 --> src/bin/data_race.rs:7:17
  |
6 |         s.spawn(|| count += 1);
  |         ----------------------
  |         |       |  |
  |         |       |  first borrow occurs due to use of `count` in closure
  |         |       first mutable borrow occurs here
  |         ...
7 |         s.spawn(|| count += 1);
  |                 ^^ ----- second borrow occurs due to use of `count` in closure
  |                 |
  |                 second mutable borrow occurs here
```

**Что происходит:**

1. Каждое замыкание меняет `count`, поэтому каждому нужно заимствование `&mut`.
2. Оба потока живут одновременно, значит, было бы два заимствования `&mut` сразу.
3. Проверка заимствований запрещает два одновременных `&mut`, поэтому гонка данных остановлена ещё до того, как программа появилась.

**Состояние гонки** — *логическая* ошибка: каждое отдельное обращение к памяти безопасно (оно внутри блокировки или атомарно), но **шаги соединены неправильно**, и результат зависит от времени. Компилятор не видит вашего замысла, поэтому остановить это не может. Весь остаток урока показывает состояния гонки в совершенно безопасном Rust.

```text
 data race       = unsafe memory access     → safe Rust: compile error
 race condition  = wrong order of safe steps → safe Rust: compiles, gives wrong results
```

## 3. Потерянное обновление

`AtomicU64` (атомарные типы вы встречали в конце Урока 05.10, подробно о них — в Уроке 14.5) — это число, которое многие потоки могут читать и писать без блокировки. Каждое отдельное `load` (чтение) и `store` (запись) безопасно. Но посмотрите, что эта программа с ними делает. Создайте `src/bin/lost_update.rs`:

```rust
use std::sync::Arc;
use std::sync::atomic::{AtomicU64, Ordering};
use std::thread;

fn main() {
    let counter = Arc::new(AtomicU64::new(0));
    let mut handles = Vec::new();

    for _ in 0..4 {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            for _ in 0..100_000 {
                // Two separate steps: read, then write. Not one step!
                let value = counter.load(Ordering::Relaxed);
                counter.store(value + 1, Ordering::Relaxed);
            }
        }));
    }
    for handle in handles {
        handle.join().unwrap();
    }

    println!("expected 400000, got {}", counter.load(Ordering::Relaxed));
}
```

Запустите её три раза командой `cargo run --bin lost_update`:

```text
expected 400000, got 108080
expected 400000, got 106163
expected 400000, got 104529
```

Ваши числа будут другими и будут меняться от запуска к запуску. Это признак состояния гонки.

**Что происходит:**

1. Четыре потока делят один счётчик через `Arc`. Каждый поток хочет прибавить 1 сто тысяч раз.
2. `load` читает текущее значение, `store` записывает `value + 1`. `Ordering::Relaxed` объясняется в Уроке 14.6; здесь это значит только «только это одно число, никаких других гарантий».
3. Между `load` и `store` одного потока другой поток тоже может выполнить `load` и прочитать **то же самое** старое значение. Потом оба записывают одно и то же новое значение. Сложений было два, а счётчик вырос на один. Одно обновление **потеряно**.
4. Когда четыре потока работают непрерывно, теряется большинство обновлений: здесь около трёх четвертей.

Вот одно плохое чередование, шаг за шагом:

```text
 time   thread A                 thread B                 counter
  1     value = load()  → 7                               7
  2                              value = load()  → 7      7
  3     store(7 + 1)                                      8
  4                              store(7 + 1)             8   ← should be 9
```

`counter += 1` выглядит как одно действие, но это **чтение-изменение-запись**: прочитать, вычислить, записать. Если между чтением и записью может выполниться другой поток, обновления теряются. Есть два способа исправить, и оба превращают три шага в одно неделимое целое:

- атомарная операция чтения-изменения-записи: `counter.fetch_add(1, Ordering::Relaxed)` (Упражнение 2);
- блокировка, которая удерживается от чтения до записи (тоже Упражнение 2).

> ⚠️ **Частая ошибка:** думать, что «каждая операция атомарна» значит «мой код атомарен». Две атомарные операции подряд — это **два** шага, и между ними может выполниться другой поток.

## 4. «Проверить, затем действовать»

Второе классическое состояние гонки использует `Mutex`, и каждое обращение защищено блокировкой. На банковском счёте 100. Два человека одновременно пытаются снять 80. Создайте `src/bin/withdraw.rs`:

```rust
use std::sync::{Arc, Mutex};
use std::thread;
use std::time::Duration;

fn withdraw(balance: &Mutex<i64>, amount: i64) -> bool {
    // Step 1: check (the lock is taken and released in this one line).
    let enough = *balance.lock().unwrap() >= amount;
    if !enough {
        return false;
    }
    // Some other work happens here, for example writing a log line.
    thread::sleep(Duration::from_millis(10));
    // Step 2: act (the lock is taken again).
    *balance.lock().unwrap() -= amount;
    true
}

fn main() {
    let balance = Arc::new(Mutex::new(100));
    let mut handles = Vec::new();

    for name in ["Alice", "Bob"] {
        let balance = Arc::clone(&balance);
        handles.push(thread::spawn(move || {
            let ok = withdraw(&balance, 80);
            println!("{name} withdraws 80: {ok}");
        }));
    }
    for handle in handles {
        handle.join().unwrap();
    }
    println!("final balance: {}", *balance.lock().unwrap());
}
```

```text
Alice withdraws 80: true
Bob withdraws 80: true
final balance: -60
```

(Первые две строки могут прийти в другом порядке.)

**Что происходит:**

1. В `withdraw` первый `lock()` создаёт временный guard-объект. Он уничтожается в конце этой инструкции, поэтому блокировка отпускается сразу после проверки.
2. Оба потока проверяют «на балансе не меньше 80?», пока баланс ещё 100. Оба получают `true`.
3. Оба спят 10 мс. Пауза нужна только для того, чтобы плохое чередование случалось каждый раз; без неё ошибка появлялась бы редко, а это хуже.
4. Оба снова берут блокировку и вычитают 80. Баланс становится −60, и это нарушает **инвариант** «баланс никогда не бывает отрицательным».

Ошибка не в какой-то одной строке. Она в промежутке между проверкой и действием: блокировку отпустили, поэтому факт «денег достаточно» к моменту действия уже был неверен. Исправление — держать **одну** блокировку и для проверки, *и* для действия. Создайте `src/bin/withdraw_fixed.rs`: скопируйте `withdraw.rs` и замените только функцию `withdraw`:

```rust
fn withdraw(balance: &Mutex<i64>, amount: i64) -> bool {
    let mut guard = balance.lock().unwrap(); // one lock for check AND act
    if *guard < amount {
        return false;
    }
    thread::sleep(Duration::from_millis(10));
    *guard -= amount;
    true
}
```

```text
Alice withdraws 80: true
Bob withdraws 80: false
final balance: 20
```

**Что происходит:** guard живёт до конца функции. Пока Алиса внутри, Боб ждёт на `lock()`. Когда Боб получает блокировку, он видит 20 и получает `false`. Кто выиграет, зависит от времени, но инвариант соблюдается всегда.

> 📏 **Соглашение:** **критическая секция** должна охватывать весь инвариант: всё, что вы проверяете, и всё, что меняете по результату проверки. «Блокировать каждую строку по отдельности» — это не потокобезопасность.

> 🔒 **Безопасность:** ошибки «проверить, затем действовать» — настоящий класс уязвимостей, он называется TOCTOU (Time Of Check To Time Of Use, «время проверки — время использования»): программа проверяет «может ли этот пользователь открыть файл?», а файл подменяют до того, как его откроют. Лекарство то же: сделать проверку и использование одним шагом.

## 5. Взаимная блокировка

Вы видели взаимную блокировку в Уроке 05.10: два потока, две блокировки, взятые в противоположном порядке. Теперь посмотрим на неё в реалистичной программе и исправим как следует. Банк переводит деньги между счетами; у каждого счёта свой мьютекс, поэтому переводы между *разными* счетами могут идти параллельно. Создайте `src/bin/transfer.rs`:

```rust
use std::sync::atomic::{AtomicU64, Ordering};
use std::sync::{Arc, Mutex};
use std::thread;
use std::time::Duration;

struct Bank {
    accounts: Vec<Mutex<i64>>,
}

impl Bank {
    fn transfer(&self, from: usize, to: usize, amount: i64) {
        let mut a = self.accounts[from].lock().unwrap();
        let mut b = self.accounts[to].lock().unwrap();
        *a -= amount;
        *b += amount;
    }
}

fn main() {
    let bank = Arc::new(Bank {
        accounts: vec![Mutex::new(1000), Mutex::new(1000)],
    });
    let done = Arc::new(AtomicU64::new(0)); // how many transfers finished

    for (from, to) in [(0, 1), (1, 0)] {
        let bank = Arc::clone(&bank);
        let done = Arc::clone(&done);
        thread::spawn(move || {
            for _ in 0..100_000 {
                bank.transfer(from, to, 1);
                done.fetch_add(1, Ordering::Relaxed);
            }
        });
    }

    // A watchdog: if no transfer finishes for one second, we are stuck.
    let mut last = 0;
    loop {
        thread::sleep(Duration::from_secs(1));
        let now = done.load(Ordering::Relaxed);
        if now == 200_000 {
            println!("all 200000 transfers done");
            break;
        }
        if now == last {
            println!("no progress after {now} transfers: deadlock!");
            std::process::exit(1);
        }
        last = now;
    }
}
```

Три запуска:

```text
no progress after 71431 transfers: deadlock!
no progress after 0 transfers: deadlock!
no progress after 30 transfers: deadlock!
```

**Что происходит:**

1. Поток 1 переводит со счёта 0 на счёт 1: он блокирует 0, затем 1. Поток 2 переводит с 1 на 0: он блокирует 1, затем 0.
2. Рано или поздно поток 1 держит блокировку 0, а поток 2 — блокировку 1 в один и тот же момент. Каждый ждёт блокировку, которую держит другой. Никто не может продолжить, и никто никогда не отпустит свою блокировку.
3. Главный поток — **сторож**. Каждую секунду он смотрит на счётчик `done`. Если число не выросло, ничего не движется, поэтому он сообщает о взаимной блокировке и завершает весь процесс через `std::process::exit(1)`. Без сторожа программа просто молча зависла бы — так взаимная блокировка и выглядит в реальной жизни.
4. *Когда* она зависнет — случайно: после 71 431 перевода или в самом начале. Вспоминайте об этом, когда кто-то говорит «у меня всё работало, когда я проверял».

### Четыре условия

Взаимная блокировка возможна, только когда **все четыре** условия выполняются одновременно (в информатике их называют условиями Коффмана):

| Условие | В нашем банке |
|---|---|
| 1. **Взаимное исключение** — ресурсом может владеть только один поток | Мьютекс одновременно держит только один поток. |
| 2. **Удержание и ожидание** — поток держит один ресурс и ждёт другой | `transfer` держит `from` и ждёт `to`. |
| 3. **Нет вытеснения** — никто не может отобрать ресурс у потока | Никто не может заставить поток отдать `MutexGuard`. |
| 4. **Циклическое ожидание** — есть круг потоков, каждый ждёт следующего | Поток 1 ждёт поток 2, который ждёт поток 1. |

Нарушьте любое одно условие — и взаимная блокировка станет невозможной. Проще всего нарушить условие 4.

### Лекарство: единый порядок блокировок

Дайте каждой блокировке номер и заставьте каждый поток брать блокировки по возрастанию номеров. Тогда круг не может образоваться: поток, который держит блокировку 5, ждёт только блокировки с номерами больше 5, поэтому никто не может ждать «назад». Создайте `src/bin/transfer_fixed.rs`: скопируйте `transfer.rs` и замените только тело `transfer`:

```rust
    fn transfer(&self, from: usize, to: usize, amount: i64) {
        if from == to {
            return; // locking the same mutex twice would hang
        }
        // Always lock the account with the smaller index first.
        let (low, high) = if from < to { (from, to) } else { (to, from) };
        let mut low_guard = self.accounts[low].lock().unwrap();
        let mut high_guard = self.accounts[high].lock().unwrap();
        if from == low {
            *low_guard -= amount;
            *high_guard += amount;
        } else {
            *high_guard -= amount;
            *low_guard += amount;
        }
    }
```

```text
all 200000 transfers done
```

**Что происходит:**

1. Теперь оба потока сначала блокируют счёт 0, а потом счёт 1, в какую бы сторону ни шёл перевод.
2. Поток, держащий блокировку 0, может ждать блокировку 1. Поток, держащий блокировку 1, никогда не ждёт блокировку 0, потому что взял её раньше. Нет круга — нет взаимной блокировки.
3. Проверка `from == to` важна: перевод со счёта на него же заблокировал бы один мьютекс дважды в одном потоке. Стандартный `Mutex` не *реентерабельный* (не позволяет тому же потоку заблокировать его снова); на macOS такая программа просто зависает навсегда.

> 💡 **Совет:** в реальном коде «номером» блокировки может быть что угодно постоянное и сравнимое: идентификатор счёта, позиция в векторе или адрес мьютекса в памяти.

## 6. Активная блокировка и голодание

Ещё два способа, которыми потоки не продвигаются, хотя и не зависают полностью:

- **Активная блокировка.** Два вежливых человека встречаются в коридоре. Оба шагают влево, потом оба вправо, потом оба влево… Они заняты, но никто не проходит. В коде это бывает, когда потоки используют `try_lock` (Урок 14.2), видят, что другая блокировка занята, отпускают всё и повторяют попытку в одном и том же ритме. Обычное лекарство — перед повторной попыткой подождать небольшое *случайное* время.
- **Голодание.** Один поток почти никогда не получает блокировку, потому что другие всегда успевают первыми. Программа работает, но один клиент ждёт минутами. Честность (fairness) блокировок — тема Урока 14.2.

## 7. Почему ваши тесты не находят эти ошибки

Ошибки конкурентности зависят от времени, а время зависит от всего: числа ядер, других программ, отладочной или релизной сборки, даже от `println!` (печать берёт блокировку внутри стандартной библиотеки, и это меняет тайминг). Тест, прошедший 1000 раз, доказывает очень мало. Поэтому ошибки конкурентности часто бывают **гейзенбагами**.

Что помогает:

1. **Проектируйте так, чтобы гонки были невозможны.** Держите критическую секцию вокруг всего инварианта. Когда можно, предпочитайте передачу сообщений (каналы) общему состоянию. Используйте единый порядок блокировок.
2. **Делайте плохие чередования вероятными.** Много потоков, много итераций и короткие паузы в «промежутке», пока вы расследуете ошибку (как мы сделали в `withdraw`).
3. **Проверяйте инварианты, а не тайминг.** В конце проверьте то, что должно быть верно всегда: общую сумму денег, число элементов, сумму.
4. **Обнаруживайте зависания вместо вечного ожидания.** Используйте сторожа или ограничение по времени.
5. **Перебирайте чередования систематически.** Крейт `loom` запускает ваш тест на *каждом* возможном чередовании небольшой модели. Вы встретите его в Уроке 14.6, а подробно изучите в Уроке 14.9.

> 🧪 **Тестирование:** хороший тест конкурентности состоит из трёх частей: запустить много потоков, которые нагружают общие данные, дождаться их всех через `join`, затем проверить инвариант. Запускайте его и через `cargo test --release`: релизная сборка быстрее, это меняет тайминг и часто показывает другие чередования.

## Частые ошибки

1. **Блокировать каждый шаг отдельно.** `if *m.lock().unwrap() > 0 { *m.lock().unwrap() -= 1; }` берёт блокировку дважды, а значит, это ошибка «проверить, затем действовать». Держите один guard на оба шага.
2. **Две атомарные операции вместо одной.** `load`, а затем `store` — это ошибка потерянного обновления. Используйте `fetch_add`, `fetch_sub` или цикл сравнения с обменом из Урока 14.5.
3. **Брать две блокировки в разном порядке в разных местах.** Взаимная блокировка, которая ждёт своего часа. Запишите порядок блокировок в комментарии и соблюдайте его везде.
4. **Блокировать один `Mutex` дважды в одном потоке.** Программа зависает (или может запаниковать; стандартная библиотека не обещает, что именно). Часто это прячется во вспомогательной функции, которая блокирует мьютекс, уже взятый вызывающим кодом.
5. **«У меня работало».** На другом компьютере тайминг другой. Проверяйте инварианты с большим числом потоков и используйте сторожа или ограничение по времени, чтобы зависание превращалось в явную ошибку.

### Упражнение 1 — Сколько потоков? (легко)

Измените число потоков в `lost_update.rs` с 4 на 1, а затем на 8 (исправьте и ожидаемое число в сообщении). Запустите каждый вариант и объясните результаты.

<details>
<summary>Подсказка</summary>

Если поток один, может ли кто-нибудь выполниться между `load` и `store`?

</details>

<details>
<summary>Ответ</summary>

Результаты на тестовой машине:

```text

expected 800000, got 169544
expected 800000, got 353120
```

С одним потоком никто другой не может выполниться между `load` и `store`, поэтому ни одно обновление не теряется и результат точный. С восемью потоками столкновений больше, теряется множество обновлений, и число скачет от запуска к запуску. Тест с одним потоком никогда бы не нашёл эту ошибку.

</details>

### Упражнение 2 — Два способа исправить потерянное обновление (средне)

Сделайте две копии `lost_update.rs`: `lu_fixed.rs`, где вместо `load` + `store` используется одна атомарная операция, и `lu_mutex.rs`, где используется `Arc<Mutex<u64>>`, но значение по-прежнему читается и записывается обратно двумя инструкциями. Обе программы должны всегда печатать `got 400000`.

<details>
<summary>Подсказка</summary>

У атомарного типа есть метод, который прибавляет и возвращает старое значение за один шаг. В версии с мьютексом возьмите guard один раз и держите его на обе инструкции.

</details>

<details>
<summary>Ответ</summary>

В `lu_fixed.rs` замените две строки внутри цикла одной (остальной файл не меняется):

```rust
                counter.fetch_add(1, Ordering::Relaxed); // one indivisible step
```

`lu_mutex.rs`:

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0u64));
    let mut handles = Vec::new();

    for _ in 0..4 {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            for _ in 0..100_000 {
                let mut guard = counter.lock().unwrap();
                let value = *guard; // read...
                *guard = value + 1; // ...and write while holding the lock
            }
        }));
    }
    for handle in handles {
        handle.join().unwrap();
    }

    println!("expected 400000, got {}", *counter.lock().unwrap());
}
```

```text
expected 400000, got 400000
```

Почему это работает: в обоих вариантах чтение и запись образуют одно целое. `fetch_add` делает это в железе, а мьютекс — тем, что не пускает другие потоки, пока жив guard. Два шага *внутри* одной критической секции — это нормально.

</details>

### Упражнение 3 — Протестируйте банк (средне)

Запустите его командой `cargo test --bin transfer_fixed`.

<details>
<summary>Подсказка</summary>

Тестовый модуль внутри файла из `src/bin/` работает так же, как в `src/main.rs`: `#[cfg(test)] mod tests { use super::*; ... }`. Чтобы получать разные пары, вычисляйте `from` и `to` из номера потока и счётчика цикла через `% 3`. Ваш `transfer` уже сразу возвращается, если `from == to`.

<details>
<summary>Ответ</summary>

Добавьте в конец `src/bin/transfer_fixed.rs`:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn transfers_keep_the_total() {
        let bank = Arc::new(Bank {
            accounts: (0..3).map(|_| Mutex::new(1000)).collect(),
        });
        let mut handles = Vec::new();
        for t in 0..4 {
            let bank = Arc::clone(&bank);
            handles.push(thread::spawn(move || {
                for i in 0..10_000 {
                    let from = (t + i) % 3;
                    let to = (t + 2 * i + 1) % 3;
                    bank.transfer(from, to, 1);
                }
            }));
        }
        for handle in handles {
            handle.join().unwrap();
        }
        let total: i64 = bank.accounts.iter().map(|a| *a.lock().unwrap()).sum();
        assert_eq!(total, 3000);
    }
}
```


Почему это работает: тест проверяет инвариант, а не тайминг. Косвенно он проверяет и взаимные блокировки: со старым `transfer` этот тест иногда зависал бы, и `cargo test` напечатал бы `has been running for over 60 seconds`. С порядком блокировок он всегда завершается.

### Упражнение 4 — Пять философов (сложно)

Классическая задача: пять философов сидят за круглым столом. Между каждыми двумя соседями лежит одна вилка, всего вилок пять. Чтобы поесть, философу нужны и левая вилка (номер `p`), и правая (номер `(p + 1) % 5`). Если каждый философ сначала берёт левую вилку, а потом правую, все могут взять по одной вилке и ждать вечно.

Напишите `src/bin/philosophers.rs`: вилки — это `Arc<Vec<Mutex<u32>>>` (число считает, сколько раз вилкой пользовались). Каждый из 5 потоков «ест» 10 000 раз: блокирует обе вилки и прибавляет 1 к каждому счётчику. Программа никогда не должна зависать и должна напечатать число использований каждой вилки.

<details>
<summary>Подсказка</summary>

Какое из четырёх условий можно нарушить? У философа 4 вилки 4 и 0. Если каждый сначала берёт вилку с меньшим номером, что делает философ 4?

</details>

<details>
<summary>Ответ</summary>

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let forks: Arc<Vec<Mutex<u32>>> = Arc::new((0..5).map(|_| Mutex::new(0)).collect());
    let mut handles = Vec::new();

    for p in 0..5 {
        let forks = Arc::clone(&forks);
        handles.push(thread::spawn(move || {
            let left = p;
            let right = (p + 1) % 5;
            // Lock order rule: the smaller fork number first.
            let (first, second) = (left.min(right), left.max(right));
            for _ in 0..10_000 {
                let mut a = forks[first].lock().unwrap();
                let mut b = forks[second].lock().unwrap();
                *a += 1; // count how often each fork was used
                *b += 1;
            }
        }));
    }
    for handle in handles {
        handle.join().unwrap();
    }
    let uses: Vec<u32> = forks.iter().map(|f| *f.lock().unwrap()).collect();
    println!("all philosophers ate 10000 times; fork uses: {uses:?}");
}
```

```text
all philosophers ate 10000 times; fork uses: [20000, 20000, 20000, 20000, 20000]
```

Почему это работает: философы 0–3 сначала берут левую вилку, а философ 4 сначала берёт вилку 0 (свою правую), потому что 0 < 4. Это разрывает круг (условие 4). Каждой вилкой пользуются два её соседа, по 10 000 раз каждый, поэтому каждый счётчик равен 20 000.

</details>

## Вопросы для самопроверки

1. Чем гонка данных отличается от состояния гонки? Что из этого возможно в безопасном Rust?

<details>
<summary>Ответ</summary>

Гонка данных — неупорядоченное обращение двух потоков к одной памяти, когда хотя бы один пишет; это неопределённое поведение, и безопасный Rust отказывается такое компилировать. Состояние гонки — логическая ошибка, при которой результат зависит от тайминга, хотя каждое отдельное обращение безопасно. В безопасном Rust состояния гонки возможны.

</details>

2. Почему `x.store(x.load(Relaxed) + 1, Relaxed)` неверно, когда это выполняют несколько потоков?

<details>
<summary>Ответ</summary>

Это чтение-изменение-запись, разбитое на два отдельных атомарных шага. Между `load` и `store` другой поток может прочитать то же старое значение, и два увеличения дадут одно изменение: обновление теряется. Используйте `fetch_add`.

</details>

3. Функция блокирует мьютекс, чтобы проверить значение, отпускает его, затем снова блокирует, чтобы изменить значение. Что это за ошибка?

<details>
<summary>Ответ</summary>

«Проверить, затем действовать». Между двумя блокировками другой поток может изменить значение, и к моменту действия проверка устаревает. Один guard должен охватывать и проверку, и действие.

</details>

4. Назовите четыре условия взаимной блокировки. Какое из них нарушает единый порядок блокировок?

<details>
<summary>Ответ</summary>

Взаимное исключение, удержание и ожидание, отсутствие вытеснения, циклическое ожидание. Единый порядок блокировок нарушает циклическое ожидание: потоки ждут только блокировки с большими номерами, поэтому круг не может образоваться.

</details>

5. Тест конкурентного кода прошёл 1000 раз подряд. Корректен ли код?

<details>
<summary>Ответ</summary>

Не обязательно. Плохое чередование может быть редким или невозможным на этой машине и в этой сборке, но вероятным на другой. Пройденные тесты повышают уверенность, но корректность должна идти от устройства кода (критические секции вокруг инвариантов, порядок блокировок), а инструменты вроде `loom` умеют проверять все чередования небольших моделей.

</details>

6. Чем взаимная блокировка отличается от активной блокировки?

<details>
<summary>Ответ</summary>

При взаимной блокировке потоки заблокированы и ничего не делают. При активной блокировке потоки активны (повторяют попытки, отпускают и снова берут блокировки), но всё равно не продвигаются.

</details>

## Итоги

- Планировщик может переключить потоки между любыми двумя шагами. Конкурентный код должен быть корректен для **каждого** чередования, а не только для тех, что вы видели.
- Безопасный Rust останавливает **гонки данных** при компиляции. Он не может остановить **состояния гонки** — логические ошибки в том, как соединены безопасные шаги.
- **Потерянное обновление** происходит, когда чтение-изменение-запись разбито на отдельные шаги. Используйте `fetch_add` или одну критическую секцию.
- **«Проверить, затем действовать»** ломается, когда блокировку отпускают между проверкой и действием. Один guard должен охватывать весь инвариант.
- **Взаимной блокировке** нужны четыре условия сразу. **Единый порядок блокировок** нарушает циклическое ожидание и является простейшим лекарством.
- Ошибки конкурентности прячутся от тестов. Проверяйте инварианты с большим числом потоков, обнаруживайте зависания сторожем или ограничением по времени и используйте `loom` (Уроки 14.6 и 14.9).
