# Урок 23.8 — Тестирование, бенчмарки и укрепление итогового проекта

> **Этап 23 — Итоговые проекты** · Урок 8 из 10 · ⏱ около 120 минут

## Что вы узнаете

- Что такое стадия укрепления итогового проекта и как найти пробелы в тестах с помощью *матрицы тестов*, построенной по проектному документу.
- Как тест «туда и обратно» на основе свойств находит настоящую ошибку, которую пропускают тесты на примерах, и как proptest навсегда сохраняет упавший случай.

- Чек-лист укрепления, который связывает уроки о надёжности, безопасности и производительности из Этапов 19–20.

## Новые слова

| Слово | Значение |
|---|---|
| **укрепление** (hardening) | Работа по устранению, одного за другим, способов, которыми программа может отказать, перегрузиться или быть атакована. |
| **матрица тестов** (test matrix) | Таблица, которая сопоставляет каждому требованию и каждому режиму отказа из проектного документа тест, который это доказывает, и показывает, каких ещё нет. |
| **свойство «туда и обратно»** (round-trip property) | Правило «decode(encode(x)) == x для любого x». Одно из самых полезных свойств для любого формата или протокола. |
| **уменьшение примера** (shrinking) | Что делает инструмент тестирования на основе свойств, найдя падающий вход: пробует всё меньшие и более простые входы, пока не найдёт самый маленький, который всё ещё падает. |
| **файл регрессий** (regression file) | Файл, в котором proptest сохраняет начальные значения (seed) упавших случаев, чтобы в каждом следующем запуске они проверялись первыми. |
| **быстрая полоса / медленная полоса** (fast lane / slow lane) | Задания CI, которые выполняются на каждую отправку за несколько минут (быстрые), и задания, которые работают дольше — после быстрых или ночью (медленные). |
| **методика бенчмарка** (benchmark methodology) | Письменное описание того, *как* вы измеряли: оборудование, версии программ, нагрузка, прогрев, повторения и точные команды. |
| **шум** (noise) | Разброс между измерениями, который вызван не вашим кодом: другие программы, изменение частоты процессора, тепловой троттлинг. |
| **запас по нагрузке** (headroom) | Расстояние между нагрузкой, на которой вы работаете, и нагрузкой, при которой система начинает не выполнять свои цели. |
| **p50 / p99 / p99.9** | Перцентили задержки (Урок 19.1): половина запросов быстрее p50 (медианы), 99% быстрее p99, 99,9% быстрее p99.9. |
| **UTC** (Coordinated Universal Time, всемирное координированное время) | Опорное время мира без часовых поясов и летнего времени; расписания CI задаются в нём. |
| **CPU** (Central Processing Unit, центральный процессор) | Процессор; «использование CPU» — какую долю его времени занимает программа. |
| **ВМ** (виртуальная машина, VM — Virtual Machine) | Целый компьютер, имитируемый программой; Linux-ВМ курса называется `dev` (Урок 11.1). |
| **TCP** (Transmission Control Protocol, протокол управления передачей) | Интернет-протокол, который даёт двум программам надёжный упорядоченный поток байтов. |
| **HTTP** (HyperText Transfer Protocol, протокол передачи гипертекста) | Протокол запросов и ответов веба; HTTPS — это HTTP поверх зашифрованного соединения. |

## 1. Стадия укрепления

Во время вех вы писали тесты на то, что обещала каждая веха. Стадия укрепления (около 15% времени, Урок 23.1) смотрит на **всю** систему и спрашивает: у какого обещания или режима отказа ещё нет теста?

Постройте **матрицу тестов** по проектному документу. Каждое требование (раздел 4 документа) и каждая строка таблицы режимов отказов (раздел 7) становится строкой:

| ID | Требование или отказ | Тест, который это доказывает | Вид | Статус |
|---|---|---|---|---|
| R1 | p99 `GET` < 5 мс при 10 000 QPS (queries per second, запросов в секунду) на одном узле | `bench/get_latency.sh` с `oha` | нагрузочный тест | готово (4,1 мс) |
| R2 | подтверждённые записи переживают `kill -9` | `m1_acknowledged_writes_survive_kill` | тест на сбой | готово |
| R3 | старый лидер не может обслуживать линеаризуемые чтения | `sim::partitioned_leader_refuses_reads` | симуляция | готово |
| F4 | у ведомого заполнен диск | — | внедрение сбоя | **нет** |
| F5 | испорченная запись журнала на диске | `fuzz/log_decoder` | фаззинг | готово, 1 ч |
| F6 | клиент присылает поле длины в 4 ГиБ | — | модульный + фаззинг | **нет** |

Столбец ID (identifier, идентификатор) нумерует строки: R — требования, F — режимы отказа, чтобы тест, задача или сообщение коммита могли сослаться на «F6». Строки с пометкой **нет** — ваша работа на этой стадии, в порядке риска. Та же таблица идёт в README в Уроке 23.9, потому что это честный ответ на вопрос «откуда вы знаете, что это работает?».

> 🧪 **Тестирование:** во время укрепления один раз запустите `cargo mutants` (Урок 09.7) на крейте ядра. Каждый *выживший мутант* — изменение вашего кода, которого не заметил ни один тест, — указывает на недостающую проверку. Убивать их все не нужно; нужно на них посмотреть.

## 2. Свойство, которое находит настоящую ошибку

Тесты на примерах проверяют случаи, о которых вы подумали. Тесты на основе свойств проверяют случаи, о которых вы не подумали. Самое полезное свойство для любого формата, протокола или устройства файла — **«туда и обратно»**: кодирование, а затем декодирование возвращает ровно то, с чего вы начали.

Вот маленький формат кадров с ошибкой, которую тесты на примерах не находят. Создайте библиотечный пакет для практики:

```bash
cd ~/projects/rust
cargo new --lib code/p23-harden
cd code/p23-harden
cargo add --dev proptest@1
```

`src/lib.rs`:

```rust
//! A tiny frame format: kind (1 byte), payload length (u16, big-endian), payload.

#[derive(Debug, Clone, PartialEq)]
pub struct Frame {
    pub kind: u8,
    pub payload: Vec<u8>,
}

pub fn encode(frame: &Frame) -> Vec<u8> {
    let len = frame.payload.len() as u16;
    let mut out = vec![frame.kind];
    out.extend_from_slice(&len.to_be_bytes());
    out.extend_from_slice(&frame.payload);
    out
}

pub fn decode(bytes: &[u8]) -> Result<Frame, String> {
    let [kind, hi, lo, rest @ ..] = bytes else {
        return Err("frame too short".to_string());
    };
    let len = u16::from_be_bytes([*hi, *lo]) as usize;
    if rest.len() != len {
        return Err(format!("length says {len} bytes, got {}", rest.len()));
    }
    Ok(Frame {
        kind: *kind,
        payload: rest.to_vec(),
    })
}

#[cfg(test)]
mod tests {
    use super::*;
    use proptest::prelude::*;

    #[test]
    fn a_small_frame_round_trips() {
        let frame = Frame {
            kind: 1,
            payload: b"hello".to_vec(),
        };
        assert_eq!(decode(&encode(&frame)), Ok(frame));
    }

    proptest! {
        #[test]
        fn every_frame_round_trips(kind in any::<u8>(), len in 0usize..70_000, fill in any::<u8>()) {
            let frame = Frame { kind, payload: vec![fill; len] };
            let decoded = decode(&encode(&frame));
            prop_assert!(decoded == Ok(frame), "a frame with {} payload bytes did not round-trip", len);
        }
    }
}
```

**Что происходит:**

1. `encode` пишет вид кадра, длину полезной нагрузки двумя байтами big-endian и саму нагрузку. `as u16` преобразует длину — и **молча отрезает** все биты выше 16, если нагрузка длиннее 65 535 байт.
2. `decode` с помощью образца среза (`[kind, hi, lo, rest @ ..]`, Урок 06.3) берёт первые три байта и проверяет, что у остатка ровно объявленная длина.
3. Тест на примере использует нагрузку в 5 байт. Он проходит и прошёл бы для любой нагрузки, которую естественно написать вручную.
4. Тест на основе свойств генерирует 256 случайных кадров: любой вид, длину от 0 до 69 999 и байт заполнения. Генерация `len` и `fill` вместо случайного `Vec` делает отчёт об ошибке коротким (случайный вектор из 65 536 байт печатался бы байт за байтом).

```bash
cargo test
```

```text

. 1/2
tests::every_frame_round_trips --- FAILED

failures:

---- tests::every_frame_round_trips stdout ----
proptest: Saving this and future failures in /Users/you/projects/rust/code/p23-harden/proptest-regressions/lib.txt
proptest: If this test was run on a CI system, you may wish to add the following line to your copy of the file. (You may need to create it.)
cc 577adc906d1865d9ceef5fb33e28dd8300da7a36149e355ea2c4f1ed7514e9ac

thread 'tests::every_frame_round_trips' (6666320) panicked at src/lib.rs:45:5:
Test failed: a frame with 65536 payload bytes did not round-trip at src/lib.rs:50.
minimal failing input: kind = 0, len = 65536, fill = 0
	successes: 75
	local rejects: 0
	global rejects: 0
```

(Ваш путь, начальное значение и число успехов будут другими.) Читайте отчёт снизу вверх:

1. После 75 прошедших случаев proptest нашёл падающий кадр, а затем **уменьшил** его: `kind = 0`, `fill = 0` и `len = 65536` — самая маленькая длина, при которой тест падает. Это число сразу называет ошибку: 65 536 — это 2¹⁶, первая длина, которая не помещается в `u16`.
2. Начальное значение упавшего случая сохранено в `proptest-regressions/lib.txt`. Закоммитьте этот файл: каждый следующий запуск на каждой машине сначала пробует этот случай, поэтому ошибка никогда не вернётся незамеченной.

Исправление — отказываться от того, что формат не может выразить, вместо того чтобы выдавать неправильный кадр:

```rust
pub fn encode(frame: &Frame) -> Result<Vec<u8>, String> {
    let len = u16::try_from(frame.payload.len())
        .map_err(|_| format!("payload of {} bytes is too long", frame.payload.len()))?;
    let mut out = vec![frame.kind];
    out.extend_from_slice(&len.to_be_bytes());
    out.extend_from_slice(&frame.payload);
    Ok(out)
}
```

и свойство меняется вместе с ним — кадр либо проходит «туда и обратно», либо `encode` отказывается от него, потому что он слишком длинный:

```rust
proptest! {
    #[test]
    fn every_frame_round_trips(kind in any::<u8>(), len in 0usize..70_000, fill in any::<u8>()) {
        let frame = Frame { kind, payload: vec![fill; len] };
        match encode(&frame) {
            Ok(bytes) => prop_assert_eq!(decode(&bytes), Ok(frame)),
            Err(_) => prop_assert!(len > usize::from(u16::MAX), "only too long payloads may fail"),
        }
    }
}
```

(Тест на примере теперь вызывает `encode(&frame).unwrap()`.) Оба теста проходят:

```text
test tests::a_small_frame_round_trips ... ok
test tests::every_frame_round_trips ... ok

test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

> 🔒 **Безопасность:** `as` между целыми типами никогда не падает; он отрезает или заворачивает. В протоколе неверное поле длины — это то, из-за чего одно сообщение читается как два или читатель выделяет гигабайты. Используйте `try_from` для каждой длины, которая пересекает границу, и пусть линт Clippy `cast_possible_truncation` (в `clippy::pedantic`) покажет пропущенные приведения.

## 3. Один конвейер: быстрая и медленная полосы

У итогового проекта есть тесты на секунды и тесты на час. Если всё запускать на каждую отправку, CI становится таким медленным, что вы перестаёте его ждать. Разделите работу:

- **Быстрая полоса** (на каждую отправку, несколько минут): форматирование, Clippy, модульные и интеграционные тесты, проверки `done-when.sh` из Урока 23.7.
- **Медленная полоса** (после прохождения быстрой и дольше каждую ночь): симуляция со многими начальными значениями, фаззинг каждой цели, сборка бенчмарков.

`.github/workflows/ci.yml`:

```yaml
name: ci

on:
  push:
    branches: [main]
  pull_request:
  schedule:
    - cron: "0 2 * * *" # every night at 02:00 UTC

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read

env:
  CARGO_TERM_COLOR: always

jobs:
  gate:
    name: fmt, clippy, tests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - run: rustup toolchain install stable --profile minimal --component rustfmt,clippy
      - uses: Swatinem/rust-cache@v2
      - run: cargo fmt --check
      - run: cargo clippy --all-targets -- -D warnings
      - run: cargo test --all-targets
      - run: ./scripts/done-when.sh

  simulation:
    name: simulation with fixed seeds
    needs: gate
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@v7
      - run: rustup toolchain install stable --profile minimal
      - uses: Swatinem/rust-cache@v2
      - run: cargo test --release --test simulation -- --include-ignored

  fuzz:
    name: fuzz every target
    needs: gate
    runs-on: ubuntu-latest
    timeout-minutes: 60
    env:
      FUZZ_SECONDS: ${{ github.event_name == 'schedule' && '600' || '60' }}
    steps:
      - uses: actions/checkout@v7
      - run: rustup toolchain install nightly --profile minimal
      - run: cargo install --locked cargo-fuzz
      - name: Fuzz each target for a while
        run: |
          for target in $(cargo +nightly fuzz list); do
            cargo +nightly fuzz run "$target" -- -max_total_time="$FUZZ_SECONDS"
          done

  benches:
    name: benchmarks still compile
    needs: gate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - run: rustup toolchain install stable --profile minimal
      - uses: Swatinem/rust-cache@v2
      - run: cargo bench --no-run
```

**Что происходит:**

1. Три триггера: отправки в `main`, pull request и `schedule` с выражением `cron` (минута, час, день месяца, месяц, день недели), которое запускает конвейер каждую ночь.
2. `gate` — быстрая полоса. Остальные задания говорят `needs: gate`, поэтому начинаются, только когда быстрая полоса зелёная; нет смысла фаззить код, который не компилируется.
3. `simulation` запускает одну тестовую цель с именем `simulation` (файл `tests/simulation.rs`) в релизном режиме и включает тесты с пометкой `#[ignore]` — обычный способ держать медленные тесты вне обычного `cargo test`.
4. `fuzz` выбирает длительность выражением: ночью 600 секунд на цель, иначе 60 секунд. `cargo fuzz list` печатает имена всех фаззинг-целей, поэтому новая цель фаззится без изменения конвейера.
5. `benches` только компилирует бенчмарки (`--no-run`). Общие машины CI слишком шумные для настоящих измерений (раздел 4), но бенчмарк, который перестал компилироваться, нужно заметить сразу.

Раннеры GitHub нельзя запустить на вашем Mac, но файл можно проверить. `actionlint` (Урок 09.12) ничего не печатает и завершается с кодом 0:

```bash
actionlint .github/workflows/ci.yml
```

Опечатка в имени задания (`needs: gaet`) — именно та ошибка, которая иначе появляется только после отправки:

```text
.github/workflows/bad.yml:33:3: job "simulation" needs job "gaet" which does not exist in this workflow [job-needs]
   |
33 |   simulation:
   |   ^~~~~~~~~~~
```

> 💡 **Совет:** когда ночной запуск находит падение фаззера или падающее начальное значение, превратите его в обычный тест, прежде чем исправлять (модульный тест с падающим входом или начальное значение в списке фиксированных). Тогда быстрая полоса навсегда защищает вас от этой ошибки.

## 4. Бенчмарки, которым можно доверять

Число без его условий нельзя проверить, сравнить или повторить. Прежде чем измерять, запишите **методику**:

1. **Оборудование и программы:** модель процессора и число ядер, память, тип диска, операционная система и версия ядра, версия Rust, профиль сборки (всегда `--release`).
2. **Нагрузка:** точная команда, размер запроса или сообщения, число соединений, частота (частота открытой модели вроде `oha -q 5000` избегает coordinated omission, Урок 19.1) и длительность.
3. **Прогрев:** отбросьте первые секунды, пока заполняются кэши и открываются соединения.
4. **Повторения:** выполните каждое измерение хотя бы три раза и сообщите медиану и разброс. Если два запуска отличаются больше чем примерно на 10%, найдите шум, прежде чем доверять любому из них.
5. **Базовая линия:** сравнивайте с чем-то: с версией до изменения, с прямым путём без вашей системы (прокси из Урока 23.4) или с настоящей системой, делающей ту же работу.
6. **Объяснение:** профиль (Урок 19.3) на интересной нагрузке и абзац, который говорит, куда уходит время.

Затем `docs/results.md` получает фиксированную форму:

```markdown
# Results

## Setup
- Machine: Apple M4 Pro, 12 cores, 24 GB; macOS 26; Rust 1.100.0, --release
- Linux runs: VM `dev` (Lima, Ubuntu 26.04, 4 vCPU, 8 GB)
- Commit: 3f2c9e1 (tag m5)

## Workload
```

(Числа выше показывают *форму* таблицы, а не настоящие измерения. В строке нагрузки `--rand-regex-url` заставляет `oha` строить URL (Uniform Resource Locator, веб-адрес) каждого запроса по шаблону, так что каждый запрос читает случайный ключ от `key-0` до `key-999`.) Раздел «Limits and honesty» обязателен. У каждого бенчмарка есть условия, которые делают его лучше или хуже реальности; если сказать о них, остальным числам начинают верить.

> ⚡ **Производительность:** сообщайте перцентили, а не средние, и всегда рядом с частотой, на которой они измерены. «p99 = 3 мс» ничего не значит без «при 5 000 запросов в секунду»; при вдвое большей частоте может быть 300 мс. Найдите частоту, на которой цель по задержке впервые не выполняется, и сообщите её как ёмкость системы — тогда вы знаете и свой **запас по нагрузке**.

## 5. Чек-лист укрепления

Чек-лист готовности к продакшену из Урока 20.9 задаёт эти вопросы сервису. Для итогового проекта пройдите по ним один раз во время укрепления и запишите ответ (или «неприменимо, потому что …») в README:

| Область | Вопрос | Как это проверить |
|---|---|---|
| Ввод | Проверяется ли каждая длина, размер и количество извне до использования? | модульные тесты с крайними значениями; фаззинг (Уроки 10.4, 20.3) |
| Паники | Может ли внешний ввод вызвать панику (`unwrap`, индексация, приведения `as`)? | `clippy::unwrap_used` для нетестового кода; фаззинг |
| Лимиты | Есть ли лимит у каждой очереди, буфера, числа соединений и размера запроса? | тест на пределе для каждого (Урок 20.8) |
| Время | Есть ли тайм-аут у каждого сетевого вызова и каждого ожидания блокировки? | внедрение сбоя с медленным соседом (Урок 20.5) |
| Падения | Надёжно ли сохраняется каждое подтверждённое изменение и протестировано ли восстановление? | тесты с `kill -9` (Урок 17.2) |
| Завершение | Завершает ли `SIGTERM` работу в полёте и освобождает ли ресурсы? | сквозной тест завершения (Урок 14.14) |
| `unsafe` | Есть ли у каждого блока `unsafe` комментарий `// SAFETY:` и запуск Miri? | ревью и `cargo miri test` (Уроки 10.12, 20.4) |
| Цепочка поставок | Проверяются ли зависимости на бюллетени безопасности и лицензии? | `cargo deny check`, `cargo audit` в CI (Уроки 10.13, 20.7) |
| Видимость | Можно ли по одним метрикам и логам понять, что делает система? | посмотрите на панель во время теста со сбоем (Урок 21.9) |

## Частые ошибки

**1. Бенчмарк отладочной сборки.** Отладочные сборки часто в десять раз медленнее, и узкие места у них другие. Всегда `--release`, и скажите об этом в методике.

**2. Один запуск — одно число.** Число может быть шумом. Исправление: три запуска, медиана и разброс.

**3. Запускать клиент бенчмарка и систему на одной загруженной машине и не говорить об этом.** Они конкурируют за CPU, и числа описывают конкуренцию. Исправление: разные машины (или ВМ для одной стороны) или ясная заметка в «Limits and honesty».

**4. Удалить `proptest-regressions/`.** Файл выглядит как мусор, кто-то добавляет его в `.gitignore`, и старая ошибка молча возвращается. Исправление: коммитьте его.

**5. Медленные тесты в быстрой полосе.** CI идёт сорок минут, вы перестаёте его ждать и начинаете отправлять на красном. Исправление: раздел 3 — быстрая полоса примерно до пяти минут, всё остальное после неё или ночью.

**6. «Укрепление» только в последнюю неделю.** За неделю тестов нельзя найти то, о чём проект никогда не думал. Исправление: матрица тестов начинается с проектного документа; укрепление заполняет пробелы, а не начинает работу.

## Попробуйте сами

1. Создайте `code/p23-harden` из раздела 2 с ошибочным `encode`, запустите `cargo test` и прочитайте уменьшенный вход в отчёте.
2. Откройте `proptest-regressions/lib.txt` и найдите строку `# shrinks to kind = 0, len = 65536, fill = 0`.
3. Примените исправление и новое свойство из раздела 2 и снова запустите `cargo test`: оба теста проходят, а proptest сначала проверил сохранённый случай.
4. Скопируйте конвейер из раздела 3 в свой итоговый проект как `.github/workflows/ci.yml`, поправьте имена своей тестовой цели и скриптов и запустите на нём `actionlint`.
5. Напишите матрицу тестов своего итогового проекта (раздел 1) и отметьте недостающие строки.

## Упражнения

### Упражнение 1 — Заполните матрицу тестов (легко)

В таблице режимов отказов вашего прокси (вариант 2) есть строки: «бэкенд медленный», «бэкенд падает посреди ответа», «клиент очень медленно присылает заголовки», «файл конфигурации неверен при перезагрузке». Для каждой назовите вид теста (модульный, интеграционный, внедрение сбоя, фаззинг, нагрузочный) и одну конкретную проверку.

<details>
<summary>Подсказка</summary>

Подумайте, чем тест должен *управлять*: бэкендом, который можно сделать медленным или убить, клиентом, которого можно сделать медленным, файлом, который можно испортить.

</details>

<details>
<summary>Ответ</summary>

| Отказ | Вид | Проверка |
|---|---|---|
| бэкенд медленный | интеграционный с управляемым `test-backend` | бэкенд, которому велено спать 3 с, при `timeout_ms = 1000` даёт `504` примерно через 1 с |
| бэкенд падает посреди ответа | внедрение сбоя | бэкенд закрывает соединение после половины тела; клиент получает ошибку (а не обрезанный `200`), а `GET` не повторяется после того, как байты ушли |
| клиент медленно присылает заголовки | интеграционный с медленным «сырым» TCP-клиентом | после `header_timeout_ms` прокси закрывает соединение, и число соединений падает |
| неверная конфигурация при перезагрузке | модульный тест `load` + интеграционный | `POST /reload` с испорченным файлом возвращает `400`, а запросы продолжаются со старыми маршрутами |

</details>

### Упражнение 2 — Напишите тест: декодер никогда не паникует на плохом вводе (средне)

Добавьте в исправленный `code/p23-harden` два свойства: (a) `decode` никогда не паникует для любого вектора байтов длиной до 64 байт; (b) каждый строгий префикс корректного закодированного кадра — это `Err` (кадр, обрезанный посередине, никогда не должен декодироваться как более короткий корректный кадр).

<details>
<summary>Подсказка</summary>

Для (a) тело теста только вызывает `decode` и игнорирует результат: паника проваливает тест. Для (b) генерируйте длину нагрузки и позицию обрезки; `prop::sample::Index` даёт индекс, который всегда допустим для среза любой длины: `cut.index(bytes.len())` лежит в `0..bytes.len()`.

</details>

<details>
<summary>Ответ</summary>

Внутри существующего блока `proptest! { … }`:

```rust
#[test]
fn decode_never_panics(bytes in prop::collection::vec(any::<u8>(), 0..64)) {
    let _ = decode(&bytes);
}

#[test]
fn every_cut_frame_is_an_error(len in 0usize..300, cut in any::<prop::sample::Index>()) {
    let bytes = encode(&Frame { kind: 7, payload: vec![1; len] }).unwrap();
    let cut_at = cut.index(bytes.len());
    prop_assert!(decode(&bytes[..cut_at]).is_err());
}
```

```text
test tests::a_small_frame_round_trips ... ok
test tests::every_cut_frame_is_an_error ... ok
test tests::every_frame_round_trips ... ok
test tests::decode_never_panics ... ok

test result: ok. 4 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.01s
```

Почему это работает: (a) — дешёвый, всегда работающий родственник фаззинг-цели: он выполняется в каждом `cargo test`, а фаззер ночью исследует гораздо дальше. (b) проверяет свойство, самое важное для потокового протокола: ещё не полный кадр должен давать «недостаточно данных», а никогда — другое сообщение. Оно проходит, потому что `decode` требует, чтобы у остатка была *ровно* объявленная длина.

</details>

### Упражнение 3 — Задание для цепочки поставок (средне)

Добавьте в конвейер из раздела 3 задание `supply-chain`, которое устанавливает `cargo-deny` и `cargo-audit` и запускает `cargo deny check` и `cargo audit`. Оно не должно ждать `gate`. Проверьте результат `actionlint`.

<details>
<summary>Подсказка</summary>

Следуйте форме других заданий. Без строки `needs:` задание начинается сразу, параллельно с `gate`. Не забудьте пустую строку между заданиями и отступ в два пробела на уровень.

</details>

<details>
<summary>Ответ</summary>

В конце `jobs:`:

```yaml
  supply-chain:
    name: licences, bans and advisories
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - run: cargo install --locked cargo-deny cargo-audit
      - run: cargo deny check
      - run: cargo audit
```

`actionlint .github/workflows/ci.yml` ничего не печатает и завершается с кодом 0. Почему это работает: проверки цепочки поставок не зависят от того, компилируется ли ваш код, поэтому они идут параллельно и сообщают о новом бюллетене безопасности даже в день, когда быстрая полоса красная. Поскольку конвейер запускается и каждую ночь, новый бюллетень по одной из ваших зависимостей появится в течение суток, даже если вы ничего не отправляли. (`cargo deny check` нужен `deny.toml` в репозитории, как в Уроке 10.13.)

</details>

### Упражнение 4 — Критически прочитайте таблицу результатов (сложно)

В `docs/results.md` друга написано: «Средняя задержка 0,8 мс, 120 000 запросов в секунду. Измерено `oha -c 500 -z 10s` на моём ноутбуке на отладочной сборке, клиент и сервер на одной машине, один запуск». Перечислите все проблемы этого измерения и как исправить каждую.

<details>
<summary>Подсказка</summary>

Пройдите по шести пунктам методики из раздела 4 и вспомните, что Урок 19.1 говорил о средних и о генераторах нагрузки с закрытой моделью.

</details>

<details>
<summary>Ответ</summary>

1. **Отладочная сборка:** числа описывают не ту программу. Используйте `--release`.
2. **Только среднее:** оно скрывает хвост. Сообщайте p50, p99 и p99.9.
3. **Закрытая модель (`-c 500`) без частоты:** клиент ждёт ответов, поэтому медленный сервер замедляет клиента и скрывает задержку (coordinated omission, Урок 19.1). Используйте фиксированную частоту (`-q`) и сообщайте задержку на этой частоте.
4. **10 секунд, без прогрева, один запуск:** слишком коротко и, возможно, шум. Отбросьте прогрев, измеряйте 60 с и больше, трижды, сообщайте медиану и разброс.
5. **Клиент и сервер на одном ноутбуке:** они конкурируют за CPU, и об этом ничего не сказано. Разделите их или скажите это в «Limits and honesty».
6. **Нет оборудования, версий, размера нагрузки и коммита:** никто не сможет повторить. Напишите раздел с настройкой.
7. **Нет базовой линии и профиля:** 120 000 в секунду по сравнению с чем и чем ограничено? Добавьте сравнение и флеймграф.

</details>

## Вопросы для самопроверки

1. Что такое матрица тестов и откуда берутся её строки?

<details>
<summary>Ответ</summary>

Таблица, которая сопоставляет каждому требованию и каждому режиму отказа из проектного документа тест, который это доказывает, со статусом. Её строки берутся из раздела требований и таблицы режимов отказов проектного документа.

</details>

2. Почему тест на примере не нашёл ошибку с `as u16` и как тест на основе свойств нашёл её так точно?

<details>
<summary>Ответ</summary>

Пример использовал нагрузку в 5 байт, далеко от предела в 65 535 байт. Тест на основе свойств пробовал длины до 69 999, нашёл падающую и уменьшил её до самой маленькой падающей длины, 65 536, — ровно 2¹⁶, что прямо указывает на 16-битное приведение.

</details>

3. Почему `proptest-regressions/` нужно коммитить?

<details>
<summary>Ответ</summary>

Там хранятся начальные значения случаев, которые уже падали. Каждый запуск, на каждой машине и в CI, сначала пробует их, поэтому старая ошибка не может вернуться незамеченной.

</details>

4. Что относится к быстрой полосе CI, а что к медленной, и зачем их разделять?

<details>
<summary>Ответ</summary>

Быстрая полоса: форматирование, Clippy, модульные и интеграционные тесты, быстрые приёмочные проверки — минуты, на каждую отправку. Медленная полоса: симуляция со многими начальными значениями, фаззинг, сборка бенчмарков — после быстрой полосы и дольше ночью. Разделение сохраняет быструю обратную связь, не отказываясь от медленных глубоких проверок.

</details>

5. Почему CI только *компилирует* бенчмарки, а не запускает их?

<details>
<summary>Ответ</summary>

Общие машины CI шумные: на том же оборудовании работают другие задания, поэтому числа ненадёжны. Компиляция всё равно ловит бенчмарки, которые перестали собираться; настоящие измерения проводятся на известном оборудовании по записанной методике.

</details>

6. Назовите четыре вещи, которые должна указывать методика бенчмарка.

<details>
<summary>Ответ</summary>

Любые четыре из: оборудование и версии программ, профиль сборки, точная нагрузка (команда, размер, соединения, частота, длительность), прогрев, число повторений с медианой и разбросом, базовая линия и ограничения установки.

</details>

7. Что такое запас по нагрузке и как его найти?

<details>
<summary>Ответ</summary>

Расстояние между нагрузкой, на которой вы работаете, и нагрузкой, при которой система впервые не выполняет свои цели. Его находят, повышая фиксированную частоту шаг за шагом, пока цель по задержке (например, p99) не перестанет выполняться; эта частота — ёмкость, а разница с обычной нагрузкой — запас.

</details>

## Итоги

- Укрепление смотрит на всю систему: постройте матрицу тестов по требованиям и режимам отказов проектного документа и заполняйте недостающие строки в порядке риска.
- Свойства «туда и обратно» находят ошибки, которые пропускают примеры; proptest уменьшает падение до минимального случая (здесь `len = 65536`) и сохраняет начальное значение в `proptest-regressions/`, который вы коммитите.
- Приведения `as` молча отрезают длины; используйте `try_from` на каждой границе.
- Один конвейер с быстрой полосой (форматирование, Clippy, тесты, приёмочные проверки) и медленной полосой (начальные значения симуляции, фаззинг, сборка бенчмарков, ночью дольше), проверенный `actionlint`.
- У надёжных бенчмарков есть записанная методика: настройка, нагрузка с фиксированной частотой, прогрев, повторения, базовая линия, профиль и честный список ограничений.
- Чек-лист укрепления спрашивает о вводе, паниках, лимитах, тайм-аутах, падениях, завершении, `unsafe`, цепочке поставок и видимости — и ответы идут в ваш README.
