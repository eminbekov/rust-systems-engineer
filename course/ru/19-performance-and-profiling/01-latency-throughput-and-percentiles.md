# Урок 19.1 — Задержка, пропускная способность и перцентили

> **Этап 19 — Производительность и профилирование** · Урок 1 из 11 · ⏱ около 135 минут

## Что вы узнаете

## Новые слова

| Слово | Значение |
|---|---|
| **задержка** (latency) | Сколько длится одна операция — от момента, когда её запросили, до момента, когда готов ответ. Измеряется во времени: мкс, мс. |
| **пропускная способность** (throughput) | Сколько операций завершается за единицу времени, например запросов в секунду (req/s). |
| **мкс** (µs, microsecond, микросекунда) | Одна миллионная секунды. 1 мс (миллисекунда) = 1000 мкс. |
| **распределение** (distribution) | Весь набор измеренных значений и то, как часто встречается каждое: много быстрых, несколько медленных. |
| **перцентиль** (percentile) | Значение, ниже которого лежит заданная доля измерений. p99 = 3 мс означает, что 99% запросов заняли не больше 3 мс. |
| **p50 / медиана** (median) | 50-й перцентиль: половина запросов быстрее, половина медленнее. |
| **хвостовая задержка** (tail latency) | Самая медленная часть распределения: p99, p99.9, максимум. Коротко — «хвост». |
| **выброс** (outlier) | Одно значение, далеко отстоящее от остальных. В задержках выбросы — это настоящие запросы, которых ждали настоящие пользователи. |
| **гистограмма** (histogram) | Структура данных, которая считает, сколько значений попало в каждый диапазон («корзину», bucket). Занимает фиксированный объём памяти, сколько бы значений вы ни добавили. |
| **закон Литтла** (Little's law) | Правило из теории очередей: запросов в работе = пропускная способность × задержка. |
| **очередь** (queue) | Работа, которая ждёт обслуживания. Время ожидания в очереди — часть задержки. |
| **скоординированный пропуск** (coordinated omission) | Ошибка измерения: тестер ждёт медленного ответа и поэтому не отправляет (и не измеряет) запросы, которые тоже были бы медленными. |
| **SLO** (Service Level Objective, цель уровня обслуживания) | Обещание команды о своём сервисе, например «задержка p99 ниже 200 мс за 30 дней». |

## 1. Два числа: задержка и пропускная способность

Представьте маленькую кофейню с одним бариста. Насколько она хороша, описывают два разных вопроса:

- **Задержка:** «Сколько я жду свой кофе?» — например, 3 минуты.
- **Пропускная способность:** «Сколько чашек кофейня делает за час?» — например, 20.

Это не одно и то же. Наймите второго бариста — пропускная способность удвоится, но каждая чашка всё так же готовится 3 минуты. Купите более быструю кофемашину — изменятся оба числа. Позвольте у двери выстроиться длинной очереди — пропускная способность останется 20 чашек в час, но ваша *задержка* вырастет: теперь вы стоите в очереди ещё до того, как начнутся эти 3 минуты.

С программами то же самое. У веб-сервиса есть задержка на запрос и пропускная способность в запросах в секунду. У функции, которая разбирает файл, есть задержка на вызов и пропускная способность в мегабайтах в секунду.

Два числа связывает простое правило — **закон Литтла**:

```text
requests in progress  =  throughput  ×  latency
        L             =      λ       ×     W

Example: 2000 req/s × 0.005 s (5 ms) = 10 requests in progress at any moment
```

(`λ`, «лямбда», и `W` — обычные обозначения в книгах; они вам не понадобятся.) Закон Литтла полезен в обе стороны. Если в вашем сервисе одновременно может выполняться не больше 10 запросов (10 потоков, 10 соединений с базой данных) и каждый занимает 5 мс, он никогда не обработает больше 2000 req/s. А если задержка вдруг удвоится при том же трафике, удвоится и число запросов в работе — и могут закончиться потоки или соединения.

> 💡 **Совет:** когда кто-то говорит «сервис быстрый», спросите: «какое из чисел?». Задержку чувствует один пользователь. Пропускная способность — это то, сколько выдерживает машина. Изменение может улучшить одно и ухудшить другое: например, сбор работы в большие пакеты даёт больше пропускной способности, но каждый элемент ждёт дольше.

## 2. Измеряем задержку: почему среднее лжёт

Создайте пакет для этого урока:

```bash
cd ~/projects/rust/code
cargo new --lib p19-latency
cd p19-latency
mkdir src/bin
```

Сначала нам нужен способ вычислять перцентиль. Поместите это в `src/lib.rs`:

```rust
//! Small helpers for measuring latency.

/// Returns the `p`-th percentile (0.0..=100.0) of a sorted slice,
/// using the "nearest rank" method.
///
/// Panics if `sorted` is empty or `p` is outside 0..=100.
pub fn percentile<T: Copy>(sorted: &[T], p: f64) -> T {
    assert!(!sorted.is_empty(), "no values");
    assert!((0.0..=100.0).contains(&p), "p must be in 0..=100, got {p}");
    // Rank = how many values must be at or below the answer.
    let rank = (p / 100.0 * sorted.len() as f64).ceil() as usize;
    // Ranks start at 1, indexes at 0. p = 0 gives rank 0: take the first value.
    let index = rank.saturating_sub(1);
    sorted[index]
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn percentiles_of_one_to_hundred() {
        let values: Vec<u32> = (1..=100).collect();
        assert_eq!(percentile(&values, 50.0), 50);
        assert_eq!(percentile(&values, 99.0), 99);
        assert_eq!(percentile(&values, 100.0), 100);
        assert_eq!(percentile(&values, 0.0), 1);
    }

    #[test]
    fn one_value_is_every_percentile() {
        assert_eq!(percentile(&[7], 0.0), 7);
        assert_eq!(percentile(&[7], 99.9), 7);
    }

    #[test]
    #[should_panic(expected = "no values")]
    fn empty_slice_panics() {
        let empty: [u32; 0] = [];
        percentile(&empty, 50.0);
    }
}
```

**Что происходит:**

1. Сначала значения нужно **отсортировать**. Тогда «99-й перцентиль из 1000 значений» — это просто значение с рангом 990: 990 значений не больше него.
2. `p / 100.0 * len` даёт ранг как дробь; `ceil` округляет вверх, поэтому ответ — всегда реально измеренное значение (это метод «ближайшего ранга»; другие инструменты могут интерполировать между двумя значениями и давать немного другие числа).
3. Ранги считаются с 1, индексы среза — с 0, поэтому вычитаем 1. `saturating_sub` оставляет 0 нулём при `p = 0`.
4. Функция обобщена по `T: Copy`, поэтому работает для `Duration`, `u64` и всего, что можно скопировать из среза.
5. Тесты используют 1..=100 — там правильный ответ очевиден: 50-й перцентиль равен 50.

Запустите `cargo test`:

```text
running 3 tests
test tests::one_value_is_every_percentile ... ok
test tests::percentiles_of_one_to_hundred ... ok
test tests::empty_slice_panics - should panic ... ok

test result: ok. 3 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Теперь — условный обработчик запросов. Большинство запросов дешёвые, но каждый 50-й делает в 100 раз больше работы — как запрос, который не нашёл данных в кэше и вынужден идти в базу данных. Создайте `src/bin/latency.rs`:

```rust
use p19_latency::percentile;
use std::hint::black_box;
use std::time::{Duration, Instant};

/// A pretend request handler. Most requests are cheap,
/// but every 50th request does 100 times more work.
fn handle_request(id: u64) -> u64 {
    let rounds = if id.is_multiple_of(50) {
        2_000_000
    } else {
        20_000
    };
    let mut x = id;
    for _ in 0..rounds {
        x = x.wrapping_mul(6364136223846793005).wrapping_add(1);
    }
    x
}

fn main() {
    let mut times: Vec<Duration> = Vec::with_capacity(1000);
    for id in 0..1000 {
        let start = Instant::now();
        black_box(handle_request(black_box(id)));
        times.push(start.elapsed());
    }

    let total: Duration = times.iter().sum();
    let mean = total / times.len() as u32;
    times.sort();

    println!("requests: {}", times.len());
    println!("mean   {mean:?}");
    for (name, p) in [("p50", 50.0), ("p90", 90.0), ("p99", 99.0), ("p99.9", 99.9)] {
        println!("{name:<6} {:?}", percentile(&times, p));
    }
    println!("max    {:?}", times[times.len() - 1]);
}
```

**Что происходит:**

1. `handle_request` выполняет фиксированный объём арифметики. `id.is_multiple_of(50)` истинно для каждого 50-го id — он получает в 100 раз больше раундов.
2. `black_box` не даёт оптимизатору выбросить работу (Урок 05.12).
3. Мы засекаем каждый вызов отдельно через `Instant` и храним каждую длительность в `Vec`.
4. **Среднее** (mean) — это сумма, делённая на количество. Затем сортируем и читаем перцентили.

Запустите командой `cargo run --release --bin latency`. Один запуск на M4 Pro (ваши числа будут другими и меняются от запуска к запуску):

```text
requests: 1000
mean   103.625µs
p50    23.042µs
p90    23.417µs
p99    2.372417ms
p99.9  23.606875ms
max    23.606875ms
```

Прочитайте числа внимательно:

- **p50 — 23 мкс.** Типичный запрос быстрый.
- **Среднее — 104 мкс**, более чем вчетверо выше медианы. *Ни один запрос не занял 104 мкс.* Среднее смешивает 980 быстрых запросов с 20 медленными и не описывает ни одну из групп.
- **p99 — 2,4 мс**: это медленная группа «промахов кэша», в 100 раз медленнее медианы.
- **p99.9 и максимум — 23 мс**, даже медленнее нашего медленного пути. Наш код никогда не делает 23 мс работы. Это была операционная система: она приостановила наш поток, чтобы выполнить что-то другое (Урок 13.9). Настоящие пользователи тоже чувствуют такие паузы, поэтому им место в измерении.

Вот почему инженеры говорят о перцентилях, а не о средних. Есть ещё одна причина, по которой хвост важен: одна страница или одно действие пользователя часто требует **многих** запросов. Если страница обращается к 100 небольшим сервисам и каждый медленнее своего p99 в 1% вызовов, то большинство страниц попадёт хотя бы на один медленный вызов (сколько именно — посчитаете в Упражнении 1). В больших системах p99 — это то, что чувствует большинство пользователей.

> ⚠️ **Частая ошибка:** выбрасывать «выбросы», потому что они «портят» измерение. В микробенчмарке одной функции (Урок 09.11) это может быть правильно: вы хотите узнать скорость кода. В измерении задержки сервиса выбросы *и есть* результат: это реальные люди, которые ждали.

> 📏 **Соглашение:** записывайте перцентили как p50, p90, p99, p99.9 и всегда указывайте единицу времени. Говорите, что именно измерено («время обработчика на сервере», «время, которое видит клиент»), и при какой нагрузке. p99 без нагрузки и условий — бесполезное число.

## 3. Гистограммы: храним миллионы значений

Хранить каждую длительность в `Vec` и сортировать — нормально для тысячи значений. Сервис, который обрабатывает 10 000 запросов в секунду, за сутки видит 864 миллиона значений; хранить их все мы не можем.

Эту задачу решает **гистограмма**. Вместо значений она хранит **счётчики**: «сколько значений было между 20 и 21 мкс», «между 21 и 22 мкс» и так далее. Чтобы найти p99, она проходит по счётчикам от меньших к большим, пока не наберёт 99% общего количества. Объём памяти не меняется, сколько бы значений вы ни добавили.

```text
bucket (µs)   count
  20..21         12  #
  21..22        610  ##############################
  22..23        320  ################
 ...
2300..2400        9
2400..2500        8
```

Крейт `hdrhistogram` (HDR = High Dynamic Range, высокий динамический диапазон: одна структура охватывает и крошечные, и огромные значения) сам выбирает корзины. Вы задаёте наименьшее значение, наибольшее значение и сколько **значащих цифр** должны быть точными. При 3 цифрах значение 4251 мкс хранится как что-то между 4250 и 4260 — для задержки этого достаточно. В этой гистограмме 17 408 счётчиков по 8 байт, около 136 КиБ, — хранит ли она десять значений или десять миллиардов.

Добавьте крейт. Его необязательные фичи (feature) нам не нужны (они сериализуют гистограммы в файлы):

```bash
cargo add hdrhistogram@7.6 --no-default-features
```

`src/bin/histogram.rs`:

```rust
use hdrhistogram::Histogram;
use std::hint::black_box;
use std::time::Instant;

fn handle_request(id: u64) -> u64 {
    let rounds = if id.is_multiple_of(50) {
        2_000_000
    } else {
        20_000
    };
    let mut x = id;
    for _ in 0..rounds {
        x = x.wrapping_mul(6364136223846793005).wrapping_add(1);
    }
    x
}

fn main() {
    // Values from 1 µs to 60 s, with 3 significant digits of precision.
    let mut hist = Histogram::<u64>::new_with_bounds(1, 60_000_000, 3).unwrap();

    for id in 0..20_000 {
        let start = Instant::now();
        black_box(handle_request(black_box(id)));
        let micros = start.elapsed().as_micros() as u64;
        hist.record(micros).unwrap();
    }

    println!("count  {}", hist.len());
    println!("mean   {:.1} µs", hist.mean());
    for q in [0.5, 0.9, 0.99, 0.999] {
        println!("p{:<5} {} µs", q * 100.0, hist.value_at_quantile(q));
    }
    println!("max    {} µs", hist.max());
}
```

**Что происходит:**

1. `Histogram::<u64>::new_with_bounds(1, 60_000_000, 3)` создаёт гистограмму для значений от 1 до 60 000 000 (мы записываем микросекунды, то есть от 1 мкс до 60 с) с 3 значащими цифрами. Она возвращает `Result`, потому что невозможные границы — это ошибка.
2. `record` добавляет одно значение. Значение выше верхней границы — ошибка (см. «Частые ошибки»).
3. `value_at_quantile(0.99)` возвращает p99. **Квантиль** (quantile) — та же идея, что перцентиль, только записанная дробью: 0.99 вместо 99.
4. `len`, `mean` и `max` дают количество, среднее и наибольшее значение.

`cargo run --release --bin histogram` (один запуск):

```text
count  20000
mean   204.0 µs
p50    23 µs
p90    24 µs
p99    4251 µs
p99.9  25199 µs
max    76927 µs
```

Форма та же, что и раньше: быстрая медиана, медленный p99 и длинный хвост пауз операционной системы.

> ⚡ **Производительность:** запись в гистограмму стоит несколько наносекунд и никогда не выделяет память, поэтому её можно делать внутри горячего цикла или обработчика запроса. Две гистограммы можно сложить методом `add`: каждый поток держит свою гистограмму (во время измерения не нужна блокировка), а в конце их объединяют. Никогда не считайте «среднее от p99» с нескольких машин: перцентили нельзя усреднять. Объедините гистограммы, затем прочитайте p99.

## 4. Пропускная способность и закон Литтла на практике

Пропускную способность измерить легко: посчитайте завершённые операции за фиксированное время. Запустим дешёвые запросы на 1, 2 и 4 потоках по одной секунде и проверим закон Литтла. `src/bin/throughput.rs`:

```rust
use std::hint::black_box;
use std::thread;
use std::time::{Duration, Instant};

/// A cheap request: always the same amount of work.
fn handle_request(id: u64) -> u64 {
    let mut x = id;
    for _ in 0..20_000 {
        x = x.wrapping_mul(6364136223846793005).wrapping_add(1);
    }
    x
}

/// Runs `workers` threads for `run_for`. Returns (requests done, total busy time).
fn run(workers: u64, run_for: Duration) -> (u64, Duration) {
    thread::scope(|s| {
        let handles: Vec<_> = (0..workers)
            .map(|w| {
                s.spawn(move || {
                    let deadline = Instant::now() + run_for;
                    let mut done = 0u64;
                    let mut busy = Duration::ZERO;
                    while Instant::now() < deadline {
                        let start = Instant::now();
                        black_box(handle_request(black_box(w * 1_000_000 + done)));
                        busy += start.elapsed();
                        done += 1;
                    }
                    (done, busy)
                })
            })
            .collect();
        handles
            .into_iter()
            .map(|h| h.join().unwrap())
            .fold((0, Duration::ZERO), |(n, b), (dn, db)| (n + dn, b + db))
    })
}

fn main() {
    let run_for = Duration::from_secs(1);
    for workers in [1, 2, 4] {
        let (done, busy) = run(workers, run_for);
        let throughput = done as f64 / run_for.as_secs_f64();
        let mean_latency = busy.as_secs_f64() / done as f64;
        // Little's law: requests in progress = throughput × latency.
        let in_progress = throughput * mean_latency;
        println!(
            "workers {workers}: {throughput:>7.0} req/s, mean latency {:>5.1} µs, in progress {in_progress:.2}",
            mean_latency * 1e6
        );
    }
}
```

**Что происходит:**

1. Каждый рабочий поток крутится до своего дедлайна, засекает каждый запрос и прибавляет время к `busy`.
2. `fold` складывает количества и занятое время всех потоков.
3. Пропускная способность = запросы ÷ секунды. Средняя задержка = занятое время ÷ запросы.
4. `throughput × mean_latency` — это `L` из закона Литтла: среднее число запросов в работе. Если `workers` потоков заняты всё время, оно должно равняться `workers`.

`cargo run --release --bin throughput` (один запуск):

```text
workers 1:   23133 req/s, mean latency  43.2 µs, in progress 1.00
workers 2:   42371 req/s, mean latency  47.1 µs, in progress 1.99
workers 4:   73023 req/s, mean latency  54.8 µs, in progress 4.00
```

Закон Литтла выполняется: 1, 2 и 4 запроса в работе. Пропускная способность растёт с числом рабочих потоков, а задержка одного запроса почти не меняется. Это кофейня с несколькими бариста. (Задержка выше, чем в разделе 2, потому что эта программа вызывает `Instant::now()` дважды на запрос и потому что у M4 Pro есть быстрые и более медленные ядра; на каком ядре работает каждый поток, решает операционная система.)

Когда та же программа запускалась второй раз, пока Mac был занят другой работой, строка для 4 потоков показала `25102 req/s, mean latency 159.3 µs`. Потокам приходилось ждать свободного ядра, поэтому каждый запрос стал медленнее, а пропускная способность упала. Настоящий сервис ведёт себя так же, когда работы больше, чем ядер: запросы начинают **вставать в очередь**, и задержка растёт задолго до того, как пропускная способность упадёт до нуля. В следующем уроке вы ясно увидите это на настоящем сервисе.

## 5. Скоординированный пропуск: тестер, который врёт

Вот ловушка, в которую попадали многие нагрузочные тесты. Представьте тестер, который должен отправлять **один запрос каждые 10 мс** и измерять каждый. Он отправляет запрос, ждёт ответа, затем отправляет следующий в следующий запланированный момент.

Теперь сервер замирает на 200 мс (например, длинная пауза на очистку памяти). Тестер отправляет запрос 50 и ждёт 200 мс. В это время он **не** отправляет запросы с 51 по 69, хотя по плану должен. Когда он продолжает, сервер снова быстрый, и все последующие запросы выглядят быстрыми. Тестер измерил *один* медленный запрос. Настоящие пользователи за время паузы отправили бы двадцать запросов, и ждать пришлось бы *всем*.

```text
plan:      |  |  |  |  |  |  |  |  |  |  |  |     one request every 10 ms
server:    ..[====== frozen 200 ms ======]..
naive:     50 sent ............. answer 50, then 51, 52 ... look fast   -> 1 slow value
honest:    51, 52 ... 69 were planned during the freeze and had to wait -> 19 more slow values
```

Тестер и сервер «координируются»: медленный сервер замедляет тестер, и тестер *пропускает* плохие измерения. Отсюда название — **скоординированный пропуск**.

Это можно точно смоделировать без всяких реальных замеров. `src/bin/omission.rs`:

```rust
use p19_latency::percentile;

/// How long the pretend server needs for request `k`, in milliseconds.
/// Request 50 hits a 200 ms pause; all others take 1 ms.
fn service_ms(k: u64) -> u64 {
    if k == 50 { 200 } else { 1 }
}

fn main() {
    let interval = 10; // the plan: one request every 10 ms
    let mut naive = Vec::new(); // measured from the moment it was really sent
    let mut honest = Vec::new(); // measured from the moment it SHOULD have been sent
    let mut server_free_at = 0; // the time when the server finishes its current request

    for k in 0..200 {
        let planned = k * interval;
        // The tester cannot send while it still waits for the previous answer.
        let sent = planned.max(server_free_at);
        let finished = sent + service_ms(k);
        server_free_at = finished;

        naive.push(finished - sent);
        honest.push(finished - planned);
    }
    naive.sort();
    honest.sort();

    println!("            p50   p90   p99   max (ms)");
    for (name, v) in [("naive", &naive), ("honest", &honest)] {
        println!(
            "{name:<8} {:>5} {:>5} {:>5} {:>5}",
            percentile(v, 50.0),
            percentile(v, 90.0),
            percentile(v, 99.0),
            v[v.len() - 1]
        );
    }
    let slow = |v: &[u64]| v.iter().filter(|&&ms| ms > 10).count();
    println!(
        "slower than 10 ms: naive {}, honest {}",
        slow(&naive),
        slow(&honest)
    );
}
```

**Что происходит:**

1. Время — просто число миллисекунд; ничего не спит, поэтому результат одинаков на любом компьютере.
2. Запрос `k` **запланирован** на момент `k × 10` мс. Реально он **отправлен** в запланированное время или, если сервер ещё занят, когда сервер освободится.
3. **Наивная** (naive) задержка отсчитывается от момента отправки. **Честная** (honest) — от запланированного момента, потому что настоящий пользователь кликнул бы именно тогда и начал ждать.
4. Запрос 51 запланирован на 510 мс, но сервер занят до 700 мс. Наивно: 1 мс. Честно: 191 мс.

`cargo run --release --bin omission`:

```text
            p50   p90   p99   max (ms)
naive        1     1     1   200
honest       1    20   182   200
slower than 10 ms: naive 1, honest 22
```

Наивный тестер сообщает p99 = 1 мс: «сервис идеален». Честный взгляд говорит, что каждый десятый запрос ждал 20 мс или больше, а p99 — 182 мс. Тот же сервер, та же пауза, совершенно разные выводы.

Как этого избежать:

- Измеряйте задержку **от запланированного момента старта**, а не от момента, когда запрос наконец ушёл.
- Используйте тестер с **открытой моделью** (open model), который продолжает отправлять с запланированной частотой, даже пока ранние запросы ещё ждут. Нагрузочный тестер из следующего урока это умеет.
- Если можно измерять только наивно, `hdrhistogram` может сам добавить недостающие значения через `record_correct` (Упражнение 3).

> 🧪 **Тестирование:** модель выше — ещё и хороший образец для тестов. Реальные замеры шумные, поэтому тесты математики перцентилей, гистограмм и «что сообщает мой инструмент» должны использовать придуманные фиксированные числа. Реальные замеры оставьте бенчмаркам.

## Частые ошибки

1. **Сообщать только среднее.** Оно скрывает медленные запросы. Сообщайте вместе p50, p99 и максимум.
2. **Измерять в режиме отладки.** Отладочные сборки бывают в десять и более раз медленнее и меняют форму распределения. Всегда `--release`.
3. **Слишком мало замеров для перцентиля.** p99.9 из 1000 значений — это одно самое большое или второе по величине значение; оно скачет от запуска к запуску. Для p99.9 нужны хотя бы десятки тысяч значений.
4. **Усреднять перцентили.** «У сервера A p99 = 10 мс, у сервера B p99 = 30 мс, значит p99 = 20 мс» — неверно. Объедините гистограммы (или сырые значения), затем прочитайте p99.
5. **Записывать значение выше верхней границы гистограммы.** Типичная причина — не та единица измерения. В `histogram.rs` замените строку с `record` на `hist.record(start.elapsed().as_nanos() as u64).unwrap();`: теперь одна пауза операционной системы в 70 мс — это 70 000 000 *наносекунд*, выше границы 60 000 000, и программа останавливается:

   ```text
   thread 'main' (5916363) panicked at src/bin/histogram.rs:26:56:
   called `Result::unwrap()` on an `Err` value: ValueOutOfRangeResizeDisabled
   ```

   (Число в скобках — ID потока; у вас оно другое.) Используйте везде одну единицу и пишите её в имени переменной (`micros`), выбирайте границы, покрывающие все возможные значения, или используйте `Histogram::new(3)`, которая растёт по мере необходимости.

## Упражнения

### Упражнение 1 — Хвост в масштабе (легко)

Странице нужно `n` независимых вызовов бэкенд-сервисов. Каждый вызов быстрый (ниже своего p99) с вероятностью 0.99. Напишите программу `src/bin/fanout.rs`, которая для `n` = 1, 10, 50 и 100 печатает процент страниц, ждущих хотя бы одного медленного вызова.

<details>
<summary>Подсказка</summary>

Все `n` вызовов быстрые с вероятностью `0.99`, умноженной на себя `n` раз: `f64::powi(0.99, n)`. «Хотя бы один медленный» — противоположное событие: `1 - это`.

</details>

<details>
<summary>Ответ</summary>

```rust
fn main() {
    let fast = 0.99; // a single call is fast (below its p99) 99% of the time
    for calls in [1, 10, 50, 100] {
        let all_fast = f64::powi(fast, calls);
        println!(
            "{calls:>3} calls: {:>4.1}% of pages wait for at least one slow call",
            (1.0 - all_fast) * 100.0
        );
    }
}
```

```text
  1 calls:  1.0% of pages wait for at least one slow call
 10 calls:  9.6% of pages wait for at least one slow call
 50 calls: 39.5% of pages wait for at least one slow call
100 calls: 63.4% of pages wait for at least one slow call
```

Почему это работает: вероятности независимых событий перемножаются. При 100 вызовах «редкий» случай в 1% становится обычным для большинства страниц — поэтому большие системы следят за p99 и p99.9 каждого компонента.

</details>

### Упражнение 2 — Тест на границы перцентиля (легко)

Напишите ещё два теста для `percentile` в `src/lib.rs`: (а) для значений 1..=20 p95 равен 19, а p95.1 — 20; (б) `p = 101.0` вызывает панику с сообщением, содержащим `p must be in 0..=100`.

<details>
<summary>Подсказка</summary>

Для (б) используйте `#[should_panic(expected = "...")]`. Помните, что `expected` достаточно быть частью сообщения.

</details>

<details>
<summary>Ответ</summary>

```rust
#[cfg(test)]
mod exercise_tests {
    use super::percentile;

    #[test]
    fn p95_of_twenty_values() {
        let values: Vec<u64> = (1..=20).collect();
        assert_eq!(percentile(&values, 95.0), 19);
        assert_eq!(percentile(&values, 95.1), 20);
    }

    #[test]
    #[should_panic(expected = "p must be in 0..=100")]
    fn p_above_100_panics() {
        percentile(&[1, 2, 3], 101.0);
    }
}
```

Теперь `cargo test` показывает 5 пройденных тестов. Почему это работает: 95% от 20 — ровно ранг 19; 95.1% от 20 — это 19.02, и `ceil` округляет до ранга 20. Именно в таких случаях «чуть выше границы» прячутся ошибки на единицу (off-by-one).

</details>

### Упражнение 3 — Исправляем скоординированный пропуск (сложно)

У `hdrhistogram` есть `record_correct(value, expected_interval)`. Если значение больше ожидаемого интервала, метод дополнительно записывает значения, которые увидели бы пропущенные запросы: `value - interval`, `value - 2 × interval` и так далее. Перепишите модель в `src/bin/corrected.rs` с двумя гистограммами: `plain` получает `record(measured)`, `corrected` получает `record_correct(measured, 10)`, где `measured = finished - sent` (наивное значение). Выведите количество, p90, p99 и максимум для обеих.

<details>
<summary>Подсказка</summary>

Используйте `Histogram::<u64>::new(3)` для обеих. Цикл такой же, как в `omission.rs`; нужно только наивное значение.

</details>

<details>
<summary>Ответ</summary>

```rust
use hdrhistogram::Histogram;

fn service_ms(k: u64) -> u64 {
    if k == 50 { 200 } else { 1 }
}

fn main() {
    let interval = 10;
    let mut plain = Histogram::<u64>::new(3).unwrap();
    let mut corrected = Histogram::<u64>::new(3).unwrap();
    let mut server_free_at = 0;

    for k in 0..200 {
        let planned = k * interval;
        let sent = planned.max(server_free_at);
        let finished = sent + service_ms(k);
        server_free_at = finished;

        let measured = finished - sent;
        plain.record(measured).unwrap();
        // Also adds the values that the missing requests would have seen.
        corrected.record_correct(measured, interval).unwrap();
    }

    for (name, h) in [("plain", &plain), ("corrected", &corrected)] {
        println!(
            "{name:<10} count {:>3}  p90 {:>3}  p99 {:>3}  max {:>3}",
            h.len(),
            h.value_at_quantile(0.90),
            h.value_at_quantile(0.99),
            h.max()
        );
    }
}
```

```text
plain      count 200  p90   1  p99   1  max 200
corrected  count 219  p90   1  p99 180  max 200
```

Почему это работает: для единственного значения 200 мс `record_correct` добавляет 190, 180, … 10 — 19 запросов, которые тестер пропустил. p99 подскакивает с 1 до 180 мс, близко к честным 182 мс. Поправка — это оценка (количество 219, а не 200, и p90 всё ещё 1), поэтому измерять от запланированного момента старта лучше, когда это возможно.

</details>

## Вопросы для самопроверки

1. Сервис обрабатывает 500 req/s, каждый запрос занимает 40 мс. Сколько запросов в среднем находится в работе?

<details>
<summary>Ответ</summary>

Закон Литтла: 500 × 0.040 = 20 запросов в работе.

</details>

2. Средняя задержка 100 мкс, а p50 — 23 мкс. Что это говорит о распределении?

<details>
<summary>Ответ</summary>

Оно перекошено: большинство запросов быстрые, а небольшое число очень медленных тянет среднее вверх. Среднее не описывает ни одного реального запроса; чтобы увидеть медленную группу, смотрите на p99 и максимум.

</details>

3. Что означает «p99 = 2,4 мс» одним предложением?

<details>
<summary>Ответ</summary>

99% измеренных запросов заняли 2,4 мс или меньше; 1% — дольше.

</details>

4. Почему при измерении задержки сервиса нужно сохранять выбросы?

<details>
<summary>Ответ</summary>

Потому что каждый выброс — это реальный запрос, которого ждал реальный пользователь. Если их убрать, сервис будет выглядеть лучше, чем он есть. (Убирать шум допустимо только в микробенчмарках чистого кода.)

</details>

5. Объясните скоординированный пропуск двумя предложениями.

<details>
<summary>Ответ</summary>

Когда система медленная, тестер, ждущий каждого ответа, отправляет меньше запросов, и медленный период даёт одно измерение вместо многих. Результат скрывает большую часть медленных запросов, и хвост выглядит гораздо лучше, чем то, что испытывают пользователи.

</details>

6. Два сервера сообщают p99 = 10 мс и p99 = 30 мс. Можно ли сказать, что p99 обоих вместе — 20 мс?

<details>
<summary>Ответ</summary>

Нет. Перцентили нельзя усреднять. Объедините сырые значения или гистограммы, затем снова вычислите p99.

</details>

## Итоги

- **Задержка** — время одной операции; **пропускная способность** — операций в секунду. Это разные числа, и изменения могут сдвигать их в разные стороны.
- **Закон Литтла:** запросов в работе = пропускная способность × задержка. Он показывает, сколько потоков или соединений нужно для нагрузки.
- **Среднее скрывает медленные запросы.** Сообщайте p50, p99, p99.9 и максимум — с единицей измерения и нагрузкой.
- Хвостовая задержка важнее с ростом системы, потому что одно действие пользователя затрагивает много компонентов.
- `hdrhistogram` записывает миллионы значений в фиксированной памяти, даёт любой перцентиль и точно объединяется.
- **Скоординированный пропуск** делает медленные системы быстрыми на вид. Измеряйте от запланированного момента старта и используйте нагрузочный тестер с открытой моделью.
