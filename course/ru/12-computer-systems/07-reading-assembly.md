# Урок 12.7 — Читаем ассемблер: arm64 и x86-64

> **Этап 12 — Компьютерные системы** · Урок 7 из 15 · ⏱ около 135 минут

## Что вы узнаете

- Как увидеть ассемблер, который компилятор Rust создаёт для ваших функций, на вашем Mac и для x86-64 Linux.
- Как читать строку ассемблера: метки, инструкции, регистры, непосредственные значения и операнды памяти.
- Соглашения о вызовах: в каких регистрах приходят аргументы и куда кладётся результат на arm64 и на x86-64.
- Как в ассемблере выглядят сравнения, ветвления, циклы, вызовы функций и стек.

## Перед началом

- Вы прошли [Урок 12.6 — Как процессор выполняет инструкции](06-how-the-cpu-runs-instructions.md).
- Свой первый ассемблер (`add w0, w1, w0` и `ret`) вы видели в [Уроке 00.3 — Как компьютер выполняет программу](../00-getting-started/03-how-a-computer-runs-a-program.md), а `extern "C"` и `#[unsafe(no_mangle)]` — в [Уроке 06.10 — FFI: вызов кода на C](../06-rust-advanced/10-ffi-calling-c.md).
- Создайте **библиотечный** пакет для Уроков 12.7 и 12.8: `cargo new --lib code/p12-asm`. Библиотеки достаточно, потому что мы хотим только смотреть на скомпилированные функции, а не запускать их.

Вам не нужно **писать** на ассемблере. Нужно **читать** его короткие фрагменты, чтобы проверить, что компилятор сделал с вашим кодом. Этим навыком пользуется каждый системный инженер, когда горячий цикл работает медленно или программа падает внутри оптимизированного кода.

## Новые слова

| Слово | Значение |
|---|---|
| **язык ассемблера** (assembly language) | Текстовая, понятная человеку форма машинного кода: одна строка на инструкцию, с названиями вместо чисел. |
| **мнемоника** (mnemonic) | Короткое название инструкции, например `add`, `ldr` или `ret`. |
| **операнд** (operand) | Вход или выход инструкции: регистр, константа или адрес в памяти. |
| **непосредственное значение** (immediate) | Константа, записанная прямо внутри инструкции, например `#3` на arm64 или `8` на x86-64. |
| **метка** (label) | Имя для места в коде, заканчивается на `:`. Ветвления переходят к меткам. |
| **директива** (directive) | Строка, начинающаяся с `.` (например, `.globl` или `.cfi_startproc`). Это указание для программы-ассемблера, а не для процессора. |
| **ABI** (Application Binary Interface, двоичный интерфейс приложений) | Правила совместной работы скомпилированного кода: куда идут аргументы, какие регистры функция может менять, как выглядит стек. |
| **соглашение о вызовах** (calling convention) | Часть ABI о вызовах функций: в каких регистрах аргументы и результат. |
| **AAPCS64** (Procedure Call Standard for the Arm 64-bit Architecture, стандарт вызова процедур для 64-битной архитектуры Arm) | Соглашение о вызовах arm64. Apple использует его с небольшими изменениями. |
| **System V AMD64 ABI** | Соглашение о вызовах x86-64 в Linux и macOS. («System V» — название старой версии Unix, документы ABI которой используются до сих пор. AMD64 — название, которое компания AMD, Advanced Micro Devices, дала x86-64.) |
| **указатель стека** (stack pointer) | Регистр, хранящий адрес вершины стека: `sp` на arm64, `rsp` на x86-64. |
| **регистр связи** (link register) | На arm64 регистр `x30` (`lr`): `bl` кладёт туда адрес возврата, а `ret` возвращается по нему. |
| **пролог / эпилог** (prologue / epilogue) | Инструкции в начале функции, которые сохраняют регистры и выделяют место на стеке / в конце, которые их восстанавливают. |
| **искажение имён** (name mangling) | Кодирование полного пути функции Rust (крейт, модуль, имя, хеш) в одно уникальное имя символа, например `_RNvCs6NKwHiZURaG_7p12_asm3add`. |

## 1. Получаем ассемблер

Поместите три маленькие функции в `src/lib.rs` пакета `code/p12-asm`:

```rust
#[inline(never)]
pub fn add(a: u64, b: u64) -> u64 {
    a + b
}

#[inline(never)]
pub fn max_of(a: i64, b: i64) -> i64 {
    if a > b { a } else { b }
}

#[inline(never)]
pub fn find(values: &[u32], target: u32) -> Option<usize> {
    for (i, &v) in values.iter().enumerate() {
        if v == target {
            return Some(i);
        }
    }
    None
}
```

**Что происходит:**

1. `#[inline(never)]` велит компилятору сохранить каждую функцию настоящей отдельной функцией. Без этого компилятор считает маленькие `pub`-функции кандидатами на **встраивание** (inlining: копирование их тела в каждого вызывающего, Урок 12.8) и вообще не создаёт их в библиотеке, так что смотреть было бы не на что.
2. `pub` делает функции частью интерфейса библиотеки, поэтому компилятор обязан их сохранить.

### Способ 1: попросить `rustc` записать файл ассемблера

`cargo rustc` передаёт компилятору дополнительные параметры. `--emit asm` просит текст на ассемблере:

```bash
cd ~/projects/rust/code/p12-asm
cargo rustc --release -- --emit asm
find target -name '*.s'
```

```text
target/release/build/p12-asm/a80bd35e5626745d/out/p12_asm-a80bd35e5626745d.s
```

(Хеш в пути у вас будет другим.) В файле около 40 строк. Часть для `add` выглядит так:

```text
	.globl	__RNvCs6NKwHiZURaG_7p12_asm3add
	.p2align	2
__RNvCs6NKwHiZURaG_7p12_asm3add:
	.cfi_startproc
	add	x0, x1, x0
	ret
	.cfi_endproc
```

Строки, начинающиеся с `.`, — **директивы** для ассемблера; странное имя — это **искажённое** имя `p12_asm::add`. Настоящих инструкций только две. Этот способ работает без дополнительных инструментов, но вывод шумный.

### Способ 2: `cargo asm`

Инструмент cargo-show-asm находит одну функцию, восстанавливает её имя и показывает только её код. Установите его один раз:

```bash
cargo install --locked cargo-show-asm
cargo asm --version
```

```text
Version: 0.2.65
```

Без имени функции `cargo asm --lib` выводит список того, что может показать; с именем — показывает эту функцию (по умолчанию он собирает в релизном режиме):

```bash
cargo asm --lib p12_asm::add
```

```text
p12_asm::add:
	add x0, x1, x0
	ret
```

В этом уроке мы опускаем строки-директивы (`.cfi_…`, `.p2align`, `.globl` и подобные), которые `cargo asm` тоже печатает, чтобы вы видели только метки и инструкции. Номера в метках вроде `LBB2_4` зависят от других функций в файле, поэтому у вас они могут отличаться.

### Ассемблер x86-64 на вашем Mac

Компилятор умеет создавать код для других целевых платформ. Для x86-64 Linux один раз добавьте стандартную библиотеку этой платформы: `rustup target add x86_64-unknown-linux-gnu`. Затем:

```bash
cargo asm --lib --target x86_64-unknown-linux-gnu p12_asm::add
```

```text
p12_asm::add:
	lea rax, [rdi + rsi]
	ret
```

Это работает без компоновщика для Linux, потому что библиотека только компилируется, но не компонуется в программу (Урок 12.12 объясняет компоновку). `cargo asm` использует для x86-64 **синтаксис Intel** (приёмник первым, как на arm64). Некоторые инструменты используют более старый **синтаксис AT&T** (по имени компании AT&T, American Telephone and Telegraph, в лабораториях Bell Labs которой был создан Unix), где приёмник идёт последним, а у регистров есть знак `%` (`leaq (%rdi,%rsi), %rax`); `cargo asm --att` показывает эту форму.

> 💡 **Совет:** Compiler Explorer (godbolt.org) делает то же самое в браузере: выберите Rust, добавьте параметр `-C opt-level=3`, и он покажет ассемблер рядом с вашим кодом, раскрасив, какой строке исходника соответствуют какие инструкции.

## 2. Читаем одну строку

Строка ассемблера — это **мнемоника**, затем **операнды** через запятую. На arm64 и в синтаксисе Intel **первый операнд — приёмник**:

```text
add  x0, x1, x0          x0 = x1 + x0                 (arm64)
lea  rax, [rdi + rsi]    rax = rdi + rsi              (x86-64)
```

Теперь `add` можно прочитать полностью, зная **соглашение о вызовах** — правило, где лежат аргументы и результаты.

| | arm64 (AAPCS64) | x86-64 (System V AMD64 ABI) |
|---|---|---|
| Целые аргументы и указатели 1–8 | `x0`, `x1`, `x2`, `x3`, `x4`, `x5`, `x6`, `x7` | `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9` (только шесть) |
| Остальные аргументы | на стеке | на стеке |
| Возвращаемое значение | `x0` (вторая часть в `x1`) | `rax` (вторая часть в `rdx`) |
| Адрес возврата | регистр `x30` (регистр связи) | на стеке (его кладёт `call`) |
| Регистры, которые функция должна вернуть вызывающему без изменений | `x19`–`x28`, `x29`, `sp` | `rbx`, `rbp`, `r12`–`r15`, `rsp` |

Итак, на arm64 `a` приходит в `x0`, `b` — в `x1`, и `add x0, x1, x0` кладёт сумму в `x0`, регистр возврата. `ret` переходит обратно по адресу из `x30`. На x86-64 `a` лежит в `rdi`, `b` — в `rsi`, а `lea` («load effective address», загрузить эффективный адрес) — это вычислитель адресов, используемый как быстрый сумматор: он вычисляет `rdi + rsi` в `rax`, не обращаясь к памяти.

**Размеры регистров.** `x0` — 64-битный регистр; `w0` — его младшие 32 бита (для `u32`, `i32`). На x86-64 `rax` — 64 бита, `eax` — его младшие 32 бита. Поэтому `add` из Урока 00.3 (для `i32`) использовал регистры `w`, а этот (для `u64`) — регистры `x`.

> 📏 **Соглашение:** ABI Rust (как вызываются обычные функции Rust) официально **не стабилен**: он может меняться между версиями компилятора, и компилятор может передавать данные иначе, если докажет, что функцию больше никто не вызывает. На практике простые функции следуют таблице выше. Только функции `extern "C"` *гарантированно* следуют соглашению о вызовах C данной платформы (Упражнение 4 использует такую).

## 3. Решения: сравнить и выбрать

В `max_of` есть `if`. Вот что из него сделал компилятор:

```bash
cargo asm --lib p12_asm::max_of
cargo asm --lib --target x86_64-unknown-linux-gnu p12_asm::max_of
```

```text
p12_asm::max_of:
	cmp x0, x1
	csel x0, x0, x1, gt
	ret
```

```text
p12_asm::max_of:
	mov rax, rsi
	cmp rdi, rsi
	cmovg rax, rdi
	ret
```

**Что происходит:**

1. `cmp x0, x1` вычисляет `x0 − x1` и выбрасывает результат, оставляя только **флаги** (N, Z, C, V из Урока 12.2: отрицательный, ноль, перенос, переполнение).
2. `csel x0, x0, x1, gt` — **условный выбор**: «`x0` = если флаги говорят *больше*, то `x0`, иначе `x1`». `gt` — **код условия**, который процессор вычисляет по флагам (для знаковых чисел).
3. На x86-64: сначала `rax = b`; затем сравнение; затем `cmovg` (*условное перемещение, если больше*) перезаписывает `rax` значением `a`, если `a > b`.

Ветвления **нет** вовсе. Обе версии вычисляют ответ инструкцией выбора, так что предсказателю ветвлений нечего угадывать (Урок 12.6). Коды условий, которые вы будете встречать часто:

| Условие | Значение (после `cmp a, b`) |
|---|---|
| `eq` / `ne` (x86: `e` / `ne`) | равно / не равно |
| `gt`, `ge`, `lt`, `le` (x86: `g`, `ge`, `l`, `le`) | знаковое больше, больше или равно, меньше, меньше или равно |
| `hi`, `hs`, `lo`, `ls` (x86: `a`, `ae`, `b`, `be`) | беззнаковое выше, выше или равно, ниже, ниже или равно |

Знаковые и беззнаковые сравнения используют **разные** коды условий, потому что читают разные флаги. Здесь работает дополнительный код из Урока 12.2: одна и та же `cmp` служит числам обоих видов.

## 4. Циклы и память: `find`

```text
p12_asm::find:
	cbz x1, LBB2_4
	mov x9, x1
	mov x8, x0
	mov x1, #0
	lsl x9, x9, #2
	mov w0, #1
LBB2_2:
	ldr w10, [x8, x1, lsl #2]
	cmp w10, w2
	b.eq LBB2_5
	add x1, x1, #1
	subs x9, x9, #4
	b.ne LBB2_2
LBB2_4:
	mov x0, #0
LBB2_5:
	ret
```

Сначала аргументы. Срез `&[u32]` — это два значения (Урок 03.6): указатель на первый элемент и длина. Поэтому `values` приходит в **двух регистрах**: указатель в `x0`, длина в `x1`. `target` идёт третьим, в `w2` (32 бита, потому что это `u32`). Результату `Option<usize>` тоже нужны два значения: метка варианта (0 для `None`, 1 для `Some`) в `x0` и индекс в `x1`.

**Что происходит:**

1. `cbz x1, LBB2_4` — «сравнить и перейти, если ноль»: если длина равна 0, перейти к `LBB2_4`, где возвращается `None`.
2. Инструкции `mov` копируют указатель в `x8`, начинают индекс `x1` с 0 и ставят `w0 = 1` (метку `Some`, заранее, на случай если значение найдётся). `#0` и `#1` — **непосредственные значения**. `lsl x9, x9, #2` сдвигает длину влево на 2: `x9` = длина × 4 = сколько байтов осталось просмотреть (каждый `u32` — 4 байта).
3. Цикл начинается с метки `LBB2_2`. `ldr w10, [x8, x1, lsl #2]` **загружает** 4 байта из памяти по адресу `x8 + (x1 << 2)`, то есть `values[i]`. Квадратные скобки означают «память по этому адресу».
4. `cmp w10, w2` и `b.eq LBB2_5`: если `values[i] == target`, перейти к концу. В этот момент `x0` равен 1, а `x1` равен `i`: функция возвращает `Some(i)`.
5. Иначе `add x1, x1, #1` (`i += 1`), а `subs x9, x9, #4` вычитает 4 из счётчика байтов **и ставит флаги** (`s` в конце `subs` означает «set flags»). `b.ne LBB2_2` переходит назад, пока счётчик не равен нулю.
6. Когда цикл заканчивается без совпадения, `mov x0, #0` ставит метку `None`, и `ret` возвращает результат.

Версия x86-64 устроена так же:

```text
p12_asm::find:
	test rsi, rsi
	je .LBB2_1
	mov ecx, edx
	shl rsi, 2
	xor eax, eax
	xor edx, edx
.LBB2_5:
	cmp dword ptr [rdi + 4*rdx], ecx
	je .LBB2_6
	inc rdx
	add rsi, -4
	jne .LBB2_5
	ret
.LBB2_1:
	xor eax, eax
	ret
.LBB2_6:
	mov eax, 1
	ret
```

Новое здесь: `test rsi, rsi` ставит флаги по `rsi & rsi` — короткий способ спросить «это ноль?». `xor eax, eax` обнуляет `eax` (XOR, *exclusive or*, исключающее ИЛИ из Урока 12.4: значение XOR само себя — 0; это обычный способ очистить регистр). `cmp dword ptr [rdi + 4*rdx], ecx` сравнивает 4-байтовое значение (*dword*, двойное слово) **прямо из памяти**, что x86-64 разрешает, а arm64 — нет (Урок 12.6: arm64 — архитектура загрузки/сохранения). Индекс лежит в `rdx`, который одновременно второй регистр возврата, поэтому `Some(i)` возвращается как `rax` = 1 и `rdx` = `i`.

## 5. Вызовы и стек

Когда функция вызывает другую функцию, она должна сохранить то, что ей ещё понадобится, потому что вызываемая функция может перезаписать регистры аргументов. Добавьте в `src/lib.rs`:

```rust
#[inline(never)]
fn square(x: u64) -> u64 {
    x.wrapping_mul(x)
}

#[inline(never)]
pub fn sum_of_squares(a: u64, b: u64) -> u64 {
    square(a).wrapping_add(square(b))
}
```

```text
p12_asm::sum_of_squares:
	stp x20, x19, [sp, #-32]!
	stp x29, x30, [sp, #16]
	add x29, sp, #16
	mov x19, x1
	bl p12_asm::square
	mov x20, x0
	mov x0, x19
	bl p12_asm::square
	add x0, x0, x20
	ldp x29, x30, [sp, #16]
	ldp x20, x19, [sp], #32
	ret
```

**Что происходит:**

1. **Пролог.** `stp x20, x19, [sp, #-32]!` («store pair», сохранить пару) сначала сдвигает указатель стека вниз на 32 байта (`!` означает «сначала обнови `sp`»), затем сохраняет туда `x20` и `x19`. Функция будет использовать эти регистры, а ABI требует вернуть их без изменений. `stp x29, x30, [sp, #16]` сохраняет **указатель кадра** `x29` и **регистр связи** `x30`; следующий `bl` перезапишет `x30`, и без сохранённой копии функция не смогла бы вернуться. `add x29, sp, #16` направляет указатель кадра на кадр этой функции (отладчики и профилировщики идут по этой цепочке кадров, чтобы напечатать трассировку стека).
2. `mov x19, x1` хранит `b` в регистре, который `square` менять не имеет права.
3. `bl p12_asm::square` — «branch with link», переход со связью: перейти к `square` и положить адрес возврата в `x30`. `a` уже лежит в `x0`, первом регистре аргументов. Результат возвращается в `x0` и сохраняется в `x20`.
4. `b` перемещается в `x0`, и `square` вызывается снова. Затем `add x0, x0, x20` складывает два квадрата.
5. **Эпилог.** `ldp` («load pair», загрузить пару) восстанавливает сохранённые регистры и возвращает `sp` на 32 вверх (`[sp], #32` означает «используй `sp`, потом прибавь 32»). `ret` переходит по восстановленному `x30`.

```text
the stack inside sum_of_squares (addresses grow upwards):

          ┌──────────────┐  ← sp before the call (sp + 32)
 sp + 24  │ x30 (return) │
 sp + 16  │ x29 (frame)  │  ← x29 points here
 sp + 8   │ x19 (saved)  │
 sp + 0   │ x20 (saved)  │  ← sp after the prologue
          └──────────────┘
```

Этот блок памяти — **кадр стека** функции, тот самый «ящик на стеке» из Урока 03.1, теперь с настоящими адресами. На x86-64 та же функция использует `push` (сдвинуть `rsp` вниз и сохранить) и `pop`, а `call` кладёт адрес возврата на стек, а не в регистр связи:

```text
p12_asm::sum_of_squares:
	push r14
	push rbx
	push rax
	mov rbx, rsi
	call p12_asm::square
	mov r14, rax
	mov rdi, rbx
	call p12_asm::square
	add rax, r14
	add rsp, 8
	pop rbx
	pop r14
	ret
```

(`push rax` лишь сдвигает `rsp` ещё на 8 байтов; ABI x86-64 требует, чтобы при каждом `call` стек был выровнен по 16 байтам. `add rsp, 8` отменяет этот сдвиг.)

> 🔒 **Безопасность:** адрес возврата живёт на стеке (x86-64) или сохраняется туда (arm64). Классическая атака перезаписывает его через переполнение буфера, чтобы `ret` перешёл в код атакующего. Безопасный Rust предотвращает само переполнение буфера. Современные процессоры добавляют защиту: на Apple Silicon адрес возврата может подписываться **аутентификацией указателей** (pointer authentication; в системных библиотеках можно увидеть инструкции вроде `pacibsp` и `retab`), и изменённый адрес обнаруживается до перехода.

## 6. Назад к Уроку 12.6: исчезнувшее ветвление

Добавьте в библиотеку `sum_big` из Урока 12.6 (с `#[inline(never)]`) и запустите `cargo asm --lib p12_asm::sum_big`. Вывод — около 180 строк, потому что компилятор сделал **векторизованный** основной цикл: инструкции вроде `uaddw.2d v24, v24, v30` работают со 128-битными **векторными регистрами** `v0`–`v31`, сразу с несколькими числами (суффиксы `.2d`, `.16b` говорят, сколько дорожек и какой ширины: 2 × 64 бита, 16 × 8 битов). В конце есть маленький скалярный цикл для последних нескольких байтов, и его стоит прочитать:

```text
LBB6_14:
	ldrsb w11, [x9], #1
	and w11, w11, w11, asr #31
	add x8, x8, w11, uxtb
	cmp x9, x10
	b.ne LBB6_14
```

**Что происходит:**

1. `ldrsb w11, [x9], #1` загружает один байт и делает **знаковое расширение** (Урок 12.2), затем сдвигает указатель `x9` вперёд на 1. У байта ≥ 128 установлен старший бит, поэтому как знаковый байт он отрицательный.
2. `and w11, w11, w11, asr #31`: последний операнд — это `w11`, **арифметически сдвинутый** вправо на 31 (Урок 12.4). Для отрицательного значения это все единицы, для положительного — все нули. И с ним оставляет значение или превращает его в 0. Это «если `v >= 128`, оставь `v`, иначе 0» без ветвления.
3. `add x8, x8, w11, uxtb` прибавляет к сумме в `x8` младший байт `w11`, **расширенный нулями** (`uxtb`).
4. Цикл идёт, пока указатель не дойдёт до конца `x10`.

Все приёмы этого этапа — дополнительный код, знаковое расширение, арифметические сдвиги, маски — в четырёх инструкциях, выбранных компилятором.

> 🧪 **Тестирование:** чтение ассемблера говорит вам, *как* работает функция, но не *правильна ли* она. Держите обычные тесты рядом с функциями, которые изучаете таким образом; в `code/p12-asm` Упражнение 3 добавляет тесты для `find` и новой функции, прежде чем вы прочитаете их ассемблер.

## Частые ошибки

> ⚠️ **Частая ошибка: функции нет.** Без `#[inline(never)]` маленькая функция в библиотеке часто не компилируется отдельно:

```rust
pub fn double(x: u64) -> u64 {
    x * 2
}
```

```text
Can't find any items matching ["p12_asm::double"]
```

Добавьте `#[inline(never)]` или смотрите на более крупную функцию, которая её вызывает. Запустите `cargo asm --lib` без имени, чтобы увидеть список существующих функций.

> ⚠️ **Частая ошибка: читать отладочный ассемблер.** Отладочные сборки держат каждую переменную на стеке и добавляют проверки переполнения, поэтому даже `add` превращается во множество строк. `cargo asm` по умолчанию использует релизный режим; с `cargo rustc` всегда передавайте `--release`.

> ⚠️ **Частая ошибка: путать порядок операндов.** В синтаксисе AT&T (`gcc`, `objdump` по умолчанию в Linux) приёмник **последний**: `mov %rsi, %rax` копирует `rsi` в `rax`. В синтаксисе Intel и на arm64 он первый. Прежде чем читать вывод инструмента, проверьте, какой синтаксис он использует.

## Упражнения

### Упражнение 1 — Прочитайте (легко)

Что вычисляют эти две функции arm64? Аргумент лежит в `x0` (или в `x0`, `x1`, `x2`):

```text
f:
	lsl x0, x0, #3
	ret
g:
	madd x0, x1, x0, x2
	ret
```

<details>
<summary>Подсказка</summary>

`lsl` — «logical shift left», логический сдвиг влево. `madd d, a, b, c` означает `d = a × b + c`.

</details>

<details>
<summary>Ответ</summary>

`f` возвращает `x * 8` (сдвиг влево на 3 умножает на 2³). `g` возвращает `a * b + c`, причём умножение и сложение — **одна** инструкция. Это настоящий вывод для:

```rust
#[inline(never)]
pub fn times_eight(x: u64) -> u64 {
    x * 8
}

#[inline(never)]
pub fn mul_add(a: u64, b: u64, c: u64) -> u64 {
    a.wrapping_mul(b).wrapping_add(c)
}
```

На x86-64 они превращаются в `lea rax, [8*rdi]` и в `imul rdi, rsi`, за которым идёт `lea rax, [rdi + rdx]`.

Почему это работает: компилятор заменяет `* 8` сдвигом (Урок 12.4 обещал, что вы это увидите) и объединяет умножение и сложение, потому что у arm64 есть инструкция для обоих сразу.

</details>

### Упражнение 2 — Предскажите, затем проверьте (средне)

Добавьте `pub fn clamp_to_100(x: i64) -> i64`, которая возвращает `x`, если он не больше 100, иначе 100. Прежде чем запускать `cargo asm`, запишите инструкции, которые ожидаете на arm64. Затем сравните.

<details>
<summary>Подсказка</summary>

Это как `max_of`, но с константой. `cmp` на arm64 умеет сравнивать с непосредственным значением: `cmp x0, #100`. Какое условие нужно в `csel`?

</details>

<details>
<summary>Ответ</summary>

```rust
#[inline(never)]
pub fn clamp_to_100(x: i64) -> i64 {
    if x > 100 { 100 } else { x }
}
```

```text
p12_asm::clamp_to_100:
	mov w8, #100
	cmp x0, #100
	csel x0, x0, x8, lt
	ret
```

Почему это работает: для `csel` константа 100 должна быть в регистре, поэтому сначала она загружается в `w8` (запись в `w8` заодно обнуляет верхнюю половину `x8`). Компилятор выбрал `lt` («оставить `x0`, если он меньше 100»), что даёт тот же результат, что и ваш `if`, для любого входа, в том числе для `x == 100`. Ваше предсказание может отличаться в таких деталях и при этом быть верным по смыслу.

</details>

### Упражнение 3 — Сначала тест, потом чтение цикла (средне)

Напишите `pub fn rfind(values: &[u32], target: u32) -> Option<usize>`, которая возвращает индекс **последнего** совпадения, используя цикл `for i in (0..values.len()).rev()` и `values[i]`. Напишите тесты для `find` и `rfind` (совпадение в середине, на краях, нет совпадения, пустой срез). Затем прочитайте ассемблер `rfind` для arm64. Как заканчивается цикл и есть ли проверка границ для `values[i]`?

<details>
<summary>Подсказка</summary>

Проверка границ проявилась бы как вызов (`bl`) функции с `panic_bounds_check` в имени. Найдите `cmn`: это `cmp` с отрицанием операнда, поэтому `cmn x9, #1` сравнивает `x9` с −1.

</details>

<details>
<summary>Ответ</summary>

```rust
#[inline(never)]
pub fn rfind(values: &[u32], target: u32) -> Option<usize> {
    for i in (0..values.len()).rev() {
        if values[i] == target {
            return Some(i);
        }
    }
    None
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn find_returns_first_match() {
        assert_eq!(find(&[5, 7, 7, 9], 7), Some(1));
        assert_eq!(find(&[5, 7, 7, 9], 5), Some(0));
        assert_eq!(find(&[5, 7, 7, 9], 4), None);
        assert_eq!(find(&[], 4), None);
    }

    #[test]
    fn rfind_returns_last_match() {
        assert_eq!(rfind(&[5, 7, 7, 9], 7), Some(2));
        assert_eq!(rfind(&[5, 7, 7, 9], 9), Some(3));
        assert_eq!(rfind(&[5, 7, 7, 9], 4), None);
        assert_eq!(rfind(&[], 4), None);
    }
}
```

```text
p12_asm::rfind:
	cbz x1, LBB3_5
	mov x8, x0
	sub x9, x1, #1
	mov w0, #1
LBB3_2:
	mov x1, x9
	ldr w9, [x8, x9, lsl #2]
	cmp w9, w2
	b.eq LBB3_6
	sub x9, x1, #1
	cmn x9, #1
	b.ne LBB3_2
	mov x0, #0
	ret
LBB3_5:
	mov x0, #0
LBB3_6:
	ret
```

Почему это работает: индекс начинается с `len − 1` и уменьшается; после индекса 0 `sub` делает его −1 (все единицы, завёрнутое значение), и `cmn x9, #1` вместе с `b.ne` останавливает цикл ровно тогда. Проверки границ **нет**: компилятор доказал, что `i` всегда меньше `len`, поэтому `values[i]` не может вызвать панику. Урок 12.8 показывает случай, когда он не может этого доказать.

</details>

### Упражнение 4 — Девять аргументов (сложно)

В соглашении о вызовах всего 8 регистров для аргументов на arm64 и 6 на x86-64. Напишите

```rust
#[unsafe(no_mangle)]
pub extern "C" fn sum9(a: i64, b: i64, c: i64, d: i64, e: i64, f: i64, g: i64, h: i64, i: i64) -> i64 {
    a + b + c + d + e + f + g + h + i
}
```

и посмотрите её на обеих платформах (`cargo asm --lib sum9`). Откуда приходит каждый аргумент?

<details>
<summary>Подсказка</summary>

Ищите операнды памяти с `sp` или `rsp`. На x86-64 в начале функции по адресу `[rsp]` лежит адрес возврата вызывающей функции.

</details>

<details>
<summary>Ответ</summary>

```text
_sum9:
	ldr x8, [sp]
	add x9, x1, x0
	add x10, x2, x3
	add x9, x9, x10
	add x10, x4, x5
	add x10, x10, x6
	add x9, x9, x10
	add x9, x9, x7
	add x0, x9, x8
	ret
```

```text
sum9:
	add rsi, rdi
	lea rax, [rdx + rcx]
	add rax, rsi
	add rax, r8
	add rax, r9
	add rax, qword ptr [rsp + 8]
	add rax, qword ptr [rsp + 16]
	add rax, qword ptr [rsp + 24]
	ret
```

Почему это работает: на arm64 `a`–`h` приходят в `x0`–`x7`, и только `i` берётся со стека (`ldr x8, [sp]`). На x86-64 `a`–`f` приходят в `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`, а `g`, `h`, `i` читаются со стека по адресам `rsp + 8`, `+ 16`, `+ 24` (по `[rsp]` лежит адрес возврата, положенный `call`). Обратите внимание и на имя: macOS добавляет подчёркивание в начало имени каждого символа (`_sum9`; поэтому и искажённые имена в разделе 1 начинаются с `__RNv`), Linux — нет. С `#[unsafe(no_mangle)]` имя не искажается, а именно это нужно коду на C, чтобы его найти (Урок 06.10). И посмотрите, как компилятор складывает парами, чтобы укоротить цепочку зависимостей (Урок 12.6), — сложение целых можно переставлять.

</details>

## Вопросы для самопроверки

1. В `add x0, x1, x0` какой регистр получает результат?

<details>
<summary>Ответ</summary>

`x0`, первый операнд. На arm64 и в синтаксисе Intel приёмник идёт первым.

</details>

2. В каких регистрах приходят первые два целых аргумента на arm64 и на x86-64 Linux и где возвращается результат?

<details>
<summary>Ответ</summary>

arm64: `x0` и `x1`, результат в `x0`. x86-64: `rdi` и `rsi`, результат в `rax`.

</details>

3. Почему аргумент `&[u32]` занимает два регистра?

<details>
<summary>Ответ</summary>

Срез — это указатель плюс длина; каждому нужен один регистр.

</details>

4. Что делает `ldr w10, [x8, x1, lsl #2]`?

<details>
<summary>Ответ</summary>

Загружает 4 байта из памяти по адресу `x8 + (x1 << 2)` в `w10`, то есть элемент `x1` массива `u32`, который начинается с `x8`.

</details>

5. Почему `sum_of_squares` сохраняет `x30` в прологе, а `add` — нет?

<details>
<summary>Ответ</summary>

`sum_of_squares` вызывает другие функции через `bl`, который перезаписывает `x30` (адрес возврата). `add` ничего не вызывает, поэтому `x30` остаётся нетронутым до её `ret`.

</details>

6. Чем `csel` отличается от условного перехода вроде `b.gt`?

<details>
<summary>Ответ</summary>

`csel` выбирает одно из двух значений, не меняя ход программы, поэтому ничего предсказывать не нужно. `b.gt` переходит в другое место, если условие истинно, и это направление предсказатель должен угадать.

</details>

7. Зачем нужен `#[inline(never)]`, чтобы увидеть маленькую библиотечную функцию через `cargo asm`?

<details>
<summary>Ответ</summary>

Маленькие `pub`-функции считаются кандидатами на встраивание и могут не компилироваться в библиотеке как отдельные функции; `#[inline(never)]` заставляет создать отдельную копию.

</details>

## Итоги

- `cargo rustc --release -- --emit asm` записывает файл `.s`; `cargo asm --lib <путь>` аккуратно показывает одну функцию, в том числе для `--target x86_64-unknown-linux-gnu`. Помечайте маленькие функции `#[inline(never)]`.
- Строка — это мнемоника и операнды; на arm64 и в синтаксисе Intel приёмник идёт первым. `[...]` — память, `#n` (arm64) — непосредственное значение.
- Аргументы идут в `x0`–`x7` (arm64) или в `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9` (x86-64); результаты — в `x0` / `rax`. Срезы и `Option<usize>` занимают два регистра. Этот ABI гарантирован только для `extern "C"`.
- `cmp` ставит флаги; `b.<cond>`, `cbz` переходят по ним; `csel` / `cmov` выбирают без ветвления. Знаковые и беззнаковые сравнения используют разные коды условий.
- Функция, которая вызывает другие, сохраняет регистры и адрес возврата в своём кадре стека (пролог) и восстанавливает их (эпилог).
- Чтение ассемблера показывает, как компилятор реализовал ваш код; правильность по-прежнему решают тесты.
